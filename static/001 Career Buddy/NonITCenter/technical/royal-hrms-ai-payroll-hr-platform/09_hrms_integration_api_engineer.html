    Module 01

    The Integration & API Engineer Role

    How Royal HRMS connects to everything around it — public APIs for customers, webhooks for real-time events, biometric clocks on factory floors, and benefits providers like insurers and pension funds.

    🔌 Course Overview: What the Role Is

    The HRMS Integration & API Engineer builds and operates the interfaces through which data enters and leaves Royal HRMS. Customers' developers call your REST APIs, partner systems receive your webhooks, thousands of biometric terminals push punches, and insurers receive enrolment files. Reliability, security and clear contracts are the job.

    🌐
    RESTful APIs
    Resource design, auth, pagination, versioning, rate limits.
    📡
    Webhooks
    Event subscriptions, signed deliveries, retries, replay.
    🖐️
    Biometric clocks
    Device protocols, punch ingestion, time sync, offline buffers.
    🏥
    Benefits connectors
    Insurance, pension, wellness providers — enrolments and deductions.

    🎯 Learning Objectives

    By the end of this course you will be able to:

    1. Design RESTful HRMS APIs with correct resources, methods, status codes and OAuth 2.0 scopes.
    2. Implement pagination, filtering, idempotency, optimistic concurrency, rate limits and versioning.
    3. Build reliable webhook delivery with outbox, signatures, retries, replay and consumer best practices.
    4. Integrate biometric clocks: push/pull patterns, time normalisation, offline buffers, dedup and fleet management.
    5. Build configurable benefits connectors with file and API standards, payroll deductions and reconciliation.
    6. Test integrations with contract, security and load tests.
    7. Troubleshoot sync gaps, webhook storms, timezone bugs and provider rejections.

    🔁 Advanced: Idempotency & Concurrency

    python@app.post("/v1/leave-requests", status_code=201)
def create_leave(req: LeaveRequestIn, idem_key: str = Header(..., alias="Idempotency-Key")):
    saved = idem_store.get(tenant(), idem_key)
    if saved:
        if saved.request_hash != hash_body(req):
            raise HTTPException(422, "Idempotency-Key reused with different payload")
        return saved.response                       # replay original response
    result = leave_service.create(tenant(), req)
    idem_store.put(tenant(), idem_key, hash_body(req), result, ttl_hours=24)
    return result
    • Optimistic concurrency: return ETag on GET; require If-Match on PATCH; respond 412 if changed.
    • Validation errors in a consistent problem format (RFC 9457 problem details).

    ✍️ Intermediate: Signing & Verification

    pythonimport hmac, hashlib, time
def sign(secret: bytes, body: bytes, ts: int) -> str:
    mac = hmac.new(secret, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    return f"t={ts},v1={mac}"

def verify(secret: bytes, body: bytes, header: str, tolerance=300) -> bool:
    parts = dict(p.split("=", 1) for p in header.split(","))
    ts = int(parts["t"])
    if abs(time.time() - ts) > tolerance:            # replay protection
        return False
    expected = hmac.new(secret, f"{ts}.".encode() + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, parts["v1"])  # constant-time compare

    🔁 Advanced: Retries, Ordering & Duplicates

    ProblemDesign
    Endpoint downExponential backoff over ~24–72 h (e.g., 1m, 5m, 30m, 2h, 6h…)
    Duplicates (at-least-once)Consumers dedupe by event id
    Out-of-order deliveryInclude created_at and a per-entity sequence; consumers ignore stale events
    Persistent failureAuto-disable subscription after N days, notify owner
    Missed eventsReplay API: POST /v1/webhook-subscriptions/{id}/replays?from=…

    🛠️ Advanced: Building a Reliable Consumer

    python@app.post("/hooks/royal-hrms")
def receive(request):
    body = request.body
    if not verify(SECRET, body, request.headers["RHRMS-Signature"]):
        return Response(status=401)
    evt = json.loads(body)
    if processed.exists(evt["id"]):
        return Response(status=200)                  # duplicate — acknowledge
    queue.enqueue(evt)                               # respond fast; process async
    processed.add(evt["id"])
    return Response(status=202)
    ⚠️
    Consumers that do heavy work before responding cause timeouts → retries → duplicates. Acknowledge fast, process asynchronously.

    🏆 Expert: Operating Webhooks at Scale

    • Delivery dashboard per subscription: success rate, latency, last error, queue age.
    • Secret rotation with overlap (two valid secrets during rotation).
    • Event schema versioning with api_version pinned per subscription.
    • Static egress IPs published for customer firewall allow-lists.
    • Tenant isolation: a subscription receives only its tenant's events — enforced in dispatcher and tested.

    ⏱️ Intermediate: Normalising Punches

    pythonfrom datetime import datetime, timedelta, timezone
def normalise(raw: dict, device) -> dict:
    local = datetime.strptime(raw["time"], "%Y-%m-%d %H:%M:%S")
    tz = timezone(timedelta(minutes=device.utc_offset_minutes))     # device site timezone
    ts = local.replace(tzinfo=tz) - timedelta(seconds=device.clock_drift_seconds)
    return {
        "tenant_id": device.tenant_id,
        "employee_id": device.user_map[raw["pin"]],                # device user -> employee
        "punched_at_utc": ts.astimezone(timezone.utc).isoformat(),
        "device_serial": device.serial,
        "verify_mode": {"1": "finger", "15": "face", "4": "card"}.get(raw["verify"], "other"),
        "dedup_key": f'{device.serial}:{raw["pin"]}:{raw["time"]}',
    }
    ⚠️
    Device clocks drift and some reset to 2000-01-01 after power loss. Sync time regularly (NTP or gateway command), track drift per device, and quarantine punches with impossible timestamps.

    📦 Advanced: Offline Buffers & Deduplication

    • Terminals store thousands of punches when offline; on reconnect they upload a backlog — ingestion must handle bursts.
    • Devices may resend the same punches → dedupe with (device_serial, device_user, device_time) unique key.
    • Late punches (hours or days) trigger recalculation of attendance for that day if payroll is not locked; otherwise create an exception.

    💰 Advanced: Payroll Deductions & Reconciliation

    Employee premium shares and voluntary contributions become payroll deductions; provider invoices must reconcile with what payroll deducted and what the employer pays.

    sql-- monthly reconciliation: payroll deductions vs insurer invoice
SELECT COALESCE(p.employee_id, i.employee_id) AS emp,
       p.amount AS payroll_deduction, i.employee_share AS invoice_share
FROM payroll_deduction p
FULL OUTER JOIN insurer_invoice_line i
  ON i.employee_id = p.employee_id AND i.period = p.period
WHERE p.period = '2026-09' AND p.component = 'GMC_EE'
  AND (p.amount IS DISTINCT FROM i.employee_share);

    In payroll, not on invoiceEnrolment file rejected by provider

    Symptom: customer's nightly sync of employees misses ~2% of updates.

    Filterupdated_since used their local time, not UTC

    🔁 Incident: Webhook Storm

    Figure 8.1 · Incident
    💡
    Fixes: batch events (employee.bulk_created with IDs), per-subscription concurrency limits, adaptive backoff on 429/503, and advise consumers to ack fast and process async.

    ⏰ Troubleshooting: Night Shift Attendance Wrong

    Punches for night shifts (22:00–06:00) appear on the wrong date, creating absent + double-present days. Cause: device in IST but gateway assumed UTC. Fix: device timezone in registry, normalise to UTC, attendance engine assigns punches to shifts by shift window, not calendar date.

    🏥 Troubleshooting: Insurer Rejects 140 Records

    • Response file shows "DOB format invalid" — insurer changed spec to DD-MM-YYYY.
    • Fix: update provider mapping config (no code), resend rejected records only, add spec version to connector and a contract test with sample file.

    🔐 Scenario: API Key Leaked in a Public Repo

    Detection via secret scanning alert. Response: revoke client secret immediately, issue new credentials, review access logs for misuse by that client, notify customer, recommend secret managers and short-lived tokens; add automatic revocation for detected leaks.

    Module 11

    Interview Preparation

    Questions asked for API, integration and platform engineering roles.

    🌱 Beginner Interview Questions

    IQ1.What makes an API RESTful?
    Resource-oriented URLs, standard HTTP methods and status codes, stateless requests, representations like JSON, cacheability where appropriate.
    IQ2.401 vs 403?
    401 = not authenticated (missing/invalid credentials); 403 = authenticated but lacks permission.
    IQ3.What is a webhook?
    An HTTP callback a system sends to a subscriber's URL when an event happens.

    🛠️ Intermediate Interview Questions

    IQ4.How do you design pagination for delta syncs?
    Cursor-based on (updated_at, id), UTC timestamps, small overlap windows with idempotent consumers.
    IQ5.How do you secure webhooks?
    HTTPS, HMAC signatures with timestamps, constant-time verification, secret rotation, IP allow-lists, thin payloads.
    IQ6.How do biometric devices integrate with cloud HRMS?
    Device push via cloud protocol, on-prem agent pulling via SDK, vendor cloud APIs, or file export; normalised through a device gateway.

    🚀 Advanced Interview Questions

    IQ7.How do you make POST requests safe to retry?
    Idempotency keys stored with request hash and response, unique constraints, replay original response, reject key reuse with different payload.
    IQ8.How do you guarantee webhook delivery?
    Transactional outbox, durable queues, retries with backoff, dead-letter, replay API, monitoring and auto-disable for persistently failing endpoints.
    IQ9.How do you handle device clock drift and offline buffers?
    Time sync commands/NTP, per-device drift tracking, UTC normalisation, quarantine impossible times, dedup keys, recalculation or exceptions for late punches.

    🏆 Expert Interview Questions

    IQ10.Design a connector framework for 50 benefits providers.
    Common lifecycle (trigger, extract, transform, deliver, acknowledge), mapping configs, change detection, transport plugins, response parsing, reconciliation, certification process and monitoring.
    IQ11.How do you evolve an API without breaking 400 integrators?
    Additive changes, OpenAPI diff checks in CI, versioning for breaking changes, deprecation headers and timelines, usage analytics to contact affected clients, SDK updates.
    IQ12.A customer reports missing webhooks for 3 hours. Walk through your investigation.
    Check dispatcher health and queue age, subscription status, delivery logs and errors for that endpoint, outbox backlog, recent deploys; replay missed events; communicate RCA.

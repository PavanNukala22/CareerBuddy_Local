    💰 The First Rule: Never Use Floats for Money

    ✅ Use decimal / integer minor units

    Decimal("1234.50") or store paise as integers (123450). Exact, predictable rounding.

    ❌ Binary floating point

    0.1 + 0.2 == 0.30000000000000004. Tiny errors accumulate across components and employees.

    pythonfrom decimal import Decimal, ROUND_HALF_UP
def rupees(x) -> Decimal:
    return Decimal(x).quantize(Decimal("1"), rounding=ROUND_HALF_UP)   # round to whole rupee
basic = Decimal("41666.6667")
print(rupees(basic))          # 41667
print(0.1 + 0.2)              # 0.30000000000000004  <- why floats are banned

    Complex Tax Calculation Logic

    Building correct income-tax and statutory logic — slab algorithms, regimes, rebates and cess, annual projection with YTD, monthly TDS spreading, statutory contributions, versioned tax tables and test strategies.

    🧾 Basic: Slab-Based Tax

    Progressive tax means each slice of income is taxed at its own rate. Below is India's new regime for FY 2025-26 (illustrative — always load rates from versioned tables, never hard-code).

    Annual taxable income (₹)Rate
    0 – 4,00,000Nil
    4,00,001 – 8,00,0005%
    8,00,001 – 12,00,00010%
    12,00,001 – 16,00,00015%
    16,00,001 – 20,00,00020%
    20,00,001 – 24,00,00025%
    Above 24,00,00030%
    pythonfrom decimal import Decimal as D
SLABS = [(D(400000), D("0")), (D(800000), D("0.05")), (D(1200000), D("0.10")),
         (D(1600000), D("0.15")), (D(2000000), D("0.20")), (D(2400000), D("0.25")),
         (None, D("0.30"))]

def slab_tax(income: D) -> D:
    tax, lower = D(0), D(0)
    for upper, rate in SLABS:
        top = income if upper is None else min(income, upper)
        if top > lower:
            tax += (top - lower) * rate
        if upper is None or income <= upper:
            break
        lower = upper
    return tax

print(slab_tax(D(1500000)))   # 20000 + 40000 + 45000 = 105000

    ➕ Intermediate: Deductions, Rebate, Cess

    Figure 2.1 · Annual tax computation
    pythonSTD_DEDUCTION = D(75000)
REBATE_LIMIT, REBATE_MAX = D(1200000), D(60000)

def annual_tax_new_regime(gross_annual: D) -> D:
    taxable = max(D(0), gross_annual - STD_DEDUCTION)
    tax = slab_tax(taxable)
    if taxable <= REBATE_LIMIT:
        tax = max(D(0), tax - REBATE_MAX)          # Section 87A rebate
    # (marginal relief just above the limit omitted for brevity — see Advanced)
    return (tax * D("1.04")).quantize(D("1"))      # + 4% health & education cess
    📌
    Real engines also handle surcharge for high incomes, marginal relief, the old regime with exemptions (HRA, 80C, 80D) and the employee's regime choice. Each is a separate, unit-tested rule.

    📅 Intermediate: Projection & Monthly TDS

    Employers deduct tax every month (TDS) so that the annual liability is spread evenly. Each month the engine re-projects the full year using actual YTD earnings plus expected future earnings.

    pythondef monthly_tds(ytd_gross: D, ytd_tds: D, monthly_gross: D, months_left: int) -> D:
    projected_annual = ytd_gross + monthly_gross * months_left      # includes this month
    annual_tax = annual_tax_new_regime(projected_annual)
    remaining = max(D(0), annual_tax - ytd_tds)
    return (remaining / months_left).quantize(D("1"))               # spread over remaining months
    💡
    Bonuses and arrears change the projection. Many engines tax one-time income in the month it is paid (not spread) to avoid under-deduction at year end.

    🏛️ Intermediate: Statutory Contributions

    ItemRule (India, illustrative)Engine notes
    Provident Fund (PF)12% employee + 12% employer of PF wages; wages often capped at ₹15,000Employer share splits into EPF and EPS (8.33% capped)
    ESI0.75% employee, 3.25% employer if gross ≤ ₹21,000/monthEligibility fixed per contribution period
    Professional TaxState-wise slabs (e.g., Maharashtra, Karnataka)Driven by work location's state
    Labour Welfare FundSmall state-wise amounts, varying frequencyHalf-yearly in some states
    pythondef pf(pf_wages: D, cap: D = D(15000), restrict_to_cap: bool = True):
    base = min(pf_wages, cap) if restrict_to_cap else pf_wages
    employee = (base * D("0.12")).quantize(D("1"))
    eps = (min(base, cap) * D("0.0833")).quantize(D("1"))
    epf_employer = employee - eps
    return {"employee_pf": employee, "employer_eps": eps, "employer_epf": epf_employer}
print(pf(D(25000)))   # {'employee_pf': 1800, 'employer_eps': 1250, 'employer_epf': 550}

    🗃️ Advanced: Versioned, Effective-Dated Rule Tables

    Tax rules change by budget, by state notification, by court order. Store rules as data with effective dates, and calculate using the version valid for the pay period, not "today".

    sqlCREATE TABLE tax_slab (
  country text, regime text, effective_from date, effective_to date,
  lower_bound numeric, upper_bound numeric, rate numeric,
  PRIMARY KEY (country, regime, effective_from, lower_bound)
);
-- engine query for period ending 2026-03-31
SELECT lower_bound, upper_bound, rate FROM tax_slab
WHERE country = 'IN' AND regime = 'NEW'
  AND DATE '2026-03-31' BETWEEN effective_from AND COALESCE(effective_to, DATE '9999-12-31')
ORDER BY lower_bound;
    • Every payslip stores the rule version IDs used — critical for audits and re-runs.
    • Retro changes (a state revises PT from April, notified in June) trigger recalculation of past periods as arrears/recoveries.

    🏆 Expert: Testing Tax Logic

    📚
    Golden test cases

    🔬

    🧪

    pythonfrom hypothesis import given, strategies as st
@given(st.integers(min_value=0, max_value=50_000_000))
def test_tax_monotonic(income):
    assert slab_tax(D(income + 1000)) >= slab_tax(D(income))
    ⚠️

    🧩 Intermediate: Components as a Dependency Graph

    Components depend on each other (HRA depends on Basic; PF on Basic; TDS on all taxable earnings). The engine builds a DAG and evaluates in topological order, detecting cycles at configuration time.

    pythonfrom graphlib import TopologicalSorter
from decimal import Decimal as D

components = {
  "BASIC":   {"deps": [],                  "f": lambda c, i: i["gross"] * D("0.40")},
  "HRA":     {"deps": ["BASIC"],           "f": lambda c, i: c["BASIC"] * D("0.50")},
  "SPECIAL": {"deps": ["BASIC", "HRA"],    "f": lambda c, i: i["gross"] - c["BASIC"] - c["HRA"]},
  "PF_EE":   {"deps": ["BASIC"],           "f": lambda c, i: min(c["BASIC"], D(15000)) * D("0.12")},
}
order = list(TopologicalSorter({k: v["deps"] for k, v in components.items()}).static_order())
calc = {}
for code in order:
    calc[code] = components[code]["f"](calc, {"gross": D(80000)})
print(order, calc)    # BASIC first, then HRA/PF_EE, then SPECIAL
    💡
    Formulas belong to tenant configuration (a safe expression language), not code. The engine evaluates them; implementation consultants configure them.

    📆 Intermediate: Proration, LOP & Joiners

    When an employee joins mid-month or has unpaid leave, earnings are prorated. Methods vary by policy: calendar days, working days, or a fixed 30-day month.

    pythondef prorate(amount: D, payable_days: D, method_days: D) -> D:
    return (amount * payable_days / method_days).quantize(D("0.01"))
# September (30 calendar days), 2 LOP days, calendar-day method
print(prorate(D(80000), D(28), D(30)))   # 74666.67

    Module 04

    Payroll Batch Fault-Tolerance

    Designing payroll runs that survive crashes, timeouts and bad data — run state machines, chunking, idempotency keys, checkpoints, retries with backoff, poison records, the saga pattern and safe re-runs.

    🛡️ Basic: What Can Go Wrong

    💥
    Worker crash
    Pod killed mid-chunk; half the employees calculated.
    ⏱️
    Timeouts
    Database or tax-table service slow under month-end load.
    🧨
    Bad record
    One employee with corrupt data throws an exception.
    🔁
    Duplicate messages
    Queue delivers a chunk twice (at-least-once delivery).
    🧍
    Human change mid-run
    Admin edits salary while the run is in progress.

    Fault-tolerance means the run completes correctly despite these, or stops in a clean, resumable state — never a half-finished, inconsistent one.

    🚦 Intermediate: Run State Machine

    Figure 4.1 · Payroll run states
    pythonALLOWED = {
  "DRAFT": {"INPUTS_LOCKED"},
  "INPUTS_LOCKED": {"CALCULATING", "DRAFT"},
  "CALCULATING": {"CALCULATED", "PARTIAL"},
  "PARTIAL": {"CALCULATING", "CALCULATED"},          # re-run failed chunks only
  "CALCULATED": {"APPROVED", "INPUTS_LOCKED"},
  "APPROVED": {"DISBURSING"},
  "DISBURSING": {"PAID", "PAYMENT_EXCEPTIONS"},
  "PAYMENT_EXCEPTIONS": {"DISBURSING", "PAID"},
  "PAID": {"CLOSED"},
}
def transition(run, new_state):
    if new_state not in ALLOWED[run.state]:
        raise IllegalTransition(f"{run.state} -> {new_state}")
    # optimistic locking prevents two workers transitioning concurrently
    updated = db.execute("UPDATE payroll_run SET state=%s, version=version+1 "
                         "WHERE id=%s AND version=%s", (new_state, run.id, run.version))
    if updated.rowcount != 1:
        raise ConcurrentModification(run.id)
    💡
    Lock inputs before calculating. Edits after lock go into the next period or force an explicit re-open — preventing "moving target" runs.

    🔑 Intermediate: Idempotency & Checkpoints

    Each chunk result is written with an idempotency key (run_id + employee_id + run_attempt-agnostic). Writing twice has no extra effect.

    sqlCREATE TABLE payslip_result (
  run_id uuid, employee_id uuid, net_pay numeric(14,2), trace jsonb,
  computed_at timestamptz DEFAULT now(),
  PRIMARY KEY (run_id, employee_id)            -- natural idempotency key
);
INSERT INTO payslip_result (run_id, employee_id, net_pay, trace)
VALUES (%(run)s, %(emp)s, %(net)s, %(trace)s)
ON CONFLICT (run_id, employee_id) DO UPDATE
  SET net_pay = EXCLUDED.net_pay, trace = EXCLUDED.trace;   -- same inputs -> same result
    • Checkpoint chunk status (PENDING → DONE / FAILED) so a restarted run processes only unfinished chunks.
    • Results are deterministic, so recomputing a chunk is safe.

    🔂 Advanced: Retries, Backoff & Poison Records

    Failure typeStrategy
    Transient (timeout, deadlock)Retry with exponential backoff + jitter, max N attempts
    Data error for one employeeDo not fail the chunk; mark employee as exception with reason
    Poison message (fails every time)After max attempts → dead-letter queue + alert
    Systemic (rule table missing)Fail fast; stop the run; page on-call
    pythonimport random, time
def with_retry(fn, attempts=5, base=0.5):
    for n in range(attempts):
        try:
            return fn()
        except TransientError:
            if n == attempts - 1:
                raise
            time.sleep(base * 2 ** n + random.uniform(0, base))   # backoff + jitter

def process_chunk(chunk):
    for emp in chunk.employees:
        try:
            result = with_retry(lambda: calculate(emp, chunk.run))
            save_result(chunk.run, emp, result)
        except DataValidationError as e:
            record_exception(chunk.run, emp, reason=str(e))      # isolate bad record
    mark_chunk_done(chunk)

    🔗 Advanced: Sagas Across Steps

    A payroll run spans services (calculation, payslip generation, disbursement, GL posting). A saga sequences them with compensating actions if a later step fails — e.g., if GL posting fails, payments are not reversed, but the journal is retried and flagged; if bank file generation fails before release, approval is re-opened.

    Figure 4.2 · Payroll saga

    🏆 Expert: Observability & Chaos Testing

    • Metrics: chunks pending/failed, exceptions by reason, run duration vs SLA, retry rate.
    • Tracing: one trace ID per run; per-chunk spans.
    • Chaos tests: kill workers mid-chunk in staging and verify totals equal a clean run.
    • Reconciliation invariant: sum of payslip nets = sum of disbursement instructions = bank file total.
    ⚠️
    The most expensive bug in payroll is double payment. Every layer — results, bank instructions, API calls — must be idempotent and reconciled.

    🧮 Advanced: Reconciliation

    Webhooks are not the final truth — the bank statement is. Daily reconciliation matches statement lines (UTR, amount, date) to instructions.

    sqlSELECT i.idempotency_key, i.amount, s.amount AS stmt_amount, s.utr
FROM disbursement_instruction i
LEFT JOIN bank_statement_line s ON s.utr = i.utr
WHERE i.run_id = :run AND (s.utr IS NULL OR s.amount <> i.amount);   -- unmatched or mismatched

    🏆 Expert: Statutory Payments & Exactly-Once Thinking

    • Statutory remittances (PF ECR uploads, ESI challans, TDS payments and quarterly 24Q returns) follow the same pipeline: generate → validate → pay → reconcile → file.
    • Exactly-once money movement is achieved with idempotency keys at every boundary + reconciliation, because networks only guarantee at-least-once.
    • Cut-off awareness: release before bank cut-offs and holidays to meet "salary on the 1st" SLAs.
    ⚠️
    Never auto-retry a payment whose outcome is unknown (timeout) without first querying status by idempotency key — blind retries cause double payments.

    Module 11

    Interview Preparation

    Questions asked for payroll engine and fintech backend roles.

    🌱 Beginner Interview Questions

    IQ1.Why should money not be stored as float?
    Binary floats cannot represent decimals exactly, causing rounding errors; use Decimal or integer minor units (paise/cents).
    IQ2.Explain gross-to-net.
    Start with earnings (gross), apply proration, add one-time items, subtract pre-tax deductions, taxes and post-tax deductions to get net pay, with rounding and validation.
    IQ3.What is TDS projection?
    Estimating annual taxable income using YTD actuals plus expected future earnings, computing annual tax, then spreading the remaining liability over remaining months.

    🛠️ Intermediate Interview Questions

    IQ4.How do you model salary components with dependencies?
    As a DAG evaluated in topological order with formulas in configuration; detect cycles at config time.
    IQ5.How do you handle retroactive salary changes?
    Recalculate affected past periods with original inputs and new rules, compute differences per component, post arrears in the current period, re-project tax; never mutate past payslips.
    IQ6.How do you keep tax rules maintainable?
    Effective-dated, versioned tables per country/regime; payslips store rule versions; golden test suites for each change.

    🚀 Advanced Interview Questions

    IQ7.How do you make a payroll run fault-tolerant?
    State machine, input locking, chunking, deterministic calculation, idempotent writes, checkpoints, retries with backoff for transient errors, per-employee exceptions, DLQ, fail-fast for systemic errors.
    IQ8.How do you prevent double payments?
    Stable idempotency keys at each boundary, status queries before retries, deduplicated webhooks, maker-checker, and reconciliation with bank statements.
    IQ9.How do you test a tax engine?
    Golden cases signed off by experts, boundary tests at thresholds, property-based tests (monotonicity, non-negative), parallel runs against previous engine, snapshot diffs.

    🏆 Expert Interview Questions

    IQ10.Design a multi-country payroll engine.
    Core pipeline with pluggable country packs implementing earnings/statutory/tax interfaces, effective-dated rule data, shared orchestration and disbursement, localisation of rounding and calendars, per-country golden tests.
    IQ11.A payment's status is unknown after a timeout during release. Walk through your handling.
    Mark PENDING_UNKNOWN; query provider by idempotency key; if processed → mark paid; if not found → safe retry with same key; if ambiguous → hold and reconcile with statement; alert if unresolved before cut-off.
    IQ12.How would you scale a run of 200,000 employees under 30 minutes?
    Chunk into ~400 messages of 500, autoscale workers on queue depth, pre-load rule tables, avoid per-employee DB round-trips, batch writes, connection pooling, per-tenant concurrency caps, measure and optimise hot paths.

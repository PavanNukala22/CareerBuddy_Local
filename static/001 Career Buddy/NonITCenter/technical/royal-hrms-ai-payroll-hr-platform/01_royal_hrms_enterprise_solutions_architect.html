    Module 01

    The Enterprise Solutions Architect Role

    What a Solutions Architect does at an AI payroll & HR platform, the vocabulary you need, and how the four core skills — multi-tenancy, cloud scaling, enterprise integrations and data isolation — fit together.

    🏛️ Course Overview: What the Role Is

    A Solutions Architect at Royal HRMS designs how the platform serves hundreds of enterprise customers from one codebase without ever mixing their data, slowing down during payroll week, or breaking the HR systems they already run (Workday, SAP SuccessFactors, Oracle HCM). You translate business requirements ("we have 40,000 employees in 12 countries") into a concrete technical design that engineering can build and that a customer's security team will sign off.

    🏢
    Multi-tenant SaaS
    One platform, many companies. You decide how tenants share compute and storage safely.
    ☁️
    Cloud scaling
    Payroll is spiky: month-end runs need 20× normal capacity for a few hours.
    🔗
    Enterprise integrations
    Customers keep Workday, SAP or Oracle as a system of record — Royal HRMS must sync with them.
    🔒
    Data isolation
    Salary, bank and ID data for one tenant must be impossible for another tenant to see.
    💡
    A useful mental model: the architect owns the "how" and the "why", not the "what". Product decides what features exist; the architect decides how they are built to be secure, scalable and integrable — and documents why each trade-off was chosen.

    🎯 Learning Objectives

    By the end of this course you will be able to:

    1. Explain multi-tenant SaaS models (silo, bridge, pool) and choose the right one for a Royal HRMS customer tier.
    2. Design tenant context propagation, tenant-aware schemas and automated tenant provisioning.
    3. Plan cloud scaling for month-end payroll peaks using queue-based autoscaling, connection pooling and pre-scaling.
    4. Design integrations with Workday, SAP SuccessFactors and Oracle HCM using canonical models and reliable delta sync.
    5. Enforce tenant data isolation with row-level security, per-tenant encryption keys and isolated caches, files and search.
    6. Write Architecture Decision Records and defend trade-offs to engineering, security and customer stakeholders.
    7. Diagnose real production incidents: slowdowns, sync drift and suspected cross-tenant leaks.

    Module 02

    Multi-Tenant SaaS Architecture

    From "what is multi-tenancy" to cell-based architectures that serve thousands of HR customers — the three classic models, tenant context, schema design, onboarding automation and tiered tenancy.

    🏢 Basic: What Multi-Tenancy Means

    Single-tenant = every customer gets their own copy of the application and database. Multi-tenant = customers share the same running application (and often the same database), and the software keeps them apart logically. Royal HRMS is multi-tenant because it lets us ship one release to every customer, pay for infrastructure once, and onboard a new company in minutes instead of weeks.

    Think of an apartment building: everyone shares the foundation, lifts and plumbing (infrastructure), but each flat has its own lock (isolation). Single-tenant is a street of detached houses — great privacy, expensive to maintain.

    ✅ Multi-tenant benefits

    One codebase and deploy, lower cost per customer, fast onboarding, shared improvements, easier analytics across the platform (anonymised).

    ❌ Multi-tenant risks

    Cross-tenant data leaks, noisy neighbours, harder per-customer customisation, one bad release affects everyone.

    🧱 Basic: The Three Tenancy Models

    ModelHow data is storedIsolationCostBest for
    SiloSeparate database (or account) per tenantStrongestHighestBanks, government, very large enterprises
    BridgeShared DB server, separate schema per tenantMediumMediumMid-market with moderate compliance needs
    PoolShared tables with a tenant_id columnLogical onlyLowestSMB tenants, high tenant counts
    Figure 2.1 · Royal HRMS hybrid tenancy
    💡
    Most mature HR platforms are hybrid: pool for small customers, silo for the largest or most regulated. The architect designs the code so a tenant can be moved between models without rewriting the app.

    🧩 Intermediate: Tenant Context Everywhere

    The single most important pattern: every request carries a tenant identity that is resolved once at the edge and propagated everywhere — into the database session, logs, queues, caches and outbound calls. Never trust a tenant_id sent in a request body.

    Figure 2.2 · Request lifecycle with tenant context
    python# FastAPI-style middleware: resolve tenant once, from the verified token only
from contextvars import ContextVar
current_tenant: ContextVar[str] = ContextVar("current_tenant")

async def tenant_middleware(request, call_next):
    claims = verify_jwt(request.headers["Authorization"])   # signature checked
    tenant_id = claims["tid"]                                # never from body/query
    if not tenant_registry.is_active(tenant_id):
        return JSONResponse({"error": "tenant suspended"}, status_code=403)
    token = current_tenant.set(tenant_id)
    try:
        return await call_next(request)
    finally:
        current_tenant.reset(token)

    Tenant-aware schema design (pool model)

    sqlCREATE TABLE employee (
  tenant_id   uuid NOT NULL,
  employee_id uuid NOT NULL,
  legal_name  text NOT NULL,
  hire_date   date NOT NULL,
  PRIMARY KEY (tenant_id, employee_id)        -- tenant first in every key
);
CREATE INDEX ix_employee_hire ON employee (tenant_id, hire_date);
    • Put tenant_id first in primary keys and indexes so every query is tenant-scoped and partition-friendly.
    • Foreign keys should include tenant_id too, so a payslip can never reference another tenant's employee.
    • Unique constraints are per tenant: two companies can both have employee number E-1001.

    ⚙️ Intermediate: Tenant Lifecycle & Configuration

    Figure 2.3 · Tenant lifecycle

    Provisioning must be fully automated: a tenant-registry entry, region assignment, DB schema or rows, encryption key, default roles, payroll calendars and feature flags — created by one idempotent workflow. Manual steps are where isolation bugs are born.

    yaml# tenant manifest — declarative, version-controlled
tenant: acme-india
tier: enterprise
region: ap-south-1
residency: IN
tenancy_model: silo
features: [ai_attendance, autonomous_payroll, ess_portal]
integrations:
  - type: workday
    mode: event_subscription
limits: {api_rps: 200, payroll_concurrency: 40}
    📌
    Customisation should be configuration, not code forks. Per-tenant behaviour lives in metadata (policies, pay rules, workflows) evaluated by one codebase. A forked codebase per customer destroys the economics of SaaS.

    🚀 Advanced: Cell-Based Architecture

    As tenant count grows, a single shared stack becomes a giant blast radius. A cell is a complete, independent copy of the stack (services + databases + queues) serving a subset of tenants. A thin routing layer maps each tenant to its cell.

    Figure 2.4 · Cell-based Royal HRMS
    • Blast radius — a bad deploy or DB failure hits one cell, not all customers.
    • Progressive delivery — deploy to a canary cell, then wave by wave.
    • Predictable scaling — each cell has a known maximum size; you add cells instead of growing one monster.
    • Tenant migration — move a growing tenant to a less loaded or dedicated cell.

    🏆 Expert: Tiering, Migration & Trade-offs

    Expert architects design for change over time: a 300-employee startup that becomes a 30,000-employee enterprise should be able to move from pool to silo with no downtime.

    Figure 2.5 · Zero-downtime tenant migration (pool to silo)
    DecisionOption AOption BExpert heuristic
    Isolation for a regulated bankPool + RLSSilo DB + own keySilo: auditors accept physical separation more easily
    5,000 tiny tenantsSchema per tenantPoolPool: thousands of schemas make migrations and connections painful
    Per-tenant customisationCode branchMetadata rules engineMetadata: one codebase, testable configurations

    ✅ Best Practices & Common Mistakes

    ✅ Best practices

    Resolve tenant from the verified token; tenant_id in every key; automate provisioning; tier tenants; test isolation in CI; design for tenant migration.

    ❌ Common mistakes

    Trusting tenant_id from the client; global caches without tenant in the key; manual onboarding scripts; per-customer forks; one giant shared database forever.

    Module 03

    Cloud Infrastructure Scaling

    How Royal HRMS absorbs the month-end payroll spike: cloud building blocks, vertical vs horizontal scaling, autoscaling signals, queue-based batch scaling, database scaling, multi-region resilience and cost control.

    ☁️ Basic: Cloud Building Blocks

    🖥️
    Compute
    Containers on Kubernetes (EKS/AKS/GKE) or serverless functions for bursty jobs.
    🗄️
    Databases
    Managed PostgreSQL for transactions, a warehouse for analytics, Redis for caching.
    📬
    Queues & streams
    SQS/Service Bus/Kafka decouple producers (payroll scheduler) from workers.
    🌐
    Networking
    Load balancers, private subnets, VPC peering for customer VPNs.
    📦
    Object storage
    Payslip PDFs, bank files, bulk imports — cheap and durable.
    📈
    Observability
    Metrics, logs and traces tagged with tenant and cell.

    Scaling means the system keeps meeting its NFRs as load grows. HR load is unusual: it is predictable but extreme — daily attendance punches at 9:00, and payroll runs on the last working days of the month.

    ↕️ Basic: Vertical vs Horizontal Scaling

    ✅ Horizontal (scale out)

    Add more identical instances behind a load balancer. Near-unlimited, fault tolerant, requires stateless services.

    ❌ Vertical only (scale up)

    Buy a bigger machine. Simple, but has a ceiling, needs downtime to resize and leaves a single point of failure.

    💡
    Stateless services are the precondition for horizontal scaling. Keep session state in tokens or Redis, files in object storage, and work in queues — never on the local disk of one pod.

    📊 Intermediate: Autoscaling Signals

    CPU is a poor signal for batch systems. Royal HRMS scales payroll workers on queue depth and API pods on request rate and latency.

    WorkloadBest scaling signalExample policy
    Public APIRequests per second, p95 latencyAdd pods when p95 > 300 ms for 2 min
    Payroll workersQueue depth / age of oldest message1 worker per 500 pending payslips, max 400
    Attendance ingestionEvents per second from clocksScale consumers by Kafka consumer lag
    Report exportsScheduled + queueScale to zero overnight
    yaml# KEDA ScaledObject — scale payroll workers by SQS queue length
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata: {name: payroll-worker}
spec:
  scaleTargetRef: {name: payroll-worker}
  minReplicaCount: 2
  maxReplicaCount: 400
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.ap-south-1.amazonaws.com/123/payroll-calc
        queueLength: "500"     # target messages per replica
    📌
    Pre-scale for known peaks. Autoscaling reacts in minutes; month-end is known in advance. Schedule warm capacity 30 minutes before the payroll window and let autoscaling handle the rest.

    📬 Intermediate: Queue-Based Batch Scaling

    Figure 3.1 · Month-end payroll fan-out
    • Chunking turns one huge job into thousands of small, retryable units.
    • Per-tenant fairness — use per-tenant queues or weighted scheduling so one 80,000-employee tenant cannot starve everyone else.
    • Backpressure — workers pull at their own pace; the DB is protected by connection pools and worker caps.

    🗄️ Advanced: Scaling the Data Tier

    TechniqueSolvesWatch out for
    Read replicasRead-heavy dashboards & reportsReplication lag — never read your own write from a replica
    Connection pooling (PgBouncer)Thousands of pods exhausting DB connectionsTransaction-mode pooling breaks session-level settings; set tenant per transaction
    Partitioning by tenant or monthHuge tables (attendance punches)Queries must include the partition key
    Sharding across clustersExceeding one cluster's write capacityCross-shard queries and rebalancing
    Caching (Redis)Repeated lookups of tax tables, policiesTenant ID must be part of every cache key

    🌍 Advanced: Resilience & Multi-Region

    Figure 3.2 · Resilience layers

    Multi-region for an HR platform is mostly about data residency and disaster recovery, not active-active writes. Tenants are pinned to a home region; DR copies stay in a legal-compatible region.

    🏆 Expert: Capacity Planning & FinOps

    Experts model capacity from business drivers: employees processed per minute × peak concurrency × safety factor. Example: 600 tenants, 2.4M employees, 70% run payroll in the last 2 days, target 30 minutes per tenant run.

    textPeak payslips/hour  = 2.4M × 0.7 / 16 working hours ≈ 105,000
Worker throughput   = 25 payslips/sec/worker = 90,000/hour
Needed workers      ≈ 105,000 / 90,000 × 1.5 safety ≈ 2 workers... per hour-slice
But tenants cluster at 18:00–21:00 → model the 3-hour peak:
  2.4M × 0.7 × 0.6 / 3h ≈ 336,000/hour → ~6 workers + headroom for retries
    • Track cost per employee per month as the key unit-economics metric.
    • Use spot/preemptible capacity for idempotent payroll chunks; keep APIs on on-demand.
    • Scale non-production to zero at night; right-size DB instances quarterly.
    ⚠️
    Mistake: scaling application pods without checking the database. 400 workers each opening 10 connections = 4,000 connections — the database falls over first.

    🏢 Intermediate: The Big Three Platforms

    🟧
    Workday
    SOAP Web Services (Human_Resources, Payroll), REST APIs, RaaS custom reports as JSON, and Workday Studio/EIB for outbound integrations.
    🟦
    SAP SuccessFactors
    OData v2/v4 APIs (e.g., PerPerson, EmpJob), Intelligent Services event notifications, SAP Integration Suite (CPI) for mapping.
    🟥

    🧬 Intermediate: Canonical Data Model & Mapping

    Every ERP names things differently (Workday "Worker", SAP "PerPerson + EmpJob", Oracle "Worker + Assignment"). Royal HRMS maps all of them into one canonical model, so payroll and analytics never care which ERP a tenant uses.

    Figure 4.2 · Adapter pattern
    Canonical fieldWorkdaySAP SuccessFactorsOracle HCM
    employee_external_idWorker_IDuserId / personIdExternalPersonNumber
    hire_dateHire_DateEmpEmployment.startDateStartDate
    cost_centerCost_Center referenceEmpJob.costCenterAssignment DepartmentId
    employment_statusWorker_StatusEmpJob.emplStatusAssignmentStatusType
    📌
    Store mappings as versioned, per-tenant configuration. One customer's "Location" may be your "Work Site", another's may be "Legal Entity".

    🔁 Advanced: Sync Patterns & Reliability

    • Watermark delta sync — remember the last successful timestamp; advance it only after the batch commits.
    • Idempotent upserts — keyed by tenant + external ID, so replays never create duplicates.
    • Ordering — apply effective-dated changes in effective-date order; a termination must not be overwritten by an older transfer.
    • Dead-letter queue (DLQ) — records that fail validation are parked with a reason, visible to the implementation team.
    • Reconciliation — a nightly job compares counts and hashes between ERP and Royal HRMS and raises drift alerts.
    Figure 4.3 · Reliable inbound sync

    🏆 Expert: Integration Governance

    ConcernExpert practice
    OwnershipDefine SoR per field in a data-ownership matrix signed by the customer
    CredentialsPer-tenant OAuth clients or ISU accounts stored in a secrets manager; rotated
    Rate limitsRespect vendor limits with token buckets per tenant per connector
    Change managementContract tests against vendor sandboxes; monitor vendor release notes (Workday bi-annual releases)
    ObservabilityDashboards per tenant: lag, failures, DLQ size, last success
    ⚠️
    Classic failure: two systems both act as master for the same field (e.g., both edit bank details) → endless overwrite loops. Always decide one owner per field.

    Module 05

    Tenant Data Isolation

    Guaranteeing that one company can never see another company's salaries — isolation layers, PostgreSQL row-level security, per-tenant encryption keys, isolated caches, queues, files and search, and how to prove isolation to auditors.

    🔒 Basic: Why Isolation Is Non-Negotiable

    HR data is among the most sensitive data a company holds: salaries, bank accounts, national IDs, medical leave. A single cross-tenant leak can end customer trust, trigger GDPR breach notification within 72 hours, and lose deals across the market. Isolation is therefore an architectural property, not a feature.

    🧱
    Defence in depth
    Several independent layers must fail before data leaks.
    🆔
    Tenant context
    Every layer knows which tenant it is acting for.
    🧪
    Provable
    Automated tests and audits demonstrate isolation continuously.

    🛡️ Intermediate: Isolation Layers

    Figure 5.1 · Defence-in-depth for tenant data

    🐘 Intermediate: PostgreSQL Row-Level Security

    In the pool model, row-level security (RLS) makes the database itself refuse cross-tenant rows — even if a developer forgets a WHERE tenant_id = ?.

    sqlALTER TABLE payslip ENABLE ROW LEVEL SECURITY;
ALTER TABLE payslip FORCE ROW LEVEL SECURITY;      -- applies to table owner too

CREATE POLICY tenant_isolation ON payslip
  USING (tenant_id = current_setting('app.tenant_id')::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);

-- application, per transaction (safe with PgBouncer transaction pooling):
BEGIN;
SET LOCAL app.tenant_id = '6f1c...';
SELECT employee_id, net_pay FROM payslip WHERE period = '2026-09';
COMMIT;
    ⚠️
    The app must connect as a non-superuser role without BYPASSRLS. Superusers ignore policies — a classic misconfiguration that silently disables isolation.

    🔑 Advanced: Per-Tenant Encryption

    Encryption at rest protects against stolen disks; per-tenant keys go further. With envelope encryption, each tenant has a key-encryption key (KEK) in a KMS; data-encryption keys (DEKs) encrypt the actual fields.

    Figure 5.2 · Envelope encryption per tenant
    • Crypto-shredding — deleting a tenant's KEK makes all their backups unreadable: a clean offboarding story for GDPR erasure.
    • BYOK / HYOK — enterprise customers can supply or hold their own key, and revoke it.
    • Encrypt high-risk fields (bank, ID, salary) at application level in addition to disk encryption.

    Customers and auditors (SOC 2, ISO 27001) will ask "how do you know tenants are isolated?". Experts answer with evidence, not promises.

    🔥 Troubleshooting: Month-End Slowdown

    Symptom: on the 30th, payroll runs for all tenants slow from 20 to 140 minutes; API p95 jumps to 4 s.

    StepCheckFinding
    1Queue depth & worker countWorkers at max 400, queue still growing
    2Database metrics3,900 active connections, CPU 98%
    3Per-tenant breakdownOne 80k-employee tenant consumes 70% of chunks
    4Root causeNo per-tenant concurrency cap; each worker holds its own DB pool
    💡
    Fix: introduce PgBouncer, cap per-tenant concurrency (weighted fair queueing), move the giant tenant to its own cell, and pre-scale DB read capacity for month-end.

    🕵️ Troubleshooting: Suspected Cross-Tenant Leak

    Symptom: an HR admin reports seeing an unfamiliar employee name in an autocomplete box.

    1. Treat as a P1 security incident; preserve logs; restrict the feature flag.
    2. Trace the request: the autocomplete service reads from Redis.
    3. Inspect cache key builder: emp_search:{prefix} — no tenant in the key.
    4. Fix: emp_search:{tenant}:{prefix}, flush cache, add CI test for all key builders.
    5. Determine exposure from logs, notify affected tenants per contract and GDPR timelines, publish an RCA.
    ⚠️
    The database had RLS — the leak bypassed it through the cache. Isolation must cover every channel, not only the database.

    🔄 Troubleshooting: Workday Sync Drift

    Symptom: 312 terminated employees still appear active in Royal HRMS and are included in the payroll preview.

    • Check DLQ: 312 records rejected — the customer added a new termination reason code not in the mapping.
    • Watermark advanced anyway because failures were treated as "processed".
    • Fix: map the new code, replay the DLQ, change logic so validation failures block payroll approval via a reconciliation gate.

    ⚖️ Trade-off Scenario: Cost vs Isolation

    Sales wants every new customer on a dedicated database "for security". As architect you show the cost per employee rises 6×, operations overhead grows linearly, and RLS + per-tenant keys already meet SOC 2. You propose tiered tenancy: silo for regulated or 10k+ employee tenants, pool for others — documented in an ADR and reflected in the pricing tiers.

    Interview Preparation

    Questions asked in Solutions Architect interviews at HR-tech and enterprise SaaS companies, grouped by level. Draft your answer, then compare with the model answer.

    🌱 Beginner Interview Questions

    IQ1.Explain multi-tenancy to a non-technical HR director.
    Like an office building shared by many companies: everyone shares the lifts and power so it is cheaper and maintained centrally, but each company's office has its own locks and keys. We use several independent locks — identity, application checks, database rules and encryption — so no one can enter another company's office.
    IQ2.What is the difference between scaling up and scaling out?
    Scaling up gives one machine more CPU/RAM — simple but limited and a single point of failure. Scaling out adds more instances behind a load balancer — needs stateless services but is effectively unlimited and resilient.
    IQ3.What is a system of record?
    The authoritative source for a specific data element. Other systems consume and must not overwrite it. Defining SoR per field avoids conflicting updates.

    🛠️ Intermediate Interview Questions

    IQ4.How do you choose between silo, bridge and pool tenancy?
    Weigh isolation and compliance needs, tenant count, cost per tenant, operational overhead and customisation. Most platforms go hybrid: pool for SMB, silo for regulated/large tenants, with code that supports moving tenants between models.
    IQ5.How would you sync employee changes from Workday?
    Use a RaaS or Get_Workers delta by last-updated timestamp or event-based outbound integration, map to canonical model, validate, idempotent upsert keyed by tenant + Worker_ID, DLQ for failures, watermark advanced only after commit, nightly reconciliation.
    IQ6.How do you prevent noisy neighbours?
    Per-tenant rate limits and concurrency caps, weighted fair queues, resource quotas per cell, moving heavy tenants to dedicated cells, and monitoring per-tenant consumption.

    🚀 Advanced Interview Questions

    IQ7.Walk through how RLS works and its pitfalls.
    Policies filter rows using a session setting like app.tenant_id. Pitfalls: superuser or BYPASSRLS roles ignore it, table owners unless FORCE is set, session-level SET leaking across pooled connections (use SET LOCAL), missing policies on new tables, and non-DB channels (cache, search) not covered.
    IQ8.Design month-end payroll scaling for 3 million employees.
    Chunk runs into messages, KEDA scale on queue depth, scheduled pre-warm, per-tenant concurrency caps, PgBouncer, read replicas for reports, spot instances for idempotent chunks, observability per tenant and SLO alerts on oldest message age; validate with load tests at 1.5× projected peak.
    IQ9.What is cell-based architecture and when would you adopt it?
    Independent full stacks each serving a subset of tenants behind a router. Adopt when blast radius, deployment risk or single-stack limits become business risks — typically hundreds of tenants or strict SLAs.

    🏆 Expert Interview Questions

    IQ10.A prospect demands data never leaves India and they hold the keys. How do you respond?
    Confirm region pinning (compute, storage, backups, logs, support access) in an Indian region, BYOK/HYOK via KMS external key store or HSM, document sub-processors, explain operational implications of key revocation, and provide architecture diagram plus contractual commitments.
    IQ11.How do you prove tenant isolation to an auditor?
    Present layered controls, CI cross-tenant tests, pen-test results targeting IDOR, RLS configuration evidence, key management policies, access logs and runtime alerts for multi-tenant result sets — all mapped to SOC 2/ISO 27001 controls.
    IQ12.How do you handle an architecture disagreement with a senior engineering lead?
    Make the decision criteria explicit (NFRs, cost, risk), write competing options into an ADR, prototype or benchmark where facts are missing, involve stakeholders, decide, record consequences and set a review date.

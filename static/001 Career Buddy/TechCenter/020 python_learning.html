    🥒 The pickle Module

    Need to save complex Python objects (lists, dicts, class instances) to disk and load them later? pickle serializes objects to a binary stream.

    import pickle

data = {"scores": [85, 72, 91], "name": "Asha"}

# SAVE

    pickle.dump(data, f)

    Module 05

    Object-Oriented Programming

    This entire module is dedicated to OOP — no libraries here (those now live in their own Libraries & Frameworks tab). Every concept below is explained from first principles with a plain-English analogy first, then the code, then why it matters. Take your time on this tab — OOP is the single biggest mental shift from "beginner Python" to "real Python."

    🧠 What is OOP, Really?

    Up to now, most of your code has probably been a list of steps: do this, then that, then this. That style is called procedural programming. It works fine for small scripts, but it gets messy once your program has many related pieces of data and behavior that belong together.

    Object-Oriented Programming (OOP) is a different way of organizing code: instead of separate variables and functions floating around, you bundle data (called attributes) and the actions on that data (called methods) into a single unit called an object.

    🏠
    Real-world analogy: think of a house blueprint versus an actual house. The blueprint (called a class in code) describes what every house of that design will have — number of rooms, door positions, a front-door-opening action. An actual house built from that blueprint (called an object or instance) is a real, specific thing: this house is at 12 MG Road and its front door is currently locked. You can build a hundred houses from one blueprint, and each one has its own front door, its own furniture, independent of the others.

    OOP is built on four core ideas, often called the "four pillars." Don't worry about memorizing the names yet — each one gets its own detailed section below with examples:

    📦
    Encapsulation
    Bundling data and the methods that work on it together, and hiding the messy internal details from the outside world.
    🧬
    Inheritance
    Letting a new class reuse and extend the code of an existing class, instead of copy-pasting.
    🎭
    Polymorphism
    Different objects responding to the "same" method call in their own specific way.
    🎨
    Abstraction
    Showing only what's necessary and hiding the complicated implementation behind a simple interface.
    📌
    You've actually been using OOP this whole time without writing your own classes: every list, string, and dictionary in Python is itself an object. When you write "hello".upper(), you're calling a method (upper) that belongs to the string object "hello". This module teaches you to build your own objects like that.

    🏗️ Classes & Objects

    A class is defined with the class keyword. It's just a template — writing a class doesn't create anything "real" yet, the same way drawing a blueprint doesn't build a house. To get a real, usable thing, you instantiate the class — that means calling it like a function, which creates an object (also called an instance).

    class Circle:
    """A circle defined by its radius."""

    def __init__(self, radius):
        self.radius = radius     # instance variable — belongs to THIS object only

    def area(self):
        return 3.14159 * self.radius ** 2

    def __repr__(self):
        return f"Circle(r={self.radius})"

c = Circle(5)     # THIS line is where the object actually gets created
print(c.area())   # 78.539… — calling a method belonging to c
print(c)           # Circle(r=5) — uses __repr__ to decide how to display c

    Let's slow down and read this line by line, the way a beginner should the first time they see a class:

    LineWhat it means in plain English
    class Circle:"I'm defining a new blueprint/template called Circle."
    def __init__(self, radius):"Whenever someone creates a new Circle, run this setup code and remember the radius they gave me."
    self.radius = radius"Store the given radius value ON this specific object, so I can use it later."
    def area(self):"Any Circle object can be asked to compute its own area — here's how."
    c = Circle(5)"Build one actual Circle, with radius 5, and give it the name c."
    c.area()"Ask the object c to run its own area method."

    🔧 __init__ and self, Explained Slowly

    These two things confuse almost every beginner at first — so let's go extra slow.

    What is __init__?

    __init__ is a special method (Python calls these "dunder" methods, short for "double underscore") that runs automatically the instant an object is created. Think of it as the "move-in setup" for a new house — the moment the house is built, someone immediately turns on the water and electricity. You never call __init__ yourself directly; Python calls it for you when you write Circle(5).

    What is self?

    self is simply a reference to the specific object that a method is being called on. It answers the question "whose radius am I looking at?" When you write c.area(), Python quietly rewrites that call behind the scenes as Circle.area(c) — so self inside the method becomes c. This is exactly how self.radius knows to look at c's radius and not some other circle's radius.

    class Dog:
    def __init__(self, name, breed):
        self.name  = name     # "self" = the dog currently being built
        self.breed = breed

    def bark(self):
        return f"{self.name} says Woof!"   # "self" = whichever dog .bark() was called on

d1 = Dog("Rex", "Labrador")
d2 = Dog("Milo", "Beagle")

d1.bark()   # "Rex says Woof!"  — self was d1
d2.bark()   # "Milo says Woof!" — self was d2, completely separate data
    ⚠️
    Beginner trap: self is not a Python keyword — it's just a convention (you could technically name it anything, but every Python developer on Earth calls it self, so never rename it). It must always be the first parameter of any regular method, and Python fills it in automatically — you never pass it yourself when calling d1.bark().

    🗂️ Instance vs Class Attributes

    There are two kinds of attributes, and mixing them up is a very common source of bugs.

    👤 Instance attribute

    Defined with self.x = ... inside a method. Belongs to one specific object. Every Dog has its own name — changing one dog's name never affects another dog.

    🏛️ Class attribute

    Defined directly inside the class body (not inside a method). Shared by every object of that class — like a rule that applies to the whole species, not one individual.

    class Dog:
    species = "Canis familiaris"   # CLASS attribute — same for every Dog ever made

    def __init__(self, name):
        self.name = name              # INSTANCE attribute — unique per object

d1 = Dog("Rex")
d2 = Dog("Milo")

d1.name, d2.name          # ('Rex', 'Milo')      — different per dog
d1.species, d2.species    # both 'Canis familiaris' — shared

    Related to this: methods can also come in three flavors, which decide what they automatically receive as their first argument:

    DecoratorFirst argumentUsed for
    (none — regular method)self (the object)Behavior that needs the specific object's data
    @classmethodcls (the class itself)Alternative constructors, or logic about the class as a whole
    @staticmethodnothing specialA helper function that's logically related to the class but needs no object or class data
    class Dog:
    count = 0
    def __init__(self, name):
        self.name = name
        Dog.count += 1            # updates the SHARED class attribute

    @classmethod
    def how_many(cls):
        return f"{cls.count} dogs created so far"

    @staticmethod
    def is_valid_name(name):
        return len(name) > 0     # doesn't need self or cls at all

    🔒 Encapsulation

    Encapsulation means bundling data with the methods that operate on it, and controlling how outside code is allowed to touch that data — hiding the messy internal details behind a clean surface.

    📺
    Analogy: a TV remote gives you a few buttons (channel up/down, volume, power) — a simple public interface. You never need to touch the internal circuit board to change the channel, and the manufacturer can redesign the internal electronics completely without changing how you use the remote. That's encapsulation: simple public interface, protected internal details.

    Python doesn't have strict "private" keywords like Java, but it uses a naming convention everyone follows:

    Naming styleConvention meaning
    self.namePublic — anyone can read/write freely
    self._name"Protected" — a hint saying "internal use, please don't touch from outside" (not enforced by Python)
    self.__name"Private" — Python actively renames it internally (name mangling) to make accidental outside access harder
    class BankAccount:
    def __init__(self, balance):
        self.__balance = balance     # "private" — outside code shouldn't set this directly

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self.__balance += amount

    @property
    def balance(self):             # a read-only "view" of the private data
        return self.__balance

acc = BankAccount(1000)
acc.deposit(500)
print(acc.balance)     # 1500 — read like an attribute, no () needed
# acc.balance = 99999   <- would raise an error: no setter defined, protecting the data
    📌
    Why bother? Without encapsulation, any code anywhere in a large program could set acc.__balance = -500 directly, bypassing all your validation rules. Forcing changes to go through methods like deposit() means you can enforce rules ("no negative deposits") in exactly one place.

    🧬 Inheritance

    Inheritance lets you create a new class that automatically gets all the attributes and methods of an existing class, and then add or override only what's different — instead of copy-pasting code.

    👨‍👩‍👧
    Analogy: think of "Animal" as a general category and "Dog", "Cat", "Cow" as specific types of animal. Every animal has a name and can speak() in some way — but how each one speaks is different. Rather than writing the "has a name" logic three separate times, you write it once in Animal and let Dog, Cat, and Cow each inherit it.
    class Animal:                            # the PARENT / BASE / SUPER class
    def __init__(self, name):
        self.name = name
    def speak(self):
        return "some generic sound"
    def describe(self):
        return f"{self.name} the {type(self).__name__}"

class Dog(Animal):                       # Dog is the CHILD / DERIVED / SUB class
    def __init__(self, name, breed):
        super().__init__(name)          # reuse Animal's setup for "name"
        self.breed = breed                # then add Dog-specific data
    def speak(self):                        # OVERRIDE — replace the parent's version
        return f"{self.name} says Woof!"

rex = Dog("Rex", "Labrador")
rex.speak()      # 'Rex says Woof!'          — Dog's own version
rex.describe()   # 'Rex the Dog'             — inherited straight from Animal, untouched

    super().__init__(name) means "run the parent class's constructor first, so I don't have to rewrite the name-setting logic myself." This keeps the parent's setup logic in exactly one place.

    Figure 5.2 · One parent, three specialized children
    📌
    Multiple inheritance (a class inheriting from more than one parent, e.g. class Robot(Machine, Animal):) is possible in Python but should be used sparingly — it can make it hard to know which parent's method actually runs. Python resolves this using an ordering called MRO (Method Resolution Order), viewable via ClassName.__mro__.

    🎭 Polymorphism

    Polymorphism ("many forms") means you can call the same method name on different objects, and each object responds in its own way — you don't need to know exactly which type of object you're dealing with to use it correctly.

    animals = [Dog("Rex", "Lab"), Cat("Whiskers"), Cow("Bessie")]

for a in animals:
    print(a.speak())    # same line of code, three different outputs
# Rex says Woof!
# Whiskers says Meow!
# Bessie says Moo!

    This is powerful because the calling code (the for loop) doesn't need an if/elif chain checking "is this a Dog? a Cat? a Cow?" — it just trusts that every object in the list understands .speak() and lets each object handle it correctly.

    🦆
    "Duck typing" is Python's informal take on this idea: "If it walks like a duck and quacks like a duck, treat it as a duck." Python doesn't check an object's exact type before calling a method — if the object has a .speak() method, that's good enough, regardless of its class.

    🎨 Abstraction

    Abstraction means exposing only the essential, simple interface of something while hiding the complicated details behind it. You've already been using abstraction: calling sorted(my_list) doesn't require you to understand the sorting algorithm running underneath.

    In your own classes, Python provides abstract base classes (via the abc module) to formally require that certain methods must be implemented by any subclass — enforcing a contract.

    from abc import ABC, abstractmethod

class Shape(ABC):                     # ABC = "Abstract Base Class"
    @abstractmethod
    def area(self):
        pass                          # no implementation here — subclasses MUST provide one

class Square(Shape):
    def __init__(self, side): self.side = side
    def area(self):
        return self.side ** 2

# Shape()          <- raises TypeError: Can't instantiate abstract class
Square(4).area()   # 16 — fine, Square provided the required method

    Trying to create a bare Shape() directly raises an error — Python is enforcing the rule that "Shape" is only a concept, not something you should use on its own; only its fully-implemented children (like Square) can be built.

    ➕ Operator Overloading (Magic Methods)

    Python lets your own objects work naturally with built-in operators like +, ==, len(), and print() — by defining special "magic" (dunder) methods. You've already met two: __init__ and __repr__.

    class Vec2:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __add__(self, other):           # defines what "+" does between two Vec2 objects
        return Vec2(self.x + other.x, self.y + other.y)

    def __eq__(self, other):            # defines what "==" means for two Vec2 objects
        return self.x == other.x and self.y == other.y

    def __repr__(self):               # defines how print() displays this object
        return f"Vec2({self.x}, {self.y})"

v1, v2 = Vec2(1, 2), Vec2(3, 4)
v1 + v2              # Vec2(4, 6)   — Python calls v1.__add__(v2) behind the scenes
v1 == Vec2(1, 2)   # True         — Python calls v1.__eq__(...) behind the scenes

    🧩 Composition — the Other Kind of Reuse

    Inheritance models an "is-a" relationship (a Dog is an Animal). Composition models a "has-a" relationship — building a class by including other objects as attributes, rather than inheriting from them.

    class Engine:
    def start(self): return "Engine roaring to life"

class Car:
    def __init__(self):
        self.engine = Engine()      # Car HAS AN Engine — not "Car IS AN Engine"

    def start(self):
        return self.engine.start()   # delegate the work to the Engine object

Car().start()   # "Engine roaring to life"
    ✅
    Rule of thumb: "Favor composition over inheritance" is a well-known guideline in professional software design. Use inheritance when one thing is genuinely a specialized version of another (Dog is an Animal). Use composition when one thing is simply built out of, or uses, another (Car has an Engine) — it's more flexible and avoids deep, fragile inheritance chains.

    🧮 Comprehensions — Deep Dive

    A comprehension is a compact way to build a new collection (list, set, or dict) by describing what you want, rather than writing out a manual loop step by step. Think of it as the difference between saying "go through every item, square it, and put the result in a new bag" (a loop, written line by line) versus "give me a bag of squares of every item" (a comprehension, written as one sentence).

    🛒
    Analogy: imagine you have a basket of fruit and want a new basket containing only the ripe ones, peeled. A traditional loop would be: "get an empty basket; for each fruit in the old basket, check if it's ripe; if so, peel it and put it in the new basket." A comprehension collapses that whole recipe into a single readable line: [peel(f) for f in basket if is_ripe(f)].

    You've already met the basic list comprehension in earlier modules. Here is the full family — the same idea applied to every collection type Python has, plus the patterns that show up constantly in real codebases and interviews.

    1 · List, Set, Dict, Generator comprehensions

    All four comprehension types share the same shape — <expression> for <item> in <iterable> — the only thing that changes is the bracket you wrap it in, and that bracket decides what kind of container you get back.

    # List comprehension
squares = [x**2 for x in range(10)]

# Set comprehension — de-duplicates automatically
unique_lengths = {len(w) for w in ["cat", "dog", "owl", "emu"]}

# Dict comprehension
squares_map = {x: x**2 for x in range(5)}

# Generator expression — lazy, no [] or {}, computed on demand
gen = (x**2 for x in range(10**6))  # uses almost no memory
    SyntaxBracket usedWhat you get back
    List comprehension[ ]A full list, all values computed immediately, kept in order
    Set comprehension{ }A set — duplicates are automatically dropped, no guaranteed order
    Dict comprehension{key: value}A dictionary mapping each key to a computed value
    Generator expression( )Nothing computed yet — values are produced one at a time only when asked for (see Iterators & Generators below)

    2 · Nested comprehensions & conditions

    Comprehensions can loop over more than one thing (nesting), and can filter which items get included using an if. It's important to notice where the if sits, because it changes its meaning completely.

    # Flatten a 2D matrix
matrix = [[1,2,3], [4,5,6]]
flat = [num for row in matrix for num in row]
# [1, 2, 3, 4, 5, 6]

# if/else INSIDE the expression (conditional expression)
labels = ["even" if n % 2 == 0 else "odd" for n in range(5)]

# if AFTER the loop = filter (only even numbers kept)
evens = [n for n in range(20) if n % 2 == 0]

    A simple way to remember the difference: an if/else placed before the for is deciding what value to produce for every single item (nothing gets dropped — a decision is made for each one). An if placed after the for is deciding whether an item makes it into the result at all (some items get skipped entirely).

    ⚠️
    Interview gotcha: a comprehension nested more than 2 levels deep is usually a readability smell. If you can't explain it in one sentence, write it as a normal loop instead.

    λ Lambda & Functional Programming

    lambda creates a small, throwaway, anonymous function inline — one expression, no return keyword, no name, no multi-line body. Use it when a function is so small and so temporary that giving it a full def name would be overkill.

    🗒️
    Analogy: a regular function defined with def is like writing a recipe down in a cookbook — it has a name, you can look it up and reuse it forever. A lambda is like scribbling a quick calculation on a sticky note to use once and throw away — not worth writing a whole recipe for.
    square = lambda x: x * x
square(5)   # 25

# Most common real use: as the "key" for sorting
people = [("Asha", 28), ("Ravi", 22), ("Zoe", 31)]
people.sort(key=lambda p: p[1])   # sort by age

    Here, key=lambda p: p[1] tells .sort() exactly one thing: "when deciding the order, look at each person's age (the second item in the tuple), not the whole tuple." Writing a full named function just for this one-line comparison would be unnecessary ceremony — that's exactly the situation lambdas are built for.

    map, filter, reduce

    These three functions are the classic "functional programming" trio, and every one of them takes a function as an argument and applies it across a collection:

    from functools import reduce

nums = [1, 2, 3, 4, 5]

doubled  = list(map(lambda x: x*2, nums))       # [2, 4, 6, 8, 10]
evens    = list(filter(lambda x: x%2==0, nums))
total    = reduce(lambda a, b: a + b, nums)      # 15 (running accumulation)
    FunctionIn plain English
    map(f, list)"Apply f to every item and give me back the transformed list." (Transform each item.)
    filter(f, list)"Keep only the items where f returns True." (Keep some, drop others.)
    reduce(f, list)"Combine all items into a single value, two at a time, left to right." (Collapse everything into one result.)
    💡
    In production Python, a list comprehension is almost always preferred over map/filter for readability — but you must recognize all three since they appear constantly in interviews and legacy code.

    🌊 Iterators & Generators

    These three related words trip up a lot of learners, so let's define them precisely. An iterable is anything you can loop over with for (lists, strings, dicts, files). An iterator is the actual "cursor" object that walks through an iterable one item at a time, remembering exactly where it left off, via a method called __next__(). A generator is simply the easiest way to build your own iterator, using the yield keyword instead of manually writing the iterator machinery.

    🎬
    Analogy: think of a Netflix series (the iterable — the whole show exists) and your "continue watching" bookmark (the iterator — it remembers exactly which episode and timestamp you stopped at, and gives you the next episode each time you press play). A generator function is like a show that gets written and filmed episode-by-episode, on demand, only once you actually click "next episode" — rather than the entire series existing in full before you start watching.
    def countdown(n):
    while n > 0:
        yield n          # pauses here, remembers state
        n -= 1

for i in countdown(3):
    print(i)              # 3, 2, 1

# Manual protocol (what "for" does under the hood)
it = iter([10, 20])
next(it)   # 10
next(it)   # 20
next(it)   # raises StopIteration

    Notice that countdown(3) doesn't compute 3, 2, 1 all at once. Calling it just creates a paused generator object. Each time the for loop asks for the next value, the function body runs until it hits yield, hands back that one value, and freezes in place — remembering every local variable exactly as it was — until asked for the next one.

    Why generators matter: they compute values lazily, one at a time, so you can process huge or even infinite sequences without ever loading everything into memory at once.

    # Reading a 10 GB log file line-by-line without exhausting RAM
def read_large_file(path):
    with open(path) as f:
        for line in f:
            yield line.strip()

    Here, even if the file were 10 GB, this function never holds more than one line in memory at a time — a plain list-building approach (return [line for line in f]) would try to load the entire file into RAM at once and could crash the program.

    🐢 List

    Builds the entire sequence in memory up front. Can be iterated many times. Supports indexing.

    ⚡ Generator

    Produces values one at a time, on demand. Exhausted after one pass. No indexing.

    🎀 Decorators

    A decorator is a function that wraps another function to add extra behavior before and/or after it runs — without ever touching or rewriting that function's original source code. This is the single most "advanced-looking" Python feature that's actually simple once it clicks.

    🎁
    Analogy: think of a decorator as gift-wrapping a present. The present itself (your original function) doesn't change at all inside the box — but the wrapping paper (the decorator) adds something extra around it, like a ribbon that logs "this gift was opened at 3:05pm" the moment someone opens it. You can gift-wrap the exact same present in different papers without ever altering what's inside.

    The @decorator_name syntax right above a function definition is just shorthand — @timer above def slow_add(...) is Python's way of automatically doing slow_add = timer(slow_add) for you.

    def timer(func):
    import time, functools
    @functools.wraps(func)             # preserves func's name/docstring
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.time()-start:.4f}s")
        return result
    return wrapper

@timer
def slow_add(a, b):
    import time; time.sleep(1)
    return a + b

slow_add(2, 3)   # prints "slow_add took 1.0003s", returns 5

    Read it in this order: timer is a function that accepts another function (func) and returns a brand-new function (wrapper). That wrapper function runs some code (start the clock), then calls the original function, then runs more code (print elapsed time), then hands back the original's result — so nothing about what slow_add actually computes has changed.

    Decorators that take their own arguments

    Sometimes you want to configure the decorator itself, like @repeat(times=3). This needs one extra layer of nested functions: an outer function that accepts the decorator's own arguments, which returns the actual decorator, which returns the wrapper.

    def repeat(times):
    def decorator(func):
        def wrapper(*args, **kwargs):
            for _ in range(times):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator

@repeat(times=3)
def greet(name): print(f"Hi {name}")

    Three of the most useful decorators are already built into Python and appear constantly in real code:

    ⏱️
    @lru_cache
    Built-in memoization decorator from functools — caches return values automatically.
    🏠
    @property
    Turns a method into a read-only attribute — the backbone of getters/setters in Python classes.
    🏗️
    @staticmethod / @classmethod
    Change what a method receives as its first argument — no self, or cls instead.

    🚪 Context Managers (with)

    The with statement guarantees that setup code runs before a block, and cleanup code always runs after it — even if the code inside the block crashes with an exception. This is most famous for files, database connections, and locks, where forgetting to clean up (like never closing a file) can leak resources.

    🚿
    Analogy: think of using a public shower room. You "enter" (turn the water on), do what you came to do, and you must "exit" (turn the water off) — no matter what happens in between, even if you slip and fall. A context manager guarantees the "turn the water off" step happens automatically, so nobody has to remember to do it manually and risk forgetting during an emergency.

    You can build your own context manager two ways: as a class with two special methods, or — more commonly — as a short function using contextlib.

    # Class-based context manager
class Timer:
    def __enter__(self):
        import time; self.start = time.time()
        return self
    def __exit__(self, exc_type, exc_val, exc_tb):
        import time; print(time.time() - self.start)
        return False   # False = don't suppress exceptions

with Timer():
    sum(range(10**6))

# Function-based, using contextlib — much shorter
from contextlib import contextmanager

@contextmanager
def open_file(path, mode):
    f = open(path, mode)
    try:
        yield f
    finally:
        f.close()

    __enter__ runs at the top of the with block (the "turn the water on" step) and whatever it returns becomes the value after as. __exit__ runs automatically the moment the block ends, whether it finished normally or an exception was raised inside it — that's the guarantee. In the function-based version, everything before yield is the setup, and everything in the finally is the guaranteed cleanup.

    🔒 Closures & *args / **kwargs

    A closure is an inner function that "remembers" the variables from its enclosing (outer) function even after that outer function has already finished running and returned. Normally, once a function finishes, its local variables disappear — a closure is the special case where they don't.

    🎒
    Analogy: imagine a factory (the outer function) that manufactures custom calculators (the inner function), each pre-configured with a specific multiplier baked in at manufacturing time, like a "×2 calculator" or a "×3 calculator." Once a calculator leaves the factory, it still remembers its own multiplier forever, even though the factory itself has long since finished that particular production run.
    def make_multiplier(factor):
    def multiply(n):
        return n * factor      # "factor" is captured from the outer scope
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)
double(5)   # 10
triple(5)   # 15 — each closure keeps its OWN "factor"

    Here, make_multiplier(2) runs once, creates the multiply function, and returns it as double. Even though make_multiplier has already finished executing, double still has access to factor = 2 forever — that captured value is what makes it a closure.

    *args and **kwargs — accepting a flexible number of arguments

    Sometimes you don't know in advance how many arguments a function will be called with. *args collects any extra positional arguments into a tuple; **kwargs collects any extra keyword arguments into a dictionary. The names args/kwargs are just convention — the important part is the * and **.

    def describe(*args, **kwargs):
    print("positional:", args)     # tuple
    print("keyword:", kwargs)      # dict

describe(1, 2, city="Hyderabad", pin=500001)

# Unpacking the other way — spreading a list/dict INTO a call
nums = [3, 7]
opts = {"sep": " - "}
print(*nums, **opts)   # 3 - 7

    This is exactly how decorators from the previous section could wrap any function, no matter how many arguments it takes: the wrapper(*args, **kwargs) pattern says "whatever you were called with, I'll catch all of it and pass it straight through to the real function."

    ∫ Bonus: Numerical Methods

    This bonus section shows Python solving problems from calculus — not because it's OOP or a library, but because it's a great showcase of plain functions and loops applied to real math. Each technique below approximates something that would otherwise need calculus by hand, using nothing but arithmetic repeated many times.

    1 · Numerical derivative (forward difference)

    A derivative measures how fast a function is changing at a point. Instead of using calculus rules, we can approximate it by checking the function's value at a point, nudging that point by a tiny amount h, and seeing how much the output changed — exactly the definition of a slope, "rise over run," just computed numerically instead of symbolically.

    def derivative(f, x, h=1e-5):
    return (f(x + h) - f(x)) / h

derivative(lambda x: x**2, 3)   # ≈ 6.0  (exact: 2x = 6)

    2 · Trapezoidal integration

    Integration finds the area under a curve. The trapezoidal rule approximates that area by slicing the region into many thin trapezoids (rather than rectangles, for a closer fit to the curve) and adding up their areas — the more slices you use, the closer the approximation gets to the true value.

    import numpy as np

def trapz(f, a, b, n=1000):
    x = np.linspace(a, b, n + 1)
    y = f(x)
    h = (b - a) / n
    return h * (y[0]/2 + y[-1]/2 + y[1:-1].sum())

trapz(np.sin, 0, np.pi)   # ≈ 2.0   (exact value)
    Figure 6.1 · Geometric idea behind the trapezoidal rule

    3 · Solving an ODE — Euler & Runge–Kutta 4

    An ODE (ordinary differential equation) describes how something changes over time via its rate of change, like dy/dx = f(x, y), without directly telling you its value. These methods "walk forward" step by step from a known starting point, estimating the next value using the known rate of change at each step — Euler's method takes one straightforward step per interval, while Runge-Kutta 4 (RK4) samples the rate of change at four cleverly chosen points per interval and blends them for a far more accurate estimate.

    Solve dy/dx = f(x, y) step by step.

    # EULER (simple, less accurate)
def euler(f, x0, y0, x_end, h):
    xs, ys = [x0], [y0]
    while xs[-1] < x_end:
        x, y = xs[-1], ys[-1]
        ys.append(y + h * f(x, y))
        xs.append(x + h)
    return xs, ys

# RUNGE-KUTTA 4 (much more accurate)
def rk4_step(f, x, y, h):
    k1 = f(x,         y)
    k2 = f(x + h/2, y + h*k1/2)
    k3 = f(x + h/2, y + h*k2/2)
    k4 = f(x + h,   y + h*k3)
    return y + h/6 * (k1 + 2*k2 + 2*k3 + k4)

    🗃️ The collections Module

    Python's built-in list/dict handle 90% of everyday needs — the collections module covers the other 10% with specialized, purpose-built containers that solve one job extremely well, so you don't have to hand-roll that logic yourself.

    🧰
    Analogy: a plain list and dict are like a flat-head screwdriver — usable for almost everything in a pinch. The tools in collections are specialized bits: a Counter is a tally-counter clicker built purely for counting, a deque is a two-ended queue-line built for fast entry and exit from both sides. You could improvise these with a plain list, but the specialized tool does the job faster and with cleaner code.
    from collections import Counter, defaultdict, namedtuple, deque, OrderedDict

# Counter — frequency counting in one line
Counter("mississippi")   # Counter({'i': 4, 's': 4, 'p': 2, 'm': 1})

# defaultdict — never raises KeyError, auto-creates missing keys
groups = defaultdict(list)
groups["fruits"].append("apple")   # no need to check if key exists first

# namedtuple — lightweight, readable, immutable record
Point = namedtuple("Point", ["x", "y"])
p = Point(3, 4)
p.x, p.y   # 3, 4 — clearer than p[0], p[1]

# deque — O(1) appends/pops from BOTH ends (a list is O(n) on the left end)
dq = deque([1,2,3])
dq.appendleft(0); dq.pop()   # deque([0, 1, 2])

    Let's unpack each one in plain terms. Counter walks through anything iterable and tallies how many times each item appears — perfect for "what's the most common word/letter/item?" questions. defaultdict behaves exactly like a normal dictionary, except that accessing a missing key doesn't crash — it silently creates one using a factory function you provide (here, list, so a missing key becomes an empty list ready to append to). namedtuple creates a tiny, immutable class-like object where you access fields by name (p.x) instead of an easy-to-mistake numeric index (p[0]). deque ("deck," short for double-ended queue) is optimized so that adding or removing items from either end is fast, unlike a regular list where removing from the front is slow because every remaining item has to shift over.

    🏷️ dataclasses

    A modern, boilerplate-free way to create classes that mainly exist to hold data — it automatically writes the repetitive parts of a class (__init__, a readable __repr__, and value-based __eq__) for you, based only on the field names and types you declare.

    📋
    Analogy: writing a plain class by hand for a simple record is like filling out a form from a completely blank sheet of paper every time — you have to draw every line and label yourself. @dataclass is a pre-printed form: you just fill in the field names and types, and the boring structural work (the lines, the labels, the layout) is already done for you.
    from dataclasses import dataclass, field

@dataclass
class Student:
    name: str
    roll_no: int
    grades: list = field(default_factory=list)   # safe mutable default

s1 = Student("Meera", 7)
print(s1)   # Student(name='Meera', roll_no=7, grades=[])
s2 = Student("Meera", 7)
s1 == s2   # True — dataclass auto-compares field values

    Notice that grades uses field(default_factory=list) instead of simply = []. This connects back to the "mutable default argument" trap covered elsewhere in this course — a plain = [] default would be created only once and shared across every Student object, causing one student's grades to leak into another's. default_factory tells the dataclass to build a brand-new empty list for every single object instead.

    💡
    Compare this to writing the equivalent plain class: you'd need to hand-write __init__, __repr__, and __eq__ yourself. @dataclass generates all three.

    🎌 Enum — Named Constants

    An enum (short for "enumeration") lets you define a small, fixed set of named, related values as a single type — instead of scattering plain strings or numbers throughout your code, where a typo can silently break everything.

    from enum import Enum, auto

class Status(Enum):
    PENDING  = auto()
    APPROVED = auto()
    REJECTED = auto()

order_status = Status.PENDING
if order_status == Status.PENDING:
    print("Waiting for approval")

    Enums prevent the classic bug of comparing "magic strings" like status == "pendign" (note the typo) where Python would happily run the comparison and silently always evaluate to False — no error, just wrong behavior that's hard to spot. With an Enum, misspelling Status.PENDNIG raises an immediate, loud AttributeError instead of failing silently. auto() simply means "don't make me pick the actual number — just assign the next one automatically."

    🏗️ Type Hints & the typing Module

    Python stays dynamically typed at runtime — it never forces you to declare types — but type hints are optional annotations you can add to say "I intend this parameter to be a string" or "this function returns a list of floats." They don't change how the code runs; they exist so tools (and other humans reading your code) can catch mistakes before the code ever executes.

    🏷️
    Analogy: type hints are like labels on storage boxes when you're moving house. The box doesn't magically refuse to hold the wrong items — you could physically put a kitchen appliance into a box labeled "books." But the label lets you (and anyone helping you move) instantly spot a mistake by glancing at it, instead of opening every box to check.
    from typing import List, Dict, Optional, Union, Tuple

def average(nums: List[float]) -> float:
    return sum(nums) / len(nums)

def find_user(user_id: int) -> Optional[str]:
    return users.get(user_id)   # None if not found — Optional[str] means "str or None"

# Python 3.10+ shorthand (equivalent to Union / Optional)
def parse(val: int | str) -> bool | None:
    ...

    Reading def average(nums: List[float]) -> float: in plain English: "this function expects a list of floats as input, and promises to return a single float." Optional[str] is shorthand for "either a string, or specifically None" — a very common pattern for functions that might not find what they're looking for. Run mypy your_file.py to statically check these hints — most companies enforce this in CI pipelines.

    📌
    Type hints are not enforced at runtime by default — Python will still run average(["a","b"]) without complaint. They exist for tooling, IDEs, and static analyzers.

    🔍 Regular Expressions (re)

    A regular expression (regex) is a mini pattern-matching language for text — instead of describing exactly what characters to find, you describe the shape of what you're looking for (e.g. "a group of digits," "anything that looks like an email address"), and Python finds every place in a string that matches that shape.

    🔎
    Analogy: searching for an exact word in a document (like Ctrl+F for "cat") only finds that literal word. A regex is like telling a very literal-minded assistant "find me anything that looks like a phone number" — you describe the pattern (digits, dashes, a certain length) and it finds every match, whatever the actual numbers happen to be.
    import re

text = "Contact: raj@mail.com or 9876543210"

# search — find the first match anywhere in the string
email = re.search(r"[\w.]+@[\w.]+", text)
email.group()   # 'raj@mail.com'

# findall — every match as a list
re.findall(r"\d+", text)   # ['9876543210']

# sub — find & replace
re.sub(r"\d", "#", text)   # masks all digits

# compile once, reuse many times (faster in loops)
pattern = re.compile(r"^\d{3}-\d{4}$")
bool(pattern.match("123-4567"))   # True

    Every regex is built from small building blocks that each mean "match this kind of character." Once you know the handful below, you can read most patterns you'll ever encounter:

    SymbolMeaning
    \ddigit
    \wword character (letter/digit/underscore)
    \swhitespace
    + / *one-or-more / zero-or-more
    ^ / $start / end of string
    (...)capturing group
    |OR

    Reading r"^\d{3}-\d{4}$" piece by piece: ^ anchors to the very start of the string, \d{3} means "exactly 3 digits," - is a literal dash, \d{4} means "exactly 4 digits," and $ anchors to the very end — together, "the entire string must be exactly 3 digits, a dash, then 4 digits, nothing more and nothing less."

    🗓️ datetime & pathlib

    datetime represents points in time (and durations between them) as proper objects instead of plain strings, so you can safely do math on dates ("7 days from now") without manually handling how many days are in each month. pathlib represents file-system paths as objects instead of plain strings, so joining folders together works correctly on Windows, macOS, and Linux alike, without you worrying about forward slashes versus backslashes.

    from datetime import datetime, timedelta

now = datetime.now()

    Module 08

    Concurrency, Testing & Tooling

    This is the module that separates hobby scripts from production software: how Python actually runs multiple things "at once", how professionals prove their code works, and how projects are packaged and shipped.

    🔐 The GIL, in Plain Terms

    CPython (the standard Python interpreter almost everyone uses) has something called the Global Interpreter Lock (GIL): a rule that says only one thread can execute Python bytecode at any single instant, even if your computer has 8 or 16 CPU cores sitting idle.

    🎤
    Analogy: imagine a meeting room with one microphone and many people who want to speak (threads). Even if the room is huge and has plenty of empty space (multiple CPU cores), only the person holding the microphone can talk at any given moment — everyone else waits their turn. The GIL is that one microphone: it doesn't stop multiple threads from existing, but it stops more than one of them from running actual Python code simultaneously.
    📌
    This means threading does not speed up CPU-heavy work (math, loops), but it does help with I/O-heavy work (network calls, file reads) because the GIL is released while waiting on I/O — the "microphone" gets handed to someone else while the current speaker is just standing there waiting for a delivery, not actually talking.

    ⚔️ Threading vs Multiprocessing vs Asyncio

    These are three different strategies for doing multiple things "at once" in Python, and choosing the wrong one for your task is a common and costly mistake. The key question to ask yourself is: is my task waiting on something slow (I/O-bound), or is it doing heavy computation (CPU-bound)?

    ApproachGood forRuns in parallel on CPU?Overhead
    threadingI/O-bound (network, disk, DB calls)No (limited by GIL)Low
    multiprocessingCPU-bound (math, image processing)Yes — separate processes, separate GILsHigher (separate memory)
    asyncioMassive numbers of I/O tasks (thousands of network requests)No — single thread, cooperativeVery low

    threading creates multiple threads that take turns using the one "microphone" (the GIL) — great when most of the waiting is spent on something external, like a slow website responding, because threads can hand off control to each other during that wait. multiprocessing sidesteps the GIL entirely by launching completely separate Python processes, each with its own memory and its own GIL — genuinely running on multiple CPU cores at once, at the cost of more memory and slower communication between processes.

    # threading — good for many slow web requests
import threading

def download(url): print(f"downloading {url}")

threads = [threading.Thread(target=download, args=(u,)) for u in urls]
[t.start() for t in threads]
[t.join() for t in threads]   # wait for all to finish

# multiprocessing — good for CPU-heavy number crunching
from multiprocessing import Pool

def square(n): return n*n

with Pool(4) as pool:                 # 4 worker processes
    results = pool.map(square, range(10))

    t.start() tells a thread to begin running in the background; t.join() tells the main program "wait here until this thread has completely finished" — without join(), your program might move on and even exit before the threads finish their work.

    ⚡ asyncio in Practice

    asyncio is a third strategy: instead of using multiple threads or processes, a single thread juggles many tasks by voluntarily pausing at await points, letting other tasks run during that pause, and resuming later. This works beautifully when you have thousands of tasks that all spend most of their time waiting (like network requests), because a single thread can juggle far more waiting tasks than the operating system could ever schedule as separate threads.

    🍳
    Analogy: a chef cooking three dishes "at once" isn't literally stirring all three pots simultaneously — they start dish A, and while it simmers (waiting), they switch to chopping vegetables for dish B, then check on a pot for dish C, cycling between tasks whenever one is in a "waiting" state. One chef, no extra cooks hired, but far more gets done than cooking one dish start-to-finish before beginning the next.
    import asyncio

async def fetch_data(name, delay):
    print(f"start {name}")
    await asyncio.sleep(delay)     # non-blocking wait — other tasks run meanwhile
    print(f"done {name}")
    return name

async def main():
    # run three "downloads" concurrently instead of one after another
    results = await asyncio.gather(
        fetch_data("A", 2), fetch_data("B", 1), fetch_data("C", 3)
    )
    print(results)   # finishes in ~3s total, not 6s

asyncio.run(main())

    The keyword async marks a function as a "coroutine" — a function that's allowed to pause itself. await is the pause point: "start this slow operation, and let other coroutines run while we wait for it." asyncio.gather(...) launches all three fetch_data calls together and waits for every one of them to finish — since they overlap their waiting time instead of doing it one after another, the total time is roughly the longest single delay (3 seconds), not the sum of all three (6 seconds).

    💡
    async/await powers modern frameworks like FastAPI and libraries like aiohttp — essential if you're moving into backend/API work.

    🧪 Testing: unittest & pytest

    Automated testing means writing code that checks your other code actually works — so instead of manually running a script and eyeballing the output every time you make a change, you write it once and re-run it instantly, forever, to catch anything you accidentally broke.

    ✔️
    Analogy: think of tests as a pre-flight checklist a pilot runs before every single takeoff — not because they expect something to be wrong, but because running the same checklist every time catches problems before they become disasters, and it takes far less effort than re-deriving from scratch whether the plane is safe to fly.
    # unittest — built into Python, no install needed
import unittest

def add(a, b): return a + b

class TestMath(unittest.TestCase):
    def test_add(self):
        self.assertEqual(add(2, 3), 5)

if __name__ == "__main__":
    unittest.main()

# pytest — the industry standard; simpler syntax, plain asserts
def test_add():
    assert add(2, 3) == 5

# run with:  pytest test_math.py  -v

    Both examples above say the exact same thing: "call add(2, 3), and if the result isn't 5, this test has failed." unittest wraps this in a class and uses methods like assertEqual; pytest lets you write it as a plain function with a plain assert statement — most teams today prefer pytest for exactly this simplicity. Fixtures (pytest) share reusable setup code across tests (e.g. "create a fresh database connection before every test"); mocking (unittest.mock) fakes external dependencies like APIs or databases so tests stay fast, isolated, and don't depend on a real network connection or server being available.

    🪵 Logging & Debugging

    Logging is how a running program records what it's doing, so you (or another developer) can look back later and understand what happened — especially important once code is running on a server somewhere you can't watch directly. Debugging tools let you pause a running program mid-execution and inspect exactly what its variables contain at that moment.

    import logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
logging.info("Server started")
logging.warning("Disk space low")
logging.error("Failed to connect to DB")

    The severity levels (INFO, WARNING, ERROR, and others like DEBUG/CRITICAL) let you set a threshold — for example, showing only warnings and errors in production while showing everything during development — without touching a single line of the logging calls themselves.

    ⚠️
    Use logging instead of print() in real applications — it supports severity levels, timestamps, and can be redirected to files without touching your code.
    # Dropping into an interactive debugger at a specific line
import pdb
pdb.set_trace()   # execution pauses here; type 'n' (next), 'c' (continue), 'p var' (print)

    Think of pdb.set_trace() as placing a bookmark in your running program. The instant execution reaches that line, everything freezes, and you get an interactive prompt right there — you can type a variable's name to see its current value, step forward one line at a time with n, or let it continue running normally with c. This is far more powerful than scattering print() statements everywhere and re-running the whole program each time.

    📦 Virtual Environments, pip & Packaging

    A virtual environment is an isolated, self-contained copy of Python and its installed packages, kept separate for each project — so Project A can use version 1.0 of a library while Project B uses version 2.0, without the two ever conflicting on the same machine.

    🧴
    Analogy: imagine sharing one bathroom cabinet between every project you've ever worked on — eventually two projects need a different strength of the same medicine, and you can only have one bottle on the shelf. A virtual environment gives every project its own private cabinet, so each can stock exactly the versions it needs without disturbing anyone else's.

Follow PEP 8 (Python's official style guide) for naming, spacing, and layout — tools like black (auto-formatter) and flake8 / ruff (linters) enforce it automatically.

    🌐 Consuming REST APIs with requests

    Much of the modern internet works by one program asking another program for data over HTTP (the same protocol your browser uses to load web pages), and getting back a structured answer instead of a rendered page. This pattern is called a REST API, and the requests library is how Python programs speak that language.

    🍽️
    Analogy: think of an API like a restaurant menu and a waiter. You (your program) don't walk into the kitchen and cook the food yourself — you tell the waiter (the API) exactly what you want using the menu's language (a URL and some parameters), and the waiter brings back a specific, structured response (the data). A GET request is like asking "what's on the menu" or "bring me dish #4"; a POST request is like submitting a new order for the kitchen to create something.
    import requests

resp = requests.get("https://api.github.com/users/python")
resp.status_code        # 200
data = resp.json()          # parses JSON response into a dict
data["public_repos"]

# POST with a JSON body and headers
resp = requests.post(
    "https://api.example.com/users",
    json={"name": "Asha", "age": 28},
    headers={"Authorization": f"Bearer {token}"}
)

    status_code is the server's short numeric verdict on how your request went — 200 means success, codes starting with 4 (like 404) mean something was wrong with your request, and codes starting with 5 mean the server itself had a problem. headers carry extra metadata alongside the actual request — here, an Authorization header proves who you are, similar to showing an ID card before being allowed to place an order.

    🧾 JSON in Depth

    JSON (JavaScript Object Notation) is the universal text format almost every API uses to send structured data — it looks strikingly similar to a Python dict/list, which is exactly why converting between the two is so simple.

    import json

data = {"name": "Asha", "skills": ["Python", "SQL"]}

text = json.dumps(data, indent=2)   # dict -> JSON string (pretty-printed)
back = json.loads(text)          # JSON string -> dict

with open("data.json", "w") as f:
    json.dump(data, f)              # write dict straight to a file

    A simple memory aid: "s" is for string — dumps ("dump string") converts a Python object into a JSON string, and loads ("load string") converts a JSON string back into a Python object. The plain dump/load (without the "s") do the same conversion but write directly to, or read directly from, an open file instead of an in-memory string.

    🍶 Building an API with Flask

    So far you've been the one calling an API. Now flip the picture: Flask lets your own Python code become the "waiter" — receiving requests from other programs (or a browser) and deciding how to respond.

    from flask import Flask, jsonify, request

app = Flask(__name__)
books = [{"id": 1, "title": "Fluent Python"}]

@app.route("/books", methods=["GET"])
def get_books():
    return jsonify(books)

@app.route("/books", methods=["POST"])
def add_book():
    new_book = request.get_json()
    books.append(new_book)
    return jsonify(new_book), 201

if __name__ == "__main__":
    app.run(debug=True)

    @app.route("/books", methods=["GET"]) means "whenever someone visits the web address /books using a GET request, run the function right below this line." jsonify(books) converts the Python list into a proper JSON HTTP response — the same format the requests library on the other end expects to receive. The 201 returned alongside the new book is the standard HTTP status code for "successfully created."

    📌
    For new production APIs, most teams now reach for FastAPI instead of Flask — same idea, but built-in type validation and automatic interactive docs.

    🗄️ SQLite from Python

    A database stores data permanently on disk in an organized, searchable way — unlike a Python list or dict, which disappears the instant your program stops running. SQLite is a lightweight, file-based database that needs no separate server to install — the entire database lives in one file — making it perfect for learning and small applications.

    import sqlite3

conn = sqlite3.connect("school.db")
cur = conn.cursor()

cur.execute("""CREATE TABLE IF NOT EXISTS students
                (id INTEGER PRIMARY KEY, name TEXT, grade INTEGER)""")

# Always use "?" placeholders — never f-strings — to prevent SQL injection
cur.execute("INSERT INTO students (name, grade) VALUES (?, ?)", ("Ravi", 9))
conn.commit()

cur.execute("SELECT * FROM students WHERE grade > ?", (5,))
print(cur.fetchall())
conn.close()

    conn (the connection) is your open line to the database file; cur (the cursor) is what actually runs SQL commands and reads back results, similar to the difference between dialing a phone line and actually speaking through it. conn.commit() permanently saves your changes to disk — without it, an insert can be silently rolled back and lost. The ? placeholders let the database library safely insert your Python values into the query without ever treating user-provided text as part of the SQL command itself.

    ⚠️
    Never build SQL with f-strings/%/+ from user input — that's the #1 cause of SQL-injection vulnerabilities. Always use parameterized ? placeholders.

    🕷️ Web Scraping Basics

    Not every website offers a clean API — sometimes the only way to get data is to download the page's raw HTML and pick out the pieces you need. Web scraping automates that "reading the page and copying the relevant bits" process.

    import requests
from bs4 import BeautifulSoup

html = requests.get("https://example.com").text
soup = BeautifulSoup(html, "html.parser")

title = soup.find("h1").text
links = [a["href"] for a in soup.find_all("a")]

    requests.get(...).text downloads the page's raw HTML as one long string — exactly what your browser receives before it gets rendered visually. BeautifulSoup then parses that raw text into a navigable structure, so instead of manually searching through HTML tags with string operations, you can ask for things like "find the first <h1> tag" or "find every <a> link" directly. Always check a site's robots.txt and terms of service before scraping — and prefer an official API when one exists.

    🔢 NumPy data science

    The foundation of numerical computing in Python — fast array operations, vectorized math, no manual loops. NumPy's core object is the array, which looks like a Python list but is actually stored in memory far more efficiently and lets you apply an operation to every element at once instead of writing a for loop.

    🏭
    Analogy: a plain Python list processes items the way one person manually stamps documents one at a time. A NumPy array processes items the way an assembly line stamps a thousand documents simultaneously with one press of the machine — "vectorized" simply means "apply this operation to the whole batch at once," which is both far less code to write and dramatically faster to run.

    Example 1 · Array basics & vectorized math

    import numpy as np

arr = np.array([1, 2, 3, 4, 5])
arr * 2            # [2, 4, 6, 8, 10] — no loop needed
arr.mean(), arr.std()   # 3.0, ≈1.41
arr[arr > 2]        # boolean mask -> [3, 4, 5]

    Compare arr * 2 to the plain-Python equivalent, [x * 2 for x in my_list] — NumPy lets you drop the loop entirely and just say "multiply the whole array by 2." The last line, arr[arr > 2], is called "boolean masking": arr > 2 first produces an array of True/False values, and using that as an index keeps only the items where it was True — a very common, very readable filtering pattern in data work.

    Example 2 · 2D arrays & matrix operations

    grid = np.array([[1,2],[3,4]])
grid.T                       # transpose
grid @ grid                   # matrix multiplication
np.linspace(0, 1, 5)         # [0., 0.25, 0.5, 0.75, 1.] — 5 evenly spaced points

    A 2D array is just a grid of numbers, like a spreadsheet without labels — rows and columns. .T flips rows into columns (the transpose); @ performs true matrix multiplication (the mathematical operation, not element-by-element multiplying); linspace ("linearly spaced") generates a fixed number of evenly spaced values between two bounds, extremely useful for plotting smooth curves.

    🐼 Pandas data science

    The standard library for tabular data — think "Excel spreadsheet, but programmable." Its core object, the DataFrame, is a table with labeled rows and columns that you can filter, sort, group, and reshape using code instead of clicking around a spreadsheet UI.

    📊
    Analogy: if NumPy is a calculator built for raw numbers, Pandas is a spreadsheet application built on top of that calculator — it adds row/column labels, lets you mix data types across columns (names, dates, numbers together), and gives you spreadsheet-like operations (filter, sort, pivot) as one-line commands instead of mouse clicks.

    Example 1 · Building & filtering a DataFrame

    import pandas as pd

df = pd.DataFrame({
    "name": ["Asha", "Ravi", "Zoe"],
    "marks": [88, 72, 95]
})
df[df["marks"] > 80]          # filter rows — Asha and Zoe
df.sort_values("marks", ascending=False)

    Here, df["marks"] pulls out a single column as a Series (a labeled 1D array); comparing it with > 80 gives the same boolean masking trick from NumPy above, and using that as a row filter keeps only the rows where the condition was True — reading almost like plain English: "give me the rows where marks is greater than 80."

    Example 2 · Reading CSV & group-by aggregation

    df = pd.read_csv("sales.csv")          # load a file straight into a table
df.groupby("region")["revenue"].sum()   # total revenue per region
df.to_csv("summary.csv", index=False)   # write results back out

    groupby("region") is the same idea as an Excel pivot table: "split all rows into buckets by their region value, then compute something (here, the sum of revenue) separately within each bucket." This one line replaces what would otherwise be many lines of manual looping and bucketing logic.

    📈 Matplotlib data science

    🌐 Requests web / http

    The de-facto standard for talking HTTP from Python — see the detailed walkthrough of GET/POST and status codes in the Web, APIs & Databases module. Here are two more patterns you'll use constantly in real projects.

    Example 1 · GET request & parsing JSON

    import requests

r = requests.get("https://api.github.com/users/python", timeout=5)
r.raise_for_status()      # throws if status is 4xx/5xx
r.json()["public_repos"]

    timeout=5 tells Python "don't wait forever if the server never responds — give up after 5 seconds," which prevents your program from freezing indefinitely on a dead connection. raise_for_status() is a safety check: instead of silently continuing with a failed request, it immediately raises an error the moment something went wrong (like a 404 or 500), so bugs surface loudly instead of causing confusing behavior later.

    Example 2 · POST with auth headers & query params

    r = requests.post(
    "https://api.example.com/orders",
    params={"store": "HYD01"},
    json={"item": "laptop", "qty": 2},
    headers={"Authorization": f"Bearer {TOKEN}"}
)

    params get appended to the URL itself (like ?store=HYD01) — typically used for filtering or identifying what you're asking for. json is the actual data payload being submitted, sent in the request's body rather than the URL. Keeping these separate mirrors how a real order form works: some info identifies "which store's system you're talking to," while other info is "the actual order being placed."

    🗄️ SQLAlchemy database / ORM

    Lets you work with databases using Python classes and objects instead of raw SQL strings. "ORM" stands for Object-Relational Mapper — it maps ("translates between") Python objects and rows in a relational database table, letting you manipulate database data the same way you'd manipulate any other Python object.

    Example 1 · Defining a model & creating a table

    from sqlalchemy import create_engine, Column, Integer, String
from sqlalchemy.orm import declarative_base

Base = declarative_base()

class User(Base):
    __tablename__ = "users"
    id   = Column(Integer, primary_key=True)
    name = Column(String)

engine = create_engine("sqlite:///app.db")
Base.metadata.create_all(engine)

    This is the same "class inheriting shared setup" pattern from the OOP module — every model inherits from Base, which is what allows SQLAlchemy to recognize it as a table definition. create_engine("sqlite:///app.db") establishes the connection to a specific database file, and create_all actually builds the real table if it doesn't already exist.

    Example 2 · Inserting & querying with a session

    from sqlalchemy.orm import Session

with Session(engine) as session:
    session.add(User(name="Meera"))
    session.commit()
    users = session.query(User).filter(User.name == "Meera").all()

    Notice that the with Session(engine) as session: line is a context manager, exactly like the ones covered in the Advanced Language module — it guarantees the database session is properly closed once the block ends. session.add(...) stages a new row for insertion, commit() permanently saves it, and query(User).filter(...) builds a search — all expressed as plain Python method calls instead of hand-written SQL strings.

    🕷️ BeautifulSoup automation / scraping

    Parses HTML/XML so you can pull structured data out of a web page. A raw web page is just a giant string of text with angle-bracket tags — BeautifulSoup reads that string and turns it into a navigable tree structure you can search through, instead of manually hunting for substrings.

    Example 1 · Extracting a page title & all links

    import requests
from bs4 import BeautifulSoup

soup = BeautifulSoup(requests.get("https://example.com").text, "html.parser")
soup.title.string
[a["href"] for a in soup.find_all("a", href=True)]

    This combines two libraries you've now met: requests fetches the raw page, and BeautifulSoup parses it. Once parsed into soup, you can navigate it almost like a Python object — soup.title jumps straight to the page's <title> tag, and find_all("a", href=True) collects every link tag that actually has an href attribute, feeding neatly into the list comprehension you already know.

    Example 2 · Pulling rows out of an HTML table

    table = soup.find("table", {"id": "prices"})
rows = []
for tr in table.find_all("tr")[1:]:      # skip header row
    cells = [td.text.strip() for td in tr.find_all("td")]
    rows.append(cells)

    find("table", {"id": "prices"}) narrows the search to one specific table by its HTML id attribute, and [1:] skips the first row (typically the header, like "Name," "Price") since it's usually not real data. This turns a messy web page into a clean list of lists — exactly the kind of structured data you'd feed into a Pandas DataFrame from earlier in this module.

    🧪 Pytest testing

    The industry-standard testing framework — plain assert, powerful fixtures, huge plugin ecosystem. Building on the testing concepts from the Concurrency & Tooling module, these two examples show the patterns that make pytest the default choice on real teams.

    Example 1 · A basic test function

    def add(a, b): return a + b

def test_add_positive_numbers():
    assert add(2, 3) == 5

# terminal: pytest -v

    pytest automatically discovers any function whose name starts with test_ in files named test_*.py — no registration or setup needed, it just finds and runs them. Running pytest -v ("verbose") lists every test individually with a pass/fail result, rather than one silent summary line.

    Example 2 · Fixtures & parametrized tests

    import pytest

@pytest.fixture
def sample_list():
    return [3, 1, 2]

@pytest.mark.parametrize("n, expected", [(2,4), (3,9), (4,16)])
def test_square(n, expected):
    assert n**2 == expected   # runs 3 times, once per pair

    A fixture is reusable setup code: any test function that accepts sample_list as a parameter automatically receives a fresh [3, 1, 2] without needing to recreate it manually every time. @pytest.mark.parametrize runs the exact same test logic multiple times with different input/expected-output pairs — instead of copy-pasting the same test three times with different numbers, you write the test once and supply a table of cases to check it against.

    🖱️ Tkinter gui

    Python's built-in GUI toolkit — no install required, good for internal tools and small desktop apps. A GUI (graphical user interface) program works fundamentally differently from the scripts you've written so far: instead of running top-to-bottom once, it sits idle waiting for user actions (clicks, typing), then reacts.

    Example 1 · A window with a label

    import tkinter as tk

root = tk.Tk()
root.title("My App")
tk.Label(root, text="Hello, Tkinter!", font=("Arial",14)).pack(pady=20)
root.mainloop()

    root represents the main application window itself. Widgets like Label are created "inside" root and then placed on screen with .pack() (one of several layout methods). root.mainloop() is the crucial last line — it starts an infinite loop that keeps the window open and listening for events; without it, the window would flash open and close instantly.

    Example 2 · Button click updates the UI

    count = tk.IntVar(value=0)

def increment():
    count.set(count.get() + 1)

tk.Label(root, textvariable=count).pack()
tk.Button(root, text="+1", command=increment).pack()

    This is event-driven programming: nothing runs the increment function until the user actually clicks the button — you register it as the command, and Tkinter calls it automatically at click time. IntVar is a special Tkinter variable that, when changed with .set(), automatically refreshes any widget displaying it (like the connected Label) — a simple built-in version of the "state updates the UI" pattern used throughout modern app development.

    🤖 Selenium automation

    Drives a real web browser programmatically — used for browser automation and end-to-end UI testing. Unlike Requests/BeautifulSoup (which only see raw HTML), Selenium controls an actual browser window, so it can interact with pages that build their content dynamically using JavaScript.

    Example 1 · Open a page & read its title

    from selenium import webdriver

driver = webdriver.Chrome()
driver.get("https://example.com")
print(driver.title)
driver.quit()

    webdriver.Chrome() literally opens a real, controllable Chrome browser window that your script now has full remote control over. driver.quit() closes it again — always call this when you're done, or leftover browser processes pile up and consume memory.

    Example 2 · Find an element, type, and click

    from selenium.webdriver.common.by import By

search_box = driver.find_element(By.NAME, "q")
search_box.send_keys("python tutorials")
driver.find_element(By.NAME, "btnK").click()

    find_element(By.NAME, "q") locates a specific element on the page — here, one with the HTML attribute name="q" (Google's actual search box). send_keys(...) simulates real keyboard typing into it, and .click() simulates an actual mouse click — this script is literally performing the same physical actions a human would, just automated.

    Frameworks — End to End

    A framework is different from a library: a library is a tool you call from your code, but a framework provides the skeleton of an entire application and calls your code at the right moments — you build inside its structure. This tab walks all three major Python web frameworks — Django, Flask, and FastAPI — end to end: from project setup through routing, data, templates, validation, auth, and deployment, so you can see the full lifecycle of a real application in each, not just an isolated snippet.

    🎸 Django · Philosophy & Architecture

    Django calls itself "the web framework for perfectionists with deadlines." Its philosophy is batteries-included: a database layer, an admin panel, a user authentication system, a templating engine, and form handling all ship together and are designed to work as one coherent system, instead of you assembling them yourself from separate libraries.

    🏢
    Analogy: building a website with Django is like moving into a fully furnished, code-compliant apartment building — plumbing, wiring, and a management office (the admin panel) are already in place and follow a consistent standard. You get productive fast, but you work within the building's existing layout rather than designing every wall from scratch.

    Django follows an architecture it calls MTV (Model-Template-View) — a close cousin of the more famous MVC (Model-View-Controller) pattern you may have heard of elsewhere:

    Django termRoleRoughly equivalent to
    ModelDefines your data shape and talks to the databaseMVC's "Model"
    TemplateDefines what the user actually sees (HTML with placeholders)MVC's "View"
    ViewThe Python function/class that receives a request, talks to Models, and picks a TemplateMVC's "Controller"

    A project in Django is the whole website; an app is a self-contained module inside it (e.g. a "blog" app, a "shop" app) that can, in principle, be reused across different projects. This is Django applying the same "break large things into smaller reusable pieces" principle you learned with functions and classes, just at the scale of an entire website.

    🏗️ Django · Project & App Setup

    Every Django site starts the same way: create a project, then create one or more apps inside it.

    pip install django
django-admin startproject mysite       # creates the overall project skeleton
cd mysite
python manage.py startapp blog       # creates a self-contained "blog" app inside it
python manage.py runserver            # starts the local dev server at 127.0.0.1:8000

    manage.py is the command center for the entire project — nearly every Django task (running the server, creating database tables, creating an admin user) goes through it. After creating the blog app, you register it by adding "blog" to the INSTALLED_APPS list inside mysite/settings.py — this is the step that tells Django "this app's models, templates, and admin registrations should actually be included."

    📌
    settings.py is the project's central configuration file — database connection details, installed apps, security keys, allowed hosts, and more all live here in one place.

    🔗 Django · URLs & Routing

    Django uses a dedicated urls.py file to map URL patterns to view functions — kept deliberately separate from the view logic itself, so you can see your entire site's structure by reading one file.

    # blog/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("", views.post_list, name="post_list"),
    path("post/<int:pk>/", views.post_detail, name="post_detail"),
]

# mysite/urls.py (project-level — includes each app's URLs)
from django.urls import path, include

urlpatterns = [
    path("blog/", include("blog.urls")),
    path("admin/", admin.site.urls),
]

    <int:pk> is a URL converter — exactly like the Flask/FastAPI path parameters you may have already seen, it captures a segment of the URL, converts it to an integer, and passes it into the view function as the argument pk (short for "primary key"). The name="post_detail" argument lets templates and other code refer to this URL by a stable name instead of hardcoding the path string — so if you later change the URL structure, every reference updates automatically.

    👁️ Django · Views

    A view is the Python function (or class) that actually handles a request — it receives the incoming request, does whatever work is needed (usually querying Models), and returns a response, typically by rendering a Template.

    # blog/views.py — function-based view
from django.shortcuts import render, get_object_or_404
from .models import Post

def post_list(request):
    posts = Post.objects.order_by("-published")
    return render(request, "blog/post_list.html", {"posts": posts})

def post_detail(request, pk):
    post = get_object_or_404(Post, pk=pk)
    return render(request, "blog/post_detail.html", {"post": post})

# Class-based equivalent — Django provides ready-made generic views
from django.views.generic import ListView

class PostListView(ListView):
    model = Post
    template_name = "blog/post_list.html"

    render(request, template_name, context_dict) is the standard pattern: it takes the current request, a template file, and a dictionary of data to inject into that template, and returns the finished HTML response. get_object_or_404 is a convenience shortcut that fetches a database row or automatically returns a proper "404 Not Found" page instead of crashing if it doesn't exist. Class-based views like ListView exist because "fetch a list of objects and render a template" is such a common pattern that Django provides it pre-built — you only override what's different.

    🗄️ Django · Models & the ORM

    A Model is a Python class that describes one kind of data your app stores, and Django's ORM (Object-Relational Mapper) automatically turns it into a real database table — you never hand-write the CREATE TABLE SQL yourself.

    # blog/models.py
from django.db import models
from django.contrib.auth.models import User

class Post(models.Model):
    title     = models.CharField(max_length=200)
    body      = models.TextField()
    published = models.DateTimeField(auto_now_add=True)
    author    = models.ForeignKey(User, on_delete=models.CASCADE)   # many posts -> one user

    def __str__(self):
        return self.title

# Common ORM queries, no SQL written by hand
Post.objects.all()                              # every post
Post.objects.filter(author=request.user)         # WHERE author_id = ...
Post.objects.get(pk=1)                          # single row, errors if not found or duplicated
Post.objects.create(title="Hi", body="...", author=u)   # INSERT

    ForeignKey establishes a relationship between two Models — here, "each Post belongs to exactly one User, and a User can have many Posts." on_delete=models.CASCADE tells Django what to do if that User is deleted: cascade the deletion to their posts too. Every one of these ORM method calls (.filter(), .get(), .create()) is translated by Django into real SQL behind the scenes, but you interact with it entirely through Python objects and methods.

    🔄 Django · Migrations

    Migrations are how Django keeps your actual database structure in sync with your Model classes as they evolve over time — every time you change a Model, you generate a migration file describing that change, then apply it.

    python manage.py makemigrations blog   # "I changed a Model — write the plan for how to update the DB"
python manage.py migrate              # "Now actually apply that plan to the database"

    Think of each migration file as a numbered, saved diff of your database schema — this gives you a full history of every structural change ever made, and lets a teammate (or a production server) apply the exact same sequence of changes to get an identical database structure, without ever writing SQL by hand.

    🖼️ Django · Templates

    A Django template is an HTML file with special placeholder syntax that gets filled in with real data at render time — this is the "V" (visual output) in Django's MTV pattern.

    <!-- blog/templates/blog/post_list.html -->
<h1>Blog</h1>
{% for post in posts %}
  <h2><a href="{% url 'post_detail' post.pk %}">{{ post.title }}</a></h2>
  <p>{{ post.published|date:"d M Y" }}</p>
{% endfor %}

    {{ post.title }} (double curly braces) outputs a value; {% for %}/{% endfor %} (curly-brace-percent) are template tags that control logic, like loops and conditionals — deliberately kept simpler than full Python so designers without deep programming knowledge can still edit templates safely. {% url 'post_detail' post.pk %} generates the correct URL by name (from the urls.py you defined earlier) rather than hardcoding the path. The pipe symbol in |date:"d M Y" applies a filter — a small transformation applied to a value before it's displayed, here formatting a raw datetime into a readable date string.

    📝 Django · Forms & Validation

    Django's forms module handles displaying an HTML form, validating submitted data, and showing errors back to the user — all from a single Python class definition, similar in spirit to how a @dataclass or Pydantic model declares a data shape.

    # blog/forms.py
from django import forms
from .models import Post

class PostForm(forms.ModelForm):
    class Meta:
        model = Post
        fields = ["title", "body"]

# In the view
def new_post(request):
    if request.method == "POST":
        form = PostForm(request.POST)
        if form.is_valid():
            post = form.save(commit=False)
            post.author = request.user
            post.save()
    else:
        form = PostForm()
    return render(request, "blog/new_post.html", {"form": form})

    A ModelForm automatically generates form fields directly from a Model's fields, so you rarely have to duplicate field definitions. The pattern "if this is a POST request, validate and save; otherwise show a blank form" is the standard shape of nearly every form-handling view you'll ever write in Django. form.is_valid() runs all validation (required fields, correct types, custom rules) and returns False with helpful error messages attached if anything's wrong — very similar in purpose to FastAPI's Pydantic validation, just applied to HTML form submissions instead of JSON.

    🛠️ Django · Admin Panel

    One of Django's signature features: a fully working, ready-to-use admin website for managing your data, generated automatically from your Models with almost no extra code.

    # blog/admin.py
from django.contrib import admin
from .models import Post

admin.site.register(Post)

# Create a superuser to log in with
python manage.py createsuperuser

    That single register call is enough to get a full create/read/update/delete interface for the Post model at /admin/ — list views, edit forms, search, and filtering all generated for you. This is often the fastest way to start populating and testing a Django app's data before any of your own templates are even built.

    🔐 Django · Authentication & Sessions

    Django ships with a complete user authentication system out of the box — user accounts, password hashing, login/logout views, and permission checks are all already built and battle-tested, so you don't build your own (famously easy to get wrong) login system from scratch.

    from django.contrib.auth.decorators import login_required

@login_required
def new_post(request):
    ...   # only reachable by logged-in users; others are redirected to login

# checking the current user anywhere in a view
if request.user.is_authenticated:
    print(request.user.username)

    @login_required is another decorator — the same concept from the Advanced Language module — that wraps a view function to check authentication before letting the real function run. Behind the scenes, Django tracks a logged-in user through a session, a small piece of server-side state tied to a cookie in the user's browser, so the server remembers who's making each request without the client having to resend credentials every time.

    🚀 Django · Static Files & Deployment

    Static files (CSS, JavaScript, images) are served separately from your dynamic Python code. During development Django serves them for you automatically; in production, a dedicated web server (like Nginx) or a cloud storage service typically takes over that job for better performance.

    # settings.py
STATIC_URL = "static/"

# template
{% load static %}
<link rel="stylesheet" href="{% static 'blog/style.css' %}">

# Before going live
python manage.py collectstatic   # gathers every app's static files into one folder
# DEBUG = False, set ALLOWED_HOSTS, use a real database (e.g. PostgreSQL) instead of SQLite

    A typical production Django deployment replaces the built-in dev server with a dedicated WSGI application server (like Gunicorn), sitting behind a reverse proxy (like Nginx) that also serves static files directly — the dev server used with runserver is explicitly not designed to handle real production traffic safely or efficiently.

    🍶 Flask · Philosophy & Setup

    Flask calls itself a microframework — "micro" refers to a small, simple core, not to limited capability. Flask deliberately ships with almost nothing beyond routing and request/response handling, and lets you pick exactly which extensions to add (a database layer, forms, login handling) as your project actually needs them.

    🧱
    Analogy: if Django is a furnished apartment, Flask is an empty plot of land with solid utilities already connected (water, electricity) — you decide exactly what to build and where. This gives more freedom and a gentler learning curve for small projects, at the cost of having to make more architectural decisions yourself as the project grows.
    pip install flask
    # app.py
from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello, Flask!"

if __name__ == "__main__":
    app.run(debug=True)   # python app.py

    Unlike Django, there's no mandatory project-generation command — a single Python file is a complete, runnable Flask application. This is exactly the tradeoff of "micro": faster to start, but you'll add structure (multiple files, folders) yourself as the app grows, rather than Django scaffolding it for you upfront.

    🔗 Flask · Routing & Requests

    Routing in Flask is defined right next to the function that handles it (unlike Django's separate urls.py) using the @app.route decorator — a single, direct mapping from a URL pattern to a Python function.

    from flask import Flask, request, jsonify

app = Flask(__name__)
posts = []

@app.route("/posts/<int:post_id>")
def get_post(post_id):
    return jsonify(posts[post_id])

@app.route("/posts", methods=["GET", "POST"])
def posts_view():
    if request.method == "POST":
        data = request.get_json()          # parsed JSON body
        posts.append(data)
        return jsonify(data), 201
    search = request.args.get("q", "")     # query string ?q=... , with default
    return jsonify([p for p in posts if search in p["title"]])

    The global request object automatically represents whatever the current incoming request is — request.method tells you GET vs POST, request.get_json() parses a JSON body, and request.args is a dict-like object for URL query parameters (the part after ?). One function handling multiple HTTP methods on the same URL, branching on request.method, is a very common Flask pattern.

    🖼️ Flask · Templates (Jinja2)

    Flask uses the Jinja2 templating engine, which will look immediately familiar after Django templates — the syntax is nearly identical since Jinja2 was directly inspired by it.

    # templates/posts.html
<h1>Posts</h1>
<ul>
{% for post in posts %}
  <li>{{ post.title }} — by {{ post.author | upper }}</li>
{% endfor %}
</ul>
    from flask import render_template

@app.route("/posts-page")
def posts_page():
    return render_template("posts.html", posts=posts)   # looks inside templates/ by default

    render_template is Flask's equivalent of Django's render — it fills a Jinja2 template with the keyword arguments you pass in (here, posts=posts makes the variable posts available inside the template). Flask automatically escapes any HTML in your data to prevent security issues like cross-site scripting, unless you explicitly mark content as safe.

    📝 Flask · Forms & Flask-WTF

    Flask's core doesn't include form handling — the popular extension Flask-WTF (built on the WTForms library) adds Django-style form classes with built-in validation.

    pip install flask-wtf
    from flask_wtf import FlaskForm
from wtforms import StringField, TextAreaField
from wtforms.validators import DataRequired

class PostForm(FlaskForm):
    title = StringField("Title", validators=[DataRequired()])
    body  = TextAreaField("Body", validators=[DataRequired()])

@app.route("/new", methods=["GET", "POST"])
def new_post():
    form = PostForm()
    if form.validate_on_submit():        # True only on a valid POST
        posts.append({"title": form.title.data, "body": form.body.data})
        return "Saved!"
    return render_template("new_post.html", form=form)

    validate_on_submit() conveniently combines two checks into one: "was this actually a POST request, and did all the fields pass their validators?" This mirrors the same "validate, then act" shape you saw in Django forms and FastAPI's Pydantic models — three different frameworks, the same underlying principle of never trusting raw incoming data until it's checked.

    🗄️ Flask · Database (Flask-SQLAlchemy)

    Flask has no built-in ORM. The most common choice is Flask-SQLAlchemy, a thin wrapper around the SQLAlchemy library you already learned, adapted to integrate cleanly with a Flask app.

    pip install flask-sqlalchemy
    from flask_sqlalchemy import SQLAlchemy

app.config["SQLALCHEMY_DATABASE_URI"] = "sqlite:///blog.db"
db = SQLAlchemy(app)

class Post(db.Model):
    id    = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200))

with app.app_context():
    db.create_all()   # creates tables for all defined models

# Usage
db.session.add(Post(title="Hi"))
db.session.commit()
Post.query.filter_by(title="Hi").first()

    Notice how closely this parallels Django's Models and the standalone SQLAlchemy you learned earlier — the same underlying idea (a Python class maps to a database table) appears in all three, just with slightly different syntax for defining columns and running queries. app_context() is a Flask-specific requirement: certain operations, like touching the database, need to know which app configuration they belong to, since a single Python process could technically run multiple Flask apps.

    🧩 Flask · Blueprints & Larger Apps

    As a Flask app grows beyond one file, Blueprints let you split routes into logical, reusable groups — Flask's answer to Django's "apps" concept, though more lightweight and optional.

    # blog/routes.py
from flask import Blueprint

blog_bp = Blueprint("blog", __name__, url_prefix="/blog")

@blog_bp.route("/")
def index():
    return "Blog home"

# app.py
from blog.routes import blog_bp
app.register_blueprint(blog_bp)   # now reachable at /blog/

    A Blueprint behaves like a mini Flask app that gets "plugged into" the main app — its routes aren't active until register_blueprint is called. This lets separate features (blog, shop, admin) live in separate files or even separate importable packages, keeping large projects organized the same way multiple Django apps do inside one project.

    🚀 Flask · Sessions, Errors & Deployment

    Flask provides a simple built-in session object for storing small bits of data per-user across requests (like "is this user logged in"), and lets you customize how errors are displayed.

    from flask import session

app.secret_key = "change-this-in-production"   # required to sign session cookies

@app.route("/login")
def login():
    session["user"] = "asha"
    return "Logged in"

@app.errorhandler(404)
def not_found(e):
    return render_template("404.html"), 404

    secret_key is used to cryptographically sign the session cookie so users can't tamper with their own session data. @app.errorhandler(404) lets you replace Flask's plain default error page with your own styled template — the same idea as a custom "Page Not Found" page on any real website. For deployment, exactly like Django, the built-in dev server (app.run()) is not meant for production; a real deployment uses a WSGI server such as Gunicorn behind Nginx.

    🚀 FastAPI · Philosophy & Setup

    FastAPI is the newest of the three, built specifically around Python's type hints and async/await. Its core philosophy: your function's type hints aren't just documentation — FastAPI actively reads them to validate data, generate interactive documentation, and provide editor autocompletion, all from the same declaration.

    📐
    Analogy: Flask and Django ask you to describe your data shape somewhat separately from your function signatures (a form class, a model class). FastAPI merges the two — the function signature itself, using ordinary Python type hints, is the specification. Write the type once, and get validation, docs, and editor support for free, instead of maintaining three things that need to stay in sync.
    pip install fastapi "uvicorn[standard]"
    # main.py
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def home():
    return {"message": "Hello, FastAPI!"}

# run with: uvicorn main:app --reload

    Notice FastAPI apps aren't started with python main.py — instead, a separate program called uvicorn (an ASGI server) loads and runs your app object. ASGI is the modern, async-capable successor to WSGI (used by Flask and Django) — it's what allows FastAPI to handle many concurrent requests efficiently using the async/await patterns from the Concurrency module.

    🔗 FastAPI · Path Operations & Parameters

    A function decorated with @app.get, @app.post, etc. is called a path operation — the combination of a URL path and an HTTP method.

    @app.get("/items/{item_id}")
def read_item(item_id: int, q: str | None = None):
    return {"item_id": item_id, "q": q}

    FastAPI decides where each parameter comes from based on where its name appears: item_id matches {item_id} in the path, so it's a path parameter — required, and type-converted to int automatically (visiting /items/abc returns an automatic validation error). q doesn't appear in the path, so it's inferred to be a query parameter (?q=...) — and because it has a default of None, it's optional.

    📦 FastAPI · Request Bodies & Pydantic

    For structured data sent in a request body (typically with POST/PUT), you declare a Pydantic model — a class built the same way you'd build a dataclass, but specialized for parsing and validating external, untrusted data.

    from pydantic import BaseModel, Field

class Post(BaseModel):
    title: str = Field(min_length=1, max_length=200)
    body: str
    published: bool = False          # optional, defaults to False

@app.post("/posts")
def create_post(post: Post):
    return {"created": post.title}

    Sending a request body that violates any rule — missing body, a title longer than 200 characters, wrong types entirely — is rejected automatically with a detailed HTTP 422 error explaining exactly what was wrong, before create_post's own code ever runs. This is validation applied at the "front door" of your application, the same protective principle behind Django Forms and Flask-WTF, just expressed through plain type hints.

    📤 FastAPI · Response Models & Status Codes

    Just as you can declare the shape of incoming data, you can declare the shape of outgoing data too — useful for hiding internal fields (like a password hash) that exist on your data but should never be sent back to a client.

    class PostOut(BaseModel):
    title: str
    published: bool
    # note: no "body" field returned to the client, even if the internal object has one

@app.post("/posts", response_model=PostOut, status_code=201)
def create_post(post: Post):
    return post   # FastAPI filters this down to only PostOut's fields

    response_model acts as an output filter — even though the function returns the full post object, FastAPI strips it down to only the fields declared on PostOut before sending the response. status_code=201 sets the correct "Created" HTTP status for a successful POST, the same convention you saw earlier in the Flask example.

    📖 FastAPI · Automatic Docs

    Because every path operation's inputs and outputs are already declared through type hints and Pydantic models, FastAPI can generate fully interactive API documentation with zero extra work.

    # After running: uvicorn main:app --reload
# Visit these in a browser automatically:
#   /docs      -> interactive Swagger UI (try requests directly from the browser)
#   /redoc     -> alternative, read-only documentation view
#   /openapi.json -> the raw machine-readable API specification

    This is a major practical advantage over Flask and Django, where equivalent documentation typically requires a separate extension and manual upkeep. In FastAPI, the documentation can never silently drift out of sync with the real code, because it's generated directly from the same type hints that actually enforce validation.

    🧩 FastAPI · Dependency Injection

    FastAPI's dependency injection system lets you declare reusable pieces of setup logic (like "get the current database session" or "verify the user is logged in") once, and have FastAPI automatically run them and hand you the result as a function parameter.

    from fastapi import Depends, HTTPException

def get_current_user(token: str):
    if token != "secret-token":
        raise HTTPException(status_code=401, detail="Invalid token")
    return {"username": "asha"}

@app.get("/profile")
def profile(user: dict = Depends(get_current_user)):
    return user

    Depends(get_current_user) tells FastAPI: "before running profile, first call get_current_user, and pass its return value in as user." If get_current_user raises an HTTPException, profile never runs at all — the client immediately gets a 401 response. This is essentially a more flexible, composable version of the @login_required decorator you saw in Django, letting you share and combine setup logic across many endpoints cleanly.

    ⚡ FastAPI · Async, Middleware & Errors

    Because FastAPI runs on ASGI, any path operation can optionally be declared async to take advantage of the non-blocking patterns from the Concurrency module — ideal when a route needs to wait on a slow network call or database query.

    import httpx

@app.get("/external")
async def call_external_api():
    async with httpx.AsyncClient() as client:
        resp = await client.get("https://api.github.com")
    return resp.json()

# Middleware runs code around EVERY request, e.g. logging or CORS
@app.middleware("http")
async def log_requests(request, call_next):
    print(f"{request.method} {request.url}")
    return await call_next(request)   # continue on to the actual route

    An async def route can await other async operations without blocking the entire server while waiting — while one request is waiting on a slow external API, FastAPI can serve other requests in the meantime, exactly like the asyncio.gather example from the Concurrency module. Middleware wraps every single request coming through the app, useful for cross-cutting concerns like logging, timing, or adding security headers, without repeating that logic in every route.

    🗄️ FastAPI · Database & Auth

    Like Flask, FastAPI has no built-in ORM — it's commonly paired with the plain SQLAlchemy library you already learned, often combined with dependency injection to manage database sessions cleanly per-request.

    from sqlalchemy.orm import Session

def get_db():
    db = SessionLocal()          # a pre-configured sessionmaker
    try:
        yield db                     # hand the session to the route
    finally:
        db.close()                  # always clean up, even on error

@app.get("/posts")
def list_posts(db: Session = Depends(get_db)):
    return db.query(PostModel).all()

    Notice get_db uses yield instead of return — the same generator-as-context-manager pattern from the Advanced Language module. FastAPI runs everything before yield, hands the session to your route via Depends, and guarantees everything after yield (the cleanup in finally) runs once the request finishes — a database-session equivalent of the file-handling context managers you learned earlier. Authentication commonly uses OAuth2 with JWT tokens, implemented as another dependency similar to get_current_user above, verifying a token on every protected route.

Every framework you'll ever encounter — in Python or any other language — is built around this same basic request-response lifecycle, just with different tools and conventions layered on top.

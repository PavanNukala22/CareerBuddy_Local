      Version Control & CI/CD

      Version Control & CI/CD

      About documentation CI

      Documentation changes should be traceable and reviewable before publication. This module explains advanced Git operations and three CI implementations while keeping validation, artifacts and release permissions separate.

      Learning Objectives

      • Create and review focused branches; choose merge or rebase with history ownership in mind.
      • Resolve conflicts by meaning and verify the resulting document.
      • Explain GitHub Actions, GitLab and Jenkins jobs, outputs and gates.

      Prerequisites

      Know what a file, folder and terminal are. Use a disposable Git repository for exercises. CI examples assume an existing project, lockfile, scripts and the stated runtime or agent.

      Fundamentals

      Commit identifies source history; branch names point to commits; CI evaluates configured checks; an artifact holds built output. A green job is not the same as a reviewed or published release.

      Core Concepts

      DistinctionWhy it matters
      Merge versus rebaseCombining histories and rewriting replayed history have different ownership effects.
      Cache versus artifactReused dependencies are not the reviewed site output.
      Validation versus publicationChecks do not themselves establish a released site.

      Git branching and focused changes

      Version Control & CI/CD

      Git branching and focused changes

      Git records snapshots of a project and connects them through commit history. A branch is a movable reference to a commit, not a separate permanent copy of every file. In docs-as-code, a short-lived branch lets an author propose a focused update while reviewers inspect the change before it reaches the shared documentation.

      Git branching and focused changes essentials

      Start from the agreed base, inspect your working tree and keep the change small enough to review. A commit should express a coherent change, such as clarifying prerequisites. A pull or merge request adds review and checks around that change. Source files, configuration and lockfiles belong in the review; generated output is handled according to the repository’s publication policy.

      Code example: Git branching and focused changes

      Create a focused documentation branch
      git status --short
git fetch origin
git switch main
git pull --ff-only
git switch -c docs/quickstart
# Edit docs/getting-started.md, then inspect the change.
git diff -- docs/getting-started.md
git add docs/getting-started.md
git commit -m "docs: clarify quickstart prerequisites"

      Reading the Git branching and focused changes example

      The example assumes a clean checkout, an existing origin remote and a main branch. fetch updates remote-tracking references; pull --ff-only refuses a merge when local main has diverged. switch -c creates the topic branch. diff lets you inspect the exact file before staging and committing it. Stop and reconcile a non-clean or diverged state rather than treating these commands as a blind sequence.

      Advanced Git branching and focused changes techniques

      Agree ownership for shared branches and keep unrelated edits out of one review. Use a lockfile change when a dependency update is intended, and explain why it affects the build. A successful text merge does not prove the resulting instructions are correct.

      Apply Git branching and focused changes

      In a disposable repository, create a docs branch and change one prerequisite. Inspect the diff and make one focused commit. Explain the difference between the working tree, staged change and commit.

      Tool reference: Git branching and focused changes — official documentation.

      Keep branch scope and review evidence connected

      A focused branch should contain a change that reviewers can understand and validate together. Explain why each edited file belongs to the request. Unrelated formatting or generated-file churn can obscure the actual documentation correction. Before review, inspect the diff and run the checks relevant to the changed content and configuration.

      Git branching and focused changes

      In the Atlas classroom repository, a navigation fix changes one page and its navigation entry. The author removes unrelated bulk formatting from the branch, making the requested behaviour and its validation easier to inspect.

      Rebasing and history ownership

      Rebase replays commits onto a different base. It can make a private topic branch follow newer main changes, but replayed commits receive new identities. A merge combines histories; rebase rewrites the commits being replayed. Understanding that distinction matters before updating a branch other people are using.

      Rebasing and history ownership essentials

      Inspect the branch and working tree, fetch the current base and rebase the private work onto that explicit reference. When a conflict pauses the operation, resolve and stage the file, then continue the rebase. Abort returns from the in-progress operation if the chosen reconciliation is not appropriate.

      Code example: Rebasing and history ownership

      Rebase a private branch onto the fetched main branch
      git switch docs/quickstart
git status --short
git fetch origin
git rebase origin/main
# If rebase pauses, resolve the file before continuing.
git add docs/getting-started.md
git rebase --continue
# To abandon an in-progress rebase instead:
# git rebase --abort

      Reading the Rebasing and history ownership example

      origin/main is the fetched remote-tracking base. --continue belongs to a paused rebase after resolution; it is not a command to run blindly after every successful rebase. --abort is the alternative when abandoning the in-progress replay. Rebuild and inspect the resulting guide after the operation.

      Advanced Rebasing and history ownership techniques

      Do not rewrite a shared branch without the team’s agreed history policy. If an already published topic must be rewritten, coordinate it; do not assume an unrestricted force push is the normal repair. The important skill is choosing the history operation and communicating its effect.

      Apply Rebasing and history ownership

      Create a private topic commit, advance main in a disposable repository and rebase the topic onto the new base. Compare commit identifiers before and after. Demonstrate an abort in a separate conflict exercise.

      Tool reference: Rebasing and history ownership — official documentation.

      Rebase with an explicit history owner

      Rebasing changes the commit history being replayed, so the operation needs a clear understanding of who uses that branch. Inspect the resulting content, not just the command’s exit status. Repeated conflict resolution can produce a technically complete rebase with an incorrect navigation or explanation.

      Rebasing and history ownership

      Merge conflicts and semantic resolution

      Version Control & CI/CD

      Merge conflicts and semantic resolution

      A merge conflict means Git could not automatically reconcile the affected changes. Conflict markers show competing text, but they do not decide which instruction is correct. A docs specialist must combine intent, product facts and reader order, then validate the edited result.

      Merge conflicts and semantic resolution essentials

      Read both changes and their surrounding context. Ask whether the two prerequisites are compatible or whether one supersedes the other. Edit the file into the intended final content and remove the markers. Stage the resolved file and complete the operation using its appropriate merge or rebase command.

      Code example: Merge conflicts and semantic resolution

      Illustrative merge conflict in a guide
      <<<<<<< HEAD
Run the client after creating a configuration file.
=======
Run the client after installing the supported runtime.
>>>>>>> docs/quickstart

Resolved prose:
Install the supported runtime and create the configuration
file before running the client.

      Reading the Merge conflicts and semantic resolution example

      The image-like sample is an illustrative conflict, not a command or live terminal result. Both prerequisite changes are compatible in this scenario, so the resolved prose retains both in a clear order. In a real change, verify that order with the product owner. HEAD and the other-side labels must be interpreted within the current operation, especially during rebase.

      Advanced Merge conflicts and semantic resolution techniques

      A clean Git status only establishes that the conflict operation is complete. Broken links, duplicated sections or contradictory procedures can remain. Use content review, a strict build and a preview after resolution.

      Apply Merge conflicts and semantic resolution

      Resolve a conflict where one author adds a runtime prerequisite and another adds configuration. Explain your final wording, inspect for remaining markers and run the documentation checks.

      Tool reference: Merge conflicts and semantic resolution — official documentation.

      Resolve the meaning, not only the conflict markers

      A clean merge means Git no longer sees unresolved conflict markers; it does not prove that the chosen document is correct. Read the competing changes in context, preserve the intended meaning and check any connected navigation, links or examples. Record an unresolved product decision rather than choosing wording arbitrarily.

      Additional worked example

      Merge conflicts and semantic resolution

      Two Atlas edits rename a page differently. The author agrees the intended title, updates the navigation reference and builds the site. Removing the markers while retaining a broken link would have produced a clean Git state with a reader-facing defect.

      GitHub Actions documentation checks

      CI means continuous integration: automated checks on proposed or integrated changes. A GitHub Actions workflow describes events, jobs and steps in YAML. For documentation, linting and a production build help reviewers catch errors before publication. Passing CI is evidence of the checks configured, not proof of every aspect of documentation quality.

      GitHub Actions documentation checks essentials

      The workflow runs on pull requests and pushes to main. A runner checks out the repository, selects the runtime, installs the locked dependencies, then runs the project’s named lint and build scripts. This example validates documentation; it does not deploy it or provide deployment credentials.

      Code example: GitHub Actions documentation checks

      .github/workflows/docs.yml
      name: Docs checks
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  docs:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with:
          node-version: '22'
          cache: npm
      - run: npm ci
      - run: npm run lint:docs
      - run: npm run build:docs
      Scripts in an existing Docusaurus package.json
      {
  "scripts": {
    "lint:docs": "markdownlint-cli2 \"docs/**/*.md\"",
    "build:docs": "docusaurus build",
    "serve:docs": "docusaurus serve"
  }
}

      Reading the GitHub Actions documentation checks example

      contents: read gives the job repository-read permission. npm ci assumes an existing compatible package-lock.json; the project must provide the two scripts and their dependencies. Node 22 and the action major tags are example selections to match the chosen project. The accompanying scripts fragment belongs inside an existing Docusaurus package.json, not a complete dependency declaration.

      Advanced GitHub Actions documentation checks techniques

      Separate untrusted change checks from a privileged publication job. Record runtime and dependency choices and use the team’s reviewed action-pinning policy. Cache reuse can speed installation; it is not the deployable build artifact.

      Apply GitHub Actions documentation checks

      Add a workflow to a training repository with the declared scripts. Introduce a broken internal link, inspect the failing build and correct it before merging.

      Tool reference: GitHub Actions documentation checks — official documentation.

      Declare the workflow’s verification boundary

      A GitHub Actions workflow establishes only what its configured triggers, jobs and commands check. Review the actual scripts and expected output rather than treating a green badge as publication evidence. Keep validation permissions and any later deployment authority separate in the project’s accepted process.

      Additional worked example

      GitHub Actions documentation checks

      Atlas CI runs lint and a production build. The result supports those checks for the recorded revision. Since the workflow contains no publication step, the release note does not say that the site has been deployed.

      GitLab CI/CD stages and artifacts

      Version Control & CI/CD

      GitLab CI/CD stages and artifacts

      A GitLab pipeline uses jobs and stages to express the documentation work. A job performs commands in an execution environment. An artifact is retained output from a job. Distinguishing source, dependency cache and generated artifact prevents a deployment from serving the wrong directory.

      GitLab CI/CD stages and artifacts essentials

      The example runs a validation stage before a build stage. Both jobs install from the lockfile because each needs a complete dependency environment. The build retains the Docusaurus build directory as an artifact for review or a later publication step. It is a build pipeline, not a complete GitLab Pages deployment.

      Code example: GitLab CI/CD stages and artifacts

      .gitlab-ci.yml
      image: node:22
stages: [validate, build]
lint_docs:
  stage: validate
  script:
    - npm ci
    - npm run lint:docs
build_docs:
  stage: build
  script:
    - npm ci
    - npm run build:docs
  artifacts:
    paths: [build/]
    expire_in: 7 days

      Reading the GitLab CI/CD stages and artifacts example

      image selects Node 22 for this example. stages establishes validate then build. script lists the commands whose status determines the job outcome. artifacts.paths names the generated directory and expire_in sets the example retention period. A later job needing the artifact should declare and verify its transfer rather than assuming shared workspace files.

      Advanced GitLab CI/CD stages and artifacts techniques

      Stage ordering and explicit dependency relationships are different mechanisms. When optimising a larger pipeline, ensure a publication path cannot bypass the checks it requires. Retain the commit identity with the artifact so you can trace what was reviewed and released.

      Apply GitLab CI/CD stages and artifacts

      Adapt the example to your chosen output directory. Explain why the source docs folder is not the artifact to publish, and identify the dependency contract of a later preview job.

      Tool reference: GitLab CI/CD stages and artifacts — official documentation.

      Distinguish pipeline stages from retained artifacts

      GitLab stages organise the configured job sequence, while artifacts retain selected outputs for later use. Confirm which files the build job creates and which directory the artifact configuration collects. A successful earlier validation stage does not establish that a later build produced a usable site.

      Additional worked example

      GitLab CI/CD stages and artifacts

      Jenkins documentation pipelines

      Version Control & CI/CD

      Jenkins documentation pipelines

      Jenkins can run a documentation pipeline declared in a versioned Jenkinsfile. Declarative stages express installation, validation and build work. The agent supplies the execution environment, so a pipeline command succeeds only when the required runtime and tools are actually available there.

      Jenkins documentation pipelines essentials

      The sample requests an agent labelled docs-node-22, which the training team must provision. Installation and checks run in order, and successful builds archive the generated files. Archiving makes an artifact available for retrieval; it does not automatically publish a site.

      Code example: Jenkins documentation pipelines

      Jenkinsfile — on a provisioned Node 22 agent
      pipeline {
  agent { label 'docs-node-22' }
  stages {
    stage('Install') {
      steps { sh 'npm ci' }
    }
    stage('Validate') {
      steps { sh 'npm run lint:docs' }
    }
    stage('Build') {
      steps { sh 'npm run build:docs' }
    }
  }
  post {
    success {
      archiveArtifacts artifacts: 'build/**',
        allowEmptyArchive: false
    }
  }
}

      Reading the Jenkins documentation pipelines example

      agent chooses the configured worker. Each sh step runs a shell command on that worker. A failing install or check should fail the pipeline. post success archives build/** only after success; allowEmptyArchive: false prevents a missing output from being accepted silently.

      Advanced Jenkins documentation pipelines techniques

      Keep environment setup, permissions and artifact retention explicit. A passing job on one long-lived agent may depend on undeclared local tools; reproduce it on a clean worker before treating the pipeline as dependable. Do not include credential values in a Jenkinsfile or log output.

      A Jenkins pipeline depends on the selected agent having the required runtime, tools and permissions. Record those assumptions and inspect the actual command failures. A missing tool is an environment problem to diagnose, while a content failure needs a source or configuration correction.

      Intermediate Concepts

      Compare the same lint/build contract across three CI systems. Explain jobs, environments and artifacts without assuming each system shares a workspace in the same way.

      Define the same validation contract across CI systems

      Separate the commands your project needs from the syntax that schedules them. Record dependency installation, prose checks, site build, output path and failure conditions. Map that contract to GitHub jobs, GitLab jobs or Jenkins stages; do not assume their runners share files automatically.

      Worked example

      A fictional team runs lint and build in separate GitLab jobs. The build directory must be passed as an artifact when a later job needs it. A green lint job alone does not show that the documentation site was built.

      Distinguish dependency caches from release artifacts

      A dependency cache speeds repeated work; a build artifact records output from a particular run. Keep the source revision and build conditions with the output. A cache hit does not establish that the current pages were generated or checked.

      Worked example

      A fictional workflow restores package dependencies and builds commit A. Reviewers inspect the generated site from that run. Publication should identify the reviewed output rather than treating the dependency cache as the website.

      Resolve meaning after resolving conflict markers

      A text merge can combine lines while leaving an incorrect procedure. Read the complete affected task, compare the product version and run relevant examples. Explain the chosen meaning in the review so that the decision is traceable.

      Worked example

      One branch changes an installation flag; another changes the prerequisite version. The writer resolves both edits and checks whether that version supports the flag before accepting the final instructions.

      Advanced Concepts

      Separate proposed-change checks from publication permissions, coordinate rewritten history and design artifact promotion so the reviewed revision reaches the reader.

      Change scenario: revise one source, dependency, route or ownership assumption. Trace which checks and outputs need to be repeated before the next accepted release.

      Promote a reviewed artifact with a revision record

      Design publication around a known source revision and accepted checks. Retain the build output, configuration and result needed to identify what was reviewed. If you rebuild before publishing, treat the new output as a new candidate when its inputs or environment differ.

      Worked example

      A fictional preview passed for commit A, but main advances to B before release. The owner either promotes the accepted A output under the release policy or checks B; approval of A does not automatically approve B.

      Separate proposed-change checks from publication authority

      Validation and production publication have different trust requirements. Restrict release credentials to the jobs and conditions that need them, and review changes to workflow definitions. Do not assume every pull-request context has the same access to secrets.

      Worked example

      A contributor proposes a docs change. The validation workflow checks its build, while a separately controlled release job handles production publishing after the required review.

      Plan a reviewable recovery after history changes

      Coordinate a rebase with the people using that branch, explain the replacement history and verify the proposed content again. Recovery should identify the intended revision and affected collaborators rather than hiding an unexpected rewrite behind a new successful run.

      Worked example

      A fictional team rebases a shared feature branch after agreement. Reviewers compare the resulting changes and rerun validation; old approvals are checked against what actually changed.

      Record a documentation artifact fingerprint

      Use this after a successful site build. Save the following script and run python artifact_fingerprint.py site from the project root. It reads the output without publishing or modifying it.

      artifact_fingerprint.py · Python
      from pathlib import Path
import hashlib
import json
import sys

root = Path(sys.argv[1]).resolve()
if not root.is_dir() or not (root / "index.html").is_file():
    raise SystemExit("Expected a built site with index.html")
records = []
for path in sorted(root.rglob("*")):
    if path.is_file() and not path.is_symlink():
        records.append({
            "path": path.relative_to(root).as_posix(),
            "sha256": hashlib.sha256(path.read_bytes()).hexdigest(),
        })
print(json.dumps(records, indent=2))

      Expected result and verification: The result is a JSON list of output paths and SHA-256 fingerprints. Compare two runs: identical files have identical fingerprints; changing one page changes its record. A fingerprint identifies bytes, not whether their content is correct.

      Troubleshooting and limits: If index.html is absent, check the generator output path. Do not point the script at the source directory and call the result a release artifact.

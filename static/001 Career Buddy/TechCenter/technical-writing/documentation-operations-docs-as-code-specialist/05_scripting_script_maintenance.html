      Scripting & Script Maintenance

      Scripting & Script Maintenance

      About documentation scripting

      Scripts reduce repeated documentation work when their behaviour is explicit. This module teaches Python transformations, Bash orchestration, Node inventories, API generation, cross-repo sync and ongoing script maintenance.

      Learning Objectives

      • Run and test the included Python, Bash and Node examples.
      • Distinguish dry run, apply, idempotency and input failure.
      • Keep generated outputs, schema revisions and cross-repository ownership clear.

      Prerequisites

      Have Python, Node.js and Bash in the chosen practice environment. On Windows, use the team’s configured terminal or WSL/Git Bash for Bash commands. Use copies of files for the exercises.

      Fundamentals

      Declare inputs, writes, outputs and failure behaviour. A deterministic result is stable for the same input; an idempotent normalisation stops changing the already-normalised input. Neither property replaces evidence that the transformation is semantically appropriate.

      Core Concepts

      DistinctionWhy it matters
      Dry run versus applyWrite intent should be explicit.
      Deterministic versus idempotentStable generated output and stable repeat transformations are related but different.
      Generated versus handwrittenOutput ownership prevents accidental overwrite.

      Python file transformations

      Scripting & Script Maintenance

      Python file transformations

      Python can automate predictable source changes across many files. A maintained transformation should define its scope, encoding, write behaviour and repeat-run result. Idempotent means running the same normalisation again does not introduce additional changes.

      Python file transformations essentials

      The example converts CRLF line endings to LF in UTF-8 Markdown. It intentionally preserves spaces, including Markdown hard-break spaces and code indentation. A dry run prints proposed differences; --apply enables writes. Run it against a disposable working copy and review the diff before accepting source changes.

      Code example: Python file transformations

      scripts/normalise_docs.py — dry run is the default
      from pathlib import Path
import argparse
import difflib

parser = argparse.ArgumentParser()
parser.add_argument("root", type=Path)
parser.add_argument("--apply", action="store_true")
args = parser.parse_args()
if not args.root.is_dir():
    parser.error("root must be an existing directory")

for path in sorted(args.root.rglob("*.md")):
    if path.is_symlink():
        continue
    before = path.read_bytes().decode("utf-8")
    after = before.replace("\r\n", "\n")
    if after == before:
        continue
    print(f"Changed: {path}")
    print("".join(difflib.unified_diff(
        before.splitlines(keepends=True),
        after.splitlines(keepends=True),
        fromfile=str(path), tofile=str(path),
    )), end="")
    if args.apply:
        path.write_bytes(after.encode("utf-8"))

      Reading the Python file transformations example

      argparse makes the target directory explicit. read_bytes followed by UTF-8 decoding preserves the original newline information for the comparison. sorted traversal gives stable order; symlink files are skipped. Only changed files are considered for a write, and unchanged content produces no repeated edit.

      Advanced Python file transformations techniques

      Define behaviour for invalid encoding or interrupted writes before scaling the script. This teaching script stops on an exception and is not a transactional batch writer. For larger production transformations, use tested parsers, staging and a recovery plan rather than broad regex replacement across fenced code and frontmatter.

      Apply Python file transformations

      Test CRLF content, LF content, non-ASCII text and Markdown hard-break spaces. Run dry mode, apply mode and a second apply; prove the expected repeat-run result.

      Tool reference: Python file transformations — official documentation.

      Treat dry run and apply as different operations

      A file transformation should declare its scope and show what it will change before applying modifications. Preserve unrelated formatting and test the script with fixtures containing relevant edge cases. A dry run establishes a planned change; it is not evidence that the source files have already been normalised.

      Bash orchestration and exit status

      Bash can sequence installed tools without replacing them. Its main documentation-operations job is orchestration: establish the working directory, run checks in order and stop when a required command fails. Quoting and exit status are part of correctness, especially when paths contain spaces.

      Bash orchestration and exit status essentials

      The example wrapper invokes the Python dry-run transformation, a strict MkDocs build and an artifact existence check. It reports success only after these checks. It requires Bash, Python and MkDocs in the environment; on Windows use the team’s configured Git Bash or WSL workflow rather than pasting Bash directly into cmd.

      Code example: Bash orchestration and exit status

      scripts/check_docs.sh — fail before reporting success
      #!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."
python scripts/normalise_docs.py docs
mkdocs build --strict
test -f site/index.html
printf '%s\n' 'Build artifact verified: site/index.html'

      Reading the Bash orchestration and exit status example

      The quoted directory expression resolves the script’s parent project directory. set -euo pipefail establishes a stricter shell policy, but it is not a universal exception handler. The Python call does not apply changes. test verifies site/index.html before printf emits the success message.

      Advanced Bash orchestration and exit status techniques

      Learn the shell’s conditional and pipeline behaviour before relying on its failure semantics. Capture tool logs and preserve meaningful return codes. Do not append an unconditional success command that hides a failing required check.

      Apply Bash orchestration and exit status

      Run the wrapper in the included lab. Then remove a required source page or invoke a missing command in a training copy; verify a nonzero exit and no success message.

      Tool reference: Bash orchestration and exit status — official documentation.

      Keep failures visible through the Bash wrapper

      A Bash wrapper should report success only after the required commands complete successfully. Understand the commands and their exit behaviour instead of assuming that a final printed message proves the workflow passed. Quote paths and verify the wrapper with both a working fixture and a deliberate failure.

      Node.js inventory and filesystem automation

      Node.js inventory and filesystem automation

      Node.js can automate documentation metadata and file inventories in a JavaScript-based toolchain. A useful script is predictable across environments: its input scope, path format, ordering, output and failure behaviour should be explicit.

      Node.js inventory and filesystem automation essentials

      The example recursively lists Markdown files under docs and writes a JSON inventory. Directory entries are interpreted using filesystem metadata rather than guessing from filenames. The final list is sorted and relative paths are normalised to slash-separated strings for portability.

      Code example: Node.js inventory and filesystem automation

      scripts/docs_inventory.mjs
      import { readdir, writeFile } from 'node:fs/promises';
import path from 'node:path';

async function listMarkdown(root, relative = '') {
  const entries = await readdir(path.join(root, relative),
    { withFileTypes: true });
  const files = [];
  for (const entry of entries) {
    const next = path.join(relative, entry.name);
    if (entry.isDirectory()) {
      files.push(...await listMarkdown(root, next));
    } else if (entry.isFile() && entry.name.endsWith('.md')) {
      files.push(next.split(path.sep).join('/'));
    }
  }
  return files.sort();
}
const files = await listMarkdown('docs');
await writeFile('docs-inventory.json',
  JSON.stringify({ files }, null, 2) + '\n', 'utf8');
console.log(`Recorded ${files.length} Markdown files.`);

      Reading the Node.js inventory and filesystem automation example

      readdir with withFileTypes identifies directories and regular files. Symlink entries are not followed by these directory/regular-file branches. writeFile serialises a stable object with a final newline. A missing input directory raises an error and causes the script to fail instead of returning an invented empty success.

      Advanced Node.js inventory and filesystem automation techniques

      For very large repositories, consider traversal cost and excluded directories. Do not include secrets or private pages in a public inventory solely because they share an extension. Test duplicate or platform-specific path cases before using the inventory as a release manifest.

      Apply Node.js inventory and filesystem automation

      Create Markdown files in nested directories and a filename containing spaces. Generate the inventory twice and compare bytes. Remove the input directory in a training copy and observe failure.

      Tool reference: Node.js inventory and filesystem automation — official documentation.

      Make filesystem inventory predictable

      A Node.js inventory should define which files it includes, how it handles paths and how results are ordered. Predictable output makes repeated reviews easier and reduces meaningless diff noise. Test filenames with spaces and supported Unicode characters instead of assuming every path is a simple ASCII word.

      API documentation generation

      API documentation can be generated from a versioned schema or source model. Generation reduces manual drift, but a generated endpoint list is not a full guide. The docs specialist maintains the schema revision, generator behaviour, output ownership and contextual explanations.

      API documentation generation essentials

      The Python example reads a local OpenAPI 3.x JSON document, sorts paths and writes operation headings and summaries. It is deliberately limited: it does not resolve references or describe every parameter, response, authentication scheme or error. A full API-reference toolchain must handle those features explicitly.

      Code example: API documentation generation

      scripts/generate_api.py — limited OpenAPI JSON example
      from pathlib import Path
import json
from html import escape

spec = json.loads(Path("api/openapi.json").read_text(encoding="utf-8"))
if not str(spec.get("openapi", "")).startswith("3."):
    raise ValueError("Expected an OpenAPI 3.x document")
lines = ["# API operations", "", "Generated from api/openapi.json.", ""]
methods = {"get", "post", "put", "patch", "delete", "head", "options", "trace"}
for route, item in sorted(spec.get("paths", {}).items()):
    for method, operation in sorted(item.items()):
        if method not in methods:
            continue
        lines.append(f"## {method.upper()} {route}")
        lines.append("")
        lines.append(escape(operation.get("summary", "No summary supplied.")))
        lines.append("")
out = Path("docs/generated/api.md")
out.parent.mkdir(parents=True, exist_ok=True)
out.write_text("\n".join(lines) + "\n", encoding="utf-8")

      Reading the API documentation generation example

      The HTTP-method allowlist excludes path-item fields such as parameters. Sorting makes output reproducible. The output lives in docs/generated/api.md, a directory reserved for generated content. escape prevents supplied summaries from becoming raw HTML in the output, but this is not a complete untrusted-Markdown sanitiser.

      Advanced API documentation generation techniques

      Validate the schema with an appropriate validator, record its revision and test generation on edge-case fixtures. Keep handwritten task guidance outside overwritten generated files. Review schema changes together with the generated diff and the product release.

      Apply API documentation generation

      Use the included two-operation schema, generate the page and inspect its diff. Run again to prove stable output. Try a non-3.x document and explain the failure; list three features a full reference generator would still need.

      Tool reference: API documentation generation — official documentation.

      Keep generated API pages tied to their source schema

      API documentation generation should identify the authoritative schema, supported input scope and output location. Generated content needs a clear ownership policy so handwritten edits are not silently overwritten. A limited classroom generator should state what it covers instead of claiming full specification support.

      Cross-repository documentation syncing

      Cross-repository sync copies approved material between separately owned sources. The hard part is not merely moving bytes; it is deciding which repository is authoritative, which revision is accepted and how conflicts, deletions and repeated runs are handled.

      Cross-repository documentation syncing essentials

      The example plans a one-way rsync into a dedicated generated directory. It creates no automatic commit, performs no upload and does not delete destination files. Record the fetched source revision before reviewing the plan. Keep handwritten files outside the generator-owned destination.

      Code example: Cross-repository documentation syncing

      Plan a one-way sync into a dedicated generated directory
      # Run from the destination repository after fetching the
# authorised source checkout at the recorded revision.
mkdir -p docs/shared-generated
rsync -avn ../source-docs/shared/ docs/shared-generated/
# -n is dry run; this command does not copy or delete.
# Review the plan, revision and owner before an approved
# apply step. Generated files have one authoritative source.

      Reading the Cross-repository documentation syncing example

      -n means dry run, -v reports planned work and -a requests archive-style copying for an approved apply operation. The trailing slash after shared means its contents are mapped into the destination. This illustrative plan does not implement a complete reconciliation or deletion policy.

      Advanced Cross-repository documentation syncing techniques

      Avoid unowned two-way sync. Define destination-only file handling, review ownership, retries and how an approved source change becomes a destination pull request. A successful copy can still be wrong if it came from the wrong revision.

      Apply Cross-repository documentation syncing

      Create two disposable repositories with one shared guide. Record the source commit, run the plan and describe an approved apply/review process. Add a destination-only file and explain the chosen preservation or deletion policy.

      Tool reference: Cross-repository documentation syncing — official documentation.

      Resolve source authority before cross-repository syncing

      A sync process needs an authoritative source, an identified revision, a destination scope and an agreed conflict policy. Review the dry-run plan before applying changes, especially when the destination contains local work. A successful file copy does not establish that the right revision or ownership policy was used.

      Script maintenance and operational contracts

      A script becomes an operational tool when someone depends on it. Maintenance includes an owner, documented interface, dependency policy, fixtures, useful diagnostics and a change process. A script that succeeded once is not yet a dependable cross-repository automation system.

      Script maintenance and operational contracts essentials

      Write a contract naming inputs, outputs, default behaviour, write scope, exit conditions and repeat-run expectations. Keep representative fixtures and run checks when changing the script. Update the documentation alongside behaviour changes so users do not follow an outdated flag or path.

      Code example: Script maintenance and operational contracts

      Illustrative script contract
      {
  "script": "scripts/normalise_docs.py",
  "input": "UTF-8 Markdown under a chosen root",
  "default": "dry run; print proposed differences",
  "writes": "only with --apply",
  "owner": "documentation-operations team",
  "repeat_run": "no additional changes after normalisation"
}

      Reading the Script maintenance and operational contracts example

      The JSON sample is a contract record for the Python normaliser, not executable configuration for a standard tool. It states dry-run default and explicit --apply writes. The owner and repeat-run expectation make it possible to ask who will review a failure or behaviour change.

      Advanced Script maintenance and operational contracts techniques

      Add bounded retries only for operations where repeating is safe. Classify deterministic input errors separately from transient service errors. For generated outputs, track the source and generator revisions so a rollback is reproducible.

      Apply Script maintenance and operational contracts

      Write a maintenance record for the inventory or API script. Include one failure fixture, expected exit behaviour, review owner and a compatibility change that would require updating users.

      Tool reference: Script maintenance and operational contracts — official documentation.

      Maintain a script through an operational contract

      A maintained script needs an owner, supported inputs, environment assumptions, fixtures and useful failure behaviour. Document what another maintainer must know to rerun or repair it. Review the contract after a dependency or source-layout change so old success evidence is not treated as proof of new behaviour.

      Compare an in-place transform, an inventory and a generated API page. Identify which owns output, which should default to dry run and what happens on malformed input.

      State input roots, supported formats, output ownership and behaviour on invalid data. Distinguish discovery from mutation and provide a reviewable change report. A successful script exit is insufficient if it silently misses required files.

      A fictional Python transformation handles only Markdown files in an approved folder. Its dry run lists planned edits and skips unsupported input visibly before any apply operation.

      Make orchestration stop on a failed prerequisite

      A Bash orchestration script should preserve the failure of a required stage and avoid publishing incomplete output. Define which commands are mandatory and how their status is handled, especially when combining commands or piping output.

      Worked example

      A fictional generation step fails but a later upload command would still succeed. The maintainer stops the workflow at the failed prerequisite and retains its diagnostic output.

      Compare inventories before and after automation

      Use a Node.js or Python inventory to show created, changed and unexpected files. Compare the result with the declared output ownership. Review deletions and changes outside that boundary rather than assuming every difference is intended.

      Worked example

      Advanced Concepts

      Design bounded retries, recovery and a reviewed cross-repo handover. Avoid broad replacement across markup syntax and do not silently erase handwritten files in a generated directory.

      Change scenario: revise one source, dependency, route or ownership assumption. Trace which checks and outputs need to be repeated before the next accepted release.

      Protect recovery during partial file transformations

      Design how work is staged, validated and applied. Temporary-file replacement can reduce exposure to incomplete writes, but filesystem and platform conditions still matter. Keep recovery steps and retained inputs explicit; do not describe one-file replacement as a transaction across an entire tree.

      A fictional transform validates a candidate file before replacing its target. If a later file fails, the script reports the partial state and uses its recorded recovery plan rather than claiming that every edit was rolled back.

      Bound retries and distinguish permanent failures

      Retry an operation only when its failure may be temporary. Define attempt limits and useful diagnostics, and make the operation safe to repeat. Invalid input or missing permission usually requires a repair rather than an endless retry loop.

      Worked example

      A fictional cross-repo sync retries a temporary fetch failure within its policy. It stops on an invalid target path and presents the error for correction instead of repeatedly changing local files.

      Keep generated and handwritten ownership separate

      Record the API specification revision, generator inputs and generated output scope. Review cross-repo changes through the target repository’s normal process. Repeat generation should not silently erase material that the generator does not own.

      Worked example

      A fictional API-doc update produces a review branch in the target repo. The owner checks the diff, validates links and confirms that handwritten migration notes remain outside the generated directory.

      Generate a deterministic API endpoint inventory

      Create a small api.json fixture with {"paths":{"/health":{"get":{}},"/users":{"post":{}}}}. Save this script and run python inventory_api.py api.json. The output is a review aid, not complete API documentation.

      inventory_api.py · Python
      from pathlib import Path
import json
import sys

spec = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
paths = spec.get("paths")
if not isinstance(paths, dict):
    raise SystemExit("Expected a paths object")
methods = {"get", "put", "post", "delete", "options", "head", "patch", "trace"}
for route, item in sorted(paths.items()):
    if not isinstance(route, str) or not route.startswith("/"):
        raise SystemExit("Expected a route beginning with /")
    if not isinstance(item, dict):
        raise SystemExit(f"Expected an object for {route}")
    for method in sorted(item):
        if method in methods:
            print(f"{method.upper()} {route}")

      Expected result and verification: The supplied fixture prints GET /health followed by POST /users. Reordering the input objects keeps the output order stable. A route item containing parameters does not list parameters as an HTTP method.

      Troubleshooting and limits: This small lab does not resolve references, validate the complete OpenAPI document or document request and response schemas. Use the project’s chosen validator and generator for those tasks; compare the generated diff before publishing.

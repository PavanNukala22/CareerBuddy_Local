    Module 01 · Information Design

    Task-Based Writing

    Task-based writing, minimalism, and adherence to style guides including the Microsoft Writing Style Guide and Google Developer Documentation Style Guide. Build practical skills through examples, visual explanations, and a 50-question focused quiz.

    🎯 Start with the goal

    Task-based writing begins with what the user wants to accomplish. Titles should make the outcome obvious.

    🎯
    User goal
    What the reader needs to accomplish.
    🧭
    Context
    What must be known before acting.
    ✅
    Outcome
    What successful completion looks like.

    📝 Write actionable steps

    Use imperative verbs and one clear action per step when practical. Preserve exact UI terminology.

    Good practiceWhy it helps
    Use precise, task-focused wordingReaders can act without guessing.
    Show dependencies before actionsPrevents avoidable failure.
    Test against the real product or processKeeps documentation accurate.

    🔎 Add prerequisites and results

    Prerequisites tell readers whether they can start. Expected results tell them whether the task succeeded.

    ✕ BAD

    Configure the settings as appropriate and continue.

    ✓ GOOD

    Select Settings, choose Notifications, and enable Email alerts.

    🧭 Sequence by dependency

    Order actions according to the actual workflow and dependencies. Avoid forcing readers to backtrack.

    💡
    Practical tip: Test procedures from a clean starting state.

    🧪 Worked example

    Task title: Export an audit report. Prerequisite: Auditor role. Steps: Open Reports → select Audit → choose date range → select Export CSV. Expected result: CSV download begins.

    🧪
    Worked example: The task communicates goal, prerequisites, actions, and success clearly.

    🔬 🎯 Advanced task modeling

    Advanced task-based writing models the user journey, dependencies, decision points, and completion evidence.

    🚀
    Advanced practice: Start from the user outcome, identify prerequisites, then design the shortest safe path to a verifiable result.
    🎯
    Design for reuse
    Build content structures that are easy to review, update, and reuse.
    🔎
    Validate with evidence
    Verify important claims, procedures, and outputs against the real source.
    🛡️
    Control risk
    Expose prerequisites, dependencies, exceptions, and recovery paths.

    🧠 🧭 Task decomposition

    If “Configure notifications” requires three roles, split the workflow at the ownership boundary and state exactly where one role hands off to another.

    Minimalism

    Task-based writing, minimalism, and adherence to style guides including the Microsoft Writing Style Guide and Google Developer Documentation Style Guide. Build practical skills through examples, visual explanations, and a 50-question focused quiz.

    🎯 Reduce unnecessary cognitive load

    Minimalism means helping users reach useful information with less unnecessary effort. It does not mean removing information users need.

    🎯
    User goal
    What the reader needs to accomplish.
    🧭
    Context
    What must be known before acting.
    ✅
    Outcome
    What successful completion looks like.

    🪜 Progressive disclosure

    Present common-path information first and reveal advanced detail when the reader needs it.

    Good practiceWhy it helps
    Use precise, task-focused wordingReaders can act without guessing.
    Show dependencies before actionsPrevents avoidable failure.
    Test against the real product or processKeeps documentation accurate.

    ✂️ Remove redundancy

    Repeated information should earn its place by adding context or supporting a different decision. Otherwise, consolidate it.

    ✕ BAD

    Configure the settings as appropriate and continue.

    ✓ GOOD

    Select Settings, choose Notifications, and enable Email alerts.

    📈 Improve signal-to-noise

    Make important information easy to see by reducing unrelated text, excessive decoration, and buried actions.

    💡
    Practical tip: Shorter is not automatically better; relevance is the test.

    🧪 Worked example

    Before: two paragraphs of architecture history followed by a two-step setup. After: prerequisites and setup first, with a link to “How the architecture works” for readers who need it.

    🧪
    Worked example: Validate the shorter version with a representative user.

    🔬 ✂️ Advanced information reduction

    Advanced minimalism deliberately removes information that does not help the reader understand, decide, or act.

    🚀
    Advanced practice: Use progressive disclosure and keep background concepts available without forcing every reader through them.
    🎯
    Design for reuse
    Build content structures that are easy to review, update, and reuse.
    🔎
    Validate with evidence
    Verify important claims, procedures, and outputs against the real source.
    🛡️
    Control risk
    Expose prerequisites, dependencies, exceptions, and recovery paths.

    🧠 🧹 Editing test

    Ask: Does the reader need this to complete the task? Does it prevent an error? Does it explain a decision? If not, move it to reference material or remove it.

    📗 Google Developer Documentation Style Guide

    Google provides guidance for developer-facing documentation, including clarity, consistency, and terminology.

    Good practiceWhy it helps
    Use precise, task-focused wordingReaders can act without guessing.
    Show dependencies before actionsPrevents avoidable failure.
    Test against the real product or processKeeps documentation accurate.

    ✍️ Voice and sentence style

    Prefer clear, direct language. Active voice often makes instructions easier to understand, but do not force awkward constructions.

    ✕ BAD

    Configure the settings as appropriate and continue.

    ✓ GOOD

    Select Settings, choose Notifications, and enable Email alerts.

    🖥️ UI terminology and consistency

    Use current UI labels and approved terminology consistently. Search for variants before publishing a large set of pages.

    💡
    Practical tip: A style guide is most useful when applied consistently across the content set.

    🧪 Worked example

    Before: “Click here to perform the login operation.” After: “Select Sign in.” The second version is shorter, uses the actual UI label, and identifies the action directly.

    🧪
    Worked example: Review the rewrite against the applicable style guide and current product UI.

    🔬 📚 Advanced style governance

    Advanced style-guide practice turns individual rules into a repeatable editorial system across writers, products, and documentation sets.

    🚀
    Advanced practice: Maintain an approved terminology list, document exceptions, and use review checklists or automated linting where possible.
    🎯
    Design for reuse
    Build content structures that are easy to review, update, and reuse.
    🔎
    Validate with evidence
    Verify important claims, procedures, and outputs against the real source.
    🛡️
    Control risk
    Expose prerequisites, dependencies, exceptions, and recovery paths.

    🧠 🧭 Rule-conflict resolution

    When two guidance sources differ, choose the governing style guide for the project, document the decision, and apply the chosen rule consistently.

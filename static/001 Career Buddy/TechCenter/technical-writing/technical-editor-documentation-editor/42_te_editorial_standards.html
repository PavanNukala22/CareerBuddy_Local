    Module 01

    Editorial Standards for Technical Editors

    Master-level grammar, clarity and syntax, plus the structured style guides (Chicago Manual of Style, Microsoft, Google) and terminology databases that keep technical content consistent.

    🏛️ Course Overview: What the Role Needs

    Editorial standards turn taste into shared, testable rules. With a clear guide, a managed termbase and automated checks, a technical editor makes content accurate, consistent and easy to use.

    ✍️
    Grammar and clarity
    Precise, plain sentences.
    📚
    Style guides
    Chicago, Microsoft, Google.
    🗂️
    Terminology
    One term, one meaning.
    🧪
    Quality
    Measurable standards.
    💡
    Editorial standards are the shared rules that make many writers sound like one reliable voice and let readers trust, scan and act on technical content.

    🎯 Learning Objectives

    By the end of this course you will be able to:

    1. Apply grammar, syntax and punctuation rules with precision.
    2. Edit for clarity: plain language, active voice, concise structure.
    3. Choose and apply style guides: Chicago, Microsoft and Google.
    4. Build and maintain terminology databases and glossaries.
    5. Write a house style guide that resolves conflicts between sources.
    6. Automate checks with linters such as Vale.
    7. Measure editorial quality with rubrics and error rates.

    Style Guides: Chicago, Microsoft and Google

    What each guide is for, key rule differences, choosing a base guide, applying overrides and resolving conflicts.

    📚 The Three Guides Compared

    TopicChicago Manual of StyleMicrosoft Writing Style GuideGoogle Developer Documentation Style Guide
    Primary useBooks, journals, publishingSoftware and product UIDeveloper docs and APIs
    Serial commaRequiredRequiredRequired
    HeadingsHeadline case (title case)Sentence caseSentence case
    VoiceFormal, flexibleWarm, conversationalConversational, friendly, respectful
    ContractionsAvoided in formal textEncouragedAllowed
    UI labelsNot specializedBold UI textBold UI text
    NumbersSpell out one to one hundredNumerals in most technical contextsNumerals for 10 and above; spell out smaller in prose
    CodeMinimal guidanceCode font for code elementsCode font for code elements
    📌
    Check the current edition before enforcing a rule; guides change. Record the edition in your house style.
    Figure 3.1 · Choosing a style guide

    ⚖️ Intermediate: Decision Hierarchy

    PrioritySourceExample
    1Legal or regulatory requirementRequired disclaimers
    2Organization house styleProduct name capitalization
    3Base style guide (e.g., Google)Sentence-case headings
    4Secondary guide (e.g., Chicago)Punctuation edge cases
    5Dictionary (e.g., Merriam-Webster)Spelling
    textHOUSE STYLE EXCERPT
Base guide: Google Developer Documentation Style Guide (current edition).
Fallback: Chicago Manual of Style, 17th ed.; dictionary: Merriam-Webster.
Overrides:
  - Product name: "Acme Cloud" (never "ACME cloud").
  - Use "sign in", not "log in".
  - Headings: sentence case. Bold UI labels; code font for commands.
Rationale and examples are recorded for each override.
    Figure 3.2 · Decision hierarchy

    🔧 Intermediate: Applying the Rules to Technical Content

    ElementRule of thumb
    Commands and codeUse code font; never smart quotes inside code
    UI textBold the label exactly as shown on screen
    PlaceholdersItalic or angle brackets; explain once
    ProceduresNumbered steps; one action per step; imperative
    WarningsUse consistent labels: Note, Caution, Warning
    LinksDescriptive text, not "click here"
    Product namesUse official capitalization; no possessives
    code# Wrong
Run "npm install" and click the <b>save</b> button.

# Right
Run <code>npm install</code>, and then click <strong>Save</strong>.
    Figure 3.3 · Technical style elements

    Module 11

    Interview Preparation

    Questions asked in Technical Editor interviews about editorial standards, grouped by level. Draft your answer, then compare with the model answer.

    🌱 Beginner Interview Questions

    IQ1.What is the difference between copyediting and proofreading?
    Copyediting fixes grammar, style and consistency; proofreading is the final check for typos and formatting.
    IQ2.How do you decide between Chicago, Microsoft and Google guides?
    By content type and audience: Chicago for publishing, Microsoft for product UI, Google for developer docs, with house overrides.
    IQ3.How do you resolve a style conflict?
    Apply the decision hierarchy, let the owner decide, record an example and add a lint rule.

    🛠️ Intermediate Interview Questions

    IQ4.What makes writing clear?
    Short sentences, active voice, plain words, parallel structure and one term per concept.
    IQ5.How do you measure readability?
    Flesch Reading Ease or grade level, plus user feedback and task success.
    IQ6.What is a termbase?

    🚀 Advanced Interview Questions

    IQ7.How do you fix inconsistent terminology?
    Audit counts, decide the approved term, bulk-replace safely, add lint rules and track compliance.
    IQ8.What is Vale?
    An open-source prose linter that enforces style rules in CI.
    IQ9.How do you handle an engineer who rejects edits?
    Verify accuracy, explain reader benefit, separate rules from preferences and compromise.

    IQ10.How do you write inclusive language rules?

    IQ11.How do you prioritize edits under time pressure?

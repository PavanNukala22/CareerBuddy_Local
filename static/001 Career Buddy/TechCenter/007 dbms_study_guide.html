    Introduction to DBMS

    Why databases exist, how they're structured, who uses them, and the languages that drive them.

    1.1 Fundamentals of Databases

    Data vs Information vs Knowledge

    Data

    Raw facts

    2024-08-15, 50000, "Asha"

    Information

    Processed data

    "Asha was hired on 15-Aug-2024 at ₹50,000."

    Knowledge

    Insights

    Advantages & Disadvantages

    ✓ Advantages

    • Data integrity via constraints (PK, FK, CHECK)
    • Security with users, roles, privileges
    • Concurrent access via transactions
    • Backup & recovery built-in
    • Reduced redundancy

    ✗ Disadvantages

    • Cost — licenses, hardware, DBAs
    • Complexity — needs trained staff
    • Overhead vs. raw files for simple apps
    • Single point of failure if not replicated

    Practice Problems

    Problem 1

    Q. A university stores student data in three flat files (Admissions, Hostels, Library). List four concrete problems.

    Solution
    1. Redundancy — same student in 3 files → shared Student table.
    2. Update anomaly — address change in 1 file, others stale → FK + transactions.
    3. No concurrency — clerks overwrite each other → locking.
    4. Hard reporting — joining files needs custom code → SQL JOIN.
    Problem 2 GATE

    Q. Which ANSI-SPARC level deals with how data is physically stored on disk?

    Answer Internal (physical) level — block size, indexes, compression. Invisible to apps thanks to physical data independence.
    Problem 3

    Q. Classify: (a) GRANT, (b) SAVEPOINT, (c) ALTER, (d) UPDATE, (e) TRUNCATE.

    Answer a → DCL, b → TCL, c → DDL, d → DML, e → DDL.

    3.3 Functional Dependencies

    X → Y means: whenever two tuples agree on X, they agree on Y.

    TypeDefinitionExample
    TrivialY ⊆ X{a,b} → a
    Non-trivialY ⊄ Xroll → name
    FullWhole composite key needed(course,term) → instructor
    PartialPart of key suffices(roll,course) → name
    TransitiveX→Y→Z, Y not keyroll → dept → dept_head

    Armstrong's Axioms

    RuleStatement
    ReflexivityY ⊆ X ⇒ X → Y
    AugmentationX → Y ⇒ XZ → YZ
    TransitivityX → Y, Y → Z ⇒ X → Z
    UnionX → Y, X → Z ⇒ X → YZ
    DecompositionX → YZ ⇒ X → Y, X → Z

    Attribute Closure (X⁺)

    1. Start: result = X.
    2. For each FD A → B: if A ⊆ result, add B.
    3. Repeat until no change.
    Worked example

    R(A,B,C,D,E), F = { A→B, B→C, CD→E, A→D }. Compute A⁺.

    Solution

    {A} → +B → {A,B} → +D(A→D) → {A,B,D} → +C(B→C) → {A,B,C,D} → +E(CD→E) → {A,B,C,D,E}. A⁺ = all attrs ⇒ A is candidate key.

    Canonical Cover

    1. Split RHS (single attribute each)
    2. Remove extraneous LHS attributes (closure test)
    3. Remove redundant FDs

    Practice Problems

    Problem 1 Medium

    R(A,B,C,D), F = { AB→C, C→D, D→A }. Find all candidate keys.

    Solution

    B never on RHS → B in every key. (AB)⁺={A,B,C,D} ✓. (BC)⁺={B,C,D,A} ✓. (BD)⁺={B,D,A,C} ✓. CKs: {AB, BC, BD}.

    Problem 2 Easy

    ON DELETE SET NULL on Order.cust_email → Customer.email. What happens when customer deleted?

    Answer Orders kept, cust_email set to NULL — preserves history.
    Chapter 04

    Normalization

    Systematic removal of redundancy and update anomalies — each higher form makes the schema cleaner.

    4.1 Why Normalize?

    rollnamecourseinstructorinst_phone
    1AshaDBMSDr Rao9090
    1AshaOSDr Patel8181
    2RaviDBMSDr Rao9090

    Insertion anomaly

    Can't add instructor without a student row.

    Update anomaly

    Phone change → must update every row.

    Deletion anomaly

    Delete Ravi → lose "Dr Rao teaches DBMS."

    4.2 Normal Forms

    Figure 4.1 — Normal forms ladder. Each higher form implies all lower ones.

    1NF — atomic values

    ✗ Not 1NF

    roll | phones
1    | 9090, 8181

    ✓ 1NF

    Student       StudentPhone
roll|name     roll|phone
1   |Asha     1   |9090
              1   |8181

    2NF — no partial dependency

    ⚠

    Single-attribute PK → automatically 2NF.

    -- Not 2NF: PK=(sid,cid), sname depends only on sid
Enroll(sid, cid, sname, grade)

-- 2NF: split
Student(sid, sname)
Enroll(sid, cid, grade)

    3NF — no transitive dependency

    For every non-trivial X → A: either X is super key or A is prime.

    -- Not 3NF: emp_id → dept_id → dept_head
Emp(emp_id, name, dept_id, dept_head)

-- 3NF
Emp(emp_id, name, dept_id)
Dept(dept_id, dept_head)

    BCNF

    For every non-trivial FD X → Y, X must be super key. Stricter than 3NF.

    🔍

    3NF but not BCNF: R(student, course, instructor). FDs: (student,course)→instructor, instructor→course. instructor→course violates BCNF (not super key) but course is prime → 3NF holds.

    4NF — multi-valued dependencies

    ✗ Not 4NF

    Person(name, hobby, language) — independent MVDs create redundant combos.

    ✓ 4NF

    PersonHobby(name, hobby) + PersonLang(name, language)

    4.3 Decomposition Properties

    Lossless join

    R₁ ∩ R₂ is super key of R₁ or R₂.

    Dependency preserving

    FDs on sub-relations imply all original FDs.

    ⚖

    Trade-off: 3NF decomposition = always lossless AND dependency preserving. BCNF = always lossless but may lose dependencies.

    Algorithm: Find highest NF

    1. Find all candidate keys.
    2. Mark prime attributes.
    3. For each FD X→Y: if X is super key → BCNF. Else if Y is prime → 3NF. Else if X ⊂ CK → fails 2NF. Else → fails 3NF.
    4. Lowest passing = highest NF.

    Denormalization

    Deliberately add redundancy for read-heavy workloads: pre-compute aggregates, store derived columns. Trade-off: faster reads, harder writes.

    Practice Problems

    Problem 1 Medium

    R(A,B,C,D), F = { AB→CD, D→A }. Highest NF?

    Solution

    CKs: {AB, BD}. Prime: {A,B,D}. Non-prime: {C}. AB→CD: AB is SK ✓. D→A: D not SK, but A is prime → 3NF. Highest = 3NF.

    Problem 2 Hard

    Decompose R(A,B,C,D,E), F = { A→B, BC→D, D→E } into BCNF. Is it dependency preserving?

    Solution

    CK = AC. A→B violates BCNF → R₁(A,B), R'(A,C,D,E). In R': D→E violates → R₂(D,E), R₂'(A,C,D). BCNF: R₁(A,B), R₂'(A,C,D), R₃(D,E). BC→D requires B+C in one table — lost. Not dependency preserving.

    6.2 Queries & Joins

    Logical execution order

    Figure 6.1 — SQL logical order: SELECT is fifth though we write it first.
    SELECT dept_id, COUNT(*) AS headcount, AVG(salary) AS avg_sal
FROM   Employee
WHERE  status = 'active'
GROUP  BY dept_id
HAVING COUNT(*) > 5
ORDER  BY avg_sal DESC;
    ⚠

    WHERE filters rows before grouping; HAVING filters groups after. Don't put aggregates in WHERE.

    Joins in SQL

    -- INNER JOIN
SELECT e.name, d.name AS dept
FROM Employee e INNER JOIN Department d ON e.dept_id = d.id;

-- LEFT JOIN — all employees, even without dept
SELECT e.name, d.name
FROM Employee e LEFT JOIN Department d ON e.dept_id = d.id;

-- SELF-JOIN — employee + manager
SELECT e.name AS emp, m.name AS mgr
FROM Employee e LEFT JOIN Employee m ON e.manager_id = m.emp_id;

    6.3 Subqueries

    TypeReturnsUsed with
    Scalar1 value=, <
    Row1 row, multi-col= (a,b)
    TableMulti-rowIN, EXISTS, ANY, ALL
    -- employees earning above avg
SELECT name, salary FROM Employee
WHERE salary > (SELECT AVG(salary) FROM Employee);

-- correlated: top earner per dept
SELECT name, salary FROM Employee e
WHERE salary = (SELECT MAX(salary) FROM Employee WHERE dept_id = e.dept_id);

-- EXISTS: depts with active employees
SELECT name FROM Department d
WHERE EXISTS (SELECT 1 FROM Employee e WHERE e.dept_id=d.id AND status='active');

    6.4 Views, Triggers, Indexes

    -- VIEW
CREATE VIEW HighEarners AS
SELECT emp_id, name, salary FROM Employee WHERE salary > 100000;

-- MATERIALIZED VIEW (Postgres)
CREATE MATERIALIZED VIEW DeptStats AS
SELECT dept_id, COUNT(*) hc, AVG(salary) avg_sal FROM Employee GROUP BY dept_id;
REFRESH MATERIALIZED VIEW DeptStats;

-- TRIGGER
CREATE TRIGGER trg_audit AFTER UPDATE OF salary ON Employee
FOR EACH ROW EXECUTE FUNCTION log_change();

-- INDEX
CREATE INDEX idx_dept ON Employee(dept_id);
CREATE UNIQUE INDEX idx_email ON Employee(email);

    Updatable view: Simple projection of one table — no joins, no GROUP BY, no DISTINCT.

    Practice Problems

    Problem 1

    List departments with employee count, including zero-employee depts.

    Solution
    SELECT d.name, COUNT(e.emp_id) AS hc
FROM Department d LEFT JOIN Employee e ON e.dept_id = d.id
GROUP BY d.name;

    COUNT(e.emp_id) gives 0 for empty depts; COUNT(*) would give 1.

    Problem 2 Hard

    Find the second-highest salary.

    Solution (3 ways)
    -- subquery
SELECT MAX(salary) FROM Employee
WHERE salary < (SELECT MAX(salary) FROM Employee);

-- OFFSET
SELECT DISTINCT salary FROM Employee ORDER BY salary DESC OFFSET 1 LIMIT 1;

-- window
SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) rk FROM Employee
) t WHERE rk = 2;

    7200 RPM, seek=8ms, transfer=100MB/s. Time for 4KB block?

    Chapter 08

    Indexing & Hashing

    Indexes: the difference between 20ms and 20s. Understand structures to predict and tune performance.

    8.1 Index Concepts

    Dense index

    One entry per record. Larger but faster.

    Sparse index

    One per block. Data must be sorted. Smaller.

    Multi-level

    Index on index → leads to B-trees.

    TypeDescription
    PrimaryOn order field of sorted file (sparse)
    ClusteringOn non-key order field
    SecondaryOn any non-ordering field (always dense)

    8.2 B+ Tree

    Figure 8.1 — B+ tree. Internal nodes = keys + pointers; data in leaves; leaves linked.
    AspectB-TreeB+ Tree
    Data locationAll nodesLeaves only
    Search depthVariableConstant (always reach leaf)
    Range queriesSlow (traversal)Fast (linked leaves)
    Branching factorLowerHigher → shallower

    Specialized indexes

    Bitmap index

    One bitmap per value. Great for low-cardinality (gender, status), warehouse AND-ing.

    Inverted index

    Word → doc list. Foundation of full-text search.

    8.3 Hashing

    SchemeIdea
    StaticFixed buckets. Overflow → chaining. Degrades when full.
    ExtendibleDirectory indexed by first d bits. Split bucket → maybe double directory.
    LinearRound-robin splits on load threshold. No directory.

    Practice Problems

    Problem 1

    B+ tree order 100, 1 billion records. Estimate height.

    Solution

    Min fanout ⌈100/2⌉ = 50. log₅₀(10⁹) ≈ 5.3 → ~6 levels. Key lookup ≈ 6 I/Os.

    Problem 2

    Why is hash index bad for WHERE age BETWEEN 20 AND 30?

    Answer Hashing destroys ordering — close values scatter across buckets. Must scan all buckets. Use B+ tree.

    9.2 Join Algorithms

    Nested-loop

    For each R row, scan S. Block-nested-loop reads R in chunks. Good with index on S.

    Sort-merge

    Sort both on join key, merge. Great when already sorted.

    Hash join

    Hash smaller table, probe with larger. Best for equality on unsorted data.

    ⚙

    Rule of thumb: equality → hash; sorted/range → sort-merge; one side small/indexed → nested-loop.

    9.3 Optimization

    Heuristic (rule-based)

    Figure 9.2 — Push σ below ⋈: shrinks intermediate before expensive join.

    Cost-based optimization

    • Enumerate plans, estimate cost using statistics (table size, histograms).
    • Dynamic programming finds optimal left-deep join order in O(2ⁿ).
    • Modern optimizers unnest correlated subqueries into joins.

    Practice Problems

    Problem 1

    R=10,000 blocks, S=500 blocks, memory=50 blocks. Block-nested-loop cost?

    Solution

    Use S as outer (smaller). Chunks = ⌈500/49⌉ = 11. I/O = 500 + 11×10,000 = 110,500.

    Problem 2 Medium

    A(1M rows), B(100 rows), C(10M). Query joins all three with filter A.region='IN'. Best order?

    Answer Push σ on A first → small A. Join with B (smallest) → join with C. Order: σ(A) ⋈ B ⋈ C.
    Chapter 10

    Transactions, Concurrency & Recovery

    How the system survives crashes and runs thousands of users without corrupting data.

    10.1 ACID Properties

    Figure 10.1 — Transaction state diagram.

    A — Atomicity

    "All or nothing." Undo logs rollback on failure.

    C — Consistency

    Takes DB from one valid state to another. Constraints hold.

    I — Isolation

    Concurrent txns don't see intermediate states. Locking / MVCC.

    D — Durability

    Committed changes survive crashes. WAL guarantees.

    10.2 Serializability

    Conflict serializability

    Two ops conflict if: different txns, same data, at least one write. Schedule is conflict-serializable iff precedence graph is acyclic.

    🧪

    Test: Build directed graph (Ti→Tj if Ti op conflicts with later Tj op). Acyclic ⇒ serializable. Topological sort = equivalent serial order.

    View serializability

    More permissive than conflict: two schedules are view-equivalent if same initial reads, same write-read pairs, and same final write. Testing is NP-complete.

    10.3 Concurrency Control

    Lock-based protocols

    LockCompatibility
    Shared (S)S with S ✓; S with X ✗
    Exclusive (X)X with anything ✗

    Two-Phase Locking (2PL)

    Figure 10.2 — 2PL: acquire locks in growing phase, release in shrinking. Guarantees conflict serializability.
    • Basic 2PL: growing → shrinking. Serializable but may deadlock.
    • Strict 2PL: Hold X-locks until commit. Prevents cascading aborts.
    • Rigorous 2PL: Hold all locks until commit.

    Timestamp-based

    • Each txn gets timestamp. Ops ordered by timestamp; conflicts → abort younger.
    • Thomas Write Rule: If writing an item already written by a younger txn, skip the write (it's obsolete) instead of aborting.

    Multiple granularity locking

    Lock at database, table, page, or row level. Use intention locks (IS, IX, SIX) to signal intent to lock at finer grain.

    10.4 Deadlocks

    Prevention

    • Wait-Die: Older waits, younger aborts.
    • Wound-Wait: Older forces younger to abort.
    • Lock ordering: Acquire in fixed order.

    Detection & Recovery

    • Wait-for graph — cycle = deadlock.
    • Pick victim (youngest/least work) and rollback.

    Concurrency anomalies

    ProblemWhat happensSolution
    Dirty readRead uncommitted dataDon't release S/X early
    Non-repeatable readRe-read gets different valueStrict 2PL
    Phantom readNew rows appear between scansIndex locks / predicate locks
    Lost updateTwo txns overwrite each otherX-lock before update

    10.5 Recovery

    Write-Ahead Logging (WAL)

    Rule: log record is written to disk before the data page. Enables undo and redo after crash.

    ConceptDescription
    UndoReverse uncommitted changes (using old values from log)
    RedoReapply committed changes not yet on disk (using new values)
    CheckpointFlush dirty pages + record active txns. Limits recovery scope.

    Recovery procedure (ARIES-style)

    1. Analysis: Scan log from last checkpoint to find active txns and dirty pages.
    2. Redo: Replay ALL logged changes from checkpoint forward (even uncommitted).
    3. Undo: Roll back any txns that didn't commit.

    Backup strategies

    TypeWhat
    FullEntire DB
    IncrementalChanges since last backup (any type)
    DifferentialChanges since last full backup
    Shadow pagingCopy-on-write: old page untouched, new page written elsewhere. Commit = swap page table.

    Practice Problems

    Problem 1

    Schedule: T1:R(A), T2:R(A), T1:W(A), T2:W(A). Is it conflict-serializable?

    Solution

    Conflicts: T1:R(A)↔T2:W(A) → T1→T2. T2:R(A)↔T1:W(A) → T2→T1. Precedence graph has cycle T1↔T2. Not conflict-serializable.

    Problem 2 Medium

    Why does Strict 2PL prevent cascading aborts?

    Answer X-locks held until commit → no other txn can read uncommitted data → if a txn aborts, no other txn has read its dirty writes, so no cascade.
    Problem 3 Hard

    After crash, log shows: [T1 start], [T1 W(A,5→10)], [checkpoint {T1}], [T2 start], [T2 W(B,20→30)], [T1 commit]. What does recovery do?

    Solution

    Analysis: Active at checkpoint: {T1}. T2 started after. T1 committed. T2 did not.
    Redo: Replay T1 W(A,10) and T2 W(B,30).
    Undo: T2 never committed → undo W(B) back to 20. Final: A=10, B=20.

    4. SQL & Query Design

    Intermediate SQL should move beyond simple SELECT statements into joins, aggregation, subqueries and window functions. The existing guide includes practical patterns such as duplicate detection, self-joins, department ranking, running totals and anti-joins. fileciteturn5file5L137-L165

    Window functions

    SELECT name, dept, salary, RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS dept_rank FROM Employee;

    A window function can calculate rankings or running totals without collapsing the rows into one row per group.

    5. Transactions & Concurrency

    Transactions protect multi-step business operations. Think about a bank transfer, order placement, ticket booking or inventory update as one logical unit.

    Atomicity

    All or nothing

    Required operations succeed together or the transaction rolls back.

    Consistency

    Valid state

    Integrity rules remain satisfied after a successful transaction.

    Isolation / Durability

    Concurrent + persistent

    Isolation controls interactions between transactions; durability protects committed work against failures according to the DBMS recovery design.

    BEGIN; UPDATE Account SET balance = balance - 1000 WHERE account_id = 101; UPDATE Account SET balance = balance + 1000 WHERE account_id = 202; COMMIT;
    AnomalyMeaning
    Dirty readReading another transaction's uncommitted data.
    Non-repeatable readThe same row can return a different committed value later.
    Phantom readA repeated range query can see newly matching rows.
    Lost updateOne concurrent update overwrites another.
    Advanced: Isolation is a trade-off. Stronger guarantees can increase blocking or retries. Choose based on business correctness and measured workload.

    6. Indexing & Query Optimization

    An index is an auxiliary access structure that can reduce the work required for common lookups. The guide already treats indexing and query optimization as dedicated chapters. fileciteturn5file7L262-L270

    CREATE INDEX idx_orders_customer_date ON Orders(customer_id, created_at); SELECT order_id, total_amount FROM Orders WHERE customer_id = 42 AND created_at >= '2026-01-01' AND created_at < '2026-02-01';
    Index considerationReason
    Frequently filtered columnsCan reduce rows examined.
    Join keysCan speed relationship lookups.
    Range/sort patternsCan support ordered access.
    Every columnNot automatically good; indexes consume storage and increase write cost.
    Optimization workflow: reproduce → inspect execution plan → identify expensive operation → make a targeted change → benchmark again.

    Durable storage

    Database performance depends heavily on how data is laid out, cached and accessed. Recovery mechanisms use logs, checkpoints and backups so the system can return to a valid state after failures.

    WAL

    Write-ahead logging records recovery information before corresponding changes are treated as durable.

    Checkpoint

    Provides a recovery reference point, reducing the amount of history that must be processed after failure.

    Backup

    Provides a recovery source for data loss, corruption or accidental deletion.

    Backup ≠ high availability: Replication can improve availability, while backups are essential for recovery from many forms of data loss.

    Give users/services only the database permissions they need.

    Parameterized SQL

    Keep values separate from SQL syntax to reduce injection risk.

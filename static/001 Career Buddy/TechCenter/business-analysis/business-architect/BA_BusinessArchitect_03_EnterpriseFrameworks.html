    Enterprise Architecture and Why Frameworks

    What enterprise architecture is, why frameworks exist, and the four kinds of framework you will meet.

    🏙️ What is Enterprise Architecture (EA)?

    Enterprise Architecture is the discipline that describes the structure of an organisation — its strategy, business, information, applications and technology — and guides how it changes. A city analogy: EA is the urban plan (zoning, roads, utilities), while a project architect designs a single building.

    Architecture levelScopeAnalogy
    EnterpriseWhole organisation or major partCity plan
    SolutionOne solution or systemA building design
    Software / TechnicalComponents, code, infrastructureWiring and plumbing
    📌
    EA answers four things: Where are we, where do we want to be, how do we get there, and how do we stay on course.

    📘 What is an architecture framework?

    An architecture framework is a structured set of methods, vocabulary, templates and guidance for creating and using architecture descriptions. It saves you from inventing structure each time and enables consistent communication.

    🗂️
    Taxonomy
    Classifies architecture artefacts (Zachman)
    🔁
    Process method
    Step-by-step approach (TOGAF ADM)
    📚
    Reference model
    Pre-built models for a domain (BIZBOK, BIAN, APQC)
    🧰
    Comprehensive
    Combines taxonomy, process and content (TOGAF, FEAF)

    🧱 What is what: key vocabulary

    TermMeaning
    StakeholderPerson or group with interest in the architecture
    ConcernInterest of a stakeholder, e.g. security, cost
    ViewRepresentation of the system from a stakeholder perspective
    ViewpointConventions for constructing a view
    ArtefactSpecific catalog, matrix or diagram
    DeliverableFormally reviewed work product
    Building blockReusable component of capability (Architecture or Solution Building Block)
    Baseline vs TargetCurrent architecture vs desired architecture
    PrincipleRule guiding architecture decisions
    ISO/IEC/IEEE 42010Standard for architecture description (stakeholders, concerns, views)

    TOGAF Fundamentals and the ADM

    The Open Group Architecture Framework: structure, ADM phases and BDAT domains.

    🧩 What TOGAF is

    TOGAF (The Open Group Architecture Framework) is the most widely used EA framework. It is a comprehensive, vendor-neutral methodology centred on the Architecture Development Method (ADM). TOGAF Standard 10th Edition reorganises the material into a Fundamental Content and a library of Series Guides for easier tailoring.

    TOGAF componentPurpose
    ADMIterative method to develop and manage architecture
    ADM Guidelines and TechniquesAdapting ADM (iteration, security, agile, digital)
    Architecture Content FrameworkMetamodel and deliverable structure
    Enterprise Continuum and ToolsClassify and reuse architecture assets
    Architecture Capability FrameworkOrganisation, process, skills, roles to run EA
    Reference modelsTechnical Reference Model, III-RM (legacy)

    🔄 The ADM cycle

    Architecture development phases
    Delivery and governance phases
    PhaseGoalKey outputs
    PreliminaryPrepare the organisation, define principles and tailor the frameworkPrinciples, governance, tailored framework
    A: Architecture VisionAgree scope, vision and stakeholdersVision, Statement of Architecture Work
    B: Business ArchitectureDefine baseline and target business architectureCapability, value stream, org, process models
    C: Information SystemsData and Application architecturesData entities, application portfolio
    D: TechnologyTechnology architecturePlatform and infrastructure models
    E: Opportunities and SolutionsIdentify delivery vehicles and gapsWork packages, transition architectures
    F: Migration PlanningPrioritise and planRoadmap, implementation and migration plan
    G: Implementation GovernanceEnsure conformance during buildCompliance assessments, contracts
    H: Architecture Change ManagementManage change after go-liveChange requests, new cycle
    Requirements ManagementCentral, continuousRequirements repository
    💡
    ADM is iterative: you can iterate within a phase, between phases or across entire cycles. It is a menu to tailor, not a waterfall to obey.

    🏗️ BDAT: the four architecture domains

    💼
    Business
    Strategy, governance, organisation, key business processes
    🗃️
    Data
    Logical and physical data assets and management
    🧮
    Application
    Blueprint for individual systems and their interactions
    🖥️
    Technology
    Software, hardware and network infrastructure

    Phase B covers Business; Phase C covers Data and Application (Information Systems); Phase D covers Technology.

    TOGAF in Depth: Content, Repository and Governance

    Artefacts, the Enterprise Continuum, the Architecture Repository, principles, compliance and tailoring.

    📦 Architecture Content Framework

    Artefact typeWhat it isExamples
    CatalogStructured list of thingsApplication catalog, role catalog, capability catalog
    MatrixRelationships between two entity typesApplication / Capability matrix, Actor / Role matrix
    DiagramGraphical pictureValue stream diagram, application communication, network diagram

    TOGAF distinguishes Architecture Building Blocks (ABBs) — what is required (specification) — from Solution Building Blocks (SBBs) — what implements it (product or component).

    📌
    ABB: "Customer Identity Service". SBB: "Okta CIAM platform configuration v3".

    🗄️ Enterprise Continuum and Architecture Repository

    Enterprise Continuum

    Classification from generic to specific: Foundation architectures, Common systems, Industry, Organisation-specific. Helps reuse assets.

    Architecture Repository

    • Architecture Metamodel
    • Architecture Capability
    • Architecture Landscape
    • Standards Information Base
    • Reference Library
    • Governance Log
    • Requirements Repository
    💡
    Landscape is typically seen at three levels: Strategic (long term), Segment (programme), Capability (project).

    🛡️ Governance, principles and compliance

    Principle (TOGAF format)Architecture principle: Data is an asset
Statement: Data is managed, valued and protected as an enterprise asset
Rationale: Accurate shared data improves decisions and reduces cost
Implications: Data stewards are named; unmanaged copies are not permitted
    • Architecture Board: cross-functional body deciding standards, compliance and dispensations.
    • Architecture Contract: agreement between development partners and sponsors.
    • Compliance review: compliant, partially compliant or non-compliant outcome.
    • Dispensation: approved temporary exception with expiry.
    • Architecture Capability Maturity Model: assesses the EA function itself.

    ✂️ Tailoring TOGAF

    TOGAF explicitly expects adaptation. Typical tailoring: shorten phases, merge B-C-D for small programmes, use agile sprints inside phases, combine with ArchiMate notation and DevOps governance.

    ContextTailoring
    Small projectLight architecture vision + decision log, skip catalogs
    Agile deliveryJust-enough upfront architecture, architecture runway, ADRs
    MergerRapid baseline and target for key domains, focus on integration
    Digital transformationEmphasise Vision, capabilities and APIs; iterate often

    BIZBOK and Business Architecture

    The Business Architecture Body of Knowledge: capabilities, value streams, information, organisation and scenario-driven use.

    📗 What BIZBOK is

    BIZBOK Guide is published by the Business Architecture Guild. Unlike TOGAF, which covers all EA domains, BIZBOK focuses on the business layer — practical modelling of the business blueprint and its use for strategy execution.

    BIZBOK elementDescription
    Capability mappingHierarchical model of what the business does
    Value stream mappingEnd-to-end stakeholder value delivery
    Organisation mappingBusiness units, partners, stakeholders
    Information mappingBusiness information concepts (not database design)
    Strategy mappingObjectives, courses of action, tactics
    Product / Initiative mappingOfferings and change initiatives
    📌
    BIZBOK defines business architecture as a blueprint of the enterprise that provides a common understanding of the organisation and aligns strategic objectives with tactical demands.

    🔭 Scenario-based business architecture

    BIZBOK encourages building only the views needed for a business scenario rather than a complete map up front. Common scenarios:

    ScenarioPrimary views used
    Business transformationCapabilities, value streams, initiatives, strategy
    Merger and acquisitionCapability comparison, organisation, information
    Customer experience improvementValue streams, stakeholder journeys, capabilities
    Regulatory compliancePolicies mapped to capabilities and information
    Cost optimisationCapability heatmaps, cost, application mapping
    Product launchProduct-capability and value stream impacts
    Scenario-driven approach: use only the views the business question requires.

    🧬 Business Motivation Model (BMM) and strategy

    • Ends: Vision, Goal, Objective (what we want).
    • Means: Mission, Strategy, Tactic (how we will get there).
    • Influencers: internal and external factors; SWOT assesses them.
    • Directives: Business policy and rule.
    ✅
    BIZBOK + TOGAF are complementary: BIZBOK gives deeper business modelling techniques, TOGAF provides the enterprise-wide process and governance.

    Zachman Framework

    The 6x6 classification schema: interrogatives, perspectives, rules and how to apply it.

    🧮 What Zachman is

    The Zachman Framework (John Zachman, 1987) is an ontology / taxonomy, not a method. It is a 6x6 matrix classifying architecture artefacts by audience perspective (rows) and interrogative (columns). It tells you what descriptions exist, not how to create them.

    Row (Perspective)AudienceWhat / How / Where / Who / When / Why
    1. Scope (Contextual)Planner / ExecutiveLists of things important to the enterprise
    2. Business Model (Conceptual)Business ownerSemantic models, business process model, organisation
    3. System Model (Logical)Architect / DesignerLogical data model, application architecture
    4. Technology Model (Physical)Engineer / BuilderPhysical data model, system design
    5. Detailed RepresentationImplementerOut-of-context component specifications
    6. Functioning EnterpriseUsersActual operating instance

    ❓ The six interrogatives (columns)

    ColumnQuestionEnterprise focusExample artefact
    WhatInventoryData / thingsEntity list, data model
    HowProcessFunctionsProcess flow
    WhereDistributionNetwork / locationsLogistics network
    WhoResponsibilityPeople / organisationOrg chart, role model
    WhenTimingTime / cyclesMaster schedule, event model
    WhyMotivationEnds / meansBusiness plan, rules
    💡
    Mnemonic: What How Where Who When Why across; Scope Business System Technology Detail Functioning down.

    📐 Rules and usage

    • Each column has a simple, primitive model; composite models combine several columns.
    • Each cell is unique and holds artefacts only of that perspective and interrogative.
    • Rows are transformations of the previous row, not decompositions.
    • Columns have no order of priority and all must be considered for completeness.
    • Use it as a checklist of what architecture descriptions are missing.
    ⚠️
    Zachman does not tell you how to build the architecture or how to govern it. Pair it with a process method such as TOGAF ADM.

    ⚖️ Zachman vs TOGAF vs BIZBOK

    AspectZachmanTOGAFBIZBOK
    TypeTaxonomy / ontologyProcess + content + governanceBusiness architecture body of knowledge
    Primary questionWhat artefacts exist?How do we develop and govern architecture?How do we model and use the business blueprint?
    ScopeWhole enterpriseWhole enterprise (BDAT)Business layer
    Prescribes method?NoYes (ADM)Techniques and scenarios
    Best used forCompleteness checks, classificationProgramme architecture workStrategy, transformation, capability work

    🎯 How to choose and combine

    1. Clarify purpose: governance, strategy, M&A, transformation, compliance?
    2. Check context: industry, size, maturity, regulatory requirements.
    3. Pick a process backbone: TOGAF ADM or a lightweight in-house method.
    4. Add content standards: BIZBOK for business views, ArchiMate for notation.
    5. Add a completeness lens: Zachman as a checklist.
    6. Define the minimum viable set: few artefacts, high usage.
    Combining frameworksTypical hybrid in a mid-size bank
Process backbone     : TOGAF ADM (tailored, agile iterations)
Business blueprint   : BIZBOK capability and value stream maps
Notation             : ArchiMate 3.x
Reference models     : BIAN service domains
Completeness check   : Zachman matrix (annual review)
Governance           : Architecture Review Board + ADRs

    💡
    Intermediate skill is choosing between options and justifying the choice, not just naming them.

    ⚙️ Lightweight and agile EA

    • Just-enough architecture: create artefacts only when they drive decisions.
    • Architecture Decision Records (ADR): short documents capturing context, decision, consequences.
    • Guardrails not gates: publish principles and patterns; review only high-risk items.
    • Architecture runway: enablers built ahead of features to reduce rework.
    • Federated model: domain architects embedded in teams, EA team sets direction.
    • Continuous roadmap: living models in repository instead of static documents.
    ADRADR-014: Adopt event streaming for order updates
Status: Accepted   Date: 2026-03-18   Deciders: Integration domain architect, Order product owner
Context: Point-to-point integrations cause delays and duplicate logic.
Decision: Publish order events to the shared streaming platform.
Consequences: Teams must register schemas; legacy batch jobs retired by Q4.

    📊 Measuring EA effectiveness

    DimensionMetric
    Alignment% initiatives mapped to strategic objectives
    Reuse% projects using standard patterns / platforms
    CostApplication count, annual licence cost, unit cost
    Compliance% projects passing architecture review at first attempt
    AgilityLead time for architecture decisions
    Quality of data% applications with owner, lifecycle and capability mapping
    EA maturityScore on an EA maturity model (e.g. TOGAF ACMM)
    ⚠️
    The leading cause of EA failure is ivory-tower architecture: heavy documentation with no link to delivery decisions or business outcomes.

    🧠 Expert insights and interview prep

    PointDetail
    What it isEnterprise frameworks are structured guidance for describing, planning and governing enterprise architecture; TOGAF is the process-centred standard, BIZBOK the business blueprint, Zachman the classification schema.
    Why it is usedThey create a common language, repeatable method, reuse of artefacts and traceability from strategy to implementation.
    How it worksThe ADM turns vision into baseline, target, gap and roadmap; the content framework defines artefacts; governance enforces conformance; repository stores reusable assets.
    How to use itSelect a minimal toolset, tailor the method, define principles, set up an architecture board, publish standards, and measure outcomes.
    Common mistakesFollowing TOGAF as a rigid waterfall; building complete models nobody uses; confusing Zachman with a method; tool-first thinking; architecture board as a bottleneck; no business ownership.
    Real-world usageA utility uses TOGAF ADM for programmes, BIZBOK capability maps for investment, ArchiMate for models, and ADRs for team decisions, reducing duplicate applications by 30% in three years.
    Interview pointsCompare TOGAF, Zachman and BIZBOK; explain ABB vs SBB; describe how you tailor ADM for agile; define what an architecture compliance review decides; show an ADR example.
    ✅
    Strong answer pattern: name the framework, state its purpose, give a real use, state a limit. E.g. "Zachman gives completeness, but no method — so I pair it with ADM."

    Process Mining Foundations

    What process mining is, what an event log looks like, and how it differs from BI, BPM and RPA.

    ⛏️ What is Process Mining?

    Process mining reconstructs how processes *really* run from the digital footprints (event logs) left in IT systems such as ERP, CRM and ticketing tools. The field was founded by Prof. Wil van der Aalst (RWTH Aachen) and bridges data science and process management.

    TypeQuestion answeredInput -> output
    Process discoveryWhat does the process actually look like?Event log -> process model
    Conformance checkingDoes reality follow the model or rule?Log + model -> deviations
    EnhancementHow can the model/process be improved?Log + model -> improved model, bottlenecks
    Prediction / monitoringWhat will happen next?Running cases -> forecasts and alerts
    💡
    Process mining shows the as-is as-it-happens, not the as-documented. It ends arguments about how the process "should" work.

    🧾 The Event Log: Minimum Data

    Every row is an event: something that happened to a case at a point in time. Three fields are mandatory.

    FieldMeaningExample
    Case IDObject the events belong toPO-4711
    ActivityWhat happenedCreate Purchase Order
    TimestampWhen it happened2026-03-02 09:14:05
    Resource (optional)Who/what did itbuyer_12
    Attributes (optional)Context: amount, country, channelEUR 12,400, DE
    event logCaseID  | Activity               | Timestamp        | Resource
PO-4711 | Create Purchase Order  | 2026-03-02 09:14 | buyer_12
PO-4711 | Approve Purchase Order | 2026-03-02 15:40 | mgr_03
PO-4711 | Goods Receipt          | 2026-03-09 11:02 | wh_07
PO-4711 | Invoice Receipt        | 2026-03-10 08:30 | ap_21
PO-4711 | Clear Invoice          | 2026-03-24 10:15 | ap_21

    A trace is the ordered sequence of activities of one case; a variant is a unique trace shared by many cases.

    🆚 Process Mining vs Other Disciplines

    DisciplineFocusDifference
    Business IntelligenceAggregated KPIsDoes not show end-to-end flow

    Task miningDesktop user actionsFine-grained clicks; mining uses system events
    RPAAutomating tasksMining finds *what* to automate
    Six SigmaSample-based analysisMining analyses 100% of cases

    Event Logs & Data Preparation

    Choosing the case notion, extracting data from source systems, fixing quality problems and staying compliant.

    🗄️ Extraction and Transformation

    Typical flow: extract tables from source systems, transform into a case / activity / timestamp structure, load into the tool, then build a data model. Roughly 60-80% of project effort is data preparation.

    ProcessTypical SAP tablesCase ID
    Purchase-to-PayEKKO / EKPO (PO header/item), EKBE (history), RBKP / RSEG (invoice), BKPF / BSEG (accounting)PO item
    Order-to-CashVBAK / VBAP (sales order), LIKP / LIPS (delivery), VBRK / VBRP (billing)Sales order item
    IT serviceTicket and change tables in ServiceNow / JiraTicket ID
    SQL sketchSELECT ebeln||ebelp AS case_id, 'Create PO Item' AS activity,
       aedat AS event_time, ernam AS resource
FROM ekpo
UNION ALL SELECT ebeln||ebelp, 'Goods Receipt', budat, ernam FROM ekbe WHERE vgabe = '1'
    📌
    Table and field names vary by system version; always confirm with the system owner.

    🧮 Choosing the Case Notion

    • Case = purchase order item shows delivery behaviour; case = invoice shows payment behaviour. Different case notions give different (all valid) views.
    • One-to-many and many-to-many relations (order lines to deliveries) cause convergence/divergence: events replicated or lost.
    • Object-centric event logs (OCEL) record multiple object types per event and avoid flattening.
    ⚠️
    Picking the wrong case ID is the number-one cause of misleading models. Validate with a process expert.

    🧹 Data Quality and Privacy

    ProblemEffectFix
    Missing timestampsBroken order, wrong durationsDerive from related tables or exclude
    Date-only timestampsMany events appear simultaneousUse secondary ordering rule or time fields
    Batch-loaded timesArtificial waiting spikesUse source event time, not load time
    Time-zone mixNegative durationsNormalise to UTC
    Duplicate eventsFake rework loopsDe-duplicate
    Incomplete casesBiased analysisFilter open vs closed cases
    • Pseudonymise personal data (resource names) to meet GDPR/privacy rules; role-based access in the tool.
    • Document data lineage so findings are auditable.

    Discovery & Variant Analysis

    Directly-follows graphs, discovery algorithms, variants, happy path, rework and bottleneck detection.

    🕸️ Process Models and Algorithms

    Model / algorithmDescriptionRemark
    Directly-Follows Graph (DFG)Nodes = activities, arcs = "A immediately followed by B" with counts/timeUsed by most commercial tools; can show spaghetti
    Petri netPlaces, transitions, tokens; formal semanticsUsed for conformance
    Alpha minerEarly algorithm based on ordering relationsSensitive to noise; teaching tool
    Heuristics minerUses frequency thresholdsHandles noise
    Inductive minerBuilds sound, block-structured models; guarantees fitnessCommon in research tools
    BPMN conversionTranslate mined model to BPMNFor documentation and redesign
    💡
    Apply the Pareto filter: show the 5-20 most frequent variants or the activities covering ~95% of cases, then drill down.

    🛣️ Variants, Happy Path and Rework

    • Happy path: the intended, most efficient sequence (often only 10-30% of cases).
    • Variant: unique sequence of activities. Hundreds of variants is normal; thousands signals poor standardization.
    • Rework: activity repeated in a case (e.g. *Change price* three times).
    • Throughput time: case start to end; waiting time: gap between consecutive events.
    variant tableVariant 1: Create PO > Approve > Goods Receipt > Invoice > Clear      42% of cases   median 11 d
Variant 2: Create PO > Goods Receipt > Invoice > Approve > Clear      9%   median 19 d  <- approval after the fact
Variant 3: Create PO > Approve > Change Price > Approve > ...          6%   median 27 d  <- rework

    🔎 Bottleneck and Performance Analysis

    1. Colour arcs by median/mean waiting time to spot the slowest transitions.
    2. Segment by attribute (country, vendor, channel, amount) to find where the delay concentrates.
    3. Compare fast vs slow cases to find differentiating attributes.
    4. Check resource workload and handover frequency (social/organizational mining).
    📌
    Use the median and percentiles (P90) as well as the mean; a few extreme cases distort averages.

    Conformance & Compliance Drift

    Checking behaviour against models and rules, measuring fitness, and detecting when real behaviour drifts away from policy.

    ✅ Conformance Checking

    TechniqueHow it works
    Token replayReplays each trace on a Petri net counting missing/remaining tokens
    AlignmentsFinds the optimal mapping of trace to model; labels deviations as log-move or model-move
    Rule-based checksDeclarative rules, e.g. "approval must precede payment", "different users create and approve"
    Quality dimensionQuestion
    FitnessCan the model replay the log? (1.0 = every trace fits)
    PrecisionDoes the model allow much more behaviour than seen?
    GeneralizationWill the model also fit unseen behaviour?
    SimplicityIs the model as simple as possible?
    💡
    Deviations come in three types: skipped (expected step missing), inserted (unexpected extra step) and wrong order.

    🛡️ Typical Compliance Checks

    ControlCheck on event data
    Four-eyes principle / SoDCreator of PO and approver are different users
    Maverick buyingInvoice or goods receipt before PO exists
    Three-way matchPO, goods receipt and invoice present before payment
    Approval limitsOrders above threshold have an approval event
    Duplicate paymentSame vendor, amount, date paid twice
    Late paymentPayment after due date
    rule exampleRule:  'Clear Invoice' must be preceded by 'Goods Receipt' and 'Approve PO'
Result: 1,284 of 24,030 cases (5.3%) violate the rule  >  EUR 3.1M exposure

    🌊 Compliance Drift (Concept Drift)

    Compliance drift is the gradual or sudden shift of real behaviour away from the approved process. In research it is called concept drift.

    Drift typePatternExample
    SuddenBehaviour changes at a point in timeNew ERP release breaks an approval step
    GradualOld and new behaviour coexistTeams slowly stop doing the check
    RecurringSeasonal return of a behaviourYear-end period-closing workarounds
    IncrementalSmall continuous steps awayShortcut grows into norm
    • Monitor the conformance rate over time per month, country and team; set alert thresholds.
    • Investigate: policy change? training gap? system defect? Or a better practice that should become the standard?

    Friction Points & Process Analytics

    Finding and quantifying friction: rework, handovers, waiting, low automation and what drives them.

    🔥 Friction Point Catalogue

    Friction pointSignal in the dataTypical cause
    Rework loopActivity repeated or revisitedMissing data, unclear specs
    Long waitHigh median gap between two activitiesApproval queue, batching
    Excessive handoversMany resource or department changes per caseUnclear ownership
    Back-and-forthA > B > A patternsRejected or incomplete input
    Manual touchesLow automation/touchless rateMissing integration
    Late eventCase misses SLABottleneck upstream
    DeviationBypassed controlsWorkaround, system limits
    ⚠️
    Friction is not always bad: a deliberate review step is a control. Separate value-adding checks from avoidable waits.

    📏 KPI Definitions

    KPIsTouchless rate   = cases with no manual event / all cases           e.g. 38%
Rework rate      = cases with a repeated activity / all cases       e.g. 21%
On-time rate     = cases finished within SLA / all cases
Avg throughput   = sum(end - start) / cases
Automation gain  = touchless-eligible cases x manual minutes x rate

    Example: 24,000 invoices a year, 21% reworked, each rework costs 18 minutes at 30 EUR/hour. Cost of rework = 24,000 x 0.21 x 0.3 h x 30 = 45,360 EUR a year.

    🧭 From Insight to Action

    1. Quantify impact in time, cost and risk for each friction point.
    2. Root-cause with attribute comparison and Lean tools (5 Whys, fishbone).
    3. Prioritise with impact-effort and strategic fit.
    4. Act: fix the process, retrain, automate, or change the rule.
    5. Monitor: keep a live dashboard to prove benefit and detect relapse.
    💡
    Pair every finding with an owner, an action and a measured target; otherwise dashboards turn into wallpaper.

    Expert: Advanced Process Analytics

    Object-centric mining, prediction, simulation, operational action, programme methodology and interview-ready summaries.

    🧠 Advanced Techniques

    • Object-centric process mining (OCPM): events link to many objects (order, item, delivery, invoice) so cross-object problems are visible without flattening.
    • Predictive process monitoring: forecast remaining time, next activity or SLA breach for running cases.
    • Simulation / digital twin: test redesigns on the discovered model before change.
    • Operational process mining: trigger actions (alerts, tasks, bots) when a live case is at risk.
    • Task mining: desktop-level capture that complements system logs for manual work.
    LevelMaturity
    DescriptiveWhat happened?
    DiagnosticWhy did it happen?
    PredictiveWhat will happen?
    PrescriptiveWhat should we do - and do it automatically?

    🗂️ Running a Process Mining Programme

    PM² (van der Aalst et al.) is a methodology with six stages: planning, extraction, data processing, mining and analysis, evaluation, process improvement and support.

    • Start with one high-volume, painful process (P2P or O2C) and a quantified business question.
    • Business case: value levers are cycle-time reduction, working-capital release, leakage prevention, compliance, automation.
    • Governance: a centre of excellence, data owners, security review, process-owner action tracking.
    • Pitfalls: tool-first thinking, wrong case ID, no business owner, insight without action, treating mining as a one-off audit.

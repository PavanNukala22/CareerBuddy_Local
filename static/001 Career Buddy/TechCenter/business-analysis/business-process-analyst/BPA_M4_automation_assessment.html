    Automation Landscape & RPA Basics

    What RPA is, its flavours, how it differs from APIs, BPM and AI, and where each fits.

    🤖 What is RPA?

    Robotic Process Automation (RPA) uses software robots ('bots') that mimic how a person works through user interfaces - clicking, typing, copying, reading screens and files - to execute rule-based digital tasks.

    TypeHow it runsBest for
    AttendedOn the employee desktop, triggered by the userFront-office help, agent assist
    UnattendedOn servers/VMs, scheduled or queue-triggered, no human presentHigh-volume back-office batches
    HybridMix: unattended run with human-in-the-loop tasksApprovals, exceptions
    ComponentRole
    Studio / DesignerWhere developers build workflows
    Orchestrator / Control RoomSchedules, queues, credentials, logs, robot management
    Robot / RunnerExecutes the workflow
    QueueHolds work items for bots (transaction-based processing)
    Credential vaultStores secrets securely
    💡
    Think of RPA as a digital employee that follows a written procedure exactly. It does not use judgement unless you add AI.

    🪜 The Automation Ladder

    RPA is a tool, not the first answer. Before building a bot, climb the ladder from cheapest and most robust:

    1. Eliminate the step (is it needed at all?).
    2. Simplify / standardize the process.
    3. Integrate with an API or native workflow.
    4. Low-code / workflow for structured approvals.
    5. RPA where no API exists or a UI is unavoidable.
    6. AI / IDP where documents or judgement are involved.
    ⚠️
    Automating a broken process only produces bad results faster. Fix, then automate.

    🧠 RPA vs IPA vs Hyperautomation

    TermMeaning
    RPARule-based UI task automation
    IPA / Intelligent AutomationRPA + AI (OCR/IDP, NLP, ML) for unstructured data and decisions
    HyperautomationCombined, orchestrated use of process mining, RPA, AI, BPM and integration to automate as much as possible
    Agentic automationAI agents that plan and act toward goals, with bots as tools and guardrails
    Process miningTask miningRPAIDPWorkflow / BPMAPIsAI agents

    Candidate Identification

    How to find, screen and rank processes that are good RPA candidates - and spot the poor ones.

    🎯 Characteristics of a Good Candidate

    CriterionGood candidatePoor candidate
    RulesClear, documented, deterministicJudgement, intuition, negotiation
    Input dataStructured, digital (Excel, forms, DB)Handwritten, unstructured, scanned (needs IDP)
    Volume / frequencyHigh and repetitiveRare or one-off
    StabilityProcess and apps change rarelyFrequent redesign, system migration
    ExceptionsLow (<15-20%) and definedHigh, unpredictable
    SystemsSeveral apps, no API, stable UISingle app with a ready API
    Human effortManual, error-prone, time-consumingAlready automated
    StandardizationSame steps across people/sitesEveryone does it differently
    📌
    Rule of thumb: high volume x high repetition x low variability x low exception rate = prime candidate.

    🔍 Discovery Methods

    • Workshops and interviews with process owners and SMEs.
    • Process mining: finds frequent, repetitive, standard paths in system logs.
    • Task mining: captures desktop activity to expose manual copy-paste work.
    • Surveys / idea portal: crowd-source ideas from staff; then validate.
    • Time-and-motion sampling: confirm real handling times.
    DocumentPurpose
    Idea intake formProcess, owner, volume, handling time, systems, pain points
    PDD (Process Definition Document)Business-level step-by-step as-is description with screenshots
    SDD (Solution Design Document)Technical design of bot, exceptions, configuration
    To-be processRedesigned flow that includes bot hand-offs

    📊 Scoring and Prioritisation

    weighted scoringCriterion              Weight  Score(1-5)  Weighted
Rule-based               25%       5         1.25
Volume / frequency       20%       4         0.80
Process stability        15%       4         0.60
Digital structured input 15%       5         0.75
Low exception rate       15%       3         0.45
Business value (savings) 10%       4         0.40
Total                100%                4.25 / 5  >  proceed to feasibility

    Plot candidates on a value vs complexity matrix: *high value / low complexity* are quick wins, *high value / high complexity* are strategic projects, *low value / high complexity* are rejected.

    💡
    Use a stage-gate: idea > qualified > PDD > feasibility > business case > build. Most ideas should drop out early.

    Feasibility & Process Readiness

    Technical, process and compliance checks that decide whether a candidate can be automated reliably.

    🔧 Technical Feasibility

    CheckQuestionRisk if ignored
    UI accessibilityCan bot read elements (selectors, DOM) or only images (Citrix/remote desktop)?Fragile image-based automation
    API availabilityDoes a supported API/integration exist?Building RPA when API is cheaper
    Data formatExcel/CSV/XML/DB vs PDF scans?Need IDP; accuracy and cost rise
    EnvironmentDev / test / prod parity; test data available?Cannot test safely
    Volumes & peaksQueue sizing, SLA windows, bot runtimeMissed deadlines
    AuthenticationMFA, CAPTCHA, shared accounts?Bots blocked or non-compliant
    Change calendarPlanned system upgrades?Rework soon after go-live
    ⚠️
    CAPTCHA is designed to stop bots; do not try to bypass it. Request an API or service account instead.

    🧱 Process Readiness and Sizing

    • Process is documented, stable for 3+ months and has a named process owner.
    • Exceptions are enumerated, with a rule for each (business exception) or an escalation (system exception).
    • Process has been simplified first: duplicated checks and unnecessary approvals removed.
    • Data quality is acceptable; garbage in will give garbage out at bot speed.
    SizeTypical traitsBuild effort (indicative)
    Small<=20 steps, 1-2 apps, <5 exception rules2-4 weeks
    Medium20-60 steps, 3-4 apps, up to ~10 exception rules4-8 weeks
    Large>60 steps, 5+ apps, many rules, AI components8+ weeks

    🛡️ Security, Risk and Compliance

    • Bots get dedicated service accounts with least privilege, stored in a credential vault; no shared human logins.
    • Segregation of duties: a bot should not both create and approve the same transaction.
    • Full audit log of every bot action; PII handled per GDPR/privacy policy.
    • Business continuity: manual fallback procedure and monitoring for bot failure.
    • Licence and vendor terms checked for each application the bot touches.

    Cost-Benefit & ROI Analysis

    Total cost of ownership, benefit types, FTE maths, ROI, payback, NPV and sensitivity analysis with a worked example.

    💸 Cost and Benefit Components

    CostsBenefits
    Licences (developer, bot/runner, orchestrator, AI/IDP)Capacity released (FTE-equivalent hours)
    Infrastructure (VMs, cloud, environments)Error and rework reduction
    Development, testing and project managementFaster cycle time and SLA compliance
    Change management and trainingCompliance and audit quality
    Support, monitoring and maintenance (often 15-25% of build per year)24/7 scalability, peak handling
    CoE overhead and governanceEmployee experience - redeployed to higher-value work
    💡
    Count hard benefits (cost out, cost avoided) separately from soft benefits (capacity, satisfaction). Finance usually accepts only hard ones in the business case.

    🧮 Formulas and Worked Example

    formulasHours saved  = automated volume x manual handling time
FTE saved    = hours saved / productive hours per FTE (about 1,600 per year)
ROI          = (total benefit - total cost) / total cost
Payback      = initial investment / net annual benefit
NPV          = sum( net cash flow_t / (1+r)^t )
    exampleVolume 60,000 invoices/yr | manual time 8 min | straight-through rate 80%
Automated = 48,000 x 8 min = 384,000 min = 6,400 h   >   FTE saved = 6,400 / 1,600 = 4.0 FTE
Benefit/yr  = 4.0 x 40,000 + error-cost saving 20,000 = 180,000
Costs       = build 70,000 once; run 60,000/yr (licences 30k + infra 10k + support 20k)
Net annual  = 180,000 - 60,000 = 120,000
Payback   = 70,000 / 120,000 = 0.58 yr  (about 7 months)
3-yr ROI  = (3 x 180,000 - (70,000 + 3 x 60,000)) / 250,000 = 290,000 / 250,000 = 116%
NPV (10%) = -70,000 + 120,000 x (0.909 + 0.826 + 0.751) = about 228,400

    🎚️ Sensitivity and Common Pitfalls

    • Test the case with straight-through rate 60 / 70 / 80%; exceptions erode benefit quickly.
    • Test volume decline, extra maintenance (UI change) and licence price changes.
    • Pitfall: counting 100% of FTE time as saved - freed minutes are scattered across people and are rarely cashable.
    • Pitfall: ignoring bot idle time, exception handling effort and monitoring cost.
    • Rule: if payback > 18-24 months or benefit is mostly soft, challenge the candidate.
    📌
    Re-measure benefit 6 months after go-live; this builds credibility and improves future estimates.

    Governance, Operating Model & Scaling

    CoE, delivery lifecycle, bot monitoring and the risks that make automation programmes fail.

    🏢 Centre of Excellence and Lifecycle

    Lifecycle stageActivities
    DiscoverIdentify and qualify ideas, PDD
    DesignSDD, exception handling, test cases
    BuildDevelop reusable components with naming and logging standards
    TestUnit, SIT, UAT, performance
    DeployRelease management, hypercare
    OperateMonitoring, incident handling, optimisation
    RetireDecommission when process or system changes
    • CoE owns standards, reusable libraries, vendor management, security and the pipeline.
    • Federated model: CoE governs, business units contribute citizen developers within guardrails.

    ⚠️ Risks and Failure Reasons

    RiskMitigation
    Bot breaks after UI changeRobust selectors, API where possible, change alerts, regression tests
    Poor process choiceStage-gate scoring, process owner sign-off
    Overstated benefitsFinance validation, post-implementation review
    Shadow automationCentral registry, governance, tool policy
    Credential leaksVault, least privilege, rotation
    Low adoption / fearEarly communication, reskilling, redeployment plan
    Scaling without maintenance budgetRing-fence 15-25% run cost
    ⚠️
    The most common cause of failure is not technology but poor candidate selection and no owner after go-live.

    📈 Operational KPIs

    • Bot utilisation = productive runtime / available runtime.
    • Straight-through processing (STP) rate and exception rate.
    • Bot success rate / MTBF, queue ageing, SLA hit rate.
    • Benefit realisation vs business case, and cost per transaction (bot vs human).

    Expert: Intelligent Automation Decisions

    Choosing between eliminate / API / RPA / AI, intelligent document processing, portfolio governance and interview summaries.

    🧭 Automation Decision Framework

    SituationPreferred solution
    Step adds no valueEliminate
    Process is messy and variableSimplify and standardize first
    System offers a stable API / webhookIntegrate via API or iPaaS
    Approval-routing, forms, structured flowWorkflow / low-code
    No API, stable UI, rules clearRPA
    Unstructured documents or emailsIDP / NLP + RPA
    Judgement with data and policyML decision support, human in the loop
    Open-ended goals, multi-step reasoningAgentic AI with guardrails and approvals
    💡
    Prefer, in order: Eliminate > Simplify > Integrate > Automate. Use RPA as a bridge, not a permanent architecture.

    📄 IDP and Accuracy Maths

    • Intelligent Document Processing = OCR + ML extraction + validation + human review.
    • Accuracy metrics: extraction accuracy per field, confidence threshold, and human-in-the-loop share.
    IDP impactInvoices 60,000 | extraction confidence >= 90% for 75% of documents (auto) | 25% reviewed (2 min each)
Review effort = 60,000 x 0.25 x 2 min = 30,000 min = 500 h  vs manual entry 60,000 x 6 min = 6,000 h  (92% less)
    📌
    Include review effort and retraining cost in the business case; AI is not 100% touchless.

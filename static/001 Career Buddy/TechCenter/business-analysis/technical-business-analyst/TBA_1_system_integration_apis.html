    Course Overview

    System Integration & APIs for Technical Business Analysts: from first interface conversation to a tested, resilient integration.

    📘 Course Overview

    • Teaches a BA to specify, read, test and troubleshoot integrations between systems: REST, SOAP, JSON/XML, Postman and integration patterns.
    • Outcome: produce an interface specification a developer can build from without a meeting, and verify the built API against it.

    • Basic HTTP knowledge (URL, headers, body), comfort with spreadsheets and BPMN/UML.
    • Install Postman (or SoapUI) and a JSON-aware editor; access to any public sandbox API.
    • No coding required; reading JavaScript snippets helps for Postman tests.

    Fundamentals & Core Concepts

    The vocabulary and principles every integration discussion depends on.

    🧱 Fundamentals

    • Client, server, endpoint, contract, payload, protocol, serialization.
    • HTTP anatomy: method, path, query, headers, body, status. TLS protects transport.
    • Synchronous vs asynchronous, stateless vs stateful, coupling and cohesion.

    🧠 Core Concepts

    • Idempotency: same call repeated yields same effect (PUT, DELETE; POST needs a key).
    • Contract-first: OpenAPI/WSDL agreed before build.
    • Backward compatibility: additive changes are safe; rename, remove or retype is breaking.
    • Eventual consistency: async systems converge, not instantly.

    🗂️ Topics & Subtopics

    • REST payloads: resources, methods, status codes, pagination, versioning, error model.
    • SOAP/WSDL: envelope, header, body, XSD, faults, WS-Security.
    • JSON/XML: JSONPath, XPath, namespaces, JSON Schema, XSD, null vs missing.
    • Postman: collections, environments, scripts, Newman, mocks, Pact.
    • Patterns and security: webhooks, queues, batch, OAuth2, JWT, mTLS, circuit breaker, DLQ.

    REST API Payload Structure

    Advanced, interview-ready depth for BAs working with integrations — what it is, why, how it works, how to use it, mistakes, real-world usage.

    🌐 REST: anatomy of a request and response

    PointDetail
    What it isREST is an architectural style where resources (nouns such as /orders/42) are manipulated through standard HTTP methods. Payloads are usually JSON. A BA reads and specifies the contract: URL, method, headers, query/path params, request body, response body, status codes.
    Why it is usedMost modern integrations (web, mobile, SaaS, microservices) expose REST. A BA who can read a payload can find missing fields, wrong data types and unclear business rules before development starts.
    How it worksClient sends METHOD /path?query + headers + optional body. Server returns a status code, headers and body. REST is stateless (each call carries its own auth/context), cacheable (GET), and uses hypermedia/links optionally (HATEOAS).
    How to use itFor every endpoint document: purpose, auth, method/URL, params with type/required/format/example, request schema, response schema per status, error model, idempotency, rate limits, versioning.
    Common mistakesVerbs in URLs (/getOrder), 200 OK with an error inside the body, mixing snake_case and camelCase, nullable vs missing field confusion, dates without timezone, money as float, no pagination on list endpoints.
    Real-world usageOrder service: POST /v1/orders creates an order, returns 201 Created + Location header; payment service is called via POST /v1/payments. BA maps each business field to a JSON attribute.
    Interview pointsExplain PUT vs PATCH, idempotency, why 401 differs from 403, how you would version an API, and how you spot a breaking change.

    🧱 HTTP methods, status codes and idempotency

    MethodPurposeSafeIdempotentTypical success
    GETRead a resource / listYesYes200
    POSTCreate or trigger an actionNoNo (needs idempotency key)201 / 202
    PUTReplace whole resourceNoYes200 / 204
    PATCHPartial updateNoNot guaranteed200 / 204
    DELETERemove resourceNoYes204
    CodeMeaningBA scenario
    400Malformed request / validationMissing mandatory field
    401Not authenticatedToken missing/expired
    403Authenticated but not allowedRole lacks permission
    404Resource not foundUnknown order id
    409ConflictDuplicate or version clash

    💡
    Retry-safe design: clients may retry on timeout, so POST payments must accept an Idempotency-Key header; the server stores key → result and replays it instead of charging twice.

    📦 Annotated REST payload and error model

    jsonPOST /v1/orders          Authorization: Bearer <token>
Content-Type: application/json   Idempotency-Key: 7c1e-...-a9
{
  "customerId": "C-1001",
  "currency": "INR",
  "items": [ { "sku": "SKU-77", "qty": 2, "unitPrice": "499.00" } ],
  "deliveryDate": "2026-10-12T10:00:00+05:30",   // ISO-8601 with offset
  "notes": null                                   // null = explicitly empty
}
--- 201 Created ---
{ "orderId": "O-9001", "status": "PENDING_PAYMENT", "total": "998.00" }
--- 422 Unprocessable ---
{ "type": "https://api.x.com/errors/validation", "title": "Invalid order",
  "status": 422, "errors": [ { "field": "items[0].qty", "code": "MIN_1" } ] }
    • Money as string/decimal, never float; dates ISO-8601 with offset; enums documented with allowed values.
    • Pagination: offset (?page=2&size=50) vs cursor (?after=abc) — cursor is stable under inserts and preferred at scale.
    • Versioning: URL (/v2), header or media type; additive changes are non-breaking, removing/renaming/retyping a field is breaking.
    • Error model: consistent structure (RFC 7807 problem+json) with machine-readable code, human title, per-field errors, and a correlation id.

    SOAP & WSDL

    Advanced, interview-ready depth for BAs working with integrations — what it is, why, how it works, how to use it, mistakes, real-world usage.

    🧼 SOAP: contract-first enterprise integration

    PointDetail
    What it isSOAP is an XML-based messaging protocol. Every message is an Envelope with optional Header (security, routing, transaction) and mandatory Body. The service is described by a WSDL and data types by XSD.
    Why it is usedBanking, insurance, telecom and government systems rely on SOAP for strict contracts, WS-Security, WS-ReliableMessaging and formal error handling (Fault). Many legacy cores will never be REST.
    How it worksWSDL defines types (XSD), message, portType (operations), binding (SOAP/HTTP) and service (endpoint). A client generates stubs from the WSDL, posts an XML envelope (usually HTTP POST) and receives a response or a soap:Fault.
    How to use itGet the WSDL, import it into Postman/SoapUI, inspect operations, build sample requests, validate against the XSD, map each element to business data, note namespaces and mandatory vs optional (minOccurs).
    Common mistakesIgnoring namespaces, sending wrong SOAPAction, treating HTTP 200 as success (faults can return 500 or 200), missing xsi:nil vs empty element, not versioning the WSDL, hand-editing generated stubs.
    Real-world usageCore-banking balance enquiry via GetAccountBalance; WS-Security UsernameToken or signed timestamp in the Header; MTOM for attachments.
    Interview pointsCompare REST and SOAP, define WSDL/XSD, explain a SOAP Fault, and say when you would wrap a SOAP service behind a REST façade.

    ⚖️ REST vs SOAP: choose with reasons

    AspectRESTSOAP
    FormatJSON (also XML, others)XML only
    ContractOpenAPI (optional, code-first or design-first)WSDL + XSD (mandatory, strict)
    TransportHTTP mostlyHTTP, JMS, SMTP
    SecurityOAuth2/JWT, TLSWS-Security (message-level) + TLS
    ErrorsHTTP status + bodysoap:Fault
    Transactions/reliabilityDesign yourself (idempotency, sagas)WS-AtomicTransaction, WS-ReliableMessaging
    WeightLight, cache-friendlyHeavier, tooling-driven
    xml<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope"
               xmlns:acc="http://bank.example/account/v2">
  <soap:Header> <wsse:Security>...</wsse:Security> </soap:Header>
  <soap:Body>
    <acc:GetAccountBalanceRequest>
      <acc:accountNo>001234567</acc:accountNo>
    </acc:GetAccountBalanceRequest>
  </soap:Body>
</soap:Envelope>
    📌
    A BA documents SOAP integrations as a field-mapping table: source field → XPath in the envelope → type/length → mandatory → transformation rule → error handling.

    JSON / XML Parsing

    Advanced, interview-ready depth for BAs working with integrations — what it is, why, how it works, how to use it, mistakes, real-world usage.

    🧩 Parsing and mapping payloads

    PointDetail
    What it isParsing converts text payloads into a navigable structure so values can be read, validated and transformed. JSON uses objects/arrays; XML uses elements, attributes and namespaces. Paths: JSONPath ($.items[*].sku) and XPath (//item/@sku).
    Why it is usedIntegrations fail on small data issues: wrong type, null vs missing, nested arrays, namespaces. BAs write mapping specs and test data, so they must read nested structures confidently.
    How it worksTokenise → build tree → query by path → validate with a schema (JSON Schema / XSD) → transform (e.g. JSON↔XML, field rename, enrichment). Streaming parsers (SAX/streaming JSON) handle very large files.
    How to use itTake a sample response, list every leaf field, mark type/length/required, define the path, add transformation + default + validation rule, and cover edge cases: empty array, null, extra unknown field, special characters, UTF-8.
    Common mistakesAssuming array always has one element, ignoring XML namespaces in XPath, number precision loss (large ids as numbers), trailing commas / comments in JSON, CDATA mishandling, date format mismatch.
    Real-world usageMapping a vendor JSON order to an internal XML message for an ERP: items[].qty → <Line><Quantity>; unit codes converted via lookup table; missing notes defaults to empty.
    Interview pointsDifferentiate JSON vs XML, attribute vs element, explain JSON Schema and XSD, and write a JSONPath to pull all SKUs priced above 500.

    🧬 Side-by-side example and schema validation

    JSON

    • Lightweight, native in JS
    • No comments, no namespaces
    • Types: string, number, boolean, null, object, array
    • Schema: JSON Schema (draft 2020-12)

    XML

    • Verbose, self-describing
    • Attributes, namespaces, comments, mixed content
    • All values are text; types come from XSD
    • Strong tooling: XSLT, XPath, XQuery
    json-schema{
  "type": "object", "required": ["customerId","items"],
  "properties": {
    "customerId": { "type": "string", "pattern": "^C-\\d{4}$" },
    "items": { "type": "array", "minItems": 1,
      "items": { "type": "object",
        "properties": { "qty": { "type": "integer", "minimum": 1 } } } }
  },
  "additionalProperties": false
}
    jsonpath / xpath$.items[?(@.unitPrice > 500)].sku          // JSONPath filter
//Line[Quantity > 1]/@sku                   // XPath predicate
//*[local-name()='Line']                    // ignores namespace prefix
    ⚠️
    null, empty string "", 0 and absent field are four different states. Always specify which one the business means (e.g., "no discount" = field omitted vs 0).

    Postman Contract Testing

    Advanced, interview-ready depth for BAs working with integrations — what it is, why, how it works, how to use it, mistakes, real-world usage.

    🧪 API contract testing with Postman

    PointDetail
    What it isA contract test verifies that an API honours its agreed interface: URL, headers, status codes, schema, data types and business invariants. Postman groups requests into collections with environments, variables, pre-request scripts and tests (JavaScript).
    Why it is usedCatches breaking changes early, lets BAs prove acceptance criteria against the real endpoint, and gives dev/QA a shared executable specification.
    How it worksImport OpenAPI/WSDL → collection. Set environment variables ({{baseUrl}}, {{token}}). Pre-request script prepares data/auth; the Tests tab asserts with pm.test and pm.expect; collection runner / Newman (CLI) executes in CI; monitors run on a schedule.
    How to use it1) Positive path per operation. 2) Negative cases (400/401/403/404/422). 3) Schema validation. 4) Boundary values. 5) Chain requests (create → get → delete) using saved variables. 6) Data-driven runs with CSV/JSON.
    Common mistakesHard-coded tokens/URLs, only checking status 200, no cleanup of created data, tests dependent on run order, secrets committed in exported collections, ignoring response time and headers.
    Real-world usageBA validates acceptance criteria "invalid quantity returns 422 with field error" before UAT; the same collection runs in the pipeline on every build.
    Interview pointsDifferentiate contract, integration and end-to-end tests; explain environments vs globals; describe how Newman fits CI; how you test an OAuth2-protected API.

    📜 Test script patterns

    javascript (Postman Tests tab)pm.test("Status is 201 and fast", () => {
  pm.response.to.have.status(201);
  pm.expect(pm.response.responseTime).to.be.below(800);
});
const body = pm.response.json();
pm.test("Schema & business rule", () => {
  pm.expect(body).to.have.property("orderId").that.is.a("string");
  pm.expect(parseFloat(body.total)).to.equal(998.00);
  pm.expect(body.status).to.be.oneOf(["PENDING_PAYMENT","CONFIRMED"]);
});
pm.test("Matches contract", () =>
  pm.response.to.have.jsonSchema(pm.collectionVariables.get("orderSchema")));
pm.collectionVariables.set("orderId", body.orderId);   // chain to next request
    💡
    Use Newman in CI: newman run orders.postman_collection.json -e uat.postman_environment.json --reporters cli,junit. Failing contract tests should block the build.
    • Consumer-driven contracts (Pact) invert ownership: consumers publish expectations, providers verify them.
    • Mock servers let front-end/BA validate the contract before the backend exists.
    • Run negative security checks: expired token → 401, other tenant's id → 403/404.

    🔌 Integration patterns every BA must name

    PatternWhat it meansUse whenRisk / BA question
    Synchronous request-responseCaller waits for answerNeed immediate result (price check)Timeouts, cascading failure – what is the SLA?
    Asynchronous messagingFire and forget via queue/topicLong tasks, decoupling, spikesOrdering, duplicates, eventual consistency
    Webhook / callbackProvider calls you on eventPayment status, shipment updatesSignature check, retries, replay
    Batch / file (SFTP, CSV)Scheduled bulk transferLegacy, large volumes, reconciliationLatency, partial failure, restart/rerun
    API gateway / façadeSingle entry point, auth, throttlingMany consumers, legacy behind modern APISingle point of failure
    ETL / ELTExtract, transform, load to warehouseAnalytics, migrationData quality, mapping rules, lineage
    📌
    Ask for every interface: who calls whom, trigger, frequency, volume, payload size, sync/async, timeout, retry, error handling, ownership, environment, SLA. This is an *interface specification checklist*.

    🔐 Authentication, authorization and resilience

    TopicDetail
    API keyIdentifies the app, not the user; weak alone
    Basic / BearerCredentials or token in Authorization header over TLS
    OAuth 2.0Delegated authorization: grants (authorization code + PKCE, client credentials), scopes, access/refresh tokens
    OpenID Connect / JWTIdentity layer; JWT = signed claims (sub, exp, scope) verified by signature
    mTLSBoth sides present certificates – service-to-service
    Rate limit / throttling429 + Retry-After; protects the provider
    Retry + backoff + jitterRetry only idempotent or keyed calls
    Circuit breaker, timeout, bulkheadStop cascading failures; fail fast with fallback
    Dead-letter queuePark poison messages for analysis
    sequence (OAuth2 client credentials)Client  -> Auth server : POST /token  grant_type=client_credentials, scope=orders.write
Auth    -> Client      : { access_token: JWT, expires_in: 3600 }
Client  -> API         : POST /v1/orders  Authorization: Bearer JWT
API     -> Client      : 201 (or 401 expired / 403 missing scope)

    Interview rapid-fire

    • What is the difference between authentication and authorization? (who you are vs what you may do)
    • How do you make a payment call safe to retry? (idempotency key + server-side dedupe)
    • What belongs in an API error contract? (stable code, message, field, correlation id)
    • Which non-functional requirements would you capture for an integration? (latency, throughput, availability, security, audit, data retention)

    Tools, Quality & Best Practices

    Tooling, test strategy and design rules.

    🔧 Tools & Workflows

    • Postman, Newman, SoapUI, Swagger/OpenAPI editor, JSONPath/XPath testers, Wireshark/Fiddler for traffic.
    • Workflow: gather requirement → draw sequence diagram → write OpenAPI/field map → mock → review with dev → contract tests → UAT evidence.
    • Version everything in Git; export collections without secrets.

    ✅ Testing & Quality

    • Test pyramid: contract tests (fast, many) → integration → end-to-end (few).
    • Cover positive, negative, boundary, security (expired token, other tenant), performance (latency budget) and resilience (timeout, 503).
    • Definition of done: schema valid, error model consistent, idempotency proven, test collection in CI.

    ⭐ Best Practices

    • Design-first contracts; examples for every field; document enums and null semantics.
    • Money as decimal string, dates ISO-8601 with offset, ids as strings.
    • Consistent error model with correlation id; never return 200 for failures.
    • Capture NFRs: latency, throughput, availability, retention, audit.
    • Never hard-code secrets; least-privilege scopes.

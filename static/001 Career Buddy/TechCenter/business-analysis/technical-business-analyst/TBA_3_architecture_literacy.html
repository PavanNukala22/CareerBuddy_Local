    Microservices

    Advanced, interview-ready depth on architecture for BAs — what it is, why, how it works, how to use it, mistakes, real-world usage.

    🧱 Microservices architecture

    PointDetail
    What it isAn application built as small, independently deployable services, each owning one business capability (Orders, Payments, Inventory) and its own data store, communicating over APIs or events.
    Why it is usedIndependent releases, team autonomy, targeted scaling, fault isolation and technology freedom. It suits large, fast-changing domains with many teams.
    How it worksServices are bounded by Domain-Driven Design bounded contexts. Clients go through an API gateway; services find each other via service discovery; each has its own DB (database-per-service). Cross-service consistency uses sagas, not distributed ACID transactions. Observability = logs, metrics, traces with a correlation id.
    How to use itIdentify business capabilities → draw context map → define each service's API/events and data ownership → decide sync vs async → state NFRs per service (SLA, scale, RTO/RPO) → plan testing (contract tests) and deployment (containers, CI/CD).
    Common mistakesDistributed monolith (shared DB, chatty calls), services split by technical layer not business capability, too fine-grained nanoservices, ignoring data consistency, no versioning, no observability, adopting it for a tiny team.
    Real-world usageRetail platform: Catalog, Cart, Order, Payment, Shipping services; checkout calls Order synchronously, while Shipping and Notification react to OrderPlaced events.
    Interview pointsMonolith vs microservices trade-offs; how you handle a transaction across services (saga); API gateway vs service mesh; why database-per-service; how you identify service boundaries.

    ⚖️ Monolith vs microservices and BA responsibilities

    Monolith

    • Single deployable, one DB
    • Simple to build/test/debug early
    • ACID transactions are easy
    • Scales as a whole; large change blast-radius

    Microservices

    • Many deployables, DB per service
    • Operational complexity (network, tracing, CI/CD)
    • Eventual consistency, sagas
    • Scale and release independently

    Entry pointAPI gateway (auth, throttling, routing)Which consumers and what limits?

    ⚠️
    If two services always change together or share one table, you likely built a distributed monolith. Boundaries should follow business capabilities and ownership.

    📣 Event-driven architecture (EDA)

    PointDetail
    What it isComponents communicate by publishing events (facts that happened: OrderPlaced) to a broker (Kafka, RabbitMQ, SNS/SQS, Azure Service Bus/Event Grid); interested consumers react independently.
    Why it is usedLoose coupling, scalability for bursts, easy to add new consumers, natural audit trail, resilience (consumers can be down and catch up).
    How it worksProducer → topic/queue → consumers. Queue = one consumer processes each message; topic/pub-sub = many subscribers. Kafka keeps an ordered, replayable log partitioned by key; consumer groups share partitions. Delivery guarantees: at-most-once, at-least-once (default; needs idempotent consumers), exactly-once (limited, costly).
    How to use itName events in past tense, define schema (JSON/Avro) with a version, set key and ordering needs, decide retry/dead-letter policy, define SLAs for lag, and document who produces and consumes each event.
    Common mistakesTreating events as commands, no schema versioning, assuming ordering across partitions, no idempotency (duplicates double-charge), missing DLQ, giant events with sensitive data, hidden coupling through payload shape.
    Real-world usagePaymentCaptured triggers Order confirmation, Invoice generation, Loyalty points and Analytics – each team owns its consumer; replay rebuilds a read model after a bug fix.
    Interview pointsEvent vs command vs message; orchestration vs choreography; how to get idempotency; what outbox pattern solves; eventual consistency and how UI copes.

    🔁 Patterns: saga, outbox, idempotency

    flow (order saga, choreography)Order      : publishes OrderPlaced

    Cloud: AWS / Azure Concepts

    Advanced, interview-ready depth on architecture for BAs — what it is, why, how it works, how to use it, mistakes, real-world usage.

    ☁️ Cloud architecture components

    PointDetail
    What it isCloud platforms rent compute, storage, networking and managed services on demand. BAs need the vocabulary and the shared-responsibility model, not the console clicks.
    Why it is usedElastic scale, pay-per-use, global reach, managed reliability and faster delivery. Requirements about availability, cost, compliance and data residency map directly to cloud design choices.
    How it worksResources live in regions (with multiple availability zones) inside a virtual network. Traffic flows through load balancers to compute; data sits in managed stores; identity (IAM) controls who can do what; monitoring and autoscaling keep it healthy.
    How to use itTranslate each NFR to a capability: availability → multi-AZ; DR → backup/replica in second region with defined RTO/RPO; security → IAM least privilege, encryption, private networking; cost → right-sizing, reserved/spot, budgets and tags.
    Common mistakesLift-and-shift without redesign, single AZ, public storage buckets, over-privileged roles, no cost limits, ignoring egress charges and data residency, treating DR as "we have backups".
    Real-world usageWeb app on ALB → ECS/AKS containers → RDS/Azure SQL, files in S3/Blob, async work via SQS/Service Bus, secrets in Secrets Manager/Key Vault, observability in CloudWatch/Azure Monitor.
    Interview pointsIaaS vs PaaS vs SaaS; region vs AZ; RTO vs RPO; horizontal vs vertical scaling; serverless trade-offs; shared responsibility.

    Quality Attributes & Trade-offs

    Advanced, interview-ready depth on architecture for BAs — what it is, why, how it works, how to use it, mistakes, real-world usage.

    🏛️ Non-functional requirements drive architecture

    PointDetail
    What it isQuality attributes (performance, scalability, availability, security, maintainability, observability, cost) are the architecturally significant requirements that shape structure more than features do.
    Why it is usedA vague NFR leads to over- or under-engineering. Quantified NFRs let architects justify choices and testers verify them.
    How it worksWrite each as a scenario: source, stimulus, environment, response, measure. Architects choose tactics (cache, queue, replica, circuit breaker) and accept trade-offs (consistency vs availability per CAP, latency vs cost).
    How to use itCapture volumes, peaks, growth, SLAs, compliance, RTO/RPO, data residency; prioritise the top 3 qualities; review with the architect; feed into acceptance tests and monitoring/alerts.
    Common mistakes"System must be fast/secure", copying NFRs from another project, forgetting peak seasons, no observability requirement, ignoring operational cost.
    Real-world usageFlash-sale: 20× peak for 30 min → autoscale, queue-based order intake, cache catalogue, CDN; accept eventual stock count display.
    Interview pointsCAP and PACELC in plain words; scale up vs out; caching layers and invalidation; sync vs async trade-off; how you elicit and quantify NFRs.

    Rapid-fire Q&A

    • Monolith or microservices for a 5-person startup? Start modular monolith; split when team/scale demands.
    • What does eventual consistency mean for the UI? Show pending states, idempotent retries, and reconcile.
    • How do you document architecture as a BA? Context + container diagrams (C4), sequence diagrams, interface catalogue, NFR table, decision log (ADR).
    • What is an ADR? A short record of a decision, its context, options and consequences.

    Tools, Quality & Best Practices

    Tooling, test strategy and rules of thumb.

    🔧 Tools & Workflows

    • Diagram tools (C4, draw.io), cloud consoles, observability (logs, metrics, traces), IaC (Terraform), CI/CD.
    • Workflow: capture NFRs, sketch context and container views, review trade-offs, record ADRs, validate with load and failure tests.

    ✅ Testing & Quality

    • Test resilience: kill a service, inject latency, replay events, fail over a region.
    • Verify SLOs with dashboards, alerts and error budgets; test security with scoped roles.

    ⭐ Best Practices

    • Prefer the simplest architecture that meets NFRs; avoid premature microservices.
    • Design for failure; make consumers idempotent; own data per service; tag resources; record every decision in an ADR.

    Troubleshooting, Interview Prep & Summary

    Diagnose problems, rehearse interviews, consolidate.

    🩺 Common Errors & Troubleshooting

    • Distributed monolith: services share a database or release together.
    • Duplicate events: consumer not idempotent.
    • Cascading outage: no timeouts or circuit breaker.
    • Surprise bill: unbounded scaling or data egress.

    🎤 Interview Preparation

    • Microservices vs monolith trade-offs; how to handle a distributed transaction; at-least-once vs exactly-once.
    • How would you pick between SQS-style queues and pub/sub topics? Explain RPO vs RTO.

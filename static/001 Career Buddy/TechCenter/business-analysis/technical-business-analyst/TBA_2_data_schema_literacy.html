    Course Overview

    Read, query, model and quality-check data so requirements, mappings and reports are precise.

    📘 Course Overview

    • Teaches a BA to query, model and validate data: SQL joins, aggregates, window functions, ERDs, mapping documents, data dictionaries and query tuning.
    • Outcome: answer business questions with correct SQL, specify schemas and mappings developers can build from, and spot data-quality risks early.

    • Choose the right JOIN and predict row counts before running a query.
    • Build aggregates and window-function reports (running totals, rank, lag/lead).

    • Write a mapping sheet and data dictionary; define DQ rules; read an execution plan.

    🧾 Prerequisites

    • Basic spreadsheet skills and familiarity with tables, rows and columns.
    • Access to any SQL sandbox (PostgreSQL, MySQL, SQLite, SQL Server).
    • No programming background required.

    Fundamentals & Core Concepts

    Vocabulary and principles the rest of the module builds on.

    🧱 Fundamentals

    • Relational model: table, row, column, primary key, foreign key, constraint, index, NULL.
    • SQL families: DQL (SELECT), DML (INSERT/UPDATE/DELETE), DDL (CREATE/ALTER), DCL, TCL.
    • Logical query order: FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.

    🧠 Core Concepts

    • Grain: what one row means; most wrong numbers come from a misunderstood grain.
    • Cardinality: 1:1, 1:N, M:N drives join fan-out and double counting.
    • Normalisation (1NF-3NF) removes redundancy; denormalisation speeds reads.
    • NULL is unknown: NULL = NULL is not true; use IS NULL.

    🗂️ Topics & Subtopics

    • Joins: INNER, LEFT, RIGHT, FULL, CROSS, SELF, anti-join, semi-join.
    • Aggregation: GROUP BY, HAVING, COUNT(DISTINCT), conditional aggregation.
    • Windows: ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, SUM() OVER.
    • Modelling: ERD, star schema, SCD types; Quality: profiling, mapping, dictionary.

    SQL Joins

    Advanced, interview-ready depth on SQL and data modelling for BAs — what it is, why, how it works, how to use it, mistakes, real-world usage.

    🔗 Relational querying and joins

    PointDetail
    What it isA relational database stores data in tables (rows/columns) linked by keys. A JOIN combines rows from two or more tables on a matching condition so business questions spanning entities can be answered.
    Why it is usedBAs validate data, reconcile reports, investigate defects, write UAT data checks and define mapping rules. Reading SQL removes dependence on developers for simple facts.
    How it worksThe engine builds a result by matching join keys. Logical order: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Optimisers pick nested-loop, hash or merge joins; indexes on join keys make them fast.
    How to use itState the business question → identify entities/tables → find keys (PK/FK) → choose join type by "do I keep unmatched rows?" → filter → verify row counts against a known total.
    Common mistakesJoin fan-out (1-to-many inflates SUM), WHERE on the right table turning a LEFT JOIN into INNER, joining on non-unique keys, NOT IN with NULLs, SELECT *, forgetting date/time-zone boundaries.
    Real-world usage"Customers who ordered but never paid": customers LEFT JOIN payments … WHERE payments.id IS NULL (anti-join) – a standard reconciliation check.
    Interview pointsExplain each join type with a Venn or example; INNER vs LEFT; anti-join; self-join; why row count changes after a join; WHERE vs HAVING.

    🧮 Join types with examples

    JoinReturnsTypical use
    INNEROnly matching rowsOrders with valid customer
    LEFTAll left + matches (NULL if none)All customers incl. no orders
    RIGHTAll right + matchesRare; swap tables and use LEFT
    FULL OUTERAll rows from bothReconcile two systems
    CROSSCartesian productGenerate calendar × product grid
    SELFTable joined to itselfEmployee → manager hierarchy
    SEMI (EXISTS)Left rows that have a match, no duplicatesCustomers with at least one order
    ANTI (LEFT … IS NULL)Left rows with no matchOrphans, missing data
    sql-- Customers with no orders in 2026 (anti-join)
SELECT c.customer_id, c.name
FROM   customers c
LEFT JOIN orders o
       ON o.customer_id = c.customer_id
      AND o.order_date >= DATE '2026-01-01'   -- filter in ON, not WHERE
WHERE  o.order_id IS NULL;

-- Employee and manager (self join)
SELECT e.name AS employee, m.name AS manager
FROM employees e LEFT JOIN employees m ON e.manager_id = m.emp_id;
    ⚠️
    Fan-out trap: joining orders to order_items then SUM(orders.total) counts each order once per item. Aggregate items first in a sub-query/CTE, or sum at the correct grain.

    Aggregations & Window Functions

    Advanced, interview-ready depth on SQL and data modelling for BAs — what it is, why, how it works, how to use it, mistakes, real-world usage.

    📊 GROUP BY, HAVING and analytic queries

    PointDetail
    What it isAggregation collapses many rows into summary rows (COUNT, SUM, AVG, MIN, MAX). Window functions compute values across related rows *without* collapsing them (ROW_NUMBER, RANK, LAG, SUM() OVER).
    Why it is usedKPIs, reconciliation totals, duplicate detection, top-N, running totals and period-over-period comparisons all rely on them.
    How it worksGROUP BY defines the grain; every non-aggregated column must be in it. HAVING filters groups after aggregation, WHERE filters rows before. Windows use OVER (PARTITION BY … ORDER BY … ROWS …).
    How to use itDeclare the grain ("one row per customer per month"), choose measures, group, filter groups with HAVING, then validate totals against a source report. Use CTEs to keep steps readable.
    Common mistakesCOUNT(*) vs COUNT(col) (NULLs ignored), average of averages, counting after a fan-out join, mixing grains, missing DISTINCT, integer division, ordering ties without a tiebreaker.
    Real-world usageFinding duplicate customers by email, month-over-month revenue growth with LAG, "top 3 products per region" with ROW_NUMBER.
    Interview pointsWHERE vs HAVING; RANK vs DENSE_RANK vs ROW_NUMBER; remove duplicates keeping latest; running total; CTE vs sub-query.

    📈 Patterns worth memorising

    sql-- 1. Duplicates
SELECT email, COUNT(*) FROM customers GROUP BY email HAVING COUNT(*) > 1;

-- 2. Top 3 products per region
WITH r AS (
  SELECT region, product, SUM(amount) AS rev,
         ROW_NUMBER() OVER (PARTITION BY region ORDER BY SUM(amount) DESC) AS rn
  FROM sales GROUP BY region, product)
SELECT * FROM r WHERE rn <= 3;

-- 3. Month-over-month growth
SELECT month, rev,
       rev - LAG(rev) OVER (ORDER BY month) AS delta
FROM monthly_revenue;

-- 4. Keep only the latest record per customer
SELECT * FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) rn
               FROM customer_history) t WHERE rn = 1;
    FunctionBehaviour on ties (scores 90, 90, 80)
    ROW_NUMBER1, 2, 3 (arbitrary among ties)
    RANK1, 1, 3 (gaps)
    DENSE_RANK1, 1, 2 (no gaps)
    💡
    Reconcile like an auditor: total rows, distinct keys, sum of amounts and min/max dates from both source and target; differences point to the failing rule.

    🗂️ Entity Relationship Diagrams (ERD)

    PointDetail
    What it isAn ERD models entities (things), attributes (facts about them) and relationships with cardinality (1:1, 1:N, M:N) and optionality. Notations: Crow's Foot, Chen, UML class.
    Why it is usedIt is the shared language between business and engineers for what data exists and how it connects; it drives database design, API resources, reports and migration mapping.
    How it worksConceptual (business entities) → Logical (attributes, keys, normalisation) → Physical (tables, types, indexes, constraints). PK uniquely identifies a row; FK enforces the link; M:N is resolved with an associative (junction) table.
    How to use itExtract nouns from requirements → define each entity's identifier → write relationship sentences ("A customer places zero or many orders; an order belongs to exactly one customer") → set cardinality/optionality → normalise → review with SMEs.
    Common mistakesStoring M:N as comma-separated values, no surrogate/business key distinction, repeating groups, derived data stored without reason, ignoring history (SCD), modelling roles as separate entities instead of one Party.
    Real-world usageE-commerce ERD: Customer 1—N Order 1—N OrderItem N—1 Product; Product N—M Category resolved through ProductCategory.
    Interview pointsDraw a crow's foot ERD live; explain PK vs FK vs unique key; resolve M:N; 1NF/2NF/3NF; logical vs physical model.

    📐 Normalisation, keys and cardinality

    erd (crow's foot, text)CUSTOMER ||──o{ ORDER ||──|{ ORDER_ITEM }o──|| PRODUCT
   || exactly one   o{ zero or many   |{ one or many   o| zero or one
PRODUCT }o──o{ CATEGORY   →  resolve with  PRODUCT_CATEGORY(product_id FK, category_id FK, PK(both))
    Normal formRuleViolation example
    1NFAtomic values, no repeating groupsphones = "98.., 97.."
    2NFNo partial dependency on part of a composite keyOrderItem stores product_name
    3NFNo transitive dependency (non-key → non-key)Customer table stores city and state derived from pincode
    BCNFEvery determinant is a candidate keyEdge cases with overlapping keys
    Key typeMeaning
    PrimaryUnique, not null identifier
    ForeignReferences another table's key; enforces referential integrity
    Candidate / AlternateAny column set that could be the PK
    CompositePK made of 2+ columns
    Surrogate vs NaturalSystem id vs business-meaningful id (email, PAN)
    📌
    Denormalise deliberately for reporting (star schema: fact + dimension tables) and say so; OLTP stays normalised, OLAP favours read speed. Mention SCD Type 2 when history must be preserved.

    🧹 Data profiling, quality and mapping

    PointDetail
    What it isProfiling inspects data (null %, distinct count, min/max, patterns, outliers). A data mapping document defines how each source field becomes a target field; a data dictionary defines every field's meaning, type, length, owner and rules.
    Why it is usedMigrations, integrations and reports fail because of dirty or misunderstood data, not code. Documenting it makes rules testable and auditable.
    How it worksProfile source → define quality rules (completeness, validity, uniqueness, consistency, timeliness, accuracy) → map and transform → load to staging → reconcile counts/sums → fix rejects → sign-off.
    How to use itMapping row: source table.column → type/length → transformation → target column → default → validation → reject handling. Add lineage and PII classification (retention, masking).
    Common mistakesMapping only happy-path values, ignoring code-list differences (M/F vs 1/2), truncation, time-zone shifts, no reconciliation, leaving duplicates, forgetting soft-deleted rows.
    Real-world usageLegacy CRM → new CRM: dedupe by email+phone, standardise country to ISO-3166, migrate 5 years history, reconcile 100% of counts and sampled field-level values.
    Interview pointsList data-quality dimensions; describe ETL vs ELT; how you validate a migration; what a data dictionary contains; what PII handling you would specify.

    📋 Mapping and validation templates

    crm.cust.gender (M/F/U)party.gender_codeLookup: M→1, F→2, U→0Unknown → 0, log
    crm.cust.phoneparty.mobile_e164Strip non-digits, add +91 if 10 digitsInvalid → reject file
    crm.cust.created (IST)party.created_utcConvert IST → UTCNull → load date

    ⚡ Performance awareness for BAs

    PointDetail
    What it isUnderstanding why a query is slow: missing indexes, scans, bad joins, large sorts, non-sargable filters. You are not the DBA, but you raise realistic NFRs and spot risks.
    Why it is usedReport timeouts, batch overruns and screen delays are requirement problems when volumes and SLAs were never stated.
    How it worksThe planner estimates cost; EXPLAIN (ANALYZE) shows scans, join methods, row estimates. Indexes (B-tree) speed equality/range lookups but slow writes and use storage. Partitioning splits large tables by date/region.
    How to use itCapture data volumes, growth, concurrency and response-time targets; request indexes on join/filter columns; avoid functions on indexed columns; paginate; archive old data.
    Common mistakesWHERE YEAR(date)=2026 (non-sargable), LIKE '%x', SELECT *, OR chains, missing statistics, testing with tiny data, unbounded exports.
    Real-world usageDashboard took 40 s; adding a composite index on (customer_id, order_date) and filtering with a date range cut it to 0.6 s.
    Interview pointsClustered vs non-clustered index, what EXPLAIN shows, OLTP vs OLAP, ACID, isolation levels, transaction vs batch, when to denormalise.

    🎯 Rapid-fire Q&A

    QuestionStrong answer
    INNER vs LEFT JOIN?INNER keeps matches only; LEFT keeps all left rows with NULLs for no match.
    WHERE vs HAVING?WHERE filters rows before grouping; HAVING filters aggregated groups.
    What is ACID?Atomicity, Consistency, Isolation, Durability – reliable transactions.
    Primary vs unique key?PK: one per table, not null; unique: many allowed, may allow one null (DB-specific).
    How find the second highest salary?DENSE_RANK() OVER (ORDER BY salary DESC) = 2, or OFFSET 1 LIMIT 1 over distinct.
    Delete vs truncate vs drop?Row removal with rollback/WHERE · fast clear, keeps structure · removes the table.
    What is a view / materialised view?Saved query / stored result refreshed on schedule.
    sql (practice schema)customers(customer_id PK, name, email UNIQUE, created_at)
orders(order_id PK, customer_id FK, order_date, status, total)
order_items(order_id FK, line_no, sku, qty, unit_price, PK(order_id,line_no))
-- Task: monthly revenue, customers with >3 orders, orders without items, avg basket by city
    📌
    In interviews always state the grain, the join type and the check you would run: "one row per customer, LEFT JOIN to keep non-buyers, verify count equals customer table."

    Tools, Quality & Best Practices

    Tooling, test strategy and rules of thumb.

    🔧 Tools & Workflows

    • SQL clients, ERD tools (dbdiagram, draw.io), Excel mapping templates, data profilers, Git for scripts.
    • Workflow: clarify metric and grain, profile source, draft mapping, write query, reconcile to a known total, document in the dictionary.

    ✅ Testing & Quality

    • Test with reconciliation: row counts, sums and distinct keys before and after a join or load.
    • Check duplicates, orphans, NULL rates, ranges, referential integrity and date logic; keep a result-sign-off checklist.

    ⭐ Best Practices

    • Always state the grain; alias every table; join on keys, filter early, avoid SELECT *.
    • Name columns consistently; document units, time zones and allowed values in the dictionary.

    Troubleshooting, Interview Prep & Summary

    Diagnose problems, rehearse interviews, consolidate.

    🩺 Common Errors & Troubleshooting

    • Row count explodes: many-to-many join, aggregate before joining.
    • Missing customers: filter on right table in WHERE turned a LEFT join into INNER; move it to ON.
    • Wrong average: NULLs ignored or averaging averages.
    • Slow query: function on indexed column, missing index, no partition filter.

    🎤 Interview Preparation

    • INNER vs LEFT vs FULL; WHERE vs HAVING; RANK vs DENSE_RANK vs ROW_NUMBER.
    • Find duplicates; second highest salary; running total; explain a 3NF design and an execution plan.

    🏁 Course Summary

    • A BA who knows grain, keys and joins prevents most reporting and migration defects.
    • Model clearly, map explicitly, reconcile always. Next: Architecture Literacy.

    Business Logic to Technical Tasks

    Advanced, interview-ready depth on turning business logic into engineering work — what it is, why, how it works, how to use it, mistakes, real-world usage.

    🔄 Technical translation: the core skill

    PointDetail
    What it isConverting business intent ("high-value customers get free delivery") into precise, testable technical work: rules, data, APIs, events, validations, tasks and acceptance criteria that engineers can build without guessing.
    Why it is usedMost defects and rework come from ambiguous requirements. A BA who translates well reduces back-and-forth, estimation risk and UAT failures.
    How it worksBusiness statement → clarify actors, trigger, inputs, outputs, rules, exceptions, data and systems → model (flow, decision table, data, API) → split into vertical slices → write acceptance criteria → trace to tasks and tests.
    How to use itUse the 7-question decomposition: Who? When triggered? What inputs/data? What rules? What outputs/side effects? What can go wrong? How measured? Then map to layers: UI, API, service logic, data, integration, security, logging.
    Common mistakesWriting the solution instead of the rule, hiding rules in prose, leaving exceptions out, splitting by technical layer so nothing is demoable, missing NFRs (audit, performance), not confirming terminology with the team.
    Real-world usage"Gold customers get free delivery above ₹999" becomes: rule table, customer.tier data source, POST /orders/price response field deliveryFee, test cases at ₹998/999/1000, audit log of applied rule.
    Interview pointsWalk through converting a vague requirement into tasks; explain how you split a story; show how you handle an exception; describe how you keep rules traceable.

    🪜 Worked example: from requirement to tasks

    requirement → tasksBUSINESS: "Gold customers get free delivery on orders above ₹999."
CLARIFY : tier source? currency? before/after discount? cancelled/returned items? multiple addresses?
RULE    : IF customer.tier = GOLD AND orderValueAfterDiscount >= 999 THEN deliveryFee = 0 ELSE fee table
TASKS   : T1 DB  - add customer.tier + effective_from/to           (data)
          T2 API - /orders/price returns deliveryFee, ruleApplied  (contract)
          T3 SVC - pricing rule engine + unit tests                (logic)
          T4 UI  - show "Free delivery applied" badge              (presentation)
          T5 INT - nightly tier sync from CRM, retry on failure    (integration)
          T6 NFR - p95 < 300 ms, audit log of ruleApplied           (quality)
ACCEPT  : Given a Gold customer And order value 999 When price is calculated Then deliveryFee is 0
    💡
    Always capture boundary and negative cases (998, 999, 1000; non-Gold; expired tier) and who owns the rule so future changes have an approver.

    Business Rules & Decision Models

    Advanced, interview-ready depth on turning business logic into engineering work — what it is, why, how it works, how to use it, mistakes, real-world usage.

    📐 Decision tables, rules and state models

    PointDetail
    What it isTechniques to express logic unambiguously: decision tables, decision trees, rule catalogues (DMN), state-transition diagrams and flowcharts/BPMN.
    Why it is usedProse hides gaps and contradictions; tables make every combination visible and directly testable. Developers can implement rules as code or a rules engine.
    How it worksList conditions and actions; enumerate combinations; mark outcomes; collapse equivalent rows; check completeness (every combination covered) and consistency (no two rules conflict). Hit policy defines precedence (first, unique, collect).
    How to use itUse decision tables for 3+ conditions, state diagrams for lifecycle (Order: New → Paid → Shipped → Delivered/Cancelled), BPMN for cross-team flow, rule IDs for traceability.
    Common mistakesMissing combinations, overlapping rules, implicit defaults, rules scattered across documents, hard-coded thresholds that should be configurable, forgetting effective dates.
    Real-world usageLoan eligibility table (age, income, credit band → approve/refer/decline) used by dev for the rule service and by QA to generate test cases.
    Interview pointsWhen do you use a decision table vs flowchart; how to verify completeness; what is a state machine; how to separate rules from code.

    🧮 Decision table and state example

    RuleTierOrder ≥ 999Coupon validDelivery feeDiscount
    R1GoldY–0Coupon if valid
    R2GoldN–49Coupon if valid
    R3RegularYY49Coupon
    R4RegularYN49None
    R5RegularN–79None
    state modelNEW --pay--> PAID --pack--> PACKED --ship--> SHIPPED --deliver--> DELIVERED
NEW|PAID --cancel--> CANCELLED      SHIPPED --return(≤7d)--> RETURN_REQUESTED
Illegal: DELIVERED → NEW ; every transition lists actor, guard, event, side effects
    • Test design: one test per rule (R1–R5) plus boundaries around 999.
    • Config vs code: thresholds (999, 49, 79) belong in configuration with owner, effective date and audit.
    • Traceability: Business Rule ID → requirement → API field → test case.

    Technical Specs: API, Mapping, Sequence

    Advanced, interview-ready depth on turning business logic into engineering work — what it is, why, how it works, how to use it, mistakes, real-world usage.

    📝 Writing artefacts engineers actually use

    PointDetail
    What it isThe documents that carry translated requirements: API specification, field-level mapping, sequence/activity diagrams, data model changes, event definitions and non-functional requirements.
    Why it is usedThey are the contract between business, developers, QA and integrators; they enable parallel work and unambiguous estimation.
    How it worksSequence diagrams show who calls whom in what order; mapping documents show every field's transformation; API specs (OpenAPI) define the interface; data models define persistence; NFRs define quality.
    How to use itKeep one source of truth, version it, review with dev + QA ("three amigos"), keep diagrams small (one scenario each), include error and timeout flows, and link to tickets.
    Common mistakesOnly happy-path sequences, missing error codes, mapping without defaults or null handling, outdated diagrams, giant documents nobody reads, specifying implementation details (technology) unnecessarily.
    Real-world usageCheckout sequence: UI → API Gateway → Order → Pricing → Payment (PSP) → Order → Notification; alt flows for payment timeout and stock failure.
    Interview pointsShow how you document an integration; difference between functional spec and technical design; what you put in a sequence diagram; how you keep docs current.

    🧭 Templates

    mermaid-style sequenceUI       -> API     : POST /orders (items, address)
API      -> Pricing : calculate(items, customerId)
Pricing  -> API     : total, deliveryFee, ruleApplied
API      -> Payment : authorize(total) timeout 5s
alt  success : Payment -> API : AUTHORIZED ; API -> UI : 201 PENDING_SHIPMENT
alt  timeout : API -> UI : 202 PROCESSING, status via webhook / polling
    Spec artefactMust contain
    API specEndpoint, params, schemas, status/error codes, auth, rate limits, examples
    Mapping sheetSource → target, type, length, transform, default, validation, reject handling
    Sequence diagramParticipants, sync/async, timeouts, alt/error paths
    Event definitionName, trigger, producer, consumers, schema, version, ordering key
    NFR tableMetric, target, measurement method, priority
    Definition of ReadyRules clear, mock/API contract agreed, data available, acceptance criteria reviewed, dependencies known
    📌
    Use RACI for decisions (who approves rule changes) and an assumptions / open-questions log with owner and due date; it protects delivery.

    Story Splitting & Acceptance Criteria

    Advanced, interview-ready depth on turning business logic into engineering work — what it is, why, how it works, how to use it, mistakes, real-world usage.

    ✂️ Splitting for value and testability

    PointDetail
    What it isBreaking large requirements into small, independently deliverable vertical slices with clear acceptance criteria and technical sub-tasks.
    Why it is usedSmall slices reduce risk, give early feedback, make estimates reliable and keep every sprint demonstrable.
    How it worksSplit by workflow step, business rule, data variation, interface, operation (CRUD), happy vs exception path, or performance level (SPIDR: Spike, Path, Interface, Data, Rule). Each slice cuts through UI→API→DB.
    How to use itStart with a walking skeleton (thin end-to-end), then add rules and exceptions. Apply INVEST and write Given/When/Then plus NFR criteria. Add technical sub-tasks with the team, not for them.
    Common mistakesLayer-based splits ("build DB" story), huge epics, criteria that restate the title, no negative cases, hidden dependencies, treating Definition of Done as acceptance criteria.
    Real-world usageEpic "Refunds" → 1) full refund to original card, 2) partial refund, 3) refund to wallet, 4) approval above ₹10k, 5) refund report.
    Interview pointsSplit a given epic live; explain SPIDR; acceptance criteria vs DoD; how you handle technical debt or spikes.

    🧪 Criteria that engineers and testers share

    gherkinFeature: Partial refund
  Scenario Outline: Refund amount validation
    Given an order of <orderTotal> already refunded <refunded>
    When the agent requests a refund of <amount>
    Then the response is <result>
    Examples:
      | orderTotal | refunded | amount | result                  |
      | 1000       | 0        | 400    | 201 REFUND_CREATED      |
      | 1000       | 700      | 400    | 422 EXCEEDS_REFUNDABLE  |
      | 1000       | 0        | 0      | 422 AMOUNT_MIN_1        |
    Quality checkQuestion
    ValueWho benefits and what measurable outcome?
    RulesAre all rule IDs referenced?
    DataSource, owner, format, retention and privacy?
    InterfacesWhich APIs/events are called or changed?
    FailureTimeout, duplicate, partial failure behaviour?
    NFRPerformance, security, audit, accessibility?
    TestBoundary and negative cases covered?

    Interview rapid-fire

    • How do you explain an API change to a non-technical stakeholder? Impact on users/process, timeline, risk and what decision you need.
    • How do you handle a developer saying "this is not feasible"? Understand constraint, offer options (scope, phasing, alternative rule), record decision and trade-off.
    • How do you ensure shared understanding? Examples, glossary, prototypes/mock APIs, three-amigos review and playback.
    • Business asks for "real-time" – what do you do? Quantify: seconds? minutes? Which events? Then choose sync/async and set SLA.

    Tools, Quality & Best Practices

    Tooling, test strategy and rules of thumb.

    🔧 Tools & Workflows

    • Jira, Confluence, draw.io/PlantUML, Postman, DMN modeller, Gherkin tools.
    • Workflow: workshop, rule extraction, decision model, spec, story split, three-amigos review, refine.

    ✅ Testing & Quality

    • Review with three amigos; execute examples as automated Gherkin tests.
    • Check completeness, consistency, testability and traceability; run a rule-coverage matrix.

    ⭐ Best Practices

    • One rule, one place; examples for every rule; explicit defaults and exceptions.
    • Keep stories small, independent and valuable; write criteria before development.

    Troubleshooting, Interview Prep & Summary

    Diagnose problems, rehearse interviews, consolidate.

    🩺 Common Errors & Troubleshooting

    • Vague terms (fast, high, soon): quantify.
    • Missing else-branch in a rule.
    • Horizontal stories that deliver nothing alone.
    • Criteria that restate the story instead of testing it.

    🎤 Interview Preparation

    • How do you turn an ambiguous requirement into tasks? Decision table vs flowchart?
    • Explain INVEST, SPIDR and three amigos; show a sequence diagram for a failed payment.

    • Translation is precision: rules, data, flows and examples.

    Components & Interfaces

    What components, interfaces, messages and states are, and where the Systems Analyst fits.

    🧩 What is Component-Level Design?

    Component-level design turns agreed system requirements into modular, testable building blocks that developers can implement. The Systems Analyst models how parts collaborate without writing code.

    TermMeaningExample
    ComponentReplaceable unit hiding internals behind interfacesPayment Service
    InterfaceContract of operations a component offers or needscharge(orderId, amount)
    ActorExternal person or system that interactsCustomer, Bank API
    LifelineA participant over time in a sequence diagram:OrderService
    MessageCall or signal between participantsvalidateCard()
    State / EventCondition between events / trigger of changePaid / paymentConfirmed
    💡
    Golden rule: high cohesion inside a component, low coupling between components.

    🧭 Where the SA fits

    1. Business requirements (BRD) — why
    2. System requirements (SRS) — what
    3. Component design — how parts collaborate
    4. Code and tests — built by developers/QA

    Diagrams are the shared language between BA, architects, developers and testers.

    Component & State Diagrams

    UML component interaction and state machine modelling.

    🔌 Component interaction (UML)

    ElementNotationMeaning
    Provided interfacelollipop ○—Service the component offers
    Required interfacesocket —(Service the component needs
    Portsmall square on borderNamed interaction point
    Dependencydashed arrowUses, but does not own
    Assembly connectorball meets socketWires provider to consumer

    Types: logical components (business capability, e.g. Billing), physical components (deployable: JAR, DLL, container), and third-party/COTS components.

    🔁 State machine diagrams

    Model an object whose behaviour depends on its history. Format: Event [guard] / action.

    text[*] -> Created
Created -> Paid      : paymentConfirmed [amount > 0] / sendReceipt()
Paid    -> Shipped   : dispatch / notifyCustomer()
Shipped -> Delivered : deliveryScan
Created -> Cancelled : cancel
Paid    -> Refunded  : refund [within 30 days]
    TypeUse
    Simple stateFlat lifecycle (order)
    Composite stateStates nested inside a state (Shipped: Packed → InTransit)
    Orthogonal regionsParallel sub-states (payment status + fulfilment status)
    History stateResume where it left off
    ⚠️
    Every state needs an exit (or be final) and every event must be handled or intentionally ignored.

    Intermediate & Advanced

    Trade-offs, expert guidance and review habits.

    📈 Intermediate Concepts

    • Sequence Diagrams: System sequence diagrams (SSD) and detailed interaction sequences.
    • Component & State Diagrams: UML component interaction and state machine modelling.
    💡
    Intermediate skill is choosing between options and justifying the choice, not just naming them.

    🎓 Expert checklist

    PointDetail
    What it isA reviewed set of diagrams, interface contracts and state rules traceable to requirements.
    Why it is usedDefects found at design cost a fraction of defects found in production.
    How to use itTrace each message to a requirement ID; give each component one responsibility; define failure paths (timeout, retry, compensation) as well as the happy path.
    Common mistakesGod components; diagrams with only happy paths; mixing business and technical detail; no versioning.
    Real-world usageCheckout redesign: sequence diagram exposed a synchronous call to the tax service that caused 6 s timeouts; changed to async with cached rates.
    Interview pointsExplain SSD vs sequence diagram, async vs sync messages, guard conditions, and cohesion vs coupling with an example.
    ✅
    Review rule: could a developer implement this and a tester derive test cases from it without asking you a question?

    Tools, Quality & Best Practices

    Workflow, review checklist and habits.

    🔧 Tools & Workflows

    Use case → SSD → detailed sequence → component diagram → state machine → trace each message to a requirement ID → design review.

    ✅ Testing & Quality

    • Every message traces to a requirement
    • Failure paths (timeout, retry, compensation) exist
    • Every state has an exit and every event is handled

    ⭐ Best Practices

    • Trace each message to a requirement ID; give each component one responsibility; define failure paths (timeout, retry, compensation) as well as the happy path.
    • Defects found at design cost a fraction of defects found in production.

    Troubleshooting & Interview Prep

    Common mistakes, interview questions and a recap.

    🩺 Common Errors & Troubleshooting

    • God components
    • diagrams with only happy paths
    • mixing business and technical detail
    • no versioning
    1. Locate the issue in the artefact
    2. Trace it to the requirement
    3. Fix, version and re-review

    🎤 Interview Preparation

    Q1. Be ready to explain: SSD vs sequence diagram
    Q2. Be ready to explain: async vs sync messages
    Q3. Be ready to explain: guard conditions

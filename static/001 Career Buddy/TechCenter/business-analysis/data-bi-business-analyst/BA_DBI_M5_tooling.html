    BI Tool Landscape & Architecture

    How data flows from source to dashboard, what each tool in the modern stack does, and how to choose between them.

    🗺️ The modern data stack

    Data moves through layers: sources (apps, databases, files) are ingested into a warehouse or lakehouse, transformed into modeled tables, then served to BI tools and analysts. ELT (load first, transform in the warehouse) has largely replaced ETL because cloud warehouses are cheap and elastic.

    LayerPurposeExamples
    IngestionMove data from sourcesFivetran, Airbyte, Kafka, custom APIs
    Storage / computeStore and query at scaleSnowflake, BigQuery, Redshift, Databricks
    TransformationClean and model with SQLdbt, Spark, stored procedures
    OrchestrationSchedule and monitor pipelinesAirflow, Dagster, dbt Cloud
    BI / visualizationDashboards and self-servePower BI, Tableau, Looker, Qlik
    AnalysisAdvanced and ad hocSQL, Python, R, notebooks
    GovernanceCatalog, lineage, qualityDataHub, Collibra, Purview
    ConceptOLTPOLAP
    PurposeRun the business (transactions)Analyze the business
    DesignNormalized, many small writesDimensional, large reads and aggregates
    ExamplesPostgreSQL app DB, ERPWarehouse, cubes

    ⚖️ Choosing a tool

    NeedGood fitReason
    Microsoft 365 / Azure shop, low license costPower BITight Office/Teams integration, strong modeling with DAX
    Rich exploratory visuals and design freedomTableauFast visual analytics, flexible calculations
    Governed metrics in codeLooker / semantic layerLookML or dbt semantic layer as single source
    SQL transformations with tests and docsdbtVersion control, lineage, testing
    Statistics, forecasting, automationPython / RLibraries and reproducibility

    Serverless analytics on Google CloudBigQueryNo infrastructure, pay per query or slot
    💡
    A BA picks tools by decision criteria: users and skills, data volume and latency, governance needs, integration, total cost and vendor support, not by brand preference.

    Power BI

    Power Query, the data model, DAX measures, filter context, time intelligence, storage modes and security in Power BI.

    ⚡ Components and data modeling

    PointDetail
    PartsPower BI Desktop (author), Service (publish, share, refresh, workspaces, apps), Gateway (reach on-prem data), Mobile, Report Builder (paginated). Dataflows and semantic models enable reuse.
    Power Query (M)Extract and clean: filter, merge, append, pivot/unpivot, change types, custom columns. Steps are recorded and repeatable. Push heavy work to the source with query folding.
    Data modelBuild a star schema: fact tables in the middle, dimension tables around. One-to-many relationships, single-direction filtering by default, a dedicated Date table marked as date table.
    Storage modesImport (fast, in-memory, scheduled refresh), DirectQuery (live, slower, source load), Dual, and Direct Lake in Fabric. Composite models mix them.
    SecurityRow-level security with DAX filters on roles; workspace roles (Admin, Member, Contributor, Viewer); sensitivity labels.
    ⚠️
    Avoid many-to-many relationships and bi-directional filters unless justified; they cause ambiguity and slow reports. Hide technical columns and use friendly names.

    🧮 DAX essentials

    ConceptMeaning
    Calculated columnComputed row by row at refresh, stored in the model (uses memory)
    MeasureComputed at query time in the current filter context; use for aggregations and KPIs
    Row contextThe current row while iterating (calculated columns, SUMX)
    Filter contextThe set of filters from slicers, rows, columns and visuals
    CALCULATEChanges filter context: the most important DAX function
    IteratorsSUMX, AVERAGEX, RANKX evaluate an expression per row of a table
    daxTotal Sales = SUM ( Sales[NetAmount] )

Sales LY = CALCULATE ( [Total Sales], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )

YoY % = DIVIDE ( [Total Sales] - [Sales LY], [Sales LY] )

Sales YTD = TOTALYTD ( [Total Sales], 'Date'[Date] )

Top Region Sales = CALCULATE ( [Total Sales], REMOVEFILTERS ( Product ), Region[Name] = "West" )

AOV = DIVIDE ( [Total Sales], DISTINCTCOUNT ( Sales[OrderID] ) )
    📌
    Use DIVIDE instead of / to handle zero safely. Time intelligence needs a continuous Date table with no gaps. Variables (VAR/RETURN) improve readability and speed.

    ⚡ Advanced: DAX Evaluation Context & Optimisation Advanced

    DAX hinges on two contexts: filter context (slicers, rows/columns, CALCULATE filters) and row context (iteration over a table). CALCULATE performs context transition, turning the current row into a filter, and modifies filters in a defined order.

    daxSales YTD = CALCULATE ( [Total Sales], DATESYTD ( 'Date'[Date] ) )
Sales PY  = CALCULATE ( [Total Sales], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )
YoY %     = VAR cur = [Total Sales] VAR py = [Sales PY]
            RETURN DIVIDE ( cur - py, py )
% of Total = DIVIDE ( [Total Sales], CALCULATE ( [Total Sales], ALLSELECTED ( Product ) ) )
Margin    = SUMX ( Sales, Sales[Qty] * ( Sales[Price] - RELATED ( Product[Cost] ) ) )
    TopicDetail
    ALL vs ALLSELECTED vs REMOVEFILTERSALL removes filters entirely; ALLSELECTED keeps slicer filters (visual-level totals)
    Iterators (SUMX, AVERAGEX)Evaluate row by row; use when the calculation needs row-level logic
    VariablesCompute once, improve readability and speed
    TREATAS / USERELATIONSHIPVirtual relationships and activating inactive relationships
    RLSRole filters via DAX expressions or mapping tables; remember they propagate along relationships
    PerformanceUse Performance Analyzer and DAX Studio; prefer measures over calculated columns; reduce cardinality; use aggregations, composite models and incremental refresh; maintain query folding in Power Query

    Tableau

    Dimensions and measures, calculations, level-of-detail expressions, extracts, order of operations and how Tableau compares with Power BI.

    🎨 Core concepts

    PointDetail
    ConnectionsLive (query source each time) or Extract (.hyper snapshot; fast, offline, scheduled refresh). Relationships (logical layer) and joins/unions (physical layer).
    Dimensions vs measuresDimensions are categorical (blue); measures are numeric and aggregated (green). Discrete (blue pill, headers) vs continuous (green pill, axes).
    Marks cardControls Color, Size, Label, Detail, Tooltip, Shape. Detail adds granularity without visible encoding.
    ProductsDesktop and Prep (author), Server / Cloud (publish, govern), Public (free, public data), Reader.
    Dashboard actionsFilter, highlight, URL, parameter and set actions; layout containers; device layouts.
    Published data sourcesCertified, shared extracts so teams use one definition.
    Order of operations (simplified)Effect
    Extract filtersReduce data at extract time
    Data source filtersApply across the source
    Context filtersCreate a first filter step; needed for Top N with other filters
    FIXED LODComputed before dimension filters
    Dimension filtersFilter by categorical fields
    INCLUDE / EXCLUDE LODAfter dimension filters
    Measure filtersFilter on aggregates
    Table calculationsRun last on the visible results

    🧪 Calculations and LOD expressions

    sql// Basic calculation
IF [Profit] < 0 THEN 'Loss' ELSE 'Profit' END

// FIXED: customer's first order date, regardless of view
{ FIXED [Customer ID] : MIN([Order Date]) }

// Cohort month number
DATEDIFF('month', { FIXED [Customer ID] : MIN([Order Date]) }, [Order Date])

// INCLUDE: average of per-customer sales within the view's level
AVG( { INCLUDE [Customer ID] : SUM([Sales]) } )

// Table calc: running total
RUNNING_SUM(SUM([Sales]))
    FeaturePower BITableau
    LanguageDAX (measures), M (Power Query)Calculated fields, LOD, table calcs
    StrengthModeling, Microsoft ecosystem, costVisual exploration, design flexibility
    ModelingStrong semantic model with relationshipsLighter model; relationships since 2020.2
    Self-serve data prepPower QueryTableau Prep
    Learning curveDAX is hard at firstLOD and table calcs need practice
    ⚠️
    Too many extracts and unpublished workbooks create metric sprawl. Publish certified data sources and keep calculations inside them.

    🎨 Advanced: Order of Operations, LOD & Table Calcs Advanced

    Tableau applies filters in a fixed order: Extract → Data source → Context → FIXED LOD → Dimension filters → INCLUDE/EXCLUDE LOD → Measure filters → Table calculations. A dimension filter does not affect a FIXED calculation unless it is added to context.

    text{ FIXED [Customer ID] : MIN([Order Date]) }                         // first purchase (cohort)
{ FIXED [Region] : SUM([Sales]) } / { FIXED : SUM([Sales]) }        // region share of total
{ INCLUDE [Customer ID] : SUM([Sales]) }                            // avg of per-customer totals
{ EXCLUDE [Category] : AVG([Profit]) }                              // ignore a view dimension
RUNNING_SUM(SUM([Sales]))  // table calc: set partitioning/addressing explicitly
    TopicDetail
    Table calcs vs LODTable calcs operate on the aggregated result in the view; LODs compute in the data source query at a specified grain
    Relationships vs joins vs blendsRelationships (logical layer) avoid duplication and retain unmatched; joins fix grain; blends are a last resort across sources
    PerformanceExtracts (Hyper), fewer marks, avoid heavy custom SQL and many quick filters, context filters sparingly, use performance recording
    InteractivityParameters with set actions, dynamic zone visibility, dashboard actions for guided analysis

    🧱 dbt: models, tests, docs

    PointDetail
    What it isdbt (data build tool) lets analysts transform data inside the warehouse using SQL SELECT statements, with version control, testing, documentation and dependency management. It does the T in ELT.
    Project layerssources (raw), staging (rename, cast, 1:1 with source), intermediate (joins, logic), marts (facts and dimensions for BI).
    ref() and source()ref('model') builds the dependency graph (DAG) and resolves schema names; source('app','orders') points at raw tables.
    Materializationsview, table, incremental (process only new rows), ephemeral (CTE), materialized view. Pick by size and freshness.
    Tests and docsGeneric tests (unique, not_null, accepted_values, relationships) plus singular SQL tests; dbt docs generate creates lineage and a data dictionary.
    SnapshotsTrack slowly changing dimensions (Type 2) automatically.
    Commandsdbt run, dbt test, dbt build, dbt docs generate, dbt run --select stg_orders+.

{{ config(materialized='incremental', unique_key='order_id') }}

WITH o AS (SELECT * FROM {{ ref('stg_orders') }}),
c AS (SELECT * FROM {{ ref('stg_customers') }})

SELECT o.order_id, o.order_date, c.customer_key,
       o.amount - o.discount AS net_amount
FROM o JOIN c USING (customer_id)
{% if is_incremental() %}
WHERE o.order_date > (SELECT MAX(order_date) FROM {{ this }})
{% endif %}

    Snowflake & BigQuery

    Cloud warehouse architecture, performance and cost control: virtual warehouses and slots, partitioning, clustering, time travel and semi-structured data.

    ❄️ Architecture and key features

    TopicSnowflakeBigQuery
    ModelSeparated storage, compute (virtual warehouses) and servicesServerless; storage and compute separated, Dremel engine
    Compute sizingChoose warehouse size (XS to 6XL), auto-suspend and auto-resume, multi-cluster for concurrencyOn-demand (billed by bytes scanned) or capacity (slots reservations/editions)
    Storage organizationMicro-partitions with automatic pruning; optional clustering keysPartitioned tables (date, integer range) and clustering columns
    Time travelQuery or restore past data (1-90 days); zero-copy clonesTime travel up to 7 days; table snapshots and clones
    Semi-structured dataVARIANT with : path and FLATTENJSON, STRUCT, ARRAY with UNNEST
    SharingSecure data sharing and marketplaceAnalytics Hub, authorized views
    SecurityRBAC, masking and row access policiesIAM, column-level and row-level security, policy tags
    sql-- Snowflake: flatten JSON and dedupe
SELECT raw:customer.id::string AS customer_id, f.value:sku::string AS sku
FROM events, LATERAL FLATTEN(input => raw:items) f
QUALIFY ROW_NUMBER() OVER (PARTITION BY raw:event_id ORDER BY loaded_at DESC) = 1;

-- BigQuery: partitioned and clustered table, scan only one day
CREATE TABLE ds.events PARTITION BY DATE(event_ts) CLUSTER BY customer_id AS SELECT * FROM ds.raw_events;
SELECT customer_id, COUNT(*) FROM ds.events
WHERE DATE(event_ts) = '2026-03-01' GROUP BY customer_id;

    💰 Performance and cost control

    PointDetail
    Cost modelSnowflake bills compute credits per second while a warehouse runs (plus storage). BigQuery on-demand bills bytes scanned; capacity bills slot time.
    Reduce scanned dataSelect needed columns (never SELECT * on columnar tables), filter on partition keys, cluster on common filters, pre-aggregate.
    Right-size computeSmall warehouse for BI, larger for heavy ELT; auto-suspend after 60 seconds; separate warehouses per workload; resource monitors and budgets with alerts.
    CachingResult cache returns identical queries free; local disk cache speeds repeated scans. Non-deterministic functions bypass it.
    MaterializationMaterialized views, aggregate tables and incremental models reduce repeated heavy queries.
    MonitoringQuery history, INFORMATION_SCHEMA / ACCOUNT_USAGE, query profile or execution graph to spot spills, skew and full scans.
    Common mistakesLeaving large warehouses running, scanning full tables for dashboards, unbounded cross joins, no cost ownership by team, and ignoring clustering when filters are selective.
    ✅
    Expert checklist: partition and cluster on filter columns, separate workloads, auto-suspend, monitor spend per team, test queries on samples, and document cost-vs-freshness trade-offs for each dashboard.

    ❄️ Advanced: Internals, Caching & Cost Governance Advanced

    PlatformKey internals and levers
    SnowflakeMicro-partitions with metadata pruning; clustering keys (check clustering depth); result cache, local disk cache, warehouse cache; multi-cluster warehouses for concurrency; Time Travel and zero-copy clone; streams + tasks and dynamic tables for incremental pipelines; search optimisation service; use Query Profile to spot spilling and unpruned scans
    BigQueryServerless slots; on-demand (bytes scanned) vs capacity editions; partition + cluster to cut bytes; nested/repeated fields with UNNEST; materialised views and BI Engine for dashboards; avoid SELECT *
    Cost controlsSnowflake: auto-suspend, right-size, resource monitors, per-team warehouses and tags. BigQuery: require_partition_filter, maximum_bytes_billed, quotas, dry runs
    GovernanceRole-based access, dynamic data masking, row access policies, column-level security, audit via ACCESS_HISTORY / audit logs

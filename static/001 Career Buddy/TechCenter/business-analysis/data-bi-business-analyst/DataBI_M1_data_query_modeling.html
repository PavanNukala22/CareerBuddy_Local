    Advanced SQL for Analytics

    Window functions, recursive CTEs, sequence patterns and the NULL semantics that quietly corrupt reports.

    🪟 Window functions in depth

    Window functions compute across a set of rows related to the current row without collapsing them. Evaluation order matters: FROM/JOIN → WHERE → GROUP BY → HAVING → WINDOW → SELECT → DISTINCT → ORDER BY → LIMIT. Windows run after GROUP BY, so you cannot filter on a window result in WHERE; use a CTE/subquery or QUALIFY (Snowflake, BigQuery, Databricks).

    sqlSELECT customer_id, order_date, amount,
  SUM(amount) OVER (PARTITION BY customer_id ORDER BY order_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)      AS running_total,
  AVG(amount) OVER (PARTITION BY customer_id ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)               AS moving_avg_7,
  LAG(amount)  OVER w AS prev_amount,
  amount - LAG(amount) OVER w AS delta,
  ROW_NUMBER() OVER w AS rn,
  PERCENT_RANK() OVER (PARTITION BY customer_id ORDER BY amount) AS pct_rank
FROM fact_orders
WINDOW w AS (PARTITION BY customer_id ORDER BY order_date);
    ConceptDetailTrap
    ROWS vs RANGEROWS counts physical rows; RANGE groups peers with equal ORDER BY valuesDefault frame with ORDER BY is RANGE UNBOUNDED PRECEDING: ties get the same running total, and it is slower
    ROW_NUMBER / RANK / DENSE_RANKUnique / gaps after ties / no gapsROW_NUMBER is non-deterministic on ties unless ORDER BY is a unique key
    FIRST_VALUE / LAST_VALUEValue at frame edgeLAST_VALUE needs ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING or it returns the current row
    NTILE(n)Equal-count bucketsNot equal-width; uneven counts give earlier buckets one extra row
    Top-N per groupROW_NUMBER() ... QUALIFY rn <= 3Use RANK/DENSE_RANK if ties must be kept

    🔁 CTEs and recursive queries

    A CTE names a subquery for readability and reuse. Whether it is materialised depends on the engine (PostgreSQL 12+ inlines by default unless MATERIALIZED; SQL Server never materialises). Recursive CTEs walk hierarchies and graphs: an anchor member plus a recursive member joined by UNION ALL, ending when no new rows appear.

    sqlWITH RECURSIVE org AS (
  SELECT emp_id, manager_id, name, 1 AS lvl, CAST(name AS VARCHAR(500)) AS path
  FROM dim_employee WHERE manager_id IS NULL
  UNION ALL
  SELECT e.emp_id, e.manager_id, e.name, o.lvl + 1, o.path || ' > ' || e.name
  FROM dim_employee e JOIN org o ON e.manager_id = o.emp_id
  WHERE o.lvl < 15                       -- cycle / runaway guard
)
SELECT * FROM org;
    ⚠️
    Always add a depth limit or a visited-path check. A cycle in the data (A reports to B, B to A) otherwise loops until the engine aborts.

    🧩 Sequence patterns: islands, sessions, pivots

    Many analytical questions are really sequence problems. Three patterns cover most of them.

    sql-- Gaps & islands: consecutive-day login streaks
SELECT user_id, MIN(d) AS streak_start, MAX(d) AS streak_end, COUNT(*) AS days
FROM (SELECT user_id, d,
        d - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY d)) * INTERVAL '1 day' AS grp
      FROM (SELECT DISTINCT user_id, event_date AS d FROM events) x) y
GROUP BY user_id, grp;

-- Sessionization: new session after a 30-minute gap
WITH f AS (SELECT *, CASE WHEN ts - LAG(ts) OVER (PARTITION BY user_id ORDER BY ts)
                         > INTERVAL '30 minutes' THEN 1 ELSE 0 END AS new_s FROM events)
SELECT *, SUM(new_s) OVER (PARTITION BY user_id ORDER BY ts) AS session_id FROM f;

-- Conditional aggregation pivot (portable)
SELECT region, SUM(CASE WHEN q='Q1' THEN rev END) AS q1, SUM(CASE WHEN q='Q2' THEN rev END) AS q2
FROM sales GROUP BY region;
    PatternTechnique
    Gaps & islandsSubtract a row number from the value; constant difference identifies each island
    SessionizationFlag boundaries with LAG, then cumulative-SUM the flags
    Dedup / latest rowROW_NUMBER() ... ORDER BY updated_at DESC, keep rn = 1
    Funnel / retentionSelf-join or conditional aggregation on first-event date and offset
    Median / percentilePERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY x)

    ❓ NULL logic and silent-error traps

    SQL uses three-valued logic: comparisons with NULL yield UNKNOWN, and WHERE keeps only TRUE rows. Frequent consequences:

    SituationBehaviourSafe approach
    x NOT IN (subquery) where subquery has a NULLReturns no rowsUse NOT EXISTS or filter NULLs
    COUNT(col) vs COUNT(*)COUNT(col) ignores NULLsState intent explicitly
    AVG(col)Denominator excludes NULLsAVG(COALESCE(col,0)) only if zero is truthful
    NULL = NULLUNKNOWN, not TRUEIS NOT DISTINCT FROM for null-safe equality
    LEFT JOIN + filter on right table in WHERESilently becomes an INNER JOINMove the predicate into the ON clause
    UNION vs UNION ALLUNION sorts/dedups (costly)Default to UNION ALL unless dedup is required

    Query Performance & Optimization

    Reading execution plans, writing sargable predicates and tuning for columnar, distributed warehouses.

    🔬 Execution plans and join algorithms

    Read the plan, not the SQL. Compare estimated vs actual rows: a large gap means stale statistics or correlated predicates, and it is the root of most bad plans. Look for the most expensive node, scans over large tables, sorts spilling to disk and nested loops over big inputs.

    Join algorithmBest whenWeakness
    Nested loopSmall outer set, indexed inner lookupExplodes on large unindexed inputs
    Hash joinLarge, unsorted, equality joinsNeeds memory; spills to disk when build side is big
    Merge (sort-merge) joinInputs already sorted on the keySorting cost if not pre-sorted
    sqlEXPLAIN (ANALYZE, BUFFERS)
SELECT c.region, SUM(o.amount)
FROM fact_orders o JOIN dim_customer c USING (customer_key)
WHERE o.order_date >= DATE '2026-01-01'
GROUP BY c.region;
-- Check: Seq Scan vs Index/Partition pruning, rows est vs actual, Sort Method: external merge (spill)

    🎯 Sargability and indexing

    A predicate is sargable when the engine can use an index or partition prune on it. Wrapping the column in a function usually defeats this.

    AvoidPrefer
    WHERE YEAR(order_date)=2026WHERE order_date >= '2026-01-01' AND order_date < '2027-01-01'
    WHERE col + 1 = 10WHERE col = 9
    LIKE '%abc' (leading wildcard)Full-text index, trigram index, or reverse-string column
    WHERE CAST(id AS VARCHAR)='5' (implicit conversion)Match the column type: WHERE id = 5
    SELECT * on columnar storesName only needed columns (column pruning)
    OR across different columnsUNION ALL of two index-friendly queries

    Index design

    • Composite index order: equality columns first, then range, then sort (the leftmost-prefix rule).
    • Covering index (INCLUDE) avoids the table lookup.
    • Low-cardinality columns suit bitmap indexes or partitioning rather than B-trees.
    • Every index slows writes and costs storage: index for the workload, not for every column.

    🏭 Warehouse-scale optimisation

    Analytical warehouses (Snowflake, BigQuery, Redshift, Synapse) are columnar and distributed. Row-store habits transfer poorly.

    TechniqueEffectNote
    Partitioning (usually by date)Prunes whole partitionsFilter on the partition column directly, not on a derived expression
    Clustering / sort keys / micro-partitionsSkips blocks within partitionsChoose columns frequently filtered or joined
    Distribution key (Redshift/Synapse)Co-locates join keysMismatched keys cause expensive data shuffles
    Broadcast small dimensionAvoids shuffling the fact tableAutomatic below a size threshold
    Pre-aggregation / materialised viewsPay compute onceNeeds refresh and invalidation strategy
    Approximate functions (APPROX_COUNT_DISTINCT)Orders of magnitude cheaperAccept ~1-2% error where valid
    Incremental processingProcess only new/changed rowsUse a watermark column and idempotent merges
    💡
    Data skew is the silent killer: one customer_id with 40% of rows overloads a single node. Salt hot keys or pre-aggregate before the join.

    🛠️ A tuning workflow and incremental loads

    Slow query? Work down this order: (1) reduce data early (filter and project before joining), (2) fix join keys and grain to avoid fan-out, (3) check statistics and plan, (4) restructure (CTE to temp table, pre-aggregate), (5) only then add hardware or cache.

    sql-- Aggregate BEFORE joining to shrink the shuffle
WITH o AS (SELECT customer_key, SUM(amount) AS rev
           FROM fact_orders WHERE order_date >= '2026-01-01' GROUP BY customer_key)
SELECT c.region, SUM(o.rev) FROM o JOIN dim_customer c USING (customer_key) GROUP BY c.region;

-- Idempotent incremental load (watermark + MERGE)
MERGE INTO tgt t USING (SELECT * FROM stg WHERE updated_at > :last_run) s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET amount = s.amount, updated_at = s.updated_at
WHEN NOT MATCHED THEN INSERT (id, amount, updated_at) VALUES (s.id, s.amount, s.updated_at);

    Dimensional Modeling

    Grain, fact table types, slowly changing dimensions and the design patterns that keep a warehouse trustworthy.

    ⭐ Star schema design and fact types

    Kimball's four steps: choose the business process → declare the grain → identify dimensions → identify facts. The grain is the most important decision. Declare it in one sentence (one row per order line per day) and never mix grains in one fact table.

    Fact typeDescriptionExampleAdditivity
    TransactionOne row per eventOrder lineFully additive
    Periodic snapshotOne row per entity per periodDaily account balanceSemi-additive (not across time)
    Accumulating snapshotOne row per process lifecycle, updated as milestones occurOrder: placed, shipped, delivered datesLag measures between milestones
    Factless factRecords an event or coverage with no measuresStudent attendance, promotion eligibilityCount only
    📝
    Non-additive facts (ratios, prices) are stored as their numerator and denominator components so they can be re-aggregated correctly.

    🕰️ Slowly changing dimensions

    Slowly Changing Dimensions preserve history when attributes change.

    TypeMechanismHistoryUse when
    0Never changesOriginal onlyBirth date, original signup channel
    1OverwriteNoneCorrections, attributes nobody analyses historically
    2New row with valid_from, valid_to, is_current and a new surrogate keyFullRegion, segment, price tier: the standard choice
    3Add a previous_value columnOne prior valueLimited before/after comparisons
    4Mini-dimension for rapidly changing attributesVia mini-dimVolatile demographics
    6 (1+2+3)Type 2 rows plus current-value columnsFull + currentReport by "as-was" and "as-is" views
    sql-- Type 2 load in two steps: close changed rows, insert new versions
UPDATE dim_customer d SET valid_to = CURRENT_DATE - 1, is_current = FALSE
FROM stg_customer s WHERE d.customer_id = s.customer_id AND d.is_current
  AND (d.segment <> s.segment OR d.region <> s.region);
INSERT INTO dim_customer (customer_id, segment, region, valid_from, valid_to, is_current)
SELECT s.customer_id, s.segment, s.region, CURRENT_DATE, DATE '9999-12-31', TRUE
FROM stg_customer s LEFT JOIN dim_customer d ON d.customer_id = s.customer_id AND d.is_current
WHERE d.customer_id IS NULL OR d.segment <> s.segment OR d.region <> s.region;
    💡
    Facts join to Type 2 dimensions on the surrogate key captured at load time, which pins each fact to the attribute values in force when it happened. Use a hash of tracked columns to detect changes cheaply.

    🧱 Advanced dimension patterns

    PatternProblem solvedDesign
    Conformed dimensionConsistent cross-process analysisOne shared dim_customer / dim_date across fact tables (drill-across)
    Role-playing dimensionSame dim, several meaningsdim_date as order_date, ship_date, delivery_date via views or aliases
    Junk dimensionMany low-cardinality flagsCombine flags into one small dimension
    Degenerate dimensionIdentifier with no attributesKeep order_number in the fact table
    Bridge tableMany-to-many (customer ↔ account)Bridge with weighting factor so measures are not double-counted
    Outrigger / snowflakeNormalised hierarchyUse sparingly; hurts usability and join cost
    Unknown memberLate-arriving or missing keysSurrogate key −1 "Unknown" row; never NULL foreign keys
    Late-arriving dimensionFact arrives before its dimension rowInsert inferred member, then update on arrival

    ⚔️ Kimball vs Inmon vs Data Vault vs OBT

    ApproachCore ideaStrengthWeakness
    Kimball (dimensional)Business-process marts of facts and dimensionsFast to deliver, BI-friendlyNeeds strict conformance across marts
    Inmon (CIF)Normalised enterprise warehouse feeding martsSingle integrated truthSlow, heavy upfront modelling
    Data Vault 2.0Hubs (keys), links (relationships), satellites (history)Auditable, parallel loading, handles changeComplex to query; needs a presentation layer
    One Big Table (OBT)Pre-joined wide tableSimple, fast on columnar enginesRedundancy, weak governance, grain confusion

    A pragmatic modern stack is layered: raw/staging → cleaned/integrated → dimensional marts → semantic layer, with OBTs generated as derived products from the star schema.

    Semantic & Analytical Modeling

    Avoiding fan-out errors, building metric layers, time intelligence and production-grade, tested transformations.

    🪤 Join traps and grain errors

    Joins at the wrong grain give plausible but wrong numbers.

    TrapCauseSymptomFix
    Fan trapJoining a one-to-many on top of another one-to-many measure (order header amount joined to order lines)Header totals multiplied by line countAggregate to the shared grain first, or keep measures at the lowest grain
    Chasm trapTwo facts joined only through a shared dimensionCartesian-like inflationAggregate each fact separately, then join on the conformed dimension
    Many-to-manyCustomers with several accountsDouble countingBridge table with allocation weights
    Join on non-unique keyDuplicates in dimensionRow count increases after joinTest uniqueness; assert row counts before/after
    sql-- Safe drill-across: aggregate each fact to (date, product) then join
WITH s AS (SELECT date_key, product_key, SUM(amount) AS sales FROM fact_sales GROUP BY 1,2),
     r AS (SELECT date_key, product_key, SUM(qty)    AS returns FROM fact_returns GROUP BY 1,2)
SELECT COALESCE(s.date_key, r.date_key) AS date_key, COALESCE(s.product_key, r.product_key) AS product_key,
       s.sales, r.returns
FROM s FULL OUTER JOIN r ON s.date_key = r.date_key AND s.product_key = r.product_key;

    🧭 Semantic layer and BI model design

    A semantic layer defines measures, dimensions and joins once, so every tool returns identical answers (dbt Semantic Layer/MetricFlow, LookML, Power BI semantic model, Cube, AtScale). It enforces the metric contract from Module 2.

    CapabilityWhy it matters
    Measures defined onceNo competing definitions of revenue or churn
    Relationship cardinality and directionPrevents fan-out and ambiguous filter paths
    Row-level and column-level securityGoverned access without per-report logic
    Aggregation awarenessRoutes queries to aggregate tables automatically
    Certified / endorsed datasetsSignals trusted sources to self-serve users
    💡
    Prefer star schemas in BI models: single-direction one-to-many relationships from dimension to fact, a dedicated date table marked as such, and bidirectional filters only when justified.

    📅 Time intelligence and non-additive measures

    A dedicated date dimension (one row per day, with fiscal calendar, week, holiday, working-day flags) powers time intelligence and avoids fragile date arithmetic.

    sql-- Year-over-year with a gap-proof calendar join
SELECT d.year_month,
       SUM(f.amount)                                        AS rev,
       LAG(SUM(f.amount), 12) OVER (ORDER BY d.year_month)  AS rev_py,
       SUM(f.amount) / NULLIF(LAG(SUM(f.amount), 12) OVER (ORDER BY d.year_month), 0) - 1 AS yoy
FROM dim_date d LEFT JOIN fact_orders f ON f.date_key = d.date_key
GROUP BY d.year_month;
    ChallengeApproach
    Semi-additive balancesTake last value per period (LAST_VALUE / end-of-period snapshot), never SUM across time
    Distinct counts do not roll upStore at lowest grain or use HLL sketches; never sum monthly distinct counts
    RatiosStore numerator and denominator; compute ratio of sums at query time
    CurrencyFact stores local amount, currency and rate-date key; convert at query time
    Time zonesStore UTC timestamps; derive local date in the date/time dimension

    🧪 Testable, idempotent transformations

    Treat models like software: version controlled, tested, documented, and rebuilt idempotently.

    sql-- dbt-style incremental model with tests declared in YAML
{{ config(materialized='incremental', unique_key='order_id') }}
SELECT order_id, customer_key, order_ts, amount
FROM {{ ref('stg_orders') }}
{% if is_incremental() %} WHERE order_ts > (SELECT MAX(order_ts) FROM {{ this }}) {% endif %}
-- schema.yml: tests: [unique, not_null] on order_id; relationships to dim_customer
    Quality controlWhat it catches
    Uniqueness and not-null on keysDuplicate and missing grain
    Referential integrity (relationships)Orphan fact rows
    Row-count and sum reconciliation to sourceDropped or duplicated data
    Freshness checksStalled pipelines
    Accepted-values and range testsInvalid categories, impossible amounts

    Idempotency: re-running a load for the same period yields the same result (MERGE or delete-and-insert by partition). Backfills must not depend on the current date.

    Module 01 · Foundations

    Foundations & Runtime

    What Node.js actually is, the engine and I/O layer underneath it, and how to get a script running and talking to your machine.

    ⬢ What is Node.js?

    Node.js is a JavaScript runtime built on Chrome's V8 engine that lets JavaScript run outside the browser — on servers, in CLIs, in build tools. It was never a new language: it's the same JS you already know, given access to the filesystem, network sockets, and the OS, instead of the DOM.

    ⚡
    Non-blocking I/O
    A single thread handles thousands of connections by never waiting idly on I/O.
    📦
    npm ecosystem
    The largest package registry in the world — over 2 million packages.
    🧩
    One language, full stack
    Same syntax on client and server; share validation, types, and utilities.
    🖥️
    Cross-platform
    Runs identically on Linux, macOS, and Windows.
    📝
    Node.js is best for I/O-heavy workloads — APIs, real-time apps, streaming, proxies. It's a poor fit for CPU-heavy work like video encoding or heavy number crunching, since that blocks the single main thread.

    Where Node.js actually fits

    It's worth being precise about this, because it's the single most common misconception new Node developers carry over from other backends. Node doesn't make individual operations faster — V8 is a fast JS engine, but it's not faster than a JIT-compiled language like Go or Java for raw computation. What Node wins on is throughput under I/O-bound concurrency: a chat server, a REST API that mostly waits on a database, a reverse proxy, a file-upload service. In each of those, the CPU is idle most of the time anyway, waiting on the network or disk — and Node's event loop lets one process serve thousands of those waiting connections cheaply, instead of paying for a thread (with its own stack, typically 1–8MB) per connection the way a traditional thread-per-request server does.

    Good fitPoor fit
    REST/GraphQL APIs, microservicesVideo/audio transcoding
    Real-time apps (chat, live dashboards via WebSockets)Large in-memory matrix/scientific computation
    Streaming proxies and gatewaysHeavy image processing at scale (without offloading to workers)
    Server-side rendering, build tooling, CLIsPassword hashing at very high volume without worker threads

    🏗️ The Runtime Architecture

    Two pieces do the real work: V8 compiles and executes your JavaScript, and libuv is a C library that provides the event loop, thread pool, and async I/O primitives that JavaScript itself doesn't have.

    Figure 1.1 · V8 executes JS, libuv handles async I/O and the event loop
    ComponentRoleWritten in
    V8Parses and JIT-compiles JavaScript to machine codeC++
    libuvEvent loop, async file/network I/O, thread pool, timersC
    Node bindingsGlue that exposes libuv/V8 capability as JS APIs (fs, net...)C++ / JS

    Where the thread pool comes in

    Not everything libuv does is truly async at the OS level. Some operations — most filesystem calls, DNS lookups via dns.lookup, and some crypto functions — have no native async OS API on every platform, so libuv fakes it with a background thread pool (4 threads by default). Your JS callback still runs on the single main thread once the result is ready, but the actual blocking work happens off to the side. This is why a flood of fs.readFile calls can start queuing once you exceed the pool size — you can raise it with UV_THREADPOOL_SIZE, but it's a signal you may want streams or a different architecture instead.

    terminal$ UV_THREADPOOL_SIZE=8 node server.js

    Reading process signals gracefully

    In production, the process almost never dies because you called exit() — it dies because an orchestrator sent it a signal (Kubernetes sends SIGTERM before force-killing with SIGKILL).     jsprocess.on('SIGTERM', async () => {
  console.log('Received SIGTERM, shutting down gracefully');
  await server.close();      // stop accepting new connections
  await db.disconnect();     // close pooled connections
  process.exit(0);
});
    Module 02 · Modules & npm

    Modules & npm

    How Node splits code into files, how the two module systems differ, and how npm resolves, installs, and versions the packages your project depends on.

    📤 CommonJS vs ES Modules

    Node started with CommonJS (require/module.exports), the original module system. Modern Node also supports ECMAScript Modules (import/export), the standard used in browsers.

    📦 CommonJS (.cjs)

    // math.js
function add(a, b) { return a + b; }
module.exports = { add };

// app.js
const { add } = require('./math');
console.log(add(2, 3));

    Synchronous, loaded at require-time. Default unless "type": "module" is set.

    📤 ES Modules (.mjs)

    // math.js
export function add(a, b) { return a + b; }

// app.js
import { add } from './math.js';
console.log(add(2, 3));

    Asynchronous, statically analyzable, supports top-level await. File extensions are required.

    AspectCommonJSES Modules
    Syntaxrequire() / module.exportsimport / export
    LoadingSynchronousAsynchronous
    Enable viaDefault, or .cjs"type":"module" in package.json, or .mjs
    Top-level awaitNot supportedSupported
    __dirnameAvailableUse import.meta.url instead

    🗂️ node_modules & the Resolution Algorithm

    When you require('lodash'), Node doesn't guess — it walks up the directory tree looking for a matching node_modules folder.

    Figure 2.1 · Node walks up parent directories until it finds the module or hits the filesystem root
    💡
    This is why a single copy of a shared dependency can live in a top-level node_modules and still be found by nested packages — npm "hoists" common versions upward automatically.

    The require cache, and why "singletons" happen by accident

    Node caches every module the first time it's required, keyed by resolved absolute path — a second require('./db') anywhere in the app returns the exact same object, not a fresh copy. This is why a module that opens a database connection and exports it is effectively a singleton throughout your app, without you writing any singleton pattern. It also explains a classic bug: if you mutate an exported object from one file, every other file that required it sees the mutation, because they all hold the same reference.

    jsconsole.log(require.cache);           // every module Node has already loaded
delete require.cache[require.resolve('./config')]; // force a fresh reload (rare, mostly for tests)

    Module 03 · Concurrency Model

    Async & the Event Loop

    The single most-asked interview topic in Node.js: how one thread serves thousands of concurrent requests without ever blocking.

    🔄 Why Asynchronous?

    Node.js runs your JavaScript on a single thread. If that thread blocked waiting on a database query or a file read, every other request would freeze. Instead, Node hands slow operations off to libuv, keeps executing other code, and gets notified via a callback/promise when the result is ready.

    ⚠️
    Synchronous, blocking calls (like fs.readFileSync on a huge file, or a tight CPU-bound loop) freeze the entire server — every other connection waits. Prefer the async variant of any I/O API.

    🌀 The Event Loop Phases

    The event loop is a loop over fixed phases, each with its own queue of callbacks to run.

    Figure 3.1 · One full turn of the loop visits each phase, then repeats
    PhaseRuns
    TimersCallbacks scheduled by setTimeout/setInterval whose time has elapsed
    Pending callbacksI/O callbacks deferred from the previous loop iteration
    PollRetrieves new I/O events; executes their callbacks (this is where most work happens)
    ChecksetImmediate() callbacks, run right after poll
    Close callbackssocket.on('close', ...) and similar cleanup

    🪜 Callbacks → Promises → async/await

    Three generations of the same idea: "run this after the async thing finishes."

    js — callback (callback hell risk)fs.readFile('a.txt', (err, a) => {
  if (err) return console.error(err);
  fs.readFile('b.txt', (err, b) => {
    if (err) return console.error(err);
    console.log(a.toString(), b.toString());
  });
});
    js — promisereadFileP('a.txt')
  .then(a => readFileP('b.txt').then(b => [a, b]))
  .then(([a, b]) => console.log(a, b))
  .catch(err => console.error(err));
    js — async/await (preferred)async function readBoth() {
  try {
    const a = await fs.promises.readFile('a.txt', 'utf8');
    const b = await fs.promises.readFile('b.txt', 'utf8');
    console.log(a, b);
  } catch (err) {
    console.error(err);
  }
}
    💡
    Use Promise.all([...]) when tasks are independent, so they run concurrently instead of one after another — a common performance mistake is await-ing them sequentially for no reason.

    Sequential vs concurrent await — the mistake in practice

    js — accidentally sequential (slow)const user = await getUser(id);        // waits ~100ms
const posts = await getPosts(id);       // then waits another ~150ms
// total: ~250ms, even though these don't depend on each other
    js — actually concurrent (fast)const [user, posts] = await Promise.all([
  getUser(id),
  getPosts(id),
]);
// total: ~150ms — both requests fire immediately, we wait for the slower one

    Also know Promise.allSettled (waits for every promise, never rejects — gives you each result's status individually) and Promise.race (resolves/rejects as soon as the first promise settles, often used for timeouts).

    ⏱️ Microtasks vs Macrotasks

    Promise callbacks (microtasks) always drain completely before the event loop moves to the next macrotask phase — this is why promise code can appear to "jump the queue" ahead of setTimeout.

    jsconsole.log('1: sync');
setTimeout(() => console.log('2: macrotask (timer)'), 0);
Promise.resolve().then(() => console.log('3: microtask'));
console.log('4: sync');

// Output: 1, 4, 3, 2
    QueueExamplesPriority
    MicrotaskPromise.then, queueMicrotask, process.nextTickDrained fully before next macrotask
    MacrotasksetTimeout, setInterval, I/O callbacks, setImmediateOne per loop phase iteration

    📡 EventEmitter Pattern

    Most of Node's core async APIs (streams, servers, processes) are built on EventEmitter — a publish/subscribe pattern baked into the platform.

    jsconst { EventEmitter } = require('events');

class OrderQueue extends EventEmitter {}
const queue = new OrderQueue();

queue.on('order', (order) => {
  console.log('Processing order', order.id);
});

queue.emit('order', { id: 42 });

    A critical gotcha: uncaught errors on emitters

    If an EventEmitter emits an 'error' event and nothing is listening for it, Node treats it as an uncaught exception and crashes the process — this is a deliberate safety default, not a bug. Any long-lived emitter (a socket, a stream, a queue) needs an 'error' listener attached, even if it just logs.

    jsqueue.on('error', (err) => console.error('queue error:', err));
// without this, queue.emit('error', new Error('boom')) would crash the process

    Core Modules

    The built-in modules ship with every Node install — no npm install needed — and cover filesystem, OS, and process concerns.

    📁 fs — File System

    Every fs function has three flavors: callback-based, promise-based (fs.promises / fs/promises), and synchronous (suffixed Sync, blocking).

const data = await readFile('config.json', 'utf8');
const config = JSON.parse(data);

await mkdir('logs', { recursive: true });
await writeFile('logs/out.txt', 'server started\n', { flag: 'a' });
    FunctionPurpose
    readFile / writeFileWhole-file read/write
    createReadStream / createWriteStreamStream large files without loading them fully into memory
    watchGet notified when a file or directory changes
    statFile metadata — size, timestamps, type
    ⚠️
    Avoid fs.readFileSync in a request handler — it blocks the event loop for every other in-flight request until the disk read finishes.

    🧭 path & os

    path builds file paths correctly across operating systems (Windows uses \, POSIX uses /) — never concatenate paths with string templates.

    jsimport path from 'node:path';
import os from 'node:os';

path.join('uploads', 'avatars', 'user.png');   // 'uploads/avatars/user.png'

os.cpus().length;      // number of logical CPU cores

    🛠️ util & child_process

    util.promisify converts an old-style callback function into one that returns a promise — handy for legacy or third-party callback APIs.

    jsimport { promisify } from 'node:util';
import { exec } from 'node:child_process';

const execP = promisify(exec);

    child_process spawns other programs — shell commands, scripts in other languages, or CPU-heavy work you want out of the main thread.

    FunctionUse case
    execRun a shell command, buffer all output
    spawnStream output as it's produced, better for large output
    forkSpawn a new Node process with an IPC channel back to the parent

    ⏲️ Timers & process.nextTick

    jssetTimeout(() => console.log('after ~100ms'), 100);
const id = setInterval(() => console.log('every 2s'), 2000);
clearInterval(id);

setImmediate(() => console.log('runs after poll phase'));
process.nextTick(() => console.log('runs before any other async work'));
    📝
    process.nextTick() callbacks run even before promise microtasks, and before the event loop proceeds to any phase. Overusing it can starve I/O entirely.
    Module 05 · Binary & Streaming Data

    Streams & Buffers

    How Node processes data that's too large to hold in memory all at once — the mechanism underneath file uploads, video, and HTTP bodies.

    🌊 Why Streams?

    Reading a 4GB video file with readFile loads all 4GB into memory before you can touch a single byte. A stream instead processes data in small chunks as they arrive — constant memory use regardless of file size.

    💾
    Low memory
    Process gigabytes of data with kilobytes of RAM.
    ⚡
    Start immediately
    Begin sending a response before the full file is even read.
    🔗
    Composable
    Chain streams together — read, transform, compress, write.

    🧩 The Four Stream Types

    TypeDirectionExample
    ReadableSource you read fromfs.createReadStream, HTTP request body
    WritableDestination you write tofs.createWriteStream, HTTP response
    DuplexBoth readable and writable, independentTCP socket
    TransformDuplex that modifies data as it passes throughzlib.createGzip()

    🔗 Piping & Backpressure

    .pipe() connects a readable stream to a writable one and automatically handles backpressure — pausing the source if the destination can't keep up, so memory doesn't balloon.

    js — stream a file through gzip to diskimport { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';

createReadStream('access.log')
  .pipe(createGzip())
  .pipe(createWriteStream('access.log.gz'))
  .on('finish', () => console.log('done compressing'));
    Figure 5.1 · Piped stream pipeline with automatic backpressure

    🧱 Buffers

    A Buffer is a fixed-size chunk of raw binary memory, outside V8's normal heap — used whenever Node deals with bytes that aren't yet decoded text (file contents, TCP packets, images).

    jsconst buf = Buffer.from('hello', 'utf8');
console.log(buf);              // <Buffer 68 65 6c 6c 6f>
console.log(buf.toString());   // 'hello'
console.log(buf.length);       // 5 (bytes, not characters)

const empty = Buffer.alloc(10);  // 10 zeroed bytes
    ⚠️
    Prefer Buffer.alloc() over the deprecated new Buffer() — alloc always zeroes memory first, while the old constructor could return uninitialized memory that leaked whatever bytes happened to be there previously (a real, exploited vulnerability in older Node apps).

    Streams under real backpressure: writing manually

    .pipe() handles backpressure for you, but it helps to see what it's actually doing. A writable stream's .write() returns false when its internal buffer is full — that's the signal to stop pushing more data until a 'drain' event fires.

    js — what .pipe() does internally, simplifiedreadable.on('data', (chunk) => {
  const ok = writable.write(chunk);
  if (!ok) {
    readable.pause();                          // slow down the source
    writable.once('drain', () => readable.resume()); // resume once there's room
  }
});
    Module 06 · Servers

    Building Servers & APIs

    From the bare http module to Express, middleware chains, and a working REST API structure.

    🌐 The Raw http Module

    Every framework — Express, Fastify, Koa — is built on top of Node's built-in http module.

    jsimport { createServer } from 'node:http';

const server = createServer((req, res) => {
  if (req.url === '/' && req.method === 'GET') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ message: 'Hello' }));
  } else {
    res.writeHead(404);
    res.end('Not found');
  }
});

server.listen(3000, () => console.log('Listening on :3000'));
    📝
    Writing routing, body parsing, and error handling by hand for every route gets tedious fast — that's exactly what a framework like Express exists to remove.

    🚂 Express.js Basics

    terminal$ npm install express
    server.jsimport express from 'express';
const app = express();

app.use(express.json());  // parse JSON request bodies

app.get('/users/:id', (req, res) => {
  res.json({ id: req.params.id, name: 'Ada' });
});

app.post('/users', (req, res) => {
  const { name } = req.body;
  res.status(201).json({ id: 1, name });
});

app.listen(3000);

    🧵 Middleware

    Middleware functions run in a chain before your route handler — each one can modify the request, respond directly, or call next() to pass control along.

    Figure 6.1 · Each middleware calls next() to continue the chain
    jsfunction logger(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next();
}

function requireAuth(req, res, next) {
  if (!req.headers.authorization) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  next();
}

app.use(logger);
app.use('/admin', requireAuth);
    ⚠️
    Forgetting to call next() (or send a response) in a middleware leaves the request hanging forever — the client will eventually time out.

    🔌 Building a REST API

    ✅ Routing & Request Validation

    Never trust request input. Validate shape and types before touching a database — libraries like zod or joi make this declarative.

    jsimport { z } from 'zod';

const createPostSchema = z.object({
  title: z.string().min(1).max(200),
  body: z.string().min(1),
});

app.post('/posts', (req, res) => {
  const result = createPostSchema.safeParse(req.body);
  if (!result.success) {
    return res.status(400).json({ errors: result.error.issues });
  }
  // result.data is now typed & safe to use
});

    Async route handlers and unhandled rejections

    Express (before v5) does not automatically catch a rejected promise thrown inside an async route handler — an uncaught error there can silently hang the request or crash the process, depending on your global handlers. Wrap async handlers, or use a small utility that does it for you.

    jsconst asyncHandler = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next);

router.get('/posts/:id', asyncHandler(async (req, res) => {
  const post = await Post.findById(req.params.id); // if this throws, asyncHandler forwards it to next()
  if (!post) throw new NotFoundError('Post');
  res.json(post);
}));

    Pagination for list endpoints

    An endpoint like GET /posts that returns everything works fine with 20 rows and falls over with 200,000. Real APIs paginate.

    jsrouter.get('/posts', async (req, res) => {
  const page = Math.max(1, parseInt(req.query.page) || 1);
  const limit = Math.min(100, parseInt(req.query.limit) || 20);
  const posts = await Post.find()
    .skip((page - 1) * limit)
    .limit(limit);
  res.json({ page, limit, data: posts });
});
    Module 07 · Persistence

    Data & Databases

    Connecting Node to a real database safely — pooled connections, an ORM layer, and config that never gets hardcoded into source.

    🗄️ SQL vs NoSQL in Node

    🐘 SQL (PostgreSQL / MySQL)

    Structured schema, relations, strong consistency. Access via pg/mysql2, or an ORM like Prisma or Sequelize.

    🍃 NoSQL (MongoDB)

    Flexible document schema, natural JSON fit. Access via the mongodb driver or the Mongoose ODM.

    🔗 Connecting with an ORM

    js — Mongoose (MongoDB)import mongoose from 'mongoose';
await mongoose.connect(process.env.MONGO_URI);

const userSchema = new mongoose.Schema({
  name: String,
  email: { type: String, unique: true },
});
const User = mongoose.model('User', userSchema);

const user = await User.create({ name: 'Ada', email: 'ada@example.com' });
    js — Prisma (SQL)// schema.prisma defines models; `npx prisma generate` builds the client
import { PrismaClient } from '@prisma/client';
const prisma = new PrismaClient();

const user = await prisma.user.create({
  data: { name: 'Ada', email: 'ada@example.com' },
});

const users = await prisma.user.findMany({ where: { name: 'Ada' } });
    💡
    An ORM/ODM buys you parameterized queries by default — a strong defense against SQL/NoSQL injection, on top of the productivity win.

    🔐 Environment Variables & Config

    Secrets and per-environment values (DB URLs, API keys) never belong in source code. Load them from the environment.

    .envDATABASE_URL=postgres://user:pass@localhost:5432/mydb
JWT_SECRET=super-long-random-string
NODE_ENV=development
    jsimport 'dotenv/config';   // loads .env into process.env

const dbUrl = process.env.DATABASE_URL;
if (!dbUrl) throw new Error('DATABASE_URL is required');
    ⚠️
    Always add .env to .gitignore. Committing real secrets to a repo — even a private one — is one of the most common causes of credential leaks.

    🏊 Connection Pooling

    Opening a new database connection per request is slow and exhausts the database's connection limit. A pool keeps a set of connections open and reused.

    js — pg poolimport pg from 'pg';
const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20,          // max simultaneous connections
  idleTimeoutMillis: 30000,
});

const { rows } = await pool.query('SELECT * FROM users WHERE id = $1', [userId]);
    📝
    Note the $1 placeholder rather than string concatenation — this is a parameterized query, the standard defense against SQL injection.

    Transactions

    When multiple writes must succeed or fail together (e.g. debit one account, credit another), wrap them in a transaction — otherwise a crash between the two steps leaves the data inconsistent forever.

    js — Prisma transactionawait prisma.$transaction([
  prisma.account.update({ where: { id: fromId }, data: { balance: { decrement: amount } } }),
  prisma.account.update({ where: { id: toId },   data: { balance: { increment: amount } } }),
]);
// both updates commit together, or neither does

    N+1 queries — the classic ORM performance trap

    Looping over a list and querying inside the loop issues one query per item — fine for 5 rows, disastrous for 5,000.

    js — N+1 (slow)const posts = await Post.find();
for (const post of posts) {
  post.author = await User.findById(post.authorId); // one query PER post
}
    js — fixed with eager loadingconst posts = await Post.find().populate('authorId'); // Mongoose: one extra query, not N
// Prisma equivalent: prisma.post.findMany({ include: { author: true } })
    Module 08 · Reliability

    Errors & Debugging

    Handling failure well is most of what separates a toy Node app from a production one — from local try/catch up to process-level safety nets.

    🧯 Error-First Callbacks & try/catch

    Old-style Node callbacks always put an error as the first argument — check it before touching the result.

    jsfs.readFile('config.json', (err, data) => {
  if (err) return console.error('read failed:', err.message);
  console.log(data.toString());
});

// with async/await, use try/catch instead
try {
  const data = await fs.promises.readFile('config.json');
} catch (err) {
  console.error('read failed:', err.message);
}

    🏷️ Custom Error Classes

    jsclass HttpError extends Error {
  constructor(status, message) {
    super(message);
    this.status = status;
    this.name = 'HttpError';
  }
}

class NotFoundError extends HttpError {
  constructor(resource) {
    super(404, `${resource} not found`);
  }
}

throw new NotFoundError('User');
    💡
    Custom error classes let a single centralized handler decide the right HTTP status and response shape by checking err.status or instanceof, instead of parsing error strings.

    🕸️ Centralized Express Error Handling

    An error-handling middleware takes four arguments — Express detects this signature and routes errors there automatically.

    jsapp.get('/users/:id', async (req, res, next) => {
  try {
    const user = await User.findById(req.params.id);
    if (!user) throw new NotFoundError('User');
    res.json(user);
  } catch (err) {
    next(err);   // hands off to the error middleware below
  }
});

// must be registered LAST, after all routes
app.use((err, req, res, next) => {
  const status = err.status || 500;
  console.error(err);
  res.status(status).json({ error: err.message || 'Internal Server Error' });
});

    🛟 uncaughtException & unhandledRejection

    These are last-resort, process-wide safety nets — not a substitute for handling errors where they occur.

    jsprocess.on('uncaughtException', (err) => {
  console.error('Uncaught exception:', err);
  process.exit(1);   // the process is in an unknown state — restart it
});

process.on('unhandledRejection', (reason) => {
  console.error('Unhandled rejection:', reason);
  process.exit(1);
});
    ⚠️
    After an uncaught exception, Node's internal state may be corrupted. The correct response is to log it and exit — let a process manager like PM2 or a container orchestrator restart the process cleanly.

    Reading a stack trace properly

    Node stack traces read top-to-bottom, innermost call first. The most common mistake is skimming past the top line (usually your own code) and staring at the deep framework internals instead — the top frame in your source is almost always where the fix belongs, even if the error message originates deep in a library.

    jsTypeError: Cannot read properties of undefined (reading 'name')
    at getUserName (/app/services/user.js:12:20)   ← fix here first
    at processTicksAndRejections (node:internal/process/task_queues:95:5)
    at async /app/routes/users.js:8:18

    Memory leaks — a real production hazard

    Because Node processes tend to live for days or weeks, small leaks compound. Common causes: event listeners added but never removed, growing in-memory caches with no eviction, and closures holding references to large objects longer than needed. node --inspect's heap snapshot comparison (two snapshots, diffed) is the standard way to hunt one down.

    🖥️ Clustering & Worker Threads

    Node uses one thread per process. To use every CPU core, run one Node process per core (cluster) — or, for CPU-heavy work inside a single request, use worker_threads.

    Figure 10.1 · The cluster module spreads load across cores
    jsimport cluster from 'node:cluster';
import os from 'node:os';

if (cluster.isPrimary) {
  os.cpus().forEach(() => cluster.fork());
} else {
  // each worker runs the actual server
  app.listen(3000);
}

    Most process managers (like PM2) and container orchestrators do this clustering for you, which is usually simpler than managing it by hand.

    Cache invalidation — the hard part

    Writing to cache is easy; knowing when to throw it away is not. Two common strategies: a short TTL (accept some staleness for simplicity) or explicit invalidation on write (delete/update the cache key the moment the underlying data changes). Stale cached data silently served to users is a much quieter bug than a crash, and correspondingly easier to ship by accident.

    js — Redis cache-aside patternasync function getUser(id) {
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached);

  const user = await db.users.findById(id);
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 300); // 5 min TTL
  return user;
}

async function updateUser(id, data) {
  const user = await db.users.update(id, data);
  await redis.del(`user:${id}`); // invalidate on write
  return user;
}

    Zero-downtime deploys

    Naively restarting a process drops every in-flight request during the restart window.

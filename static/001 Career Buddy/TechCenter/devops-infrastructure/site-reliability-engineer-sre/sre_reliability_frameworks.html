    Module 01 · Foundations

    Reliability Fundamentals

    Reliability is the feature users notice most when it is missing. SLIs, SLOs, SLAs and error budgets turn "is the service good enough?" from an opinion into a number.

    🛡️ What is reliability? Basic

    Reliability is the probability that a service does what users expect, when they expect it. Site Reliability Engineering (SRE) treats it as a measurable product feature, not a vague goal.

    🚗
    Analogy: a car that starts 99 days out of 100 sounds great, until you realise that is 3–4 failed mornings a year. Reliability is always defined from the user's point of view.

    ❌ Without measurement

    • "The site feels slow"

    • Dev and Ops argue about priorities

    • Outages treated as shameful

    • Either too risky or over-engineered

    ✅ With SLIs / SLOs

    • "p99 latency was 420 ms vs 300 ms target"

    • One shared number to decide with

    • Failure is budgeted and expected

    • Balance of speed vs stability

    🔤 SLI vs SLO vs SLA Basic

    Three terms, three jobs. Learn them as a chain: you measure (SLI), aim (SLO), then promise (SLA).

    TermFull nameMeaningExampleWho cares
    SLIService Level IndicatorA measured number about service health% of requests answered in < 300 msEngineers
    SLOService Level ObjectiveInternal target for an SLI over a time window99.9% of requests < 300 ms over 30 daysEng + Product
    SLAService Level AgreementContract with customers, with penalties99.5% uptime or 10% creditBusiness / Legal
    SLI (measure)→SLO (target)→SLA (contract)
    📌
    Always set the SLO stricter than the SLA. If SLA = 99.5%, run SLO = 99.9% so you get warned before you owe money.

    ⏱️ What does "nines" really mean? Basic

    Availability targets are quoted in "nines". Each extra nine is roughly 10× harder and costlier.

    AvailabilityDowntime / 30 daysDowntime / yearTypical for
    99%7.2 hours3.65 daysInternal tools
    99.9% (three nines)43.2 min8.76 hoursMost SaaS APIs
    99.95%21.6 min4.38 hoursPayments, B2B
    99.99% (four nines)4.3 min52.6 minCore infra, DNS
    99.999%26 sec5.3 minTelecom, rarely worth it
    pythondef allowed_downtime_minutes(slo, days=30):
    return (1 - slo) * days * 24 * 60

print(allowed_downtime_minutes(0.999))   # 43.2 minutes

    Module 02 · Measure

    Service Level Indicators

    An SLI is a ratio: good events ÷ valid events. Pick indicators that reflect what the user feels, not what the server finds convenient to count.

    📏 The golden formula Basic

    SLI = good events / valid events × 100%. It always lands between 0% and 100%, which makes SLIs easy to compare and alert on.

    🍕
    Example: a pizza shop gets 1,000 orders; 970 arrive hot and within 30 min. SLI = 970/1000 = 97%.
    promql# Availability SLI: share of non-5xx requests, last 5m
sum(rate(http_requests_total{job="api",code!~"5.."}[5m]))
/
sum(rate(http_requests_total{job="api"}[5m]))

    🧩 Types of SLIs Basic

    Choose the type by service shape:

    TypeQuestion it answersGood forExample SLI
    AvailabilityDid it respond successfully?APIs, web appsNon-5xx / all requests
    LatencyWas it fast enough?Interactive requestsRequests under 300 ms / all
    ThroughputCan it keep up?Pipelines, batchJobs processed per minute
    CorrectnessWas the answer right?Data, search, billingRecords with valid checksum / all
    FreshnessHow stale is the data?Caches, dashboardsRows updated in < 5 min / all
    DurabilityIs data still there?Storage, backupsObjects readable after 1 yr
    CoverageDid we process everything?ETL, indexingDocs indexed / docs received

    🔬 Where to measure Intermediate

    Closer to the user is more truthful but noisier.

    Vantage pointProsCons
    Application metricsEasy, rich labelsMisses crashes before the app counts
    Load balancer / ingressSees all traffic, includes errorsNo business meaning
    Synthetic probesCatches full-path outagesLow sample size
    Real User MonitoringTrue user experienceClient noise, privacy
    ⚠️
    Never use CPU, memory or pod restarts as an SLI. They are causes (use for debugging), not user-visible symptoms.

    🧠 Critical User Journeys (CUJ) Intermediate

    Start with 2–4 journeys, not every endpoint. Example for an e-commerce site:

    JourneySLITarget
    Browse catalogLatency: GET /products < 400 ms99%
    CheckoutAvailability: POST /checkout success99.95%
    Order emailFreshness: sent within 2 min99%
    Percentiles over averagesExclude health checksCount retries carefullyUse histograms

    🎯 Expert: percentiles & histograms Expert

    Averages hide pain: 99 requests at 100 ms and 1 at 10 s average ~200 ms yet one user waited ten seconds. Use threshold-based SLIs built on histogram buckets.

    promql# Latency SLI: share of requests faster than 300 ms
sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
    💡
    Bucket boundaries must include your threshold (0.3 here), otherwise you cannot compute the SLI exactly. Plan buckets before shipping the metric.

    Module 03 · Target & Promise

    SLOs and SLAs

    An SLO is the reliability target your team signs up for. An SLA is the legal wrapper. Done well, SLOs end arguments; done badly, they become a vanity metric.

    🎯 Writing a good SLO Basic

    Formula: SLI + target + window.

    text"99.9% of checkout requests succeed over a rolling 30 days"
  SLI    = successful checkout requests / all checkout requests
  Target = 99.9%
  Window = rolling 30 days

    ❌ Bad SLOs

    • "The site is always up" (100%)

    • No window, no SLI

    • Based on CPU usage

    • Set by guess, never reviewed

    ✅ Good SLOs

    • Achievable and below 100%

    • Clear ratio and window

    • User-visible symptom

    • Reviewed quarterly with product

    🪟 Window types Intermediate

    Rolling windows are smoother; calendar windows match business reporting.

    WindowBehaviourUse when
    Rolling 28/30 daysOld failures age out graduallyEngineering decisions, alerting
    Calendar monthResets on the 1stSLA reports, billing
    Per-quarterLong, forgivingStrategic reviews

    📜 SLA essentials Intermediate

    An SLA lists what is measured, how, exclusions and the remedy.

    ItemExample
    MetricMonthly uptime of the public API
    Target99.5%
    ExclusionsScheduled maintenance, customer-caused outages, force majeure
    Remedy< 99.5% → 10% credit; < 99.0% → 25% credit
    📌
    Real-world SLAs: AWS S3 offers 99.9% with credits; Google Cloud and Azure follow similar tiered credits.

    🔗 Expert: composite SLOs Expert

    If your service needs three dependencies in series, availabilities multiply:

    pythondeps = [0.999, 0.999, 0.999]       # DB, cache, auth
combined = 1
for d in deps: combined *= d
print(round(combined*100, 3))      # 99.7  -> you cannot promise 99.9%
    💡
    Fixes: make dependencies soft (fallbacks, caches), add redundancy (parallel multiplies the failure rates instead), or negotiate tighter SLOs with the dependency owner.

    Module 04 · Spend

    Error Budgets

    The error budget is the amount of unreliability you are allowed. It converts reliability into currency that product and engineering can spend together.

    💰 What is an error budget? Basic

    Error budget = 100% − SLO. A 99.9% SLO over 30 days leaves 0.1% — about 43 minutes of failure, or 1 in 1,000 bad requests.

    🏦
    Analogy: a monthly bank balance. Risky deploys, experiments and outages all spend it. Quiet weeks let it recover. Empty balance = stop spending.
    pythonslo, total, bad = 0.999, 10_000_000, 4_200
budget   = (1 - slo) * total       # 10,000 allowed bad requests
consumed = bad / budget            # 0.42  -> 42% used
print(f"{consumed:.0%} of budget used, {1-consumed:.0%} left")

    📋 Error budget policy Intermediate

    A written policy decides what happens at each level, agreed by product, engineering and leadership before an incident.

    Budget remainingAction
    > 50%Ship freely, run experiments, chaos tests
    25–50%Extra review for risky changes, prioritise reliability bugs
    0–25%Only low-risk changes, pause feature launches
    ExhaustedFeature freeze; team works only on reliability until recovered
    ✅
    Result: nobody argues "is it stable enough to ship?". The number answers it.

    🔥 Burn rate Intermediate

    Burn rate = how fast you consume budget relative to the plan. Burn rate 1 = exactly exhausted at the window end; 14.4 = gone in ~2 days.

    promql# burn rate = error ratio / allowed error ratio
(1 - (sum(rate(http_requests_total{code!~"5.."}[1h]))
      / sum(rate(http_requests_total[1h]))))
/ (1 - 0.999)

    🚨 Expert: multi-window multi-burn alerts Expert

    Alert on budget consumption speed, not raw error spikes. Google SRE Workbook recommends pairing a long and a short window to cut noise.

    SeverityBurn rateLong windowShort windowBudget spent
    Page14.41 h5 min2%
    Page66 h30 min5%
    Ticket13 days6 h10%
    yaml- alert: ErrorBudgetFastBurn
  expr: slo:burnrate1h > 14.4 and slo:burnrate5m > 14.4
  labels: {severity: page}
  annotations: {summary: "Burning 2% of monthly budget per hour"}

    Module 05 · Operate at scale

    Expert Practices

    Make SLOs part of how the organisation works: defined as code, reviewed regularly and wired into planning.

    🧾 SLO as code Expert

    Store SLOs in Git (OpenSLO, Sloth, Pyrra) so alerts and dashboards are generated, reviewed and versioned.

    yaml# sloth.yml
version: "prometheus/v1"
service: "checkout"
slos:
  - name: "requests-availability"
    objective: 99.9
    sli:
      events:
        error_query: sum(rate(http_requests_total{code=~"5.."}[{{.window}}]))
        total_query: sum(rate(http_requests_total[{{.window}}]))
    alerting: {name: CheckoutAvailability}

    🔁 The SLO review loop Expert

    Measure→Review monthly→Adjust SLO→Plan reliability work→Measure
    • Too many nines unused? Tighten or ship faster.
    • Budget always empty? Loosen or invest in reliability.
    • Users unhappy though SLO green? Wrong SLI; revisit journeys.

    ⚠️ Common pitfalls Expert

    • Targeting 100% (impossible, kills velocity)
    • Too many SLOs (aim for 3–5 per service)
    • Averages instead of percentiles
    • SLO set without product buy-in
    • Alerting on causes (CPU) instead of burn rate

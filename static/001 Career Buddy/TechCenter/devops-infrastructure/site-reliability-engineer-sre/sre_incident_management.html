    Module 01 · Foundations

    Incident Management Basics

    An incident is any unplanned event that degrades the service. Good incident management is about restoring service fast and learning so it does not repeat.

    🚨 What is an incident? Basic

    Incident ≠ every alert. It is an event that impacts users or SLOs and needs a coordinated response.

    Detect→Triage→Mitigate→Resolve→Postmortem→Prevent
    🔥
    Analogy: a fire brigade. First stop the fire (mitigate), later investigate the cause (root cause). Do not debug wiring while the house burns.

    📶 Severity levels Basic

    Severity sets urgency, people involved and communication cadence.

    LevelImpactExampleResponse
    SEV1Major outage / data lossCheckout down for all usersPage everyone, update every 15 min
    SEV2Serious degradationSearch 5× slowerPage on-call, update every 30 min
    SEV3Minor / workaround existsOne region has delayed emailsTicket, next business day
    SEV4CosmeticTypo on dashboardBacklog

    ⏲️ Key metrics Intermediate

    MetricMeaning
    MTTDMean time to detect
    MTTAMean time to acknowledge
    MTTM / MTTRMean time to mitigate / restore
    MTBFMean time between failures
    📌
    Reduce MTTM first (rollback, failover). Customers care about recovery, not the root cause.

    Module 02 · Human side

    On-Call Rotations

    On-call is a sustainable responsibility when it is shared fairly, tooling is good and alerts are meaningful.

    📟 Rotation models Basic

    Common models:

    ModelHow it worksBest for
    Primary / secondarySecondary backs up if primary misses a pageMost teams
    Follow-the-sunTeams in different time zones hand off dailyGlobal companies, no night shifts
    Weekly rotationOne person for 7 daysSmall teams
    Tiered (L1/L2/SME)Escalate to experts if neededLarge orgs

    🔔 Good alerts Intermediate

    • Actionable: a human must do something now
    • Symptom-based: alert on user pain, not CPU
    • Linked to a runbook and dashboard
    yaml# PagerDuty-style escalation policy
level_1: primary_oncall     # ack within 5 min
level_2: secondary_oncall   # after 5 min no ack
level_3: engineering_manager
    ⚠️
    Alert fatigue is dangerous. If more than ~2 pages per 12-hour shift, fix alerts before adding people.

    🤝 Handoff checklist Intermediate

    • Open incidents and their status
    • Risky changes planned this week
    • Flapping alerts to tune
    • Compensation / time off after a hard shift

    Module 03 · During the fire

    Running an Incident

    Clear roles and calm communication beat heroics.

    🎖️ Roles Intermediate

    Based on the Incident Command System:

    🧭
    Incident Commander
    Owns the response, delegates, makes decisions. Does not debug.
    🔧
    Ops Lead
    Hands on the keyboard, executes mitigation
    📣
    Comms Lead
    Updates status page, execs and support
    📝
    Scribe
    Keeps a timeline of what, who, when

    🛠️ Mitigate first Intermediate

    Fast mitigations:

    Rollback deployFeature flag offFail over regionScale upShed loadRestart
    bash# Mitigation example: roll back a bad release
kubectl rollout undo deployment/checkout -n prod
kubectl rollout status deployment/checkout -n prod

    📣 Communication template Expert

    Update on a fixed cadence even when there is no news.

    text[14:20 UTC] SEV2 - Checkout errors
Impact:  ~12% of checkouts failing since 14:05
Status:  Mitigating - rolling back release 4.18
Next:    Update at 14:50 or sooner
IC: @alex   Comms: @priya

    Module 04 · Learn

    Postmortems and Root-Cause Analysis

    A blameless postmortem asks "how did the system allow this?" instead of "who did this?". People who fear blame hide information.

    📄 Postmortem template Basic

    • Summary and impact (users, duration, revenue)
    • Timeline (detection, escalation, mitigation)
    • Root cause(s) and contributing factors
    • What went well / badly / lucky
    • Action items with owner and due date
    ✅
    Actions must be specific and tracked, e.g. "Add canary stage to checkout pipeline - @sam - 14 Nov", not "be more careful".

    ❓ 5 Whys (basic RCA) Basic

    Ask "why?" repeatedly until you reach a fixable process or system cause.

    Why?Answer
    1. Why was checkout down?Pods crashed with out-of-memory
    2. Why OOM?New release cached all products
    3. Why shipped?Load test used a small dataset
    4. Why small?No production-like test data
    5. Why not?No standard process for test data

    🔍 Other RCA methods Intermediate

    MethodIdeaUse when
    Fishbone (Ishikawa)Group causes by category: people, process, tech, environmentMany possible causes
    Fault treeBoolean tree of AND/OR failuresSafety-critical analysis
    Timeline analysisAlign events to find triggersComplex multi-system incidents
    Contributing factorsReject a single "root cause", list severalModern distributed systems

    🧠 Expert: beyond human error Expert

    "Human error" is a symptom. Look for missing guardrails: no review, unclear docs, risky tool defaults, tests that cannot catch the bug.

    💡
    Ask: "Would a competent engineer under the same pressure make the same choice?" If yes, fix the system.

    Module 05 · Break it on purpose

    Chaos Engineering

    Inject controlled failures to find weaknesses before users do.

    🧪 The scientific method Basic

    Chaos is not random breakage. It is an experiment:

    Define steady state→Hypothesis→Inject failure→Observe→Fix
    📌
    Example hypothesis: "If one of 3 API pods dies, error rate stays below 0.1%."

    🧰 Tools Intermediate

    ToolTypeNotes
    GremlinSaaS, agent-basedSafe UI, CPU, network, shutdown, blackhole attacks
    Chaos MeshKubernetes-native, CNCFCRDs for pod, network, IO, time faults
    LitmusChaosKubernetes, CNCFChaosHub experiments
    AWS FISCloud serviceFaults on AWS resources

    📦 Chaos Mesh example Intermediate

    Kill one pod of the checkout service:

    yamlapiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata: {name: kill-checkout, namespace: chaos}
spec:
  action: pod-kill
  mode: one
  selector:
    namespaces: [prod]
    labelSelectors: {app: checkout}

    Add 300 ms network latency:

    yamlkind: NetworkChaos
spec:
  action: delay
  mode: all
  selector: {labelSelectors: {app: checkout}}
  delay: {latency: "300ms", jitter: "50ms"}
  duration: "5m"

    🎮 Expert: Game Days & safety Expert

    • Start in staging, small blast radius, then production
    • Abort conditions: stop if error budget burn > threshold
    • Run with on-call present and a status channel
    • Automate experiments in CI/CD (continuous chaos)

    Module 06 · Survive the worst

    Disaster Recovery

    DR is how you recover from losing a data center, region or your data.

    ⏱️ RTO and RPO Basic

    TermQuestionExample
    RTOHow long can we be down?Restore within 1 hour
    RPOHow much data can we lose?At most 5 minutes of data
    🎯
    Smaller RTO/RPO = higher cost. Set per service tier, not company-wide.

    🏗️ DR strategies Intermediate

    StrategyRTO / RPOCostHow
    Backup & restoreHours / hours$Backups in another region
    Pilot lightTens of minutes$$Minimal core running, scale on disaster
    Warm standbyMinutes$$$Scaled-down copy always running
    Active-activeSeconds / ~0$$$$Traffic served from multiple regions

    🧯 Expert: prove it works Expert

    • 3-2-1 backups: 3 copies, 2 media, 1 offsite
    • Test restores regularly (an untested backup is a hope)
    • Run regional failover drills
    • Keep DR runbooks outside the failing infra
    bash# Backup restore drill (nightly job)
pg_restore --dbname=restore_test /backups/latest.dump
psql restore_test -c "SELECT count(*) FROM orders;"

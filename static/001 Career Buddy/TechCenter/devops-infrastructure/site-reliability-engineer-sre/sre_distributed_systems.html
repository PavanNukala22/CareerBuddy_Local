    Module 01 · Foundations

    Distributed Systems Fundamentals

    A distributed system is many computers cooperating to look like one. It scales and survives failures, but introduces partial failure, latency and inconsistency.

    🌐 What and why Basic

    Instead of one big machine, use many small ones for scale, availability and locality.

    🍕
    Analogy: one pizza oven (single server) vs a chain of shops. More capacity and one shop closing is fine, but keeping every menu and price identical is hard.

    ❌ Challenges

    • Networks drop and delay messages

    • Clocks disagree

    • Nodes fail partially

    • Hard to debug

    ✅ Benefits

    • Horizontal scaling

    • No single point of failure

    • Low latency near users

    • Independent deploys

    🙈 Fallacies of distributed computing Basic

    • The network is reliable
    • Latency is zero
    • Bandwidth is infinite
    • The network is secure
    • Topology does not change
    • There is one administrator
    • Transport cost is zero
    • The network is homogeneous
    📌
    Every one of these is false. Design for timeouts, retries and partial failure from day one.

    ⚖️ CAP theorem & consistency Intermediate

    During a network Partition you must choose Consistency or Availability.

    ChoiceBehaviour in partitionExamples
    CPReject some requests to stay correctetcd, ZooKeeper, HBase
    APAnswer always, may be staleCassandra, DynamoDB (default), DNS
    Consistency modelMeaning
    Strong / linearizableReads see the latest write
    EventualReplicas converge given time
    CausalRelated events seen in order
    Read-your-writesYou see your own updates

    Module 02 · The wire

    Networking Protocols

    Most outages blend application and network behaviour. Understand the layers.

    🧱 TCP/IP stack Basic

    LayerRoleExamples
    ApplicationWhat apps sayHTTP, gRPC, DNS, TLS
    TransportReliable / fast deliveryTCP, UDP, QUIC
    InternetAddressing and routingIP, ICMP
    LinkLocal deliveryEthernet, Wi-Fi, ARP
    SYN→SYN-ACK→ACK→Data→FIN

    The TCP 3-way handshake adds 1 round trip before any data flows.

    🆚 TCP vs UDP vs QUIC Basic

    TCPUDPQUIC
    Reliable, orderedYesNoYes
    Handshake cost1 RTT + TLSNone0–1 RTT with TLS 1.3
    Head-of-line blockingYesNoPer-stream only
    Used byHTTP/1.1, HTTP/2DNS, video, gamesHTTP/3

    📨 HTTP/1.1 → 2 → 3 and gRPC Intermediate

    ProtocolKey ideaSRE impact
    HTTP/1.1One request per connection at a timeMany connections, keep-alive tuning
    HTTP/2Multiplexed streams, header compressionFew long-lived connections; LB must balance requests
    HTTP/3HTTP over QUICBetter on lossy mobile networks
    gRPCHTTP/2 + Protobuf, streaming, deadlinesNeeds L7 load balancing; propagate deadlines
    ⚠️
    gRPC reuses one HTTP/2 connection, so a plain L4 balancer sends everything to one backend. Use an L7 proxy (Envoy) or client-side balancing.

    🔥 Expert: reading a latency breakdown Expert

    Slow request? Split time into phases: DNS → TCP connect → TLS → first byte → download. High connect means network or SYN backlog; high TTFB means slow backend; high DNS means resolver problems.

    Module 03 · Under the hood

    Linux Kernel Tuning

    Defaults suit a laptop. Busy servers often need limits raised, but tune with measurements, never from copy-pasted blog lists.

    🧮 Resources the kernel manages Intermediate

    CPU scheduler, memory, file descriptors, network buffers, and disk I/O. Bottlenecks usually show as saturation.

    🧭
    Use the USE method (Brendan Gregg): for each resource check Utilization, Saturation, Errors.
    bashuptime                 # load average
vmstat 1               # run queue, swap, io wait
iostat -x 1            # disk utilisation
sar -n DEV 1           # network throughput

    🌐 Network sysctls Intermediate

    Persist in /etc/sysctl.d/99-tuning.conf, then sysctl --system.

    confnet.core.somaxconn = 4096                  # accept queue length
net.ipv4.tcp_max_syn_backlog = 8192        # half-open connections
net.ipv4.ip_local_port_range = 10240 65535 # more outbound ports
net.ipv4.tcp_tw_reuse = 1                  # reuse TIME_WAIT sockets
net.core.rmem_max = 16777216               # socket buffers
net.core.wmem_max = 16777216

    📂 Limits, memory & cgroups Intermediate

    • File descriptors: raise ulimit -n / LimitNOFILE (“too many open files”)
    • vm.swappiness low (e.g. 10) for databases
    • Transparent Huge Pages: often disabled for databases
    • cgroups: how containers limit CPU and memory; exceeding the memory limit triggers the OOM-killer
    bashulimit -n                               # current fd limit
cat /sys/fs/cgroup/memory.max           # container memory limit
dmesg | grep -i "killed process"        # OOM kills

    🚀 Expert: eBPF & conntrack Expert

    Use eBPF tools (bpftrace, bcc) for low-overhead tracing. Watch nf_conntrack: a full table silently drops packets.

    bashsudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
sysctl net.netfilter.nf_conntrack_max
conntrack -C        # current entries
    ⚠️
    Change one setting at a time, record before/after metrics, and roll out through canary hosts.

    Module 04 · Design

    Scalable Architecture

    Scaling is a toolbox: spread load, copy data, remember results and absorb bursts.

    ⚖️ Load balancing Basic

    TypeLayerNotes
    L4TCP/UDPVery fast, no HTTP awareness (NLB, HAProxy tcp)
    L7HTTP/gRPCRouting by path/header, retries (Envoy, NGINX, ALB)
    DNS / GSLBDNSGeographic or failover routing
    Round robinLeast connectionsConsistent hashingHealth checks

    🗄️ Replication & sharding Intermediate

    TechniqueIdeaTrade-off
    ReplicationCopies of the same dataAvailability, read scaling; replication lag
    ShardingSplit data by keyWrite scaling; hot shards, resharding pain
    Partitioning by timeNew table per day/monthEasy retention, uneven load

    ⚡ Caching & queues Intermediate

    • Cache: CDN, Redis, local; plan invalidation and stampede protection
    • Queue: Kafka, SQS, RabbitMQ decouple producers from consumers and absorb bursts
    Client→CDN→LB→App→Cache→DB

    🗳️ Expert: consensus Expert

    Raft and Paxos let nodes agree on a value despite failures. A cluster of 2f+1 nodes survives f failures (3 nodes tolerate 1; 5 tolerate 2). Used by etcd, Consul and Kafka KRaft.

    📌
    Always run an odd number of voters so a network split cannot create two majorities.

    Module 05 · Fail gracefully

    Resilience Patterns

    You cannot prevent failure, so design for degraded success.

    🧱 Core patterns Intermediate

    PatternWhat it doesExample
    TimeoutBound waiting3 s deadline per call
    Retry + backoffRecover from transient errors3 tries with jitter
    Circuit breakerStop calling a failing dependencyOpen after 50% errors, probe later
    BulkheadIsolate resourcesSeparate thread pool per dependency
    Load sheddingReject excess work earlyReturn 503 above capacity
    Graceful degradationReduced feature setShow cached recommendations

    🔌 Circuit breaker in code Expert

    pythonimport time
class Breaker:
    def __init__(self, max_fail=5, reset=30):
        self.f, self.max, self.reset, self.opened = 0, max_fail, reset, 0
    def call(self, fn):
        if self.f >= self.max and time.time() - self.opened < self.reset:
            raise RuntimeError("circuit open")      # fail fast
        try:
            r = fn(); self.f = 0; return r
        except Exception:
            self.f += 1; self.opened = time.time(); raise
    ⚠️
    Retries multiply load: 3 layers × 3 retries = 27× traffic on the bottom service. Use retry budgets and deadlines propagated across calls.

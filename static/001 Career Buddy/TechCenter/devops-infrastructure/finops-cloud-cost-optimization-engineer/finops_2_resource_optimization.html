    Topic 01 · Compute

    Workload Right-sizing

    Match resource size to what the workload actually needs. The single biggest and safest savings lever in most estates.

    🔰 Basics: What Is Right-sizing?

    Right-sizing means choosing the cheapest instance size/type/configuration that still meets performance requirements. Over-provisioning happens because engineers size for peak, copy old settings, or fear outages.

    Basic exampleAn m5.4xlarge (16 vCPU, 64 GiB) averages 8% CPU and 20% memory. Moving to m5.xlarge (4 vCPU, 16 GiB) cuts that instance's cost by about 75% with little risk.
    Right-sizing directionMeaning
    Down-sizeSmaller size in the same family
    Re-familySwitch to a better-fit family (compute, memory, burstable)
    Re-generationMove to newer generation or Graviton/ARM for better price-performance
    Re-architectServerless, autoscaling, or managed service

    🧪 Intermediate: Method and Metrics

    1. Collect 2–4 weeks of CPU, memory, network, disk metrics (memory needs an agent such as the CloudWatch agent).
    2. Choose a statistic: use P95/P99 not average, so spikes are respected.
    3. Pick target: aim for 40–70% peak utilisation headroom depending on criticality.
    4. Test in staging or on one canary instance.
    5. Change, monitor, roll back if latency/error SLOs break.
    ToolCloudNotes
    Compute OptimizerAWSML-based EC2/EBS/Lambda/ECS recommendations
    Azure AdvisorAzureFlags under-used VMs and suggests size
    GCP RecommenderGCPMachine-type recommendations
    Kubecost / VPAKubernetesRequest/limit recommendations

    🚀 Expert: Containers, Autoscaling and Risk

    • Kubernetes: set requests near P90–P95 usage, limits carefully (CPU limits can throttle). Use Vertical Pod Autoscaler (recommend mode first) and Horizontal Pod Autoscaler.
    • Bin-packing: Karpenter or Cluster Autoscaler to consolidate nodes.
    • Graviton/ARM: often around 20% better price-performance but needs ARM-compatible builds.
    • Databases: right-size using IOPS, connections and buffer-hit ratios, not only CPU.
    resources:
  requests: { cpu: "250m", memory: "512Mi" }   # ~P95 of observed usage
  limits:   { memory: "768Mi" }                # memory limit yes; avoid hard CPU limit
    ⚠️
    Never right-size from average CPU alone, never from a quiet week (month-end jobs!), and never change production without a rollback plan. Savings that cause incidents are not savings.

    Topic 02 · Waste elimination

    Terminating Idle Resources

    Resources that cost money but deliver no value. The easiest 5–15% saving in many bills.

    🔰 Basics: What Counts as Idle?

    Unattached volumes
    EBS/Managed disks not attached to any VM still bill per GB.
    Stopped VMs
    Compute stops billing but attached disks and IPs still bill.
    Unused IPs / LBs
    Public IPv4 addresses and load balancers with no traffic bill hourly.
    Old snapshots & AMIs
    Forgotten backups grow forever.
    Dev/test off-hours
    Non-prod running 24×7 when used ~50 of 168 hours per week.
    Zombie projects
    Experiments nobody owns.
    ExampleRunning a dev environment 24×7 = 168 h. Running 8am–8pm Mon–Fri = 60 h. Savings: (168−60)/168 ≈ 64% just by scheduling.

    🧪 Intermediate: Detect, Notify, Delete Safely

    1. Detect with rules: CPU < 5% and network < 1 MB/day for 14 days; 0 requests on a load balancer; unattached for 30 days.
    2. Tag and notify the owner (idle-candidate=2026-10-05).
    3. Grace period (7–14 days) with an easy opt-out.
    4. Snapshot then stop; delete after a second grace period.
    5. Report savings.
    # List unattached EBS volumes (AWS CLI)
aws ec2 describe-volumes --filters Name=status,Values=available \
  --query 'Volumes[].[VolumeId,Size,CreateTime]' --output table

    🚀 Expert: Automation and Guardrails

    • Schedulers: AWS Instance Scheduler, Azure Automation/Start-Stop v2, or Kubernetes CronJobs scaling dev namespaces to zero at night.
    • Policy-as-code: Cloud Custodian or Config rules to auto-stop idle assets.
    • TTL tags: expires-on enforced on sandbox accounts.
    • Scale-to-zero: serverless and KEDA for event-driven workloads.
    policies:
  - name: stop-idle-dev-ec2
    resource: ec2
    filters:
      - "tag:env": dev
      - type: metrics
        name: CPUUtilization
        days: 7
        value: 3
        op: less-than
    actions: [ stop ]
    ⚠️
    Idle is not always waste: DR standby, license servers, quarterly batch hosts. Always confirm with the owner and keep a restore path.

    Topic 03 · Storage

    Storage Lifecycle Policies

    Automatically move data to cheaper tiers as it ages, and delete it when it has no value.

    🔰 Basics: Storage Tiers

    Data is hot when new and cold when old. Colder tiers cost less per GB but charge more for retrieval and have minimum storage durations.

    AWS S3 classUse forNotes
    StandardFrequently accessedNo retrieval fee
    Intelligent-TieringUnknown/changing accessAuto-moves objects; small monitoring fee per object
    Standard-IA / One Zone-IAInfrequent access30-day minimum; retrieval fee
    Glacier Instant RetrievalRare but millisecond access90-day minimum
    Glacier Flexible RetrievalArchive, minutes–hours90-day minimum
    Glacier Deep ArchiveLong-term compliance180-day minimum; hours to retrieve

    Azure: Hot → Cool → Cold → Archive. GCP: Standard → Nearline → Coldline → Archive.

    🧪 Intermediate: Lifecycle Rules

    {
 "Rules":[{
  "ID":"logs-tiering","Status":"Enabled","Filter":{"Prefix":"logs/"},
  "Transitions":[{"Days":30,"StorageClass":"STANDARD_IA"},
                 {"Days":90,"StorageClass":"GLACIER"}],
  "Expiration":{"Days":365},
  "NoncurrentVersionExpiration":{"NoncurrentDays":30},
  "AbortIncompleteMultipartUpload":{"DaysAfterInitiation":7}
 }]}
    Example10 TB of logs kept in S3 Standard costs about $230/month (approx. $0.023/GB). After 90 days in Glacier Flexible at about $0.0036/GB it costs about $36/month. Prices vary by region; always check current pricing.
    💡
    Always add AbortIncompleteMultipartUpload and noncurrent version expiration. They are invisible cost leaks.

    🚀 Expert: Avoiding Lifecycle Traps

    • Small objects: IA classes bill a minimum of 128 KB per object; per-object transition fees make millions of tiny files costly. Compact/aggregate first.
    • Minimum duration: deleting before 30/90/180 days still charges the remainder.
    • Intelligent-Tiering is safer when access patterns are unpredictable.
    • Other storage: EBS gp2→gp3 (cheaper, tunable IOPS), snapshot retention, EFS Infrequent Access, database backup retention, log retention (CloudWatch Logs groups default to never expire!).
    • Analytics: S3 Storage Lens and Storage Class Analysis reveal access patterns to design the rules.

    Topic 04 · Compute pricing

    Spot Instance Integration

    Run interruption-tolerant workloads on spare cloud capacity at steep discounts, often 60–90% below on-demand.

    🔰 Basics: What Is Spot?

    Cloud providers sell unused capacity cheaply, but can reclaim it. AWS gives a 2-minute interruption notice; Azure Spot and GCP Spot VMs give short notices too (about 30 seconds on GCP).

    Good for SpotPoor for Spot
    Batch, CI/CD runners, data processing, renderingSingle-node databases
    Stateless web tiers behind autoscalingStateful apps without replication
    Dev/test, ML training with checkpointsHard real-time or licence-bound apps

    🧪 Intermediate: Design for Interruption

    1. Diversify across many instance types, sizes and AZs (10+ pools).
    2. Use capacity-optimized / price-capacity-optimized allocation, not lowest-price.
    3. Handle the 2-minute notice: drain, checkpoint, deregister from load balancer.
    4. Mix with on-demand base capacity (e.g., 30% on-demand floor, 70% Spot).
    ExampleASG with MixedInstancesPolicy: base 2 on-demand, then 80% Spot above base across m5/m5a/m6i/c5 in 3 AZs. Interruptions in one pool are absorbed by others.

    🚀 Expert: Spot on Kubernetes and Blended Strategy

    • Karpenter provisions Spot nodes with automatic instance-type flexibility and fallback to on-demand.
    • Node termination handler cordons/drains on interruption notices.
    • PodDisruptionBudgets + multiple replicas to keep SLOs.
    • Taints/tolerations: only interruption-tolerant pods land on Spot.
    • Blend: Savings Plans for steady base, Spot for burst, on-demand for the rest.
    # Karpenter NodePool snippet
requirements:
  - key: karpenter.sh/capacity-type
    operator: In
    values: ["spot","on-demand"]
    📌
    Savings math: if on-demand is $0.10/h and Spot averages $0.03/h, effective saving is 70%. Subtract the engineering cost of interruption handling and occasional on-demand fallback.

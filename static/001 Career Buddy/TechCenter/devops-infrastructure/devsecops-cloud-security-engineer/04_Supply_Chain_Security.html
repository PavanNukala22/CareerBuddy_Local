    Software Supply Chain Foundations

    What the software supply chain is, how attackers abuse it, and the frameworks that organise the defence.

    ⛓️ What is the software supply chain?

    Everything that goes into producing and delivering your software: source code, third-party libraries, build tools, CI/CD systems, container base images, registries, and the people with access. If any link is tampered with, every user downstream inherits the compromise.

    Figure · Every stage is an attack surface
    📌
    Analogy: a food supply chain. Checking the final meal is not enough — you need to trust the farm, the transport, the factory and the packaging.

    📰 Famous attacks (and the lesson)

    IncidentWhat happenedLesson
    SolarWinds (2020)Attackers compromised the build system and inserted a backdoor into a signed update sent to ~18,000 customersProtect and verify the build; a valid signature ≠ trustworthy build
    Log4Shell (2021)Critical RCE in a ubiquitous logging libraryYou must know every component you ship → SBOM
    Codecov (2021)Modified bash uploader script exfiltrated CI secretsPin and verify third-party scripts; keep secrets out of CI env
    event-stream / ua-parser-js / colorsMaintainer takeover or sabotage of popular npm packagesPin versions, review updates, lockfiles
    Dependency confusion (2021)Public package with the same name as an internal one gets installedScoped/namespaced registries, registry priority rules
    3CX (2023)A compromised upstream dependency led to a trojanised desktop appAttacks cascade — vendor-of-a-vendor risk
    xz-utils (2024)A long-con maintainer persona planted a backdoor in a core compression libraryOpen-source maintainer trust and review are part of your attack surface
    💡
    Pattern: attackers prefer to compromise one upstream to reach thousands of downstream victims.

    🎭 Attack types

    📥
    Malicious dependency
    Typosquatting (reqeusts), dependency confusion, hijacked maintainer.
    🏭
    Build compromise
    Poisoned CI runner, altered build script, stolen signing key.
    📦
    Artifact tampering
    Image or package swapped in the registry after build.
    🔓
    Credential theft
    CI tokens, PATs, publish keys used to push malicious releases.
    🧟
    Vulnerable component
    Known-CVE library shipped unknowingly.
    🧑‍💻
    Insider / social
    Malicious contributor, hostile PR, compromised developer laptop.

    Module 02 · Inventory

    SBOM — Software Bill of Materials

    The ingredient list of your software: what SBOMs contain, the SPDX and CycloneDX formats, how to generate and consume them, and how VEX reduces noise.

    🧾 What is an SBOM?

    A Software Bill of Materials is a machine-readable inventory of every component in a piece of software — names, versions, suppliers, licences, hashes and relationships. Like an ingredient label.

    Without SBOM

    • "Are we using Log4j?" → days of grepping
    • Unknown licences discovered at audit
    • Cannot answer customer questionnaires

    With SBOM

    • Query every release in minutes
    • Instant impact analysis for new CVEs
    • Licence & supplier visibility
    • Evidence for regulators and customers

    📐 Formats: SPDX vs CycloneDX

    SPDXCycloneDX
    StewardLinux Foundation (ISO/IEC 5962)OWASP (ECMA-424)
    OriginLicence complianceSecurity & vulnerability use cases
    FormatsJSON, YAML, tag-value, RDF, XLSXJSON, XML, protobuf
    StrengthsRich licence & provenance dataLightweight; supports services, VEX, ML-BOM, CBOM
    Minimum elements (NTIA)Supplier, name, version, unique ID, dependency relationships, author, timestampSame
    json// CycloneDX (abridged)
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "metadata": { "component": { "type": "application", "name": "shop-api", "version": "1.4.2" } },
  "components": [{
    "type": "library",
    "name": "log4j-core",
    "version": "2.14.1",
    "purl": "pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1",
    "licenses": [{ "license": { "id": "Apache-2.0" } }],
    "hashes": [{ "alg": "SHA-256", "content": "ab12..." }]
  }]
}
    💡
    purl (package URL) is the universal identifier: pkg:npm/lodash@4.17.21, pkg:pypi/requests@2.32.0, pkg:oci/nginx@sha256:...

    ⚙️ Generating SBOMs

    Figure · SBOM lifecycle
    bash# Syft (Anchore) – image or directory
syft shop-api:1.4.2 -o spdx-json=sbom.spdx.json -o cyclonedx-json=sbom.cdx.json
syft dir:. -o cyclonedx-json > sbom-source.json

# Trivy
trivy image --format cyclonedx --output sbom.cdx.json shop-api:1.4.2

# Language-native (CycloneDX)
cyclonedx-py environment -o sbom.json            # Python
npx @cyclonedx/cyclonedx-npm --output-file sbom.json   # Node
    📌
    Build-time SBOMs (from the build tool) are usually more accurate for app dependencies; image-scan SBOMs capture OS packages. Mature teams generate both and merge.

    🔎 Consuming SBOMs: vulnerability matching

    bash# Scan an SBOM instead of re-scanning the image
grype sbom:./sbom.cdx.json --fail-on high
trivy sbom sbom.cdx.json --severity HIGH,CRITICAL

# "Are we affected by Log4Shell?" across all stored SBOMs
grep -l '"log4j-core"' sboms/*.json

    At scale, feed SBOMs into OWASP Dependency-Track — it ingests CycloneDX, monitors continuously for new CVEs, applies policy and shows portfolio-wide exposure.

    🧯 VEX — Vulnerability Exploitability eXchange

    A scanner may report 200 CVEs, yet many cannot be exploited in your product. A VEX document states the exploitability status of each CVE for a specific product so consumers can ignore the noise.

    StatusMeaning
    not_affectedVulnerable code not present or not reachable (give a justification)
    affectedExploitable — here is the remediation
    fixedPatched in this version
    under_investigationAnalysis in progress
    json{
  "vulnerabilities": [{
    "id": "CVE-2021-44228",
    "analysis": { "state": "not_affected",
                  "justification": "code_not_reachable",
                  "detail": "JndiLookup class removed from the shaded jar" },
    "affects": [{ "ref": "pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1" }]
  }]
}

    ✅ SBOM best practices

    1. Generate an SBOM for every release, automatically in CI.
    2. Include transitive dependencies and hashes.
    3. Sign the SBOM and attach it to the image (see next module) — an unsigned SBOM can be forged.
    4. Store SBOMs in a searchable system (Dependency-Track, artifact repo).
    5. Share with customers on request; publish VEX alongside.
    6. Treat SBOMs as living: re-evaluate against new CVEs daily, not just at build.

    Module 03 · Trust

    Image Signing with Cosign & Sigstore

    Prove an artifact came from you and was not modified. Learn digital signatures, keyed vs keyless signing, attestations and verification policies.

    ✍️ Why sign artifacts?

    A container tag like shop-api:latest can be overwritten by anyone with registry access. A signature binds an identity to an exact image digest, so deployers can verify: "this digest was produced by my pipeline."

    ThreatHow signing helps
    Registry compromised / tag overwrittenDigest signature no longer matches
    Rogue image deployedAdmission policy rejects unsigned images
    Insider pushes untested buildOnly the CI identity can produce valid signatures
    Mix-up between environmentsAttestations record how/where it was built
    📌
    Signatures reference the image digest (sha256:…), never a mutable tag.

    🌐 Sigstore ecosystem

    🖊️
    Cosign
    CLI/library to sign, verify and attach attestations to OCI artifacts.
    🪪
    Fulcio
    Certificate authority issuing short-lived (10-minute) certificates bound to an OIDC identity.
    📒
    Rekor
    Public, tamper-evident transparency log of all signatures.
    🔭
    Policy controller
    Kubernetes admission control enforcing Sigstore signatures.
    Figure · Keyless signing flow — no long-term private key to steal

    🔑 Signing: key-based vs keyless

    🗝️ Key-based

    bashcosign generate-key-pair      # cosign.key + cosign.pub
cosign sign --key cosign.key \
  registry.acme.io/shop-api@sha256:ab12...
cosign verify --key cosign.pub \
  registry.acme.io/shop-api@sha256:ab12...
    • Works air-gapped
    • You must protect + rotate the private key (use KMS/HSM: --key awskms:///alias/sign)

    🪄 Keyless (OIDC)

    bash# in GitHub Actions (id-token: write)
cosign sign --yes \
  registry.acme.io/shop-api@sha256:ab12...

cosign verify \
  --certificate-identity-regexp "https://github.com/acme/shop-api/.github/workflows/release.yml@refs/tags/.*" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  registry.acme.io/shop-api@sha256:ab12...
    • No key management
    • Identity = who/what/where built it
    • Logged in Rekor
    💡
    Verification must pin the expected identity (workflow + repo + issuer). "Any valid signature" is not a policy — attackers can sign with their own identity.

    📎 Attestations: signing claims about the artifact

    Beyond "who signed", an attestation is a signed statement (in-toto format) about the artifact: its SBOM, its build provenance, its test or vulnerability scan results.

    bash# Attach and sign an SBOM attestation
cosign attest --yes --predicate sbom.cdx.json --type cyclonedx \
  registry.acme.io/shop-api@sha256:ab12...

# Attach vulnerability scan result
trivy image --format cosign-vuln -o vuln.json shop-api:1.4.2
cosign attest --yes --predicate vuln.json --type vuln registry.acme.io/shop-api@sha256:ab12...

# Verify attestation and read it
cosign verify-attestation --type cyclonedx \
  --certificate-identity-regexp ".*" --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  registry.acme.io/shop-api@sha256:ab12... | jq .payload -r | base64 -d | jq .

    🛂 Enforcing at deploy time (Kubernetes)

    Signing is useless unless something refuses unsigned images. Use an admission controller.

    yaml# Kyverno verifyImages policy
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-signed-images }
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30
  rules:
    - name: check-cosign
      match: { any: [{ resources: { kinds: [Pod] } }] }
      verifyImages:
        - imageReferences: ["registry.acme.io/*"]
          mutateDigest: true            # rewrite tag → digest
          attestors:
            - entries:
                - keyless:
                    issuer: https://token.actions.githubusercontent.com
                    subject: "https://github.com/acme/*"
                    rekor: { url: https://rekor.sigstore.dev }
    📌
    Alternatives: Sigstore policy-controller, Ratify + OPA Gatekeeper, Notation (CNCF Notary Project) as another signing standard, especially for Azure/AWS registries.

    🧪 Complete GitHub Actions example

    yamlname: release
on: { push: { tags: ["v*"] } }
permissions: { contents: read, id-token: write, packages: write }
jobs:
  build-sign:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3

      - run: cosign attest --yes --predicate sbom.cdx.json --type cyclonedx ghcr.io/acme/shop-api@${{ steps.build.outputs.digest }}

    Module 04 · Build Integrity

    SLSA — Supply-chain Levels for Software Artifacts

    The maturity framework for build integrity: levels, provenance, in-toto, and how to reach SLSA Build L3 in practice.

    🏔️ What is SLSA?

    SLSA (pronounced "salsa") is an OpenSSF framework: a checklist of increasingly strong guarantees that an artifact was built from the expected source, by the expected process, without tampering. It answers "can I trust how this was built?"

    Figure · SLSA focuses on provenance — a verifiable build record
    📌
    SLSA v1.0 (2023) defines the Build track (Levels 0–3). Source and other tracks are evolving; check slsa.dev for current specs.

    🪜 Build track levels

    Figure · Each level raises the cost of tampering
    LevelRequirementsStops
    L1Build is scripted; provenance generated (even if unsigned)Mistakes, enables audit
    L2Runs on a hosted build platform that generates and signs provenanceTampering after build; forged provenance by developers
    L3Build platform hardens: isolated, ephemeral environments; signing secrets inaccessible to build stepsCompromise via one build influencing another; key theft by build scripts

    📜 Provenance & in-toto

    Provenance is a signed attestation (an in-toto statement) with the SLSA predicate: what was built, from which repo and commit, by which builder, with what parameters.

    json{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{ "name": "ghcr.io/acme/shop-api", "digest": { "sha256": "ab12..." } }],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "https://actions.github.io/buildtypes/workflow/v1",
      "externalParameters": { "workflow": { "repository": "https://github.com/acme/shop-api", "ref": "refs/tags/v1.4.2" } },
      "resolvedDependencies": [{ "uri": "git+https://github.com/acme/shop-api", "digest": { "gitCommit": "9fceb02..." } }]
    },
    "runDetails": { "builder": { "id": "https://github.com/slsa-framework/slsa-github-generator/..." } }
  }
}
    💡
    Consumers verify: Is the signature valid? Is the builder trusted? Does the source repo + ref match what I expect?

    🏗️ Reaching SLSA Build L3 on GitHub

    The slsa-github-generator runs the provenance step in an isolated reusable workflow, so your build steps cannot touch the signing identity.

    yamljobs:
  build:
    runs-on: ubuntu-latest
    outputs: { digest: "${{ steps.push.outputs.digest }}" }
    steps:
      - uses: actions/checkout@v4
      - id: push
        uses: docker/build-push-action@v6
        with: { push: true, tags: "ghcr.io/acme/shop-api:${{ github.ref_name }}" }

  provenance:
    needs: build
    permissions: { actions: read, id-token: write, packages: write }
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v2.0.0
    with:
      image: ghcr.io/acme/shop-api
      digest: ${{ needs.build.outputs.digest }}
    secrets:
      registry-username: ${{ github.actor }}
      registry-password: ${{ secrets.GITHUB_TOKEN }}
    bash# Consumer verifies provenance before deploying
slsa-verifier verify-image ghcr.io/acme/shop-api@sha256:ab12... \
  --source-uri github.com/acme/shop-api --source-tag v1.4.2
# or: cosign verify-attestation --type slsaprovenance ...

    🧩 Practical requirements for higher levels

    ControlWhy
    Hosted, ephemeral, isolated runnersOne build cannot poison the next
    No long-lived secrets in build stepsBuild scripts cannot steal the signing identity
    Reviewed, protected branches & tagsSource integrity (two-person review)
    Hermetic / pinned dependencies (digests, lockfiles)Same inputs → same outputs
    Reproducible builds (aim)Independent rebuild verifies the binary

    Module 05 · Practice

    Hardening the Pipeline & Dependencies

    Concrete defences: dependency pinning, registry controls, CI/CD hardening, repository protections and continuous health scoring.

    📌 Pin everything

    ItemDoDon't
    npm / pip / MavenCommit lockfiles; npm ci, pip install --require-hashesnpm install with caret ranges in CI
    Docker base imageFROM python:3.12-slim@sha256:…FROM python:latest
    GitHub Actionsuses: actions/checkout@<40-char-sha>uses: foo/bar@main
    Install scriptsVerify checksum / signature of downloaded toolscurl … | bash
    bashpip-compile --generate-hashes requirements.in -o requirements.txt
pip install --require-hashes -r requirements.txt
npm ci --ignore-scripts          # install exact lockfile versions, skip lifecycle scripts

    🏪 Control where packages come from

    • Run an internal proxy/registry (Artifactory, Nexus, CodeArtifact, Harbor) — builds pull only from it.
    • Defeat dependency confusion: use scoped names (@acme/lib), claim your names publicly, configure the proxy to prefer internal sources.
    • Add a cooldown / quarantine for brand-new package versions before they are allowed in.
    • Block packages with failing malware / reputation scans (Socket, Snyk, Phylum, OSV malicious-package feed).
    • Mirror critical base images into your own registry.
    ini# .npmrc – scoped packages only from the private registry
@acme:registry=https://npm.acme.io/
registry=https://npm.acme.io/virtual-proxy/
always-auth=true

    🏭 CI/CD pipeline hardening checklist

    AreaControl
    IdentityOIDC to cloud — no static keys; least-privilege GITHUB_TOKEN (permissions: block per job)
    RunnersEphemeral, isolated, no self-hosted runners on public-PR triggers
    SecretsScoped to environments, masked, never available to fork PRs
    WorkflowsReview changes to .github/workflows (CODEOWNERS); avoid pull_request_target with untrusted code
    Third-party actionsPin by SHA; allow-list org-wide; Dependabot to update
    ArtifactsSign, attest, store immutable; promote the same digest across environments
    EgressRestrict build network to required hosts (e.g. StepSecurity Harden-Runner)
    ⚠️
    A classic mistake: a workflow triggered by pull_request_target that checks out and runs code from the pull request — it gives an outside contributor access to repository secrets.

    🛡️ Protect the source repository

    • Branch protection / rulesets: required reviews, status checks, signed commits, no force-push.
    • CODEOWNERS for sensitive paths (workflows, Dockerfiles, IaC).
    • Enforce MFA / phishing-resistant keys and short-lived tokens for all contributors.
    • Turn on secret scanning + push protection, Dependabot alerts, code scanning.
    • Review third-party app/OAuth installations regularly.

    📊 OpenSSF Scorecard — grade your dependencies

    bashscorecard --repo=github.com/expressjs/express --show-details
# Checks: Branch-Protection, Code-Review, Pinned-Dependencies, Signed-Releases,
#         Token-Permissions, Vulnerabilities, Maintained, Dangerous-Workflow, ...
    💡
    Use Scorecard in two directions: improve your own repos, and use scores as one signal when choosing new dependencies (a 2/10 repo with one unreviewed maintainer is riskier).

    🔬 Detecting malicious packages

    • Red flags: very new version of an old package, install scripts that make network calls, obfuscated code, maintainer change, name close to a popular package.
    • Tools: OSV malicious-package advisories, Socket, Phylum, Snyk, guarddog (open source).
    • Defence in depth: --ignore-scripts, sandboxed install steps, egress allow-lists in CI.
    bashguarddog pypi scan requests-extra            # heuristic malware rules for PyPI packages
guarddog npm verify package-lock.json

    Expert: End-to-End Architecture & Governance

    Combine SBOM, signing, SLSA and policy into one trusted delivery architecture, then govern it with metrics, vendor risk and compliance.

    🏗️ Reference architecture: build → verify → admit

    Figure · Producer side — create trustworthy evidence
    Figure · Consumer side — verify before running
    ✅
    Principle: "never trust, always verify" — the cluster admits only artifacts whose evidence satisfies your policy, regardless of who pushed them.

    📏 Policy as code for supply chain

    regopackage supplychain

default allow = false

allow {
  input.signature.valid
  input.signature.issuer == "https://token.actions.githubusercontent.com"
  startswith(input.signature.subject, "https://github.com/acme/")
  input.provenance.slsa_level >= 3
  count(critical_vulns) == 0
}

critical_vulns[v] {
  v := input.vulnerabilities[_]
  v.severity == "CRITICAL"
  not v.vex_status == "not_affected"
}

    Evaluate this policy in the pipeline (conftest) and at admission (Gatekeeper/Kyverno) so the same rule is enforced twice.

    🧬 Handling a Log4Shell-style zero-day

    1. Query SBOM inventory (Dependency-Track) — which products ship the vulnerable package, which versions?
    2. Prioritise by exposure: internet-facing + reachable first; issue VEX for unaffected products.
    3. Mitigate quickly (config flag / WAF rule) while a fix is prepared.
    4. Patch → rebuild → sign → redeploy through the normal pipeline (no hand-built images).
    5. Verify new SBOMs no longer contain the version; block it with a policy.
    6. Communicate status to customers with VEX and release notes.
    📌
    Time-to-answer "are we affected?" is the key metric. Teams with SBOM inventories answer in minutes; teams without take weeks.

    🤝 Third-party and vendor risk

    • Request SBOM + VEX + SLSA attestations from suppliers; make it a contract term.
    • Assess critical open-source deps: maintainers, funding, bus factor, Scorecard, release signing.
    • For critical components consider vendoring / forking with your own review, or paying for support.
    • Track end-of-life versions — unsupported libraries have no future patches.

    🧪 Capstone lab

    Module 01 · Foundations

    Secrets & Identity Foundations

    What secrets are, why they leak, and the identity fundamentals (authentication, authorisation, least privilege) that every cloud engineer needs.

    🔑 What is a "secret"?

    A secret is any value that grants access or proves identity: if an attacker gets it, they become you. Secrets are the #1 way attackers move from "a leaked repo" to "your production database".

    🗝️
    API keys & tokens
    Cloud access keys, GitHub PATs, Stripe keys.
    🔐
    Credentials
    DB passwords, SSH keys, service-account passwords.
    📜
    Certificates & private keys
    TLS keys, code-signing keys, JWT signing keys.
    🧬
    Encryption keys
    Data keys and master keys protecting data at rest.
    ⚠️
    Secret sprawl: the same password copied into code, .env files, CI variables, Slack messages and wikis. Every copy is another place to leak and another thing to rotate.

    💥 How secrets leak

    Leak pathExamplePrevention
    Hard-coded in sourceAWS_SECRET="AKIA…" in app.pySecret scanning, vault retrieval at runtime
    Committed .env / config.env pushed to public GitHub.gitignore, pre-commit hooks
    Baked into imagesENV DB_PASS=… in Dockerfile layersRuntime injection, build secrets (--secret)
    CI/CD logsecho $TOKEN printed in pipelineMasking, OIDC instead of static tokens
    Shared chat / ticketsPassword pasted in SlackShare via vault links, rotate on exposure
    Over-broad accessEvery dev can read prod secretsRBAC, JIT access, audit
    📌
    Bots scrape public GitHub commits within seconds. If a secret is ever pushed, assume it is compromised → rotate it. Deleting the commit is not enough; it lives in git history and forks.

    🪪 Identity basics: AuthN, AuthZ, Accounting

    Figure · The identity chain — each step must hold
    ConceptMeaningExample
    PrincipalAny identity that can actHuman user, service, role, workload
    Authentication (AuthN)Proving who you arePassword + MFA, certificate, OIDC token
    Authorisation (AuthZ)Deciding what you may doIAM policy, RBAC, ABAC
    Least privilegeOnly the permissions needed, only when neededRead-only to one bucket, not s3:*
    Human vs machine identityMachines outnumber humans 10–50×Pods, Lambdas, CI jobs, bots

    🧭 Core principles

    1. Never store secrets in code — fetch them at runtime from a secrets manager.
    2. Short-lived beats long-lived — prefer tokens that expire in minutes over passwords that live for years.
    3. Least privilege — scope every identity tightly.
    4. Rotate automatically — humans forget; schedulers don't.
    5. Audit everything — every read of a secret should be logged.
    6. Assume breach — design so one leaked secret has a small blast radius.

    👤 Human identity: SSO, MFA, PAM

    • SSO (IAM Identity Center / Entra / Okta) — one identity, central offboarding.
    • MFA — prefer phishing-resistant FIDO2/passkeys over SMS.
    • Just-in-time (JIT) access — elevate for a ticketed time window, then auto-expire.
    • PAM — privileged session brokering and recording; break-glass accounts sealed and alarmed.
    • Access reviews — quarterly recertification of who has what.

    🔍 Finding excess permissions

    bash# Which permissions has this role actually used?

# Generate a least-privilege policy from CloudTrail activity
aws accessanalyzer start-policy-generation --policy-generation-details principalArn=arn:aws:iam::123456789012:role/shop-api
    💡
    Workflow: start slightly broad in dev → observe real usage → generate a tight policy → promote that to prod.

    Module 03 · Encryption Keys

    KMS & Encryption

    How encryption keys are created, protected and used. Learn envelope encryption, key policies and rotation with AWS KMS.

    🔒 Encryption fundamentals

    Symmetric

    One key encrypts and decrypts. Fast. AES-256-GCM. Used for bulk data.

    Asymmetric

    Key pair: public encrypts/verifies, private decrypts/signs. Slower. RSA, ECC. Used for key exchange and signatures.

    StateProtection
    At restDisk / DB / bucket encryption with KMS keys
    In transitTLS 1.2+/mTLS
    In useConfidential computing (Nitro Enclaves, SGX)

    ✉️ Envelope encryption

    KMS never encrypts your 5 GB file directly. It protects a small data key, and the data key encrypts the data. This keeps the master key inside the HSM-backed service.

    Figure · Envelope encryption — the CMK never leaves KMS
    pythonimport boto3, os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
kms = boto3.client("kms")

dk  = kms.generate_data_key(KeyId="alias/app-data", KeySpec="AES_256")
aes = AESGCM(dk["Plaintext"]); nonce = os.urandom(12)
ct  = aes.encrypt(nonce, b"credit-card-1234", b"orders-v1")      # encrypt with data key
blob = nonce + ct
store(blob, dk["CiphertextBlob"])                                  # save encrypted data key beside data
# later: kms.decrypt(CiphertextBlob=...) → plaintext data key → decrypt blob

    🗝️ KMS key types

    TypeWho managesRotationCost / control
    AWS owned keyAWS (invisible)AWSFree, no control
    AWS managed key (aws/s3)AWS in your accountAutomatic yearlyFree, limited control
    Customer managed key (CMK)YouOptional auto (default 365d, configurable) or manualSmall cost, full policy control
    Imported key material (BYOK)You supply the bitsManual onlyCompliance-driven
    CloudHSM / External Key StoreYou, dedicated HSMYouHighest control & assurance
    💡
    Use a CMK when you need: cross-account sharing, custom key policies, audit by key, disable/schedule-deletion, or regulatory proof of ownership.

    📜 Key policies and grants

    Every KMS key has a key policy — the primary access control. IAM policies work only if the key policy allows IAM to delegate.

    json{
  "Sid": "AllowAppRoleUseOnly",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::123456789012:role/shop-api" },
  "Action": ["kms:Decrypt","kms:GenerateDataKey"],
  "Resource": "*",
  "Condition": { "StringEquals": { "kms:ViaService": "s3.ap-south-1.amazonaws.com" } }
}
    • Separation of duties: key administrators (manage, rotate) ≠ key users (encrypt/decrypt).
    • Encryption context — extra authenticated data ({"tenant":"acme"}) bound to ciphertext and visible in CloudTrail.
    • Grants — temporary, programmatic permission delegation to services.

    🔄 Creating and rotating a key

    bashaws kms create-key --description "app data key" --key-usage ENCRYPT_DECRYPT
aws kms create-alias --alias-name alias/app-data --target-key-id <key-id>
aws kms enable-key-rotation --key-id <key-id>
aws kms get-key-rotation-status --key-id <key-id>

# Safe deletion: 7–30 day waiting period, can be cancelled
aws kms schedule-key-deletion --key-id <key-id> --pending-window-in-days 30
    📌
    KMS rotation creates new backing key material; the key ID and alias stay the same and old ciphertext still decrypts. Applications need no change.

    Module 04 · AWS

    AWS Secrets Manager

    Store, retrieve, version and automatically rotate secrets with AWS Secrets Manager — and know when Parameter Store is enough.

    🗄️ What it is

    AWS Secrets Manager stores secrets encrypted with KMS, controls access by IAM, audits via CloudTrail, versions values, and can rotate them automatically using Lambda.

    Figure · Retrieval and rotation flow

    ⌨️ Create, read, update (CLI + SDK)

    bashaws secretsmanager create-secret --name prod/shop/db \
  --kms-key-id alias/app-data \
  --secret-string '{"username":"app","password":"S3cr3t!","host":"db.internal"}'

aws secretsmanager get-secret-value --secret-id prod/shop/db --query SecretString --output text
aws secretsmanager put-secret-value --secret-id prod/shop/db --secret-string file://new.json
    pythonimport boto3, json
sm = boto3.client("secretsmanager")
cred = json.loads(sm.get_secret_value(SecretId="prod/shop/db")["SecretString"])
conn = psycopg2.connect(host=cred["host"], user=cred["username"], password=cred["password"])
# Cache with the AWS Secrets Manager caching client to cut cost + latency

    🔁 Automatic rotation

    Rotation runs a Lambda through four steps. Secrets Manager provides ready-made templates for RDS, Aurora, Redshift, DocumentDB.

    StepWhat happens
    createSecretGenerate new password, store as AWSPENDING version
    setSecretChange the password in the database
    testSecretLog in with the pending credential
    finishSecretPromote AWSPENDING → AWSCURRENT
    bashaws secretsmanager rotate-secret --secret-id prod/shop/db \
  --rotation-lambda-arn arn:aws:lambda:ap-south-1:123456789012:function:rds-rotator \
  --rotation-rules AutomaticallyAfterDays=30
    Figure · Version stages make rotation safe and reversible

    🛡️ Securing access

    json// Resource policy: only the app role may read; deny everything outside the org
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "secretsmanager:GetSecretValue",
  "Resource": "*",
  "Condition": { "StringNotEquals": { "aws:PrincipalOrgID": "o-abc123xyz" } }
}
    • Use one secret per application/environment; name with a path: prod/shop/db.
    • Replicate to a second region for DR; use a CMK if sharing cross-account.
    • Alarm on GetSecretValue from unusual principals (CloudTrail + GuardDuty).

    ⚖️ Secrets Manager vs Parameter Store vs Vault

    SSM Parameter StoreAWS Secrets ManagerHashiCorp Vault
    Primary useConfig + simple secretsSecrets with rotationEnterprise secrets, dynamic creds, PKI, encryption
    Auto rotationNo (DIY)Yes (Lambda)Yes + dynamic secrets
    CostStandard params freePer secret + API callsSelf-host or HCP
    Multi-cloudAWS onlyAWS onlyYes
    Dynamic short-lived credsNoLimitedCore feature
    💡
    Rule of thumb: AWS-only and simple → Secrets Manager (+ Parameter Store for non-sensitive config). Multi-cloud / dynamic secrets / PKI / advanced policy → Vault.

    Module 05 · HashiCorp

    HashiCorp Vault

    The industry-standard secrets platform: architecture, auth methods, secrets engines, policies, dynamic secrets, Transit encryption and Kubernetes integration.

    🏰 Vault architecture

    Vault is a server that sits in front of your secrets. Every request is authenticated, authorised by policy, audited, then served from an encrypted storage backend.

    Figure · Vault request lifecycle
    ConceptMeaning
    Seal / UnsealVault starts sealed; the master key is split via Shamir shares (or auto-unsealed by KMS/HSM). Sealed Vault cannot decrypt anything.
    TokenResult of authentication; carries policies and a TTL
    Auth methodHow clients log in (Kubernetes, AppRole, OIDC, AWS IAM, LDAP…)
    Secrets enginePlug-in that stores/generates secrets (KV, Database, AWS, PKI, Transit, SSH)
    PolicyHCL rules granting capabilities on paths
    LeaseTime-bound validity of a dynamic secret; revocable
    Audit deviceImmutable log of every request
    Namespace (Enterprise/HCP)Multi-tenant isolation

    🚀 Quick start (dev mode)

    bashvault server -dev                         # in-memory, unsealed – learning only!
export VAULT_ADDR=http://127.0.0.1:8200
export VAULT_TOKEN=<root-token-from-output>

vault status
vault secrets enable -path=secret kv-v2
vault kv put secret/shop/api api_key=abc123 db_pass=S3cr3t
vault kv get secret/shop/api
vault kv get -field=api_key secret/shop/api
vault kv metadata get secret/shop/api     # version history (kv-v2)
    ⚠️
    Dev mode stores data in memory with a known root token. Never use it in production. Production = Raft/Consul storage, TLS, auto-unseal, audit enabled, root token revoked.

    📏 Policies (least privilege on paths)

    hcl# shop-api-policy.hcl
path "secret/data/shop/api" {
  capabilities = ["read"]
}
path "database/creds/shop-readonly" {
  capabilities = ["read"]
}
path "secret/data/shop/*" {
  capabilities = ["deny"]    # deny the rest of the subtree; the more specific path above still wins
}
    bashvault policy write shop-api shop-api-policy.hcl
vault token create -policy=shop-api -ttl=1h
    📌
    Capabilities: create, read, update, delete, list, sudo, deny. In KV v2 the API path includes /data/ (and /metadata/).

    ⚡ Dynamic secrets — the killer feature

    Instead of a shared database password that lives for years, Vault creates a unique DB user per request that expires automatically. A leak is harmless within minutes.

    Figure · Dynamic database credentials
    bashvault secrets enable database
vault write database/config/shopdb plugin_name=postgresql-database-plugin \
  allowed_roles="shop-readonly" \
  connection_url="postgresql://{{username}}:{{password}}@db:5432/shop" \
  username="vault_admin" password="$VAULT_DB_ADMIN_PW"

vault write database/roles/shop-readonly db_name=shopdb \
  creation_statements="CREATE ROLE \"{{name}}\" LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl=1h max_ttl=24h

vault read database/creds/shop-readonly      # → unique username/password, lease_id
vault lease revoke <lease_id>                # instantly kill the credential

    🔐 Transit engine — encryption as a service

    Apps send plaintext to Vault, get ciphertext back, and never handle the encryption key. Great for tokenising PII without a custom crypto library.

    bashvault secrets enable transit
vault write -f transit/keys/customer-data
vault write transit/encrypt/customer-data plaintext=$(echo -n "4111-1111" | base64)
# → ciphertext "vault:v1:8SDd3WHDOjf7..."
vault write transit/decrypt/customer-data ciphertext="vault:v1:8SDd3WHDOjf7..."
vault write -f transit/keys/customer-data/rotate     # new key version; old ciphertext still decrypts
vault write transit/rewrap/customer-data ciphertext="vault:v1:..."   # upgrade to latest version without exposing data

    📛 PKI engine — internal certificates

    bashvault secrets enable pki
vault write pki/root/generate/internal common_name="acme.internal" ttl=87600h
vault write pki/roles/services allowed_domains="svc.acme.internal" allow_subdomains=true max_ttl=72h
vault write pki/issue/services common_name="shop-api.svc.acme.internal" ttl=24h
    💡
    Short-lived certs (hours, not years) make revocation almost unnecessary. Pair with cert-manager in Kubernetes.

    Rotation, Zero-Trust & Expert Practices

    Zero-downtime rotation patterns, secret-leak response, detecting exposure, break-glass design and secrets governance at scale.

    🔄 Rotation strategies

    StrategyHowDowntime riskWhen
    Single-user rotateChange the password in placeBrief auth failures while apps refreshLow-risk internal services
    Alternating-usersTwo DB users; rotate one while the other servesNoneProduction databases
    Dynamic secretsNew unique credential per leaseNoneBest default (Vault)
    Dual-key overlapIssue new key, accept both for a grace window, retire oldNoneAPI keys, signing keys, JWT keys (JWKS)
    Certificate renewalAuto-renew at 2/3 of lifetimeNoneTLS / mTLS
    Figure · Zero-downtime rotation pattern
    💡
    Make apps re-read secrets (cache with short TTL, reload on auth failure). An app that only reads its secret at start-up makes rotation an outage.

    🕵️ Detect leaked secrets

    bash# Pre-commit: stop it before it leaves the laptop
gitleaks protect --staged --redact
# Whole repo + history
trufflehog git file://. --only-verified        # verified = tested live against the provider
detect-secrets scan > .secrets.baseline
    • Enable GitHub secret scanning + push protection on every org repo.
    • Use cloud-side detection: GuardDuty credential-exfiltration findings, AWS auto-quarantine policy on exposed keys.
    • Scan container images, CI logs and artifacts too — not just source.

    🚨 Playbook: "A secret has leaked!"

    1. Revoke/rotate immediately — rotation first, investigation second.
    2. Scope — CloudTrail / Vault audit: what did this credential do since exposure?
    3. Contain — disable the principal, revoke sessions, block IPs.
    4. Clean — remove from history (git filter-repo) only after rotation; it is hygiene, not remediation.
    5. Root-cause — why was it in code? Add guardrail (push protection, template).
    6. Report — notify per policy / regulation if data was accessed.
    bashaws iam update-access-key --user-name ci-bot --access-key-id AKIA... --status Inactive
aws iam delete-access-key --user-name ci-bot --access-key-id AKIA...
# find everything the key did
aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIA...

    🧱 Zero-trust & secretless architecture

    • Authenticate every call (mTLS / SPIFFE IDs) — network location grants nothing.
    • Remove secrets where possible: IAM roles, workload identity and OIDC mean there is nothing to steal.
    • Short TTL + continuous verification — tokens in minutes, re-authorise often.
    • Policy as code for access (OPA, Cedar) reviewed via pull request.
    Figure · Zero-trust pillars for secrets

    🛟 Break-glass & resilience

    • Keep a break-glass admin path (root / emergency role) with hardware MFA, sealed credentials and alarm-on-use.
    • Back up Vault Raft snapshots (vault operator raft snapshot save) and test restores.
    • Document unseal / recovery key custody (Shamir shares to different people) or use cloud auto-unseal.
    • Multi-region: Secrets Manager replication or Vault performance/DR replication.
    • Define RTO/RPO — if Vault is down, can apps start from cached leases?

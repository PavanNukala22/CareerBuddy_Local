    Cloud Security Foundations

    Why cloud security is different, who is responsible for what, and how CSPM, CWPP, CIEM and CNAPP fit together.

    ☁️ Why cloud security is different

    In the cloud, infrastructure is code and APIs. A single wrong setting — one public storage bucket, one over-permissive role — can expose an entire company in seconds. Resources are also ephemeral: containers live minutes, accounts multiply, and nobody can track them by hand.

    ⚡
    Speed
    Teams deploy hundreds of times a day — security must keep pace.
    🧩
    Complexity
    Thousands of services and IAM permissions per account.
    🌍
    Exposure
    Everything is one API call from the internet.
    🔄
    Drift
    Console changes silently break what IaC defined.

    🤝 The Shared Responsibility Model

    Figure · Responsibility shifts as you move up the service stack
    📌
    Almost all real-world cloud breaches are on the customer side — misconfiguration, leaked credentials and excessive permissions — not a failure of the provider's data centre.

    Module 02 · Posture

    CSPM — Cloud Security Posture

    Continuously discover cloud assets, compare them to security benchmarks, and prioritise the issues that actually create attack paths.

    🧭 What does CSPM do?

    Figure · The continuous CSPM loop
    • Inventory — every account, region, resource, including shadow IT.
    • Misconfiguration detection — public storage, unencrypted disks, no MFA, open ports.
    • Compliance mapping — CIS, PCI-DSS, HIPAA, SOC 2, ISO 27001, NIST.
    • Drift detection — alerts when reality differs from IaC.
    • Remediation — guidance, tickets, or automatic fixes.

    🕸️ Attack paths & toxic combinations

    Modern CSPM goes beyond a flat list. It builds a graph of resources, networks, identities and data to expose chains an attacker would follow. Individually "medium" issues can combine into a critical path.

    Figure · A toxic combination: four moderate findings = one critical attack path
    💡
    Ask of every finding: Is it internet-exposed? Is it exploitable? What can it reach? Is sensitive data behind it? Fix the issues sitting on a path first.

    🏢 Multi-account strategy

    • Use AWS Organizations with separate accounts for prod, dev, security, log archive and shared services.
    • Guardrails: Service Control Policies (SCPs) to prevent dangerous actions org-wide (e.g. leaving the org, disabling CloudTrail).
    • Delegate a security tooling account as admin for Security Hub, GuardDuty and Config — no workloads there.
    • Tag every resource with owner, env, data-class so findings route to the right team.

    🚀 Enabling Security Hub (CLI)

    bash# Enable Security Hub with default standards
aws securityhub enable-security-hub --enable-default-standards

# Turn on CIS and FSBP explicitly
aws securityhub batch-enable-standards --standards-subscription-requests \
  StandardsArn=arn:aws:securityhub:us-east-1::standards/aws-foundational-security-best-practices/v/1.0.0

# Enable GuardDuty + Inspector
aws guardduty create-detector --enable
aws inspector2 enable --resource-types EC2 ECR LAMBDA

# List critical, active findings
aws securityhub get-findings --filters '{
  "SeverityLabel":[{"Value":"CRITICAL","Comparison":"EQUALS"}],
  "RecordState":[{"Value":"ACTIVE","Comparison":"EQUALS"}]}' --max-items 5
    💡
    In an AWS Organization, designate a delegated administrator and enable auto-enable for new accounts so no account is left unmonitored.

    Wiz & Prisma Cloud

    How commercial CNAPP platforms discover risk across multi-cloud environments, build security graphs and unify code-to-cloud security.

    🔮 Wiz — agentless, graph-driven

    Wiz connects with read-only API access and uses agentless snapshot scanning — it reads disk snapshots of VMs, containers and serverless to find vulnerabilities, secrets and malware without installing anything. Everything is placed into the Wiz Security Graph.

    ⚖️ Agentless vs agent-based

    🛰️ Agentless

    • Instant coverage, zero deploy effort
    • No performance impact on workloads
    • Great for vulnerability, config, secrets
    • Cannot see live process behaviour or block attacks

    🕵️ Agent / sensor

    • Real-time process, file & network visibility
    • Can detect and block runtime attacks
    • Needed for drift and zero-day behaviour
    • Operational cost: deploy, upgrade, compatibility
    ✅
    Best practice is both: agentless for breadth and posture, a runtime sensor (or Falco) on critical workloads for depth.

    📋 Operating a CNAPP: the daily routine

    1. Connect all accounts/subscriptions/projects (automate through Organizations).
    2. Define ownership — map projects/tags to teams.
    3. Review top Issues by risk, not by raw count.
    4. Route tickets to owners with SLAs; auto-close when resolved.
    5. Track compliance score trend and MTTR.
    6. Exceptions require owner + expiry, reviewed monthly.

    Container & Runtime Security (Falco)

    Protect running containers and Kubernetes: image scanning, hardening, admission control and real-time threat detection with Falco.

    🐳 Container security lifecycle

    Figure · Defence in depth from Dockerfile to runtime

    CWPP for containers means securing five layers: image, registry, host, orchestrator (Kubernetes) and runtime.

    📐 Harden the image and the pod

    Dockerfile best practices

    dockerfileFROM gcr.io/distroless/python3-debian12
WORKDIR /app
COPY --chown=nonroot:nonroot app/ .
USER nonroot
ENTRYPOINT ["python","main.py"]
    • Minimal / distroless base
    • Pin by digest
    • Multi-stage builds
    • No secrets in layers

    Pod security context

    yamlsecurityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }
    • Drop all capabilities
    • Read-only root FS
    • No privileged / hostPath
    • Pod Security Standards: restricted

    🔎 Image scanning with Trivy

    bashtrivy image --severity HIGH,CRITICAL --ignore-unfixed shop-api:1.4.2
trivy image --format sarif -o trivy.sarif shop-api:1.4.2
trivy k8s --report summary cluster          # scan a running cluster

    Scan at build (gate), in the registry (continuous — new CVEs appear daily) and at runtime (what is actually deployed).

    🦅 Falco — runtime threat detection

    Falco (CNCF graduated project) watches Linux system calls using an eBPF probe or kernel module and evaluates them against rules. It answers: "Is something happening inside a container that should never happen?"

    Figure · Falco architecture

    Anatomy of a Falco rule

    yaml- rule: Terminal shell in container
  desc: A shell was spawned in a container with an attached terminal
  condition: >
    evt.type = execve and evt.dir = < and container.id != host
    and proc.name in (bash, sh, zsh) and proc.tty != 0
  output: >
    Shell in container (user=%user.name container=%container.name
    image=%container.image.repository cmd=%proc.cmdline)
  priority: WARNING
  tags: [container, shell, mitre_execution]
    FieldMeaning
    ruleUnique name
    conditionBoolean expression over syscall fields (evt.*, proc.*, fd.*, container.*, k8s.*)
    outputMessage with fields substituted
    priorityEMERGENCY … DEBUG
    macro / listReusable condition / value sets

    🤖 Auto-remediation: detect → decide → fix

    Figure · Event-driven remediation architecture
    pythonimport boto3
s3 = boto3.client("s3")

def handler(event, context):
    for f in event["detail"]["findings"]:
        bucket = f["Resources"][0]["Id"].split(":::")[-1]
        s3.put_public_access_block(
            Bucket=bucket,
            PublicAccessBlockConfiguration={
                "BlockPublicAcls": True, "IgnorePublicAcls": True,
                "BlockPublicPolicy": True, "RestrictPublicBuckets": True})
        print(f"Blocked public access on {bucket}")
    ⚠️
    Auto-fix only low-risk, reversible issues (public bucket, missing tag). For production-impacting fixes use an approval step and tag-based opt-outs.

    📜 Prevent: policy as code & IaC scanning

    Stop misconfigurations before they reach the cloud. Scan Terraform in the PR and enforce guardrails with OPA/Sentinel/Checkov.

    hcl# ❌ flagged by Checkov (CKV_AWS_18/19/21...)
resource "aws_s3_bucket" "data" {
  bucket = "customer-data"
}

# ✅ compliant
resource "aws_s3_bucket" "data" { bucket = "customer-data" }
resource "aws_s3_bucket_public_access_block" "data" {
  bucket                  = aws_s3_bucket.data.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
resource "aws_s3_bucket_server_side_encryption_configuration" "data" {
  bucket = aws_s3_bucket.data.id
  rule { apply_server_side_encryption_by_default { sse_algorithm = "aws:kms" } }
}
    bashcheckov -d . --framework terraform --check CKV_AWS_18,CKV_AWS_19 --soft-fail-on LOW
terraform plan -out tf.plan && terraform show -json tf.plan > plan.json
conftest test plan.json -p policy/

    🎯 Detection engineering with Falco & GuardDuty

    • Map every rule to MITRE ATT&CK for Containers/Cloud (tag them).
    • Start with default rules, then tune out noise using exceptions — never delete rules wholesale.
    • Write custom rules for your crown jewels: "any process reading /var/run/secrets outside the app binary".
    • Test detections with attack simulation: Stratus Red Team, Atomic Red Team, Falco Event Generator.
    bash# Simulate a cloud attack technique and confirm your alert fires
stratus detonate aws.credential-access.ec2-get-password-data
# Generate Falco test events
kubectl run event-generator --image=falcosecurity/event-generator --restart=Never -- run syscall

    🚑 Cloud incident response playbook

    1. Detect — GuardDuty / Falco / Wiz alert with context.
    2. Contain — isolate: attach a deny-all security group, revoke role sessions (aws iam put-role-policy deny with aws:TokenIssueTime), cordon the node.
    3. Preserve evidence — snapshot disks, export CloudTrail, capture container filesystem.
    4. Eradicate — rotate credentials, rebuild from a clean image (never "clean" a compromised host).
    5. Recover — redeploy, verify, restore traffic.
    6. Learn — blameless review; add a detection and a preventive guardrail.
    bash# Contain a compromised EC2: swap to an isolation SG
aws ec2 modify-instance-attribute --instance-id i-0abc --groups sg-isolate
# Snapshot for forensics
aws ec2 create-snapshot --volume-id vol-0abc --description "IR-2026-014"

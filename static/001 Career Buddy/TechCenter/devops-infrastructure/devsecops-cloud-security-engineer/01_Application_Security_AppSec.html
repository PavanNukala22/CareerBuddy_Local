    AppSec Foundations

    What application security is, why we "shift left", the vocabulary every engineer must know, and where each testing technique fits in the delivery pipeline.

    🛡️ What is Application Security?

    Application Security (AppSec) is the practice of finding, fixing and preventing security weaknesses in software — in the code you write, the libraries you import, the services you deploy and the APIs you expose. Firewalls protect the network; AppSec protects the logic an attacker can reach through the network.

    🔎
    Find
    Detect flaws early with automated scanners and code review.
    🔧
    Fix
    Give developers clear, actionable remediation guidance.
    🧱
    Prevent
    Secure-by-default frameworks, patterns and guardrails.
    📈
    Measure
    Track risk, MTTR and coverage to prove improvement.
    💡
    DevSecOps in one line: security becomes a shared responsibility that is automated inside the CI/CD pipeline instead of a manual gate at the end of the project.

    ⬅️ Why "Shift Left"?

    The later a defect is found, the more it costs. A bug caught in the IDE costs minutes; the same bug found in production can cost an incident, a breach notification and a reputation hit. Shift-left moves security checks to the earliest possible stage.

    Figure · Security checks along the delivery pipeline — cheaper to fix the further left you go
    📌
    "Shift left" does not mean "stop testing later". Mature teams do shift-left + shift-right: prevent early, detect continuously in production.

    Module 02 · Code Security

    SAST — Static Analysis

    Understand how static analysers read your code, the different types of SAST engines, and get hands-on with SonarQube, Snyk Code and Semgrep.

    🧠 What is SAST and how does it work?

    Static Application Security Testing analyses source code, bytecode or binaries without executing them. It is "white-box" testing: the tool sees every line, including code paths that tests never reach.

    Figure · How a SAST engine turns code into findings

    The key idea is taint analysis: data from an untrusted source (HTTP parameter) must not reach a dangerous sink (SQL execute, eval, file open) without passing a sanitiser.

    ConceptMeaningExample
    SourceWhere untrusted data entersrequest.args["id"]
    SinkDangerous functioncursor.execute(q)
    SanitiserCleans/validates dataParameter binding, html.escape
    RulePattern describing a flaw"string concat in SQL query"

    🧩 Types of SAST engines

    TypeHow it detectsStrengthWeakness
    Pattern / regexText or token matchingVery fast, simple rulesMany false positives
    AST / semanticMatches structure of syntax treeUnderstands language, low noiseSingle-file view
    Data-flow / taintTracks values across functions and filesFinds injection chainsSlower, needs build info
    Symbolic / abstract interpretationReasons about all possible valuesDeep bugs (null, overflow)Complex, costly
    IaC SASTScans Terraform, K8s, DockerfilesCatches misconfig pre-deployCannot see runtime state
    AI-assistedLLM explains / suggests fixes, ranks findingsFaster triageVerify suggestions; not a replacement for rules

    ✅ SAST is great at

    • Finding flaws early, in the IDE or PR
    • Pointing to the exact line
    • Covering code paths tests miss
    • Enforcing coding standards

    ⚠️ SAST struggles with

    • False positives that waste time
    • Runtime / config issues (it never runs the app)
    • Business-logic and auth flaws
    • Language / framework coverage gaps

    🐞 A real finding: SQL Injection

    Below is the classic flaw every SAST tool detects (CWE-89), followed by the fix.

    ❌ Vulnerable

    python@app.route("/user")
def user():
    uid = request.args["id"]          # SOURCE
    q = "SELECT * FROM users WHERE id=" + uid
    return db.execute(q).fetchall()   # SINK

    ✅ Fixed

    python@app.route("/user")
def user():
    uid = request.args["id"]
    q = "SELECT * FROM users WHERE id = %s"
    return db.execute(q, (uid,)).fetchall()  # parameterised
    💡
    Attacker sends id=1 OR 1=1 → the vulnerable query returns every user. Parameter binding keeps data separate from SQL code.

    🐶 Snyk Code — developer-first SAST

    Snyk Code is a cloud-based, AI-assisted engine with IDE plugins, CLI and PR checks. It returns data-flow paths and suggested fixes.

    bash# authenticate once
snyk auth

# scan the current project's source
snyk code test

# fail only on high+ findings, output SARIF for GitHub code scanning
snyk code test --severity-threshold=high --sarif-file-output=snyk.sarif

# ignore an accepted finding with justification (writes .snyk policy)
snyk ignore --id=<issue-id> --reason="Input validated upstream" --expiry=2026-12-31
    ⚠️
    Always add an expiry date and reason to every suppression. Permanent, unexplained ignores silently become the biggest risk in your backlog.

    🔍 Semgrep — write your own rules (open-source)

    Semgrep matches code patterns that look like the source itself, so security engineers can write custom rules in minutes.

    yamlrules:
  - id: no-eval-user-input
    languages: [python]
    severity: ERROR
    message: "eval() on request data allows remote code execution (CWE-95)"
    pattern: eval(request.$X.get(...))
    bashsemgrep scan --config p/owasp-top-ten --config rules/ --error

    🧹 Triage: handling false positives

    1. Reproduce — can you trace source → sink?
    2. Check sanitiser — is the data validated earlier (framework, middleware)?
    3. Decide — True Positive (fix) / False Positive (suppress with reason) / Won't Fix (accept risk, owner + expiry).
    4. Tune — disable noisy rules, exclude generated code and test fixtures.
    5. Gate on new findings only, so teams are not blocked by legacy debt.
    ✅
    Goal: a scanner developers trust. Aim for <10–20% false-positive rate; otherwise people start ignoring every alert.

    Module 03 · Dependencies

    SCA — Dependency Scanning

    Modern apps are mostly other people's code. Learn how Software Composition Analysis finds vulnerable and risky libraries, and how to prioritise what actually matters.

    📦 What is SCA and why does it matter?

    Software Composition Analysis inventories every open-source library your app uses (direct and transitive), then matches each name+version against vulnerability databases and licence rules. A typical project is composed mostly of third-party code, so most of your attack surface is code you never wrote.

    📌
    Log4Shell (CVE-2021-44228) hit teams that had never heard of Log4j — it was buried several levels down their dependency tree. SCA answers "where do we use it?" in minutes.
    Figure · The SCA scanning loop

    🌳 Direct vs transitive dependencies

    textmy-app
├── express 4.17.1            <- DIRECT   (you chose it)
│   ├── qs 6.7.0              <- TRANSITIVE (pulled in by express)
│   └── body-parser 1.19.0    <- TRANSITIVE
└── lodash 4.17.20            <- DIRECT
    • Lockfiles (package-lock.json, poetry.lock, go.sum) pin exact versions — scan the lockfile, not just the manifest.
    • A vulnerable transitive package is fixed by upgrading the direct parent, or by an override/resolution entry.
    • Dev dependencies usually carry lower risk than runtime ones — but they run in your CI, so don't ignore them.

    NVDNIST National Vulnerability Database — CVE records + CVSS
    GitHub Advisory DB (GHSA)Curated, ecosystem-aware advisories
    OSVOpen, machine-friendly format used by OSV-Scanner & pip-audit
    Vendor DBsSnyk intel, Red Hat, Debian, Alpine security trackers

    🎯 Prioritising: not every CVE is urgent

    A big project can show hundreds of CVEs. Triage with several signals, not just CVSS:

    • Exploit maturity — public PoC? seen in the wild?
    • Exposure — internet-facing service vs internal batch job.

    Module 04 · Runtime Testing

    DAST — Dynamic Testing

    Attack your running application the way a real adversary would. Learn DAST concepts and run OWASP ZAP in baseline, full, API and authenticated modes.

    🌐 What is DAST?

    Dynamic Application Security Testing is black-box: the scanner knows nothing about your code. It crawls the running app, sends malicious requests (SQLi, XSS, path traversal…) and watches the responses.

    Figure · A DAST scan lifecycle

    ⚖️ SAST vs DAST vs IAST vs RASP

    SASTDASTIASTRASP
    SeesSource codeRunning app from outsideRunning app from insideRunning app from inside
    WhenCommit / PRStaging / test envDuring QA testsProduction
    FindsCode flaws, line numbersRuntime & config flawsAccurate runtime flawsBlocks attacks live
    False positivesHigherLowerLowestLow
    Language dependentYesNoYes (agent)Yes (agent)
    💡
    They are complementary. SAST finds the flaw in the code; DAST proves it is exploitable in the deployed environment.

    ⚡ OWASP ZAP — the core features

    🕷️
    Spider / Ajax Spider
    Crawls classic and JavaScript-heavy apps to build a site map.
    👂
    Passive scanner
    Analyses traffic without attacking — headers, cookies, info leaks. Safe anywhere.
    💥
    Active scanner
    Sends attack payloads. Only run against test environments.
    🧪
    Fuzzer
    Mutates inputs to uncover unexpected behaviour.
    🔐
    Contexts & auth
    Defines scope, users and login so ZAP can test behind the login page.
    🧰
    API & Automation
    REST API, Automation Framework (YAML), Docker images for CI.

    🧯 Safe DAST practice

    • Scan staging/ephemeral environments with test data — never run an active scan against production.
    • Get written authorisation for every target; scanning without permission is illegal.
    • Rate-limit and use a dedicated test account; active scans can create junk records or lock accounts.
    • Re-test after the fix — the pipeline should confirm the alert disappears.
    • Tune with a rules file (-c rules.tsv) to ignore known-accepted alerts.

    Module 05 · CI/CD Integration

    Pipeline Integration

    Put SAST, SCA, secret scanning, container scanning and DAST into real pipelines — GitHub Actions, GitLab CI and Jenkins — with sensible quality gates.

    🏗️ Reference secure pipeline

    Figure · Where each scan runs in a secure CI/CD pipeline
    💡
    Rule of thumb: fast checks block the PR (<10 min), slow checks run on a schedule (nightly full DAST, deep scans).

    🐙 GitHub Actions: SAST + SCA + secrets + container

    yamlname: secure-ci
on: [pull_request]
permissions:
  contents: read
  security-events: write
jobs:
  appsec:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }          # full history for secret scan

      - name: Secret scan
        uses: gitleaks/gitleaks-action@v2

      - name: SAST – SonarQube
        uses: SonarSource/sonarqube-scan-action@v5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
          SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}

      - name: SCA – Snyk Open Source
        run: npx snyk test --severity-threshold=high
        env: { SNYK_TOKEN: "${{ secrets.SNYK_TOKEN }}" }

      - name: Build image
        run: docker build -t shop-api:${{ github.sha }} .

      - name: Image scan – Trivy
        uses: aquasecurity/trivy-action@master   # pin to a release tag or SHA in production
        with:
          image-ref: shop-api:${{ github.sha }}
          severity: HIGH,CRITICAL
          exit-code: "1"
    ⚠️
    Pin third-party actions to a full commit SHA. A mutable tag like @master is itself a supply-chain risk (see the Supply Chain module).

    🚦 Quality gates & SLAs

    SeverityPipeline actionFix SLA (example)
    Critical (KEV / reachable)Block merge24–72 hours
    HighBlock merge on new findings7–14 days
    MediumWarn + create ticket30–60 days
    Low / InfoReport onlyNext maintenance window
    • Gate on new code — don't punish teams for legacy debt on day one.
    • Baseline first, then ratchet: record today's findings, forbid growth, burn down over time.
    • Provide an exception workflow (owner, reason, expiry) instead of letting people disable the scan.

    🔇 Reducing noise: a practical checklist

    1. Start in report-only mode for 2 weeks; measure findings and false positives.
    2. Exclude vendored, generated and test-fixture paths.
    3. Deduplicate findings across tools in one place (e.g. DefectDojo).
    4. Turn on blocking for Critical only, then High, then expand.
    5. Review gate failures weekly: which rules cause the most friction?

    Expert AppSec Practices

    Move from running scanners to running a security programme: threat modelling, risk-based vulnerability management, custom rules, maturity models and metrics.

    🗺️ Threat modelling with STRIDE

    Scanners find implementation bugs. Threat modelling finds design flaws before code exists. Draw a data-flow diagram (actors, processes, data stores, trust boundaries) then ask STRIDE questions at each element.

    LetterThreatViolatesExample mitigation
    SSpoofingAuthenticationMFA, signed tokens
    TTamperingIntegrityHMAC, DB constraints, signing
    RRepudiationNon-repudiationAudit logs
    IInformation disclosureConfidentialityEncryption, least data
    DDenial of serviceAvailabilityRate limits, autoscaling
    EElevation of privilegeAuthorisationLeast privilege, RBAC checks

    📐 Risk-based vulnerability management

    SignalQuestion it answers
    CVSSHow bad could it be?
    EPSSHow likely is exploitation soon?
    KEVIs it being exploited now?
    ReachabilityDoes my code even call it?
    Asset criticalityWhat data / revenue is behind it?
    SSVC decision treeAct, Attend, Track* or Track? (CISA-style stakeholder-specific outcome)

    📜 Custom rules & policy as code

    Expert teams encode their own standards: "never call our legacy crypto helper", "all controllers must call authorize()".

    yamlrules:
  - id: controller-missing-authz
    languages: [java]
    severity: WARNING
    message: "Controller method without @PreAuthorize"
    patterns:
      - pattern: |
          @GetMapping(...)
          $RET $METHOD(...) { ... }
      - pattern-not: |
          @PreAuthorize(...)
          @GetMapping(...)
          $RET $METHOD(...) { ... }

    Pair this with OPA / Conftest for pipeline policy, e.g. "no container may run as root".

    regopackage main
deny[msg] {
  input.kind == "Deployment"
  not input.spec.template.spec.securityContext.runAsNonRoot
  msg := "Deployment must set runAsNonRoot: true"
}

    🗂️ ASPM & central vulnerability management

    Application Security Posture Management aggregates results from many scanners, deduplicates, correlates to the owning service/team and tracks SLAs. Open-source option: DefectDojo; commercial: Snyk AppRisk, Cycode, Apiiro, etc.

    • Ingest SARIF / JSON from every tool
    • Map finding → repo → service → team owner
    • Auto-create Jira tickets with due dates from the SLA
    • Dashboards for leadership: open criticals, MTTR, SLA breaches

    • Nominate one security champion per squad — trained, first line of triage.
    • Run secure coding katas (OWASP Juice Shop, WebGoat) and CTF days.

    🧪 Capstone lab

    1. Fork a deliberately vulnerable app (OWASP Juice Shop or DVWA).
    2. Add Gitleaks, Semgrep and Snyk/Trivy SCA to a PR workflow.
    3. Run ZAP baseline against a docker-compose staging copy; export HTML report.
    4. Create a quality gate: block on new High+; collect findings in DefectDojo.
    5. Fix 3 real findings, re-run, and record before/after metrics.

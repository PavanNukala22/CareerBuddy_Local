Module 01 · Core Concepts

Observability Foundations

What observability is, how it differs from monitoring, and the vocabulary every tool in this module builds on.

🔭 Monitoring vs Observability

Monitoring watches known failure modes: "is CPU above 90%?". Observability is the ability to ask new questions about a system from the data it emits, without shipping new code: "why are only EU users on app v2.3 slow?".

MonitoringObservability
QuestionIs it broken?Why is it broken?
Failure modesKnown unknownsUnknown unknowns
DataPredefined metrics and checksHigh-cardinality, rich context events
OutputDashboards, alertsExploration, correlation, root cause
💡
Rule of thumb: monitoring tells you something is wrong; observability lets you find what and why. You need both.

🧱 The Pillars: Metrics, Logs, Traces (+ Events, Profiles)

📈
Metrics
Numbers over time. Cheap, aggregatable, great for alerting and trends. http_requests_total
📜
Logs
Timestamped records of discrete events. Rich detail, expensive at scale.
🧵
Traces
The path of one request across services, built from spans. Shows where time went.
🔥
Profiles
Code-level CPU/memory attribution (continuous profiling). Newer fourth signal.

How they work together: an alert fires on a metric (error rate up), you jump to a trace exemplar to see which service is slow, then read that service's logs for the exact exception.

Metric alert→Trace exemplar→Correlated logs→Root cause

📐 Frameworks: Golden Signals, RED, USE

Frameworks tell you what to measure first.

FrameworkSignalsBest for
Golden Signals (Google SRE)Latency, Traffic, Errors, SaturationAny user-facing service
REDRate, Errors, DurationRequest-driven microservices
USE (Brendan Gregg)Utilization, Saturation, ErrorsResources: CPU, disk, network, queues

Example: for a checkout API (RED): requests/sec, % of 5xx, p95 latency. For its database host (USE): CPU %, run-queue length, disk errors.

🧬 Key Concepts You Must Know

Cardinality Intermediate

The number of unique label/tag combinations of a metric. user_id as a label with 1M users creates 1M time series and can crash your TSDB or inflate your bill. Never label by unbounded values (user ID, email, request ID, raw URL).

Push vs Pull Basic

Pull: server scrapes targets (Prometheus). Push: agent sends data to the backend (Datadog Agent, OTLP). Pull makes "is the target up?" free; push suits short-lived jobs and firewalled networks.

Sampling Expert

Keeping only a fraction of traces. Head sampling decides at request start (cheap, can miss errors). Tail sampling decides after the trace completes (keeps errors and slow requests, needs buffering).

OpenTelemetry (OTel) Intermediate

Vendor-neutral CNCF standard: APIs, SDKs, the OTLP protocol and the Collector. Instrument once, send to any backend below.

⚠️
Vendor lock-in: proprietary agents are convenient but make switching vendors costly. OTel keeps your instrumentation portable.

Module 02 · Metrics & Dashboards

Prometheus and Grafana

The open-source standard for metrics collection, and the dashboarding layer that sits on top of almost everything.

🔥 Prometheus: Basics

Prometheus is a time-series database plus a scraper. It pulls text metrics from HTTP /metrics endpoints at a fixed interval and stores them with labels.

App /metrics→Prometheus scrape + TSDB→PromQL→Grafana / Alertmanager
text# exposition format
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 10234
http_requests_total{method="GET",status="500"} 12

Four metric types

TypeBehaviourExample
CounterOnly goes up (resets on restart)requests_total. Query with rate()
GaugeGoes up and downmemory_bytes, queue_depth
HistogramCounts in buckets, allows percentiles server-siderequest_duration_seconds_bucket
SummaryClient-side quantiles, not aggregatable across instancesrpc_duration_seconds{quantile="0.99"}

⚙️ Prometheus: Config and Exporters 

yamlglobal:
  scrape_interval: 15s
scrape_configs:
  - job_name: node
    static_configs:
      - targets: ['10.0.0.5:9100']
  - job_name: k8s-pods
    kubernetes_sd_configs: [{role: pod}]   # service discovery
rule_files: ['alerts.yml', 'recording.yml']
alerting:
  alertmanagers: [{static_configs: [{targets: ['alertmanager:9093']}]}]

Exporters expose metrics for things you cannot modify: node_exporter (Linux hosts), blackbox_exporter (probe URLs), mysqld_exporter, kube-state-metrics. Short-lived batch jobs push to the Pushgateway.

🚀 Prometheus: Intermediate to Expert

Recording rules Intermediate

Pre-compute expensive queries so dashboards load fast.

yamlgroups:
- name: api
  rules:
  - record: job:http_requests:rate5m
    expr: sum by (job) (rate(http_requests_total[5m]))

Scaling and long-term storage Expert

A single Prometheus is not horizontally scalable or durable. Patterns: federation (a parent scrapes children), remote_write to Thanos / Mimir / Cortex / VictoriaMetrics for global view, HA pairs and years of retention; sharding by job/label; --storage.tsdb.retention.time tuning.

⚠️
Watch prometheus_tsdb_head_series. A sudden jump means a cardinality explosion. Use metric_relabel_configs to drop offending labels.

📊 Grafana: Basics to Expert

Grafana does not store metrics; it queries data sources (Prometheus, Loki, Elasticsearch, Tempo, CloudWatch, SQL) and visualizes them.

LevelConcepts
BasicData sources, dashboards, panels (time series, stat, gauge, table, heatmap), time range picker, Explore view
IntermediateVariables ($env, $service) for reusable dashboards, annotations, transformations, Grafana Alerting with contact points and notification policies, folders and permissions
ExpertProvisioning as code (YAML data sources/dashboards, Terraform, Grafonnet/Jsonnet), correlations between logs, metrics and traces, LGTM stack (Loki, Grafana, Tempo, Mimir), SSO/RBAC, dashboard-as-code in Git CI
promql# Panel query using a dashboard variable
sum by (status) (rate(http_requests_total{service="$service", env="$env"}[$__rate_interval]))
💡
Good dashboard design: top row = golden signals (answers "are we healthy?"), then drill-down rows per component. Keep one purpose per dashboard and link to runbooks.
Module 03 · ELK / OpenSearch / Jaeger

Logs and Distributed Tracing

Centralized log search with ELK and OpenSearch, and following a single request across services with Jaeger.

🪵 ELK Stack and OpenSearch

App logs→Beats / Filebeat→Logstash (parse)→Elasticsearch (index)→Kibana (search)
ComponentRole
ElasticsearchDistributed search and analytics engine (Lucene). Stores JSON documents in indices split into shards
LogstashPipeline: input → filter (grok, mutate, geoip) → output
BeatsLightweight shippers: Filebeat (logs), Metricbeat, Packetbeat
KibanaUI: Discover, dashboards, Lens, alerting

OpenSearch is the Apache-2.0 fork of Elasticsearch 7.10 (plus Kibana → OpenSearch Dashboards), created by AWS after Elastic changed its license in 2021. Concepts and APIs are very similar; newer features have diverged.

text# Logstash filter: parse an access log line
filter {
  grok  { match => { "message" => "%{COMBINEDAPACHELOG}" } }
  date  { match => ["timestamp", "dd/MMM/yyyy:HH:mm:ss Z"] }
}

Intermediate to Expert

  • Intermediate Mappings (explicit field types), analyzers, structured JSON logs, ECS (Elastic Common Schema) for consistent field names.
  • Expert Index Lifecycle Management (ILM; ISM in OpenSearch): hot → warm → cold → delete; data streams; shard sizing (aim for tens of GB per shard); avoid mapping explosions.
  • Expert Cost trade-off: ELK indexes everything (fast search, high storage). Loki indexes only labels (cheap, slower full-text).
text# Kibana KQL
service.name : "checkout" and log.level : "error" and not message : "timeout*"

🧵 Distributed Tracing and Jaeger

A trace is the whole journey of a request; it is made of spans (one operation each, with start time, duration, attributes, parent). A shared trace_id is propagated between services in headers (W3C traceparent).

textTrace 4bf92f35...  total 480 ms
 └─ api-gateway        GET /checkout           480 ms
     ├─ auth-service   validate token           20 ms
     └─ order-service  create order            430 ms
         ├─ db         INSERT orders            25 ms
         └─ payment    POST /charge            380 ms   ← bottleneck

Jaeger (CNCF graduated, created at Uber) collects, stores and visualizes traces. Components: SDK/OTel exporters → collector → storage (Elasticsearch/OpenSearch, Cassandra, Badger for dev) → query service + UI. Jaeger v2 is rebuilt on the OpenTelemetry Collector and ingests OTLP natively.

LevelWhat to learn
BasicRead the waterfall view, find the longest span, compare traces, search by service/tag/duration
IntermediateSpan attributes and events, error tags, context propagation, service dependency graph (DAG)
ExpertHead vs tail sampling strategies, adaptive sampling, storage sizing, linking traces to logs via trace_id and to metrics via exemplars
💡
Tip: put trace_id into every log line. Then from a slow trace you can pull the exact logs, and vice versa.
Module 04 · Commercial Platforms

Commercial Observability Platforms

All-in-one SaaS platforms: faster to start, less to operate, but you pay per host, GB or user.

🐶 Datadog

SaaS platform covering infrastructure, APM, logs, RUM, synthetics and security. A Datadog Agent on each host/container collects metrics, logs and traces and ships them out (push).

  • Basic Install agent, enable integrations (700+), build dashboards, create monitors (metric, log, APM, composite).
  • Intermediate Unified Service Tagging: tags env, service, version tie metrics, logs and traces together; custom metrics via DogStatsD.
  • Expert Watchdog anomaly detection, SLO tracking, Terraform-managed monitors, tag-based cost control (custom metrics and log indexing are the usual bill drivers).
text# Datadog monitor query (metric alert)
avg(last_5m):avg:system.cpu.user{env:prod,service:checkout} by {host} > 90

🧠 Dynatrace

Differentiator: automation and AI. OneAgent auto-discovers processes, injects instrumentation without code changes, and builds a live topology map (Smartscape). PurePath captures end-to-end distributed traces. Davis AI does causal root-cause analysis and groups related symptoms into one problem instead of many alerts. Grail is its data lakehouse queried with DQL.

  • Basic Deploy OneAgent, view services, problems feed.
  • Intermediate Management zones/tags, request attributes, custom alerting profiles, anomaly detection settings.
  • Expert Davis tuning, SLOs, workflows/automation, OpenTelemetry ingest, DQL analytics.

🟢 New Relic

Full-stack platform on one telemetry database. Language APM agents (Java, .NET, Node, Python, Go, Ruby, PHP) plus infrastructure agent and OTLP ingest. Everything is queried with NRQL. Pricing is based on data ingest (GB) and users.

sqlSELECT percentile(duration, 95) FROM Transaction
WHERE appName = 'checkout' FACET name SINCE 1 hour ago TIMESERIES
  • Basic Install agent, read APM summary, errors inbox.
  • Intermediate NRQL dashboards, alert conditions (static, baseline), distributed tracing, entities and tags.
  • Expert Applied Intelligence (issue correlation), workloads, Terraform provider, ingest cost governance, drop rules.

⚖️ Choosing a Tool

NeedGood fit
Free, Kubernetes-native metrics, you can operate itPrometheus + Grafana (+ Loki/Tempo)
Heavy log search and analyticsELK or OpenSearch
Tracing only, open sourceJaeger (or Tempo)
Small team, want everything fastDatadog or New Relic
Large enterprise, minimal manual config, AI root causeDynatrace
Avoid lock-inOpenTelemetry + any backend
💡
Decision factors: total cost at your data volume, operational burden, team skills, compliance/data residency, and portability. Most real organisations run a hybrid.
Module 05 · Troubleshooting & Labs

Real-World Scenarios and Troubleshooting

What actually breaks in production, how to diagnose it with each tool, and a starter lab you can run locally.

🧪 Starter Lab: Prometheus + Grafana in Docker

Run a local stack in minutes. Save as docker-compose.yml next to a prometheus.yml (see the Prometheus module) and run docker compose up -d.

yamlservices:
  prometheus:
    image: prom/prometheus
    volumes: ['./prometheus.yml:/etc/prometheus/prometheus.yml']
    ports: ['9090:9090']
  node-exporter:
    image: prom/node-exporter
    ports: ['9100:9100']
  grafana:
    image: grafana/grafana
    ports: ['3000:3000']      # login admin/admin, add Prometheus data source http://prometheus:9090

Exercise: (1) open localhost:9090/targets and confirm both jobs are UP; (2) run 100 - avg(rate(node_cpu_seconds_total{mode="idle"}[5m]))*100; (3) graph it in Grafana with a threshold line at 80.

🪵 Elasticsearch / OpenSearch Troubleshooting

textGET _cluster/health             # green / yellow / red
GET _cat/shards?v&s=state       # find UNASSIGNED shards
GET _cluster/allocation/explain # WHY a shard is not assigned
GET _cat/indices?v&s=store.size:desc
Status / issueMeaningAction
GreenAll primary and replica shards assignedHealthy
YellowAll primaries OK, some replicas unassigned (common on a single-node cluster)Add nodes or set replicas to 0 on dev
RedAt least one primary shard unassigned: data unavailableRun allocation explain; fix disk/node loss; restore from snapshot
Index turns read-onlyDisk crossed the flood-stage watermark (default 95%)Free space or add disk, delete old indices via ILM, then clear the read-only block
Slow search / heap pressureToo many shards, huge mappings, wildcard queriesFewer, larger shards; ILM rollover; limit fields; use filters not wildcards
💡
Default disk watermarks: low 85% (no new shards to the node), high 90% (relocate shards away), flood-stage 95% (indices become read-only).

🧵 Tracing, Grafana and Commercial-Tool Problems

ToolProblemLikely cause and fix
JaegerTraces broken into separate fragmentsContext not propagated: async queues/threads or a proxy dropping the traceparent header. Inject/extract context on message headers
JaegerSome spans or whole traces missingSampling dropped them, collector queue full, or exporter timeouts. Check collector drop metrics

General method: 1) confirm the data is being produced, 2) confirm it is being shipped (agent/collector logs), 3) confirm it is being stored, 4) confirm your query/time range is right. Walk the pipeline left to right.

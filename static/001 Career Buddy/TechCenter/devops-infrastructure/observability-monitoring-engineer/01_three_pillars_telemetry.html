    Module 01 · Foundations

    Observability Foundations

    What observability really is, how it differs from monitoring, and the vocabulary (SLI, SLO, golden signals) every other topic builds on.

    🔭 Monitoring vs Observability

    Basic The core idea

    Monitoring tells you when something is wrong using checks you defined in advance (“CPU > 90%”). Observability is a property of a system: can you understand its internal state purely from the data it emits (telemetry) — including for problems you never predicted?

    📟 Monitoring

    • Answers known questions
    • Dashboards + threshold alerts
    • “Is the checkout service up?”
    • Detects known-unknowns

    🔍 Observability

    • Lets you ask new questions
    • Explore, slice, correlate
    • “Why are only iOS users in Pune slow after v2.3?”
    • Handles unknown-unknowns
    💡
    Analogy: A car dashboard (monitoring) shows speed and fuel. A mechanic with a full diagnostic port (observability) can find a fault you never thought to put a gauge on.

    Intermediate Telemetry: the raw material

    Telemetry is data emitted by your systems. The classic types are called signals: metrics, logs, traces (the “three pillars”), with profiles and events emerging as additional signals.

    Applicationemits telemetry
    →
    Collector / Agentenrich & route
    →
    Backendstore & index
    →
    Dashboards / Alertshumans & automation
    Telemetry pipeline at a glance

    Expert High cardinality & high dimensionality

    Debugging unknowns requires slicing data by fields with many unique values (user_id, request_id, build_sha). Metrics systems struggle here (each unique label combination is a new time series), which is why logs and traces carry the high-cardinality context while metrics stay low-cardinality and cheap.

    🎯 SLI, SLO, SLA and Error Budgets

    Basic Definitions

    TermMeaningExample
    SLI (Indicator)A measured number describing service health% of HTTP requests answered < 300 ms without 5xx
    SLO (Objective)Internal target for an SLI over a window99.9% of requests good over 30 days
    SLA (Agreement)Contract with customers, with penalties99.5% uptime or service credits
    Error budget100% − SLO = allowed unreliability0.1% of 30 days ≈ 43 min of downtime

    Intermediate Choosing SLIs

    Pick SLIs from the user’s point of view: availability, latency, correctness, freshness, throughput. Measure at the edge (load balancer / client) rather than deep inside a service.

    Expert Error budget policy

    If the budget is burning fast, freeze risky releases and invest in reliability. If budget is plentiful, ship faster. This turns reliability into a data-driven negotiation between product and engineering. (Alert design on top of this is covered in the Alerting Strategy module.)

    📐 Golden Signals, RED and USE

    Basic The three methods

    🏅
    Four Golden Signals
    Google SRE: Latency, Traffic, Errors, Saturation. Best general-purpose starting point for any service.
    🔁
    RED Method
    For request-driven services: Rate, Errors, Duration. Used per microservice / endpoint.
    🖥️
    USE Method
    For resources (CPU, disk, NIC): Utilisation, Saturation, Errors. Brendan Gregg’s method for infrastructure.

    Intermediate Worked example: checkout API

    SignalWhat to measureTelemetry
    Rate / TrafficRequests per second to /checkoutMetric (counter)
    Errors5xx ratio, failed paymentsMetric + log
    Duration / Latencyp50 / p95 / p99 request timeMetric (histogram) + trace
    SaturationDB connection pool in use, queue depthMetric (gauge)
    ⚠️
    Common mistake: averaging latency. Averages hide tail pain — always track percentiles (p95/p99).

    🗂️ Types of Monitoring

    TypeWhat it isExample
    InfrastructureHosts, VMs, nodes, networkNode CPU, disk I/O, packet loss
    Application (APM)Code-level performance, errors, tracesSlow SQL query inside a Java method
    Log monitoringSearch and alert on eventsSpike of OutOfMemoryError
    Synthetic (blackbox)Scripted probes from outsidePing login page every minute from 5 regions
    Real User Monitoring (RUM)Browser/mobile telemetry from real usersCore Web Vitals, JS errors
    WhiteboxInternal metrics exposed by the app itself/metrics endpoint
    Network / SecurityFlow logs, DNS, auditVPC flow logs
    💡
    Use blackbox to know users are hurting; use whitebox to know why.

    Module 02 · Pillar 1

    Metrics

    Numeric measurements aggregated over time — cheap, fast, and perfect for dashboards and alerts.

    📊 What is a Metric?

    Basic Definition

    A metric is a number measured at a point in time, identified by a name and a set of labels (also called attributes / dimensions / tags). A series of samples over time is a time series.

    prometheushttp_requests_total{method="GET", route="/cart", status="200"}  1027   @ 12:00:15
http_requests_total{method="GET", route="/cart", status="200"}  1049   @ 12:00:30

    Why metrics? They are tiny, pre-aggregated, cheap to store for months or years, and fast to query — ideal for detection (“something is wrong”).

    Intermediate Push vs Pull collection

    ⬇️ Pull (Prometheus)

    Server scrapes /metrics on a schedule. Easy to tell if a target is down (up == 0). Great for long-lived services.

    ⬆️ Push (StatsD, OTLP, Datadog agent)

    App/agent sends data out. Better for short-lived jobs, serverless, and firewalled environments.

    🧮 Metric Types

    Basic Counter, Gauge

    TypeBehaviourUse forExample
    CounterOnly goes up (resets on restart)Requests, errors, bytes senthttp_requests_total
    GaugeGoes up and downMemory, queue length, temperaturequeue_depth
    HistogramCounts observations in bucketsLatency, payload sizehttp_request_duration_seconds_bucket
    SummaryClient-side pre-computed quantilesQuantiles for a single instancerpc_duration_seconds{quantile="0.99"}
    📝
    You almost never graph a raw counter. You graph its rate: rate(http_requests_total[5m]).

    Intermediate Histogram vs Summary

    • Histogram buckets are aggregatable across instances — you can compute a fleet-wide p99. You choose bucket boundaries up front.
    • Summary quantiles are accurate per instance but cannot be averaged across instances.
    promql# fleet-wide p99 latency from histogram buckets
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

    Expert Native / exponential histograms

    OpenTelemetry’s exponential histogram and Prometheus native histograms auto-scale buckets, removing guesswork about boundaries and giving far better percentile accuracy at lower cost. Trade-off: newer backend support requirements.

    🏷️ Labels, Cardinality and Cost

    Basic Labels

    Labels let you slice: region, service, status_code. Each unique combination of label values creates a new time series.

    Intermediate Cardinality explosion

    Series count = product of distinct values of each label. route(50) × status(10) × pod(200) = 100,000 series for one metric. Adding user_id (1M values) would produce billions — crashing the backend or your budget.

    LabelSafe?Why
    method, status_class✅Bounded, small
    route (templated: /users/{id})✅Bounded
    path (raw: /users/8841)❌Unbounded
    user_id, trace_id, email❌Put in logs/traces instead

    Expert Controlling cardinality

    • Drop or relabel labels at scrape time (metric_relabel_configs) or in the OTel Collector (attributes / transform processors).
    • Use per-tenant series limits and monitor prometheus_tsdb_head_series.
    • Pre-aggregate with recording rules and downsample long-term data.

    📈 Aggregation, Percentiles and Exemplars

    Basic Why percentiles?

    If 99 requests take 100 ms and 1 takes 10 s, the mean is ~200 ms (looks fine) while p99 is 10 s (one user in a hundred is miserable). Alert on p95/p99, not the mean.

    Intermediate Rate vs increase vs irate

    FunctionReturns
    rate()Per-second average increase over the window (smooth, best for alerts)
    irate()Per-second rate using last two samples (spiky, good for zoomed graphs)
    increase()Total increase over the window

    Expert Exemplars

    An exemplar attaches a sample trace_id to a histogram bucket observation. In Grafana you see a latency spike on a graph, click the dot, and jump straight to the exact slow trace — bridging metrics → traces.

    Module 03 · Pillar 2

    Centralized Logging

    Timestamped records of discrete events — the richest source of context when you are debugging.

    📜 What is a Log?

    Basic Definition and levels

    A log is an immutable, timestamped record of something that happened. Logs carry the high-cardinality detail (user, order, exception stack) that metrics cannot.

    LevelMeaningExample
    TRACE / DEBUGDeveloper detail, noisyCache key computed
    INFONormal business eventsOrder 8841 placed
    WARNUnexpected but recoveredRetry 2/3 for payment gateway
    ERROROperation failedPayment declined: timeout
    FATALService cannot continueCannot bind to port

    Intermediate Types of logs

    Application logsAccess logs (nginx)System / syslogAudit logsDatabase slow-query logsKubernetes eventsSecurity / WAF logs

    🧱 Structured vs Unstructured Logging

    ❌ Unstructured

    text2026-10-05 10:15:02 ERROR Payment failed for user 42 order 8841 after 3 retries

    ✅ Structured (JSON)

    json{"ts":"2026-10-05T10:15:02Z","level":"ERROR",
 "msg":"payment failed","user_id":42,"order_id":8841,
 "retries":3,"service":"checkout",
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736"}

    Structured logs are machine-parseable: you can filter level=ERROR AND service=checkout without fragile regexes, and aggregate by any field.

    Intermediate Correlation IDs

    Always include trace_id and span_id (and a request/correlation ID) in every log line. That single field links a log to its trace and to every other service’s logs for the same request.

    Expert Pitfalls

    • PII / secrets: redact emails, tokens, card numbers at the source or in the pipeline.
    • Multi-line stack traces: configure multiline parsing or emit JSON so one event stays one record.
    • Log volume cost: sample DEBUG, drop health-check noise, route by value.

    🏗️ Centralized Logging Architecture

    Basic Why centralize?

    Containers are ephemeral — when a pod dies its local logs vanish. A central store gives search across all services, retention, access control and alerting.

    Appsstdout / files
    →
    AgentFluent Bit / Filebeat / OTel
    →
    BufferKafka (optional)
    →
    ProcessorLogstash / Vector
    →
    StoreElasticsearch / Loki
    →
    UIKibana / Grafana
    Typical centralized logging pipeline

    Intermediate Collection patterns on Kubernetes

    PatternHowTrade-off
    Node agent (DaemonSet)One agent per node reads /var/log/containersMost common, efficient
    SidecarAgent container per podIsolation, but more resource use
    Direct push from appSDK sends logs to backend/OTLPNo file hop, couples app to backend

    Expert Cost and retention strategy

    • Tiered storage: hot (7 days, fast SSD) → warm → cold/object storage → delete.
    • Index vs label-only approaches: Elasticsearch indexes every field (powerful, costly); Loki indexes only labels (cheap, grep-style).
    • Log-to-metrics: convert high-volume logs (e.g. 200 OK access lines) into counters and drop the raw lines.

    Module 04 · Pillar 3

    Distributed Tracing

    Follow a single request as it hops across many services — the best tool for finding where time is spent.

    🧵 Traces and Spans

    Basic Core concepts

    A trace is the full journey of one request. It is made of spans — each span is one unit of work (an HTTP call, a DB query) with a start time, duration, and metadata.

    🌳
    Trace
    Tree of spans sharing one trace_id.
    📦
    Span
    Operation with span_id, parent_span_id, name, start, duration, status.
    🏷️
    Attributes
    Key/value details: http.method, db.system.
    ⚡
    Events
    Timestamped notes inside a span (e.g. an exception).
    textGET /checkout  (gateway)            [==================== 480ms ====================]
 ├─ auth.verify (auth-svc)           [== 40ms ==]
 ├─ cart.get (cart-svc)                      [=== 60ms ===]
 └─ payment.charge (payment-svc)                       [========== 350ms ==========]
     └─ SELECT ... (postgres)                               [======= 310ms =======]  ← the bottleneck

    The waterfall instantly shows that 310 ms of the 480 ms is one database query — something a metric alone could never pinpoint.

    Intermediate Span kinds and status

    SERVER, CLIENT, PRODUCER, CONSUMER, INTERNAL. Status is UNSET, OK or ERROR. Span links connect causally-related traces (e.g. a batch job triggered by many messages).

    🔗 Context Propagation

    Intermediate How services stay in the same trace

    When service A calls service B, A injects trace context into the request headers; B extracts it and creates child spans. The default standard is W3C Trace Context:

    httptraceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ver  trace-id (16 bytes)               parent span-id  flags(sampled)

    tracestate carries vendor data. Baggage carries user-defined key/values (e.g. tenant=acme) to every downstream service.

    Expert Where propagation breaks

    • Message queues — inject context into message headers.
    • Async thread pools / goroutines — context must be passed explicitly.
    • Proxies and gateways that strip unknown headers.
    • Mixed formats (B3 vs W3C) — configure composite propagators.
    ⚠️
    Baggage is sent on every call and may leave your trust boundary — never put secrets or PII in it.

    🎲 Sampling

    Basic Why sample?

    Tracing every request at scale is expensive. Sampling keeps a representative subset.

    StrategyDecision madeProsCons
    Head-basedAt trace start (e.g. 10%)Simple, cheapMay drop the rare error trace
    Tail-basedAfter trace completesKeep all errors & slow tracesNeeds buffering, a stateful collector
    ProbabilisticRandom fixed ratioPredictable costBlind to importance
    Rate-limitedN traces/secBounded volumeSkews at low traffic

    Expert Tail-sampling policy example

    yamlprocessors:
  tail_sampling:
    decision_wait: 10s
    policies:
      - {name: errors,  type: status_code, status_code: {status_codes: [ERROR]}}
      - {name: slow,    type: latency,     latency: {threshold_ms: 1000}}
      - {name: baseline,type: probabilistic, probabilistic: {sampling_percentage: 5}}

    Keep 100% of errors, 100% of requests > 1 s, and 5% of everything else.

    Module 05 · The Standard

    OpenTelemetry (OTel)

    The vendor-neutral CNCF standard for generating, collecting and exporting metrics, logs and traces.

    🧩 What is OpenTelemetry?

    Basic Why it exists

    Before OTel, every vendor shipped its own agent and format, causing lock-in. OpenTelemetry (merger of OpenTracing + OpenCensus) gives one API, SDK, wire protocol and Collector. Instrument once, send to any backend.

    🔌
    API
    Interfaces your code calls (create span, record metric). No-op if no SDK.
    ⚙️
    SDK
    Implementation: sampling, batching, exporting.
    📡
    OTLP
    OpenTelemetry Protocol over gRPC (4317) or HTTP (4318).
    🚚
    Collector
    Standalone service that receives, processes and exports telemetry.
    📖
    Semantic Conventions
    Standard attribute names like http.request.method, service.name.
    🏷️
    Resource
    Describes who emits data: service, version, pod, region.
    Your codeOTel API
    →
    OTel SDKsample, batch
    →
    OTLP
    →
    Collectorreceive → process → export
    →
    Prometheus / Tempo / Jaeger / Datadog …
    OTel end-to-end

    🛠️ Auto vs Manual Instrumentation

    🤖 Automatic

    Agent or library hooks into frameworks (Spring, Express, Flask, JDBC) with zero code changes. Fast coverage of HTTP, DB, messaging.

    ✍️ Manual

    You add spans/metrics for business logic: checkout.apply_coupon, cart.size. Gives meaning that auto cannot guess.

    💡
    Best practice: start with auto-instrumentation for breadth, then add manual spans and attributes where business insight matters.
    pythonfrom opentelemetry import trace
tracer = trace.get_tracer("checkout")

with tracer.start_as_current_span("apply_coupon") as span:
    span.set_attribute("coupon.code", "DIWALI10")
    span.set_attribute("cart.items", 3)

    🚚 The OTel Collector

    Intermediate Pipeline model

    Every pipeline = receivers (get data in) → processors (transform) → exporters (send out). Connectors bridge pipelines; extensions add health checks, auth.

    yamlreceivers:
  otlp:
    protocols: { grpc: {}, http: {} }
processors:
  memory_limiter: { check_interval: 1s, limit_mib: 512 }
  batch: {}
  attributes/redact:
    actions:
      - { key: user.email, action: delete }
exporters:
  prometheusremotewrite: { endpoint: http://mimir:9009/api/v1/push }
  otlp/tempo:            { endpoint: tempo:4317, tls: { insecure: true } }
  loki:                  { endpoint: http://loki:3100/loki/api/v1/push }
service:
  pipelines:
    traces:  { receivers: [otlp], processors: [memory_limiter, batch], exporters: [otlp/tempo] }
    metrics: { receivers: [otlp], processors: [memory_limiter, batch], exporters: [prometheusremotewrite] }
    logs:    { receivers: [otlp], processors: [memory_limiter, attributes/redact, batch], exporters: [loki] }

    Intermediate Deployment patterns

    PatternDescriptionWhen
    No collectorSDK exports straight to backendDemos, small apps
    Agent (DaemonSet/sidecar)Collector next to each workloadLocal batching, host metrics
    GatewayCentral scalable collector tierRedaction, routing, tail sampling
    Agent + GatewayTwo-tierProduction standard

    Expert Advanced collector features

    • spanmetrics connector: derive RED metrics from traces.
    • Load-balancing exporter: route spans of one trace to the same gateway so tail sampling works.
    • Distributions: otelcol-contrib, or build a slim custom one with ocb.

    Correlation & Maturity

    The three pillars are most powerful when connected. See how an engineer moves between them during an incident.

    🕵️ The Debugging Workflow

    Alertmetric: p99 > 2s

    Logs by trace_idwhat error?

    Fix & verifymetric recovers

    QuestionBest pillar
    Is something wrong? How bad? Trend?Metrics
    Where in the call chain is the latency?Traces

    Intermediate Linking techniques

    • Shared service.name / resource attributes across all signals.
    • trace_id in logs → Grafana “logs for this trace” button.
    • Exemplars on histograms → metric to trace.
    • Span metrics → trace to metric.

    🧪 Beyond Three Pillars

    🔥
    Continuous Profiling
    CPU/memory flame graphs over time (Pyroscope, Parca). Answers which function.
    📅
    Events
    Deploys, feature-flag flips, config changes overlaid on graphs.
    👥
    RUM & Synthetics
    Front-end and outside-in signals.
    🧬
    eBPF
    Kernel-level, zero-code telemetry (Beyla, Pixie).
    📝
    Experts argue the pillars are a means, not the goal. The goal is fast, confident answers to arbitrary questions.

    📈 Observability Maturity and Cost

    LevelCharacteristics
    1 · ReactiveHost metrics, ad-hoc logs, users report outages
    2 · ProactiveDashboards, threshold alerts, central logs
    3 · Service-levelTracing, SLOs, golden-signal dashboards
    4 · PredictiveOTel everywhere, correlation, anomaly detection, error-budget policy
    5 · AutonomousAutomated remediation, continuous profiling, observability-driven development

    Expert Managing cost

    Telemetry cost grows with volume × retention. Levers: sampling, cardinality limits, log filtering, tiered retention, and routing low-value data to cheap storage. Treat observability spend as a budgeted product.

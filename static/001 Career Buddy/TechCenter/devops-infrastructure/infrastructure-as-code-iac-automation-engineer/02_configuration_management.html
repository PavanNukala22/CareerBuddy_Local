    Module 01 · Configuration Management · Foundations

    What is Configuration Management?

    Provisioning creates the machine; configuration management makes it behave. Learn the models (push/pull, agent/agentless, mutable/immutable) that explain every tool.

    🧭 Provisioning vs Configuration

    Configuration Management (CM) automates the setup and ongoing state of the software inside servers: packages, files, users, services, kernel settings, security hardening and application deployments.

    Typical division of work in a modern platform.
    LayerQuestion it answersTools
    ProvisioningWhich VMs, networks and databases exist?Terraform, OpenTofu, Pulumi, CDK
    Image buildingWhat does the base image contain?Packer, EC2 Image Builder
    ConfigurationWhat is installed and how is it set up?Ansible, SaltStack, Puppet, Chef

    🔀 Key Models

    Push model

    • A control node pushes changes when you run it.
    • Ansible (default), Salt (salt command), Puppet Bolt.
    • Simple, on-demand; no continuous enforcement unless scheduled.

    Pull model

    • Agents pull their desired state on a timer.
    • Puppet agent (default every 30 min), Salt minion, Chef client.
    • Continuous enforcement and automatic drift correction.

    Agentless

    • Uses SSH / WinRM; nothing to install.
    • Ansible, Salt SSH.
    • Easy to start; relies on network reachability.

    Agent-based

    • A daemon runs on each node.
    • Puppet, Salt minion.
    • Scales to very large fleets; extra software to maintain.

    Mutable infrastructure

    • Update servers in place over time.
    • Config tools shine here.
    • Risk: configuration drift and snowflakes.

    Immutable infrastructure

    • Never patch; replace with a freshly built image.
    • Packer + Terraform.
    • Predictable; slower per change but safer.

    ♾️ Idempotency & Desired State

    A good CM run is idempotent: the first run changes things, later runs report “0 changed”. Tools achieve this by checking current state before acting.

    bash# NOT idempotent: appends a line every run
echo "net.ipv4.ip_forward=1" >> /etc/sysctl.conf
    yaml# Idempotent: the module checks the file and only changes it when needed
- name: Enable IP forwarding
  ansible.posix.sysctl:
    name: net.ipv4.ip_forward
    value: "1"
    state: present
    💡
    Rule of thumb: prefer purpose-built modules/resources (package, file, service) over raw shell commands. If you must run a command, add a guard such as creates: or unless.

    Module 02 · Configuration Management · Ansible

    Ansible

    Agentless, YAML-based automation over SSH. Start with ad-hoc commands, grow into roles and collections, and finish with dynamic inventory, safe rollouts and testing.

    🧩 Architecture & Vocabulary

    🖥️
    Control node
    Where you run ansible. Needs Python; Linux/macOS (WSL on Windows).
    🎯
    Managed nodes
    Targets reached by SSH (or WinRM). Usually only need Python.
    📒
    Inventory
    Hosts and groups you manage.
    📜
    Playbook
    YAML list of plays → tasks → modules.
    Modules are copied to the node, run, and removed.
    📝
    Ansible is packaged as ansible-core (engine) plus collections (modules and plugins such as amazon.aws, community.general).

    📒 Inventory & Ad-hoc Commands

    BASIC Define hosts and groups

    yaml# inventory/hosts.yml
all:
  children:
    web:
      hosts:
        web1.example.com:
        web2.example.com:
      vars:
        http_port: 8080
    db:
      hosts:
        db1.example.com: { ansible_user: ubuntu }
    bashansible all -i inventory/hosts.yml -m ping
ansible web -i inventory/hosts.yml -m ansible.builtin.apt -a "name=htop state=present" --become
ansible db  -i inventory/hosts.yml -m ansible.builtin.setup -a "filter=ansible_distribution*"

    Put per-group and per-host variables in group_vars/web.yml and host_vars/web1.example.com.yml next to the inventory.

    📜 Your First Playbook

    BASIC Install, configure, start

    yaml# site.yml
- name: Configure web servers
  hosts: web
  become: true
  vars:
    http_port: 8080
  tasks:
    - name: Install nginx
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Render site config
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/conf.d/app.conf
        mode: "0644"
      notify: Restart nginx

    - name: Ensure nginx is running and enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Restart nginx
      ansible.builtin.service:
        name: nginx
        state: restarted
    jinja2# templates/nginx.conf.j2  (Jinja2)
server {
  listen {{ http_port }};
  server_name {{ inventory_hostname }};
}
    bashansible-playbook -i inventory/hosts.yml site.yml --check --diff   # dry run
ansible-playbook -i inventory/hosts.yml site.yml
    ✅
    Handlers run only when a task reports changed and only once at the end of the play, so nginx restarts only when its config really changed.

    🔤 Variables, Facts, Conditionals & Loops

    INTERMEDIATE Control flow in YAML

    yaml- name: Install packages per OS family
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop: "{{ common_packages }}"
  when: ansible_facts['os_family'] == "Debian"

- name: Check app health
  ansible.builtin.uri:
    url: "http://{{ inventory_hostname }}:{{ http_port }}/health"
    status_code: 200
  register: health
  retries: 5
  delay: 3
  until: health.status == 200

- name: Show result
  ansible.builtin.debug:
    msg: "{{ health.status }} from {{ inventory_hostname | upper }}"
    ConceptWhat it is
    factsAuto-discovered host data (ansible_facts): OS, IPs, memory, etc.
    registerSave a task result into a variable
    whenRun a task only if a Jinja2 condition is true
    loopRepeat a task over a list
    FiltersTransform values: default(), join, to_json, regex_replace
    📝
    Variable precedence has many levels. Remember the ends: role defaults/ are the lowest (easiest to override), command-line -e extra vars are the highest.

    🔐 Ansible Vault

    bashansible-vault create group_vars/prod/vault.yml

    🛡️ Error Handling & Safe Rollouts

    EXPERT Blocks, rescue and rolling updates

    yaml- hosts: web
  become: true
  serial: "25%"                 # update a quarter of the fleet at a time
  max_fail_percentage: 10       # abort the rollout if too many fail
  tasks:
    - name: Deploy with rollback
      block:
        - name: Deploy new version
          ansible.builtin.unarchive:
            src: "app-{{ app_version }}.tar.gz"
            dest: /opt/app
        - name: Health check
          ansible.builtin.uri: { url: "http://localhost:8080/health" }
      rescue:
        - name: Roll back
          ansible.builtin.command: /opt/app/rollback.sh
      always:
        - name: Record attempt
          ansible.builtin.debug: { msg: "Deploy attempt finished" }

    - name: Run a command idempotently
      ansible.builtin.command: /opt/app/migrate.sh
      args:
        creates: /opt/app/.migrated        # skip if file exists

    Module 03 · Configuration Management · SaltStack

    SaltStack (Salt)

    Fast, event-driven configuration and remote execution. Salt combines a configuration engine with a high-speed message bus, making it popular for very large fleets.

    🏛️ Architecture

    Minions keep a persistent connection to the master and react in seconds.
    • Master: holds states (/srv/salt), pillar (/srv/pillar) and keys.
    • Minion: agent on each node; authenticates with a public key accepted by the master.
    • Salt SSH: agentless mode for nodes without a minion.
    • Proxy minions: manage devices that cannot run an agent (network gear).
    bashsalt-key -L                # list minion keys
salt-key -a web1           # accept a key
salt '*' test.ping

    🎯 Targeting & Remote Execution

    BASIC Run anything, anywhere, fast

    bashsalt 'web*' pkg.install nginx                  # glob by minion id
salt -G 'os:Ubuntu' cmd.run 'uptime'           # by grain
salt -C 'G@role:web and not G@env:dev' state.apply   # compound match
salt -L 'web1,web2' service.restart nginx      # explicit list
salt '*' grains.items                          # inspect facts
    ConceptMeaning
    Execution moduleImperative one-off function, e.g. pkg.install, cmd.run
    State moduleDeclarative, idempotent desired state, e.g. pkg.installed
    GrainsStatic facts about a minion (OS, CPU, roles you set)
    PillarSecure, minion-targeted data defined on the master (passwords, per-env values)

    📜 States (SLS files)

    BASIC A web server in Salt

    yaml# /srv/salt/nginx/init.sls
nginx_pkg:
  pkg.installed:
    - name: nginx

nginx_conf:
  file.managed:
    - name: /etc/nginx/conf.d/app.conf
    - source: salt://nginx/files/app.conf.jinja
    - template: jinja
    - require:
      - pkg: nginx_pkg

nginx_service:
  service.running:
    - name: nginx
    - enable: True
    - watch:
      - file: nginx_conf
    yaml# /srv/salt/top.sls
base:
  'role:web':
    - match: grain
    - nginx
  'db*':
    - postgres
    bashsalt 'web*' state.apply test=True    # dry run
salt 'web*' state.apply nginx
salt '*' state.highstate             # apply everything top.sls assigns
    💡
    Requisites control order and reactions: require (run after), watch (react to changes), onchanges, onfail, unless/onlyif guards.

    🔑 Pillar & Jinja

    INTERMEDIATE Separate data from logic

    yaml# /srv/pillar/postgres.sls
postgres:
  max_connections: 200
  password: {{ salt['vault'].read_secret('secret/db')['password'] }}
    yaml# state using pillar and grains
postgres_conf:
  file.managed:
    - name: /etc/postgresql/postgresql.conf
    - source: salt://postgres/postgresql.conf.jinja
    - template: jinja
    - context:
        max_conn: {{ pillar['postgres']['max_connections'] }}
        host: {{ grains['fqdn'] }}

    ⚡ Reactor, Beacons & Orchestration (Expert)

    EXPERT Event-driven infrastructure

    Everything in Salt produces events on the bus. Beacons watch a minion (file changes, services, load) and emit events; the Reactor on the master maps events to actions.

    yaml# /etc/salt/master.d/reactor.conf
reactor:
  - 'salt/minion/*/start':
    - /srv/reactor/highstate_on_start.sls
    yaml# /srv/reactor/highstate_on_start.sls
apply_highstate:
  local.state.apply:
    - tgt: {{ data['id'] }}

    EXPERT Orchestration across many nodes

    yaml# /srv/salt/orch/deploy.sls  (run with: salt-run state.orchestrate orch.deploy)
update_db:
  salt.state:
    - tgt: 'db*'
    - sls: postgres.migrate

update_web:
  salt.state:
    - tgt: 'web*'
    - sls: app.deploy
    - require:
      - salt: update_db
    📝
    Salt’s project governance and release cadence have changed over the years. Before choosing it for a new platform, check the current release notes, supported versions and community activity.

    Module 04 · Configuration Management · Puppet

    Puppet

    A mature, model-driven, pull-based tool for continuously enforcing desired state across large fleets. Declarative DSL, strong separation of data (Hiera), and rich reporting.

    🏛️ How Puppet Works

    Agent runs every 30 minutes by default and corrects drift automatically.
    • Facter gathers facts (OS, IPs, hostname).
    • Puppet Server compiles a node-specific catalog from manifests + Hiera data.
    • Resource Abstraction Layer: package works on apt, yum, pkg… you declare once.
    • PuppetDB stores facts, catalogs and reports for querying.
    📝
    Puppet is owned by Perforce. A community fork named OpenVox also exists. Concepts in this tab apply to both; check which distribution your organisation uses.

    📜 Manifests & Resources

    BASIC The package–file–service pattern

    puppetpackage { 'nginx':
  ensure => installed,
}

file { '/etc/nginx/conf.d/app.conf':
  ensure  => file,
  owner   => 'root',
  mode    => '0644',
  content => epp('profile/nginx_app.conf.epp', { 'port' => 8080 }),
  require => Package['nginx'],
  notify  => Service['nginx'],
}

service { 'nginx':
  ensure => running,
  enable => true,
}
    bashpuppet parser validate site.pp
puppet apply site.pp --noop           # show what would change
puppet apply site.pp
puppet agent -t --noop                # dry-run against the server
puppet resource service nginx         # inspect live state
    💡
    Relationships: require/before set order; notify/subscribe set order and trigger a refresh (e.g. restart service). The arrows -> and ~> do the same.

    🧱 Classes, Modules & Parameters

    INTERMEDIATE Organise code

    puppet# modules/nginx/manifests/init.pp
class nginx (
  Integer $port          = 80,
  String  $package_name  = 'nginx',
  Boolean $enable_ssl    = false,
) {
  package { $package_name: ensure => installed }

  file { '/etc/nginx/conf.d/default.conf':
    content => epp('nginx/default.conf.epp', { 'port' => $port }),
    notify  => Service['nginx'],
  }

  service { 'nginx': ensure => running, enable => true }
}
    puppetinclude nginx                       # use Hiera/defaults
class { 'nginx': port => 8080 }     # resource-like declaration with parameters
    bashpdk new module nginx
pdk validate        # lint + syntax
pdk test unit       # rspec-puppet tests

    INTERMEDIATE Data separate from code

    EXPERT The roles and profiles pattern

    puppetclass profile::webserver {          # technology stack = "profile"
  include nginx
  include profile::monitoring
}

class role::app_server {            # business function = "role"
  include profile::base
  include profile::webserver
}

node 'web1.example.com' { include role::app_server }   # one role per node
    ✅
    Rule: a node has exactly one role; roles include profiles; profiles configure component modules. This keeps large codebases understandable.

    🚦 Code Delivery & Scale (Expert)

    • Environments: one Git branch = one environment (production, staging), deployed by r10k or Code Manager with a Puppetfile for module dependencies.
    • Testing: puppet-lint, pdk validate, rspec-puppet unit tests, Litmus/Beaker acceptance tests.
    • Safe rollouts: --noop everywhere first, canary environments, run staggering to avoid thundering herds.
    • Orchestration: Bolt runs ad-hoc commands, tasks and plans agentlessly over SSH/WinRM.
    • Reporting: query PuppetDB (PQL) to answer “which nodes have package X version Y?”.

    Module 05 · Configuration Management · Packer

    Packer & Golden Image Pipelines

    Bake configuration into machine images once, then launch identical servers everywhere. Learn Packer templates, provisioners, hardening, testing and image lifecycle.

    🖼️ What is a Golden Image?

    A golden image is a pre-built, tested, hardened machine image (AMI, Azure image, VMware template, container image) that contains your OS configuration, security baseline and agents. Servers start from it ready to go.

    ⏱️
    Fast boot
    No long configuration step at launch; autoscaling reacts quickly.
    🔒
    Consistent security
    CIS hardening and patches baked in and tested once.
    ♻️
    Immutable
    Replace servers with a new image instead of patching.
    🌐
    Multi-cloud
    One template, many builders (AWS, Azure, GCP, VMware, Docker).
    The golden-image pipeline.

    📜 Your First Template

    BASIC HCL2 template for AWS

    hclpacker {
  required_plugins {
    amazon  = { source = "github.com/hashicorp/amazon",  version = ">= 1.3.0" }
    ansible = { source = "github.com/hashicorp/ansible", version = ">= 1.1.0" }
  }
}

variable "region" { default = "ap-south-1" }

locals {
  ts = regex_replace(timestamp(), "[- TZ:]", "")
}

source "amazon-ebs" "al2023" {
  region        = var.region
  instance_type = "t3.small"
  ssh_username  = "ec2-user"
  ami_name      = "golden-al2023-${local.ts}"
  encrypt_boot  = true

  source_ami_filter {
    filters = {
      name                = "al2023-ami-2023*-x86_64"
      virtualization-type = "hvm"
      root-device-type    = "ebs"
    }
    owners      = ["amazon"]
    most_recent = true
  }

  tags = {
    Name      = "golden-al2023"
    BuildTime = local.ts
    Baseline  = "cis-l1"
  }
}

build {
  sources = ["source.amazon-ebs.al2023"]

  provisioner "shell" {
    inline = ["sudo dnf -y update", "sudo dnf -y install amazon-cloudwatch-agent"]
  }

  provisioner "ansible" {
    playbook_file = "./ansible/harden.yml"
  }

  post-processor "manifest" {
    output = "manifest.json"       # records the resulting AMI id for later stages
  }
}
    bashpacker init .
packer fmt .
packer validate .
packer build -var region=ap-south-1 .
packer build -only='amazon-ebs.al2023' .
    ConceptMeaning
    sourceBuilder configuration: how to start a temporary machine and capture an image
    buildWhich sources to build and which steps to run
    provisionerStep that configures the temporary machine (shell, file, ansible, powershell…)
    post-processorRuns after the image exists (manifest, compress, push to registry)

    🛡️ Hardening & Security Baseline

    INTERMEDIATE Bake security in

    • Apply an OS benchmark (CIS / STIG) via an Ansible role or script.
    • Disable password SSH, remove default users, set sensible sysctl and audit rules.
    • Install monitoring, logging and security agents.
    • Remove build-time secrets, SSH keys and shell history in a final cleanup step.
    hclsource "amazon-ebs" "secure" {
  # ...
  encrypt_boot  = true
  kms_key_id    = "alias/golden-image"
  ssh_interface = "session_manager"      # no public SSH needed during the build
  metadata_options {
    http_tokens                 = "required"   # enforce IMDSv2
    http_endpoint               = "enabled"
    http_put_response_hop_limit = 1
  }
}

build {
  sources = ["source.amazon-ebs.secure"]
  provisioner "shell" {
    inline = [
      "sudo rm -f /home/*/.ssh/authorized_keys /root/.ssh/authorized_keys",
      "sudo cloud-init clean --logs",
      "history -c"
    ]
  }
}
    ⚠️
    Never put credentials in a template or bake them into images. Use IAM instance profiles during the build and mark any variables sensitive = true.

    🧪 Testing Images Before Publishing

    EXPERT Automated verification

    hclbuild {
  sources = ["source.amazon-ebs.al2023"]

    ✅
    If any provisioner fails, Packer terminates the temporary instance and no image is published. A failing test therefore blocks a bad golden image automatically.

    🔁 Image Lifecycle & Delivery (Expert)

    EXPERT From AMI to production

    1. Nightly or on-change build in CI (new base AMI, new patches, new role version).
    2. Test in the build, then in a staging account with an integration test.
    3. Promote: tag as candidate → approved; share AMIs to other accounts/regions.
    4. Consume: Terraform/launch templates look up the newest approved image.
    5. Retire: deprecate and delete old images; keep a rollback window.
    hcl# Terraform side: always use the latest APPROVED golden image
data "aws_ami" "golden" {
  most_recent = true
  owners      = ["self"]
  filter {
    name   = "tag:Status"
    values = ["approved"]
  }
  filter {
    name   = "name"
    values = ["golden-al2023-*"]
  }
}

resource "aws_launch_template" "app" {
  image_id      = data.aws_ami.golden.id
  instance_type = "t3.small"
}
    • HCP Packer registry tracks image metadata and channels (e.g. production) so downstream Terraform runs can reference a channel, not an AMI id.
    • Multi-cloud: one build block can list several sources (amazon-ebs, azure-arm, googlecompute) to produce equivalent images in parallel.
    • Rollout: use an ASG instance refresh to replace instances gradually with the new image.

    Module 06 · Configuration Management · Putting it together

    Choosing & Combining Tools

    How Ansible, Salt, Puppet and Packer compare, and how to combine them with Terraform in a clean, layered workflow.

    ⚔️ Comparison

    AnsibleSaltStackPuppetPacker
    Primary roleConfig + orchestrationConfig + remote execution + eventsContinuous state enforcementImage building
    ModelPush (agentless)Push/pull (agent or SSH)Pull (agent)Build-time
    LanguageYAML + Jinja2YAML + Jinja2 (SLS)Puppet DSL + HieraHCL2
    Learning curveLowestMediumSteepestLow
    StrengthSimplicity, huge ecosystemSpeed, event-driven, scaleCompliance reporting, drift correctionImmutable, fast launches
    Typical useDeployments, ad-hoc ops, hardeningLarge heterogeneous fleetsLong-lived server estatesGolden AMIs, VM templates

    🧱 A Layered Reference Architecture

    Bake what is stable, configure what is dynamic.
    Put in the image (Packer)Apply at launch / run time
    OS patches, hardening, agents, runtimesEnvironment-specific settings, service discovery
    Rarely changing softwareSecrets (fetched from a vault), feature flags
    Anything slow to installApplication version when you deploy frequently
    💡
    Rule of thumb: bake slow and stable things; configure fast and variable things. Over-baking forces a new image for every small change; under-baking makes boot slow and fragile.

    🚫 Common Anti-Patterns

    Anti-patternBetter approach
    Running shell everywhereUse idempotent modules/resources; guard commands
    SSH-ing in to “just fix it”Change code, run the pipeline; treat manual change as drift
    One giant playbook / manifestRoles, profiles and modules with clear interfaces

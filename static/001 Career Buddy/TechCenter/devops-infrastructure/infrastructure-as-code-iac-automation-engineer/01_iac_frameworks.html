    Module 01 · Foundations

    What is Infrastructure as Code?

    Learn the core ideas behind every IaC tool: declarative vs imperative, idempotency, state, and the plan → apply lifecycle. Master these once and every framework becomes easy to pick up.

    🏗️ What is IaC?

    Infrastructure as Code (IaC) means describing servers, networks, databases, permissions and every other piece of infrastructure in text files that live in Git, instead of clicking through a cloud console. The files are reviewed, tested, versioned and executed by a tool that makes reality match the files.

    📜
    Versioned
    Every change is a Git commit: who, what, when, and why.
    🔁
    Repeatable
    Build identical dev, test and prod environments from the same code.
    🔍
    Reviewable
    Pull requests and plan output replace "who clicked what?".
    ⚡
    Fast
    Create or destroy a full environment in minutes, not days.
    💡
    Mental model: Console clicking is like cooking without a recipe. IaC is the written recipe plus a robot chef that only changes what is different from the last time.

    ⚖️ Declarative vs Imperative

    This is the most important distinction in the whole course.

    Declarative — "what"

    • You describe the desired end state.
    • The tool works out the steps.
    • Terraform, OpenTofu, CloudFormation, Bicep, Kubernetes manifests.
    • Easy to reason about; limited logic.

    Imperative — "how"

    • You write the steps to run.
    • You handle ordering and conditions.
    • Shell scripts, AWS CLI, raw SDK calls.
    • Flexible; easy to create inconsistent results.

    Pulumi and AWS CDK sit in between: you write real programming languages, but the program only declares resources. The engine still computes a desired state and diffs it, so they behave declaratively.

    bash# Imperative: run twice and the second run fails (bucket exists)
aws s3api create-bucket --bucket my-app-logs --region us-east-1
    hcl# Declarative: run 100 times, result is identical
resource "aws_s3_bucket" "logs" {
  bucket = "my-app-logs"
}

    🔄 Core Principles

    PrincipleMeaningWhy it matters
    IdempotencyRunning the same code repeatedly gives the same result.Safe to re-run after failures or in pipelines.
    ImmutabilityReplace resources instead of editing them in place.Avoids snowflake servers and hidden changes.
    StateA record of which real resources belong to your code.Lets the tool compute diffs, updates and deletes.
    DriftReal infrastructure differs from code (manual change).Detected by plan/refresh; fixed by apply or code update.
    ModularityReusable building blocks with inputs and outputs.Standardises patterns across teams.
    Least privilegeThe deploy identity can only do what it needs.Limits blast radius of a bad apply.
    The universal IaC loop — every framework in this course follows it.

    Module 02 · IaC Frameworks · Terraform

    Terraform Foundations

    From your first resource to variables, data sources and loops. By the end you can build a small, parameterised environment safely.

    🚀 Install & the Core Workflow

    BASIC The four commands

    Terraform reads .tf files in the current directory (the root module), downloads provider plugins, then compares your code with state and reality.

    bashterraform init       # download providers/modules, configure the backend
terraform fmt        # canonical formatting
terraform validate   # syntax and internal consistency check
terraform plan -out=tfplan   # show what WOULD change, save the plan
terraform apply tfplan       # execute exactly the saved plan
terraform destroy            # remove everything this config manages
    💡
    Always apply a saved plan file in automation. It guarantees that what was reviewed is exactly what runs.

    🧱 HCL Building Blocks

    BASIC Your first configuration

    hclterraform {

  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }

  region = var.region
}

  type    = string
  default = "ap-south-1"
}

  value = aws_s3_bucket.logs.arn

    🔁 Loops: count vs for_each

    INTERMEDIATE Creating many similar resources

    📋 Reading a Plan

    SymbolMeaningCare level
    +Will be createdLow
    ~Will be updated in placeCheck the changed attributes
    -/+Will be destroyed and recreatedHigh — downtime or data loss risk
    -Will be destroyedHigh — confirm intent
    ✅
    Habit of professionals: read the plan summary line ("Plan: 2 to add, 1 to change, 1 to destroy") first. Any unexpected destroy means stop and investigate.

    Advanced Terraform

    📦 Modules & Composition

    INTERMEDIATE Calling a module

    hclmodule "network" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"          # always pin

  name = "prod-vpc"
  cidr = "10.0.0.0/16"
  azs             = ["ap-south-1a", "ap-south-1b"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
}

resource "aws_instance" "app" {
  subnet_id = module.network.private_subnets[0]
  ami = data.aws_ami.al2023.id
  instance_type = "t3.small"
}

    EXPERT Composition over giant modules

    • Build small, single-purpose modules (network, database, service) and compose them in a root module.
    • Expose only what callers need as variable; return what others need as output.
    • Prefer passing IDs and objects in over modules that look things up themselves.
    • Do not hide providers inside reusable modules; let the root module pass them in.
    💡
    See the State & Drift Management module for full module authoring: structure, semantic versioning, testing and publishing.

    🧮 Expressions: for, splat, dynamic blocks

    INTERMEDIATE for expressions and conditionals

    hcllocals {

  name_to_cidr = { for k, s in var.subnets : k => s.cidr }
  public_only  = { for k, s in var.subnets : k => s if s.public }
  instance_ids = aws_instance.a[*].id           # splat
  size = var.env == "prod" ? "m5.large" : "t3.micro"
}

    EXPERT dynamic blocks and templatefile

  name   = "web"

    🛡️ Meta-arguments & Lifecycle

    hclresource "aws_db_instance" "main" {
  # ...
  lifecycle {
    prevent_destroy       = true             # plan fails if it would delete
    create_before_destroy = true             # new first, then remove old
    ignore_changes        = [tags["LastScan"]] # tolerate outside edits
    replace_triggered_by  = [aws_launch_template.app.latest_version]
  }
}
    SettingUse it for
    prevent_destroyDatabases, state buckets, KMS keys — guard rails against accidents
    create_before_destroyZero-downtime replacement (watch for name collisions)
    ignore_changesAttributes legitimately managed elsewhere (autoscaling desired count, scanner tags)
    replace_triggered_byForce replacement when another resource or attribute changes
    depends_onHidden dependencies Terraform cannot see (e.g. IAM policy propagation)

    🧹 Refactoring Safely: moved, import, removed

    EXPERT Change code without destroying infrastructure

    hcl# Rename a resource without recreating it
moved {
  from = aws_instance.web
  to   = aws_instance.app
}

# Adopt an existing resource into state (Terraform 1.5+)
import {
  to = aws_s3_bucket.legacy
  id = "legacy-company-bucket"
}

# Stop managing a resource but keep it in the cloud (1.7+)
removed {
  from = aws_s3_bucket.old
  lifecycle { destroy = false }
}
    bashterraform plan -generate-config-out=generated.tf   # draft HCL for imported resources
terraform plan -refresh-only                       # see drift without proposing changes
    ✅
    Config-driven moved and import blocks go through plan and code review, unlike ad-hoc terraform state mv commands. Prefer them for team work.

    ✅ Validation: preconditions, postconditions, checks

    hclresource "aws_instance" "app" {
  ami           = data.aws_ami.al2023.id
  instance_type = var.instance_type

  lifecycle {
    precondition {
      condition     = data.aws_ami.al2023.architecture == "x86_64"
      error_message = "AMI must be x86_64."
    }
    postcondition {
      condition     = self.public_ip == null || var.allow_public
      error_message = "Public IP not allowed in this environment."
    }
  }
}

check "site_healthy" {
  data "http" "ping" { url = "https://${aws_lb.app.dns_name}/health" }
  assert {
    condition     = data.http.ping.status_code == 200
    error_message = "Health endpoint is not returning 200."
  }
}

    precondition/postcondition block the run; check blocks only warn, which makes them ideal for continuous health assertions.

    🧪 Testing with terraform test

    Terraform 1.6+ ships a native test framework. Files ending in .tftest.hcl run assertions against a plan (fast, free) or a real apply (full integration).

    hcl# tests/network.tftest.hcl
variables {
  env  = "dev"
  cidr = "10.10.0.0/16"
}

run "plan_is_valid" {
  command = plan
  assert {
    condition     = aws_vpc.main.cidr_block == "10.10.0.0/16"
    error_message = "Unexpected VPC CIDR"
  }
}

run "apply_and_check" {
  command = apply
  assert {
    condition     = output.vpc_id != ""
    error_message = "VPC id output missing"
  }
}
    bashterraform test                      # run every *.tftest.hcl
terraform test -filter=tests/network.tftest.hcl
    💡
    Test pyramid for IaC: fmt/validate/lint (seconds) → plan-mode tests and policy checks (minutes) → apply-mode tests in a sandbox account (slow, selective) → Terratest for cross-tool scenarios.

    Module 04 · IaC Frameworks · OpenTofu

    OpenTofu

    The open-source, Terraform-compatible alternative governed by the Linux Foundation. Learn why it exists, how to migrate, and which features go beyond Terraform.

    📖 What is OpenTofu?

    BASIC Origin story

    In August 2023 HashiCorp changed Terraform’s licence from MPL 2.0 to the Business Source License. The community responded with the OpenTF manifesto, then a fork now called OpenTofu, hosted by the Linux Foundation under the open MPL 2.0 licence. The first stable release (1.6) arrived in January 2024.

    🔓
    Open governance
    Community steering committee, vendor-neutral foundation.
    🤝
    HCL compatible
    Same language, same providers, same workflow.
    🔐
    New features
    State encryption, early evaluation, provider iteration.
    🧰
    Own registry
    registry.opentofu.org mirrors providers and modules.
    bashtofu init
tofu plan -out=tfplan
tofu apply tfplan
    📝
    The CLI binary is tofu. Commands, flags, files and state format match Terraform, so your Terraform knowledge transfers directly.

    🚚 Migrating from Terraform

    INTERMEDIATE A safe migration checklist

    1. Check your Terraform version against the OpenTofu compatibility notes (migrate from a version OpenTofu supports; do this before adopting newer Terraform-only features).
    2. Back up state (enable bucket versioning, or copy the state file).
    3. Install tofu (package manager, container image, or tofu GitHub Action).
    4. Run tofu init then tofu plan — expect no changes.
    5. Update CI images and pipelines to call tofu; keep Terraform available until the first clean apply.
    6. Remember that once applied with OpenTofu, going back to an older Terraform may not be supported if newer state features were used.
    bashcp terraform.tfstate backup-$(date +%F).tfstate
tofu init -upgrade
tofu plan          # must report: No changes. Your infrastructure matches the configuration.
    ⚠️
    Never test a migration directly on production first. Rehearse in a copy of the stack or a non-production workspace.

    🆚 What is Different?

    FeatureTerraform (BSL)OpenTofu (MPL 2.0)
    LicenceBusiness Source LicenseMPL 2.0, Linux Foundation
    State and plan encryptionBackend-level encryption onlyBuilt-in client-side encryption (since 1.7)
    Early evaluationVariables not allowed in backend config or module sourcesVariables and locals allowed in backend config and module source
    Provider iterationUse aliases manuallyfor_each on provider blocks (since 1.9)
    Override files.tf / .tf.jsonAlso .tofu files take priority over .tf of the same name
    GovernanceSingle vendorCommunity steering committee
    EcosystemHCP Terraform, SentinelWorks with Spacelift, env0, Atlantis, Terragrunt, and others
    💡
    Features evolve quickly on both sides. Always confirm availability in the current release notes before standardising on a feature.

    🔐 State Encryption (Expert)

    EXPERT Encrypt state and plan files client-side

    hclterraform {
  encryption {
    key_provider "pbkdf2" "main" {
      passphrase = var.state_passphrase      # >= 16 chars, supplied securely
    }
    method "aes_gcm" "default" {
      keys = key_provider.pbkdf2.main
    }
    state {
      method   = method.aes_gcm.default
      enforced = true                        # refuse to write unencrypted state
    }
    plan {
      method = method.aes_gcm.default
    }
  }
}

    In production prefer a cloud KMS key provider (for example AWS KMS) over a passphrase so key rotation and access are governed by IAM.

    ✅
    This closes a long-standing gap: even someone with read access to the state bucket cannot read secrets without the key.

    🧭 Choosing Terraform or OpenTofu

    Pick OpenTofu when

    • Open-source licensing is a company requirement.
    • You want built-in state encryption.
    • You want vendor-neutral governance.
    • Your tooling (Atlantis, Spacelift, env0, etc.) already supports it.

    Pick Terraform when

    • You rely on HCP Terraform / Sentinel / HashiCorp support contracts.
    • You need newest Terraform-only features.
    • Your organisation already standardised on it and licence terms are acceptable.
    📝
    Good news: the skills in this course apply to both. Learn HCL once, choose the binary per organisation.

    🎯 Pulumi Mental Model

    📁
    Project
    A directory with Pulumi.yaml and your program.

    ⏳ Outputs & apply() — the key concept

    INTERMEDIATE Values that are not known until deploy time

    A resource’s ID or URL does not exist until the cloud creates it, so Pulumi returns an Output<T> — a promise-like value. You cannot print or concatenate it as a plain string; you transform it.

    pythonbucket = aws.s3.BucketV2("site")

# WRONG: bucket.bucket is an Output, not a str
# url = "https://" + bucket.bucket + ".s3.amazonaws.com"

url = bucket.bucket.apply(lambda name: f"https://{name}.s3.amazonaws.com")
url2 = pulumi.Output.concat("https://", bucket.bucket, ".s3.amazonaws.com")
pulumi.export("url", url)
    ⚠️
    Do not create resources inside apply() callbacks: they will not appear in preview. Pass Outputs directly to other resources instead — Pulumi tracks the dependency for you.

    🔧 A Production CI/CD Pipeline

    EXPERT Plan on pull request, apply on merge

    yamlname: terraform
on:
  pull_request:
  push: { branches: [main] }

permissions:
  id-token: write       # OIDC to AWS, no long-lived keys
  contents: read
  pull-requests: write

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::111122223333:role/ci-plan
          aws-region: ap-south-1
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -input=false
      - run: terraform fmt -check
      - run: terraform validate
      - run: terraform plan -input=false -out=tfplan
      - uses: actions/upload-artifact@v4
        with: { name: tfplan, path: tfplan }

  apply:
    needs: plan
    if: github.ref == 'refs/heads/main'
    environment: production        # manual approval gate
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { name: tfplan }
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init -input=false
      - run: terraform apply -input=false tfplan
    💡
    Use OIDC federation to assume cloud roles. Give the plan role read-only access and the apply role write access, behind an approval gate.

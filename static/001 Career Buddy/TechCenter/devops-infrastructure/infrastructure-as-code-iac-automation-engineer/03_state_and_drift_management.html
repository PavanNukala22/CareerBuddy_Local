    Module 01 · State & Drift · Foundations

    Understanding IaC State

    State is the memory of your IaC tool. Learn what it holds, why it exists, how to inspect it, and the rules that keep it safe.

    🧠 What is State?

    When Terraform or OpenTofu creates an S3 bucket, it receives a real ID from AWS. State records the mapping “this block in my code = that real object in the cloud”, plus every attribute the provider returned.

    A plan compares all three: code vs state vs reality.
    🔗
    Mapping
    Links aws_s3_bucket.logs to the real bucket ID.
    📦
    Metadata
    Dependencies, provider info, resource schema versions.
    🚀
    Performance
    Caches attributes so large estates plan quickly.
    🗑️
    Deletion tracking
    Knows what to destroy when you remove code.

    🔬 Inside a State File

    json{
  "version": 4,
  "terraform_version": "1.9.0",
  "serial": 42,
  "lineage": "3f1c2a9e-....",
  "outputs": { "bucket_arn": { "value": "arn:aws:s3:::demo-logs-dev" } },
  "resources": [
    {
      "mode": "managed",
      "type": "aws_s3_bucket",
      "name": "logs",
      "provider": "provider[\"registry.terraform.io/hashicorp/aws\"]",
      "instances": [ { "attributes": { "id": "demo-logs-dev", "bucket": "demo-logs-dev" } } ]
    }
  ]
}
    FieldMeaning
    serialIncrements with each state change; used to detect conflicting writes
    lineageUnique ID of this state’s history; prevents mixing unrelated state files
    resourcesEvery managed object with its attributes — including secrets such as passwords
    ⚠️
    State often contains plain-text secrets (database passwords, private keys, tokens). Treat the state bucket like a password vault: encrypt, restrict, audit.

    🔍 Inspecting State Safely

    BASIC Read-only commands

    bashterraform state list                         # every resource address
terraform state show aws_s3_bucket.logs      # attributes of one resource
terraform show                               # human-readable whole state
terraform show -json | jq '.values.root_module.resources[].address'
terraform output                             # root module outputs
terraform state pull > backup-$(date +%F).json   # download a copy (backup)
    ✅
    These commands never change infrastructure. Make state pull backups a habit before any risky operation.

    📏 The Golden Rules

    RuleWhy
    Never edit the state file by handOne wrong character breaks the mapping; use state mv/rm, import, moved blocks instead
    Never commit state to GitSecrets leak; merges corrupt it. Add *.tfstate* to .gitignore
    Use remote state with lockingTeams and CI need one shared source of truth
    One state per blast-radius boundarySmaller states plan faster and limit damage
    Only the pipeline writes stateDevelopers get read access; apply happens from CI

    🌐 State in Other Tools

    ToolWhere “state” lives
    Terraform / OpenTofuState file in a backend (S3, GCS, Azure Blob, HCP Terraform…)
    PulumiPulumi Cloud, or self-managed backend (S3, Azure Blob, GCS, file)
    AWS CloudFormation / CDKManaged by AWS inside each CloudFormation stack (no file to host)
    Crossplane / Kubernetes controllersKubernetes API objects, continuously reconciled

    Module 02 · State & Drift · Backends

    Remote State Backends

    Where state lives, how to secure it, how to bootstrap it, and how to lay out many states for many teams.

    🗄️ Choosing a Backend

    BackendLockingNotes
    Amazon S3Native lockfile (use_lockfile) or legacy DynamoDB tableMost common on AWS; versioning + KMS encryption
    Google Cloud StorageBuilt inEnable object versioning
    Azure Blob (azurerm)Blob leaseUse Entra ID auth where possible
    HCP Terraform (cloud block)Built in, run queueManaged state, RBAC, run history, policy
    PostgreSQL / HTTP / ConsulVariesSelf-hosted options for special cases
    LocalNone meaningfulLearning only
    📝
    OpenTofu supports the same backend types, and can additionally encrypt state client-side before it reaches the backend.

    🪣 S3 Backend in Practice

    BASIC Configuration

    hclterraform {
  backend "s3" {
    bucket       = "acme-tfstate-prod"
    key          = "prod/network/terraform.tfstate"
    region       = "ap-south-1"
    encrypt      = true
    kms_key_id   = "alias/tfstate"
    use_lockfile = true          # S3-native locking (recent Terraform/OpenTofu versions)
    # dynamodb_table = "tf-locks"  # legacy locking, being deprecated
  }
}
    💡
    S3-native locking writes a small .tflock object using conditional writes, so you no longer need a separate DynamoDB table. Confirm support in your tool version’s release notes.

    🥾 Bootstrapping the Backend

    INTERMEDIATE The chicken-and-egg problem

    The bucket that stores state must exist before you can store state in it. Create it with a tiny separate configuration (local state, or created once by hand/CLI), then never touch it again.

    hclresource "aws_s3_bucket" "tfstate" {
  bucket = "acme-tfstate-prod"
  lifecycle { prevent_destroy = true }
}

resource "aws_s3_bucket_versioning" "v" {
  bucket = aws_s3_bucket.tfstate.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "e" {
  bucket = aws_s3_bucket.tfstate.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = aws_kms_key.tfstate.arn
    }
  }
}

resource "aws_s3_bucket_public_access_block" "b" {
  bucket                  = aws_s3_bucket.tfstate.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_lifecycle_configuration" "l" {
  bucket = aws_s3_bucket.tfstate.id
  rule {
    id     = "expire-old-versions"
    status = "Enabled"
    filter {}
    noncurrent_version_expiration { noncurrent_days = 90 }
  }
}
    ✅
    Must-haves: versioning (rollback), encryption, public access block, TLS-only bucket policy, restricted IAM, and lifecycle cleanup of old versions.

    🧩 Partial Configuration & Environments

    INTERMEDIATE Keep backend settings out of code

    hcl# main.tf
terraform {
  backend "s3" {}      # filled at init time
}
    hcl# envs/prod.backend.hcl

    🗺️ State Layout & Blast Radius

    EXPERT How to split state

    layouts3://acme-tfstate-prod/
  prod/network/terraform.tfstate     # VPC, subnets, routing (changes rarely)
  prod/data/terraform.tfstate        # databases, queues
  prod/platform/terraform.tfstate    # EKS, shared services
  prod/app-checkout/terraform.tfstate
  prod/app-search/terraform.tfstate  # each team owns its own state
    QuestionGuidance
    Too big?A state with thousands of resources makes plans slow and risky. Split by lifecycle and ownership
    Too small?Hundreds of tiny states create dependency chaos. Group things that change together
    Cross-state data?Prefer a published contract (SSM parameters, outputs, data sources) over reading another team’s whole state
    hcl# Option A: read outputs of another state (couples you to its backend)
data "terraform_remote_state" "network" {
  backend = "s3"
  config  = { bucket = "acme-tfstate-prod", key = "prod/network/terraform.tfstate", region = "ap-south-1" }
}

# Option B: look up by tags / SSM (looser coupling, preferred for many teams)
data "aws_ssm_parameter" "private_subnets" {
  name = "/prod/network/private_subnet_ids"
}

    🔒 Access Control & Auditing

    • Write access only for the pipeline role; humans get read-only (or none, for sensitive states).
    • Separate IAM roles per environment; a dev role cannot read prod state.
    • Enable CloudTrail data events / access logs on the bucket and alert on access by unexpected principals.
    • Enable MFA delete / object lock for the most critical buckets.
    • Replicate state buckets cross-region for disaster recovery.

    Module 03 · State & Drift · Concurrency

    State Locking & Concurrency

    Prevent two runs from writing state at once. Learn how locks work, what to do with stale locks, and how to queue pipeline runs.

    🔐 Why Locking Exists

    Imagine two engineers run apply on the same stack at the same moment. Both read the same state, both change infrastructure, and the last one to write state overwrites the other’s record — leaving real resources the tool no longer knows about.

    A lock serialises operations that can change state.

    ⚙️ How Locks Work

    BackendMechanism
    S3 (native)Creates a <key>.tflock object with a conditional write; fails if it already exists
    S3 (legacy)DynamoDB item with LockID as the key (conditional put)
    GCS / Azure BlobObject/blob lease or lock object
    HCP TerraformRun queue: one run per workspace at a time
    hcl# Legacy DynamoDB lock table (still common in older estates)
resource "aws_dynamodb_table" "locks" {
  name         = "tf-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"
  attribute {
    name = "LockID"
    type = "S"
  }
}

    Commands that write state (apply, destroy, state mv/rm, import) take the lock. plan also locks by default because it refreshes state.

    ⏱️ Lock Flags & Stuck Locks

    BASIC Everyday usage

    bashterraform apply -lock-timeout=10m     # wait up to 10 minutes instead of failing instantly
terraform plan  -lock=false           # skip locking (read-only plans only; use with care)

    INTERMEDIATE When a lock is stale

    If a run crashes (CI runner killed, laptop closed), the lock may remain. The error shows a Lock ID, who holds it, and when it started.

    exampleError: Error acquiring the state lock
Lock Info:
  ID:        8a6f1e0c-....
  Operation: OperationTypeApply
  Who:       ci-runner-17
  Created:   2026-05-02 09:14:31 UTC
    bashterraform force-unlock 8a6f1e0c-....    # ONLY after confirming no run is active
    ⚠️
    Before force-unlocking: check the CI system and ask the person named in Who. Forcing a lock while an apply is running can corrupt state. Never script force-unlock into pipelines.

    🚦 Serialising CI/CD Runs

    INTERMEDIATE GitHub Actions concurrency groups

    yamlname: apply-prod-network
on:
  push: { branches: [main], paths: ["prod/network/**"] }

concurrency:
  group: tf-prod-network      # one run per stack
  cancel-in-progress: false   # QUEUE, never cancel a running apply

jobs:
  apply:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: terraform -chdir=prod/network init -input=false
      - run: terraform -chdir=prod/network apply -input=false -auto-approve -lock-timeout=15m
    💡
    Cancel-in-progress must be false for apply jobs. Killing an apply midway can leave a lock and a half-applied change. Atlantis, Spacelift, env0 and HCP Terraform also queue runs per stack.

    🧯 Failure Scenarios

    SymptomLikely causeResponse
    “Error acquiring the state lock”Another run activeWait or use -lock-timeout
    Lock persists after CI crashStale lockVerify nothing runs, then force-unlock
    “state data in S3 does not have the expected content”Digest mismatch from legacy lock tableRestore consistent state version; fix digest per backend docs
    Serial conflict / lineage mismatchMixed up two state files or stale local copyPull the correct state; never push over a different lineage
    Partial apply failed halfwayAPI error mid-runFix cause, re-run apply; state records completed resources

    🧰 Locking in Other Tools

    • Pulumi: the backend locks a stack during updates. pulumi cancel aborts a stuck update; pulumi stack export/import repairs state if needed.
    • CloudFormation / CDK: a stack can run only one operation at a time (UPDATE_IN_PROGRESS); no external lock to manage.
    • HCP Terraform / Spacelift / env0: built-in run queues provide locking plus approvals and audit logs.

    Module 04 · State & Drift · Modules

    Writing Production-Grade Modules

    Design clean interfaces, version and publish modules, test them, and avoid the anti-patterns that make shared code painful.

    📐 Module Structure

    layoutterraform-aws-secure-bucket/
  main.tf          # resources
  variables.tf     # inputs
  outputs.tf       # outputs (the module's public contract)
  versions.tf      # required_version + required_providers
  README.md        # generated with terraform-docs
  examples/
    basic/main.tf
    complete/main.tf
  tests/
    defaults.tftest.hcl
    📝
    Naming convention for registries: terraform-<PROVIDER>-<NAME> (for example terraform-aws-secure-bucket).

    🧱 Designing Inputs & Outputs

    INTERMEDIATE A good interface is small, typed and validated

    hcl# variables.tf
variable "name" {
  type        = string
  description = "Bucket name (globally unique)."
  validation {
    condition     = can(regex("^[a-z0-9][a-z0-9.-]{2,62}$", var.name))
    error_message = "Use 3-63 lowercase letters, digits, dots or hyphens."
  }
}

variable "versioning" {
  type        = bool
  description = "Enable object versioning."
  default     = true
}

variable "lifecycle_rules" {
  type = list(object({
    id              = string
    expire_days     = number
    prefix          = optional(string, "")
  }))
  description = "Optional expiration rules."
  default     = []
}

variable "tags" {
  type    = map(string)
  default = {}
}
    hcl# main.tf
resource "aws_s3_bucket" "this" {
  bucket = var.name
  tags   = var.tags
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id
  versioning_configuration {
    status = var.versioning ? "Enabled" : "Suspended"
  }
}

resource "aws_s3_bucket_public_access_block" "this" {
  bucket                  = aws_s3_bucket.this.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# outputs.tf
output "bucket_id"  { value = aws_s3_bucket.this.id }
output "bucket_arn" { value = aws_s3_bucket.this.arn }
    • Secure by default: public access blocked, encryption on; make insecure choices explicit opt-ins.
    • Hide complexity: expose business-level inputs, not every provider argument.
    • Outputs are a contract: removing or renaming an output is a breaking change.

    🔗 Composition & Providers

    EXPERT How modules should fit together

    Do

    • Compose small modules in a root module.
    • Declare required_providers (source and version constraints) inside the module.
    • Receive provider configuration from the caller via providers = { ... }.
    • Accept IDs/objects as inputs for loose coupling.

    Avoid

    • Provider blocks with credentials or regions inside reusable modules.
    • Deeply nested module chains (hard to debug).
    • One “mega module” that builds everything.
    • Modules that silently look up global data you cannot override.
    hcl# versions.tf in the module
terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source                = "hashicorp/aws"
      version               = ">= 5.0"
      configuration_aliases = [aws.replica]     # caller must pass this alias
    }
  }
}

    🏷️ Versioning & Publishing

    EXPERT Semantic versioning for infrastructure

    ChangeBumpExample
    Bug fix, no interface changePATCH 1.2.3Corrected a tag default
    New optional input/outputMINOR 1.3.0Added lifecycle_rules
    Removed/renamed input, output, or forces resource replacementMAJOR 2.0.0Changed bucket naming scheme
    hclmodule "logs" {
  source  = "app.terraform.io/acme/secure-bucket/aws"   # private registry
  version = "~> 1.3"                                    # allow 1.x, not 2.0
  name    = "acme-logs-prod"
}

module "logs_git" {
  source = "git::https://git.example.com/infra/terraform-aws-secure-bucket.git?ref=v1.3.2"
  name   = "acme-logs-dev"
}
    hcl# Refactoring inside a module without destroying resources for callers
moved {
  from = aws_s3_bucket_versioning.bucket_v
  to   = aws_s3_bucket_versioning.this
}
    ✅
    Ship a CHANGELOG, tag releases in Git, and publish to a private registry (HCP Terraform, Artifactory, GitHub tags). Callers pin versions and upgrade deliberately.

    Module 05 · State & Drift · Drift

    Drift Detection & Automation

    Infrastructure changes outside your code all the time. Learn to detect it automatically, decide what to do about it, and prevent it.

    🌊 What is Drift?

    Drift is any difference between what your IaC says and what actually exists. A security group edited in the console, an autoscaling group changed by a scaling policy, a resource deleted by someone — all are drift.

    🖱️
    Manual change
    Console/CLI hotfixes during incidents.
    🤖
    Other automation
    Autoscaling, operators, scripts, other pipelines.
    🗑️
    Deleted resources
    Removed outside IaC; plan wants to recreate.
    👻
    Shadow resources
    Created outside IaC; never in state at all.
    TypeExampleDetected by plan?
    Attribute driftSecurity group rule added in consoleYes
    Resource missingS3 bucket deleted manuallyYes (will recreate)
    Unmanaged resourceEC2 instance never added to codeNo — needs inventory tools

    🔎 Detecting Drift

    BASIC Terraform / OpenTofu

    bashterraform plan -detailed-exitcode
# exit 0 = no changes   | exit 1 = error   | exit 2 = changes present (drift or pending code change)

terraform plan -refresh-only          # show ONLY differences between state and reality
terraform apply -refresh-only         # accept reality into state (no infra change)

    INTERMEDIATE Other engines

    bash# Pulumi
pulumi preview --refresh --expect-no-changes

# CloudFormation / CDK
aws cloudformation detect-stack-drift --stack-name Storage
aws cloudformation describe-stack-resource-drifts --stack-name Storage \
    --stack-resource-drift-status-filters MODIFIED DELETED
    ApproachStrengthLimitation
    plan -detailed-exitcodeFree, simple, runs anywhereOnly resources in state
    HCP Terraform health assessments / Spacelift / env0Scheduled drift runs, dashboards, notificationsPlatform dependency
    AWS Config / Azure PolicyContinuous compliance on all resourcesDetects rule violations, not “diff vs code”
    Cloud inventory + tag auditFinds unmanaged (shadow) resourcesNeeds tagging discipline
    CloudFormation drift detectionNative for CFN/CDK stacksNot every resource type is supported
    📝
    The open-source driftctl project, once popular for finding unmanaged resources, is no longer maintained. Use platform features, cloud-native inventory or current commercial tools instead.

    🤖 Automating Detection

    INTERMEDIATE Scheduled pipeline

    yamlname: drift-detection
on:
  schedule: [{ cron: "0 3 * * *" }]     # nightly
  workflow_dispatch:

permissions: { id-token: write, contents: read, issues: write }

jobs:
  drift:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        stack: [prod/network, prod/data, prod/platform]
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::111122223333:role/ci-readonly-plan
          aws-region: ap-south-1
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_wrapper: false }
      - name: Plan
        id: plan
        working-directory: ${{ matrix.stack }}
        run: |
          terraform init -input=false
          set +e
          terraform plan -detailed-exitcode -input=false -lock=false -no-color | tee plan.txt
          echo "code=${PIPESTATUS[0]}" >> "$GITHUB_OUTPUT"
      - name: Open issue on drift
        if: steps.plan.outputs.code == '2'
        run: gh issue create --title "Drift in ${{ matrix.stack }}" --body-file ${{ matrix.stack }}/plan.txt
        env: { GH_TOKEN: "${{ github.token }}" }
      - name: Fail on error
        if: steps.plan.outputs.code == '1'
        run: exit 1
    💡
    Use a read-only role for drift jobs and -lock=false so a nightly scan never blocks real deployments. Post results to Slack/Teams or ticketing systems.

    🩹 Remediation: Revert, Accept or Ignore

    DecisionWhenHow
    Revert (code wins)Change was unauthorised or accidentalterraform apply from the pipeline
    Accept (reality wins)Change was legitimate (incident hotfix)Update the code to match, then apply -refresh-only or import
    Ignore (another system owns it)Attribute managed elsewhere, e.g. autoscaling countlifecycle { ignore_changes = [desired_capacity] }
    hclresource "aws_autoscaling_group" "app" {
  min_size         = 2
  max_size         = 10
  desired_capacity = 2
  lifecycle {
    ignore_changes = [desired_capacity]    # the scaler owns this value
  }
}
    ⚠️
    Blindly reverting can cause outages (for example, undoing an emergency firewall change). Triage first: who changed it, why, and is it still needed?

    🚧 Preventing Drift

    EXPERT Make the right path the only path

    • Restrict console/CLI writes in production with IAM or Service Control Policies; allow writes only for the pipeline role and a monitored break-glass role.
    • Alert on out-of-band changes: CloudTrail + EventBridge rule for write events from principals other than the pipeline.
    • Tag everything with ManagedBy=terraform and the owning repo; audit for resources missing the tag.
    • Post-incident hygiene: every emergency change gets a follow-up PR within a set time.
    • Continuous reconciliation: GitOps controllers (Crossplane, Flux Terraform controller, Argo-based setups) re-apply desired state automatically.
    json{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyConsoleWritesInProd",
    "Effect": "Deny",
    "Action": ["ec2:*", "rds:*", "s3:Put*", "iam:*"],
    "Resource": "*",
    "Condition": {
      "StringNotLike": { "aws:PrincipalArn": [
        "arn:aws:iam::*:role/terraform-apply", "arn:aws:iam::*:role/break-glass" ] }
    }
  }]
}
    📝
    The SCP above is a simplified illustration. Real policies need careful scoping (and testing in a sandbox) to avoid locking out essential services.

    2Nightly automated detection with notifications
    3Severity triage, owners per stack, SLA to resolve
    4Preventive controls (SCP/IAM) + auto-remediation for safe classes of drift + shadow-resource inventory

    Module 06 · State & Drift · Operations

    State Surgery & Disaster Recovery

    Refactor, split and repair state without destroying real infrastructure — and recover when something goes wrong.

    🛠️ The State Toolbox

    Command / featurePurposeRisk
    moved { } blockRename/move a resource in code (reviewed, repeatable)Low
    import { } block / terraform importAdopt an existing resource into stateLow–medium
    removed { } block / state rmStop managing a resource without destroying itMedium
    terraform state mvMove addresses or move between state filesMedium
    apply -replace=ADDRForce recreation of one resource (replaces deprecated taint)High
    state pushOverwrite remote stateVery high — last resort
    ✅
    Order of preference: config-driven blocks (moved, import, removed) → targeted CLI commands → state push. Always back up first.

    ✂️ Splitting a State Safely

    EXPERT Move database resources out of a monolith

    1. Back up both states: terraform state pull > monolith.json.
    2. Write the new stack’s code (new backend key) with import blocks for the resources to adopt.
    3. Run plan in the new stack — it must show imports and no creates/destroys.
    4. apply the new stack (state now knows the resources).
    5. In the old stack add removed { lifecycle { destroy = false } } blocks (or state rm) so it forgets them without deleting.
    6. plan both stacks: expect no changes everywhere.
    hcl# NEW stack
import {
  to = aws_db_instance.orders
  id = "orders-prod"
}
resource "aws_db_instance" "orders" { /* exact same arguments as before */ }

# OLD stack
removed {
  from = aws_db_instance.orders
  lifecycle { destroy = false }
}
    ⚠️
    Never run the old stack’s apply before the new stack has imported the resource, or you will destroy a production database.

    🚑 Recovery Scenarios

    SituationWhat to do
    State file deleted or lostRestore the previous object version from the versioned bucket (aws s3api list-object-versions → copy the good version back). If no backup, re-import every resource.
    State corrupted by a bad writeRestore last good version; verify with plan; check serial and lineage.

    📋 Incident Runbook

    Calm, repeatable steps beat heroics.
    • Freeze pipelines for the affected stack to avoid parallel writes.
    • Capture evidence: state version IDs, plan output, CloudTrail events.
    • Prefer reversible actions; test the procedure on a copy of the state (-state=copy.tfstate or a sandbox backend).
    • Document the incident and add a prevention control (policy, alert, lock, review rule).

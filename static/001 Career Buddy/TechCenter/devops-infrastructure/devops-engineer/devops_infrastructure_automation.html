    Module 01 · Foundations

    Infrastructure Automation Fundamentals

    Four tools, four jobs. Terraform creates infrastructure, Ansible configures it, Docker packages software, and Kubernetes runs those packages at scale.

    🧭 What is what? Basic

    Infrastructure automation means describing infrastructure in files and letting software apply them, instead of clicking in consoles or typing commands by hand.

    ToolCategoryJobOne-line example
    TerraformProvisioning (IaC)Create cloud resources"Make a VPC, 3 subnets and a database"
    AnsibleConfiguration managementConfigure servers and apps"Install nginx and copy this config on 50 servers"
    DockerContainerisationPackage app + dependencies"Bundle my app into one portable image"
    KubernetesOrchestrationRun, scale and heal containers"Keep 5 copies of this container running"
    🏗️
    Analogy: building a restaurant. Terraform builds the building, Ansible installs the kitchen equipment, Docker prepares standard meal boxes, and Kubernetes is the manager who keeps enough cooks and boxes ready for the rush.

    🧩 Types and key concepts Basic

    ConceptMeaningExamples
    DeclarativeDescribe the end result; tool finds the stepsTerraform, Kubernetes YAML
    Imperative / proceduralDescribe the stepsBash, docker run, ad-hoc commands
    Mutable infrastructureUpdate servers in placeAnsible patching a VM
    Immutable infrastructureReplace instead of changeNew container image or AMI per release
    IdempotentSafe to run repeatedly with the same resultAnsible modules, terraform apply
    Agentless vs agentWhether software must be installed on targetsAnsible (SSH, agentless) vs Puppet (agent)

    🔄 How they fit together Intermediate

    A typical flow in a real team:

    Terraform→Cloud network + K8s cluster→Docker build→Image in registry→Kubernetes deploy
    📌
    Ansible slots in where long-lived servers exist: bootstrapping VMs, hardening OS, installing agents, or configuring a self-managed cluster.

    Module 02 · Provision

    Terraform

    Terraform (HashiCorp) uses the HCL language to create and manage infrastructure on AWS, Azure, GCP, Kubernetes and hundreds of other platforms through providers.

    🧱 Building blocks Basic

    BlockPurpose
    providerPlugin that talks to a platform API
    resourceA thing to create (VM, bucket, subnet)
    dataLook up something that already exists
    variable / outputInputs and results
    moduleReusable package of resources
    localsNamed expressions
    hclprovider "aws" { region = "eu-west-1" }

variable "env" { default = "dev" }

resource "aws_instance" "web" {
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"
  tags          = { Name = "web-${var.env}" }
}

output "public_ip" { value = aws_instance.web.public_ip }

    ⌨️ Workflow and state Basic

    The loop is always init → plan → apply.

    bashterraform init       # download providers/modules
terraform fmt -check # style check
terraform validate   # syntax check
terraform plan -out=tfplan   # preview (+ create, ~ change, - destroy)
terraform apply tfplan       # execute exactly that plan
terraform destroy            # tear down
    ⚠️
    State (terraform.tfstate) maps your code to real resources and may contain secrets. Store it in a remote, encrypted, locked backend (S3 + DynamoDB, Azure Blob, GCS, Terraform Cloud). Never commit it.

    📦 Modules, loops and environments Intermediate

    Modules avoid copy-paste; for_each and count create many similar resources.

    hclmodule "network" {
  source = "./modules/vpc"
  cidr   = "10.0.0.0/16"
}

resource "aws_s3_bucket" "buckets" {
  for_each = toset(["logs", "backups", "assets"])
  bucket   = "acme-${each.key}"
}
    Environment strategyHowTrade-off
    WorkspacesSame code, separate stateEasy; risky if folders look identical
    Directory per envenvs/dev, envs/prod calling shared modulesClear, a bit more files
    TerragruntWrapper that keeps DRY configsExtra tool

    🧠 Expert practices Expert

    • Split state by layer (network, data, apps) to reduce blast radius.
    • Pin provider and module versions; commit .terraform.lock.hcl.
    • import blocks adopt existing resources; moved blocks refactor safely; lifecycle.prevent_destroy protects critical items.
    • Run plan in pull requests, apply only after merge and approval (Atlantis, GitHub Actions, GitLab CI).
    • Scan with tfsec, Checkov or Trivy; test with terraform test or Terratest.

    Module 03 · Configure

    Ansible

    Ansible configures servers over SSH using human-readable YAML. It needs no agent on the target, only Python and SSH.

    📘 Core concepts Basic

    TermMeaning
    Control nodeMachine where you run Ansible
    InventoryList of hosts and groups
    ModuleUnit of work (apt, copy, service)
    TaskOne call to a module
    PlaybookOrdered list of plays and tasks
    RoleReusable folder structure of tasks, templates, defaults
    HandlerTask that runs only when notified by a change
    CollectionPackaged modules, roles and plugins
    ini# inventory.ini
[web]
web1.example.com
web2.example.com

[db]
db1.example.com ansible_user=admin

    ▶️ First playbook Basic

    Install and start nginx on all web servers:

    yaml- name: Configure web servers
  hosts: web
  become: true
  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
    - name: Copy site config
      ansible.builtin.template:
        src: site.conf.j2
        dest: /etc/nginx/conf.d/site.conf
      notify: Reload nginx
  handlers:
    - name: Reload nginx
      ansible.builtin.service: {name: nginx, state: reloaded}
    bashansible-playbook -i inventory.ini site.yml --check --diff   # dry run
ansible-playbook -i inventory.ini site.yml
ansible web -i inventory.ini -m ping                        # ad-hoc
    ✅
    Run it twice: the second run reports changed=0. That is idempotency.

    🔐 Variables, templates and Vault Intermediate

    Jinja2 templates fill in variables; Ansible Vault encrypts secrets in Git.

    jinja# templates/site.conf.j2
server {
  listen {{ http_port | default(80) }};
  server_name {{ inventory_hostname }};
}
    bashansible-vault create group_vars/all/vault.yml
ansible-playbook site.yml --ask-vault-pass
    FeatureUse
    whenRun task conditionally (when: ansible_os_family == "Debian")
    loopRepeat a task over a list
    block/rescueError handling
    tagsRun part of a playbook

    🧠 Expert practices Expert

    • Roles + collections with ansible-galaxy; version them.
    • Dynamic inventory from AWS/Azure/GCP so hosts are never hand-listed.
    • Test roles with Molecule and lint with ansible-lint.
    • serial: 10% for rolling updates; max_fail_percentage to stop bad rollouts.
    • AWX / Ansible Automation Platform adds RBAC, scheduling and audit.
    yaml- hosts: web
  serial: "20%"            # update 20% of hosts at a time
  max_fail_percentage: 10
  roles: [common, nginx, app]

    Module 04 · Package

    Docker

    Docker packages an application with everything it needs into an image, which runs as a container that behaves the same on any host.

    📦 Images, containers, registries Basic

    TermMeaningAnalogy
    ImageRead-only template built from layersA recipe + sealed ingredients
    ContainerRunning instance of an imageA cooked meal
    DockerfileInstructions to build an imageThe recipe card
    RegistryStorage for images (Docker Hub, ECR, ACR, GCR)A warehouse
    VolumePersistent storage outside the containerA pantry that survives
    bashdocker build -t myapp:1.0 .
docker run -d --name web -p 8080:80 myapp:1.0
docker ps
docker logs -f web
docker exec -it web sh
docker stop web && docker rm web
docker push myreg.example/myapp:1.0

    📝 Dockerfile and multi-stage builds Intermediate

    Multi-stage builds keep the final image small by leaving build tools behind.

    dockerfile# Stage 1: build
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

# Stage 2: runtime (tiny)
FROM gcr.io/distroless/static
COPY --from=build /app /app
USER 65532
EXPOSE 8080
ENTRYPOINT ["/app"]
    💡
    Put rarely-changing steps (install dependencies) before frequently-changing ones (copy source) so Docker reuses cached layers.

    🕸️ Networking, volumes and Compose Intermediate

    Docker Compose describes a multi-container app in one file:

    yamlservices:
  web:
    build: .
    ports: ["8080:8080"]
    environment:
      DB_HOST: db
    depends_on: [db]
  db:
    image: postgres:16
    volumes: [dbdata:/var/lib/postgresql/data]
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/pg
volumes:
  dbdata:
    bridge (default)hostnoneoverlay (multi-host)

    🛡️ Expert: security and optimisation Expert

    • Run as non-root, read-only root filesystem, drop capabilities.
    • Use minimal base images (distroless, alpine) and pin digests, not latest.
    • Scan images (Trivy, Grype), sign them (cosign), generate an SBOM.
    • Never bake secrets into layers; use build secrets or runtime injection.
    • Understand the plumbing: namespaces isolate, cgroups limit, a runtime (containerd, runc) executes.
    bashdocker run --read-only --cap-drop ALL --security-opt no-new-privileges \
  --memory 256m --cpus 0.5 myapp:1.0
trivy image myapp:1.0

    Module 05 · Orchestrate

    Kubernetes

    Kubernetes (K8s) runs containers across many machines. You declare the desired state; controllers constantly work to make reality match it.

    🏛️ Architecture Basic

    ComponentWhereRole
    kube-apiserverControl planeFront door for all requests
    etcdControl planeCluster database
    kube-schedulerControl planeChooses a node for each pod
    controller-managerControl planeRuns control loops (replicas, nodes, etc.)
    kubeletEvery nodeStarts and watches pods
    kube-proxyEvery nodeService networking rules
    Container runtimeEvery nodecontainerd / CRI-O
    kubectl→API server→etcd→Scheduler→kubelet→Pod running

    🧱 Key objects Basic

    ObjectPurposeUse when
    PodSmallest unit; one or more containersAlmost never created directly
    DeploymentManages replicas and rolling updatesStateless apps
    StatefulSetStable identity and storageDatabases, queues
    DaemonSetOne pod per nodeLog/monitor agents
    Job / CronJobRun to completion / on scheduleBatch, backups
    ServiceStable address (ClusterIP, NodePort, LoadBalancer)Expose pods
    Ingress / GatewayHTTP routing from outsideDomains and paths
    ConfigMap / SecretConfiguration / sensitive dataInject settings
    PersistentVolumeClaimRequest storageStateful data

    📄 Deployment and Service Intermediate

    Three replicas with health probes and resource limits:

    yamlapiVersion: apps/v1
kind: Deployment
metadata: {name: web}
spec:
  replicas: 3
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - name: web
        image: myreg.example/web:1.4.2
        ports: [{containerPort: 8080}]
        readinessProbe: {httpGet: {path: /healthz, port: 8080}}
        livenessProbe:  {httpGet: {path: /healthz, port: 8080}, initialDelaySeconds: 10}
        resources:
          requests: {cpu: 100m, memory: 128Mi}
          limits:   {memory: 256Mi}
---
apiVersion: v1
kind: Service
metadata: {name: web}
spec:
  selector: {app: web}
  ports: [{port: 80, targetPort: 8080}]
    bashkubectl apply -f web.yaml
kubectl get pods -o wide
kubectl describe pod web-xxxx
kubectl logs deploy/web
kubectl rollout status deploy/web
kubectl rollout undo deploy/web
kubectl scale deploy/web --replicas=5

    📈 Scaling, config and packaging Intermediate

    • HPA scales pods by CPU or custom metrics; Cluster Autoscaler / Karpenter scales nodes.
    • Helm packages manifests as charts with values; Kustomize overlays patches per environment.
    yamlapiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: web}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: web}
  minReplicas: 3
  maxReplicas: 20
  metrics:
  - type: Resource
    resource: {name: cpu, target: {type: Utilization, averageUtilization: 70}}

    🛡️ Expert: security and operations Expert

    • RBAC: least-privilege roles per team/service account.
    • NetworkPolicy: default-deny, then allow only needed traffic.
    • Pod Security Standards: non-root, no privileged, seccomp.
    • PodDisruptionBudget, topology spread and anti-affinity for availability.
    • Debug flow: get → describe → logs → events (look for Pending, CrashLoopBackOff, ImagePullBackOff, OOMKilled).
    yamlapiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny, namespace: prod}
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]

    Module 06 · End to end

    Combining the Tools

    A realistic pipeline links all four tools. Each does only what it is best at.

    🔗 Reference workflow Intermediate

    1. Terraform creates the VPC, an EKS/AKS/GKE cluster and a container registry.
    2. Developer pushes code; CI builds a Docker image, scans it and pushes it with a version tag.
    3. Kubernetes pulls the image and performs a rolling update.
    4. Ansible hardens any VMs outside the cluster (bastions, build agents, databases).
    yaml# GitHub Actions (simplified)
jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t $REG/web:${{ github.sha }} .
      - run: trivy image --exit-code 1 --severity HIGH,CRITICAL $REG/web:${{ github.sha }}
      - run: docker push $REG/web:${{ github.sha }}
      - run: kubectl set image deploy/web web=$REG/web:${{ github.sha }}

    ✅ Expert checklist Expert

    • Everything in Git; no manual console changes (detect drift).
    • Separate pipelines for infrastructure and application.
    • Immutable, versioned artifacts promoted across environments.
    • Secrets from a vault (HashiCorp Vault, cloud secret managers), never in repos.
    • Policy as code (OPA/Gatekeeper, Kyverno, Sentinel) and automated scanning in CI.
    • Observability from day one: metrics, logs, traces, alerts.

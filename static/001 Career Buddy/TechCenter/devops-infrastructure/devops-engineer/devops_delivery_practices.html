    Delivery Practices Fundamentals

    How code travels from a developer's laptop to users, and how teams keep that journey fast, safe and boring.

    🚚 Delivery vs deployment vs release Basic

    TermMeaningExample
    Continuous DeliveryEvery change is always releasable; a human approves the releaseMerge, tests pass, press "deploy"
    Continuous DeploymentEvery passing change goes to production automaticallyMerge, tests pass, live in 10 minutes

    💡

    Module 02 · Source control

    Trunk-Based Development

    Everyone integrates into a single branch (main, the "trunk") at least daily. Branches live for hours, not weeks.

    🌲 The core rules Basic

    • One shared trunk that is always releasable.
    • Branches are short-lived (under ~1–2 days) or none at all.
    • Commit small, merge often, rebase from trunk frequently.
    • A fast CI pipeline runs on every merge; a broken trunk is fixed or reverted immediately.

    ❌ Long-lived branches

    • Weeks of divergence

    • Big, risky merges

    • Late discovery of conflicts

    • Releases are events

    ✅ Trunk-based

    • Small daily merges

    • Conflicts found in minutes

    • Continuous integration for real

    • Releases are non-events

    Pull trunk→Small change→Local tests→PR / pair review→Merge to main→CI + deploy

    🚩 Feature flags: ship unfinished work safely Intermediate

    Incomplete features merge to trunk but stay hidden behind a flag.

    pythonimport featureflags as ff   # LaunchDarkly, Unleash, Flagsmith, OpenFeature...

def checkout(user, cart):
    if ff.is_enabled("new-payment-flow", user_id=user.id):
        return new_payment_flow(user, cart)     # dark-launched
    return old_payment_flow(user, cart)
    Flag typePurposeLifetime
    Release flagHide unfinished featureDays to weeks; delete after
    Experiment flagA/B testsWeeks
    Ops / kill switchTurn off a risky part during incidentsLong-lived
    Permission flagPlan or customer entitlementLong-lived
    ⚠️
    Flags are debt. Give every flag an owner and a removal date, or the code fills with dead paths.

    🔁 Branch by abstraction Intermediate

    For large changes (swapping a library or database client): introduce an interface, switch implementations behind it, remove the old one.

    Add interface→Route old code through it→Build new implementation→Switch by flag→Delete old

    🛠️ Expert: making trunk-based work Expert

    • Fast CI (under ~10 minutes): parallel tests, caching, test pyramid.
    • Branch protection: required checks, at least one review, linear history.
    • Pre-merge checks: lint, unit tests, security scan; post-merge: integration and deploy.
    • Release from trunk with tags; for emergencies use release branches cut from trunk and cherry-pick fixes.
    • Pair or mob programming and small PRs (under ~200 lines) reduce review latency.
    • Revert first, debug later when trunk breaks.

    Module 03 · Deployment strategy

    Blue/Green Deployments

    Run two identical production environments. Blue serves users now; deploy to Green, test it, then switch traffic in one step. Roll back by switching back.

    🔵🟢 How it works Basic

    Analogy: a train with a spare track. Prepare the new train on the spare track, check everything, then flip the switch.

    Blue (v1) live→Deploy v2 to Green→Test Green→Switch router to Green→Keep Blue as rollback
    ProsCons
    Instant cut-over and instant rollbackDouble the infrastructure cost during the switch
    Full pre-production testing on real infraDatabase changes need care (both versions share data)
    No mixed versions serving usersAll-or-nothing: no gradual exposure

    ☸️ Example on Kubernetes Intermediate

    Two Deployments with a Service whose selector flips between them:

    yaml# Service currently points at blue
apiVersion: v1
kind: Service
metadata: {name: web}
spec:
  selector: {app: web, color: blue}     # change to "green" to switch
  ports: [{port: 80, targetPort: 8080}]
    bashkubectl apply -f web-green.yaml                   # deploy v2 as "green"
kubectl rollout status deploy/web-green
curl http://web-green.internal/healthz            # smoke test
kubectl patch svc web -p '{"spec":{"selector":{"app":"web","color":"green"}}}'
# rollback = patch back to "blue"
    📌
    Other implementations: swap target groups on an AWS ALB, swap slots in Azure App Service, switch DNS weights, or use Argo Rollouts blueGreen strategy.

    🗄️ Expert: handling the database Expert

    Both colours share one database, so schema changes must work with old and new code. Use the expand / contract pattern:

    Expand: add new column (nullable)→Deploy code that writes both→Backfill data→Switch reads to new→Contract: drop old column later
    yaml# Argo Rollouts blue/green
strategy:
  blueGreen:
    activeService: web-active
    previewService: web-preview
    autoPromotionEnabled: false          # manual approval after tests
    scaleDownDelaySeconds: 600           # keep old version for fast rollback
    ⚠️
    Never ship a destructive migration (drop column, rename) in the same release as the code that needs it gone. Rollback would break.

    Module 04 · Deployment strategy

    Canary Rollouts

    Send a small share of real traffic to the new version first. If metrics look healthy, increase gradually; if not, stop and roll back with limited damage.

    🐤 The idea Basic

    Named after canaries in coal mines: a few users detect problems early, so most users never see them.

    1% traffic→Watch metrics→10%→Watch→50%→Watch→100%
    🎯
    Decision metrics: error rate, latency (p95/p99), saturation, plus a business metric such as checkout conversion.

    ⚖️ Strategy comparison Basic

    StrategyHowRiskCostRollback speed
    RecreateStop old, start newDowntimeLowSlow
    Rolling updateReplace pods graduallyMixed versions brieflyLowMinutes
    Blue/GreenTwo full environments, flipLow (tested first)High (2×)Instant
    CanaryGradual traffic shiftLowest exposureMediumFast
    A/B testDifferent versions to different user groups for learningExperiment-drivenMediumFast
    Shadow (mirror)Copy traffic to new version, ignore its responsesNone to usersMediumn/a

    📝 Examples: NGINX Ingress and Argo Rollouts Intermediate

    Simple canary with NGINX Ingress annotations (10% to the canary service):

    yamlmetadata:
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"

    Automated, step-by-step canary with Argo Rollouts:

    yamlapiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: {name: web}
spec:
  replicas: 5
  selector: {matchLabels: {app: web}}
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: {duration: 5m}
        - setWeight: 50
        - pause: {duration: 10m}
      # weights above 100% complete automatically
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - {name: web, image: myreg.example/web:2.0.0}

    🤖 Expert: automated analysis and rollback Expert

    Let metrics decide. Argo Rollouts AnalysisTemplates (or Flagger, Spinnaker/Kayenta) query Prometheus and abort on failure.

    yamlapiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: {name: success-rate}
spec:
  metrics:
  - name: success-rate
    interval: 1m
    failureLimit: 2
    successCondition: result[0] >= 0.99
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{app="web",code!~"5.."}[2m]))
          / sum(rate(http_requests_total{app="web"}[2m]))
    ✅
    Link to SLOs: abort the rollout if the canary burns error budget faster than a threshold. Use header-, cookie- or user-based routing (service mesh: Istio, Linkerd) to target employees or beta users first.

    Module 05 · Operating model

    GitOps Workflows

    GitOps makes Git the single source of truth for the desired state of your systems. An agent in the cluster pulls and applies that state continuously.

    🧭 Four principles Basic

    1. Declarative: the whole system is described in files.
    2. Versioned and immutable: stored in Git with full history.
    3. Pulled automatically: agents fetch approved changes.
    4. Continuously reconciled: agents correct any drift.
    📖
    Analogy: a thermostat. You set the target temperature (Git); the thermostat (agent) keeps turning heating on and off until the room matches.

    🔀 Push vs pull delivery Basic

    Push (traditional CI/CD)Pull (GitOps)
    Who deploysCI pipeline runs kubectl applyAgent inside cluster (Argo CD, Flux)
    Cluster credentialsStored in CI (risk)Stay inside the cluster
    DriftUndetected until next deployDetected and healed continuously
    RollbackRe-run pipelinegit revert
    AuditPipeline logsGit history
    Dev pushes app code→CI builds image→CI commits new tag to config repo→Argo CD / Flux detects change→Cluster updated

    🧠 Expert: scale, secrets and promotion Expert

    • Separate repos for app code and environment config; promote by PR from dev → staging → prod.
    • Secrets: Sealed Secrets, SOPS, or External Secrets Operator syncing from Vault/cloud secret managers. Never plain secrets in Git.
    • ApplicationSet generates apps per cluster/team; use sync waves for ordering.
    • Image automation: Argo CD Image Updater or Flux image controllers commit new tags.
    • Policy: admission control with Kyverno or OPA Gatekeeper; protect prod with required approvals and CODEOWNERS.
    • Emergency changes still go through Git, as a fast-tracked PR, so the record stays true.

    Module 06 · End to end

    A Complete Delivery Flow

    Real teams combine all four practices.

    🔗 Reference flow Intermediate

    1. Trunk-based: a developer merges a small PR to main with the new code behind a feature flag.
    2. CI builds, tests, scans and pushes an image tagged with the commit SHA.
    3. GitOps: CI opens a PR/commit in the config repo bumping the tag for staging, then prod.
    4. Argo CD syncs the change; Argo Rollouts performs a canary (10% → 50% → 100%) with automated metric analysis.
    5. Rollback is automatic on failed analysis, or a git revert of the config commit.
    6. Finally the flag is turned on gradually, then removed in a later cleanup commit.
    PracticeAnswers the question
    Trunk-based developmentHow do we merge safely and often?
    Feature flagsHow do we release without redeploying?
    Blue/Green or CanaryHow do we expose the new version safely?
    GitOpsHow do we keep clusters matching Git and roll back easily?

    ✅ Expert checklist Expert

    • Deploys are boring, frequent and reversible.
    • Automated rollback tied to SLO metrics.
    • Database changes are backward compatible (expand/contract).
    • Every flag has an owner and expiry.
    • Environment state is in Git, secrets are encrypted, drift is auto-corrected.
    • DORA metrics tracked and reviewed monthly.

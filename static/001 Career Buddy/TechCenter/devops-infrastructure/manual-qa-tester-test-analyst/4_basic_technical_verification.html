    Module 01 · Foundations

    Technical Verification Fundamentals

    How a web application is layered, what each layer proves, and which tool inspects which layer.

    🧠 Why manual testers need technical verification Basic

    A screen can look right while the data behind it is wrong. A "Saved successfully" message means nothing if the database has no row. Technical verification lets you see below the user interface and prove what really happened — and report defects precisely enough that developers can fix them quickly.

    🏧
    Analogy: an ATM receipt says "₹5,000 withdrawn". The bank statement (database) is the proof. A good tester checks both.
    Three tools, three layers: DevTools for the browser, Postman/Swagger for the API, SQL for the database.
    LayerQuestionTool
    UIWhat does the user see? Does the page behave?Browser DevTools — Elements, Console
    Network / APIWhat was sent and received? Status, payload, speed?DevTools Network tab, Postman, Swagger UI
    DatabaseWas data stored, updated, deleted correctly?SQL client (MySQL Workbench, DBeaver, pgAdmin, SSMS)

    🌐 How the web works — the minimum you need Basic

    1. You type a URL or click; the browser (client) builds an HTTP request.
    2. The server receives it, runs business logic and queries the database.
    3. The server sends back an HTTP response (status + headers + body, often JSON or HTML).
    4. The browser renders the response as the page.
    Client→HTTP request→Server / API→SQL query→Database

    Key vocabulary

    TermMeaning
    URLAddress of a resource: https://shop.test/api/orders/101
    HTTP / HTTPSProtocol for requests; HTTPS = encrypted
    Client / ServerAsker / answerer
    APIInterface letting programs talk to each other
    JSONText data format: {"id":101,"status":"PAID"}
    Cookie / Session / TokenHow the server remembers who you are
    Database / Table / RowOrganised storage of data

    🧪 What to verify where Basic

    Test action in UIUI checkAPI checkDB check
    Register userWelcome pagePOST /users → 201, id returnedRow in users, password hashed, created_at set
    Place orderConfirmation textPOST /orders → 201Row in orders, items in order_items, stock reduced
    Cancel orderStatus "Cancelled"PATCH status → 200status = 'CANCELLED', refund row created
    Delete accountLogged outDELETE /users/id → 204Row removed or marked inactive; related data handled
    🎯 Key takeaways
    • UI, API and database can each be wrong independently — check them all.
    • Know the request/response cycle; most defects live in it.
    • Use the right tool per layer: DevTools, Postman/Swagger, SQL.

    SQL for Database Verification

    From your first SELECT to JOINs, integrity checks, safe data changes and expert queries.

    🗄️ What is a database and SQL? Basic

    A relational database stores data in tables (like spreadsheets) made of rows (records) and columns (fields). SQL (Structured Query Language) is the language to ask questions of the data and change it.

    📒
    Analogy: Excel sheets that can be linked. "Orders" has a customer_id column that points to a row in "Customers" — that link is a foreign key.

    Practice schema used in this course

orders   (order_id PK, customer_id FK, order_date, status, total)
order_items(item_id PK, order_id FK, product_id FK, quantity, unit_price)

    ⚠️
    Safety first: run queries on the test database only. Use SELECT for verification. Never run UPDATE or DELETE without a WHERE clause and permission.

    🔎 SELECT basics Basic

    SQLSELECT * FROM orders;                                   -- every column, every row
SELECT order_id, status, total FROM orders;             -- chosen columns
SELECT DISTINCT status FROM orders;                     -- unique values only
SELECT * FROM orders WHERE status = 'PAID';             -- filter rows
SELECT * FROM orders WHERE total > 500 AND status = 'PAID';
SELECT * FROM orders ORDER BY order_date DESC;          -- newest first
SELECT * FROM orders ORDER BY total DESC LIMIT 5;       -- top 5 (MySQL/Postgres)
-- SQL Server uses: SELECT TOP 5 * FROM orders ORDER BY total DESC;

    WHERE operators

    OperatorExampleMeaning
    = <> > < >= <=total >= 1000Comparison
    AND / OR / NOTstatus='PAID' AND total>500Combine conditions
    INstatus IN ('NEW','PAID')Match a list
    BETWEENtotal BETWEEN 100 AND 500Inclusive range
    LIKEname LIKE 'A%'Pattern: % any chars, _ one char
    IS NULL / IS NOT NULLemail IS NULLMissing values — never use = NULL
    📝
    SQL keywords are not case-sensitive, but string values often are (depends on the database). Text goes in single quotes: 'PAID'.

    🧮 Aggregates, GROUP BY and HAVING Intermediate

    SQLSELECT COUNT(*) FROM orders;                               -- how many rows
SELECT COUNT(*) FROM orders WHERE status='PAID';
SELECT SUM(total) AS revenue FROM orders WHERE status='PAID';
SELECT AVG(total), MIN(total), MAX(total) FROM orders;

SELECT status, COUNT(*) AS cnt                             -- rows per status
FROM orders
GROUP BY status;

SELECT customer_id, SUM(total) AS spent                    -- big spenders only
FROM orders
GROUP BY customer_id
HAVING SUM(total) > 1000;

    WHERE filters rows before grouping; HAVING filters groups after.

    🔗 JOINs — combining tables Intermediate

    SQLSELECT o.order_id, c.name, o.total
FROM orders o
INNER JOIN customers c ON c.customer_id = o.customer_id;    -- only matching rows

SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id;        -- all customers, even with no orders

SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;                                   -- customers with NO orders

SELECT o.order_id, p.name, i.quantity, i.unit_price
FROM orders o
JOIN order_items i ON i.order_id = o.order_id
JOIN products p    ON p.product_id = i.product_id
WHERE o.order_id = 101;                                     -- full order detail

    ✏️ INSERT, UPDATE, DELETE and transactions Intermediate

    Testers sometimes prepare or reset test data. Do it carefully, only on test environments.

    SQLINSERT INTO customers (name,email,city) VALUES ('Test User','t1@test.com','Hyderabad');
UPDATE orders SET status='NEW' WHERE order_id = 104;      -- ALWAYS use WHERE
DELETE FROM customers WHERE email='t1@test.com';          -- ALWAYS use WHERE

-- Safe pattern: preview first
SELECT * FROM orders WHERE order_id = 104;                -- 1) see what will change
UPDATE orders SET status='NEW' WHERE order_id = 104;      -- 2) change
SELECT * FROM orders WHERE order_id = 104;                -- 3) confirm

BEGIN;                                                    -- transaction: can be undone
UPDATE products SET stock = 0 WHERE category='Toys';
ROLLBACK;                                                 -- undo (COMMIT would save)

    ACID in one line: a transaction is Atomic (all or nothing), Consistent, Isolated and Durable. Test cases: payment fails halfway → no half-written order.

    🚀 Expert SQL for QA Expert

    SQL-- Subquery: customers who spent more than the average order
SELECT name FROM customers
WHERE customer_id IN (SELECT customer_id FROM orders WHERE total > (SELECT AVG(total) FROM orders));

-- Latest order per customer (window function)
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) rn
  FROM orders o) t
WHERE rn = 1;

-- Find duplicates and keep one (preview!)
SELECT email, MIN(customer_id) keep_id, COUNT(*) FROM customers GROUP BY email HAVING COUNT(*)>1;

-- CASE expression for status buckets
SELECT order_id,
       CASE WHEN total >= 1000 THEN 'LARGE' WHEN total >= 100 THEN 'MEDIUM' ELSE 'SMALL' END AS size
FROM orders;

-- Reconciliation: orders paid but no payment record
SELECT o.order_id FROM orders o
LEFT JOIN payments p ON p.order_id=o.order_id
WHERE o.status='PAID' AND p.payment_id IS NULL;

-- Query plan (is a query slow?)
EXPLAIN SELECT * FROM orders WHERE customer_id = 1;

    Verification mindset

    • Constraints: test NOT NULL, UNIQUE, foreign-key and CHECK rules via the UI and confirm DB errors are handled gracefully.
    • Data types: rounding of decimals, time zones in timestamps, character encoding (emoji, Indian languages).
    • Soft delete: row stays with is_deleted = 1 — check UI hides it and reports exclude it.
    • Audit columns: created_at, updated_at, updated_by change correctly.
    • Migration testing: row counts and checksums before/after; sample rows compared field by field.

    🧱 Elements tab — inspecting the DOM Basic

    The DOM (Document Object Model) is the page's structure as the browser sees it. Click the select-element icon (Ctrl+Shift+C), click anything on the page and its HTML appears.

    What testers do here

    • Verify text, id, class, placeholder, maxlength, required, disabled attributes match the requirement.
    • Check input types: type="email", type="password" (is a password masked?).
    • Temporarily edit text or styles to reproduce a visual issue (changes vanish on refresh).
    • Inspect styles: colour, font-size, margins; compare with the design.
    • Check accessibility attributes: alt, aria-label, label-for links.
    • Test client-side validation bypass: remove disabled / maxlength and check the server still validates — a classic defect.
    HTML<input type="text" id="coupon" name="coupon" maxlength="10" placeholder="Enter coupon">
<button id="applyBtn" class="btn btn-primary" disabled>Apply</button>

    🏋️ DevTools practice Basic

    PracticeExercise 3.1 — Find the API behind a button

    On any shopping site, open Network → Fetch/XHR, click "Add to cart". Record: method, URL, status, request payload keys, response keys.

    ▶ Show solution

    Typical result: POST /api/cart/items, 200/201, payload {productId, quantity}, response includes cart with updated total. Verify that quantity in payload equals what you chose, and the total in response equals the total on screen.

    PracticeExercise 3.2 — Client-side validation bypass

    A form has maxlength="10" on "name". How do you test server-side validation?

    ▶ Show solution

    In Elements, delete the attribute (or use Postman) and send 200 characters. Expected: server returns 400 with a message (or trims safely). If it returns 500 or stores 200 chars → defect.

    PracticeExercise 3.3 — Interpret

    Request returned 403. User is logged in. What does it mean? Next step?

    ▶ Show solution

    The server knows who you are but you lack permission. Check the user's role: if this role should have access → defect; if not → expected, and the UI should have hidden the action.

    Module 04 · API layer

    API Testing with Postman & Swagger

    REST, HTTP, JSON, authentication, Postman collections and tests, Swagger, and expert chaining.

    🔌 What is an API? Basic

    An API (Application Programming Interface) lets one program ask another to do something. The web page, the mobile app and other systems all use the same API to talk to the backend.

    🍽️
    Analogy: a restaurant. You (client) give an order to the waiter (API); the kitchen (server/DB) prepares the food; the waiter brings it back. You never walk into the kitchen. Testing the API is talking to the waiter directly, without the menu (UI) in between.

    REST APIs use HTTP and treat things as resources with URLs (/users, /orders/101) and methods for actions.

    Why test APIs manually?

    • Earlier than the UI exists — shift-left.
    • Faster and more precise than clicking.
    • Test inputs the UI would block (negative, huge, malformed).
    • Find defects in the layer where they actually live.

    🔐 Authentication & authorisation Intermediate

    TypeHowTest
    Basic AuthUsername:password (Base64) in headerWrong/missing credentials → 401
    API keyKey in header or queryMissing / revoked key
    Bearer token (JWT)Authorization: Bearer <token>Expired token, tampered token, wrong audience
    OAuth 2.0Token from an auth server (client id/secret, scopes)Insufficient scope → 403
    Session cookieBrowser holds session idLogout invalidates session

    Authentication = who are you? (401). Authorisation = what may you do? (403). Always test: no token, expired token, token of another user, token with a lower role.

    📮 Postman — hands-on Basic

    Postman is a desktop/web app to build, send and organise API requests without code.

    New request→Choose method→Enter URL→Add headers/auth→Add body→Send→Inspect response

    Key concepts

    ConceptWhat it is

    VariablesReusable values: {{token}}, {{orderId}}
    Params / Headers / Body / Auth tabsWhere you build each part

    Your first tests

    Postman test// Tests tab
pm.test("Status is 201", () => pm.response.to.have.status(201));
pm.test("Response time < 800ms", () => pm.expect(pm.response.responseTime).to.be.below(800));
pm.test("Content-Type is JSON", () => pm.response.to.have.header("Content-Type", /json/));

const body = pm.response.json();
pm.test("Order has id and status NEW", () => {
  pm.expect(body.orderId).to.be.a("number");
  pm.expect(body.status).to.eql("NEW");
});
pm.environment.set("orderId", body.orderId);   // save for the next request
    💡
    Name requests as POST Create order – valid, POST Create order – missing customerId so the collection reads like a test suite.

    📘 Swagger / OpenAPI Basic

    OpenAPI is a standard way to describe an API (endpoints, parameters, responses). Swagger UI turns that description into an interactive web page where you can read and try each endpoint.

    1. Open the Swagger URL (often /swagger-ui or /docs).
    2. Click Authorize and paste a token if needed.
    3. Expand an endpoint → Try it out → fill parameters/body → Execute.
    4. Read the actual curl, URL, response code and body.
    OpenAPI (YAML)paths:
  /orders/{id}:
    get:
      summary: Get order by id
      parameters:
        - name: id
          in: path
          required: true
          schema: { type: integer }
      responses:
        "200": { description: OK }
        "404": { description: Order not found }

    Tester use: the spec is a requirement document — check every documented response code and field type; report mismatches between spec and real behaviour. Import the spec into Postman to auto-create a collection.

    🎯 What to test in an API Intermediate

    CategoryExamples (POST /orders)
    Happy pathValid body → 201, correct fields, DB row created
    Status codes404 for unknown id, 400 for bad body, 401/403 for auth issues
    Required fieldsRemove each mandatory field one at a time → 400 with clear message
    Data typesString in numeric field, null, array instead of object
    Boundariesquantity 0, 1, max, max+1, negative
    Business rulesDuplicate coupon, out-of-stock product, closed store
    SchemaField names, types, no extra/missing fields, date formats (ISO 8601)
    IdempotencySame PUT/DELETE twice; retry of POST creating duplicates?
    Pagination / filtering / sorting?page=2&limit=10, invalid page, sort order
    SecurityNo token, other user's data (IDOR), injection strings, sensitive data in response
    PerformanceResponse time, big payloads
    Error formatConsistent error JSON; no stack traces leaked

    Verify one business action through the UI, the API and the database.

    🧪 Capstone — verify "Place order" across UI, API and DB Expert

    Scenario: a customer buys 2 × product 1001 (₹600 each) with coupon MOVIE10 (10%, min ₹1,000).

    PracticeStep 1 — UI + DevTools

    What do you capture in DevTools?

    ▶ Show solution
    • Network: POST /api/orders — payload (productId, quantity=2, coupon), status 201, response with orderId and total.
    • Console: no red errors.
    • Elements: displayed total = 1,080.00 (1,200 − 10%).
    PracticeStep 2 — API with Postman

    Which extra checks?

    ▶ Show solution
    • GET /orders/{id} → same total and items.
    • Repeat POST with quantity 0, 99999, missing coupon, invalid coupon.
    • Call without token → 401; with other user's token → 403/404.
    • Replay POST twice → duplicate order created? (idempotency risk)
    PracticeStep 3 — SQL

    Write the queries.

    ▶ Show solution
    SELECT * FROM orders WHERE order_id = :id;                  -- total = 1080.00, status NEW/PAID
SELECT * FROM order_items WHERE order_id = :id;            -- product 1001, qty 2, unit_price 600
SELECT stock FROM products WHERE product_id=1001;          -- reduced by 2
SELECT * FROM coupon_usage WHERE order_id = :id;           -- one record for MOVIE10
SELECT order_id, COUNT(*) FROM orders GROUP BY order_id HAVING COUNT(*)>1;  -- no duplicates
    PracticeStep 4 — Write the bug

    Suppose the UI shows ₹1,080 but the DB has total = 1200 and no coupon_usage row. Draft the bug summary.

    ▶ Show solution

    Title: Order total in DB ignores coupon: UI shows 1,080.00, orders.total = 1200.00 (order 105). Evidence: UI screenshot, API response (total: 1200), SQL result, request payload. Severity: High — financial mismatch, wrong invoice. Hint for dev: UI calculates discount client-side; server does not apply it.

    Module 01 · Foundations

    Requirements Fundamentals

    What requirements are, the types you will meet, what makes them good — and why testers read them before a line of code exists.

    📋 What is a requirement? Basic

    A requirement is a statement of what a stakeholder needs the system to do, or a quality it must have. Requirements are the contract between the business, the developers and the testers. They are also the main test oracle — the source of truth for what "correct" means.

    🏠
    Analogy: an architect's blueprint. The builder builds from it; the inspector checks the finished house against it. If the blueprint says "door" but not where, both will argue later. Requirements analysis is reading the blueprint before the walls go up.

    Why testers analyse requirements

    🛡️
    Prevent defects
    A bug found in a document costs minutes; found in production costs days.
    🧩
    Find ambiguity
    Vague words become different behaviours in different heads.
    🧪
    Ensure testability
    If you cannot say what "pass" looks like, the requirement is untestable.
    🔗
    Enable traceability
    Every requirement should map to at least one test.

    🗂️ Types of requirements Basic

    TypeQuestion it answersExample
    Business requirementWhy does the organisation want this?Reduce cart abandonment by 10%.
    User / stakeholder requirementWhat does the user need to achieve?A shopper can save an item for later.
    Functional requirementWhat must the system do?System sends an OTP to the registered mobile on login.
    Non-functional requirement (NFR)How well must it do it?Search results appear within 2 seconds for 95% of requests.
    ConstraintWhat limits the solution?Must run on Android 10+; data stored in India.
    Business ruleWhich policy applies?Refund only within 7 days of delivery.

    NFR categories to remember

    PerformanceSecurityUsabilityAccessibilityReliabilityCompatibilityScalabilityMaintainabilityLocalisationCompliance

    📥 Where requirements come from Basic

    BRD / FRD / SRS documentsUser stories in JiraWireframes / Figma designsMeeting notesEmails & chatsExisting system behaviourRegulations & standardsSupport ticketsCompetitor products

    In Agile teams the main sources are user stories, acceptance criteria, design mock-ups and conversations. In traditional teams: the SRS (Software Requirements Specification).

    ✅ Qualities of a good requirement Basic

    QualityMeaningBadBetter
    Clear / unambiguousOne interpretation"The page should load quickly""Page loads in ≤ 2 s on 4G for 95% of requests"
    TestableYou can design a pass/fail check"User-friendly UI""A new user completes sign-up in ≤ 3 steps without help"
    CompleteNo missing cases"Accept payment""Accept UPI, card, wallet; show error on failure"
    ConsistentNo contradictionsPage A: max 5 items; Page B: max 10One agreed limit
    AtomicOne need per statement"Login with OTP and remember device and show history"Three separate requirements
    TraceableHas an ID and source—REQ-042 ← BR-007

    🔎 Static testing: reviewing requirements Intermediate

    Static testing examines work-products without running code. Reviewing requirements is the cheapest, earliest test you can do.

    Review typeFormalityTypical use
    Informal reviewLow — a colleague reads itQuick feedback
    WalkthroughAuthor leads the group through itKnowledge sharing
    Technical reviewExperts check technical correctnessDesign validation
    InspectionFormal roles, checklists, metricsHigh-risk documents

    Ambiguity word list — flag these on sight

    fastquicklyuser-friendlyeasyetc.and/oras appropriateshould (vs must)someseverallargeflexiblesecuresimilar toTBDnormallyusuallyif possibleminimalefficient
    🎯 Key takeaways
    • Requirements are the main test oracle.
    • Know functional vs non-functional vs business rules.
    • Good requirements are clear, testable, complete, consistent, atomic, traceable.
    • Reviewing requirements is the earliest and cheapest test.

    Module 02 · Agile requirements

    User Stories & Acceptance Criteria

    Read, question and improve stories using INVEST and a tester's checklist.

    📖 What is a user story? Basic

    A user story is a short description of a feature told from the user's perspective — a placeholder for a conversation, not a full specification.

    templateAs a  <type of user / role>
I want  <goal / capability>
So that <benefit / business value>

    Example:

    storyAs a registered shopper
I want to save items to a wishlist
So that I can buy them later without searching again

    The 3 Cs (Ron Jeffries)

    🗂️
    Card
    The short written story.
    💬
    Conversation
    Discussion that fills in the details.
    ✔️
    Confirmation
    Acceptance criteria that prove it is done.

    📏 INVEST — what makes a good story Basic

    LetterPrincipleTester's question
    IIndependentCan it be built and tested alone?
    NNegotiableIs detail still open for discussion?
    VValuableIs the benefit clear?
    EEstimableIs it clear enough to size?
    SSmallFits in one sprint?
    TTestableCan I write pass/fail checks?
    ⚠️
    A story failing Testable is a red flag. Raise it in refinement, not at the end of the sprint.

    🎯 Acceptance Criteria (AC) Basic

    Acceptance criteria are the conditions a story must meet to be accepted. They are the tester's starting point and the Definition of "Done" for that story.

    Two common formats

    📃 Rule-oriented (checklist)

    • Password must be 8–16 characters

    • Must contain 1 digit and 1 uppercase

    • Show inline error on invalid input

    • Strength meter updates live

    🎭 Scenario-oriented (Given-When-Then)

    • Given I am on Sign-up

    • When I enter "abc" as password

    • Then I see "Minimum 8 characters"

    • And the Register button is disabled

    Example — complete story with AC

    story + ACStory: As a shopper I want to apply a coupon so that I get a discount.

AC1: A valid coupon code reduces the cart total by its percentage.
AC2: An invalid or expired code shows "Coupon is not valid"; total unchanged.
AC3: Only one coupon can be applied per order.
AC4: Coupon MOVIE10 applies only if cart total >= 1000.
AC5: Code entry is case-insensitive; spaces are trimmed.
AC6: Discount is shown as a separate line on the order summary.

    🔬 Analysing a story: the tester's question list Intermediate

    Before writing any test, interrogate the story. Use this checklist:

    AreaQuestions
    WhoWhich roles/personas? Guest, logged-in, admin? Permissions?
    WhatExactly which actions? What are the inputs and outputs?
    DataValid ranges, formats, mandatory vs optional, max length, special characters?
    RulesWhich business rules apply? What are the exceptions?
    FlowMain path, alternate paths, error paths? What happens after success?
    StatesWhich statuses exist? Allowed transitions?
    MessagesWhat exact text for success and errors? Localised?
    NFRPerformance, security, accessibility, browsers, devices?
    IntegrationWhich APIs/emails/SMS/payments are involved?
    Out of scopeWhat is explicitly NOT included?

    Example: spotting gaps in AC2 above

    • What about a coupon that was valid yesterday but expired today at midnight (time zone)?
    • What if the cart changes after applying the coupon and total drops below 1000?
    • Is the discount applied before or after tax?
    • Can a coupon be used by the same user twice?

    These unanswered questions are requirement defects. Log them as questions to the Product Owner.

    🏋️ Practice Basic

    PracticeExercise 2.1 — Improve the story

    Rewrite and add AC: "The user should be able to login easily."

    ▶ Show solution

    Story: As a registered customer I want to log in with email and password so that I can see my orders.

    • AC1: Valid email + correct password → dashboard opens in ≤ 3 s.
    • AC2: Wrong password → "Invalid email or password" (no hint which one).
    • AC3: After 5 failed attempts the account is locked for 15 minutes.
    • AC4: "Show password" toggle works.
    • AC5: Email is case-insensitive; password is case-sensitive.
    • AC6: "Forgot password" link visible.
    PracticeExercise 2.2 — Find the ambiguities

    Story: "As an admin I want to export reports quickly so that I can share them." List at least 6 questions.

    ▶ Show solution
    • Which reports? All? Date range?
    • What formats — CSV, PDF, Excel?
    • How fast is "quickly" — max rows and seconds?
    • Who can export — only admin or managers too?
    • Is exported data masked (PII)?
    • What happens with 1 million rows — async email link?
    • Time zone of dates in the export?

    Module 03 · Specification by example

    BDD & Gherkin

    Write Given-When-Then scenarios the whole team can read and test from.

    🥒 What is BDD? Basic

    Behaviour-Driven Development (BDD) is a collaboration practice where business, developers and testers agree on behaviour using concrete examples written in plain language. The examples become specification, acceptance tests and living documentation.

    🤝
    Analogy: instead of arguing over the sentence "support discounts", the team says "if I buy ₹1,200 of goods with coupon MOVIE10, what do I pay?" — "₹1,080". Examples end arguments.

    The Three Amigos

    💼
    Business (Product Owner)
    Knows what is needed and why.
    👨‍💻
    Developer
    Knows how it can be built.
    🧪
    Tester
    Asks what if — finds edge cases and gaps.

    They meet before development to discuss each story and write examples. Testers shape the examples.

    🥬 Gherkin syntax Basic

    Gherkin is the plain-text language used to write BDD scenarios in .feature files.

    gherkinFeature: Coupon on cart
  As a shopper
  I want to apply a coupon
  So that I pay less

  Scenario: Valid coupon reduces total
    Given my cart total is 1200 rupees
    When I apply coupon "MOVIE10"
    Then the total becomes 1080 rupees
    And the order summary shows a discount of 120 rupees

  Scenario: Invalid coupon is rejected
    Given my cart total is 1200 rupees
    When I apply coupon "FAKE99"
    Then I see the message "Coupon is not valid"
    And the total stays 1200 rupees
    KeywordPurpose
    FeatureNames the capability; free-text description beneath
    ScenarioOne concrete example of behaviour
    GivenContext / precondition — the starting state
    WhenThe action or event (usually ONE)
    ThenExpected observable outcome
    And / ButContinue the previous step type
    BackgroundSteps shared by all scenarios in the file
    Scenario Outline + ExamplesOne template run with many data rows
    @tagsLabel scenarios: @smoke @regression @wip
    #Comment line

    🧬 Scenario Outline & Background Intermediate

    gherkinFeature: Age validation on registration

  Background:
    Given I am on the registration page

  Scenario Outline: Age boundaries
    When I enter age "<age>"
    And I click Register
    Then I see "<result>"

    Examples:
      | age | result                    |
      | 17  | You must be 18 or older   |
      | 18  | Registration successful   |
      | 60  | Registration successful   |
      | 61  | Age above allowed limit   |
      | abc | Enter a valid number      |

    One outline = five tests. This is exactly where EP and BVA from the Test Design course plug in: the Examples table holds your boundary values.

    ✍️ Writing good scenarios Intermediate

    ❌ Imperative (too detailed)

    • Given I open Chrome

    • And I type www.shop.com in the address bar

    • When I click the field with id "coupon"

    • And I type "MOVIE10" and press Tab…

    • Breaks whenever UI changes

    ✅ Declarative (behaviour)

    • Given my cart total is 1200 rupees

    • When I apply coupon "MOVIE10"

    • Then the total becomes 1080 rupees

    • Readable by business

    • Stable when UI changes

    Rules of thumb

    • One scenario = one behaviour. Title says what, steps show how it is proven.
    • Use business language, not button names or IDs.
    • Single When — multiple Whens mean multiple behaviours.
    • Then must be observable — a message, a total, a status — not "system works".
    • Keep it short — 3–7 steps.
    • Use concrete data — "1200 rupees", not "a big amount".

    Anti-patterns

    Anti-patternWhy bad
    Scenario as a UI scriptBrittle, unreadable
    Many Given/When/Then chains in one scenarioTests several behaviours; unclear failures
    Vague outcome ("Then it works")Not testable
    Duplicating scenarios for each data rowUse Scenario Outline
    Technical jargon (SQL, selectors)Business cannot review
    Written by testers alone, after codingLoses the BDD collaboration value

    🔧 BDD tooling overview Intermediate

    Gherkin can be just documentation for manual testers, or executable via a framework:

    ToolLanguage
    CucumberJava, JavaScript, Ruby
    SpecFlow / Reqnroll.NET
    BehavePython
    BehatPHP

    As a manual tester you may write and review Gherkin and execute scenarios manually. Developers/automation engineers bind each step to code ("step definitions"). A well-written scenario can later be automated without rewriting.

    Manual testing with Gherkin in Jira / Azure DevOps

    • Store scenarios in the story's AC or as test cases (Xray, Zephyr, Azure Test Plans).
    • Tag with @smoke, @regression to build test suites.
    • Link each scenario back to the story ID for traceability.

    Module 04 · Requirements → tests

    Writing Test Cases from Requirements

    Turn stories and AC into traceable, high-quality test cases using design techniques.

    🛠️ From requirement to test case: the process Basic

    Read & understand→Ask questions→Identify test conditions→Apply design techniques→Write test cases→Review & trace
    TermMeaningExample
    Test condition"Something to verify" — derived from requirementCoupon below minimum total is rejected
    Test caseSpecific inputs + steps + expected result for a conditionTotal 999.99, apply MOVIE10 → message shown
    Test scenarioHigh-level end-to-end ideaApply a coupon and complete the purchase
    Test suiteCollection of test cases for a purposeCheckout regression suite

    🧾 Worked example: one story → many tests Intermediate

    Story: As a user I can reset my password via an emailed link. AC: link valid 30 minutes; new password 8–16 chars with one digit; old password cannot be reused; link works once.

    Step 1 — Test conditions

    • Request reset with registered / unregistered email
    • Link validity: before, at and after 30 min
    • New-password rules (length, digit)
    • Old password reuse
    • Link single-use
    • Mail delivery content

    Step 2 — Test cases (techniques applied)

    IDTitleSteps / dataExpectedTechnique
    TC01Reset with registered emailEnter anita@example.com → Submit"Reset link sent"; email receivedMain flow
    TC02Unregistered emailEnter nouser@x.comSame neutral message (no user enumeration)Negative / security
    TC03Link used at 29:59Click link at 29 min 59 sReset page opensBVA
    TC04Link used at 30:01Click at 30 min 01 s"Link expired"BVA
    TC05Password 7 chars"Abcde1x" → SaveRejected: min 8BVA
    TC06Password 8 chars"Abcdef12"AcceptedBVA
    TC07Password 17 chars17-char valid stringRejected: max 16BVA
    TC08No digit"Abcdefgh"Rejected: digit requiredEP
    TC09Old password reusedEnter previous passwordRejected: cannot reuseBusiness rule
    TC10Link reuseOpen used link again"Link already used"State
    TC11Login with new passwordLogin after resetSuccess; old password failsEnd-to-end

    📝 Writing great test cases Intermediate

    1️⃣
    One purpose
    A test case verifies one thing. If it fails you know why.
    🧍
    Independent
    Does not depend on another case having run first.
    🔢
    Exact data
    "Enter 17" not "enter a small number".
    👁️
    Observable result
    Specify what you will see/check — text, status, DB value.
    ♻️
    Repeatable
    Anyone gets the same result.
    🔗
    Traceable
    Linked to requirement ID.

    Positive vs negative vs edge

    KindGoalExample
    PositiveSystem works with valid inputValid coupon applied
    NegativeSystem handles invalid input gracefullyExpired coupon message
    Edge / boundaryLimits behave correctlyTotal exactly 1000.00
    Non-functionalQuality attributesPage loads ≤ 2 s; keyboard-only navigation

    Template

    test caseID:           TC_CART_021          Requirement: REQ-CART-07 / Story ST-512
Title:        Valid coupon reduces cart total
Priority:     High                 Type: Functional / Positive
Preconditions: User logged in; cart total = 1200; coupon MOVIE10 active
Test data:    Coupon = MOVIE10
Steps:
  1. Open Cart
  2. Enter MOVIE10 in coupon field
  3. Click Apply
Expected:     Total shows 1080; discount line 120; message "Coupon applied"
Postcondition: Coupon marked used once for this order
    ⚠️
    Avoid: "Check that the page works", "Verify login", "Test with valid and invalid data" — these are conditions, not test cases.

    📦 Test data & priorities Intermediate

    Test data

    • Create specific accounts per role and state (new, active, locked, premium).
    • Mask production data — never use real customer PII.
    • Reset data between runs where tests change it.
    • Keep boundary and special-character data sets ready.

    Prioritising

    PriorityMeaningRun when
    P1 / HighCore money/safety/login flowsEvery build (smoke)
    P2 / MediumImportant featuresRegression cycle
    P3 / LowCosmetic, rare pathsIf time permits

    🔗 Requirements Traceability Matrix (RTM) Intermediate

    An RTM maps requirements ⇄ test cases ⇄ defects. It proves coverage and shows the impact of change.

    Req IDRequirementTest casesStatusDefects
    REQ-01Apply valid couponTC_CART_021, 022Passed—
    REQ-02Reject invalid couponTC_CART_023, 024FailedBUG-310
    REQ-03One coupon per orderTC_CART_025Not run—
    REQ-04Min total for MOVIE10— noneGap!—

    Forward traceability: requirement → tests (is everything tested?). Backward: test → requirement (is every test needed?). Coverage = requirements with ≥ 1 test ÷ total requirements.

    🏋️ Practice Basic

    PracticeExercise 4.1 — Write test cases

    Story: user can upload a profile picture (JPG/PNG, max 2 MB). Write at least 8 test cases.

    ▶ Show solution
    1. Upload JPG 1 MB → success
    2. Upload PNG 1 MB → success
    3. Upload exactly 2 MB → success (boundary)
    4. Upload 2.01 MB → error "Max 2 MB"
    5. Upload GIF → error "Only JPG/PNG"
    6. Upload .exe renamed to .jpg → rejected
    7. Upload 0-byte file → error
    8. Cancel the file dialog → no change
    9. Replace existing picture → new one shown
    PracticeExercise 4.2 — Build a mini RTM

    REQ-1 search by name, REQ-2 filter by price, REQ-3 sort by rating. You have tests: TC1 (search), TC2 (search empty), TC3 (filter). What gap exists?

    ▶ Show solution

    REQ-3 has no test — a coverage gap (66%). Write sort tests: ascending/descending, ties, no ratings, sort + filter together.

    Module 05 · Planning

    Test Planning & Strategy

    Scope, approach, risk, entry/exit criteria, estimation and reporting.

    🗺️ Test plan vs test strategy Basic

    Test StrategyTest Plan
    ScopeOrganisation / product wideOne project / release / sprint
    ChangesRarelyPer release
    Answers"How do we test in general?""What, who, when, how for THIS release?"
    OwnerQA Manager / ArchitectTest Lead / Analyst

    A test plan is the document that explains what will be tested, how, by whom, when and with which risks. In Agile it may be a one-page plan per sprint or release.

    🧱 Parts of a test plan (IEEE 829 style) Intermediate

    SectionWhat to write
    1. Introduction / ObjectivesPurpose of testing this release
    2. Scope — InFeatures and platforms to be tested
    3. Scope — OutWhat will NOT be tested, and why
    4. Test approachLevels, types, techniques, manual vs automation, exploratory
    5. Entry criteriaWhen testing may start (build deployed, smoke passed, data ready)
    6. Exit criteriaWhen it may stop (100% P1 passed, no open Critical/High, 95% executed)
    7. Test environmentURLs, devices, browsers, DB, accounts, third-party stubs
    8. Test dataWhat data, how created, how protected
    9. Roles & responsibilitiesWho does what
    10. Schedule & estimationDates, effort, milestones
    11. Risks & mitigationLate builds, unstable env, unclear requirements…
    12. DeliverablesTest cases, bug reports, summary report, RTM
    13. MetricsExecution %, pass %, defect density, coverage
    14. Suspension / resumption criteriaWhen to pause (blocker bugs) and resume

    ⚖️ Risk-based testing Intermediate

    You cannot test everything, so test what matters most first. Risk = Likelihood × Impact.

    FeatureLikelihood (1–5)Impact (1–5)Risk scoreTest depth
    Payment4 (new gateway)520Deep: all techniques + exploratory
    Login2510Standard + security
    Wishlist326Light
    Footer links111Smoke only

    What raises likelihood?

    • New or complex code, many integrations
    • Changed late in the sprint
    • History of defects
    • New team or unclear requirements

    What raises impact?

    • Money, legal, safety, privacy
    • Number of users affected
    • No workaround, brand damage

    🚪 Entry & exit criteria with examples Intermediate

    🚪 Entry criteria

    • Requirements/AC reviewed

    • Build deployed to QA

    • Smoke test passed

    • Test data & accounts ready

    • Test cases reviewed

    🏁 Exit criteria

    • 100% of P1 and ≥ 90% of P2 executed

    • 0 open Critical / High defects

    • Remaining defects accepted by PO

    • RTM coverage 100%

    • Summary report signed off

    ⏱️ Estimation basics Intermediate

    MethodHow
    Work BreakdownList tasks (design, execute, retest, regression) and add time to each
    Three-point(Optimistic + 4×Likely + Pessimistic) ÷ 6
    Past dataUse previous sprint/release effort for similar stories
    Planning poker (Agile)Team votes story points including testing effort

    Example three-point: O = 2 days, M = 4, P = 12 → (2 + 16 + 12) ÷ 6 = 5 days. Always add time for retesting and regression — fixes come back.

    📊 Test execution tracking & the summary report Expert

    Daily status snapshot

    MetricValue
    Planned test cases200

    Passed128 (80% of executed)

    Test Summary Report contents

    • Scope tested and not tested
    • Execution & pass/fail statistics, RTM coverage

    Module 06 · Advanced

    Expert Requirements Analysis

    Model requirements, test NFRs, measure coverage and embed quality in Agile.

    🧠 Expert: deep requirement analysis techniques Expert

    1. Decompose and model

    • Draw flowcharts, state diagrams, data-flow from text. Gaps show up as missing arrows.
    • Build decision tables for every "if / else" paragraph.
    • Create a glossary — same word, same meaning everywhere.

    2. Check each requirement against a test-readiness list

    CheckQuestion
    InputsAll inputs, types, ranges and mandatory/optional defined?
    OutputsAll outputs and messages defined?
    RulesCalculation formulas, rounding, precedence?
    ErrorsEvery failure path and message?
    StatesInitial, final, illegal states?
    PermissionsWho can/can't do it?
    Data lifecycleCreate/Update/Delete/Archive and audit?
    DependenciesWhich other features/systems are affected?
    NFRPerformance, security, accessibility, compatibility numbers?

    3. Impact analysis for changes

    When a requirement changes, use the RTM to find all linked tests and affected modules; update, add or retire tests; plan regression for neighbours.

    🛡️ Testing non-functional requirements Expert

    NFRTurn it into a testable statementManual checks
    Performance95% of searches ≤ 2 s with 500 usersStopwatch / DevTools Network timing; hand over to performance tools
    SecurityPasswords stored hashed; session expires in 15 minTest access without login, role escalation, error messages leaking info, HTTPS
    Usability90% of new users finish checkout without helpWalk-throughs, label clarity, error text
    AccessibilityWCAG 2.1 AAKeyboard-only navigation, screen reader basics, colour contrast, alt text
    CompatibilityLatest 2 versions of Chrome/Firefox/Safari/Edge; Android 10+Browser/device matrix
    LocalisationHindi, Telugu, EnglishText expansion, date/number formats, RTL

    If an NFR has no number, ask for one. "Fast" is not testable; "≤ 2 s" is.

    🎯 Coverage models Expert

    CoverageMeasuresFormula
    Requirement coverageRequirements with testsCovered ÷ Total
    AC coverageAcceptance criteria with ≥ 1 scenarioCovered AC ÷ Total AC
    Technique coveragePartitions / boundaries / transitions testedTested ÷ Identified
    Risk coverageHigh-risk items testedTested high-risk ÷ All high-risk
    Execution coveragePlanned tests runExecuted ÷ Planned
    ⚠️
    100% requirement coverage ≠ no defects. It means every requirement has at least one test, not that every behaviour is verified. Combine with risk and exploratory testing.

    🔄 Agile practice: quality in the sprint Expert

    Backlog refinement→Sprint planning→Three Amigos→Develop & test in parallel→Demo / review→Retrospective
    • Refinement: challenge stories against INVEST; add examples and AC.
    • Definition of Ready: story has AC, designs, test data, dependencies clear.
    • Definition of Done: code reviewed, tests written/run, no open High defects, docs updated.
    • Shift-left: prepare tests from AC while the developer codes; test each increment immediately.
    • Living documentation: scenarios are updated whenever behaviour changes so they remain trusted.
    🎯 Key takeaways
    • Model requirements (flows, states, tables) to find gaps.
    • Convert every NFR into a measurable statement.
    • Coverage numbers must be read with risk, not alone.
    • In Agile, testers influence quality at refinement, not after development.

    🏋️ Practice Expert

    PracticeExercise 6.1 — Analyse a vague requirement

    "The system must send timely notifications to users about their orders." Produce 8 questions and 5 testable restatements.

    ▶ Show solution

    Questions: which events? Channels (email/SMS/push)? How soon is "timely"? Opt-out? Retry on failure? Languages? Quiet hours? Duplicate prevention?

    Restated: (1) On status change to Shipped an SMS is sent within 60 s. (2) Email contains order ID and tracking link. (3) Users who opted out receive none. (4) Failure retried 3 times at 5-min intervals. (5) No duplicate for the same event.

    Module 07 · Hands-on

    A capstone: take one story from questions to Gherkin, test cases and a plan.

    🧪 Capstone — from story to test plan Expert

    Story: As a library member I want to borrow books so that I can read at home.

    AC: (1) Max 3 books at a time. (2) Loan period 14 days. (3) Fine ₹2/day after due date; fine cap ₹100. (4) A member with fine > ₹50 cannot borrow. (5) A reserved book cannot be borrowed by others. (6) Reference books cannot be borrowed.

    PracticeTask A — Questions for the Product Owner

    List at least 6 clarifications.

    ▶ Show solution
    • Does the 14-day loan include the borrow day?
    • Are weekends/holidays counted for fines?
    • Can a loan be renewed? How many times?
    • Is the "fine > 50" check strictly greater or ≥ 50?
    • How long is a reservation held?
    • What message for each rejection?
    • Do different member types (student, staff) have different limits?
    PracticeTask B — Gherkin

    Write 3 scenarios incl. one Outline for the 3-book limit.

    ▶ Show solution
    Scenario Outline: Borrowing limit
  Given I currently hold <held> books
  When I try to borrow 1 more book
  Then the result is "<result>"
  Examples:
    | held | result                       |
    | 0    | Borrowed                     |
    | 2    | Borrowed                     |
    | 3    | Limit of 3 books reached     |

Scenario: Fine blocks borrowing
  Given I have an unpaid fine of 51 rupees
  When I try to borrow a book
  Then I see "Clear your fine first"

Scenario: Reference book
  When I try to borrow a reference book
  Then I see "Reference books cannot be borrowed"
    PracticeTask C — Test cases with techniques

    List 10 tests using BVA/EP/decision table.

    ▶ Show solution
    1. Borrow with 2 held → success (BVA 3-limit)
    2. Borrow with 3 held → rejected
    3. Return on day 14 → no fine; day 15 → ₹2
    4. Fine after 50 days → ₹100 (cap); 51 days → ₹100
    5. Fine ₹50 → can borrow; ₹50.01 → blocked (clarify)
    6. Reserved by another member → rejected
    7. Reserved by me → allowed
    8. Reference book → rejected
    9. Two members borrow the last copy simultaneously
    10. Renewal after due date
    PracticeTask D — Test plan snapshot

    Write scope, 3 risks, entry, exit.

    ▶ Show solution

    In: borrow, return, fine, reservation rules. Out: member registration. Risks: date/time-zone calculation; concurrency on last copy; unclear renewal rules. Entry: AC clarified, test data (members with 0–3 books, fines 0/50/51). Exit: all P1 pass, no open High, AC coverage 100%.

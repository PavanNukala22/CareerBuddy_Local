    Module 01 · Foundations

    Defect Fundamentals

    What a defect is, how it lives and dies in a workflow, and why teams track them formally.

    🐞 What is a defect? Basic

    A defect (bug, fault, issue) is a flaw in a product — in code, configuration, requirements or design — that can cause the product to behave differently from what is expected. When the defect is exercised you see a failure.

    🏥
    Analogy: a hospital chart. The patient (software) shows symptoms (failure). The doctor (tester) writes clear notes — symptoms, when they started, what was tried — and passes them to the specialist (developer). A defect report is that chart. Bad notes = wrong or delayed treatment.
    TermMeaning
    Error / mistakeHuman slip
    Defect / Bug / FaultFlaw in an artefact
    FailureObservable wrong behaviour
    IncidentAny unexpected event requiring investigation — may or may not be a defect
    Enhancement / Change requestNew behaviour not in original requirements — not a defect

    Why do defects happen? (root-cause categories)

    Unclear requirementsCoding mistakeDesign flawMissing validationIntegration mismatchEnvironment / configurationData issueThird-party changeTime pressureRegression from another change

    ♻️ The defect lifecycle Basic

    Every defect travels through statuses until it is resolved. Names differ per team, the idea is constant.

    A typical defect workflow with the reopen and reject loops.
    StatusMeaningWho moves it
    New / OpenReported, not yet reviewedTester
    AssignedOwner chosenLead / triage
    In ProgressDeveloper investigating/fixingDeveloper
    Fixed / ResolvedFix delivered to a buildDeveloper
    Ready for retestFix deployed in test environmentDeveloper / build system
    Verified → ClosedTester confirmed the fixTester
    ReopenedFix did not work or bug returnedTester
    Rejected / Not a bugWorks as designed, cannot reproduce, invalidDeveloper / triage
    DuplicateSame as an existing defectTriage
    Deferred / Won't fixValid, but postponed or acceptedProduct Owner

    🧱 Why track defects formally? Basic

    📚
    Single source of truth
    Everyone sees the same status; nothing lost in chat.
    🔁
    Reproduce & fix
    Developers get what they need to act.
    📈
    Measure quality
    Trends, density and leakage guide decisions.
    🧾
    Audit & learning
    History shows what went wrong and how it was fixed.

    Defect vs failure vs "works as designed"

    • Defect: behaviour contradicts the requirement or reasonable expectation.
    • Works as designed (WAD): behaviour matches the requirement but surprises the user → raise it as an improvement/question, not a defect.
    • Requirement defect: the requirement itself is missing or wrong — still a defect, found early.

    🔦 Types of defects Basic

    TypeExample
    FunctionalCoupon applies twice
    UI / VisualButton overlaps text on mobile
    UsabilityError message does not explain what to fix
    PerformanceReport takes 40 s
    SecurityOrder of another user visible by changing ID in URL
    CompatibilityLayout broken in Safari
    DataTotal rounding wrong by 0.01
    IntegrationEmail not sent after payment
    DocumentationHelp page shows old screenshot
    🎯 Key takeaways
    • A defect is a flaw; a failure is the symptom you see.
    • Statuses show where a defect is in its life.
    • Track every defect in one tool for visibility and learning.
    • Separate defects from change requests and "works as designed".

    Writing Clear, Reproducible Bug Reports

    Anatomy of a perfect report, evidence, isolation, severity vs priority — with good-vs-bad examples.

    🧬 Anatomy of a great bug report Basic

    A great report lets a developer reproduce, understand and fix the problem without asking you a single question.

    FieldWhat to writeTip
    Title / SummaryWhat is wrong, where, and under what condition"Coupon MOVIE10 applied twice on page refresh — total becomes negative"
    EnvironmentBuild/version, URL, OS, browser/device, user role"QA env, build 2.4.1-rc3, Chrome 126, Windows 11"
    PreconditionsState needed before step 1"Logged in as premium user; cart = ₹1,200"
    Steps to reproduceNumbered, exact, minimalStart from a known point; one action per step
    Test dataExact inputs, accounts, IDsCoupon: MOVIE10
    Expected resultWhat should happen + reference"Total ₹1,080 (AC-3)"
    Actual resultWhat really happened"Total ₹-120"
    FrequencyAlways / intermittent (3 of 5)Intermittent bugs: note conditions
    Severity & PriorityImpact and urgencySee next tab
    EvidenceScreenshot, video, HAR, logs, console errorsAnnotate; hide personal data
    LinksRequirement, test case, related bugsTraceability

    ⚖️ Good vs bad: a live comparison Basic

    ❌ Poor report

    Title: Coupon not working

    Description: I tried applying coupon but it is wrong. Please check.

    No steps, no data, no screenshot, no environment.

    Developer reply: "Cannot reproduce. Which coupon? Which browser?" → 2 days lost.

    ✅ Strong report

    Title: Applying MOVIE10 twice makes cart total negative (₹-120)

    Env: QA, build 2.4.1, Chrome 126 / Win 11

    Steps: 1 Add item ₹1,200. 2 Apply MOVIE10 → ₹1,080. 3 Apply MOVIE10 again.

    Expected: 2nd attempt rejected (AC-3). Actual: total ₹-120.

    Video + console log attached. Reproducible 5/5.

    Writing the steps

    repro steps1. Log in as user qa_premium@test.com / password in Vault
2. Open https://qa.shop.test/products/1001
3. Click "Add to cart"  (price shown: 1,200.00)
4. Click Cart icon (top-right)
5. Enter MOVIE10 in "Coupon" field, click Apply   -> total 1,080.00 (correct)
6. Click Apply again without changing the field
Expected: message "Only one coupon allowed"; total remains 1,080.00
Actual:   total changes to -120.00
    💡
    Number the steps, keep them atomic, include the actual data. Re-run your own steps once from a clean state before submitting.

    🔬 Reproduce, isolate, minimise Intermediate

    Reproduce→Find minimal steps→Vary one factor→Identify scope→Collect evidence→Write report

    Isolation questions

    • Does it happen on other browsers / devices / users / roles?
    • Does it happen with other data (different product, amount)?
    • Is it new (regression)? Check the previous build.
    • Does it depend on timing, network speed or order of actions?
    • Is the UI wrong, or is the API/DB wrong? (see Technical Verification course)

    Intermittent defects

    • Record frequency ("4 out of 10 runs") and conditions (time, data, load).
    • Capture video, network HAR file, console log, timestamps and user ID so developers can search server logs.
    • Never close it as "cannot reproduce" — mark intermittent and keep evidence.

    📸 Evidence that helps Intermediate

    EvidenceUse forTool
    Screenshot (annotated)Visual and message defectsOS snipping tool, Lightshot, Jira capture
    Screen recording / GIFFlows, timing, animationsLoom, OBS, built-in recorder
    Console errorsJavaScript failuresBrowser DevTools → Console
    HAR file / network callAPI errors, slow callsDevTools → Network → Export HAR
    Request/response bodyWrong data from APIPostman / DevTools
    Logs / correlation IDBackend errorsAsk dev/DevOps; note timestamp
    DB screenshot / queryData mismatchesSQL client
    ⚠️
    Remove passwords, tokens, card numbers and personal data from screenshots and HAR files before attaching them.

    🎚️ Severity vs Priority Intermediate

    💥 Severity

    How badly the defect affects the system / user. Usually set by the tester.

    ⏰ Priority

    How soon it must be fixed from a business view. Usually set by Product Owner / Lead.

    SeverityDefinitionExample
    CriticalSystem down, data loss, security breach, no workaroundPayment charged but no order created
    HighMajor feature broken; workaround difficultCannot apply any coupon
    MediumFeature partly impaired; workaround existsSort by price ignores decimals
    LowMinor / cosmeticMisaligned icon by 2 px

    Priority × Severity examples

    CombinationExample
    High severity + High priorityCheckout crashes for all users
    High severity + Low priorityCrash in a rarely used admin report used once a year
    Low severity + High priorityCompany name misspelled on home page before launch
    Low severity + Low priorityTooltip misaligned 1 px on an old browser

    (a) Typo "Recieve" on About page. (b) App crashes on launch for Android 14 users (20% of users). (c) Invoice shows tax 18% instead of 5% for one product. (d) Footer link opens a blank page on IE11 (0.1% of users).

    • (a) Low severity, Low priority (High if brand-sensitive launch page)
    • (b) Critical / High
    • (c) High (or Critical – legal/financial) / High
    • (d) Low / Low

    🟦 Jira — in depth Basic

    Core ideas

    • Issue types: Epic, Story, Task, Bug, Sub-task.
    • Project contains issues; board (Scrum/Kanban) visualises workflow columns.
    • Workflow: statuses and allowed transitions (e.g. To Do → In Progress → In Review → Done).
    • Fields: Summary, Description, Priority, Assignee, Reporter, Labels, Components, Affects Version, Fix Version, Environment, Attachments, Linked issues.

    Creating a bug in Jira — step by step

    Create→Project + Issue type = Bug→Summary→Description (template)→Priority, Components, Versions→Attach evidence→Assign / Create

    JQL — Jira Query Language

    JQLproject = SHOP AND issuetype = Bug AND status != Done        -- all open bugs
project = SHOP AND priority in (Highest, High) AND resolution = Unresolved
assignee = currentUser() AND status = "In Progress"
created >= -7d AND reporter = currentUser() ORDER BY created DESC
issuetype = Bug AND fixVersion = "2.4.1" AND status = Done          -- fixed in release
labels = regression AND component = Checkout
text ~ "coupon" AND issuetype = Bug                                   -- search text

    WIQL examples

    WIQLSELECT [System.Id],[System.Title],[System.State]
FROM WorkItems
WHERE [System.TeamProject] = @project
  AND [System.WorkItemType] = 'Bug'
  AND [System.State] <> 'Closed'
  AND [Microsoft.VSTS.Common.Severity] = '1 - Critical'
ORDER BY [Microsoft.VSTS.Common.Priority] ASC

    Module 04 · Management

    Triage, Retest & Metrics

    Run triage, work with developers, verify fixes and measure quality responsibly.

    🧑‍⚖️ Defect triage Intermediate

    Triage is the regular meeting (or process) where new defects are reviewed, validated, prioritised and assigned.

    Validate (real? reproducible?)→Check duplicates→Set severity/priority→Assign owner & target build→Decide: fix / defer / reject

    Who attends

    QA lead/analyst, development lead, product owner (and sometimes support). The tester explains impact; the developer estimates effort; the PO decides business priority.

    Triage decisions

    DecisionWhen
    Fix nowHigh business impact or blocking release
    Fix in next release / DeferLow impact, workaround exists
    Reject – works as designedMatches approved requirement (raise change request if user need is real)
    Reject – cannot reproduceNeeds more info; return with questions
    DuplicateLink to the original and close
    Need infoReporter must supply data or evidence

    🤝 Working with developers Intermediate

    • Be factual: "Total shows -120; expected 1,080" — never "you broke it".
    • Offer help: sit together (pair debugging), share the session, give a script or data.
    • Respond fast to questions on your bugs; stale bugs rot.
    • Disagree with evidence: cite the requirement, screenshot, API response, not opinion.
    • Close the loop: retest promptly and comment the build and result.
    💬
    Phrasing: "Here's a 20-second video and the failing request. Is this expected after AC-3? If yes I'll update the test; if not, it looks like a regression from build 2.4.0."

    🔁 Retest, regression & verification Intermediate

    ActivityPurposeScope
    Confirmation (re-test)Check the specific defect is fixedThe exact failing steps
    Regression testCheck the fix broke nothing elseRelated and high-risk areas
    Smoke testIs the build stable enough to test?Critical paths

    Verification checklist

    • Run the original steps on the fixed build in the same environment.
    • Test neighbouring scenarios: other data, roles, browsers.
    • Check data layer if the bug affected data (DB values).
    • Add or update a regression test case.
    • Comment: build number, result, evidence. Close — or reopen with new evidence.

    📈 Defect metrics Intermediate

    MetricFormula / meaningUsed for
    Defect densityDefects ÷ size (KLOC, story points, function points)Compare module quality
    Defect leakageDefects found in production ÷ (found in test + production)Test effectiveness
    Defect Removal Efficiency (DRE)Defects found before release ÷ total defectsQuality of process
    Defect ageToday − date reportedBacklog health
    Reopen rateReopened ÷ fixedFix quality
    Rejection rateRejected ÷ reportedReport quality / requirement clarity
    Open defects by severityCount per severityRelease readiness
    Defect trendCreated vs resolved per weekStabilisation

    Worked example

    Testing found 90 defects; production found 10 later. Leakage = 10 ÷ 100 = 10%; DRE = 90 ÷ 100 = 90%.

    ⚠️
    Metrics are for learning, not blaming. Never rank individual testers by bug count — people will log trivial bugs and argue over numbers.

    🧯 Special situations Expert

    SituationWhat to do
    Duplicate suspectedSearch by keywords/component first; add your evidence to the existing bug; link, don't duplicate
    Blocked testsMark tests Blocked, link the blocking bug, raise the risk in the status report
    Bug found in productionRaise with production incident process; note customer impact; add regression test
    Security vulnerabilityDo not publish details broadly; use restricted visibility and follow security policy
    Disagreement on validityEscalate to Product Owner with the requirement reference
    Cannot reproduceGather logs/HAR, retry on same build/data/time zone, ask dev for log time range
    🎯 Key takeaways
    • Triage decides what, who and when; tester provides impact and evidence.
    • Retest the exact steps, then regress neighbours.
    • Metrics inform decisions — never use them to blame.
    • Handle duplicates, blockers and security bugs by process.

    Module 05 · Advanced

    RCA, Prevention & Release Readiness

    Root cause analysis, dashboards, go/no-go decisions and integrations.

    🔍 Root Cause Analysis (RCA) Expert

    Fixing a bug solves one problem. Understanding why it happened prevents a family of them.

    5 Whys

    5-whysBug: Order total became negative after applying a coupon twice
Why 1: The discount was subtracted twice.
Why 2: The coupon-applied flag was not checked on the second call.
Why 3: The check was in the UI only; the API did not validate.
Why 4: Backend requirement did not state "one coupon per order".
Why 5: Story refinement did not include the tester/PO conversation about limits.
Action: Add AC "one coupon per order" + API validation + automated API test.

    Fishbone (Ishikawa) categories

    PeopleProcessRequirementsCodeEnvironmentToolsDataThird parties

    Defect injection source & detection phase

    Injected inFound inRelative cost
    RequirementsRequirements review1×
    RequirementsSystem test~10×
    RequirementsProduction~50–100×

    🧬 Defect prevention & process improvement Expert

    • Categorise root causes for every High/Critical bug; review trends monthly.
    • Update checklists (requirement review, code review, test design) with each learning.
    • Add regression tests for escaped defects (manual first, automate when stable).
    • Feed lessons into the retrospective with actions, owners, dates.
    • Clustering: if 60% of bugs come from one module, add targeted reviews, pairing or refactoring.

    📊 Dashboards & release readiness Expert

    Typical dashboard gadgets:

    Created vs Resolved (trend)Open defects by severityOpen defects by componentAverage defect ageDefects by root causeReopen rateSprint bug burndown

    Release readiness / go-no-go checklist

    CheckTarget
    Open Critical defects0
    Open High defects0 or accepted with workaround and PO sign-off
    Execution of planned tests≥ 95% (100% P1)
    Pass rate of P1100%
    Regression suitePassed on release candidate
    Known issues listDocumented and shared with support
    Rollback planReady and tested
    📝
    The tester's role is to inform the decision: "Here are the open risks, here is the impact, here is my recommendation". The business makes the release call.

    🤖 Automation & integrations Expert

    • Test tools → tracker: failing automated tests can auto-create bugs with logs and screenshots (e.g. Xray, Zephyr, ADO Test Plans).
    • CI → tracker: link commits/PRs to bugs using IDs (fix SHOP-231: validate coupon); status transitions can be automated (merged → Ready for QA).
    • Chat → tracker: Slack/Teams bots create and post updates.
    • Bulk edits & automation rules: auto-assign by component; auto-comment when no response in 3 days; auto-transition on linked PR merge.
    • APIs: Jira REST / ADO REST / Bugzilla REST for reports and imports.

    🏋️ Practice Expert

    PracticeExercise 5.1 — RCA

    Production bug: users in IST time zone see offers expire 5½ hours early. Do a 5-Whys.

    ▶ Show solution
    1. Offer end time was compared in UTC against local midnight.
    2. Dates stored without time zone information.
    3. Requirement said "valid till 31-Dec" with no time zone.
    4. Test environment servers run in IST so the issue never appeared.
    5. Action: define time zone rules, test with servers in UTC, add boundary tests around midnight in multiple zones.
    PracticeExercise 5.2 — Go / no-go

    Open: 0 Critical, 2 High (one with workaround, one blocks Wallet), 14 Medium. P1 pass 100%, execution 97%. Recommendation?

    ▶ Show solution

    Conditional go: release with Wallet disabled (feature flag) if PO accepts, or fix the blocking High first. Document the known issues, workaround and monitoring plan.

    Module 06 · Hands-on

    Practice Lab

    Log realistic defects and make triage decisions.

    🧪 Hands-on lab: log 5 bugs Basic

    Open any practice site (e.g. a demo shop or the app you are testing) and find real defects, or use these simulated observations. For each, write a full bug report using the template, choose severity & priority and name the best status/resolution if the dev replies as shown.

    PracticeCase 1

    On a flight-booking page, choosing return date earlier than departure date still lets you click "Search" and shows flights.

    ▶ Show solution

    Title: Search allows return date earlier than departure date. Steps: 1 Open Flights. 2 Set departure 20-Dec, return 15-Dec. 3 Click Search. Expected: validation error "Return must be after departure". Actual: results shown with confusing prices. Sev: Medium, Pri: Medium.

    PracticeCase 2

    Developer replies: "Works as designed — product owner said users can book multi-city." What now?

    ▶ Show solution

    Ask for the story/AC reference. If multi-city is the case, this is not a defect; update the test, and raise a usability improvement (clear UI) as an enhancement ticket. Status: Rejected / Works as designed, with a comment linking the AC.

    PracticeCase 3

    Randomly, 1 in 6 times, "Pay" button does nothing on mobile Safari.

    ▶ Show solution

    Intermittent: record 6 tries, device and iOS version, network type. Capture screen recording, Safari console (via Mac). Title: "Pay button unresponsive intermittently (1/6) on iOS 17 Safari". Severity Critical/High (blocks payments), Priority High.

    PracticeCase 4

    Admin can see another admin's salary field by changing ?id=55 in the URL.

    ▶ Show solution

    Security defect (IDOR / broken access control). Severity Critical. Restrict visibility, include exact URL and role, no real data in screenshots. Notify security lead through the defined path.

    PracticeCase 5

    Fix delivered. How do you verify?

    ▶ Show solution

    Re-run original steps on the new build; test other roles, IDs and direct API call; confirm response 403 and no data in the page source; add regression test; comment "Verified on build 2.5.0-rc1" and close.

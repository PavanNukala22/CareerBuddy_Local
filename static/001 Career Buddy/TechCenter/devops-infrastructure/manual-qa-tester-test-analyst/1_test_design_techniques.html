    Module 01 · Foundations

    Testing Fundamentals

    What testing is, why exhaustive testing is impossible, and why test design techniques exist — everything you need before designing your first test.

    🔍 What is software testing? Basic

    Software testing is the activity of running (or examining) a software product to find out whether it does what it should do, and doesn't do what it shouldn't. A tester collects information about quality so that people can make good decisions — "is it safe to release?".

    🍽️
    Analogy: a food inspector at a restaurant. They do not cook the meal; they check the kitchen, taste the dish and compare it against hygiene rules and the menu promise. They cannot taste every grain of rice — so they choose smart samples. Test design techniques are exactly that: choosing smart samples.

    A Manual QA Tester / Test Analyst does this by hand — reading requirements, designing tests, executing them through the UI or tools, observing results and reporting defects — without writing automation code.

    🎯
    Find defects
    Reveal problems before customers do.
    📏
    Build confidence
    Show the product meets the agreed requirements.
    🛡️
    Prevent defects
    Reviewing requirements early stops bugs being coded at all.
    📊
    Give information
    Provide risk and quality data to stakeholders.

    🐞 Error, defect and failure Basic

    Three words that sound alike but describe three different moments in a bug's life:

    Error (human mistake)→Defect / Bug (wrong code or document)→Failure (wrong behaviour at run time)
    TermMeaningExample
    Error / MistakeA human slip while analysing, designing or coding.Developer misreads "18 or older" as "older than 18".
    Defect / Bug / FaultThe flaw that the mistake leaves behind in the product.Code says age > 18 instead of age >= 18.
    FailureVisible wrong behaviour when the defect is executed.A user who is exactly 18 is rejected at registration.
    📝
    Not every defect causes a failure — a defect in code that is never executed stays hidden. Testing can only show failures; the tester then helps trace them back to defects.

    ♾️ Why we cannot test everything — and why techniques exist Basic

    Imagine a single input box that accepts a whole number from 1 to 100,000. Testing "every" value means 100,000 tests. A form with five such fields means 1025 combinations. That is exhaustive testing — and it is impossible.

    So testers must select a small, powerful set of tests. Test design techniques are systematic recipes for that selection, with a promise: "if there is a bug of this kind, one of these tests will probably catch it."

    ❌ Without techniques

    • Tests picked by gut feeling

    • Many redundant tests, big gaps

    • Cannot explain "how much testing is enough"

    • Results differ person to person

    ✅ With techniques

    • Tests chosen by a repeatable logic

    • Fewer tests, higher defect yield

    • Coverage can be measured and explained

    • Consistent across the team

    📜 The seven testing principles Basic

    #PrincipleWhat it means in practice
    1Testing shows presence of defectsPassing tests never prove "no bugs"; they only reduce risk.
    2Exhaustive testing is impossibleUse risk and techniques to focus effort.
    3Early testing saves time and moneyReview requirements before code exists (shift-left).
    4Defects cluster togetherA few modules hold most bugs — look harder there.
    5Pesticide paradoxRepeating the same tests stops finding new bugs; refresh them.
    6Testing is context dependentA banking app and a game need different testing.
    7Absence-of-defects fallacyA bug-free product that does not meet user needs is still a failure.

    ⚖️ Verification vs Validation, levels and types Basic

    🔧 Verification

    "Are we building the product right?"

    Checks work-products against specifications: reviews, walkthroughs, static analysis.

    🧑‍💼 Validation

    "Are we building the right product?"

    Checks the product meets real user needs: running the software, UAT.

    Test levels (where)

    Unit→Integration→System→Acceptance (UAT)

    Test types (what)

    FunctionalNon-functional (performance, security, usability)RegressionSmoke / SanityRe-testing (confirmation)CompatibilityAccessibility

    As a manual tester you mostly work at system and acceptance level — testing the whole application the way a user would.

    🧾 Anatomy of a test case Basic

    A test case is a documented set of inputs, preconditions, steps and expected results used to check one specific behaviour.

    FieldPurposeExample
    IDUnique referenceTC_REG_014
    TitleOne-line intentRegistration rejects age 17
    PreconditionsState needed before startingUser is on the Sign-up page, logged out
    Test dataExact inputsAge = 17
    StepsNumbered actions1. Enter age 17   2. Click Register
    Expected resultWhat should happen — decided from the requirement, not from the appError "You must be 18 or older"; no account created
    Actual result / StatusFilled during executionPass / Fail / Blocked / Skipped
    PriorityBusiness importanceHigh
    ⚠️
    The test oracle (how you know what is "expected") must come from requirements, user stories or domain rules — never from "whatever the app currently does".

    🌳 The family of test design techniques Basic

    ⬛
    Black-box (specification-based)
    Tests derived from requirements without looking at code. Equivalence Partitioning, Boundary Value Analysis, Decision Tables, State Transition, Use-case testing.
    ⬜
    White-box (structure-based)
    Tests derived from code structure — statement, branch coverage. Mostly developers; testers should know the idea.
    🧠
    Experience-based
    Tests derived from skill and intuition. Exploratory testing, error guessing, checklists.

    This course follows a path from the simplest technique to the most open-ended:

    Equivalence Partitioning→Boundary Value Analysis→Decision Table→State Transition→Exploratory
    🎯 Key takeaways
    • Testing = smart sampling, because exhaustive testing is impossible.
    • Error → defect → failure: you observe failures, you report defects.
    • A test case needs an expected result taken from an independent oracle.
    • Black-box techniques come from requirements; experience-based from skill.

    Module 02 · Black-box technique

    Equivalence Partitioning

    Group inputs that behave alike and test one value per group — the fastest way to cut hundreds of tests to a handful.

    🧩 What is Equivalence Partitioning (EP)? Basic

    Equivalence Partitioning divides all possible inputs (or outputs) into groups — partitions — where the system should behave the same way for every value in the group. Because they behave alike, you test just one representative from each partition.

    🚌
    Analogy: a school bus charges by age group — child (0–12), adult (13–59), senior (60+). To check the fare logic you don't ride with every age; you check one child, one adult, one senior. The groups are "equivalence classes".

    Core assumption

    If one value in a partition exposes a defect, every value in that partition would; if one passes, the rest are expected to pass.

    Valid vs invalid partitions

    ✅
    Valid partition
    Values the requirement says are accepted. Test them to confirm correct processing.
    🚫
    Invalid partition
    Values that must be rejected. Test them to confirm correct error handling.

    📐 Step-by-step procedure Basic

    1 Identify input→2 Find rules / ranges→3 Split valid & invalid→4 Pick one value each→5 Write test cases

    Worked example — "Age" field

    Requirement: An insurance form accepts whole-number ages from 18 to 60 inclusive.

    Three numeric partitions — one test each.
    PartitionRangeValid?Representative
    EP1age ≤ 17Invalid10
    EP218 – 60Valid35
    EP3age ≥ 61Invalid75
    EP4Non-numeric (letters, symbols)Invalid"abc", "#$%"
    EP5Decimal numberInvalid25.5
    EP6Empty / blankInvalid(nothing)
    EP7Negative numberInvalid-5

    Only 7 tests cover thousands of possible entries.

    🛒 EP on business rules and outputs Intermediate

    EP is not just for numbers. Partition anything with distinct behaviour: user roles, file types, payment methods, order amounts, even outputs.

    Example — shipping fee

    Order total up to 499.99 → ₹50 fee. 500 and above → free shipping.

    PartitionOrder totalExpected outputTest value
    EP10.01 – 499.99Fee ₹50250
    EP2500.00 and aboveFee ₹0800
    EP30 or negativeError-10
    EP4Not a numberError"ten"

    Example — file upload (type partitions)

    Allowed: .jpg .pngNot allowed: .exeNot allowed: .pdfNo extensionZero-byte fileVery large file

    Multiple inputs

    When a screen has several fields, partition each one, then combine carefully:

    • Valid combination: use one valid value from every field — can cover all valid partitions in a few tests.
    • Invalid tests: change only one field to invalid per test, keep others valid — otherwise you can't tell which invalid value caused the error (defect masking).
    ⚠️
    Never combine two invalid values in one test unless you are deliberately testing that combination. The first error message may hide the second defect.

    📏 Coverage and common mistakes Intermediate

    EP coverage = (partitions tested ÷ total partitions) × 100. Aim for 100% of identified partitions.

    MistakeWhy it hurtsFix
    Forgetting invalid partitionsOnly "happy path" testedAlways ask "what else could be entered?"
    Overlapping partitionsSame value belongs to two groupsMake ranges mutually exclusive
    Missing data-type partitionsLetters, symbols, blank untestedAdd type/format partitions
    Choosing a boundary as representativeMixes EP and BVAChoose a typical middle value; use BVA for edges
    Wrong oracleExpectation guessed from appDerive from requirement
    🎯 Key takeaways
    • Split inputs into groups that behave the same; test one value per group.
    • Always include invalid partitions: type, format, blank, negative, too large.
    • Vary one invalid field at a time to avoid masking.
    • EP finds class defects; boundaries are the next technique.

    Module 03 · Black-box technique

    Boundary Value Analysis

    Defects live on the edges. Learn 2-value and 3-value BVA, data-type boundaries and hidden technical limits.

    📍 What is Boundary Value Analysis (BVA)? Basic

    Boundary Value Analysis focuses on the edges of partitions. Experience shows that developers make mistakes at boundaries far more often than in the middle — typically by confusing < with <= or being off by one.

    🎢
    Analogy: a height bar at a theme park: "must be at least 120 cm." The interesting tests are 119, 120 and 121 cm — not 90 or 170.
    Boundary values for an age field 18–60 (3-value BVA).

    The classic bug BVA catches

    pseudo-codeif (age > 18 && age < 60) {   // BUG: should be >= 18 and <= 60
    accept();
}

    Tests for 25 or 40 pass. Only 18 and 60 reveal the defect.

    ✌️ 2-value vs 3-value BVA Basic

    MethodValues per boundaryAge 18–60 exampleUse when
    2-valueBoundary + nearest value in the neighbouring partition17, 18, 60, 61Standard; efficient
    3-valueBoundary + both neighbours17, 18, 19, 59, 60, 61Higher-risk areas (finance, medical)
    🧮 Try it — Boundary calculator

    Step is the smallest unit the field supports: 1 for integers, 0.01 for money, 0.1 for one decimal.

    🧮 Applying BVA to different data types Intermediate

    MoneySmallest unit 0.01Discount tier ≥ ₹10099.99, 100.00, 100.01
    Text lengthCharacters countName max 50 chars49, 50, 51 characters; 0 and 1 for min
    DateDay before / on / afterOffer valid till 31-Dec30-Dec, 31-Dec, 01-Jan; leap day 29-Feb
    TimeSeconds/minutes edgesSession timeout 15 min14:59, 15:00, 15:01
    CollectionsItem countCart 1–20 items0, 1, 2, 19, 20, 21
    File sizeBytesUpload ≤ 5 MB4.99 MB, 5 MB, 5.01 MB
    PaginationRecords per page10 per page10 records, 11 records, 0 records

    Worked example — tiered discount

    Order value: up to 99.99 → 0% · 100.00–499.99 → 5% · 500.00 and above → 10%.

    BoundaryTest valuesExpected discount
    Lower limit (0.00)-0.01 / 0.00 / 0.01Error / 0% / 0%
    First tier edge99.99 / 100.00 / 100.010% / 5% / 5%
    Second tier edge499.99 / 500.00 / 500.015% / 10% / 10%

    🔗 EP + BVA together Intermediate

    The two techniques are partners. EP finds the groups; BVA picks the edges of ordered groups. A solid design uses both:

    Partition the input (EP)→Mark ordered boundaries→Add BVA values at edges→Add one mid-value per partition→Add invalid types (letters, blank)

    For age 18–60 the final set is: 17, 18, 19, 35 (mid), 59, 60, 61, plus "abc", blank, -5, 25.5.

    BVA beyond a single field

    • Output boundaries: choose inputs so the result lands exactly on a limit (e.g. total becomes exactly 500.00 after tax).
    • Internal limits: max database field length, API payload size, session limits, 32-bit integer maximum (2,147,483,647).
    • Multiple variables: hold all other variables at nominal values while one moves through its boundaries.

    🧠 Expert: robust, worst-case and non-obvious boundaries Expert

    VariantIdeaWhen
    Robust BVAInclude values beyond the invalid side (min−1, max+1) to test error handlingAlways for user-facing inputs
    Worst-case BVACombine boundaries of all variables (5n tests)Safety-critical, small variable count
    Hidden boundariesLimits not in the requirement: DB column size, UI truncation, timeout, rate-limitAsk developers / inspect DevTools

    Hunting hidden boundaries

    • Paste 5,000 characters into a "name" field — does the UI break or the DB truncate silently?
    • Enter 2147483648 (int overflow), 0.1+0.2 style decimals, multi-byte characters (emoji, "ñ") that count differently in bytes and characters.
    • Check time zones and daylight-saving changes around date boundaries; midnight and month/year rollovers.
    ⚠️
    Ask "is the limit inclusive or exclusive?" If the requirement says "up to 60", clarify before you assume. Ambiguous wording is itself a defect in the requirement.
    🎯 Key takeaways
    • Bugs love edges: test min−1, min, min+1, max−1, max, max+1.
    • Know the smallest step of the data type (1, 0.01, 1 char, 1 day).
    • Use EP for the groups and BVA for the edges.
    • Look for hidden technical boundaries, not only documented ones.

    Decision Tables, Pairwise & Other Techniques

    When rules combine, when parameters multiply and how to choose the right technique.

    📋 Decision table testing Intermediate

    EP and BVA test inputs one at a time. Real business logic often depends on combinations of conditions. A decision table lists every combination of conditions (rules) and the action the system must take.

    Example — loan approval

    Approve if credit score is good and income is sufficient. If score is good but income is low, send for manual review. Otherwise reject.

    Rule 1Rule 2Rule 3Rule 4
    Credit score good?YYNN
    Income sufficient?YNYN
    Action: Approve✔
    Action: Manual review✔
    Action: Reject✔✔

    Each column becomes at least one test case. With n binary conditions there are 2n rules — 3 conditions = 8 rules, 5 conditions = 32 rules.

    How to build one

    List conditions→List actions→Enumerate combinations→Fill expected actions→Merge impossible/identical rules→Make test cases
    💡
    Collapse rules where one condition does not matter (marked "–"). Rules 3 and 4 above could merge into "score bad → reject".

    🔀 Pairwise (all-pairs) testing Expert

    A page with 4 settings of 3 options each has 34 = 81 combinations. Research shows most bugs are triggered by the interaction of just two parameters. Pairwise testing chooses the smallest set where every pair of values appears at least once — here about 9–10 tests instead of 81.

    TestBrowserOSLanguage
    1ChromeWindowsEnglish
    2ChromemacOSHindi
    3FirefoxWindowsHindi
    4FirefoxmacOSEnglish
    5SafariWindowsTelugu
    6SafarimacOSEnglish

    Tools such as PICT (Microsoft) or free web pairwise generators create these tables for you.

    📖 Use-case and user-journey testing Intermediate

    Derive tests from end-to-end user scenarios: a main success path, alternate paths and exception paths.

    PathOnline purchase example
    MainSearch → add to cart → checkout → pay → confirmation email
    AlternatePay with wallet instead of card; apply coupon
    ExceptionPayment declined; item goes out of stock during checkout; session expires

    🧠 Error guessing and checklists Intermediate

    Error guessing uses experience to predict where bugs hide. Build a personal fault list:

    Empty / null inputLeading & trailing spacesSpecial characters <> ' " % \SQL-like text ' OR 1=1 --Very long stringsCopy-paste with formattingDouble-click SubmitBrowser Back after submitDuplicate recordPast / future datesLeap day 29-FebZero and negative valuesUnicode / emojiSession timeout mid-action

    🗺️ Choosing the right technique Expert

    SituationBest technique
    Input fields with ranges or groupsEquivalence Partitioning + BVA
    Several conditions drive a business outcomeDecision table
    Behaviour depends on history / statusState transition
    Many configuration parametersPairwise
    Journey across screens or systemsUse-case testing
    Little documentation, need fast learningExploratory testing
    Past defect patterns knownError guessing / checklists
    📝
    Experts combine techniques: specification-based techniques give systematic coverage; exploratory testing finds what the specification forgot.

    Module 05 · Black-box technique

    State Transition Testing

    Test systems whose behaviour depends on their current state and history — from order workflows to ATM PIN logic.

    🔄 What is State Transition Testing? Basic

    Some systems behave differently depending on their current state and on what happened before. A user account can be Active, Locked or Closed; an order can be New, Paid, Shipped. State transition testing checks that the system moves correctly between states when events occur — and that it refuses illegal moves.

    🚦
    Analogy: a traffic light. Red → Green → Yellow → Red is allowed. Red → Yellow directly is not. You can test the legal cycle, and you can test that illegal jumps are impossible.

    The four building blocks

    ⭕
    State
    A condition the system stays in until something happens (Locked, Paid).
    ⚡
    Event
    Trigger that may cause a change (enter wrong PIN, click Pay).
    ➡️
    Transition
    Move from one state to another caused by an event.
    🎬
    Action / Output
    What the system does during the move (send email, show error).

    🧭 State diagram and state table Basic

    Example — an order lifecycle. Only New and Paid orders may be cancelled.

    Order lifecycle. Red arrows = cancel; cancelling a Shipped order must be blocked.

    State table (shows valid and invalid cells)

    Current statePayShipDeliverCancel
    NewPaidInvalidInvalidCancelled
    PaidInvalidShippedInvalidCancelled (+refund)
    ShippedInvalidInvalidDeliveredInvalid
    DeliveredInvalidInvalidInvalidInvalid
    CancelledInvalidInvalidInvalidInvalid
    📝
    The table matters more than the diagram: it forces you to look at every cell. Diagrams usually show only valid transitions; defects love the empty cells.

    📏 Designing tests & coverage levels Intermediate

    Coverage levels

    LevelMeaningFor the order example
    All statesVisit every state at least onceNew, Paid, Shipped, Delivered, Cancelled
    All valid transitions (0-switch)Execute every valid single transitionpay, ship, deliver, cancel-from-New, cancel-from-Paid = 5
    All invalid transitionsAttempt every invalid celle.g. ship a New order, cancel a Shipped order
    N-switch (sequences)Chains of N+1 transitions (1-switch = pairs)pay→ship, ship→deliver, new→cancel→(pay)…

    Test cases for 0-switch + selected invalid

    IDStartEventExpected endCheck
    ST1NewPayPaidReceipt email sent
    ST2PaidShipShippedTracking id created
    ST3ShippedDeliverDeliveredReview request sent
    ST4NewCancelCancelledNo charge
    ST5PaidCancelCancelledRefund initiated
    ST6NewShipNo changeError "Pay first"
    ST7ShippedCancelNo changeCancel option hidden / rejected

    🏧 Worked example — ATM PIN with memory Intermediate

    Rule: Three wrong PIN attempts in a row retain the card. A correct PIN at any time shows the menu.

    StateCorrect PINWrong PIN
    Card inserted (0 fails)MenuWrong-1
    Wrong-1MenuWrong-2
    Wrong-2MenuCard retained
    Menu——
    Card retainedNo actionNo action

    This system needs memory — it must remember how many failures happened. Test the sequence wrong, wrong, correct (counter must reset) and wrong, wrong, wrong (card kept). Also test that the counter resets for the next card.

    🧠 Expert: sequences, concurrency and time Expert

    • Round-trip paths: test sequences that return to a start state (Active → Suspended → Active) to expose leftover data.
    • Time-based events: session timeout, OTP expiry, scheduled jobs — the "event" is the clock. Test just before and just after.
    • Concurrent events: two tabs press Pay and Cancel together; double-click Pay; race conditions.
    • Back / refresh / deep links: browser Back after a state change; opening a URL meant for a different state.
    • Data consequences: after each transition verify the database state, emails, audit log and downstream systems — not only the screen.
    🎯 Key takeaways
    • Identify states, events, transitions and actions.
    • Build a state table to expose invalid transitions.
    • Cover all states → all valid transitions → invalid transitions → sequences.
    • Test history (counters), time and concurrency for expert depth.

    Module 06 · Experience-based technique

    Exploratory Testing

    Learn, design and execute at the same time — with charters, heuristics, tours and disciplined notes.

    🧭 What is exploratory testing? Basic

    Exploratory testing is simultaneous learning, test design and test execution. You don't follow a pre-written script; you explore the software, observe, form a hypothesis and decide the next test based on what you just learned.

    🕵️
    Analogy: a scripted test is a guided tour with a printed itinerary. Exploratory testing is a detective walking into a room — every clue shapes the next question.

    📄 Scripted testing

    • Tests designed in advance

    • Repeatable, easy to audit

    • Good for regression and compliance

    • Risk: only finds what was imagined

    🧭 Exploratory testing

    • Design + execution at the same time

    • Adapts to what is discovered

    • Great for new features, thin specs

    • Risk: needs skill and good notes

    Exploratory ≠ random clicking. It is structured by a goal (charter), a time-box and notes.

    📜 Charters and session-based testing Intermediate

    A charter is a one-sentence mission for a session:

    templateExplore  <area / feature>
With     <resources: data, tools, personas, configuration>
To discover  <information: risks, defects, behaviours>

    Example: Explore the checkout payment page with expired, international and 3-D-Secure cards to discover problems with error handling.

    Session-Based Test Management (SBTM)

    Pick a charter→Time-box 60–120 min→Test & take notes→Log bugs / questions→Debrief with lead
    Session sheet fieldContents
    CharterMission of the session
    Tester / date / durationWho, when, how long
    Build & environmentApp version, browser, data set
    NotesWhat was tested, observations, ideas
    BugsIDs of defects raised
    Issues / questionsBlockers and unclear requirements
    TBS split% time on Test design/execution, Bug investigation, Setup

    Tours (James Whittaker)

    🏛️
    Landmark tour
    Visit the key features in a chosen order.
    💰
    Money tour
    Test the features that earn the revenue.
    🚪
    Back-alley tour
    Visit the least-used corners of the app.
    🗑️
    Garbage-collector tour
    Systematically go through every item — every menu, every link.
    😈
    Antisocial tour
    Do the wrong thing: invalid, hostile, unexpected input.
    🛋️
    Couch-potato tour
    Do as little as possible: accept defaults, leave fields empty.

    Other quick mnemonics

    • CRUD: Create, Read, Update, Delete — for every data object.
    • Goldilocks: too big, too small, just right.
    • Interrupt: lose network, refresh, press Back, switch tab, lock phone mid-action.
    • FEW HICCUPPS (oracles): Familiar problems, Explainability, World, History, Image, Comparable products, Claims, User expectations, Product, Purpose, Statutes.

    ✍️ Taking good notes & reporting Intermediate

    If it isn't written down it didn't happen. Use a timestamped log:

    session notes10:02  Charter: explore profile photo upload
10:05  JPG 2MB ok. PNG ok. GIF accepted? -> yes (spec says only JPG/PNG)  [Q1]
10:12  Photo 12MB -> spinner never ends, no error     [BUG-231]
10:20  Upload, then Back, then Forward -> old photo shown   [IDEA: caching]
10:31  Idea: test on mobile Safari, same file  -> TODO

    Mark entries as Bug, Question, Idea, Todo. Finish each session with a debrief: what was covered, what was found, what is still risky.

    When to use exploratory testing

    • New feature with incomplete documentation
    • After scripted tests pass — to hunt for what scripts missed
    • Time pressure — high value per hour
    • Learning an unfamiliar product (onboarding)
    • Investigating a bug cluster

    🧠 Expert: making exploration repeatable and measurable Expert

    • Risk-driven charters: rank features by business impact × likelihood of failure; write charters for the top risks first.
    • Test ideas map: draw a mind map of the product; colour areas "explored / partly / untouched" to show coverage visually.
    • Paired exploratory sessions: a tester + a developer or BA. Different perspectives find different bugs; the developer learns what hurts users.
    • Bug bashes: time-boxed event where many people explore before release; give them charters and a shared bug template.
    • Convert discoveries into scripts: a bug found exploratorily becomes a regression test (manual or automated) so it cannot return.
    • Metrics: sessions per week, bugs per session, TBS ratio, charter coverage — measures of learning, not just bug count.
    ⚠️
    Common pitfalls: no charter (aimless clicking), no notes (cannot repeat or defend), no time-box (endless), testing only the happy path. Fix: charter + timer + notes + debrief.
    🎯 Key takeaways
    • Exploratory = learn + design + execute together, with a charter and time-box.
    • Heuristics (SFDIPOT, tours, CRUD) give structure to curiosity.
    • Notes and debrief make the work visible and defensible.
    • Complement, never replace, scripted techniques.

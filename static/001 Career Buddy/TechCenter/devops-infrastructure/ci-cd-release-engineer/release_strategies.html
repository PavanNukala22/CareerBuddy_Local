    Module 01 · Foundations

    Release Strategy Fundamentals

    Separate deploying code from releasing features, then pick the right rollout pattern.

    🧭 Deploy ≠ Release

    Basic

    Deploy = put new code on servers. Release = expose it to users. Decoupling them (with feature flags and progressive rollout) is the root of low-risk delivery.

    Deploycode is live, dark
    →
    Enable for 1%flag / canary
    →
    Observemetrics, errors
    →
    Ramp 10→50→100%
    →
    Releaseeveryone
    Progressive delivery in one picture.

    🗂️ Deployment strategy types

    StrategyHow it worksRiskRollback speedBest for
    RecreateStop old, start newHigh (downtime)SlowDev/batch jobs
    RollingReplace pods graduallyMediumMediumStateless services
    Blue-GreenTwo full envs, switch trafficLowInstant (flip back)Critical apps, need 2× capacity
    CanarySmall % of traffic to new versionLowFastUser-facing services
    A/B testSegments see variants to measure impactLowFast (flag)Product experiments
    ShadowMirror traffic to new, ignore responseVery lown/aValidating rewrites

    🧠 Choosing

    💡
    Decision shortcut: need zero downtime and instant undo → blue-green. Need real-user evidence at low blast radius → canary. Need to test business hypotheses → feature flag + A/B. Cost-constrained → rolling.
    Module 02 · Control

    Feature Flags & LaunchDarkly

    Turn features on and off at runtime without redeploying.

    🚩 What are feature flags?

    Basic
    🚀
    Release flagHide unfinished work; short-lived.
    🧪
    Experiment flagServe variants to measure impact.
    🛑
    Ops / kill switchDisable a risky or failing path instantly.
    🔑
    Permission flagEntitlements per plan or customer; long-lived.

    Basic usage in code (LaunchDarkly Node SDK):

    javascriptconst ld = require('@launchdarkly/node-server-sdk');
const client = ld.init(process.env.LD_SDK_KEY);
await client.waitForInitialization({ timeout: 5 });
const ctx = { kind: 'user', key: user.id, plan: user.plan, country: user.country };
const on = await client.variation('new-checkout', ctx, false);  // false = safe default
if (on) renderNewCheckout(); else renderOldCheckout();

    🎛️ Targeting & progressive rollout

    Intermediate
    • Targeting rules: internal staff → beta customers → percentage rollout.
    • Contexts can be users, orgs, devices; attributes drive rules.
    • Guarded releases: auto-pause or roll back when error rate/latency regress.
    • Approvals & scheduled changes protect production environments.

    Beta 5%

    25%
    →
    50% + guardrail
    →
    100%

    🤖 Automating flag management

    Expert

    Treat flags as code: create, enforce naming, and clean up via the REST API or Terraform in the pipeline.

    bash# Turn a flag ON for 25% in production from CI after canary passes
curl -s -X PATCH "https://app.launchdarkly.com/api/v2/flags/my-proj/new-checkout" \
  -H "Authorization: $LD_API_TOKEN" -H "Content-Type: application/json; domain-model=launchdarkly.semanticpatch" \
  -d '{"environmentKey":"production","instructions":[{"kind":"updateFallthroughWithRollout","rolloutWeights":{"on":25000,"off":75000}}]}'
    hclresource "launchdarkly_feature_flag" "new_checkout" {
  project_key = "my-proj"
  key         = "new-checkout"
  name        = "New checkout"
  variation_type = "boolean"
  temporary   = true            # must be cleaned up
  tags        = ["team-payments", "release"]
}
    ⚠️
    Flag debt: every temporary flag needs an owner and expiry. Use code references + stale-flag reports, and delete the flag and dead branch once at 100%.
    Module 03 · Rollout

    Progressive Delivery

    Ship to a few, watch the data, then expand: canary, blue-green and rings.

    🐤 Canary with Argo Rollouts

    Intermediate

    Argo Rollouts replaces Deployment with a Rollout that steps traffic and runs automated analysis.

    yamlapiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: payments }
spec:
  replicas: 10
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: { duration: 5m }
        - analysis: { templates: [ { templateName: success-rate } ] }
        - setWeight: 50
        - pause: { duration: 10m }
        - setWeight: 100

    📊 Automated analysis

    Expert
    yamlapiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: success-rate }
spec:
  metrics:
    - name: success-rate
      interval: 1m
      failureLimit: 2                       # 2 bad samples = abort + rollback
      successCondition: result[0] >= 0.99
      provider:
        prometheus:
          address: http://prometheus:9090
          query: sum(rate(http_requests_total{app="payments",code!~"5.."}[2m])) / sum(rate(http_requests_total{app="payments"}[2m]))

    Tools in this space: Argo Rollouts, Flagger, Harness CV, Spinnaker, service meshes (Istio/Linkerd) for traffic splitting.

    💍 Ring-based & regional rollout

    Expert
    Ring 0internal
    →
    Ring 11 region, 5%
    →
    Ring 2beta customers
    →
    Ring 3GA, region by region
    Each ring has a bake time and automatic health gate.
    • Blast radius grows only after SLOs hold during the bake time.
    • Avoid releases on Fridays or during peak load unless fully automated and flag-protected.
    Module 04 · Safety

    Automated Rollback Mechanisms

    Detect failure fast and recover without a war room.

    🚨 Triggers & mechanisms

    TriggerTypical signalMechanism
    Failed health checkReadiness/liveness probeKubernetes stops rollout; rollout undo
    SLO breach5xx rate, p99 latency (Prometheus/Datadog)Argo/Flagger aborts canary
    Business metric dropConversion, checkout successFlag guardrail turns feature off
    Failed smoke testPost-deploy test job redPipeline runs rollback stage
    ManualOn-call decisionOne-click redeploy of previous artifact
    ✅
    Fastest rollback = flag off (seconds). Next = traffic switch (blue-green). Slowest = redeploy previous build.

    🔙 Pipeline example

    Intermediate
    bashhelm upgrade --install payments ./chart --set image.tag="$TAG" --atomic --timeout 5m   # auto-rollback on failure
./smoke.sh https://payments.example.com || {
  echo "Smoke failed -> rollback"; helm rollback payments 0 --wait; exit 1; }
# Kubernetes native:
kubectl rollout status deploy/payments --timeout=180s || kubectl rollout undo deploy/payments

    🗄️ Database changes: the hard part

    Expert

    Code rolls back; data does not. Use the expand → migrate → contract pattern so old and new versions both work against the schema.

    Expandadd nullable column
    →
    Deploy v2writes both
    →
    Backfill
    →
    Switch reads
    →
    Contractdrop old column later
    • Never ship destructive migrations in the same release as the code change.
    • Keep releases backward compatible for at least one version.
    • Rehearse rollback in staging; track MTTR.
    Module 05 · Governance

    Artifact Promotion

    Build once, promote the same immutable artifact through environments.

    📦 Build once, promote many

    Basic

    Never rebuild per environment. Rebuilding can change dependencies or behaviour, so what you tested is no longer what you ship. Instead promote the same artifact (identified by digest) as it passes gates.

    Buildonce
    →
    dev reposnapshot
    →
    Promotetests pass
    →
    staging repo
    →
    Promoteapproval + scans
    →
    prod reporelease
    Promotion moves or copies the identical bits between repositories/tags.

    🏷️ Promotion in practice

    Intermediate
    bash# Container: retag by digest, never rebuild
DIGEST=$(crane digest registry/app:build-742)
crane tag registry/app@$DIGEST staging
# after staging gates
crane tag registry/app@$DIGEST prod
# JFrog Artifactory: promote build between repos
jf rt build-promote my-build 742 --status=Released --target-repo=release-local --copy=true

    🚧 Gates & expert controls

    GateCheck
    QualityTests, coverage, static analysis
    SecurityVulnerability scan, license, SBOM present
    ProvenanceSignature verified (cosign), SLSA attestation
    ComplianceChange ticket approved, peer review, OPA policy
    RuntimeCanary / verification green in previous env
    💡
    Deploy by digest (image@sha256:…) in production manifests; tags are mutable, digests are not.

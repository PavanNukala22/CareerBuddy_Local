    Module 01 · Foundations

    CI/CD Pipeline Fundamentals

    What a pipeline is, the vocabulary every release engineer must know, and how the main orchestrators compare.

    🔁 What is a pipeline?

    Basic

    A pipeline is an automated, versioned sequence of steps that takes code from a commit to production. CI (Continuous Integration) merges and verifies code frequently; CD means either Continuous Delivery (always releasable, human approves deploy) or Continuous Deployment (every green build goes live automatically).

    Commitpush / PR
    →
    Buildcompile, package
    →
    Testunit, lint, SAST
    →
    Publishartifact + image
    →
    Deploystaging
    →
    Verifysmoke, e2e
    →
    Releaseprod
    A typical end-to-end pipeline. Highlighted stage = the hand-off from CI to CD.
    ⚡
    CIIntegrate often; every push builds and tests.
    📦
    Continuous DeliveryArtifact is always deployable; release is a button.
    🚀
    Continuous DeploymentNo human gate; automation decides.
    🧱
    Pipeline as CodePipelines live in Git: reviewable, versioned, reusable.

    📖 Core vocabulary

    TermMeaningExample
    TriggerEvent that starts a runpush, PR, tag, cron, webhook
    Stage / Job / StepGroup → unit of work → single commandtest stage → unit job → pytest step
    Runner / AgentMachine that executes jobsGitHub-hosted VM, Jenkins agent, GitLab runner

    Module 02 · Orchestrator

    GitHub Actions

    From your first workflow to reusable workflows, OIDC and environment protection.

    🌱 Your first workflow

    Basic

    A workflow is a YAML file with on (triggers), jobs, and steps.

    yamlname: ci
on: { push: { branches: [main] }, pull_request: {} }
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci && npm test

    🧮 Matrix, needs & artifacts

    Intermediate

    strategy.matrix fans a job out over versions/OSes; needs builds a dependency graph; artifacts pass files between jobs.

    yamljobs:
  build:
    strategy:
      fail-fast: false
      matrix: { os: [ubuntu-latest, windows-latest], node: [18, 20] }
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build
      - uses: actions/upload-artifact@v4
        with: { name: dist-${{ matrix.os }}-${{ matrix.node }}, path: dist/ }
  deploy:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production        # approvals + secrets scoped here
    steps: [ { run: echo deploying } ]

    ♻️ Reusable workflows & composite actions

    Expert
    📞
    Reusable workflowworkflow_call: a whole pipeline you call from many repos with inputs/secrets.
    🧩
    Composite actionBundle several steps into one action (action.yml).
    yaml# org/platform-workflows/.github/workflows/build.yml
on:
  workflow_call:
    inputs: { image: { type: string, required: true } }
    secrets: { REGISTRY_TOKEN: { required: true } }
# caller repo
jobs:
  build:
    uses: org/platform-workflows/.github/workflows/build.yml@v3
    with: { image: payments-api }
    secrets: inherit
    🔐
    Expert hardening: authenticate to AWS/GCP with OIDC (permissions: id-token: write) instead of long-lived keys; pin third-party actions to a commit SHA; set minimal permissions:; use concurrency: to cancel superseded runs.
    Module 03 · Orchestrator

    GitLab CI/CD

    Stages, rules, DAG pipelines, includes and child pipelines.

    🌱 Stages and jobs

    Basic

    Jobs in the same stage run in parallel; stages run in order.

    yamlstages: [build, test, deploy]
build:
  stage: build
  image: node:20
  script: [npm ci, npm run build]
  artifacts: { paths: [dist/], expire_in: 1 week }
test:
  stage: test
  script: [npm test]
  cache: { key: $CI_COMMIT_REF_SLUG, paths: [node_modules/] }

    🔀 Rules, needs (DAG) and environments

    Intermediate 
    yamldeploy_prod:
  stage: deploy
  script: ./deploy.sh prod
  needs: [test]                       # start as soon as test is done (DAG)
  rules:
    - if: $CI_COMMIT_TAG
    - if: $CI_COMMIT_BRANCH == "main"
      when: manual                    # approval gate
  environment: { name: production, url: https://app.example.com }
    ⚠️
    only/except is legacy. Use rules: everywhere for predictable behaviour.

    🏗️ Includes, templates and child pipelines

    Expert 
    yamlinclude:
  - project: platform/ci-templates
    ref: v2.4.0                       # always pin a version
    file: /templates/docker-build.yml
  - template: Security/SAST.gitlab-ci.yml
.deploy_base:                         # hidden job = reusable template
  script: ./deploy.sh $ENV
deploy_stg:
  extends: .deploy_base
  variables: { ENV: staging }
trigger_services:                     # dynamic child pipeline per service
  trigger: { include: services/pipeline.yml, strategy: depend }

    Expert tips: parallel:matrix, merge-request pipelines, merge trains, resource_group for serialised deploys, and CI/CD components catalog.

    Module 04 · Orchestrator

    Jenkins and Harness

    Declarative pipelines and shared libraries, plus Harness templates and governance.

    🧰 Jenkins declarative pipeline

    Basic
    groovypipeline {
  agent { label 'docker' }
  options { timeout(time: 30, unit: 'MINUTES'); disableConcurrentBuilds() }
  stages {
    stage('Build') { steps { sh 'mvn -B package' } }
    stage('Test')  { steps { sh 'mvn test' } post { always { junit 'target/surefire-reports/*.xml' } } }
    stage('Deploy') { when { branch 'main' } steps { input 'Deploy to prod?'; sh './deploy.sh' } }
  }
  post { failure { slackSend message: "Build failed: ${env.BUILD_URL}" } }
}

    📚 Shared libraries (template maintenance)

    Expert

    Put reusable steps in a Git repo under vars/ and load with @Library('platform@v5').

    groovy// vars/standardPipeline.groovy
def call(Map cfg) {
  pipeline { agent any
    stages { stage('Build'){ steps { sh cfg.buildCmd } }
             stage('Scan'){ steps { sh "trivy fs ${cfg.scanPath ?: '.'}" } } } }
}
// Jenkinsfile in each repo
@Library('platform@v5') _
standardPipeline(buildCmd: 'npm ci && npm run build')
    💡
    Use Configuration as Code (JCasC) and Job DSL to rebuild Jenkins from Git; run agents as ephemeral Kubernetes pods.

    🐚 Scripting best practices

    Intermediate

    Keep real logic in scripts, not YAML, so it is testable locally and portable between orchestrators.

    bash#!/usr/bin/env bash
set -euo pipefail                      # fail fast, no unset vars, pipe errors count
trap 'echo "failed at line $LINENO" >&2' ERR
: "${IMAGE:?IMAGE required}"
retry() { for i in 1 2 3; do "$@" && return 0 || sleep $((i*5)); done; return 1; }
retry docker push "$IMAGE"
    • Lint with shellcheck; unit-test with bats.
    • Make scripts idempotent: re-running must be safe.
    • Never echo secrets; mask them and prefer short-lived tokens.

    ⚡ Speed, security and observability

    AreaTechnique
    SpeedDependency + Docker layer cache, parallel jobs, path filters, test sharding, ephemeral autoscaled runners

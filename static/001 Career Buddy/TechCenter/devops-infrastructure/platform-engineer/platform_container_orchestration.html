    Module 01 · Foundations

    Kubernetes Fundamentals

    Kubernetes keeps containers running in the state you declared, across many machines.

    ☸️ What is orchestration? Basic

    Orchestration automates deploying, scaling, healing and networking of containers. You declare desired state; Kubernetes continuously makes actual state match it.

    🎼
    Analogy: a conductor. Musicians (containers) play; the conductor (control plane) keeps tempo, replaces absent players and adds more when the piece gets louder.

    🗺️ Big picture diagram Basic

    How a Deployment becomes running Pods

    🧱 Core objects Basic

    📦
    Pod
    Smallest unit: one or more containers sharing network.
    🔁
    Deployment
    Keeps N replicas running; handles rolling updates.
    🌐
    Service
    Stable virtual IP and DNS for a set of pods.
    🔑
    ConfigMap / Secret
    Config and credentials injected into pods.
    🚪
    Ingress
    HTTP routing from outside into Services.

    📝 First Deployment Basic

    yamlapiVersion: apps/v1
kind: Deployment

spec:
  replicas: 3

  template:

    🏗️ Cluster architecture: control plane and nodes Basic

    📖 What it is

    A cluster has a control plane that decides and worker nodes that run containers.

    🎯 Why it matters

    When something breaks you need to know which component owns the job.

    🧩 Types

    • API server: the front door; every command goes through it.
    • etcd: key-value database storing all cluster state.
    • Scheduler: picks a node for each new pod.
    • Controller manager: runs controllers such as Deployment and Node.
    • Kubelet: agent on each node starting containers.
    • kube-proxy / CNI: service routing and pod networking.

    🧪 Example

    You run kubectl apply. The API server stores the Deployment in etcd, the controller creates pods, the scheduler assigns nodes, and each kubelet starts the containers.

    🧰 Workload types: which controller for which job Basic

    📖 What it is

    Kubernetes has several workload controllers, each for a different pattern of running containers.

    🎯 Why it matters

    Using a Deployment for a database or a cron job is a common beginner error.

    🧩 Types

    • Deployment: stateless web apps and APIs.
    • StatefulSet: databases needing stable names and storage (db-0, db-1).
    • DaemonSet: one pod per node: log shippers, monitoring agents.
    • Job / CronJob: run to completion, or on a schedule: backups, reports.

    🧪 Example

    yamlapiVersion: batch/v1
kind: CronJob
metadata: {name: nightly-backup}
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - {name: backup, image: acme/backup:1.2}

    ❤️ Probes, labels and namespaces Basic

    📖 What it is

    Labels tag objects so Services and Deployments find them. Namespaces separate teams or environments. Probes tell Kubernetes whether a container is alive and ready.

    🎯 Why it matters

    Without a readiness probe, traffic reaches pods that are still starting, causing errors during every deploy.

    🧩 Types

    • Liveness: restart the container if it hangs.
    • Readiness: only send traffic when it returns OK.
    • Startup: give slow apps time before liveness begins.

    🧪 Example

    Namespace payments-dev and payments-prod hold the same app; a ResourceQuota in each limits CPU so dev cannot starve prod.

    Helm Charts and Cluster Operations

    Package apps once, configure them per environment, and run clusters safely.

    ⛵ What is Helm? Intermediate

    Helm is the package manager for Kubernetes. A chart is a folder of templated manifests; values fill the blanks; a release is one installed copy.

    textmychart/
  Chart.yaml        # name, version
  values.yaml       # defaults
  templates/
    deployment.yaml
    service.yaml
    yaml# templates/deployment.yaml (excerpt)
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repo }}:{{ .Values.image.tag }}"
    bashhelm install shop ./mychart -f values-prod.yaml
helm upgrade shop ./mychart --set image.tag=1.4.2
helm rollback shop 1

    💾 Storage and networking Intermediate

    📖 What it is

    PersistentVolumeClaims request disk; Ingress routes HTTP; NetworkPolicy limits which pods may talk.

    🎯 Why it matters

    Data must survive pod restarts, and by default every pod can reach every other pod.

    🧩 Types

    • PV / PVC / StorageClass: the claim is bound to dynamically provisioned storage.
    • Service types: ClusterIP (internal), NodePort, LoadBalancer.
    • Ingress: host and path routing with TLS.
    • NetworkPolicy: default-deny then allow only needed flows.

    🧪 Example

    yamlapiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: db-allow-api-only}
spec:
  podSelector: {matchLabels: {app: db}}
  ingress:
  - from: [{podSelector: {matchLabels: {app: api}}}]
    ports: [{port: 5432}]

    ⛵ Helm in depth: environments, hooks and dependencies Intermediate

    📖 What it is

    Beyond basic templating, Helm supports per-environment values files, chart dependencies, and hooks that run Jobs at lifecycle points.

    🎯 Why it matters

    Real platforms ship one chart used by hundreds of services; this is how they stay consistent.

    🧩 Types

    • Values layering: values.yaml then values-prod.yaml then --set; later wins.
    • Dependencies: declare a Redis or Postgres subchart in Chart.yaml.
    • Hooks: pre-upgrade migration Job.
    • Library charts: shared templates other charts include.

    🧪 Example

    yaml# Chart.yaml
dependencies:
- {name: redis, version: 19.x, repository: oci://registry-1.docker.io/bitnamicharts}
# templates/migrate-job.yaml
metadata:
  annotations: {"helm.sh/hook": pre-upgrade, "helm.sh/hook-weight": "0"}

    Module 03 · Extending Kubernetes

    Custom Controllers and Operators

    Teach Kubernetes new resource types and automate day-2 operations in code.

    🧠 Controllers and the reconcile loop Expert

    A controller watches resources, compares desired vs actual and acts to close the gap. It is level-based and must be idempotent: running it twice must not break anything.

    Watch event→Read desired→Observe actual→Create / update / delete→Update status

    📐 CRD: define your own API Expert

    A CustomResourceDefinition adds a new kind. Developers then request a database with a few lines.

    yamlapiVersion: platform.acme.io/v1
kind: Database
metadata: {name: orders-db}
spec:
  engine: postgres
  version: "16"
  storageGB: 50

    🧑‍🔧 Operator in Go (kubebuilder) Expert

    gofunc (r *DatabaseReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var db platformv1.Database
    if err := r.Get(ctx, req.NamespacedName, &db); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    sts := buildStatefulSet(&db)            // desired
    ctrl.SetControllerReference(&db, sts, r.Scheme)
    if _, err := controllerutil.CreateOrUpdate(ctx, r.Client, sts, func() error { return nil }); err != nil {
        return ctrl.Result{}, err
    }
    db.Status.Ready = true
    return ctrl.Result{}, r.Status().Update(ctx, &db)
}
    ⚠️
    Use finalizers for cleanup of external resources, set owner references so children are garbage collected, and never block the loop with long calls.

    🪜 Operator capability levels Expert

    📖 What it is

    The Operator Capability Model grades how much day-2 work an operator automates.

    🎯 Why it matters

    It gives you a roadmap: do not start with auto-tuning before install and upgrade are reliable.

    🧩 Types

    • Level 1: basic install
    • Level 2: seamless upgrades
    • Level 3: full lifecycle: backup, restore, failure recovery
    • Level 4: deep insights: metrics, alerts, logs
    • Level 5: auto pilot: auto-scaling, tuning, healing

    🧪 Example

    A Postgres operator: L1 creates a cluster, L2 upgrades 15 to 16, L3 takes WAL backups and restores, L4 exposes replication lag, L5 resizes storage automatically.

    🌍 Admission control, multi-cluster and safe upgrades Expert

    📖 What it is

    Admission controllers can validate or mutate objects at the API. Multi-cluster management runs many clusters consistently.

    🎯 Why it matters

    At scale one cluster per region or per tenant is normal; policy and upgrades must be automated.

    🧩 Types

    • Validating webhook / Kyverno: reject pods running as root.
    • Mutating webhook: inject sidecars or default labels.
    • Fleet GitOps: ArgoCD ApplicationSets deploy one app to all clusters.
    • Upgrade strategy: upgrade a canary cluster first, then waves; check deprecated APIs with kubectl-convert or Pluto.

    🧪 Example

    yamlapiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: {name: disallow-root}
spec:
  validationFailureAction: Enforce
  rules:
  - name: run-as-non-root
    match: {any: [{resources: {kinds: [Pod]}}]}
    validate:
      message: "Containers must not run as root"
      pattern: {spec: {securityContext: {runAsNonRoot: true}}}

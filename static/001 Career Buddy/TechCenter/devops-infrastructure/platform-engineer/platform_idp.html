    Module 01 · Foundations

    What is an Internal Developer Platform?

    An IDP is the self-service layer that lets developers get infrastructure, pipelines and environments without filing tickets.

    🏗️ What is an IDP? Basic

    An Internal Developer Platform is a curated set of tools, APIs and workflows built by a platform team so developers can self-serve what they need to build, ship and run software.

    🍽️
    Analogy: a company canteen. You do not buy raw ingredients and cook; you pick from a tested menu. The platform is the canteen, the Golden Path is the recommended meal.
    🧑‍💻
    Developer portal
    The UI/catalog devs see (Backstage, Port).
    ⚙️
    Platform orchestrator
    The engine that provisions things (Terraform, Crossplane, Humanitec).
    🛤️
    Golden Path
    The paved, supported way to do a task.

    🗺️ Big picture diagram Basic

    Developer self-service flow through an IDP

    🛤️ Golden Paths explained Basic

    A Golden Path is an opinionated, pre-wired route for a common task, e.g. “create a new Python API”. It bundles repo, CI, Kubernetes manifests, monitoring and docs.

    Pick template→Fill form→Repo + CI created→Deployed to dev→Dashboards ready
    💡
    Golden Paths are optional but easiest. If they are mandatory, you built a cage, not a path.

    🏛️ Types of platforms and what each is for Basic

    📖 What it is

    Platforms differ in how much they do for developers. Knowing the type tells you what to build first.

    🎯 Why it matters

    Teams often buy a portal before they have anything for the portal to call. Picking the right type avoids a pretty page with no automation behind it.

    🧩 Types

    • Portal-only: a catalog and docs front-end; links out to existing tools. Quick win, little automation.
    • Pipeline-centred: standard CI/CD templates every team reuses. Good first step for delivery consistency.
    • Orchestrator-based: a backend that provisions infrastructure from a developer request (Humanitec, Crossplane, Terraform automation).
    • Full IDP: portal + orchestrator + guardrails + metrics, run as a product.

    🧪 Example

    A 20-person company starts pipeline-centred (one shared GitHub Actions template). At 200 engineers it adds Backstage for discovery, then Crossplane so developers can request a database without a ticket.

    📶 Platform maturity levels Basic

    📖 What it is

    A maturity model describes how far a platform has progressed, from ad hoc scripts to a measured product.

    🎯 Why it matters

    It helps you set realistic goals and explain to leadership why investment is needed.

    🧩 Types

    • Level 1 Provisional: ad hoc scripts, ticket-driven, few users.
    • Level 2 Operationalised: shared tooling and a small team, some self-service.
    • Level 3 Scalable: product management, multiple Golden Paths, defined SLOs.
    • Level 4 Optimising: data-driven, platform improves itself from usage metrics.

    🧪 Example

    Self-check: Can a new developer deploy to production on day one without asking anyone? If yes, you are at least Level 3 for onboarding.

    Module 02 · Tooling

    Backstage and Port in practice

    Learn the main building blocks of the two most common portals and see real configuration.

    📚 Software Catalog Intermediate

    The catalog is the single inventory of services, owners, APIs and docs. In Backstage every component is described by a catalog-info.yaml in its repo.

    yamlapiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: payments-api
  description: Handles card payments
  annotations:
    github.com/project-slug: acme/payments-api
spec:
  type: service
  lifecycle: production
  owner: team-payments
  dependsOn: [resource:payments-db]

    🧩 Software Templates (Scaffolder) Intermediate

    Templates power Golden Paths: a form collects inputs, then steps create the repo, register it in the catalog and open a PR.

    yamlapiVersion: scaffolder.backstage.io/v1beta3
kind: Template
metadata: {name: python-api}
spec:
  owner: platform-team
  type: service
  parameters:
    - title: Service info
      properties:
        name: {type: string}
  steps:
    - id: fetch
      action: fetch:template
      input: {url: ./skeleton, values: {name: ${{ parameters.name }}}}
    - id: publish
      action: publish:github
      input: {repoUrl: github.com?repo=${{ parameters.name }}&owner=acme}
    - id: register
      action: catalog:register
      input: {repoContentsUrl: ${{ steps.publish.output.repoContentsUrl }}}

    📖 TechDocs & Plugins Intermediate

    TechDocs renders Markdown from the repo as docs inside the portal (docs-as-code). Plugins add views such as Kubernetes status, PagerDuty, or CI runs on each service page.

    🏗️ Backstage architecture in detail Intermediate

    📖 What it is

    Backstage has a React frontend, a Node.js backend, a database (PostgreSQL in production), and plugins that add pages and backend logic. Authentication uses providers such as GitHub, Okta or Azure AD. The catalog ingests entities from Git by scanning repositories for catalog-info.yaml.

    🎯 Why it matters

    Understanding the parts tells you what to scale, secure and upgrade. Most production issues are plugin versions, catalog ingestion errors and auth misconfiguration.

    🧩 Types

    • Entity kinds: Component, API, Resource, System, Domain, Group, User.
    • Relations: ownedBy, dependsOn, providesApi, consumesApi; these build the dependency graph.
    • Providers: GitHub, GitLab or LDAP discovery that auto-registers entities.

    🧪 Example

    yaml# app-config.yaml (excerpt)
auth:
  providers:
    github: {development: {clientId: ${GH_ID}, clientSecret: ${GH_SECRET}}}
catalog:
  providers:
    github:
      acme:
        organization: acme
        catalogPath: /catalog-info.yaml
        schedule: {frequency: {minutes: 30}, timeout: {minutes: 3}}

    🎛️ Port: blueprints, entities and self-service actions Intermediate

    📖 What it is

    Port models your software as blueprints (a schema, like a class), entities (instances) and actions (buttons that trigger automation). Data arrives from integrations (GitHub, Kubernetes, PagerDuty) so no manual upkeep.

    🎯 Why it matters

    You get a catalog and self-service without writing a React app, which is why teams reach value in days.

    🧩 Types

    • Blueprint: defines properties and relations, e.g. Service, Environment, Database.
    • Action: self-service form that triggers a webhook, GitHub workflow or pipeline.
    • Scorecard: rules that rate each entity, e.g. has on-call and runbook.

    🧪 Example

    json{ "identifier": "service",
  "title": "Service",
  "schema": { "properties": {
    "language": {"type": "string", "enum": ["go","python","java"]},
    "tier": {"type": "string", "enum": ["critical","standard"]} } },
  "relations": { "team": {"target": "team", "many": false} } }

    Module 03 · Scale

    Designing an IDP at scale

    Move from a portal that lists things to a platform that governs and measures them.

    🧬 Reference architecture Expert

    Five planes: Developer control (portal), Integration & delivery (Git, CI/CD), Resource (Terraform/Crossplane), Monitoring, Security.

    Portal→Git→CI→Orchestrator→Cluster / Cloud

    ✅ Scorecards & maturity Expert

    Scorecards grade each service on production readiness (owner set, runbook, SLO, on-call, no critical CVEs). Show a score, do not block, and let teams see how to improve.

    json{ "identifier": "prod-readiness",
  "rules": [
    {"property": "owner", "operator": "isNotEmpty"},
    {"property": "runbook_url", "operator": "isNotEmpty"},
    {"property": "slo_defined", "operator": "=", "value": true} ] }

    🔌 Extending with custom actions Expert

    Wrap internal APIs as scaffolder actions or portal self-service actions, e.g. “request a database” calls your provisioning API and returns the connection secret reference.

    ⚠️
    Anti-patterns: a portal nobody owns, stale catalog data, mandatory templates with no escape hatch, building before talking to developers.

    🧭 Designing and versioning a Golden Path Expert

    📖 What it is

    Designing a Golden Path is a repeatable process: study the most common journey, remove choices that do not help, automate the rest, then maintain it like a product.

    🎯 Why it matters

    Unversioned paths drift. Services created last year silently differ from today's standard.

    🧩 Types

    • Step 1 Discover: map the journey from idea to production and time each step.
    • Step 2 Standardise: choose language, CI, runtime, observability defaults.
    • Step 3 Automate: encode in a template plus pipeline plus policy.
    • Step 4 Version: tag template versions and publish upgrade PRs to existing services (e.g. Renovate, Cookiecutter-based updates).

    🧪 Example

    Template python-api v2.1 moves from Flask to FastAPI. The platform opens an automated pull request in every v2.0 repo, so adoption of the new standard needs one click, not a migration project.

    🛡️ Governance, RBAC and multi-tenancy in the portal Expert

    📖 What it is

    Governance controls who can see and do what in the portal and what policies apply to anything it creates.

    🎯 Why it matters

    A portal that can create cloud resources is also a powerful attack surface if every user has every action.

    🧩 Types

    • RBAC: limit actions by team and environment (only SREs may create prod).
    • Policy as code: OPA or Kyverno checks run on everything created by templates.
    • Audit: every action recorded with who, what, when.
    • Cost guardrails: quotas and TTLs on self-service resources.

    🧪 Example

    The create-database action allows small and medium for developers; large needs a manager approval step in the workflow.

    Module 01 · Foundations

    Infrastructure as Code Basics

    IaC means describing servers, networks and permissions in text files, stored in Git, and letting a tool build them. Clicking in a console does not scale and cannot be reviewed.

    📝 What is IaC? Basic

    You write the desired state (e.g. "one VPC, three subnets, one database"). The tool compares it with reality and makes the changes needed.

    🏗️
    Analogy: an architect's blueprint. Anyone can rebuild the same house from it, review it before building, and see exactly what changed between versions.

    ❌ Manual console clicks

    • Nobody knows who changed what

    • Dev and prod drift apart

    • Slow, error-prone rebuilds

    • No review, no rollback

    ✅ Infrastructure as Code

    • Every change is a Git commit

    • Identical environments from the same code

    • Rebuild in minutes

    • Pull-request review and history

    🧩 Types of IaC tools Basic

    StyleIdeaExamples
    DeclarativeSay what you want; tool works out the stepsTerraform, OpenTofu, CloudFormation, Bicep
    ImperativeSay how, step by stepShell scripts, AWS CLI, Pulumi (code with state)
    Programming-language basedReal languages that generate or drive templatesAWS CDK, Pulumi, CDK for Terraform
    Configuration managementConfigure inside serversAnsible, Chef, Puppet
    ToolScopeLanguageState
    TerraformMulti-cloudHCLState file
    OpenTofuMulti-cloud (open-source Terraform fork)HCLState file
    CloudFormationAWS onlyYAML / JSONManaged by AWS (stacks)
    AWS CDKAWS (generates CloudFormation)TypeScript, Python, Java, Go, C#CloudFormation stacks
    Azure BicepAzure onlyBicep DSLManaged by Azure (ARM)

    🔑 Key ideas Intermediate

    • Idempotent: applying twice gives the same result.
    • State: a record of what exists, used to calculate changes.
    • Plan, then apply: preview changes before they happen.
    • Drift: reality differs from code because someone changed it by hand.
    • Immutable infrastructure: replace instead of patching in place.
    Write code→Git pull request→Plan→Review→Apply→Monitor drift

    Module 02 · Terraform

    Terraform

    Terraform (HashiCorp) uses HCL to manage resources across thousands of providers: AWS, Azure, Google, Kubernetes, GitHub, Datadog and more.

    🧱 Core building blocks Basic

    BlockPurpose
    providerPlugin that talks to an API (aws, azurerm, google)
    resourceSomething to create (bucket, VM, role)
    dataRead existing information
    variableInput parameter
    outputValue exposed after apply
    moduleReusable bundle of resources
    localsNamed expressions
    hclterraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}
provider "aws" { region = var.region }

variable "region" { default = "eu-west-1" }

resource "aws_s3_bucket" "logs" {
  bucket = "acme-logs-${var.env}"
  tags   = { Env = var.env, Owner = "platform" }
}
output "bucket_arn" { value = aws_s3_bucket.logs.arn }

    ⌨️ The workflow Basic

    bashterraform init      # download providers and modules
terraform fmt       # format code
terraform validate  # check syntax
terraform plan      # preview: + create  ~ change  - destroy
terraform apply     # execute the plan
terraform destroy   # remove everything
    ⚠️
    Always read the plan. A -/+ (replace) on a database means data loss.

    🗃️ State and remote backends Intermediate

    State maps your code to real resources. Never keep it on a laptop for a team: use a remote backend with locking.

    hclterraform {
  backend "s3" {
    bucket         = "acme-tf-state"
    key            = "prod/network.tfstate"
    region         = "eu-west-1"
    dynamodb_table = "tf-locks"      # state locking
    encrypt        = true
  }
}
    📌
    State can hold secrets in plain text. Encrypt the bucket, restrict access, and never commit state to Git.

    📦 Modules and loops Intermediate

    Modules remove copy-paste. Call one for each environment:

    hclmodule "vpc" {
  source   = "git::https://github.com/acme/tf-modules.git//vpc?ref=v2.3.0"
  name     = "prod"
  cidr     = "10.0.0.0/16"
  az_count = 3
}

resource "aws_iam_user" "devs" {
  for_each = toset(["asha", "ravi", "mei"])
  name     = each.key
}

    🧠 Expert: workspaces, imports, moved blocks, testing Expert

    • Separate state per environment and per layer (network, data, apps) to shrink blast radius.
    • import block brings existing resources under management; moved block refactors without destroy.
    • lifecycle { prevent_destroy = true } on critical resources.
    • Test with terraform test, Terratest, and scan with tfsec / Checkov / Trivy.
    hclimport {
  to = aws_s3_bucket.legacy
  id = "acme-legacy-bucket"
}
moved {
  from = aws_instance.web
  to   = module.web.aws_instance.this
}

    Module 03 · OpenTofu

    OpenTofu

    OpenTofu is an open-source fork of Terraform created in 2023 after HashiCorp moved Terraform to the Business Source License. It is governed by the Linux Foundation under the MPL 2.0 license.

    🍴 What it is and why it exists Basic

    • Same HCL language, providers and workflow as Terraform (up to the fork point).
    • Command is tofu instead of terraform.
    • Community-driven roadmap through the Linux Foundation.
    TerraformOpenTofu
    LicenseBSL (source-available)MPL 2.0 (open source)
    Commandterraformtofu
    GovernanceHashiCorp (now IBM)Linux Foundation, community
    Registryregistry.terraform.ioregistry.opentofu.org
    Notable extrasHCP Terraform integrationBuilt-in state encryption, early variable evaluation
    📌
    Features differ as the projects evolve; check release notes before assuming parity.

    🔄 Migrating from Terraform Intermediate

    bashtofu init      # re-initialise with OpenTofu providers
tofu plan      # should show no changes
tofu apply
    • Back up state first.
    • Pin versions and test in a non-prod workspace.
    • Check any HCP Terraform / Sentinel dependencies.

    🔐 State encryption example Expert

    Encrypt state and plan files at rest with a key you control:

    hclterraform {
  encryption {
    key_provider "pbkdf2" "main" { passphrase = var.state_passphrase }
    method "aes_gcm" "default"  { keys = key_provider.pbkdf2.main }
    state { method = method.aes_gcm.default }
    plan  { method = method.aes_gcm.default }
  }
}

    Module 04 · AWS native

    AWS CloudFormation and CDK

    CloudFormation is AWS's own declarative engine. AWS CDK lets you write infrastructure in a normal programming language, then synthesises CloudFormation.

    ☁️ CloudFormation basics Basic

    A template (YAML/JSON) defines resources; deploying it creates a stack. AWS stores the state for you and rolls back on failure.

    ConceptMeaning
    TemplateThe code
    StackA deployed instance of a template
    Change setPreview of changes (like terraform plan)
    StackSetsDeploy one template to many accounts/regions
    Drift detectionFinds manual changes
    yamlAWSTemplateFormatVersion: "2010-09-09"
Parameters:
  Env: {Type: String, Default: dev}
Resources:
  LogBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub "acme-logs-${Env}"
      VersioningConfiguration: {Status: Enabled}
Outputs:
  BucketArn: {Value: !GetAtt LogBucket.Arn}

    💻 AWS CDK: infrastructure in TypeScript Intermediate

    Constructs come in three levels: L1 (raw CloudFormation), L2 (sensible defaults), L3 (patterns).

    typescriptimport * as cdk from 'aws-cdk-lib';
import * as s3 from 'aws-cdk-lib/aws-s3';

class StorageStack extends cdk.Stack {
  constructor(scope: cdk.App, id: string) {
    super(scope, id);
    new s3.Bucket(this, 'Logs', {
      versioned: true,
      encryption: s3.BucketEncryption.S3_MANAGED,
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
    });
  }
}
new StorageStack(new cdk.App(), 'StorageStack');
    bashcdk bootstrap   # one-time per account/region
cdk diff        # preview
cdk deploy

    ⚖️ Terraform vs CloudFormation vs CDK Expert

    NeedBest fit
    Multi-cloud or SaaS providersTerraform / OpenTofu
    AWS only, no state to manageCloudFormation
    Developers who prefer loops, types and testsAWS CDK
    Same-day support for new AWS featuresCloudFormation / CDK (usually first)
    💡
    Use cdk-nag to apply AWS Solutions security rules to CDK apps automatically.

    Module 05 · Azure native

    Azure Bicep

    Bicep is a clean language that compiles to ARM templates. It replaces verbose ARM JSON and is the recommended native IaC for Azure.

    💪 Basics Basic

    • Declarative, no state file: Azure Resource Manager tracks resources.
    • Day-0 support for new Azure resource types.
    • Scopes: resource group, subscription, management group, tenant.
    bicepparam location string = resourceGroup().location
param env string = 'dev'

resource storage 'Microsoft.Storage/storageAccounts@2023-01-01' = {
  name: 'acmelogs${env}${uniqueString(resourceGroup().id)}'
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
  properties: {
    minimumTlsVersion: 'TLS1_2'
    allowBlobPublicAccess: false
  }
}
output storageId string = storage.id
    bashaz deployment group what-if -g rg-app -f main.bicep   # preview
az deployment group create  -g rg-app -f main.bicep

    🧩 Modules and loops Intermediate

    Reuse with modules and create many resources with loops:

    bicepmodule vnet 'modules/vnet.bicep' = {
  name: 'vnetDeploy'
  params: { name: 'hub', addressPrefix: '10.0.0.0/16' }
}

var subnets = ['web', 'app', 'data']
resource sn 'Microsoft.Network/virtualNetworks/subnets@2023-05-01' = [for (s, i) in subnets: {
  name: '${vnet.outputs.name}/${s}'
  properties: { addressPrefix: '10.0.${i}.0/24' }
}]
    📌
    Publish shared modules to an Azure Container Registry or the public Bicep registry and pin versions.

    Module 06 · Guardrails

    Cloud Governance Policies

    Governance keeps teams fast and safe: rules for security, cost, compliance and consistency, enforced by code rather than by email.

    🏛️ Pillars of governance Basic

    Governance rests on a few pillars:

    🔐
    Security & compliance
    Encryption, public access blocks, approved regions
    💰
    Cost
    Budgets, tags, rightsizing, quotas
    🏷️
    Tagging
    Owner, cost centre, environment, data class
    🗂️
    Account structure
    Org, OUs, accounts / subscriptions per workload
    📜
    Audit & logging
    CloudTrail, Activity Log, central logging account

    🛡️ Preventive vs detective controls Intermediate

    TypeWhenExamples
    PreventiveBlocks bad action before it happensAWS SCP, Azure Policy deny, permission boundaries, Terraform policy gates
    DetectiveFinds problems after the factAWS Config, Security Hub, Azure Defender, drift detection
    CorrectiveFixes automaticallyConfig remediation, Azure Policy modify/deployIfNotExists, Lambda auto-fix
    json// AWS SCP: block leaving approved regions (except global services)
{ "Effect": "Deny",
  "NotAction": ["iam:*", "organizations:*", "route53:*", "cloudfront:*", "support:*"],
  "Resource": "*",
  "Condition": { "StringNotEquals": {
      "aws:RequestedRegion": ["eu-west-1", "eu-central-1"] } } }

    📐 Azure Policy example Intermediate

    Deny storage accounts that allow public blob access:

    json{
  "if": { "allOf": [
    { "field": "type", "equals": "Microsoft.Storage/storageAccounts" },
    { "field": "Microsoft.Storage/storageAccounts/allowBlobPublicAccess", "equals": true }
  ]},
  "then": { "effect": "deny" }
}

    🤖 Expert: policy as code in the pipeline Expert

    Check plans before apply, using Open Policy Agent (OPA/Conftest), HashiCorp Sentinel, Checkov or tfsec.

    regopackage terraform

deny[msg] {
  r := input.resource_changes[_]
  r.type == "aws_s3_bucket"
  not r.change.after.tags.Owner
  msg := sprintf("Bucket %v must have an Owner tag", [r.address])
}
    Pull request→fmt + validate→plan→Policy check (OPA / Checkov)→Approval→Apply
    ✅
    Pair with a landing zone (AWS Control Tower, Azure Landing Zones) so every new account starts with logging, guardrails and network already in place.

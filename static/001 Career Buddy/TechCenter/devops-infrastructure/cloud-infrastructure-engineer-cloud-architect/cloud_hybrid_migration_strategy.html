    Module 01 · Foundations

    Cloud Migration Basics

    Migration means moving applications, data and workloads to the cloud (or between clouds) with minimum risk, downtime and cost surprise.

    🚚 Why migrate? Basic

    Common drivers: closing a data centre, avoiding hardware refresh, scaling on demand, using managed services, disaster recovery, or meeting a business deadline (such as a lease ending).

    🏠
    Analogy: moving house. You decide what to take as-is, what to replace, what to throw away, and what to leave behind, and you pack in waves, not all in one night.

    ❌ Lift everything blindly

    • Unknown dependencies break at cutover

    • Costs spike (oversized servers)

    • No rollback plan

    • Legacy problems moved, not fixed

    ✅ Planned migration

    • Discovered inventory and dependency map

    • Right-sized targets, cost forecast

    • Waves with tested rollback

    • Each app gets a deliberate strategy

    🗺️ The three phases Basic

    AWS describes migration as three phases; Azure and Google use similar steps.

    Assess→Mobilize→Migrate and Modernize
    PhaseGoalTypical outputs
    AssessKnow what you have and the business caseInventory, TCO, readiness score
    MobilizeBuild the foundation and skillsLanding zone, networking, security baseline, pilot
    Migrate & modernizeMove in waves, then improveCutovers, decommission, optimisation

    📋 Discovery: what to collect Intermediate

    • Servers: CPU, memory, disk, OS, utilisation (at least 2–4 weeks of data)
    • Dependencies: who talks to whom, ports, external systems
    • Licensing, compliance and data-residency rules
    • Business criticality, owners and allowed downtime
    📌
    Tools: AWS Application Discovery Service / Migration Hub, Azure Migrate, Google Migration Center, plus CMDB exports.

    Module 02 · Strategy

    Cloud Migration Patterns (the 6 Rs)

    Every application gets one strategy. Gartner coined five Rs; AWS grew it to six (and a seventh, Relocate).

    🔁 The strategies at a glance Basic

    RMeaningEffortExample
    Rehost"Lift and shift": same VM in the cloudLowMove a VMware VM to EC2 with Application Migration Service
    Replatform"Lift, tinker and shift": small changes for managed servicesLow–MedSelf-managed MySQL → Amazon RDS
    RepurchaseReplace with SaaSMediumOn-prem CRM → Salesforce; Exchange → Microsoft 365
    Refactor / Re-architectRedesign cloud-nativeHighMonolith → microservices on Lambda / containers
    RetireSwitch offVery lowUnused reporting server decommissioned
    RetainKeep where it is for nowNoneMainframe with compliance limits, revisit later
    Relocate (7th)Move VMware estate without changesLowVMware Cloud on AWS

    ⚖️ Choosing a strategy Intermediate

    A simple decision path per application:

    Still needed?→No → Retire→SaaS exists? → Repurchase→Hard to move? → Retain→Need speed? → Rehost→Easy managed win? → Replatform→Else → Refactor
    QuestionIf YES
    Is the app unused or duplicated?Retire
    Does a good SaaS replace it?Repurchase
    Is there a hard deadline (exit a data centre)?Rehost first, optimise later
    Is the DB/OS the main pain?Replatform
    Is scaling or velocity the business goal?Refactor

    🧮 Example: portfolio plan Intermediate

    Typical portfolio split from real programmes: most apps rehost, a smaller share is retired or repurchased, and only a few are refactored.

    pythonapps = {
 "intranet-wiki":  "Retire",
 "hr-system":      "Repurchase",     # Workday
 "orders-db":      "Replatform",     # MySQL -> RDS
 "legacy-batch":   "Rehost",
 "checkout":       "Refactor",       # to containers/serverless
 "mainframe-core": "Retain",
}
from collections import Counter

    🧠 Expert: wave planning Expert

    • Wave 0: pilot with low-risk apps to prove the landing zone and runbooks.
    • Group apps by dependency, so chatty systems move together (avoid cross-site latency).
    • Pick cutover windows by business calendar.
    • Keep a rollback path (replication stays on until sign-off).
    • Track metrics: apps migrated, cost vs forecast, incidents per wave.
    ⚠️
    Refactoring everything first is the classic failure: the programme runs out of time. Rehost to meet the date, then modernise with data from running in the cloud.

    Containerized Platforms

    Containers package an app and its dependencies so it runs the same everywhere, which makes them the favourite stepping stone between rehost and full refactor.

    📦 Containers vs VMs Basic

    Virtual machineContainer
    IncludesFull guest OSApp + libraries, shares host kernel
    Start timeMinutesSeconds
    SizeGBsMBs
    IsolationStrong (hypervisor)Process-level (namespaces, cgroups)
    DensityTens per hostHundreds per host
    dockerfileFROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
USER 1000
CMD ["gunicorn", "-b", "0.0.0.0:8080", "app:app"]

    🧭 Platform options Intermediate

    OptionLevelBest forExamples
    Serverless containersYou manage only the containerSimple services, no cluster opsAWS Fargate, Cloud Run, Azure Container Apps
    Managed container serviceProvider-specific orchestratorAWS-only simplicityAmazon ECS
    Managed KubernetesProvider runs the control planePortability, rich ecosystemEKS, AKS, GKE
    Self-managed KubernetesYou run everythingOn-prem, special needskubeadm, OpenShift, Rancher

    ☸️ Kubernetes example Intermediate

    A Deployment keeps three replicas running and a Service gives them one stable address.

    yamlapiVersion: apps/v1
kind: Deployment
metadata: {name: web}
spec:
  replicas: 3
  selector: {matchLabels: {app: web}}
  template:
    metadata: {labels: {app: web}}
    spec:
      containers:
      - name: web
        image: myreg.example/web:1.4.2
        ports: [{containerPort: 8080}]
        resources:
          requests: {cpu: 250m, memory: 256Mi}
          limits:   {memory: 512Mi}
---
apiVersion: v1
kind: Service
metadata: {name: web}
spec:
  selector: {app: web}
  ports: [{port: 80, targetPort: 8080}]

    Module 04 · Link

    Hybrid Cloud Connectivity

    Hybrid means some workloads stay on-premises while others run in the cloud, so the network between them becomes critical.

    🌉 Hybrid vs multi-cloud Basic

    ModelMeaningExample
    Hybrid cloudOn-prem + public cloud work togetherCore DB on-prem, web tier in AWS
    Multi-cloudTwo or more public cloudsAnalytics on GCP, apps on AWS
    Edge / distributed cloudCloud services at your siteAWS Outposts, Azure Stack HCI
    📌
    Typical reasons: data residency, latency to factory floors, long-life hardware, regulation, or a staged migration.

    🔌 Connectivity options Intermediate

    OptionBandwidthLatencySetupUse
    Site-to-site VPNUp to ~1.25 Gbps per tunnelVariable (internet)HoursStart, backup, small sites
    Dedicated link (Direct Connect, ExpressRoute, Interconnect)1–100 GbpsLow, stableWeeksProduction hybrid, bulk data
    SD-WANAggregatedOptimisedDaysMany branches
    Colocation / cloud exchange (Equinix, Megaport)FlexibleLowDaysMulti-cloud private paths
    Data centre→Router (BGP)→Direct Connect + VPN backup→Transit Gateway→VPCs

    🧾 Example: VPN with Terraform Intermediate

    Create the AWS side of a site-to-site VPN (you supply your router's public IP).

    hclresource "aws_customer_gateway" "office" {
  bgp_asn    = 65010
  ip_address = "203.0.113.10"      # on-prem router public IP
  type       = "ipsec.1"
}
resource "aws_vpn_connection" "to_office" {
  customer_gateway_id = aws_customer_gateway.office.id
  transit_gateway_id  = aws_ec2_transit_gateway.hub.id
  type                = "ipsec.1"
}
    ⚠️
    Plan IP ranges early: overlapping on-prem and cloud CIDRs are the number one hybrid blocker. Also plan hybrid DNS (forwarders both ways) and identity (federate your directory).

    🛡️ Expert: resilience and routing Expert

    • Two dedicated links in two locations, plus VPN as tertiary path.
    • Use BGP with route filters and prefix limits; prefer the dedicated path via local preference or AS-path prepending.
    • Enable BFD for fast failover.
    • Encrypt dedicated links (MACsec or IPsec over the link) when required.
    • Test failover with scheduled drills, not during an outage.

    Migration Tools, Data and Cutover

    Picking the right mover for servers, databases and bulk data saves weeks.

    🧰 Tools by workload Intermediate

    WorkloadAWSAzureGoogle Cloud
    Servers (rehost)Application Migration Service (MGN)Azure MigrateMigrate to Virtual Machines
    DatabasesDatabase Migration Service (DMS) + Schema Conversion ToolAzure Database Migration ServiceDatabase Migration Service
    Bulk offline dataSnowball / SnowconeData BoxTransfer Appliance
    Online file transferDataSyncAzCopy / Storage MoverStorage Transfer Service

    🔄 Cutover patterns Intermediate

    PatternHowDowntimeRisk
    Big bangStop, copy, switchHoursHigh, hard rollback
    Phased / waveMove apps in groupsPer appMedium
    Parallel runBoth sites live, compareNear zeroCost of two environments
    Replicate then switchContinuous sync, short final cutoverMinutesLow
    Initial copy→Continuous replication→Test in cloud→Freeze→Cutover (DNS / LB)→Hold rollback window

    🏁 Expert: landing zone and FinOps Expert

    • Landing zone first: accounts/subscriptions, network, identity, logging, guardrails ready before wave 1 (AWS Control Tower, Azure Landing Zones).
    • Rightsize after 30 days of real metrics; use Savings Plans/Reservations only after stable.
    • Decommission the source: unused data centre cost is the biggest missed saving.
    • Tag everything with owner and cost centre from day one.
    ✅
    Success check: cost per workload tracked, incidents per wave falling, old hardware switched off, and a backlog of modernisation work prioritised by data.

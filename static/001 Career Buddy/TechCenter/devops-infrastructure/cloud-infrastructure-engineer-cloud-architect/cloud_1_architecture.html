    Cloud Fundamentals

    What cloud is, service and deployment models, shared responsibility, regions and zones — plus a cross-cloud service cheat-sheet.

    ☁️ What is cloud computing? Basic

    Cloud computing means renting computing resources — servers, storage, databases, networking, AI — over the internet from a provider, on demand, and paying only for what you use, instead of buying and running your own data centre.

    🔌
    Analogy: electricity. You don't build a power plant; you plug in and pay per unit. Cloud is compute-as-a-utility: switch on 100 servers for an hour, then switch them off.

    Five essential characteristics (NIST)

    🖱️
    On-demand self-service
    Provision resources yourself in minutes, no ticket to a vendor.
    🌐
    Broad network access
    Reachable over the network from many device types.
    🧮
    Resource pooling
    Provider shares hardware across many customers (multi-tenancy).
    📈
    Rapid elasticity
    Scale out and in automatically as demand changes.
    📏
    Measured service
    Metered usage, pay-as-you-go billing.

    Example: a ticket-booking site expects 50× traffic on a film release day. On-premises you must buy servers for the peak and they idle the other 364 days. In the cloud you scale to 200 instances for the day and back to 4 afterward.

    🥞 Service models: IaaS, PaaS, SaaS, FaaS Basic

    Analogy — pizza: IaaS = buy a kitchen and make it yourself; PaaS = take-and-bake; SaaS = eat at the restaurant.

    🤝 Shared responsibility model Basic

    Security in the cloud is split. The provider secures "of the cloud" (data centres, hardware, hypervisor). You secure "in the cloud" (your data, identities, configuration, network rules).

    🏭 Provider's job

    • Physical security of data centres

    • Power, cooling, hardware

    • Hypervisor and core network

    • Managed-service software patching (PaaS)

    🧑‍💻 Your job

    • IAM and access policies

    • Data classification and encryption choices

    • Network rules (security groups / firewalls)

    • OS patching on IaaS VMs

    • Application code and configuration

    ⚠️
    Most real cloud breaches are customer misconfiguration — a public storage bucket, an over-permissive role — not provider failures.

    Well-Architected Frameworks

    The AWS, Azure and Google Cloud frameworks: pillars, examples, comparison and how to run a review.

    🏛️ What is a Well-Architected Framework? Basic

    A Well-Architected Framework (WAF) is a provider-published set of pillars, design principles and review questions that help you judge whether a workload is secure, reliable, efficient and cost-effective. All three major clouds publish one.

    🏗️
    Analogy: a building-code checklist. It doesn't draw your house, but it tells the inspector what to check: fire exits (reliability), locks (security), electricity bill (cost).

    It is a conversation tool, not a certification: you review a workload, find risks, and plan improvements. Trade-offs between pillars are expected — e.g. higher reliability costs more.

    🟧 AWS Well-Architected — six pillars Basic

    PillarCore questionExample practice
    Operational ExcellenceHow do we run and improve operations?Infrastructure as code; small frequent deployments; runbooks; post-incident learning
    SecurityHow do we protect data and systems?Least-privilege IAM, encryption at rest/in transit, CloudTrail logging, MFA
    ReliabilityHow does the workload recover from failure?Multi-AZ, auto scaling, health checks, tested backups, quotas monitoring
    Performance EfficiencyAre resources right for the job?Right-size instances, caching, CDN, pick managed services, load test
    Cost OptimizationDo we avoid unnecessary spend?Budgets & tags, Savings Plans/Reserved, shut down dev at night, S3 lifecycle
    SustainabilityDo we minimise environmental impact?Efficient hardware (Graviton), higher utilisation, regions with cleaner energy

    AWS provides the Well-Architected Tool in the console and lenses for serverless, SaaS, machine learning, data analytics, etc.

    🔬 Applying a WAF — worked example Intermediate

    Workload: an online store on one EC2 server, one database, public IP, admin credentials in code.

    PillarFinding (risk)Fix
    ReliabilitySingle server and DB = single point of failureTwo AZs, load balancer, Auto Scaling, RDS Multi-AZ
    SecurityCredentials in source code; wide-open security groupSecrets Manager; least-privilege IAM role; SG allows only LB
    OperationsManual deployments by SSHIaC + CI/CD pipeline, blue/green
    PerformanceAll images served from the serverS3 + CloudFront CDN, ElastiCache
    CostServer sized for peak, runs 24/7Auto scaling, Savings Plan for baseline
    SustainabilityLow utilisationRight-size, Graviton instances

    Review process

    Define workload→Answer pillar questions→Identify risks (High/Med)→Prioritise improvement plan→Implement→Re-review regularly

    🧠 Expert: trade-offs and design principles Expert

    • Pillars conflict. Multi-region active-active (Reliability) multiplies cost and complexity. Architects document the decision with an ADR (Architecture Decision Record): context, options, decision, consequences.
    • Design by business criticality: a payroll batch job and a payment API deserve different availability targets. Tier workloads (Tier 0–3) with explicit SLOs.
    • Shift-left WAF: encode pillars as automated guardrails — policy-as-code, IaC scanning, budget alerts — not only annual reviews.
    • Common principles: stop guessing capacity · test at production scale · automate everything · evolve architectures · drive by data · rehearse failure ("game days").
    ⚠️
    Anti-patterns: treating the WAF as a one-time audit; "lift and shift" without re-architecting for the cloud; ignoring cost until the first big bill; designing for 99.999% when the business only needs 99.9%.
    🎯 Key takeaways
    • WAF = pillars + questions + review, not a certificate.
    • AWS has 6 pillars, Azure 5, GCP 5 plus system design.
    • Every finding should map to a concrete fix.
    • Document trade-offs; automate guardrails.

    Module 03 · Resilience

    High Availability

    Availability maths, redundancy, multi-AZ design, resilience patterns and expert-level static stability and cells.

    ⏱️ What is high availability? Basic

    High availability (HA) is designing a system so it keeps working — with little or no downtime — when components fail. You can't prevent failures; you design so that one failure does not stop the service.

    🏥
    Analogy: a hospital with a backup generator, two entrances and several doctors on shift. If one fails, patients are still treated.

    Availability and the "nines"

    AvailabilityDowntime / yearDowntime / monthTypical target
    99%3.65 days~7.3 hoursDev/test, batch
    99.9%8.76 hours~43 minutesStandard business apps
    99.95%4.38 hours~22 minutesImportant apps
    99.99%52.6 minutes~4.4 minutesPayments, core APIs
    99.999%5.26 minutes~26 secondsTelecom, trading — very costly

    Formula: Availability = Uptime ÷ (Uptime + Downtime).

    Vocabulary

    TermMeaning
    SPOFSingle Point of Failure — one component whose failure stops everything
    RedundancyExtra copies so another can take over
    FailoverAutomatic switch from failed to healthy component
    Fault toleranceKeeps running without any interruption when a part fails (stronger than HA)
    ResilienceAbility to recover quickly from disruption
    SLA / SLO / SLIContract / internal target / measured indicator

    🧱 Building blocks of an HA architecture Basic

    Classic multi-AZ web architecture: no single point of failure at any tier.
    ⚖️
    Load balancer
    Spreads traffic across healthy instances in multiple AZs; removes failed ones via health checks.
    📈
    Auto Scaling
    Replaces failed instances and adds capacity under load.
    🧬
    Stateless apps
    Session data in Redis/DB, not on the server — any instance can serve any user.
    🗄️
    Multi-AZ database
    Synchronous standby in another AZ with automatic failover (RDS Multi-AZ, Azure zone-redundant HA, Cloud SQL HA).
    📦
    Shared / replicated storage
    S3 / Blob / GCS replicate across AZs automatically.
    ❤️
    Health checks
    Detect failure quickly: HTTP /health, TCP, deep checks.

    🧮 Calculating availability Intermediate

    Serial (all must work): multiply availabilities. Parallel (any one is enough): 1 − (1−A)n.

    worked exampleSerial:   Web 99.9% × App 99.9% × DB 99.9%  = 0.999^3 = 99.70%    (worse than each part!)
Parallel: two web servers, each 99.9%        = 1 - (0.001)^2 = 99.9999%
Mixed:    LB 99.99% × [2 x App 99.9% in parallel = 99.9999%] × DB Multi-AZ 99.95%
          = 0.9999 × 0.999999 × 0.9995 ≈ 99.94%
    📝
    Real availability is limited by the weakest shared dependency (one DNS provider, one deployment pipeline, one region) and by human error — most outages come from bad changes, not hardware.

    🧯 Failure domains and graceful degradation Intermediate

    Instance→Rack / host→Availability Zone→Region→Provider / global

    Each step is a bigger failure domain. Spread replicas across at least two (preferably three) AZs. Use graceful degradation: if recommendations service fails, show the product page without it — don't fail the whole page.

    Resilience patterns

    PatternWhat it does
    Retry with exponential backoff + jitterRetries transient errors without overwhelming the service
    TimeoutNever wait forever
    Circuit breakerStop calling a failing dependency; fail fast; recover later
    BulkheadIsolate resource pools so one failure can't consume everything
    Queue / bufferAbsorb spikes; decouple producers from consumers
    IdempotencySafe retries (same request twice = same result)

    🧠 Expert: static stability, cell-based design, SLOs Expert

    • Static stability: after an AZ failure the system keeps working with pre-provisioned capacity — don't depend on scaling up in a crisis (control-plane may be impaired).
    • Cell-based architecture: split customers into independent "cells" (full stacks). A bad deploy or noisy tenant hits one cell, limiting blast radius to e.g. 5% of users.
    • Deployment safety: canary / blue-green, automatic rollback, change freezes; most incidents are caused by changes.
    • SLO engineering: define SLI (e.g. % requests < 300 ms and non-5xx), target SLO 99.9%, error budget = 0.1% ≈ 43 min/month. Budget burned → freeze features, fix reliability.
    • Dependency mapping: compute each dependency's availability; a hard dependency on a 99.5% service caps you at 99.5%.
    • Quotas & capacity: request quota increases and capacity reservations in advance for failover regions/AZs.
    🎯 Key takeaways
    • HA = no single point of failure across tiers and AZs.
    • Serial dependencies reduce availability; parallel redundancy raises it.
    • Use stateless apps, health checks, auto scaling, Multi-AZ data.
    • Expert level: static stability, cells, SLOs and safe deployments.

    Module 04 · Global design

    Multi-Region Redundancy

    When and how to go multi-region: patterns, global routing, data replication, consistency and operations.

    🌍 Why multi-region? Basic

    A region is large but not immortal: power events, networking faults, severe weather or faulty provider changes can affect a whole region. Multi-region architecture runs your workload in two or more regions.

    🛡️
    Disaster survival
    Region-wide outage does not stop the business.
    ⚡
    Lower latency
    Serve users from the nearest region (India + Europe + US).
    ⚖️
    Compliance / data residency
    Keep EU data in EU, Indian data in India.
    📈
    Capacity & scale
    Spread load; avoid single-region limits.
    ⚠️
    Multi-region is expensive and complex. Many workloads are better served by a well-built multi-AZ design plus a tested DR plan. Choose multi-region only when the business requirement (RTO/RPO, latency, regulation) justifies it.

    Read-local, write-globalReads served locally; writes go to one primary regionContent site: global reads, one write regionMinutes for writes
    Geo-partitioned (sharded by region)Each user's data lives in a home regionEU customers → Frankfurt onlyPer-region

    🔄 Data replication & consistency Intermediate

    Compute is easy to duplicate; data is the hard part. Two key terms:

    • Synchronous replication: write confirmed only after both copies saved → RPO ≈ 0 but higher latency (needs short distance).
    • Asynchronous replication: write confirmed locally, copied later → fast but small data loss (RPO seconds) on failure.

    CAP theorem in one minute

    During a network partition between regions you must choose: Consistency (reject some requests to stay correct) or Availability (accept requests, resolve conflicts later). Banks choose consistency; social feeds usually choose availability (eventual consistency).

    Conflict handling in active-active: last-writer-wins, versioning/CRDTs, or partition ownership (each record has a "home" region).

    🧠 Expert: operating multi-region Expert

    • Region independence: avoid shared global dependencies in the data path (a global control plane or a single identity provider is a hidden SPOF). Know which services are global vs regional.
    • Control plane vs data plane: during large outages, data planes (serving requests) are far more reliable than control planes (creating resources, changing DNS). Pre-provision and use static stability; keep failover as a simple data-plane action (health-check driven).
    • Split-brain: two regions both think they are primary → conflicting writes. Use fencing, quorum or a witness.
    • Cost control: data transfer between regions is billed — compress, replicate only what is needed, tier non-critical data to async or backup-only.
    • Compliance: verify replication doesn't move regulated data to a non-permitted country; use Org Policy / SCP region restrictions.
    • Testing: regular, automated failover and failback drills; measure actual RTO/RPO; chaos engineering (AWS Fault Injection Service, Azure Chaos Studio, Gremlin).
    🎯 Key takeaways
    • Use multi-region only when RTO/RPO, latency or law demand it.
    • Global DNS / anycast routes users to healthy regions.
    • Replication choice (sync vs async) sets RPO and latency.
    • Prefer data-plane failover and pre-provisioned capacity.

    Module 05 · Recovery

    Disaster Recovery

    RTO, RPO, the four DR strategies, backups, planning, drills and cyber-recovery.

    🌪️ What is disaster recovery (DR)? Basic

    Disaster Recovery is the plan, tools and practice for restoring systems and data after a serious disruption — region outage, ransomware, accidental deletion, data corruption, human error.

    🛡️ High availability (HA)

    • Handles small failures (server, AZ)

    • Automatic, seconds

    • Continuous operation

    🆘 Disaster recovery (DR)

    • Handles large disasters (region, data loss, attack)

    • Often a controlled declaration + runbook

    • Restore service within agreed limits

    The two numbers that drive everything

    ⏳
    RTO — Recovery Time Objective
    Maximum acceptable downtime. "We must be back within 1 hour."
    💾
    RPO — Recovery Point Objective
    Maximum acceptable data loss measured in time. "We can lose at most 5 minutes of data."
    timeline  last good backup        disaster          service restored
        |<------ RPO ------->|<------- RTO ------->|
   (data you lose)                   (time you are down)

    Related: RLO (recovery level — what % of functionality), MTD (maximum tolerable downtime), BIA (Business Impact Analysis — which systems matter and what an hour of downtime costs).

    🪜 The four DR strategies Basic

    The DR spectrum — pay more for faster recovery and less data loss.
    StrategyWhat is running in DR regionRPORTOUse for
    Backup & RestoreOnly backups (copied cross-region)HoursHours – daysNon-critical, dev/test, archives
    Pilot LightCore data replicated; minimal infra (DB), app servers OFF but defined as IaC/AMIsMinutes10s of minutesImportant systems, moderate budget
    Warm StandbyScaled-down full copy running continuouslySeconds–minutesMinutesBusiness-critical apps
    Multi-site Active-ActiveFull capacity in both regions, serving usersNear zeroNear zeroMission-critical, global

    Analogy: backup & restore = spare-parts in a box; pilot light = the gas pilot flame, ready to ignite the full burner; warm standby = a second car idling; active-active = two engines running the plane together.

    💾 Backups done right Basic

    • 3-2-1 rule: 3 copies, on 2 different media/accounts, 1 off-site (other region/account).
    • Immutability: WORM / object lock / vault lock so ransomware or an admin cannot delete backups.
    • Separate account / subscription for backup vault; restricted roles.
    • Encrypt with keys also available in DR region.
    • Test restores — an untested backup is a hope, not a backup.
    • Retention by policy: daily 35 days, monthly 12, yearly 7 (compliance driven).

    • Who declares a disaster (decision authority, criteria).

    4Update Route 53 to the DR ALB (failover record or manual switch).
    5Monitor, communicate, plan failback.

    Measured outcome: drill achieved RTO 28 min / RPO 4 s. The target was RTO 30 min — pass, but note that DNS TTL of 300 s contributed 5 minutes; reduce to 60 s.

    🧠 Expert: resilience engineering and cyber-recovery Expert

    • DR for ransomware / corruption differs from DR for outage: replicas copy the corruption too. Use point-in-time recovery, immutable backups, and a clean-room restore with scanning.
    • Automated failover vs decision-gated: automate detection; keep a human decision for region failover if false positives are costly.
    • Game days & chaos engineering: inject failure deliberately (AWS FIS, Azure Chaos Studio) and measure real RTO/RPO; track results as KPIs.
    • Dependency DR: identity (IdP), DNS, certificates, secrets, CI/CD, monitoring and third-party APIs must also survive the disaster. If your pipeline lives in the failed region you can't deploy.
    • Data consistency across services: restore DB, queue and object store to a consistent point; plan reconciliation jobs.
    • Cost model: DR cost ≈ standby infra + replication + data transfer + testing effort — compare with cost of downtime per hour from the BIA.
    • Governance: evidence for auditors (ISO 22301, SOC 2, RBI/IRDAI guidelines in India): dated test reports and remediation.
    ⚠️
    Common DR failures: backups never restored; DR region without quota; keys/secrets not replicated; runbooks outdated; failback never practised; DNS TTL too high; shared dependency in the failed region.
    🎯 Key takeaways
    • RTO = how long down; RPO = how much data lost.
    • Four strategies from cheap/slow to expensive/fast.
    • Immutable, isolated, tested backups defend against ransomware.
    • A DR plan that is not tested regularly does not exist.

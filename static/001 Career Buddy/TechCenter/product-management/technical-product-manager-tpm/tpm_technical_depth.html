    Module 01

    Technical Depth for Technical Product Managers

    The technical foundation a TPM needs: API design (REST and GraphQL), microservice architecture, data schemas and system scalability, explained for product decisions.

    🏛️ Course Overview: What the Role Needs

    A Technical Product Manager (TPM) owns products whose users are often developers or whose success depends on architecture: APIs, platforms, data and infrastructure. Technical depth lets a TPM judge options, spot risk and speak credibly with engineers.

    🔌
    API design
    Judge REST and GraphQL contracts as products.
    🧱
    Architecture
    Reason about services, boundaries and coupling.
    🗄️
    Data schemas
    Understand models, keys, migrations and evolution.
    📈
    Scalability
    Know what breaks first as load grows.
    💡
    A TPM does not out-code engineers. A TPM asks sharper questions and spots product risk hidden inside technical choices.

    🎯 Learning Objectives

    By the end of this course you will be able to:

    1. Review an API design for usability, consistency, versioning and security.
    2. Compare REST, GraphQL and gRPC and recommend one with reasons.
    3. Explain microservice boundaries, communication styles and failure modes.
    4. Read a data schema and discuss normalization, indexes and migrations.
    5. Reason about scalability: bottlenecks, caching, queues and sharding.
    6. Translate technical constraints into product impact and cost.
    7. Run an architecture review conversation with confidence.

    🧱 Basic: Monolith vs Microservices

    Figure 3.1 · A microservice architecture
    AspectMonolithMicroservices
    DeployOne unitMany independent units
    Team fitSmall teamsMany autonomous teams
    ComplexityIn the codeIn the network and operations
    ScalingWhole appPer service
    FailureFails togetherPartial failure
    Speed earlyFasterSlower to start

    ✂️ Intermediate: Service Boundaries and Communication

    Boundary ruleMeaning
    Business capabilitySplit by what the business does (payments, catalog)
    Data ownershipEach service owns its data; others ask via API
    Team ownershipOne team owns a service end to end
    Change togetherThings that change together stay together
    Figure 3.2 · Asynchronous event flow
    StyleWhenTrade-off
    Synchronous (REST/gRPC)Need an answer nowCoupling and cascading failure
    Asynchronous (queue/event)Fire and process laterEventual consistency, harder debugging

    🛟 Intermediate: Resilience Patterns

    PatternWhat it does
    TimeoutStop waiting for a slow service
    Retry with backoffTry again with growing delay
    Circuit breakerStop calling a failing service
    BulkheadIsolate resources so one failure stays local
    FallbackReturn a safe default
    IdempotencyMake retries safe

    System Scalability

    Load, bottlenecks, caching, queues, replication, sharding and capacity thinking for product decisions.

    📈 Scaling Basics

    Figure 5.1 · The scaling loop
    TechniqueHelps withCost
    CachingRead-heavy loadStale data, invalidation
    Load balancerSpreading requestsExtra component
    Read replicasRead scaleReplication lag
    QueuesSpikes and slow tasksEventual results
    ShardingWrite and data scaleComplexity
    CDNStatic and edge contentCache control

    🧮 Worked Example: Capacity Estimate

    textFeature: order history API
Users: 2,000,000 monthly, 10% daily active = 200,000
Each opens history 3 times/day = 600,000 requests/day
Average rate = 600,000 / 86,400 = about 7 requests/second
Peak (10x average) = about 70 requests/second
If one instance serves 100 req/s, a single instance suffices;
run 2-3 for availability, not for capacity.
    💡
    Estimate before debating. A quick calculation often shows the feature needs no scaling work at all, or reveals the real risk.

    Real-World Scenarios & Troubleshooting

    Case studies: a slow checkout API, a microservice split gone wrong, a risky schema migration and a partner breaking after an API change.

    🐢 Case Study: The Slow Checkout API

    p95 latency on checkout jumps from 600 ms to 3 s during sales events and conversion drops.

    Figure 8.1 · Diagnosing slow checkout
    ✅
    Outcome: one missing index and a cached price lookup cut p95 to 450 ms without new servers.

    🧩 Case Study: Microservice Split Gone Wrong

    1. Symptoms: simple features need five teams and chained calls.
    2. Cause: boundaries by technical layer, shared database tables.
    3. Action: re-draw boundaries by business capability; assign data ownership.
    4. Result: independent releases and fewer cross-team dependencies.
    Figure 8.2 · Fixing service boundaries

    🚧 Troubleshooting: A Risky Schema Migration

    StepAction
    1Estimate table size and lock risk
    2Use expand and contract in small steps
    3Rehearse in a production-like copy
    4Schedule with rollback plan and monitoring
    5Communicate window and impact

    💥 Scenario: Partner Breaks After an API Change

    A field was renamed without notice and a partner's integration fails. Restore compatibility (accept both names), contact the partner, add contract tests and a deprecation policy with usage tracking, and publish a changelog.

    Module 11

    Interview Preparation

    Questions asked in Technical Product Manager interviews about technical depth, grouped by level. Draft your answer, then compare with the model answer.

    🌱 Beginner Interview Questions

    IQ1.How would you evaluate an API design?
    Check naming and consistency, error handling, pagination, versioning, authentication, rate limits, documentation and developer experience, then link gaps to user impact.
    IQ2.REST or GraphQL?
    REST for simple, cacheable public resources; GraphQL when clients need flexible data shapes across services. Consider caching, cost control, tooling and team skill.
    IQ3.What are the trade-offs of microservices?
    Team autonomy and independent scaling against operational complexity, network failures, data consistency and testing difficulty.

    🛠️ Intermediate Interview Questions

    IQ4.How do you decide service boundaries?
    Follow business capabilities and data ownership, align with teams, and keep things that change together together.
    IQ5.How do you handle breaking API changes?
    Prefer additive changes, version when needed, give deprecation windows with usage tracking, communicate and provide migration guides.
    IQ6.What should a PM know about databases?
    Relational versus other stores, keys and indexes, migrations, consistency needs and data growth, enough to ask good questions and assess risk.

    🚀 Advanced Interview Questions

    IQ7.How do you approach scalability?
    Measure first, estimate load and peaks, find bottlenecks, then apply caching, queues, replicas or sharding as justified by cost and risk.
    IQ8.How do you read an architecture diagram?
    Identify boundaries, owners, data flows and external dependencies, trace a request end to end, and mark single points of failure.
    IQ9.What is eventual consistency?
    Data becomes consistent across components after a delay. It enables scale and decoupling but affects UX and requires careful product design.

    🏆 Expert Interview Questions

    IQ10.How do you explain technical debt to executives?
    Use business terms: slower delivery, incident risk and cost, with options and a recommendation.
    IQ11.How do you work with an architect who disagrees?
    Clarify goals and constraints, compare options with data, document the decision, and escalate only with a clear framing if still unresolved.
    IQ12.Tell me about a technical decision you influenced.
    Describe the context, options and trade-offs, how you gathered evidence, the decision and the measurable outcome.

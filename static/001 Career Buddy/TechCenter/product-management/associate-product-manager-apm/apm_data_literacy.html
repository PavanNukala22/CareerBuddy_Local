    Module 01

    Data Literacy for Product Managers

    Why data skills matter for an APM, the questions data can and cannot answer, and how basic SQL, funnels and analytics tools fit together.

    🏛️ Course Overview: What the Role Needs

    Data literacy is the ability to ask a good question, find the right numbers, read them correctly and explain what they mean. An Associate Product Manager (APM) does not need to be a data scientist, but you do need enough SQL and analytics skill to check a claim yourself instead of waiting days for someone else to run a report.

    🗄️
    Basic SQL
    Pull users, events and orders yourself with SELECT, WHERE, GROUP BY and JOIN.
    🔻
    Funnel conversion
    Measure how many users complete each step and find where they drop.
    📈
    Analytics tools
    Read Google Analytics, Mixpanel and Amplitude reports with confidence.
    🧪
    Sound judgement
    Separate real signals from noise, bias and bad data.
    💡
    A useful mental model: data answers "what happened" and "how much"; users and experiments answer "why". Strong APMs combine numbers with conversations rather than trusting either alone.

    🎯 Learning Objectives

    By the end of this course you will be able to:

    1. Turn a vague product question into a precise, measurable question with a metric and a time window.
    2. Write basic SQL: filter, sort, count, group, join tables and work with dates.
    3. Define funnel steps, calculate step and overall conversion rates and find the biggest drop-off.
    4. Segment funnels by device, channel or cohort to find who is affected.
    5. Read standard reports in Google Analytics 4, Mixpanel and Amplitude and explain how they differ.
    6. Write an event tracking plan and check that events fire correctly.
    7. Spot common data traps such as bad joins, double counting, small samples and Simpson's paradox.

    Module 02

    Basic SQL for Product Managers

    From your first SELECT to joins, dates and CTEs: the SQL an APM needs to answer product questions about users, events and orders.

    🗄️ Basic: Tables, Rows and SELECT

    A database table is like a spreadsheet: columns describe the fields, rows are the records. SQL (Structured Query Language) lets you ask questions of those tables. Think of a library catalogue: you describe what you want and the system finds it.

    usersuser_idsignup_datecountryplan
    row1012026-09-01INfree
    row1022026-09-03INpro
    row1032026-09-04USfree
    sql-- Show 10 users
SELECT user_id, signup_date, country
FROM users
LIMIT 10;
    💡
    Read a query in this order: FROM (which table) → WHERE (which rows) → GROUP BY (how to bundle) → SELECT (which columns) → ORDER BY (sorting). It is not the order you write it, but it is how it works.

    🔎 Basic: Filtering, Sorting and Counting

    ClausePurposeExample
    WHEREKeep matching rowsWHERE country = 'IN'
    AND / ORCombine conditionsWHERE plan = 'pro' AND country = 'IN'
    ORDER BYSort resultsORDER BY signup_date DESC
    COUNTCount rowsCOUNT(*)
    DISTINCTRemove duplicatesCOUNT(DISTINCT user_id)
    sql-- How many Indian users signed up in September 2026?
SELECT COUNT(*) AS new_users
FROM users
WHERE country = 'IN'
  AND signup_date >= '2026-09-01'
  AND signup_date <  '2026-10-01';
    📌
    Use COUNT(DISTINCT user_id) when you mean people, and COUNT(*) when you mean rows or events. Mixing them up is the most common beginner error.

    📊 Intermediate: GROUP BY and Aggregates

    Aggregates (COUNT, SUM, AVG, MIN, MAX) summarise many rows. GROUP BY makes one summary per group.

    sql-- Orders and revenue by country this month
SELECT u.country,
       COUNT(*)      AS orders,
       SUM(o.amount) AS revenue,
       AVG(o.amount) AS avg_order_value
FROM orders o
JOIN users u ON u.user_id = o.user_id
WHERE o.created_at >= '2026-10-01'
GROUP BY u.country
ORDER BY revenue DESC;
    RuleReason
    Every non-aggregated column in SELECT must be in GROUP BYThe database needs to know how to bundle rows
    Use WHERE to filter rows before groupingIt is faster and clearer
    Use HAVING to filter groups after groupingFor example HAVING COUNT(*) > 10

    🔗 Intermediate: JOINs

    A JOIN combines rows from two tables using a shared column, such as user_id.

    Figure 2.1 · How a join feeds an analysis
    JoinReturnsUse when
    INNER JOINOnly matching rows in both tablesYou want users who have orders
    LEFT JOINAll rows from the left table, matches from the rightYou want all users, with or without orders
    sql-- Users who signed up in September and have never ordered
SELECT u.user_id
FROM users u
LEFT JOIN orders o ON o.user_id = u.user_id
WHERE u.signup_date >= '2026-09-01'
  AND u.signup_date <  '2026-10-01'
  AND o.order_id IS NULL;
    ⚠️
    Watch for join duplication: joining one user to many orders multiplies user rows. Count with DISTINCT or aggregate before joining.

    📅 Advanced: Dates, CASE and CTEs

    Product questions are almost always about time. Use date functions to group by day or week, CASE to create categories, and CTEs (WITH) to break a long query into readable steps.

    sql-- Weekly new users, with a share who ordered within 7 days
WITH new_users AS (
  SELECT user_id, signup_date
  FROM users
  WHERE signup_date >= '2026-08-01'
),
first_orders AS (
  SELECT user_id, MIN(created_at) AS first_order_at
  FROM orders
  GROUP BY user_id
)
SELECT date_trunc('week', n.signup_date) AS week,
       COUNT(*) AS new_users,
       COUNT(f.user_id) FILTER (WHERE f.first_order_at < n.signup_date + interval '7 days') AS ordered_in_7d,
       ROUND(COUNT(f.user_id) FILTER (WHERE f.first_order_at < n.signup_date + interval '7 days') * 100.0 / COUNT(*), 1) AS pct
FROM new_users n
LEFT JOIN first_orders f ON f.user_id = n.user_id
GROUP BY 1
ORDER BY 1;
    📌
    Date function names differ by database (PostgreSQL date_trunc, BigQuery DATE_TRUNC, MySQL DATE_FORMAT). Learn the idea, then check your company's syntax.

    🏆 Expert: Writing Reliable, Readable Queries

    HabitWhy it matters
    Sanity-check totals against a known numberCatches wrong joins and filters early
    Name CTEs by meaning (new_users, first_orders)Others can review your logic
    Comment assumptions in the queryFuture you will thank you
    Test on a tiny date range firstFast feedback; cheaper queries
    Avoid SELECT * on big tablesSpeed and cost
    Ask an analyst to review important queriesA second pair of eyes avoids public mistakes
    • Know your grain: one row per user? per event? per order? Most mistakes come from mixing grains.
    • Prefer half-open date ranges (>= start and < next day) so no timestamps are missed.

    ✅ Best Practices & Common Mistakes

    ✅ Best practices

    Know the grain of each table; use COUNT(DISTINCT) for people; filter dates with half-open ranges; check totals against a known number; keep queries readable with CTEs.

    ❌ Common mistakes

    Joining without checking duplicates; counting events as users; forgetting time zones; SELECT * on huge tables; trusting a query that nobody has reviewed.

    Module 03

    Tracking Funnel Conversions

    How to define funnel steps, calculate step and overall conversion, find the biggest drop-off, segment results and build funnels in SQL.

    🔻 Basic: What a Funnel Is

    A funnel is an ordered list of steps users take toward a goal — like water narrowing through a funnel, fewer users reach each next step. It shows where users leave so you know where to look.

    Figure 3.1 · Example e-commerce funnel
    💡
    Always write the funnel as a specific goal for a specific user: "new mobile users in the first 7 days reaching their first paid order".

    🧮 Basic: Conversion Rate Maths

    MeasureFormulaExample
    Step conversionUsers at step N ÷ users at step N−11,600 ÷ 3,200 = 50%
    Overall conversionUsers at last step ÷ users at first step540 ÷ 10,000 = 5.4%
    Drop-off1 − step conversion1 − 50% = 50%
    Absolute dropUsers lost at the step3,200 − 1,600 = 1,600 users
    StepUsersStep conversionOverall
    Visit10,000—100%
    Sign up3,20032%32%
    Add to cart1,60050%16%
    Checkout90056%9%
    Paid54060%5.4%
    📌
    The biggest percentage drop is not always the biggest opportunity. Compare absolute users lost and how fixable the step is.

    🧩 Intermediate: Defining Steps and Rules

    DecisionOptionsGuidance
    Step orderStrict order vs any orderUse strict order for linear journeys like checkout
    Time window1 hour, 1 day, 7 daysChoose a realistic window for the goal
    Counting unitUsers, sessions, devicesProduct funnels usually count users
    Entry ruleFirst time vs every timeState it clearly to avoid double counting
    ExclusionsTest accounts, bots, employeesFilter them out consistently
    textFunnel: First order for new mobile users
Entry: signup_complete (first time), platform in (android, ios)
Steps: signup_complete -> add_to_cart -> checkout_start -> payment_success
Window: 7 days from signup
Unit: unique users
Exclude: internal test accounts

    🗄️ Intermediate: A Funnel in SQL

    sql-- 7-day funnel for new users from signup to first payment
WITH base AS (
  SELECT user_id, MIN(event_time) AS t0
  FROM events
  WHERE event_name = 'signup_complete'
    AND event_time >= '2026-09-01' AND event_time < '2026-10-01'
  GROUP BY user_id
),
steps AS (
  SELECT b.user_id,
         MIN(e.event_time) FILTER (WHERE e.event_name = 'add_to_cart')      AS t_cart,
         MIN(e.event_time) FILTER (WHERE e.event_name = 'checkout_start')   AS t_checkout,
         MIN(e.event_time) FILTER (WHERE e.event_name = 'payment_success')  AS t_paid
  FROM base b
  JOIN events e ON e.user_id = b.user_id
   AND e.event_time BETWEEN b.t0 AND b.t0 + interval '7 days'
  GROUP BY b.user_id
)
SELECT COUNT(*)                                        AS signed_up,
       COUNT(t_cart)                                   AS added_to_cart,
       COUNT(t_checkout) FILTER (WHERE t_checkout >= t_cart) AS started_checkout,
       COUNT(t_paid)     FILTER (WHERE t_paid >= t_checkout) AS paid
FROM steps;
    ⚠️
    Check the order of timestamps. A user who paid before adding to cart (tracking bug or edge case) should not count as a clean funnel completion.

    🏆 Expert: Cohorts, Time-to-Convert and Pitfalls

    TechniqueQuestion it answers
    Cohort funnelDo newer cohorts convert better than older ones?
    Time to convertHow long between signup and first order? Is the window right?
    Multi-path funnelsWhich routes lead to conversion beyond the main path?
    Counterfactual checkWhat would conversion be without the campaign or release?
    PitfallWhat goes wrongSafeguard
    SurvivorshipLooking only at users who finishedInclude everyone who entered
    Simpson's paradoxOverall improves while each segment worsens due to mix changeAlways view key segments
    Mixed windowsComparing a 1-day and a 7-day funnelFix the window
    Tracking changesEvent renamed so numbers dropCheck release notes and tracking plan

    ✅ Best Practices & Common Mistakes

    ✅ Best practices

    Define entry, steps, order, window and unit; reconcile with a known total; segment before concluding; track both rate and absolute users; save the funnel definition for reuse.

    ❌ Common mistakes

    Changing step definitions between reports; ignoring time windows; reading percentages without volumes; forgetting to exclude test users; trusting a funnel after a tracking change.

    Interpreting Web & App Analytics

    How to read Google Analytics, Mixpanel and Amplitude: users, sessions and events, standard reports, retention and path analysis, and what each tool is best for.

    📈 Basic: What Analytics Tools Do

    Analytics tools collect events from your website or app, store them and turn them into reports. They answer questions such as "how many people used this feature this week?" without writing SQL every time.

    Figure 4.1 · How analytics data flows
    💡
    Know the tool's unit of counting (users, sessions or events) before reading any number. Most confusion comes from comparing unlike units.

    🧱 Basic: Core Concepts

    ConceptMeaningExample
    UserA person or device identified by an ID12,400 active users this week
    SessionA group of interactions within a time windowOne visit lasting 6 minutes
    EventA single recorded actionview_item, purchase
    Property / parameterDetail attached to an eventprice = 499, platform = ios
    User propertyDetail about the userplan = pro, country = IN
    ConversionAn event marked as a goalpurchase
    Dimension / metricCategory vs numberCountry (dimension), revenue (metric)
    📌
    A dimension is how you slice (country, device). A metric is what you measure (users, revenue). Reports are a metric broken down by dimensions.

    🔍 Intermediate: Google Analytics 4 (GA4)

    GA4 is an event-based tool widely used for websites and apps, strong on acquisition (where users come from) and marketing attribution.

    GA4 areaWhat it showsUse it to
    AcquisitionChannels, sources and campaigns bringing usersCompare channel quality
    EngagementEvents, pages, engaged sessionsSee what users do on the site or app
    MonetisationPurchases and revenueTrack e-commerce performance
    RetentionReturning users over timeSee stickiness
    Explore → Funnel explorationCustom funnels with segmentsFind drop-offs
    RealtimeActivity in the last 30 minutesCheck tracking after a release
    ⚠️
    GA4 may sample or apply thresholds on large or filtered reports, and numbers can differ slightly from your database. Treat GA4 as directional and reconcile important figures with SQL.

    Mixpanel and Amplitude are product analytics tools focused on what users do inside a product: funnels, retention, flows and cohorts.

    🏆 Expert: Choosing the Right Tool and Reconciling Numbers

    QuestionBest starting point
    Where do our new users come from?GA4 acquisition reports
    Where in onboarding do users drop?Mixpanel or Amplitude funnel
    Do users who try feature X stay longer?Behavioural cohort in Amplitude or Mixpanel (then validate in SQL)

    ✅ Best practices

    Know units and definitions; reconcile key numbers; use segments; compare equal time periods; save reports and annotate releases; use the right tool for the question.

    ❌ Common mistakes

    Mixing users and sessions; trusting a single dashboard; ignoring sampling; reading correlation as cause; comparing a weekday with a holiday.

    Module 05

    Event Tracking & Instrumentation

    How product data gets created: event naming, properties, a tracking plan, working with engineers, and testing that events fire correctly.

    🏷️ Basic: Why Tracking Needs a Plan

    You can only analyse what was recorded. If a button tap was never tracked, no tool can recover it. An instrumentation plan decides which actions to record and how to name them so reports are reliable.

    🎯
    Start from questions
    List the decisions you need to make, then the events required.
    🏷️
    Consistent names
    One naming style across web, iOS and Android.
    🧾
    Useful properties
    Add detail that lets you slice: platform, plan, source.
    🧪
    Test before release
    Verify each event fires once with correct values.

    ✍️ Basic: Event Naming and Properties

    Good practiceExampleAvoid
    Object + past-tense actionorder_completed, item_addedclick, button1
    Lowercase with underscorescheckout_startedCheckoutStarted vs checkout-started mixed
    Specific namessearch_submittedevent_17
    Properties for detailorder_completed {amount, currency}order_completed_499_inr (one event per value)
    Few high-quality events40 well-defined events600 noisy events
    💡
    Use properties, not new events, for variations. "button_clicked {button_name: buy_now}" scales; "buy_now_clicked", "pay_clicked" and so on multiply quickly.

    📋 Intermediate: Writing a Tracking Plan

    yaml# tracking plan excerpt
event: order_completed
description: User successfully paid for an order
trigger: Payment confirmation screen is shown after server success
platforms: [web, ios, android]
properties:
  order_id:   {type: string, required: true}
  amount:     {type: number, required: true, unit: INR}
  item_count: {type: integer, required: true}
  coupon:     {type: string, required: false}
owner: payments squad
used_in: [checkout_funnel, revenue_dashboard]
    FieldWhy it matters
    TriggerDefines exactly when it fires — prevents double fires
    Required propertiesEnsures analysis works later
    OwnerSomeone to ask when numbers look wrong
    Used inShows what breaks if you change it

    ⚠️ Statistical Traps and Honest Interpretation

    TrapWhat happensSafeguard
    Small sampleRandom noise looks like a trendReport sample size; avoid strong claims on tiny groups
    Simpson's paradoxTrend reverses when split by segmentCheck key segments
    Survivorship biasOnly successes are visibleInclude everyone who entered
    Cherry-pickingChoosing a favourable time windowFix the window before looking
    Correlation ≠ causeTwo metrics move togetherUse experiments or a plausible mechanism
    Many comparisonsSomething will look significant by chancePre-decide the primary comparison
    💡
    Write conclusions with confidence and limits: "Likely caused by v5.2 (high confidence; 18k users); not yet tested whether the campaign contributed."

    Symptom: checkout conversion fell from 62% to 51% in a week.

    ⚖️ Troubleshooting: Two Dashboards Show Different Numbers

    1. Write down both definitions: users, events, time zone, filters, refresh time.
    2. Check the data sources and any sampling or consent differences.
    3. Reproduce each number with a simple query or report.
    4. Find the gap (for example one counts sessions, one counts users).
    5. Agree on the metric dictionary entry and tell everyone which number is the source of truth.
    ⚠️
    Do not average the two numbers or quietly choose the one you like. Explain the gap, then standardise.
    Figure 8.2 · Reconciling two dashboards

    ❓ Troubleshooting: An Event Stopped Firing

    • Find the exact date it stopped and compare with release dates.
    • Check by platform and app version.
    • Open the debug view on a test build and repeat the action.
    • Ask the owning engineer; check the tracking plan trigger definition.
    • Fix, backfill if possible, annotate the gap on dashboards.

    📉 Troubleshooting: A Decision on Thin Data

    A test with 120 users shows a 9-point lift. Leadership wants to ship. As APM you report the sample size and the range, explain what the data can and cannot say, and propose extending the test for another week while rolling the feature out to a small share behind a flag.

    💡
    Offer a reversible next step instead of a flat "no": a staged rollout gives speed and safety.

    ⚖️ Trade-off Scenario: Speed vs Certainty

    A campaign launches tomorrow and the tracking plan is only 80% implemented. You choose which events are essential for the decision (purchase, signup), ship those, defer the nice-to-have events, and document the gaps and the date they return — so the team can move fast without being blind.

    Module 11

    Interview Preparation

    Questions asked in APM interviews about data literacy, SQL, funnels and analytics, grouped by level. Draft your answer, then compare with the model answer.

    🌱 Beginner Interview Questions

    IQ1.Why should an APM know SQL?
    To answer product questions quickly without waiting for an analyst, to understand how data is structured, to validate dashboards and to have credible conversations with engineers and data teams. The aim is reliable basic analysis, not becoming a database engineer.
    IQ2.What is a conversion funnel?
    An ordered sequence of steps a user takes toward a goal (visit, signup, purchase). It shows how many users reach each step and where they drop off. A good funnel defines the entry point, the unit (users or sessions) and the time window.
    IQ3.What is the difference between a session, a user and an event?
    An event is a single action (button click). A session is a group of events in one visit. A user is a person or device across sessions. Tools count them differently, so always state which unit a metric uses.

    🛠️ Intermediate Interview Questions

    IQ4.How would you find where users drop off in onboarding?
    Define the funnel steps and window, compute volumes and step conversion, then segment by platform, version, channel and country to find who drops. Combine with qualitative evidence such as session recordings or interviews to understand why, then propose an experiment.
    IQ5.Your analytics tool and the database disagree. What do you do?
    Compare definitions, date ranges and time zones, then look at consent, ad blockers and missing events by platform. Reproduce both numbers, explain the gap, and agree which source is the reference for each metric.
    IQ6.What is the difference between GA4 and tools like Mixpanel or Amplitude?
    GA4 is strong for web acquisition and marketing analysis. Mixpanel and Amplitude are event-centred product analytics tools, strong for funnels, retention and cohorts by user. Many teams use both, so know which question goes to which tool.

    🚀 Advanced Interview Questions

    IQ7.How do you choose the right success metric for a feature?
    Start from the user and business goal, pick a primary metric that reflects the value delivered (such as weekly active use of the feature), add guardrails (errors, retention, revenue) and a leading indicator. Define it precisely and set a target and review date before launch.
    IQ8.Weekly active users grew 15% but revenue is flat. How do you investigate?
    Check the definition of active, the user mix (new vs existing, free vs paying), conversion and ARPU by segment, and whether growth came from low-value channels or from a tracking change. Then decide whether the growth is meaningful for the business.
    IQ9.How do you read a retention curve?
    Look at where the curve drops and where it flattens. A flattening curve means a retained core. Compare cohorts over time, segment by acquisition source and behaviour in the first week, and relate changes to releases.

    🏆 Expert Interview Questions

    IQ10.A test shows a 6% lift on a small sample. Do you ship?
    Report the sample size, the range of plausible effect and the risk. Do not claim a win from thin data. Extend the test or roll out gradually behind a flag with guardrail metrics, and decide with predefined criteria.
    IQ11.How do you make sure a new feature will be measurable at launch?
    Write the tracking plan in the requirements, add tracking acceptance criteria, test events in a debug view before release, build the dashboard early and reconcile counts with the database in the first days after launch.
    IQ12.How do you explain a complex analysis to a non-technical executive?
    Lead with the answer and recommendation, show one or two simple charts, state the key number and the limits, avoid jargon, and finish with the decision you need and the next step. Keep the details in an appendix.

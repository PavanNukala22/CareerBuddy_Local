    Module 01 · Foundations

    MLOps Foundations

    Understand what MLOps is, why machine learning systems need operational practices beyond writing code, and how the MLOps lifecycle connects development, deployment, monitoring, and continuous improvement.

    🧭 What is MLOps?

    MLOps is the engineering discipline that combines machine learning development with software engineering and operations practices so that ML systems can be built, deployed, monitored, and improved reliably over time. It borrows heavily from DevOps, but it exists because a trained model on its own is not a product — it becomes useful only once it is packaged, served, watched in production, and kept up to date as the world around it changes.

    A common misconception is that MLOps is just "deploying a model." In practice it is much broader: it covers how data is collected and validated, how experiments are tracked and compared, how training is made repeatable, how a model is packaged and served, how its predictions are monitored, and how retraining is triggered when performance degrades. Each of those stages has its own failure modes, and MLOps is the set of practices that keeps them from silently breaking.

    🔁
    Reproducibility
    Anyone on the team can re-run a training job and get a comparable model from the same code, data, and configuration.
    ⚙️
    Automation
    Pipelines replace manual, ad-hoc scripts for data prep, training, testing, and deployment.
    🚀
    Deployment
    Models are packaged and served through a defined, tested path into production, not copy-pasted onto a server.
    📈
    Monitoring
    Once live, a model's predictions, inputs, and business impact are tracked so problems are caught early.
    📝
    MLOps is a set of practices and principles, not a single tool or vendor. Tools like MLflow, DVC, or Kubeflow can implement pieces of it, but adopting a tool without the underlying practices (versioning, testing, monitoring) does not make a team "MLOps-mature."

    🚧 Why MLOps Matters

    Teams that skip MLOps practices tend to hit the same wall once a model moves from a notebook to production: it worked during the demo, and then it quietly stops working, and nobody can say exactly why. The problems below are the ones that MLOps practices exist specifically to prevent.

    ProblemWhat actually happens
    Works on my machineA model trained in one data scientist's notebook can't be reproduced by anyone else because the exact library versions, data snapshot, or random seed were never recorded.
    Manual deploymentSomeone SSHes into a server and copies a model.pkl file by hand, with no record of which version is running where.
    Untracked experimentsDozens of training runs happen, but only the final accuracy number survives — the parameters and dataset used to get it are lost.
    Data inconsistencyThe features computed at training time don't exactly match the features computed at serving time, so the model behaves differently in production.
    Model driftThe real world changes — user behavior, prices, seasonality — and the model's accuracy quietly degrades without anyone noticing.
    Difficult rollbackA bad model reaches production and there is no fast, tested way to revert to the previous known-good version.
    No monitoringA model can be silently wrong for weeks because nobody is watching prediction quality or input data health.
    ⚠️
    The most expensive version of this problem is not a crash — it's a model that keeps running and keeps returning predictions, just wrong ones, while every downstream system trusts them.

    ⚖️ MLOps vs DevOps

    MLOps grew out of DevOps and shares its goal of fast, safe, automated delivery — but an ML system has more moving parts than a typical application, because the model's behavior depends on data as much as on code. A DevOps pipeline that only tests and deploys code has nothing to say about a dataset silently shifting or a model's accuracy quietly dropping.

    AspectDevOpsMLOps
    What shipsApplication codeCode + data + a trained model
    TestingUnit and integration tests on codeCode tests, plus data validation tests and model-quality tests
    Deployment unitAn application build/artifactA model artifact plus the serving infrastructure around it
    MonitoringApplication metrics: latency, errors, uptimeApplication metrics + model metrics (accuracy, drift) + data quality metrics
    VersioningSource code in GitCode, datasets, and model versions, each tracked separately

    In short: DevOps assumes that if the code passes its tests, the behavior is fixed. MLOps can't make that assumption, because a model's behavior is a function of the data it was trained on and the data it sees in production — both of which can change without a single line of code changing.

    🔄 The MLOps Lifecycle

    An ML system is never really "finished." It moves through a repeating lifecycle: data is collected and prepared, features are engineered, a model is trained and evaluated, the winning version is registered and deployed, and its behavior in production is monitored. When monitoring detects that performance has degraded, that triggers retraining — closing the loop back to the start.

    Figure 1.1 · The MLOps lifecycle is a loop, not a straight line

    The loop matters more than any single stage. A team that trains a great model once and never revisits it has done data science, not MLOps — MLOps is specifically the discipline of keeping that loop running cheaply and safely, so the system keeps working as data and business conditions change.

    🪜 MLOps Maturity Levels

    Not every team needs the same amount of automation on day one. Google's widely-used framework describes three broad maturity levels, and most organizations start at Level 0 and grow into the others as the cost of manual work starts to outweigh the cost of building pipelines.

    🧑‍💻
    Level 0 — Manual process
    Data scientists manually prepare data, train in notebooks, and hand a model file to engineers to deploy by hand. Slow, error-prone, and hard to reproduce.
    🛠️
    Level 1 — ML pipeline automation
    Training itself becomes an automated, repeatable pipeline that can be re-run on new data, but deployment of new models to production is still a manual step.
    🤖
    Level 2 — CI/CD/CT automation
    A full pipeline automatically tests, builds, and deploys new models, and can be triggered by new data or detected drift — continuous training (CT), not just continuous integration.
    LevelTrainingDeploymentTypical team size
    0 — ManualManual, notebook-drivenManual copy of model artifactSmall team, early-stage project
    1 — Pipeline automationAutomated, repeatable pipelineStill largely manualGrowing team, model retrained periodically
    2 — CI/CD/CTAutomated and triggerableAutomated, tested, monitoredMature ML platform team
    💡
    Maturity level is a description, not a scoreboard. A small internal tool that is retrained twice a year may be perfectly well served by Level 0 — the goal is matching the amount of automation to the actual risk and change-rate of the system.
    Module 02 · Lifecycle

    ML Project Lifecycle

    Follow an ML project from a business problem to a deployed system that learns from its own production feedback.

    🎯 Problem Definition

    Every ML project should start from a business problem, not a model. "Reduce customer churn" is a business problem; "predict, for each customer, the probability they cancel in the next 30 days" is the ML problem it translates into. Getting this translation right up front saves months of wasted modeling work later.

    ElementQuestion it answersExample
    Business problemWhat outcome does the business actually want?Reduce customer churn by 10%
    ML problemWhat prediction task solves it?Binary classification: will this customer churn in 30 days?
    Target variableWhat exactly are we predicting?churned (0/1), labeled from past cancellations
    Success metricsHow do we know it worked?Precision at top-decile risk score; downstream retention lift
    ConstraintsWhat limits the solution?Predictions must be explainable to a human agent; latency < 200ms
    📝
    A model with 95% accuracy can still be useless if the success metric was defined wrong — for example, if churn is rare, a model that always predicts "no churn" can hit 95% accuracy while catching zero at-risk customers.

    📥 Data Collection

    Training data rarely lives in one convenient place. A realistic ML project pulls from several sources, and part of the job is understanding how fresh, complete, and trustworthy each source is before relying on it.

    🗄️
    Databases
    Transactional systems (orders, accounts, support tickets) — usually the most reliable source of ground truth.
    🔌
    APIs
    Third-party or internal services providing enrichment data, like weather, pricing, or geolocation.
    📄
    Files
    CSV/Parquet exports, logs, or data drops from partners — often less structured and needing extra validation.
    🌊
    Event streams
    Real-time clickstream or sensor data via Kafka/Kinesis, useful for near-real-time features.

    Data warehouses (Snowflake, BigQuery, Redshift) typically sit downstream of all of these, aggregating them into tables that are easier for a training pipeline to query consistently.

    🧹 Data Preparation

    Raw data is almost never ready to train on directly. Preparation turns messy, inconsistent records into a clean table the model can learn from — and doing it consistently (not by hand, one time) is what makes later retraining possible.

    StepWhat it doesCommon mistake
    CleaningFix or remove malformed records (bad types, impossible values)Silently dropping rows without checking whether the drop rate is small and random
    Missing valuesImpute or flag nullsImputing with the mean computed on the full dataset, leaking test-set information into training
    OutliersCap, transform, or investigate extreme valuesRemoving outliers that are actually the rare cases the model most needs to learn (e.g. fraud)
    EncodingTurn categories into numbers (one-hot, ordinal, embeddings)Encoding a category using values seen only in the training set, breaking on unseen categories in production
    ScalingNormalize numeric ranges for scale-sensitive modelsFitting the scaler on the full dataset instead of only the training split
    Train/val/test splitSeparate data so evaluation reflects unseen performanceSplitting randomly when data has a time component, letting the model "see the future"
    ⚠️
    Any transformation that learns something from data — a mean, a scaler, an encoding — must be fit only on the training split, then applied unchanged to validation, test, and production data.

    🏋️ Training & Evaluation

    Training fits a model's parameters to the training split. Validation data, held out during training, is used to tune hyperparameters and pick between candidate models. The test set is touched only once, at the very end, to give an honest estimate of how the chosen model performs on data it has never influenced in any way.

    Cross-validation extends this idea when data is limited: the training data is split into k folds, and the model is trained k times, each time validating on a different fold. This gives a more stable estimate of performance than a single train/validation split, at the cost of k times the training compute.

    Task typeCommon metrics
    ClassificationAccuracy, Precision, Recall, F1, ROC-AUC
    RegressionMAE, RMSE, R²
    Ranking / recommendationNDCG, MAP, Precision@k
    💡
    Pick the evaluation metric before looking at results, not after. Choosing whichever metric happens to look best after the fact is a subtle form of overfitting to your own judgment.

    ♻️ Deployment & Feedback

    Once a model is deployed, its predictions start generating new information: users act on recommendations, fraud analysts confirm or reject flagged transactions, customers churn or don't. That production feedback is itself valuable data — often more representative of the real world than the original training set.

    Figure 2.1 · Production feedback closes the loop back into training data

    Designing for this loop matters: if there's no way to capture ground-truth outcomes after a prediction (did the customer actually churn? was the transaction actually fraud?), the model can never be properly re-evaluated or improved, no matter how good the original training process was.

    Module 03 · Data

    Data &amp; Feature Engineering

    Learn how to version datasets, build reliable features, keep training and serving consistent through a feature store, and catch bad data before it reaches a model.

    🗂️ Data Versioning

    Code versioning alone isn't enough for ML, because the same training script run against two different snapshots of a dataset can produce two very different models. Data versioning tracks which exact version of a dataset produced which model, the same way Git tracks which commit produced which build.

    Tools like DVC (Data Version Control) pair with Git: the large data files live in cloud storage, while Git tracks small pointer files that record exactly which version of the data was used. This gives you data lineage — a traceable path from raw source data, through every transformation, to the final training set — which is essential when you need to answer "why did the model do that?" months later.

    bash$ dvc add data/raw/transactions.csv
$ git add data/raw/transactions.csv.dvc
$ git commit -m "Track March transactions snapshot"
$ dvc push   # uploads the actual data to remote storage
    📝
    Reproducibility requires both code and data versions to be pinned together — a Git commit hash by itself doesn't tell you which dataset snapshot trained the model unless the data version is recorded alongside it.

    🧬 Feature Engineering

    Feature engineering turns raw fields into inputs a model can actually learn from. The right features often matter more to final model quality than the choice of algorithm.

    🔢
    Numerical features
    Scaled or transformed numbers — e.g. log-transforming a skewed price, or binning age into ranges.
    🏷️
    Categorical features
    One-hot, ordinal, or embedding encodings for things like country, product category, or device type.
    📝
    Text features
    TF-IDF vectors, or dense embeddings from a language model, turning free text into numeric input.
    ⏱️
    Time-based features
    Day-of-week, rolling averages, or "days since last purchase" — features that summarize history.
    python# time-based feature: rolling 7-day purchase count per customer
df["purchases_last_7d"] = (
    df.groupby("customer_id")["order_ts"]
      .transform(lambda s: s.rolling("7D").count())
)

    🏬 Feature Stores

    A feature store is a central system for computing, storing, and serving features consistently across both training and production. It usually has two halves: an offline store for large historical batches used in training, and an online store for low-latency lookups at prediction time.

    🗄️ Offline store

    Optimized for large batch reads over history. Used to build training datasets. Backed by a data warehouse or data lake.

    ⚡ Online store

    Optimized for single-record, millisecond lookups. Used to fetch a customer's current features at request time. Backed by a key-value store like Redis or DynamoDB.

    ⚠️
    Training-serving skew happens when the feature logic used offline (for training) diverges even slightly from the logic used online (for serving) — for example, one computes a 7-day average and the other computes a 7-calendar-day average that includes today. A feature store's main value is guaranteeing both paths compute features the exact same way.

    ✅ Data Validation

    Data validation catches problems in incoming data before they reach training or a live model — the ML equivalent of input validation in traditional software, applied to whole datasets instead of single requests.

    CheckWhat it catches
    Schema validationA column is missing, renamed, or has changed type (string instead of int)
    Missing valuesA previously-complete column suddenly has 30% nulls
    Range validationAn age field contains a negative number or a value of 400
    Distribution checksA feature's typical range or shape has shifted since the training data was collected
    Duplicate detectionThe same record appears multiple times, silently over-weighting it during training
     
    python# a minimal schema check before training
expected_cols = {"customer_id", "tenure_months", "monthly_spend", "churned"}
missing = expected_cols - set(df.columns)
assert not missing, f"Missing expected columns: {missing}"

    🕳️ Data Leakage

    Data leakage happens when information that would not be available at real prediction time sneaks into the training data, making the model look far more accurate during evaluation than it will ever be in production.

    Leakage exampleWhy it's a problem
    Using "total refunds this year" to predict churnThis total includes refunds that happened after the customer churned — it's a consequence of churn, not a cause
    Scaling features using statistics from the full datasetThe training process implicitly "sees" information from the test set
    Including a hospital's discharge date to predict readmissionDischarge date is only known once the outcome is essentially already decided
    ⚠️
    A model that performs suspiciously well in offline evaluation is one of the most common signs of data leakage — before celebrating, check whether every feature would genuinely have been available at the moment the prediction needs to be made.
    Module 04 · Tracking

    Experiment Tracking

    Stop losing good results to memory and spreadsheets — track parameters, metrics, and artifacts for every training run so any of them can be compared or reproduced later.

    🧪 Why Track Experiments?

    A real modeling effort means dozens or hundreds of training runs: different feature sets, hyperparameters, and algorithms. Without a system to record them, teams fall back on spreadsheets, filenames like model_final_v3_REAL.pkl, or memory — none of which scale, and none of which let you answer "what exactly produced our best result?" six months later.

    ⚙️
    Parameters
    Learning rate, tree depth, regularization — the knobs that were set for this run.
    📊
    Metrics
    Accuracy, loss, F1 — the numbers that came out of this run.
    🗃️
    Dataset versions
    Exactly which data snapshot this run trained and evaluated on.
    📦
    Model versions
    The trained artifact itself, tied back to the run that produced it.

    🧾 Parameters, Metrics &amp; Artifacts

    Experiment tracking tools generally organize what they record into three categories, each answering a different question about a run.

    CategoryExamplesQuestion it answers
    Parameterslearning_rate=0.01, n_estimators=200What settings produced this run?
    Metricsval_accuracy=0.91, val_loss=0.24How good was this run?
    Artifactsmodel.pkl, confusion_matrix.png, feature_importance.csvWhat did this run actually produce?

    🔁 Experiment Tracking Workflow

    Every tracked experiment follows roughly the same shape: code is executed as a "run," the chosen parameters are logged before training starts, training produces metrics and artifacts as it goes, and once several runs exist they can be compared side by side to pick a winner.

    Figure 4.1 · The shape of a tracked experiment, from code to comparison

    📓 MLflow Concepts

    MLflow is one widely-used open-source tool for experiment tracking (not the only one — Weights & Biases and Neptune solve the same problem). Its core vocabulary is worth knowing regardless of which tool a team ends up using.

    ConceptMeaning
    ExperimentA named collection of related runs, e.g. "churn-model-v2"
    RunOne execution of training code, with its own parameters, metrics, and artifacts
    ParameterAn input setting logged for a run (immutable once logged)
    MetricA numeric result logged for a run, optionally over time (e.g. loss per epoch)
    ArtifactAny output file associated with a run — a model, a plot, a report
    ModelA specially-tracked artifact that MLflow can register and serve directly

    ♻️ Reproducing an Experiment

    The real test of an experiment tracking setup is whether someone else — or you, a year later — can take a logged run and reproduce essentially the same result. That requires the run to have captured code version, data version, parameters, and environment together.

    pythonimport mlflow

mlflow.set_experiment("churn-model-v2")

with mlflow.start_run():
    mlflow.log_param("n_estimators", 200)
    mlflow.log_param("max_depth", 6)

    model.fit(X_train, y_train)
    preds = model.predict(X_val)

    mlflow.log_metric("val_accuracy", accuracy_score(y_val, preds))
    mlflow.sklearn.log_model(model, "model")
    💡
    Log the Git commit hash and a pointer to the exact data version (e.g. a DVC hash) as parameters on every run. That one habit is usually the difference between "we can reproduce this" and "we think this is close to what we had."
    Module 05 · Training

    Model Training &amp; Reproducibility

    Turn ad-hoc training scripts into repeatable pipelines, and make sure that "train it again" reliably gets you a comparable model.

    🏭 Training Pipelines

    A training pipeline is a repeatable, automated sequence — load data, validate it, engineer features, train, evaluate, save artifacts — instead of a notebook run cell by cell in whatever order the author happened to click. Turning a notebook into a pipeline is usually the single highest-leverage step a team can take toward MLOps maturity.

    📥
    Ingest
    Pull a specific, versioned dataset snapshot.
    ✅
    Validate
    Run schema and quality checks before training starts.
    🏋️
    Train & evaluate
    Fit the model and score it against a held-out set.
    📦
    Persist
    Save the model, metrics, and metadata as versioned artifacts.
    📝
    Tools like Airflow, Kubeflow Pipelines, or a simple scheduled script can all implement this idea — the important part is that the same pipeline can be re-run against new data and produce a comparable result, not which orchestrator runs it.

    🗒️ Configuration Management

    Hardcoding hyperparameters and paths directly in training code makes every run subtly different and hard to compare. Externalizing them into a config file makes each run's settings explicit, version-controllable, and easy to diff against another run.

    yaml# config/train.yaml
model:
  type: gradient_boosting
  n_estimators: 200
  max_depth: 6
  learning_rate: 0.05

data:
  version: "2026-08-01"
  train_split: 0.8

training:
  random_seed: 42
  early_stopping_rounds: 20

    The training script then reads this file instead of embedding values inline, and the exact config used for a run is logged alongside its metrics — so "which settings gave us 0.91 accuracy?" is always answerable.

    🎲 Random Seeds &amp; Determinism

    Many parts of ML training involve randomness: how data is split, how weights are initialized, how a model samples subsets of features. Without fixing a random seed, running the exact same code on the exact same data can still produce a slightly different model every time, which makes debugging and comparison unreliable.

    pythonimport random, numpy as np

SEED = 42
random.seed(SEED)
np.random.seed(SEED)
# most frameworks also expose their own seed setting, e.g.
# torch.manual_seed(SEED)
    ⚠️
    Setting a seed makes runs comparable, but it does not guarantee bit-for-bit determinism across different hardware, library versions, or GPU parallelism — for strict reproducibility, the environment and library versions need to be pinned too, not just the seed.

    📐 Model Evaluation

    The right metric depends entirely on the task and, for classification, on how balanced the classes are. Accuracy alone is often misleading when one outcome is much rarer than the other.

    MetricFormula / meaningWhen it matters most
    AccuracyCorrect predictions / total predictionsBalanced classes only
    PrecisionTrue positives / predicted positivesFalse positives are costly (e.g. flagging good transactions as fraud)
    RecallTrue positives / actual positivesFalse negatives are costly (e.g. missing an actual fraud case)
    F1Harmonic mean of precision and recallNeed a single balance between the two
    ROC-AUCRanking quality across all thresholdsComparing models independent of a chosen threshold
    MAE / RMSEAverage (or squared) prediction errorRegression tasks — RMSE penalizes large errors more

    🧱 Model Artifacts

    A trained model is rarely just one file. Everything needed to reproduce a prediction — not just the model's weights — needs to be saved and versioned together, or the model becomes useless the moment it's separated from the code that built it.

    ArtifactWhy it's needed
    model.pkl / model.ptThe trained model weights/parameters themselves
    Tokenizer / vocabularyFor text models, converts raw text into the exact input format the model expects
    Preprocessing pipelineScalers, encoders, and imputers — must be applied identically at serving time
    MetadataTraining date, data version, metric scores, library versions used
     
    pythonimport joblib

joblib.dump({
    "model": trained_model,
    "scaler": fitted_scaler,
    "feature_names": feature_columns,
    "trained_on": "2026-08-01",
}, "artifacts/churn_model_v3.joblib")
    Module 06 · Serving

    Model Packaging &amp; Serving

    Turn a trained model file into a deployable, callable service — packaged consistently and served the way other applications expect to consume it.

    📦 Why Package Models?

    A model file by itself isn't deployable — it needs a runtime, its dependencies, its preprocessing logic, and an interface for other systems to call it. Packaging bundles all of that together so the model can be deployed the same way every time, on any machine that can run the package, instead of depending on one engineer's laptop having the right library versions installed.

    📝
    Packaging is what makes a model portable between a data scientist's environment, a staging server, and production — without it, "it worked in my notebook" becomes a permanent state of the project.

    🌐 REST API Model Serving

    The most common way to serve a model to other applications is behind a REST API: a client sends input features in a request, and the service returns a prediction. FastAPI is a popular choice in Python because it's lightweight, fast, and generates request validation and docs automatically.

    pythonfrom fastapi import FastAPI
import joblib

app = FastAPI()
bundle = joblib.load("artifacts/churn_model_v3.joblib")
model, scaler = bundle["model"], bundle["scaler"]

@app.post("/predict")
def predict(payload: dict):
    features = scaler.transform([payload["features"]])
    prediction = model.predict(features)
    return {"prediction": prediction.tolist()}
    💡
    Always apply the exact same preprocessing (like scaler.transform) at serving time that was used at training time — this is one of the most common sources of training-serving skew.

    ⏱️ Batch vs Online Inference

    Not every model needs to answer in real time. Choosing between batch and online inference is mostly a question of how fresh a prediction needs to be, and how many predictions need to be made at once.

    Batch inferenceOnline inference
    LatencyMinutes to hours is fineMilliseconds to seconds required
    TriggerRuns on a schedule (e.g. nightly)Runs per incoming request
    Typical use caseScoring an entire customer list for a weekly reportFraud check on a single transaction as it happens
    InfrastructureA scheduled job reading/writing large tablesAn always-on API service

    🐳 Dockerizing an ML Model

    A Dockerfile packages the model, its code, and its exact dependencies into a single, portable image — so the service that ran correctly in testing runs identically in production, regardless of what's installed on the host machine.

    dockerfileFROM python:3.11-slim

WORKDIR /app

# copy dependency manifest first so Docker can cache this layer
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# now copy the application code and model artifact
COPY app/ ./app
COPY artifacts/ ./artifacts

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
    LinePurpose
    FROM python:3.11-slimBase image with a minimal Python runtime
    COPY requirements.txt + RUN pip installInstalls dependencies in their own cached layer
    COPY app/ / artifacts/Adds application code and the trained model
    EXPOSE / CMDDeclares the port and the command that starts the server

    Module 07 · CI/CD

    CI/CD for Machine Learning

    Extend familiar CI/CD automation to cover data and model quality, not just application code — and see how continuous training fits in.

    🔧 What CI/CD Means

    Continuous Integration (CI) means every code change is automatically built and tested as soon as it's pushed, catching problems early instead of at release time. Continuous Delivery/Deployment (CD) extends that automation to actually releasing the change — to staging automatically, and to production either automatically or with a single approval click.

    📝
    For ML systems, a closely related third idea is Continuous Training (CT): automatically retraining a model when new data or detected drift warrants it, which has no equivalent in traditional software CI/CD.

    🏗️ CI Pipeline for ML

    An ML-aware CI pipeline runs more than code tests — it also checks the data and the model quality before anything is considered safe to package.

    Figure 7.1 · A CI pipeline for an ML project checks code, data, and model quality

    🧪 ML-Specific Testing

    Testing an ML system means testing more layers than testing a typical application, because correctness depends on data and model behavior, not just code logic.

    Test typeWhat it checks
    Unit testsIndividual functions — a feature transform, a data-cleaning step — behave correctly on known inputs
    Data validation testsIncoming data matches the expected schema, ranges, and distribution
    Feature testsComputed features match expected values for known example rows
    Model quality testsThe newly trained model meets a minimum accuracy/metric threshold before being allowed to deploy
    Integration testsThe full serving path — API in, prediction out — works end to end

    ⚙️ GitHub Actions Example

    A GitHub Actions workflow can run these checks automatically on every push, failing the build (and blocking deployment) if any check fails.

    yamlname: ml-ci
on: [push]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - name: Run unit tests
        run: pytest tests/unit
      - name: Validate data schema
        run: python scripts/validate_data.py
      - name: Check model quality gate
        run: python scripts/check_model_metrics.py --min-accuracy 0.85

    🔁 Continuous Training

    Continuous training closes the loop between monitoring and the CI/CD pipeline: instead of a human deciding "it's time to retrain," a trigger — new data arriving, or drift crossing a threshold — kicks off the same automated training pipeline used in CI, and if the new model passes its quality gate, it moves forward toward deployment.

    💡
    Continuous training should still pass through the same tests and quality gates as any other model change — automating retraining is not the same as skipping validation.
    Module 08 · Registry

    Model Registry &amp; Deployment

    Manage model versions centrally, understand the stages a model moves through, and choose a rollout strategy that limits risk when something goes wrong.

    🗃️ What is a Model Registry?

    A model registry is a central catalog of trained models — recording every version, which run and dataset produced it, its evaluation metrics, and its current stage (staging, production, archived). It's the difference between models scattered across individual laptops and a single source of truth for "what's actually running right now."

    🔢 Model Versions

    Every time a model is retrained and registered, it gets a new version — v1, v2, v3 — rather than overwriting the previous one. Keeping old versions around is what makes rollback and comparison possible later.

    VersionStatusNotes
    v1ArchivedOriginal baseline model, replaced after drift was detected
    v2ArchivedRetrained on fresher data, improved recall but regressed precision slightly
    v3ProductionCurrent live model, passed all quality gates
    📝
    Versioning matters even when a new version looks strictly better on paper — production behavior can differ from offline evaluation, and having the previous version on hand is what makes a fast rollback possible if that happens.

    🚦 Model Lifecycle

    A model typically moves through defined stages, each with its own level of scrutiny — the same way application code moves from a feature branch through staging to production.

    Figure 8.1 · A model's stages, from development to archive

    🚀 Deployment Strategies

    Rolling out a new model version carries the same risk as rolling out new application code — plus the extra risk that the model's behavior, not just its stability, might be worse. Several rollout strategies exist to limit that risk.

    StrategyHow it worksBest for
    Blue/GreenTwo full environments exist; traffic switches all at once from old (blue) to new (green)Fast, clean cutover with an instant rollback path
    CanaryNew version receives a small % of traffic first, then gradually more if metrics hold upCatching problems before they affect all users
    ShadowNew version receives a copy of live traffic but its predictions are not shown to users, only loggedValidating a new model's real-world behavior with zero user risk
    Rolling deploymentInstances are replaced gradually, a few at a timeMinimizing downtime during a routine, low-risk update

    ⏪ Rollback

    Because the registry keeps every previous model version, rolling back can be as simple as pointing the serving layer back at the last known-good version — no retraining required. This only works, though, if rollback was planned for in advance: the previous version's artifact, preprocessing code, and dependencies all need to still be available and compatible.

    ⚠️
    A common mistake is rolling back the model artifact but forgetting that the feature pipeline or API contract has since changed — a rollback needs to restore a whole compatible version of the system, not just swap one file.
    Module 09 · Monitoring

    Monitoring &amp; Observability

    Watch a deployed model on three levels — system health, model quality, and data health — so problems are caught before they cost the business money.

    👀 Why Monitor ML Systems?

    Deploying a model is the midpoint of its lifecycle, not the end. Unlike a traditional application, an ML system can fail silently: the service stays up, requests get 200 responses, and predictions keep flowing — while the predictions themselves quietly become wrong as the real world drifts away from what the model learned.

    📝
    "Is the service up?" and "is the model still right?" are two completely different questions, and a system can pass the first while badly failing the second.

    🖥️ System Monitoring

    System-level monitoring is the same as for any backend service — it tells you whether the infrastructure serving the model is healthy.

    MetricWhat it signals
    CPU / memoryWhether the serving instance has enough resources for the current load
    LatencyHow long a prediction request takes end to end
    ThroughputHow many requests per second the service can handle
    Error rateHow often requests fail outright (5xx errors, timeouts)

    🎯 Model Monitoring

    Model monitoring goes further, watching whether the model's actual behavior and quality are holding up — something system metrics can't tell you at all.

    📊
    Prediction distribution
    Is the model suddenly predicting one class far more often than it used to?
    ✅
    Accuracy
    Once ground truth arrives, is the model still as correct as it was at training time?
    ⚖️
    Precision / Recall
    Are false positives or false negatives creeping up for a specific segment?
    💰
    Business metrics
    Is the metric the model was built to move — churn rate, fraud losses — actually moving?

    🧪 Data Quality Monitoring

    Since a model is only as good as the data flowing into it right now, monitoring the incoming data itself catches problems before they show up as bad predictions.

    CheckExample issue caught
    Missing valuesAn upstream system starts sending nulls for a field that used to always be populated
    Schema changesA field's type silently changes from integer to string after an upstream release
    Distribution changesAverage order value doubles overnight after a pricing change, outside the range the model was trained on
    Feature anomaliesA feature that should always be between 0 and 1 starts showing values of 50

    🛰️ ML Observability Architecture

    Observability ties monitoring signals from every layer — the application, the model, and the data — into logs, metrics, and traces that feed a dashboard, with alerts firing when something crosses a threshold.

    Figure 9.1 · Signals from the app, model, and data converge into dashboards and alerts
    💡
    Monitoring tells you a number crossed a threshold; observability is what lets you then trace back why — which upstream data field, which model version, which segment of users.
    Module 10 · Drift

    Model Drift &amp; Retraining

    Understand the two ways a model's world can shift underneath it, how to detect that early, and how to decide when to retrain.

    📉 Data Drift

    Data drift (also called covariate shift) is a change in the distribution of the model's input features over time — the relationship between inputs and outputs may be unchanged, but the inputs themselves now look different from what the model was trained on.

    📝
    Example: a model trained mostly on desktop-browser traffic starts seeing 70% mobile traffic after a marketing campaign. The features look statistically different, even if mobile users don't behave any differently once you control for device.

    🔀 Concept Drift

    Concept drift is a change in the actual relationship between inputs and the target — the same input now genuinely predicts a different outcome than it used to. This is a deeper problem than data drift, because retraining on the same features won't help unless the training data reflects the new relationship.

    📉 Data drift

    Inputs look different. Example: average transaction size grows due to inflation.

    🔀 Concept drift

    The input-output relationship itself changes. Example: a spending pattern that used to indicate fraud is now normal behavior post-pandemic.

    🔍 Detecting Drift

    Drift detection compares the distribution of live production data (or predictions) against a reference — usually the training data — and flags a meaningful statistical difference.

    TechniqueHow it works
    Statistical testsKolmogorov-Smirnov or chi-squared tests compare two distributions for a feature
    Distribution comparisonVisual or numeric comparison of histograms between training data and recent production data
    PSI (Population Stability Index)A single score summarizing how much a feature's distribution has shifted; higher PSI means more drift
    Monitoring metricsSimple thresholds on prediction distribution or accuracy, alerting when they move outside an expected range

    🔁 Retraining Strategies

    Once drift or degraded performance is confirmed, a team needs a policy for when to actually retrain — retraining constantly is wasteful, but retraining too rarely lets a stale model keep making poor predictions.

    StrategyHow it triggersTrade-off
    Scheduled retrainingRuns on a fixed calendar (weekly, monthly)Simple and predictable, but may retrain when unnecessary or too late
    Trigger-based retrainingFires when a drift metric crosses a thresholdMore efficient, but requires reliable monitoring to trigger on
    Manual retrainingA person decides based on judgment or a reportFlexible, but slow and easy to forget

    🤖 Automated Retraining Pipeline

    Putting the previous sections together, an automated retraining pipeline lets drift detection directly trigger the same training pipeline used elsewhere, gated by the same validation and quality checks before a new version ever reaches production.

    Figure 10.1 · Drift detection triggers retraining, still gated by validation and evaluation
    ⚠️
    Automating the trigger should never mean automating away the quality gate — a newly retrained model still needs to beat (or at least match) the current production model's metrics before it's promoted.
    Module 11 · Cloud & K8s

    Cloud, Containers &amp; Kubernetes

    Package a model into a container, store it in a registry, and let Kubernetes run, scale, and route traffic to it reliably.

    📦 Containers for ML

    Docker packages a model service with its exact runtime, libraries, and system dependencies into a single portable image. For ML specifically, this solves a very common pain point: a model trained with one version of scikit-learn or PyTorch can behave subtly differently, or fail to load at all, under a different version — containers pin that down.

    📮 Container Registry

    A container registry (Docker Hub, Amazon ECR, Google Artifact Registry) stores built images so they can be pulled by any environment that needs to run them — the same image that passed testing in CI is exactly what runs in production.

    Figure 11.1 · An image moves from build to a running deployment through a registry
    bash$ docker build -t registry.example.com/churn-model:v3 .
$ docker push registry.example.com/churn-model:v3
$ docker pull registry.example.com/churn-model:v3   # on the target server

    ☸️ Kubernetes Basics

    Kubernetes orchestrates containers across a cluster of machines — restarting failed containers, scaling them up or down, and routing traffic to them. A handful of core concepts cover most of what you need to reason about a model deployment.

    ConceptWhat it is
    PodThe smallest deployable unit — one or more containers running together
    DeploymentDescribes how many replicas of a pod should run, and manages rolling updates
    ServiceA stable network address that routes traffic to the current healthy pods
    ConfigMapNon-secret configuration values injected into pods (e.g. a model version tag)
    SecretSensitive values (API keys, credentials) injected into pods securely

    🧭 Kubernetes Model Serving

    In a typical setup, a Kubernetes Service sits in front of several replica pods, each running the same containerized model server — spreading incoming requests across them and automatically routing around any pod that fails its health check.

    Figure 11.2 · A Service load-balances requests across replica model-serving pods

    📈 Scaling ML Inference

    As traffic grows, a model service needs to scale — but ML workloads bring some scaling considerations that don't apply to typical stateless services.

    TechniqueWhat it does
    Horizontal scalingRuns more replica pods of the same model server to handle more concurrent requests
    AutoscalingAutomatically adds or removes replicas based on current CPU/GPU load or request queue depth
    GPU workloadsDeep learning models may need GPU-enabled nodes, which are more expensive and often scarcer than CPU nodes
    Load balancingDistributes requests evenly across replicas so no single pod becomes a bottleneck
    💡
    GPU inference often benefits more from batching multiple requests together than from adding raw replica count — batching amortizes the fixed cost of a GPU call across several predictions at once.

    ✅ Production Checklist

    Before calling an ML system "production-ready," it's worth checking it against the practices covered across this whole course.

    ⏪
    Rollback
    A tested path exists to return to the previous model version quickly.
    🔒
    Security
    Secrets, model access, and data access are all properly restricted.

    MLOps is the discipline that keeps an ML system trustworthy after the demo is over. The core loop — data, training, evaluation, deployment, monitoring, retraining — repeats for as long as the system is in production, and every practice in this course exists to make that loop faster, safer, and more automatic.

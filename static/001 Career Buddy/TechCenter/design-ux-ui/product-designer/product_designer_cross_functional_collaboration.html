    Module 01 · Foundations

    What is Cross-Functional Collaboration?

    Start from zero: who you work with, what each role owns, and how decisions get made in a product team.

    🧭 What is Cross-Functional Collaboration?

    A cross-functional team brings people with different skills — product, design, engineering, QA, data, marketing — together to deliver one outcome. Collaboration means working together from the start, not passing work along a line.

    🔴 Hand-off line

    PM writes spec → Designer makes screens → Engineers build → QA tests. Each step surprises the next. Rework is common.

    🟢 Collaborative team

    PM, Designer and Tech lead shape the problem together, engineers join research, designers join QA. Fewer surprises, faster delivery.

    👥 Who's Who: Types of Roles

    RoleOwnsWhat they need from the designer
    Product Manager (PM)The "why" and "what": goals, priorities, roadmapClear problem understanding, options with trade-offs, user evidence
    Engineers (front-end, back-end, mobile)The "how": architecture, code, performanceComplete states, edge cases, specs, early feasibility talks
    Tech Lead / ArchitectTechnical direction and riskEarly sight of big ideas to judge feasibility
    QA / Test engineerQuality and test coverageExpected behaviour for every state and edge case
    Data analystMetrics, tracking, analysisEvents to track, success metrics
    Marketing / Sales / SupportGo-to-market and customer voiceRelease info, customer-facing copy, feedback loops
    Stakeholders / leadershipStrategy, budget, approvalsProgress, decisions needed, risks

    🔺 The Product Trio

    Most modern teams are led by a product trio: PM + Designer + Tech lead. They make discovery and scope decisions together.

    Module 02 · Agile & Scrum

    Agile & Scrum Workflows

    Understand Agile values, the types of Agile frameworks, and exactly how Scrum works week to week.

    🔄 What is Agile?

    Agile is a way of working that delivers value in small, frequent increments and adapts to feedback, instead of one big plan delivered at the end (often called "Waterfall").

    Agile Manifesto valuesover…
    Individuals and interactionsProcesses and tools
    Working softwareComprehensive documentation
    Customer collaborationContract negotiation
    Responding to changeFollowing a plan

    🗂️ Types of Agile Frameworks

    FrameworkHow it worksBest for
    ScrumFixed-length sprints (1–4 weeks) with set roles and eventsProduct teams building features
    KanbanContinuous flow on a board; limit work in progressSupport, maintenance, design-system teams
    ScrumbanScrum events + Kanban flowTeams with mixed planned and unplanned work
    SAFe / LeSSScaling Agile across many teamsLarge enterprises with many squads
    Shape Up6-week cycles, shaped pitches, cool-downSmall product companies

    🧑‍🤝‍🧑 Scrum Roles & Artifacts

    👥 Roles

    • Product Owner — owns and orders the backlog (often the PM).
    • Scrum Master — coaches the process, removes blockers.
    • Developers — everyone building the increment, including designers.

    📦 Artifacts

    • Product backlog — ordered list of everything the product might need.
    • Sprint backlog — items chosen for this sprint + plan.
    • Increment — usable, done work at the end of the sprint.

    🛤️ Where Design Fits: Dual-Track Agile

    Design can't start a feature in the same sprint engineers build it. Dual-track Agile runs two connected tracks:

    TrackWhat happensDesigner's work
    Discovery trackResearch, framing, prototypes for work 1–2 sprints aheadInterviews, prototypes, usability tests
    Delivery trackEngineers build validated work this sprintAnswer questions, review builds, design QA
    💡
    Aim to have designs for the next sprint validated and refined before sprint planning — but not so far ahead that they go stale.

    Module 03 · Product Managers

    Partnering with Product Managers

    Share ownership of the problem, shape requirements together and prioritise with clear frameworks.

    🤝 The PM–Designer Partnership

    🎯
    Shared goal
    Both own the outcome metric, not just their deliverables.
    🗣️
    Weekly 1:1
    Align on priorities, evidence and upcoming decisions.
    📑
    Co-own the brief
    PM brings business context; designer brings user evidence.
    ⚖️
    Healthy tension
    PM pushes for speed/scope; designer pushes for quality/usability.

    📄 Types of Requirement Documents

    DocumentWhat it containsDesigner's input
    PRD (Product Requirements Doc)Problem, goals, users, scope, metrics, requirementsUser problems, flows, open questions
    One-pager / briefShort version: problem, why now, successEvidence and risks
    User story"As a [user], I want [goal], so that [benefit]"Write and refine with PM
    EpicA large body of work split into storiesMap flows to stories

    📊 Prioritisation Frameworks

    FrameworkHow it worksBest for
    RICE(Reach × Impact × Confidence) ÷ EffortComparing many ideas with numbers
    MoSCoWMust / Should / Could / Won't haveScoping a release
    KanoBasic needs, performance features, delightersUnderstanding what users expect vs love
    Impact vs Effort 2×2Quick wins, big bets, fill-ins, money pitsFast workshops
    EXAMPLE · RICE score
    IdeaReach / qtrImpact (0.25–3)ConfidenceEffort (person-months)RICE

    Guest checkout wins — and the designer's research is what raised its confidence to 80%.

    🧯 Handling Disagreement with a PM

    1. Go back to the shared goal and metric.
    2. Bring evidence: data, test clips, quotes.
    3. Offer options with trade-offs (fast/basic vs slower/better).
    4. Propose a test to settle it if evidence is missing.
    5. Disagree and commit once a decision is made; record it.
    Q. RICE stands for…

    • B Risk, Insight, Cost, Execution
    • C Reach, Iterate, Code, Evaluate
    • D Rank, Impact, Cost, Effort

    Module 04 · Engineers

    Partnering with Engineers

    Involve engineers early, write clear stories and acceptance criteria, and hand off designs that get built right.

    🛠️ Involve Engineers Early

    WhenWhat to do
    DiscoveryInvite an engineer to 1–2 interviews; share prototypes for feasibility
    IdeationAsk "What would make this easy or hard to build?"
    Before refinementWalk through flows, states, edge cases
    During buildBe available; answer questions within hours
    Before releaseDesign QA together on real devices
    💡
    Engineers often suggest a cheaper solution that is 90% as good. Early conversations save weeks.

    ✍️ User Stories & Acceptance Criteria

    User story: As a returning shopper, I want to reorder my last basket, so that I can buy groceries in under a minute.

    Acceptance criteria (Given / When / Then):

    GivenWhenThen
    I have at least one past orderI open the home screenI see a "Reorder last basket" card with item count and total
    Some items are out of stockI tap ReorderAvailable items are added and I see "2 items unavailable" with alternatives
    I have no past ordersI open the home screenThe card is not shown
    📌
    Good acceptance criteria include states and edge cases — they become the QA test cases.

    🧮 Estimation Basics

    • Story points measure relative effort/complexity (1, 2, 3, 5, 8, 13), not hours.
    • Planning poker: each person estimates privately, then discusses differences.
    • Designers should join estimation to explain complexity hidden in states and animations.
    • Velocity = points completed per sprint; used for planning, not judging people.

    📦 Handoff Checklist

    🔀
    Flows
    User flow linked to every screen.
    🎛️
    States & edge cases
    Matrix of empty, loading, error, success.
    🧱
    System components
    Token and component names, not raw values.
    ✏️
    Final copy
    Every label, message and error text.
    🎞️
    Motion specs
    Trigger, duration, easing.
    ♿
    Accessibility
    Focus order, labels, contrast notes.

    🤝 Handling Technical Constraints

    EXAMPLE · Real-time map tracking

    Designer wants a live courier map updating every second. Engineer: "That will drain battery and cost a lot in API calls." Solution together: update every 15 seconds, animate smoothly between points, and show "Updated 10s ago". Users still feel it is live; cost drops 90%.

    Q. Which acceptance criterion is best written?
    • A The page should be good
    • B Given I enter a wrong OTP 3 times, when I submit again, then I see "Too many attempts. Try again in 10 minutes" and the button is disabled
    • C Make the OTP screen fast
    • D Users must like the OTP flow

    💬 Handling Feedback

    Feedback heardResponse that works
    "Make the logo bigger.""What are you hoping it will achieve? Brand recall? Let's look at the goal."
    "I don't like the colour.""Thanks — is it about readability or brand feel? Our tokens meet contrast rules, but I can show options."
    "Users will want X.""Interesting — we can check that in Friday's interviews."
    "Can we add 5 more features?""Here's the impact on timeline. Which would you trade out?"
    ✅
    Separate opinion from evidence, and the problem from the suggested solution.

    🚫 Saying No (Without Saying No)

    • "Yes, and here is what we would delay to make room."
    • "Not now — let's add it to the backlog and score it with RICE."
    • "Let's test the smallest version first."

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    👥 Teams & Agile Questions

    What is the product trio?
    PM, designer and tech lead making discovery and scope decisions together: valuable/viable, desirable/usable and feasible.
    Explain Scrum events.
    Sprint planning, daily stand-up, backlog refinement, sprint review (demo to stakeholders) and retrospective (improve the process).
    How does design fit into Scrum?
    Through dual-track Agile: discovery runs a sprint or two ahead to validate work, while the designer supports the delivery track with questions, reviews and design QA.
    Scrum vs Kanban?
    Scrum uses fixed sprints with set roles and events; Kanban uses continuous flow with work-in-progress limits — good for support or design-system teams.

    🤝 Working with PMs & Engineers Questions

    How do you prioritise features?
    Frameworks like RICE ((Reach × Impact × Confidence) ÷ Effort), MoSCoW for release scope, Kano for expectations vs delighters, plus evidence from research.
    How do you handle disagreement with a PM?
    Return to the shared goal, bring evidence, offer options with trade-offs, propose a test if evidence is missing, then disagree and commit once decided.
    When do you involve engineers?
    From discovery: invite them to interviews, check feasibility on early ideas, walk through flows and edge cases before refinement, and do design QA together.
    Write an acceptance criterion.
    Given I have a past order, when I open the home screen, then I see a "Reorder last basket" card with item count and total.

    🗺️ Stakeholder Management Questions

    How do you map stakeholders?
    A power–interest grid: manage closely (high/high), keep satisfied (high power), keep informed (high interest), monitor (low/low).
    How do you present design work?
    Context and goal, evidence of the problem, two or three options with trade-offs, a recommendation, and a clear ask — telling people what feedback you need.
    How do you respond to "make the logo bigger"?
    Ask what goal it should achieve, separate the problem from the suggested solution, and evaluate options against that goal.
    How do you say no to a feature request?
    "Yes, and here is what we'd delay", "Let's score it in the backlog", or "Let's test the smallest version first" — making trade-offs visible.
    What is a blameless retrospective?
    A review that focuses on improving the process rather than blaming people, ending with owned action items.

    Navigate a realistic sprint with competing priorities, technical constraints and stakeholder pressure.

    0 / 0 correct

    🍱 Scenario: TiffinGo "Subscription Pause"

    TiffinGo delivers daily home-style meals by monthly subscription. 22% of cancellations say "I'm travelling for a week". The PM wants a Pause subscription feature in the next 2-week sprint. The Head of Sales wants a referral programme first. The tech lead warns that billing changes are risky.

    1️⃣ Task 1 · Map the People

    ✍️ List the stakeholders, place them on the power–interest grid, and say how you'll engage each.
    Model answer: Head of Product / PM → manage closely (trio syncs). Head of Sales → keep satisfied (show data that Pause protects revenue; schedule referral next). Tech lead & billing engineer → manage closely (feasibility from day 1). Support lead → keep informed (new FAQs, macros). Finance → keep satisfied (billing impact).

    2️⃣ Task 2 · Prioritise

    Q. Pause: Reach 3,000/qtr, Impact 2, Confidence 80%, Effort 2. Referral: Reach 10,000, Impact 0.5, Confidence 50%, Effort 3. Which has the higher RICE?
    • A Referral (833)
    • B Pause (2,400)
    • C They are equal
    • D Can't calculate

    3️⃣ Task 3 · Work with Engineering

    ✍️ The tech lead says flexible pause dates need a billing rewrite (3 sprints). What do you propose?
    Model answer: Options: (A) full flexible pause — 3 sprints; (B) pause in fixed blocks of 7 days, extending the subscription end date (no billing change) — 1 sprint; (C) manual pause via support — 0 sprints. Recommend B: covers the "travelling for a week" need, low risk. Measure usage; if many users want custom dates, plan A later.

    4️⃣ Task 4 · Write the Story

    ✍️ Write the user story and 3 acceptance criteria (Given/When/Then), including an edge case.
    Model answer: Story: As a subscriber who is travelling, I want to pause my meals for a week, so that I don't pay for food I can't eat. AC1: Given an active subscription, when I choose "Pause 7 days" starting tomorrow, then no meals are delivered for 7 days and my end date moves by 7 days. AC2: Given it is after 9 pm, when I pause from tomorrow, then I see "Tomorrow's meal is already being prepared — pause starts the day after". AC3: Given I already used 2 pauses this month, when I try again, then I see the limit and a link to contact support.
    Q. Which Scrum event is the right place to demo Pause to the Head of Sales?
    • A Daily stand-up
    • B Sprint review
    • C Retrospective
    • D Backlog refinement

    5️⃣ Task 5 · Retro

    ✍️ The feature shipped but QA found 6 missing states late. Write 2 retro action items.
    Model answer: (1) Add a state matrix and edge-case list to the Definition of Ready — no story enters a sprint without it (owner: designer, from next sprint). (2) Run a 30-minute design–QA walkthrough during refinement so QA writes test cases early (owner: QA lead). Review both at the next retro.

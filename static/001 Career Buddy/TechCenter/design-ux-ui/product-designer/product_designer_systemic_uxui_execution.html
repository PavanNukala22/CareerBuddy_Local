    Module 01 · Foundations

    What is Systemic UX/UI Execution?

    Start from zero: UX vs UI, what "systemic" means, design systems, and the building blocks of every screen.

    🧭 What is Systemic UX/UI Execution?

    UX/UI execution is turning a validated idea into complete, buildable screens. Systemic means you design the whole system — every flow, state, edge case and interaction — using shared, reusable rules, not one beautiful "happy path" screen.

    🔴 Non-systemic

    One polished home screen in Figma. No empty, loading or error states. Engineers guess the rest, so the live product looks inconsistent.

    🟢 Systemic

    Complete flows, every state designed, edge cases mapped, components from the design system, clear specs. The live product matches the design.

    ⚖️ UX vs UI

    UX (User Experience)UI (User Interface)
    QuestionDoes it work and feel easy?Does it look clear and consistent?
    FocusFlows, structure, logic, contentVisual layout, colour, type, components
    ArtefactsUser flows, wireframes, IA, journey mapsMockups, components, style guides
    ExampleCheckout has 3 steps, not 6Primary button is navy, 48px tall, 8px radius
    💡
    A Product Designer owns both. Great UI on a broken flow still fails; a great flow with confusing UI also fails.

    🧱 Design Systems — The "System" in Systemic

    A design system is a shared library of rules and parts that every screen is built from.

    LayerWhat it isExample
    Design tokensNamed values for colour, spacing, type, radius, motioncolor.primary = #14213D space.4 = 16px
    ComponentsReusable UI parts with variants and statesButton (primary/secondary, default/hover/disabled/loading)
    PatternsProven combinations that solve common problemsForm with inline validation; empty-state pattern
    GuidelinesWhen and how to use each part"Use only one primary button per screen."

    📖 Key Terms (What is What)

    User flowThe path a user takes to complete a task, across screens and decisions.
    WireframeA low-detail layout showing structure, not visual style.
    MockupA static high-fidelity screen with final visuals.
    PrototypeA clickable/interactive version used to test.
    StateHow a screen or component looks in a given condition: empty, loading, error, success…
    Edge caseA rare or extreme situation the design must still handle.
    Micro-interactionA small, single-purpose moment of feedback, e.g. a like animation.
    HandoffSharing specs and assets so engineers can build exactly what was designed.

    📐 Layout, Grid & Spacing

    • Grid: 4 columns on mobile, 8 on tablet, 12 on desktop, with consistent gutters.
    • 8-point spacing: use 4, 8, 16, 24, 32, 48… so spacing feels consistent and maps to tokens.
    • Touch targets: at least 44×44 px (iOS) / 48×48 dp (Android).
    • Line length: 45–80 characters for comfortable reading.
    BreakpointWidthTypical layout
    Mobile< 600pxSingle column, bottom nav
    Tablet600–1024pxTwo columns or master–detail
    Desktop> 1024pxSidebar + content, data tables

    🔠 Visual Hierarchy

    📏
    Size
    Bigger = more important. One clear headline per screen.
    ⚫
    Weight & colour
    Bold or brand colour draws attention — use sparingly.
    📍
    Position
    Top-left (LTR) and above the fold get seen first.
    🌬️
    White space
    Space groups related items and separates unrelated ones.
    EXAMPLE · One primary action

    A payment screen has "Pay ₹1,499" as a full-width primary button, "Change payment method" as a text link, and nothing else competing. Users never wonder what to do next.

    Module 03 · States

    States: Empty, Loading, Error & More

    Real products spend most of their time outside the happy path. Learn every state type and how to design it.

    🎛️ What is a UI State?

    A state is how a screen or component looks and behaves in a particular condition. Most bugs users notice are undesigned states: a blank screen while loading, a cryptic error, a list with no explanation when it's empty.

    Figure 3.1 · The five core screen states (Scott Hurff's "UI stack")

    📭 Empty States — Types

    TypeSituationDesign it to…Example copy
    First useNew user, no data yetExplain value + one clear action"No invoices yet. Create your first one in 30 seconds." [Create invoice]
    User clearedUser finished everythingReward and reassure"Inbox zero 🎉 You're all caught up."
    No resultsSearch or filter finds nothingHelp them recover"No results for 'iphnoe'. Did you mean iPhone?" [Clear filters]
    No permission / lockedFeature needs upgrade or accessExplain why and how"Reports are on the Pro plan." [See plans]
    💡
    An empty state is an invitation to act, not a dead end. Always include the next step.

    ⏳ Loading States — Types

    PatternUse whenNotes
    Skeleton screenLoading a known layout (feeds, cards)Feels faster than a spinner; mirrors final layout
    SpinnerShort, unknown wait (1–3 s) on small areasAvoid full-screen spinners for long waits
    Progress barLong, measurable tasks (upload, export)Show %, time left, allow cancel
    Optimistic UIAction very likely to succeed (like, send)Show success instantly; roll back if it fails
    Button loadingAfter submitDisable button + spinner to prevent double payment
    Lazy / progressiveHeavy images or long listsLoad visible content first
    Wait timeWhat users feelWhat to show
    < 0.1 sInstantNothing
    0.1–1 sSlight delaySubtle feedback (button pressed)
    1–10 sWaitingSkeleton or spinner
    > 10 sLeavingProgress bar, time estimate, background processing + notify

    🚨 Error States — Types

    TypeExampleGood design
    ValidationInvalid PAN formatInline, next to the field, explain the rule: "PAN has 10 characters, e.g. ABCDE1234F"
    System / server500 errorPlain language + retry: "We couldn't load your orders. Try again."
    Network / offlineNo internetKeep cached content, banner "You're offline", queue actions
    PermissionCamera access deniedExplain why it's needed + link to settings
    Not found (404)Deleted productExplain + offer search or similar items
    Timeout / rate limitOTP expiredSay what happened + "Resend OTP" with countdown
    Payment failureBank declinedReassure money status: "No money was deducted." + alternative methods
    ⚠️
    Never show raw codes like "Error 0x80040154" alone, blame the user ("You entered wrong data!"), or erase what the user typed.

    🧩 Other States to Design

    ✅
    Success
    Confirm what happened and what's next. "Payment sent. Ref: 8823…"
    🔒
    Disabled
    Explain why an action is unavailable (tooltip or helper text).
    🌓
    Partial
    Some widgets loaded, one failed — show the rest + retry for the failed one.
    📶
    Offline
    Read-only cached data; sync when back online.

    Module 04 · Edge-Case Mapping

    Edge-Case Mapping

    Find and design for the unusual, extreme and messy situations before users find them for you.

    🧷 What is an Edge Case?

    An edge case is a situation at the extreme or unusual end of normal use: a 60-character name, zero results, 10,000 items, no network, a user without permission. Edge-case mapping is systematically listing them for each flow and deciding how the design handles each.

    📌
    Edge cases are rare for one user but common at scale: 1% of 2 million users is 20,000 people.

    🗂️ Types of Edge Cases

    CategoryExamples
    Data volume0, 1, many (10,000) items; very long lists; pagination
    Content lengthVery long names, addresses, product titles; empty optional fields
    Data formatSpecial characters, emojis, non-Latin scripts (Hindi, Tamil), RTL languages
    User & permissionsGuest vs logged in, admin vs viewer, expired subscription, suspended account
    Connectivity & deviceOffline, slow 2G, small screens, landscape, low storage, old OS
    TimeTime zones, midnight rollovers, expired sessions, deadlines passed
    InterruptionsIncoming call mid-payment, app backgrounded, back button, double tap
    AccessibilityScreen readers, 200% text zoom, colour blindness, keyboard only
    ConcurrencyTwo people edit the same record; item sold out while in cart

    📏 The 0 – 1 – Many Rule

    CountDesign questionExample (notifications)
    0What does empty look like?"No notifications yet"
    1Does the singular grammar work?"1 new notification" (not "1 new notifications")
    ManyDoes it scale, truncate, paginate?"99+" badge; grouped by day; "Mark all as read"

    🧮 The Edge-Case Matrix

    EXAMPLE · Profile card in a hiring app
    Edge caseRiskDesign decision
    Name is 48 charactersBreaks layoutWrap to 2 lines, then truncate with ellipsis + full name on tap
    No profile photoEmpty circle looks brokenShow initials on a colour from the token set
    Name in DevanagariFont fallback uglyUse Noto Sans family which supports Indic scripts
    Candidate withdrewActions still activeGrey card, "Withdrawn" badge, disable "Schedule interview"
    Text zoom 200%Overlapping textCard grows vertically; no fixed heights

    🔍 How to Find Edge Cases

    1. Walk every step of the user flow and ask "what if…?"
    2. Use the categories table as a checklist.
    3. Review real production data (longest names, max cart size).
    4. Ask engineers and QA — they think in edge cases daily.
    5. Check support tickets for "weird" situations.
    6. Test with real devices, slow networks and assistive tech.
    Q. Which is an edge case for a food-ordering cart?
    • A User adds one pizza
    • B Restaurant closes while the user is checking out
    • C User sees the menu
    • D User taps "Add to cart"

    Module 05 · Micro-interactions

    Micro-interactions & Motion

    Design the small moments of feedback that make an interface feel responsive, clear and alive.

    ✨ What is a Micro-interaction?

    A micro-interaction is a contained moment built around one small task: toggling a setting, liking a post, pulling to refresh, seeing a password-strength meter. Done well, users barely notice them — they just feel the product is responsive.

    ⚙️ The 4 Parts (Dan Saffer Model)

    Figure 5.1 · Anatomy of a micro-interaction
    EXAMPLE · Pull to refresh
    • Trigger: user pulls the list down past 64px.
    • Rules: fetch new items; if none, say so.
    • Feedback: spinner appears, list springs back, "3 new posts" toast.
    • Loop: after 3 refreshes with no new content, show "You're up to date".

    🗂️ Types of Micro-interactions

    TypePurposeExample
    FeedbackConfirm an actionButton press state, "Copied!" tooltip
    StatusShow system stateUpload progress, typing indicator
    ValidationPrevent errorsPassword strength meter, live format check
    NavigationShow where you wentTab underline sliding, shared-element transition
    DelightAdd personalityConfetti on first payment (use sparingly)
    HapticPhysical confirmationLight vibration on successful scan

    ⏱️ Timing & Easing

    InteractionDuration
    Button press / hover80–150 ms
    Small component change (toggle, checkbox)150–200 ms
    Panel / modal open200–300 ms
    Page transition300–400 ms (rarely more)
    • Ease-out for things entering (fast start, gentle stop).
    • Ease-in for things leaving.
    • Ease-in-out for things moving on screen.
    • Respect prefers-reduced-motion: replace movement with fades or none.
    ⚠️
    Motion must have a purpose: explain a change, give feedback or guide attention. Decorative animation that delays the user is a cost, not a feature.

    🧠 Check Yourself

    Q. In the Saffer model, what is the "trigger" for a password-strength meter?
    • A The colour green
    • B The user typing in the password field
    • C The server
    • D The submit button turning grey
    ✍️ Design the micro-interaction for "Add to wishlist". Describe trigger, rules, feedback and loops.
    Model answer: Trigger: tap heart icon. Rules: if logged out, ask to sign in and remember the item; else save optimistically. Feedback: heart fills with a 150ms scale-up, haptic tick, toast "Saved to wishlist · View". If save fails, heart un-fills and toast "Couldn't save. Try again". Loop: tapping again removes (heart empties, toast with Undo).

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🧱 Design System & Screen Design Questions

    What does "systemic" UX/UI execution mean?
    Designing every flow, state and edge case from shared rules and components, not just a polished happy-path screen, so the built product stays consistent.
    What are design tokens?
    Named values for colour, spacing, type, radius and motion. Primitive tokens hold raw values; semantic tokens describe purpose (color.action.primary) so changes propagate everywhere.
    Explain atomic design.
    Atoms (inputs, labels) combine into molecules (a search field), organisms (headers, card lists), templates (layouts) and pages (templates with real content).
    User flow vs wireflow vs journey map?
    A user flow shows paths and decisions; a wireflow connects wireframes with that logic; a journey map covers the whole experience over time, including emotions and offline touchpoints.

    🎛️ States & Edge Case Questions

    Which states do you design for every screen?
    Ideal, empty, loading, partial and error, plus success, disabled and offline where relevant — documented in a state matrix.
    How do you design a good empty state?
    Explain why it is empty and offer one clear next action. First-use, cleared, no-results and locked empties each need different copy.
    Skeleton screen or spinner?
    Skeletons for loading known layouts like feeds; spinners for short, unknown waits on small areas; progress bars for long measurable tasks.
    How do you find edge cases?
    Walk the flow asking "what if…", apply the 0–1–many rule, check long content and multiple scripts, permissions, offline, interruptions and accessibility settings, and review with QA and engineers.
    What makes a good error message?
    Plain language, placed next to the problem, explaining what happened and how to fix it, keeping the user's input, and never blaming the user.

    ✨ Interaction, Accessibility & Handoff Questions

    Describe the anatomy of a micro-interaction.
    Trigger, rules, feedback and loops & modes (Dan Saffer). Example: tapping a heart saves an item with a quick scale animation, a toast and an undo.
    What accessibility checks do you always do?
    Contrast (4.5:1 for body text), visible focus, labels on inputs, target sizes, not relying on colour alone, screen-reader order and reduced-motion support.
    What does a good handoff include?
    Flows, components and tokens, a full state matrix, edge-case decisions, final copy, motion specs and accessibility notes — walked through live with engineers.
    What is design QA?
    Testing the built product against the designs, states and edge cases on real devices and slow networks, logging issues by severity before release.

    Apply everything to one feature: flow, states, edge cases, micro-interactions and handoff.

    📄 Scenario: "Upload Documents" in a Loan App

    QuickLoan needs users to upload PAN, Aadhaar and 3 months of bank statements to apply for a personal loan. Today, 41% of applicants drop off at this step. Support tickets mention "upload stuck", "file too big" and "don't know if it worked".

    1️⃣ Task 1 · Map the Flow

    ✍️ Write the user flow for uploading the three documents, including decisions.
    Model answer: Start: Documents checklist (3 items, progress 0/3) → choose item → source: camera / gallery / PDF → preview + crop → upload with progress → auto-check (readable? right document?) → if fail: reason + retake → item ticked → repeat → all 3 done → "Submit for review" → success with expected review time. Users can leave and resume; progress is saved.

    2️⃣ Task 2 · Design the States

    Q. A 12 MB bank-statement PDF is uploading on 3G. Best loading state?
    • A Full-screen spinner with no text
    • B Progress bar with % and Cancel, rest of the checklist still usable
    • C Nothing until it finishes
    • D A confetti animation
    ✍️ List the empty, loading, error and success states for one document item.
    Model answer: Empty: "PAN card — Upload a clear photo of the front" + example thumbnail + Upload button. Loading: thumbnail + progress bar % + Cancel. Errors: file too large ("Max 5 MB — we can compress it for you" [Compress]), blurry ("Text isn't readable. Retake in good light"), wrong document ("This looks like an Aadhaar. Please upload your PAN"), network ("Upload paused — we'll resume when you're online"). Success: green tick, "Uploaded", Replace link.

    3️⃣ Task 3 · Map Edge Cases

    ✍️ List at least 5 edge cases and your design decision for each.
    Model answer: (1) Password-protected bank PDF → ask for password field. (2) User has e-statement only on email → allow forwarding to a unique upload email. (3) App killed mid-upload → resume on reopen. (4) Camera permission denied → explain + gallery option + settings link. (5) Statement covers only 2 months → "We need 3 months: Feb–Apr" with missing month highlighted. (6) Screen reader → each item announces status "PAN, uploaded".

    4️⃣ Task 4 · Micro-interactions

    Q. Which micro-interaction best answers "don't know if it worked"?
    • A A spinning logo for 3 seconds
    • B Item card animates to a tick + checklist counter updates to 2/3 + haptic tick
    • C Background colour changes randomly
    • D A sound plays on every tap

    5️⃣ Task 5 · Handoff & QA

    ✍️ What will you include in your handoff and what will you check in design QA?
    Model answer: Handoff: flow diagram, component variants from the design system, state matrix, edge-case list with decisions, file-size and format rules, copy for every message, motion specs (tick 200ms ease-out), accessibility notes. QA: test on a low-end Android on throttled 3G, kill app mid-upload, deny camera, upload 20MB PDF, use TalkBack, check contrast; log issues by severity; success metric to watch after release: document-step drop-off (41% → target 25%).

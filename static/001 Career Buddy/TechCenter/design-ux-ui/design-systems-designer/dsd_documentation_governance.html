    Module 01 · Foundations

    What is Design System Governance?

    Start from zero: what documentation and governance mean, why systems fail without them, and the main governance models.

    🧭 What is Governance?

    Governance is the set of processes, roles and rules that decide how a design system changes: who can propose components, how they are reviewed, how versions are released and how teams are supported. Documentation explains what exists and how to use it correctly.

    🔴 Without governance

    Duplicate components, inconsistent versions, breaking changes with no warning, teams stop trusting the system.

    🟢 With governance

    Clear contribution path, predictable releases, documented decisions, high adoption and trust.

    🏛️ Types of Governance Models

    ModelHow it worksProsCons
    CentralisedA dedicated team builds and owns everythingConsistent qualityBottleneck; may miss product needs
    FederatedDesigners from product teams contribute and decide togetherClose to real needsHarder to keep consistent
    HybridCore team owns foundations; product teams contribute with reviewBalance of bothNeeds clear process
    SolitaryOne team's system that others borrowFast to startDoesn't scale

    👥 Roles

    RoleResponsibility
    System lead / ownerVision, roadmap, priorities
    Design system designersComponents, tokens, Figma libraries, docs
    Design system engineersCoded components, tooling, releases
    ContributorsPropose and build components from product teams
    Accessibility specialistStandards and audits
    Champions / ambassadorsAdvocate adoption inside product teams

    📖 Key Terms

    Contribution modelHow others propose and add to the system.
    Component lifecycleStages from proposal to removal.
    Semantic versioningMAJOR.MINOR.PATCH version numbers.
    Release notes / changelogWhat changed in each version.
    DeprecationMarking something for future removal, with guidance.
    Documentation portalWebsite where the system is documented (Zeroheight, Storybook, Supernova).
    RFCRequest for Comments — written proposal for a significant change.

    Module 02 · Lifecycle

    Component Lifecycle Management

    Move components from idea to stable to retirement with clear stages and criteria.

    🔄 Lifecycle Stages

    Figure 2.1 · Component lifecycle
    StageExit criteria
    Proposed → AlphaNeed confirmed in 2+ products; no existing component fits
    Alpha → BetaDesign + code built, accessible, documented basics
    Beta → StableUsed in production by pilot teams; feedback addressed; full docs
    Stable → DeprecatedReplaced or no longer needed; migration path ready
    Deprecated → RemovedUsage near zero; next major version

    🤝 Contribution Process

    1. Check the system and backlog — does something already exist?
    2. Propose via a form or RFC: problem, use cases, screenshots, alternatives.
    3. Triage by the core team: accept, extend existing, or keep local.
    4. Design & build with pairing and reviews (design, accessibility, code).
    5. Document and release with notes.
    6. Support and gather feedback.
    Contribution sizeExamplePath
    Small fixTypo, icon added, bugDirect PR + review
    EnhancementNew variant or propertyProposal + design review
    New componentDate range pickerRFC + full lifecycle

    🧠 Check Yourself

    Q. A component works but should not be used in new work. Status?
    • A Stable
    • B Beta
    • C Deprecated
    • D Alpha
    ✍️ A team asks for a new "Stepper" component. What do you check first?
    Model answer: Whether an existing component or pattern (progress indicator, tabs) covers the need; how many products need it; the use cases and states required; accessibility requirements; and whether to build it as a system component or keep it local first.

    Module 03 · Versioning

    Versioning & Release Notes

    Release changes predictably so teams can upgrade with confidence.

    🔢 Semantic Versioning

    PartWhen to bumpExample
    MAJOR (2.0.0)Breaking changes: removed/renamed components, props or tokensButton "type" prop renamed to "variant"
    MINOR (1.4.0)New backward-compatible featuresNew "Tertiary" button variant
    PATCH (1.4.1)Backward-compatible bug fixesFixed focus ring offset
    📌
    Pre-releases like 2.0.0-beta.1 let pilot teams test before a major release.

    📝 Writing Release Notes

    markdown## v2.3.0 — 14 Oct 2026
### Added
- DateRangePicker (beta) — select start and end dates. Docs: /components/date-range-picker
### Changed
- Button: loading state now announces "Loading" to screen readers
### Fixed
- Input: error text now linked with aria-describedby
### Deprecated
- Tag component → use Chip. Removal planned in v3.0.0. Migration guide: /migrate/tag-to-chip
    • Group by Added / Changed / Fixed / Deprecated / Removed / Breaking.
    • Link to docs and migration guides.
    • Note impact for designers and engineers.
    • Keep Figma library versions and code package versions aligned or mapped.

    🎨 Figma Library Releases

    • Use branching for big changes; review before merging.
    • Publish with a clear description (Figma shows it to consumers on update).
    • Avoid renaming or deleting published components without deprecation — instances may break or detach.
    • Announce updates in a channel and changelog.

    📚 Storybook Basics

    tsx// Button.stories.tsx
import { Button } from "./Button";
export default { title: "Components/Button", component: Button };
export const Primary = { args: { variant: "primary", children: "Save" } };
export const Loading = { args: { variant: "primary", loading: true, children: "Saving" } };
export const Disabled = { args: { disabled: true, children: "Save" } };
    • Controls let anyone change props live.
    • Addons: a11y (axe checks), viewport, interactions, visual regression (Chromatic).
    • Stories can be embedded in Zeroheight pages.

    ✍️ Writing Good Docs

    • Lead with when to use / when not to use.
    • Show real examples, not lorem ipsum.
    • Keep it short; link out for depth.
    • Use the same names as Figma and code.
    • Review docs as part of every release.

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🏛️ Governance Questions

    Centralised vs federated governance?
    Centralised: a core team owns everything — consistent but a bottleneck. Federated: product teams contribute and decide — closer to needs but harder to keep consistent. Most mature systems use a hybrid.
    How does your contribution process work?
    Check existing options, propose via form/RFC, triage, design and build with reviews (design, accessibility, code), document, release and support.
    How do you decide whether a component belongs in the system?
    Used in multiple products, solves a common need, stable enough to maintain, and can't be met by extending an existing component.
    How do you handle a team that keeps building custom components?
    Understand why (missing features, speed, awareness), fix gaps, offer pairing and support, and make the system the easiest path.

    🔢 Lifecycle & Versioning

    Describe the component lifecycle.
    Proposed → alpha → beta → stable → deprecated → removed, with clear exit criteria at each stage.
    Explain semantic versioning.
    MAJOR for breaking changes, MINOR for backward-compatible features, PATCH for fixes.
    How do you deprecate a component?
    Mark it deprecated in Figma, code and docs, provide a replacement and migration guide, announce it in release notes, track usage and remove it in the next major version.
    What makes good release notes?
    Grouped changes (added, changed, fixed, deprecated, breaking), impact for designers and engineers, links to docs and migration steps.
    How do you keep Figma and code versions in sync?
    Shared changelog, matching names, release checklists that cover both, and versioned token and component packages mapped to Figma library publishes.

    📚 Documentation & Metrics

    Zeroheight vs Storybook?
    Zeroheight is a documentation site for guidelines that embeds Figma and code; Storybook shows live coded components with controls and testing. Many teams embed Storybook in Zeroheight.
    What belongs on a component doc page?
    Overview, anatomy, variants, states, usage do/don't, content guidance, accessibility, code and props, related components, changelog.
    How do you measure design system success?
    Adoption in design and code, detach rate, version currency, time saved, accessibility and UI quality, satisfaction and support load.
    How do you keep docs up to date?
    Make docs part of the definition of done for every change, review them in each release, and assign ownership per component.

    Practice: Fix a Struggling Design System

    Set up governance, lifecycle and documentation for a real-feeling system with low trust.

    0 / 0 correct

    🧯 Scenario: Nimbus Design System

    Nimbus is used by 8 product teams. Problems: three different date pickers in production, a rename of Button props broke two apps without warning, docs live in an outdated PDF, and teams say "it's faster to build our own".

    1️⃣ Task 1 · Governance Model

    Q. Which model fits best?
    • A Solitary
    • B Hybrid: core team owns foundations; product teams contribute via a reviewed process
    • C No governance
    • D Fully federated with no core team
    ✍️ Define the contribution process in 5 steps.
    Model answer: 1. Search system/backlog. 2. Submit proposal (problem, use cases, screenshots). 3. Weekly triage: accept, extend existing or keep local. 4. Co-design/build with design, a11y and code review. 5. Document, release with notes, gather feedback in beta.

    2️⃣ Task 2 · Date Pickers

    ✍️ How do you consolidate three date pickers?
    Model answer: Audit all three and their use cases; design one DatePicker (with range option) covering them; release as beta to pilot teams; mark old pickers deprecated with a migration guide; track usage; remove in next major.

    3️⃣ Task 3 · Versioning

    Q. The Button prop rename should have been released as…
    • A A PATCH
    • B A MINOR
    • C A MAJOR with deprecation period and migration notes
    • D Unannounced

    4️⃣ Task 4 · Documentation

    ✍️ Plan the new documentation portal.
    Model answer: Zeroheight site embedding Figma frames and Storybook stories; each component page: overview, anatomy, variants, states, do/don't, content, accessibility, code/props, changelog; owners per component; docs update required in the definition of done.

    5️⃣ Task 5 · Metrics

    ✍️ Which 4 metrics will prove the system is improving?
    Model answer: 1. Figma component coverage and detach rate. 2. % of apps on the latest major version. 3. Number of duplicate custom components in audits. 4. Quarterly satisfaction score from designers and engineers.

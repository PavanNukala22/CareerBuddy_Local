    Module 01 · Foundations

    What is Accessibility (a11y)?

    Start from zero: what accessibility means, who it serves, the POUR principles and how WCAG 2.1/2.2 is structured.

    🧭 What is Accessibility?

    Accessibility (a11y) means people with disabilities can perceive, understand, navigate and interact with products. For a design system, accessibility is built into every token and component so every product team inherits it by default.

    👁️
    Visual
    Blindness, low vision, colour blindness.
    👂
    Auditory
    Deaf and hard of hearing.
    🖐️
    Motor
    Limited dexterity, tremors, one-handed use.
    🧠
    Cognitive
    Memory, attention, learning differences.
    📌
    Disabilities can be permanent (one arm), temporary (broken wrist) or situational (holding a baby, bright sunlight). Accessible design helps everyone.

    🏛️ POUR Principles

    PrincipleMeaningExample
    PerceivableInformation can be seen/heardAlt text, captions, contrast
    OperableInterface can be usedKeyboard access, enough time, target size
    UnderstandableContent and behaviour are clearLabels, consistent navigation, error help
    RobustWorks with assistive technologiesValid semantics, correct ARIA

    📚 WCAG Structure & Levels

    LevelMeaningTypical target
    AMinimum — essential barriers removedMust
    AAStandard most laws and policies requireDesign system default
    AAAEnhanced — not always achievable for all contentSpecific needs
    VersionNotes
    WCAG 2.1 (2018)Added mobile, low vision and cognitive criteria (reflow, non-text contrast, target size AAA)
    WCAG 2.2 (2023)Adds focus not obscured, focus appearance (AAA), dragging movements, target size minimum (AA), consistent help, redundant entry, accessible authentication; removes 4.1.1 Parsing

    📖 Key Terms

    Assistive technology (AT)Screen readers (NVDA, JAWS, VoiceOver, TalkBack), switch access, magnifiers, voice control.
    Accessible nameWhat AT announces for an element ("Search, button").
    RoleWhat an element is (button, link, checkbox).
    StateCurrent condition (checked, expanded, disabled).
    FocusWhich element receives keyboard input.
    Success criterion (SC)A testable WCAG requirement, e.g. SC 1.4.3 Contrast (Minimum).
    Q. What does the "O" in POUR stand for?
    • A Optional
    • B Operable
    • C Organised
    • D Open

    Module 02 · Contrast

    Colour & Contrast

    Meet contrast requirements for text, components and graphics, and never rely on colour alone.

    🎨 Contrast Requirements

    Success criterionLevelRequirement
    1.4.3 Contrast (Minimum)AAText 4.5:1; large text (≥ 24 px regular or ≥ 18.66 px bold) 3:1
    1.4.6 Contrast (Enhanced)AAAText 7:1; large text 4.5:1
    1.4.11 Non-text ContrastAAUI components (borders, focus indicators, icons) and meaningful graphics 3:1
    1.4.1 Use of ColourAColour must not be the only way to convey information
    💡
    Disabled components are exempt from contrast rules — but they should still be clearly identifiable, and you should consider explaining why something is disabled.

    🧪 Testing Contrast

    PairRatioResult
    #37352F on #FFFFFF~12.6:1✅ AAA text
    #787774 on #FFFFFF~4.5:1✅ AA text (borderline)
    #A3A3A3 on #FFFFFF~2.5:1❌ fails text and UI
    #14213D button on #FFFFFF page~16:1✅ component boundary
    • Tools: Stark, Contrast plugin (Figma), WebAIM Contrast Checker, axe DevTools.
    • Bake checks into tokens: every text/background semantic pair documented with its ratio.
    • Check every mode (light, dark, high contrast) and brand theme.

    🚦 Beyond Colour

    EXAMPLE · Form error

    ❌ Red border only. ✅ Red border + error icon + text "Enter a valid PIN code (6 digits)" linked to the input with aria-describedby.

    Q. Minimum contrast for a text-input border against the page (AA)?
    • A 1.5:1
    • B 3:1
    • C 4.5:1
    • D 7:1

    Module 03 · Focus States

    Focus States & Keyboard Access

    Make every interaction reachable by keyboard with clear, unobscured focus indicators.

    ⌨️ Keyboard Criteria

    Success criterionLevelRequirement
    2.1.1 KeyboardAAll functionality available via keyboard
    2.1.2 No Keyboard TrapAFocus can always move away
    2.4.3 Focus OrderAOrder preserves meaning and operability
    2.4.7 Focus VisibleAAKeyboard focus indicator is visible
    2.4.11 Focus Not Obscured (Minimum)AA (2.2)Focused element not entirely hidden by sticky headers, banners
    2.4.13 Focus AppearanceAAA (2.2)Indicator at least a 2 px perimeter with 3:1 contrast change
    2.4.1 Bypass BlocksASkip link to main content

    🎯 Designing Focus Indicators

    • Use a focus token: e.g. 2 px outline + 2 px offset in color.focus.ring, 3:1 against adjacent colours.
    • Show focus on keyboard navigation (:focus-visible), not necessarily on mouse click.
    • Never remove outlines without a replacement.
    • Design focus for every component variant and on dark/coloured backgrounds (double ring: dark + light).
    css.btn:focus-visible {
  outline: 2px solid var(--color-focus-ring);
  outline-offset: 2px;
}

    🧭 Keyboard Patterns

    ComponentKeys
    ButtonEnter / Space activate
    LinkEnter
    CheckboxSpace toggles
    Radio groupArrow keys move selection; Tab enters/leaves group
    TabsArrow keys between tabs; Tab into panel
    Menu / listboxArrows navigate; Enter selects; Esc closes
    Modal dialogFocus moves in, trapped inside, Esc closes, focus returns to trigger
    Q. In a modal dialog, where should focus go when it closes?
    • A Top of the page
    • B Back to the element that opened it
    • C Nowhere
    • D The footer

    Module 04 · Semantics

    Screen Reader Semantics

    Give every element the right role, name, state and structure so assistive technologies understand the UI.

    🗣️ Name, Role, Value (SC 4.1.2)

    ElementRoleNameState/value
    Search buttonbutton"Search"—
    Mute toggleswitch / button"Mute notifications"aria-checked / aria-pressed
    Accordion headerbutton"Shipping details"aria-expanded="true"
    Quantity fieldspinbutton / textbox"Quantity"value 2
    💡
    First rule of ARIA: use native HTML elements (button, a, input, select) whenever possible. ARIA only adds meaning; it doesn't add behaviour.

    🧱 Semantic Structure

    • Headings in logical order (h1 → h2 → h3); screen reader users navigate by headings.
    • Landmarks: header, nav, main, aside, footer.
    • Lists for groups of items (users hear "list, 5 items").
    • Tables with header cells for data.
    • Labels: every input has a visible label programmatically linked.
    html<label for="pin">PIN code</label>
<input id="pin" inputmode="numeric" aria-describedby="pin-err" aria-invalid="true">
<p id="pin-err">Enter a valid 6-digit PIN code</p>

    🖼️ Images, Icons & Live Updates

    ContentGuidance
    Informative imageMeaningful alt text describing purpose
    Decorative imageEmpty alt (alt="") so it's skipped
    Icon-only buttonaria-label ("Close") — icon itself hidden
    Toasts & async resultsLive region (role="status" or aria-live="polite")
    Errors on submitMove focus to error summary or announce with role="alert"

    📝 Documenting Semantics in Specs

    Design-system docs should include an accessibility spec per component: role, accessible name source, states, keyboard interaction, focus management and announcements.

    Q. A close button shows only an "×" icon. What does it need?
    • A Nothing
    • B An accessible name like aria-label="Close"
    • C A red colour
    • D A tooltip only

    Module 05 · Tap Targets

    Tap Targets, Input & WCAG 2.2 Additions

    Make controls easy to hit and input forgiving for motor and cognitive needs.

    👆 Target Size

    CriterionLevelRequirement
    2.5.8 Target Size (Minimum)AA (2.2)At least 24 × 24 CSS px, or enough spacing so a 24 px circle doesn't overlap another target
    2.5.5 Target Size (Enhanced)AAAAt least 44 × 44 CSS px
    Platform guidance—iOS 44 × 44 pt, Material 48 × 48 dp
    💡
    Design-system default: visible element can be smaller (e.g. 20 px icon), but the hit area is 44–48 px.

    🧩 Other WCAG 2.2 Criteria

    CriterionLevelDesign implication
    2.5.7 Dragging MovementsAAProvide single-pointer alternative to drag (e.g. move buttons for reorder)
    3.2.6 Consistent HelpAHelp options in the same place across pages
    3.3.7 Redundant EntryADon't make users re-enter info already given (auto-fill, "same as billing")
    3.3.8 Accessible Authentication (Minimum)AANo cognitive tests like memorising passwords without alternatives — allow paste, password managers, OTP, passkeys

    🧠 Reflow, Text & Motion

    CriterionRequirement
    1.4.4 Resize Text (AA)Text resizes to 200% without loss of content
    1.4.10 Reflow (AA)No horizontal scroll at 320 CSS px width (except data tables, maps)
    1.4.12 Text Spacing (AA)Layout survives increased line/letter/word spacing
    2.3.1 Three Flashes (A)No flashing more than 3 times per second
    2.2.2 Pause, Stop, Hide (A)Moving content over 5 s can be paused

    🧪 Testing Accessibility

    • Automated: axe, Lighthouse, WAVE — catch ~30–40% of issues.
    • Manual: keyboard-only walkthrough, zoom to 200%/400%, reduced motion.
    • Screen readers: NVDA/JAWS (Windows), VoiceOver (macOS/iOS), TalkBack (Android).
    • Usability testing with people with disabilities.
    Q. Minimum target size in WCAG 2.2 AA?
    • A 16 × 16 px
    • B 24 × 24 CSS px (or sufficient spacing)
    • C 44 × 44 px required
    • D 100 × 100 px

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🏛️ WCAG Fundamentals

    What are the POUR principles?
    Perceivable, Operable, Understandable and Robust — the four principles WCAG is organised around.
    What is new in WCAG 2.2?
    Focus not obscured (AA) and focus appearance (AAA), dragging movements, target size minimum (AA), consistent help, redundant entry and accessible authentication; 4.1.1 Parsing was removed.
    Which conformance level should a design system target?
    AA as the baseline for all components, with AAA where practical (e.g. 7:1 text options, 44 px targets).
    Why build accessibility into the design system?
    Every product inherits accessible tokens and components by default, reducing repeated work and risk.

    🎨 Contrast & Focus

    What are the contrast requirements?
    Text 4.5:1 (large text 3:1) at AA, 7:1 at AAA; UI components, focus indicators and meaningful graphics 3:1.
    How do you design focus states for a system?
    A focus token (e.g. 2 px ring with offset, 3:1 contrast), shown with :focus-visible, applied to every interactive variant and tested on all backgrounds and themes.
    What is focus not obscured?
    WCAG 2.2 SC 2.4.11: a focused element must not be completely hidden by sticky headers, cookie banners or other overlays.
    How should a modal handle focus?
    Move focus into the dialog, keep it inside while open, close with Esc, and return focus to the element that opened it.
    Is colour alone acceptable to show errors?
    No — add icons, text and programmatic association so the error is perceivable without colour.

    🗣️ Semantics & Input

    What is the first rule of ARIA?
    Use native HTML elements whenever possible; add ARIA only when native semantics are insufficient.
    How do you document component accessibility?
    Role, accessible name source, states, keyboard interactions, focus management, announcements, contrast and target size per component.
    What are WCAG target size rules?
    2.5.8 AA: at least 24 × 24 CSS px or sufficient spacing; 2.5.5 AAA: 44 × 44 CSS px. Systems usually adopt 44–48 px hit areas.
    How do you test accessibility?
    Automated scans plus manual keyboard, zoom and screen-reader testing, and research with disabled users.

    0 / 0 correct

    🧾 Scenario: GovPay Design System Audit

    GovPay, a public payments platform, must meet WCAG 2.2 AA. You audit four components: a grey placeholder-only input, an icon-only "×" chip, a drag-to-reorder list, and a sticky header that covers focused fields when tabbing.

    1️⃣ Task 1 · Input

    ✍️ List the issues with a placeholder-only input (#A3A3A3 text) and fixes.
    Model answer: Issues: no persistent label (3.3.2, 1.3.1), placeholder contrast ~2.5:1 fails 1.4.3, border may fail 1.4.11, errors shown by colour only. Fixes: visible label linked with for/id, placeholder only as a hint with ≥4.5:1 text, border ≥3:1, error text + icon via aria-describedby and aria-invalid.

    2️⃣ Task 2 · Icon Chip

    Q. The chip's "×" is 16 px with no spacing. What fails?
    • A Nothing
    • B Target size (2.5.8) and accessible name (4.1.2)
    • C Only colour
    • D Only motion
    ✍️ Specify the fixed remove button.
    Model answer: Hit area at least 24 × 24 (system default 44 px) with the 16 px icon centred; aria-label="Remove filter: Paid"; visible focus ring from the focus token; keyboard: Enter/Space removes and focus moves to the next chip or the field.

    3️⃣ Task 3 · Drag List

    Q. Which WCAG 2.2 criterion applies to drag-to-reorder?
    • A 2.5.7 Dragging Movements
    • B 1.4.3 Contrast
    • C 2.4.1 Bypass Blocks
    • D 3.1.1 Language
    ✍️ Design the alternative.
    Model answer: Add "Move up / Move down" buttons (or a "Move to position" menu) on each row, operable by single tap and keyboard, with a live region announcing "Item moved to position 3 of 5".

    4️⃣ Task 4 · Sticky Header

    ✍️ How do you fix focused fields hidden under the sticky header?
    Model answer: Meets SC 2.4.11 by adding scroll-padding-top equal to the header height so focused elements scroll into view below it, reducing header height on scroll, and testing by tabbing through long forms at 200% zoom.

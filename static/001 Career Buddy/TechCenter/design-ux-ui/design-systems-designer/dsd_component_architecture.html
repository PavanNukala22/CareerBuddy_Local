    Module 01 · Foundations

    What is Component Architecture?

    Start from zero: what a component is, why modular design scales, and the vocabulary of component systems.

    🧭 What is a Component?

    A component is a reusable UI building block — button, input, card, modal — defined once with all its variations and states. Component architecture is how components are structured, composed and configured so a whole product can be built from a small, reliable set of parts.

    🔴 Ad-hoc design

    Every designer draws their own button. 14 slightly different buttons ship; changing one style means hunting through files.

    🟢 Modular system

    One Button component with variants and properties. Update the master; every instance updates.

    🗂️ Types of Components

    TypeDescriptionExamples
    Primitives / atomsSmallest building blocksIcon, text, divider, avatar
    Basic componentsSingle-purpose controlsButton, input, checkbox, badge
    Composite componentsBuilt from basic componentsSearch field, list item, card
    PatternsRecurring solutions combining componentsForm with validation, empty state
    Templates / layoutsPage-level structureDashboard layout, settings page
    Local / product componentsSpecific to one product, not in core systemTrading order ticket

    🧱 Principles of Modular Design

    🎯
    Single responsibility
    Each component does one job well.
    🧩
    Composable
    Small parts combine into bigger ones.
    ⚙️
    Configurable
    Props/properties instead of copies.
    🔒
    Encapsulated
    Internal details hidden; clear API.
    📏
    Token-driven
    Values come from tokens, not raw numbers.
    ♿
    Accessible by default
    States and semantics built in.

    📖 Key Terms

    Main componentThe master definition in Figma.
    InstanceA copy linked to the main component.
    VariantA version of a component defined by property values (size=lg, state=hover).
    Component propertyA configurable option: text, boolean, instance swap, variant.
    SlotAn area where any content can be placed (via instance swap or native slot features).
    OverrideA change on an instance (text, colour) that persists through updates.
    DetachingBreaking the link to the main — avoid in system usage.

    🧩 Nesting Patterns

    EXAMPLE · List item component
    • Outer frame: horizontal, padding 12/16, gap 12, fill width.
    • Leading slot: avatar or icon (hug).
    • Text stack: vertical, gap 2, fill width so long text wraps and pushes trailing content correctly.
    • Trailing slot: badge, chevron or toggle (hug).
    • Min height 56 px for touch targets.
    💡
    Use wrap for chip groups and tag lists, and max width on text to keep line lengths readable.

    Localisation (German, Hindi)Longer words and taller scripts
    RTLMirroring of leading/trailing slots

    Module 03 · Variants & Properties

    Variants, Component Properties & Slots

    Design clean component APIs that are easy to use and map directly to code props.

    🎛️ Types of Component Properties

    Property typeUseExample
    VariantVisual versions and statesSize: sm/md/lg · State: default/hover/pressed/disabled
    BooleanShow/hide a layerShow icon: true/false
    TextEditable text exposed at top levelLabel: "Save changes"
    Instance swapSwap a nested componentIcon: ic_search / ic_close
    Nested instance propsExpose child properties on the parentCard exposes its Button label
    Slot (native / via swap)Flexible content regionModal body accepts any content

    🧮 Avoiding Variant Explosion

    EXAMPLE · Button

    Size (3) × Type (4) × State (5) × Icon left (2) × Icon right (2) = 240 variants. Instead: variants only for Size, Type and State (60), and boolean + instance-swap properties for icons. Hover/pressed can be handled with interactive components.

    💡
    Rule of thumb: use variants for visual changes that need different layers or styles; use booleans, text and instance swaps for content toggles.

    🔗 Design API = Code API

    Figma propertyReact prop
    Type = Primaryvariant="primary"
    Size = mdsize="md"
    Show leading icon (boolean) + Icon (swap)leadingIcon={<SearchIcon />}
    Label (text)children / label
    State = Disableddisabled={true}
    State = Loadingloading={true}
    react<Button variant="primary" size="md" leadingIcon={<SearchIcon />} loading={false}>
  Search
</Button>
    📌
    Agree property names with engineering. If Figma says "Type" and code says "variant", designers and developers misunderstand each other.

    Module 04 · Composition

    Composition Patterns & Slots

    Build flexible components through composition instead of endless configuration.

    🧩 Configuration vs Composition

    ⚙️ Configuration

    One component with many props: <Card title image footer badge actions …>. Easy at first, rigid and bloated later.

    🧱 Composition

    Small parts assembled: <Card><Card.Media/><Card.Header/><Card.Body/><Card.Footer/></Card>. Flexible and predictable.

    🗂️ Slot Patterns in Figma

    PatternHowUse
    Placeholder swapEmpty "Slot" component swapped for contentModal body, card content
    Native slotsFigma's slot feature where availableFree-form content areas
    Preferred instancesCurated list in instance swapAllowed icons or footers
    Sub-componentsCard.Header, Card.Footer as separate componentsComposable building blocks

    🧷 Edge-Case Handling in Components

    Edge caseComponent behaviour
    Very long labelWrap to 2 lines or truncate with tooltip (document which)
    Missing imageFallback placeholder with initials or icon
    No actionsFooter collapses, spacing adjusts
    LoadingSkeleton variant of the component
    ErrorError variant with message slot
    Disabled + tooltipExplain why disabled
    Overflow (many tags)"+3" overflow chip

    Module 05 · Scaling

    Scaling a Component Library

    Organise, test and evolve a large component library across teams.

    🗄️ Library Structure

    LayerContent
    Foundations libraryTokens/variables, styles, icons, grids
    Core componentsButtons, inputs, navigation, overlays
    PatternsForms, tables, empty states
    Product librariesDomain components built on core
    TemplatesPage layouts and flows
    • Use clear page and naming structure: Button / Primary / Medium.
    • Hide internal building blocks with a leading "." or "_".
    • Publish with descriptions and links to documentation.

    🧪 Quality Checklist for a Component

    • All variants and states (default, hover, focus, pressed, disabled, loading, error).
    • Built with auto layout and token variables only.
    • Stress-tested for long text, empty content, RTL, 200% text.
    • Accessible: contrast, focus indicator, target size, labels.
    • Properties named like code props.
    • Documented usage, do/don't, anatomy and accessibility notes.

    📈 Measuring Adoption

    Component coverage% of product screens built with library components (Figma library analytics)
    Detach rateHow often instances are detached — high means gaps in the system
    Code adoptionImports of system components vs custom ones
    Contribution rateProposals and PRs from product teams

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🧱 Component Fundamentals

    What makes a good component?
    Single responsibility, composable, configured via clear properties, token-driven, accessible by default, stress-tested and documented.
    Primitive vs composite components?
    Primitives are the smallest parts (icon, text); composites combine basic components (search field = input + button).
    When should something become a system component?
    When it is used in multiple products or places, solves a common need, and is stable enough to maintain; otherwise keep it local.
    Why avoid detaching instances?
    Detached copies stop receiving updates, creating inconsistency and hidden debt.

    🎛️ Variants & Auto Layout

    How do you avoid variant explosion?
    Use variants only for visual changes needing different structure/styles; use boolean, text and instance-swap properties for content toggles; use interactive components for hover/pressed.
    Hug vs fill vs fixed?
    Hug sizes to content, fill stretches to the parent, fixed keeps an explicit size. Text that should wrap usually uses fill.
    How do you stress-test a component?
    Long and empty content, 200% text size, narrow/wide containers, translations, RTL and every state.
    How do Figma properties map to code?
    Variants map to enum props (size, variant), booleans to boolean props, text to string/children, instance swaps to slot/ReactNode props — with names agreed with engineering.
    What are slots?
    Flexible content regions in a component where designers can place any approved content, avoiding endless configuration props.

    📈 Scaling & Edge Cases

    Configuration vs composition?
    Configuration exposes many props on one component; composition assembles sub-components. Composition scales better for complex, varied content.
    How do you handle edge cases in components?
    Define behaviour for long text, missing images, empty slots, loading and error states, overflow and disabled reasons — as variants or documented rules.
    How do you measure library health?
    Coverage, detach rate, code adoption, contribution rate and number of open issues or requests.
    How do you structure a large Figma library?
    Separate foundations, core components, patterns, product libraries and templates; consistent naming; hidden internal parts; descriptions linked to docs.

    Practice: Architect a Data Table Component

    Design the architecture of a complex, real-feeling component.

    0 / 0 correct

    📊 Scenario: OpsBoard Admin Data Table

    OpsBoard needs one data table for orders, users and invoices: sorting, selection, inline status badges, row actions, pagination, loading/empty/error states, and compact/comfortable density. Today each team builds its own table.

    1️⃣ Task 1 · Decompose

    ✍️ Break the table into sub-components.
    Model answer: Table (container) → Toolbar (search, filters, bulk actions) → Header row → Header cell (sortable, sort direction) → Body row (selectable, hover, selected) → Cell types (text, number, badge, avatar+text, actions menu) → Pagination → State views (loading skeleton rows, empty, error).

    2️⃣ Task 2 · Properties

    ✍️ Define properties for the Header cell.
    Model answer: Variants: Sort = none/asc/desc; Align = left/right; State = default/hover/focus. Boolean: sortable, show info icon. Text: label. Swap: info tooltip icon. Code: <HeaderCell sortable sort="asc" align="right">Amount</HeaderCell>.
    Q. Density (compact/comfortable) is best handled by…
    • A Duplicating the whole table
    • B A density token mode or one variant property controlling row height and padding tokens
    • C Different components per team
    • D Manual resizing

    3️⃣ Task 3 · Edge Cases

    ✍️ List 5 edge cases and how the table handles them.
    Model answer: Long customer names → truncate with tooltip; 0 rows → empty state with "Clear filters"; 10,000 rows → pagination/virtualisation; loading → 8 skeleton rows; numeric columns → right-aligned tabular figures; failed load → error row with Retry; narrow screens → horizontal scroll with sticky first column.

    4️⃣ Task 4 · Adoption

    Q. After release, the Orders team detaches the table often. First step?
    • A Ban detaching
    • B Interview the team, find missing needs, and add them as properties or slots
    • C Ignore
    • D Delete the component

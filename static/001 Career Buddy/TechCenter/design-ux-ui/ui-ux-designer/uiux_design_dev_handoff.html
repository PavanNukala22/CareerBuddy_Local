    Module 01 · Foundations

    What is Design-to-Development Handoff?

    Start from zero: what handoff is, why it fails, and what developers need from designers.

    🧭 What is Handoff?

    Handoff is the process of sharing designs, specs, assets and behaviour with developers so they can build exactly what was designed. Modern handoff is continuous collaboration, not a single "throw it over the wall" moment.

    🔴 Poor handoff

    A link to a Figma file with 60 unnamed frames. Missing states, unclear spacing, assets not exportable. Developers guess.

    🟢 Good handoff

    Organised file marked "Ready for dev", annotated flows, all states, tokens, exportable assets, walkthrough meeting, design QA.

    📦 What Developers Need

    🗺️
    Flows
    How screens connect, including errors.
    🎛️
    States
    Empty, loading, error, success, disabled.
    📏
    Specs
    Spacing, sizes, type, colours as tokens.
    🖼️
    Assets
    Icons, images, illustrations in the right formats.
    ✍️
    Copy
    Final text for every label and message.
    ♿
    Accessibility
    Labels, focus order, contrast notes.

    🗂️ Types of Handoff Artefacts

    Writing Developer Specs

    Document layout, behaviour, content and edge cases so developers don't have to guess.

    📏 Visual Specs

    SpecExample
    SpacingCard padding space-4 (16px), gap space-3 (12px)
    TypographyTitle: heading/sm (20/600/1.3), body/md (16/400/1.5)
    ColourBackground color/bg/surface, text color/text/primary
    SizesButton height 48, icon 24, avatar 40
    Radius & elevationradius/md (8px), shadow/level-1
    BreakpointsMobile < 600, tablet 600–1024, desktop > 1024
    💡
    Reference tokens and components, not raw values — "Button / Primary / md" beats "navy 48px box".

    ⚙️ Behaviour Specs

    ElementBehaviour spec
    Search fieldDebounce 300 ms; min 2 characters; show recent searches on focus; Esc clears
    Save buttonDisabled until form changes; loading spinner; success toast "Saved"

    🧷 States, Edge Cases & Copy

    • A state matrix per component: default, hover, focus, pressed, disabled, loading, empty, error, success.
    • Edge cases: long names (truncate after 2 lines), missing images (placeholder), 0/1/many items, offline.
    • Final copy for labels, errors, empty states and confirmations.
    • Responsive notes: what stacks, hides or changes per breakpoint.
    Q. Which spec is most useful to a developer?
    • A "Make it look nice"
    • B "Card uses padding space-4 and title heading/sm; title truncates after 2 lines"
    • C "Use some blue"
    • D "Like the old one"

    ✅ Asset Checklist

    • Mark layers as exportable in Figma (export settings set).
    • Consistent naming: type_name_size_variant.
    • Optimise files (SVGO, Squoosh) and set size budgets.
    • Transparent backgrounds where needed.
    • Alt text or descriptions for meaningful images.
    • Store in the shared library/repo, not personal folders.

    Understand how designs become code so you design things that can be built well.

    🧱 How Figma Maps to CSS

    FigmaCSS
    Auto layoutdisplay: flex
    Gapgap
    Paddingpadding
    Hug / fillwidth: fit-content / flex: 1
    Corner radiusborder-radius
    Drop shadowbox-shadow
    Layout gridCSS Grid / max-width containers
    Text stylefont-family, font-size, font-weight, line-height
    css.card {
  display: flex; flex-direction: column; gap: 12px;
  padding: 16px; border-radius: 8px;
  background: var(--color-bg-surface);
}

    ⚠️ Common Constraints

    Design choiceCode realityDesigner action
    Text in imagesNot translatable, not accessibleUse live text over images
    Fixed-height cards with variable textContent overflowsDesign flexible heights or truncation rules
    Custom fonts everywhereLoad time, licensingLimit families/weights
    Pixel-perfect on one screen sizeReal screens varyDesign responsive behaviour
    Fancy scroll effectsPerformance, accessibilityCheck feasibility early
    Native controls restyled heavilySome (date pickers, selects) are hard to styleUse the system component or agree on a custom one

    🧩 Semantic HTML Basics

    • Buttons are <button>, links are <a> — not styled divs.
    • Every input has a <label>.
    • Headings in order (h1 → h2 → h3).
    • Specify which element in annotations for non-obvious cases (e.g. "this is a link, opens new page").
    • Units: px for fixed, rem for scalable text, % / fr for flexible layouts.
    Q. Why avoid putting key text inside images?
    • A File size only
    • B Not translatable, not accessible, can't reflow
    • C Figma blocks it
    • D Fonts look bad

    🔎 Design QA

    • Test the build on real devices and browsers.
    • Check against the state matrix, edge cases and responsive behaviour.
    • Log issues with screenshots, expected vs actual, and severity (blocker / major / minor / polish).
    • Prioritise with developers; retest fixes.
    • Don't chase pixel-perfection over meaningful issues.
    EXAMPLE · Design QA log entry
    IssueError message appears above the field instead of below
    Expected vs actualBelow field, 4px gap, red icon + text / Above field, no icon
    SeverityMajor (consistency + accessibility)
    DeviceAndroid 13, Chrome
    Q. What should a design QA issue include?
    • A "Looks off"
    • B Screenshot, expected vs actual, severity and device
    • C Only the severity
    • D Nothing

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    📦 Handoff Basics

    What makes a good handoff?
    Organised files marked ready for dev, complete flows and states, token-based specs, final copy, exportable assets, accessibility notes and a live walkthrough — followed by design QA.
    How do you organise a Figma file for handoff?
    Pages for exploration, ready for dev and archive; named frames by flow; a cover with status; annotations; links to tickets.
    Why reference tokens instead of raw values?
    Tokens keep design and code consistent, make theming possible and prevent one-off values.
    How early should developers be involved?
    From the start — feasibility checks during design save rework and lead to better solutions.

    📏 Specs & Assets

    What should behaviour specs cover?
    Triggers, rules, validation, loading/empty/error/success states, edge cases, timings and keyboard/accessibility behaviour.
    How do you write acceptance criteria?
    Given/When/Then statements describing testable behaviour for each state and edge case.
    How do you prepare icons for developers?
    SVG on a consistent grid, outlined strokes, optimised, named type_name_size_variant, and as Vector Drawables/PDF for native apps.
    How do you handle images for the web?
    WebP/AVIF with fallbacks, responsive sizes via srcset, size budgets and alt text.
    Why avoid text inside images?
    It can't be translated, read by screen readers, resized or reflowed.

    🧱 HTML/CSS & QA

    How does Figma auto layout map to CSS?
    Auto layout behaves like Flexbox: direction, gap, padding, alignment, hug (fit-content) and fill (flex: 1).
    Name design choices that are hard to build.
    Fixed heights with variable text, heavily restyled native controls, complex scroll effects, many custom fonts and pixel-perfect single-size layouts.
    What is design QA?
    Reviewing the built product against designs, states, edge cases and responsive rules, logging issues with evidence and severity.
    How do you handle a developer saying "this can't be built"?
    Understand the constraint, explore alternatives together, prioritise the user goal over the exact visual, and document the agreed solution.

    Practice: Hand Off a Profile Settings Screen

    Prepare a complete, real-feeling handoff package and run design QA.

    0 / 0 correct

    ⚙️ Scenario: LearnHub Profile Settings

    LearnHub is redesigning Profile Settings: avatar upload, name, email (verified), phone, language selector, notification toggles and "Delete account". Developers start next sprint on web and Android.

    1️⃣ Task 1 · Specs

    ✍️ Write behaviour specs for the avatar upload.
    Model answer: Tap avatar → choose camera/gallery (Android) or file picker (web); accepted JPG/PNG/WebP up to 5 MB; crop to square; upload with progress ring; success: new avatar + toast "Photo updated"; errors: too large ("Max 5 MB"), wrong type, network failure with Retry; fallback avatar shows initials.

    2️⃣ Task 2 · States & Edge Cases

    ✍️ List states and edge cases for the email field.
    Model answer: States: verified (badge), unverified (warning + "Resend link"), editing, validating, invalid format, already in use, saving, saved. Edge cases: very long email (truncate middle with full value on focus), verification link expired, change requires password confirmation.

    3️⃣ Task 3 · Assets & Constraints

    Q. The language selector uses a heavily customised native dropdown. Best handoff approach?
    • A Insist on pixel-perfect custom styling
    • B Agree with developers on the design-system Select component or a bottom sheet list on Android
    • C Use an image of the dropdown
    • D Skip it

    4️⃣ Task 4 · Delete Account

    ✍️ Specify the delete-account behaviour.
    Model answer: Separate "Danger zone" section; "Delete account" opens a confirmation dialog explaining consequences, requires typing DELETE or password, primary destructive button in error colour with a clear label "Delete my account"; cancel is easy; after success, sign out and show confirmation email notice. Accessibility: focus moves into dialog and returns on cancel.

    5️⃣ Task 5 · Design QA

    Q. In QA, toggles have no visible focus on web. Severity?
    • A Polish
    • B Major — accessibility issue for keyboard users
    • C None
    • D Cosmetic

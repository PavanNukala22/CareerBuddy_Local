    Module 01 · Foundations

    What is Behavioral Modeling?

    Start from zero: what interaction design is, what "behaviour" means in an interface, and the models IxDs use to describe it.

    🧭 What is Interaction Design (IxD)?

    Interaction design defines how a product behaves in response to people: what happens when you tap, type, swipe, wait or make a mistake. Visual design decides how things look; interaction design decides how they act.

    👆
    Input
    What the user does: tap, type, drag, speak.
    ⚙️
    Logic
    The rules that decide what happens next.
    🔄
    State
    The condition the interface is in right now.
    💬
    Feedback
    How the system shows what happened.

    🧠 What is Behavioral Modeling?

    Behavioral modeling is describing a product's behaviour precisely — every state it can be in, every event that can happen, and every rule that decides the response — before it is built. A good model removes guesswork for engineers and exposes missing cases early.

    🔴 Without a model

    "The button submits the form." — But what if the form is invalid? Already submitting? Offline? Session expired?

    🟢 With a model

    A diagram and table listing states (idle, validating, submitting, success, error) and the exact events and conditions that move between them.

    🗂️ Types of Behavioral Models

    ModelDescribesBest for
    State machine / statechartStates, events, transitionsComponents and flows with clear modes
    Flowchart / user flowSteps and decisions in sequenceTask paths across screens
    Decision tableCombinations of conditions → outcomesComplex rules (pricing, eligibility)
    Sequence diagramMessages between user, UI and server over timeAsync behaviour, API calls
    Conceptual / mental modelObjects, relationships and actions users think inAligning the product with user expectations
    Interaction spec / annotationsWritten behaviour rules on screensDeveloper handoff

    📖 Key Terms (What is What)

    StateA distinct condition of the UI, e.g. "Loading" or "Expanded".
    EventSomething that happens: user tap, timer ends, server responds.
    TransitionMovement from one state to another, triggered by an event.
    Guard / conditionA rule that must be true for a transition to happen.
    Action / effectWhat the system does during a transition (save, animate, show toast).
    Mental modelWhat the user believes about how the system works.
    Conceptual modelHow the designer intends the system to be understood.
    Affordance / signifierWhat actions are possible / the cue that shows it.

    Module 02 · State Machines

    State Machines

    Model interface behaviour as states, events and transitions — the most powerful tool in an IxD's kit.

    ⚙️ What is a State Machine?

    A finite state machine (FSM) is a model where the system is always in exactly one state from a fixed list, and moves between states only when specific events happen.

    Figure 2.1 · A form submit button as a state machine

    🧱 Parts of a State Machine

    PartExample (submit button)
    StatesIdle, Submitting, Success, Error
    Initial stateIdle
    EventsSUBMIT, RESOLVE, REJECT, RETRY, RESET
    TransitionsIdle —SUBMIT→ Submitting
    GuardsSUBMIT only if form is valid
    ActionsOn Submitting: disable button, show spinner, call API
    💡
    Because the button can only be in one state, "double payment" bugs disappear: there is simply no SUBMIT transition out of Submitting.

    🗂️ Types of State Machines

    TypeIdeaExample
    Simple FSMFlat list of statesToggle: On ⇄ Off
    Hierarchical (nested) statesStates inside statesPlayer › Playing › (Buffering / Streaming)
    Parallel (orthogonal) statesIndependent regions active at onceText editor: Bold on/off AND Italic on/off
    History statesRemember the last sub-stateReturn to the last tab you opened
    StatechartsFSM + nesting + parallel + history (David Harel)Complex apps; tools like XState

    📋 The State Transition Table

    Current stateEventGuardNext stateAction
    IdleSUBMITform validSubmittingShow spinner, call API
    IdleSUBMITform invalidIdleShow field errors
    SubmittingRESOLVE—SuccessShow confirmation
    SubmittingREJECT—ErrorShow message + Retry
    ErrorRETRY—SubmittingCall API again
    SubmittingSUBMIT—(ignored)—
    📌
    Fill every cell of "state × event". Empty cells are where bugs hide.

    🧠 Check Yourself

    Q. Which is a benefit of modeling a button as a state machine?
    • A Nicer colours
    • B Impossible states (e.g. loading and error at once) cannot happen
    • C Faster servers
    • D Fewer screens
    ✍️ Model a "Play/Pause" video control: list states and events.
    Model answer: States: Paused (initial), Loading, Playing, Ended, Error. Events: PLAY, PAUSE, BUFFER, READY, END, FAIL, REPLAY. Transitions: Paused —PLAY→ Loading —READY→ Playing; Playing —PAUSE→ Paused; Playing —BUFFER→ Loading; Playing —END→ Ended —REPLAY→ Loading; any —FAIL→ Error.

    Module 03 · Conditional Logic

    Conditional Logic

    Define the rules that decide what users see and what happens — clearly, completely and testably.

    🔀 What is Conditional Logic?

    Conditional logic is the set of "if this, then that" rules behind an interface: show a field only if…, enable a button when…, send a reminder unless…. Designers must specify these rules so behaviour is predictable.

    logicIF cart_total >= 499 AND delivery_city IN serviceable_cities
    THEN show "Free delivery"
ELSE IF cart_total < 499
    THEN show "Add ₹{499 - cart_total} more for free delivery"
ELSE
    show "Delivery not available in your city"

    🗂️ Types of Conditions

    TypeExample
    User attributeIF user.plan = "Pro" THEN show Export
    Input valueIF age < 18 THEN ask guardian details
    System stateIF offline THEN queue the message
    Time-basedIF after 9 pm THEN delivery starts tomorrow
    PermissionIF role = viewer THEN hide Edit
    Combined (AND / OR / NOT)IF verified AND NOT blocked THEN allow payment

    📊 Decision Tables

    When several conditions combine, a decision table lists every combination so nothing is missed.

    Logged in?Item in stock?Address saved?Result
    No——Ask to sign in (keep cart)
    YesNo—Show "Notify me" instead of Buy
    YesYesNoGo to address form
    YesYesYesGo straight to payment
    💡
    With n yes/no conditions there are 2ⁿ combinations. Collapse rows using "—" (doesn't matter) where a condition has no effect.

    Q. 3 independent yes/no conditions give how many combinations?
    • A 3

    ✍️ Write the rules for when a "Resend OTP" link is enabled.
    Model answer: IF seconds_since_last_send ≥ 30 AND resend_count < 3 THEN enable "Resend OTP"; ELSE IF resend_count ≥ 3 THEN hide link and show "Too many attempts — try again in 10 minutes" or "Call me instead"; ELSE show "Resend in {30 − seconds}s" countdown (disabled).

    Module 04 · Mental Model Alignment

    Mental Model Alignment

    Make the system behave the way users expect — and make its behaviour visible when it can't.

    🧠 What is a Mental Model?

    A mental model is a user's internal explanation of how something works, built from past experience. When the product's behaviour matches it, the product feels "intuitive". When it doesn't, users make errors and blame themselves.

    Figure 4.1 · Don Norman: users only see the system image, so it must communicate the designer's model

    🌉 Gulfs of Execution & Evaluation

    ➡️ Gulf of execution

    "How do I do what I want?" Users can't find or understand the action. Fix with clear signifiers, labels and visible options.

    ⬅️ Gulf of evaluation

    "Did it work? What state is it in?" Users can't tell the result. Fix with feedback, status and clear state changes.

    EXAMPLE · Cloud file "Save"

    Users expect files to save when they press Save (desktop mental model). A cloud app autosaves, so there is no button — users worry. Fix: show "All changes saved · 2 s ago" (closes the gulf of evaluation).

    🔧 Tools to Align Mental Models

    PrincipleMeaningExample
    AffordanceWhat actions an object allowsA slider can be dragged
    SignifierA cue that shows the affordanceDrag handle dots on a card
    MappingControls relate naturally to effectsVolume slider up = louder
    ConstraintsLimit possible actionsDate picker greys out past dates
    ConsistencySame action, same result everywhereSwipe left always = archive
    FeedbackImmediate response to actionToggle animates and updates label

    🔍 Finding Users' Mental Models

    • Interviews: "Explain to me how you think this works."
    • Card sorting: how users group concepts.
    • Usability tests: watch where expectations break ("I thought this would…").
    • Analytics: repeated undo, back-button use, rage taps.
    Q. Users can't tell whether their message was sent. Which gulf?
    • A Execution
    • B Evaluation
    • C Mapping
    • D Affordance

    Module 05 · Complex Input Flows

    Complex Input Flows

    Design multi-step, conditional and error-prone input flows that people can finish.

    📝 What is a Complex Input Flow?

    A complex input flow collects a lot of information, with dependencies between fields, validation rules, and sometimes multiple sessions: loan applications, insurance claims, tax filings, onboarding.

    🗂️ Types of Input Flow Patterns

    PatternHowUse when
    Single long formAll fields on one page, groupedFew fields; users need overview
    Wizard / stepperSteps with progress indicatorMany fields; logical stages
    ConversationalOne question at a timeMobile; simple answers
    Progressive / conditionalFields appear based on answersMany optional branches
    Inline editingEdit values in placeSettings, tables
    Save & resumeDraft saved, return laterLong or document-heavy flows

    ✅ Validation Strategies

    StrategyWhen it firesGood for
    On submitWhen user submitsShort forms
    On blur (leave field)After leaving a fieldMost fields — not too early
    Live / as you typeEvery keystrokePassword strength, character counts
    Positive inlineShows success ✓Complex formats (IFSC, PAN)
    Server-side asyncAfter API checkUsername availability, pincode lookup
    ⚠️
    Don't show "invalid" while the user is still typing the first characters — validate on blur, then re-validate live once an error is shown.

    🧷 Input Behaviour Details

    • Input masks and auto-formatting: phone 98765 43210, card numbers in groups of 4.
    • Correct keyboards: numeric for OTP and pincode, email keyboard for email.
    • Autofill and smart defaults (detect city from pincode).
    • Preserve input on error and on back navigation.
    • Dependency rules: changing "Country" resets "State" with a notice.

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    ⚙️ State Machine Questions

    What is a finite state machine and why use one in UI design?
    A model where the UI is always in exactly one state from a fixed list and moves between states only on defined events. It makes behaviour explicit, exposes missing cases and prevents impossible states such as "loading and error at the same time".
    What is the difference between a state, an event and a transition?
    A state is the current condition (Submitting). An event is something that happens (SUBMIT, RESOLVE). A transition is the move from one state to another caused by an event, optionally with a guard and an action.
    What is a guard?
    A condition that must be true for a transition to happen, e.g. SUBMIT moves Idle → Submitting only if the form is valid.
    How do statecharts differ from simple state machines?
    Statecharts add nested (hierarchical) states, parallel regions and history states, so complex components can be modelled without a state explosion.
    How would you prevent a double payment with a state model?
    Have no SUBMIT transition out of the Submitting state. The button is disabled there, so a second tap is ignored by design rather than by a patch.

    🔀 Logic & Mental Model Questions

    When would you use a decision table?
    When several conditions combine (logged in, in stock, address saved). The table lists every combination so no outcome is forgotten, and it doubles as a test plan.
    Explain the gulfs of execution and evaluation.
    Execution: users can't figure out how to do what they want — fix with signifiers and clear options. Evaluation: users can't tell what happened — fix with feedback and visible status.
    Affordance vs signifier?
    An affordance is what an object allows you to do. A signifier is the cue that tells you it is possible, like drag-handle dots or an underline on a link.
    How do you discover users' mental models?
    Interviews ("explain how you think this works"), card sorting, usability tests watching for broken expectations, and analytics signals like repeated undo or back taps.

    📝 Input Flow & Handoff Questions

    When do you show validation errors?
    Usually on blur, not on the first keystroke. Once an error is visible, re-validate live so it clears as soon as the input is fixed. Use live validation for things like password strength.
    Wizard or single long form — how do you choose?
    A single page for short forms where overview matters; a wizard for many fields with natural stages, with progress, back navigation and save-and-resume.
    How do you hand off behaviour to engineers?
    A statechart or flow, a state × event transition table, decision tables for rules, copy for every message, and Given/When/Then acceptance criteria per transition.
    Why replace isLoading / isError / isSuccess with one status value?
    Three booleans allow 8 combinations, most impossible. One status ("idle" | "loading" | "success" | "error") allows exactly the valid states.

    0 / 0 correct

    🚕 Scenario: GoRide Booking

    GoRide is a ride-hailing app. Users choose pickup and drop, see fares, request a ride, wait for a driver, ride and pay. Support tickets show: "I booked twice by mistake", "I didn't know the driver cancelled", and "The fare changed after I booked".

    1️⃣ Task 1 · States

    ✍️ List the states of a ride request from the user's point of view.
    Model answer: Idle (choosing locations) → Fare quote → Requesting → Searching for driver → Driver assigned → Driver arriving → Driver arrived → On trip → Payment pending → Completed. Exception states: No drivers found, Driver cancelled, User cancelled, Payment failed, Offline.

    2️⃣ Task 2 · Transitions

    Q. Which transition stops "I booked twice by mistake"?
    • A Requesting —REQUEST→ Requesting (creates another ride)
    • B No REQUEST transition exists from Requesting/Searching; the button becomes "Cancel request"
    • C Allow unlimited requests
    • D Hide the button randomly
    ✍️ What happens on DRIVER_CANCELLED while in "Driver arriving"?
    Model answer: Next state: Searching for driver (automatic re-match) if under 3 attempts; else "No drivers found". Actions: keep the same fare, notify via push + in-app banner "Your driver cancelled — finding you another one", haptic notification. User can cancel without fee.

    3️⃣ Task 3 · Conditional Logic

    ✍️ Write rules for showing a cancellation fee warning.
    Model answer: IF state = Driver arriving AND minutes_since_assignment > 3 AND NOT driver_late THEN show "Cancelling now costs ₹40" before confirming; ELSE IF driver_late (ETA exceeded by 5+ min) THEN cancel free with message "No fee — your driver is running late"; ELSE cancel free.

    4️⃣ Task 4 · Mental Model

    Q. "The fare changed after I booked" signals a mismatch in…
    • A Users expect a fixed price once confirmed; the system treats it as an estimate
    • B Font choice
    • C Colour contrast
    • D Card sorting

    5️⃣ Task 5 · Handoff

    ✍️ Write 2 acceptance criteria for the Searching state.
    Model answer: Given I am in Searching, when 90 seconds pass with no driver, then I see "No drivers nearby" with options "Try again" and "Schedule for later". Given I am in Searching, when I tap Cancel, then the request is cancelled with no fee and I return to Fare quote with locations kept.

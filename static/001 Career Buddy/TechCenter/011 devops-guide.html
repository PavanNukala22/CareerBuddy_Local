DevOps

The culture, practices, and tooling that unite software development and IT operations into one continuous delivery loop.

What is DevOps?

DevOps is a set of practices, cultural philosophies, and tools that combine software development (Dev) and IT operations (Ops). Its goal is to shorten the systems development life cycle and provide continuous delivery with high software quality. Instead of developers writing code and "throwing it over the wall" to a separate operations team to deploy and run, DevOps merges these two functions into a single, collaborative workflow — often carried out by one cross-functional team that owns a service from the first commit to production monitoring.

Before DevOps, most organizations worked in silos. Developers were measured on how fast they shipped features; operations teams were measured on how stable and available systems stayed. Those incentives conflicted — developers wanted to release often, operations wanted to release rarely to minimize risk. DevOps resolves that conflict by making both teams responsible for the same outcome: fast, safe, and reliable delivery of value to users.

In one sentence: DevOps is the discipline of automating and monitoring every step of software construction, from integration and testing to release and infrastructure management, so that changes reach users quickly, safely, and predictably.

Why Does DevOps Matter?

Organizations that adopt DevOps practices consistently deploy more frequently, recover from failures faster, and ship fewer defects than those that don't. The reasons come down to a handful of concrete business and engineering outcomes:

  • Speed to market. Automated pipelines let teams ship a change minutes after it's written instead of waiting for a scheduled release window weeks away.
  • Reliability. Infrastructure as Code and automated testing remove manual, error-prone steps, so environments are consistent and reproducible every time.
  • Faster recovery. Continuous monitoring and small, frequent releases mean that when something breaks, it's easy to find which change caused it and roll it back.
  • Better collaboration. Shared ownership between developers and operations removes the "it worked on my machine" blame cycle and aligns everyone around the same metrics.
  • Scalability. Automation and cloud-native tooling let a small team safely operate infrastructure that would otherwise require a much larger operations staff.

The Three Pillars

Most DevOps practices fall under three foundational pillars. Every tool discussed later in this guide — Jenkins, Docker, Terraform, Prometheus, AWS — exists to serve one or more of these pillars.

I.

Culture & Collaboration

Shared ownership, blameless post-mortems, and cross-functional teams that own a service end-to-end rather than handing it off between silos.

II.

Automation

Removing manual, repetitive work — building, testing, provisioning infrastructure, and deploying — and replacing it with code that runs the same way every time.

III.

Measurement & Feedback

Continuous monitoring, logging, and metrics that tell teams how a system is performing in the real world, so problems are caught before users notice.

The DevOps Lifecycle

DevOps is usually visualized as an infinite loop with eight stages, split between the development side and the operations side:

  • Plan — Define requirements, break work into tickets, and prioritize the backlog (tools: Jira, Linear, Azure Boards).
  • Code — Write and review application code (tools: Git, GitHub, GitLab, VS Code).
  • Build — Compile source code and dependencies into a deployable artifact, such as a binary or container image.
  • Test — Run automated unit, integration, and security tests against the build.
  • Release — Package a tested build and prepare it for deployment, often with a version tag or changelog.
  • Deploy — Push the release to a target environment (staging, then production) using an automated pipeline.
  • Operate — Keep the running system healthy: scaling, patching, and managing configuration.
  • Monitor — Collect metrics, logs, and traces to detect issues and feed learnings back into the next planning cycle.

Understanding DevOps at Every Level

DevOps is a deep field. The way you should think about it changes depending on how far into your journey you are. Use this as a self-check for where you currently stand.

BASIC

"I understand the idea"

You can explain that DevOps merges Dev and Ops, and you know that CI/CD, containers, and cloud are part of the toolchain. Example: you understand that pushing code to GitHub can automatically trigger a test run.

INTERMEDIATE

"I can build a pipeline"

You can write a working CI/CD pipeline, containerize an app with Docker, and provision basic cloud infrastructure with Terraform. Example: you set up GitHub Actions to build, test, and deploy a Node.js app to a cloud VM automatically on every merge to main.

ADVANCED

"I design the system"

You design multi-environment pipelines with rollback strategies, run Kubernetes clusters at scale, enforce IaC across teams with modules and policy-as-code, and build observability systems that predict incidents before they happen. Example: you architect a blue-green deployment on Kubernetes with automated canary analysis driven by Prometheus metrics.

A Worked Example: One Feature, Start to Finish

To make the abstract concrete, here is how a single feature — "add a dark mode toggle" — moves through a mature DevOps workflow:

  1. A developer creates a branch and writes the feature, committing small, frequent changes.
  2. On push, a CI/CD pipeline (e.g. GitHub Actions) automatically lints the code, runs unit tests, and builds a container image with Docker.
  3. The image is pushed to a container registry and deployed to a staging environment defined entirely by Infrastructure as Code (Terraform), so staging is identical to production.
  4. Automated integration tests run against staging; if they pass, the pipeline waits for a one-click approval to promote to production.
  5. The release rolls out gradually (a canary or rolling deployment) via Kubernetes, while Prometheus and Grafana watch error rates and latency in real time.
  6. If metrics stay healthy, the rollout completes. If they spike, the pipeline automatically rolls back, and the team is alerted before most users ever notice.

Every subsequent section of this guide covers one link in that chain in depth.

CI/CD Pipelines

The automated assembly line that takes a code change from a developer's laptop to a running production system, testing it at every step.

What is CI/CD?

CI/CD stands for Continuous Integration and Continuous Delivery (or Continuous Deployment). It refers to the practice of automatically building, testing, and shipping code every time a developer makes a change, instead of manually assembling a release every few weeks.

  • Continuous Integration (CI) — every time code is pushed, it is automatically merged into a shared branch, compiled, and tested. This catches integration bugs within minutes instead of weeks, when many developers' changes would otherwise collide.
  • Continuous Delivery (CD) — after CI passes, the application is automatically packaged into a release-ready artifact. A human still clicks "deploy," but the artifact is always in a deployable state.
  • Continuous Deployment (also CD) — a stricter version of delivery where every change that passes all automated tests is deployed to production automatically, with no human approval step.

Rule of thumb: if a human has to press a button to release, it's Continuous Delivery. If the pipeline releases on its own once tests pass, it's Continuous Deployment.

Anatomy of a Pipeline

Regardless of which tool runs it, almost every CI/CD pipeline is a sequence of stages, each of which must succeed before the next begins:

  1. Source — triggered by a git event: a push, a pull request, a tag, or a schedule.
  2. Build — compile the application and resolve dependencies (e.g. npm install && npm run build, or mvn package).
  3. Test — run unit tests, then integration tests, then sometimes end-to-end UI tests. Fast tests run first so failures are caught cheaply.
  4. Static analysis & security scan — lint the code, check for known-vulnerable dependencies, and scan for leaked secrets.
  5. Package — produce a versioned, immutable artifact: a container image, a JAR file, a compiled binary.
  6. Publish — push the artifact to a registry (Docker Hub, GitHub Container Registry, Artifactory, ECR).
  7. Deploy — release the artifact to an environment (dev → staging → production), usually with a strategy such as rolling, blue-green, or canary.
  8. Verify — run smoke tests or watch health metrics after deploy, and automatically roll back if something regresses.

Beginner Example: A Minimal Pipeline

Here is the simplest possible CI pipeline for a Node.js project using GitHub Actions. It runs on every push and pull request, installs dependencies, and runs the test suite:

.github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm run lint
      - run: npm test

This is "Continuous Integration" only — it verifies the code is healthy, but doesn't deploy anything yet.

Intermediate Example: Build, Test, and Deploy

Extending the pipeline above to build a Docker image and deploy it to a server on every merge to main turns it into full CI/CD:

.github/workflows/deploy.yml
name: Build and Deploy

on:
  push:
    branches: [main]

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Log in to registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push image
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to server via SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: deploy
          key: ${{ secrets.SSH_KEY }}
          script: |
            docker pull ghcr.io/${{ github.repository }}:${{ github.sha }}
            docker stop app || true
            docker run -d --rm --name app -p 80:3000 \
              ghcr.io/${{ github.repository }}:${{ github.sha }}

Advanced Example: Multi-Environment Pipeline with Approvals

At an advanced level, pipelines fan out to multiple environments, require manual approval gates for production, and run canary verification before completing the rollout. A conceptual outline:

Source (PR merged to main)
   │
   ▼
Build & Unit Test  ──fail──▶  Notify Slack, block merge
   │ pass
   ▼
Security Scan (SAST + dependency check)
   │ pass
   ▼

   │

   │
   ▼

   │ pass
   ▼

   │

This pattern — often implemented with tools like Argo Rollouts or Spinnaker on top of Kubernetes — is what most large engineering organizations run in production.

CI/CD Tools, Explained

There isn't one "correct" CI/CD tool — the right choice depends on where your code lives, what you're deploying to, and how much control you need over the underlying infrastructure. Here are the tools you'll encounter most often:

Jenkins

SELF-HOSTED

The original open-source automation server, first released in 2011. Jenkins runs on your own infrastructure and is configured with a Jenkinsfile written in Groovy-based pipeline syntax. It has the largest plugin ecosystem of any CI tool (2,000+ plugins), which makes it extremely flexible but also more work to maintain.

  • Best for: organizations that need full control and already run their own servers
  • Config file: Jenkinsfile
  • Example trigger: pipeline { agent any; stages { stage('Build'){ steps { sh 'make build' } } } }

GitHub Actions

SAAS / HOSTED

GitHub's built-in CI/CD, configured with YAML files living in .github/workflows/. Because it's native to GitHub, it requires zero setup for repos already hosted there and has a huge marketplace of reusable "actions."

  • Best for: teams already using GitHub who want the fastest path to a working pipeline
  • Config file: .github/workflows/*.yml
  • Runs on: GitHub-hosted runners or your own self-hosted runners

GitLab CI/CD

SAAS OR SELF-HOSTED

Deeply integrated into GitLab, configured via a single .gitlab-ci.yml file. GitLab positions itself as a full DevOps platform — source control, CI/CD, container registry, and even basic Kubernetes management in one product.

  • Best for: teams that want an all-in-one platform rather than stitching tools together
  • Config file: .gitlab-ci.yml

CircleCI

SAAS

A cloud-native CI/CD platform known for fast build times through aggressive caching and parallelism. Popular with startups that want speed without managing servers.

  • Best for: teams that want managed infrastructure and fast, parallelized test runs
  • Config file: .circleci/config.yml

Azure DevOps / Pipelines

SAAS / HOSTED

Microsoft's DevOps suite, bundling Boards (planning), Repos (git hosting), Pipelines (CI/CD), Artifacts, and Test Plans. Common in enterprises already invested in the Microsoft ecosystem.

  • Best for: enterprises using Azure, .NET, or Microsoft's broader tooling
  • Config file: azure-pipelines.yml

Argo CD

GITOPS / KUBERNETES

A GitOps continuous delivery tool for Kubernetes. Instead of a pipeline pushing changes to a cluster, Argo CD continuously watches a git repo and pulls changes into the cluster to match it — the cluster's state is always a mirror of git.

  • Best for: teams running Kubernetes who want declarative, auditable deployments
  • Core idea: git is the single source of truth for what's running

Containers & Orchestration

Packaging an application with everything it needs to run, then automating how thousands of those packages are scheduled, scaled, and kept alive.

What is a Container?

A container is a lightweight, standalone package that bundles an application's code together with all of its dependencies — libraries, system tools, runtime — so it runs identically no matter where it's deployed. Containers solve the classic "it works on my machine" problem: if the container runs on your laptop, it will run exactly the same way in staging and production, because it's the same filesystem and dependencies every time.

Containers are often confused with virtual machines, but they work very differently:

Virtual MachineContainer
What it virtualizesAn entire physical machine, including the OS kernelOnly the application layer — containers share the host's OS kernel
Startup timeMinutes (booting a full OS)Seconds (or less)
SizeGigabytesMegabytes
Density per hostTens of VMsHundreds of containers
IsolationStrong (separate kernel)Process-level (namespaces + cgroups)

Beginner Example: Your First Dockerfile

A Dockerfile is a plain-text recipe describing how to build a container image. Here's one for a simple Node.js app:

Dockerfile
FROM node:20-alpine

WORKDIR /app
COPY package*.json ./
RUN npm ci --production

COPY . .

EXPOSE 3000
CMD ["node", "server.js"]

Building and running it:

docker build -t my-app:1.0 .
docker run -p 3000:3000 my-app:1.0

That's it — my-app:1.0 is now a portable, immutable image that runs the same way on any machine with Docker installed.

Intermediate Example: Multi-Container Apps with Compose

Real applications rarely consist of a single container — you usually need a web server, a database, and maybe a cache running together. Docker Compose lets you define and run multi-container applications from one file:

docker-compose.yml
version: "3.9"
services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      - DATABASE_URL=postgres://user:pass@db:5432/app
    depends_on:
      - db
      - cache

  db:
    image: postgres:16
    environment:
      - POSTGRES_PASSWORD=pass
    volumes:
      - db-data:/var/lib/postgresql/data

  cache:
    image: redis:7-alpine

volumes:
  db-data:

Running docker compose up starts all three services, networks them together automatically, and lets web reach the database simply by hostname (db).

Advanced Example: Orchestration with Kubernetes

Docker Compose works well on a single machine, but production systems need to run across many machines, self-heal when a container crashes, and scale automatically under load. That's the job of an orchestrator — and the dominant one is Kubernetes (often abbreviated "K8s").

Kubernetes takes a declarative approach: you describe the desired state ("I want 3 replicas of this app always running") and Kubernetes continuously works to make reality match that description — restarting crashed containers, rescheduling them onto healthy machines, and scaling them up or down.

deployment.yml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: my-app
          image: ghcr.io/org/my-app:1.0
          ports:
            - containerPort: 3000
          resources:
            requests: { cpu: "100m", memory: "128Mi" }
            limits: { cpu: "500m", memory: "256Mi" }
          readinessProbe:
            httpGet: { path: /healthz, port: 3000 }
            initialDelaySeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 3000
  type: LoadBalancer

This one file tells Kubernetes: always keep 3 healthy copies of my-app running, only send traffic to a copy once it responds successfully to /healthz, and expose the whole group behind a single load-balanced address. If a node dies, Kubernetes reschedules the lost containers elsewhere automatically.

Container & Orchestration Tools, Explained

Docker

CONTAINER RUNTIME

The tool that made containers mainstream. Docker provides the CLI, the daemon that runs containers, the Dockerfile build format, and Docker Hub, the most widely used public image registry.

  • Best for: local development and building images — the industry default
  • Key commands: docker build, docker run, docker compose up

Podman

DAEMONLESS RUNTIME

A drop-in alternative to Docker with an (almost) identical CLI, built by Red Hat. Its key difference: Podman is daemonless — there's no always-on background service running as root, which improves security. It can also run containers as a normal, non-root user by default.

  • Best for: security-conscious teams, especially in regulated or enterprise Linux environments
  • Key detail: alias docker=podman works for most day-to-day commands

containerd

LOW-LEVEL RUNTIME

The core container runtime that actually pulls images and runs containers under the hood — both Docker and Kubernetes use containerd internally. Most developers never interact with it directly, but it's worth knowing it's there.

  • Best for: understanding what's actually running your containers under Docker/K8s

Kubernetes (K8s)

ORCHESTRATOR

The industry-standard orchestrator, originally designed at Google. It schedules containers across a cluster of machines, restarts failed ones, load-balances traffic, and scales workloads automatically based on demand.

  • Best for: production workloads at any meaningful scale
  • Core objects: Pod, Deployment, Service, Ingress, ConfigMap, Secret

Docker Swarm

ORCHESTRATOR

Docker's own, much simpler built-in orchestrator. It has a fraction of Kubernetes' complexity — and a fraction of its features. Good for small teams that need basic multi-node scheduling without a steep learning curve.

  • Best for: small deployments where Kubernetes would be overkill

Helm

K8S PACKAGE MANAGER

The "npm for Kubernetes." Helm packages a set of Kubernetes YAML manifests into a reusable, templated bundle called a chart, so you can install a complex application (e.g. a full Prometheus + Grafana monitoring stack) with one command.

  • Best for: installing and templating complex Kubernetes applications
  • Key command: helm install my-release ./chart

Infrastructure as Code

Defining servers, networks, and databases in version-controlled text files instead of clicking through a cloud console — so infrastructure can be reviewed, tested, and reproduced like any other code.

What is Infrastructure as Code?

Infrastructure as Code (IaC) is the practice of managing and provisioning infrastructure — servers, load balancers, databases, networking, DNS, permissions — through machine-readable configuration files, rather than manual processes in a web console. The configuration lives in git alongside application code, which means every infrastructure change goes through the same review, versioning, and audit trail as a code change.

Before IaC, infrastructure was usually provisioned by hand: an engineer would log into a cloud console, click "Create instance," fill in a form, and hope they remembered the exact settings next time they needed to do it again. This is slow, inconsistent, and impossible to audit. IaC replaces that with a file like this:

conceptual example
resource "server" "web" {
  size   = "small"
  region = "us-east-1"
  count  = 3
}

Run that file through a tool, and it creates exactly 3 small servers in us-east-1 — every time, on any machine, with no room for human error.

Declarative vs. Imperative IaC

  • Declarative — you describe the end state you want ("I want 3 servers"), and the tool figures out how to get there, including what to create, change, or destroy. Terraform and CloudFormation work this way.
  • Imperative — you describe the exact steps to take ("create this server, then install this package, then start this service"). Ansible and shell scripts work this way.

Most real-world DevOps setups use both: declarative tools to provision the infrastructure (the servers, networks, databases) and imperative tools to configure what runs on top of it (installing software, managing config files).

Beginner Example: Provisioning a Server with Terraform

Terraform is the most widely used IaC tool. It uses a declarative language called HCL (HashiCorp Configuration Language). This example provisions a single AWS virtual machine:

main.tf
terraform {
  required_providers {
    aws = { source = "hashicorp/aws" }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"

  tags = {
    Name = "web-server"
  }
}

Applying it:

terraform init      # download the AWS provider plugin
terraform plan       # preview what will be created/changed
terraform apply       # actually create the resources

Terraform keeps a state file that records exactly what it created, so next time you run terraform apply, it only changes what's different — it won't recreate a server that already exists.

Intermediate Example: Reusable Modules

As infrastructure grows, teams package common patterns into reusable modules, so a "standard web app environment" can be created with a few lines instead of hundreds:

main.tf
module "web_app" {
  source        = "./modules/web-app"
  environment   = "production"
  instance_count = 3
  instance_type = "t3.medium"
  vpc_id        = module.network.vpc_id
  subnet_ids    = module.network.private_subnet_ids
}

module "network" {
  source     = "./modules/vpc"
  cidr_block = "10.0.0.0/16"
}

This same module can be reused to spin up an identical, isolated staging environment just by changing the environment variable — a huge advantage over manually clicking through a console.

Advanced Example: Provisioning + Configuration Together

In a mature setup, Terraform provisions the raw infrastructure, and a configuration tool like Ansible installs and configures the software on top of it. A conceptual flow:

# 1. Terraform provisions 3 servers and outputs their IPs
terraform apply -auto-approve
terraform output -json instance_ips > ips.json

# 2. Ansible uses that inventory to configure each server
ansible-playbook -i ips.json deploy-app.yml
deploy-app.yml (Ansible playbook)
- hosts: web
  become: true
  tasks:
    - name: Install dependencies
      apt:
        name: [nginx, nodejs, npm]
        state: present

    - name: Copy application code
      copy:
        src: ./dist/
        dest: /var/www/app/

    - name: Start the app service
      systemd:
        name: my-app
        state: started
        enabled: true

At an even more advanced level, teams enforce policy-as-code (e.g. with OPA/Sentinel) so a Terraform plan is automatically rejected in CI if it would, for example, create a publicly accessible database — catching security misconfigurations before they ever reach production.

Infrastructure as Code Tools, Explained

Terraform

DECLARATIVE / MULTI-CLOUD

Built by HashiCorp, Terraform is the most widely adopted IaC tool because it's cloud-agnostic — the same tool and workflow can provision AWS, Azure, GCP, and even non-cloud resources like DNS records or GitHub repos, through a huge ecosystem of "providers."

  • Language: HCL
  • Best for: multi-cloud or cloud-agnostic infrastructure

AWS CloudFormation

DECLARATIVE / AWS-ONLY

AWS's own native IaC service. It's tightly integrated with every AWS service on day one (Terraform sometimes lags behind on brand-new AWS features) but only works for AWS — there's no multi-cloud story.

  • Language: JSON or YAML templates
  • Best for: AWS-only shops that want first-party support

Pulumi

DECLARATIVE / MULTI-CLOUD

Similar in purpose to Terraform, but instead of a domain-specific language, you write infrastructure using real programming languages — Python, TypeScript, Go, or C# — which lets you use loops, functions, and existing testing frameworks.

  • Language: Python / TypeScript / Go / C#
  • Best for: teams that want infrastructure defined in a language they already know

Ansible

IMPERATIVE / AGENTLESS

A configuration management tool that installs software and manages configuration on existing servers over SSH — no agent needs to be pre-installed. Often paired with Terraform: Terraform builds the server, Ansible configures what runs on it.

  • Language: YAML "playbooks"
  • Best for: configuring software on servers after they exist

Chef & Puppet

IMPERATIVE / AGENT-BASED

Older but still widely used configuration management tools that run an agent on each managed server, which periodically pulls and applies configuration. More heavyweight than Ansible, but battle-tested in large, long-running enterprise environments.

  • Language: Ruby DSL
  • Best for: large, established enterprises with existing Chef/Puppet infrastructure

AWS CDK

DECLARATIVE / AWS-ONLY

The "Cloud Development Kit" lets you define AWS infrastructure using real code (TypeScript, Python, Java) that compiles down to a CloudFormation template — combining CloudFormation's native AWS support with Pulumi-like developer ergonomics.

  • Language: TypeScript / Python / Java / C#
  • Best for: AWS-only teams who want to write infra in a real programming language

Monitoring & Observability

Knowing what your system is doing right now, why it broke five minutes ago, and getting a page before your users notice something is wrong.

Monitoring vs. Observability

These terms are often used interchangeably, but they mean slightly different things:

  • Monitoring is watching a predefined set of metrics and alerting when they cross a threshold — "alert me if CPU usage exceeds 90%." It answers questions you already know to ask.
  • Observability is the broader ability to ask new questions about a system's internal state just from its external outputs, without having to ship new code to answer them — "why did requests from mobile users in Europe get slow between 2:03 and 2:11 PM yesterday?" It's what lets you debug problems you didn't anticipate.

Observability is built on three types of telemetry data, often called the three pillars:

1

Metrics

Numeric measurements over time — CPU usage, request rate, error rate, latency percentiles. Cheap to store and great for dashboards and alerting.

2

Logs

Timestamped, discrete events — "user 4821 failed login at 14:03:02." Best for understanding exactly what happened during a specific incident.

3

Traces

The full path of a single request as it moves through multiple services, showing exactly where time was spent. Essential for debugging microservices.

Beginner Example: Scraping a Metric with Prometheus

Prometheus is the de facto standard for metrics collection. It works by "scraping" (periodically pulling) metrics from an HTTP endpoint that your application exposes. Most web frameworks have a library that exposes a /metrics endpoint automatically:

/metrics endpoint output (exposed by your app)
# HELP http_requests_total Total number of HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 15234
http_requests_total{method="GET",status="500"} 12

# HELP http_request_duration_seconds Request latency
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.1"} 14200
http_request_duration_seconds_bucket{le="0.5"} 15100
http_request_duration_seconds_bucket{le="1.0"} 15220

Telling Prometheus to scrape it:

prometheus.yml
scrape_configs:
  - job_name: 'my-app'
    scrape_interval: 15s
    static_configs:
      - targets: ['my-app:3000']

Intermediate Example: Visualizing with Grafana

Grafana connects to Prometheus (and many other data sources) and turns raw metrics into dashboards. A query written in Prometheus's query language, PromQL, powers each panel:

PromQL — error rate over the last 5 minutes
sum(rate(http_requests_total{status="500"}[5m]))
  /
sum(rate(http_requests_total[5m]))

This single query computes the percentage of requests returning a server error, refreshed continuously — the kind of number that typically drives an on-call alert. A typical alerting rule built on top of it:

alert-rules.yml
groups:
  - name: app-alerts
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(http_requests_total{status="500"}[5m]))
          / sum(rate(http_requests_total[5m])) > 0.05
        for: 2m
        labels:
          severity: page
        annotations:
          summary: "Error rate above 5% for 2+ minutes"

Advanced Example: Centralized Logging & Distributed Tracing

At scale, logs and traces from dozens of microservices need to be centralized so they can be searched and correlated together. A common architecture:

[ App 1 ] ─┐
[ App 2 ] ─┼─ logs ──▶ Fluent Bit / Logstash ──▶ Elasticsearch ──▶ Kibana
[ App 3 ] ─┘

[ App 1 ] ─┐
[ App 2 ] ─┼─ traces ──▶ OpenTelemetry Collector ──▶ Jaeger / Tempo
[ App 3 ] ─┘

[ App 1 ] ─┐
[ App 2 ] ─┼─ metrics ──▶ Prometheus ──▶ Grafana (dashboards + alerts)
[ App 3 ] ─┘

With OpenTelemetry instrumentation in each service, a single request that touches five microservices produces one connected trace, letting an engineer see in one screen that a checkout request was slow specifically because the "inventory-service" took 800ms to respond — instead of manually cross-referencing five separate log files.

Monitoring & Observability Tools, Explained

Prometheus

METRICS

An open-source metrics collection and time-series database, originally built at SoundCloud, now the de facto standard for metrics in the Kubernetes ecosystem. It pulls ("scrapes") metrics rather than having apps push them.

  • Best for: real-time metrics and alerting, especially in Kubernetes

Grafana

VISUALIZATION

The most widely used dashboarding tool in DevOps. It doesn't store data itself — it connects to Prometheus, Elasticsearch, Loki, and dozens of other sources to build a single pane of glass across all your telemetry.

  • Best for: dashboards that combine multiple data sources in one view

ELK / EFK Stack

LOGGING

Elasticsearch (search & storage), Logstash or Fluentd/Fluent Bit (log shipping & parsing), and Kibana (visualization) — a self-hosted stack for centralizing and searching logs from every service in one place.

  • Best for: full-text log search across a large fleet of services

Grafana Loki

LOGGING

A log aggregation system designed to be much cheaper to run than Elasticsearch by only indexing metadata (labels) rather than the full text of every log line, and pairing natively with Grafana for visualization.

  • Best for: teams already using Grafana who want lower-cost log storage

Jaeger / Grafana Tempo

TRACING

Distributed tracing backends that store and visualize traces collected via OpenTelemetry, letting you follow a single request across every microservice it touched and see exactly where time was spent.

  • Best for: debugging latency in microservice architectures

Datadog

SAAS / ALL-IN-ONE

A commercial, fully managed observability platform combining metrics, logs, traces, uptime checks, and security monitoring in one product with minimal setup — trading self-hosting effort for a subscription cost.

  • Best for: teams that want a single managed platform with no infrastructure to run

New Relic

SAAS / APM

A managed Application Performance Monitoring (APM) platform, historically strong at code-level performance insight — pinpointing exactly which function or database query inside your application is slow.

  • Best for: deep, code-level performance diagnostics

PagerDuty / Opsgenie

INCIDENT RESPONSE

Not telemetry tools themselves — they receive alerts from Prometheus, Datadog, etc., and handle routing them to the right on-call engineer by phone, SMS, or push notification, with escalation policies if nobody responds.

  • Best for: making sure alerts actually reach a human who can act on them

How to Use This Page

What matters is recognizing the category a service belongs to (compute, storage, database, networking...) and knowing one or two default choices per category. Amazon Web Services — Services in Detail

AWS has the broadest catalog of any provider (200+ services). Below are the 33 you'll run into constantly, grouped into the same categories used throughout this guide.

Compute

Where AWS application code and containers actually run.

EC2

COMPUTE

EC2 (Elastic Compute Cloud) is AWS's core virtual machine service — resizable compute instances you fully control, choosing the OS, installing your own packages, and managing patching yourself.

  • Example: Hosting a Node.js API on a t3.medium instance, SSHing in to install dependencies and configure a process manager directly.

Lambda

COMPUTE

A serverless compute service that runs a single function in response to an event — an HTTP request, a file upload, a schedule — and bills only for the milliseconds it actually executes. There's no server to provision or patch.

  • Example: A Lambda triggered by an S3 upload event that automatically resizes a newly uploaded image before it's served to users.

Elastic Beanstalk

COMPUTE

A Platform-as-a-Service layer over EC2, Auto Scaling, and Elastic Load Balancing — you upload your application code and Beanstalk provisions and wires up the underlying infrastructure for you.

  • Example: Deploying a Flask app by zipping the code and running eb deploy, without touching an EC2 instance or a load balancer directly.

ECS

COMPUTE

Elastic Container Service — AWS's own container orchestrator. It runs Docker containers on a cluster of EC2 instances or on Fargate, and is generally simpler to operate than Kubernetes for teams that don't need Kubernetes' full flexibility.

  • Example: Running a fleet of Dockerized microservices in production without standing up or managing a Kubernetes control plane.

EKS

COMPUTE

Elastic Kubernetes Service — a managed Kubernetes control plane. AWS runs the control plane; you bring (or let AWS manage) the worker nodes and deploy with standard kubectl/Helm tooling.

  • Example: A team that already uses Helm charts on-prem moves the same workloads into AWS, keeping identical tooling and manifests.

Auto Scaling

COMPUTE

EC2 Auto Scaling automatically adds or removes EC2 instances in a group based on demand, defined by a launch template and scaling policies tied to metrics like CPU.

  • Example: A group scales from 2 to 10 instances during a flash sale once average CPU crosses 70%, then scales back down overnight to save cost.

Storage

Where files, backups, and static assets live.

S3

STORAGE

Simple Storage Service — durable, virtually unlimited object storage organized into buckets. It's the default place to put files that aren't a database record.

  • Example: Storing user-uploaded profile photos and a compiled React frontend bundle, served directly or through a CDN.

EBS

STORAGE

Elastic Block Store — persistent block storage volumes that attach to a single EC2 instance, behaving like a virtual hard drive that survives instance stop/start.

  • Example: The root volume of an EC2 instance running a database, with automated nightly snapshots for backup.

EFS

STORAGE

Elastic File System — a managed NFS file system that multiple EC2 instances can mount and share simultaneously, unlike EBS which attaches to only one instance at a time.

  • Example: A shared uploads directory mounted by six web servers behind a load balancer, so any server can read a file any other server wrote.

S3 Glacier

STORAGE

A low-cost archival storage class for data that's rarely accessed, trading retrieval speed (minutes to hours) for a much lower storage price than standard S3.

  • Example: Archiving seven years of compliance logs that must be retained but are almost never read.

Databases

Where structured and unstructured application data lives.

RDS

DATABASE

A managed relational database service supporting Postgres, MySQL, MariaDB, SQL Server, and Oracle — AWS handles patching, automated backups, and failover.

  • Example: The primary transactional database behind a web app, running as a Multi-AZ Postgres instance for automatic failover.

DynamoDB

DATABASE

A fully managed NoSQL key-value and document database delivering single-digit-millisecond latency at virtually any scale, with no servers to manage.

  • Example: Storing shopping-cart or session data keyed by user ID, where access patterns are simple, predictable lookups rather than complex joins.

Aurora

DATABASE

AWS's own MySQL- and Postgres-compatible relational engine, built on distributed storage that makes it faster and more horizontally scalable than stock RDS.

  • Example: A high-traffic e-commerce database that needs to add read replicas quickly as read traffic grows during peak shopping seasons.

ElastiCache

DATABASE

A managed in-memory data store (Redis or Memcached) used to cache frequently accessed data and take load off the primary database.

  • Example: Caching the results of an expensive product-search query so repeat requests for the same search skip the database entirely.

Redshift

DATABASE

A managed, columnar data warehouse built for large-scale analytical SQL queries across billions of rows, rather than fast transactional reads/writes.

  • Example: Running nightly batch queries across years of clickstream data to populate a business-intelligence dashboard.

Networking

How traffic gets routed to, from, and between AWS resources.

VPC

NETWORKING

Virtual Private Cloud — an isolated network you define, with your own IP range, subnets, route tables, and gateways controlling what can reach what.

  • Example: A VPC with public subnets for load balancers and private subnets for app servers and databases that aren't directly reachable from the internet.

Elastic Load Balancing

NETWORKING

A family of load balancers (Application, Network, and Gateway) that distribute incoming traffic across multiple targets and continuously health-check each one.

  • Example: An Application Load Balancer routes /api/* to one target group and /admin/* to another, and stops sending traffic to any instance that fails its health check.

CloudFront

NETWORKING

AWS's content delivery network — caches content at edge locations around the world so users load it from a nearby location instead of the origin server.

  • Example: Caching a static frontend bundle so a user in Tokyo loads it from a nearby edge node instead of a server in Virginia.

Route 53

NETWORKING

A managed DNS service that also supports health checks and routing policies like failover, weighted, and latency-based routing.

  • Example: Automatically routing traffic to a backup region if the primary region's health check starts failing.

API Gateway

NETWORKING

A fully managed service for creating, publishing, and securing REST, HTTP, and WebSocket APIs, commonly placed in front of Lambda functions.

  • Example: Exposing a set of Lambda functions as a versioned REST API with built-in request throttling and API-key authentication, with no server to manage.

Identity, Security & Secrets

Who's allowed to do what, and where credentials are safely stored.

IAM

SECURITY

Identity and Access Management — controls exactly who (or what service) can perform which actions on which AWS resources, via users, roles, and fine-grained policies.

  • Example: Granting an EC2 instance a role that lets it read from one specific S3 bucket and nothing else, rather than giving it broad account access.

KMS

SECURITY

Key Management Service — creates and manages the encryption keys used to encrypt data at rest across AWS services, with tightly controlled access to who can decrypt.

  • Example: Encrypting an RDS database and an S3 bucket with a customer-managed KMS key, so only explicitly authorized IAM roles can ever decrypt the data.

Secrets Manager

SECURITY

Securely stores credentials, API keys, and other secrets, and can automatically rotate them on a schedule without app downtime.

  • Example: Storing a database password and rotating it every 30 days automatically, while the app simply fetches the current secret at runtime.

WAF

SECURITY

Web Application Firewall — sits in front of CloudFront, an ALB, or API Gateway and blocks requests matching malicious patterns like SQL injection or known bot signatures.

  • Example: A managed rule that blocks requests containing SQL-injection patterns before they ever reach the application.

Monitoring & Management

Seeing what's happening across an AWS account and acting on it.

CloudWatch

MONITORING

Collects metrics, logs, and alarms from across AWS resources, and can trigger automated actions like scaling or paging an on-call engineer.

  • Example: An alarm that pages on-call when average CPU exceeds 85% for five minutes straight, or that automatically triggers an Auto Scaling event.

CloudTrail

MONITORING

Records every API call made within an AWS account — who made it, when, and from where — providing a complete audit trail for security and compliance.

  • Example: Investigating who deleted a production S3 bucket by searching CloudTrail for the corresponding DeleteBucket event.

Systems Manager

MONITORING

An operational hub for fleets of instances: patch management, running commands without SSH access, and centralized configuration storage in Parameter Store.

  • Example: Running a patch job across 200 EC2 instances at 2am without ever opening inbound SSH access to any of them.

CI/CD & Developer Tools

AWS-native pipeline, build, and provisioning tooling.

CodePipeline

DEVTOOLS

AWS's managed CI/CD orchestration service — chains together source, build, test, and deploy stages into a single automated release process.

  • Example: A pipeline that pulls from a GitHub repo, triggers a CodeBuild test run, then deploys to ECS automatically once tests pass.

CodeBuild

DEVTOOLS

A fully managed build service that compiles code, runs tests, and produces deployable artifacts in an isolated, ephemeral container per build.

  • Example: Running a test suite and a docker build in a clean container on every pull request, with no shared build server to maintain.

CloudFormation

DEVTOOLS

AWS's native Infrastructure-as-Code service — defines resources in a YAML or JSON template that's provisioned and torn down as a single unit called a stack.

  • Example: A template that creates a VPC, an RDS instance, and a load balancer together, so deleting the stack cleanly removes all three at once.

Messaging & Event-Driven Architecture

How independent AWS services talk to each other asynchronously.

SQS

MESSAGING

Simple Queue Service — a fully managed message queue used to decouple services so one component's slowness doesn't block another's response time.

  • Example: An order-placed message dropped onto a queue, picked up independently by a worker that handles payment processing, so a slow payment gateway never blocks the checkout API's response.

SNS

MESSAGING

Simple Notification Service — pub/sub messaging that fans a single published message out to many subscribers at once (email, SMS, Lambda, SQS queues).

  • Example: A single "new signup" event that simultaneously triggers a welcome email, a Slack notification, and an analytics pipeline event.

EventBridge

MESSAGING

A serverless event bus that routes events between AWS services, custom applications, and SaaS partners based on rules you define, without any polling.

  • Example: Automatically triggering a Lambda function whenever a new file lands in a specific S3 prefix, with zero polling infrastructure required.

Cloud & Comparisons

The three major cloud platforms — and a working map of the 25+ services that show up over and over again in a DevOps career, however you name them.

The Big Three

Almost every DevOps job touches one of three major public clouds. They compete on the same categories of service — compute, storage, databases, networking — but under different names and with different strengths.

  • AWS (Amazon Web Services) — launched in 2006, the oldest and largest provider by market share. Known for having the broadest service catalog (200+ services) and the deepest maturity in most categories.
  • Microsoft Azure — strongest where an organization already runs on Microsoft technology (Windows Server, Active Directory, .NET, Office 365). Very common in large enterprises.
  • Google Cloud Platform (GCP) — leverages Google's own infrastructure and is generally considered the strongest for data analytics, machine learning, and Kubernetes (Google created Kubernetes and GCP's managed offering, GKE, is widely regarded as the most polished).

None of them is objectively "best." The right choice depends on existing investments (a .NET shop leans Azure), team expertise, specific service maturity, and — very often — which one your employer or client has already picked.

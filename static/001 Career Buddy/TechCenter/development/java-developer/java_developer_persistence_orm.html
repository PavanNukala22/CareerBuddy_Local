    Module 01 · Foundations

    Persistence & ORM Foundations

    Start from zero: what persistence and ORM are, the types of tools in the Java stack and the key vocabulary.

    🗄️ What is Persistence?

    Persistence means keeping data alive after the program stops. Java objects live in memory (heap) and vanish on shutdown; a database stores them on disk. A persistence layer is the part of your application that saves and loads objects.

    💾
    Save
    Write objects as rows (INSERT/UPDATE).
    🔍
    Load
    Read rows back as objects (SELECT).
    🔁
    Transact
    Group changes so they all succeed or all fail.
    🧱
    Map
    Translate between objects and tables.
    💡
    Rule of thumb: JDBC = you write SQL and map results by hand. ORM (JPA/Hibernate) = you work with objects and the framework writes SQL for you.

    ⚖️ What is ORM? The Impedance Mismatch

    ORM (Object-Relational Mapping) automatically maps Java classes to tables, fields to columns and object references to foreign keys. It exists because objects and tables model data differently:

    ConceptObject worldRelational world
    Identity== / equals()Primary key
    RelationshipsObject references, collectionsForeign keys, join tables
    InheritanceClass hierarchiesNo native support (needs a strategy)
    TypesRich types, enums, nested objectsFixed column types
    Navigationorder.getCustomer()JOIN queries

    🧩 Types — The Java Persistence Stack

    LayerWhat it isLevel of abstraction
    JDBCLow-level API in java.sql; send SQL, read ResultSetLowest
    SQL mappersMyBatis, jOOQ, Spring JdbcTemplate — you keep the SQL, they reduce boilerplateLow–mid
    JPAJakarta Persistence — a specification (annotations + EntityManager API). Not runnable by itselfHigh
    HibernateThe most popular JPA implementation (also has native features)High
    Spring Data JPAGenerates repositories on top of JPA/HibernateHighest

    Databases covered in this module

    📖 Key Terms (What is What)

    EntityA Java class mapped to a table (@Entity).
    Persistence contextThe first-level cache/“workspace” of managed entities inside one EntityManager.
    DialectHibernate’s adapter for a specific database’s SQL flavour.
    TransactionA unit of work with ACID guarantees.
    Connection poolA reusable set of open DB connections (e.g. HikariCP).
    DTOPlain object used to carry data, not managed by the ORM.
    Lazy / EagerLoad related data on demand / immediately.
    N+1 problem1 query for a list + N extra queries for each item’s relation.

    Module 02 · JDBC

    JDBC — Java Database Connectivity

    Talk to the database directly: connections, SQL, transactions, batching and pooling.

    🔌 What is JDBC?

    JDBC (Java Database Connectivity) is the standard Java API for talking to relational databases. You add a vendor driver (a JAR) and write the same code for any database; only the URL and driver change.

    Core typeRole
    DriverManager / DataSourceObtains a Connection
    ConnectionSession with the database; controls transactions
    Statement / PreparedStatementSends SQL; the prepared version takes parameters safely
    CallableStatementCalls stored procedures/functions
    ResultSetCursor over returned rows

    Driver types

    Type 1 (JDBC-ODBC bridge, removed), Type 2 (native API), Type 3 (middleware), Type 4 (pure Java, direct to DB — what you use today).

    ▶️ Your First Query

    javaString url  = "jdbc:postgresql://localhost:5432/shop";   // Oracle: jdbc:oracle:thin:@//host:1521/ORCLPDB1
String sql  = "SELECT id, name, price FROM product WHERE price > ?";

try (Connection con = DriverManager.getConnection(url, "app", "secret");
     PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setBigDecimal(1, new BigDecimal("100"));
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            System.out.println(rs.getLong("id") + " " + rs.getString("name"));
        }
    }
}  // try-with-resources closes everything, even on exceptions
    ⚠️
    Never build SQL by concatenating user input ("... WHERE name='" + input + "'"). That is SQL injection. Always use PreparedStatement placeholders.

    🔄 Transactions, Batching & Pooling

    javacon.setAutoCommit(false);                 // start a manual transaction
try {
    debit.executeUpdate();
    credit.executeUpdate();
    con.commit();                         // both succeed
} catch (SQLException e) {
    con.rollback();                       // or neither does
    throw e;
}

// Batch: one network round-trip for many rows
for (Product p : products) { ps.setString(1, p.name()); ps.addBatch(); }
ps.executeBatch();

    Connection pooling: opening a connection is expensive (network + auth). A pool such as HikariCP keeps connections open and lends them out.

    javaHikariConfig cfg = new HikariConfig();
cfg.setJdbcUrl(url); cfg.setUsername("app"); cfg.setPassword("secret");
cfg.setMaximumPoolSize(10);               // start small; size by DB cores, not by user count
DataSource ds = new HikariDataSource(cfg);
    💡
    Close a pooled connection with close() — it returns to the pool, it is not really closed. Leaked connections are a classic production outage.

    🎓 Expert Notes & Check

    • Fetch size: ps.setFetchSize(500) streams large results; PostgreSQL needs autocommit off for cursor-based fetching.
    • Generated keys: prepareStatement(sql, Statement.RETURN_GENERATED_KEYS); on Oracle name the column: new String[]{"ID"}.
    • Batch rewriting: PostgreSQL reWriteBatchedInserts=true speeds up batch inserts.
    • Timeouts: set setQueryTimeout and pool connection timeouts to avoid hangs.
    Q. Why use PreparedStatement?

    Module 03 · JPA & Hibernate

    JPA & Hibernate

    Map objects to tables, manage lifecycle, query, and avoid the classic performance traps.

    🏛️ What are JPA and Hibernate?

    JPA standardises ORM in Java: annotations for mapping, EntityManager for operations, JPQL for queries. Hibernate is the engine that turns these into SQL for your database through its dialect.

    ComponentMeaning
    EntityManagerFactoryHeavy, built once per app; holds mappings and pools
    EntityManager (≈ Hibernate Session)Light, per unit of work; owns the persistence context
    EntityTransactionTransaction boundary (Spring uses @Transactional)
    persistence.xml / application.ymlConfiguration

    📦 Mapping Entities

    java@Entity @Table(name = "product")
public class Product {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)   // PostgreSQL; Oracle 12c+ also supports IDENTITY
    private Long id;

    @Column(nullable = false, length = 120)
    private String name;

    @Column(precision = 10, scale = 2)
    private BigDecimal price;

    @Enumerated(EnumType.STRING)          // never ORDINAL — reordering the enum corrupts data
    private Status status;

    @Version private Long version;        // optimistic locking
    protected Product() {}                // JPA needs a no-arg constructor
}

    ID generation strategies

    StrategyHowBest for
    IDENTITYDB auto-increment columnPostgreSQL/Oracle 12c+; disables insert batching
    SEQUENCEDB sequence (allocationSize pre-fetches IDs)Best performance; default choice
    TABLECounter tableRarely; portability only
    UUIDGenerated in JavaDistributed systems

    🔗 Relationships

    TypeAnnotationExample
    One-to-One@OneToOneUser ↔ Profile
    One-to-Many / Many-to-One@OneToMany / @ManyToOneOrder ↔ OrderLine
    Many-to-Many@ManyToMany + join tableStudent ↔ Course
    java@Entity class Order {
    @Id @GeneratedValue Long id;
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    List<OrderLine> lines = new ArrayList<>();
    void add(OrderLine l) { lines.add(l); l.setOrder(this); }   // keep both sides in sync
}
@Entity class OrderLine {
    @Id @GeneratedValue Long id;
    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "order_id")
    Order order;                                                 // owning side = holds the FK
}

    Inheritance strategies: SINGLE_TABLE (fast, nullable columns), JOINED (normalised, joins), TABLE_PER_CLASS (unions, rarely good).

    🔁 Entity Lifecycle & Persistence Context

    New / Transient→ persist()Managed→ detach / closeDetached→ remove()Removed
    javaem.getTransaction().begin();
Product p = em.find(Product.class, 1L);   // SELECT, now MANAGED
p.setPrice(new BigDecimal("499"));        // no save() needed
em.getTransaction().commit();             // dirty checking → UPDATE issued automatically
    💡
    The first-level cache returns the same instance for the same ID within one persistence context. Flush = sync changes to DB; commit = make them permanent.

    🔎 Querying: JPQL, Criteria, Native, Spring Data

    java// JPQL — queries entities, not tables
List<Product> list = em.createQuery(
    "select p from Product p where p.price > :min order by p.name", Product.class)
    .setParameter("min", BigDecimal.TEN).setMaxResults(20).getResultList();

// Native SQL when you need DB-specific features
em.createNativeQuery("select * from product where data @> '{\"tag\":\"new\"}'", Product.class);

// Spring Data JPA
interface ProductRepo extends JpaRepository<Product, Long> {
    List<Product> findByPriceGreaterThanOrderByName(BigDecimal min);
    @Query("select new com.shop.ProductDto(p.id, p.name) from Product p")
    List<ProductDto> summaries();                     // DTO projection: loads only what you need
}

    🚀 Expert: Fetching, N+1, Caching & Locking

    The N+1 problem

    java// BAD: 1 query for orders + N queries for each order.getLines()
orderRepo.findAll().forEach(o -> o.getLines().size());

// FIX 1: fetch join          FIX 2: entity graph          FIX 3: batch fetching
@Query("select distinct o from Order o join fetch o.lines")
List<Order> withLines();
@EntityGraph(attributePaths = "lines") List<Order> findAll();
// application.yml → spring.jpa.properties.hibernate.default_batch_fetch_size: 50
    TopicKey points
    Fetch type@ManyToOne/@OneToOne default EAGER — set LAZY explicitly; @OneToMany default LAZY
    LazyInitializationExceptionAccessing a lazy relation after the session closed; fix with fetch join/DTO, not open-in-view hacks
    L2 cacheShared across sessions (Ehcache/Infinispan); good for read-mostly reference data
    Optimistic lock@Version; conflict → OptimisticLockException; best for web apps
    Pessimistic lockLockModeType.PESSIMISTIC_WRITE → SELECT … FOR UPDATE; use for hot rows
    Batchinghibernate.jdbc.batch_size=50, order_inserts=true; needs SEQUENCE ids
    equals/hashCodeBase on a business key or ID carefully; avoid Lombok @Data on entities
    Q. Which is the best fix for a lazy-loaded collection causing N+1 on a list screen?
    • A Switch everything to EAGER
    • B Fetch join / entity graph / batch fetching
    • C Call getLines() in a loop
    • D Disable transactions
    Q. What triggers an automatic UPDATE for a managed entity?
    • A Calling save() twice

    🔀 SQL Differences You Must Know

    TaskPostgreSQLOracle
    Auto IDsGENERATED ALWAYS AS IDENTITY, SERIALGENERATED AS IDENTITY (12c+), sequences + seq.NEXTVAL
    PaginationLIMIT 10 OFFSET 20OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY (12c+); old: ROWNUM
    Text typetext, varchar(n)VARCHAR2(n), CLOB
    Numbersinteger, numeric(p,s)NUMBER(p,s)
    BooleansNative booleanNative only from 23ai; earlier use NUMBER(1)
    Empty stringDistinct from NULLTreated as NULL
    Current timenow()SYSDATE / SYSTIMESTAMP
    Dummy tableNot needed: SELECT 1SELECT 1 FROM DUAL (optional from 23ai)
    UpsertINSERT … ON CONFLICT DO UPDATEMERGE INTO …
    JSONjsonb + GIN indexJSON type / JSON_VALUE (21c+)
    EXAMPLE · Pagination in both databases
    sql-- PostgreSQL
SELECT * FROM product ORDER BY id LIMIT 10 OFFSET 20;
-- Oracle 12c+
SELECT * FROM product ORDER BY id OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;
    💡
    With JPQL, setFirstResult/setMaxResults makes Hibernate generate the right syntax for each database — one reason to prefer JPQL over native SQL.

    📈 Indexes, Plans & Tuning

    • Index = sorted lookup structure. Index foreign keys and columns used in WHERE/JOIN/ORDER BY.
    • Read the plan: PostgreSQL EXPLAIN (ANALYZE, BUFFERS); Oracle EXPLAIN PLAN / DBMS_XPLAN.DISPLAY. Watch for full table scans on large tables.
    • PostgreSQL index types: B-tree (default), Hash, GIN (JSONB/arrays/full-text), GiST (geo), BRIN (huge ordered tables), partial indexes.
    • Oracle index types: B-tree, bitmap (low cardinality, read-heavy), function-based, reverse key.
    • Isolation defaults: PostgreSQL and Oracle both default to READ COMMITTED.
    • Plan reuse: parameterised queries let both databases reuse plans — another reason to avoid string concatenation.
    sqlCREATE INDEX idx_order_customer ON orders (customer_id);
CREATE INDEX idx_prod_tags ON product USING GIN (data);          -- PostgreSQL JSONB
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer_id = 42;

    0 / 0 correct

    🛒 Scenario: ShopKart Order Service

    ShopKart is a Spring Boot service with Customer, Order and OrderLine tables. It runs PostgreSQL in development and Oracle in production. The orders list page takes 8 seconds and logs 1,200 SQL statements per request.

    📝 Tasks

    ✍️ Task 1 · Diagnose: why 1,200 statements for one page, and how do you confirm it?
    Model answer: Classic N+1: one query loads orders, then lazy collections/associations (lines, customer) load per row. Confirm with org.hibernate.SQL logging, Hibernate statistics, or a tool like datasource-proxy; assert the statement count in tests.
    ✍️ Task 2 · Fix it without making relations EAGER.
    Model answer: Use a fetch join or @EntityGraph for the list use-case, or better a DTO projection with only the columns the screen needs. For collections add default_batch_fetch_size. Do not fetch-join a collection together with setMaxResults (in-memory pagination) — page the IDs first, then fetch.
    ✍️ Task 3 · Write an entity mapping for Order that works on both PostgreSQL and Oracle.
    Model answer: Use @GeneratedValue(strategy = SEQUENCE) with a named @SequenceGenerator (both DBs support sequences), BigDecimal for money, @Enumerated(STRING), avoid relying on native boolean columns, and paginate through JPQL instead of native LIMIT.
    ✍️ Task 4 · Two users edit the same order at the same time. Prevent lost updates.
    Model answer: Add @Version for optimistic locking; catch OptimisticLockException and ask the user to reload/merge. Use PESSIMISTIC_WRITE only for hot rows like stock counters.
    ✍️ Task 5 · Bulk-import 100,000 order lines quickly.
    Model answer: Use SEQUENCE ids with allocationSize=50, hibernate.jdbc.batch_size=50, order_inserts=true; flush() and clear() the persistence context every batch; on PostgreSQL add reWriteBatchedInserts=true; or use plain JDBC batch / COPY for maximum speed.

    ✅ Quick Checks

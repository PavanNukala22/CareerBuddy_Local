    Module 01 · Foundations

    Enterprise Java Landscape

    What "enterprise tech" means, why systems are split into services, and how messaging and testing fit in.

    🧭 What is Enterprise Tech?

    Enterprise software serves many users and business processes at once (banking, retail, logistics). It must be reliable, scalable, secure and maintainable for years. Java dominates this space because of the JVM, strong typing, mature frameworks (Spring) and a huge ecosystem.

    🏢 Monolith

    One deployable unit. Simple to start, hard to scale and release independently as it grows.

    🧩 Microservices

    Many small services, each owning one business capability and its data. Independent deploys, more operational complexity.

    🧩
    Microservices
    Split a system into small independent services.
    📨
    Messaging
    Kafka / ActiveMQ let services talk asynchronously.
    🧪
    JUnit 5
    Write and run automated tests.
    🎭
    Mockito
    Replace dependencies with controllable fakes.

    🔄 Synchronous vs Asynchronous

    StyleHow it worksExampleTrade-off
    SynchronousCaller waits for the replyREST / gRPC callSimple, but callers fail when the callee is down
    AsynchronousCaller sends a message and moves onKafka topic, JMS queueResilient and decoupled, but eventual consistency

    📖 Key Terms

    ServiceA separately deployable program owning one capability.
    BrokerServer that stores and routes messages (Kafka, ActiveMQ).
    Producer / ConsumerSender and receiver of messages.
    IdempotentDoing it twice has the same effect as once.
    Eventual consistencyData across services becomes consistent after a short delay.
    Test doubleA fake used in place of a real dependency (mock, stub, spy).
    Testing pyramidMany unit tests, fewer integration tests, very few end-to-end tests.

    Module 02 · Microservices Architectures

    Microservices Architectures

    From what a microservice is, to resilience, data consistency patterns and observability.

    🧩 What are Microservices?

    An architectural style that structures an application as a set of small, autonomous, independently deployable services, each modelled around a business capability and owning its own data store.

    • Single responsibility — one service, one business capability
    • Loose coupling — talk through APIs or events only
    • Database per service — never share tables
    • Independent lifecycle — build, test, deploy separately
    • Design for failure — networks and services will fail

    🗂️ Types & Styles

    DimensionTypesNotes
    DecompositionBy business capability, by subdomain (DDD bounded context), strangler fig (gradual migration)Start from bounded contexts, not technical layers
    CommunicationSynchronous (REST, gRPC) · Asynchronous (events, commands)Prefer async between services for resilience
    DataDatabase per service · shared DB (anti-pattern)Cross-service queries need APIs, CQRS or events
    Service rolesDomain services · API gateway · BFF · aggregatorsBFF = Backend-for-Frontend per client type

    🏗️ Building Blocks

    🚪
    API Gateway
    Single entry: routing, auth, rate limiting (Spring Cloud Gateway).
    🔎
    Service Discovery
    Services find each other (Eureka, Consul, Kubernetes DNS).
    ⚙️
    Config Server
    Central externalised config (Spring Cloud Config, K8s ConfigMaps).
    🛡️
    Resilience
    Retry, timeout, circuit breaker (Resilience4j).

    ☕ Example: A Spring Boot Microservice

    Order Service (REST + JPA)
    java@RestController
@RequestMapping("/orders")
class OrderController {
    private final OrderService service;
    OrderController(OrderService service) { this.service = service; }

    @PostMapping
    ResponseEntity<OrderDto> create(@Valid @RequestBody CreateOrder req) {
        return ResponseEntity.status(201).body(service.create(req));
    }
    @GetMapping("/{id}")
    OrderDto get(@PathVariable Long id) { return service.find(id); }
}
    💡
    Keep controllers thin; business rules live in the service/domain layer so they are easy to unit test.

    🛡️ Intermediate: Resilience

    A downstream call can be slow or down. Without protection, threads pile up and the failure cascades.

    • Timeout — never wait forever
    • Retry with backoff — only for idempotent calls
    • Circuit breaker — CLOSED → OPEN after failures → HALF-OPEN to probe
    • Bulkhead — isolate resources per dependency
    • Fallback — degrade gracefully
    java@CircuitBreaker(name = "payment", fallbackMethod = "paymentFallback")
@Retry(name = "payment")
public PaymentResult charge(Order o) {
    return paymentClient.charge(o);
}
PaymentResult paymentFallback(Order o, Throwable t) {
    return PaymentResult.pending(o.getId());   // queue for later
}

    🧬 Expert: Data Consistency Patterns

    With a database per service there are no distributed ACID transactions. Use these patterns:

    PatternIdea
    SagaSequence of local transactions; each step has a compensating action. Choreography (events) or Orchestration (a coordinator).
    OutboxWrite the data and the event to the same DB transaction; a relay publishes the event — avoids "DB saved but message lost".
    CQRSSeparate write model from read models optimised for queries.
    Event SourcingStore state as an append-only log of events; rebuild state by replay.
    Idempotent consumerTrack processed message IDs so redelivery is harmless.
    Order Saga (choreography)

    OrderCreated → Payment service charges → PaymentCompleted → Inventory reserves → StockReserved → Order confirmed. If payment fails: PaymentFailed → Order cancelled (compensation).

    📡 Expert: Observability, Security & Delivery

    • Three pillars: logs (structured, with correlation ID), metrics (Micrometer + Prometheus), traces (OpenTelemetry)
    • Security: OAuth2/JWT at the gateway, mTLS between services, least privilege, secrets in a vault
    • Delivery: containers + Kubernetes, CI/CD per service, blue-green/canary releases, consumer-driven contract tests (Pact)
    • Anti-patterns: distributed monolith, shared database, chatty services, no ownership
    Q. Which pattern prevents "order saved but event never published"?
    • A Circuit breaker
    • B Transactional outbox
    • C Bulkhead
    • D API gateway
    Q. In a saga, what undoes a completed step when a later step fails?
    • A Rollback of a 2PC
    • B Compensating transaction
    • C Retry
    • D Cache eviction

    Module 03 · Messaging & ActiveMQ

    Messaging & Apache ActiveMQ

    What messaging is, JMS concepts, queues vs topics, reliability, and production patterns.

    📨 What is Messaging?

    Messaging lets applications exchange data through an intermediary called a message broker. The sender does not need the receiver to be online; the broker stores the message until it is delivered.

    • Decoupling in time, location and technology
    • Load levelling — absorb traffic spikes
    • Reliability — persistent storage and redelivery

    🗂️ Types: Queue vs Topic

    Queue (point-to-point)Topic (publish/subscribe)
    ReceiversEach message goes to one consumerEach message goes to all subscribers
    Use caseWork distribution, order processingNotifications, event broadcast
    ScalingAdd competing consumersDurable subscriptions to avoid missing messages

    JMS (Jakarta Messaging) is the standard Java API. ActiveMQ comes in two flavours: Classic (5.x) and Artemis (next generation, higher performance, the base of Red Hat AMQ). Both support JMS, AMQP, MQTT and STOMP.

    ☕ Example: Spring JMS

    Producer and Listener
    java@Service
class OrderPublisher {
    private final JmsTemplate jms;
    OrderPublisher(JmsTemplate jms) { this.jms = jms; }
    void send(OrderEvent e) { jms.convertAndSend("orders.queue", e); }
}

@Component
class OrderListener {
    @JmsListener(destination = "orders.queue")
    void onMessage(OrderEvent e) { /* process */ }
}

    🛟 Intermediate: Reliability

    FeatureMeaning
    Persistent deliveryMessage survives broker restart (stored on disk)
    Acknowledgement modesAUTO, CLIENT, DUPS_OK, SESSION_TRANSACTED
    Transacted sessionCommit/rollback a group of sends and receives
    Redelivery policyRetry count and delay before giving up
    Dead Letter Queue (DLQ)Poison messages end up in ActiveMQ.DLQ for inspection
    Message selectorsFilter by header, e.g. type = 'PREMIUM'

    🏭 Expert: Production Topics

    • Virtual topics — publish to a topic but let each consumer group read its own queue (scale + pub/sub)
    • High availability — master/slave with shared store, or Artemis replication/live-backup
    • Network of brokers — federate brokers across sites
    • Flow control — memory/store limits and producer throttling
    • Idempotent consumers — ActiveMQ is at-least-once, so duplicates are possible
    • Security — TLS, authentication, per-destination authorisation
    ⚠️
    Never swallow exceptions in a listener: the message is acknowledged and silently lost. Let it fail so redelivery and the DLQ work.
    Q. Which destination delivers a message to every subscriber?
    • A Queue
    • B Topic
    • C DLQ
    • D Selector

    Module 04 · Apache Kafka

    Apache Kafka

    A distributed event log: architecture, producers, consumer groups, delivery guarantees, and streaming.

    🌊 What is Kafka?

    Apache Kafka is a distributed, durable, append-only event log. Producers append events to topics; consumers read them at their own pace and can replay history. It is used for event-driven microservices, data pipelines, log aggregation and stream processing.

    🏛️ Architecture

    📚
    Topic
    Named stream of events, split into partitions.
    🧱
    Partition
    Ordered, immutable log. Ordering is guaranteed only within a partition.
    🖥️
    Broker
    Kafka server. Partitions are replicated across brokers.
    👥
    Consumer group
    Consumers sharing partitions; each partition goes to one consumer in the group.
    OffsetPosition of a record within a partition.
    KeyRecords with the same key go to the same partition (keeps order per key).
    Replication factorCopies of each partition (commonly 3).
    ISRIn-sync replicas that can take over if the leader fails.
    RetentionHow long records are kept (time or size), independent of consumption.
    KRaftBuilt-in controller quorum that replaces ZooKeeper in modern Kafka.

    ☕ Example: Spring Kafka

    Producer & Consumer
    java@Service
class OrderProducer {
    private final KafkaTemplate<String, OrderEvent> kafka;
    OrderProducer(KafkaTemplate<String, OrderEvent> kafka) { this.kafka = kafka; }
    void publish(OrderEvent e) { kafka.send("orders", e.orderId(), e); } // key = orderId
}

@Component
class OrderConsumer {
    @KafkaListener(topics = "orders", groupId = "inventory")
    void handle(OrderEvent e) { /* reserve stock */ }
}
    💡
    Using orderId as the key keeps all events of one order in order.

    🎯 Intermediate: Delivery Guarantees & Offsets

    SettingEffect
    acks=allLeader waits for all in-sync replicas — strongest durability
    enable.idempotence=trueProducer retries do not create duplicates
    min.insync.replicas=2Writes fail if fewer replicas are in sync
    enable.auto.commit=falseCommit offsets after processing for at-least-once
    auto.offset.resetearliest or latest when there is no committed offset

    Semantics: at-most-once (commit before processing), at-least-once (commit after — the default choice, needs idempotent consumers), exactly-once (idempotent producer + transactions within Kafka).

    🧠 Expert: Streams, Connect, Schemas & Operations

    • Kafka Streams — Java library for stateful stream processing (joins, windows, aggregations)
    • Kafka Connect — ready-made connectors to move data in/out of DBs and systems (CDC with Debezium feeds the outbox pattern)
    • Schema Registry — Avro/Protobuf schemas with compatibility rules for safe evolution
    • Error handling — retry topics and a dead-letter topic (DefaultErrorHandler, @RetryableTopic)
    • Scaling — consumers ≤ partitions; watch consumer lag; avoid hot keys; rebalances pause consumption
    • Transactions — transactional.id, read_committed consumers
    KafkaActiveMQ
    ModelDistributed log, pull-basedBroker with queues/topics, push-based
    ReplayYes (retention)No (message removed once consumed)
    ThroughputVery highModerate
    RoutingTopics + partitionsRich: selectors, virtual topics, JMS
    Best forEvent streaming, large scale pipelinesEnterprise integration, task queues, JMS apps

    Module 05 · JUnit 5

    JUnit 5

    Unit testing basics through parameterized tests, extensions and parallel execution.

    🧪 What is Unit Testing & JUnit?

    A unit test checks the smallest piece of code (a method/class) in isolation and runs in milliseconds. JUnit 5 is the standard Java testing framework, made of three parts:

    🧱
    JUnit Platform
    Launches test engines; used by IDEs and build tools.
    ✨
    JUnit Jupiter
    The new programming model and annotations (org.junit.jupiter).
    🕰️
    JUnit Vintage
    Runs old JUnit 3/4 tests.
    Test typeScopeSpeed
    UnitOne class, dependencies fakedms
    IntegrationSeveral components, real DB/brokerseconds
    ContractAgreement between services (Pact)seconds
    End-to-endWhole systemminutes

    🏁 Basics: Structure & Assertions

    Calculator test (Arrange – Act – Assert)
    javaclass PriceCalculatorTest {
    @Test
    @DisplayName("applies 10% discount for premium customers")
    void premiumDiscount() {
        var calc = new PriceCalculator();
        BigDecimal result = calc.total(new BigDecimal("100"), Tier.PREMIUM);
        assertEquals(new BigDecimal("90.00"), result);
    }
    @Test
    void negativeAmountRejected() {
        assertThrows(IllegalArgumentException.class,
            () -> new PriceCalculator().total(new BigDecimal("-1"), Tier.BASIC));
    }
}
    AssertionUse
    assertEquals / assertNotEqualsCompare values (expected first)
    assertTrue / assertFalse / assertNullConditions
    assertThrowsException expected
    assertAllGroup assertions; all are reported
    assertTimeoutMust finish in time
    assertIterableEquals / assertArrayEqualsCollections and arrays

    🔁 Intermediate: Lifecycle, Parameterized & Nested

    AnnotationRuns
    @BeforeAll / @AfterAllOnce per class (static)
    @BeforeEach / @AfterEachBefore/after every test
    @Disabled, @Tag("slow")Skip or group tests
    @NestedGroup related tests in inner classes
    @TimeoutFail slow tests
    java@ParameterizedTest
@CsvSource({"100,PREMIUM,90.00", "100,BASIC,100.00", "0,BASIC,0.00"})
void discounts(String amount, Tier tier, String expected) {
    assertEquals(new BigDecimal(expected),
        new PriceCalculator().total(new BigDecimal(amount), tier));
}
// other sources: @ValueSource, @EnumSource, @MethodSource

    🧠 Expert: Extensions, Dynamic Tests & Execution

    • Extensions (@ExtendWith) replace JUnit 4 runners/rules: MockitoExtension, SpringExtension, custom BeforeEachCallback, ParameterResolver
    • Dynamic tests — @TestFactory returns DynamicTest objects generated at runtime
    • Conditional execution — @EnabledOnOs, @EnabledIfEnvironmentVariable, assumeTrue
    • Parallel execution — junit.jupiter.execution.parallel.enabled=true (tests must be thread-safe)
    • Test instance lifecycle — @TestInstance(PER_CLASS)
    • Tags + Maven/Gradle profiles to split fast unit tests from slow integration tests
    💡
    Good tests are Fast, Independent, Repeatable, Self-validating, and Timely (F.I.R.S.T.). Test behaviour, not implementation.

    Module 06 · Mockito

    Mockito

    Test doubles, stubbing, verification, captors, spies, and advanced mocking.

    🎭 What is Mocking? Types of Test Doubles

    Real dependencies (database, REST client, broker) make tests slow and flaky. A test double replaces them. Mockito is the most popular Java library to create them.

    DoubleWhat it does
    DummyPassed around, never used
    StubReturns canned answers
    MockStub + records calls so you can verify interactions
    SpyWraps a real object; real methods run unless stubbed
    FakeWorking lightweight implementation (in-memory repository)

    🏁 Basics: Mock, Stub, Verify

    Unit-testing a service with Mockito + JUnit 5
    java@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock PaymentClient paymentClient;
    @Mock OrderRepository repo;
    @InjectMocks OrderService service;

    @Test
    void confirmsOrderWhenPaymentSucceeds() {
        when(paymentClient.charge(any())).thenReturn(PaymentResult.ok());
        when(repo.save(any(Order.class))).thenAnswer(i -> i.getArgument(0));

        Order o = service.place(new CreateOrder("A1", 2));

        assertEquals(Status.CONFIRMED, o.getStatus());
        verify(paymentClient).charge(any());
        verify(repo, times(1)).save(o);
    }
}
    APIPurpose
    when(..).thenReturn(..)Stub a return value
    when(..).thenThrow(..)Simulate failure
    doThrow(..).when(mock).voidMethod()Stub void methods
    verify(mock, times/never/atLeast)Check interactions
    verifyNoMoreInteractions(mock)Nothing unexpected happened

    🔧 Intermediate: Matchers, Captors, Answers, Spies

    • Matchers: any(), eq(), argThat() — if one argument uses a matcher, all must
    javaArgumentCaptor<OrderEvent> cap = ArgumentCaptor.forClass(OrderEvent.class);
verify(publisher).send(cap.capture());
assertEquals("A1", cap.getValue().orderId());

// BDD style
given(repo.findById(1L)).willReturn(Optional.of(order));
then(repo).should().findById(1L);

// consecutive calls (retry scenario)
when(client.call()).thenThrow(new IOException()).thenReturn("ok");

// Spy
List<String> real = new ArrayList<>();
List<String> spy = spy(real);
doReturn(99).when(spy).size();
    ⚠️
    With spies prefer doReturn(..).when(spy).method() — when(spy.method()) calls the real method first.

    🧠 Expert: Strict Stubs, Static Mocks & Pitfalls

    • Strict stubs (default with MockitoExtension) — fails on unused stubbings (UnnecessaryStubbingException)
    • Static / constructor mocking — mockStatic(UUID.class) inside try-with-resources (inline mock maker is the default in Mockito 5)
    • Spring Boot: @MockBean (newer Spring Boot versions provide @MockitoBean) replaces a bean in the Spring context
    • Deep stubs (RETURNS_DEEP_STUBS) hint at a Law-of-Demeter smell
    • Pitfalls: mocking value objects or the class under test, over-verifying implementation details, mocks that duplicate production logic, mocking what you do not own (wrap it first), testing messaging with mocks only (add integration tests)
    Mocking a Kafka producer
    java@Mock KafkaTemplate<String, OrderEvent> kafka;
@InjectMocks OrderProducer producer;

@Test void publishesWithOrderIdAsKey() {
    producer.publish(new OrderEvent("A1"));
    verify(kafka).send(eq("orders"), eq("A1"), any(OrderEvent.class));
}
    Q. Which creates a mock that also records calls for verification?
    • A Dummy
    • B Mock
    • C Fake
    • D Stub only
    Q. Why use doReturn().when(spy)?
    • A It is faster
    • B It avoids calling the real method during stubbing
    • C It verifies calls
    • D It resets the spy

    Module 07 · Practice

    Practice: Order Platform

    Design, messaging and test an order platform using everything in this course.

    🛒 Scenario

    An e-commerce platform has Order, Payment and Inventory services. When a customer places an order, payment must be charged and stock reserved. Peak sales produce thousands of orders per minute.

    0 / 0 correct

    1️⃣ Task 1 · Architecture

    ✍️ Propose service boundaries, communication style and how you keep data consistent.
    Model answer: Three services, each with its own database. Order service publishes OrderCreated via the outbox pattern; Payment and Inventory react asynchronously. Use a choreographed saga with compensations (PaymentFailed → cancel order, release stock). REST only for synchronous reads via the gateway.

    2️⃣ Task 2 · Messaging

    Q. Order events must be replayable and processed at very high volume by several independent services. Best fit?
    • A ActiveMQ queue
    • B Kafka topic with consumer groups
    • C Shared database table
    • D REST polling
    ✍️ Choose a partition key and a consumer configuration for the Inventory service.
    Model answer: Key = orderId (or productId if stock ordering matters). Manual offset commit after processing (at-least-once), idempotent handling by storing processed event IDs, a DLQ topic for poison messages, and as many consumers as partitions.
    Q. A legacy billing system exposes JMS. Which broker is the natural integration point?
    • A Kafka
    • B ActiveMQ
    • C Redis
    • D None

    3️⃣ Task 3 · Write Tests

    ✍️ List 4 JUnit 5 + Mockito tests for OrderService.place().
    Model answer: (1) payment succeeds → order CONFIRMED and event published; (2) payment fails → order CANCELLED, no event; (3) assertThrows for invalid quantity; (4) parameterized test over discount tiers. Use @Mock PaymentClient/Repository, ArgumentCaptor for the published event, and verifyNoMoreInteractions.
    Q. Which test should use a real Kafka broker (e.g. Testcontainers) rather than mocks?
    • A Unit test of discount logic
    • B Integration test that a message is really produced and consumed
    • C A getter test
    • D A parameterized test

    4️⃣ Task 4 · Resilience

    ✍️ The Payment service is slow. Explain what you add to Order service.
    Model answer: Timeout on the client, retry with exponential backoff only for idempotent calls, a circuit breaker with fallback (mark order PENDING_PAYMENT and retry via a queue), bulkhead for the payment thread pool, and metrics/alerts on failure rate.

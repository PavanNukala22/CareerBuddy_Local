    Java Language & Runtime: What Is What

    Start from zero: what Java, the JDK and the JVM are, how code travels from source to execution, and which versions matter.

    ☕ What is Java?

    Java is a general-purpose, object-oriented, strongly typed programming language and a platform (compiler, runtime, standard libraries). Java source is compiled to bytecode, a compact instruction set that any Java Virtual Machine (JVM) can run — this is the idea behind “Write Once, Run Anywhere”.

    🌍
    Platform independent
    The same .class files run on any OS that has a JVM.
    🧱
    Object-oriented
    Programs are built from classes, objects and interfaces.
    🧹
    Automatic memory
    The garbage collector frees unused objects for you.
    🧵
    Built-in concurrency
    Threads, locks and the java.util.concurrent library ship with the JDK.
    🛡️
    Safe by design
    No pointer arithmetic, array bounds checks, bytecode verification.
    💡
    Java is the language; the JVM is the runtime. Other languages — Kotlin, Scala, Groovy, Clojure — also compile to JVM bytecode and share the same runtime, GC and threading model that you will learn in this course.

    🔵 Primitive

    • Stored on the stack (locals) or inside objects
    • Never null
    • Fast, no object overhead

    🧾 The Object Contract: equals & hashCode

    Every class extends Object. Collections such as HashMap and HashSet rely on equals() and hashCode(). The contract: equal objects must have equal hash codes.

    javaimport java.util.*;

public class Demo {
    public static void main(String[] a) {
        Set<Point> set = new HashSet<>();
        set.add(new Point(1, 2));
        System.out.println(set.contains(new Point(1, 2)));  // true (thanks to hashCode+equals)
    }
}

final class Point {
    private final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;     // pattern matching (Java 16+)
        return x == p.x && y == p.y;
    }
    @Override public int hashCode() { return Objects.hash(x, y); }
    @Override public String toString() { return "Point(" + x + "," + y + ")"; }
}
    ⚠️
    If you override equals but not hashCode, lookups in hash-based collections silently fail. Never use mutable fields in hashCode for objects stored as keys. In modern Java, a record generates all of this for you.

public class Demo {
    // Generic method with a bounded type
    static <T extends Comparable<T>> T max(List<? extends T> items) {
        T best = null;
        for (T t : items) if (best == null || t.compareTo(best) > 0) best = t;
        return best;

        System.out.println(wc);                                  // counts per word
        List<Integer> nums = new ArrayList<>(List.of(1, 2, 3, 4));
        nums.removeIf(n -> n % 2 == 0);                          // safe removal
        System.out.println(nums);                                // [1, 3]

    }
}

    HashMap internals (a favourite interview topic)

    • Array of buckets; index = (n-1) & hash; collisions form a linked list.
    • A bucket with ≥ 8 nodes (and table size ≥ 64) becomes a red-black tree (Java 8+), giving O(log n) worst case.
    • Resizes (doubles) when size exceeds capacity × loadFactor (default 0.75).
    • Not thread-safe — use ConcurrentHashMap for shared access (see Module 07).
    📌
    List.of(), Set.of(), Map.of() and stream.toList() return unmodifiable collections. Java 21 adds sequenced collections (getFirst(), reversed()).

    📦 Records

    A record is a transparent, shallowly immutable data carrier. The compiler generates the constructor, accessors, equals, hashCode and toString.

    javaimport java.util.*;

public class Demo {
    public static void main(String[] args) {
        Money m = Money.inr(100).plus(Money.inr(50));
        System.out.println(m);                                  // Money[amount=150, currency=INR]
        System.out.println(m.equals(new Money(150, "INR")));    // true
        System.out.println(new HashSet<>(List.of(m)).contains(new Money(150, "INR"))); // true
    }
}

record Money(long amount, String currency) {
    Money {                                   // compact canonical constructor = validation
        if (amount < 0) throw new IllegalArgumentException("negative");
        currency = currency.toUpperCase();    // normalise before fields are assigned
    }
    static Money inr(long a) { return new Money(a, "inr"); }   // static factory
    Money plus(Money o) {                                      // records may have methods
        if (!currency.equals(o.currency)) throw new IllegalArgumentException("currency");
        return new Money(amount + o.amount, currency);
    }
}
    • Records are implicitly final and cannot extend classes (they can implement interfaces).
    • Components are final; a record holding a List is only shallowly immutable — copy with List.copyOf() in the constructor.
    • Perfect for DTOs, value objects, map keys and local helper types inside streams.

    🔀 Switch Expressions & Pattern Matching

    Switch expressions return a value, use -> arms (no fall-through) and must be exhaustive. Pattern matching tests the shape of a value and binds variables in one step.

    javapublic class Demo {
    enum Day { MON, TUE, SAT, SUN }

    static String kind(Day d) {
        return switch (d) {                       // exhaustive over the enum: no default needed
            case SAT, SUN -> "weekend";
            case MON, TUE -> "weekday";
        };
    }
    static String describe(Object o) {            // pattern matching for switch (Java 21)
        return switch (o) {
            case null            -> "null!";
            case Integer i when i > 100 -> "big int " + i;
            case Integer i       -> "int " + i;
            case String s        -> "string of length " + s.length();
            case int[] arr       -> "int array of " + arr.length;
            default              -> "other " + o;
        };
    }
    public static void main(String[] args) {
        System.out.println(kind(Day.SAT));            // weekend
        System.out.println(describe(500));            // big int 500
        System.out.println(describe("hello"));        // string of length 5
        Object x = "text";
        if (x instanceof String s && !s.isEmpty()) System.out.println(s.toUpperCase());
    }
}
    📌
    Order matters: a more specific pattern (Integer i when i > 100) must come before a general one, or the compiler reports it as dominated.

    🔐 Sealed Classes & Record Patterns

    A sealed type lists exactly which classes may extend it. Combined with records and pattern-matching switch you get algebraic data types with compiler-checked exhaustiveness.

    java

public class Demo {
    static double area(Shape s) {
        return switch (s) {                        // no default: compiler proves all cases covered
            case Circle(double r)         -> Math.PI * r * r;     // record deconstruction pattern
            case Rect(double w, double h) -> w * h;
            case Square(double side)      -> side * side;
        };
    }
    public static void main(String[] args) {
        System.out.printf("%.2f %.1f %.1f%n", area(new Circle(1)), area(new Rect(2, 3)), area(new Square(4)));
    }
}

sealed interface Shape permits Circle, Rect, Square {}
record Circle(double r) implements Shape {}
record Rect(double w, double h) implements Shape {}
record Square(double side) implements Shape {}
    💡
    Add a new permitted subtype and every non-default switch that uses Shape stops compiling — the compiler tells you exactly where to update. That is the main benefit.

    🏗️ What is the JVM? (Architecture)

    The JVM is a virtual computer implemented in software. It reads bytecode and turns it into real CPU instructions while managing memory, threads and security.

    Figure 4.1 · Main subsystems of the JVM
    Class Loader SubsystemLocates .class data, loads, links and initialises classes.
    Runtime Data AreasMemory the JVM uses while a program runs: heap, metaspace, stacks, PC registers.
    Execution EngineRuns bytecode: interpreter, JIT compilers and the garbage collector.
    Native InterfaceLets Java call native code (JNI, and the newer Foreign Function & Memory API).

    📥 Class Loading, Linking & Initialization

    Classes are loaded lazily — the first time they are needed. Each class goes through three phases:

    PhaseStepWhat happens
    1. Loading—A class loader reads the bytes and creates a Class object.
    2. LinkingVerificationBytecode is checked for structural safety (valid types, stack discipline).
    2. LinkingPreparationStatic fields are allocated and set to default values (0, null, false).
    2. LinkingResolutionSymbolic references become direct references (may be lazy).
    3. Initialization—Static initialisers and static field assignments run, once, thread-safely.

    🧹 What is Garbage Collection?

    Garbage collection (GC) automatically finds objects that the program can no longer reach and reclaims their memory. You never call free(); you only stop referencing objects.

    Figure 5.1 · Reachability from GC roots decides what is garbage
    Reachable objectCan be reached by following references from a GC root.
    GarbageAn object that is unreachable. Cycles between garbage objects do not keep them alive.
    Stop-the-world (STW)A pause where all application threads halt so the GC can work safely.
    ThroughputFraction of time spent running application code rather than GC.
    LatencyLength of individual pauses (p99 / max pause).
    FootprintMemory the JVM consumes.
    Allocation rateMB/s of new objects created — the main driver of GC frequency.
    💡
    Every collector balances throughput ↔ latency ↔ footprint. You can optimise two; the third pays.

    ♻️ Core GC Algorithms

    AlgorithmHow it worksPros / cons
    Mark–SweepMark reachable objects, sweep the rest into a free list.Simple; causes fragmentation.
    Mark–CompactMark, then slide live objects together.No fragmentation; moving objects costs time.
    CopyingCopy live objects to an empty space; wipe the old space.Very fast when most objects are dead (young gen); needs spare space.
    GenerationalSeparate young and old spaces and collect young often.Exploits “most objects die young”.
    Concurrent (tri-colour marking)Mark while the application runs, using barriers to track changes.Short pauses; extra CPU and barriers.
    Figure 5.2 · Generational heap layout (Serial / Parallel / G1 regions follow the same idea)
    • Minor GC — collects the young generation. Frequent, short.
    • Major / Old GC — collects the old generation (concurrent in G1 / ZGC).
    • Mixed GC (G1) — young regions plus some old regions with the most garbage.
    • Full GC — whole heap (and metaspace); usually a long STW. A sign of trouble.

    🧪 The Collectors (Types)

    Serial-XX:+UseSerialGCTiny heaps, single-core containers, CLI toolsSingle-threaded STW, lowest overhead
    Parallel-XX:+UseParallelGCBatch jobs, max throughputMulti-threaded STW young + old

    🧱 G1 Deep Dive

    G1 (Garbage-First) splits the heap into equal-sized regions (1–32 MB). Each region acts as Eden, Survivor, Old or Humongous, and G1 collects the regions with the most garbage first to meet your pause goal.

    G1 conceptMeaning
    Remembered setPer-region record of incoming references so a region can be collected without scanning the whole heap.
    Humongous objectObject ≥ 50% of a region; allocated in contiguous regions directly in old space — can cause fragmentation and early cycles.
    Concurrent marking cycleStarts when heap occupancy passes -XX:InitiatingHeapOccupancyPercent (default 45%).
    Evacuation failureNo free region to copy survivors → expensive Full GC. Fix: bigger heap, lower IHOP, reduce allocation rate.
    Pause-time goalA target, not a guarantee; G1 adjusts young size to try to meet it.

    ⚡ ZGC & Low-Latency Collection

    ZGC does almost all work — marking, relocation, reference processing — concurrently while your threads run. Pause time does not grow with heap size.

    • Coloured pointers + load barriers: metadata bits in references let the GC move objects while threads run.
    • Generational ZGC (Java 21, default from 23) collects young objects often, sharply reducing CPU and memory overhead.
    • Trade-off: slightly lower raw throughput than Parallel/G1 and more memory headroom needed.
    bashjava -XX:+UseZGC -XX:+ZGenerational -Xmx16g -Xlog:gc -jar app.jar

    ✅ Choose G1 when

    • General web services
    • Moderate heaps (a few GB – tens of GB)
    • You want the safe default
    • Pauses of 50–200 ms are acceptable

    ⚡ Choose ZGC when

    • Strict p99 latency (trading, gaming, real-time APIs)
    • Very large heaps
    • You can spare CPU and memory headroom
    • Pauses must stay in the millisecond range

    🧵 What is a Thread? (Process vs Thread)

    A process is a running program with its own memory. A thread is a lightweight path of execution inside a process; all threads of a process share the same heap but each has its own stack.

    Creation costHeavyLighter (platform thread ≈ 1 MB stack reserved)

    💥 Race Conditions & Data Races

    A race condition occurs when correctness depends on the unlucky timing of threads. The classic example is count++: it is really read → add → write — three steps that can interleave.

    javapublic class Demo {
    static int unsafe = 0;
    static int safe = 0;
    static final Object LOCK = new Object();

    public static void main(String[] args) throws Exception {
        Runnable r = () -> {
            for (int i = 0; i < 100_000; i++) {
                unsafe++;                              // NOT atomic -> lost updates
                synchronized (LOCK) { safe++; }        // mutual exclusion
            }
        };
        Thread a = new Thread(r), b = new Thread(r);
        a.start(); b.start(); a.join(); b.join();
        System.out.println("unsafe = " + unsafe + " (expected 200000; on multi-core machines usually LESS, and it varies per run)");
        System.out.println("safe   = " + safe);       // always 200000
    }
}
    ⚠️
    Three things to remember: atomicity (compound actions happen as one), visibility (one thread’s writes become seen by others) and ordering (the compiler/CPU may reorder instructions). Thread-safety must provide all three.

    synchronizedMutual exclusion + visibility (happens-before on unlock → lock)Fairness; non-blocking behaviour

    javapublic class Demo {
    // 1. volatile stop flag: guarantees the worker SEES the change
    static volatile boolean running = true;

    // 2. Bounded buffer using wait()/notifyAll() on the same monitor
    static class Buffer {
        private final java.util.Queue<Integer> q = new java.util.ArrayDeque<>();
        private final int cap = 2;
        synchronized void put(int v) throws InterruptedException {
            while (q.size() == cap) wait();            // ALWAYS wait in a loop (spurious wakeups)
            q.add(v); notifyAll();
        }
        synchronized int take() throws InterruptedException {
            while (q.isEmpty()) wait();
            int v = q.remove(); notifyAll(); return v;
        }
    }

    public static void main(String[] args) throws Exception {
        Thread w = new Thread(() -> { while (running) { /* work */ } System.out.println("stopped"); });
        w.start(); Thread.sleep(100); running = false; w.join();

        Buffer buf = new Buffer();
        Thread prod = new Thread(() -> { try { for (int i = 1; i <= 5; i++) buf.put(i); } catch (InterruptedException e) {} });
        Thread cons = new Thread(() -> { try { int s = 0; for (int i = 0; i < 5; i++) s += buf.take(); System.out.println("sum=" + s); } catch (InterruptedException e) {} });
        prod.start(); cons.start(); prod.join(); cons.join();
    }
}

    • Never synchronise on strings, boxed primitives or this exposed to outside code — use a private final Object lock.

    🧬 Java Memory Model & Happens-Before

    The Java Memory Model (JMM) defines when one thread’s writes are guaranteed to be visible to another. Without a happens-before relationship, a reader may see stale values or reordered operations.

    Happens-before ruleMeaning
    Program orderWithin one thread, earlier actions happen-before later ones.
    Monitor lockAn unlock happens-before every later lock of the same monitor.
    VolatileA write to a volatile happens-before every later read of it.
    Thread start / joinstart() happens-before the thread’s first action; its last action happens-before join() returns.
    Final fieldsCorrectly constructed objects publish their final fields safely.
    Executors / futuresSubmitting a task happens-before it runs; its result happens-before Future.get().
    javapublic class Demo {
    // Double-checked locking: correct ONLY with volatile
    static class Config {
        private static volatile Config instance;
        private Config() {}
        static Config get() {
            Config c = instance;                       // 1st check (no lock)
            if (c == null) {
                synchronized (Config.class) {
                    c = instance;
                    if (c == null) instance = c = new Config();   // volatile prevents partial publication
                }
            }
            return c;
        }
    }
    // Simpler and always safe: initialisation-on-demand holder
    static class Holder {
        private Holder() {}
        private static class Lazy { static final Holder INSTANCE = new Holder(); }  // class init is thread-safe
        static Holder get() { return Lazy.INSTANCE; }
    }
    public static void main(String[] args) {
        System.out.println(Config.get() == Config.get());
        System.out.println(Holder.get() == Holder.get());
    }
}

        ExecutorService pool = Executors.newFixedThreadPool(4);
        for (int t = 0; t < 4; t++)
            pool.submit(() -> { for (int i = 0; i < 100_000; i++) { counter.incrementAndGet(); adder.increment(); } });
        pool.shutdown(); pool.awaitTermination(10, TimeUnit.SECONDS);
        System.out.println(counter.get() + " " + adder.sum());   // 400000 400000

        // The CAS retry loop that sits behind updateAndGet
        AtomicInteger max = new AtomicInteger(5);
        int candidate = 9, prev;
        do { prev = max.get(); } while (candidate > prev && !max.compareAndSet(prev, candidate));
        System.out.println(max);                                  // 9

}

public class Demo {
    static class Account {
        private final ReentrantLock lock = new ReentrantLock();
        private long balance = 100;

        boolean withdraw(long amt) throws InterruptedException {
            if (!lock.tryLock(200, TimeUnit.MILLISECONDS)) return false;   // avoid waiting forever
            try {                                                         // ALWAYS unlock in finally
                if (balance < amt) return false;
                balance -= amt;
                return true;
            } finally { lock.unlock(); }
        }

    static class Stats {                        // StampedLock optimistic read
        private final StampedLock sl = new StampedLock();
        private double x, y;
        void move(double dx, double dy) { long s = sl.writeLock(); try { x += dx; y += dy; } finally { sl.unlockWrite(s); } }
        double dist() {
            long s = sl.tryOptimisticRead();    // no blocking
            double cx = x, cy = y;
            if (!sl.validate(s)) {              // a writer intervened -> fall back to a real read lock
                s = sl.readLock();
                try { cx = x; cy = y; } finally { sl.unlockRead(s); }
            }
            return Math.sqrt(cx * cx + cy * cy);
        }
    }

    CompletableFuture represents a result that will arrive later and lets you compose steps without blocking: transform, combine, handle errors and set timeouts.

    javaimport java.util.concurrent.*;
import java.util.List;

public class Demo {
    static String fetchUser(int id)   { sleep(100); return "user" + id; }
    static int    fetchScore(String u) { sleep(100); return u.length() * 10; }
    static void   sleep(long ms)       { try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); } }

    public static void main(String[] args) throws Exception {
        ExecutorService io = Executors.newFixedThreadPool(4);       // pass your own pool for blocking work

        CompletableFuture<Integer> pipeline = CompletableFuture
                .supplyAsync(() -> fetchUser(7), io)                 // async step 1
                .thenApplyAsync(Demo::fetchScore, io)                // step 2 uses step 1's result
                .orTimeout(2, TimeUnit.SECONDS)                      // fail if too slow
                .exceptionally(ex -> -1);                            // recover from any failure
        System.out.println("score = " + pipeline.get());             // 50

        // Run independent calls in parallel and combine
        CompletableFuture<String> a = CompletableFuture.supplyAsync(() -> fetchUser(1), io);
        CompletableFuture<String> b = CompletableFuture.supplyAsync(() -> fetchUser(2), io);
        System.out.println(a.thenCombine(b, (x, y) -> x + "+" + y).join());   // user1+user2

        // Wait for a whole list
        List<CompletableFuture<String>> all = List.of(1, 2, 3).stream()
                .map(i -> CompletableFuture.supplyAsync(() -> fetchUser(i), io)).toList();
        CompletableFuture.allOf(all.toArray(new CompletableFuture[0])).join();
        System.out.println(all.stream().map(CompletableFuture::join).toList());

        io.shutdown();
    }
}

    Rules of thumb

    • Write simple blocking code — no need for reactive callbacks to scale.
    • Do not pool virtual threads; use a Semaphore to limit access to scarce resources (DB connections, rate-limited APIs).
    • Virtual threads do not make CPU-bound code faster.
    • Pinning: in Java 21 a virtual thread inside a synchronized block or native call cannot unmount while blocked and holds its carrier (fixed for synchronized in Java 24). Prefer ReentrantLock on Java 21 around blocking calls.
    • Avoid heavy ThreadLocal caches; they are per-thread and there are now millions of threads.
    • Spring Boot 3.2+ / Tomcat / Jetty: enable with spring.threads.virtual.enabled=true.

    🧱 Structured Concurrency & Scoped Values

    Structured concurrency treats a group of related tasks as one unit of work: they start together, finish together, and if one fails the others are cancelled — no leaked threads. In Java 21 it is a preview API (--enable-preview); the API was reshaped in later releases, so check the current JEP before adopting.

    java// Java 21 preview API (compile & run with --enable-preview --release 21)
import java.util.concurrent.*;
import java.util.concurrent.StructuredTaskScope.Subtask;

public class Demo {
    static String user()  throws InterruptedException { Thread.sleep(100); return "Asha"; }
    static int    orders() throws InterruptedException { Thread.sleep(150); return 3; }

    public static void main(String[] args) throws Exception {
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            Subtask<String>  u = scope.fork(Demo::user);        // each fork = a virtual thread
            Subtask<Integer> o = scope.fork(Demo::orders);
            scope.join().throwIfFailed();                       // wait for both; cancel the other if one fails
            System.out.println(u.get() + " has " + o.get() + " orders");
        }
    }
}

    ❌ Unstructured (CompletableFuture / raw threads)

    • Child tasks can outlive the caller
    • Failure of one task does not cancel the rest
    • Thread dumps do not show the parent–child relationship

    ✅ Structured

    • Task lifetime is bound to a lexical scope
    • Automatic cancellation on failure / timeout
    • Easier to reason about and observe

    Scoped values (ScopedValue, finalised in Java 25) share immutable data with child tasks cheaply and safely — a modern replacement for ThreadLocal in virtual-thread code.

    🌿 Fork/Join & Parallel Streams

    Fork/Join splits a CPU-bound problem into smaller subtasks (fork), runs them on a work-stealing pool, and merges results (join). Idle workers steal tasks from busy workers’ queues.

    javaimport java.util.concurrent.*;
import java.util.stream.*;

public class Demo {
    static class SumTask extends RecursiveTask<Long> {
        private static final int THRESHOLD = 10_000;
        private final int[] a; private final int lo, hi;
        SumTask(int[] a, int lo, int hi) { this.a = a; this.lo = lo; this.hi = hi; }
        @Override protected Long compute() {
            if (hi - lo <= THRESHOLD) { long s = 0; for (int i = lo; i < hi; i++) s += a[i]; return s; }
            int mid = (lo + hi) >>> 1;
            SumTask left = new SumTask(a, lo, mid), right = new SumTask(a, mid, hi);
            left.fork();                              // run left asynchronously
            return right.compute() + left.join();    // compute right here, then join
        }
    }
    public static void main(String[] args) {
        int[] data = IntStream.rangeClosed(1, 1_000_000).toArray();
        long fj  = ForkJoinPool.commonPool().invoke(new SumTask(data, 0, data.length));
        long par = IntStream.of(data).parallel().asLongStream().sum();
        System.out.println(fj + " " + par);          // 500000500000 500000500000
    }
}
    ⚠️
    Use parallel streams only for large, CPU-bound, stateless, side-effect-free work. They share the common pool — one blocking task can slow the whole application. Always measure.

    📐 Performance: Scalability, Contention & Amdahl’s Law

    Adding threads rarely gives linear speed-up. Amdahl’s law: if a fraction s of the work is serial, the maximum speed-up with N processors is

    Speedup(N) = 1 / ( s + (1 − s) / N )

    With 10 % serial work (s = 0.1) and 16 cores the speed-up is only ≈ 6.4×, and the limit as N → ∞ is 10×.

    🧭 Design Guidelines for Thread-Safe Code

    1. Share nothing if you can: confine data to one thread.
    2. Make it immutable: final fields, records, List.copyOf.
    3. If shared and mutable: guard every access with the same lock, or use an atomic / concurrent class.
    4. Document thread-safety (@ThreadSafe / @GuardedBy style comments).
    5. Never call alien code while holding a lock.
    6. Always acquire multiple locks in a fixed global order.
    7. Use higher-level tools (executors, queues, CompletableFuture, virtual threads) instead of raw wait/notify.
    8. Handle interruption and shut executors down on exit.

    Interview Preparation: Java Language & Runtime

    ☕ Core Java & Modern Java

    What is the difference between JDK, JRE and JVM?
    JVM runs bytecode (and manages memory, threads, JIT). JRE = JVM + class libraries. JDK = JRE + development tools such as javac, jar, jcmd. Since Java 11 there is no separate JRE download; use jlink for a custom runtime.
    Why is String immutable? What are the benefits?
    Immutability enables the string pool (sharing), caches the hash code, makes strings thread-safe without locks and safe as map keys, and prevents security-sensitive values (class names, file paths) from changing after validation.
    Explain == vs equals() and the equals/hashCode contract.
    == compares primitives by value and objects by reference. equals() compares logical equality. If a.equals(b) then a.hashCode() == b.hashCode() must hold, otherwise hash-based collections malfunction.
    How does HashMap work internally?
    An array of buckets indexed by (n-1) & hash(key). Collisions are chained in a linked list, converted to a red-black tree at 8 nodes (table ≥ 64). It resizes at load factor 0.75, rehashing entries. Not thread-safe; use ConcurrentHashMap.
    Checked vs unchecked exceptions — which would you choose in an API?
    Checked exceptions represent recoverable conditions callers must handle; unchecked represent programming errors. Modern APIs prefer unchecked exceptions with clear documentation, wrapping checked ones with the cause preserved.
    What are records and when would you not use them?
    Records are concise immutable data carriers with generated constructor, accessors, equals, hashCode, toString. Do not use them for mutable entities (e.g. JPA entities), when you need inheritance, or when you need to hide the representation.
    What are sealed classes and pattern matching for switch?
    Sealed types restrict which classes may extend them. A pattern-matching switch over a sealed hierarchy is checked for exhaustiveness at compile time, so you can omit default and get a compile error when a new subtype is added.
    Intermediate vs terminal stream operations?
    Intermediate operations (filter, map, sorted) are lazy and return a stream. A terminal operation (collect, forEach, reduce) triggers the pipeline. A stream can be consumed once.

    🧠 JVM Internals

    Describe the JVM memory areas.
    Heap (objects, shared), Metaspace (class metadata, native memory), per-thread stacks (frames), PC register, native method stack, plus code cache and direct memory.
    What happens when a class is loaded?
    Loading (read bytes, create Class), Linking (verify, prepare static defaults, resolve references), then Initialization (static initialisers run once, thread-safely) — all triggered lazily on first use.
    Explain parent delegation in class loaders.
    A loader asks its parent first (Application → Platform → Bootstrap). Only if the parent cannot find the class does the child load it. This guarantees core classes cannot be replaced.
    StackOverflowError vs OutOfMemoryError?
    StackOverflowError: a thread’s stack is exhausted, usually infinite or very deep recursion. OutOfMemoryError: heap, metaspace, direct memory or native threads exhausted. The message after OOM tells which area.
    How does the JIT compiler work?
    The interpreter profiles code; hot methods are compiled by C1 (quick) and then C2 (aggressive: inlining, escape analysis, loop optimisations). Speculative optimisations are undone (deoptimisation) if assumptions fail. This is why warm-up matters for benchmarks.
    What changed from PermGen to Metaspace?
    PermGen (fixed-size heap area) was removed in Java 8. Class metadata now lives in Metaspace, allocated from native memory and growing on demand, bounded by MaxMetaspaceSize.
    Strong, soft, weak and phantom references?
    Strong references prevent collection. Soft ones are cleared when memory is tight (caches). Weak ones are cleared at the next GC once no strong reference exists. Phantom references enable post-mortem cleanup (Cleaner).

    🧹 Garbage Collection

    How does the JVM decide an object is garbage?
    By reachability from GC roots (thread stacks, static fields, JNI references, class loaders). Anything unreachable is garbage, including cyclic structures. Java does not use reference counting.
    What is the generational hypothesis?
    Most objects die young. So the heap is split into young (Eden + survivors) collected frequently with a cheap copying algorithm, and old generation collected less often.
    Minor vs major vs full GC?
    Minor: young generation only. Major/old: old generation (concurrent in G1/ZGC). Full: the whole heap including metaspace, usually stop-the-world and long; frequent full GCs indicate leaks or a mis-sized heap.
    How does G1 differ from Parallel GC?
    Parallel maximises throughput with long, multi-threaded stop-the-world collections. G1 divides the heap into regions, runs concurrent marking and collects the most garbage-rich regions first to meet a pause-time goal.
    When would you pick ZGC?
    For strict tail latency or very large heaps: pauses are around a millisecond regardless of heap size because marking and relocation are concurrent (coloured pointers + load barriers). Costs: some throughput and extra memory headroom.
    Your service has rising heap after every GC and eventually OOM. What do you do?
    Confirm with GC logs / jstat, take a heap dump (jcmd GC.heap_dump), analyse the dominator tree and paths to GC roots in MAT, fix the retaining reference (static cache, listener, ThreadLocal), then verify with a flat post-GC curve under load.
    What is a humongous object in G1?
    An object larger than half a region. It is allocated in contiguous regions of old space, can fragment the heap and trigger early concurrent cycles. Avoid giant arrays or increase region size.

    🧵 Multithreading

    Process vs thread? Concurrency vs parallelism?
    A process has its own memory; threads share the process heap and have their own stack. Concurrency is structuring work as overlapping tasks; parallelism is executing tasks simultaneously on multiple cores.
    Runnable vs Callable? start() vs run()?
    Runnable.run() returns nothing and cannot throw checked exceptions; Callable.call() returns a value and can throw. start() creates a new thread that calls run(); calling run() directly executes in the current thread.
    Explain the thread lifecycle.
    NEW → RUNNABLE → (BLOCKED | WAITING | TIMED_WAITING) → RUNNABLE → TERMINATED.
    synchronized vs volatile?
    synchronized gives mutual exclusion and visibility. volatile gives visibility and ordering of one variable but no atomicity of compound actions like i++.
    What is a deadlock and how do you prevent it?
    Threads hold locks and wait for each other in a cycle. Prevent by ordering lock acquisition globally, using tryLock with timeouts, holding fewer locks or using lock-free structures. Detect via jstack/jcmd or ThreadMXBean.
    Why must wait() be called in a loop?
    Because of spurious wakeups and because another thread may change the condition before you reacquire the lock; you must re-check the predicate after waking.
    How do you stop a thread safely?
    Cooperatively: use interrupt() and have the task check isInterrupted() / handle InterruptedException, or a volatile flag. Thread.stop() is unsafe and removed.

    ⚙️ Concurrency (java.util.concurrent)

    What is the Java Memory Model and happens-before?
    The JMM specifies when writes by one thread are visible to others. Happens-before edges (lock/unlock, volatile write/read, thread start/join, executor submit/get) guarantee visibility and ordering. Without them, behaviour is undefined for data races.
    ReentrantLock vs synchronized?
    ReentrantLock adds tryLock, timed and interruptible locking, fairness and multiple Conditions, but must be unlocked in finally. synchronized is simpler and automatically released; both are reentrant.
    How does ConcurrentHashMap achieve thread safety?
    Since Java 8 it uses CAS for empty bins and synchronises on the first node of a bin for updates; reads are lock-free. Atomic methods like merge and computeIfAbsent avoid check-then-act races. Null keys/values are not allowed.
    Explain the ThreadPoolExecutor parameters.
    Core size, max size, keep-alive, work queue, thread factory and rejection handler. Order of use: core threads → queue → extra threads up to max → rejection. An unbounded queue means max size is never used.
    Why are Executors.newFixedThreadPool and newCachedThreadPool risky?
    Fixed uses an unbounded queue (memory growth); cached allows unbounded threads. Prefer an explicit ThreadPoolExecutor with a bounded queue, named threads and a rejection policy.
    CountDownLatch vs CyclicBarrier vs Semaphore?
    Latch: one-time wait for N events. Barrier: N threads meet at a point repeatedly. Semaphore: limits concurrent access via permits.
    How do you compose async tasks with CompletableFuture and avoid starving the pool?
    Chain with thenApply/thenCompose/thenCombine, handle errors with exceptionally/handle, set time limits with orTimeout, and supply a dedicated executor for blocking calls instead of the common ForkJoinPool.

    🪶 Virtual Threads & Expert Scenarios

    What problem do virtual threads solve?
    They make the simple thread-per-request model scale. Blocking is cheap because a blocked virtual thread unmounts from its carrier, so millions of concurrent tasks are possible without reactive code.
    When would virtual threads not help?
    CPU-bound work (cores are the limit), code pinned by synchronized around blocking calls on Java 21, or when a downstream resource (DB pool, rate limit) is the bottleneck — limit it with a Semaphore.
    Why should you not pool virtual threads?
    They are cheap, short-lived objects; pooling adds contention and hides the one-thread-per-task benefit. Pool scarce resources, not threads.
    What is structured concurrency?
    Treating concurrent subtasks as a unit with a defined scope: they all finish (or are cancelled) before the scope exits, errors propagate and no threads leak. Available as a preview API since Java 21.
    A service shows high latency but low CPU. How do you investigate?
    Take several thread dumps (jcmd Thread.print) to see where threads wait (locks, I/O, pool queues); check pool queue depth and GC pauses; use JFR for lock contention and socket events; check downstream timeouts and connection pool saturation.
    How would you design a thread-safe, high-throughput cache?
    Use ConcurrentHashMap or Caffeine with bounded size and eviction, use computeIfAbsent to avoid stampedes, keep values immutable, expose metrics, and avoid holding locks while loading values.

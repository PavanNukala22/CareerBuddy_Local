    What is Testing? Concepts, Types and Setup

    Start from zero: what testing is, the types of tests, test doubles, the AAA pattern and how to create a .NET test project.

    🧭 What is Software Testing?

    Software testing is the activity of running your code (or inspecting it) to check that it behaves as expected, and to find defects before your users do. A test is a small piece of code or a procedure with a clear question: "Given this input, does the system produce this result?"

    In .NET, an automated test is simply a C# method, marked with an attribute such as [Fact] or [Test], that a test runner discovers and executes (via dotnet test, Visual Studio Test Explorer, Rider or a CI server).

    🖐️ Manual testing

    A person clicks through the app and checks results. Flexible and good for exploration, but slow, repetitive and hard to repeat exactly.

    🤖 Automated testing

    Code checks code. Runs in seconds, runs on every commit, never gets tired. Best for regression protection.

    Why do developers write tests?

    🐞
    Catch bugs early
    A bug found while coding costs minutes; the same bug in production costs hours or money.
    🛡️
    Safe refactoring
    Change the internals confidently: green tests mean behaviour is preserved.
    📖
    Living documentation
    Tests show exactly how a class is meant to be used.
    🚀
    Faster delivery
    CI pipelines can deploy automatically when the tests pass.

    🗂️ Types of Testing

    Tests are classified in several ways. The most useful for a .NET developer is by scope (how much of the system is involved).

    The test pyramid: write many fast unit tests, fewer integration tests, very few end-to-end tests.
    TypeWhat it checksSpeedTypical .NET tools
    Unit testOne class or method in isolation; collaborators are replaced by test doublesMillisecondsxUnit, NUnit, Moq
    Integration testSeveral real components together (e.g. service + database, API pipeline)SecondsWebApplicationFactory, Testcontainers, EF Core SQLite
    End-to-end (E2E)Whole system through the UI or public APIMany secondsPlaywright, Selenium
    Contract testTwo services agree on request/response shapeSecondsPact.NET
    Performance / load testSpeed and behaviour under loadMinutesBenchmarkDotNet, k6, NBomber
    Smoke testA tiny set of checks that the app starts and key paths workSecondsAny runner with a filter
    Regression testOld behaviour still works after a change (any test that stays in the suite)VariesAll of the above

    Other ways to classify

    ClassificationMeaning
    Black-boxTest only inputs and outputs, without looking at the implementation.
    White-boxTest knowing the internal branches; aim to cover every path.
    Functional vs non-functionalFunctional: what it does. Non-functional: performance, security, usability, reliability.
    State vs interaction testingState: assert on the returned value or object state. Interaction: assert that a collaborator was called (this is where Moq is used).

    🧪 Anatomy of a Good Unit Test

    Every readable unit test follows Arrange – Act – Assert.

    Arrange – Act – Assert (AAA): the standard shape of a readable test.
    C#public class PriceCalculator
{
    public decimal ApplyDiscount(decimal price, int percent)
    {
        if (price < 0) throw new ArgumentOutOfRangeException(nameof(price));
        if (percent is < 0 or > 100) throw new ArgumentOutOfRangeException(nameof(percent));
        return Math.Round(price - price * percent / 100m, 2);
    }
}

// xUnit test
public class PriceCalculatorTests
{
    [Fact]
    public void ApplyDiscount_TenPercentOnHundred_ReturnsNinety()
    {
        // Arrange
        var sut = new PriceCalculator();

        // Act
        var result = sut.ApplyDiscount(100m, 10);

        // Assert
        Assert.Equal(90m, result);
    }
}

    Naming convention used throughout this module: Method_Scenario_ExpectedResult. The SUT (system under test) is the object being tested.

    The FIRST principles

    FastHundreds of tests should run in seconds.
    IsolatedA test never depends on another test, on execution order or on shared mutable state.
    RepeatableSame result on every machine and every run (no real clock, random or network).
    Self-validatingPass or fail automatically; no human reading logs.
    TimelyWritten together with (or before) the production code.

    🎭 Test Doubles: Dummy, Stub, Fake, Spy, Mock

    Real classes often depend on a database, an email service or a payment gateway. In a unit test you replace those dependencies with test doubles. People often say "mock" for all of them, but there are five kinds:

    DoublePurposeExample
    DummyFills a parameter, never usedPassing null or an empty logger
    StubReturns canned answersA repository that always returns customer #5
    FakeWorking but simplified implementationIn-memory repository using a Dictionary
    SpyRecords how it was calledEmail sender that stores sent messages in a list
    MockPre-programmed with expectations and verifies the callsMock<IEmailSender> + Verify(...) (Moq)
    EXAMPLE · Which double?

    A test needs IClock to always say "2025-01-01". That is a stub (it supplies data). A test checks that IEmailSender.Send was called once. That is a mock (it verifies behaviour).

    Q. A hand-written in-memory implementation of IOrderRepository backed by a List is a…
    • A Dummy
    • B Fake
    • C Mock
    • D Integration test

    🔁 TDD and BDD in One Minute

    🔴🟢🔵 TDD

    Red: write a failing test. Green: write the simplest code that passes. Refactor: clean up while tests stay green. Repeat in tiny steps.

    🗣️ BDD

    Describe behaviour in business language (Given / When / Then), often with Gherkin files and tools such as Reqnroll (the community successor to SpecFlow).

    Module 02 · xUnit

    xUnit.net: From First Test to Fixtures

    Facts, Theories, assertions, lifecycle, fixtures, output, parallelism and async tests, each with examples.

    🧭 What is xUnit.net?

    xUnit.net is a free, open-source unit-testing framework for .NET created by the original author of NUnit. It is the default for dotnet new xunit and is used by ASP.NET Core and the .NET runtime repositories.

    🆕
    New instance per test
    Every test method gets a fresh object. No shared state by accident.
    🏗️
    Constructor = setup
    No [SetUp] attribute. Use the constructor and IDisposable.
    🧩
    Fixtures via DI
    IClassFixture<T> injects shared context cleanly.
    ⚡
    Parallel by default
    Test classes run in parallel unless put in the same collection.
    📝
    This module uses the widely-used xUnit v2 API (xunit package). xUnit v3 (xunit.v3) keeps almost the same attributes and assertions; the main differences are in project setup and async lifecycle signatures.

    1️⃣ Your First Tests: [Fact]

    [Fact] marks a test with no parameters that is always true. Any public method with [Fact] in a public class is discovered.

    C#using Xunit;

public class PriceCalculatorTests
{
    private readonly PriceCalculator _sut = new();

    [Fact]
    public void ApplyDiscount_ZeroPercent_ReturnsSamePrice()
    {
        Assert.Equal(250m, _sut.ApplyDiscount(250m, 0));
    }

    [Fact]
    public void ApplyDiscount_NegativePrice_Throws()
    {
        var ex = Assert.Throws<ArgumentOutOfRangeException>(() => _sut.ApplyDiscount(-1m, 10));
        Assert.Equal("price", ex.ParamName);
    }
}
    💡
    The field initialiser _sut = new() runs for every test because xUnit creates a new class instance per test.

    2️⃣ Assert Class: The Everyday Toolbox

    GoalxUnit assertion
    EqualityAssert.Equal(expected, actual), Assert.NotEqual(...)
    Floating pointAssert.Equal(0.3, 0.1 + 0.2, precision: 5)
    BooleanAssert.True(cond), Assert.False(cond)
    NullAssert.Null(x), Assert.NotNull(x)
    ReferenceAssert.Same(a, b), Assert.NotSame(a, b)
    StringsAssert.Contains("ab", s), StartsWith, EndsWith, Matches(regex, s)
    CollectionsAssert.Empty, Assert.Single, Assert.Contains, Assert.All(items, i => ...), Assert.Collection(items, first => ..., second => ...), Assert.Equal(expectedList, actualList)
    RangeAssert.InRange(value, low, high)
    TypesAssert.IsType<T>(obj) (exact), Assert.IsAssignableFrom<T>(obj)
    ExceptionsAssert.Throws<T>(() => ...) (exact type), Assert.ThrowsAny<T> (derived allowed), await Assert.ThrowsAsync<T>(() => ...)
    EventsAssert.Raises<EventArgs>(h => obj.Changed += h, h => obj.Changed -= h, () => obj.Do())
    Fail explicitlyAssert.Fail("reason") (v2.5+)
    C#[Fact]
public void Orders_AreFiltered()
{
    var orders = new[] { new Order(1, 50m), new Order(2, 150m), new Order(3, 300m) };

    var big = orders.Where(o => o.Total > 100m).ToList();

    Assert.Equal(2, big.Count);
    Assert.All(big, o => Assert.True(o.Total > 100m));
    Assert.Collection(big,
        first  => Assert.Equal(2, first.Id),
        second => Assert.Equal(3, second.Id));
}

    📊 Data-Driven Tests: [Theory]

    A Theory runs the same test with different data. Each row is reported as a separate test case.

    InlineData: small constant sets

    C#[Theory]
[InlineData(100, 10, 90)]
[InlineData(200, 50, 100)]
[InlineData(80, 0, 80)]
[InlineData(80, 100, 0)]
public void ApplyDiscount_ReturnsExpected(decimal price, int percent, decimal expected)
{
    Assert.Equal(expected, new PriceCalculator().ApplyDiscount(price, percent));
}

[Theory]
[InlineData(101)]
[InlineData(-1)]
public void ApplyDiscount_InvalidPercent_Throws(int percent)
{
    Assert.Throws<ArgumentOutOfRangeException>(() => new PriceCalculator().ApplyDiscount(10m, percent));
}

    MemberData and TheoryData: complex objects

    C#public static TheoryData<Order, decimal> ShippingCases => new()
{
    { new Order(1, 499m), 49m },   // below free-shipping limit
    { new Order(2, 500m), 0m  },   // free shipping
    { new Order(3, 0m),   0m  },
};

[Theory]
[MemberData(nameof(ShippingCases))]
public void Shipping_IsCalculated(Order order, decimal expected)
{
    Assert.Equal(expected, ShippingCalculator.For(order));
}

    ClassData and custom data attributes: reuse across classes

    C#public class InvalidEmails : TheoryData<string>
{
    public InvalidEmails() { Add(""); Add("   "); Add("no-at-sign"); Add("a@"); }
}

[Theory]
[ClassData(typeof(InvalidEmails))]
public void Validator_RejectsInvalidEmail(string email) =>
    Assert.False(EmailValidator.IsValid(email));
    SourceUse when
    [InlineData]A handful of simple constants (numbers, strings)
    [MemberData]Objects, computed data, shared with other tests
    [ClassData]Large reusable data sets in their own class
    Custom DataAttributeData from JSON/CSV files or a database (override GetData)
    ⚠️
    Only serialisable values (primitives, strings, enums, etc.) appear as separate rows in Test Explorer. Complex objects still run, but may be grouped under one entry.

    🧱 Setup, Teardown and Test Lifecycle

    xUnit has no [SetUp]/[TearDown]. The lifecycle for each test is: constructor → test method → Dispose().

    C#public class TempFileTests : IDisposable
{
    private readonly string _path;

    public TempFileTests()                     // runs BEFORE each test
    {
        _path = Path.GetTempFileName();
    }

    [Fact]
    public void Writes_Text()
    {
        File.WriteAllText(_path, "hello");
        Assert.Equal("hello", File.ReadAllText(_path));
    }

    public void Dispose() => File.Delete(_path);   // runs AFTER each test
}

    Async setup with IAsyncLifetime

    C#public class ApiTests : IAsyncLifetime
{
    private HttpClient _client = default!;

    public async Task InitializeAsync()        // async "setup"
    {
        _client = new HttpClient();
        await Task.Delay(1);
    }

    public Task DisposeAsync()                 // async "teardown" (v2 signature)
    {
        _client.Dispose();
        return Task.CompletedTask;
    }
}

    🤝 Sharing Expensive Setup: Fixtures and Collections

    Some setup is costly (database, web host). Share it with fixtures instead of repeating it per test.

    MechanismShared acrossCreated
    Constructor / DisposeOne testPer test
    IClassFixture<T>All tests in one classOnce per class
    ICollectionFixture<T> + [Collection]All tests in several classesOnce per collection
    C#public class DatabaseFixture : IDisposable
{
    public SqliteConnection Connection { get; }

    public DatabaseFixture()
    {
        Connection = new SqliteConnection("DataSource=:memory:");
        Connection.Open();                      // created once
    }
    public void Dispose() => Connection.Dispose();
}

// 1) Class fixture: injected through the constructor
public class CustomerRepoTests : IClassFixture<DatabaseFixture>
{
    private readonly DatabaseFixture _db;
    public CustomerRepoTests(DatabaseFixture db) => _db = db;
}

// 2) Collection fixture: shared by many classes (and they run sequentially)
[CollectionDefinition("Database")]
public class DatabaseCollection : ICollectionFixture<DatabaseFixture> { }

[Collection("Database")]
public class OrderRepoTests
{
    public OrderRepoTests(DatabaseFixture db) { }
}
    ⚠️
    A fixture is shared, so tests that mutate it can affect each other. Reset data in the constructor of each test class or use transactions/unique data.

    ⚙️ Output, Traits, Skip and Parallelism

    Writing output: ITestOutputHelper

    Console.WriteLine is not captured in xUnit. Inject ITestOutputHelper instead.

    C#public class DiagnosticTests
{
    private readonly ITestOutputHelper _output;
    public DiagnosticTests(ITestOutputHelper output) => _output = output;

    [Fact]
    public void Shows_Output() => _output.WriteLine("Visible in test results");
}

    Traits, Skip and filtering

    C#[Fact, Trait("Category", "Unit")]
public void Fast_Test() { }

[Fact(Skip = "Waiting for bug #4521")]
public void Temporarily_Disabled() { }
    Shelldotnet test --filter "Category=Unit"
dotnet test --filter "Category!=Integration"

    Parallelism rules

    • Tests inside one class/collection run sequentially.
    • Different classes/collections run in parallel.
    • Disable globally if tests share static state:
    C#[assembly: CollectionBehavior(DisableTestParallelization = true)]

    ⏳ Async Tests and Common Mistakes

    C#[Fact]
public async Task GetCustomer_Unknown_ThrowsNotFound()
{
    var sut = new CustomerService(new FakeRepo());

    await Assert.ThrowsAsync<NotFoundException>(() => sut.GetAsync(999));
}
    • Return Task, never async void (the runner cannot await it).
    • Never use .Result or .Wait() in tests; await instead.
    • Assert.Throws must receive a lambda, not the result of calling the method.
    • Do not put if/for logic in assertions; use [Theory].
    Q. How does xUnit give each test a clean state?
    • A [SetUp] runs before each test
    • B It creates a new instance of the test class for every test
    • C It resets static fields automatically
    • D It runs tests in a single thread
    Q. You need a database shared by tests in three different classes. Use…
    • A IClassFixture
    • B Constructor
    • C ICollectionFixture with [Collection]
    • D static fields

    Module 03 · NUnit

    NUnit: Constraints, Data-Driven Tests and Lifecycle

    The constraint model, setup attributes, TestCase / TestCaseSource, combinatorial testing and how NUnit compares with xUnit.

    🧭 What is NUnit?

    NUnit is one of the oldest and most feature-rich .NET test frameworks (a port of JUnit). It is attribute-driven, has a powerful constraint model (Assert.That(actual, Is.EqualTo(expected))) and many built-in tools for data-driven tests.

    Shelldotnet new nunit -n Shop.Core.Tests
# packages: NUnit, NUnit3TestAdapter, Microsoft.NET.Test.Sdk (+ NUnit.Analyzers)
    📝
    NUnit 4 moved the old Assert.AreEqual style into ClassicAssert (namespace NUnit.Framework.Legacy). Prefer the constraint model Assert.That for new code.

    1️⃣ First Tests: [TestFixture] and [Test]

    C#using NUnit.Framework;

[TestFixture]
public class PriceCalculatorTests
{
    private PriceCalculator _sut = null!;

    [SetUp]
    public void SetUp() => _sut = new PriceCalculator();   // runs before EACH test

    [Test]
    public void ApplyDiscount_TenPercentOnHundred_ReturnsNinety()
    {
        var result = _sut.ApplyDiscount(100m, 10);

        Assert.That(result, Is.EqualTo(90m));
    }

    [Test]
    public void ApplyDiscount_NegativePrice_Throws()
    {
        Assert.That(() => _sut.ApplyDiscount(-5m, 10),
                    Throws.TypeOf<ArgumentOutOfRangeException>());
    }
}

    [TestFixture] is optional on non-generic, non-parameterised classes, but it is good documentation.

    🎯 Constraint Model: Assert.That

    Assertions read like English: Assert.That(actual, constraint).

    AreaExamples
    EqualityIs.EqualTo(5), Is.Not.EqualTo(5), Is.EqualTo(0.3).Within(0.0001), Is.EqualTo("ABC").IgnoreCase
    ComparisonIs.GreaterThan(1), Is.LessThanOrEqualTo(10), Is.InRange(1, 10), Is.Positive
    Null / boolIs.Null, Is.Not.Null, Is.True, Is.False
    TypeIs.TypeOf<Dog>(), Is.InstanceOf<Animal>()
    StringsDoes.Contain("x"), Does.StartWith("x"), Does.Match(regex), Is.Empty
    CollectionsHas.Count.EqualTo(3), Does.Contain(x), Is.EquivalentTo(list) (same items, any order), Is.Ordered, Is.Unique, Is.SubsetOf(list), Has.Exactly(2).Matches<int>(n => n > 5), Has.Some.EqualTo(4), Is.All.GreaterThan(0)
    PropertiesHas.Property("Name").EqualTo("Ann")
    ExceptionsThrows.TypeOf<T>(), Throws.InstanceOf<T>(), Throws.Nothing, Throws.ArgumentNullException
    CombineIs.GreaterThan(0).And.LessThan(100), Is.EqualTo(1).Or.EqualTo(2)
    C#[Test]
public void Order_IsCreatedCorrectly()
{
    var order = OrderFactory.Create("C1", 3);

    // All assertions run; every failure is reported (not just the first)
    Assert.Multiple(() =>
    {
        Assert.That(order.CustomerId, Is.EqualTo("C1"));
        Assert.That(order.Lines, Has.Count.EqualTo(3));
        Assert.That(order.Status,  Is.EqualTo(OrderStatus.New));
        Assert.That(order.Total,   Is.GreaterThan(0m));
    });
}
    💡
    Assert.Multiple is great for checking several properties of one object. It avoids the "fix one failure, find the next" loop.

    🧱 Setup, Teardown and Lifecycle

    AttributeRunsTypical use
    [SetUp]Before every test in the fixtureCreate the SUT, reset data
    [TearDown]After every test (even if it failed)Delete temp files
    [OneTimeSetUp]Once before all tests in the fixtureStart a database or host
    [OneTimeTearDown]Once after all tests in the fixtureStop the database
    [SetUpFixture]Once per namespace (or assembly if in the global namespace)Global initialisation
    C#[TestFixture]
public class RepositoryTests
{
    private SqliteConnection _conn = null!;

    [OneTimeSetUp]
    public void OneTimeSetUp() { _conn = new("DataSource=:memory:"); _conn.Open(); }

    [SetUp]
    public async Task SetUp() => await Seeder.ResetAsync(_conn);   // async setup is supported

    [TearDown]
    public void TearDown() =>
        TestContext.WriteLine($"Finished {TestContext.CurrentContext.Test.Name}");

    [OneTimeTearDown]
    public void OneTimeTearDown() => _conn.Dispose();
}
    ⚠️
    Key difference from xUnit: NUnit creates one fixture instance for all tests in the class, so instance fields are shared. Always re-initialise state in [SetUp].

    📊 Data-Driven Tests

    [TestCase]: inline data (with ExpectedResult)

    C#[TestCase(100, 10, ExpectedResult = 90)]
[TestCase(200, 50, ExpectedResult = 100)]
[TestCase(80, 0,   ExpectedResult = 80, TestName = "No discount")]
public decimal ApplyDiscount_Cases(decimal price, int percent)
    => _sut.ApplyDiscount(price, percent);

    [TestCaseSource]: complex data

    C#private static IEnumerable<TestCaseData> ShippingCases()
{
    yield return new TestCaseData(new Order(1, 499m)).Returns(49m).SetName("Below limit");
    yield return new TestCaseData(new Order(2, 500m)).Returns(0m).SetName("Free shipping");
}

[TestCaseSource(nameof(ShippingCases))]
public decimal Shipping(Order order) => ShippingCalculator.For(order);

    [Values], [Range], [Combinatorial] and [Pairwise]: generate combinations

    C#[Test]
public void Combinations(
    [Values("Gold", "Silver")] string tier,
    [Values(1, 5, 10)] int qty)            // 2 x 3 = 6 runs (default is Combinatorial)
{
    Assert.That(Pricing.For(tier, qty), Is.GreaterThan(0));
}

[Test, Pairwise]                            // covers every PAIR of values, fewer runs
public void Pairs([Values("A","B","C")] string a, [Values(1,2,3)] int b, [Values(true,false)] bool c) { }
    AttributeMeaning
    [Values]Explicit list for one parameter
    [Range(1, 5)]Numeric range
    [Random(...)]Random values (use with care: repeatability)
    [Combinatorial]All combinations (default)
    [Sequential]First with first, second with second…
    [Pairwise]Every pair of values at least once (smart reduction)

    🏷️ Control Attributes: Category, Retry, Timeout, Order…

    AttributePurpose
    [Category("Unit")]Group tests; run with dotnet test --filter "TestCategory=Unit" (NUnit adapter maps categories to TestCategory)
    [Ignore("reason")]Skip a test (reason is mandatory)
    [Explicit]Run only when selected explicitly
    [Retry(3)]Re-run up to 3 times on failure (hides flakiness, use sparingly)
    [Repeat(10)]Run 10 times (useful to hunt a race condition)
    [Timeout(2000)]Fail if it runs over 2000 ms
    [Order(1)]Hint order within a fixture (avoid depending on it)
    [Parallelizable(ParallelScope.All)]Allow parallel execution (NUnit is sequential by default)
    [Description] / [Author]Metadata for reports
    Assume.That(cond)Mark the test inconclusive if a precondition is not met
    C#[Test, Category("Unit"), Timeout(1000)]
public async Task GetAsync_ReturnsCustomer()
{
    var sut = new CustomerService(new InMemoryRepo());

    var c = await sut.GetAsync(1);

    Assert.That(c, Is.Not.Null);
    Assert.That(await sut.CountAsync(), Is.EqualTo(1));
}

[Test]
public void Async_Exception()
{
    Assert.ThrowsAsync<NotFoundException>(async () => await new CustomerService(new InMemoryRepo()).GetAsync(999));
}

    Module 04 · Moq

    Moq: Mocking, Setup, Verify and Beyond

    Why we mock, how to program and verify mocks, argument matchers, strict vs loose behaviour, and advanced scenarios.

    🧭 What is Mocking and What is Moq?

    Mocking means replacing a real dependency with a controllable stand-in so you can test one class in isolation. Moq is the most widely used .NET mocking library. It generates the stand-in at runtime from an interface (or a class with virtual members) and lets you setup behaviour and verify calls.

    A mock replaces a dependency: you program it, run the SUT, then verify the interaction.
    Use a mock when…Do NOT mock when…
    The dependency is slow or external (DB, HTTP, email, clock)It is a simple value object or DTO (just create it)
    You must force a failure (timeout, exception) that is hard to produceYou own the type and it is cheap and deterministic (use the real one)
    You want to verify a side-effect happened (email sent)You are writing an integration test (use the real thing)
    Shelldotnet add package Moq

    The class we will test throughout this module:

    C#public interface IPaymentGateway { Task<PaymentResult> ChargeAsync(string customerId, decimal amount); }
public interface IOrderRepository { Task SaveAsync(Order order); Order? Find(int id); }
public interface IEmailSender     { Task SendAsync(string to, string subject, string body); }

public class OrderService
{
    private readonly IPaymentGateway _payments;
    private readonly IOrderRepository _repo;
    private readonly IEmailSender _email;

    public OrderService(IPaymentGateway payments, IOrderRepository repo, IEmailSender email)
        => (_payments, _repo, _email) = (payments, repo, email);

    public async Task<bool> PlaceOrderAsync(Order order)
    {
        var result = await _payments.ChargeAsync(order.CustomerId, order.Total);
        if (!result.Success) return false;

        await _repo.SaveAsync(order);
        await _email.SendAsync(order.CustomerEmail, "Order confirmed", $"Order #{order.Id}");
        return true;
    }
}

    🏗️ Designing for Testability

    Good tests start with good design. Code is easy to test when its dependencies are visible and replaceable.

    🚫 Hard to test

    Creates its own dependencies (new SqlRepo()), reads DateTime.Now, uses static helpers, does I/O inside business logic.

    ✅ Easy to test

    Receives dependencies through the constructor, depends on interfaces, takes time from TimeProvider, keeps pure logic separate from I/O.

    C#// Before: untestable

{
    public bool IsOverdue(Invoice i) => i.DueDate < DateTime.Now;      // hidden dependency on the clock
}

// After: testable with .NET 8 TimeProvider
public class InvoiceService(TimeProvider clock)
{
    public bool IsOverdue(Invoice i) => i.DueDate < clock.GetUtcNow().UtcDateTime;
}

// Test (package: Microsoft.Extensions.TimeProvider.Testing)
[Fact]
public void IsOverdue_AfterDueDate_True()
{
    var time = new FakeTimeProvider(new DateTimeOffset(2025, 1, 10, 0, 0, 0, TimeSpan.Zero));
    var sut  = new InvoiceService(time);
    var inv  = new Invoice { DueDate = new DateTime(2025, 1, 5, 0, 0, 0, DateTimeKind.Utc) };

    Assert.True(sut.IsOverdue(inv));

    time.Advance(TimeSpan.FromDays(-10));      // move the fake clock
    Assert.False(sut.IsOverdue(inv));
}

    Interview Preparation

    Click a question to reveal a model answer. Covers fundamentals, xUnit, NUnit, Moq and senior-level topics.

    🌱 Fundamentals

    What is the difference between unit, integration and E2E tests?
    Unit tests check one class in isolation with dependencies replaced. Integration tests check real components working together (API + DB). E2E tests drive the whole system through the UI. Follow the pyramid: many unit, fewer integration, very few E2E.
    What is AAA?
    Arrange, Act, Assert: set up inputs and dependencies, execute the one behaviour under test, then verify the outcome.
    Stub vs mock vs fake vs spy?
    Stub returns canned data. Mock is pre-programmed and verifies interactions. Fake is a working simplified implementation (in-memory repo). Spy records calls for later inspection. Dummy only fills a parameter.
    What makes a good unit test?
    Fast, isolated, repeatable, self-validating, timely (FIRST); one behaviour per test; clear name; no logic; tests behaviour not implementation.
    What is TDD?
    Red-Green-Refactor: write a failing test, make it pass with the simplest code, refactor with tests green.

    🧪 xUnit and NUnit

    How does xUnit handle setup and teardown?
    Constructor for setup, IDisposable.Dispose for teardown, IAsyncLifetime for async. A new instance of the class is created per test.
    Fact vs Theory?
    [Fact] is a parameterless test that is always true. [Theory] runs once per data row from [InlineData], [MemberData] or [ClassData].
    Class fixture vs collection fixture?
    IClassFixture<T> shares one instance among tests in a single class. ICollectionFixture<T> with [Collection] shares across several classes, which then run sequentially.
    How does xUnit run tests in parallel?
    Test collections run in parallel; tests inside a collection (by default one class) run sequentially. Disable with CollectionBehavior(DisableTestParallelization = true).
    Key differences between NUnit and xUnit?
    NUnit: one instance per fixture, [SetUp]/[OneTimeSetUp], constraint model, Assert.Multiple, rich data attributes, sequential by default. xUnit: new instance per test, constructor setup, fixtures by DI, parallel by default, no [SetUp].
    How do you test that an exception is thrown?
    xUnit: Assert.Throws<T>(() => ...) or await Assert.ThrowsAsync<T>(...). NUnit: Assert.That(() => ..., Throws.TypeOf<T>()) or Assert.ThrowsAsync<T>.
    TestCase vs TestCaseSource vs Pairwise in NUnit?
    TestCase for inline constants, TestCaseSource for objects and computed data, Pairwise to cover every pair of parameter values with fewer runs than all combinations.

    🎭 Moq and Design

    How do you set up and verify with Moq?
    mock.Setup(x => x.Method(args)).Returns(value) to program; pass mock.Object to the SUT; mock.Verify(x => x.Method(args), Times.Once) to check interactions.
    Strict vs Loose mocks?
    Loose (default) returns defaults for un-setup calls. Strict throws on un-setup calls. Strict catches unexpected interactions but makes tests more brittle.
    How do you capture an argument passed to a mock?
    Use Callback<T>(arg => captured = arg) on the setup, or inspect mock.Invocations. Then assert on the captured value.
    Can Moq mock static or sealed classes?
    No. It generates proxies, so only interfaces and virtual/abstract members can be intercepted. Wrap static or sealed dependencies behind an interface.
    How do you test code that uses HttpClient?
    Pass an HttpClient built on a fake HttpMessageHandler (a hand-written stub or a Moq mock with Protected().Setup("SendAsync", ...)).
    When should you NOT use a mock?
    For simple value objects, pure logic, or when the real dependency is cheap and deterministic. Over-mocking couples tests to implementation. Use integration tests for wiring.
    How do you make time-dependent code testable?
    Inject TimeProvider (.NET 8+) or an IClock abstraction and use FakeTimeProvider in tests.

    🚀 Senior-Level Questions

    How do you test an ASP.NET Core API end to end inside a test project?
    WebApplicationFactory<Program> hosts the app in memory, CreateClient() gives an HttpClient, and ConfigureTestServices swaps real services (payment, email) for fakes. Use SQLite or Testcontainers for the database.
    Is 100% code coverage a good goal?
    No. Coverage shows executed lines, not verified behaviour. Aim for meaningful coverage of business logic, use mutation testing (Stryker) to measure assertion strength, and review branches that matter.
    How do you deal with flaky tests?
    Find the non-determinism (time, random, threads, order, shared state, network), inject or isolate it, remove Thread.Sleep, quarantine temporarily with a tracked ticket, and never hide with blind retries.
    How do you structure a large test suite?
    Separate Unit / Integration / E2E projects, tag with Traits or Categories, run unit tests on every commit and integration tests in CI stages, share builders and fixtures, keep names descriptive.
    How do you test private methods?
    You usually do not. Test them through public behaviour. If a private method has complex logic worth testing directly, extract it into its own class.

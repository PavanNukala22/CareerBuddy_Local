    Complexity & Big-O

    Why data structures, algorithms and OOP matter, and how to measure how fast and how big your code grows.

    🧭 What are data structures, algorithms and OOP?

    Every program does two things: it stores data and it works on that data. Computer Science fundamentals give you a vocabulary and a toolkit for doing both well.

    📦
    Data structure
    A way to organise data in memory so that certain operations are fast. Examples: array, hash map, tree, graph.
    ⚙️
    Algorithm
    A finite, step-by-step recipe that turns an input into an output. Examples: binary search, merge sort, Dijkstra.
    🏗️
    Object-oriented programming
    A way to structure code around objects that bundle data (state) with the functions that act on it (behaviour).

    They matter because the same problem can be solved in ways that differ by a factor of a million in speed. Searching 1,000,000 sorted user IDs one by one may take 1,000,000 steps; binary search takes about 20.

    Why it mattersWhat it looks like at work
    PerformanceA page that loads in 50 ms instead of 5 s because a lookup uses a hash map, not a list scan.
    ScalabilityCode that still works when users grow from 1,000 to 10,000,000.
    MaintainabilityWell-designed classes that a teammate can change safely.
    InterviewsMost developer interviews test data structures, algorithms and OOP design directly.
    💡
    You do not need to memorise every algorithm. You need to recognise which tool fits which problem and know its cost.

    📏 Measuring algorithms: time and space

    We cannot judge an algorithm by stopwatch alone — the time depends on the machine, the language and the input. Instead we count how the number of basic steps grows as the input size n grows.

    ⏱️ Time complexity

    How the number of operations grows with n. Answers: how long will this take on a big input?

    💾 Space complexity

    How much extra memory the algorithm needs as n grows (not counting the input itself, usually).

    pythondef total(nums):          # n = len(nums)
    s = 0                 # 1 step, 1 extra variable
    for x in nums:        # loop runs n times
        s += x            # 1 step each time
    return s              # 1 step
# time ~ n + 2 steps  -> O(n)
# extra space: one variable -> O(1)

    We drop constants and smaller terms: 3n + 2 becomes O(n), and n² + 5n becomes O(n²). For large n the biggest term dominates.

    EXAMPLE · Time vs space trade-off

    To check whether a list has duplicates you can compare every pair (O(n²) time, O(1) space) or remember what you have seen in a set (O(n) time, O(n) space). Spending memory to save time is one of the most common trade-offs.

    pythondef has_dup(nums):
    seen = set()
    for x in nums:
        if x in seen:
            return True
        seen.add(x)
    return False

    📈 Big-O classes and how fast they grow

    Big-O notation describes an upper bound on growth. O(n) means: for large inputs, the work grows at most proportionally to n. Here are the classes you will meet most, from fastest to slowest.

    ClassNameTypical example
    O(1)ConstantRead arr[i], look up a key in a hash map (average)
    O(log n)LogarithmicBinary search, balanced BST lookup
    O(n)LinearScan a list once, sum an array
    O(n log n)LinearithmicMerge sort, heap sort, Python's sorted()
    O(n²)QuadraticCompare every pair, bubble sort
    O(2ⁿ)ExponentialGenerate all subsets, naive recursive Fibonacci
    O(n!)FactorialGenerate all permutations, brute-force travelling salesman

    A typical machine does roughly 10⁸–10⁹ simple operations per second. So O(n²) with n = 1,000,000 (10¹² steps) takes many minutes, while O(n log n) finishes in well under a second.
    💡
    Logs in Big-O are usually base 2, but the base does not matter: log₂ n and log₁₀ n differ only by a constant factor.

    🎲 Best, average and worst case

    The same algorithm can take different amounts of work on different inputs of the same size. We describe three cases:

    CaseMeaningLinear search for x in n items
    Best caseThe luckiest inputx is the first item → O(1)
    Average caseExpected work over typical inputsx is somewhere in the middle → about n/2 checks → O(n)
    Worst caseThe unluckiest inputx is last or missing → n checks → O(n)

    When people say "the complexity is …" without qualification they usually mean the worst case, because it is a guarantee. Some well-known exceptions are quoted by average case:

    Algorithm / structureAverageWorstWhy the worst case happens
    Hash map lookupO(1)O(n)Many keys collide into the same bucket
    Quick sortO(n log n)O(n²)Bad pivots, e.g. always the smallest element on sorted input
    Unbalanced BST searchO(log n)O(n)Inserting sorted data turns the tree into a linked list
    Big-O (O)Upper bound: grows no faster than this.
    Big-Omega (Ω)Lower bound: grows at least this fast.
    Big-Theta (Θ)Tight bound: grows exactly at this rate (both O and Ω).
    📝
    In everyday developer speech, "Big-O" is often used loosely to mean the tight bound. In interviews, saying "O(n) worst case, O(1) best case" shows precision.

    ♻️ Amortised analysis: the dynamic array

    Some operations are usually cheap but occasionally expensive. Amortised analysis averages the cost over a long sequence of operations — it is a guarantee about the total, not a probability.

    A Python list or Java ArrayList is a dynamic array. It keeps spare capacity. When it is full, append allocates a bigger block (typically 1.5×–2× larger) and copies every element across.

    Append #Capacity beforeCopies needed
    11 (empty slot)0
    21 → grows to 21
    32 → grows to 42
    440
    54 → grows to 84
    6–880
    98 → grows to 168

    With doubling, the copies over n appends add up to at most 1 + 2 + 4 + … < 2n. So n appends cost O(n) in total, which is amortised O(1) per append, even though one single append can cost O(n).

    pythonimport sys
a = []
for i in range(10):
    a.append(i)
    print(len(a), sys.getsizeof(a))   # size in bytes jumps only now and then
    ⚠️
    Amortised O(1) is not the same as average-case O(1). Average case depends on the input distribution; amortised cost is guaranteed over any sequence of operations.

    🔍 Deriving Big-O from code

    You can usually read complexity straight from the shape of the code. Follow these rules:

    1. Simple statements (assignment, arithmetic, index access) are O(1).
    2. A loop that runs n times over an O(1) body is O(n).
    3. Nested loops multiply: n × n = O(n²).
    4. Sequential blocks add, and the bigger term wins: O(n) + O(n²) = O(n²).
    5. A loop that halves (or doubles) its variable each time is O(log n).
    6. Different inputs get different letters: looping over a and then over b is O(a + b); nested is O(a × b).
    python# O(n): one pass
for x in nums:
    print(x)

# O(n^2): every pair
for i in range(n):
    for j in range(n):
        print(i, j)

# Still O(n^2): the inner loop runs n-1, n-2, ... 1 times = n(n-1)/2
for i in range(n):
    for j in range(i + 1, n):
        print(i, j)

# O(log n): i halves each time
i = n
while i > 1:
    i //= 2

# O(n log n): n iterations, each doing O(log n) work
for x in nums:
    j = 1
    while j < n:
        j *= 2
    EXAMPLE · Hidden costs

    Watch out for library calls inside loops. if x in my_list is O(n), so putting it inside a loop over n items makes the whole thing O(n²). Changing my_list to a set makes each check O(1) on average and the loop O(n).

    For recursive code, ask two questions: how many calls are made in total, and how much work does each call do? Binary search makes one call on half the input → O(log n). Naive Fibonacci makes two calls per level → about O(2ⁿ).

    Linear Data Structures

    Arrays, strings, linked lists, stacks, queues, hash tables and sets — how they work, what they cost and when to use each.

    📦 Arrays and dynamic arrays

    An array stores elements in one contiguous block of memory. Because every slot has the same size, the address of element i is simply start + i × size — so reading any index is O(1). This is called random access.

    A fixed-size array (Java int[]) cannot grow. A dynamic array (Python list, Java ArrayList, C++ vector) grows by allocating a larger block and copying, as you saw in Module 01.

    OperationDynamic arrayWhy
    Read / write by indexO(1)Address is computed directly
    Append at endO(1) amortisedOccasional resize copies everything
    Insert / delete at front or middleO(n)Later elements must shift by one
    Remove from end (pop())O(1)Nothing shifts
    Search unsortedO(n)Must check each element
    Search sorted (binary search)O(log n)Halve the range each step
    pythonnums = [10, 20, 30]
nums.append(40)        # [10, 20, 30, 40]   O(1) amortised
nums.insert(0, 5)      # [5, 10, 20, 30, 40] O(n) - everything shifts right
x = nums[2]            # 20                 O(1)
nums.pop()             # removes 40          O(1)
nums.pop(0)            # removes 5           O(n)

    javaint[] fixed = new int[5];               // size fixed at 5, all zeros
List<Integer> list = new ArrayList<>();  // dynamic
list.add(10);                            // append
list.add(0, 5);                          // insert at index 0 -> shift, O(n)
int first = list.get(0);                 // 5, O(1)
    💡
    Arrays are also cache-friendly: neighbouring elements sit next to each other in memory, so CPUs read them very quickly. This often makes arrays faster in practice than structures with the same Big-O.

    🔤 Strings

    A string is a sequence of characters — essentially an array of characters. In both Python and Java, strings are immutable: every "change" creates a new string.

    That makes repeated concatenation in a loop a classic performance trap. Each s = s + piece may copy the whole string so far, giving O(n²) total work for n pieces.

    ❌ Slow pattern

    pythons = ""
for word in words:

    ✅ Fast pattern

    pythons = ",".join(words)     # one pass, O(total length)

    sb.append(w).append(',');   // amortised O(1) per append
}

    🔗 Linked lists

    A linked list stores each element in a separate node. Each node holds a value and a pointer (reference) to the next node. Nodes can live anywhere in memory, so there is no random access — to reach the 5th node you must walk from the head.

    Singly linked

    Each node has next. You can only walk forwards. Uses less memory.

    Doubly linked

    Each node has next and prev. You can walk both ways and delete a node in O(1) if you hold a reference to it.

    pythonclass Node:
    def __init__(self, val, next=None):
        self.val = val
        self.next = next

# build 1 -> 2 -> 3
head = Node(1, Node(2, Node(3)))

def print_list(head):
    cur = head
    while cur:
        print(cur.val, end=" ")
        cur = cur.next
# print_list(head) -> 1 2 3

def push_front(head, val):
    return Node(val, head)      # O(1): new node points at old head

    javaclass Node {
    int val;

}
// Java's built-in LinkedList<E> is a doubly linked list
LinkedList<Integer> ll = new LinkedList<>();

    EXAMPLE · Valid parentheses

    Push every opening bracket; on a closing bracket, the top of the stack must be its partner.

    pythondef is_valid(s):
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    for ch in s:
        if ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
        else:
            stack.append(ch)
    return not stack

    🚶 Queues and deques (FIFO)

    A queue is First In, First Out: like a line at a shop, you add at the back (enqueue) and remove from the front (dequeue). A deque (double-ended queue, pronounced "deck") allows O(1) add and remove at both ends.

    pythonfrom collections import deque

q = deque()
q.append("job1")       # enqueue at the back
q.append("job2")
first = q.popleft()    # dequeue from the front -> "job1"   O(1)

d = deque([1, 2, 3])
d.appendleft(0)        # [0, 1, 2, 3]
d.pop()                # removes 3

    javaQueue<String> q = new ArrayDeque<>();
q.offer("job1");          // enqueue
q.offer("job2");
String first = q.poll();  // "job1" (returns null if empty)

Deque<Integer> d = new ArrayDeque<>();
d.offerFirst(0);
d.offerLast(9);

    #️⃣ Hash tables

    A hash table (Python dict, Java HashMap) maps keys to values with average O(1) insert, lookup and delete. It uses a hash function to turn a key into a number, then uses hash(key) % capacity to choose a bucket in an underlying array.

    How a hash table finds a value

    Collisions

    Two different keys can land in the same bucket — a collision. There are two classic fixes:

    StrategyHow it worksUsed by
    Separate chainingEach bucket holds a small list (or tree) of entriesJava HashMap (lists that become trees when a bucket gets large)
    Open addressingOn collision, probe other slots (linear, quadratic, double hashing) until a free one is foundPython dict

    The load factor = entries ÷ buckets. When it passes a threshold (0.75 in Java's HashMap), the table grows and rehashes every entry. Keeping the load factor low keeps chains short and lookups O(1) on average. If many keys collide, operations degrade towards O(n).

    pythoncounts = {}
for word in ["a", "b", "a", "c", "a"]:
    counts[word] = counts.get(word, 0) + 1
print(counts)            # {'a': 3, 'b': 1, 'c': 1}
print("b" in counts)     # True, O(1) average

    javaMap<String, Integer> counts = new HashMap<>();
for (String w : new String[]{"a", "b", "a"}) {
    counts.merge(w, 1, Integer::sum);
}
// counts -> {a=2, b=1}
    ⚠️
    Keys must be immutable (or at least never change while stored). In Python, lists cannot be dict keys; use tuples. In Java, if you override equals() you must override hashCode() so equal objects hash the same.

    🌲 Binary tree traversals

    A traversal visits every node once. The three depth-first orders differ only in when you visit the current node relative to its children.

    pythonclass TreeNode:

def preorder(node):            # Node, Left, Right
    if node:
        print(node.val, end=" ")
        preorder(node.left)
        preorder(node.right)

    if node:

        print(node.val, end=" ")
        inorder(node.right)

def postorder(node):           # Left, Right, Node
    if node:
        postorder(node.left)
        postorder(node.right)
        print(node.val, end=" ")

from collections import deque
def level_order(root):         # breadth-first, level by level
    q = deque([root] if root else [])

        node = q.popleft()
        print(node.val, end=" ")
        if node.left:
            q.append(node.left)
        if node.right:
            q.append(node.right)

    🔎 Binary search trees and balance

    A binary search tree (BST) keeps an ordering rule at every node: all values in the left subtree are smaller, all values in the right subtree are larger. The example tree above is a BST, which is why its in-order traversal comes out sorted.

    pythondef search(node, target):
    while node:
        if target == node.val:
            return node
        node = node.left if target < node.val else node.right
    return None

def insert(node, val):
    if node is None:
        return TreeNode(val)
    if val < node.val:
        node.left = insert(node.left, val)
    elif val > node.val:
        node.right = insert(node.right, val)
    return node          # duplicates ignored

    Deleting has three cases: a leaf (just remove it), a node with one child (link the child to the parent), and a node with two children (replace its value with its in-order successor — the smallest value in the right subtree — then delete that successor).

    🔤 Tries (prefix trees)

    A trie stores strings character by character along paths from the root. Words that share a prefix share nodes. Lookup and insert cost O(L) where L is the word length — independent of how many words are stored.

    pythonclass TrieNode:
    def __init__(self):
        self.children = {}
        self.is_word = False

class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word):
        node = self.root
        for ch in word:
            node = node.children.setdefault(ch, TrieNode())
        node.is_word = True

    def contains(self, word):
        node = self._walk(word)
        return node is not None and node.is_word

    def starts_with(self, prefix):
        return self._walk(prefix) is not None

    def _walk(self, s):
        node = self.root
        for ch in s:
            node = node.children.get(ch)
            if node is None:
                return None
        return node

    🚶 Breadth-first and depth-first search

    BFS explores level by level using a queue. DFS goes as deep as possible along one path before backtracking, using recursion or a stack. Both are O(V + E) with an adjacency list. Always keep a visited set so cycles do not cause infinite loops.

    pythonfrom collections import deque

def bfs(graph, start):
    visited = {start}
    order = []
    q = deque([start])
    while q:
        u = q.popleft()
        order.append(u)
        for v in graph[u]:
            if v not in visited:
                visited.add(v)        # mark when enqueued
                q.append(v)
    return order

def dfs(graph, u, visited=None, order=None):
    if visited is None:
        visited, order = set(), []
    visited.add(u)
    order.append(u)
    for v in graph[u]:
        if v not in visited:
            dfs(graph, v, visited, order)
    return order

    🗺️ Topological sort and shortest paths

    Topological sort

    For a DAG, a topological order lists every vertex before all vertices it points to — e.g. the order to run build steps or take courses with prerequisites. Kahn's algorithm repeatedly takes vertices with no remaining incoming edges.

    pythonfrom collections import deque

def topo_sort(graph):
    indeg = {u: 0 for u in graph}
    for u in graph:
        for v in graph[u]:
            indeg[v] += 1
    q = deque([u for u in graph if indeg[u] == 0])
    order = []
    while q:
        u = q.popleft()
        order.append(u)
        for v in graph[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)
    if len(order) != len(graph):
        raise ValueError("graph has a cycle")
    return order

topo_sort(graph)   # ['A', 'B', 'C', 'D', 'E', 'F']

    Shortest paths: Dijkstra's algorithm

    For weighted graphs with non-negative edge weights, Dijkstra always expands the unvisited vertex with the smallest known distance, using a min-heap.

    pythonimport heapq

def dijkstra(graph, src):
    dist = {u: float("inf") for u in graph}
    dist[src] = 0
    pq = [(0, src)]
    while pq:
        d, u = heapq.heappop(pq)
        if d > dist[u]:
            continue                  # stale entry, already improved
        for v, w in graph[u]:
            if d + w < dist[v]:
                dist[v] = d + w
                heapq.heappush(pq, (dist[v], v))
    return dist

    🔍 Linear search vs binary search

    Linear search checks items one by one: O(n), works on any list. Binary search works only on sorted data: compare with the middle item, then throw away the half that cannot contain the target. Each step halves the range, so it takes O(log n) — about 20 comparisons for a million items.

    pythondef linear_search(arr, target):
    for i, x in enumerate(arr):
        if x == target:
            return i
    return -1

def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1          # inclusive range [lo, hi]
    while lo <= hi:                   # <= so a 1-element range is checked
        mid = (lo + hi) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            lo = mid + 1              # target is to the right
        else:
            hi = mid - 1              # target is to the left
    return -1

binary_search([1, 3, 5, 7, 9, 11], 7)   # 3
binary_search([1, 3, 5, 7, 9, 11], 4)   # -1

    🫧 Simple sorts: bubble, selection, insertion

    These three are O(n²) in general, but they are easy to understand and teach the core ideas. Insertion sort is genuinely useful for small or nearly sorted arrays.

    pythondef bubble_sort(a):
    n = len(a)
    for i in range(n - 1):
        swapped = False
        for j in range(n - 1 - i):        # largest values "bubble" to the end
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
                swapped = True
        if not swapped:                   # already sorted -> O(n) best case
            break

def selection_sort(a):
    n = len(a)
    for i in range(n - 1):
        m = i
        for j in range(i + 1, n):         # find the minimum of the rest
            if a[j] < a[m]:
                m = j
        a[i], a[m] = a[m], a[i]           # put it in position i

def insertion_sort(a):
    for i in range(1, len(a)):
        key = a[i]
        j = i - 1
        while j >= 0 and a[j] > key:      # shift bigger items right
            a[j + 1] = a[j]
            j -= 1
        a[j + 1] = key

    🔀 Merge sort

    Merge sort is divide and conquer: split the array in half, sort each half recursively, then merge the two sorted halves. There are log n levels of splitting and each level does O(n) merging work, so it is O(n log n) in every case.

    pythondef merge_sort(a):
    if len(a) <= 1:
        return a
    mid = len(a) // 2
    left = merge_sort(a[:mid])
    right = merge_sort(a[mid:])
    return merge(left, right)

def merge(left, right):
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:       # <= keeps equal items in order -> stable
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:])
    out.extend(right[j:])
    return out

merge_sort([38, 27, 43, 3, 9, 82, 10])   # [3, 9, 10, 27, 38, 43, 82]

    ⚡ Quick sort

    Quick sort picks a pivot, partitions the array so smaller items go left and larger items go right, then recursively sorts each side. It sorts in place and is very fast in practice.

    pythonimport random

def quick_sort(a, lo=0, hi=None):
    if hi is None:
        hi = len(a) - 1
    if lo < hi:
        p = partition(a, lo, hi)
        quick_sort(a, lo, p - 1)
        quick_sort(a, p + 1, hi)

def partition(a, lo, hi):                 # Lomuto scheme
    r = random.randint(lo, hi)            # random pivot avoids the sorted-input trap
    a[r], a[hi] = a[hi], a[r]
    pivot = a[hi]
    i = lo                                # a[lo:i] holds items < pivot
    for j in range(lo, hi):
        if a[j] < pivot:
            a[i], a[j] = a[j], a[i]
            i += 1
    a[i], a[hi] = a[hi], a[i]             # pivot to its final place
    return i

    ⛰️ Heap sort and counting sort

    Heap sort

    Build a max-heap from the array (O(n)), then repeatedly swap the root (the maximum) to the end and sift down the rest. O(n log n) in every case, O(1) extra space, but not stable.

    pythondef heap_sort(a):
    n = len(a)

    def sift_down(i, size):
        while True:
            largest, l, r = i, 2 * i + 1, 2 * i + 2
            if l < size and a[l] > a[largest]:
                largest = l
            if r < size and a[r] > a[largest]:
                largest = r
            if largest == i:
                return
            a[i], a[largest] = a[largest], a[i]
            i = largest

    for i in range(n // 2 - 1, -1, -1):   # build max-heap
        sift_down(i, n)
    for end in range(n - 1, 0, -1):       # move max to the end
        a[0], a[end] = a[end], a[0]
        sift_down(0, end)

    Counting sort

    Comparison sorts cannot beat O(n log n) in the worst case. Counting sort avoids comparisons: when keys are small integers in a range 0..k, count each value, then write them out. Time and space are O(n + k).

    pythondef counting_sort(nums, k):          # values in 0..k
    count = [0] * (k + 1)
    for x in nums:
        count[x] += 1
    out = []
    for value, times in enumerate(count):
        out.extend([value] * times)
    return out

counting_sort([3, 0, 2, 3, 1], 3)   # [0, 1, 2, 3, 3]
    📝
    Counting sort is great for ages (0–150), exam scores (0–100) or ratings (1–5). It is a poor choice when k is huge compared with n — sorting 10 numbers up to 1,000,000,000 would need a billion counters. Radix sort extends the idea digit by digit.

    🔁 Recursion, base cases and the call stack

    A recursive function solves a problem by calling itself on a smaller version of the same problem. Every recursive function needs:

    1. A base case that returns directly without recursing.
    2. A recursive case that moves strictly closer to the base case.
    pythondef factorial(n):
    if n <= 1:            # base case
        return 1
    return n * factorial(n - 1)   # recursive case: smaller n

factorial(3)   # 6
    EXAMPLE · What the call stack looks like for factorial(3)
    StepCall stack (top last)Note
    1factorial(3)waits for factorial(2)

    3factorial(3) → factorial(2) → factorial(1)base case returns 1

    Each call adds a stack frame holding its local variables, so recursion depth d costs O(d) memory. Missing or unreachable base cases cause infinite recursion and a stack overflow (RecursionError in Python, StackOverflowError in Java).

    ⚠️
    Python's default recursion limit is about 1,000 frames and Python does not optimise tail calls. For very deep problems (e.g. DFS on a 100,000-node chain) convert recursion to a loop with an explicit stack.
    💡
    To design recursion, trust the "leap of faith": assume the function already works for smaller inputs, and only write how to combine those answers.

    👉 Two pointers and sliding window

    Two pointers

    Use two indexes that move toward each other or in the same direction, replacing a nested loop with a single pass. It works especially well on sorted arrays and strings.

    pythondef pair_with_sum(sorted_nums, target):
    lo, hi = 0, len(sorted_nums) - 1
    while lo < hi:
        s = sorted_nums[lo] + sorted_nums[hi]
        if s == target:
            return lo, hi
        if s < target:
            lo += 1          # need a bigger sum
        else:
            hi -= 1          # need a smaller sum
    return None

pair_with_sum([1, 2, 4, 7, 11], 15)   # (2, 4) -> 4 + 11

def is_palindrome(s):
    i, j = 0, len(s) - 1
    while i < j:
        if s[i] != s[j]:
            return False
        i += 1
        j -= 1
    return True

    Sliding window

    Keep a window [left, right] over a contiguous part of an array or string. Extend the right edge, and shrink the left edge when a rule is broken. Each element enters and leaves the window at most once → O(n).

    pythondef max_sum_k(nums, k):                    # fixed-size window
    window = sum(nums[:k])
    best = window
    for i in range(k, len(nums)):
        window += nums[i] - nums[i - k]    # add new, drop old
        best = max(best, window)
    return best

max_sum_k([2, 1, 5, 1, 3, 2], 3)   # 9  (5 + 1 + 3)

def longest_unique(s):                     # variable-size window
    last = {}
    start = best = 0
    for i, ch in enumerate(s):
        if ch in last and last[ch] >= start:
            start = last[ch] + 1           # jump past the repeat
        last[ch] = i
        best = max(best, i - start + 1)
    return best

    Prefix sums

    Precompute running totals once in O(n); then any range sum is a subtraction in O(1).

    pythonnums = [3, 1, 4, 1, 5]
prefix = [0]
for x in nums:
    prefix.append(prefix[-1] + x)      # [0, 3, 4, 8, 9, 14]

def range_sum(i, j):                   # sum of nums[i..j] inclusive
    return prefix[j + 1] - prefix[i]

range_sum(1, 3)   # 1 + 4 + 1 = 6

    Hashing for lookups

    Many O(n²) "search for a partner" problems become O(n) by storing what you have seen in a hash map.

    pythondef two_sum(nums, target):
    seen = {}                          # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:
            return [seen[target - x], i]
        seen[x] = i
    return []

two_sum([2, 7, 11, 15], 9)   # [0, 1]

# prefix sums + hashing: count subarrays that sum to k
def count_subarrays(nums, k):
    seen = {0: 1}                      # prefix sum -> how many times
    total = count = 0
    for x in nums:
        total += x
        count += seen.get(total - k, 0)
        seen[total] = seen.get(total, 0) + 1
    return count

count_subarrays([1, 1, 1], 2)   # 2

    ✂️ Divide and conquer

    Divide and conquer splits a problem into independent sub-problems, solves them (usually recursively), and combines the results. Merge sort, quick sort and binary search all follow this pattern.

    The three steps of divide and conquer
    pythondef power(x, n):                 # x ** n in O(log n) multiplications
    if n == 0:
        return 1
    half = power(x, n // 2)
    if n % 2 == 0:
        return half * half
    return half * half * x

    🤑 Greedy algorithms and when they fail

    A greedy algorithm makes the locally best choice at each step and never reconsiders. It is fast and simple — but only correct when the problem has the greedy-choice property (a local best choice is always part of some optimal solution).

    EXAMPLE · Interval scheduling: greedy works

    Choose the maximum number of non-overlapping meetings. Greedy rule: always pick the meeting that ends earliest.

    pythondef max_meetings(intervals):
    intervals.sort(key=lambda m: m[1])     # by end time
    count, end = 0, float("-inf")
    for start, finish in intervals:
        if start >= end:
            count += 1
            end = finish
    return count

max_meetings([(1, 3), (2, 4), (3, 5), (6, 7)])   # 3
    EXAMPLE · Coin change: greedy can fail

    Coins [1, 3, 4], amount 6. Greedy takes the biggest coin first: 4 + 1 + 1 = 3 coins. The optimal answer is 3 + 3 = 2 coins. Greedy happens to work for standard currency systems like 1, 5, 10, 25 but not for arbitrary coins — use dynamic programming instead.

    🧮 Dynamic programming

    Dynamic programming (DP) solves problems with overlapping sub-problems and optimal substructure by solving each sub-problem once and storing the answer.

    Naive recursive Fibonacci recomputes fib(3), fib(2) … many times — about O(2ⁿ) calls. Storing results makes it O(n).

    Memoisation (top-down)

    pythonfrom functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

fib(50)   # 12586269025

    Tabulation (bottom-up)

    pythondef fib(n):
    if n < 2:
        return n
    prev, cur = 0, 1
    for _ in range(2, n + 1):
        prev, cur = cur, prev + cur
    return cur          # O(n) time, O(1) space
    EXAMPLE · Climbing stairs

    You can climb 1 or 2 steps at a time. How many ways to reach step n? The last move was either 1 step (from n − 1) or 2 steps (from n − 2), so ways(n) = ways(n-1) + ways(n-2), with ways(1) = 1 and ways(2) = 2. For n = 5: 1, 2, 3, 5, 8.

    EXAMPLE · Coin change (minimum coins)
    pythondef coin_change(coins, amount):
    INF = float("inf")
    dp = [0] + [INF] * amount          # dp[a] = fewest coins for amount a
    for a in range(1, amount + 1):
        for coin in coins:
            if coin <= a and dp[a - coin] + 1 < dp[a]:
                dp[a] = dp[a - coin] + 1
    return dp[amount] if dp[amount] != INF else -1

coin_change([1, 3, 4], 6)   # 2  (3 + 3)
coin_change([2], 3)         # -1 (impossible)
# time O(amount x len(coins)), space O(amount)

    🔙 Backtracking

    Backtracking builds candidates step by step and undoes the last choice when it leads nowhere. It explores a tree of choices with DFS: choose → explore → un-choose. Use it to generate all subsets, permutations or combinations, and for puzzles like N-Queens and Sudoku.

    pythondef subsets(nums):
    res, path = [], []
    def backtrack(start):
        res.append(path[:])            # record a copy of the current subset
        for i in range(start, len(nums)):
            path.append(nums[i])       # choose
            backtrack(i + 1)           # explore
            path.pop()                 # un-choose
    backtrack(0)
    return res

subsets([1, 2, 3])
# [[], [1], [1, 2], [1, 2, 3], [1, 3], [2], [2, 3], [3]]

def permutations(nums):
    res, path, used = [], [], [False] * len(nums)
    def backtrack():
        if len(path) == len(nums):
            res.append(path[:])
            return
        for i in range(len(nums)):
            if used[i]:
                continue
            used[i] = True
            path.append(nums[i])
            backtrack()
            path.pop()
            used[i] = False
    backtrack()
    return res

len(permutations([1, 2, 3]))   # 6

    All subsets of n items2ⁿO(n · 2ⁿ)
    All permutations of n itemsn!O(n · n!)
    Combinations choose k of nC(n, k)O(k · C(n, k))
    ⚠️
    Append a copy (path[:]) to the results. Appending path itself stores a reference that later becomes empty after all the pops.
    💡
    Pruning — stopping early when a partial candidate cannot succeed — is what makes backtracking practical (e.g. stop adding numbers once a running sum exceeds the target).

    SOLID & Design Patterns

    Principles and proven patterns for code that is easy to change, test and extend — plus the anti-patterns to avoid.

    🧭 Principles that keep code healthy

    Good design is about making change cheap. Requirements will change; well-designed code lets you change one place without breaking ten others.

    🔁
    DRY — Don't Repeat Yourself
    Every piece of knowledge should live in one place. Duplicate business rules drift apart and cause bugs.
    💋
    KISS — Keep It Simple
    Prefer the simplest design that works. Clever code is harder to read, test and debug.
    🙅
    YAGNI — You Aren't Gonna Need It
    Do not build features or abstractions "just in case". Add them when a real need appears.

    Coupling and cohesion

    ConceptMeaningAim for
    CouplingHow much one module depends on the internals of anotherLow — modules talk through small, stable interfaces
    CohesionHow closely the responsibilities inside one module belong togetherHigh — a class does one focused job
    EXAMPLE · Spotting the difference

    A ReportService that formats PDFs, queries the database, sends emails and parses CSVs has low cohesion. If a CheckoutService reads cart._items directly instead of calling cart.total(), the two are tightly coupled: changing the cart's internals breaks checkout.

    ⚠️
    DRY is about duplicated knowledge, not similar-looking lines. Forcing two unrelated pieces of code to share an abstraction just because they look alike creates coupling that hurts later.

    📏 Complexity

    What is Big-O notation, and why do we drop constants and smaller terms?

    Big-O describes how an algorithm's cost grows as the input size n grows, as an upper bound. We drop constants and lower-order terms because for large n they stop mattering: 3n² + 100n + 7 is dominated by n². Big-O lets us compare algorithms independently of hardware and language. Constants still matter in practice for small inputs, so I would also measure real performance when it counts.

    What is the difference between time and space complexity? Give a trade-off.

    Time complexity is how the number of operations grows; space complexity is how the extra memory grows. A classic trade-off is duplicate detection: comparing all pairs is O(n²) time and O(1) space, while a hash set is O(n) time and O(n) space. Caching and memoisation are the same idea: spend memory to save time.

    Explain amortised complexity using a dynamic array.

    A dynamic array appends into spare capacity in O(1). When full, it allocates a bigger array (e.g. double) and copies everything — O(n) for that one append. Because capacity doubles, total copying over n appends is less than 2n, so n appends cost O(n) overall: amortised O(1) each. This is a guarantee over any sequence, not an average over random inputs.

    What is the time complexity of each snippet?
    python# A
for i in range(n):
    j = 1
    while j < n:
        j *= 2

# B
i = n
while i > 0:
    for _ in range(i):
        pass
    i //= 2

    A is O(n log n): n outer iterations, each with a doubling inner loop of about log n steps. B is O(n), not O(n log n): the inner work is n + n/2 + n/4 + … which sums to less than 2n.

    Is an O(log n) algorithm always faster than an O(n) one?

    No. Big-O describes growth for large n and hides constant factors. For small inputs, a simple O(n) scan over a cache-friendly array can beat an O(log n) tree lookup that chases pointers. That is why libraries use insertion sort for tiny sub-arrays inside O(n log n) sorts. For large n, the better growth rate wins.

    📦 Data structures

    Array vs linked list — when would you choose each?

    Arrays give O(1) index access and excellent cache locality, but inserting or deleting in the middle is O(n). Linked lists give O(1) insert/delete at a known node but O(n) access by index and extra pointer memory. I default to a dynamic array, and choose a linked list when I frequently splice nodes I already hold, such as the recency list inside an LRU cache.

    Reverse a singly linked list.
    pythondef reverse(head):
    prev, cur = None, head
    while cur:
        nxt = cur.next      # remember the rest
        cur.next = prev     # flip the pointer
        prev, cur = cur, nxt
    return prev             # new head

    O(n) time, O(1) space. The key is saving cur.next before overwriting it.

    How do you detect a cycle in a linked list?
    pythondef has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:
            return True
    return False

    Floyd's tortoise-and-hare: the fast pointer moves two steps, the slow one step. If there is a cycle they must meet inside it; otherwise fast reaches the end. O(n) time, O(1) space. A hash set of visited nodes also works but uses O(n) space.

    Check whether a string of brackets is valid, e.g. "([]{})".

    Use a stack. Push each opening bracket. For a closing bracket, the stack must be non-empty and its top must be the matching opener; pop it. At the end the stack must be empty. Time O(n), space O(n).

    pythondef is_valid(s):
    pairs = {")": "(", "]": "[", "}": "{"}
    stack = []
    for ch in s:
        if ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
        else:
            stack.append(ch)
    return not stack
    How does a hash map work internally?

    It hashes the key to an integer, maps it to a bucket index (e.g. hash % capacity), and stores the entry there. Collisions are handled by chaining (a list or tree per bucket, as in Java's HashMap) or open addressing (probing other slots, as in Python's dict). When the load factor exceeds a threshold (0.75 in Java) it resizes and rehashes. Operations are O(1) on average and O(n) worst case if many keys collide. Keys must have consistent equals/hashCode and must not change while stored.

    🌳 Trees and graphs

    How do you check whether a binary tree is a valid BST?
    pythondef is_bst(node, lo=float("-inf"), hi=float("inf")):
    if node is None:
        return True
    if not (lo < node.val < hi):
        return False
    return (is_bst(node.left, lo, node.val) and
            is_bst(node.right, node.val, hi))

    Pass down the allowed range. Comparing each node only with its direct children is a common bug: a value deep in the left subtree must be smaller than every ancestor it sits left of. An in-order traversal that checks values are strictly increasing also works. O(n) time, O(h) space.

    Find the maximum depth of a binary tree.
    pythondef max_depth(node):
    if node is None:
        return 0
    return 1 + max(max_depth(node.left), max_depth(node.right))

    Post-order recursion: the depth of a node is one more than its deeper child. O(n) time, O(h) stack space. BFS counting levels is an alternative that avoids deep recursion.

    When would you use BFS instead of DFS?

    BFS explores level by level with a queue, so it finds the fewest-edge path in unweighted graphs — e.g. minimum moves in a maze, degrees of separation. DFS goes deep with a stack or recursion and suits exhaustive exploration: cycle detection, topological sort, connected components, backtracking. Both are O(V + E). BFS can use a lot of memory on wide graphs; DFS uses memory proportional to depth.

    Given course prerequisites, can all courses be finished? (cycle detection in a directed graph)

    Model courses as vertices and prerequisites as directed edges. All courses can be finished exactly when the graph has no cycle. Use Kahn's algorithm: compute in-degrees, repeatedly remove vertices with in-degree 0. If the number removed equals the number of courses, there is no cycle and the removal order is a valid schedule. Alternatively, DFS with three colours (unvisited, in progress, done) — reaching an "in progress" vertex means a cycle. O(V + E).

    Count the islands in a grid of '1' (land) and '0' (water).
    pythondef num_islands(grid):
    rows, cols = len(grid), len(grid[0])

    def sink(r, c):
        if r < 0 or c < 0 or r >= rows or c >= cols or grid[r][c] != "1":
            return
        grid[r][c] = "0"                 # mark visited
        sink(r + 1, c); sink(r - 1, c)
        sink(r, c + 1); sink(r, c - 1)

    count = 0
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] == "1":
                count += 1
                sink(r, c)               # remove the whole island
    return count

    Each cell is visited a constant number of times: O(rows × cols) time. Mention that recursion depth can reach rows × cols, so for large grids use BFS or an explicit stack, and ask whether modifying the input is allowed.

    🔀 Sorting and searching

    Merge sort or quick sort — which would you choose?

    Quick sort is usually faster in memory: in place, cache-friendly, O(n log n) average, but O(n²) worst case without good pivot choice and not stable. Merge sort guarantees O(n log n), is stable and works well for linked lists and external sorting, but needs O(n) extra memory. In practice I use the language's built-in sort (Timsort in Python, TimSort for objects in Java), which is stable and adaptive.

    What is a stable sort and when does it matter?

    A stable sort keeps equal elements in their original relative order. It matters when sorting by multiple keys in passes: sort orders by time, then stably by customer, and each customer's orders stay in time order. Merge sort, insertion sort and Timsort are stable; quick sort, heap sort and selection sort typically are not.

    Find the first index of a target in a sorted array that contains duplicates.
    pythondef first_index(a, target):
    lo, hi = 0, len(a)             # half-open range [lo, hi)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < target:
            lo = mid + 1
        else:
            hi = mid               # mid could be the answer; keep it
    return lo if lo < len(a) and a[lo] == target else -1

first_index([1, 2, 2, 2, 5], 2)   # 1

    This is a lower-bound binary search (same as bisect_left). Note that with a half-open range the loop condition is lo < hi and the update is hi = mid — be consistent with one convention. O(log n).

    How would you sort a 100 GB file on a machine with 8 GB of RAM?

    Use external merge sort. Read chunks that fit in memory (say 4 GB), sort each in memory and write it to disk as a sorted run. Then do a k-way merge of the runs, using a min-heap holding the current smallest item from each run, streaming output to disk with buffered reads and writes. Total time is O(n log n) comparisons; the real cost is disk I/O, so minimise the number of passes.

    Find the k-th largest element in an unsorted array.

    Options: sort and index, O(n log n). Better: keep a min-heap of size k — push each element and pop when the size exceeds k; the root is the answer. O(n log k) time, O(k) space. Best average: quickselect, partitioning like quick sort but recursing into one side only, O(n) average and O(n²) worst.

    pythonimport heapq
def kth_largest(nums, k):
    heap = []
    for x in nums:
        heapq.heappush(heap, x)
        if len(heap) > k:
            heapq.heappop(heap)
    return heap[0]

kth_largest([3, 2, 1, 5, 6, 4], 2)   # 5

    🧩 Problem-solving techniques

    Two Sum: return indices of two numbers that add up to a target.
    pythondef two_sum(nums, target):
    seen = {}                        # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:
            return [seen[target - x], i]
        seen[x] = i
    return []

    Brute force checks every pair, O(n²). The hash map stores values already seen, so each complement check is O(1) average: O(n) time, O(n) space. Checking before inserting avoids using the same element twice. If the array is sorted, two pointers give O(1) space.

    How do you recognise a dynamic programming problem, and how do you approach it?

    Signs: the problem asks for a count, minimum, maximum or yes/no over many choices, and a brute-force recursion solves the same sub-problems repeatedly (overlapping sub-problems), with the optimal answer built from optimal sub-answers (optimal substructure). Approach: write the recursive brute force, define the state clearly, add memoisation (top-down), then convert to tabulation (bottom-up) if needed and reduce space by keeping only the rows you need.

    last = {}
    start = best = 0
    for i, ch in enumerate(s):
        if ch in last and last[ch] >= start:
            start = last[ch] + 1
        last[ch] = i
        best = max(best, i - start + 1)
    return best

    Design an LRU (least recently used) cache with O(1) get and put.

    Combine a hash map (key → node, for O(1) lookup) with a doubly linked list ordered by recency (for O(1) move-to-front and evict-from-tail). In Python, OrderedDict provides both:

    pythonfrom collections import OrderedDict

class LRUCache:
    def __init__(self, capacity):
        self.capacity = capacity
        self.data = OrderedDict()

    def get(self, key):
        if key not in self.data:
            return -1
        self.data.move_to_end(key)          # mark as most recent
        return self.data[key]

    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = value
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)   # evict least recent

    In Java, LinkedHashMap with access order and an overridden removeEldestEntry does the same.

    When does a greedy algorithm fail? Give an example.

    Greedy fails when a locally best choice can block the globally best solution. Coin change with coins [1, 3, 4] and amount 6: greedy picks 4 + 1 + 1 (3 coins), but 3 + 3 uses 2. Similarly 0/1 knapsack cannot be solved by best value-per-weight. Use dynamic programming there. Greedy is safe when you can prove the greedy-choice property, e.g. interval scheduling by earliest finish time.

    Abstract class or interface — how do you choose?

    Use an interface to define a capability that unrelated classes can share, and because a class can implement many of them. Use an abstract class when closely related classes share state, constructors or substantial code, and an is-a relationship is genuine. Since Java 8, interfaces can have default methods, so I start with an interface and introduce an abstract base class only for real shared implementation.

    Why "favour composition over inheritance"?

    Inheritance couples a subclass to its parent's implementation; changes in the base class can break subclasses, and behaviour is fixed at compile time. Composition holds other objects behind interfaces and delegates to them, so you can swap behaviour at run time (Strategy), test parts in isolation and avoid class explosions like ElectricConvertibleSportsCar. I still use inheritance for true is-a hierarchies that obey the Liskov principle.

class FareStrategy(Protocol):
    def quote(self, km: float) -> float: ...

class EconomyFare:
    def quote(self, km): return 2.0 + 1.0 * km

class XlFare:
    def quote(self, km): return 3.5 + 1.6 * km

class FareService:
    def __init__(self, strategies: dict, surge_provider):
        self.strategies = strategies          # injected
        self.surge = surge_provider           # injected

    def quote(self, ride_type, km, zone):
        base = self.strategies[ride_type].quote(km)
        return round(base * self.surge.multiplier(zone), 2)

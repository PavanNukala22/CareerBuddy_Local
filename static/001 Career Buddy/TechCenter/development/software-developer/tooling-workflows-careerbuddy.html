    Module 13 · Foundations

    Git Fundamentals

    Git is a distributed version control system. It records snapshots of your project so you can go back in time, work on features in parallel and merge the work of many people safely.

    📘 Why version control matters

    • History: every change has an author, a date and a message, so you can see who changed what and why.
    • Safety: a bad change can be undone without losing other work.
    • Parallel work: branches let several people build features at the same time.
    • Collaboration and review: pull requests, CI checks and releases all build on Git.

    🌿 Installation and first-time configuration

    git --version                          # check it is installed
git config --global user.name  "Asha Rao"
git config --global user.email "asha@example.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"
git config --list                      # verify

    🔀 The three areas

    Files move from the working directory (what you edit) to the staging area with git add, then into the repository as a commit with git commit. Staging lets you choose exactly what goes into each commit.

    CommandWhat it doesExample
    git initTurns the current folder into a new repositorygit init
    git cloneCopies a remote repository, with full historygit clone https://github.com/user/app.git
    git statusShows changed, staged and untracked filesgit status -s
    git addStages changes for the next commitgit add app.py or git add -p
    git commitSaves the staged snapshot with a messagegit commit -m "Add tax calculator"
    git logShows commit historygit log --oneline --graph --all
    git diffShows line-level differencesgit diff (unstaged), git diff --staged

    ↩️ .gitignore for Python projects

    A .gitignore lists files Git must never track: generated files, secrets and local environments.

    __pycache__/
*.pyc
.venv/
venv/
.env
.pytest_cache/
.idea/
.vscode/
dist/
build/
*.egg-info/
.DS_Store
    ⚠️
    Common mistake: adding a file to .gitignore after it was already committed does nothing. Run git rm --cached .env to stop tracking it. If a secret was ever pushed, rotate the secret; deleting the file does not remove it from history.
    ⚠️
    Other mistakes: committing with vague messages ("fix", "update"), making huge commits that mix unrelated changes, and committing without running git status first.

    Module 13 · Collaboration

    Branching, Merging & Undoing

    A branch is a lightweight movable pointer to a commit. Creating one is instant, so teams use a branch for every feature or fix and keep main stable.

    📘 Branches and merging

    git branch                         # list branches
git branch feature/login           # create
git switch feature/login           # move to it (modern)
git switch -c feature/login        # create and move
git checkout feature/login         # older equivalent
git checkout -b feature/login      # older create and move
git switch main
git merge feature/login            # bring the feature into main
git branch -d feature/login        # delete after merge

    git switch only changes branches; git checkout also restores files, which is why it was split in two. Prefer switch and restore in new work.

    🌿 Merge conflicts

    A conflict happens when two branches change the same lines (or one deletes a file the other edits). Git cannot choose, so it pauses and marks the file:

    <<<<<<< HEAD
TAX_RATE = 0.18
=======
TAX_RATE = 0.20
>>>>>>> feature/new-rate

    Edit the file to the correct final content and delete the three marker lines. Then run git add on the file and git commit (or git merge --continue). Use git merge --abort to back out. Always run the tests after resolving.

    🔀 git stash

    Shelves uncommitted changes so you can switch tasks with a clean directory.

    git stash push -m "wip: report export"
git stash list
git stash pop            # restore and drop
git stash apply          # restore and keep

    ↩️ git reset and git revert

    git reset --soft HEAD~1    # undo commit, keep changes staged
git reset --mixed HEAD~1   # undo commit, keep changes unstaged (default)
git reset --hard HEAD~1    # undo commit AND discard changes (dangerous)
git revert a1b2c3d         # new commit that reverses a1b2c3d
git restore app.py         # discard unstaged edits to one file
    ⚠️
    Rule: use reset only on commits you have not pushed. For anything already shared, use revert. A recoverable safety net exists: git reflog lists where HEAD has been, which often rescues a mistaken reset --hard.

    🌐 Tags and releases

    git tag v1.0.0                          # lightweight tag
git tag -a v1.0.0 -m "First stable release"
git push origin v1.0.0                  # tags are not pushed by default

    A tag marks a commit permanently, usually using semantic versioning (MAJOR.MINOR.PATCH). GitHub and GitLab turn a tag into a Release with notes and downloadable files.

    Module 13 · Collaboration

    Remotes, GitHub/GitLab & Reviews

    A remote is a copy of the repository hosted elsewhere. origin is the conventional name for the one you cloned from.

    📘 Remotes, GitHub/GitLab, reviews and authentication

    git remote add origin git@github.com:user/app.git
git remote -v
git fetch origin               # download, do not change my files
git pull origin main           # fetch + merge
git push -u origin feature/login   # first push sets upstream
git push                       # later pushes

    🌿 Pull Requests / Merge Requests and code review

    A PR (GitHub) or MR (GitLab) proposes merging one branch into another. It is where teammates review the diff, comment, request changes and where automated tests run. Good PRs are small, have a clear description of what and why, link the issue and pass CI before review. Good reviewers check correctness, tests, readability and security, and give specific, kind feedback.

    🔀 SSH keys and authentication

    ssh-keygen -t ed25519 -C "asha@example.com"
cat ~/.ssh/id_ed25519.pub      # paste into GitHub/GitLab: Settings → SSH keys
ssh -T git@github.com          # test the connection

    You can authenticate over SSH (key pair; the private key never leaves your machine) or HTTPS (a personal access token, not your password). Never share or commit a private key.

    Bash Command-Line Fundamentals

    The terminal is the window; Bash is the shell program inside it that reads and runs your commands. Developers use it because it is fast, scriptable and the same on servers.

    📘 Bash command-line fundamentals

    CommandPurposeExample
    pwdPrint current directorypwd
    lsList filesls -la
    cdChange directorycd ~/projects/app, cd ..
    mkdirMake directorymkdir -p src/utils
    touchCreate empty file / update timetouch main.py
    cpCopycp -r src backup
    mvMove or renamemv old.py new.py
    rmDelete (no recycle bin)rm file.txt, rm -r folder
    catPrint a filecat requirements.txt
    head / tailFirst / last linestail -f app.log
    grepSearch textgrep -rn "TODO" src/
    findSearch for filesfind . -name "*.py"
    echoPrint text or a variableecho $HOME
    clearClear the screenclear or Ctrl+L
    ⚠️
    Common mistake: rm -rf with a wrong path or an unquoted variable can delete far more than intended and cannot be undone. Run ls on the same path first.

    🌿 Environment variables, pipes and redirection

    export API_KEY="abc123"            # set for this session and child processes
echo $API_KEY
python -c "import os; print(os.environ['API_KEY'])"

ls | wc -l                         # pipe: output of one becomes input of next
grep -rn "def " src/ | head -5
python main.py > out.txt           # redirect stdout, overwrite
python main.py >> out.txt          # append
python main.py 2> err.txt          # redirect errors only
python main.py > all.txt 2>&1     # both streams to one file

    Keep secrets in environment variables or a .env file (git-ignored), never in source code.

    🔀 File permissions

    ls -l run.sh              # -rw-r--r--  owner can read/write; group and others read
chmod +x run.sh           # make executable
chmod 755 run.sh          # rwx for owner, r-x for group and others

    Permissions are three digits (owner, group, others). Read = 4, write = 2, execute = 1, so 755 means 7 (rwx), 5 (r-x), 5 (r-x).

    Module 13 · Command Line

    Running Python from the Terminal

    📘 Python from the command line

    python --version
python main.py                         # run a script
python -m venv .venv                   # create virtual environment
source .venv/bin/activate              # Windows: .venv\Scripts\activate
pip install requests pytest
pip freeze > requirements.txt          # record dependencies
pip install -r requirements.txt        # recreate on another machine
pytest -v                              # run all tests
pytest tests/test_math.py::test_add    # run one test
python -m pytest --maxfail=1 -q

    Use a virtual environment for every project so each one has its own package versions. Commit requirements.txt but never .venv/.

    🌿 A Bash script that automates Python tasks

    #!/usr/bin/env bash
# check.sh : set up, test and run the project
set -e                                 # stop on first error

[ -d .venv ] || python -m venv .venv
source .venv/bin/activate
pip install -q -r requirements.txt

echo "Running tests..."
pytest -q

echo "Starting app..."
python main.py "$@"
    chmod +x check.sh
./check.sh

    Module 13 · Hands-on

    Practical Workflows

    📘 A. Create a repository for a Python project

    mkdir calculator && cd calculator
git init
python -m venv .venv
printf ".venv/\n__pycache__/\n.env\n" > .gitignore
echo "def add(a, b):
    return a + b" > calc.py
git status
git add .
git commit -m "Initial commit: add calc module"

    🌿 B. Feature branch, commit, push

    git switch -c feature/subtract
# edit calc.py, add tests/test_calc.py
pytest -q
git status
git add calc.py tests/
git commit -m "Add subtract function with tests"
git push -u origin feature/subtract

    🔀 C. Open a Pull / Merge Request

    After pushing, GitHub or GitLab prints a link. Open it, choose the base branch (main), write a title and a description covering what changed, why and how you tested it, then request reviewers. Address comments by pushing more commits to the same branch; the PR updates itself. After approval and passing CI, click Merge, then locally:

    git switch main
git pull
git branch -d feature/subtract

    ↩️ D. Resolve a merge conflict

    git switch feature/subtract
git merge main                 # CONFLICT (content): Merge conflict in calc.py
git status                     # shows "both modified: calc.py"
# open calc.py, keep the correct code, remove the markers
pytest -q
git add calc.py
git commit                     # completes the merge
git push

    🌐 E. Git and Bash together

    git log --oneline | head -5            # last five commits
git diff --name-only main | grep "\.py$"   # changed Python files
git status -s | grep "^??"             # untracked files
find . -name "*.py" -not -path "./.venv/*" | xargs grep -n "print("

    Module 13 · Real World

    A Professional Git Workflow

    📘 A professional workflow

    Create branch→Write Python code→Test→git status→git add→git commit→git push→PR / MR→Code review→Merge
    1. Sync and branch: git switch main && git pull, then git switch -c feature/ISSUE-42-export-csv.
    2. Code and test: write the function and tests; run pytest until green.
    3. Check: git status and git diff to confirm only intended files changed.
    4. Commit: stage selectively, write a clear message in the imperative ("Add CSV export").
    5. Push and open PR: link the issue, describe the change and how you tested it.
    6. Review and CI: automated tests and linters run; reviewers comment; you push fixes.
    7. Merge and clean up: merge (often squash), delete the branch, pull the updated main.
    💡
    Best practices: commit small and often; one purpose per commit; never commit directly to main; pull before you push; never commit secrets or virtual environments; protect main so it requires reviews and passing tests.

    Module 13 · Career

    Interview Preparation

    Select a question to reveal a model answer.

    📘 Interview preparation

    What is Git and why use it?

    A distributed version control system that tracks changes, enables parallel work through branches, and lets you restore any earlier state. Every developer has a full copy of the history.

    What is the difference between Git and GitHub?

    Git is the tool; GitHub is a hosting service built around it that adds pull requests, issues, Actions and access control. GitLab and Bitbucket are alternatives.

    Explain the staging area. Why does it exist?

    It is a holding area between your working directory and the commit. It lets you build commits from selected changes (even parts of a file with git add -p), so each commit stays focused.

    What is the difference between git fetch and git pull?

    fetch only downloads; pull is fetch plus merge. Fetching first lets you inspect incoming changes safely.

    How do you resolve a merge conflict?

    Run git status to find conflicted files, edit them to remove markers and keep the right code, run tests, git add the files, then commit. Communicate with the other author if intent is unclear. git merge --abort cancels.

    When would you use merge and when rebase?

    Merge to integrate shared work and preserve history. Rebase to tidy your own local or feature branch before review. The golden rule: never rebase commits others have based work on.

    How do you undo a commit that is already pushed?

    Use git revert <hash>, which adds a new undoing commit and keeps history intact. reset plus force-push rewrites shared history and disrupts teammates.

    What does git stash do?

    It saves uncommitted changes on a stack and gives you a clean working directory, so you can switch branches. git stash pop brings them back.

    What is .gitignore and what should a Python project ignore?

    A file listing patterns Git should not track: __pycache__/, *.pyc, .venv/, .env, .pytest_cache/, build output and IDE folders. It only affects untracked files.

    What is a pull request and what makes a good one?

    A request to merge a branch, with a place for review and CI. Good ones are small, well described, linked to an issue, tested, and respond promptly to feedback.

    How do SSH keys work for Git?

    You generate a public/private key pair. The public key is registered with the host; the private key stays local and proves your identity, so no password is sent.

    What are tags and how do they differ from branches?

    A tag is a fixed label on one commit (e.g. v1.2.0) used for releases. A branch moves forward as you commit.

    What does `chmod +x script.sh` do?

    Adds execute permission so you can run ./script.sh. Without it the shell refuses with "Permission denied".

    Difference between `>`, `>>` and `|`?

    > writes output to a file (overwriting), >> appends, | sends one command's output into another command's input.

    How do you find all Python files containing "TODO"?

    grep -rn "TODO" --include="*.py" . or find . -name "*.py" | xargs grep -n "TODO".

    How do you keep a team workflow healthy?

    Protected main, short-lived branches, mandatory reviews, CI on every PR, consistent commit messages, and a documented branching strategy.

    Practice Questions

    📘 Practice questions

    Q1. Which command shows differences between staged changes and the last commit?
    1. git diff
    2. git diff --staged
    3. git log -p
    4. git status

    Answer: B.

    Explanation: Plain git diff compares working directory to the index (unstaged work). --staged compares the index to HEAD.

    Scenario: You staged three files and want a last look before committing. Run git diff --staged.

    Q2. You committed a password into config.py and have not pushed. What is the best fix?
    1. Add config.py to .gitignore
    2. git revert HEAD
    3. Remove the password, then git commit --amend
    4. Delete the repository

    Answer: C.

    Explanation: Amend rewrites the unpushed commit so the secret never reaches history. .gitignore does not affect tracked files, and revert would keep the secret in history. If it had been pushed, you would also have to rotate the password.

    Scenario: Move the secret to an environment variable and read it with os.environ.

    Q3. What is the difference between `git switch -c x` and `git branch x`?

    Answer: switch -c creates the branch and moves you onto it; branch x only creates it.

    Explanation: Forgetting to switch is a common mistake: commits then land on your old branch.

    Scenario: You ran git branch feature/api, edited code and committed. Your commit is on main. Fix: git branch feature/api already points there, so git reset --hard origin/main on main (before pushing) and git switch feature/api.

    Q4. A teammate's push was rejected: "Updates were rejected because the remote contains work you do not have." What do you do?
    1. git push --force
    2. git pull (or fetch and merge/rebase), resolve conflicts, then push
    3. Delete the remote branch
    4. Clone the repo again

    Answer: B.

    Explanation: The remote has commits you lack. Integrate them first. Forcing would erase your teammate's work.

    Q5. Which is safe for undoing a bad commit on a shared main branch?
    1. git reset --hard HEAD~1 then force push
    2. git revert HEAD
    3. git rebase -i
    4. git stash

    Answer: B.

    Explanation: Revert adds a new commit and preserves history that others have already pulled.

    Q6. Merge conflict scenario: what must you do before `git commit` finishes the merge?

    Answer: Edit the files to remove <<<<<<<, =======, >>>>>>>, keep the intended code, run tests, and git add each file.

    Explanation: Staging a file tells Git it is resolved.

    Scenario: Both you and a teammate changed the same function signature. Talk to them, choose the combined version, then run pytest.

    Q7. What does `ls -l` show that `ls` does not?

    Answer: Permissions, owner, group, size and modification time.

    Explanation: A string like -rwxr-xr-- starts with the file type, then owner, group and others permissions.

    Q8. What does `chmod 644 notes.txt` set?
    1. Everyone can read, write, execute
    2. Owner read/write; group and others read-only
    3. Owner read-only
    4. Only others can read

    Answer: B.

    Explanation: 6 = 4+2 (rw-), 4 = r--, 4 = r--.

    Q9. Write a command that saves the names of all failing-test lines from pytest to failures.txt.

    Answer: pytest 2>&1 | grep FAILED > failures.txt

    Explanation: 2>&1 merges errors into the stream, the pipe filters lines with grep, and > writes the result.

    Q10. A new teammate clones your repo and the app fails with ModuleNotFoundError. What is likely missing and how do you fix it?

    Answer: Dependencies were not installed. Create a virtual environment and run pip install -r requirements.txt.

    Explanation: The repo should contain requirements.txt (made with pip freeze) but not .venv/. Document the steps in the README or provide a setup script like check.sh.

    Q11. Real workflow: you are halfway through a feature and an urgent bug arrives. What do you do?

    Answer: git stash push -m "wip", git switch main, git pull, git switch -c hotfix/login-crash, fix, test, commit, push, open PR. Then git switch feature/x and git stash pop.

    Explanation: Stash keeps unfinished work safe without a messy half-commit.

    Q12. Which statement about tags is true?
    1. git push sends tags automatically
    2. Tags move with each commit
    3. Tags must be pushed explicitly, e.g. git push origin v1.0.0
    4. Tags can only be created on GitHub

    Answer: C.

    Explanation: Tags are local until pushed; git push --tags pushes all of them.

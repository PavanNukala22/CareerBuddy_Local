    Developer Workflow Fundamentals

    The everyday tools a developer uses, and how code travels from your laptop to production.

    🧰 The developer's daily toolkit

    Writing code is only part of the job. Every day a developer also runs commands, tracks changes, shares work with a team and ships it safely. A small set of tools does almost all of this work. Learn them well once and they serve you in every language and every company.

    📝
    Editor / IDE
    Where you write code. VS Code, IntelliJ IDEA, PyCharm, Vim. Gives syntax highlighting, debugging, refactoring and Git integration.
    💻
    Terminal & shell
    A text window (terminal) running a command interpreter (shell, often Bash). Fast, scriptable and available on every server.
    🌿
    Git
    The version control system. Records every change as a commit so you can review, undo and combine work.
    ☁️
    GitHub / GitLab
    Hosting platforms for Git repositories. Add pull/merge requests, code review, issues and CI.
    📦
    Package managers
    Install libraries and tools: npm, pip, Maven, apt, Homebrew, winget. Keep dependencies repeatable.
    ⚙️
    CI/CD
    Automation that builds, tests and deploys every change: GitHub Actions, GitLab CI, Jenkins.
    ToolQuestion it answersExample command
    ShellHow do I run and automate things?ls -la
    GitWhat changed, when, and why?git log --oneline
    GitHub/GitLabHow does my team review and merge?gh pr create
    Package managerHow do I install dependencies?npm install
    CIDoes every change still build and pass tests?.github/workflows/ci.yml
    💡
    You do not need to master everything on day one. A fresher who is comfortable with cd, ls, git status, git add, git commit and git push can already contribute to a real project.

    🗺️ A typical day: from task to production

    Most teams follow the same loop for every change, whether it is a one-line bug fix or a large feature. Learn this loop and you will recognise it in almost every company.

    The everyday developer loop: every change goes through a branch and a review.
    1. Pull the latest main so you start from current code.
    2. Branch: create a short-lived branch such as feature/login-page.
    3. Code and test locally.
    4. Commit small, logical steps with clear messages.
    5. Push the branch to the shared remote (GitHub/GitLab).
    6. Open a pull request (GitLab calls it a merge request).
    7. Review: teammates comment, CI runs tests automatically.
    8. Merge into main once approved and green.
    9. Deploy: often automatic from main via CI/CD.
    bashgit switch main
git pull                              # 1. get latest main
git switch -c feature/login-page      # 2. new branch
# ... edit files ...                  # 3. code
git add src/login.js
git commit -m "feat: add login form"  # 4. commit
git push -u origin feature/login-page # 5. push
# 6. open a pull request on GitHub / merge request on GitLab

    🕰️ Why version control?

    Without version control, teams email zip files or keep folders named project_final_v2_REALLY_final. Nobody knows which copy is correct, and a bad change cannot be undone cleanly. A version control system (VCS) records every change with who made it, when, and why.

    Without version controlWith Git
    Copies of folders, unclear which is latestOne history; every commit has an ID
    Overwriting each other's workBranches let people work in parallel, then merge
    "It worked yesterday" with no way backGo back to any previous commit
    No record of why code changedCommit messages explain the reason
    Hard to review changesDiffs show exactly which lines changed
    ⏪
    Undo
    Return a file or the whole project to any earlier state.
    👥
    Collaborate
    Many developers change the same codebase safely.
    🔍
    Audit
    See who changed a line and the commit that explains it.
    🧪
    Experiment
    Try an idea on a branch; delete it if it fails.
    EXAMPLE · Finding when a bug appeared

    A price calculation broke sometime last week. With Git you run git log -p -- src/price.js to see every change to that file, or git bisect to binary-search the commit that introduced the bug. Without version control you would be guessing.

    🌐 Local vs remote

    Git is distributed: every developer has a full copy of the repository, including its whole history, on their own machine. A remote is another copy of the same repository, usually hosted on GitHub or GitLab, that the team agrees to share through.

    Local repository

    • Lives on your laptop in the .git folder
    • Commit, branch, diff and log work offline
    • Private until you push
    • Fast: no network needed

    Remote repository

    • Lives on a server (GitHub, GitLab, Bitbucket)
    • Default name is origin
    • Shared by the whole team
    • You sync with fetch, pull and push
    bash$ git remote -v
origin  git@github.com:acme/shop.git (fetch)
origin  git@github.com:acme/shop.git (push)

$ git status
On branch main
Your branch is ahead of 'origin/main' by 2 commits.
  (use "git push" to publish your local commits)
    📝
    "Ahead by 2 commits" means you have two local commits the remote does not have yet. Nothing reaches your team until you git push.

    🤝 Working in a team: habits that matter

    Tools only help if the team uses them consistently. These habits separate a smooth team from a chaotic one.

    🔄
    Pull often
    Sync with main at least daily so your branch never drifts far.
    ✂️
    Small commits
    One logical change per commit. Easy to review and easy to revert.
    🌱
    Short-lived branches
    Merge within days, not weeks, to avoid painful conflicts.
    💬
    Clear messages
    Explain why the change was made, not just what.
    ✅
    Green before merge
    Never merge with failing tests or CI.
    🔐
    No secrets in Git
    Passwords and API keys go in environment variables or a secret manager.
    EXAMPLE · A good day vs a bad day

    Good: Priya pulls main at 9am, branches, commits three small steps, opens a PR at 3pm, gets review, merges at 5pm. Bad: Ravi works on a branch for three weeks without pulling, then faces 40 conflicting files the day before release.

    🔐 Permissions, ownership and sudo

    Every file has an owner, a group, and three sets of permissions: for the user (u), the group (g) and others (o). Each set is a mix of read (r), write (w) and execute (x).

    bash$ ls -l deploy.sh
-rwxr-x---  1 priya dev  420 Oct  7 10:02 deploy.sh
│└┬┘└┬┘└┬┘     └─┬─┘ └┬┘
│ u  g  o      owner group
└ type: - file, d directory, l symlink
    SymbolNumberOn a fileOn a directory
    r4Read the contentsList the entries
    w2Modify the fileCreate/delete entries
    x1Run it as a programEnter it with cd

    Add the numbers for each set: rwx = 7, r-x = 5, r-- = 4. So rwxr-x--- is 750.

    CommandEffect
    chmod 755 script.shrwxr-xr-x: owner full, others read + run
    chmod 644 notes.txtrw-r--r--: typical file
    chmod 600 ~/.ssh/id_ed25519Owner read/write only (private keys must be this strict)
    chmod +x script.shSymbolic: add execute for everyone
    chmod u+x,go-w fileAdd x for user; remove w for group and others
    chown priya:dev fileChange owner and group (usually needs sudo)
    sudo apt updateRun one command as the superuser (root)
    ⚠️
    Avoid chmod 777. It lets anyone modify or run the file. Use sudo only when needed: it bypasses all permission checks.

    Bash Scripting & Automation

    📜 Your first script

    A Bash script is a plain text file of commands that run top to bottom. If you type the same five commands every day, put them in a script.

    bash#!/usr/bin/env bash
# hello.sh - my first script
echo "Hello, $USER! Today is $(date +%A)."
echo "You are in: $(pwd)"

    bash$ chmod +x hello.sh      # make it executable (once)
$ ./hello.sh             # run it (./ = "in this folder")
Hello, priya! Today is Tuesday.
You are in: /home/priya/scripts
$ bash hello.sh          # alternative: no execute bit needed
    Shebang (#!)First line; tells the OS which interpreter runs the file. #!/usr/bin/env bash finds bash on the PATH; #!/bin/bash uses a fixed path.
    chmod +xAdds the execute permission so you can run ./script.sh.
    ./Needed because the current folder is not on PATH by default.
    #Starts a comment (except in the shebang).
    💡
    Name scripts with a .sh extension and keep them in the repository (for example a scripts/ folder) so the whole team can use and review them.

    🏷️ Variables and quoting

    Assign with name=value and no spaces around =. Read with $name or ${name}.

    bashname="Priya"
count=3
greeting="Hi $name"          # double quotes expand variables
literal='Hi $name'           # single quotes keep text literal
echo "$greeting"             # Hi Priya
echo "$literal"              # Hi $name
echo "${name}_backup"        # Priya_backup (braces mark the end of the name)
echo "Files: $(ls | wc -l)"  # command substitution
today=$(date +%F)            # 2026-10-07
echo $(( count * 2 ))        # arithmetic: 6
    FormBehaviour
    "$var"Expands the variable, keeps it as one word (spaces safe). Use this by default.
    '$var'No expansion at all: prints the literal text $var.
    $var (unquoted)Expands, then splits on spaces and expands wildcards. Source of many bugs.
    $(command)Replaced by the command's output.
    $(( 2 + 3 ))Integer arithmetic.
    ${var:-default}Use default if var is unset or empty.
    EXAMPLE · Why quoting matters
    bashfile="my report.txt"
rm $file      # WRONG: tries to delete "my" and "report.txt"
rm "$file"    # RIGHT: deletes the single file "my report.txt"
    ⚠️
    name = "Priya" (with spaces) is an error: Bash tries to run a command called name.

    🛡️ Safer scripts: set -euo pipefail

    By default Bash keeps going after a failing command, treats unset variables as empty strings and ignores failures inside pipelines. That is dangerous. Most professional scripts start with a strict mode line.

    bash#!/usr/bin/env bash
set -euo pipefail
    OptionEffectBug it prevents
    -eExit when a command failsDeploying after the build failed

    -o pipefailA pipeline fails if any part failscurl … | tar x hiding a failed download

    📄 Reading files line by line

    The safe pattern uses while IFS= read -r. IFS= keeps leading spaces, -r keeps backslashes literal.

    bash#!/usr/bin/env bash
set -euo pipefail
# servers.txt has one hostname per line
while IFS= read -r host; do
  [[ -z "$host" || "$host" == \#* ]] && continue   # skip blanks and comments
  if ping -c1 -W2 "$host" > /dev/null 2>&1; then
    echo "UP   $host"
  else
    echo "DOWN $host"
  fi
done < servers.txt

    Git Fundamentals

    Snapshots, the three areas, everyday commands and working with remotes.

    🌿 What Git is

    Git is a free, open-source, distributed version control system created by Linus Torvalds in 2005 for Linux kernel development. It records the history of a project as a series of snapshots called commits.

    📸
    Snapshots, not diffs
    Each commit stores the full state of tracked files (unchanged files are reused, so it stays small).
    🌐
    Distributed
    Every clone has the full history. Commit, branch and log work offline.
    🔒
    Integrity
    Every object is identified by a hash of its content; history cannot change silently.
    🌱
    Cheap branching
    Branches are tiny pointers, so creating and switching them is instant.

    Git (the tool)

    Runs on your machine. Command line: git. Works with or without any server.

    GitHub / GitLab (the platforms)

    Websites that host Git repositories and add pull/merge requests, issues, CI and permissions.

    📝
    Git is the engine; GitHub and GitLab are garages where teams park and share their repositories.

    Branching, Merging & Rebasing

    Work in parallel, combine work cleanly, resolve conflicts and keep history readable.

    🌱 Branches are just pointers

    A branch is a tiny file containing one commit hash. When you commit, the current branch moves forward to the new commit. That is why creating a branch is instant, even in a huge repository.

    bash          C3  <── feature
         /
C1 ── C2 ── C4  <── main  <── HEAD

    bash$ git branch                       # list local branches (* = current)
* main
  feature/login
$ git branch -a                    # include remote-tracking branches
$ git switch -c feature/search     # create and switch (Git 2.23+)
$ git checkout -b feature/search   # older equivalent, still works
$ git switch main                  # switch to an existing branch
$ git switch -                     # back to the previous branch
$ git branch -d feature/search     # delete (only if merged)
$ git branch -D spike/old-idea     # force delete (unmerged work is lost)
$ git branch -m old-name new-name  # rename
$ git push origin --delete feature/search   # delete the remote branch

    git switch / git restore

    Introduced in Git 2.23 to split the overloaded checkout: switch changes branches, restore restores files. Clearer and safer.

    git checkout

    The original all-in-one command. It still works and appears in older docs: checkout -b = switch -c, checkout -- file = restore file.

    💡
    Name branches by purpose: feature/cart-coupons, fix/login-timeout, chore/upgrade-node. Many teams add the ticket ID: feature/PROJ-142-coupons.

    🔀 Fast-forward vs three-way merge

    git merge feature brings the commits of feature into the branch you are on. Git chooses one of two strategies.

    Fast-forward

    If main has not moved since you branched, Git simply moves the main pointer forward. No new commit is created and history stays linear.

    bashbefore:  C1 ── C2  <── main
                 \
                  C3 ── C4  <── feature

after:   C1 ── C2 ── C3 ── C4  <── main, feature

    Three-way merge

    If both branches have new commits, Git combines them using three snapshots: the two branch tips and their common ancestor (the merge base). It records a merge commit with two parents.

    bashbefore:  C1 ── C2 ── C5  <── main
                 \
                  C3 ── C4  <── feature

after:   C1 ── C2 ── C5 ── M  <── main      (M has parents C5 and C4)
                 \         /
                  C3 ── C4

    bash$ git switch main
$ git merge feature/search
Merge made by the 'ort' strategy.
 src/search.js | 40 ++++++++++++++++
$ git merge --no-ff feature/search   # always create a merge commit
$ git merge --ff-only origin/main    # refuse unless a fast-forward is possible
    📝
    --no-ff keeps a visible record that a group of commits arrived together as one feature. --ff-only is a safe way to update a local branch without creating surprise merges.

    ⚔️ Resolving merge conflicts step by step

    A conflict happens when both branches changed the same lines of the same file (or one edited a file the other deleted). Git stops and asks you to decide. Conflicts are normal, not a disaster.

    bash$ git merge feature/discount
Auto-merging src/price.js
CONFLICT (content): Merge conflict in src/price.js
Automatic merge failed; fix conflicts and then commit the result.

$ git status
You have unmerged paths.
        both modified:   src/price.js

    javascriptfunction total(items) {
<<<<<<< HEAD
  return sum(items) * 1.18;          // main: add 18% tax
=======
  return sum(items) * 0.9;           // feature: 10% discount
>>>>>>> feature/discount
}
    1. Open the file. Between <<<<<<< HEAD and ======= is your current branch's version; between ======= and >>>>>>> feature/discount is the incoming version.
    2. Decide the correct result. It may be one side, the other, or a combination: return sum(items) * 0.9 * 1.18;
    3. Delete all marker lines (<<<<<<<, =======, >>>>>>>).
    4. Run the tests to make sure the combined code works.
    5. git add src/price.js to mark it resolved.
    6. git commit (or git merge --continue) to finish the merge.
    CommandUse
    git merge --abortGive up and return to the state before the merge
    git diff during a conflictShows the conflicting hunks
    git checkout --ours file / --theirsTake one whole side for a file (then git add)
    git mergetoolOpen a configured visual merge tool
    💡
    Prevent conflicts: pull main into your branch often, keep branches short-lived, and avoid mass reformatting in feature branches.

    📐 Rebase: replaying commits

    git rebase main takes the commits on your branch and replays them on top of the latest main, creating new commits with new hashes. The result is a straight, linear history without a merge commit.

    bashbefore:  C1 ── C2 ── C5  <── main
                 \
                  C3 ── C4  <── feature

$ git switch feature
$ git rebase main

after:   C1 ── C2 ── C5 ── C3' ── C4'  <── feature   (C3', C4' are new commits)

    bash# If a conflict happens during rebase:
$ git status                 # see the conflicting file
# ...fix the file, then:
$ git add src/price.js
$ git rebase --continue      # move on to the next commit
$ git rebase --skip          # drop this commit (rarely)
$ git rebase --abort         # go back to how things were

# Update your branch from the remote with rebase instead of merge
$ git pull --rebase
    📝
    During a rebase, "ours" and "theirs" are swapped compared with a merge: "ours" is the branch you are rebasing onto, "theirs" is your commit being replayed.

    🧹 Interactive rebase: squash and reword

    Before opening a pull request you can tidy your own commits with git rebase -i. The editor lists commits oldest first; change the word in front of each one.

    bash$ git rebase -i HEAD~4

pick   a1b2c3d feat: add search box
squash 4d5e6f7 wip
fixup  8a9b0c1 fix typo
reword 2c3d4e5 add tests

# Commands:
# p, pick   = use commit
# r, reword = use commit, but edit the message
# e, edit   = stop to amend the commit
# s, squash = meld into previous commit, combine messages
# f, fixup  = like squash, but discard this commit's message
# d, drop   = remove commit

    Result: three messy commits become one clean feat: add search box commit, and the test commit gets a better message. You can also reorder lines to reorder commits.

    bash# Autosquash workflow
$ git commit --fixup=a1b2c3d          # creates "fixup! feat: add search box"
$ git rebase -i --autosquash main     # fixup commit is moved and marked automatically
    ⚠️
    Interactive rebase rewrites history. Use it on commits that only exist on your branch. If you already pushed them, you will need git push --force-with-lease, which is fine only for a branch nobody else works on.

    ⚖️ Merge vs rebase and the golden rule

    MergeRebase
    History shapeTrue, branching history with merge commitsLinear, as if work happened in sequence
    Rewrites commits?No, existing commits are untouchedYes, creates new commits with new hashes
    Safe on shared branches?YesNo, only on your own local/private commits

    The golden rule of rebasing: never rebase commits that exist outside your repository and that others may have based work on. Rewriting shared history forces teammates to untangle duplicated commits.
    EXAMPLE · A common team policy

    Developers rebase their own feature branch on main to stay current and squash fixups before review. The PR is then merged into main through the platform (merge commit or squash merge). Nobody rebases main itself.

    ⏮️ git reset: soft, mixed and hard

    git reset <commit> moves the current branch pointer back to <commit>. The mode decides what happens to the staging area and your files.

    ModeBranch pointerStaging areaWorking directoryUse when

    🛟 Reflog: recover lost commits

    The reflog is a local diary of every position HEAD (and each branch) has been at: commits, resets, rebases, checkouts. If a commit seems lost after a bad reset or rebase, it is almost always still in the reflog (entries are kept for about 90 days by default).

    bash$ git reset --hard HEAD~3          # oops, three commits gone from the branch

$ git reflog
a1a1a1a (HEAD -> main) HEAD@{0}: reset: moving to HEAD~3
d4d4d4d HEAD@{1}: commit: feat: export to CSV
c3c3c3c HEAD@{2}: commit: feat: filters
b2b2b2b HEAD@{3}: commit: feat: search

$ git reset --hard d4d4d4d         # move main back to where it was
# or keep main as is and save the work on a new branch:
$ git branch recovered d4d4d4d
    📝
    The reflog is local only. It is not pushed or cloned, and it cannot recover changes that were never committed.

    Clean untracked files

    bash$ git clean -n        # dry run: list what WOULD be deleted
Would remove debug.log
Would remove tmp/
$ git clean -fd       # force delete untracked files and directories
$ git clean -fdx      # also delete ignored files (build output, node_modules)
    ⚠️
    Always run git clean -n first. Deleted untracked files were never in Git and cannot be recovered.

    --force-with-lease vs --force

    After rewriting your own branch (rebase, amend), a normal push is rejected because the remote history differs. You must force push.

    git push --force

    Overwrites the remote branch with yours, no questions asked. If a teammate pushed in the meantime, their commits are silently destroyed.

    git push --force-with-lease

    Overwrites only if the remote branch is still where your last fetch saw it. If someone pushed new commits, the push is refused so you can fetch and review first.

    💡
    Make --force-with-lease your habit, and protect main on GitHub/GitLab so nobody can force push to it at all.

    Interview Preparation

    🗺️ Workflow

    Walk me through how you take a task from ticket to production.

    I pull the latest main, create a short-lived branch named after the ticket, implement in small commits with clear messages, and run tests locally. I push and open a pull request with a description linking the ticket. CI runs, teammates review, I address feedback, and once approved and green it is merged (often squash-merged). The pipeline deploys from main, and I verify the change in staging or production and close the ticket.

    Why do teams use version control instead of shared folders?

    It gives a complete, auditable history (who changed what, when and why), lets many people work in parallel on branches, makes it easy to review diffs, and allows rolling back to any earlier state. It also integrates with CI so every change is tested.

    What is the difference between Git and GitHub?

    Git is the distributed version control tool that runs locally. GitHub (like GitLab or Bitbucket) is a hosting platform for Git repositories that adds collaboration: pull requests, code review, issues, permissions and CI. You can use Git without GitHub, but not the other way round.

    How do you keep your feature branch from drifting away from main?

    Keep branches short-lived, and regularly integrate main: git fetch then either git rebase origin/main (for a private branch) or git merge origin/main. Small PRs merged within days avoid large conflicts.

    What makes a good pull request?

    It is small and focused on one change, has a clear title and a description covering what, why, how and testing, links the issue, passes CI, and has tidy commits. Screenshots help for UI changes. The author reviews their own diff first.

    💻 Command line

    What is the difference between a terminal, a shell and Bash?

    The terminal is the window that displays text. The shell is the program that interprets commands inside it. Bash is one specific shell (others are Zsh, Fish, PowerShell).

    Explain chmod 755 and when you would use it.

    Each digit is the sum of read (4), write (2), execute (1) for user, group and others. 755 = rwxr-xr-x: the owner can do everything, everyone else can read and execute. It is typical for scripts and directories. Private keys use 600.

    What does 2>&1 do?

    It redirects file descriptor 2 (stderr) to wherever file descriptor 1 (stdout) currently points. cmd > out.log 2>&1 captures both normal output and errors in one file. Order matters.

    How would you find which process is using port 8080 and stop it?

    lsof -i :8080 or ss -ltnp | grep 8080 shows the PID. Then kill <PID> sends SIGTERM for a graceful stop; kill -9 <PID> only if it refuses.

    How do you find all files containing a string, recursively, with line numbers?

    grep -rn "text" .. Add -i for case-insensitive, --include="*.js" to limit file types, or use find . -name "*.js" | xargs grep -n text.

    📜 Bash scripting

    Why should you quote variables in Bash?

    Unquoted $var undergoes word splitting and glob expansion, so a value with spaces or * becomes several arguments. "$var" keeps it as one argument. rm $file with file="my report.txt" would try to delete two files.

    What does set -euo pipefail do?

    -e exits on any failing command, -u treats unset variables as errors, and -o pipefail makes a pipeline fail if any stage fails. Together they stop scripts from silently continuing after errors.

    What is the difference between $@ and $*?

    Quoted, "$@" expands to each argument as a separate word, preserving spaces inside arguments. "$*" joins all arguments into one string. Use "$@" to pass arguments on.

    How do you check if a command succeeded in a script?

    Use its exit code: if command; then …; fi, or $? right after it (0 = success), or chain with && / ||. With set -e a failing command stops the script.

    How would you run a script every night at 2am and keep its output?

    Add a cron entry with crontab -e: 0 2 * * * /opt/scripts/job.sh >> /var/log/job.log 2>&1. Use absolute paths because cron has a minimal environment.

    🌿 Git basics

    Explain the working directory, staging area and repository.

    The working directory holds the files you edit. git add copies selected changes into the staging area (index), which is the draft of the next commit. git commit saves the staged snapshot permanently into the repository. This lets you craft focused commits.

    What is the difference between git fetch and git pull?

    git fetch downloads new commits and updates remote-tracking branches like origin/main without touching your branches or files. git pull is fetch followed by merge (or rebase) into the current branch.

    What is HEAD?

    A pointer to what you have checked out: normally a branch name, which in turn points to the latest commit. When HEAD points straight at a commit, you are in detached HEAD state.

    A file is in .gitignore but Git still tracks it. Why, and how do you fix it?

    .gitignore only applies to untracked files. The file was committed before. Run git rm --cached <file> to remove it from the index while keeping it locally, then commit.

    What makes a good commit message?

    A short imperative subject (about 50 characters), a blank line, then a body explaining why. One logical change per commit. Many teams use Conventional Commits like fix(auth): handle expired token.

    🔀 Branching and recovery

    Merge vs rebase: when do you use each?

    Merge preserves history and is safe on shared branches; it adds a merge commit. Rebase replays commits on a new base for a linear history but rewrites hashes, so I use it only on my own unpushed or private branch (for example updating from main or squashing before a PR). Never rebase shared history.

    How do you resolve a merge conflict?

    Run git status to see conflicted files, open each, choose the correct code between the <<<<<<<, ======= and >>>>>>> markers, remove the markers, run tests, git add the files, and git commit (or git rebase --continue). git merge --abort backs out.

    Explain git reset --soft, --mixed and --hard.

    All move the current branch to a commit. --soft keeps changes staged; --mixed (default) keeps them in the working directory but unstaged; --hard discards them from both. Use revert instead for pushed commits.

    You accidentally ran git reset --hard. How do you recover?

    Committed work is recoverable: git reflog shows the previous HEAD positions; git reset --hard <hash> or git branch rescue <hash> restores it. Uncommitted changes in tracked files are lost.

    How would you find which commit introduced a bug?

    git bisect start, mark the current commit bad and a known good tag good, then test each commit Git checks out and mark it good or bad until Git names the first bad commit. git bisect run <test-script> automates it. git blame and git log -S help for specific lines or strings.

    🤝 GitHub/GitLab collaboration

    What is the difference between a fork and a branch?

    A branch is a line of development inside one repository. A fork is a separate server-side copy of the whole repository under your account, used when you lack write access, typically in open source. You open a PR from the fork to the original.

    What are protected branches and why use them?

    Branch rules on the platform that block direct pushes and force pushes, require PR approvals and passing status checks, and sometimes require CODEOWNER review. They keep main stable and reviewed.

    Compare GitHub flow, Git flow and trunk-based development.

    GitHub flow: main always deployable, short feature branches and PRs; good for continuous deployment. Git flow: develop, release and hotfix branches; suits versioned, scheduled releases but is heavier. Trunk-based: integrate into main at least daily with feature flags; requires strong automated testing.

    Why prefer --force-with-lease over --force?

    --force-with-lease overwrites the remote branch only if it is still at the commit you last fetched, so it refuses when a teammate has pushed new work. --force overwrites unconditionally and can destroy others' commits.

    A secret was pushed to GitHub. What do you do?

    First revoke/rotate the secret immediately, because it must be considered compromised. Then remove it from the code (use environment variables or a secret manager), and if required purge it from history with git filter-repo or BFG, coordinating a force push. Add the file to .gitignore and enable secret scanning.

    📊 Task 5 · Log analysis script

    ✍️ Write a Bash script top_errors.sh that takes a log file as its argument, fails with a usage message if none is given, and prints the 5 most frequent lines containing ERROR with counts.
    Model answer: #!/usr/bin/env bash
    set -euo pipefail
    log="${1:?Usage: $0 <logfile>}"

    grep "ERROR" "$log" | sort | uniq -c | sort -rn | head -n 5

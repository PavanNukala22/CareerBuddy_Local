    Software Quality Fundamentals

    What quality means, why bugs get expensive, the kinds of testing and who owns quality.

    🎯 What software quality means

    Software quality is how well software does what users need, reliably, now and as it changes. It is not only “no bugs”. A program can pass every test and still be slow, confusing or impossible to change.

    Most teams think about quality in two halves:

    ✅
    External quality
    What users feel: correct results, speed, reliability, security, usability.
    🧱
    Internal quality
    What developers feel: readable code, good tests, simple design, easy to change.
    🔁
    Fitness for purpose
    Does it solve the real problem? Correct code for the wrong requirement is still low quality.
    ⏳
    Sustainability
    Can the team keep shipping safely next month and next year without slowing down?

    The ISO/IEC 25010 standard lists quality characteristics such as functional suitability, performance efficiency, compatibility, usability, reliability, security, maintainability and portability. You do not need to memorise it, but it is a useful reminder that quality has many sides.

    💡
    Internal quality drives external quality over time. Messy code is where tomorrow’s bugs hide.

    💸 The cost of bugs by stage

    A bug costs more the later it is found. Found while typing, it costs seconds. Found in production, it can cost hours of investigation, an emergency release, unhappy customers and sometimes money or reputation.

    Where the bug is foundTypical cost to fixWhy
    While writing code / in the IDESecondsThe context is in your head; nothing else depends on it yet.
    Unit test run on your machineMinutesFast feedback, small change, no one else affected.
    Code reviewMinutes to an hourAnother person explains it; a quick fix before merge.
    CI / integration testingHoursNeed to reproduce, possibly across services and teams.
    QA / staging / UATHours to daysRe-test cycle, release may slip.
    ProductionDays, plus business impactIncident handling, hotfix, data repair, customer trust.

    The exact multipliers quoted in old studies (10×, 100×) vary a lot between projects, so do not treat them as laws. The direction is what matters: earlier feedback is cheaper feedback.

    EXAMPLE · Discount bug

    A developer writes price * 0.1 instead of price * 0.9 for a 10% discount. A unit test catches it in 2 seconds. If it reaches production, every order for a day is charged 10% of the price, and finance must reconcile thousands of orders.

    🐞 Error vs defect vs failure

    These three words are often mixed up. The ISTQB vocabulary separates them as a chain of cause and effect:

    TermWhat it isWhere it livesExample
    Error (mistake)A human action that produces a wrong resultIn a person’s headThe developer misreads the spec and thinks the limit is 100, not 1000.
    Defect (bug, fault)A flaw in the code, design or documentIn the artefactif amount > 100: is written in the code.
    FailureThe system visibly behaves wrongly when the defect is executedAt run timeA customer’s valid ₹500 transfer is rejected.
    An error causes a defect; a defect may cause a failure
    📝
    Not every defect causes a failure. A defect in code that never runs (or only runs on rare input) stays hidden until those conditions happen. This is why tests must hit unusual inputs, not just the happy path.

    🧰 Types of testing

    Different tests answer different questions. A healthy project uses several kinds.

    TypeQuestion it answersScopeSpeedWho usually writes it
    UnitDoes this function/class work on its own?One unit, dependencies fakedMillisecondsDeveloper
    IntegrationDo these parts work together (DB, API, queue)?Two or more real componentsSecondsDeveloper
    End-to-end (E2E)Does a full user journey work?Whole system via UI or APISeconds to minutesDeveloper / QA
    RegressionDid a change break something that used to work?Any level; re-run existing testsVariesEveryone (automated suite)
    SmokeIs the build basically alive?A few critical pathsFastDev / QA / pipeline
    AcceptanceDoes it meet the agreed business requirement?Feature levelVariesQA / product / customer
    PerformanceIs it fast enough under expected and peak load?SystemMinutes to hoursDev / performance engineer
    SecurityCan it be attacked or misused?Code, dependencies, running systemVariesDev / security team
    💡
    “Regression” is a purpose, not a level. Your unit, integration and E2E tests together form your regression suite.

    🔺 The test pyramid

    The test pyramid (popularised by Mike Cohn) says: write many fast unit tests, fewer integration tests and a small number of end-to-end tests.

    LayerHow manySpeedCost to maintainConfidence per test
    E2E / UI (top)FewSlowHigh (brittle)High — real user path
    Integration (middle)SomeMediumMediumMedium
    Unit (base)ManyVery fastLowNarrow but precise

    ✅ Pyramid

    • Most bugs caught by fast unit tests
    • Failures point straight at the broken code
    • Full suite runs in minutes
    • A handful of E2E tests prove the wiring

    ❌ Ice-cream cone (anti-pattern)

    • Mostly manual or UI tests, few unit tests
    • Slow, flaky feedback — hours per run
    • Failures are hard to diagnose
    • Teams stop trusting and running the tests

    Some teams prefer the “testing trophy” (more integration tests) for UI-heavy apps. The shared idea is the same: favour tests that are fast and reliable, and keep slow, brittle tests few.

    ⚖️ Functional vs non-functional testing

    Functional

    Checks what the system does against requirements.

    • Login with valid password succeeds
    • Discount of 10% applied to totals over ₹1000
    • API returns 404 for unknown order

    Non-functional

    Checks how well it does it.

    • Checkout responds in under 300 ms at p95
    • Handles 2,000 requests per second
    • Passwords stored hashed, not plain text
    • Screen reader can use the form
    Non-functional areaExample test or tool
    Performance / loadLoad test with JMeter, Gatling, k6 or Locust
    SecurityDependency scan, SAST, penetration test
    Usability / accessibilityUser testing, axe / Lighthouse accessibility checks
    ReliabilityChaos testing, failover drills
    CompatibilityRun on several browsers / OS versions

    ⬅️ Shift-left and who owns quality

    Shift-left means moving testing and quality checks earlier (to the left on a timeline): clarify requirements before coding, write tests with the code, run checks on every commit, review small changes.

    Who owns quality? The whole team. Modern teams do not “throw code over the wall” to QA. Developers write automated tests for their own code; testers bring exploratory testing skills and risk thinking; product owners define clear acceptance criteria; operations/SRE watch production.

    RoleQuality contribution
    DeveloperUnit/integration tests, clean code, reviews, fixing root causes
    QA / test engineerTest strategy, exploratory testing, automation frameworks, risk analysis
    Product ownerClear acceptance criteria and examples
    ReviewerSecond pair of eyes on correctness, design and tests
    DevOps / SREPipelines, monitoring, alerting, safe deployments
    ⚠️
    “QA will catch it” is a dangerous mindset. Testers find bugs; they cannot test quality into badly built code.

    Some teams also “shift right”: they learn from production using monitoring, feature flags and canary releases. Shift-left and shift-right work together.

    🔄 The quality loop

    Quality is not one step. It is a loop that runs for every change:

    The quality loop — feedback from monitoring feeds the next change
    StepCatches
    Write codeTypos, type errors (IDE, compiler, linter)
    Unit testLogic errors in small pieces
    Code reviewDesign problems, missing cases, readability, security
    CI pipeline“Works on my machine” issues, integration breaks, style violations
    DeployConfiguration and environment problems (with staged rollouts)
    MonitorReal-world failures, performance regressions, unexpected usage

    Key terms

    Test caseA set of inputs, steps and expected results for one check.
    Test suiteA collection of test cases run together.
    AssertionA statement that checks a condition and fails the test if it is false.
    Verification“Did we build the product right?” — matches the spec.
    Validation“Did we build the right product?” — meets the user’s real need.
    RegressionSomething that used to work and now does not.
    Test coverageHow much of the code is executed by the tests.
    Quality gateA rule a change must pass before it moves on (e.g. all tests green).

    Unit Testing

    Write fast, focused tests with pytest and JUnit 5 — and read their output with confidence.

    🧩 What is a unit test?

    A unit test checks a small piece of code — usually one function, method or class — in isolation, automatically, in milliseconds. If it fails, you should know almost exactly where the problem is.

    Good unit tests are FIRST

    LetterPropertyMeaningBreaks it
    FFastRuns in milliseconds so you run the suite constantlyReal network/DB calls, sleep()
    IIndependentNo test depends on another test or on run orderShared global state, tests that must run in sequence
    RRepeatableSame result every time, on any machineUsing the current time, random numbers, real clock
    SSelf-validatingPass/fail decided by assertions, not by a human reading outputTests that just print() results
    TTimelyWritten close to (or before) the production codeTests added months later, if ever
    💡
    A unit test should fail for one reason. If a single test checks ten behaviours, a failure tells you little.

    📐 Arrange – Act – Assert

    Almost every good test follows the same three-part shape, called AAA:

    PartWhat you doTip
    ArrangeSet up inputs, objects and fakesKeep it short; extract helpers or fixtures if it grows
    ActCall the one thing you are testingUsually a single line
    AssertCheck the result or the effectAssert on behaviour, not on internal details
    pythondef test_cart_total_applies_ten_percent_discount():
    # Arrange
    cart = Cart()
    cart.add(Item("book", price=500), qty=2)

    # Act
    total = cart.total(discount_percent=10)

    # Assert
    assert total == 900

    Behaviour-driven teams call the same three parts Given – When – Then.

    🐍 pytest essentials

    pytest is the most popular Python test framework. Test files are named test_*.py (or *_test.py), test functions start with test_, and you check results with a plain assert.

    python# src/shop/pricing.py
def apply_discount(price: float, percent: int) -> float:
    if not 0 <= percent <= 100:
        raise ValueError("percent must be between 0 and 100")
    return round(price * (100 - percent) / 100, 2)

    python# tests/test_pricing.py
import pytest
from shop.pricing import apply_discount

def test_ten_percent_off():
    assert apply_discount(200.0, 10) == 180.0

def test_zero_percent_returns_same_price():
    assert apply_discount(99.99, 0) == 99.99

def test_rejects_negative_percent():
    with pytest.raises(ValueError, match="between 0 and 100"):
        apply_discount(100.0, -5)

@pytest.mark.parametrize("price, percent, expected", [
    (100.0, 0, 100.0),
    (100.0, 50, 50.0),
    (100.0, 100, 0.0),
    (19.99, 15, 16.99),
])
def test_apply_discount_table(price, percent, expected):
    assert apply_discount(price, percent) == expected

    Check the last row: 19.99 × 85 / 100 = 16.9915, which rounds to 16.99. Always verify expected values by hand — never copy them from the code’s own output.

    Fixtures — reusable setup

    pythonimport pytest

@pytest.fixture
def cart():
    c = Cart()
    c.add(Item("pen", price=10), qty=3)
    return c          # each test gets a fresh cart

def test_total(cart):
    assert cart.total() == 30

def test_remove_item(cart):
    cart.remove("pen")
    assert cart.total() == 0

    A fixture is requested by naming it as a parameter. By default it is created again for every test (scope="function"), which keeps tests independent. Use yield inside a fixture to run clean-up code after the test. Put shared fixtures in conftest.py — pytest finds them automatically.

    📝
    Floating-point results: compare with pytest.approx, e.g. assert 0.1 + 0.2 == pytest.approx(0.3). A plain == would fail.

    🧼 Pure functions, side effects and project layout

    A pure function returns a value that depends only on its inputs and changes nothing outside itself. It is the easiest code in the world to test: call it, check the result.

    Code with side effects — reading the clock, calling an API, writing a file or database — is harder, because the result depends on the outside world.

    Hard to test

    pythonfrom datetime import date

def is_weekend_sale():
    # depends on the real clock
    return date.today().weekday() >= 5

    Easy to test

    pythonfrom datetime import date

def is_weekend_sale(today: date) -> bool:
    return today.weekday() >= 5

def test_saturday_is_sale():
    assert is_weekend_sale(date(2024, 6, 1))

    1 June 2024 was a Saturday (weekday() == 5; Monday is 0). Passing the date in makes the test repeatable on any day.

    💡
    Design trick — functional core, imperative shell: keep the business logic pure, and push I/O to a thin outer layer. Then most of your code can be unit-tested without mocks.

    Test Doubles & Test Design

    Mocks, stubs and fakes; designing the right test cases; coverage, TDD, BDD and keeping tests trustworthy.

    🎭 The five kinds of test double

    A test double is any object that stands in for a real dependency during a test — like a stunt double in a film. Gerard Meszaros named five kinds:

    DoubleWhat it doesUsed forExample
    DummyPassed around but never usedFilling a required parameterNone or an empty object for an unused logger
    StubReturns canned answersControlling inputs to the code under testExchange-rate service that always returns 83.0
    FakeA working but simplified implementationRealistic behaviour without the costIn-memory repository using a dict instead of a database
    MockPre-programmed with expectations; the test verifies the callsChecking outputs — interactionsVerify email.send() was called once with the customer’s address
    SpyWraps or records calls to a real (or stub) objectChecking what happened while keeping real behaviourMockito spy(realList) then verify(list).add("x")
    💡
    Rule of thumb: stubs feed data in, mocks check messages out. Stub queries; mock commands.

    In everyday speech people call all of these “mocks”, and libraries like unittest.mock and Mockito can create any of them. The distinction matters when you decide what to assert.

    🐍 Mocking in Python: unittest.mock and monkeypatch

    def __init__(self, payment_gateway, mailer):

    ☕ Mocking in Java with Mockito

    javaimport static org.junit.jupiter.api.Assertions.*;
import static org.mockito.ArgumentMatchers.*;
import static org.mockito.Mockito.*;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock PaymentGateway gateway;
    @Mock Mailer mailer;
    @InjectMocks OrderService service;   // built with the two mocks

    @Test
    void successfulChargeSendsConfirmation() {
        when(gateway.charge(7L, 500.0)).thenReturn(ChargeResult.ok());

        boolean ok = service.place(new Order(7L, 500.0, "a@x.com"));

        assertTrue(ok);
        verify(mailer).send("a@x.com", "Order confirmed");
    }

    @Test
    void failedChargeSendsNothing() {
        when(gateway.charge(anyLong(), anyDouble())).thenReturn(ChargeResult.failed());

        service.place(new Order(7L, 500.0, "a@x.com"));

        verify(mailer, never()).send(anyString(), anyString());
    }

    @Test
    void gatewayTimeoutPropagates() {
        when(gateway.charge(anyLong(), anyDouble()))
            .thenThrow(new GatewayTimeoutException());

        assertThrows(GatewayTimeoutException.class,
            () -> service.place(new Order(1L, 1.0, "b@x.com")));
    }
}

    🕸️ Over-mocking and dependency injection

    Mocks are powerful, but too many of them make tests brittle and dishonest:

    • Brittle — tests check how the code works (which private helper was called, in what order) so any refactor breaks them, even when behaviour is unchanged.
    • Dishonest — the mock returns what you think the real dependency returns. If you are wrong, every test passes and production fails.
    • Hard to read — 20 lines of mock setup for 1 line of action.
    GuidelineWhy

    📊 Code coverage: what it does and does not mean

    Coverage measures which code your tests execute. Tools: coverage.py / pytest-cov for Python, JaCoCo for Java.

    pythondef shipping_fee(total, is_member):

    ⚠️
    100% coverage does not mean bug-free. A test can execute code without asserting anything useful. Coverage shows what is not tested; it cannot prove what is tested well.

    🎲 Flaky tests and test smells

    A flaky test passes and fails on the same code without any change. It destroys trust: people start re-running CI until it goes green and ignore real failures.

    CauseExampleFix

    Order dependenceTest B relies on data left by test AFresh setup per test; run in random order (pytest-randomly)
    Async / timingsleep(1) then assert; slower CI machine failsWait for a condition with a timeout, not a fixed sleep
    Shared resourcesTwo parallel tests use the same DB row or portUnique data per test; isolated containers
    Network / external servicesCalls a real third-party APIStub it; keep a few contract/integration tests
    RandomnessRandom input without a fixed seedFix the seed or log it
    Unordered collectionsAsserts on set/dict iteration orderSort, or compare as sets
    💡

    🧭 A systematic debugging method

    Debugging is not guessing and changing random lines. It is the scientific method applied to code.

    🔍 git bisect and rubber-duck debugging

    “It worked in last month’s release.” git bisect uses binary search over your commit history to find the commit that introduced a bug. With 1,000 commits it needs only about 10 steps (2¹⁰ = 1024).

    bashgit bisect start
git bisect bad                 # current commit is broken
git bisect good v2.3.0         # this tag was fine
# git checks out a commit in the middle; test it, then tell git:
git bisect good                # or: git bisect bad
# ...repeat until git prints "<sha> is the first bad commit"
git bisect reset               # return to where you started

# Fully automatic: the script exits 0 = good, 1-127 = bad (125 = skip)

    💡

    🚨 Debugging in production safely

    You usually cannot attach a debugger to a live production server. Instead you rely on observability — the three pillars:

    PillarAnswersTools (examples)
    LogsWhat happened, in detail, for this request?ELK / OpenSearch, Splunk, Loki, CloudWatch
    MetricsHow much / how often / how fast, over time?Prometheus + Grafana, Datadog
    TracesWhere did this request spend its time across services?OpenTelemetry, Jaeger, Zipkin
    1. Check dashboards: when did error rate or latency change? Does it line up with a deployment?
    2. Find a failing request’s trace/correlation ID and follow it through logs of every service.
    3. Stop the bleeding first — roll back or switch off the feature flag — then investigate.
    4. Reproduce in a lower environment with the same data shape (anonymised).
    5. Fix, add a regression test, deploy, and watch the metrics return to normal.
    6. Write a blameless post-incident review.
    ⚠️

    Code Reviews

    Review code like a senior: what to check, how to give and receive feedback, and what to automate away.

    👀 Why we review code

    A code review (or pull request / merge request review) is when teammates read a change before it is merged. Finding bugs is only one of the benefits.

    🐞
    Catch defects early
    Logic errors, missed edge cases and security holes — before they reach users.
    🧠
    Share knowledge
    At least two people understand every change; no single point of failure.
    📏
    Keep the codebase consistent
    Shared conventions, patterns and architecture.
    🎓
    Mentor and learn
    Juniors learn from seniors — and seniors learn new ideas too.
    🔐
    Accountability & audit
    Many regulated teams must show every change was reviewed.
    🧹
    Improve design
    A fresh reader spots confusing names and over-complex code.
    📝
    Reviews are a conversation about the code, never a judgement of the person. The goal is that the codebase gets better with every merge.

    ✅ What reviewers check

    AreaQuestions to ask
    CorrectnessDoes it do what the ticket says? Edge cases: empty, null, zero, large, concurrent? Errors handled?
    DesignIs the logic in the right layer/class? Does it fit the existing architecture? Is it over-engineered?
    ReadabilityClear names? Small functions? Would a new teammate understand it in 6 months? Comments explain why, not what?
    TestsAre there tests for the new behaviour and the bug being fixed? Do they assert something meaningful? Would they fail if the code were wrong?
    SecurityInput validated? SQL built with parameters? Secrets kept out of code and logs? Authorisation checked?
    PerformanceN+1 queries? Loops inside loops on big data? Unbounded memory? Missing pagination or indexes?
    OperabilityUseful logs and metrics? Feature flag? Safe migration and rollback?
    Docs & APIPublic APIs documented? Breaking changes flagged? README / changelog updated?

    💡

    📦 PR size and a good description

    Small pull requests get faster and better reviews. Studies of review effectiveness (e.g. the SmartBear/Cisco study) found that reviewers find fewer defects per line once a review goes beyond roughly 200–400 lines, or past an hour of reviewing.

    ~50–200 linesReviewed within hours, with real attention
    ~400 linesStill reviewable, but needs a focused block of time
    1,000+ lines“LGTM” after a skim — bugs slip through; long wait; painful merge conflicts

    How to keep PRs small

    • Separate refactoring from behaviour changes (two PRs).
    • Split a feature into slices: data model → API → UI.
    • Hide unfinished work behind a feature flag so partial code can merge safely.
    • Use stacked PRs when one change depends on another.

    Good review comments are kind, specific, and explain why. Prefer questions to commands, and make the weight of each comment clear.

    🤝 Receiving feedback

    • Assume good intent. The reviewer is spending their time to help your code succeed.
    • Don’t take it personally. Comments are about the code, and code can always improve.
    • Reply to every comment — “Done”, “Fixed in abc123”, or a reasoned reply.
    • Push back politely with reasons if you disagree: data, constraints, trade-offs.
    • If a question was needed, the code may be unclear — often the best answer is to improve a name or add a comment, not to explain in the PR.
    • Self-review first. Read your own diff before asking anyone; you will catch the debug prints and TODOs.
    • Say thanks. Reviews are work.

    CI/CD Awareness

    How pipelines build, test and ship your code — and what every developer needs to know to keep them green and fast.

    🔁 CI vs continuous delivery vs continuous deployment

    PracticeWhat it meansRelease to production
    Continuous Integration (CI)Everyone merges small changes to the main branch often (at least daily). Each merge is automatically built and tested.Not covered

    Keeping pipelines fast

    • Run the fastest, most likely-to-fail checks first (lint, unit tests) — fail fast.
    • Cache dependencies; reuse Docker layers.
    • Run independent jobs in parallel; shard large test suites across runners.
    • Keep slow E2E suites small; run the full set nightly or before release.
    • Only run what changed in monorepos (path filters).
    • Fix or quarantine flaky tests — retries hide problems and waste time.

    Feature flags separate deployment from release: code ships to production switched off, then is turned on for staff, then 10% of users, then everyone. If something breaks, turn the flag off — no redeploy. Tools: LaunchDarkly, Unleash, Flagsmith, or a simple config table.

    Rollback

    • Redeploy the previous artifact version (this is why artifacts are versioned and immutable).
    • Switch traffic back (blue-green) or set the canary to 0%.
    • Turn off the feature flag.
    • Database migrations make rollback hard — use expand-and-contract: add new columns first, migrate, and drop old ones only in a later release, so both versions work against the schema.
    • Roll forward (ship a quick fix) only when it is truly faster and safer than rolling back.

    Interview Preparation

    Click a question to reveal a model answer.

    🎯 Quality fundamentals

    What is the difference between an error, a defect and a failure?

    An error is a human mistake (misreading a requirement). It can produce a defect — a flaw in the code or document. When the defective code runs under the right conditions, the system shows a failure — visibly wrong behaviour. Not every defect causes a failure; some sit in rarely executed paths.

    Explain the test pyramid. Why is the ice-cream cone a problem?

    The pyramid has many fast unit tests at the base, fewer integration tests, and few slow end-to-end tests at the top. This gives fast, precise, reliable feedback. The ice-cream cone inverts it — mostly manual/UI tests — so feedback is slow, flaky and expensive, failures are hard to locate, and people stop trusting the suite.

    What does “shift-left” mean in practice?

    Finding problems earlier: clarifying acceptance criteria before coding, writing unit tests with the code (or first, with TDD), running linters and tests in pre-commit and CI on every push, reviewing small PRs, and doing security scanning in the pipeline rather than at the end.

    Who is responsible for quality in an agile team?

    The whole team. Developers own automated tests and clean code for their changes; testers bring strategy, exploratory testing and risk analysis; product owners define clear acceptance criteria; reviewers and ops add further checks. Quality cannot be tested in at the end by one role.

    What is the difference between verification and validation?

    Verification: are we building the product right — does it meet the specification? (reviews, unit tests). Validation: are we building the right product — does it meet the user’s real need? (acceptance testing, user feedback).

    🧩 Unit testing

    What makes a good unit test?

    FIRST: fast, independent, repeatable, self-validating and timely. It tests one behaviour, follows Arrange-Act-Assert, has a descriptive name, asserts on observable behaviour rather than internals, and fails for a clear reason with a helpful message.

    How do you test that a function raises an exception in pytest and in JUnit 5?

    pytest: with pytest.raises(ValueError, match="percent"): apply_discount(100, -5). JUnit 5: var ex = assertThrows(IllegalArgumentException.class, () -> calc.apply(100, -5)); then optionally assertEquals("...", ex.getMessage()).

    What are pytest fixtures and how do they differ from JUnit’s @BeforeEach?

    Fixtures are functions decorated with @pytest.fixture that tests request by naming them as parameters. They can have scopes (function, class, module, session), use yield for teardown, depend on other fixtures, and be shared via conftest.py. @BeforeEach is a method that runs before every test in the class; it is less granular — every test gets the same setup.

    How do you test code that depends on the current time or random numbers?

    Make the dependency explicit: pass the date/clock or random generator in (dependency injection), e.g. Java’s Clock or a today parameter. Then the test passes a fixed value. Alternatives: freeze time with a library (freezegun, time-machine) or seed the generator.

    Why are parameterised tests useful? Any downside?

    They run one test body over many input/expected rows, removing duplication and making the cases easy to scan and extend — ideal for boundary values. Downside: if cases need different setup or assertions, forcing them into one table makes the test harder to read; then write separate tests.

    🎭 Mocks and test design

    What is the difference between a mock and a stub?

    A stub supplies canned answers so the code under test gets controlled inputs; you assert on the result. A mock is set up with expectations and you verify the interactions — that a call happened with the right arguments. Stubs for queries, mocks for commands.

    What are the dangers of over-mocking?

    Tests become coupled to implementation details and break on every refactor; they can pass while production fails because the mock’s behaviour differs from the real dependency; and setup becomes long and hard to read. Mock only at boundaries you own, use fakes or real objects for the rest, and back mocks with some integration tests.

    Explain boundary value analysis with an example.

    Bugs cluster at the edges of ranges. For a field valid from 1 to 100, test 0 and 1 at the lower edge and 100 and 101 at the upper edge (three-value BVA adds 2 and 99). This catches mistakes such as using < instead of <=.

    Is 100% code coverage a good goal?

    Coverage is a useful negative indicator: it shows code no test executes. 100% does not prove correctness — tests can run code without meaningful assertions, and line coverage misses untaken branches. Chasing 100% often yields low-value tests. Better: a sensible threshold, branch coverage, checking new code, and mutation testing for strength.

    Describe TDD. When would you not use it?

    Red: write a small failing test. Green: write the simplest code to pass. Refactor: improve the design with tests green. Repeat in tiny steps. It is less useful for exploratory spikes, throwaway prototypes, or UI layout work where the expected result is not yet known — though you can add tests once the design settles.

    🔍 Debugging

    Walk me through how you debug a bug you have never seen before.

    Reproduce it reliably (exact inputs, environment). Isolate — shrink the input and the code path, ideally into a failing unit test. Form one hypothesis, test it with logs or a debugger, change one thing at a time. Fix the root cause, verify with the reproduction and full suite, and commit the failing test as a regression test.

    How do you read a stack trace?

    Find the exception type and message first. In Python, the last frame is where it was raised (most recent call last); in Java, the top frame is. Look for the first frame in your own code rather than library code. For wrapped exceptions, read the final “Caused by” for the root cause.

    When would you use logging instead of a debugger?

    When you cannot pause the program: production, distributed systems, timing-sensitive or concurrency bugs (pausing changes behaviour), or problems that only appear over time. Logs with levels, structured fields and correlation IDs let you reconstruct what happened. A debugger is better for exploring local, reproducible logic bugs.

    What is git bisect and when is it useful?

    A binary search over commit history. You mark a known good and a known bad commit; git checks out midpoints and you mark each good or bad until it identifies the first bad commit. git bisect run <script> automates it. Useful for regressions where “it used to work” and many commits have landed since.

    How do you debug an intermittent failure in production?

    Look at metrics to find when it started and correlate with deploys or traffic; use traces and correlation IDs to follow failing requests across services; check for patterns (one host, one region, specific inputs, time of day). Mitigate first (roll back, feature flag). Add targeted logging if needed, reproduce in staging, then fix and add a regression test. Suspect race conditions, resource exhaustion and timeouts.

    👀 Code reviews

    What do you look for when reviewing a pull request?

    In order of importance: correctness and edge cases, tests that prove the behaviour, security (input validation, secrets, authorisation), design fit, readability and naming, performance hot spots, and operability (logs, flags, migrations). Formatting is left to tools.

    How do you give critical feedback without upsetting the author?

    Comment on the code, not the person. Be specific, explain the impact and the why, suggest an option, and ask questions rather than issue commands. Label weight (blocking vs nit), mention what is done well, and move long discussions to a quick call.

    Why should pull requests be small?

    Small PRs are reviewed faster and more thoroughly; reviewer attention and defect detection drop sharply on large diffs. They also reduce merge conflicts, make bisecting and rollback easier, and keep work flowing. Split refactors from features and use feature flags for incomplete work.

    What should be automated rather than reviewed by humans?

    Formatting (Black, Prettier), linting (ruff, ESLint, Checkstyle), type checks, test runs and coverage, static analysis and security scanning (SonarQube, Semgrep, dependency scanners). These run in pre-commit hooks and CI as required checks, so humans focus on logic and design.

    Name some code smells and how you would fix them.

    Long method → extract methods. Duplicated code → extract a shared function. Magic numbers → named constants. Deep nesting → guard clauses. God class → split by responsibility. Long parameter list → parameter object. Always refactor with tests in place.

    🚀 CI/CD

    What is the difference between continuous delivery and continuous deployment?

    Both keep every passing change releasable through an automated pipeline. In continuous delivery a person approves the production release; in continuous deployment it goes to production automatically with no manual step.

    What stages would you put in a CI pipeline, and in what order?

    Checkout → install/build → lint and format check → unit tests (fast, fail early) → static analysis/security scan → package an immutable artifact → deploy to staging → integration/E2E/smoke tests → deploy to production with a safe strategy. Fast, cheap checks come first.

    The main build is red and it’s your commit. What do you do?

    Treat it as top priority. Tell the team. If I can fix it within minutes, do it; otherwise revert my commit immediately to make main green, then investigate on a branch. Never skip or comment out the failing test to get green.

    Compare blue-green and canary deployments.

    Blue-green keeps two full environments and switches all traffic at once, giving instant rollback but costing double infrastructure. Canary routes a small percentage of traffic to the new version and increases it while monitoring, limiting blast radius but needing good metrics and traffic control.

    What are the DORA metrics and why do they matter?

    Deployment frequency and lead time for changes (speed), change failure rate and time to restore service (stability). DORA research shows high performers do well on both; they help teams find bottlenecks — but should not be used to rank individuals.

    Relational Fundamentals

    What a relational database is, how data is organised in tables, and how an application talks to it.

    🗄️ What is a database?

    A database is an organised collection of data that a program can store, search and change safely. Your phone contacts, a bank's accounts and an online shop's orders all live in databases.

    A DBMS (Database Management System) is the software that manages the data: it stores it on disk, answers queries, enforces rules and lets many users work at the same time without corrupting anything. A RDBMS (Relational DBMS) is a DBMS that stores data in tables made of rows and columns, and links tables using keys. You talk to an RDBMS using SQL (Structured Query Language).

    🐘
    PostgreSQL
    Open source, standards-focused, rich types (JSONB, arrays), powerful extensions.
    🐬
    MySQL
    Open source, very popular for web apps; InnoDB is its default transactional engine.
    🪶
    SQLite
    A database in a single file, embedded inside apps and phones. No server.
    🏢

    Commercial RDBMSs common in large enterprises.

    💡

    🧱 Tables, rows, columns and schema

    🔑 Keys and constraints

    Constraints are rules the database enforces on every insert and update. They protect data quality even when application code has bugs.

    ConstraintWhat it guaranteesShop example
    PRIMARY KEYEach row has a unique, non-null identifiercustomers.customer_id
    FOREIGN KEYA value must exist in another table's keyorders.customer_id → customers
    UNIQUENo two rows share the value (NULLs are allowed)customers.email
    NOT NULLThe column must always have a valueproducts.name
    CHECKA condition must be trueprice >= 0, quantity > 0
    DEFAULTValue used when none is suppliedstatus DEFAULT 'pending'
    sqlCREATE TABLE orders (
    order_id     INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  INTEGER NOT NULL REFERENCES customers (customer_id),
    order_date   DATE NOT NULL DEFAULT CURRENT_DATE,
    status       VARCHAR(20) NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','shipped','delivered','cancelled'))
);
    EXAMPLE · A constraint saving you
    sqlINSERT INTO orders (customer_id) VALUES (99);
-- ERROR: insert or update on table "orders" violates foreign key constraint
--        "orders_customer_id_fkey"
-- DETAIL: Key (customer_id)=(99) is not present in table "customers".

    There is no customer 99, so the database refuses to create an “orphan” order.

    A composite key uses several columns together. In order_items the primary key is (order_id, product_id): the same product can appear in many orders, but only once per order.

    ⚠️
    Foreign keys also control deletes. By default you cannot delete a customer who still has orders. ON DELETE CASCADE deletes child rows automatically — powerful, but use it deliberately.

    🔗 Relationships: 1:1, 1:N and M:N

    Tables are linked through keys. There are three kinds of relationship:

    TypeMeaningHow it is builtExample
    One-to-one (1:1)One row matches at most one rowFK that is also UNIQUE (or shared PK)customer ↔ customer_profile
    One-to-many (1:N)One parent, many childrenFK on the “many” sidecustomer → orders
    Many-to-many (M:N)Many on both sidesA junction table with two FKsorders ↔ products via order_items

    An order can contain many products and a product can be in many orders. You cannot store that with a single foreign key, so order_items sits in the middle. It also stores facts about the pair: quantity and unit_price.

    sql-- 1:1 example: at most one profile per customer
CREATE TABLE customer_profiles (
    customer_id  INTEGER PRIMARY KEY REFERENCES customers (customer_id),
    birthday     DATE,
    newsletter   BOOLEAN NOT NULL DEFAULT false
);
    1️⃣
    1:1
    Split rarely used or sensitive columns into their own table.
    🌳
    1:N
    The most common link. The child holds the parent's key.
    🔀
    M:N
    Always resolved with a junction (bridge / link) table.
    💡
    A self-referencing relationship links a table to itself. customers.referred_by points at another customer — used later for self joins and recursive queries.

    ⚖️ SQL vs NoSQL at a glance

    Relational (SQL) databases are not the only option. NoSQL is an umbrella term for databases that use other models: documents, key-value pairs, wide columns or graphs.

    AspectRelational (SQL)NoSQL
    Data modelTables with fixed columnsDocuments, key-value, column-family, graph
    SchemaDefined up front, enforcedFlexible; often checked by the app
    RelationshipsJoins and foreign keysUsually embedded or denormalised
    TransactionsStrong ACID by defaultVaries; many now offer ACID per document or more
    Scaling styleMostly vertical + read replicasOften designed for horizontal sharding
    ExamplesPostgreSQL, MySQL, SQL ServerMongoDB, Redis, Cassandra, Neo4j
    📝
    The line is blurry: PostgreSQL stores JSON documents with JSONB, and MongoDB supports multi-document transactions. Pick based on your data's shape and consistency needs, not fashion. For orders, payments and stock, a relational database is the usual default.

    🔌 How an application talks to a database

    Your code never reads the database files directly. It goes through a driver — a library that opens a network connection to the database server and speaks its wire protocol.

    From a function call in your app to rows coming back
    1. The app asks the driver for a connection (usually from a pool).
    2. It sends an SQL statement, ideally with parameters kept separate from the SQL text.
    3. The server parses the SQL, the planner picks the cheapest way to run it.
    4. The executor reads tables and indexes and builds the result.
    5. Rows stream back; the driver turns them into objects, tuples or maps.
    pythonimport psycopg  # PostgreSQL driver for Python

with psycopg.connect("postgresql://shop_app@localhost/shop") as conn:
    rows = conn.execute(
        "SELECT name, city FROM customers WHERE city = %s", ("Pune",)
    ).fetchall()
print(rows)   # [('Asha Rao', 'Pune'), ('Chen Li', 'Pune')]
    DriverLibrary that implements the database protocol: psycopg (Python), JDBC drivers (Java), mysql2 (Node).
    Connection stringHost, port, database, user and options in one URL.
    Client toolInteractive program for humans: psql, mysql, pgAdmin, MySQL Workbench.

    🗣️ SQL sublanguages: DDL, DML, DCL, TCL

    SQL commands fall into families. Interviewers love asking which command belongs where.

    FamilyStands forPurposeCommands
    DDLData Definition LanguageCreate and change structureCREATE, ALTER, DROP, TRUNCATE
    DMLData Manipulation LanguageRead and change rowsSELECT, INSERT, UPDATE, DELETE
    DCLData Control LanguagePermissionsGRANT, REVOKE
    TCLTransaction Control LanguageGroup changes into unitsBEGIN, COMMIT, ROLLBACK, SAVEPOINT
    sql-- DDL: change structure
ALTER TABLE customers ADD COLUMN phone VARCHAR(30);

-- DML: change data
UPDATE customers SET phone = '+91 98000 00000' WHERE customer_id = 1;

-- DCL: control access
GRANT SELECT ON customers TO reporting_user;

-- TCL: make changes atomic
BEGIN;
UPDATE products SET stock = stock - 1 WHERE product_id = 1;
INSERT INTO orders (customer_id) VALUES (1);
COMMIT;
    📝
    Some books put SELECT in its own group, DQL (Data Query Language). Also note: in MySQL, DDL statements cause an implicit commit, while PostgreSQL can run most DDL inside a transaction and roll it back.

    Data Modelling and Normalisation

    Turn requirements into a clean schema: entities, types, keys and the normal forms.

    🧭 From requirements to entities

    Good schemas start from plain-English requirements, not from SQL. Read the requirements and underline the nouns (candidate entities and attributes) and the verbs (relationships).

    EXAMPLE · Shop requirements
    • A customer has a name, a unique email and an optional city.
    • A customer can be referred by another customer.
    • A customer places zero or more orders; each order has a date and a status.
    • An order contains one or more products, each with a quantity and the price paid.
    • A product has a name, category, current price and stock level.
    Found in the textBecomesShop result
    Nouns with their own identityEntities → tablescustomers, orders, products
    Describing wordsAttributes → columnsname, email, price, status
    Verbs between nounsRelationships → keysplaces (1:N), contains (M:N)
    Facts about a relationshipColumns on a junction tablequantity, unit_price in order_items
    A repeatable modelling process
    💡
    Ask “can this have more than one?” for every attribute. If an order can have several products, products cannot be a single column on orders.

    🗺️ ER diagrams and crow's foot notation

    An Entity-Relationship (ER) diagram draws entities as boxes and relationships as lines. The most common style in industry is crow's foot: the line ends show how many rows can be on each side.

    Line endMeaning
    Single bar |Exactly one
    Circle + bar o|Zero or one (optional)
    Crow's foot + bar |<One or many
    Circle + crow's foot o<Zero or many

    Entities and relationships only. Good for talking to business people.
    🧩
    Logical model
    Adds attributes, keys and normalisation, still database-independent.
    🛠️

    Real tables, types, indexes for one specific RDBMS.
    📝

    🔢 Choosing data types

    The right type saves space, speeds up queries and blocks bad data. The most important rule: never store money in floating-point types.

    NeedPostgreSQLMySQLNotes
    Whole numbersINTEGER, BIGINTINT, BIGINTUse BIGINT for ids in large/fast-growing tables
    Money / exact decimalsNUMERIC(10,2)DECIMAL(10,2)Exact. 10 digits in total, 2 after the point
    Approximate numbersREAL, DOUBLE PRECISIONFLOAT, DOUBLEScientific values; 0.1 + 0.2 is not exactly 0.3
    Short textVARCHAR(n) or TEXTVARCHAR(n)In Postgres TEXT and VARCHAR perform the same
    Long textTEXTTEXT, MEDIUMTEXTMySQL TEXT columns have extra limits (indexing needs a prefix length)
    True/falseBOOLEANBOOLEAN (= TINYINT(1))MySQL has no real boolean type
    Date onlyDATEDATEBirthdays, order dates
    Date + timeTIMESTAMP / TIMESTAMPTZDATETIME / TIMESTAMPPrefer time-zone-aware storage for events
    Unique idsUUIDBINARY(16) or CHAR(36)Postgres has a native 16-byte UUID type
    Semi-structuredJSON, JSONBJSONPostgres JSONB is binary and indexable with GIN
    sql-- Why not FLOAT for money?
SELECT 0.1::float8 + 0.2::float8;      -- 0.30000000000000004
SELECT 0.1::numeric + 0.2::numeric;    -- 0.3
    ⚠️
    Time zones: Postgres TIMESTAMPTZ stores an absolute instant (normalised to UTC) and shows it in the session time zone; plain TIMESTAMP stores no zone at all. In MySQL, TIMESTAMP is converted to UTC for storage but only covers 1970–2038, while DATETIME stores the wall-clock value as given.
    💡
    Postgres JSON keeps the exact text (including key order and duplicates); JSONB parses it into a binary form that is faster to query. Use JSONB unless you must preserve the original text.

    Here is the full PostgreSQL schema behind the sample data. Notice how every requirement became a type or a constraint.

    sqlCREATE TABLE customers (

    name         VARCHAR(100) NOT NULL,

    name        VARCHAR(120) NOT NULL,

);

CREATE TABLE orders (
    order_id     INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  INTEGER NOT NULL REFERENCES customers (customer_id),

    unit_price  NUMERIC(10,2) NOT NULL,          -- price at the time of sale
    PRIMARY KEY (order_id, product_id)
);

    🧹 Normalisation: 1NF, 2NF and 3NF

    Normalisation removes redundancy so each fact is stored once. Redundant data causes anomalies: an update changes one copy but not another, a delete loses unrelated facts, an insert is impossible without dummy data.

    1NF — atomic values, no repeating groups

    Before: one cell holds a list.

    order_idcustomerproducts
    101Asha RaoLaptop, Coffee Mug
    103Asha RaoDesk Chair, Coffee Mug

    After: one row per order line, each cell holds one value.

    order_idproduct
    101Laptop
    101Coffee Mug
    103Desk Chair
    103Coffee Mug

    2NF — no partial dependency on part of a composite key

    Before: key is (order_id, product_id) but product_name depends only on product_id.

    order_idproduct_idproduct_namequantity
    1014Coffee Mug2
    1034Coffee Mug4
    1054Coffee Mug1

    Renaming the mug means updating three rows. After: move product_name to products; keep only quantity and unit_price in order_items.

    3NF — no transitive dependency (non-key → non-key)

    Before: customer_city depends on customer_id, which depends on the key order_id.

    order_idcustomer_idcustomer_city
    1011Pune
    1031Pune

    If Asha moves, every order row needs updating. After: city lives only in customers.

    💡
    Memory hook: every non-key column must depend on the key (1NF), the whole key (2NF), and nothing but the key (3NF). BCNF tightens 3NF so every determinant is a candidate key.

    ⚖️ Denormalisation trade-offs

    Denormalisation deliberately adds redundancy to make reads faster or simpler. It is a tool for measured performance problems, not a starting point.

    Benefits

    • Fewer joins on hot read paths
    • Pre-computed totals for dashboards
    • Simpler reporting queries

    Costs

    • Copies can drift out of sync
    • Writes become slower and more complex
    • More storage and more code to test
    EXAMPLE · Storing an order total

    Adding orders.total_amount avoids summing order_items on every page view. But now every insert, update or delete of an order line must also update the total — in a transaction, a trigger, or application code — or the numbers will disagree.

    TechniqueUse when
    Materialised viewHeavy reports that can be a few minutes stale
    Summary / rollup tableDashboards over millions of rows, refreshed by a job
    Cached column + triggerA hot value read far more often than written
    Separate analytics storeOLAP workloads (data warehouse, columnar database)
    📝
    Copying unit_price into order_items is not denormalisation — it is a different fact (the historical price), so it belongs there.

    🆔 Surrogate vs natural keys

    A natural key comes from the real world (email, ISBN, country code). A surrogate key is a meaningless generated id (identity integer or UUID).

    AspectNatural keySurrogate key
    MeaningHas business meaningNo meaning, just an id
    StabilityCan change (people change emails)Never changes
    SizeOften wide stringsSmall (4–8 byte int, 16 byte UUID)
    JoinsSlower on wide keysFast, compact foreign keys
    Duplicate protectionBuilt inNeeds an extra UNIQUE constraint

    Common practice: a surrogate primary key plus a UNIQUE constraint on the natural key. That is exactly what customers does with customer_id and email.

    🔢
    Identity / sequence
    Small, ordered, great index locality. Reveals row counts if exposed in URLs.
    🎲
    UUID v4
    Random, globally unique, safe to generate in the app. Random inserts fragment B-tree indexes.
    ⏱️
    UUID v7
    Time-ordered UUID: global uniqueness with better index locality.

    SQL Basics

    Read, filter, sort and change data with SELECT, WHERE, ORDER BY, INSERT, UPDATE and DELETE.

    🔍 SELECT and column aliases

    SELECT reads data. You list the columns you want, then FROM the table. SELECT * returns every column — handy when exploring, but avoid it in application code: it fetches data you do not need and breaks when columns are added or reordered.

    sqlSELECT name, price, stock,
       price * stock AS stock_value      -- computed column with an alias
FROM   products
ORDER  BY stock_value DESC;

    Result:

    namepricestockstock_value
    Laptop900.0054500.00
    Headphones120.00202400.00
    Coffee Mug12.501001250.00
    Desk Chair150.0081200.00
    Notebook4.0000.00

    An alias renames a column or table in the result. AS is optional, but writing it makes intent clear. Table aliases (FROM products p) shorten long queries and are required for self joins.

    💡
    Need spaces or capitals in an alias? Quote it: AS "Stock Value" in PostgreSQL (double quotes), or with backticks / double quotes in MySQL. Single quotes are for string values, not names.

    SQL keywords are case-insensitive (select = SELECT). Upper-case keywords and lower-case names is the most common style. End statements with ;.

    Deep pages with OFFSET 100000 are slow: the database still reads and throws away 100,000 rows. Use keyset pagination instead: WHERE order_id > :last_seen_id ORDER BY order_id LIMIT 20.
    ⚠️
    DISTINCT is not a fix for duplicate rows caused by a wrong join. Find the join that multiplies rows instead of hiding it.

    Always list the columns. Columns you leave out get their DEFAULT (or NULL).

    🧠 Logical order of query execution

    You write SELECT first, but the database logically evaluates the clauses in a different order. Knowing this order explains many confusing errors.

    Logical evaluation order of a SELECT statement
    ConsequenceWhy

    You can use a SELECT alias in ORDER BYORDER BY runs after SELECT

    sqlSELECT name, price * stock AS stock_value

    Joins and Aggregation

    Combine tables with joins, then summarise rows with COUNT, SUM, AVG, GROUP BY and HAVING.

    🔗 INNER JOIN: matching rows only

    Data is split across tables, so most real queries join them back together. A join pairs rows from two tables using a condition in ON, usually foreign key = primary key.

    sqlSELECT o.order_id, c.name, o.status
FROM   orders o
INNER JOIN customers c ON c.customer_id = o.customer_id
ORDER  BY o.order_id;

    Result:

    order_idnamestatus
    101Asha Raodelivered
    102Ben Carterdelivered
    103Asha Raoshipped
    104Chen Licancelled
    105Dara Okaforpending

    INNER JOIN (or just JOIN) keeps only pairs where the condition is true. Eva Novak has no orders, so she does not appear. Asha appears twice because she has two orders.

    EXAMPLE · Joining four tables — Asha's order lines

       oi.quantity * oi.unit_price AS line_total
FROM   orders o
JOIN   order_items oi ON oi.order_id   = o.order_id
JOIN   products    p  ON p.product_id  = oi.product_id
WHERE  o.customer_id = 1

    ⬅️ LEFT and RIGHT JOIN

    A LEFT JOIN keeps every row from the left table. When there is no match, the right side's columns are filled with NULL.

    sqlSELECT c.name, o.order_id
FROM   customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
ORDER  BY c.customer_id, o.order_id;

    Result:

    nameorder_id
    Asha Rao101
    Asha Rao103
    Ben Carter102
    Chen Li104
    Dara Okafor105
    Eva NovakNULL

    A RIGHT JOIN is the mirror image: it keeps every row of the right table. Products that were never sold:

    sqlSELECT p.name, oi.order_id
FROM   order_items oi
RIGHT JOIN products p ON p.product_id = oi.product_id
WHERE  oi.order_id IS NULL;          -- -> Notebook
    💡
    Most teams write only LEFT JOINs (swap the table order) because left-to-right reading is easier. The pattern LEFT JOIN … WHERE right.id IS NULL is called an anti-join: rows with no match.
    EXAMPLE · ON vs WHERE in a LEFT JOIN
    sql-- filter in ON: keeps all customers, only attaches delivered orders
SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id AND o.status = 'delivered';
-- 5 rows: Asha 101, Ben 102, Chen NULL, Dara NULL, Eva NULL

SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'delivered';
-- 2 rows: Asha 101, Ben 102

    🔄 FULL OUTER JOIN and CROSS JOIN

    A FULL OUTER JOIN keeps unmatched rows from both sides. Imagine a small list of store cities, and we want to see which customers live near a store and which stores have no customers.

FROM   customers c

ORDER  BY c.customer_id;

    A CROSS JOIN has no condition: it returns every combination (the Cartesian product). 5 customers × 5 products = 25 rows. Useful for generating grids, such as every product × every month for a sales report with zeros.

    🚧 Common mistakes

    1. Selecting a column that is neither grouped nor aggregated

    sqlSELECT city, name, COUNT(*) FROM customers GROUP BY city;
-- PostgreSQL: ERROR: column "customers.name" must appear in the GROUP BY clause
--             or be used in an aggregate function

    Which name should the database show for Pune — Asha or Chen? It cannot know. MySQL 5.7+ rejects this too with the default ONLY_FULL_GROUP_BY mode; older MySQL silently returned an arbitrary name. Fix: group by the column, aggregate it (STRING_AGG / GROUP_CONCAT), or remove it.

    📝
    PostgreSQL allows a column that is functionally dependent on a grouped primary key: after GROUP BY c.customer_id you may select c.name.

    2. Row multiplication after a join

    Joining a parent to its children repeats the parent's values once per child. Summing a parent column then over-counts.

    sqlSELECT p.category, SUM(p.stock) AS stock, SUM(oi.quantity) AS units_sold
FROM   products p
JOIN   order_items oi ON oi.product_id = p.product_id
GROUP  BY p.category;

    Result:

    categorystock (WRONG)units_sold
    Electronics454
    Furniture81
    Kitchen3007

    Kitchen really has 100 mugs in stock, but the mug appears in 3 order lines so its stock is added 3 times. Fix: aggregate the child table first, then join one row per product.

    sqlSELECT p.category, SUM(p.stock) AS stock, SUM(s.units) AS units_sold
FROM   products p
LEFT JOIN (SELECT product_id, SUM(quantity) AS units
           FROM order_items GROUP BY product_id) s
       ON s.product_id = p.product_id
GROUP  BY p.category;      -- Electronics 25, Furniture 8, Kitchen 100, Stationery 0

    3. COUNT(*) with a LEFT JOIN

    COUNT(*) counts Eva's NULL-filled row as 1. Use COUNT(o.order_id) to count only real orders (Eva → 0).

    🪆 Subqueries: scalar, IN, EXISTS and correlated

    🧱 CTEs: WITH and recursive queries

    A Common Table Expression (CTE) names a subquery at the top of a statement. It reads top-down like a recipe and can be referenced several times.

    sqlWITH order_totals AS (
    SELECT order_id, SUM(quantity * unit_price) AS total
    FROM   order_items
    GROUP  BY order_id
)
SELECT o.order_id, o.status, t.total
FROM   orders o
JOIN   order_totals t ON t.order_id = o.order_id
WHERE  t.total > 150
ORDER  BY t.total DESC;

    Result:

    order_idstatustotal
    101delivered925.00
    104cancelled240.00
    103shipped200.00

    Recursive CTEs

    A recursive CTE has an anchor part (the starting rows) UNION ALL a recursive part that joins back to the CTE itself. It repeats until no new rows appear. Perfect for trees: referral chains, org charts, category hierarchies.

    sqlWITH RECURSIVE chain AS (
    SELECT customer_id, name, 0 AS depth          -- anchor: Asha
    FROM   customers WHERE customer_id = 1
    UNION ALL
    SELECT c.customer_id, c.name, ch.depth + 1    -- recursive step
    FROM   customers c
    JOIN   chain ch ON c.referred_by = ch.customer_id
)
SELECT name, depth FROM chain ORDER BY depth, name;

    Result:

    namedepth
    Asha Rao0
    Ben Carter1
    Chen Li1
    Dara Okafor2
    📝
    MySQL supports CTEs and WITH RECURSIVE from version 8.0. In PostgreSQL 12+ a CTE used once is usually inlined into the main query; add MATERIALIZED to force it to be computed separately.
    ⚠️
    A recursive CTE over data with a cycle (A refers B, B refers A) loops until an error or limit. Guard it with a depth limit or Postgres 14's CYCLE clause.

    🪟 Window functions: ROW_NUMBER, RANK, DENSE_RANK

    A window function computes a value over a set of related rows without collapsing them. GROUP BY returns one row per group; a window function keeps every row and adds a column. The OVER (…) clause defines the window.

    sqlSELECT p.name,
       COALESCE(SUM(oi.quantity), 0) AS units,
       ROW_NUMBER() OVER (ORDER BY COALESCE(SUM(oi.quantity), 0) DESC, p.name) AS row_num,
       RANK()       OVER (ORDER BY COALESCE(SUM(oi.quantity), 0) DESC)         AS rnk,
       DENSE_RANK() OVER (ORDER BY COALESCE(SUM(oi.quantity), 0) DESC)         AS dense_rnk
FROM   products p
LEFT JOIN order_items oi ON oi.product_id = p.product_id
GROUP  BY p.product_id, p.name
ORDER  BY units DESC, p.name;

    Result:

    nameunitsrow_numrnkdense_rnk
    Coffee Mug7111
    Headphones3222
    Desk Chair1333
    Laptop1433
    Notebook0554
    FunctionOn a tieGaps after a tie?
    ROW_NUMBER()Different numbers (arbitrary unless ORDER BY breaks the tie)No
    RANK()Same numberYes — 3, 3, then 5
    DENSE_RANK()Same numberNo — 3, 3, then 4

    PARTITION BY = restart per group

    sqlSELECT name, category, price,
       RANK() OVER (PARTITION BY category ORDER BY price DESC) AS rank_in_category
FROM   products;
-- Laptop 1, Headphones 2 (Electronics); Desk Chair 1; Coffee Mug 1; Notebook 1
    📝

    📈 Running totals, LAG/LEAD and top-N per group

)
SELECT o.order_id, o.order_date, t.total,
       SUM(t.total) OVER (ORDER BY o.order_date) AS running_total,
       LAG(t.total)  OVER (ORDER BY o.order_date) AS previous_total
FROM   orders o JOIN t ON t.order_id = o.order_id
ORDER  BY o.order_date;

    👁️ Views and materialised views

    A view is a saved query that behaves like a table. It stores no data; each time you query it, the underlying query runs.

    sqlCREATE VIEW order_totals AS
SELECT o.order_id, o.customer_id, o.status,
       SUM(oi.quantity * oi.unit_price) AS total
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.order_id
GROUP  BY o.order_id, o.customer_id, o.status;

SELECT * FROM order_totals WHERE status = 'delivered';   -- 101: 925.00, 102: 120.00
GRANT SELECT ON order_totals TO reporting_user;          -- expose a view, not raw tables

    A materialised view stores the query's result physically. Reads are fast, but the data is a snapshot until refreshed.

    sql-- PostgreSQL
CREATE MATERIALIZED VIEW monthly_sales AS
SELECT date_trunc('month', o.order_date) AS month,
       SUM(oi.quantity * oi.unit_price)   AS revenue
FROM   orders o JOIN order_items oi ON oi.order_id = o.order_id
WHERE  o.status <> 'cancelled'
GROUP  BY 1;

CREATE UNIQUE INDEX ON monthly_sales (month);
REFRESH MATERIALIZED VIEW CONCURRENTLY monthly_sales;   -- readers are not blocked

    View

    • Always up to date
    • No storage
    • As slow as its query
    • Simplifies and secures access

    Materialised view

    • Stale until REFRESH
    • Uses disk; can be indexed
    • Very fast reads
    • Great for heavy reports
    📝
    MySQL has views but no materialised views; teams emulate them with summary tables refreshed by events or jobs.

    🔁 Upserts: insert or update

    An upsert inserts a row, or updates it if a row with the same unique key already exists — in one atomic statement, without a race between “check” and “insert”.

    sql-- PostgreSQL: ON CONFLICT (needs a unique constraint or index on the target)
INSERT INTO customers (name, email, city)
VALUES ('Asha Rao', 'asha@example.com', 'Mumbai')
ON CONFLICT (email)

    Indexes, Transactions and Performance

    Make queries fast with the right indexes and keep data correct under concurrency.

    📚 What an index is: the B-tree

    Without an index, finding WHERE customer_id = 42 means reading every row: a sequential (full table) scan. An index is a separate sorted structure that points to rows, like the index at the back of a book.

    The default index type in both PostgreSQL and MySQL is the B-tree (balanced tree). It keeps keys sorted, so it supports =, <, >, BETWEEN, ORDER BY and prefix LIKE 'abc%'. A lookup takes about log(n) steps: a million rows need only 3–4 page reads.

    sqlCREATE INDEX ix_orders_customer_id ON orders (customer_id);
CREATE UNIQUE INDEX ux_customers_email ON customers (email);   -- also enforces uniqueness
CREATE INDEX ix_customers_lower_email ON customers (lower(email)); -- expression index (Postgres)
DROP INDEX ix_orders_customer_id;                              -- MySQL: DROP INDEX ... ON orders

    HashEquality onlyPostgreSQL; MySQL MEMORY engine
    GINJSONB keys, arrays, full-textPostgreSQL
    GiST / SP-GiSTGeometry, ranges, nearest-neighbourPostgreSQL (PostGIS)
    BRINHuge append-only tables ordered by timePostgreSQL
    FULLTEXTWord search in textMySQL InnoDB
    📝
    Primary keys and UNIQUE constraints automatically create an index. Foreign keys do not in PostgreSQL — index FK columns such as orders.customer_id yourself. InnoDB creates an index on FK columns automatically if none exists.
    💡
    InnoDB stores the table itself inside the primary-key B-tree (a clustered index); secondary indexes store the PK value. PostgreSQL stores rows in an unordered heap, and every index points to a physical row location.

    🧩 Composite indexes and the leftmost-prefix rule

    A composite index covers several columns. It is sorted by the first column, then by the second within equal first values, and so on — like a phone book sorted by surname, then first name.

    sqlCREATE INDEX ix_orders_cust_date ON orders (customer_id, order_date);
    Query conditionCan use the index efficiently?Why

    WHERE customer_id = 1 ORDER BY order_dateYes, and no sort stepRows already in date order per customer
    WHERE order_date >= '2026-02-01'Usually noSkips the leftmost column (like finding all “Johns” in a phone book)
    WHERE customer_id > 1 AND order_date = '2026-02-11'PartlyRange on the first column; second column only filters
    💡
    Column order rule of thumb: columns tested with equality first, then the column used for a range or sort. One index on (a, b) also serves queries on a alone, so a separate index on a is usually redundant.
    📝
    MySQL 8.0.13+ and PostgreSQL 18 can sometimes use a skip scan when the leftmost column has few distinct values, but do not design around it.

    🎯 Covering indexes and when indexes hurt

    A covering index contains every column a query needs, so the database can answer from the index alone without visiting the table: an index-only scan (Postgres) or “Using index” (MySQL EXPLAIN).

    sql-- PostgreSQL 11+: key columns + extra payload columns
CREATE INDEX ix_orders_cust_date_incl ON orders (customer_id, order_date) INCLUDE (status);

SELECT order_date, status FROM orders WHERE customer_id = 1;   -- index-only scan possible

    💳 Transactions and ACID

    A transaction groups statements into one all-or-nothing unit. Placing an order must reduce stock and create the order — never just one.

UPDATE products SET stock = stock - 1

INSERT INTO orders (customer_id) VALUES (5) RETURNING order_id;   -- say 106
INSERT INTO order_items (order_id, product_id, quantity, unit_price)

COMMIT;                                  -- or ROLLBACK to undo everything

    IIsolationConcurrent transactions don't see each other's half-done workLocks, MVCC

    📝

    💡

    🔒 Locking and deadlocks

    Writers take row locks: two transactions cannot update the same row at the same time — the second waits. To prevent lost updates when you read a value and then write based on it, lock the row while reading:

    sqlBEGIN;
SELECT stock FROM products WHERE product_id = 1 FOR UPDATE;   -- others now wait
-- app checks stock >= quantity
UPDATE products SET stock = stock - 1 WHERE product_id = 1;
COMMIT;
    TechniqueHowGood for
    Atomic updateSET stock = stock - 1 WHERE stock >= 1Simple counters — no read needed
    Pessimistic lockingSELECT … FOR UPDATEHigh contention, short transactions
    Optimistic lockingA version column: UPDATE … SET version = version + 1 WHERE id = ? AND version = ?Low contention; 0 rows updated = someone else won, retry
    Queue-style workersFOR UPDATE SKIP LOCKEDMany workers taking different jobs

    Deadlocks

    EXAMPLE · Two transactions waiting for each other
    textT1: UPDATE products SET stock = stock - 1 WHERE product_id = 1;   -- locks row 1
T2: UPDATE products SET stock = stock - 1 WHERE product_id = 2;   -- locks row 2
T1: UPDATE products SET stock = stock - 1 WHERE product_id = 2;   -- waits for T2
T2: UPDATE products SET stock = stock - 1 WHERE product_id = 1;   -- waits for T1 -> deadlock

PostgreSQL: ERROR: deadlock detected
MySQL:      ERROR 1213 (40001): Deadlock found when trying to get lock;
            try restarting transaction

    The database detects the cycle and aborts one transaction so the other can finish.

    • Lock rows in a consistent order (e.g. sort product ids before updating).
    • Keep transactions short and touch as few rows as possible.
    • Index the columns in your WHERE so fewer rows (and gaps) get locked.
    • Catch deadlock / serialization errors and retry the transaction.

    🕰️ MVCC basics

    MVCC (Multi-Version Concurrency Control) is how PostgreSQL and InnoDB let readers and writers work at the same time: an update creates a new version of the row instead of overwriting it in place, and each transaction sees the versions that match its snapshot.

    The headline benefit: readers don't block writers and writers don't block readers. Only two writers on the same row wait for each other.

    PostgreSQL

    • Old and new row versions live in the table heap
    • Each version is stamped with transaction ids (xmin / xmax)
    • Dead versions are cleaned up by VACUUM (autovacuum)
    • Neglected vacuum → table bloat and, in the extreme, transaction-id wraparound

    MySQL InnoDB

    • The row is updated in place
    • Old versions are rebuilt from undo logs
    • A purge thread removes undo records no longer needed
    • Very long transactions keep undo history alive and slow things down
    Under REPEATABLE READ, T1 still sees the old stock value from its snapshot; under READ COMMITTED it sees T2's committed value
    💡
    Long-running transactions are an MVCC anti-pattern in both engines: they pin old row versions, block cleanup and grow storage. Monitor them (pg_stat_activity, information_schema.innodb_trx).

    💉 SQL injection and parameterised queries

    SQL injection happens when user input is pasted into SQL text, so the input can change the query's meaning. It is one of the most common and damaging web vulnerabilities.

    python# NEVER do this
email = request.args["email"]               # attacker sends:  ' OR '1'='1
sql = f"SELECT * FROM customers WHERE email = '{email}'"
# becomes: SELECT * FROM customers WHERE email = '' OR '1'='1'   -> every customer!

    The fix is a parameterised query (prepared statement): the SQL text has placeholders and the values travel separately, so they are always treated as data, never as SQL.

    python# Python + psycopg 3 (PostgreSQL). %s is a placeholder, not string formatting.
with conn.cursor() as cur:
    cur.execute(
        "SELECT customer_id, name FROM customers WHERE email = %s",
        (email,),
    )
    row = cur.fetchone()

    java// Java + JDBC (works with PostgreSQL and MySQL drivers)
String sql = "SELECT customer_id, name FROM customers WHERE email = ?";
try (Connection con = dataSource.getConnection();
     PreparedStatement ps = con.prepareStatement(sql)) {
    ps.setString(1, email);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            System.out.println(rs.getInt("customer_id") + " " + rs.getString("name"));
        }
    }
}
    ⚠️
    Placeholders work for values only. Table names, column names and ASC/DESC cannot be parameters — pick them from a fixed allow-list in code (or use psycopg.sql.Identifier).

    The N+1 query problem

    Loading a list (1 query) and then lazily loading a relationship for each item (N more queries) is the classic ORM performance bug.

    python# SQLAlchemy 2.x — N+1: 1 query for customers + 1 query per customer for orders

    print(customer.name, len(customer.orders))      # lazy load fires here

# Fix: eager-load the relationship in a second batched query (2 queries total)
stmt = select(Customer).options(selectinload(Customer.orders))
for customer in session.scalars(stmt):
    print(customer.name, len(customer.orders))

    🧱 Fundamentals

    What is the difference between a database, a DBMS and an RDBMS?

    A database is the organised data itself. A DBMS is the software that stores it, answers queries, enforces rules and handles concurrency and recovery. An RDBMS is a DBMS based on the relational model: data in tables, relationships through keys, queried with SQL. PostgreSQL and MySQL are RDBMSs; MongoDB is a (document) DBMS but not relational.

    Primary key vs foreign key vs unique key?

    A primary key uniquely identifies each row; only one per table; never NULL. A unique key also forbids duplicates, but a table can have several and they accept NULLs (e.g. email). A foreign key is a column that must match a key in another table, enforcing referential integrity (orders.customer_id → customers.customer_id). PK and UNIQUE create indexes automatically; in PostgreSQL an FK does not, so index it yourself.

    What is NULL? How is it different from 0 or an empty string?

    NULL means unknown or not applicable. 0 and '' are real, known values. Comparisons with NULL give UNKNOWN, so city = NULL never matches — use IS NULL. Aggregates other than COUNT(*) skip NULLs, and NOT IN with a NULL in the list returns no rows. Handle NULLs with COALESCE, IS [NOT] DISTINCT FROM or NOT NULL constraints.

    Bonus point: MySQL commits implicitly around DDL, while PostgreSQL supports transactional DDL.

    When would you choose a relational database over NoSQL?

    When data is structured and related (customers, orders, payments), when you need multi-row ACID transactions, strong constraints, and flexible ad-hoc queries with joins and aggregation. NoSQL fits very high write throughput with simple access patterns, schema-less documents, caching (Redis) or graph traversals. Many systems use both: PostgreSQL as the system of record plus Redis as a cache.

    🗺️ Modelling

    Explain 1NF, 2NF and 3NF with an example.
    • 1NF: atomic values, no repeating groups — not products = 'Laptop, Mug' in an order row.
    • 2NF: 1NF + no partial dependency on part of a composite key — product_name must not sit in order_items(order_id, product_id, …) because it depends only on product_id.
    • 3NF: 2NF + no transitive dependency — customer_city must not sit in orders because it depends on customer_id, not on order_id.

    Summary: every non-key column depends on the key, the whole key and nothing but the key.

    How do you model a many-to-many relationship?

    With a junction table that has a foreign key to each side and usually a composite primary key over both. In the shop, order_items(order_id, product_id) links orders and products and also stores the relationship's own data: quantity and unit_price.

    Surrogate or natural primary key — which do you prefer?

    Usually a surrogate key (identity or UUID) as the primary key, plus a UNIQUE constraint on the natural key. Surrogates are small, stable and fast to join; natural keys like email can change and are wide. Natural keys are fine when truly immutable and compact (ISO country codes).

    When would you denormalise a schema?

    Only after measuring a real read-performance problem: e.g. a dashboard that sums millions of order lines on every view. Options: a cached total_amount column maintained in the same transaction or by a trigger, a summary table, or a materialised view. Trade-off: faster reads for slower, more complex writes and a risk of inconsistent copies.

    Which data type would you use for money and for event times?

    Money: NUMERIC(p,s) / DECIMAL(p,s) (or integer minor units such as cents) — never FLOAT, which cannot represent 0.1 exactly. Event times: TIMESTAMPTZ in PostgreSQL; in MySQL store UTC in DATETIME (or TIMESTAMP, which converts to UTC but only reaches 2038). Convert to local time in the presentation layer.

    🔍 Querying

    Find the second highest salary.

    Assume employees(id, name, salary). Three common answers:

    sql-- 1. Subquery: highest salary below the maximum
SELECT MAX(salary) AS second_highest
FROM   employees
WHERE  salary < (SELECT MAX(salary) FROM employees);

-- 2. Distinct + offset
SELECT DISTINCT salary FROM employees
ORDER  BY salary DESC
LIMIT 1 OFFSET 1;

-- 3. Window function (easy to generalise to the Nth)
SELECT DISTINCT salary
FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS dr
      FROM employees) t
WHERE dr = 2;

    Mention ties (use DISTINCT / DENSE_RANK, not ROW_NUMBER) and the empty case: option 1 returns a single NULL row, options 2 and 3 return no rows. On the shop data the second highest product price is 150.00.

    How do you find and remove duplicate rows?
    sql-- find duplicate emails
SELECT lower(email) AS email, COUNT(*)
FROM   customers
GROUP  BY lower(email)
HAVING COUNT(*) > 1;

-- delete duplicates, keeping the lowest id of each email
DELETE FROM customers
WHERE customer_id IN (
    SELECT customer_id FROM (
        SELECT customer_id,
               ROW_NUMBER() OVER (PARTITION BY lower(email)
                                  ORDER BY customer_id) AS rn
        FROM customers) t
    WHERE rn > 1);

    Then add a UNIQUE constraint (or unique index on lower(email)) so duplicates cannot come back. Check foreign keys first — orders may point at the rows you are deleting.

    List customers who have never placed an order.
    sqlSELECT c.customer_id, c.name
FROM   customers c
WHERE  NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

-- equivalent anti-join
SELECT c.customer_id, c.name
FROM   customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE  o.order_id IS NULL;

    Both return Eva Novak. Avoid NOT IN (SELECT customer_id FROM orders) if the column can be NULL — one NULL makes it return nothing.

    Why can't I use a SELECT alias in WHERE?

    Because of the logical processing order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. The alias is created in SELECT, after WHERE runs. Repeat the expression, or wrap the query in a subquery/CTE. ORDER BY can use aliases because it runs after SELECT.

    ROW_NUMBER vs RANK vs DENSE_RANK — and how to get the top 1 per group?

    On ties ROW_NUMBER gives distinct numbers (1, 2, 3, 4), RANK repeats and leaves gaps (1, 2, 2, 4), DENSE_RANK repeats without gaps (1, 2, 2, 3). Top-N per group: number rows with ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) in a subquery and keep rn = 1 — each customer's latest order. Use RANK if ties should all be returned.

    What is the difference between WHERE and HAVING?

    WHERE filters individual rows before grouping and cannot use aggregates. HAVING filters groups after GROUP BY and can use aggregates such as HAVING SUM(total) > 100. Put non-aggregate filters in WHERE so fewer rows are grouped.

    After adding a join my SUM doubled. Why, and how do you fix it?

    A one-to-many join repeats each parent row once per child, so summing a parent column (or joining two independent child tables) multiplies values. Fix: aggregate the child table in a subquery/CTE first and join one row per key, use COUNT(DISTINCT …) where appropriate, or check row counts before and after each join. Do not paper over it with DISTINCT.

    COUNT(*) vs COUNT(column) vs COUNT(DISTINCT column)?

    COUNT(*) counts rows; COUNT(col) counts non-NULL values; COUNT(DISTINCT col) counts different non-NULL values. On customers: 5, 4 and 3 for city. With a LEFT JOIN, count a column from the right table (COUNT(o.order_id)) so customers without orders show 0.

    ⚡ Performance and transactions

    How does an index speed up a query, and when would you not add one?

    A B-tree index keeps keys sorted with pointers to rows, so a lookup takes O(log n) page reads instead of scanning the table; it also serves ranges and ORDER BY. Skip or reconsider an index when the table is tiny, the column has low selectivity, the table is write-heavy, the query wraps the column in a function (use an expression index instead), or an existing composite index already covers it.

    How do you choose the column order in a composite index?

    Leftmost-prefix rule: the index helps queries that constrain its leading column(s). Put equality-filtered columns first, then the range or sort column. (customer_id, order_date) serves WHERE customer_id = ? AND order_date >= ? and WHERE customer_id = ? ORDER BY order_date, but usually not WHERE order_date >= ? alone.

    A query is slow in production. How do you investigate?
    1. Reproduce with real parameters; find it via pg_stat_statements or MySQL's slow query log.
    2. Run EXPLAIN ANALYZE: look for sequential scans on big tables, bad row estimates, sorts spilling to disk, nested loops over many rows.
    3. Check indexes on WHERE / JOIN / ORDER BY columns; refresh statistics with ANALYZE.
    4. Rewrite: avoid functions on indexed columns, fetch fewer columns, paginate with keysets, fix N+1 patterns.
    5. Check locks and waits, not just CPU — pg_stat_activity / SHOW ENGINE INNODB STATUS.
    6. Measure again and add a regression test or monitor.
    Explain isolation levels and the anomalies they prevent.

    READ UNCOMMITTED allows dirty reads; READ COMMITTED prevents dirty reads; REPEATABLE READ also prevents non-repeatable reads; SERIALIZABLE behaves as if transactions ran one at a time, preventing phantoms and write skew. Defaults: PostgreSQL READ COMMITTED, MySQL InnoDB REPEATABLE READ. Postgres RR is snapshot isolation (no phantoms), and both databases may abort a transaction at higher levels, so apps must retry.

    What is a deadlock and how do you avoid it?

    Two transactions each hold a lock the other needs, so neither can proceed. The database detects the cycle and aborts one (PostgreSQL “deadlock detected”, MySQL error 1213). Avoid it by locking rows in a consistent order, keeping transactions short, indexing WHERE columns so fewer rows are locked, and retrying the aborted transaction. For read-modify-write use SELECT … FOR UPDATE (pessimistic) or a version column (optimistic).

    🐘 PostgreSQL, MySQL and the application

    What are the main differences between PostgreSQL and MySQL?
    • Auto ids: IDENTITY/SERIAL vs AUTO_INCREMENT; identifier quoting: "double" vs `backticks`.
    • Postgres has JSONB with GIN indexes, arrays, ranges, extensions (PostGIS, pgvector), RETURNING, FULL OUTER JOIN, partial indexes, transactional DDL.
    • MySQL: InnoDB clustered primary key, case-insensitive default collation, simple and very widespread replication and hosting.
    • Defaults: Postgres READ COMMITTED, MySQL REPEATABLE READ. Upsert: ON CONFLICT vs ON DUPLICATE KEY UPDATE.
    How do you prevent SQL injection?

    Use parameterised queries / prepared statements everywhere (%s in psycopg, ? in JDBC PreparedStatement, bound parameters in ORMs). Never build SQL by concatenating user input. Allow-list identifiers such as sort columns, run the app with a least-privilege user, and hide raw database errors from users.

    What is the N+1 query problem and how do you fix it?

    Loading N parent objects with one query and then lazily loading a relationship per object, issuing N extra queries. It is invisible in code but slow over the network. Fix with eager loading: SQLAlchemy selectinload/joinedload, JPA JOIN FETCH / @EntityGraph, EF Core Include, or one hand-written join. Detect it by logging SQL and counting queries per request.

    Why use a connection pool, and how big should it be?

    Opening connections is slow (TCP, TLS, auth, a new backend process in Postgres) and servers allow only a limited number. A pool reuses a small set of connections. Size it small — often around 2× CPU cores of the database server across all app instances — and use PgBouncer/ProxySQL when there are many app instances. Always return connections and set timeouts.

    How do you change the schema of a live production database safely?

    Use versioned migrations (Flyway, Liquibase, Alembic, EF migrations) reviewed like code and applied by the pipeline. Follow expand and contract: add nullable columns/new tables first, deploy code that writes both, backfill in batches, switch reads, then remove the old structure in a later release. Watch for locking DDL: create indexes CONCURRENTLY in Postgres, use online DDL (ALGORITHM=INPLACE/INSTANT) in MySQL, and always have a tested backup.

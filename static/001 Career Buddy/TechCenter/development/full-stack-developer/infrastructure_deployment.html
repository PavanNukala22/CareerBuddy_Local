    What is Infrastructure & Deployment?

    Start from zero: environments, hosting models, networking and the Linux skills behind every deployment.

    🧭 What is Infrastructure & Deployment?

    Infrastructure is everything your code needs in order to run: computers (servers), networks, storage, databases, operating systems, and the tools that glue them together. Deployment is the act of taking code from a developer's laptop and making it run, reliably and securely, where real users can reach it.

    "It works on my machine" is not a deployment strategy. This course teaches how to go from localhost to a production system that is repeatable, observable and safe to change.

    🔴 Manual, ad-hoc deployment

    SSH into a server, git pull, restart by hand. Each server slightly different. Nobody remembers the steps. Rollback = panic.

    🟢 Automated, repeatable deployment

    Code is packaged (Docker), pushed through a pipeline (CI/CD), and deployed to managed infrastructure — identical every time, with a one-click rollback.

    🔄 The Journey from Code to Users

    Every topic in this course fits one of those five boxes. DevOps is the practice of making the whole loop fast and safe.

    Docker Fundamentals

    What containers are, how images work, essential commands, your first Dockerfile and persistent data.

    🐳 What is Docker?

    Docker packages an application together with everything it needs (runtime, libraries, system tools, config) into a standard unit called a container. That container runs the same on your laptop, a teammate's machine, CI and the cloud.

    🔴 Without containers

    "Install Node 18, then Python 3.10, set these 12 env vars, install libssl…" — and it still fails on someone's machine.

    🟢 With containers

    docker run my-app — one command, identical everywhere, isolated from everything else on the host.

    📦
    Shipping-container analogy: before standard shipping containers every cargo needed special handling. Docker is the standard box for software — any ship (server) can carry any box.

    🧅 Image Layers & Build Cache

    Each Dockerfile instruction creates a layer. Docker caches layers; if a layer and everything above it is unchanged, it is reused. So order matters: put things that change rarely (dependencies) before things that change often (source code).

    🔴 Cache-busting order

    COPY . .
    RUN npm ci
    Any source edit re-installs all dependencies (minutes).

    🟢 Cache-friendly order

    COPY package*.json ./
    RUN npm ci
    COPY . .
    Dependencies re-install only when package files change.

    💾 Data Persistence: Volumes & Bind Mounts

    A container's filesystem is ephemeral — delete the container and its data is gone. Keep data (databases, uploads) outside the container.

    TypeSyntaxUse for
    Named volume-v pgdata:/var/lib/postgresql/dataDatabases; managed by Docker (production)
    Bind mount-v $(pwd):/appLive code reload in development
    tmpfs--tmpfs /tmpTemporary, in-memory scratch data
    bashdocker volume create pgdata
docker run -d --name db -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data -p 5432:5432 postgres:16
docker rm -f db                         # container gone…
docker run -d --name db -e POSTGRES_PASSWORD=secret -v pgdata:/var/lib/postgresql/data postgres:16
# …data is still there

    🏗️ Multi-Stage Builds

    Build tools (compilers, dev dependencies) are not needed at runtime. A multi-stage build compiles in one stage and copies only the result into a small, clean final image — smaller, faster and safer.

    dockerfile# ---------- Stage 1: build ----------
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build                      # e.g. TypeScript → dist/

# ---------- Stage 2: production ----------
FROM node:20-alpine AS prod
ENV NODE_ENV=production
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist     # take only the built output
USER node                              # do not run as root
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "dist/server.js"]
    dockerfile# Frontend example: build with Node, serve static files with NGINX (~25 MB final image)
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 80

    🎼 Docker Compose: Multi-Container Apps

    Real apps need several services — API, database, cache. Docker Compose defines them all in one YAML file and starts everything with one command.

    yaml# docker-compose.yml
services:
  api:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://lms:${DB_PASSWORD}@db:5432/lms     # "db" = service name = hostname
      REDIS_URL: redis://cache:6379
    depends_on:
      db: { condition: service_healthy }
    restart: unless-stopped

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: lms
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB: lms
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lms"]
      interval: 5s
      retries: 10

  cache:
    image: redis:7-alpine

volumes:
  pgdata:
    bashdocker compose up -d --build     # build + start everything
docker compose ps
docker compose logs -f api
docker compose exec db psql -U lms
docker compose down             # stop and remove containers (add -v to delete volumes too)
    📌
    Inside a Compose network containers reach each other by service name (db, cache), never localhost — localhost inside a container means that container itself.

    🔐 Secrets & Configuration

    • Never COPY .env into an image or commit it to git.
    • Pass config at runtime: -e, --env-file, Compose environment:, or the platform's secret manager.
    • In production use a secrets service: AWS Secrets Manager / SSM Parameter Store, GCP Secret Manager, HashiCorp Vault, Doppler.
    • Use build secrets for private package tokens so they never land in a layer:
    dockerfile# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=npm_token \
    NPM_TOKEN=$(cat /run/secrets/npm_token) npm ci

# docker build --secret id=npm_token,src=$HOME/.npm_token -t app .
    🚨
    Already committed a secret? Rotate it immediately — deleting the commit is not enough. Assume it is compromised.

    🛡️ Container Security Checklist

    • ✅ Non-root USER, read-only root filesystem where possible (--read-only)
    • ✅ Drop capabilities: --cap-drop ALL; never use --privileged in production
    • ✅ Scan images in CI (Trivy / Grype / Docker Scout); fail on critical CVEs
    • ✅ Pull from trusted registries; pin by digest (image@sha256:…) for critical workloads
    • ✅ Never mount the Docker socket (/var/run/docker.sock) into app containers
    • ✅ Set resource limits so one container cannot starve others
    bashdocker run -d --read-only --cap-drop ALL --memory 512m --cpus 1 --pids-limit 200 \
  --security-opt no-new-privileges -p 3000:3000 lms-api:1.0
trivy image lms-api:1.0

    ☁️ What is Cloud Computing?

    Cloud computing means renting computing resources — servers, storage, databases, networking — over the internet, on demand, and paying only for what you use, instead of buying and maintaining hardware.

    ⚡
    On-demand
    Provision a server in minutes, delete it when done.
    📈
    Elastic
    Scale up for traffic spikes, down at night.
    💳
    Pay-as-you-go
    Opex instead of capex; per second/hour/request billing.
    🌍
    Global
    Deploy near your users in dozens of regions.
    🛡️
    Managed
    Provider handles hardware, patches, durability.

    📍 Regions, Availability Zones & the Shared Responsibility Model

    • Region: a geographic area (e.g. AWS ap-south-1 Mumbai, GCP asia-south1). Pick the one closest to your users and compliant with data-residency rules.
    • Availability Zone (AZ): separate data centres within a region. Spread across ≥2 AZs for high availability.
    • Edge locations: CDN points of presence for caching close to users.
    • Shared responsibility: the provider secures the cloud (hardware, facilities); you secure what you put in the cloud (IAM, data, configs, patching your OS).

    🔑 Identity & Access Management (IAM)

    IAM controls who can do what on which resource. It is the most important cloud security topic.

    PrincipalA user, role or service that makes requests.
    PolicyJSON document listing allowed/denied actions on resources.
    RoleTemporary identity assumed by a service or person — preferred over long-lived access keys.
    Least privilegeGrant only the permissions required, nothing more.
    MFAMulti-factor authentication — enable on the root/owner account first.
    json{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::lms-uploads-prod/*"
  }]
}
    • Never use the root account for daily work; lock it with MFA.
    • Give applications roles (EC2 instance profile, ECS task role, GCP service account), not hard-coded keys.
    • Never commit access keys. If leaked, deactivate and rotate immediately.
    • Set billing alerts / budgets on day one.

    ▲ Vercel: Deploying Front-ends in Minutes

    Vercel builds and hosts front-end frameworks (Next.js, React, Vue, Svelte, Astro) on a global edge network. Every push creates a build; every pull request gets its own preview URL; merging to main deploys to production.

    bashnpm i -g vercel
vercel login
vercel                 # first deploy → preview URL (answers a few setup prompts)
vercel --prod          # promote to production
vercel env add API_URL production   # set an environment variable
vercel logs <deployment-url>
    • Git integration: import the repo at vercel.com/new → automatic builds on every push.
    • Environment Variables: Project → Settings → Environment Variables (separate values for Production / Preview / Development). Only names prefixed NEXT_PUBLIC_ / VITE_ are exposed to the browser — never put secrets in those.
    • Custom domain: Settings → Domains → add app.example.com → create the CNAME/A record Vercel shows. HTTPS certificate is automatic.
    • Instant rollback: Deployments → pick an earlier one → "Promote to Production".
    • Serverless / Edge Functions: files in /api (or Next.js route handlers) become scalable endpoints with no server management.
    json// vercel.json — rewrites API calls to your backend and sets headers
{
  "rewrites": [{ "source": "/api/:path*", "destination": "https://api.example.com/v1/:path*" }],
  "headers": [{ "source": "/(.*)", "headers": [{ "key": "X-Content-Type-Options", "value": "nosniff" }] }]
}
    📌
    Limits: serverless functions have execution-time and size limits and no local persistent disk. Long-running or stateful back-ends belong on containers/VMs. Always check Vercel's current plan limits.

    ♾️ What are CI, CD and CD?

    CI/CD automates the path from commit to production. The three terms are often confused:

    TermMeaningWhat happens automatically
    CI — Continuous IntegrationMerge small changes to the main branch often; verify each one automaticallyInstall → lint → test → build on every push / PR
    CD — Continuous DeliveryEvery passing change is ready to releaseArtifact built and deployed to staging; production deploy needs a manual approval
    CD — Continuous DeploymentEvery passing change goes to productionFully automatic release to users (needs strong tests + monitoring)
    💡
    Why bother? Smaller releases are less risky, bugs are found minutes after introduction, deployments become boring, and the team ships many times a day instead of once a quarter.

    🧰 Pipeline Vocabulary

    Pipeline / WorkflowThe whole automated process, defined in a file in your repo.
    Stage / JobA group of steps (e.g. "test", "build", "deploy"). Jobs can run in parallel.
    StepOne command or action inside a job.
    Runner / AgentThe machine that executes the job (GitHub-hosted, self-hosted).
    TriggerWhat starts it: push, pull_request, tag, schedule, manual.
    ArtifactFiles produced by a job and passed to later jobs or kept (reports, builds).
    CacheSaved dependencies to speed up later runs.
    SecretEncrypted variable available to pipelines (tokens, keys).
    Gate / ApprovalA check or human sign-off required to proceed.
    EnvironmentNamed deploy target (staging, production) with its own secrets and rules.
    ToolConfig fileNotes
    GitHub Actions.github/workflows/*.ymlBuilt into GitHub; huge marketplace of actions
    GitLab CI/CD.gitlab-ci.ymlAll-in-one DevOps platform
    JenkinsJenkinsfileSelf-hosted, very flexible, more upkeep
    CircleCI, Travis.circleci/config.ymlHosted CI services
    AWS CodePipeline, Cloud BuildConsole / YAMLCloud-native pipelines

    runs-on: ubuntu-latest

          context: .

    🔒 Pipeline Security

    • Store tokens in encrypted secrets; they are masked in logs. Never echo them.
    • Prefer OIDC / workload identity (short-lived credentials) over stored cloud keys.
    • Give the workflow the minimum permissions:; scope secrets per environment.
    • Pin third-party actions to a commit SHA — a tag can be moved by an attacker (supply-chain attack).
    • Do not expose secrets to workflows triggered by forked pull requests.
    • Scan: dependencies (npm audit, Dependabot), code (CodeQL, Semgrep), secrets (Gitleaks), images (Trivy), IaC (tfsec/Checkov).
    • Sign images (cosign) and generate an SBOM for compliance.

    🗃️ Database Migrations & Safe Releases

    Code can roll back in seconds; data cannot. Use the expand → migrate → contract pattern so old and new code both work during a rollout:

    • Expand: add the new column/table (nullable, with default) — old code ignores it.
    • Deploy code that writes to both and reads the new one; backfill old rows in batches.
    • Contract: after everything uses the new field, remove the old column in a later release.
    bash# Run migrations as a separate, controlled step BEFORE the new version receives traffic
npx prisma migrate deploy          # or: alembic upgrade head / flyway migrate / knex migrate:latest
    ⚠️
    Never rename or drop a column in the same release that stops using it. Always back up and rehearse risky migrations on a staging copy.

    Explain what happens when you push code that triggers a deploy.
    The push triggers the CI workflow on a runner: checkout, install (cached), lint, test, build a Docker image, scan it, tag with the commit SHA and push to the registry. The CD stage authenticates to the cloud (OIDC), updates the service to the new image (rolling/canary), waits for health checks, runs smoke tests, and — after approval for production — repeats. If checks fail, the deploy halts or auto-rolls back; metrics and logs confirm user impact.
    Blue-green vs canary — when do you choose each?
    Blue-green when you want an instant, all-or-nothing switch and instant rollback and can afford duplicate capacity. Canary when you want to limit blast radius by exposing a small percentage first and judge by real metrics; it needs traffic splitting and solid observability.
    How do you handle secrets in CI/CD?
    Never in git or images. Store in the CI platform's encrypted secrets or a secrets manager, scope them per environment, prefer OIDC federation so no long-lived cloud keys exist, mask logs, restrict forked-PR access, rotate regularly and scan repos for leaks (Gitleaks).
    A deploy caused errors in production. What do you do?
    Mitigate first: roll back to the previous known-good image (or disable the feature flag) and confirm metrics recover. Communicate status. Then investigate with logs/traces, reproduce in staging, fix forward with a test, and write a blameless post-mortem with preventative actions (better tests, canary, alerts).

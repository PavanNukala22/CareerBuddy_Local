    Deployment Fundamentals

    How code on your laptop becomes a live, secure web app that real users can reach.

    🚀 From localhost to production

    On your laptop, TaskFlow runs at http://localhost:3000 (Next.js) and http://localhost:4000 (Express API), talking to a local PostgreSQL. Only you can see it. Deployment is the process of taking that code and running it on computers that are always on, reachable on the internet, and safe for real users.

    Production is different from your laptop in important ways:

    ConcernOn localhostIn production
    Who uses itOnly youReal users, possibly thousands at once
    UptimeRuns while your laptop is onExpected to be up 24/7
    Addresslocalhost:3000A domain such as app.taskflow.dev over HTTPS
    DataThrow-away test dataReal customer data that must be backed up and protected
    SecretsOften in a local .env fileStored in a secrets manager or platform settings
    ErrorsYou see them in your terminalNeed logging, monitoring and alerts
    Buildnpm run dev with hot reloadOptimised build: npm run build then npm start

    The Next.js app users load in the browser.
    ⚙️
    API

    🗄️
    Database
    PostgreSQL holds tasks, users and teams.
    ⚡

    💡
    "It works on my machine" is the classic deployment problem. Most of this course is about making production behave predictably — the same code, the same dependencies, the same steps every time.

    🌱 Environments: dev, staging and production

    An environment is one complete running copy of your app with its own config, database and URL. Teams usually keep at least three.

    EnvironmentPurposeDataWho uses it
    Development (dev)Write and try code quicklyFake or seeded dataEach developer, usually locally
    StagingA production-like rehearsal before releaseRealistic but not real customer dataTeam, QA, product owners
    Production (prod)The live appReal user dataCustomers

    Some teams add preview environments — a short-lived copy of the app for every pull request, so reviewers can click around a change before it merges.

    EXAMPLE · TaskFlow environments
    • localhost:3000 — dev, Postgres in Docker on the laptop
    • staging.taskflow.dev — staging, its own small database, deployed from the main branch
    • app.taskflow.dev — production, deployed after staging checks pass
    • pr-142.preview.taskflow.dev — preview for pull request #142
    ⚠️
    Never point staging or dev at the production database. A test script or a bad migration could delete real customer data.

    🔁 The flow of a modern deployment

    Most teams automate deployment so that a merge to the main branch triggers a fixed sequence of steps. This is a pipeline.

    A typical automated deployment for TaskFlow
    1. git push — a developer merges code to main.
    2. CI build — a CI server (for example GitHub Actions) checks out the code and installs dependencies.
    3. Run tests — lint, unit and integration tests. Any failure stops the pipeline.
    4. Build image — the app is packaged into a Docker image.
    5. Push to registry — the image is stored in a registry such as Docker Hub, Amazon ECR or Google Artifact Registry.
    6. Deploy — the hosting platform pulls the new image and starts it.
    7. Health check — the platform calls an endpoint like /health to confirm the app is working.
    8. Live — traffic is switched to the new version. If the check fails, the old version keeps serving.
    📝
    The same artifact (image) should move from staging to production. Rebuilding for each environment risks shipping something slightly different from what you tested.

    🏗️ Servers, containers, serverless and PaaS

    🌐 DNS, domains and HTTPS

    Users type app.taskflow.dev, not an IP address. DNS (the Domain Name System) translates names into addresses. You buy a domain from a registrar and manage its records at a DNS provider (often the same company, or Route 53, Cloud DNS, Cloudflare).

    RecordPoints a name to…Example

    🔐 Environment variables and secrets

    The same code runs in dev, staging and production. What changes is configuration: database URLs, API keys, feature flags. The standard way to pass config is environment variables (one of the Twelve-Factor App rules: store config in the environment).

    🧱 Build-time vs runtime configuration

    Some values are used when the app is built, others when it runs. Mixing them up is a very common deployment bug.

    Build time

    • Read while running npm run build or docker build
    • Baked into the output files or image
    • In Next.js, NEXT_PUBLIC_* variables are inlined into the browser bundle
    • Changing them needs a new build

    Runtime

    • Read when the process starts (process.env on the server)
    • Can differ per environment using the same image
    • Right place for secrets and server-only config
    • Changing them needs only a restart
    EXAMPLE · A NEXT_PUBLIC bug in TaskFlow

    The team builds one Docker image of the Next.js app and sets NEXT_PUBLIC_API_URL only at runtime on the server. The browser still calls the old URL, because the value was inlined during next build when the variable was empty.

    Fix: pass it at build time (for example as a build argument), build one image per environment for public values, or have the browser call a same-origin path like /api that the server proxies.

    ⚠️
    Anything with a NEXT_PUBLIC_ prefix is visible to every user in the browser. Never put secrets there.

    🔀 Reverse proxies and key terms

    A reverse proxy sits in front of your app servers and forwards requests to them. Nginx, Caddy, Traefik and cloud load balancers all play this role.

    • TLS termination — handles HTTPS so the app can speak plain HTTP internally.
    • Routing — /api/* to Express, everything else to Next.js.
    • Load balancing — spreads requests across several app instances.
    • Extras — compression, caching static files, request size limits, rate limits.
    nginxserver {
    listen 80;
    server_name app.taskflow.dev;

    location /api/ {
        proxy_pass http://api:4000/;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        proxy_pass http://web:3000;
    }
}
    📝
    Behind a proxy, Express sees the proxy's IP, not the user's. Set app.set('trust proxy', 1) so req.ip and secure cookies work correctly.

    Docker Essentials

    Package the TaskFlow API into a small, secure, repeatable container image.

    🐳 Images vs containers

    Docker packages an app together with its runtime and dependencies, so it runs the same way on any machine with a container runtime.

    Image

    • A read-only template: OS files, Node.js, your code, node_modules
    • Built from a Dockerfile
    • Made of stacked layers
    • Named with a tag, e.g. taskflow-api:1.4.0
    • Like a class, or a recipe

    Container

    • A running (or stopped) instance of an image
    • Adds a thin writable layer on top
    • Has its own process, network and filesystem view
    • Many containers can run from one image
    • Like an object, or the cooked meal

    Containers are not virtual machines. They share the host's Linux kernel and are isolated with kernel features (namespaces and cgroups), so they start in seconds and use little memory. On macOS and Windows, Docker Desktop runs a small Linux VM to provide that kernel.

    📝
    Anything written inside a container's writable layer is lost when the container is removed. Data that must survive (like a database) belongs in a volume.

    📄 Dockerfile instructions

    A Dockerfile is a text file of instructions. Docker runs them top to bottom to build an image.

    InstructionWhat it doesExample
    FROMBase image to start from (must come first, apart from ARG)FROM node:22-alpine
    WORKDIRSets (and creates) the working directory for later instructionsWORKDIR /app
    COPYCopies files from the build context into the imageCOPY package*.json ./
    RUNRuns a command at build time and saves the result as a layerRUN npm ci --omit=dev
    ENVSets an environment variable in the image (build and runtime)ENV NODE_ENV=production
    ARGA build-time variable, passed with --build-argARG APP_VERSION
    EXPOSEDocuments the port the app listens on (does not publish it)EXPOSE 4000
    USERRuns later instructions and the container as this userUSER node
    CMDDefault command when the container starts; easy to overrideCMD ["node", "src/server.js"]
    ENTRYPOINTThe fixed executable; CMD becomes its default argumentsENTRYPOINT ["node"]
    HEALTHCHECKCommand Docker runs to test the container's healthHEALTHCHECK CMD wget -qO- http://localhost:4000/health

    CMD vs ENTRYPOINT

    dockerfileENTRYPOINT ["node"]
CMD ["src/server.js"]
# docker run taskflow-api                 -> node src/server.js
# docker run taskflow-api scripts/seed.js -> node scripts/seed.js

    Arguments after the image name in docker run replace CMD. To replace ENTRYPOINT you need --entrypoint. Use the exec form (JSON array) so your app runs as PID 1 and receives stop signals like SIGTERM directly; the shell form CMD node src/server.js wraps it in /bin/sh -c.

    💡
    Prefer COPY over ADD. ADD also fetches URLs and auto-extracts local tar files, which is surprising. Use it only when you need those features.

    🛠️ A Dockerfile for the TaskFlow API

    Here is a straightforward, production-minded Dockerfile for the Express API.

    EXAMPLE · Why npm ci?

    npm ci installs exactly what package-lock.json says, fails if the lock file and package.json disagree, and starts from a clean node_modules. That makes builds reproducible. --omit=dev skips devDependencies such as Jest and ESLint.

    🧅 Layer caching and instruction order

    Each instruction creates a layer. Docker caches layers. When it rebuilds, it reuses a cached layer if the instruction and its inputs haven't changed. As soon as one layer changes, every layer after it is rebuilt.

    Slow order

    dockerfileCOPY . .
RUN npm ci

    Any code change invalidates COPY . ., so npm ci runs again on every build.

    Fast order

    dockerfileCOPY package*.json ./
RUN npm ci
COPY . .

    Dependencies are reinstalled only when the package files change.

    • Put things that change rarely (base image, system packages, dependencies) near the top.
    • Put things that change often (your source code) near the bottom.
    • Combine related RUN commands and clean up in the same layer, e.g. apk add --no-cache curl.
    • Use docker build --no-cache when you need to force a full rebuild.
    💡
    BuildKit (the default builder) supports cache mounts: RUN --mount=type=cache,target=/root/.npm npm ci keeps the npm download cache between builds.

    🪶 Smaller, safer images: multi-stage builds and non-root

    Smaller images pull faster, start faster and contain fewer packages with vulnerabilities.

    Base tagBased onNotes
    node:22Debian (full)Large; includes compilers and many tools
    node:22-slimDebian (minimal)Much smaller; glibc, so most native modules just work
    node:22-alpineAlpine LinuxVery small; uses musl libc, which occasionally breaks native modules
    DistrolessGoogle distroless imagesNo shell or package manager; smallest attack surface, harder to debug

    A multi-stage build uses one stage to build (with dev tools) and copies only the output into a clean final stage. Here is one for the TaskFlow Next.js frontend, using Next.js output: 'standalone' in next.config.js:

    dockerfile# web/Dockerfile
FROM node:22-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:22-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ARG NEXT_PUBLIC_API_URL
ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL
RUN npm run build

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build --chown=node:node /app/.next/standalone ./
COPY --from=build --chown=node:node /app/.next/static ./.next/static
COPY --from=build --chown=node:node /app/public ./public
USER node
EXPOSE 3000
ENV PORT=3000 HOSTNAME=0.0.0.0
CMD ["node", "server.js"]
    • Only the final stage ends up in the image; the build tools and full node_modules are left behind.
    • COPY --from=build copies files from an earlier stage.
    • USER node — the official Node images include an unprivileged node user. Running as non-root limits damage if the app is compromised.
    • Build with docker build --build-arg NEXT_PUBLIC_API_URL=https://api.taskflow.dev -t taskflow-web ./web.
    ✅
    Typical result: a single-stage full image of several hundred MB shrinks to a fraction of that with Alpine plus a standalone multi-stage build. Check with docker images.

    Docker Compose & the Local Full Stack

    Run TaskFlow's web, API, Postgres and Redis together with one command.

    🎼 Why Docker Compose?

    A real app is several containers: TaskFlow needs a web frontend, an API, PostgreSQL and Redis. Starting each with a long docker run command is tedious and error-prone. Docker Compose describes all of them in one YAML file and manages them together.

    📄
    One file
    compose.yaml (or docker-compose.yml) is the single source of truth.
    ▶️
    One command
    docker compose up builds and starts everything.
    🌐
    Shared network
    Services find each other by name, e.g. db.
    💾
    Volumes
    Database data survives restarts.
    📝
    Use Compose v2: the command is docker compose (a space, built into the Docker CLI). The old docker-compose Python tool is retired. The top-level version: key is obsolete and can be removed.

    📄 The TaskFlow compose file

    yaml# compose.yaml (repo root)
services:
  web:
    build:
      context: ./web
      args:
        NEXT_PUBLIC_API_URL: http://localhost:4000
    ports:
      - "3000:3000"
    depends_on:
      - api
    networks: [frontend]

  api:
    build: ./api

    KeyMeaning
    servicesEach entry is one container definition. The key (api, db) is the service name.
    buildBuild an image from a folder (a string) or with options: context, dockerfile, args, target.
    imageUse this image, or (with build) the name to tag the built image.
    ports"HOST:CONTAINER" — quote them; YAML can misread some unquoted values.

    In this file db and cache publish no ports. Only services on the same network can reach them — safer, and no clash with a Postgres already installed on your laptop.

    🏷️ Service names are hostnames

    Compose creates a network for the project and runs a built-in DNS on it. Every service can reach another by its service name on the container port.

    api containerRediscache:6379Service name + container port

    EXAMPLE · The two-URL trap

    TaskFlow's Next.js app fetches tasks in two places: in server components (running in the web container) and in the browser. The server must use http://api:4000; the browser must use http://localhost:4000 (or a public URL). Many teams keep two variables, e.g. API_URL_INTERNAL and NEXT_PUBLIC_API_URL.

    ⚠️
    Inside a container, localhost is the container itself. DATABASE_URL=postgres://…@localhost:5432/… in the api container gives ECONNREFUSED, because no Postgres runs inside the api container.

    💾 Persistent data and seeding the database

    Postgres stores its files under /var/lib/postgresql/data. Mounting the named volume pgdata there keeps tasks and users when containers are recreated.

    The official Postgres image runs any .sql or .sh files in /docker-entrypoint-initdb.d — but only when the data directory is empty (first start with a new volume).

    sql-- db/init/01-schema.sql

    🔥 Dev workflow: bind mounts and hot reload

    For development you want code changes to show up instantly without rebuilding the image. Bind-mount the source folder and run the dev server. A separate override file keeps this out of the production setup.

    yaml# compose.override.yaml — merged automatically by `docker compose up`
services:
  api:
    build:
      context: ./api
      target: dev            # a 'dev' stage in the Dockerfile with devDependencies
    command: npm run dev     # node --watch or nodemon
    volumes:
      - ./api/src:/app/src   # bind mount: edit on host, container sees it
    environment:
      NODE_ENV: development
  web:
    build:
      context: ./web
      target: deps           # the stage that has all node_modules
    command: npm run dev
    volumes:
      - ./web:/app
      - /app/node_modules    # anonymous volume: keep the container's node_modules
      - /app/.next
    • The anonymous /app/node_modules volume stops the host folder from hiding the Linux-built dependencies installed in the image.
    • On macOS/Windows file-watching through mounts can be slow or miss events; Next.js and nodemon support polling (for example WATCHPACK_POLLING=true).
    • Compose also offers develop: watch (docker compose watch) which syncs files or rebuilds on change without bind mounts.
    💡
    Use docker compose -f compose.yaml up to ignore the override file, or keep a compose.prod.yaml and combine files with multiple -f flags.

    💰 Costs, free tiers and managed vs self-hosted databases

    • Cloud bills are usage-based: compute time, storage, requests and especially data transfer out.
    • Free tiers and credits exist on AWS, GCP and Vercel but have limits and change over time — read the current pricing pages, don't rely on memory.
    • Set a budget alert on day one (AWS Budgets, GCP Billing budgets).
    • Common surprises: idle load balancers, NAT gateways, forgotten VMs or DBs in test projects, large log volumes, minimum instances kept warm.

    Managed DB (RDS, Cloud SQL)

    • Automated backups and point-in-time recovery
    • One-click high availability (standby in another zone)
    • Patching handled for you
    • Costs more per GB/CPU than a raw VM

    Self-hosted (Postgres on a VM or in a container)

    • Cheapest on paper, full control
    • You own backups, restores, upgrades, failover
    • Easy to lose data with a bad volume setup
    • Hidden cost: your team's time
    ✅
    For production data, a managed database is almost always the right default for an app team.

    🧩 GitHub Actions anatomy

    WorkflowA YAML file in .github/workflows/. A repo can have many.
    Event (on)What triggers the workflow: push, pull_request, workflow_dispatch (manual), schedule.
    JobA set of steps that runs on one runner. Jobs run in parallel unless linked with needs.

    🔑 Secrets, variables and environments

    • Repository secrets — ${{ secrets.NAME }}. Encrypted, masked in logs, not passed to workflows triggered from forks.
    • Variables — ${{ vars.NAME }} for non-secret config (region, project ID).
    • Environment secrets — scoped to staging or production; a job only gets them if it declares environment: production.
    • Protection rules — required reviewers, wait timers, and which branches may deploy to an environment.
    • GITHUB_TOKEN — an automatic, short-lived token. Limit it with permissions:.

    Long-lived cloud keys (avoid)

    Store an AWS access key or GCP JSON key as a secret. If it leaks, it works until someone notices and rotates it.

    OIDC federation (prefer)

    GitHub issues a short-lived signed token per run; AWS (aws-actions/configure-aws-credentials with a role ARN) or GCP (Workload Identity Federation) trust it and return temporary credentials. Nothing permanent to leak.

    ⚠️
    Never echo a secret, and be careful with pull_request_target: it runs with secrets in the context of the base repo, so checking out and running untrusted PR code there is dangerous.

    🚦 Deployment strategies and rollback

    StrategyHow it worksProsCons
    RecreateStop all old instances, then start new onesSimpleDowntime
    RollingReplace instances a few at a time; old and new run side by side brieflyNo downtime, no extra capacity needed; default on ECS and KubernetesTwo versions serve traffic during rollout; rollback is another rollout
    Blue-greenRun the new version (green) next to the old (blue), test it, then switch all traffic at onceInstant switch and instant rollback (switch back)Needs double capacity during the switch
    CanarySend a small share of traffic (e.g. 5%) to the new version, watch metrics, then increaseLimits blast radius; real-traffic validationNeeds good metrics and traffic splitting
    bash# Cloud Run: deploy without traffic, then shift gradually (canary)
gcloud run deploy taskflow-api --image=$IMAGE --region=europe-west1 --no-traffic --tag=canary
gcloud run services update-traffic taskflow-api --region=europe-west1 --to-tags=canary=10
# looks good -> send everything to the newest revision
gcloud run services update-traffic taskflow-api --region=europe-west1 --to-latest
# rollback: send 100% back to the previous revision
gcloud run services update-traffic taskflow-api --region=europe-west1 --to-revisions=taskflow-api-00041-abc=100
    💡
    Make rollback boring: deploy immutable image tags, keep the previous version available, and practise rolling back before you need it. Feature flags let you turn off a feature without redeploying.

    🗃️ Database migrations in deployments

    Code rolls back easily; data does not. During a rolling or canary deploy, old and new code run at the same time against the same database, so every schema change must work with both versions.

    Expand / contract (parallel change)

    Renaming tasks.title to tasks.name without downtime
    1. Expand: add the new column name (nullable). Old code ignores it.
    2. Deploy code that writes to both title and name.
    3. Backfill: UPDATE tasks SET name = title WHERE name IS NULL (in batches for big tables).
    4. Deploy code that reads name.
    5. Deploy code that no longer uses title.
    6. Contract: drop title in a later release.
    • Run migrations as a separate pipeline step or one-off job before the new code is deployed (e.g. gcloud run jobs execute migrate or an ECS run-task), not inside every app instance at startup.
    • Migrations should be backward compatible, small, and ideally reversible.
    • Beware locking: adding an index on a big Postgres table should use CREATE INDEX CONCURRENTLY.
    ⚠️
    Never deploy code that needs a column in the same step that renames or drops a column the currently running code still uses — the old instances will start throwing errors mid-rollout.

    🚀 Deployment fundamentals

    What happens between git push and a feature being live?

    A CI pipeline checks out the code, installs dependencies, runs lint and tests, builds an artifact (usually a Docker image tagged with the commit SHA) and pushes it to a registry. The deploy step tells the platform to run the new image; health checks confirm it works before traffic moves over. If checks fail, the old version keeps serving.

    Why have a staging environment?

    It's a production-like rehearsal: same image, similar infrastructure and config, but test data. It catches problems that only appear with real infrastructure — env vars, networking, migrations — before users see them.

    How do you manage configuration and secrets across environments?

    Same code and image everywhere; config through environment variables. Secrets live in a secrets manager or the platform's encrypted settings and are injected at runtime. Nothing secret in Git, images or NEXT_PUBLIC_ variables, and the app validates required config at startup.

    What is the difference between build-time and runtime configuration?

    Build-time values are baked into the output during the build — for example NEXT_PUBLIC_* vars inlined into the browser bundle — so changing them needs a rebuild. Runtime values are read when the process starts, so one image can be promoted across environments by changing only runtime config.

    Explain how a request reaches your app at app.taskflow.dev.

    The browser resolves the name via DNS (a CNAME or A record), opens a TLS connection to the load balancer or CDN, which presents a certificate for the domain. The proxy/load balancer forwards the request to a healthy app instance, which may call the database and returns the response along the same path.

    🐳 Docker

    What is the difference between an image and a container?

    An image is a read-only layered template; a container is a running instance of it with a thin writable layer, its own process tree and network. Many containers can run from one image.

    How do you make Docker builds fast?

    Order instructions from least to most frequently changing: copy package*.json, run npm ci, then copy the source. Use .dockerignore to keep the context small, BuildKit cache mounts, and registry or CI layer caching.

    How do you shrink and harden an image?

    Slim or Alpine (or distroless) bases, multi-stage builds so build tools stay behind, npm ci --omit=dev, run as a non-root USER, no secrets in layers, pin base image versions and scan images with a tool such as Trivy.

    CMD vs ENTRYPOINT — when would you use each?

    ENTRYPOINT fixes the executable; CMD gives default arguments that docker run arguments replace. Most app images just use CMD ["node", "server.js"]. Use exec (JSON) form so the process is PID 1 and receives SIGTERM for graceful shutdown.

    Where should a containerised Postgres keep its data?

    In a named volume mounted at /var/lib/postgresql/data, so data survives container removal. In production, prefer a managed database with backups instead of a database container.

    🎼 Docker Compose

    Why use Docker Compose in development?

    It defines the whole stack — web, API, Postgres, Redis — in one versioned file, so a new developer runs docker compose up and gets identical services, networking and seeded data.

    How do containers in Compose talk to each other?

    Compose creates a network with DNS; each service is reachable by its service name on its container port, e.g. db:5432. localhost inside a container refers to that container only.

    depends_on doesn't stop my API crashing on startup. Why?

    Plain depends_on only orders container start; Postgres may not accept connections yet. Add a healthcheck to the DB and condition: service_healthy, and make the app retry connections anyway.

    How do you get hot reload with Compose?

    Use an override file that bind-mounts the source into the container and runs the dev server (node --watch, nodemon, next dev), with an anonymous volume for node_modules. Or use docker compose watch.

    Would you use Compose in production?

    For a single-server side project, yes, it's reasonable. For anything needing high availability, rolling deploys and autoscaling across machines, use a managed container platform (Cloud Run, ECS) or Kubernetes.

    ☁️ Cloud hosting

    How would you host TaskFlow and why?

    Next.js on Vercel for Git-based deploys, previews and CDN; the Express API as a container on Cloud Run (or ECS Fargate) for autoscaling without servers; Postgres on Cloud SQL (or RDS) in the same region with backups; Redis managed if needed. Secrets in Secret Manager; CI via GitHub Actions with OIDC.

    Explain the shared responsibility model.

    The provider secures the physical infrastructure and the layers it manages. The customer always owns its data, identities and access, app code and configuration. The more managed the service, the more the provider takes on (e.g. OS patching on Fargate vs EC2).

    What are security groups and how would you set them up?

    Stateful virtual firewalls. Load balancer: 443 from the internet. API: its port only from the load balancer's security group. Database: 5432 only from the API's security group. No SSH or DB ports open to the world.

    When would you choose serverless functions over containers?

    For spiky or event-driven work (webhooks, image processing, scheduled jobs) where scale-to-zero and per-request billing help. Containers suit long-running servers, WebSockets, steady traffic and heavy dependencies; cold starts and execution limits make functions a poor fit there.

    Managed database or self-hosted?

    Managed by default: automated backups, point-in-time recovery, patching and failover. Self-hosting is cheaper on paper but your team then owns backups, upgrades, replication and recovery testing.

    🔄 CI/CD

    Continuous delivery vs continuous deployment?

    Both keep main always releasable and automate the pipeline. Delivery has a manual approval before production; deployment ships every change that passes all checks automatically.

    How do you run integration tests that need a database in CI?

    Use a service container (e.g. postgres:16) with a health check, point DATABASE_URL at it, run migrations, then the tests. Each run gets a clean, disposable database.

    How should a pipeline authenticate to the cloud?

    With OIDC federation: GitHub issues a short-lived token, the cloud trusts it for a specific repo/branch/environment and returns temporary credentials for a least-privilege role. No long-lived keys stored as secrets.

    How do you speed up a slow pipeline?

    Cache dependencies and Docker layers, run independent jobs in parallel, use path filters so unrelated changes skip jobs, cancel superseded runs with concurrency, fail fast with lint first, and split slow test suites.

    What stops broken code reaching main?

    Branch protection or rulesets: PRs required, approvals, required status checks, up-to-date branches or a merge queue, and no force pushes.

    🛠️ Production operations

    Compare rolling, blue-green and canary deployments.

    Rolling replaces instances gradually with no extra capacity. Blue-green runs a full new environment and switches traffic at once, giving instant rollback at double cost. Canary sends a small share of traffic to the new version and increases it while watching metrics, limiting blast radius.

    How do you do database migrations with zero downtime?

    Expand/contract: add new structures in a backward-compatible way, deploy code that works with both, backfill, switch reads, and only remove the old structure in a later release. Run migrations as a separate pipeline step.

    A deploy just increased the error rate. What do you do?

    Mitigate first: roll back to the previous image or shift traffic back. Then look at logs, traces and error tracking for the new release, fix forward with tests, and write a blameless post-incident review.

    What makes an app horizontally scalable?

    Statelessness: sessions in Redis or tokens, files in object storage, single-run scheduled jobs, config from env. Then put instances behind a load balancer with autoscaling and protect the database with pooling and a max instance count.

    What do you monitor and alert on?

    The golden signals — traffic, errors, latency, saturation — plus uptime checks and error tracking. Alert on user-facing symptoms against SLOs, make every alert actionable, and link a runbook.

    🚨 Task 5 · A failed deploy and rollback

    Ten minutes after a deploy, 5xx errors jump from 0.1% to 12%. Logs show column "priority" does not exist. The new code expects a column the migration was supposed to add, but the migration step was skipped.

    ✍️ What do you do right now, and what do you change so this can't happen again?
    Model answer:
    • Now: roll back — shift Cloud Run traffic to the previous revision (or redeploy the previous SHA). Confirm error rate recovers. Communicate in the incident channel.
    • Then: run the migration properly (it's additive, so safe for the old code), redeploy the new image, watch metrics.
    • Prevent: make migrations a required pipeline step before deploy, make code tolerate the old schema (expand/contract), use canary or readiness checks so bad revisions get limited traffic, alert on error rate, write a blameless review.

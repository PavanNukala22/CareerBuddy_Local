    Data Layer Fundamentals

    Where data lives in a full-stack app, SQL vs NoSQL, basic data modelling, and the tools that sit between your code and the database.

    🧭 Where data lives in a full-stack app

    A full-stack app has three big parts: the frontend (what the user sees), the backend API (business rules) and the data layer (databases plus the code that talks to them). The browser never talks to the database directly. It calls the API, and only the API holds database credentials.

    Throughout this course we use TaskFlow, a team task tracker. Users belong to projects, projects contain tasks, and tasks have comments. Every change ("Asha moved task #42 to Done") is also written to an activity log.

    🐘
    PostgreSQL
    Core TaskFlow data: users, projects, tasks, comments. Relational, strict schema, ACID transactions.
    🍃
    MongoDB
    Activity and audit events: high-volume, append-mostly, flexible shape per event type.
    🧰
    ORM / ODM
    Prisma, TypeORM or Hibernate map tables to objects; Mongoose maps MongoDB documents to models.
    🔑
    Environment variables
    Connection strings and passwords live in env vars, never in the frontend bundle or in Git.
    🗂️
    Migrations
    Versioned scripts that change the schema step by step, the same way on every environment.
    📦
    Connection pool
    A small set of open database connections reused by many requests.
    One TaskFlow request: from a click to JSON and back
    EXAMPLE · Opening a project board

    Asha opens the "Website Redesign" board. The React page calls GET /api/projects/7/tasks. The API handler calls prisma.task.findMany({ where: { projectId: 7 } }). Prisma sends a parameterised SELECT to PostgreSQL, gets rows back, turns them into typed JavaScript objects, and the handler returns them as JSON.

    ⚠️
    Never put a database URL or password in frontend code. Anything shipped to the browser can be read by anyone. Only server code (API routes, server components, backend services) may connect to the database.

    ⚖️ SQL vs NoSQL — and when to use each

    SQL (relational) databases store data in tables with fixed columns and enforce relationships with foreign keys. NoSQL is a family name for stores that use other models; for application developers the most common is the document model (MongoDB), where each record is a JSON-like document.

    AspectSQL (PostgreSQL)Document NoSQL (MongoDB)
    Data shapeTables, rows, columnsCollections of JSON-like (BSON) documents
    SchemaDeclared up front, enforced by the databaseFlexible; optional JSON Schema validation
    RelationshipsForeign keys and JOINsEmbed related data or store references; $lookup for joins
    TransactionsACID, multi-row and multi-table, the default way of workingSingle-document writes are atomic; multi-document transactions exist but cost more
    Query languageSQLMQL (filter objects) and aggregation pipelines
    Scaling outUsually scale up plus read replicas; sharding needs extra toolsBuilt-in sharding across many servers
    Great forBusiness data with many relationships and strict rulesVarying shapes, nested data read together, high-volume events

    Many real systems use polyglot persistence: each kind of data goes to the store that fits it best.

    EXAMPLE · Polyglot persistence in TaskFlow
    • PostgreSQL: users, projects, memberships, tasks, comments. These have strong relationships and rules (a task must belong to a real project; an email must be unique).
    • MongoDB: activity events such as task.created, task.moved, comment.added. They are written often, rarely updated, and each type carries different details.
    • The two are linked by IDs only: an event stores projectId and taskId copied from PostgreSQL.
    💡
    Default to a relational database for core business data. Add a second store only when you have a clear reason, because every extra database adds backups, monitoring and consistency work.

    🧩 Data modelling basics: entities and relationships

    An entity is a thing you store data about (User, Project, Task). Each entity has attributes (title, status, dueDate) and a primary key that identifies it uniquely. Entities are linked by relationships, and the relationship type decides where the foreign key goes.

    TypeMeaningTaskFlow exampleHow it is stored in SQL
    One-to-one (1:1)Each A has at most one BUser ↔ UserProfileForeign key with a UNIQUE constraint on one side
    One-to-many (1:N)One A has many B; each B has one AProject → Taskstasks.project_id references projects.id
    Many-to-many (M:N)Many A relate to many BUsers ↔ Projects (members)A join table project_members(project_id, user_id, role)
    textusers ──< project_members >── projects ──< tasks ──< comments
  │                                         │
  └──────────── assignee (0..1) ────────────┘
( ──< means "one to many" )

    Good modelling habits:

    • Give every table a stable primary key (TaskFlow uses uuid).
    • Store each fact once (normalisation). Keep the project name in projects, not copied into every task.
    • Put extra data about a relationship on the join table (a member's role belongs on project_members).
    • Use constraints (NOT NULL, UNIQUE, CHECK, foreign keys) so the database rejects bad data even if the app has a bug.
    📝
    An optional relationship (a task may have no assignee yet) is a nullable foreign key. A required one (every task has a project) is NOT NULL.

    🛠️ Raw SQL vs query builder vs ORM vs ODM

    There are four common ways for application code to talk to a database. They trade control for convenience.

    ApproachWhat you writeExamplesProsCons
    Raw SQL (driver)SQL strings with parameterspg (node-postgres), JDBC, psycopgFull control, fastest path, every SQL featureManual mapping, no type safety, easy to repeat code
    Query builderSQL built with method chainsKnex, Kysely, jOOQComposable, safer than string building, close to SQLStill thinking in tables; limited object mapping
    ORMClasses / models; the tool writes SQLPrisma, TypeORM, Hibernate, SequelizeFast CRUD, relations, migrations, typesHidden queries, N+1 risk, complex SQL can be awkward
    ODMSchemas / models for documentsMongoose (MongoDB)Validation, defaults, hooks on top of a schemaless storeExtra layer and overhead; some features need raw driver

    The same TaskFlow query — open tasks in a project — three ways:

    javascript// 1. Raw SQL with node-postgres ($1 is a bound parameter)
const { rows } = await pool.query(
  'SELECT id, title FROM tasks WHERE project_id = $1 AND status <> $2',
  [projectId, 'DONE']
);

// 2. Query builder (Knex)
const tasks = await knex('tasks')
  .select('id', 'title')
  .where({ project_id: projectId })
  .whereNot({ status: 'DONE' });

// 3. ORM (Prisma)
const tasks2 = await prisma.task.findMany({
  where: { projectId, status: { not: 'DONE' } },
  select: { id: true, title: true },
});
    💡
    ORMs are not "all or nothing". Most teams use the ORM for 90% of queries and drop to raw SQL (safely parameterised) for reports, bulk updates or database-specific features.

    📖 Key terms

    Data layerThe databases plus the code (drivers, ORMs, repositories) that reads and writes them.
    SchemaThe structure of the data: tables, columns, types and constraints (or the expected document shape).
    Primary key (PK)Column(s) that uniquely identify a row, such as tasks.id.
    Foreign key (FK)Column that references another table's primary key, such as tasks.project_id.
    NormalisationOrganising tables so each fact is stored once, avoiding update anomalies.
    DenormalisationDeliberately copying data to make reads faster, at the cost of keeping copies in sync.
    ORMObject-Relational Mapper: maps relational rows to objects in your language.
    ODMObject-Document Mapper: maps documents (for example MongoDB) to objects; Mongoose is the best-known.
    DriverThe low-level library that speaks the database's network protocol.
    MigrationA versioned, ordered change to the schema, applied by a tool.
    Connection poolReusable open connections shared by requests to avoid reconnecting each time.
    TransactionA group of statements that succeed or fail together (ACID).
    Polyglot persistenceUsing several kinds of database in one system, each for the data it suits.
    Parameterised queryA query where values are sent separately from the SQL text, preventing SQL injection.

    PostgreSQL and SQL for App Developers

    Build the TaskFlow schema, then write the CRUD, join, aggregate and transaction queries an API really needs.

    🏗️ The TaskFlow schema in PostgreSQL

    PostgreSQL is a free, open-source relational database known for correctness and rich features. Current releases are in the 16–18 range. We start by creating TaskFlow's tables. Every ORM later in this course generates something very close to this.

    sqlCREATE TABLE users (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email       text NOT NULL UNIQUE,
  name        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE projects (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  owner_id    uuid NOT NULL REFERENCES users(id),
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE project_members (            -- M:N join table
  project_id  uuid REFERENCES projects(id) ON DELETE CASCADE,
  user_id     uuid REFERENCES users(id)    ON DELETE CASCADE,
  role        text NOT NULL DEFAULT 'member'
              CHECK (role IN ('owner', 'admin', 'member')),
  PRIMARY KEY (project_id, user_id)
);

CREATE TABLE tasks (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id  uuid NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  assignee_id uuid REFERENCES users(id) ON DELETE SET NULL,   -- optional
  title       text NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
  status      text NOT NULL DEFAULT 'TODO'
              CHECK (status IN ('TODO', 'IN_PROGRESS', 'DONE')),
  priority    smallint NOT NULL DEFAULT 2,
  due_date    date,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE comments (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  task_id     uuid NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  author_id   uuid NOT NULL REFERENCES users(id),
  body        text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
    FeatureWhat it does here
    uuid + gen_random_uuid()Random, globally unique IDs (built in since PostgreSQL 13). Safe to expose in URLs; PostgreSQL 18 also adds uuidv7() for time-ordered IDs.
    timestamptzTimestamp with time zone. Stored as UTC and converted on display. Prefer it over timestamp for events.
    REFERENCES … ON DELETE CASCADEDeleting a project deletes its tasks; deleting a task deletes its comments.
    ON DELETE SET NULLDeleting a user un-assigns their tasks instead of deleting them.
    CHECKRejects invalid values (unknown status, empty title) at the database level.
    UNIQUENo two users can share an email; PostgreSQL creates an index for it automatically.
    ⚠️
    PostgreSQL indexes primary keys and UNIQUE columns automatically, but not foreign key columns. Add indexes such as tasks(project_id) yourself, or joins and cascading deletes become slow.

    ✏️ CRUD: insert, select, update, delete

    CRUD means Create, Read, Update, Delete. In SQL these are INSERT, SELECT, UPDATE and DELETE. PostgreSQL's RETURNING clause sends back the affected rows, so the API does not need a second query.

    sql-- Create a task and get its generated id back
INSERT INTO tasks (project_id, title, assignee_id)
VALUES ($1, 'Design homepage', $2)
RETURNING id, status, created_at;

-- Read one task
SELECT id, title, status, due_date FROM tasks WHERE id = $1;

-- Update: move a task to Done
UPDATE tasks
SET status = 'DONE', updated_at = now()
WHERE id = $1
RETURNING id, status;

-- Delete
DELETE FROM tasks WHERE id = $1;

-- Upsert: add a member, or change their role if already a member
INSERT INTO project_members (project_id, user_id, role)
VALUES ($1, $2, 'admin')
ON CONFLICT (project_id, user_id) DO UPDATE SET role = EXCLUDED.role;
    ⚠️
    An UPDATE or DELETE without WHERE changes every row. In psql, run risky statements inside BEGIN so you can ROLLBACK.
    💡
    $1, $2 are placeholders. The driver sends values separately from the SQL text, so user input can never change the query. Never build SQL by concatenating strings.

    🔍 Filtering, sorting and pagination

    sqlSELECT id, title, status, priority, due_date
FROM tasks
WHERE project_id = $1
  AND status IN ('TODO', 'IN_PROGRESS')
  AND (due_date IS NULL OR due_date >= CURRENT_DATE)
  AND title ILIKE '%' || $2 || '%'     -- case-insensitive search
ORDER BY priority DESC, created_at DESC
LIMIT 20 OFFSET 40;                    -- page 3 of 20
    ClauseUseWatch out
    WHEREFilter rowsUse IS NULL, not = NULL (which is never true)
    INMatch any value in a listLong lists from the app are fine as an array parameter: = ANY($1)
    ILIKECase-insensitive pattern match (PostgreSQL)A leading % cannot use a normal B-tree index
    ORDER BYSort resultsWithout it, row order is not guaranteed
    LIMIT / OFFSETSimple page-number pagingDeep offsets get slower: the database still reads the skipped rows

    For long or infinite-scroll lists, use keyset (cursor) pagination: remember the last row you showed and ask for rows after it.

    sql-- next page after the last task shown (created_at, id)
SELECT id, title, created_at
FROM tasks
WHERE project_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 20;
    📝
    Always sort by a unique tie-breaker (here id) when paging. Otherwise rows with equal timestamps can repeat or be skipped between pages.

    📊 Aggregates: GROUP BY and HAVING

    Dashboards need totals. GROUP BY collapses rows into groups; aggregate functions (COUNT, SUM, AVG, MIN, MAX) summarise each group. WHERE filters rows before grouping; HAVING filters groups after.

    sqlSELECT p.name,
       COUNT(t.id)                                AS total,
       COUNT(*) FILTER (WHERE t.status = 'DONE')  AS done
FROM projects p
LEFT JOIN tasks t ON t.project_id = p.id
GROUP BY p.id, p.name
HAVING COUNT(t.id) >= 2
ORDER BY p.name;
    nametotaldone
    Mobile App21
    Website Redesign31
    EXAMPLE · Why Onboarding is missing

    The LEFT JOIN keeps Onboarding with one row of NULL task columns. COUNT(t.id) counts only non-NULL values, so its total is 0, and HAVING COUNT(t.id) >= 2 removes the group. Note that COUNT(*) would have counted that NULL row as 1 — a classic mistake.

    • FILTER (WHERE …) gives conditional counts in one pass (PostgreSQL and SQLite; elsewhere use SUM(CASE WHEN … THEN 1 ELSE 0 END)).
    • Every selected column must be grouped or aggregated. Grouping by the primary key p.id lets PostgreSQL accept other columns of p.
    • Push aggregation into SQL rather than loading thousands of rows into the API to count them.

    ⚡ Indexes and EXPLAIN (the basics)

    An index is a sorted lookup structure (a B-tree by default) that lets PostgreSQL find rows without reading the whole table. It speeds up reads but costs disk space and slows writes a little, so index the columns your queries actually filter, join and sort on.

    sql-- The board query filters by project and status
CREATE INDEX tasks_project_status_idx ON tasks (project_id, status);

-- Foreign keys used in joins
CREATE INDEX tasks_assignee_idx ON tasks (assignee_id);
CREATE INDEX comments_task_idx  ON comments (task_id);

-- On a busy production table, avoid blocking writes:
CREATE INDEX CONCURRENTLY tasks_due_idx ON tasks (due_date);

    EXPLAIN shows the plan PostgreSQL chose; EXPLAIN ANALYZE also runs the query and shows real times and row counts.

    Seq ScanReads every row. Fine for tiny tables; a red flag on big ones with selective filters.
    Index Scan / Index Only ScanUses an index to jump to matching rows (index-only: no table visit needed).

    🔒 Transactions and JSONB

    A transaction makes several statements succeed or fail together. If anything fails, ROLLBACK undoes all of them.

    sqlBEGIN;
  INSERT INTO tasks (project_id, title, assignee_id)
  VALUES ($1, 'Fix signup bug', $2)
  RETURNING id;                         -- say it returns $3
  INSERT INTO comments (task_id, author_id, body)
  VALUES ($3, $2, 'Created from bug report #881');
COMMIT;   -- both rows saved; on error, ROLLBACK saves neither
    • The default isolation level is READ COMMITTED: each statement sees data committed before it started.
    • Keep transactions short. Never wait for user input or call slow external APIs inside one; locks are held until commit.
    • Use SELECT … FOR UPDATE to lock rows you are about to change based on their current value.

    jsonb stores JSON in a binary, indexable form. It is handy for small, flexible extras without a schema change.

    sqlALTER TABLE tasks ADD COLUMN metadata jsonb NOT NULL DEFAULT '{}';

UPDATE tasks SET metadata = '{"source": "github", "labels": ["bug", "ui"]}'
WHERE id = $1;

SELECT title, metadata->>'source' AS source      -- ->> returns text
FROM tasks
WHERE metadata @> '{"labels": ["bug"]}';           -- containment

CREATE INDEX tasks_metadata_gin ON tasks USING gin (metadata);
    📝
    Use jsonb for genuinely variable data. Fields you filter, join or constrain on every day (status, due date) deserve real columns.

    MongoDB for the Activity Log

    Documents, embedding vs referencing, CRUD from mongosh and Node.js, indexes, aggregation and validation — using TaskFlow's activity events.

    📄 Documents and collections

    MongoDB stores documents: JSON-like objects saved in a binary format called BSON. Documents live in collections, and collections live in a database. Every document has a unique _id; if you do not supply one, the driver generates an ObjectId.

    Relational termMongoDB termNote
    DatabaseDatabaseSame idea
    TableCollectionNo fixed columns by default
    RowDocumentCan contain nested objects and arrays
    ColumnFieldDifferent documents may have different fields
    Primary key_idAlways indexed and unique
    JOINEmbedding, or $lookup in aggregationDesign so most reads need no join

    BSON adds types plain JSON lacks: ObjectId, Date, Decimal128, 64-bit integers and binary data. Store timestamps as real Date values, not strings, so range queries, sorting and TTL indexes work.

    📝
    The current major versions are MongoDB 7.0 and 8.0. Concepts in this tab apply to both, and to MongoDB Atlas, the managed cloud service.

    🗂️ Designing TaskFlow's activity events

    TaskFlow writes one event for every meaningful change. Events are append-mostly (written once, rarely edited), high-volume, and each type carries different details. That makes them a good fit for a MongoDB collection called activity_events.

    javascript// One document in taskflow_events.activity_events
{
  _id: ObjectId("6703f1c2a9e4b51d2c8f0a11"),
  type: "task.moved",
  projectId: "3b8f6c1e-…",            // uuid copied from PostgreSQL
  taskId: "9d2a0e44-…",
  actor: { id: "a1c9…", name: "Asha" },  // small snapshot, embedded
  details: { from: "IN_PROGRESS", to: "DONE" },
  createdAt: ISODate("2026-10-08T09:14:03Z")
}

// A different event type has different details
{
  type: "comment.added",
  projectId: "3b8f6c1e-…",
  taskId: "9d2a0e44-…",
  actor: { id: "b77e…", name: "Ben" },
  details: { commentId: "c0f2…", preview: "Looks good, merging" },
  createdAt: ISODate("2026-10-08T09:20:41Z")
}
    • Design for the queries. The feed reads "latest events for project X" and "history of task Y", so projectId, taskId and createdAt are top-level fields.
    • Snapshot the actor's name. The feed should show who did it at that time without querying PostgreSQL for every row.
    • Keep a stable envelope. Common fields (type, projectId, actor, createdAt) are always present; only details varies.
    • IDs, not foreign keys. MongoDB cannot enforce references into PostgreSQL. The app writes the event after the SQL change commits.
    💡
    For pure time-ordered metrics MongoDB also offers time series collections. A regular collection is simpler when events are queried by project or task and occasionally updated.

    🔀 Embed vs reference

    The central MongoDB modelling choice is whether related data goes inside a document (embedding) or in another document pointed to by an id (referencing).

    Embed when…

    • Data is read together with its parent
    • The child belongs to one parent only
    • The number of children is small and bounded
    • Example: the actor snapshot and details inside an event

    Reference when…

    • The related data is large or grows without limit
    • It is shared by many parents
    • It changes often and must be updated in one place
    • Example: events reference a project by projectId rather than embedding all events in a project document
    ⚠️
    A single document can be at most 16 MB. An unbounded array ("all events of a project" inside the project document) will eventually hit the limit and makes every update rewrite a huge document. This is the unbounded array anti-pattern.
    PatternShapeTaskFlow use
    Embedded objectactor: { id, name }Small snapshot read with every event
    Embedded bounded arraylabels: ['bug', 'ui']A handful of labels on an event
    Reference by idtaskId: '9d2a…'Linking to data owned by PostgreSQL
    Extended referenceid plus a few copied fieldsActor id plus name, to avoid a lookup

    🔎 Query operators and projections

    A MongoDB filter is an object. Plain values mean equality; operators starting with $ express everything else.

    OperatorExampleMatches
    $eq / $ne{ type: { $ne: 'comment.added' } }Not equal
    $gt $gte $lt $lte{ createdAt: { $gte: ISODate('2026-10-01') } }Ranges (numbers, dates, strings)
    $in / $nin{ type: { $in: ['task.created', 'task.moved'] } }Any of / none of a list
    $exists{ 'details.commentId': { $exists: true } }Field present
    $or / $and{ $or: [{ taskId: 't9' }, { 'actor.id': 'u1' }] }Combine conditions
    $regex{ 'actor.name': { $regex: '^As' } }Pattern match (anchored prefixes can use an index)
    Array equality{ labels: 'bug' }Any array element equals 'bug'
    $elemMatch{ items: { $elemMatch: { qty: { $gt: 5 }, sku: 'A1' } } }One element meets all conditions

    Dot notation ('actor.name') reaches into nested fields; the quotes are required. A projection chooses which fields come back:

    javascript// only type and createdAt, hide _id
db.activity_events.find(
  { projectId: "p1", createdAt: { $gte: ISODate("2026-10-01T00:00:00Z") } },
  { type: 1, createdAt: 1, _id: 0 }
)
    📝
    A projection cannot mix inclusion and exclusion, except for _id, which may be excluded from an inclusion projection.

    ⚡ Indexes and the aggregation pipeline

    Without an index MongoDB performs a COLLSCAN (reads every document). Create indexes that match your filters and sorts.

    javascript// Project feed: equality on projectId, sort by createdAt
db.activity_events.createIndex({ projectId: 1, createdAt: -1 })

// Task history
db.activity_events.createIndex({ taskId: 1, createdAt: -1 })

// TTL: delete events automatically after 365 days (field must hold Dates)
db.activity_events.createIndex({ createdAt: 1 }, { expireAfterSeconds: 31536000 })

// Check the plan: look for IXSCAN rather than COLLSCAN
db.activity_events.find({ projectId: "p1" }).sort({ createdAt: -1 }).explain("executionStats")
    💡
    Order compound index fields by the ESR rule: Equality fields first, then Sort fields, then Range fields.

    🛡️ Schema validation

    "Schemaless" does not have to mean "anything goes". MongoDB can validate documents on insert and update with a $jsonSchema validator.

    javascriptdb.createCollection("activity_events", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["type", "projectId", "actor", "createdAt"],
      properties: {
        type:      { enum: ["task.created", "task.moved", "task.deleted", "comment.added"] },
        projectId: { bsonType: "string" },

    include

    typescriptprisma.task.findMany({

    • Cursor pagination: cursor: { id: lastId }, skip: 1, take: 20 with a stable orderBy.

    🔒 Transactions and type safety

    Prisma offers two forms of $transaction:

    typescript// 1. Sequential batch: independent queries, all-or-nothing
const [task, log] = await prisma.$transaction([
  prisma.task.update({ where: { id }, data: { status: 'DONE' } }),
  prisma.comment.create({ data: { taskId: id, authorId: userId, body: 'Closed' } }),
]);

// 2. Interactive: use results of one query in the next. Use tx, not prisma!
await prisma.$transaction(async (tx) => {
  const member = await tx.projectMember.findUnique({
    where: { projectId_userId: { projectId, userId } },
  });
  if (!member) throw new Error('Not a member');   // throwing rolls back
  await tx.task.update({ where: { id: taskId }, data: { assigneeId: userId } });
}, { timeout: 10000 });
    ⚠️
    Inside an interactive transaction, every query must use the tx client. A stray prisma. call runs outside the transaction. Keep the callback short — no slow HTTP calls inside.

    🧷 Raw SQL safely: $queryRaw

    When a query is easier in SQL (reports, window functions, PostgreSQL-specific features), use raw queries. The tagged template form is safe: each ${…} becomes a bound parameter, not text pasted into the SQL.

    typescript// SAFE: ${projectId} is sent as parameter $1
const rows = await prisma.$queryRaw<{ status: string; total: bigint }[]>`
  SELECT status, COUNT(*) AS total
  FROM tasks
  WHERE project_id = ${projectId}::uuid
  GROUP BY status`;
// COUNT(*) comes back as a BigInt; convert with Number(row.total)

// Writes: $executeRaw returns the number of affected rows
const n = await prisma.$executeRaw`
  UPDATE tasks SET priority = priority + 1 WHERE due_date < now()`;

// DANGEROUS: string concatenation = SQL injection
await prisma.$queryRawUnsafe(`SELECT * FROM tasks WHERE title = '${userInput}'`);
    • Placeholders can only replace values, not table or column names. For dynamic identifiers, choose from a fixed allow-list.
    • Use Prisma.sql and Prisma.join([...ids]) to build safe dynamic fragments such as IN (…) lists.
    • If you must use $queryRawUnsafe, pass values as extra arguments ($queryRawUnsafe('… WHERE id = $1', id)) — never concatenate input.
    • Raw results are not mapped through @map; you get database column names.

    🐢 Avoiding the N+1 query problem

    The N+1 problem: one query loads a list of N items, then the code runs one more query per item. With 50 tasks that is 51 round trips.

    typescript// BAD: 1 query for tasks + 1 query per task for its assignee
const tasks = await prisma.task.findMany({ where: { projectId } });
for (const t of tasks) {
  t.assigneeName = t.assigneeId
    ? (await prisma.user.findUnique({ where: { id: t.assigneeId } }))?.name
    : null;
}

// GOOD: let Prisma load the relation in bulk
const tasks2 = await prisma.task.findMany({
  where: { projectId },
  select: { id: true, title: true, assignee: { select: { name: true } } },
});

    With include/select on a relation, Prisma by default runs one extra query per relation level using WHERE id IN (…) — so 2 queries here, not 51. It can also load relations with a single SQL JOIN via relationLoadStrategy: 'join' (the relationJoins preview feature).

    • Turn on query logging in development: new PrismaClient({ log: ['query'] }), and watch for repeated near-identical queries.
    • Aggregate in the database (groupBy, _count, $queryRaw) instead of counting in a loop.
    • Loops that call the database inside map or for are the usual suspects, including GraphQL resolvers (use DataLoader there).
    typescript// Dashboard counts per status in one query
const byStatus = await prisma.task.groupBy({
  by: ['status'],
  where: { projectId },
  _count: { _all: true },
});
// [{ status: 'TODO', _count: { _all: 4 } }, { status: 'DONE', _count: { _all: 7 } }, …]

    🏷️ TypeORM entities with decorators

    TypeORM is a TypeScript ORM (popular with NestJS) where each table is a class and decorators describe columns and relations. The current line is 0.3.x. It needs reflect-metadata and "experimentalDecorators": true plus "emitDecoratorMetadata": true in tsconfig.json.

    typescriptimport {
  Entity, PrimaryGeneratedColumn, Column, ManyToOne, OneToMany,
  JoinColumn, CreateDateColumn, UpdateDateColumn, Index,
} from 'typeorm';

@Index(['projectId', 'status'])

  @PrimaryGeneratedColumn('uuid')
  id!: string;

  @Column({ length: 200 })
  title!: string;

  @Column({ type: 'enum', enum: TaskStatus, default: TaskStatus.TODO })
  status!: TaskStatus;

  @Column({ name: 'due_date', type: 'date', nullable: true })
  dueDate!: string | null;

  @Column({ name: 'project_id', type: 'uuid' })
  projectId!: string;                      // raw FK value, handy for filters

  @ManyToOne(() => Project, (project) => project.tasks, { onDelete: 'CASCADE' })
  @JoinColumn({ name: 'project_id' })
  project!: Project;                      // the owning side holds the FK

  @ManyToOne(() => User, { nullable: true, onDelete: 'SET NULL' })

  @Column() name!: string;

}

    🗃️ TypeORM migrations — and why synchronize is unsafe

    synchronize: true tells TypeORM to alter the database at startup until it matches your entities. It is handy for a throwaway prototype and dangerous anywhere else.

    • A renamed property can be applied as drop column + add column, deleting the data.
    • There is no reviewed SQL, no history and no rollback plan.
    • Several app instances starting together can race to alter the same tables.
    • Changes happen at deploy time, silently, with the app's credentials.

    Instead, generate migrations, review them, commit them and run them in the deploy pipeline:

    bashnpx typeorm-ts-node-commonjs migration:generate src/migrations/AddTaskPriority -d src/data-source.ts
npx typeorm-ts-node-commonjs migration:run    -d src/data-source.ts
npx typeorm-ts-node-commonjs migration:revert -d src/data-source.ts   # undo the last one

    🧠 Persistence context, entity states and @Transactional

    The persistence context is the set of managed entities tracked by one EntityManager (a Hibernate Session), usually one per transaction. It acts as a first-level cache: loading the same id twice returns the same object without a second query.

    StateMeaningHow you get there
    Transient (new)A plain object, unknown to JPAnew Task()
    Managed (persistent)Tracked; changes are saved automatically at flushpersist(), find(), query results, merge()'s return value
    DetachedWas managed, but its persistence context closedTransaction ended, detach(), clear()
    RemovedScheduled for DELETE at flushremove()
    java@Service
public class TaskService {
    private final TaskRepository tasks;
    public TaskService(TaskRepository tasks) { this.tasks = tasks; }

    @Transactional
    public void complete(UUID id) {
        Task t = tasks.findById(id).orElseThrow();   // managed
        t.setStatus(TaskStatus.DONE);                // no save() call needed
    }   // commit -> flush -> dirty checking issues: UPDATE tasks SET status=?, version=? …

    @Transactional(readOnly = true)
    public List<TaskDto> board(UUID projectId) { … }
}

    Dirty checking: at flush time Hibernate compares each managed entity with the snapshot taken when it was loaded and writes UPDATEs for what changed.

    • Spring's @Transactional works through a proxy: calling the method from another method in the same class bypasses it.
    • By default it rolls back on unchecked exceptions (RuntimeException, Error), not on checked ones, unless you set rollbackFor.
    • readOnly = true lets Hibernate skip dirty checking and lets drivers/routers use read-only optimisations.
    • Put transactions on service methods (one use case = one transaction), not on controllers or repositories one by one.

    🐢 The N+1 problem and LazyInitializationException

    With LAZY associations, Hibernate returns proxies and loads them when first touched. Touching them in a loop causes N+1 queries:

    javaList<Task> tasks = taskRepository.findByProjectIdAndStatusOrderByCreatedAtDesc(pid, TODO); // 1 query

    names.add(t.getAssignee().getName());   // +1 query per distinct assignee
}

    JOIN FETCHselect t from Task t left join fetch t.assignee where …One query, explicit, per use case
    @EntityGraph@EntityGraph(attributePaths = {"assignee"}) on a repository methodSame effect without writing JPQL
    Batch fetching@BatchSize(size = 50) or hibernate.default_batch_fetch_size=50Loads proxies in groups with IN (…): N+1 becomes 1 + N/50
    DTO projectionselect new …Dto(t.id, t.title, a.name) from Task t left join t.assignee aRead-only screens; fetches only needed columns

    ⚠️
    Avoid fixing N+1 by switching to FetchType.EAGER: it loads the association everywhere, and with JPQL queries it often still runs as extra selects. Also, JOIN FETCH of two List collections at once throws MultipleBagFetchException — fetch one collection per query or use batch fetching.

    LazyInitializationException happens when you touch an uninitialised lazy association after the persistence context has closed — for example, serialising an entity to JSON in a controller after the service's transaction ended.

    • Load what the view needs inside the transaction (JOIN FETCH, entity graph).
    • Return DTOs from services instead of entities, so JSON serialisation never touches lazy proxies.
    • Set spring.jpa.open-in-view=false. Spring Boot enables Open Session in View by default (and logs a warning); it hides the problem by keeping a connection open during view rendering, which costs connections and hides N+1.

    ⚖️ ORM trade-offs: when to drop to SQL

    🚀
    ORM strengths
    Fast CRUD, relationship mapping, change tracking, portable queries, migrations and type safety.
    🕳️
    Leaky abstraction
    You still need SQL knowledge: plans, indexes, locks and transactions behave the same underneath.
    🐌
    Hidden costs
    Lazy loading, N+1, over-fetching whole entities, and huge persistence contexts in batch jobs.
    🧾
    Reports and analytics
    Window functions, CTEs, complex GROUP BYs read better as native SQL or a view.
    📦
    Bulk operations
    Updating 100k rows through entities is slow; one UPDATE statement is not.
    🧩
    DB-specific features
    jsonb operators, full-text search, ON CONFLICT, LISTEN/NOTIFY often need raw SQL.

    A healthy rule: ORM for the write model and simple reads, SQL for heavy reads and bulk work — always parameterised, and kept in one repository class so it is easy to find and test.

    💡
    Turn on SQL logging in development (spring.jpa.show-sql or, better, logging.level.org.hibernate.SQL=debug plus Hibernate statistics) and count queries per request in integration tests. Most ORM performance bugs are visible in the log long before production.

    🧩 Fundamentals and data modelling

    How do you choose between SQL and NoSQL for a new feature?

    Start from the data and the queries. If the data has many relationships, strict rules and needs multi-row transactions (users, projects, tasks, billing), use a relational database. If records are self-contained, vary in shape, are written at high volume and read as a whole (activity events, logs, content), a document store fits. In TaskFlow both exist: PostgreSQL for core data, MongoDB for the activity log. I add a second store only when the benefit outweighs the extra operations work.

    How do you model a many-to-many relationship, and where do extra attributes go?

    With a join table holding both foreign keys, usually as a composite primary key: project_members(project_id, user_id). Attributes of the relationship itself, like a member's role or joined_at, belong on the join table. In ORMs I map it as an explicit entity/model rather than an implicit many-to-many, so those columns are reachable.

    When would you use an ORM, a query builder or raw SQL?

    An ORM for everyday CRUD and relationship handling — it gives types, migrations and less boilerplate. A query builder when I want composable SQL without full mapping. Raw, parameterised SQL for reports, bulk updates and database-specific features (jsonb, window functions, ON CONFLICT). Most production apps mix the ORM with a few well-tested raw queries.

    How do you keep database credentials safe in a full-stack app?

    Credentials live in environment variables or a secret manager, never in Git or the frontend bundle. Only server code connects to the database. I use a least-privilege app user, a separate migration user where possible, TLS in the connection string, different credentials per environment, and rotate secrets. In Next.js no DB variable gets the NEXT_PUBLIC_ prefix.

    What is normalisation, and when would you denormalise?

    Normalisation stores each fact once so updates cannot create inconsistent copies — the project name lives only in projects. I denormalise deliberately when reads dominate and joining is costly or impossible, for example copying the actor's name into each MongoDB activity event. The price is keeping copies in sync, or accepting that they are historical snapshots.

    🐘 PostgreSQL and SQL

    Explain INNER JOIN vs LEFT JOIN with an example.

    INNER JOIN keeps only rows that match on both sides; LEFT JOIN keeps all rows from the left table and fills missing right columns with NULL. Listing tasks with JOIN users ON users.id = tasks.assignee_id hides unassigned tasks; a LEFT JOIN shows them with a NULL assignee. A common bug is filtering the right table in WHERE, which turns a LEFT JOIN back into an inner join.

    WHERE vs HAVING — and why does COUNT(*) vs COUNT(column) matter?

    WHERE filters rows before grouping; HAVING filters groups after aggregation. COUNT(*) counts rows, COUNT(col) counts non-NULL values. After a LEFT JOIN, a project with no tasks produces one row of NULLs: COUNT(*) says 1, COUNT(t.id) correctly says 0.

    How do you decide which indexes to add?

    From real queries: what the hot endpoints filter, join and sort on, found via pg_stat_statements and EXPLAIN ANALYZE. I index foreign keys (PostgreSQL does not do it automatically), use composite indexes with equality columns first, e.g. (project_id, status), and remove unused indexes because every index slows writes. On live tables I use CREATE INDEX CONCURRENTLY.

    Why is OFFSET pagination slow for deep pages, and what is the alternative?

    With OFFSET 100000 the database still reads and discards 100,000 rows. Keyset pagination remembers the last row's sort key and asks for WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20, which an index serves directly. It is stable while rows are inserted, but cannot jump to an arbitrary page number.

    When do you need a transaction, and what goes wrong with long ones?

    Whenever several writes must all succeed or all fail — creating a task and its first comment, or moving money. Long transactions hold locks and old row versions, blocking other writers and preventing VACUUM from cleaning up. Keep them short: no user waits or slow HTTP calls inside, and lock only what you must (SELECT … FOR UPDATE).

    🍃 MongoDB

    How do you decide between embedding and referencing?

    Embed what is read together, owned by one parent and bounded in size — like the actor snapshot and details in an activity event. Reference what is large, shared, frequently updated independently, or unbounded — like events of a project, which go in their own collection with a projectId. The 16 MB document limit and update cost rule out unbounded arrays.

    How would you design TaskFlow's activity collection and its indexes?

    One activity_events collection with a stable envelope: type, projectId, taskId, actor {id, name}, details, createdAt as a Date. Indexes follow the queries: { projectId: 1, createdAt: -1 } for the project feed, { taskId: 1, createdAt: -1 } for task history, and optionally a TTL index to expire old events. A $jsonSchema validator enforces the envelope.

    What is the ESR rule?

    When building a compound index, put fields used for Equality first, then fields used for Sort, then Range filters. This lets MongoDB seek to the equality prefix, read entries already in sort order, and avoid an in-memory sort.

    Does MongoDB support transactions? When would you use them?

    Yes: single-document operations are always atomic, and multi-document ACID transactions are supported on replica sets and sharded clusters. They cost more (coordination, time limits), so I design documents so most writes touch one document. If nearly every write needs a multi-document transaction, the data is probably better in a relational database.

    When is MongoDB a poor choice?

    When the data is highly relational and queried in many ad-hoc combinations, when strict cross-record invariants must hold on every write (balances, stock), or when the team mostly needs reporting with complex joins. Those workloads fit PostgreSQL better, which can also store flexible bits in jsonb.

    🔷 Prisma

    What is the difference between include and select?

    include returns all scalar fields of the model plus the relations you list. select returns only the fields you list, and can nest selects into relations. They cannot both be used at the same level. I prefer select for API responses to keep payloads small and avoid leaking sensitive columns; the generated TypeScript types follow whichever you use.

    migrate dev vs migrate deploy vs db push?

    migrate dev is for development: it generates a migration from schema changes, applies it, and may reset the database on drift. migrate deploy applies committed pending migrations without prompts or resets — that is what CI and production run. db push syncs the schema without creating migration files — fine for prototypes, not for a production history.

    How do Prisma transactions work?

    Two forms. The array form $transaction([q1, q2]) runs independent queries in order inside one transaction. The interactive form $transaction(async (tx) => { … }) lets you read, decide and write, using the tx client; throwing rolls back. Nested writes are already transactional. Interactive transactions should be short and have a timeout.

    Is $queryRaw safe from SQL injection?

    The tagged template form is: each ${value} becomes a bound parameter. $queryRawUnsafe with string concatenation is not. Parameters cannot replace identifiers, so dynamic column or table names must come from an allow-list. Prisma.sql and Prisma.join build safe dynamic fragments.

    Why do people create a Prisma singleton in Next.js?

    In development, hot reload re-evaluates modules; new PrismaClient() on every reload creates new connection pools and exhausts database connections. Storing the client on globalThis in non-production reuses one instance. In serverless production, I also use a connection pooler and a small connection limit.

    🧱 TypeORM and Mongoose

    Why is synchronize: true dangerous in production?

    It alters the schema at startup to match the entities, without review or history. A rename can become drop + add and lose data, several instances can race, and there is no rollback plan. I keep it false, generate migrations, review the SQL, commit them and run migration:run in the pipeline.

    Compare eager, lazy and explicit relation loading in TypeORM.

    Eager relations are joined on every find* call (not by QueryBuilder), which bloats queries. Lazy relations are Promise properties loaded on access — easy N+1 in loops. Explicit loading with relations or leftJoinAndSelect loads exactly what each use case needs, so it is my default.

    When would you use the TypeORM QueryBuilder instead of find options?

    For joins with conditions, aggregates and GROUP BY, subqueries, or selecting a few columns with getRawMany(). Values always go in named parameters (:projectId, (:...ids)). For very complex reports I use a raw parameterised query instead.

    What do Mongoose middleware hooks do, and what is a common gotcha?

    Hooks run before or after document operations (save, validate) or query operations (find, findOneAndUpdate, updateMany). Gotcha: logic in pre('save') does not run for updateOne/findOneAndUpdate, and update validators are off unless runValidators: true. Also, use normal functions so this is bound.

    When do you use populate() vs lean()?

    populate() resolves ObjectId references with extra queries ($in per path) — convenient but not a database join; for heavy cases $lookup in an aggregation may be better. lean() is a separate concern: it returns plain objects without document overhead, so I use it on read-only endpoints, often together with populate.

    ☕ Hibernate and JPA

    What is the difference between JPA and Hibernate?

    JPA (Jakarta Persistence) is the specification: annotations, EntityManager, JPQL and lifecycle rules. Hibernate ORM is an implementation of it, with extra features like batch fetching, @CreationTimestamp and its own dialects. Spring Data JPA sits on top and generates repositories.

    What is the persistence context and dirty checking?

    The persistence context is the set of managed entities for one EntityManager, usually per transaction. It guarantees one object per id and caches loads. At flush, Hibernate compares managed entities with their loaded snapshots and issues UPDATEs for changes — so in a @Transactional method, setting a field is enough; no save() needed.

    How do you detect and fix the N+1 problem in Hibernate?

    Detect it with SQL logging or Hibernate statistics and query-count assertions in tests. Fix it per use case: left join fetch in JPQL, @EntityGraph(attributePaths = …), batch fetching (@BatchSize or hibernate.default_batch_fetch_size), or a DTO projection. Switching to EAGER is not a fix — it loads data everywhere and can still issue extra selects.

    What causes LazyInitializationException and how do you prevent it?

    Touching an uninitialised lazy association after the persistence context closed — typically during JSON serialisation in the controller. Prevent it by fetching what the use case needs inside the transaction (join fetch, entity graph) and returning DTOs. I disable spring.jpa.open-in-view so the problem shows in development instead of being hidden.

    How do you manage schema changes in a Spring Boot + Hibernate app?

    With Flyway or Liquibase: versioned migrations in the repo, run automatically at startup or in the pipeline, recorded in a history table. Hibernate runs with ddl-auto=validate (or none), never update in production. Applied migrations are never edited; I add new ones and use expand-and-contract for zero-downtime changes.

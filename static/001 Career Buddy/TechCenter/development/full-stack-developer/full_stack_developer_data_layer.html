    Module 01 · Foundations

    What is the Data Layer?

    Start from zero: what a database is, why apps need one, and how SQL and NoSQL differ.

    🧭 What is a Database?

    A database is organised, persistent storage that many users and programs can read and write safely at the same time. Variables disappear when a program stops; a database keeps data and protects it from corruption, duplicates and conflicting updates. The data layer is the part of your app that talks to it.

    🗂️ Types of Databases

    TypeModelExamplesBest for
    Relational (SQL)Tables, rows, columns, relationshipsPostgreSQL, MySQLStructured data, transactions, reporting
    Document (NoSQL)JSON-like documentsMongoDBFlexible, nested, fast-changing data
    Key-valueKey → valueRedis, DynamoDBCaching, sessions, counters
    Wide-columnRows with dynamic columnsCassandraHuge write-heavy workloads
    GraphNodes and edgesNeo4jSocial networks, recommendations
    SearchInverted indexElasticsearchFull-text search

    ⚖️ SQL vs NoSQL

    🧱 SQL (PostgreSQL)

    Fixed schema, JOINs, strong ACID transactions. Choose when data is related and correctness matters (payments, enrolments).

    🍃 NoSQL (MongoDB)

    Flexible schema, data stored together, scales out easily. Choose when records vary in shape or are read as one unit (activity feeds, catalogues).

    💡
    Not either/or. Many production systems use PostgreSQL as the source of truth and Redis for caching.

    🔒 ACID in One Minute

    AtomicityAll steps of a transaction succeed, or none do.
    ConsistencyData always satisfies the rules (constraints).
    IsolationConcurrent transactions do not see each other's half-done work.
    DurabilityOnce committed, data survives crashes.
    EXAMPLE · Bank transfer

    Debit A and credit B must be one atomic transaction. If the credit fails, the debit rolls back.

    Module 02 · SQL & PostgreSQL

    SQL & PostgreSQL

    Design tables, query with joins and aggregates, add indexes, and use transactions.

    🏗️ Creating Tables (DDL)

    sqlCREATE TABLE students (
  id    SERIAL PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name  TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE courses (id SERIAL PRIMARY KEY, title TEXT NOT NULL, price NUMERIC(8,2) CHECK (price >= 0));
CREATE TABLE enrolments (
  student_id INT REFERENCES students(id) ON DELETE CASCADE,
  course_id  INT REFERENCES courses(id),
  enrolled_at TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (student_id, course_id)       -- prevents duplicates
);
    Primary keyUniquely identifies a row.
    Foreign keyPoints to a row in another table; enforces integrity.
    ConstraintsNOT NULL, UNIQUE, CHECK keep bad data out.

    ✏️ CRUD Queries (DML)

    sqlINSERT INTO students (email, name) VALUES ('a@x.com', 'Asha');
SELECT id, name FROM students WHERE name LIKE 'A%' ORDER BY created_at DESC LIMIT 10;
UPDATE courses SET price = 499 WHERE id = 3;
DELETE FROM enrolments WHERE student_id = 7 AND course_id = 3;
    ⚠️
    Always include WHERE on UPDATE/DELETE — without it, every row changes. Never build SQL by concatenating user input; use parameters ($1, $2).

    🔗 JOINs & Aggregates

    sql-- students with the courses they take
SELECT s.name, c.title
FROM students s
JOIN enrolments e ON e.student_id = s.id
JOIN courses c    ON c.id = e.course_id;

-- courses with enrolment counts (including zero)
SELECT c.title, COUNT(e.student_id) AS learners
FROM courses c LEFT JOIN enrolments e ON e.course_id = c.id
GROUP BY c.id HAVING COUNT(e.student_id) >= 0
ORDER BY learners DESC;
    JOINReturns
    INNEROnly matching rows in both tables
    LEFTAll left rows, matches or NULL
    RIGHTAll right rows, matches or NULL
    FULLAll rows from both

    🧬 Normalisation

    Store each fact once. 1NF: atomic values, no repeating columns. 2NF: every column depends on the whole key. 3NF: no column depends on a non-key column. Denormalise deliberately only for proven read performance.

    ⚡ Indexes, Transactions & EXPLAIN

    sqlCREATE INDEX idx_enrol_course ON enrolments (course_id);

BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;                                   -- or ROLLBACK on error

EXPLAIN ANALYZE SELECT * FROM students WHERE email = 'a@x.com';
    🔎
    Index trade-off
    Faster reads, slower writes and more disk. Index columns used in WHERE, JOIN, ORDER BY.
    🧭
    Seq Scan vs Index Scan
    EXPLAIN shows which one runs. A Seq Scan on a big table is a red flag.
    🧱
    Isolation levels
    Read Committed (default), Repeatable Read, Serializable — stronger = safer, slower.
    🧩
    PostgreSQL extras
    JSONB columns, CTEs (WITH), window functions, full-text search.

    MongoDB (NoSQL)

    Documents, collections, CRUD, the aggregation pipeline and how to model data.

    🍃 What is MongoDB?

    MongoDB stores documents (BSON, similar to JSON) in collections. Documents in one collection can have different fields, and can nest arrays and objects.

    SQLMongoDB
    DatabaseDatabase
    TableCollection
    RowDocument
    ColumnField
    JOIN$lookup or embedding

    ✏️ CRUD

    javascriptdb.courses.insertOne({ title: "React", tags: ["js","ui"], lessons: [{ n: 1, name: "JSX" }] });
db.courses.find({ tags: "js", price: { $lt: 1000 } }).sort({ title: 1 }).limit(10);
db.courses.updateOne({ title: "React" }, { $set: { price: 499 }, $push: { tags: "hooks" } });
db.courses.deleteOne({ title: "React" });
    Operators$eq $gt $lt $in $and $or $set $push $inc
    _idAuto-generated unique ObjectId per document.

    🧮 Aggregation Pipeline

    javascriptdb.enrolments.aggregate([
  { $match: { status: "active" } },
  { $group: { _id: "$courseId", learners: { $sum: 1 } } },
  { $sort: { learners: -1 } },
  { $limit: 5 },
  { $lookup: { from: "courses", localField: "_id", foreignField: "_id", as: "course" } }
]);

    🧩 Data Modelling: Embed or Reference?

    📦 Embed

    Put related data inside the document. One read, atomic update. Use for "contains" relations that are small and read together (a course's lessons).

    🔗 Reference

    Store the other document's _id. Use for large, unbounded or shared data (students ↔ courses).

    ⚠️
    Documents are limited to 16 MB and unbounded arrays hurt performance. Model for your queries, and create indexes: db.courses.createIndex({ title: 1 }).

    Module 04 · ORMs & ODMs

    ORMs & ODMs: Prisma, TypeORM, Hibernate

    Map database rows to objects in code — and avoid the classic traps.

    🔌 What is an ORM / ODM?

    An ORM (Object-Relational Mapper) lets you work with SQL tables as objects in your language. An ODM does the same for document databases (Mongoose for MongoDB). Benefits: less boilerplate, type safety, migrations, built-in protection against SQL injection. Cost: abstraction can hide slow queries.

    ToolLanguageDatabaseStyle
    PrismaTypeScript/NodePostgreSQL, MySQL, MongoDB…Schema file + generated type-safe client
    TypeORMTypeScript/NodeMost SQL DBsDecorators on classes
    Hibernate / JPAJavaMost SQL DBsAnnotations, powers Spring Data JPA
    MongooseNodeMongoDBSchemas and models (ODM)

    🏷️ TypeORM, Hibernate & Mongoose

    typescript// TypeORM
@Entity() class Course {
  @PrimaryGeneratedColumn() id: number;

    java// Hibernate / JPA

  @OneToMany(mappedBy = "course", fetch = FetchType.LAZY) List<Enrolment> enrolments;
}
    javascript// Mongoose
const Course = mongoose.model("Course", new mongoose.Schema({
  title: { type: String, required: true }, price: { type: Number, min: 0 }
}));

    🐌 The N+1 Problem & Migrations

    EXAMPLE · N+1 queries

    Loading 100 courses then looping to fetch each course's teacher = 1 + 100 queries. Fix: eager-load with include (Prisma), relations/JOIN FETCH (TypeORM/Hibernate), or populate (Mongoose).

    💡
    Use migrations (versioned schema changes in Git) — never edit production tables by hand. Turn on query logging in development to catch slow or repeated queries.

    Module 05 · Expert: Performance & Scale

    Performance, Scaling & Reliability

    Query tuning, safe migrations, replication, sharding and backup strategy.

    🏎️ Query Tuning

    📈
    Composite indexes
    Order matters: index (course_id, enrolled_at) serves queries filtering on course_id, or both.
    🎯
    Covering & partial indexes
    Index only the rows you query: WHERE status='active'.
    📄
    Keyset pagination
    WHERE id > $last LIMIT 20 beats big OFFSETs.
    🧹
    VACUUM & statistics
    Keep PostgreSQL tables healthy so the planner picks good plans.

    🌍 Scaling Strategies

    StrategyWhatWatch out for
    Vertical scalingBigger machineHas a ceiling
    Read replicasCopies serve readsReplication lag
    Caching (Redis)Hot data in memoryInvalidation
    PartitioningSplit big tables by range/hashQuery design
    ShardingSplit data across serversComplexity; cross-shard queries
    📝
    CAP theorem: in a network partition a distributed store must choose between consistency and availability. Know which your use case needs.

    🛟 Safe Operations

    Zero-downtime migrationAdd nullable column → backfill → deploy code → add constraint (expand/contract).
    Backups & PITRAutomated backups plus point-in-time recovery. Test restores regularly.
    Connection poolingPgBouncer or built-in pools stop connection exhaustion.
    Least privilegeApp uses a limited DB role, never the superuser.
    Encryption & PIITLS in transit, encryption at rest, mask personal data.

    Model, query and optimise real data.

    🎯 Scenario

    An LMS stores students, courses, enrolments and lesson progress. Reports must show learners per course and each student's completion %.

    1️⃣ Task 1 · Schema

    ✍️ List the tables, their primary keys and the foreign keys.
    Model answer: students(id), courses(id), lessons(id, course_id→courses), enrolments(student_id, course_id) PK composite, progress(student_id, lesson_id) PK composite with completed_at.
    Q. Which constraint prevents a student enrolling twice in the same course?
    • A CHECK on price
    • B Composite PRIMARY KEY (student_id, course_id)
    • C NOT NULL on name
    • D Index on title

    2️⃣ Task 2 · Query

    ✍️ Write SQL for the number of learners per course, including courses with none.
    Model answer: SELECT c.title, COUNT(e.student_id) FROM courses c LEFT JOIN enrolments e ON e.course_id=c.id GROUP BY c.id; — LEFT JOIN keeps courses with zero enrolments.

    3️⃣ Task 3 · Optimise

    Q. A report on enrolments by course is slow and EXPLAIN shows a Seq Scan. First fix?
    • A Add RAM
    • B Add an index on enrolments(course_id)
    • C Switch to MongoDB
    • D Delete data
    ✍️ Where would MongoDB fit in this system?
    Model answer: Flexible, nested content such as lesson content blocks or activity/event logs; keep enrolments and payments in PostgreSQL for transactions.

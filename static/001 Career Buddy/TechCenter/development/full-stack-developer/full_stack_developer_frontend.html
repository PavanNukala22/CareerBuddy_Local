    Full Stack & Web Fundamentals

    What a full-stack developer does, how the layers of a web app fit together, and how the browser turns code into a page.

    🧑‍💻 What does a full-stack developer do?

    A full-stack developer can build every part of a web application: the screens people use in the browser (the frontend), the server code that holds the business rules (the backend or API), the database that stores the data, and the infrastructure that runs and deploys it all.

    Nobody is an expert in everything. A good full-stack developer is strong in one or two layers and comfortable enough in the others to ship a feature from the database column all the way to the button on screen — and to debug a problem wherever it lives.

    🖥️
    Frontend
    HTML, CSS, JavaScript/TypeScript, React or Next.js. What users see and touch.
    🔌

    Node/Express, FastAPI or Spring. Validates input, applies rules, talks to the database.
    🗄️

    🧅 The layers of a web app and how a request flows

    Every feature in a web app is a round trip through the layers. The user does something in the UI, the frontend calls the API, the API reads or writes the database, and the response comes back so the UI can update.

    One full-stack round trip: from a click to an updated screen

    EXAMPLE · Moving a task to “Done”

    The user drags a card. React updates the card optimistically, then sends PATCH /api/tasks/42 with {"status":"done"}. Express checks the user is logged in and is a member of the project, runs UPDATE tasks SET status = 'done' WHERE id = 42, writes an activity log entry to MongoDB, and returns the updated task as JSON. If the API fails, the UI rolls the card back and shows an error.

    📝
    The browser can never be trusted. Anything the frontend checks (required fields, permissions) must be checked again on the server.

    🌐 How the browser turns code into a page

    When you open https://taskflow.app/board, the browser looks up the server's IP address (DNS), opens a secure connection (TLS), sends an HTTP request, and receives HTML. Then it builds the page:

    1. Parse HTML → DOM: a tree of elements the browser and JavaScript can work with.
    2. Parse CSS → CSSOM: the style rules. CSS is render-blocking — the browser waits for it before painting.
    3. Run JavaScript: a classic <script> pauses HTML parsing; defer and type="module" scripts run after parsing.
    4. Render tree → layout → paint → composite: work out sizes and positions, draw pixels, and combine layers on screen.
    html<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>TaskFlow</title>
    <link rel="stylesheet" href="/styles.css">   <!-- render-blocking -->
    <script src="/app.js" defer></script>      <!-- runs after parsing -->
  </head>
  <body>
    <div id="root"></div>
  </body>
</html>
    DOMDocument Object Model — the live tree of elements. JavaScript and React change it to update the page.
    Reflow / layoutRecalculating positions and sizes. Triggered by changes to size, content or fonts.
    RepaintRedrawing pixels (e.g. a colour change) without changing layout. Cheaper than reflow.
    HydrationAttaching React's event handlers to HTML that was already rendered on the server.

    ⚖️ Client-side vs server-side rendering

    Where is the HTML built? That one question explains most modern frontend architectures.

    StrategyHTML is built…Good forTrade-off
    CSR — client-side renderingIn the browser by JavaScript (empty <div id="root"> first)Highly interactive apps behind a loginSlower first paint, weak SEO, big JS bundle
    SSR — server-side renderingOn the server for every requestPersonalised or fast-changing pagesServer work per request; needs hydration
    SSG — static site generationOnce, at build timeMarketing pages, docs, blogsData is only as fresh as the last build
    ISR / revalidationAt build time, then refreshed in the backgroundProduct or content pages that change sometimesUsers may briefly see slightly old data

    Pure CSR (e.g. a Vite + React SPA)

    • Server sends a nearly empty HTML file
    • Browser downloads JS, then fetches data
    • User sees a spinner first
    • Simple hosting: static files on a CDN

    Server rendering (e.g. Next.js)

    • Server fetches data and sends real HTML
    • User sees content quickly
    • React hydrates it to make it interactive
    • Needs a server or serverless runtime
    💡
    Modern frameworks mix strategies per page. In TaskFlow, the public landing page is static, while the logged-in board is rendered on the server with fresh data and then becomes interactive in the browser.

    📦 The box model, units and specificity

    Every element is a box: content, then padding, then border, then margin. By default width sets only the content size, which makes maths awkward — so almost every project starts with box-sizing: border-box.

    css*, *::before, *::after { box-sizing: border-box; }

.task-card {
  width: 100%;
  padding: 0.75rem 1rem;          /* inside the border */
  border: 1px solid var(--border);
  margin-block-end: 0.5rem;       /* space below the card */
  border-radius: 0.5rem;
}

    ⏳ Promises, async/await and fetch done right

    Network calls take time, so JavaScript returns a Promise — a placeholder for a future value. async/await lets you write that code top-to-bottom.

    typescriptexport async function getTasks(projectId: number): Promise<Task[]> {
  const res = await fetch(`/api/projects/${projectId}/tasks`, {
    headers: { Accept: "application/json" },
  });

  // fetch only rejects on network failure — NOT on 404 or 500!
  if (!res.ok) {
    throw new Error(`Failed to load tasks: ${res.status}`);
  }
  return res.json() as Promise<Task[]>;
}

export async function createTask(input: NewTask): Promise<Task> {
  const res = await fetch("/api/tasks", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(input),
  });
  if (!res.ok) throw new Error(`Create failed: ${res.status}`);
  return res.json();
}

    🔄 The event loop in two minutes

    JavaScript runs on one main thread. Slow work (network, timers) is handed to the browser or Node; when it finishes, a callback is queued. The event loop runs queued work only when the call stack is empty.

    javascriptconsole.log("1 sync");
setTimeout(() => console.log("4 macrotask (timer)"), 0);
Promise.resolve().then(() => console.log("3 microtask (promise)"));
console.log("2 sync");
// Output: 1 sync, 2 sync, 3 microtask (promise), 4 macrotask (timer)
    1. Run all synchronous code on the call stack.
    2. Drain the microtask queue (Promise callbacks, await continuations, queueMicrotask).
    3. Browser may render (style, layout, paint).
    4. Take the next macrotask (timers, events, network callbacks) and repeat.
    💡
    A long synchronous loop (say, sorting 100,000 tasks) blocks clicks and rendering — that is what a poor INP score measures. Move heavy work to the server, paginate, or use a Web Worker.

    🌊 useEffect for data fetching — and its pitfalls

    useEffect runs code after render to synchronise with something outside React: the network, a timer, a subscription. The dependency array says when to re-run it.

    🪝 Custom hooks: useTasks

    A custom hook is a function whose name starts with use and which calls other hooks. It packages stateful logic so components stay simple and the logic can be reused and tested.

    tsx// hooks/useTasks.ts
export function useTasks(projectId: number) {
  const [tasks, setTasks] = useState<Task[]>([]);
  const [error, setError] = useState<Error | null>(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    let ignore = false;
    setLoading(true);
    api<Task[]>(`/projects/${projectId}/tasks`)
      .then(data => { if (!ignore) { setTasks(data); setError(null); } })
      .catch(err => { if (!ignore) setError(err); })
      .finally(() => { if (!ignore) setLoading(false); });
    return () => { ignore = true; };
  }, [projectId]);

  async function moveTask(id: number, status: TaskStatus) {
    const before = tasks;
    setTasks(ts => ts.map(t => (t.id === id ? { ...t, status } : t)));   // optimistic
    try {
      await api(`/tasks/${id}`, { method: "PATCH", body: JSON.stringify({ status }) });
    } catch {
      setTasks(before);                                                  // roll back
    }
  }

  return { tasks, loading, error, moveTask };
}

// In a component
const { tasks, loading, error, moveTask } = useTasks(projectId);

    • Call hooks only at the top level of a component or custom hook — never inside loops, conditions or nested functions.
    • Call them only from React function components or custom hooks.
    • Each call to a custom hook gets its own state; hooks share logic, not data.

    Responsive UI Design

    Make TaskFlow work beautifully on a phone, a tablet and a wide monitor — accessible, fast and themeable.

    📱 Mobile-first and the viewport meta tag

    Responsive design means one codebase that adapts to any screen size and input method. Mobile-first means you write the base styles for small screens and add complexity with min-width media queries as space grows.

    html<!-- Without this, phones render at ~980px wide and zoom out -->
<meta name="viewport" content="width=device-width, initial-scale=1">

    css/* Base = phone: one column, stacked */
.board { display: grid; gap: 1rem; }

/* Tablet and up: two columns */
@media (min-width: 48rem) {
  .board { grid-template-columns: repeat(2, 1fr); }
}

/* Desktop: three columns + sidebar */
@media (min-width: 64rem) {
  .app   { grid-template-columns: 15rem 1fr; }
  .board { grid-template-columns: repeat(3, 1fr); }
}

    Mobile-first (min-width)

    • Simple base styles that every device gets
    • Adds layout as space increases
    • Phones download and apply less override CSS
    • Forces you to prioritise content

    Desktop-first (max-width)

    • Base styles assume a large screen
    • Overrides strip things away for small screens
    • Often ends in long chains of undo rules
    • Still common in older codebases
    ⚠️
    Never disable zoom with user-scalable=no or maximum-scale=1. People with low vision rely on pinch-zoom.

    📏 Breakpoints, media queries and container queries

    Choose breakpoints where your content breaks, not for specific phone models. Common starting points are about 40rem, 48rem, 64rem and 80rem. Media queries can also test capabilities and preferences, not just width.

    🧭 Full-stack fundamentals

    Walk me through what happens when a user clicks “Save” on a task form in a full-stack app.

    The form's submit handler (or a Server Action) collects the values and the frontend validates them for quick feedback. It sends an HTTP request — say POST /api/tasks with a JSON body and the session cookie. The API authenticates the user, checks they may edit that project, validates the body again (e.g. with Zod), and writes to PostgreSQL inside a transaction. It returns 201 with the created task. The frontend updates its state or cache (or revalidates the page), and React re-renders the board. On failure it shows an error and, if it updated optimistically, rolls back.

    Compare CSR, SSR and SSG. How would you choose for TaskFlow?

    CSR builds HTML in the browser with JavaScript — simple hosting, but slower first paint and weaker SEO. SSR renders HTML per request — fresh, personalised data with fast first paint, at the cost of server work. SSG renders once at build time — fastest and cheapest, but data is only as fresh as the build (or the revalidation interval). For TaskFlow: SSG for the marketing site and docs, SSR/dynamic rendering for the logged-in board, and client-side updates for interactions such as dragging cards.

    Why must validation happen on both the client and the server?

    Client validation is for user experience: instant feedback without a round trip. But the client is fully controlled by the user — DevTools, curl or a script can send anything. The server is the only place you can enforce rules and protect data integrity and security. Sharing one schema (e.g. Zod in a shared package) keeps both sides consistent.

    How do you debug “the data on screen is wrong”?

    Split the problem at the API boundary. Open the Network panel and look at the response. If the JSON is wrong, the bug is on the server: check the API handler, the SQL query and the data in the database. If the JSON is right, the bug is in the frontend: check how state is updated, stale caches, wrong keys, or a mapping/formatting function. Then reproduce it in a test so it stays fixed.

    What is CORS and how would you fix a CORS error between the Next.js app and the Express API?

    Browsers block a page from reading responses from another origin (scheme + host + port) unless the server allows it with headers like Access-Control-Allow-Origin. Non-simple requests (JSON POST, custom headers) trigger an OPTIONS preflight. The fix is on the API: configure the cors middleware to allow the exact frontend origin (and credentials: true if cookies are sent). Alternatives: put both behind the same domain, or call the API from the Next.js server (BFF), where CORS does not apply.

    🎨 HTML & CSS

    Why does semantic HTML matter in an app, not just on content sites?

    Native elements give behaviour and meaning for free: a <button> is focusable and works with Enter/Space; <label for> makes inputs clickable and announced; landmarks (<nav>, <main>) let screen-reader users jump around. It also improves SEO and makes CSS and tests simpler, because you can select by role. Rebuilding these with <div> and ARIA is more code and more bugs.

    Explain the CSS cascade and specificity. How do you avoid specificity wars?

    When rules conflict, the browser compares origin and importance, then cascade layers, then specificity (IDs > classes/attributes/pseudo-classes > elements), then source order. To avoid wars: style with single classes, avoid IDs and !important, use component-scoped approaches (CSS Modules, Tailwind), and use @layer to order resets, base styles, components and utilities explicitly.

    When do you use Flexbox and when Grid?

    Flexbox is one-dimensional and content-driven: a toolbar, a card footer, centring an icon next to text. Grid is two-dimensional and layout-driven: the app shell (sidebar + content), a board of columns, a card gallery. They combine well — Grid for the page frame and Flexbox inside components. repeat(auto-fit, minmax(…, 1fr)) gives a responsive grid without media queries.

    What are CSS custom properties and how do they help with theming?

    They are variables (--accent: #2563eb) read with var(--accent). They live at runtime, inherit through the DOM and follow the cascade, so a theme switch can redefine tokens on :root or a [data-theme="dark"] selector and every component updates — no rebuild and no duplicated stylesheets. JavaScript can also read and set them.

    A z-index of 9999 does not bring a dropdown above a card. Why?

    z-index only competes within the same stacking context. If the dropdown's ancestor creates a stacking context (transform, opacity < 1, filter, or position with a z-index), the dropdown cannot escape it, however high its number. Fixes: remove the property creating the context, raise the ancestor's z-index, or render the dropdown in a portal at the end of <body> — or use the native popover attribute / <dialog>, which render in the top layer.

    🟨 JavaScript & TypeScript

    Explain the event loop and the difference between microtasks and macrotasks.

    JavaScript runs on a single thread with a call stack. Async work is handled by the host (browser or Node); callbacks are queued. When the stack is empty, the event loop first drains all microtasks (Promise reactions, await continuations, queueMicrotask), then the browser may render, then it takes the next macrotask (a timer, an event, a message). That is why a resolved Promise's .then runs before a setTimeout(…, 0) callback.

    What are common mistakes with fetch?

    Not checking res.ok (fetch resolves on 404/500); forgetting Content-Type: application/json and JSON.stringify for bodies; not handling network errors; firing requests in sequence that could run in parallel with Promise.all; no timeout or cancellation (AbortController); race conditions where an older response overwrites a newer one; and trusting the response shape without validation.

    interface or type — which do you use?

    Both describe object shapes. interface can be extended with extends and merged by redeclaring it (useful for augmenting library types). type can express anything: unions, intersections, mapped and conditional types, tuples. Many teams use type by default and interface for public object contracts; what matters most is consistency.

    How do you keep frontend and backend types in sync?

    If both sides are TypeScript, put schemas in a shared workspace package and derive types from them (z.infer<typeof TaskSchema>), so runtime validation and static types match. If the backend is FastAPI or Spring, generate TypeScript types from its OpenAPI spec in CI. End-to-end options such as tRPC or Server Actions share types automatically. In every case, validate untrusted data at the boundary — a type assertion like as Task is not a check.

    What is the difference between any and unknown?

    any switches off type checking: you can call anything on it and errors spread silently. unknown accepts any value but forces you to narrow it (with typeof, instanceof, a type guard or a schema parse) before use. Use unknown for untrusted input such as JSON.parse results or catch errors.

    ⚛️ React

    What triggers a re-render in React, and how do you avoid unnecessary ones?

    A component re-renders when its state changes, when its parent re-renders, or when a Context it reads changes. Re-rendering is usually cheap; optimise only when profiling shows a problem. Techniques: keep state close to where it is used, split large contexts, avoid creating new object/array props each render for memoised children, use memo / useMemo / useCallback where measured, virtualise long lists — or let the React Compiler handle memoisation automatically.

    Why are keys important in lists?

    Keys identify items between renders so React can match old and new elements. With stable keys (database IDs), reordering or inserting items keeps each item's DOM and state attached to the right data. Using the index breaks this when the list changes order — inputs can show the wrong values. Random keys are worse: every item remounts on every render.

    What are the pitfalls of fetching data in useEffect?

    Race conditions (an older response arriving last), missing cleanup, missing or unstable dependencies causing stale data or infinite loops, request waterfalls (child fetches start only after parent renders), no caching or deduplication, and double requests in Strict Mode development. Fixes: abort or ignore stale requests in cleanup, use a data library such as TanStack Query, or fetch in Server Components in Next.js.

    When would you use Context, and when not?

    Use Context for values many components at different depths need and that change rarely: current user, theme, locale, feature flags. Do not use it as a general store for fast-changing data — every consumer re-renders on each change. Server data belongs in a server-state cache (TanStack Query) or Server Components; shareable UI state such as filters belongs in the URL; local UI state stays in useState.

    What is a custom hook and why write one?

    A function whose name starts with use and that calls other hooks. It extracts stateful logic — e.g. useTasks(projectId) handling fetch, loading, errors and optimistic moves — so components focus on rendering, the logic is reusable and it can be tested on its own. Each component that calls it gets its own independent state.

    ▲ Next.js

    Explain Server Components vs Client Components.

    Server Components are the default in the App Router. They run only on the server, can be async, access the database and secrets, and send no component JavaScript to the browser. Client Components ("use client") are pre-rendered on the server and hydrated in the browser; they can use state, effects, event handlers and browser APIs. Best practice: keep pages and data fetching on the server and push "use client" down to the interactive leaves, passing serialisable props.

    Route Handler or Server Action — how do you choose?

    Use a Server Action for mutations triggered by your own UI — forms and buttons — because it gives typed calls, progressive enhancement and easy revalidation. Use a Route Handler when something other than your React UI calls the endpoint: a mobile app, a webhook, a third-party integration, or when you need GET, custom status codes or streaming responses. Both are public HTTP endpoints, so both must authenticate, authorise and validate.

    How do loading.tsx, error.tsx and Suspense work together?

    loading.tsx wraps the route segment's page in a <Suspense> boundary so a fallback shows instantly while the server renders. You can add finer <Suspense> boundaries around slow parts (an activity feed) so the rest streams first. error.tsx is a Client Component error boundary for that segment; it receives the error and a reset function to retry, while the layout around it stays usable.

    What is the difference between DATABASE_URL and NEXT_PUBLIC_API_URL in a Next.js app?

    Variables without a prefix are only available on the server — safe for secrets such as DATABASE_URL. NEXT_PUBLIC_ variables are inlined into the client JavaScript at build time, so anyone can read them and changing them requires a rebuild. Never put secrets behind that prefix.

    How would you protect the /projects/[projectId] page so only project members can see it?

    Use a proven auth library to issue an HttpOnly session cookie. Optionally redirect signed-out users early in Middleware/Proxy for UX. The real check happens on the server, close to the data: in the page's data-access function, read the session, verify a membership row exists for that project and user, and call notFound() or return 403 otherwise. Apply the same check in every Route Handler and Server Action that touches the project.

    📱 Responsive & accessible UI

    What does mobile-first mean, and why is it the usual approach?

    Write base styles for the smallest screen, then add layout with min-width media queries as space grows. It keeps the base simple, sends phones less override CSS, and forces you to prioritise content. Combine it with intrinsic layouts (auto-fit/minmax, clamp()) and container queries so fewer breakpoints are needed.

    Media queries vs container queries?

    Media queries respond to the viewport (and user preferences such as dark mode or reduced motion) — right for page-level layout. Container queries respond to the size of a component's container — right for reusable components like a task card that may appear in a narrow sidebar or a wide main area. Declare a container with container-type: inline-size and query it with @container.

    How do you make the drag-and-drop TaskFlow board accessible?

    Provide a non-drag alternative: a “Move to…” menu or buttons on each card (WCAG 2.2 Dragging Movements). Support the keyboard (focusable cards, arrow keys or menu), announce moves through a live region, keep a visible :focus-visible style, show status by text not just colour, ensure targets are large enough, and test with a screen reader. Libraries such as dnd-kit include keyboard sensors and announcements.

    What are the Core Web Vitals and their “good” thresholds?

    LCP (Largest Contentful Paint) ≤ 2.5 s for loading, INP (Interaction to Next Paint) ≤ 200 ms for responsiveness, and CLS (Cumulative Layout Shift) ≤ 0.1 for visual stability — measured at the 75th percentile of real visits. Improve LCP with server rendering, a fast backend and a prioritised hero image; INP with less JavaScript and shorter tasks; CLS with image dimensions and reserved space.

    How do you implement dark mode properly?

    Define colours as custom-property tokens; set color-scheme: light dark; switch token values under prefers-color-scheme: dark and let a data-theme attribute override the OS choice. Store the user's choice (cookie, so the server renders the right theme without a flash). Re-check contrast for every token in both themes, and avoid pure white on pure black for long text.

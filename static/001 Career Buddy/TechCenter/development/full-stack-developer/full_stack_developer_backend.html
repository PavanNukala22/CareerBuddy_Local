    Backend Fundamentals for Full Stack Developers

    What the backend does in a full-stack app, how a request flows through its layers, and how to choose between Node, Python and Java.

    🧭 What the backend does in a full-stack app

    A full-stack app has two halves. The frontend runs in the user's browser and draws the screens. The backend runs on a server you control. It receives requests from the frontend, applies business rules, talks to the database and sends back a response, usually JSON.

    In TaskFlow, our running example, the Next.js frontend shows a board of tasks. When a user drags a task to “Done”, the browser sends PATCH /api/tasks/42 with {"status": "done"}. The backend checks the user is logged in, checks they belong to the task's project, updates PostgreSQL, writes an activity log entry to MongoDB and returns the updated task.

    📊

    ⚠️

    APIApplication Programming Interface — the set of URLs and rules the frontend uses to talk to the backend.
    RESTA style of API where URLs name resources (/tasks) and HTTP methods name actions (GET, POST, PATCH, DELETE).
    JSONJavaScript Object Notation — the usual text format for request and response bodies.

    🔁 HTTP request and response

    Every interaction is an HTTP request followed by a response. A request has a method, a path, headers and an optional body. A response has a status code, headers and an optional body.

    🛤️ How a request flows through the layers

    Inside the backend a request passes through several layers. Each layer has one job. The names differ slightly between frameworks, but the shape is the same in Express, FastAPI, Django and Spring Boot.

    A TaskFlow request travelling through the backend layers
    LayerJobTaskFlow example
    RouteMatch method + path to a handler.POST /api/tasks → createTask
    MiddlewareCross-cutting work that runs before (and after) handlers.Parse JSON, log the request, check the session cookie, CORS.
    Controller (handler)Translate HTTP to a function call: read params/body, validate, call the service, pick the status code.Reads req.body, validates it, returns 201.

    EXAMPLE · Who decides the 403?

    The rule “only project members may add tasks” is a business rule, so it lives in the service. The service throws a ForbiddenError. The error-handling middleware (or @ControllerAdvice in Spring) turns it into a 403 JSON response. This way the same rule also protects a CLI script or a background job that calls the service directly.

    🧱 Layered architecture and separation of concerns

    Separation of concerns means each piece of code has one reason to change. HTTP details stay in controllers, rules stay in services, SQL stays in repositories. When you move from Express to Fastify, only the controllers change. When you add an index or switch ORM, only repositories change.

    🪶 Stateless servers

    A stateless server keeps nothing about a user in its own memory between requests. Everything it needs comes from the request (a cookie, a token) or from shared storage (PostgreSQL, Redis). Any copy of the server can answer any request.

    Stateless copies behind a load balancer share state through external stores
    StateBad place (in-process)Good place (shared)
    Login sessionsA JavaScript object / Python dict in memoryRedis or a database sessions table, or a signed token
    Uploaded filesThe container's local diskObject storage such as Amazon S3
    CachesPer-process map (fine only for small, read-only data)Redis
    Scheduled jobsA setInterval in every copyOne scheduler or a job queue
    EXAMPLE · Why TaskFlow users got logged out

    A developer stored sessions in an in-memory map. With one server it worked. After scaling to three copies, each request could land on a different copy that had never seen the session, so users were randomly logged out. Moving sessions to Redis made every copy see the same data.

    💡
    Stateless servers can be restarted, replaced and scaled at any time. That is what platforms like Kubernetes, AWS ECS and serverless functions expect.

    Node.js & Express

    🟢 The Node.js runtime and event loop

    Node.js runs JavaScript outside the browser, using Chrome's V8 engine. For full-stack developers the big win is one language — TypeScript — on both sides. Use an LTS (long-term support) release such as Node 22 or 24 for production.

    Node runs your JavaScript on one main thread. Slow I/O (database queries, HTTP calls, file reads) is handed to the operating system or a small thread pool. While Node waits, the event loop runs other requests. When the I/O finishes, its callback or awaited promise continues.

    Non-blocking I/O: one thread serves many requests while each waits on the database
    ⚠️
    Anything CPU-heavy or synchronous (fs.readFileSync per request, a huge JSON.parse, image resizing, bcrypt.hashSync) blocks the single thread and freezes every request. Use async APIs, worker threads or a background job.
    V8Google's JavaScript engine that compiles JS to machine code.
    libuvThe C library that gives Node its event loop and thread pool.
    Non-blockingStarting I/O and continuing other work instead of waiting idle.

    🧩 Middleware: JSON, CORS, logging and auth

    A middleware is a function (req, res, next). It can read or change the request, end the response, or call next() to pass control on. Middleware runs in the order you register it.

    Order of middleware in the TaskFlow API
    typescriptimport cors from 'cors';
import { randomUUID } from 'node:crypto';

app.use(express.json());
app.use(cors({
  origin: ['https://taskflow.dev', 'http://localhost:3000'],
  credentials: true,                       // allow cookies from the Next.js app
}));

// tiny request logger
app.use((req, res, next) => {
  const start = Date.now();
  req.id = randomUUID();
  res.on('finish', () => {
    log.info({ id: req.id, method: req.method, url: req.originalUrl,
               status: res.statusCode, ms: Date.now() - start }, 'request');
  });
  next();
});

// custom auth middleware (session lookup simplified)
export async function requireAuth(req, res, next) {
  const user = await sessions.findUser(req.cookies?.sid);
  if (!user) return res.status(401).json({ error: 'Not logged in' });
  req.user = user;
  next();
}

app.use('/api/tasks', requireAuth, tasksRouter);   // only protects task routes
    ⚠️
    A middleware must either send a response or call next(). If it does neither, the request hangs until the client times out.
    💡
    Reading cookies needs the cookie-parser middleware. In TypeScript, add id and user to the Request type with declaration merging.

    🚨 Async handlers and centralised error handling

    In Express 5, if an async handler throws or its promise rejects, Express automatically passes the error to the error-handling middleware. (In Express 4 you needed try/catch + next(err) or a wrapper like express-async-errors.)

    An error-handling middleware has four parameters (err, req, res, next) and is registered after all routes. It turns every error into a consistent JSON response.

    typescript// src/errors.ts
export class AppError extends Error {
  constructor(public status: number, message: string, public code = 'ERROR') {
    super(message);
  }
}
export class NotFoundError extends AppError {
  constructor(what: string) { super(404, `${what} not found`, 'NOT_FOUND'); }
}

// src/middleware/error-handler.ts
import type { ErrorRequestHandler } from 'express';
import { ZodError } from 'zod';

export const errorHandler: ErrorRequestHandler = (err, req, res, _next) => {
  if (err instanceof ZodError) {
    return res.status(400).json({ error: 'VALIDATION', details: err.issues });
  }
  if (err instanceof AppError) {
    return res.status(err.status).json({ error: err.code, message: err.message });
  }
  req.log?.error({ err }, 'unhandled error');
  res.status(500).json({ error: 'INTERNAL', message: 'Something went wrong' });
};

// src/app.ts - last
app.use(errorHandler);
    ⚠️
    Never send err.stack or raw database messages to the client in production. Log them on the server; send a short, safe message and maybe a request ID.
    EXAMPLE · A 404 for an unknown task

    The service calls tasksRepo.findById(99), gets null and throws new NotFoundError('Task'). Express 5 forwards the rejection, the error handler sees an AppError and replies 404 {"error":"NOT_FOUND","message":"Task not found"}. The controller has no try/catch at all.

    ✅ Validation with Zod

    Never trust req.body. Zod describes the expected shape once and gives you both runtime validation and a TypeScript type. The same schema can be shared with the Next.js frontend form.

    typescript// src/schemas/task.schema.ts
import { z } from 'zod';

export const CreateTaskSchema = z.object({
  projectId: z.number().int().positive(),
  title: z.string().trim().min(1).max(200),
  description: z.string().max(5000).optional(),
  dueDate: z.coerce.date().optional(),
  assigneeId: z.number().int().positive().optional(),
});
export type CreateTaskInput = z.infer<typeof CreateTaskSchema>;

export const ListTasksQuery = z.object({
  status: z.enum(['todo', 'in_progress', 'done']).optional(),
  page: z.coerce.number().int().min(1).default(1),
});

    Schema.parse(data)Returns typed data or throws a ZodErrorInside handlers, letting the error handler return 400
    Schema.safeParse(data)Returns { success, data } or { success: false, error }When you want to branch without exceptions
    💡
    Zod strips unknown keys by default, so a client cannot sneak "role": "admin" into an object you later save. Use z.strictObject if you want unknown keys to be an error instead.

    🗂️ A TaskFlow tasks router in TypeScript

    Putting it together: routes map URLs to controllers, controllers validate and call the service, the service holds the rules and calls the repository.

    typescript// src/routes/tasks.routes.ts
import { Router } from 'express';
import * as ctrl from '../controllers/tasks.controller.js';

export const tasksRouter = Router();
tasksRouter.get('/', ctrl.list);
tasksRouter.post('/', ctrl.create);
tasksRouter.get('/:id', ctrl.getOne);
tasksRouter.patch('/:id', ctrl.update);
tasksRouter.delete('/:id', ctrl.remove);

// src/controllers/tasks.controller.ts
import type { Request, Response } from 'express';
import { CreateTaskSchema, ListTasksQuery } from '../schemas/task.schema.js';
import * as taskService from '../services/task.service.js';

export async function list(req: Request, res: Response) {
  const q = ListTasksQuery.parse(req.query);
  res.json(await taskService.list(req.user, q));
}

export async function create(req: Request, res: Response) {
  const input = CreateTaskSchema.parse(req.body);
  const task = await taskService.create(req.user, input);
  res.status(201).location(`/api/tasks/${task.id}`).json(task);
}

export async function getOne(req: Request, res: Response) {
  const id = Number(req.params.id);
  res.json(await taskService.getById(req.user, id));   // throws NotFoundError
}
// update and remove follow the same pattern

    typescript// src/services/task.service.ts
export async function create(user: User, input: CreateTaskInput) {
  if (!(await membersRepo.isMember(user.id, input.projectId))) {
    throw new AppError(403, 'Not a member of this project', 'FORBIDDEN');
  }
  const task = await tasksRepo.insert({ ...input, status: 'todo', createdBy: user.id });
  await activityLog.record({ type: 'task.created', taskId: task.id, userId: user.id }); // MongoDB
  return task;
}
    💡

    🔗 Services, beans and constructor injection

    Spring creates and wires objects for you. These managed objects are beans, held in the application context. You ask for a dependency by declaring it as a constructor parameter; Spring passes in the bean. This is dependency injection.

    java@Service
public class TaskService {

    private final TaskRepository tasks;
    private final ProjectMemberRepository members;
    private final CurrentUser currentUser;

    // single constructor: no @Autowired needed
    public TaskService(TaskRepository tasks, ProjectMemberRepository members, CurrentUser currentUser) {
        this.tasks = tasks;
        this.members = members;
        this.currentUser = currentUser;
    }

    @Transactional
    public TaskResponse create(CreateTaskRequest req) {
        Long userId = currentUser.id();
        if (!members.existsByProjectIdAndUserId(req.projectId(), userId)) {
            throw new ForbiddenException("Not a member of this project");
        }
        Task task = new Task(req.projectId(), req.title(), req.dueDate(), userId);
        return TaskResponse.from(tasks.save(task));
    }

    @Transactional(readOnly = true)
    public TaskResponse get(Long id) {
        return tasks.findById(id).map(TaskResponse::from)
                .orElseThrow(() -> new TaskNotFoundException(id));
    }
}

    🔑 Password hashing with bcrypt and Argon2

    Never store passwords, and never encrypt them. Store a slow, salted hash. At login, hash the attempt the same way and compare. A salt is random data stored with each hash so identical passwords get different hashes and precomputed tables are useless.

    AlgorithmNotes
    Argon2idModern first choice (winner of the Password Hashing Competition). Memory-hard, which slows GPU attacks.
    bcryptProven and everywhere. Use a cost factor of at least 10–12. Only the first 72 bytes of the password are used.
    scrypt / PBKDF2Acceptable where required (e.g. FIPS). PBKDF2 needs a very high iteration count.
    MD5, SHA-1, SHA-256 aloneNever for passwords — far too fast to brute-force.

    🍪 Session cookies vs JWT for a web app

    After login the server must recognise the user on later requests. Two common approaches:

    Server-side session

    • Server creates a random session ID and stores { userId, expires } in Redis or the database.
    • Browser receives it in a cookie: sid=8f3c....
    • Each request: look up the ID. Logout or “sign out everywhere” = delete the row.
    • Needs a shared store, one extra lookup per request.

    JWT (JSON Web Token)

    • Server signs a token containing claims like {"sub": 9, "role": "member", "exp": ...}.
    • Any server with the key can verify it without a lookup.
    • Hard to revoke before it expires — keep access tokens short (minutes) and use refresh tokens.
    • Payload is only encoded, not encrypted: anyone can read it.

    For a browser-based app like TaskFlow, the safest default is to keep the session ID or token in a cookie with the right flags, not in localStorage where any injected script (XSS) can read it.

    HttpOnlyJavaScript cannot read the cookie, so an XSS bug cannot steal it.
    SecureOnly sent over HTTPS.
    SameSite=LaxNot sent on most cross-site requests (blocks most CSRF); still sent on top-level link navigation. Strict is tighter; None requires Secure and allows cross-site use.
    Max-Age / ExpiresHow long the cookie lives; omit for a browser-session cookie.
    Path / DomainWhich URLs receive the cookie.

    🏎️ Performance basics and the twelve-factor checklist

    The N+1 query problem: you load N tasks with one query, then run one more query per task to load its assignee — N+1 round trips. It is invisible with 5 rows and painful with 5,000.

    StackFix for N+1
    Raw SQL / NodeOne JOIN, or a second query with WHERE id = ANY($1) for all IDs; Prisma include batches it
    Django ORMselect_related (foreign key, JOIN) and prefetch_related (many-to-many / reverse)
    SQLAlchemyselectinload / joinedload options
    JPA / HibernateJOIN FETCH in JPQL, @EntityGraph, or batch fetching

Keep the pool small (often 10–20 per instance) — total connections = pool size × instances, and PostgreSQL has a hard max_connections limit. Serverless functions may need an external pooler such as PgBouncer or a provider's pooled URL.

    🧭 Fundamentals

    Walk me through what happens when the TaskFlow frontend creates a task.

    The Next.js form sends POST /api/tasks with JSON and the session cookie. The API's middleware parses JSON, logs the request with a request ID and authenticates the cookie. The router calls the controller, which validates the body and calls the task service. The service checks the user is a project member, applies defaults and calls the repository, which runs a parameterised INSERT in PostgreSQL. The controller returns 201 with the new task and a Location header; errors at any step go to the central error handler, which returns a consistent JSON error.

    Why separate controllers, services and repositories?

    Each layer has one reason to change. Controllers know HTTP, services hold business rules, repositories hold data access. Services can be unit-tested with fake repositories, reused by jobs and scripts, and survive a framework or ORM change. For a tiny app keep it light, but keep rules out of route handlers.

    What is the difference between 401 and 403?

    401 Unauthorized means the request has no valid authentication — the user is not logged in or the token is invalid. 403 Forbidden means the server knows who you are but you are not allowed to do this. Some APIs return 404 instead of 403 for other users' resources to avoid revealing that they exist.

    What does it mean for a server to be stateless, and why does it matter?

    No per-user data is kept in process memory between requests; sessions, files and caches live in shared services like Redis, PostgreSQL and S3. Then any instance can serve any request, so you can scale horizontally, deploy with rolling restarts and recover from crashes without logging users out.

    How do you manage configuration across dev, staging and production?

    Config comes from environment variables (twelve-factor). Locally a git-ignored .env file supplies them, with a committed .env.example. In deployed environments the platform or a secrets manager injects them. Config is validated at startup so a missing value fails fast. Spring Boot adds profiles; the same build artefact is promoted through every environment.

    🟢 Node and Express

    Explain the Node.js event loop and what blocks it.

    Node runs JavaScript on one main thread. I/O is delegated to the OS or libuv's thread pool, and when it completes the callback or promise continuation is queued and run by the event loop. Synchronous CPU work — big JSON parsing, crypto with sync APIs, tight loops, readFileSync — blocks the thread, so no other request progresses. Fix with async APIs, worker threads, a job queue, or more processes.

    How does error handling work in Express 5?

    Errors thrown in sync handlers and rejected promises from async handlers are passed to the next error-handling middleware automatically. You register one handler with four parameters (err, req, res, next) after all routes. It maps known error types (validation, not found, forbidden) to status codes and logs unknown ones, returning a generic 500. In Express 4 async errors needed next(err) or a wrapper.

    How do you validate requests in an Express + TypeScript API?

    Define a Zod schema per input, call .parse (or safeParse) on req.body, req.query and req.params, and derive the TypeScript type with z.infer. Zod strips unknown keys and coerces query strings where asked. ZodErrors go to the error handler as 400s. The same schemas can be shared with the frontend.

    ESM or CommonJS for a new project, and why?

    ESM: it is the JavaScript standard, supports static analysis and top-level await, and matches frontend code. Set "type": "module" and, in TypeScript, "module": "NodeNext". CommonJS is still found in older packages; modern Node can import CJS from ESM, and recent versions can also require() most ESM.

    How would you structure middleware order in an Express app?

    Security headers (helmet) and CORS first, then body parsing with size limits, request ID and logging, rate limiting for sensitive routes, authentication, then routers (with per-route authorisation), a 404 handler, and finally the error-handling middleware. Order matters because middleware runs in registration order.

    🐍 Django and FastAPI

    When would you choose Django over FastAPI?

    Django when you want batteries included: ORM, migrations, admin back office, auth and a mature ecosystem — great for data-heavy CRUD products. FastAPI when you want a lean, async JSON API with Pydantic validation and automatic OpenAPI docs — common for ML/AI services and high-concurrency I/O.

    What does Depends do in FastAPI?

    It declares a dependency that FastAPI resolves per request: a DB session, the current user, settings. Dependencies can depend on others, can use yield for cleanup after the response, and can be replaced in tests with app.dependency_overrides.

    What is the difference between async def and def endpoints in FastAPI?

    async def endpoints run on the event loop and must only await non-blocking libraries. Plain def endpoints run in a thread pool, so blocking calls are acceptable. Calling blocking code inside async def stalls every request on that worker.

    Explain Django migrations.

    makemigrations compares models with the previous migration state and writes Python migration files; migrate applies unapplied migrations and records them in the django_migrations table. Migrations are committed to Git and run during deployment, never edited after being applied in shared environments.

    How do you avoid N+1 queries in Django?

    Use select_related for foreign keys and one-to-one (SQL JOIN) and prefetch_related for many-to-many and reverse relations (a second batched query). Spot problems with Django Debug Toolbar or query logging and assert query counts in tests with assertNumQueries.

    ☕ Spring Boot

    What does @SpringBootApplication do?

    It combines @SpringBootConfiguration, @EnableAutoConfiguration and @ComponentScan. Auto-configuration creates beans based on the classpath and properties; component scanning registers annotated classes in the main class's package and sub-packages.

    Why prefer constructor injection?

    Dependencies are explicit and can be final; the object is never half-built; circular dependencies fail fast; and unit tests can create the class with new and fakes without Spring. With a single constructor no @Autowired is needed.

    How do you handle errors globally in Spring Boot?

    A @RestControllerAdvice class with @ExceptionHandler methods maps exceptions to responses, ideally ProblemDetail (RFC 9457). Validation failures from @Valid raise MethodArgumentNotValidException, which you map to 400 with field errors.

    What are Spring profiles used for?

    Profiles group configuration and beans by environment — dev, test, prod. You activate them with SPRING_PROFILES_ACTIVE; profile-specific YAML documents or files override defaults, and @Profile can enable beans conditionally. Secrets still come from env vars or a secrets manager.

    Why not return JPA entities from controllers?

    Entities mirror the database, may include sensitive fields and have lazy relations that trigger extra queries or serialisation errors outside a transaction. Returning DTOs (records) decouples the API contract from the schema and lets each evolve independently.

    🔐 Auth and security

    Sessions or JWT for a Next.js + API web app?

    For a first-party browser app, server-side sessions in an HttpOnly, Secure, SameSite=Lax cookie are simple and easy to revoke. JWTs suit stateless verification across many services or third-party clients; use short-lived access tokens and refresh tokens, and still prefer HttpOnly cookies over localStorage in browsers.

    How should passwords be stored?

    As salted, slow hashes using Argon2id (preferred) or bcrypt with a suitable cost; never plain, encrypted or with a fast hash like SHA-256. Compare with the library's verify function, use async APIs in Node and return the same error for unknown email and wrong password.

    What is CORS and what is it not?

    CORS is a browser rule: a server lists which origins may read its responses from JavaScript, with preflight requests for non-simple calls. It is not authentication or authorisation — non-browser clients ignore it. With credentials you must name exact origins rather than *.

    How do you prevent SQL injection?

    Never build SQL by concatenating input. Use parameterised queries or an ORM/query builder that binds values, validate input with schemas, use least-privilege database users, and be careful with raw-SQL escape hatches and dynamic ORDER BY columns (use allow-lists).

    How would you add Google sign-in?

    Use OAuth 2.0 Authorization Code with PKCE via OpenID Connect, through a library (Auth.js, Passport, Authlib, Spring Security OAuth2 Client) or a hosted identity provider. Verify the ID token, map it to a local user, create your own session, and apply your own authorisation rules.

    🚀 Production

    What makes a backend production-ready?

    Structured logs with request IDs, metrics and traces; consistent error handling and error tracking; health checks; validated config and secrets from a manager; graceful shutdown; migrations; tests in CI; rate limiting and security headers; and capacity basics like pagination, indexes, caching and connection pools.

    Liveness vs readiness probes?

    Liveness asks whether the process is healthy; failing it restarts the container, so it should not depend on the database. Readiness asks whether the instance can serve traffic; failing it removes the instance from the load balancer until it recovers.

    When do you move work to a background job?

    When it is slow, can fail and needs retries, or is not needed for the response: emails, webhooks, report generation, image processing. Use a durable queue (BullMQ, Celery, RabbitMQ/Kafka with Spring) with idempotent jobs, retries with back-off and a dead-letter queue.

    How do you test a backend?

    Unit-test services with fake repositories; integration-test endpoints in-process (Supertest, TestClient, MockMvc) against a real database started by Testcontainers; add a few end-to-end tests through the frontend. Run all in CI on every pull request.

    A list endpoint got slow as data grew. How do you investigate?

    Measure first: APM traces and logs show where time goes. Check the SQL — N+1 queries, missing indexes (EXPLAIN ANALYZE), unbounded results without pagination. Then check pool saturation and payload size. Fix the biggest cost, add a regression test or query-count assertion, and consider caching only after the queries are sound.

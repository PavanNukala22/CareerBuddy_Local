    Module 01 · Foundations

    What is an API?

    Start from zero: what APIs are, how a request travels, the different types, and your first live call.

    🧭 What is an API?

    An API (Application Programming Interface) is a contract that lets one piece of software talk to another without knowing how the other one works inside. You send a request in an agreed format; you get a response in an agreed format.

    A web API does this over the network, usually HTTP. When your phone shows today's weather, the app is not measuring the weather itself — it calls a weather API and displays the result.

    🔴 Without an API

    Every app would need direct access to every database and codebase it depends on. Changing one system would break all the others, and security would be impossible.

    🟢 With an API

    Each system exposes a small, documented, controlled surface. Clients depend on the contract, not on the internals — so either side can change safely.

    💡
    Remember: an API is an interface, not an implementation. The same API can be backed by Node.js today and Go next year without clients noticing.

    🍽️ The Restaurant Analogy

    Think of a restaurant. You (the client) do not walk into the kitchen. You read the menu (API documentation), tell the waiter (the API) what you want, and the waiter brings back a dish from the kitchen (the server and database).

    RestaurantWeb API
    CustomerClient — browser, mobile app, another server
    MenuAPI documentation (OpenAPI / Swagger)
    OrderHTTP request (method + URL + headers + body)
    WaiterThe API layer (routes and controllers)
    KitchenBusiness logic and database
    DishHTTP response (status code + headers + JSON body)
    "Sorry, we are out of that"404 Not Found / 409 Conflict

    🔄 The Request–Response Cycle

    Every web API call follows the same loop. Understanding it end to end makes everything else easier to debug.

    • DNS turns api.example.com into an IP address.
    • TCP + TLS open a secure connection (the "S" in HTTPS).
    • The server routes the request to a handler, validates input, runs logic, talks to the database.
    • It replies with a status code, headers and usually a JSON body.

    🏷️ Types of APIs by Audience

    🌍
    Public (Open) APIs
    Available to any developer, often with a free key. Examples: OpenWeather, GitHub, Stripe.
    🤝
    Partner APIs
    Shared only with approved business partners under an agreement. Example: airline booking APIs for travel sites.
    🔒
    Private (Internal) APIs
    Used inside one company between its own services and apps. Never exposed to the public internet directly.
    🧩
    Composite APIs
    Combine several calls into one so the client makes a single round trip (an API gateway or BFF pattern).

    📦 Data Formats: JSON, XML, YAML

    APIs exchange text-based representations of data. JSON is the default for modern web APIs because it is compact, human-readable and native to JavaScript.

    Module 02 · HTTP & REST Principles

    HTTP & REST Principles

    Methods, status codes, headers, REST constraints and URL design — the grammar every API speaks.

    🌐 HTTP: The Language of the Web

    HTTP (HyperText Transfer Protocol) is the set of rules for how clients and servers exchange messages. REST APIs are built directly on top of it, so knowing HTTP well is knowing half of API development.

    A request has four parts, a response has three:

    httpPOST /api/v1/courses HTTP/1.1          ← request line: METHOD  PATH  VERSION
Host: api.example.com                   ← headers
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
                                        ← blank line
{ "title": "REST 101", "level": "basic" }   ← body (optional)
    httpHTTP/1.1 201 Created                    ← status line: VERSION  CODE  REASON
Content-Type: application/json
Location: /api/v1/courses/17            ← headers

{ "id": 17, "title": "REST 101", "level": "basic" }   ← body

    🔧 HTTP Methods (Verbs)

    The method tells the server what you want to do with the resource in the URL.

    MethodPurposeSafe?Idempotent?Has body?Example
    GETReadYesYesNoGET /users/42
    POSTCreate / trigger actionNoNoYesPOST /users
    PUTReplace whole resourceNoYesYesPUT /users/42
    PATCHPartial updateNoUsuallyYesPATCH /users/42
    DELETERemoveNoYesRarelyDELETE /users/42
    HEADLike GET, headers onlyYesYesNoCheck if a file exists
    OPTIONSAsk what is allowed (CORS preflight)YesYesNoBrowser sends automatically
    SafeDoes not change server state. Crawlers and prefetchers may call it freely.
    IdempotentCalling it once or 10 times leaves the server in the same state. Makes retries safe.
    PUT vs PATCH

    Resource: {"name":"Asha","city":"Guntur","age":24}

    PUT /users/42 with {"name":"Asha"} replaces everything — city and age are gone.

    PATCH /users/42 with {"city":"Vijayawada"} changes only the city.

    🚦 HTTP Status Codes

    Status codes are grouped by their first digit. Always return the most accurate code — clients depend on it.

    RangeMeaningCommon codes
    1xxInformational101 Switching Protocols (WebSocket upgrade)
    2xxSuccess200 OK · 201 Created · 202 Accepted · 204 No Content
    3xxRedirection301 Moved Permanently · 302 Found · 304 Not Modified
    4xxClient error (your fault)400 Bad Request · 401 Unauthorized · 403 Forbidden · 404 Not Found · 405 Method Not Allowed · 409 Conflict · 422 Unprocessable Entity · 429 Too Many Requests
    5xxServer error (our fault)500 Internal Server Error · 502 Bad Gateway · 503 Service Unavailable · 504 Gateway Timeout
    ⚠️
    401 vs 403: 401 = "I don't know who you are" (missing/invalid credentials). 403 = "I know who you are, but you are not allowed." 400 vs 422: 400 = malformed request (bad JSON); 422 = well-formed but fails validation rules (email invalid).
    ActionSuccess codeNotes
    GET one / many200Empty list is still 200 [], not 404
    POST create201 + Location headerReturn the created resource
    PUT / PATCH update200 (with body) or 204
    DELETE204Deleting an already-deleted item → 204 or 404, be consistent
    Long-running job202 AcceptedReturn a status URL to poll

    🏷️ Important Headers

    HeaderDirectionPurpose
    Content-TypeBothFormat of the body: application/json
    AcceptRequestFormat the client wants back
    AuthorizationRequestCredentials: Bearer <token>
    Cache-ControlResponseCaching rules: max-age=60, no-store
    ETag / If-None-MatchBothConditional requests → 304 Not Modified
    LocationResponseURL of a newly created resource
    Retry-AfterResponseSeconds to wait after 429 / 503
    User-AgentRequestWho is calling (browser, curl, your SDK)
    Access-Control-Allow-OriginResponseCORS: which origins may call from a browser

    🏛️ What is REST?

    REST (Representational State Transfer) is an architectural style described by Roy Fielding in 2000. It is not a protocol or a standard — it is a set of constraints. An API that follows them is called RESTful.

    📦
    Resources & URIs
    Everything is a resource identified by a URL: /courses/7.
    🪪
    Representations
    The client gets a representation (JSON), not the database row itself.
    🚫
    Stateless
    No server session. Each request contains all needed info (token, params).
    ♻️
    Cacheable
    Responses declare whether and how long they can be cached.
    🧱
    Client–Server
    UI and data storage are separated so each can evolve independently.
    🪜
    Layered System
    Load balancers, gateways and caches can sit in between invisibly.
    🔗
    Uniform Interface
    Same conventions everywhere: standard verbs, status codes, media types.

    Richardson Maturity Model — a ladder for how "REST-y" an API is:

    LevelDescriptionExample
    0One endpoint, one verb (RPC over HTTP)POST /api with {"action":"getUser"}
    1Separate resourcesPOST /users/42
    2Proper HTTP verbs + status codes (where most real APIs sit)GET /users/42 → 200
    3Hypermedia (HATEOAS): responses contain links to next actions"links": {"orders": "/users/42/orders"}

    🧭 URL Design Rules

    • Use nouns, plural: /courses, not /getCourses.
    • Let the verb be the HTTP method: DELETE /courses/7, not /deleteCourse?id=7.
    • Show hierarchy with nesting (max 2 levels): /courses/7/lessons.
    • Use lowercase kebab-case: /course-categories.
    • Use query strings for filter / sort / page: /courses?level=basic&sort=-created&page=2.
    • No trailing slash, no file extensions, no verbs.

    🔴 Avoid

    POST /createNewUser
    GET /getAllCourses
    POST /users/42/delete
    GET /Course_List/

    🟢 Prefer

    POST /users
    GET /courses
    DELETE /users/42
    GET /courses

    📌
    Actions that are not CRUD (e.g. "publish a course", "reset password"): model them as sub-resources or state changes — POST /courses/7/publish or PATCH /courses/7 {"status":"published"}. Pick one convention and keep it.

    Module 03 · API Design

    Designing a Great API

    Resource modelling, OpenAPI, pagination, error formats and versioning — before you write a line of server code.

    📐 Design-First Thinking

    Good APIs are designed, not just coded. Poor API design is expensive because once clients depend on it, you cannot change it freely. The recommended workflow:

    💡
    Contract-first (spec before code) lets frontend and backend teams work in parallel using a mock server, and keeps documentation from drifting out of date.

    🧩 Resource Modelling

    Identify the nouns of your domain and how they relate. Example: an LMS.

    textCourse ──< Lesson
Course ──< Enrollment >── User
Lesson ──< Quiz ──< Question
User   ──< Submission >── Quiz

Resulting endpoints
GET    /courses                     list courses
POST   /courses                     create course
GET    /courses/{id}                one course
PATCH  /courses/{id}                update
DELETE /courses/{id}                delete
GET    /courses/{id}/lessons        lessons of a course
POST   /courses/{id}/enrollments    enrol the current user
GET    /users/{id}/enrollments      a user's enrolments
    • Don't expose your database tables blindly. Design for what clients need.
    • Use IDs that don't leak information (UUIDs / ULIDs instead of auto-increment if enumeration is a concern).
    • Keep nesting shallow: prefer /lessons/9 over /courses/7/modules/3/lessons/9.

    📄 OpenAPI (Swagger) Specification

    OpenAPI is the industry-standard, machine-readable format for describing REST APIs. From one YAML file you can generate docs, mock servers, client SDKs and validation.

    PatternRequestProsCons
    Offset / page?page=3&limit=20Simple; jump to any pageSlow on huge tables; duplicates if data changes
    Cursor (keyset)?after=eyJpZCI6MTIwfQ&limit=20Fast, stable for feedsNo random page jumps
    Time-based?since=2026-01-01T00:00ZGood for syncNeeds a reliable timestamp

    ❌ Error Handling Design

    Errors are part of your API's UX. Use a consistent shape so clients can handle every failure the same way. The standard is RFC 9457 Problem Details (application/problem+json); a simple custom shape is also fine if it is consistent.

    jsonHTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/v1/users",
  "errors": [
    { "field": "email", "message": "Must be a valid email address" },
    { "field": "password", "message": "Minimum 8 characters" }
  ],
  "requestId": "req_8f3a2c"
}
    • Never leak stack traces, SQL or file paths to clients — log them server-side with a requestId.
    • Use a machine-readable code/type plus a human-readable message.
    • Return all validation errors at once, not one at a time.

    🔢 API Versioning

    Once published, an API is a promise. Versioning lets you introduce breaking changes without breaking existing clients.

    StrategyExampleNotes
    URL path/v1/coursesMost common and easiest to see/cache/route
    HeaderAccept: application/vnd.lms.v2+jsonClean URLs; harder to test in a browser
    Query param/courses?version=2Easy, but easy to forget; avoid for long term

    Breaking changes: removing/renaming a field, changing a type, making an optional field required, changing status codes. Non-breaking: adding optional fields or new endpoints. Announce a deprecation with the Deprecation and Sunset headers and a migration guide.

    🔁 Full CRUD (In-Memory)

    Start with an array before adding a database — it lets you focus on the HTTP part.

    javascript// src/app.js
import express from 'express';
export const app = express();
app.use(express.json());

let courses = [
  { id: 1, title: 'REST 101',   level: 'basic' },
  { id: 2, title: 'Docker 101', level: 'basic' },
];
let nextId = 3;

// READ many  — supports ?level=basic
app.get('/api/v1/courses', (req, res) => {
  const { level } = req.query;
  res.json(level ? courses.filter(c => c.level === level) : courses);
});

// READ one
app.get('/api/v1/courses/:id', (req, res) => {
  const course = courses.find(c => c.id === Number(req.params.id));
  if (!course) return res.status(404).json({ title: 'Course not found', status: 404 });
  res.json(course);
});

// CREATE
app.post('/api/v1/courses', (req, res) => {
  const course = { id: nextId++, ...req.body };
  courses.push(course);
  res.status(201).location(`/api/v1/courses/${course.id}`).json(course);
});

// PARTIAL UPDATE
app.patch('/api/v1/courses/:id', (req, res) => {
  const course = courses.find(c => c.id === Number(req.params.id));
  if (!course) return res.status(404).json({ title: 'Course not found', status: 404 });
  Object.assign(course, req.body);
  res.json(course);
});

// DELETE
app.delete('/api/v1/courses/:id', (req, res) => {
  const before = courses.length;
  courses = courses.filter(c => c.id !== Number(req.params.id));
  if (courses.length === before) return res.status(404).json({ title: 'Course not found', status: 404 });
  res.status(204).end();
});

    🧅 Middleware

    Middleware are functions that run between the request arriving and your handler. Each can read/modify req and res, then call next() to pass control on — or end the response. They are how logging, auth, validation, CORS and error handling are added cleanly.

    javascript// Request logger
app.use((req, res, next) => {
  const start = Date.now();
  res.on('finish', () => console.log(`${req.method} ${req.originalUrl} ${res.statusCode} ${Date.now() - start}ms`));
  next();
});

// ... routes go here ...

// 404 for anything unmatched
app.use((req, res) => res.status(404).json({ title: 'Route not found', status: 404 }));

// Central error handler — 4 arguments tells Express it is an error handler
app.use((err, req, res, next) => {
  console.error(err);                       // log full detail server-side
  const status = err.status || 500;
  res.status(status).json({
    title: status === 500 ? 'Internal Server Error' : err.message,
    status,
  });
});
    📌
    Order matters: middleware runs in the order it is registered. Express 5 forwards errors from async handlers to the error handler automatically; on Express 4 wrap them or use express-async-errors.

    ✅ Input Validation

    Never trust client input. Validate shape, types and ranges at the edge, before the data reaches your logic or database. Zod (JS/TS), Joi, Pydantic (Python) and Bean Validation (Java) do this declaratively.

    javascript// src/schemas/course.schema.js
import { z } from 'zod';

export const CourseInput = z.object({
  title: z.string().trim().min(3).max(120),
  level: z.enum(['basic', 'intermediate', 'expert']).default('basic'),
  price: z.number().nonnegative().optional(),
});

// src/middleware/validate.js
export const validate = (schema) => (req, res, next) => {
  const result = schema.safeParse(req.body);
  if (!result.success) {
    return res.status(422).json({
      title: 'Validation failed',
      status: 422,
      errors: result.error.issues.map(i => ({ field: i.path.join('.'), message: i.message })),
    });
  }
  req.body = result.data;     // sanitised + defaults applied
  next();
};

// usage
app.post('/api/v1/courses', validate(CourseInput), createCourse);

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

export async function list({ level, limit = 20, offset = 0 }) {
  const { rows } = await pool.query(
    `SELECT * FROM courses
     WHERE ($1::text IS NULL OR level = $1)
     ORDER BY created_at DESC LIMIT $2 OFFSET $3`,
    [level ?? null, limit, offset]);
  return rows;
}

export async function create({ title, level }) {
  const { rows } = await pool.query(
    'INSERT INTO courses (title, level) VALUES ($1, $2) RETURNING *',
    [title, level]);
  return rows[0];
}

export async function findById(id) {
  const { rows } = await pool.query('SELECT * FROM courses WHERE id = $1', [id]);
  return rows[0] ?? null;
}

    Module 05 · Authentication & Security

    Authentication, Authorization & API Security

    API keys, JWT, OAuth 2.0, CORS, rate limiting and the OWASP API Top 10.

    🔐 Authentication vs Authorization

    🪪 Authentication (AuthN)

    Who are you? Verifying identity — password, token, key, biometrics. Failure → 401.

    🚪 Authorization (AuthZ)

    What may you do? Checking permissions for a specific action or resource. Failure → 403.

    Most real-world API breaches come from broken authorization (user A reading user B's data), not from broken passwords.

    🗝️ Authentication Methods

    MethodHow it worksUse forWatch out
    API KeyStatic secret in a header: X-API-Key: abc123Server-to-server, identifying an appNo user identity; leaks are permanent until rotated
    Basic AuthBase64(user:password) in AuthorizationInternal tools, quick testsMust be HTTPS; credentials on every call
    Session cookieServer stores session; browser sends cookieTraditional web appsCSRF protection needed; sticky/shared session store
    JWT BearerSigned token carrying claims; Authorization: Bearer …SPAs, mobile, microservicesHard to revoke; keep short-lived
    OAuth 2.0 / OIDCDelegated login via an authorisation server (Google, Auth0, Keycloak)"Sign in with …", third-party accessComplex — use a proven library/provider
    mTLSBoth sides present certificatesZero-trust service-to-serviceCertificate management overhead

    🎫 JWT in Depth

    A JSON Web Token has three Base64URL parts separated by dots: header.payload.signature. The server signs it; anyone can read it, but only the holder of the secret/private key can create a valid one.

    textHEADER    {"alg":"HS256","typ":"JWT"}
PAYLOAD   {"sub":"42","role":"student","iat":1790000000,"exp":1790000900}
SIGNATURE HMAC_SHA256(base64(header) + "." + base64(payload), SECRET)

import bcrypt from 'bcrypt';

// --- login ---
app.post('/api/v1/auth/login', async (req, res) => {
  const { email, password } = req.body;
  const user = await users.findByEmail(email);
  const ok = user && await bcrypt.compare(password, user.passwordHash);
  if (!ok) return res.status(401).json({ title: 'Invalid email or password', status: 401 }); // same message for both!

  const accessToken = jwt.sign(
    { sub: String(user.id), role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: '15m' });
  res.json({ accessToken, tokenType: 'Bearer', expiresIn: 900 });
});

// --- auth middleware ---
export function requireAuth(req, res, next) {
  const [type, token] = (req.headers.authorization || '').split(' ');
  if (type !== 'Bearer' || !token) return res.status(401).json({ title: 'Missing token', status: 401 });
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);   // checks signature + exp
    next();
  } catch {
    res.status(401).json({ title: 'Invalid or expired token', status: 401 });
  }
}

// --- role check (authorization) ---
export const requireRole = (...roles) => (req, res, next) =>
  roles.includes(req.user.role) ? next() : res.status(403).json({ title: 'Forbidden', status: 403 });

app.delete('/api/v1/courses/:id', requireAuth, requireRole('admin'), deleteCourse);
    ⚠️
    JWT rules: never put secrets in the payload (it is only encoded, not encrypted); keep access tokens short (5–15 min); pair with a refresh token stored in an HttpOnly; Secure; SameSite cookie; always verify exp; pin the algorithm; use a long random secret (or RS256/ES256 keys).

    Passwords: never store plain text or fast hashes (MD5/SHA-1). Use bcrypt, scrypt or Argon2 with a per-user salt.

    🧱 A Reusable API Client

    Wrap fetch once so every call gets the base URL, auth header, JSON parsing, timeouts and consistent errors.

    javascript// api.js
const BASE = import.meta.env.VITE_API_URL ?? 'http://localhost:3000/api/v1';

export class ApiError extends Error {
  constructor(status, body) {
    super(body?.title || `HTTP ${status}`);
    this.status = status;
    this.body = body;
  }
}

export async function api(path, { method = 'GET', body, token, signal } = {}) {
  const res = await fetch(`${BASE}${path}`, {
    method,
    headers: {
      Accept: 'application/json',
      ...(body && { 'Content-Type': 'application/json' }),
      ...(token && { Authorization: `Bearer ${token}` }),
    },
    body: body ? JSON.stringify(body) : undefined,
    signal: signal ?? AbortSignal.timeout(10_000),        // 10 s timeout
  });

  const data = res.status === 204 ? null : await res.json().catch(() => null);
  if (!res.ok) throw new ApiError(res.status, data);
  return data;
}

// usage
const list = await api('/courses?level=basic');
await api('/courses', { method: 'POST', body: { title: 'Docker 101' }, token });

    🔁 Resilience: Timeouts, Retries & Backoff

    Networks fail. Retry only when it is safe (idempotent requests) and useful (5xx, 429, network error) — never retry 400/401/403/404/422.

    javascriptasync function withRetry(fn, { retries = 3, base = 300 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();
    } catch (err) {
      const retryable = !err.status || err.status >= 500 || err.status === 429;
      if (!retryable || attempt >= retries) throw err;
      const delay = base * 2 ** attempt + Math.random() * 100;   // exponential backoff + jitter
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

const courses = await withRetry(() => api('/courses'));
    • Exponential backoff: wait 0.3 s, 0.6 s, 1.2 s … so you don't hammer a struggling server.
    • Jitter: randomness prevents thousands of clients retrying at the same instant.
    • Respect the Retry-After header if present.
    • Use an Idempotency-Key header to make POST retries safe (see Expert module).

    ⚛️ Consuming an API in React

    javascriptimport { useEffect, useState } from 'react';
import { api } from './api';

export function CourseList({ level }) {
  const [state, setState] = useState({ status: 'loading', data: [], error: null });

  useEffect(() => {
    const ctrl = new AbortController();               // cancel on unmount / level change
    setState(s => ({ ...s, status: 'loading' }));

    api(`/courses?level=${encodeURIComponent(level)}`, { signal: ctrl.signal })
      .then(data => setState({ status: 'success', data, error: null }))
      .catch(error => {
        if (error.name !== 'AbortError') setState({ status: 'error', data: [], error });
      });

    return () => ctrl.abort();
  }, [level]);

  if (state.status === 'loading') return <p>Loading…</p>;
  if (state.status === 'error')   return <p role="alert">Could not load courses: {state.error.message}</p>;
  if (!state.data.length)         return <p>No courses found.</p>;
  return <ul>{state.data.map(c => <li key={c.id}>{c.title}</li>)}</ul>;
}

    🌍 CORS from the Client's View

    If your React app on http://localhost:5173 calls an API on http://localhost:3000, the browser blocks reading the response unless the API replies with the right Access-Control-Allow-Origin header. These are different origins (scheme + host + port).

    • "Simple" requests (GET, basic POST) are sent directly; the browser checks the response headers.
    • Requests with JSON bodies, custom headers or PUT/PATCH/DELETE trigger a preflight OPTIONS request first.
    • Fix it on the server (allow the origin) or during development use a proxy (vite.config.js → server.proxy). Don't "fix" it by disabling browser security.

    🪝 Webhooks

    A webhook is an HTTP callback: when something happens (payment succeeded, code pushed), the provider POSTs to a URL you registered. It replaces wasteful polling.

    • Verify the signature (HMAC) so attackers cannot fake events.
    • Respond 2xx fast, then process asynchronously via a queue.
    • Be idempotent — providers retry, so the same event may arrive more than once (dedupe by event id).
    • Providers retry with backoff on non-2xx; support replays from their dashboard.
    javascriptimport crypto from 'node:crypto';

// Need the RAW body to compute the signature
app.post('/webhooks/payments', express.raw({ type: 'application/json' }), (req, res) => {
  const received = req.get('X-Signature') || '';
  const expected = crypto.createHmac('sha256', process.env.WEBHOOK_SECRET)
                         .update(req.body).digest('hex');

  const a = Buffer.from(received), b = Buffer.from(expected);
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) return res.sendStatus(401);

  const event = JSON.parse(req.body);
  queue.add('payment-event', event);      // process later, deduplicate by event.id
  res.sendStatus(200);                    // acknowledge quickly
});

    🔂 Idempotency Keys

    Networks time out after the server did the work. If the client retries a POST /payments, the customer could be charged twice. The fix: the client sends a unique Idempotency-Key; the server stores the first result and replays it for repeats.

    javascriptapp.post('/api/v1/payments', requireAuth, async (req, res) => {
  const key = req.get('Idempotency-Key');
  if (!key) return res.status(400).json({ title: 'Idempotency-Key header required', status: 400 });

  const cached = await redis.get(`idem:${req.user.sub}:${key}`);
  if (cached) {
    const { status, body } = JSON.parse(cached);
    return res.status(status).set('Idempotent-Replay', 'true').json(body);
  }

  const result = await payments.charge(req.body);                      // do the work once
  await redis.set(`idem:${req.user.sub}:${key}`, JSON.stringify({ status: 201, body: result }), { EX: 86400 });
  res.status(201).json(result);
});
    🧠
    Expert detail: two simultaneous requests with the same key can still race. Take an atomic lock first (SET key value NX EX 30) and return 409 while the first request is in progress. Also compare the request body hash and reject a reused key with a different payload (422).

    When would you choose GraphQL over REST?
    When many different clients need different slices of related data (rich UIs, mobile with bandwidth limits) and you can invest in schema governance, query cost limits and DataLoader batching. REST is simpler for resource-oriented CRUD and gets free HTTP caching.
    How do you make a POST safe to retry?
    Require an Idempotency-Key; store the result of the first execution keyed by (user, key) with a TTL; replay it on duplicates; lock to handle concurrent duplicates; reject key reuse with a different payload.
    How would you design rate limiting for a multi-instance API?
    Token bucket per API key/user, counters in Redis (atomic Lua script or INCR+EXPIRE), enforced at the gateway; different tiers per plan; 429 with Retry-After; separate stricter limits for login and expensive endpoints.
    How do you prevent BOLA?
    Never trust IDs from the client. Always scope queries by the authenticated principal (WHERE id=$1 AND user_id=$2), centralise the policy checks, use unpredictable IDs as defence-in-depth, and write tests that try cross-tenant access.

    REST & HTTP Fundamentals

    What an API is, how HTTP requests and responses work, and how one click in TaskFlow travels from the browser to the database and back.

    🔌 What is an API?

    An API (Application Programming Interface) is a contract that lets one program ask another for data or actions. The caller only needs to know the shape of the request and the response — not how the other side works inside.

    In full-stack work, “the API” usually means a web API: a server that accepts HTTP requests and returns JSON. In TaskFlow, our team task tracker, the React/Next.js frontend never talks to PostgreSQL directly. It calls the Express API, and the API talks to the database.

    🖥️
    Frontend (client)
    React + TypeScript in the browser. Shows tasks, sends user actions to the API.
    🚪
    API (server)
    Express routes such as GET /api/tasks. Validates input, checks permissions, runs business rules.
    🗄️
    Database
    PostgreSQL stores users, projects, tasks and comments. Only the API can reach it.
    📜
    Contract
    The agreed list of endpoints, bodies, status codes and errors that both sides rely on.
    💡
    As a full-stack developer you own both ends of the contract. A good habit: design the request and response first, then build the server and the client against that shape.

    🏛️ REST principles and resources

    REST (Representational State Transfer) is an architectural style for web APIs. You model your system as resources (nouns) identified by URLs, and you act on them with a small, fixed set of HTTP methods (verbs).

    PrincipleWhat it meansTaskFlow example
    Client–serverUI and data storage are separate and evolve independentlyThe Next.js app can be redesigned without touching the API
    StatelessEach request carries everything needed (e.g. the token); the server keeps no per-client session between callsEvery call sends Authorization: Bearer <token>
    Uniform interfaceResources have URLs; standard methods and status codes are usedGET /api/tasks/42 always means “read task 42”
    CacheableResponses say whether and how long they can be cachedCache-Control: max-age=60 on a project list
    Layered systemClients cannot tell if there is a proxy, CDN or gateway in betweenA CDN or load balancer sits in front of Express

    Resources and URLs

    Use plural nouns, not verbs. The method says what to do; the URL says to what.

    Good (RESTful)Avoid (RPC-style)
    GET /api/projects/7/tasksGET /api/getTasksForProject?id=7
    POST /api/projects/7/tasksPOST /api/createTask
    PATCH /api/tasks/42POST /api/updateTaskStatus
    DELETE /api/tasks/42GET /api/deleteTask?id=42
    ⚠️
    Never change data with GET. Browsers, crawlers and link previewers may call GET URLs on their own — a GET /deleteTask link can wipe data.

    🔧 HTTP methods: safe and idempotent

    A method is safe if it does not change server state. It is idempotent if sending it once or ten times leaves the server in the same state. These properties tell clients, proxies and retry logic what is risky to repeat.

    MethodPurposeSafe?Idempotent?Typical success code
    GETRead a resource or listYesYes200 OK
    HEADLike GET, headers onlyYesYes200 OK
    POSTCreate a resource / run an actionNoNo201 Created (or 200/202)
    PUTReplace a resource completelyNoYes200 OK or 204 No Content
    PATCHPartially update a resourceNoNot guaranteed200 OK
    DELETERemove a resourceNoYes204 No Content
    OPTIONSAsk what is allowed (used by CORS preflight)YesYes204 No Content
    EXAMPLE · Why idempotency matters

    The user clicks “Delete task” and the network drops before the response arrives. The client can safely retry DELETE /api/tasks/42 — the task is gone either way. Retrying POST /api/tasks is different: it may create a second task. Tab 2 shows how an Idempotency-Key header fixes that.

    📝
    Idempotent is about the server state, not the response. A second DELETE may return 404 instead of 204, yet the state is the same: no task 42.

    🚦 Status codes you will use every day

    The status code is the first thing a client should check. Group by the first digit: 2xx success, 3xx redirect, 4xx the client got something wrong, 5xx the server failed.

    CodeNameWhen TaskFlow returns it
    200OKGET a task or list; PATCH that returns the updated task
    201CreatedPOST created a task; include a Location header and the new task
    204No ContentDELETE succeeded; no body
    304Not ModifiedClient sent If-None-Match and the ETag still matches
    400Bad RequestMalformed JSON or an invalid query parameter
    401UnauthorizedNo token, or the token is invalid/expired — “who are you?”
    403ForbiddenLogged in, but not a member of this project — “you may not”
    404Not FoundTask 999 does not exist (or is hidden from this user)
    409ConflictDuplicate project name, or a version conflict on update
    422Unprocessable ContentWell-formed JSON that breaks rules, e.g. empty title
    429Too Many RequestsRate limit hit; send Retry-After
    500Internal Server ErrorAn unexpected bug; log it, return a generic message
    503Service UnavailableDatabase down or maintenance; clients may retry later
    💡
    Many teams return 400 for every validation failure; others use 400 for unreadable input and 422 for rule violations. Either is fine — be consistent and document it.

    🔁 One click, end to end

    Follow what happens when a user marks a task as done in TaskFlow. Every full-stack feature follows this same loop.

    A TaskFlow request, from click to screen
    1. The user clicks the checkbox; the React handler runs.
    2. The client sends PATCH /api/tasks/42 with body {"status":"done"} and the auth token.
    3. Express matches the route router.patch("/tasks/:id", …).
    4. Middleware checks the token (401 if missing) and the body schema (400/422 if wrong).
    5. The service checks the user belongs to the project (403 if not) and updates PostgreSQL.
    6. The API returns 200 with the updated task as JSON.
    7. The client checks response.ok, parses JSON and updates state (or the query cache).
    8. React re-renders; the task appears ticked.
    tsx// client: the click handler
async function markDone(id: number) {
  const res = await fetch(`/api/tasks/${id}`, {
    method: "PATCH",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ status: "done" }),
  });
  if (!res.ok) throw new Error(`Update failed: ${res.status}`);
  const updated: Task = await res.json();
  setTasks(ts => ts.map(t => (t.id === id ? updated : t)));
}

    ts// server: the matching Express route
router.patch("/tasks/:id", requireAuth, async (req, res) => {
  const body = UpdateTaskSchema.parse(req.body);           // throws -> error middleware -> 400
  const task = await taskService.update(req.user.id, Number(req.params.id), body);
  res.json(task);                                           // 200 + JSON
});

    Designing the TaskFlow API

    Model resources, design URLs and bodies, add pagination and a consistent error format, and capture it all in an OpenAPI contract.

    🗺️ Resource modelling and URL design

    Start from the domain, not the database. TaskFlow has four core resources and clear ownership: a project has many tasks; a task has many comments; users are members of projects.

    ResourceCollection URLItem URLBelongs to
    Project/api/projects/api/projects/:projectIdMembers (users)
    Task/api/projects/:projectId/tasks/api/tasks/:taskIdOne project
    Comment/api/tasks/:taskId/comments/api/comments/:commentIdOne task
    User/api/users/api/users/:userId, /api/me—

    URL rules of thumb

    • Plural nouns, lowercase, hyphens for multi-word names: /api/time-entries.
    • Nest only one level to show ownership on create/list: /projects/7/tasks. Address the item itself at the top level: /tasks/42.
    • IDs go in the path; optional filters, sorting and paging go in the query string.
    • Actions that are not CRUD can be modelled as sub-resources: POST /api/tasks/42/assignments or a status field changed with PATCH.
    💡
    Deep nesting like /projects/7/tasks/42/comments/9 forces clients to know every parent ID. Shallow URLs are easier to build, cache and authorise.

    • Use consistent casing. TaskFlow uses camelCase in JSON even though PostgreSQL columns are snake_case; the data layer maps between them.
    • Return the full resource after create/update so the client can update its cache without a second request.

    🔎 Filtering, sorting and pagination

    A project may hold thousands of tasks. Never return an unbounded list. Use query parameters for filters, sorting and paging, and a stable response envelope.

    httpGET /api/projects/7/tasks?status=todo&assigneeId=3&sort=-dueDate&limit=20&cursor=eyJpZCI6MTIwfQ
    ParameterMeaningExample
    statusFilter by field valuestatus=todo
    qFree-text searchq=release
    sortSort field; leading - for descendingsort=-dueDate
    limitPage size, with a server-side maximum (e.g. 100)limit=20
    page / offsetOffset paginationpage=3
    cursorOpaque cursor paginationcursor=eyJpZCI6MTIwfQ

    Offset pagination

    • SQL LIMIT 20 OFFSET 40.
    • Easy “jump to page 7” and total counts.
    • Slow on large offsets (DB still scans skipped rows).
    • Rows inserted or deleted while paging cause duplicates or gaps.

    Cursor (keyset) pagination

    • SQL WHERE (due_date, id) > ($1, $2) ORDER BY due_date, id LIMIT 20.
    • Fast at any depth with an index.
    • Stable while data changes — ideal for infinite scroll.
    • No random page jumps; cursor is opaque to clients.

    Response envelope

    json{
  "data": [
    { "id": 121, "title": "Fix login bug", "status": "todo", "dueDate": "2026-10-10" }
  ],
  "page": {
    "limit": 20,
    "nextCursor": "eyJpZCI6MTQwfQ",
    "hasMore": true
  }
}
    📝
    Encode the cursor (for example base64 of the last row's sort key and id) so clients treat it as opaque. You can then change its internals without breaking anyone.

    🧯 A consistent error format

    Clients need errors they can rely on. TaskFlow uses Problem Details (RFC 9457, which replaced RFC 7807) with media type application/problem+json, plus a list of field errors for forms.

    typeStable URI identifying the error kind — clients branch on this, not on title text

    ⚠️
    Never leak stack traces, SQL or internal hostnames in errors. Log details on the server; return a safe message and a trace id.

    🔢 Versioning and idempotency

    Versioning

    Once clients depend on your API, breaking changes need a new version. Common strategies:

    StrategyExampleNotes
    URL path/api/v1/tasksMost visible and easy to route; very common
    HeaderAccept: application/vnd.taskflow.v2+jsonClean URLs; harder to test in a browser
    Date-based headerTaskFlow-Version: 2026-10-01Fine-grained, used by Stripe-style APIs
    Query string/api/tasks?version=2Simple but easy to forget and pollutes caching

    If the TaskFlow frontend is the only client and deploys together with the API, you often skip URL versions and evolve additively. Public or mobile clients (which update slowly) need explicit versions.

    Idempotency keys for POST

    POST is not idempotent. If a create request times out, the client cannot know whether the task was created. The fix: the client generates a unique key per user action and the server stores the first result for that key.

    httpPOST /api/projects/7/tasks
Idempotency-Key: 6f1c2b8e-4c1a-4b8e-9d55-2f7a9c1e0b31
Content-Type: application/json

{"title": "Write release notes"}
    1. Server looks up the key (scoped to the user). If found, it returns the stored response — no second insert.
    2. If not found, it processes the request and saves key + status + body (with an expiry, e.g. 24h).
    3. If the same key arrives with a different body, reject it (commonly 422 or 409).

    API-first (design-first)

    • Write the OpenAPI spec first and review it.
    • Frontend builds against a mock server while backend implements.
    • Generate types/clients from the spec.
    • Best when several teams or external consumers depend on the API.

    Code-first

    • Write routes and schemas in code first.
    • Generate the spec from code (e.g. Zod → OpenAPI, FastAPI, springdoc).
    • Fast for small teams; spec always matches code.
    • Risk: design is not reviewed before it ships.
    💡
    Whichever you choose, keep one source of truth and generate the rest. Hand-maintained docs that drift from code are worse than none.

    🏗️ Project structure: routes, controllers, services

    🧱 Full CRUD for tasks with Prisma

    We use Prisma as the data layer (raw pg with SQL works just as well). Express 5 automatically forwards errors thrown in async handlers to the error middleware — no more try/catch + next(err) boilerplate.

    ts// modules/tasks/task.service.ts
import { prisma } from "../../db";
import { HttpError } from "../../lib/problem";
import type { CreateTaskInput, UpdateTaskInput } from "./task.schemas";

async function assertMember(userId: number, projectId: number) {
  const m = await prisma.membership.findUnique({
    where: { userId_projectId: { userId, projectId } },
  });
  if (!m) throw new HttpError(403, "You are not a member of this project");
}

async function findTaskForUser(userId: number, id: number) {
  const task = await prisma.task.findUnique({ where: { id } });
  if (!task) throw new HttpError(404, "Task not found");
  await assertMember(userId, task.projectId);
  return task;
}

export const taskService = {
  async list(userId: number, projectId: number, limit: number, cursor?: number) {
    await assertMember(userId, projectId);
    const rows = await prisma.task.findMany({
      where: { projectId },
      orderBy: { id: "asc" },
      take: limit + 1,                       // fetch one extra to know hasMore
      ...(cursor ? { cursor: { id: cursor }, skip: 1 } : {}),
    });
    const hasMore = rows.length > limit;
    const data = hasMore ? rows.slice(0, limit) : rows;
    return { data, page: { limit, hasMore, nextCursor: hasMore ? data.at(-1)!.id : null } };
  },
  async create(userId: number, projectId: number, input: CreateTaskInput) {
    await assertMember(userId, projectId);
    return prisma.task.create({ data: { ...input, projectId } });
  },
  get: findTaskForUser,
  async update(userId: number, id: number, input: UpdateTaskInput) {
    await findTaskForUser(userId, id);
    return prisma.task.update({ where: { id }, data: input });
  },
  async remove(userId: number, id: number) {
    await findTaskForUser(userId, id);
    await prisma.task.delete({ where: { id } });
  },
};

import { Router } from "express";

taskRouter.use(requireAuth);

    res.json(await taskService.list(req.user!.id, res.locals.params.projectId, limit, cursor));
  });

  async (req, res) => {
    const task = await taskService.create(req.user!.id, res.locals.params.projectId, res.locals.body);
    res.status(201).location(`/api/tasks/${task.id}`).json(task);
  });

taskRouter.get("/tasks/:id", validate({ params: IdParam("id") }), async (req, res) => {
  res.json(await taskService.get(req.user!.id, res.locals.params.id));
});

taskRouter.patch("/tasks/:id", validate({ params: IdParam("id"), body: UpdateTask }), async (req, res) => {
  res.json(await taskService.update(req.user!.id, res.locals.params.id, res.locals.body));
});

taskRouter.delete("/tasks/:id", validate({ params: IdParam("id") }), async (req, res) => {
  await taskService.remove(req.user!.id, res.locals.params.id);
  res.status(204).end();
});

    In Express 5, req.query is a read-only getter, so the validate middleware stores parsed values on res.locals instead of overwriting req.query.

    🛡️ Validation with Zod

    Never trust req.body. TypeScript types vanish at runtime — a client can send anything. Zod validates at runtime and gives you static types from the same schema.

    🌐 CORS, rate limiting and logging

    CORS for the frontend origin

    If the Next.js app runs on https://app.taskflow.dev and the API on https://api.taskflow.dev, they are different origins. The browser blocks the frontend from reading API responses unless the API sends the right CORS headers.

  allowedHeaders: ["Content-Type", "Authorization", "Idempotency-Key"],

    • With credentials: true the API must echo a specific origin, never *.
    • Requests with JSON bodies or an Authorization header trigger an OPTIONS preflight; the cors middleware answers it.

    Rate limiting

    Rate limits protect against abuse and runaway clients. Over the limit, return 429 with Retry-After. Use a shared store (e.g. Redis) when you run several API instances; apply stricter limits to /auth/login.

    Logging

    Use structured JSON logs (pino) with a request id per call, method, path, status and duration. Never log passwords, tokens or full request bodies with personal data.

    📡 fetch in depth

    fetch() is built into every modern browser and Node 18+. It returns a Promise of a Response. Two facts trip up almost everyone:

    🧩 A typed API client module

    Do not scatter fetch calls across components. Put them in one module that knows the base URL, auth, JSON handling and error shape. Components then call api.tasks.list(7) and get typed data.

    ts// src/lib/api.ts
import type { Task, CreateTaskInput, UpdateTaskInput } from "@taskflow/contracts";

const BASE_URL = process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:4000";

export class ApiError extends Error {
  constructor(public status: number, public problem: Problem | null) {
    super(problem?.title ?? `HTTP ${status}`);
  }
}
export interface Problem { type: string; title: string; status: number; errors?: { field: string; message: string }[] }
export interface Page<T> { data: T[]; page: { limit: number; hasMore: boolean; nextCursor: number | null } }

async function request<T>(path: string, init: RequestInit = {}): Promise<T> {
  const res = await fetch(`${BASE_URL}${path}`, {
    ...init,
    credentials: "include",
    headers: { Accept: "application/json", ...(init.body ? { "Content-Type": "application/json" } : {}), ...init.headers },
  });
  if (res.status === 204) return undefined as T;
  const body = await res.json().catch(() => null);
  if (!res.ok) throw new ApiError(res.status, body);
  return body as T;
}

export const api = {
  tasks: {
    list: (projectId: number, opts: { cursor?: number; limit?: number; signal?: AbortSignal } = {}) => {
      const qs = new URLSearchParams({ limit: String(opts.limit ?? 20) });
      if (opts.cursor) qs.set("cursor", String(opts.cursor));
      return request<Page<Task>>(`/api/projects/${projectId}/tasks?${qs}`, { signal: opts.signal });
    },
    get: (id: number) => request<Task>(`/api/tasks/${id}`),
    create: (projectId: number, input: CreateTaskInput) =>
      request<Task>(`/api/projects/${projectId}/tasks`, { method: "POST", body: JSON.stringify(input) }),
    update: (id: number, input: UpdateTaskInput) =>
      request<Task>(`/api/tasks/${id}`, { method: "PATCH", body: JSON.stringify(input) }),
    remove: (id: number) => request<void>(`/api/tasks/${id}`, { method: "DELETE" }),
  },
};
    ⚠️
    The as T cast is a promise, not a check. For untrusted or external APIs, parse responses with the same Zod schema (TaskSchema.parse(body)) so a backend change fails loudly instead of rendering undefined.

    Optimistic updates

    Ticking a checkbox should feel instant. An optimistic update changes the UI before the server answers, then rolls back if the request fails. A pessimistic update waits for the server first.

    tsxasync function toggleDone(task: Task) {
  const previous = tasks;
  const next = task.status === "done" ? "todo" : "done";
  setTasks(ts => ts.map(t => (t.id === task.id ? { ...t, status: next } : t)));   // 1. update UI now

}

    return await call();

    🕳️ useEffect fetching pitfalls

    Fetching in useEffect works, but it is easy to get wrong. The classic bug is a race condition: the user switches from project 7 to project 8 quickly, the request for 7 finishes last, and the screen shows project 7's tasks under project 8's title.

    tsx// ❌ Buggy: no cleanup, no error state, races between projects
useEffect(() => {
  fetch(`/api/projects/${projectId}/tasks`).then(r => r.json()).then(setTasks);
}, [projectId]);

// ✅ Better: abort stale requests in the cleanup function
useEffect(() => {
  const controller = new AbortController();
  setStatus("loading");
  api.tasks.list(projectId, { signal: controller.signal })
    .then(page => { setTasks(page.data); setStatus("success"); })
    .catch(err => {
      if (err.name !== "AbortError") setStatus("error");
    });
  return () => controller.abort();      // runs when projectId changes or on unmount
}, [projectId]);

    Even the “better” version still lacks caching, deduplication (two components fetching the same list make two requests), background refresh, retries and invalidation after mutations. That is why teams use a server-state library.

    ✏️ Mutations, invalidation and optimistic rollback

    useMutation runs writes (POST/PATCH/DELETE). After success you usually invalidate related queries so they refetch, or write the server's response straight into the cache.

    tsxexport function useCreateTask(projectId: number) {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: (input: CreateTaskInput) => api.tasks.create(projectId, input),
    onSuccess: (task) => {
      qc.setQueryData(taskKeys.detail(task.id), task);                       // seed detail cache
      return qc.invalidateQueries({ queryKey: ["tasks", "list", projectId] }); // refetch lists (prefix match)
    },
  });
}

    Optimistic update with rollback

    tsxexport function useToggleTask(projectId: number) {
  const qc = useQueryClient();
  const key = taskKeys.list(projectId);
  return useMutation({
    mutationFn: (t: Task) => api.tasks.update(t.id, { status: t.status === "done" ? "todo" : "done" }),
    onMutate: async (t) => {
      await qc.cancelQueries({ queryKey: key });              // stop in-flight refetches overwriting us
      const previous = qc.getQueryData<Page<Task>>(key);      // snapshot
      qc.setQueryData<Page<Task>>(key, old => old && {
        ...old,
        data: old.data.map(x => x.id === t.id ? { ...x, status: x.status === "done" ? "todo" : "done" } : x),
      });
      return { previous };                                     // becomes "context"
    },
    onError: (_err, _t, context) => {
      if (context?.previous) qc.setQueryData(key, context.previous);   // rollback
      toast.error("Couldn't update task");
    },
    onSettled: () => qc.invalidateQueries({ queryKey: key }),  // re-sync with the server either way
  });
}

    Debounced search

    Do not hit /api/tasks?q= on every keystroke. Wait until the user pauses (e.g. 300 ms); the query library cancels outdated requests via the signal.

    tsxfunction useDebounced<T>(value: T, ms = 300) {
  const [v, setV] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setV(value), ms);
    return () => clearTimeout(id);
  }, [value, ms]);
  return v;
}

    Deprecation

    1. Ship the replacement (new field or /v2 endpoint) alongside the old one.
    2. Mark the old one deprecated in OpenAPI (deprecated: true) and send a Deprecation header plus a Sunset header with the removal date.
    3. Monitor usage of the old endpoint; contact remaining consumers.
    4. Remove it after the sunset date — return 410 Gone for a while if useful.
    💡
    Expand–contract (parallel change): add the new shape, migrate clients, then remove the old shape. With a frontend and API deployed separately, never remove something the currently deployed frontend still uses.

    🛡️ Security and performance checklist

    Security

    • Validate every input (body, params, query, headers) on the server.
    • Authenticate every non-public route; authorise per resource (object-level checks stop IDOR, e.g. reading /tasks/43 of another team).
    • Never return secrets: password hashes, tokens, internal ids you do not need. Use explicit response DTOs.
    • Prevent mass assignment: allow-list writable fields (.strict() in Zod).
    • Rate-limit, especially login and expensive endpoints.
    • HTTPS everywhere; Secure/httpOnly/SameSite cookies; strict CORS allow-list.
    • Parameterised queries (Prisma/pg placeholders) — never string-built SQL.
    • Security headers (Helmet), body size limits, dependency scanning.

    Performance

    • Avoid N+1 queries: load tasks with assignees via a join or include, not one query per task.
    • Paginate every list with a maximum limit.
    • Index columns used in filters and sorts ((project_id, status)).
    • Keep payloads lean: select needed fields; consider ?fields= or a lighter list representation.
    • Enable compression (gzip/brotli) at the proxy or via compression().
    • Use ETags and Cache-Control; cache hot reads (Redis) where safe.
    • Measure: p95 latency per endpoint, slow-query logs, tracing.

    🌐 REST & HTTP

    Walk me through what happens when a user clicks “Mark done” in a React app backed by a REST API.

    The click handler calls the API client, which sends PATCH /api/tasks/42 with {"status":"done"}, Content-Type: application/json and credentials. If it is cross-origin, the browser may send a CORS preflight first. Express matches the route, middleware authenticates (401 if not), validates the body (400/422), the service checks permission (403) and updates the database. The API returns 200 with the updated task. The client checks res.ok, updates state or the query cache, and React re-renders. With an optimistic update the UI changes immediately and rolls back on error.

    What makes an API RESTful?

    Resources identified by URLs, manipulated through a uniform interface of standard HTTP methods and status codes, with stateless requests (each carries its own auth and context), cacheable responses, and a layered client–server architecture. In practice: nouns in URLs, correct methods, meaningful status codes, and consistent representations. Strict REST also includes hypermedia (HATEOAS), which most JSON APIs skip.

    Explain safe vs idempotent methods with examples.

    Safe methods do not change state: GET, HEAD, OPTIONS. Idempotent methods may change state, but repeating them gives the same result: PUT and DELETE (and all safe methods). POST is neither, and PATCH is not guaranteed to be idempotent (e.g. “increment counter”). It matters for retries: clients and proxies can retry idempotent calls safely; POST needs an idempotency key.

    What is the difference between 401 and 403?

    401 Unauthorized means the request lacks valid authentication — no token, expired or invalid; the client should log in or refresh, and the server should send WWW-Authenticate. 403 Forbidden means the server knows who you are but you are not allowed; re-authenticating will not help. Sometimes 404 is used instead of 403 to avoid revealing that a resource exists.

    How would you debug a request that works in Postman but fails in the browser?

    Open the DevTools Network tab. Look for a failed preflight OPTIONS request or a console “blocked by CORS policy” message — Postman ignores CORS, browsers enforce it. Check whether cookies are sent (credentials: "include", SameSite, Secure), whether the base URL/env var is right, and whether mixed content (HTTP from an HTTPS page) is blocked. “Copy as cURL” reproduces the browser's exact request for comparison.

    🗺️ API design

    Design the endpoints for tasks and comments in a task tracker.

    GET/POST /api/projects/:projectId/tasks to list and create; GET/PATCH/PUT/DELETE /api/tasks/:id for an item; GET/POST /api/tasks/:id/comments and PATCH/DELETE /api/comments/:id. Keep nesting to one level, put filters/sort/pagination in the query string, return 201 + Location on create and 204 on delete, use a single problem+json error format, and document it in OpenAPI.

    Offset vs cursor pagination — when would you use each?

    Offset (LIMIT/OFFSET) is simple and supports page numbers and totals, good for admin tables over small data. It gets slow at large offsets and duplicates or skips rows when data changes. Cursor (keyset) pagination uses the last item's sort key, is fast at any depth with an index and stable under inserts, so it suits feeds and infinite scroll, but it cannot jump to an arbitrary page.

    How do you make POST requests safe to retry?

    Require an Idempotency-Key header generated by the client per user action. The server stores key, request hash and response; a repeat with the same key returns the stored response instead of creating a duplicate, and the same key with a different body is rejected. Keys expire after a window, and storage must handle concurrent duplicates (unique constraint or lock).

    How do you version an API, and when do you need to?

    You need a new version for breaking changes that clients cannot adopt immediately — typical for public or mobile clients. Options: URL path (/v1), media-type or custom header, or date-based versions. Prefer additive, backward-compatible evolution so versions are rare; when you must break, run old and new in parallel, mark the old one deprecated with Deprecation/Sunset headers, and monitor usage before removal.

    API-first or code-first — which do you prefer?

    API-first when multiple teams or external consumers depend on the API: the OpenAPI spec is reviewed early, the frontend builds against mocks in parallel, and clients are generated. Code-first suits a small team owning both ends: schemas in code (Zod, Pydantic) generate the spec so it never drifts. Either way, have one source of truth and generate docs, types and validation from it.

    🏗️ Building APIs

    How do you structure an Express API so it stays maintainable?

    Feature modules with routes, controllers, services and schemas; a data layer (Prisma or pg); shared middleware for auth, validation and errors; typed config loaded once. Controllers handle HTTP only, services hold business rules without req/res, so they are unit-testable. A central error middleware maps domain errors to status codes and a consistent problem+json body.

    How do you validate requests, and why is TypeScript not enough?

    TypeScript types are erased at runtime — a client can send anything. I validate body, params and query with a runtime schema such as Zod at the edge, strip or reject unknown keys to prevent mass assignment, coerce query strings to numbers, and return 400/422 with per-field errors. z.infer gives the static type, and the schema can be shared with the frontend form.

    How does error handling work in Express 5?

    Route handlers can be async; a thrown error or rejected promise is forwarded to the error middleware automatically (Express 4 needed next(err) or a wrapper). Error middleware has four params and is registered after routes and a 404 handler. It logs unexpected errors with a request id, maps known errors (validation, not found, unique-constraint) to 4xx, and returns a generic message for 5xx without stack traces.

    How do you configure CORS correctly for a SPA with cookie auth?

    Use an explicit allow-list of origins from config, credentials: true (so the response echoes the exact origin, never *), allowed methods and headers including custom ones, exposed headers like Location and ETag, and a preflight maxAge. Register CORS before auth so OPTIONS is not rejected. Cookies need SameSite and Secure plus CSRF protection. Remember CORS is not security against non-browser clients.

    How would you protect an API from abuse?

    Authentication and per-resource authorisation, input validation and body size limits, rate limiting (per user/IP, with a shared Redis store and stricter limits on login), pagination caps, timeouts on DB and outbound calls, HTTPS, security headers, no sensitive data in responses or logs, and monitoring/alerts on 4xx/5xx and 429 spikes.

    💻 Client consumption

    Why doesn't fetch throw on a 500 response, and how do you handle it?

    fetch's promise only rejects on network-level failures (offline, DNS, CORS, abort). Any HTTP response — including 404 and 500 — resolves. So the client must check res.ok or res.status, parse the error body (problem+json), and throw a typed ApiError. I centralise this in an API client wrapper so components never repeat it.

    How do you cancel requests and add timeouts?

    Pass an AbortSignal to fetch. Use an AbortController for manual cancel (e.g. in a useEffect cleanup), AbortSignal.timeout(ms) for timeouts, and AbortSignal.any to combine them. Ignore AbortError in UI error handling. TanStack Query passes a signal into queryFn and aborts outdated requests automatically.

    When would you choose axios over fetch?

    When I want built-in interceptors (auth headers, 401 refresh), automatic JSON, rejection on non-2xx, a timeout option and upload progress events. fetch is built in, smaller and integrates with Next.js server caching. Either way I wrap it in a typed API client so the choice is an implementation detail.

    How do you handle an expired access token in the client?

    On a 401, call the refresh endpoint once (sharing a single in-flight refresh promise across parallel requests), retry the original request if refresh succeeds, otherwise clear state and redirect to login with a return URL. Do not refresh on 403. Keep tokens in httpOnly cookies where possible so scripts cannot steal them.

    Explain optimistic updates and their risks.

    The UI applies the change before the server confirms, making interactions feel instant. Risks: the server may reject it (needs rollback and a clear message), concurrent edits may conflict, and in-flight refetches can overwrite the optimistic state (cancel them first). Use them for likely-to-succeed, reversible actions; use pessimistic updates for payments or destructive actions.

    🌊 Data fetching & state

    What problems do you hit when fetching in useEffect?

    Race conditions (an older request resolves last and overwrites newer data), state updates after unmount, no caching or dedupe, manual loading/error state, no retries or background refresh, and duplicate requests in Strict Mode exposing missing cleanup. Fixes: abort in cleanup or ignore stale results; better, use a server-state library or server components.

    How does TanStack Query decide when to refetch?

    Data younger than staleTime is fresh and served from cache. Once stale, it is refetched in the background on triggers: a new component mounting the query, window refocus, network reconnect, a refetchInterval, or explicit invalidation. Unused queries are removed after gcTime. The query key decides identity, so every input to the fetch must be in the key.

    How do you implement an optimistic mutation with rollback in TanStack Query?

    In onMutate: cancel related queries, snapshot the current cache with getQueryData, write the optimistic value with setQueryData, and return the snapshot as context. In onError: restore the snapshot. In onSettled: invalidate the queries to re-sync with the server.

    When would you fetch on the server in Next.js instead of the client?

    For the initial render of pages: Server Components fetch close to the API, keep tokens and internal URLs off the client, avoid loading spinners and improve SEO. Client-side fetching (TanStack Query) suits highly interactive, frequently changing data after load. Route Handlers act as a BFF to aggregate calls, hide secrets and avoid CORS. Per-user data must not land in shared caches — use cache: "no-store" or private caching.

    How do ETags work, and what else can they do besides caching?

    The server sends an ETag fingerprint; the client later sends If-None-Match and gets 304 Not Modified with no body if unchanged, saving bandwidth. ETags also enable optimistic concurrency: the client sends If-Match on PATCH/PUT, and the server returns 412 Precondition Failed if the resource changed since the client read it, preventing lost updates.

    🧪 Testing & evolution

    How would you test a REST endpoint end to end at the API level?

    Integration tests with Supertest (or TestClient/MockMvc) against the real app and a real test database, reset between tests. Cover the happy path and every contract error: 400/422 with field errors, 401, 403, 404, 409. Assert status, key headers (Location, Content-Type) and body shape. Keep unit tests for complex service logic.

    What is contract testing and why use it?

    It verifies that a consumer and a provider agree on the API shape without running the whole system. With Pact, the frontend's tests record expected interactions and the API's CI verifies them; alternatively, validate responses against the OpenAPI spec. It catches breaking changes before deploy, which matters when frontend and API ship independently.

    How do you test React components that call APIs?

    With Testing Library and MSW: MSW intercepts requests at the network layer, so the real API client and hooks run. Default handlers cover success; tests override them for errors, empty lists or slow responses. Use a fresh QueryClient per test with retries off. Assert what the user sees (loading, error, data), not implementation details.

    Which API changes are breaking, and how do you roll them out safely?

    Breaking: removing or renaming fields, changing types or status codes, making optional inputs required, tightening validation, changing error formats; new enum values can break exhaustive clients. Roll out with expand–contract: add the new shape, migrate clients, mark the old deprecated with Sunset dates, monitor usage, then remove. Version only when parallel shapes are impractical.

    A task list endpoint got slow as data grew. How do you investigate?

    Measure first: endpoint p95 latency, tracing and slow-query logs. Typical causes: N+1 queries (fix with joins/include), missing indexes on filter/sort columns, unbounded result sets (paginate with a max limit; prefer cursors for deep paging), oversized payloads (select only needed fields, compress), and repeated hot reads (ETags, caching). Confirm with EXPLAIN ANALYZE and re-measure after each change.

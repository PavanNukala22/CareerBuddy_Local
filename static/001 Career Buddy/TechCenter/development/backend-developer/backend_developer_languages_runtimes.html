    Backend Fundamentals

    What a backend does, how a request travels through it, and how the five big runtimes execute your code.

    🧭 What does a backend do?

    The backend is the part of an application that runs on servers, not on the user's device. The user never sees it directly. It receives requests from browsers, mobile apps or other services, applies business rules, reads and writes data, and sends back a response — usually JSON.

    📥
    Accept requests
    Listen on a port, parse HTTP, check the input is valid.
    🔐
    Protect
    Authenticate users, check permissions, rate-limit abusers.
    🧠
    Apply business rules
    “An order needs stock”, “a refund needs a reason”.
    🗄️
    Store data
    Talk to databases, caches, file storage and queues.
    🔌
    Integrate
    Call payment providers, email services and other internal APIs.
    📊
    Observe
    Write logs, metrics and traces so problems can be found.

    The frontend is what the user touches; the backend is the source of truth. A browser can be modified by anyone, so every important rule must be enforced on the backend, even if the frontend checks it too.

    EXAMPLE · Placing an order

    The shop's web page sends POST /orders with a basket. The backend checks the user is logged in, checks each item is in stock, calculates the price itself (never trusting the price sent by the browser), charges the card through a payment API, saves the order in the database and returns 201 Created with the new order ID.

    💡
    A good mental model: the backend is a set of functions that other programs call over the network. Everything else — frameworks, databases, queues — exists to make those functions correct, fast and reliable.

    🔁 Client–server and the life of a request

    In the client–server model a client (browser, phone app, another service) sends a request, and a server waits for requests and answers them. The client always starts the conversation; the server responds. One server handles many clients at once.

    A typical request path through a backend
    StepWhat happens
    1. ClientResolves the domain via DNS, opens a TLS connection and sends an HTTP request such as GET /orders/42.
    2. Load balancerSpreads traffic across several copies (instances) of your app. Often terminates TLS. Examples: Nginx, HAProxy, AWS ALB.
    3. Web serverThe HTTP server inside or in front of your app (Node's node:http, Uvicorn, Tomcat, Kestrel, Go's net/http) parses the request.
    4. Route handlerThe framework matches method + path to your function (a controller or handler). Middleware runs first: logging, auth, parsing.
    5. Service layerYour business logic. Kept separate from HTTP so it can be tested and reused.
    6. DatabaseA repository/ORM runs SQL or a query against PostgreSQL, MySQL, MongoDB, Redis…
    7. ResponseThe handler turns the result into JSON, sets a status code and headers, and the response travels back.
    📝
    Most backends are stateless: they keep no user state in memory between requests (state lives in the database, cache or token). That is what lets a load balancer send each request to any instance.
    EXAMPLE · Layers in code

    A handler getOrder(req, res) reads the ID from the path, calls orderService.find(id), which calls orderRepository.findById(id). If the repository returns nothing, the service raises a “not found” error and the handler maps it to 404. Each layer has one job.

    🧵 Processes, threads, concurrency and parallelism

    ProcessA running program with its own memory space. Processes are isolated: one crashing does not corrupt another.
    ThreadA path of execution inside a process. Threads share the process's memory, so they are cheaper but need care (locks) when sharing data.
    ConcurrencyDealing with many tasks at once by interleaving them. One cook switching between three pans.
    ParallelismDoing many tasks at the same instant on several CPU cores. Three cooks, three pans.

    Concurrency

    About structure: making progress on many things. Possible on a single core. Ideal when tasks mostly wait (network, disk, database).

    Parallelism

    About execution: really running at once. Needs several cores. Ideal for CPU-heavy work (image resizing, compression, ML inference).

    RuntimeMain concurrency modelParallel CPU work?
    Node.jsOne JavaScript thread + event loop; I/O handled asynchronouslyVia worker_threads or several processes (cluster)
    Python (CPython)Threads or asyncio; the GIL lets one thread run Python bytecode at a timeVia several processes (default build)
    JavaOS threads, thread pools, and (Java 21+) virtual threadsYes, threads run on all cores
    GoGoroutines scheduled by the Go runtime onto OS threadsYes, by default on all cores
    C# / .NETThread pool + async/await on TaskYes, threads run on all cores
    💡
    Most web backends are I/O-bound: a request spends most of its time waiting for the database or another API. That is why good concurrency (not raw CPU speed) usually decides how many requests a server can handle.

    ⏳ Blocking vs non-blocking I/O

    I/O (input/output) is anything that leaves the CPU: reading a file, querying a database, calling an API. It is thousands to millions of times slower than CPU work.

    Blocking I/O

    The thread stops and waits until the data arrives. Simple to write. To serve 1,000 waiting requests you need about 1,000 threads, and classic OS threads each reserve memory for their stack.

    pythondata = requests.get(url)   # thread waits here
print(data.status_code)

    Non-blocking I/O

    The program starts the operation and is notified when it completes; meanwhile the same thread serves other work. One thread can juggle thousands of connections.

    javascriptconst res = await fetch(url); // thread is free while waiting
console.log(res.status);

    Modern runtimes hide the difference in different ways:

    • Node.js and Python's asyncio: you write await; an event loop resumes your code when the I/O is done.
    • C#: async/await releases the thread back to the pool while waiting.
    • Go and Java virtual threads: you write normal blocking-looking code; the runtime parks the cheap goroutine/virtual thread and reuses the OS thread.
    ⚠️
    In an event-loop runtime, one accidentally blocking call (a synchronous file read, a long loop, time.sleep() inside an async def) freezes every request on that loop, not just one.

    Node.js: JavaScript on the Server

    The event loop, modules, HTTP servers, Express, async error handling, streams and CPU-heavy work.

    🟢 What Node.js is and how the event loop works

    Node.js runs JavaScript outside the browser. It combines Google's V8 engine (which runs and JIT-compiles JavaScript) with libuv (a C library that provides the event loop and asynchronous I/O). Use an even-numbered LTS release (Node 22 or 24) in production.

    Your JavaScript runs on one main thread. When you start I/O (a database query, a file read, an HTTP call), Node hands it off and keeps going. When the result is ready, a callback is queued and the event loop runs it. That is how one thread serves thousands of concurrent connections.

    Event loop phases, repeated on every tick (idle/prepare is internal)
    PhaseRuns
    TimersCallbacks from setTimeout / setInterval whose time has passed
    Pending callbacksSome system-level callbacks deferred from the previous loop (e.g. certain TCP errors)
    PollWaits for new I/O events and runs their callbacks — most of your code runs here
    ChecksetImmediate callbacks
    Close callbacksClose events such as socket.on('close')

    Between callbacks Node drains two microtask queues: process.nextTick callbacks and promise reactions (.then / code after await). Microtasks always run before the loop moves on to the next timer or I/O callback.

    javascriptconsole.log('A');
setTimeout(() => console.log('B'), 0);          // macrotask (timers phase)
Promise.resolve().then(() => console.log('C')); // microtask
console.log('D');
// Output: A D C B

    The libuv thread pool

    Network sockets use the operating system's own async mechanisms (epoll, kqueue, IOCP). Work that has no good async OS API — most fs calls, dns.lookup, crypto.pbkdf2/scrypt, zlib — runs on libuv's thread pool, which has 4 threads by default (UV_THREADPOOL_SIZE changes it).

    ⚠️
    Never block the event loop. A synchronous fs.readFileSync in a request handler, a huge JSON.parse, a catastrophic regex or a long for loop stops every request on that process until it finishes.

    🌍 A minimal HTTP server with node:http

    Node can serve HTTP with no framework at all. This is worth seeing once, because every framework builds on it.

    javascriptimport http from 'node:http';

const server = http.createServer((req, res) => {
  if (req.method === 'GET' && req.url === '/health') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ status: 'ok' }));
    return;
  }
  res.writeHead(404, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ error: 'Not found' }));
});

const port = Number(process.env.PORT ?? 3000);
server.listen(port, () => console.log(`Listening on ${port}`));

    Notice what is missing: path parameters, body parsing, validation, error handling, middleware. Writing these by hand for every route is why frameworks exist.

    📝
    req is a readable stream (the body arrives in chunks) and res is a writable stream. To read a JSON body manually you must collect the chunks, then JSON.parse them — frameworks do this for you.

    🚏 Express: routing, middleware and errors

    ⏱️ async/await and error handling

    Almost every Node API is asynchronous. Modern code uses promises with async/await instead of nested callbacks.

    javascriptimport { readFile } from 'node:fs/promises';

async function loadConfig(path) {
  try {
    const text = await readFile(path, 'utf8');
    return JSON.parse(text);
  } catch (err) {
    throw new Error(`Cannot load config from ${path}`, { cause: err });
  }
}

// run independent I/O in parallel, not one after another
const [user, orders] = await Promise.all([
  users.findById(id),
  orders.findByUser(id),
]);

    Promise.allAll succeed (rejects on the first failure)Independent calls that must all work

    Unhandled rejections

    If a promise rejects and nobody handles it, Node (since v15) treats it like an uncaught exception: it prints the error and exits the process. This is a feature — a half-broken process is worse than a restart.

    javascriptprocess.on('unhandledRejection', (reason) => {
  logger.error({ reason }, 'unhandled rejection');
  process.exit(1);           // let the orchestrator restart us
});
    ⚠️
    Forgetting await is the most common async bug: const user = users.findById(id) gives you a Promise, not a user, and any rejection escapes your try/catch.

    For timeouts and cancellation, pass an AbortSignal: fetch(url, { signal: AbortSignal.timeout(2000) }) aborts the request after 2 seconds.

    🌊 Streams

    A stream processes data piece by piece instead of loading it all into memory. A 5 GB file can be copied, compressed and uploaded with a few kilobytes of RAM.

    TypeExample
    Readablefs.createReadStream, an incoming HTTP request
    Writablefs.createWriteStream, an HTTP response
    DuplexA TCP socket (read and write)
    Transformzlib.createGzip() — modifies data as it passes through
    javascriptimport { createReadStream, createWriteStream } from 'node:fs';
import { createGzip } from 'node:zlib';
import { pipeline } from 'node:stream/promises';

// compress a large export without loading it into memory
await pipeline(
  createReadStream('orders-2026.csv'),
  createGzip(),
  createWriteStream('orders-2026.csv.gz'),
);
    💡
    Use pipeline() rather than chaining .pipe(). It forwards errors, cleans up every stream on failure and handles backpressure — pausing the fast producer when the slow consumer's buffer is full.

    🏋️ CPU-heavy work: worker_threads and cluster

    The event loop is great for I/O and bad for long computations. Two built-in tools add real parallelism:

    worker_threads

    Extra JavaScript threads inside one process, each with its own V8 isolate and event loop. They communicate by messages (and can share memory with SharedArrayBuffer). Use for CPU tasks: image processing, hashing, parsing big files.

    cluster / multiple processes

    Forks several Node processes that share one listening port, roughly one per CPU core. Scales request handling across cores. In containers, running several replicas behind a load balancer is often simpler.

    javascript// main.js
import { Worker } from 'node:worker_threads';

export function resizeInWorker(imagePath) {
  return new Promise((resolve, reject) => {
    const worker = new Worker(new URL('./resize-worker.js', import.meta.url),
                              { workerData: imagePath });
    worker.once('message', resolve);
    worker.once('error', reject);
  });
}

// resize-worker.js
import { parentPort, workerData } from 'node:worker_threads';
const result = heavyResize(workerData);   // CPU work, off the main thread
parentPort.postMessage(result);
    📝
    Starting a worker costs a few milliseconds and memory. For many small tasks use a worker pool (e.g. the Piscina library) instead of a new worker per request.

    🐍 Why Python on the backend?

    Python is readable, quick to write and has a vast ecosystem. On the backend it powers APIs, admin systems, data pipelines and — above all — anything near data science and machine learning, because the model code is already Python.

    ✍️
    Fast to write
    Little boilerplate; prototypes become products quickly.
    🔋
    Batteries included
    Rich standard library plus PyPI with hundreds of thousands of packages.
    🤖
    Data & AI
    NumPy, pandas, PyTorch, scikit-learn — serve models in the same language.
    🐢
    Trade-off
    Pure-Python CPU code is slower than Go, Java or C#; heavy maths runs in C/Rust extensions.

    The standard interpreter is CPython. It compiles your .py files to bytecode and interprets it. Use a supported version (3.12 or 3.13 at the time of writing) and pin it per project.

    📝
    Python is dynamically typed (types are checked at run time) but supports optional type hints. Modern frameworks such as FastAPI and Pydantic actually use those hints at run time for validation.

    🔌 WSGI vs ASGI, Gunicorn and Uvicorn

    Python web frameworks do not open sockets themselves. A separate application server accepts HTTP connections and calls your app through a standard interface.

    How a request reaches Python code

    WSGI (PEP 3333)

    Synchronous: one request occupies one worker thread or process until it finishes. No WebSockets. Servers: Gunicorn, uWSGI, mod_wsgi. Frameworks: Flask, Django (classic).

    pythondef app(environ, start_response):
    start_response("200 OK", [("Content-Type", "text/plain")])
    return [b"ok"]

    ASGI

    Asynchronous: async callables, so one worker can handle many concurrent requests while they wait on I/O. Supports WebSockets and long-lived connections. Servers: Uvicorn, Hypercorn, Granian, Daphne. Frameworks: FastAPI, Starlette, Django (ASGI mode).

    pythonasync def app(scope, receive, send):
    ...  # await send({...})

    🔄 asyncio basics

    asyncio is Python's built-in event loop. A function defined with async def is a coroutine; await pauses it until the awaited operation is done, letting the loop run other coroutines meanwhile.

    pythonimport asyncio

async def fetch_status(client: httpx.AsyncClient, url: str) -> int:
    response = await client.get(url, timeout=5.0)
    return response.status_code

async def main() -> None:
    urls = ["https://example.com", "https://example.org"]
    async with httpx.AsyncClient() as client:
        # run the requests concurrently
        results = await asyncio.gather(*(fetch_status(client, u) for u in urls))
    print(results)

asyncio.run(main())

    asyncio.run(main())Start the event loop (once, at the program entry point)
    asyncio.gather(...)Run awaitables concurrently and collect results
    asyncio.TaskGroup()Structured concurrency (3.11+): if one task fails, the others are cancelled
    asyncio.timeout(2)Cancel a block that takes too long (3.11+)

    ⚠️

In FastAPI, a plain def endpoint is run in a thread pool automatically, so blocking code is safer there than in async def.

    🪶 Virtual threads (Java 21+)

    A platform thread is a thin wrapper over an OS thread: about 1 MB of reserved stack and costly to create, so servers cap them at a few hundred. Virtual threads (final in Java 21) are lightweight threads managed by the JVM. You can have millions.

    Platform threads

    • 1 Java thread = 1 OS thread
    • Pooled because they are expensive
    • A blocking call ties up an OS thread
    • Concurrency limited by pool size

    Virtual threads

    • Many virtual threads run on a few carrier OS threads
    • Cheap: create one per task, never pool them
    • On blocking I/O the JVM unmounts the virtual thread and frees the carrier
    • Concurrency limited by downstream resources (DB connections)
    javatry (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (long id : orderIds) {
        executor.submit(() -> enrich(id));   // plain blocking code inside
    }
}

    properties# Spring Boot 3.2+: serve requests on virtual threads
spring.threads.virtual.enabled=true

    What changes — and what does not

    • You keep simple, blocking, readable code and still get event-loop-like scalability for I/O-bound work.
    • They do not make CPU-bound code faster.
    • Your database pool (e.g. 10 connections) is now the real limit — protect downstreams with semaphores or rate limits.
    • Avoid caching expensive objects in ThreadLocal — with millions of threads that wastes memory.
    • Before Java 24, blocking inside synchronized could pin the carrier thread; JDK 24 (JEP 491) largely removed that problem.
    ✅
    For most new I/O-heavy Spring services on Java 21+, enabling virtual threads is a better first step than rewriting to reactive (WebFlux).

    errors.As(err, &target)Is there an error of this type in the chain? If so, fill target
    errors.Join(e1, e2)Combine several errors into one

    error

    For expected failures: not found, invalid input, timeout. Returned and handled.

    panic

    For programmer bugs or impossible states (nil map write, index out of range). Unwinds the stack; recover() in a deferred function can stop it. net/http recovers panics per request, but do not use panic for control flow.

    ⚠️
    Comparing with err == ErrNotFound fails once the error has been wrapped. Always use errors.Is.

    🚦 Goroutines, channels and synchronisation

    A goroutine is a function running concurrently, started with go f(). It begins with a stack of a few kilobytes that grows as needed, and the Go scheduler multiplexes goroutines onto OS threads (M:N scheduling), using all CPU cores by default (GOMAXPROCS).

    Channels are typed pipes between goroutines. “Do not communicate by sharing memory; share memory by communicating.”

    gofunc fetchAll(ctx context.Context, ids []int) []Result {
    results := make(chan Result, len(ids))   // buffered channel
    var wg sync.WaitGroup

    for _, id := range ids {
        wg.Add(1)
        go func() {                          // Go 1.22+: id is per-iteration
            defer wg.Done()
            results <- fetch(ctx, id)
        }()
    }

    wg.Wait()
    close(results)                           // lets range terminate

    var out []Result
    for r := range results {
        out = append(out, r)
    }
    return out
}

    goselect {                                  // wait on several channels
case r := <-results:
    handle(r)
case <-ctx.Done():
    return ctx.Err()                      // cancelled or timed out
case <-time.After(500 * time.Millisecond):
    log.Println("still waiting...")
}

    ⏲️ context.Context: cancellation and timeouts

    A context.Context carries a deadline, a cancellation signal and request-scoped values across API boundaries. By convention it is the first parameter of any function that does I/O.

    gofunc (h *Handler) GetRecommendations(w http.ResponseWriter, r *http.Request) {
    // r.Context() is cancelled automatically if the client disconnects
    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
    defer cancel()                        // always release resources

    req, err := http.NewRequestWithContext(ctx, http.MethodGet, h.recoURL, nil)
    if err != nil {
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }
    resp, err := h.client.Do(req)
    if errors.Is(err, context.DeadlineExceeded) {
        http.Error(w, "upstream timeout", http.StatusGatewayTimeout)
        return
    }
    // ...
}

    FunctionCreates a context that…

    🌐 An HTTP server with net/http and JSON

    Since Go 1.22, the standard http.ServeMux supports methods and path wildcards, so many services need no router library.

    gopackage main

import (
    "encoding/json"
    "log"
    "net/http"
    "strconv"
    "time"
)

type Item struct {
    ID   int    `json:"id"`
    Name string `json:"name"`
}

func writeJSON(w http.ResponseWriter, status int, v any) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    json.NewEncoder(w).Encode(v)
}

func main() {
    mux := http.NewServeMux()

    mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
        writeJSON(w, http.StatusOK, map[string]string{"status": "ok"})
    })

    mux.HandleFunc("GET /items/{id}", func(w http.ResponseWriter, r *http.Request) {
        id, err := strconv.Atoi(r.PathValue("id"))
        if err != nil {
            http.Error(w, "id must be a number", http.StatusBadRequest)
            return
        }
        writeJSON(w, http.StatusOK, Item{ID: id, Name: "Desk lamp"})
    })

    mux.HandleFunc("POST /items", func(w http.ResponseWriter, r *http.Request) {
        var in Item
        if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
            http.Error(w, "invalid JSON", http.StatusBadRequest)
            return
        }
        writeJSON(w, http.StatusCreated, in)
    })

    srv := &http.Server{
        Addr:              ":8080",
        Handler:           mux,
        ReadHeaderTimeout: 5 * time.Second, // protect against slow clients
    }
    log.Fatal(srv.ListenAndServe())
}

    🌐 Backend fundamentals

    Walk me through what happens when a request hits your backend.

    DNS resolves the domain; the client opens a TCP (or QUIC) connection with TLS and sends the HTTP request. A load balancer or reverse proxy picks a healthy instance. The app's HTTP server parses the request, middleware runs (logging, auth, body parsing), the router dispatches to a handler, which validates input and calls the service layer. The service applies business rules and calls repositories that query the database or cache. The result is serialised to JSON with a status code and headers, then travels back. Logs, metrics and traces are emitted along the way, tagged with a request ID.

    What is the difference between concurrency and parallelism? Give a backend example.

    Concurrency is structuring a program to make progress on many tasks by interleaving them; parallelism is executing tasks at the same instant on multiple cores. A Node.js server handling 5,000 open connections on one thread is concurrent but not parallel. A Go service hashing passwords across 8 cores is parallel. Most web backends need concurrency because they are I/O-bound.

    Why should backends be stateless, and where does state go instead?

    If an instance keeps sessions or carts in memory, a request routed to another instance loses them, and restarts or scaling events drop data. Stateless instances can be added, removed and restarted freely behind a load balancer. State moves to a database, a distributed cache such as Redis, object storage, or a signed token (e.g. a JWT) held by the client.

    Which HTTP status codes would you return for validation errors, missing auth, forbidden access, conflicts and rate limits?

    400 (or 422) for invalid input, 401 when the client is not authenticated, 403 when authenticated but not allowed, 409 for a conflict such as a duplicate or version clash, and 429 for rate limiting, ideally with a Retry-After header. Server faults are 5xx: 500 for unexpected errors, 503 when temporarily unavailable, 504 when an upstream timed out.

    How do you manage configuration and secrets across environments?

    Follow twelve-factor: one build artifact, configuration injected through environment variables (or a config service), validated at startup so mistakes fail fast. Secrets come from a secret manager (Vault, AWS Secrets Manager, Azure Key Vault, Kubernetes Secrets) and are never committed; .env files are for local development only and are git-ignored. Logs must not print secrets.

    🟢 Node.js

    Explain the Node.js event loop. How can one thread handle thousands of connections?

    Node runs JavaScript on one thread. I/O is delegated to the OS (epoll/kqueue/IOCP) or libuv's thread pool, so the main thread never waits. When an operation completes, its callback is queued; the event loop cycles through phases — timers, pending callbacks, poll (I/O), check (setImmediate), close — running ready callbacks, and drains microtasks (process.nextTick, promise reactions) between callbacks. Since each request mostly waits on I/O, one thread can interleave thousands of them.

    What runs on the libuv thread pool, and when would you resize it?

    Operations without a good async OS API: most fs calls, dns.lookup, CPU-heavy crypto (pbkdf2, scrypt) and zlib. The pool has 4 threads by default. If a service does many concurrent file or crypto operations, they queue behind those 4 threads; you can raise UV_THREADPOOL_SIZE (set before the pool is first used). Network sockets do not use the pool.

    How do you handle CPU-intensive work in Node.js?

    Keep it off the event loop. Options: worker_threads (ideally a pool like Piscina) for CPU tasks inside the process; multiple processes via cluster or multiple container replicas to use all cores for request handling; offloading to a job queue and a separate worker service; or moving the hot path to a faster language or a native addon. Also break long loops into chunks and avoid synchronous APIs in handlers.

    What happens with an unhandled promise rejection, and how do you handle errors in Express?

    Since Node 15 an unhandled rejection crashes the process by default, like an uncaught exception — the process should be restarted by the orchestrator rather than limp on. In Express, register a four-argument error middleware (err, req, res, next) after the routes. Express 5 forwards rejected promises from async handlers to it automatically; in Express 4 you had to call next(err) or use a wrapper.

    ES modules vs CommonJS — what are the practical differences?

    ESM uses static import/export, supports top-level await, is the JavaScript standard, and is enabled by "type": "module" or .mjs. CommonJS uses require/module.exports, loads synchronously and provides __dirname. ESM can import CommonJS; modern Node (22.12+, 20.19+) can also require() synchronous ES modules. New projects should use ESM.

    🐍 Python

    Compare Django, Flask and FastAPI. When would you choose each?

    Django is batteries-included — ORM, migrations, admin, auth — ideal for data-heavy apps and back offices built fast. Flask is a minimal WSGI micro-framework for small services where you choose every component. FastAPI is an ASGI, async-first API framework that uses type hints and Pydantic for validation and generates OpenAPI docs — a strong default for JSON APIs, microservices and ML model serving.

    What is the GIL and how does it affect a Python web server?

    In the default CPython build, the Global Interpreter Lock lets only one thread execute Python bytecode at a time per process. It is released during blocking I/O, so threads and asyncio work well for I/O-bound web services. CPU-bound Python code does not speed up with threads; you scale with multiple worker processes (Gunicorn/Uvicorn workers, ProcessPoolExecutor) or native extensions that release the GIL. Python 3.13 introduced an optional experimental free-threaded build, officially supported from 3.14 but still not the default.

    Explain WSGI vs ASGI.

    WSGI is the synchronous interface: the server calls app(environ, start_response) and a worker is busy for the whole request. ASGI is its async successor: async def app(scope, receive, send) lets one worker interleave many requests and supports WebSockets and long-lived connections. Gunicorn serves WSGI apps (Flask, classic Django); Uvicorn or Hypercorn serve ASGI apps (FastAPI, Starlette, Django in ASGI mode).

    What mistakes do people make with asyncio in FastAPI?

    Calling blocking code — requests, time.sleep, sync DB drivers, heavy CPU — inside async def endpoints, which freezes the event loop for every request on that worker. Fixes: use async libraries (httpx, asyncpg, async SQLAlchemy), declare the endpoint with plain def so FastAPI runs it in a thread pool, or use asyncio.to_thread. Also: forgetting to await, and creating a new HTTP client per request instead of reusing one.

    How do you run background work in a Python backend?

    For durable jobs, use a task queue such as Celery (or RQ, Dramatiq, arq) with a broker like Redis or RabbitMQ: the API enqueues a task with IDs and returns quickly; workers process it with retries. Tasks should be idempotent and small in payload. FastAPI's BackgroundTasks is fine for small fire-and-forget work tied to one process, but it is lost if the process dies. Scheduled jobs use Celery beat or a platform scheduler.

    ☕ Java

    How does the JVM execute code, and why is Java fast despite using bytecode?

    javac produces bytecode; the JVM loads classes, verifies them, and starts by interpreting. It profiles execution and JIT-compiles hot methods (C1 quickly, C2 with aggressive optimisations such as inlining and escape analysis) into machine code. Long-running servers therefore reach near-native throughput after warm-up. Memory is managed by a generational GC such as G1 or ZGC.

    Explain dependency injection in Spring and why constructor injection is preferred.

    Spring's IoC container creates beans (@Service, @Repository, @RestController…) and supplies their dependencies. Constructor injection makes dependencies explicit and final, makes the class easy to construct in unit tests without Spring, prevents partially initialised objects, and surfaces circular dependencies early. With a single constructor no @Autowired is needed.

    What are virtual threads and when do they help?

    Virtual threads (Java 21) are lightweight threads scheduled by the JVM onto a small number of carrier OS threads. When a virtual thread blocks on I/O it is unmounted, freeing the carrier. You can create one per task — millions — so simple blocking code scales like async code for I/O-bound workloads. They do not speed up CPU-bound work, should not be pooled, and shift the bottleneck to resources such as DB connection pools. In Spring Boot 3.2+ enable them with spring.threads.virtual.enabled=true.

    How do you handle errors consistently in a Spring REST API?

    Throw domain exceptions (e.g. OrderNotFoundException) from services, and map them once in a @RestControllerAdvice class with @ExceptionHandler methods returning ProblemDetail (RFC 9457) and the right status. Validate input with @Valid and Bean Validation, map MethodArgumentNotValidException to 400 with field errors, and have a catch-all handler that logs and returns a generic 500.

    What is the N+1 problem in JPA and how do you fix it?

    Loading a list of N entities and then lazily accessing an association on each triggers one query for the list plus N more queries. Fix with a fetch join (join fetch in JPQL), @EntityGraph, batch fetching, or a DTO projection query that selects exactly the needed columns. Detect it by enabling SQL logging or statistics in development and in tests.

    🐹 Go

    How do goroutines differ from OS threads?

    Goroutines are managed by the Go runtime, start with a small stack (a few KB) that grows on demand, and are multiplexed onto OS threads by an M:N scheduler (GOMAXPROCS threads run Go code in parallel). Creating and switching them is far cheaper than OS threads, so a service can run hundreds of thousands. When a goroutine blocks on network I/O, the runtime parks it and uses the netpoller, keeping the thread busy with other goroutines.

    Explain Go's approach to errors, including wrapping.

    Errors are values returned as the last result and checked with if err != nil. Add context while preserving the cause using fmt.Errorf("load order %d: %w", id, err). Callers inspect the chain with errors.Is (sentinel values like sql.ErrNoRows) and errors.As (typed errors). panic is reserved for programmer errors or unrecoverable states, not normal control flow.

    What is context.Context used for and what are the rules?

    It carries cancellation, deadlines and request-scoped values across API boundaries. Rules: pass it as the first parameter (ctx context.Context), never store it in a struct, always call the cancel function (defer cancel()), propagate it to DB and HTTP calls, and use WithValue only for request-scoped data such as a request ID — not for optional parameters. In handlers start from r.Context(), which is cancelled when the client goes away.

    How would you avoid goroutine leaks and data races?

    Every goroutine needs a guaranteed exit: close channels when producers finish, select on ctx.Done() in loops, and avoid sends to channels nobody reads (use buffers or select with cancellation). Use sync.WaitGroup or errgroup to wait for completion. For races, protect shared state with sync.Mutex or confine it to one goroutine and communicate via channels, and run tests with go test -race.

    Do you need a framework like Gin for a Go REST API?

    Often not. Since Go 1.22, http.ServeMux supports method matching and wildcards ("GET /items/{id}", r.PathValue), and encoding/json handles JSON. Middleware is just func(http.Handler) http.Handler. chi adds route groups while staying net/http-compatible. Gin and Echo add binding, validation and convenience at the cost of a framework-specific context type. Choose based on team preference and needs.

    🟣 C# and choosing a stack

    Explain singleton, scoped and transient lifetimes and the captive dependency problem.

    Singleton: one instance for the app's lifetime (must be thread-safe). Scoped: one per request scope — e.g. DbContext. Transient: a new instance on every resolution. A captive dependency occurs when a longer-lived service holds a shorter-lived one, such as a singleton holding a scoped DbContext: it is then shared across requests and threads. ASP.NET Core validates scopes in Development and throws; fix it by changing lifetimes or by creating a scope with IServiceScopeFactory.

    How does the ASP.NET Core middleware pipeline work?

    Middleware components form an ordered chain; each receives HttpContext and a next delegate, can act before calling next, and after it returns. The order of registration is the order of execution: exception handling first, then HTTPS redirection, static files, routing, CORS, authentication, authorization and finally endpoints. A middleware can short-circuit by not calling next (e.g. returning 401).

    Why should you avoid .Result and .Wait() in ASP.NET Core?

    They block a thread-pool thread while waiting for async I/O. Under load, many blocked threads cause thread-pool starvation: requests queue up even though the CPU is idle, and the pool grows slowly. In some environments with a synchronization context it can also deadlock. Use async/await all the way and pass CancellationTokens.

    Minimal APIs or controllers?

    Both use the same routing, DI, middleware and hosting. Minimal APIs map lambdas directly in Program.cs (grouped with MapGroup), have less ceremony, good performance and better Native AOT support — great for microservices. Controllers organise endpoints into classes with attributes, filters and conventions, which large teams with MVC experience may prefer. Mixing both in one app is fine.

    A company asks you to pick a backend language for a new service. How do you decide?

    Start from constraints: the team's existing skills and hiring market; the workload (I/O-bound API, CPU-heavy processing, real-time, ML); latency and memory targets; required libraries (ML → Python; Azure/AD → .NET; enterprise integration → Java); and operational standards (existing CI/CD, observability, platform). Then pick the simplest stack meeting them — e.g. Go for a lean high-throughput worker, FastAPI for model serving, Node/TypeScript for a BFF next to a React team — and state the trade-offs explicitly.

    Module 01 · Foundations

    What is System Design?

    Start from zero: what a system is, why design matters, and how a monolith differs from distributed systems.

    🧭 What is System Design?

    System design is the process of deciding how the parts of a software product (services, databases, queues, caches) are arranged and talk to each other so it meets its goals: correct, fast, reliable and easy to change.

    As a backend developer you move from "does my function work?" to "does the whole system keep working when traffic grows 100x and a server dies?"

    Example: an online food-order app

    A user taps Place order. Behind it: validate the cart, charge the card, tell the restaurant, assign a rider, send notifications. System design decides whether this is one program or many, and what happens when payment is slow.

    🏛️ Monolith vs Distributed

    🟢 Monolith

    One codebase, one deployable unit, usually one database. Simple to build, test and debug. Hard to scale parts independently; one bug can take everything down.

    🔵 Distributed (microservices)

    Many small services, each owning one job and its data, communicating over the network. Independent scaling and deployment, but more complexity: latency, partial failure, data consistency.

    💡
    Start with a well-structured monolith for a new product. Split into services when team size or scaling pain justifies it.

    🎯 Quality attributes

    ⚡
    Latency
    Time to answer one request.
    📈
    Throughput
    Requests handled per second.
    🛡️
    Availability
    Percent of time the system works (99.9% ≈ 8.8 h downtime a year).
    🔁
    Scalability
    Ability to handle more load by adding resources.
    🧱
    Consistency
    Do all readers see the same data?
    🔧
    Maintainability
    How easily can teams change it?

    📖 Key terms

    Horizontal scalingAdd more machines. Vertical scaling: bigger machine.
    StatelessA service that keeps no user session in memory, so any instance can serve any request.
    Load balancerSpreads requests across instances.
    SynchronousCaller waits for the reply (HTTP/gRPC).
    AsynchronousCaller sends work and continues; result arrives later (queues, events).
    CAP theoremDuring a network partition choose consistency or availability.
    IdempotentDoing it twice has the same effect as once.
    SLA / SLOPromised / targeted reliability level.

    Module 02 · Microservices

    Microservices Architecture

    What they are, how to split a system, how services talk, and the patterns that keep them healthy.

    🧩 What is a microservice?

    A microservice is a small, independently deployable service built around one business capability (Orders, Payments, Catalog) that owns its own data and exposes an API.

    Single responsibilityOne service, one business capability.
    Own your dataNo service reads another's database directly.
    Independent deployRelease one service without redeploying others.
    Design for failureAssume any call can be slow or fail.

    ✂️ How to split: decomposition

    StrategyIdeaExample
    By business capabilityOne service per thing the business doesOrders, Billing, Shipping
    By subdomain (DDD)Bounded contexts from domain-driven designCustomer vs Fulfilment context
    Strangler figGradually route features from monolith to new servicesMove Search out first
    ⚠️
    Avoid the distributed monolith: services that must be deployed together or share a database get all the pain and none of the benefit.

    🔌 Communication styles

    StyleTypesUse when
    SynchronousREST, gRPC, GraphQLYou need an immediate answer (get price, validate user)
    AsynchronousEvents, commands via a brokerWork can happen later; you want loose coupling

    API Gateway is the single entry point for clients: routing, auth, rate limiting. Service discovery lets services find each other's addresses (Consul, Kubernetes DNS).

    🛠️ Resilience patterns

    🔌
    Circuit breaker
    Stop calling a failing service for a while; fail fast.
    🔁
    Retry + backoff
    Retry transient errors with growing, jittered delays.
    ⏱️
    Timeout
    Never wait forever on a remote call.
    🚧
    Bulkhead
    Isolate resources so one failure cannot drain everything.
    🧯
    Fallback
    Return cached or default data when a dependency is down.
    pythondef call_with_retry(fn, tries=4):
    for i in range(tries):
        try: return fn(timeout=2)
        except TransientError:
            time.sleep((2**i) + random.random())  # backoff + jitter
    raise

    Module 03 · Message Brokers

    Message Brokers: Kafka & RabbitMQ

    What a broker is, the messaging models, and how Apache Kafka and RabbitMQ really work.

    📬 What is a message broker?

    A message broker is middleware that receives messages from producers, stores them, and delivers them to consumers. Producer and consumer never talk directly, so they can fail, scale and deploy independently.

    Analogy

    A post office: you drop a letter and leave. The recipient collects it when ready. Neither needs to be present at the same time.

    ModelHow it worksExample
    Point-to-point (queue)Each message goes to exactly one consumer in a groupProcess each order once
    Publish/subscribe (topic)Each message goes to every interested subscriberOrder placed → email, analytics, inventory
    Log (streaming)Ordered, retained, replayable record of eventsKafka

    🐇 RabbitMQ

    A smart broker using AMQP. Producers publish to an exchange, which routes to queues via bindings; consumers read from queues and ack messages. Messages are removed once acknowledged.

    ExchangeRouting
    directExact routing-key match
    topicPattern match, e.g. order.*.eu
    fanoutCopy to all bound queues
    headersMatch on message headers

    Strengths: flexible routing, per-message TTL, priorities, dead-letter queues, low latency, easy task queues. Limits: not built for replaying history or multi-million-msg/sec streams.

    python# pika: publish a durable task
ch.queue_declare('emails', durable=True)
ch.basic_publish('', 'emails', body, properties=pika.BasicProperties(delivery_mode=2))
# consumer: ack only after success
def cb(ch, m, p, body):
    send(body); ch.basic_ack(m.delivery_tag)

    🌊 Apache Kafka

    A distributed, durable commit log. Messages are appended to a topic, split into partitions, and kept for a retention period whether or not they were read. Consumers track their own offset.

    🗂️
    Topic & partition
    Order is guaranteed within a partition. Same key → same partition.
    👥
    Consumer group
    Each partition is read by one consumer in the group; add consumers to scale.
    🧬
    Replication
    Each partition has a leader and followers; acks=all + min.insync.replicas for durability.
    ⏪
    Replay
    Reset offsets to reprocess history.
    python# kafka-python: key keeps one customer's events ordered
producer.send('orders', key=b'cust-42', value=event)
for msg in consumer:   # group_id='billing'
    handle(msg.value); consumer.commit()

    ⚖️ Kafka vs RabbitMQ

    AspectRabbitMQKafka
    ModelSmart broker, dumb consumerDumb log, smart consumer
    RetentionDeleted after ackKept by time/size; replayable
    OrderingPer queuePer partition
    ThroughputThousands–100k/sHundreds of thousands–millions/s
    RoutingRich (exchanges)Topic + key only
    Best forTask queues, RPC, complex routingEvent streaming, logs, analytics, event sourcing
    💡
    Others to know: Amazon SQS/SNS (managed), Google Pub/Sub, Apache Pulsar, NATS, Redis Streams.

    Module 04 · Asynchronous Processing

    Asynchronous Processing

    Why and how to move work off the request path, and make it reliable.

    ⏳ What is async processing?

    Instead of doing slow work inside the user's request, accept it, put a message on a queue, reply immediately (HTTP 202 Accepted), and let workers finish it in the background.

    🔴 Synchronous

    Upload video → transcode (90 s) → respond. User waits; a spike times out.

    🟢 Asynchronous

    Upload → enqueue job → respond in 100 ms with a job id → worker transcodes → notify.

    🧰 Common patterns

    PatternDescriptionExample
    Work queueWorkers compete for jobsImage resize, emails
    Event-drivenServices react to published eventsOrderPlaced → inventory, billing
    Request–reply over brokerReply sent to a reply queue with correlation idAsync RPC
    Fan-out / fan-inSplit a job, then aggregateBatch report
    Scheduled/delayed jobsRun at a later timeCart-abandon reminder
    Competing consumersScale by adding workersCelery, Sidekiq, BullMQ

    🛡️ Reliability essentials

    Delivery guaranteesAt-most-once (may lose), at-least-once (may duplicate), exactly-once (hard; effectively achieved via idempotency or transactions).
    Idempotent consumerStore processed message ids; skip repeats.
    Dead-letter queuePark messages that keep failing for inspection.
    BackpressureSlow producers or buffer when consumers fall behind.
    Poison messageA message that always crashes the consumer.
    pythondef handle(msg):
    if db.exists('processed', msg.id): return   # idempotency
    with db.transaction():
        charge(msg.order_id)
        db.insert('processed', msg.id)
    ack(msg)
    ⚠️
    Most brokers give at-least-once delivery, so assume duplicates will arrive. Make consumers idempotent.
    Q. A consumer crashes after charging a card but before ack. The message is redelivered. What protects the customer?
    • A Larger queue
    • B Idempotent processing keyed by message id
    • C Faster consumers
    • D Fanout exchange

    Advanced Distributed Patterns

    Data consistency across services, event sourcing, Kafka internals and operating at scale.

    🔄 Saga pattern

    Without cross-service ACID transactions, a saga is a sequence of local transactions, each with a compensating action if a later step fails.

    StyleHowTrade-off
    ChoreographyServices react to each other's eventsSimple, but flow is hard to trace
    OrchestrationA coordinator tells each service what to doClear flow, one more component
    Order saga

    Create order → reserve stock → charge payment. If payment fails: release stock → cancel order.

    📤 Transactional outbox & CDC

    Problem: you update the DB and publish an event; one can succeed while the other fails. Outbox: write the event to an outbox table in the same DB transaction; a relay (or CDC tool like Debezium) publishes it to the broker.

    sqlBEGIN;
  UPDATE orders SET status='PAID' WHERE id=42;
  INSERT INTO outbox(topic, key, payload) VALUES('orders','42','{...}');
COMMIT;

    📚 Event sourcing & CQRS

    Event sourcing stores every change as an immutable event; current state is derived by replaying. CQRS separates the write model from read-optimised views built from events. Great for audit and replay; costs complexity and eventual consistency.

    🔬 Kafka deep dive

    Exactly-onceIdempotent producer (enable.idempotence=true) + transactions + read_committed consumers, within Kafka.
    RebalancingPartitions are reassigned when consumers join/leave; use cooperative rebalancing.
    Log compactionKeep only the latest record per key (changelog topics).
    Partition countCaps parallelism; choose by target throughput, hard to reduce later.
    Hot partitionSkewed keys overload one partition; choose better keys.
    Consumer lagGap between latest offset and committed offset; key health metric.

    📡 Operating at scale

    📊
    Observability
    Metrics, logs, distributed tracing (OpenTelemetry) with correlation ids.
    📜
    Schema evolution
    Avro/Protobuf + schema registry; backward-compatible changes.
    🔐
    Security
    mTLS, SASL/ACLs, per-service credentials.
    🧪
    Testing
    Contract tests (Pact), chaos testing, replay tests.
    🚦
    Rate & flow control
    Quotas, backpressure, autoscale on lag.

    💬 Interview practice

    Q. When would you pick Kafka over RabbitMQ?
    Pick Kafka for high-throughput event streams, replay, multiple independent consumers of the same data, event sourcing and analytics. Pick RabbitMQ for task queues, rich routing, priorities and per-message handling with low latency.
    Q. How do you keep data consistent across microservices without distributed transactions?
    Use sagas with compensating actions, the transactional outbox to publish events reliably, idempotent consumers for at-least-once delivery, and accept eventual consistency where the business allows it.
    Q. A consumer group's lag keeps growing. What do you check?
    Consumer throughput and errors, slow downstream calls, rebalance storms, partition count vs consumer count, hot partitions, poison messages blocking a partition. Then scale consumers (up to partition count), optimise processing, or add batching.
    Q. Explain the difference between at-least-once and exactly-once.
    At-least-once never loses messages but may redeliver; exactly-once means the effect happens once. True end-to-end exactly-once is achieved via idempotent producers, transactions or idempotent consumers that dedupe by id.

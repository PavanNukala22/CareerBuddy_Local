    Module 01 · Basic · System Design Fundamentals

    System Design Fundamentals

    Requirements, scaling, load balancing, availability, latency and the back-of-the-envelope maths every backend developer needs.

    🏗️ What is system design?

    System design is the work of deciding how the parts of a software system fit together so that it does the right job, for the right number of users, at an acceptable cost. Writing one function is programming. Deciding that orders go into PostgreSQL, images go into object storage, emails are sent by a background worker and everything sits behind a load balancer — that is system design.

    As a backend developer you design systems at many sizes: one endpoint, one service, or a whole platform. The same questions come up every time: What must it do? How much load? What happens when something fails? What does it cost?

    📋 Functional vs non-functional requirements

    Functional requirements say what the system does: “a user can place an order”, “a seller can upload a product image”. Non-functional requirements (NFRs, also called quality attributes) say how well it must do it: how fast, how reliable, how big.

    Quality attributePlain meaningHow it is usually stated
    ScalabilityCan it handle more load by adding resources?“Support 10× today's traffic for a sale”
    AvailabilityIs it up and answering when users need it?“99.95% of requests succeed each month”
    LatencyHow long one request takes“p99 checkout API under 300 ms”
    ThroughputHow much work per unit of time“5,000 orders per second at peak”
    ConsistencyDo all readers see the latest write?“Stock count must never be oversold”
    DurabilityOnce saved, does data survive failures?“No acknowledged order is ever lost”
    Security / complianceWho may see or change what“Card data never stored; GDPR delete in 30 days”
    Cost / maintainabilityCan the team afford and run it?“Run on a 4-person team, under $X per month”
    EXAMPLE · Requirements for a food-delivery app
    • Functional: browse restaurants, place an order, pay, track the courier, receive notifications.
    • Non-functional: 50k concurrent users at dinner peak; order placement p99 under 500 ms; payments strongly consistent; courier location may be a few seconds stale (eventual consistency is fine); 99.95% availability.
    📝
    Use percentiles, not averages, for latency. p50 is the median; p99 means 99% of requests are faster than this. An average of 80 ms can hide a p99 of 3 seconds that annoys one user in a hundred.

    📈 Scaling: vertical vs horizontal, and stateless services

    When one server is not enough, you have two options.

    Vertical scaling (scale up)

    • Buy a bigger machine: more CPU, RAM, faster disk.
    • No code changes — simplest first step.
    • Has a hard ceiling and gets expensive fast.
    • Still a single point of failure.
    • Common for databases early on.

    Horizontal scaling (scale out)

    • Add more machines and share the load.
    • Needs a load balancer and stateless app servers.
    • Practically no ceiling; cheap commodity machines.
    • Survives individual server failures.
    • Brings distributed-system problems (consistency, coordination).

    Horizontal scaling only works well if your application servers are stateless: any server can handle any request because nothing important lives in its memory between requests. Session data, uploaded files and caches move to shared stores.

    State that breaks scalingWhere to move it
    User sessions in server memorySigned tokens (JWT) or a shared session store such as Redis
    Uploaded files on local diskObject storage (S3, Azure Blob, GCS)
    In-process cache that must be sharedDistributed cache (Redis)
    Scheduled jobs running on “server 1”A scheduler with locking, or a job queue
    ⚠️
    “Sticky sessions” (the load balancer always sends a user to the same server) are a workaround, not a cure. If that server dies, the user's session dies with it, and load becomes uneven.
    Scale upMake one machine bigger (vertical).
    Scale outAdd more machines (horizontal).
    Stateless serviceKeeps no per-client data between requests; any instance can serve any request.
    Auto-scalingAutomatically adding or removing instances based on metrics such as CPU or queue length.

    ⏱️ Availability nines and latency numbers

    Availability is the fraction of time (or of requests) that the system works. It is quoted in “nines”. The table uses a 365-day year (8,760 hours) and an average month of about 30.4 days.

    99.9% (three nines)≈ 8.76 h≈ 43.8 min≈ 1.44 min
    99.95%≈ 4.38 h≈ 21.9 min≈ 43.2 s

    EXAMPLE · Dependencies multiply

    If a request needs service A (99.9%) and service B (99.9%) in series, the best you can expect is 0.999 × 0.999 ≈ 99.8%. If you run two independent copies of a component in parallel and need only one, unavailability multiplies instead: 1 − (0.001 × 0.001) = 99.9999%. Redundancy raises availability; long chains of synchronous calls lower it.

    Lessons: memory is roughly 1,000× faster than an SSD random read; a network hop inside a data centre costs about half a millisecond; crossing an ocean costs tens to hundreds of milliseconds. So cache hot data, avoid chatty service-to-service calls and put content near users.

    🧮 Back-of-the-envelope estimation: a worked example

    Estimation turns vague words like “big” into numbers that drive decisions: one database or many? Do we need a cache? Round aggressively — you want the right order of magnitude, not exact figures.

    Handy approximationValue
    Seconds in a day86,400 ≈ 105
    Seconds in a month≈ 2.6 million
    1 million requests per day≈ 12 per second
    1 KB × 1 million1 GB
    1 KB × 1 billion1 TB
    Peak trafficOften 2–5× the average
    EXAMPLE · A URL shortener
    1. Writes: 100 million new short links per month ÷ 2.6 million s ≈ 40 writes/s.
    2. Reads: read-heavy, say 100 reads per write → ≈ 4,000 reads/s on average; plan for ~10,000/s at peak.
    3. Storage: ~500 bytes per record (URL, code, owner, timestamps). Keep 5 years: 100 M × 12 × 5 = 6 billion records × 500 B ≈ 3 TB.
    4. Bandwidth: 4,000 reads/s × 500 B ≈ 2 MB/s — tiny.
    5. Cache: ≈ 345 million reads per day; caching the hottest 20% of a day's lookups ≈ 70 M × 500 B ≈ 35 GB — fits in a small Redis cluster.
    6. Conclusion: writes are modest; reads dominate, so a cache in front of a replicated key-value or SQL store is enough. No exotic tech needed.
    💡
    Say your assumptions out loud and write them down. If the interviewer changes one (“make it 1 billion links a month”), you can redo the maths in seconds.

    Monoliths & Microservices

    How to structure a backend, where to draw service boundaries, how services talk, and how to migrate safely.

    🏛️ Monolith, modular monolith and microservices

    A monolith is one deployable application containing all features, usually with one database. Microservices split the system into small services, each owning one business capability and its own data, deployed independently. In between sits the modular monolith: one deployable, but with strict internal module boundaries.

    MonolithModular monolithMicroservices
    DeployablesOneOneMany (one per service)
    DatabaseOne shared schemaOne DB, schema/tables owned per moduleOne per service
    Module callsIn-process function callsIn-process through public module APIsNetwork calls (HTTP, gRPC, messages)
    TransactionsSimple ACID transactionsSimple ACID transactionsSagas, eventual consistency
    ScalingScale the whole appScale the whole appScale each service separately
    Team fitOne small teamOne to a few teamsMany autonomous teams
    Operational costLowLowHigh: CI/CD, observability, platform
    Main riskBecomes a “big ball of mud”Boundaries erode without disciplineA “distributed monolith”
    📝
    A distributed monolith is the worst of both worlds: many services that must be deployed together, share a database or call each other synchronously in long chains. You pay the network costs of microservices without gaining independence.

    ✂️ When to split — and when not to

    Microservices are an organisational and scaling tool, not a goal. Start with a well-structured monolith unless you have a clear reason.

    Good reasons to split

    • Several teams keep blocking each other in one codebase and release train.
    • One part has very different load (e.g. search or image processing) and must scale alone.
    • One part needs a different technology or runtime.
    • Different reliability or security needs (e.g. isolate payments for PCI DSS).
    • Release cadence: one area changes daily, another quarterly.

    Bad reasons to split

    • “Netflix does it.”
    • A team of three people with one product.
    • The domain is still unclear and boundaries change monthly.
    • No automated tests, CI/CD, monitoring or on-call yet.
    • To fix messy code — you will get messy code spread over a network.
    💡
    A practical path: build a modular monolith first, enforce module boundaries (no reaching into another module's tables), and extract a module into a service only when one of the good reasons appears. The boundaries are then already proven.

    🗺️ Service boundaries: DDD and database per service

    Domain-driven design (DDD) gives the best tool for drawing boundaries: the bounded context. Inside a bounded context, words have one precise meaning and one model. The same real-world word can mean different things in different contexts.

    EXAMPLE · “Product” means different things
    Bounded contextWhat “product” means hereData it owns
    CatalogueSomething we describe and showTitle, description, images, categories
    PricingSomething with a price and discountsPrice lists, promotions, tax class
    InventorySomething we count in a warehouseSKU, stock level, reservations
    ShippingSomething with weight and sizeDimensions, weight, hazardous flag

    Each bounded context is a candidate service. Good boundaries have high cohesion (things that change together live together) and low coupling (a change in one service rarely forces a change in another).

    Database per service

    Each service owns its data and is the only one that reads or writes its tables. Others get data through its API or through events it publishes. This is what makes independent deployment possible: you can change your schema without breaking anyone.

    NeedHow to solve it without sharing a database
    Order service needs the customer's nameCopy the needed fields from a CustomerUpdated event into a local read model
    Report across orders and paymentsStream events into a data warehouse or reporting store
    Update orders and stock “together”Use a saga with compensating actions (see Module 03)
    ⚠️
    A shared database between services is the most common cause of a distributed monolith. One schema change can break five teams at once.

    Ubiquitous languageThe shared vocabulary of developers and domain experts within one context.

    📡 Communication styles: synchronous vs asynchronous

    Services talk in two broad ways. Synchronous: the caller sends a request and waits for the answer (REST over HTTP, gRPC). Asynchronous: the sender publishes a message to a broker and carries on; consumers process it later (Kafka, RabbitMQ, SQS).

    REST (HTTP/JSON)gRPCAsync messaging
    StyleRequest/responseRequest/response and streamingFire-and-forget events or commands
    FormatJSON textProtocol Buffers (binary) over HTTP/2Any (JSON, Avro, Protobuf)
    Coupling in timeBoth must be upBoth must be upConsumer can be down; broker buffers
    Best forPublic APIs, simple CRUDFast internal calls, strict contractsWorkflows, notifications, fan-out, spikes
    Main painChatty calls add latencyHarder to debug by hand, browser needs a proxyEventual consistency, duplicates, ordering

    💡
    Rule of thumb: use a synchronous call when the user is waiting for the answer right now (e.g. “is this coupon valid?”). Use asynchronous messaging when something only needs to happen eventually (send the email, update analytics, rebuild the search index).

    Clients should not need to know about 30 internal services. An API gateway is a single entry point that routes requests and handles cross-cutting concerns.

    🔭 Observability: logs, metrics, traces

    In a monolith, one stack trace shows what happened. In microservices, one user click may touch ten services. Observability is the ability to understand what is happening inside from the data the system emits.

    📜
    Logs
    Timestamped events. Use structured JSON with fields like service, level, trace_id.
    📊
    Metrics
    Numbers over time: request rate, error rate, latency percentiles, queue lag. Cheap to store and alert on.
    🧵
    Traces
    One request's path across services, made of spans with timings. Shows where the time went.

    A correlation ID (or trace ID) is generated at the edge and passed along every call and message, so you can search all logs for one request. The W3C standard header is traceparent. OpenTelemetry is the vendor-neutral standard and SDKs for producing logs, metrics and traces, which you export to tools such as Jaeger, Grafana Tempo, Prometheus or a commercial backend.

    🌿 Conway's law and the strangler fig migration

    Conway's law: organisations design systems that mirror their communication structure. Four teams tend to produce four big components. Teams therefore use the inverse Conway manoeuvre: shape teams around the architecture you want, e.g. one team owns checkout end to end.

    To move from a monolith to services, avoid the “big-bang rewrite”. The strangler fig pattern (named after a vine that slowly grows around a tree) replaces the monolith one piece at a time behind a routing layer.

    Strangler fig: grow the new system around the old one, piece by piece
    EXAMPLE · Extracting notifications first
    1. Put an API gateway in front of the monolith; all traffic still goes to the monolith.
    2. Pick a low-risk, well-bounded capability: sending emails and SMS.
    3. The monolith publishes an OrderPlaced event; the new notification service consumes it and sends the email.
    4. Run both in parallel briefly (old path behind a feature flag), compare results, then switch off the old code.
    5. Move on to the next capability, e.g. search, then payments.
    ⚠️
    Extract the data with the code. A new service that still reads the monolith's tables directly is not independent.

    Resilience & Distributed Data

    Design for failure: timeouts, retries, circuit breakers, CAP and PACELC, sagas, the outbox pattern and idempotency.

    🌩️ The fallacies of distributed computing

    Once your system is more than one process, every call can fail in new ways. The classic eight fallacies of distributed computing (Peter Deutsch and colleagues at Sun) list the false assumptions developers make.

    FallacyRealityWhat you design for
    The network is reliablePackets drop, connections reset, DNS failsTimeouts, retries, idempotency
    Latency is zeroEvery hop adds ~0.5 ms+ and long tailsFewer, coarser calls; caching; async
    Bandwidth is infiniteLarge payloads saturate linksPagination, compression, small messages
    The network is secureTraffic can be read or forgedTLS/mTLS, authentication everywhere
    Topology doesn't changeInstances and IPs change constantlyService discovery, health checks
    There is one administratorMany teams, clouds and vendorsClear ownership, contracts, automation
    Transport cost is zeroSerialisation and data transfer cost CPU and moneyEfficient formats, co-location
    The network is homogeneousMixed hardware, protocols, versionsStandard protocols, backward-compatible APIs
    📝
    A remote call has three outcomes, not two: success, failure, or unknown (timeout). With a timeout you cannot tell whether the other side did the work. That single fact drives most patterns in this module.

    🔁 Timeouts, retries, exponential backoff and jitter

    Timeouts come first. A call without a timeout can hang forever and hold a thread, a connection and memory. Set connect and read timeouts on every HTTP client, database driver and broker client, and keep the total within the caller's own deadline.

    Retries fix transient failures (a dropped connection, a 503 during a deploy). Done badly, they multiply load on a struggling service. Rules:

    • Retry only transient errors (timeouts, 502/503/504, connection reset) — never 400 or 422.
    • Retry only operations that are idempotent or carry an idempotency key.
    • Use exponential backoff: wait 100 ms, 200 ms, 400 ms, 800 ms… up to a cap.
    • Add jitter (randomness) so thousands of clients do not retry at the same instant.
    • Limit attempts (e.g. 3–5) and retry at one layer only, otherwise 3 layers × 3 retries = 27 calls.
    pythonimport random, time

RETRYABLE = (TimeoutError, ConnectionError)

def call_with_retry(fn, attempts=5, base=0.1, cap=5.0):
    for attempt in range(attempts):
        try:
            return fn()
        except RETRYABLE:
            if attempt == attempts - 1:
                raise
            # "full jitter": random wait between 0 and the exponential ceiling
            ceiling = min(cap, base * 2 ** attempt)
            time.sleep(random.uniform(0, ceiling))
    ⚠️
    A retry storm happens when a service slows down, every client retries, and the extra traffic keeps it down. Backoff, jitter, retry budgets and circuit breakers together prevent it.

    🔌 Circuit breakers, bulkheads, rate limiting and graceful degradation

    A circuit breaker wraps calls to a dependency. When too many calls fail, it “opens” and fails fast for a while instead of waiting on a dead service.

    Circuit breaker states (a failed trial in half-open returns to open)
    StateBehaviourMoves to
    ClosedCalls go through; failures are counted in a sliding windowOpen when the failure rate passes a threshold (e.g. 50%)
    OpenCalls fail immediately or use a fallbackHalf-open after a wait (e.g. 30 s)
    Half-openA few trial calls are allowedClosed if they succeed; Open if they fail
    🚢
    Bulkhead
    Separate pools (threads, connections) per dependency, like watertight compartments, so one slow dependency cannot use up every thread.
    🚦
    Rate limiting
    Cap requests per client or key (token bucket, sliding window). Excess gets 429 Too Many Requests with Retry-After.
    🪫
    Load shedding
    When overloaded, reject low-priority work early (503) to keep important requests fast.
    🧯
    Graceful degradation
    Keep the core working when extras fail: show the product page without recommendations.
    EXAMPLE · Product page with a failing recommendation service

    The recommendation call has a 200 ms timeout and a circuit breaker. When the breaker is open, the page returns a cached “popular items” list. Checkout uses a separate connection pool (bulkhead), so its latency is unaffected. Users barely notice the outage.

    🩺 Health checks: liveness vs readiness

    Orchestrators and load balancers ask each instance “are you OK?”. There are two different questions:

    LivenessReadiness
    QuestionIs the process stuck or broken?Can it serve traffic right now?
    If it failsThe container is restartedThe instance is removed from the load balancer (not restarted)
    Should checkOnly the process itself (event loop alive, no deadlock)Own dependencies needed to serve: DB pool, warm cache, config loaded

    ⚠️
    Never put a shared dependency (the database, another service) into the liveness check. If the database blips, every pod fails liveness and Kubernetes restarts the whole fleet at once — turning a small outage into a big one.

    Kubernetes also has a startup probe for slow-starting apps: liveness checks wait until the startup probe has passed.

    🔺 CAP, PACELC and consistency models

    The CAP theorem: when a network Partition splits the nodes of a replicated data store, it must choose between Consistency (every read sees the latest write, or an error) and Availability (every request gets a non-error answer, possibly stale). Partitions will happen, so in practice the choice is CP or AP during a partition.

    PACELC extends this: if there is a Partition, choose A or C; Else (normal operation), choose Latency or Consistency. Even without failures, waiting for replicas to confirm costs time.

    System (typical configuration)PACELCMeaning

    🧾 Distributed transactions: why not 2PC, and how sagas work

    With a database per service, “create order, charge card, reserve stock” spans three databases. A single ACID transaction is not available.

    Two-phase commit (2PC) uses a coordinator: phase 1 asks every participant to prepare, phase 2 tells all to commit. It is usually avoided in microservices because participants hold locks while waiting, the coordinator is a blocking single point of failure, it couples services in time, and most brokers and HTTP APIs do not support it.

    A saga is a sequence of local transactions. Each step commits in its own service and triggers the next. If a step fails, previously completed steps are undone by compensating transactions.

    Happy path of an order saga
    StepLocal transactionCompensation if a later step fails
    1. OrderCreate order with status PENDINGMark order CANCELLED
    2. InventoryReserve 2 units of SKU-42Release the reservation
    3. PaymentCharge £40Refund £40 (if charged)
    4. OrderMark order CONFIRMED— (final step)

    Choreography

    • No central controller; each service reacts to events.
    • OrderCreated → inventory reserves → StockReserved → payment charges…
    • Loosely coupled and simple for 2–4 steps.
    • Hard to see the whole flow; risk of cyclic dependencies.

    Orchestration

    • A saga orchestrator tells each service what to do next.
    • State machine is explicit and easy to monitor.
    • Better for long or complex flows with many branches.
    • Orchestrator is extra code; tools: Temporal, AWS Step Functions, Camunda.
    ⚠️
    Sagas give no isolation: other requests can see the intermediate PENDING state. Design for it with semantic locks (status fields), and make every step and compensation idempotent because messages may be delivered twice.

    📤 Transactional outbox and idempotency

    The dual-write problem: a service saves an order to its database and publishes OrderPlaced to Kafka. If it crashes between the two, the database and the event stream disagree. There is no transaction spanning both.

    The transactional outbox fixes this: write the event into an outbox table in the same local transaction as the business data. A separate relay reads the outbox and publishes to the broker, retrying until it succeeds.

    sqlBEGIN;
INSERT INTO orders (id, customer_id, total_pence, status)
VALUES ('ord_8812', 'cus_17', 4000, 'PENDING');

INSERT INTO outbox (id, aggregate_id, event_type, payload, created_at)
VALUES ('evt_51a0', 'ord_8812', 'OrderPlaced',
        '{"orderId":"ord_8812","totalPence":4000}', now());
COMMIT;
-- A relay (polling, or CDC such as Debezium reading the WAL) publishes outbox rows to Kafka

    The relay may publish a row twice (it can crash after publishing but before marking the row as sent), so delivery is at-least-once. Consumers must therefore be idempotent: processing the same message twice has the same effect as once.

    Natural idempotencyUse “set status = PAID” instead of “add £40”; upserts instead of inserts

    Message Brokers & Apache Kafka

    Why services talk through brokers, and how Kafka's topics, partitions, replication, producers and consumer groups really work.

    📬 Why messaging? Queues vs publish/subscribe

    A message broker is a server that receives messages from producers and delivers them to consumers. Instead of service A calling service B directly, A hands a message to the broker and moves on.

    🔗
    Decoupling
    The producer does not know who consumes, how many consumers there are, or whether they are up right now.
    🛢️
    Buffering
    A flash sale creates 50,000 orders a minute; the broker stores them while workers process at their own pace.
    ⏩
    Asynchrony
    The user gets a fast response; slow work (emails, PDFs, analytics) happens later.
    📣
    Fan-out
    One OrderPlaced event feeds billing, shipping, email and analytics.
    Point-to-point queuePublish/subscribe (topic)
    DeliveryEach message goes to one consumer among many workersEach message goes to every subscriber
    Typical useWork distribution: “resize this image”Events: “an order was placed”
    ScalingAdd workers to drain the queue fasterAdd subscribers without touching the producer
    ExamplesRabbitMQ queue, Amazon SQSKafka topic, RabbitMQ fanout/topic exchange, SNS, Google Pub/Sub
    📝
    Kafka combines both: different consumer groups each get every message (pub/sub), while consumers inside one group share the partitions (queue-like work distribution).

    🧱 Kafka core concepts: topics, partitions, offsets, brokers

    Apache Kafka is a distributed, replicated, append-only commit log. Messages (called records) are not deleted when read; they stay for a configured retention period, so many consumers can read them at their own pace and even replay history.

    ConceptMeaning
    RecordKey (optional), value, timestamp and headers
    TopicA named stream of records, e.g. orders
    PartitionA topic is split into ordered logs; the unit of parallelism and ordering
    OffsetThe position of a record within a partition: 0, 1, 2, … (never reused)
    BrokerA Kafka server storing partitions; a cluster has several
    ProducerClient that appends records to topics
    Consumer / consumer groupClients that read records; a group shares the work
    ControllerBroker role managing cluster metadata and leader election (KRaft)

    💡
    Partitions are how Kafka scales: more partitions means more consumers can read in parallel and more brokers share the load. But you cannot easily reduce the partition count later, and adding partitions changes which partition a key maps to.

    🛡️ Replication, leaders, ISR and KRaft

    Each partition is copied to several brokers. The replication factor (RF) is the number of copies; RF = 3 is the usual production choice. One replica is the leader and handles all writes (and, by default, reads); the others are followers that copy from it.

    The in-sync replicas (ISR) are the replicas that are fully caught up with the leader. If the leader fails, a new leader is elected from the ISR, so no acknowledged data is lost.

    SettingTypical valueEffect
    replication.factor3Three copies of each partition on different brokers
    min.insync.replicas2With acks=all, a write needs at least 2 in-sync copies or it is rejected
    acks (producer)allLeader waits for all current ISR members before acknowledging
    unclean.leader.election.enablefalse (default)Never elect an out-of-sync replica (avoids silent data loss)
    EXAMPLE · RF=3, min.insync.replicas=2

    One broker dies: the ISR shrinks to 2, writes with acks=all still succeed. A second broker dies: ISR = 1 < 2, producers get NotEnoughReplicas errors — Kafka prefers refusing writes over accepting writes that could be lost. Reads keep working from the remaining leader.

    KRaft: Kafka without ZooKeeper

    Older Kafka stored cluster metadata in a separate Apache ZooKeeper ensemble. KRaft (Kafka Raft) moves metadata into Kafka itself: a small quorum of controller nodes replicates a metadata log using the Raft consensus protocol. Kafka 4.0 removed ZooKeeper support entirely — every Kafka 4.x cluster runs in KRaft mode. Benefits: one system to operate, faster controller failover and support for far more partitions.

    📝
    In KRaft, run 3 (or 5) controllers so the quorum survives 1 (or 2) controller failures. Small clusters can run combined broker+controller nodes; production usually separates them.

    📤 Producers: keys, partitioning, acks and idempotence

    The producer decides which partition each record goes to:

    • With a key: the default partitioner hashes the key (murmur2) modulo the number of partitions, so the same key always goes to the same partition — and therefore keeps its order. Use the order ID or customer ID as the key.
    • Without a key: records are spread across partitions in batches (the “sticky” partitioner), with no ordering between them.
    • Explicit partition: possible, but rarely needed.
    acksProducer waits forDurabilityLatency
    0Nothing — fire and forgetRecords can be lost silentlyLowest
    1The leader to write itLost if the leader dies before followers copy itLow
    all (or -1)All in-sync replicasSafe while at least min.insync.replicas copies existHighest

    Idempotent producer: the broker assigns the producer an ID, and every batch carries a sequence number per partition. If a retry re-sends a batch that was already written, the broker detects the duplicate and drops it. This removes duplicates caused by producer retries and keeps per-partition order.

    ✅
    Since Kafka 3.0 the Java producer defaults to acks=all and enable.idempotence=true. Check your client library's defaults — librdkafka-based clients (Python, Go, .NET) also default to acks=all, but you should set enable.idempotence=true explicitly.
    ⚠️
    Idempotence only removes duplicates from producer retries within one producer session. If your application crashes and re-sends the same business event, Kafka sees a new record.

    📥 Consumers, consumer groups, rebalancing and offset commits

    Consumers pull records from brokers. Consumers that share a group.id form a consumer group. Within a group, each partition is assigned to exactly one consumer; one consumer may own several partitions.

    Topic with 6 partitionsResult
    Group with 2 consumers3 partitions each
    Group with 6 consumers1 partition each — maximum parallelism
    Group with 8 consumers6 busy, 2 idle — extra consumers do not help
    Second group analyticsIndependently reads all 6 partitions from its own offsets

    A rebalance reassigns partitions when consumers join, leave, crash (miss heartbeats) or take too long between polls (max.poll.interval.ms). Old “eager” rebalances paused the whole group; the cooperative protocol moves only the partitions that change. Kafka 4.0 also made the new consumer rebalance protocol (KIP-848, group.protocol=consumer) generally available, where the broker computes assignments incrementally.

    Each group stores its position per partition as a committed offset in the internal __consumer_offsets topic. The committed offset is the next record to read. When the commit happens decides your delivery guarantee:

    Commit timingIf the consumer crashes mid-batchGuarantee
    Commit before processingRecords committed but not processed are skippedAt-most-once
    Commit after processingRecords processed but not committed are re-readAt-least-once (most common)
    Auto-commit every 5 s (default)Depends on the client and on when processing finishesJava: at-least-once if each batch is processed before the next poll; background committers can commit unprocessed records
    💡
    auto.offset.reset decides where a new group starts: latest (default, only new records) or earliest (from the oldest retained record).

    🗄️ Retention, log compaction, ordering and exactly-once

    Cleanup policyWhat Kafka keepsUse for
    delete (default)Records newer than retention.ms (default 7 days) and/or under retention.bytesEvent streams, logs, metrics
    compactAt least the latest record per key; older values for the same key are removed in the backgroundCurrent state: customer profiles, prices, config
    compact,deleteLatest per key, but also deleted after retentionBounded changelogs

    In a compacted topic, a record with a key and a null value is a tombstone: it tells compaction to remove that key entirely after delete.retention.ms.

    Ordering guarantees

    Kafka guarantees order only within a partition. Two records in different partitions have no defined order. So if all events for order ord_8812 must be processed in order, give them the same key. Ordering also needs the idempotent producer (or max.in.flight.requests.per.connection=1) so retries cannot reorder batches.

    Exactly-once semantics (EOS) — stated carefully

    Kafka offers exactly-once for read-process-write pipelines inside Kafka: consume from topic A, produce results to topic B, and commit the consumer offsets in one transaction. Either all of it becomes visible or none does. Pieces:

    • Idempotent producer plus a stable transactional.id.
    • beginTransaction(), produce output, sendOffsetsToTransaction(), commitTransaction().
    • Downstream consumers set isolation.level=read_committed so they never see aborted records.
    • Kafka Streams wraps all of this with processing.guarantee=exactly_once_v2.
    ⚠️
    EOS does not extend to side effects outside Kafka. If your consumer charges a card or sends an email, a crash can still cause a repeat. For external systems you need idempotent consumers (dedupe keys) — “effectively once”.

    RabbitMQ & Choosing a Broker

    Exchanges, bindings and queues, acknowledgements, dead-lettering and quorum queues — then how to choose between RabbitMQ, Kafka and cloud services.

    🐇 The AMQP model: exchanges, bindings, queues

    RabbitMQ is a message broker built around smart routing. Producers never write to a queue directly: they publish to an exchange with a routing key. The exchange uses bindings (rules) to copy the message into zero or more queues. Consumers read from queues, and each message in a queue is delivered to one consumer, which must acknowledge it.

    Producer → exchange → (bindings) → queue → consumer → acknowledgement
    ConceptMeaning
    Connection / channelOne TCP connection per app; lightweight channels multiplexed inside it
    ExchangeRouting component that receives published messages
    Routing keyA string attached by the producer, e.g. order.eu.placed
    BindingLink from exchange to queue, with a binding key or header match
    QueueOrdered buffer that stores messages until consumed and acknowledged
    Virtual host (vhost)Logical namespace for exchanges, queues and permissions
    📝
    RabbitMQ 4.x speaks AMQP 0-9-1 (the classic protocol used by most client libraries) and natively supports AMQP 1.0, plus MQTT and STOMP via plugins. Unlike Kafka, a queue message is normally removed once acknowledged — RabbitMQ is a smart broker with relatively simple consumers.

    ✅ Acknowledgements, prefetch and publisher confirms

    Reliability needs guarantees on both sides of the broker.

    MechanismSideWhat it does
    Manual ack (basic.ack)ConsumerTell RabbitMQ the message is fully processed; only then is it deleted
    Nack / reject with requeue=trueConsumerPut the message back on the queue for another attempt
    Nack / reject with requeue=falseConsumerDiscard it, or dead-letter it if the queue has a DLX
    Auto-ackConsumerMessage counts as delivered when sent — lost if the consumer crashes (at-most-once)
    Prefetch (basic.qos)ConsumerMax unacknowledged messages per consumer/channel; controls flow and fairness
    Publisher confirmsProducerBroker confirms each message once it is safely handled (written to disk / replicated)

    If a consumer's connection dies with unacknowledged messages, RabbitMQ redelivers them to another consumer with the redelivered flag set. That is at-least-once delivery, so consumers must still be idempotent.

    💡
    Prefetch sizing: prefetch_count=1 gives the fairest distribution for slow jobs (PDF rendering) but lowest throughput. Values like 10–100 suit fast handlers. Unlimited prefetch can flood one consumer's memory while others sit idle.
    ⚠️
    Requeuing a message that always fails creates a hot loop: the same poison message is redelivered thousands of times a second. Use a delivery limit and dead-lettering instead (next sections).

    💾 Durability, quorum queues and streams

    Surviving a broker restart needs both a durable queue and persistent messages:

    • Durable exchanges and queues survive restarts (durable=True).
    • Persistent messages (delivery_mode=2) are written to disk.
    • Publisher confirms tell the producer when that has happened.
    Queue typeWhat it isUse it for
    Classic queueSingle-node queue (not replicated)Temporary, non-critical or exclusive/auto-delete queues
    Quorum queueReplicated queue using the Raft consensus protocol across (typically) 3 or 5 nodesDefault choice for any message you cannot afford to lose
    StreamAppend-only replicated log; messages are not removed on consumption; consumers read from an offsetLarge fan-out, replay, very high throughput — Kafka-like use cases
    📝
    Classic mirrored queues were removed in RabbitMQ 4.0 — quorum queues are the replicated queue type. Quorum queues have a built-in delivery limit (default 20 in 4.x): after that many failed deliveries the message is dropped or dead-lettered.

    RabbitMQ Streams (x-queue-type: stream) bring a log model to RabbitMQ: many consumers can read the same messages independently, start from the beginning, a timestamp or a stored offset, and replay. Super streams partition a stream for scale, similar to Kafka partitions.

    ☠️ Dead-letter exchanges, TTL and delayed retries

    A dead-letter exchange (DLX) receives messages that a queue could not deliver successfully. A message is dead-lettered when:

    • A consumer rejects or nacks it with requeue=false.
    • Its TTL expires (per-message expiration or queue x-message-ttl).
    • The queue is over its length limit (x-max-length) with the default drop-head overflow.
    • A quorum queue's delivery limit is exceeded.

    RabbitMQ adds an x-death header recording why and from where, which helps debugging.

    EXAMPLE · Retry after 30 seconds, then park
    1. Main queue emails has x-dead-letter-exchange = emails.retry.
    2. On a transient failure the consumer nacks with requeue=false → message goes to emails.retry.30s.
    3. emails.retry.30s has x-message-ttl = 30000, no consumers, and its own DLX pointing back at the main exchange.
    4. After 30 s the message expires and returns to emails for another attempt.
    5. The consumer counts attempts (from x-death); after 5 it publishes the message to a parking-lot queue for humans to inspect.
    💡
    TTL-based retry queues work because expired messages are dead-lettered. Keep one retry queue per delay, since expiry happens at the head of a queue in order.

    📦 Delivery semantics and idempotent consumers

    Networks make true exactly-once delivery impossible in general: a consumer can finish its work and crash just before the ack. So the industry standard is at-least-once delivery + idempotent consumers = effectively-once processing.

    sql-- Idempotent consumer: record the message id in the SAME transaction as the side effect

    ☠️ Poison messages, retries and dead-letter queues

    A poison message can never be processed: malformed JSON, a reference to a deleted customer, a bug triggered by one field. If you retry it forever it blocks the queue (or a Kafka partition) and burns CPU.

    Failure typeExampleRight response
    TransientTimeout, 503 from a partner, DB failoverRetry with exponential backoff + jitter
    Permanent / poisonValidation error, unknown schema version, bugDo not retry; send to a DLQ with the error and context
    UnknownUnexpected exceptionRetry a few times, then DLQ

    In Kafka there is no built-in DLQ for plain consumers. Common pattern: on failure publish the record to orders.retry.1m, orders.retry.10m topics (consumed after a delay) and finally to orders.dlq, then commit the original offset so the partition keeps moving. Kafka Connect and Spring Kafka provide DLQ support.

    ✅
    Treat the DLQ as a work queue for humans: alert when it is non-empty, keep the original payload, headers, error message and stack trace, and build a redrive tool to send fixed messages back to the main queue.

    🚥 Ordering, partition keys and back-pressure

    Parallel consumers and retries can reorder messages. Decide where order truly matters — usually per entity (per order, per account), not globally.

    • Kafka: use the entity ID as the record key so all its events land in one partition, handled by one consumer at a time.
    • RabbitMQ: one queue with a single active consumer (x-single-active-consumer), or the consistent-hash exchange to shard by key.
    • SQS FIFO / Service Bus sessions / Pub/Sub ordering keys: order per message group or session.
    • Make handlers tolerate disorder anyway: carry a version or timestamp and ignore stale updates.
    ⚠️
    A retry that is pushed to a separate retry topic breaks per-key order: event 2 may be processed while event 1 waits in the retry topic. If strict order matters, either block that key (pause the partition) or make later events check the entity's version.

    📣 Event-driven architecture, event sourcing and CQRS

    In an event-driven architecture, services announce facts that have happened (OrderPlaced) and others react. An event is a fact in the past tense; a command (ChargePayment) is a request to one specific receiver.

    StyleWhat the event containsProsCons
    Event notificationJust the ID and type: {orderId: 42}Small, minimal couplingConsumers call back for details — extra load and latency
    Event-carried state transferThe data consumers need: items, totals, addressConsumers keep local copies; no callbacksBigger events; schema evolution matters
    Event sourcingEvery change is an event; the event log is the source of truthFull audit history, replay, temporal queriesComplex; needs snapshots, upcasting, projections

    CQRS (Command Query Responsibility Segregation) separates the write model (commands, validation, transactions) from one or more read models optimised for queries. Events update the read models asynchronously, so reads are eventually consistent.

    CQRS: commands update the write side; events build read models
    📝
    CQRS and event sourcing are often used together but are independent. You can use CQRS with an ordinary database, and most systems need neither. Use them where read and write needs truly differ or a full audit history is required.

    Use a schema registry (Avro, Protobuf or JSON Schema) and evolve events in a backward-compatible way: add optional fields, never rename or remove fields in place.

    🛒 Worked example: order placed → payment → inventory → email

    Put it all together for a shop. The checkout API must answer fast; payment, stock and email happen through events. Services react to each other's events (a choreographed saga), each step with its own compensation.

    Event flow for one order, keyed by orderId so its events stay in order
    1. API: POST /orders with an Idempotency-Key. The order service validates and, in one DB transaction, inserts the order (PENDING) and an outbox row. Responds 202 Accepted with the order ID.
    2. Outbox relay (Debezium CDC) publishes OrderPlaced to Kafka topic orders with key orderId.
    3. Payment service (group payment) charges the card, passing orderId as the provider's idempotency key, records it, and emits PaymentCaptured or PaymentFailed via its own outbox.
    4. Inventory service consumes PaymentCaptured and reserves stock idempotently (processed-messages table). If stock is gone it emits StockUnavailable; the order service then triggers a refund (compensation) and marks the order CANCELLED.
    5. Order service consumes StockReserved, marks the order CONFIRMED and emits OrderConfirmed.
    6. Notification service consumes OrderConfirmed and pushes an email job to RabbitMQ; a worker sends it with retries, a DLQ and a dedupe key of orderId + template.
    7. Observability: one trace ID flows through HTTP headers and message headers; dashboards show lag per consumer group and DLQ sizes.

    📐 Fundamentals & estimation

    What is the difference between vertical and horizontal scaling, and which would you use first?

    Vertical scaling adds CPU/RAM to one machine: no code changes, but it has a ceiling, gets expensive and remains a single point of failure. Horizontal scaling adds machines behind a load balancer: near-unlimited and fault tolerant, but the app must be stateless and you take on distributed-system issues. I scale stateless app servers horizontally from the start (it is cheap with containers) and often scale the database vertically first, adding read replicas, caching and finally sharding as needed.

    Explain L4 vs L7 load balancing.

    An L4 balancer works on TCP/UDP connections — IPs and ports — so it is very fast and usually passes TLS through. An L7 balancer understands HTTP: it terminates TLS and routes by host, path, header or cookie, and can add retries, rate limits and compression. Use L4 for raw TCP or extreme throughput, L7 for web APIs and microservice routing.

    How much downtime does 99.99% availability allow, and how do dependencies affect it?

    About 52.6 minutes per year, or about 4.4 minutes per month. Availabilities of serial dependencies multiply: a service needing three 99.99% dependencies can be at most ≈ 99.97%. Redundant parallel components improve availability because their unavailabilities multiply instead.

    Estimate the QPS and storage for 10 million daily active users each posting 2 photos a day.

    Writes: 20 million posts/day ÷ ~86,400 s ≈ 230 writes/s, peak maybe ~700/s. Storage: if a photo averages 2 MB, that is 40 TB/day, ≈ 14.6 PB/year before replication — so photos go to object storage behind a CDN, while metadata (~1 KB/post → 20 GB/day) fits a sharded database. Reads are likely 10–100× writes, so the CDN and caching matter most.

    Why do you use p99 latency instead of the average?

    Averages hide the tail. A few very slow requests barely move the mean but hurt real users — and in microservices a page that fans out to many services is likely to hit at least one slow call. p95/p99 show what the slowest users experience and are what SLOs should be written against.

    🧩 Microservices

    When would you NOT use microservices?

    When the team is small, the domain is still changing, or there is no mature CI/CD, monitoring and on-call. Microservices add network failures, eventual consistency, distributed debugging and operational cost. A modular monolith gives clean boundaries without those costs, and modules can be extracted later when team or scaling needs justify it.

    How do you decide service boundaries?

    Use domain-driven design: find bounded contexts where terms have one meaning and data changes together (catalogue, pricing, inventory, ordering). Aim for high cohesion and low coupling, align services with teams (Conway's law), and give each service its own data. If two services always change and deploy together, the boundary is probably wrong.

    Why database per service, and how do you query across services?

    Owning its data lets a service change its schema and deploy independently, and prevents hidden coupling through shared tables. For cross-service queries: API composition (call several services and join), local read models built from events (CQRS), or streaming data into a warehouse for reporting.

    What does an API gateway do, and what is a BFF?

    A gateway is the single entry point: routing, TLS termination, authentication, rate limiting, request IDs, sometimes caching and response aggregation. A Backend for Frontend is a gateway layer specific to one client (mobile, web) that shapes and aggregates data for it, owned by that client's team. Keep business logic out of gateways.

    How do you debug a slow request that crosses eight services?

    Distributed tracing: the edge creates a trace ID (W3C traceparent), every service propagates it over HTTP and message headers and emits spans via OpenTelemetry. The trace view shows which span took the time. Then use the trace ID to find structured logs for that request and check the service's RED metrics for wider patterns.

    🛡️ Resilience & distributed data

    How do you design retries safely?

    Only retry transient errors, only for idempotent operations (or with idempotency keys), with a timeout on every attempt, exponential backoff with jitter, a small attempt limit and retries at one layer only. Combine with a circuit breaker and retry budget so retries cannot amplify an outage.

    Explain the circuit breaker pattern.

    The breaker wraps calls to a dependency. Closed: calls pass and failures are counted. If the failure rate exceeds a threshold it opens: calls fail fast or use a fallback, giving the dependency time to recover and freeing the caller's threads. After a wait it goes half-open and lets a few trial calls through: success closes it, failure reopens it.

    Explain CAP and PACELC with an example.

    CAP: during a network partition a replicated store must either reject some requests to stay consistent (CP) or answer with possibly stale data (AP). PACELC adds that even without partitions you trade latency for consistency. Cassandra with default settings is PA/EL; Spanner is PC/EC. I choose per data type: stock reservations and payments need consistency; likes and view counts can be eventual.

    Why avoid two-phase commit in microservices? What do you use instead?

    2PC holds locks across services while a coordinator waits, blocks if the coordinator fails, couples services in time and is unsupported by most brokers and HTTP APIs. Instead use a saga: local transactions per service with compensating actions, via choreography (events) or orchestration (a coordinator such as Temporal). Combine with the outbox pattern and idempotent steps.

    What is the dual-write problem and how does the outbox pattern solve it?

    Writing to the database and publishing to a broker are two separate operations; a crash between them leaves them inconsistent. The outbox writes the event into an outbox table in the same local transaction as the business change. A relay (polling or CDC like Debezium) publishes it afterwards, at-least-once, so consumers must be idempotent.

    📜 Kafka

    How does Kafka guarantee ordering?

    Only within a partition. Records with the same key go to the same partition (hash of key mod partition count), and one consumer per group reads a partition in order. So key by the entity whose order matters (orderId). Use the idempotent producer so retries cannot reorder, and remember that adding partitions remaps keys.

    Explain acks, replication factor and min.insync.replicas together.

    RF is how many copies of each partition exist. acks=all makes the leader wait for all in-sync replicas. min.insync.replicas sets the minimum ISR size for such writes to be accepted. With RF=3 and min ISR=2, one broker can fail and writes continue with no acknowledged data lost; if two fail, producers get errors instead of silently risking loss.

    What happens during a consumer group rebalance, and how do you reduce its impact?

    Partitions are reassigned when members join, leave, crash or exceed max.poll.interval.ms. With the old eager protocol everyone stops; uncommitted work may be re-processed. Reduce impact with cooperative rebalancing or the new KIP-848 consumer protocol (GA in Kafka 4.0), static membership (group.instance.id) for rolling restarts, committing offsets on revocation and keeping processing per poll short.

    Does Kafka support exactly-once?

    Yes, for read-process-write within Kafka: idempotent producer plus transactions that atomically write output records and consumer offsets; consumers use read_committed. Kafka Streams enables it with exactly_once_v2. It does not cover external side effects such as emails or payments — those need idempotent consumers.

    What changed with KRaft and Kafka 4.0?

    KRaft replaces ZooKeeper: a quorum of controller nodes stores cluster metadata in an internal Raft-replicated log. Kafka 4.0 removed ZooKeeper mode completely, so clusters must migrate to KRaft (via a 3.x bridge release) before upgrading. Benefits: one system to run, faster failover, more partitions per cluster.

    🐇 RabbitMQ

    Explain exchanges, bindings and queues.

    Producers publish to an exchange with a routing key. Bindings connect exchanges to queues with a key or header rule. The exchange type decides matching: direct (exact key), fanout (all bound queues), topic (patterns with * for one word and # for zero or more) and headers. Consumers read from queues and ack each message.

    How do you make sure RabbitMQ does not lose messages?

    Durable quorum queues; persistent messages; publisher confirms on the producer (and mandatory or an alternate exchange for unroutable messages); manual acks after processing on the consumer; a DLX for failures; a cluster of 3+ nodes; alerts on queue depth and unacked counts. Consumers stay idempotent because redelivery is possible.

    What is prefetch and how do you choose it?

    basic.qos limits how many unacknowledged messages a consumer holds. Low values (1) give fair dispatch for slow, uneven jobs; higher values (10–100+) raise throughput for fast handlers. Too high and one consumer hoards messages and memory; too low and consumers wait on network round trips. Measure and tune.

    How do you implement delayed retries in RabbitMQ?

    Nack with requeue=false into a retry queue that has a message TTL and a dead-letter exchange pointing back at the main exchange. When the TTL expires the message returns for another attempt. Use one queue per delay step (e.g. 10 s, 1 min, 10 min), count attempts via x-death, and park the message in a final DLQ after the limit.

    Kafka or RabbitMQ — how do you choose?

    Kafka for a retained, replayable event log: high throughput, many independent consumer groups, per-key ordering, stream processing, CDC. RabbitMQ for task queues and routing: per-message ack, TTL, priorities, DLX, flexible exchanges, competing consumers without partition limits. Also weigh what the team can operate and managed offerings; many companies run both.

    ⚙️ Async processing & design scenarios

    Design a URL shortener.

    API: POST /links → short code; GET /{code} → 301/302 redirect. Scale: e.g. 100 M links/month ≈ 40 writes/s, ~4,000 reads/s, ~3 TB over 5 years. Codes: 7 Base62 characters give 627 ≈ 3.5 trillion codes; generate from a distributed ID (counter ranges per server or Snowflake-style IDs) encoded in Base62, or random codes with a uniqueness check. Storage: key-value or SQL keyed by code, replicated. Reads: Redis cache plus CDN-level caching of redirects. Extras: click analytics published asynchronously to Kafka, rate limiting on creation, malicious-URL scanning. Use 302 if you need every click counted, 301 if caching matters more.

    Design a notification system (email, SMS, push).

    Producers (order, marketing) publish notification requests to a broker. A notification service validates, looks up user preferences and opt-outs, renders templates, and routes to per-channel queues (email, SMS, push) so a slow SMS provider cannot block email. Channel workers call providers with retries, backoff and circuit breakers; failures go to DLQs. Dedupe keys prevent double sends; per-user rate limits and quiet hours prevent spam; priority queues keep OTPs ahead of newsletters. Track delivery status via provider webhooks and expose metrics on lag, success rate and cost.

    How do you handle a request that takes five minutes?

    Accept it and process it asynchronously: return 202 Accepted with a job ID and a Location status URL, enqueue a job (with an idempotency key), let workers process it, and expose status by polling, webhook or WebSocket. Store results in object storage and give a download link. Make the job resumable and idempotent.

    A consumer group's lag keeps growing. How do you investigate?

    Check if it is all partitions (consumers too slow or too few) or one (hot key or a poison message stuck in retries). Look at processing time per message, downstream latency, error and retry rates, rebalancing frequency and recent deploys. Fixes: scale consumers up to the partition count, add partitions (mind key ordering), batch work, move slow side effects to another queue, fix the hot key or send the poison message to a DLQ.

    How do you guarantee an event is processed only once?

    You make the effect happen once rather than the delivery: at-least-once delivery (commit/ack after processing) plus idempotent handlers — a processed-messages table with a unique key in the same transaction as the side effect, idempotency keys for external APIs, upserts and version checks. Inside Kafka-only pipelines, Kafka transactions give exactly-once.

    Module 01 · Foundations

    What is an API? What is API Architecture?

    Start from zero: what an API is, how clients and servers talk, the main API styles, and how to choose between them.

    🧭 What is an API?

    API stands for Application Programming Interface. It is a contract that defines how one piece of software can ask another piece of software to do something — and what it will get back. The caller does not need to know how the work is done internally.

    🍽️ Restaurant analogy

    You (client) read the menu (API docs), tell the waiter (API) your order, the kitchen (server) cooks, and the waiter brings the dish back. You never enter the kitchen.

    📱 Real example

    A weather app sends GET /forecast?city=Guntur to a weather server and receives JSON with temperature and rain chances.

    Every API interaction has the same ingredients:

    📨
    Request
    What the client asks: an action, a target, optional data.
    📬
    Response
    What the server returns: a result, data or an error.
    📜
    Contract
    The agreed shape of requests and responses (docs / schema).
    🚚
    Transport
    The network protocol carrying the messages: HTTP, HTTP/2, TCP.
    🧱
    Format
    How data is encoded: JSON, Protobuf, XML.

    🏛️ What is API Architecture?

    API architecture is the set of design decisions that determines how an API is built and consumed: the communication style, resource/operation model, data format, security, versioning, error handling and scaling approach. Two APIs can do the same job but be architected very differently.

    The decisions every API architect makes

    DecisionQuestion to answerExamples
    StyleHow will clients talk to the server?REST, GraphQL, gRPC, WebSocket
    ContractHow is the interface described?OpenAPI, GraphQL SDL, .proto, AsyncAPI
    TransportWhich protocol carries messages?HTTP/1.1, HTTP/2, WebSocket frames
    FormatHow is data encoded?JSON, Protobuf, XML, MessagePack
    SecurityWho is calling and what may they do?API keys, JWT, OAuth 2.0, mTLS
    EvolutionHow will it change without breaking clients?Versioning, deprecation, additive changes
    OperationsHow is it protected and observed?Rate limits, caching, logging, tracing
    💡
    Remember: there is no “best” API style. Each is a tool that fits certain problems. A backend developer’s job is to pick — and often combine — them wisely.

    Module 02 · RESTful APIs

    RESTful APIs — From Basics to Expert

    Resources, HTTP methods, status codes, design rules, pagination, caching, versioning, security and advanced patterns.

    🌐 What is REST?

    REST (Representational State Transfer) is an architectural style defined by Roy Fielding (2000). Data and functionality are modelled as resources (nouns) identified by URLs. Clients use standard HTTP methods to act on them and exchange representations (usually JSON).

    httpGET    /books          -> list books
GET    /books/17       -> get book 17
POST   /books          -> create a book
PUT    /books/17       -> replace book 17
PATCH  /books/17       -> update some fields of book 17
DELETE /books/17       -> delete book 17
    💡
    A REST API follows REST principles. “RESTful” APIs that follow most (not all) rules are common and fine in practice.

    The 6 REST constraints

    🧍
    Client–Server
    UI and data storage are separated and evolve independently.
    🚫
    Stateless
    Each request contains everything needed; no server-side session.
    🗃️
    Cacheable
    Responses declare whether they can be cached.
    🧩
    Uniform Interface
    Resources, standard methods, self-descriptive messages, HATEOAS.
    🧅
    Layered System
    Proxies, gateways, load balancers can sit between client and server.
    📦
    Code on Demand
    Optional: server can send executable code (e.g. JavaScript).

    🧭 Resource Design & URL Naming

    ✅ Good

    • GET /users
    • GET /users/5/orders
    • POST /orders
    • GET /orders?status=paid&sort=-date

    ❌ Avoid

    • GET /getAllUsers (verb in URL)
    • POST /deleteUser/5
    • GET /User_Orders (inconsistent case)
    • /users/5/orders/9/items/3/tax/2 (too deep)
    • Use plural nouns for collections: /products.
    • Use lowercase and hyphens: /order-items.
    • Express relationships by nesting one or two levels: /customers/7/orders.
    • For actions that are not CRUD, model them as sub-resources: POST /orders/9001/cancellation or POST /payments/55/refunds.
    • Identify resources by IDs in the path; use the query string for filter, sort, search, pagination.
    📝
    Collection vs item: /orders is a collection; /orders/9001 is one item. Same noun, different level.

    🔧 Methods, Idempotency & Status Codes in Practice

    Which status code?

    SituationCode
    Successful read / update returning body200 OK
    Resource created (send Location header)201 Created
    Accepted for background processing202 Accepted
    Success, nothing to return (delete / update)204 No Content
    Malformed JSON, bad parameter400 Bad Request
    Missing or invalid credentials401 Unauthorized
    Authenticated but not allowed403 Forbidden
    Resource does not exist404 Not Found
    Method not supported on this URL405 Method Not Allowed
    Conflict (duplicate, version mismatch)409 Conflict
    Valid JSON but fails business validation422 Unprocessable Content
    Too many requests429 Too Many Requests
    Unexpected server bug500 Internal Server Error
    Upstream service failed / down / slow502 / 503 / 504

    PUT vs PATCH

    httpPUT /users/5                    PATCH /users/5
{ "name":"Asha",                { "phone":"98480-00000" }
  "email":"a@x.com",            -> only phone changes
  "phone":"98480-00000" }
-> whole record replaced

    PUT is idempotent (same body → same state). PATCH can be, but is not guaranteed — e.g. “increment counter” is not idempotent.

    🧪 Hands-on: Build a REST API (Node.js + Express)

    A complete in-memory Books API with validation and correct status codes.

    javascriptconst express = require('express');
const app = express();
app.use(express.json());

let books = [{ id: 1, title: 'Clean Code', author: 'Robert Martin' }];
let nextId = 2;

// LIST with filtering + pagination
app.get('/api/v1/books', (req, res) => {
  const { author, page = 1, limit = 10 } = req.query;
  let result = author ? books.filter(b => b.author === author) : books;
  const start = (page - 1) * limit;
  res.json({ data: result.slice(start, start + +limit), page: +page, total: result.length });
});

// READ one
app.get('/api/v1/books/:id', (req, res) => {
  const book = books.find(b => b.id === +req.params.id);
  if (!book) return res.status(404).json({ error: 'Book not found' });
  res.json(book);
});

// CREATE
app.post('/api/v1/books', (req, res) => {
  const { title, author } = req.body;
  if (!title || !author)
    return res.status(422).json({ error: 'title and author are required' });
  const book = { id: nextId++, title, author };
  books.push(book);
  res.status(201).location('/api/v1/books/' + book.id).json(book);
});

// PATCH
app.patch('/api/v1/books/:id', (req, res) => {
  const book = books.find(b => b.id === +req.params.id);
  if (!book) return res.status(404).json({ error: 'Book not found' });
  Object.assign(book, req.body);
  res.json(book);
});

// DELETE
app.delete('/api/v1/books/:id', (req, res) => {
  books = books.filter(b => b.id !== +req.params.id);
  res.status(204).end();
});

app.listen(3000, () => console.log('API on :3000'));

    Test it with curl

    bashcurl -i localhost:3000/api/v1/books
curl -i -X POST localhost:3000/api/v1/books \
     -H "Content-Type: application/json" \
     -d '{"title":"Refactoring","author":"Martin Fowler"}'
curl -i -X DELETE localhost:3000/api/v1/books/1

    Always cap limit (e.g. max 100) so a client cannot request a million rows.

    🚨 Error Handling

    Return a consistent error body so clients can handle problems programmatically. The standard is RFC 9457 Problem Details (application/problem+json).

    jsonHTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.shop.com/errors/validation",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/api/v1/orders",
  "errors": [
    { "field": "quantity", "message": "must be >= 1" }
  ],
  "traceId": "7f3a9c2e"
}
    ⚠️
    Never leak stack traces, SQL or internal paths in error responses. Log details server-side and give the client a traceId to quote to support.

    🗃️ Caching & Conditional Requests

    HeaderPurpose
    Cache-Control: max-age=60Clients/CDNs may reuse the response for 60 s
    Cache-Control: no-storeNever cache (sensitive data)
    ETag: "v7"Version fingerprint of the representation
    If-None-Match: "v7"Client asks “send only if changed” → server replies 304 Not Modified
    Last-Modified / If-Modified-SinceTime-based variant of the same idea
    httpGET /books/17           ->  200 OK   ETag: "v7"   {...body...}
GET /books/17
If-None-Match: "v7"     ->  304 Not Modified   (no body, saves bandwidth)

    Only GET (and HEAD) responses are normally cached.

    🔢 Versioning & Evolution

    ApproachExampleNote
    URL path/api/v2/ordersMost common, very visible
    HeaderAccept: application/vnd.shop.v2+jsonClean URLs, harder to test in browser
    Query/orders?version=2Simple but easy to forget
    • Additive changes are non-breaking: new optional fields, new endpoints.
    • Breaking changes: removing/renaming fields, changing types, making optional fields required, changing meaning.
    • Deprecate with notice: Deprecation and Sunset response headers + docs + a migration period.
    • Clients should ignore unknown fields (“tolerant reader”).

    🔐 Security Basics for REST

    • HTTPS everywhere — never plain HTTP.
    • Authentication: API keys (simple, identify an app), Bearer JWT (identify a user), OAuth 2.0 / OIDC (delegated access).
    • Authorization: check every request — role plus ownership (prevents BOLA/IDOR: user A reading /orders/9001 that belongs to user B).
    • Validate input (type, length, range) and use parameterised queries.
    • Rate limit and return 429 with Retry-After.
    • CORS: allow only trusted origins; do not use * with credentials.
    • Do not put secrets or tokens in URLs (they land in logs).
    httpGET /api/v1/orders/9001
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0

    🏆 Expert Topics

    Idempotency keys (safe retries for POST)

    httpPOST /payments
Idempotency-Key: 6a1f-92bd-44c1
{ "orderId": 9001, "amount": 1998 }
-> server stores the key + result; a retry with the same key returns the SAME response
   instead of charging twice.

    Optimistic concurrency with ETag

    httpGET /documents/3                -> ETag: "v5"
PUT /documents/3
If-Match: "v5"                  -> 200 OK (updated, new ETag "v6")
PUT /documents/3  If-Match: "v5" -> 412 Precondition Failed (someone else changed it)

    Long-running operations

    httpPOST /reports                 -> 202 Accepted   Location: /jobs/88
GET  /jobs/88                 -> 200 {"status":"RUNNING","progress":40}
GET  /jobs/88                 -> 303 See Other  Location: /reports/512

    More expert ideas

    HATEOAS (Richardson Level 3)
    Responses include links telling the client what it can do next: "_links": {"cancel": "/orders/9001/cancellation"}. It decouples clients from hard-coded URLs but is rarely fully used.
    Richardson Maturity Model
    Level 0: single endpoint (RPC over HTTP) · Level 1: resources · Level 2: HTTP verbs + status codes (where most “REST” APIs live) · Level 3: hypermedia controls.
    JSON Patch vs Merge Patch
    application/merge-patch+json sends a partial object (null removes a field). application/json-patch+json sends operations: [{"op":"replace","path":"/phone","value":"..."}] — precise but more complex.
    Contract-first with OpenAPI
    Write an openapi.yaml first; generate docs (Swagger UI), mock servers, client SDKs and request validation from it. See Module 06.
    Bulk & batch operations
    Prefer POST /orders/batch returning per-item results (207 Multi-Status style) over hundreds of separate calls; define partial-failure behaviour clearly.
    Webhooks
    Let clients register a URL; send signed (HMAC) events such as order.paid with retries and an event ID so receivers can deduplicate.

    ✅ Best Practices & Anti-patterns

    ✅ Do

    • Nouns, plurals, consistent naming
    • Correct status codes
    • Paginate every list
    • Version from day one
    • Document with OpenAPI
    • Use idempotency keys for payments

    ❌ Don’t

    • Return 200 with {"error":..}
    • Use GET to change data
    • Expose database IDs/structure blindly
    • Return huge unbounded lists
    • Break clients silently
    • Skip auth checks on “internal” endpoints

    Module 03 · GraphQL

    GraphQL — From Basics to Expert

    A query language for APIs: schema, queries, mutations, subscriptions, resolvers, performance, security and federation.

    🕸️ What is GraphQL?

    GraphQL is a query language and runtime for APIs, created at Facebook (2012, open-sourced 2015). Instead of many fixed endpoints, a server exposes one endpoint (usually POST /graphql) and a strongly-typed schema. The client sends a query describing exactly the data it wants, and receives exactly that shape.

    😩 Problems with REST it solves

    Over-fetching: /users/5 returns 40 fields, the screen needs 2. Under-fetching: a profile screen needs 3 calls (user, posts, followers).

    😀 GraphQL approach

    One request, ask for user { name posts { title } followers { count } } and receive only that.

    graphqlquery {
  user(id: 5) {
    name
    posts(first: 2) { title }
  }
}
    json{ "data": { "user": { "name": "Asha", "posts": [ { "title": "Hello" }, { "title": "APIs 101" } ] } } }
    💡
    GraphQL is not a database and not tied to any one. It is a layer between clients and your data sources (databases, REST APIs, microservices).

    🗂️ Types of Operations & Core Concepts

    OperationPurposeREST analogy
    QueryRead dataGET
    MutationCreate / update / delete dataPOST / PUT / PATCH / DELETE
    SubscriptionReceive live updates pushed by the serverWebSocket / SSE
    SchemaThe full description of types and operations the API supports. Single source of truth.
    TypeObject shape like User with typed fields.
    FieldA piece of data on a type, e.g. name.
    ResolverA function that fetches the value of one field.
    ArgumentInput to a field: user(id: 5).
    VariableParameter passed separately from the query text ($id).
    IntrospectionClients can ask the schema about itself — powers GraphiQL, docs and codegen.
    One query is split across resolvers that fetch from different sources and are merged into one response.

    📐 Schema Definition Language (SDL)

    The schema is written in SDL. ! means non-null, [Post!]! means a non-null list of non-null posts.

    graphqlscalar DateTime

enum Role { USER ADMIN }

interface Node { id: ID! }

type User implements Node {
  id: ID!
  name: String!
  email: String
  role: Role!
  posts(first: Int = 10, after: String): [Post!]!
}

type Post implements Node {
  id: ID!
  title: String!
  body: String
  author: User!
  createdAt: DateTime!
}

union SearchResult = User | Post

input CreatePostInput {
  title: String!
  body: String
}

type Query {
  user(id: ID!): User
  posts(first: Int, after: String): [Post!]!
  search(text: String!): [SearchResult!]!
}

type Mutation {
  createPost(input: CreatePostInput!): Post!
  deletePost(id: ID!): Boolean!
}

type Subscription {
  postAdded: Post!
}
    ElementMeaning
    ScalarsInt, Float, String, Boolean, ID + custom (DateTime)
    Object typeNamed set of fields
    EnumFixed set of allowed values
    InterfaceShared fields several types must implement
    UnionField can return one of several types
    Input typeStructured argument for mutations (cannot be used as output)

    🔎 Writing Queries

    Variables, aliases, fragments, directives

    graphqlquery GetUser($id: ID!, $withPosts: Boolean = false) {
  me: user(id: $id) {            # alias "me"
    ...UserBasics                # fragment reuse
    posts(first: 3) @include(if: $withPosts) {
      title
    }
  }
  other: user(id: 99) { ...UserBasics }
}

fragment UserBasics on User {
  id
  name
  role
}
    json// variables sent separately (safe + cacheable)
{ "id": "5", "withPosts": true }

    Sending a query over HTTP

    bashcurl -X POST http://localhost:4000/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"query($id:ID!){ user(id:$id){ name } }","variables":{"id":"5"}}'
    Inline fragments for unions/interfaces
    search(text:"api"){ ... on User { name } ... on Post { title } }; use __typename to know which type came back.
    @skip / @include
    Built-in directives to conditionally include fields based on variables.
    Introspection query
    { __schema { types { name } } } lists every type. Often disabled in production for private APIs.

    ✏️ Mutations & Subscriptions

    Mutation

    graphqlmutation CreatePost($input: CreatePostInput!) {
  createPost(input: $input) {
    id
    title
    author { name }     # ask for the result you need right away
  }
}

    Convention: one input argument, return the changed object (or a payload type with errors). Top-level mutation fields run serially; query fields may run in parallel.

    Subscription

    graphqlsubscription {
  postAdded { id title author { name } }
}

    Subscriptions run over a persistent connection — usually WebSocket using the graphql-ws protocol (see Module 05) — and the server pushes a message each time the event fires.

    🛠️ Hands-on: Build a GraphQL Server (Apollo Server)

    Install: npm i @apollo/server graphql

    javascriptimport { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';

const typeDefs = `#graphql
  type Book { id: ID!  title: String!  author: Author! }
  type Author { id: ID!  name: String!  books: [Book!]! }
  type Query { books: [Book!]!  book(id: ID!): Book }
  type Mutation { addBook(title: String!, authorId: ID!): Book! }
`;

const authors = [{ id: '1', name: 'Robert Martin' }];
const books = [{ id: '1', title: 'Clean Code', authorId: '1' }];

const resolvers = {
  Query: {
    books: () => books,
    book: (_, { id }) => books.find(b => b.id === id),
  },
  Mutation: {
    addBook: (_, { title, authorId }) => {
      if (!authors.find(a => a.id === authorId))
        throw new Error('Unknown author');
      const book = { id: String(books.length + 1), title, authorId };
      books.push(book);
      return book;
    },
  },
  Book:   { author: (b) => authors.find(a => a.id === b.authorId) },
  Author: { books:  (a) => books.filter(b => b.authorId === a.id) },
};

const server = new ApolloServer({ typeDefs, resolvers });
const { url } = await startStandaloneServer(server, { listen: { port: 4000 } });
console.log('GraphQL ready at', url);
    💡
    Open the printed URL in a browser: Apollo’s sandbox lets you explore the schema and run queries interactively.

    🚨 Error Handling

    GraphQL almost always returns HTTP 200. Problems appear in an errors array and data may be partial.

    json{
  "data": { "user": null },
  "errors": [{
    "message": "User not found",
    "path": ["user"],
    "extensions": { "code": "NOT_FOUND" }
  }]
}
    • Use extensions.code (UNAUTHENTICATED, FORBIDDEN, BAD_USER_INPUT) for machine-readable errors.
    • For expected business errors, model them in the schema: union CreateUserResult = User | EmailTaken | InvalidInput.
    • Return 400 for invalid queries and 401 for missing auth at the HTTP layer if you wish.

    🚀 Performance: The N+1 Problem & DataLoader

    Fetching 50 posts and then each post’s author triggers 1 + 50 database calls — the N+1 problem.

    textQuery: posts { title author { name } }
 SELECT * FROM posts LIMIT 50;           -- 1 query
 SELECT * FROM users WHERE id = 1;       -- 50 more queries
 SELECT * FROM users WHERE id = 2;       -- (one per post)
 ...

    DataLoader batches and caches lookups within one request:

    javascriptimport DataLoader from 'dataloader';

// create PER REQUEST (so cache is not shared between users)
const makeLoaders = () => ({
  userById: new DataLoader(async (ids) => {
    const rows = await db.query('SELECT * FROM users WHERE id = ANY($1)', [ids]);
    return ids.map(id => rows.find(r => r.id === id));   // keep input order!
  }),
});

const resolvers = {
  Post: { author: (post, _, { loaders }) => loaders.userById.load(post.authorId) },
};
// Result: 2 queries total instead of 51
    ⚠️
    The batch function must return results in the same order and length as the keys. Creating loaders globally causes data to leak between users.

    📄 Pagination (Relay Cursor Connections)

    The community standard for lists. Each item is an edge with a cursor; pageInfo tells you if more exists.

    🏆 Expert Topics

    Schema design principles
    Design around client needs, not database tables. Use specific mutation names (approveOrder, not updateOrder), nullable fields only when data may truly be missing, and evolve by adding fields and marking old ones @deprecated(reason: "...") — GraphQL needs no versioning.
    Federation (Apollo Federation / schema stitching)
    Multiple teams own sub-graphs (Users, Orders, Reviews). A gateway/router composes them into one supergraph. Types are extended across services using @key: type User @key(fields:"id") { id: ID! orders: [Order!]! }.
    Caching
    HTTP caching is harder because everything is a POST. Options: CDN with persisted queries sent as GET, client normalised caches (Apollo Client, Relay), response caching with @cacheControl, and DataLoader per-request caching.
    File uploads
    Not in the core spec. Use the multipart request spec, or (often better) get a pre-signed URL via a mutation and upload straight to object storage.
    Observability
    Name every operation (query GetUser), log operation name + duration + error counts, and trace resolvers to find slow fields (Apollo Studio, OpenTelemetry).
    Testing
    Unit-test resolvers; integration-test with server.executeOperation(); add schema checks in CI to catch breaking changes.

    Module 04 · gRPC

    gRPC — From Basics to Expert

    High-performance, contract-first RPC with Protocol Buffers over HTTP/2: all four call types, security, evolution and production patterns.

    ⚡ What is gRPC?

    gRPC (gRPC Remote Procedure Calls) is an open-source RPC framework from Google. A client calls a method on a remote server as if it were a local function. It uses Protocol Buffers (binary) for messages and HTTP/2 for transport.

    📜
    Contract-first
    You define services and messages in a .proto file.
    🏭
    Code generation
    Client and server stubs generated for 10+ languages.
    🚀
    Fast & compact
    Binary Protobuf is small; HTTP/2 multiplexes calls on one connection.
    🌊
    Streaming
    Built-in client, server and bidirectional streaming.
    ⏱️
    Deadlines
    First-class timeouts and cancellation across services.
    Client and server can be written in different languages; both are generated from the same .proto contract.
    📝
    Mostly used for service-to-service (internal) communication in microservices. Browsers cannot speak native gRPC, so public web APIs use gRPC-Web or REST/GraphQL at the edge.

    🧬 Protocol Buffers (Protobuf) Basics

    Protobuf is a language-neutral way to define structured data. Every field has a type, a name and a unique field number. The number — not the name — is what is sent on the wire.

    protobufsyntax = "proto3";
package shop.v1;

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;   // proto3: first value must be 0
  PENDING = 1;
  PAID = 2;
  SHIPPED = 3;
}

message Item {
  string sku      = 1;
  int32  quantity = 2;
  double price    = 3;
}

message Order {
  int64                id        = 1;
  string               customer  = 2;
  repeated Item        items     = 3;      // list
  OrderStatus          status    = 4;
  map<string, string>  metadata  = 5;      // key-value
  oneof payment {                          // only one can be set
    string card_token = 6;
    string upi_id     = 7;
  }
  google.protobuf.Timestamp created_at = 8;
}
    Protobuf typeMeaning
    int32, int64, uint32…Integers (varint-encoded, small numbers use fewer bytes)
    float, doubleFloating point
    bool, string, bytesBoolean, UTF-8 text, raw bytes
    repeated TList of T
    map<K,V>Dictionary
    oneofExactly one of several fields

    JSON {"id":1,"customer":"Asha"} is 27 bytes; the same Protobuf message is roughly 10 bytes.

    🔐 Security: TLS, mTLS & Auth

    • TLS encrypts the channel — mandatory outside local development.

    🏆 Expert Topics

    Schema evolution rules (never break the wire)
    Safe: add new fields with new numbers, add new RPCs, add enum values. Never: change a field’s number or type, reuse a deleted number. Mark removed ones reserved 4; reserved "old_name";. Version packages (shop.v1 → shop.v2) for real breaking changes.
    Deadlines & cancellation propagation
    Always set a deadline on the client. The deadline travels with the call; downstream services see the remaining time and stop work when it expires or the client cancels — preventing cascading slow-downs.
    Retries & hedging
    Configure a service config retry policy only for idempotent methods and status codes like UNAVAILABLE, with exponential backoff and a retry budget. Retry storms can take down a recovering service.
    Load balancing
    HTTP/2 keeps one long-lived connection, so L4 balancers send all calls from a client to one backend. Use client-side balancing (round-robin via DNS/xDS) or an L7 proxy (Envoy, NGINX) that balances per-call.
    Interceptors
    Middleware around calls: authentication, logging, metrics, tracing (OpenTelemetry), validation. Available on both client and server.
    Health checking & reflection
    Implement grpc.health.v1.Health for Kubernetes probes and load balancers; enable reflection in non-production for tools like grpcurl.
    gRPC-Web & transcoding
    Browsers cannot access HTTP/2 framing directly. gRPC-Web (via Envoy proxy) or gRPC-Gateway / Envoy transcoding exposes the same service as REST+JSON for web and third parties.
    Flow control & backpressure
    HTTP/2 flow control stops fast producers from overwhelming slow consumers in streams. Respect it: check the return value of write() and wait for drain.
    Message size
    Default max ~4 MB per message. Stream large payloads in chunks instead of raising limits.

    Module 05 · WebSockets & Real-time

    WebSockets — From Basics to Expert

    Real-time two-way communication: polling, SSE, the WebSocket protocol, building servers, scaling, security and production patterns.

    🔌 What is a WebSocket?

    WebSocket (RFC 6455) is a protocol that gives a browser and server a persistent, full-duplex connection over a single TCP socket. After an initial HTTP handshake, either side can send messages at any time, with very little overhead per message.

    📮 HTTP (request–response)

    The client must always start. To get updates it keeps asking: “anything new? anything new?” — wasteful and delayed.

    📞 WebSocket (phone call)

    Connect once, stay connected. The server pushes data the moment it exists. Ideal for chat, live scores, trading, games, collaboration.

    One HTTP handshake upgrades the connection; afterwards both sides exchange frames freely.

    🔀 Types: Ways to Get Real-time Data

    TechniqueHow it worksDirectionBest for
    Short pollingClient repeats GET every N secondsPullRare updates, simplest
    Long pollingServer holds the request until data exists, then client re-asksPull (simulated push)Fallback for old networks
    Server-Sent Events (SSE)One long HTTP response streaming text/event-streamServer → client onlyNotifications, live feeds, progress
    WebSocketUpgraded persistent TCP connectionBoth waysChat, games, collaboration, trading
    WebTransportHTTP/3 (QUIC) streams and datagramsBoth waysEmerging; low-latency media/games
    💡
    Rule of thumb: only server → client updates? Use SSE (simpler, auto-reconnect, works over plain HTTP). Need the client to send frequent messages too? Use WebSocket.

    1 · Opening handshake

    httpGET /chat HTTP/1.1

Upgrade: websocket

    The server proves it understood the upgrade by hashing the client key (Sec-WebSocket-Accept). URLs use ws:// (plain) or wss:// (TLS — always use this in production).

    2 · Frames

    OpcodeFrame typePurpose
    0x1TextUTF-8 text (usually JSON)
    0x2BinaryRaw bytes (Protobuf, images, audio)
    0x8CloseStarts graceful shutdown with a code and reason
    0x9 / 0xAPing / PongHeartbeat — check the peer is alive
    0x0ContinuationPart of a fragmented message

    Client → server frames are masked (to protect proxies). Per-message overhead is only 2–14 bytes versus hundreds of bytes of HTTP headers.

    3 · Close codes

    CodeMeaning
    1000Normal closure
    1001Going away (page closed / server restart)
    1008Policy violation (e.g. auth failed)
    1009Message too big
    1011Server error
    4000–4999Application-defined (e.g. 4001 = token expired)

    🛠️ Hands-on: Chat Server (Node.js + ws)

    Install: npm i ws. This server supports nicknames, rooms, broadcast and heartbeats.

    javascriptconst { WebSocketServer, WebSocket } = require('ws');
const wss = new WebSocketServer({ port: 8080, maxPayload: 64 * 1024 }); // limit message size

const rooms = new Map();   // roomName -> Set<ws>

function broadcast(room, payload, except) {
  for (const client of rooms.get(room) || []) {
    if (client !== except && client.readyState === WebSocket.OPEN)
      client.send(JSON.stringify(payload));
  }
}

wss.on('connection', (ws, req) => {
  ws.isAlive = true;
  ws.on('pong', () => (ws.isAlive = true));

  ws.on('message', (raw) => {
    let msg;
    try { msg = JSON.parse(raw); }
    catch { return ws.send(JSON.stringify({ type: 'error', message: 'invalid JSON' })); }

    switch (msg.type) {
      case 'join':
        ws.room = String(msg.room || 'general');
        ws.name = String(msg.name || 'guest').slice(0, 20);
        if (!rooms.has(ws.room)) rooms.set(ws.room, new Set());
        rooms.get(ws.room).add(ws);
        broadcast(ws.room, { type: 'system', text: ws.name + ' joined' });
        break;
      case 'chat':
        if (!ws.room) return;
        broadcast(ws.room, { type: 'chat', from: ws.name, text: String(msg.text).slice(0, 500), ts: Date.now() });
        break;
      default:
        ws.send(JSON.stringify({ type: 'error', message: 'unknown type' }));
    }
  });

  ws.on('close', () => {
    rooms.get(ws.room)?.delete(ws);
    if (ws.room) broadcast(ws.room, { type: 'system', text: ws.name + ' left' });
  });
});

// heartbeat: terminate dead connections every 30 s
setInterval(() => {
  wss.clients.forEach((ws) => {
    if (!ws.isAlive) return ws.terminate();
    ws.isAlive = false;
    ws.ping();
  });
}, 30000);

    🧱 Designing a Message Protocol

    WebSocket gives you a raw pipe — you must define the message format. Use an envelope with a type and optional correlation ID.

    json// client -> server (a request that expects a reply)
{ "type": "order.subscribe", "id": "c-101", "payload": { "orderId": 9001 } }

// server -> client (reply to c-101)
{ "type": "ack", "replyTo": "c-101", "ok": true }

// server -> client (event pushed later)
{ "type": "order.updated", "payload": { "orderId": 9001, "status": "SHIPPED" }, "seq": 412 }
    • type — what the message means (routing).
    • id / replyTo — correlate requests and replies (WebSocket has no built-in request–response).
    • seq — sequence numbers let clients detect missed messages after a reconnect.
    • version — add a protocol version for evolution.
    • Choose JSON for simplicity, or Protobuf/MessagePack for bandwidth-sensitive apps.

    🔄 Reliability: Heartbeats & Reconnection

    Connections will drop (mobile networks, proxies idle-timeout at 60 s, deployments). A production client must reconnect automatically.

    javascriptfunction connect(attempt = 0) {
  const ws = new WebSocket(url + '?token=' + token);

  ws.onopen = () => { attempt = 0; resubscribe(ws); fetchMissedSince(lastSeq); };

  ws.onclose = (e) => {
    if (e.code === 1008) return;                       // auth failure: don't retry blindly
    const delay = Math.min(30000, 500 * 2 ** attempt)  // exponential backoff
                + Math.random() * 500;                 // jitter avoids thundering herd
    setTimeout(() => connect(attempt + 1), delay);
  };
  return ws;
}
    💡
    Recovery pattern: after reconnecting, send the last seq you processed (or fetch missed data from a REST endpoint) so no events are lost.

    📈 Scaling WebSockets (Intermediate → Expert)

    Each connection is stateful and pinned to one server. With several servers, a message from a user on Server A must reach a user on Server B.

    Servers publish messages to a shared broker; every server forwards them to its own connected clients.
    • Sticky sessions / upgrade-aware load balancer: the handshake and the socket must reach the same server; configure proxy timeouts (proxy_read_timeout) and the Upgrade headers (NGINX).
    • Pub/Sub backplane: Redis, NATS, Kafka or a managed service so all nodes see all events.
    • Presence & state: store who is online / which rooms in Redis with TTL — not in process memory.
    • Backpressure: check ws.bufferedAmount; drop or coalesce updates for slow clients instead of buffering forever.
    • Capacity: a tuned Node.js server can hold tens of thousands of idle sockets; watch file descriptors, memory per connection and CPU on fan-out.
    • Graceful deploys: send close code 1001, let clients reconnect with jitter to avoid a reconnect storm.
    javascript// Redis backplane with ioredis
const pub = new Redis(), sub = new Redis();
sub.subscribe('chat:general');
sub.on('message', (channel, data) => broadcastLocal('general', JSON.parse(data)));
function publish(room, msg) { pub.publish('chat:' + room, JSON.stringify(msg)); }

    🚦 Rate Limiting Algorithms

    AlgorithmIdeaTrade-off
    Fixed window100 requests per calendar minuteBursts at window edges (200 in 2 s)
    Sliding windowCount requests in the last 60 sMore accurate, more memory
    Token bucketBucket refills at a steady rate; each request takes a token; allows burstsMost popular
    Leaky bucketRequests drain at a constant rateSmooths traffic, adds queueing delay
    javascript// Token bucket in a few lines (per client key; use Redis for multi-server)
function allow(bucket, { capacity = 10, refillPerSec = 5 } = {}) {
  const now = Date.now() / 1000;
  bucket.tokens = Math.min(capacity, (bucket.tokens ?? capacity) + (now - (bucket.ts ?? now)) * refillPerSec);
  bucket.ts = now;
  if (bucket.tokens >= 1) { bucket.tokens -= 1; return true; }
  return false;                    // -> respond 429 + Retry-After
}

    🛡️ Resilience: Timeouts, Retries, Circuit Breakers

    • Timeouts everywhere: every outbound call needs one — a missing timeout is how one slow service takes down ten.
    • Retries with exponential backoff + jitter — only for idempotent operations (or when using idempotency keys).
    • Circuit breaker: after repeated failures, “open” the circuit and fail fast for a while, then probe with a few calls (half-open) before closing again.
    • Bulkheads: isolate resource pools so one dependency cannot exhaust all threads/connections.
    • Graceful degradation: serve cached or partial data when a non-critical dependency is down.

    ⚡ Performance Toolbox

    • Compress responses (gzip / brotli); keep payloads small, send only needed fields.
    • Cache at every level: CDN → gateway → application (Redis) → database.
    • Paginate and stream large results instead of building giant arrays in memory.
    • Avoid N+1 database queries (joins, batching, DataLoader).
    • Use connection pooling and keep-alive; prefer HTTP/2 or HTTP/3 where possible.
    • Move slow work off the request path: return 202 Accepted and process via a queue (Kafka / RabbitMQ / SQS).
    • Measure first — profile and look at p95/p99 latency, not averages.

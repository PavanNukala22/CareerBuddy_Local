    API Fundamentals

    What an API is, what travels over the wire, and the main API styles you will meet as a backend developer.

    🔌 What is an API?

    An API (Application Programming Interface) is a contract that lets one piece of software ask another for data or actions. The caller does not need to know how the other side works inside — it only needs to know the shape of the request and the response.

    When people say “API” in backend work they nearly always mean a web API: a server that accepts requests over the network (usually HTTP) and returns structured data (usually JSON). A mobile app, a website, a partner company or another internal service can all be clients of the same API.

    🍽️
    Like a restaurant menu
    The menu lists what you can order and how. You do not walk into the kitchen — the waiter (the API) carries requests and results.
    📜
    A contract
    Endpoints, inputs, outputs and errors are agreed in advance so client and server teams can work independently.
    🧱
    An abstraction
    The server can change its database or language without breaking clients, as long as the contract stays the same.
    🔐
    A gate
    The API decides who may do what: authentication, authorisation, validation and rate limits live here.
    Who calls the APIExample
    Web front endA React page loads GET /api/products to show a product list
    Mobile appAn iOS app posts POST /api/orders when the user taps “Buy”
    Another backend serviceThe order service asks the payment service to charge a card
    A partner or public developerA shop uses Stripe's or Twilio's API to take payments or send SMS
    A scheduled jobA nightly script pulls reports from an analytics API
    💡
    As a backend developer you are usually the provider of APIs and also a consumer of other teams' and vendors' APIs. Good API design makes both roles easier.

    🛣️ The journey of an API call

    A single API call passes through many layers before your code even runs. Knowing them helps you find where latency or errors come from.

    A typical path of one HTTPS API request
    1. Client — the app builds the request: method, URL, headers, JSON body.
    2. DNS — the hostname api.shop.example.com is resolved to an IP address (often cached).
    3. TCP + TLS — a connection is opened and encrypted. Connections are reused (keep-alive) so later calls skip this cost.
    4. Load balancer — spreads traffic across many server instances and terminates TLS in many setups.
    5. API gateway — a front door that checks API keys or tokens, applies rate limits, routes to the right service and logs the call.
    6. Service handler — your code: parse and validate input, check permissions, run business logic.
    7. Data layer — read or write a database, cache or another service.
    8. Response — status code, headers and body travel back the same way.
    EXAMPLE · Where did the time go?

    A call takes 900 ms. Tracing shows: DNS 2 ms, TLS 40 ms, gateway 5 ms, handler 20 ms, database query 820 ms. The fix is an index or a cache on the database query, not a faster web framework. Always measure each hop before optimising.

    🧾 JSON: the language of web APIs

    JSON (JavaScript Object Notation) is a text format for structured data. It is human-readable, supported by every language, and is the default body format for REST and GraphQL APIs.

    RESTful API Design

    Resources, URLs, methods, status codes, pagination and error formats — designing APIs that are predictable and easy to use.

    🏛️ What makes an API RESTful?

    REST (Representational State Transfer) is an architectural style described by Roy Fielding in 2000. It is not a protocol or a library — it is a set of constraints. An API that follows them is called RESTful. In practice, “REST API” usually means resource-oriented URLs, HTTP methods with their proper meaning, status codes and JSON bodies.

    ConstraintWhat it meansWhy it helps
    Client–serverUI and data storage are separated; they talk only through the APIEach side can evolve and scale independently
    StatelessEach request carries everything needed (e.g. the auth token). The server keeps no session between requestsAny server instance can handle any request — easy horizontal scaling
    CacheableResponses say whether and how long they may be cachedFewer requests, lower latency, less server load
    Uniform interfaceResources identified by URIs, manipulated through representations, self-descriptive messages, hypermedia (HATEOAS)Every resource works the same way, so the API is predictable
    Layered systemClients cannot tell if they talk to the origin or a proxy, CDN, gateway or load balancerInfrastructure can be added without client changes
    Code on demand (optional)Server may send executable code (e.g. JavaScript) to the clientRarely used in JSON APIs
    📝
    “Stateless” does not mean the server has no data — it has a database full of state. It means no per-client conversation state is kept in server memory between requests.
    EXAMPLE · Stateful vs stateless

    Stateful: the client calls POST /login, the server remembers “connection 17 is Alice” in memory, and later calls rely on that. If the next request lands on another server, it fails. Stateless: each request sends Authorization: Bearer <token>; any server can verify the token and answer.

    🧭 Resources, nouns and URL design

    REST models your domain as resources — nouns such as products, orders and customers. URLs name resources; HTTP methods say what to do with them. Avoid verbs in the path.

    Avoid (RPC-style verbs)Prefer (resources + methods)
    GET /getAllProductsGET /products
    POST /createOrderPOST /orders
    POST /updateOrder?id=9876PATCH /orders/9876
    GET /deleteUser/5DELETE /users/5
    GET /getOrdersForCustomer?c=7GET /customers/7/orders
    • Use plural nouns for collections: /products, and an id for one item: /products/42.
    • Use lowercase and hyphens: /delivery-zones, not /DeliveryZones or /delivery_zones.
    • Nest only to show ownership, and keep it shallow — at most one level: /orders/9876/items. Prefer /items/555 over /customers/7/orders/9876/items/555.
    • Put filters, sort order and paging in the query string, not the path.
    • No file extensions; use the Accept header to pick the format.
    EXAMPLE · Actions that are not CRUD

    Some operations are not simple create/read/update/delete, such as cancelling an order. Options: model it as a state change (PATCH /orders/9876 with {"status": "CANCELLED"}), or as a sub-resource that is created (POST /orders/9876/cancellation). A pragmatic action endpoint like POST /orders/9876/cancel is also widely accepted — just be consistent.

    🔧 HTTP methods and their semantics

    Each method has a defined meaning. Two properties matter a lot: safe (does not change server state) and idempotent (sending the same request many times has the same effect on the server as sending it once).

    MethodTypical useSafeIdempotentSuccess codes
    GETRead a resource or collectionYesYes200
    HEADLike GET but headers only (check existence, size, ETag)YesYes200
    OPTIONSAsk which methods are allowed; used by CORS preflightYesYes204 / 200
    POSTCreate a resource in a collection, or trigger a processNoNo201, 200, 202
    PUTReplace the whole resource at a known URL (or create it there)NoYes200, 204, 201
    PATCHPartially update a resourceNoNot guaranteed200, 204
    DELETERemove a resourceNoYes204, 200, 202

    PUT — full replacement

    httpPUT /users/5
{"name": "Asha", "email": "asha@x.io", "city": "Pune"}

    Fields you leave out are reset or removed. Sending it twice gives the same result.

    PATCH — partial update

    httpPATCH /users/5
Content-Type: application/merge-patch+json
{"city": "Mumbai"}

    Only city changes. JSON Merge Patch (RFC 7396) and JSON Patch (RFC 6902) are common formats.

    ⚠️
    Never change data with GET. Crawlers, prefetchers, caches and retry logic assume GET is safe. A GET /users/5/delete link will eventually delete things by accident.
    💡
    Idempotency is about the server state, not the response. DELETE /orders/1 may return 204 the first time and 404 the second time — it is still idempotent because the order is gone either way.

    🚦 Status codes you must know

    Return the most specific correct status code. Clients, proxies, monitoring and retry logic all depend on it.

    CodeNameWhen to use it
    200OKSuccessful GET, or a PUT/PATCH/POST that returns a body
    201CreatedA POST (or PUT) created a resource. Include a Location header with its URL
    202AcceptedWork was queued and will finish later
    204No ContentSuccess with no body — common for DELETE or updates that return nothing
    301Moved PermanentlyResource has a new permanent URL (308 is the variant that keeps the method and body)
    304Not ModifiedConditional GET: the client's cached copy (matched by ETag or date) is still valid; no body
    400Bad RequestMalformed request: invalid JSON, wrong types, missing required query parameter
    401UnauthorizedNot authenticated: missing, invalid or expired credentials. Send WWW-Authenticate
    403ForbiddenAuthenticated, but not allowed to do this
    404Not FoundResource does not exist (also used to hide resources the caller may not know about)
    405Method Not AllowedPath exists but not for this method. Send an Allow header
    409ConflictRequest conflicts with current state: duplicate unique key, version conflict
    415Unsupported Media TypeBody format not supported (e.g. missing Content-Type: application/json)
    422Unprocessable ContentWell-formed request that fails business validation (e.g. quantity must be at least 1)
    429Too Many RequestsRate limit exceeded. Send Retry-After
    500Internal Server ErrorUnexpected bug or failure on the server
    502 / 504Bad Gateway / Gateway TimeoutA proxy or gateway got a bad or no response from the upstream service

    📝
    Teams differ on 400 vs 422 for validation errors. A common rule: 400 when the request cannot be parsed or is structurally wrong, 422 when it parses fine but the values break business rules. Pick one convention and document it.
    ⚠️
    Do not return 200 OK with {"error": "not found"} in the body. Clients, caches and monitoring will treat it as success.

    🔎 Filtering, sorting and pagination

    Collections grow. Never return an unbounded list — always page it, and let clients filter and sort with query parameters.

    httpGET /v1/orders?status=PAID&createdAfter=2026-09-01&sort=-createdAt&limit=20

    🧯 Error responses: RFC 9457 Problem Details

    Clients need errors that are consistent and machine-readable. RFC 9457 (which replaced RFC 7807) defines a standard JSON error body with the media type application/problem+json.

    httpHTTP/1.1 422 Unprocessable Content

{
  "type": "https://api.shop.example.com/problems/validation-error",
  "title": "Your request is not valid.",
  "status": 422,
  "detail": "2 fields failed validation.",
  "instance": "/v1/orders",
  "errors": [
    { "pointer": "/quantity", "detail": "must be at least 1" },
    { "pointer": "/productId", "detail": "product 999 does not exist" }
  ],
  "traceId": "4bf92f3577b34da6"

    MemberMeaning
    typeA URI that identifies the problem type (can link to docs). Defaults to about:blank

    ⚠️
    Never leak stack traces, SQL or internal hostnames in error bodies. Log them server-side with a trace id and return only the id.

    🔗 HATEOAS and the Richardson Maturity Model

    HATEOAS (Hypermedia As The Engine Of Application State) means responses contain links telling the client what it can do next, much like links on a web page. The client follows links instead of hard-coding URLs.

    json{
  "id": 9876,
  "status": "PENDING",
  "_links": {
    "self":   { "href": "/v1/orders/9876" },
    "pay":    { "href": "/v1/orders/9876/payment", "method": "POST" },
    "cancel": { "href": "/v1/orders/9876/cancellation", "method": "POST" }
  }
}
    Richardson levelDescription
    Level 0One URL, everything is a POST (classic RPC / SOAP style)
    Level 1Separate URLs for resources
    Level 2Resources + correct HTTP methods and status codes — where most “REST” APIs are
    Level 3Level 2 + hypermedia controls (HATEOAS)
    📝
    Few public JSON APIs implement full HATEOAS, but links for pagination (next/prev) and for available actions are common and useful. Formats like HAL and JSON:API standardise them.

    Production-Ready REST APIs

    Versioning, idempotency, caching, rate limits, CORS, OpenAPI, gateways, webhooks — what it takes to run an API that real clients depend on.

    🏷️ Versioning and API evolution

    Once clients depend on your API you cannot change it freely. Mobile apps stay installed for years; partners deploy on their own schedule. The goal is to evolve without breaking, and to version only when a breaking change is unavoidable.

    StrategyExampleProsCons
    URL pathGET /v2/orders/9876Obvious, easy to route, easy to test in a browser and cacheVersion is part of the resource URL; tends to version the whole API at once
    Custom headerAPI-Version: 2026-10-01Clean URLs; date-based versions allow small, frequent changes (Stripe style)Less visible; easy to forget; caches need Vary: API-Version
    Media typeAccept: application/vnd.shop.v2+jsonMost “pure” REST; version per representationHarder to use and test; less tooling support
    Query parameterGET /orders?version=2SimpleMixes versioning with filtering; easy to drop by accident
    Usually backward-compatible ✅Breaking ❌
    Adding a new endpointRemoving or renaming an endpoint or field
    Adding an optional request fieldMaking an optional field required
    Adding a field to a responseChanging a field's type ("42" → 42) or format
    Adding a new optional query parameterChanging the meaning of an existing value or default
    Adding a new enum value — if clients were told to tolerate unknown valuesChanging status codes or error format clients rely on

    💡
    Follow the tolerant reader rule and ask clients to do the same: ignore unknown fields, do not fail on new enum values. That is what makes additive changes safe.
    📝
    When you retire a version, announce it early, add Deprecation and Sunset response headers (RFC 9745 and RFC 8594), watch traffic per version and contact remaining clients before switching it off.

    🔁 Idempotency keys for safe retries

    Networks fail. A mobile app sends POST /payments, the server charges the card, but the response is lost in a tunnel. The app retries — and the customer is charged twice. Because POST is not idempotent, you need an idempotency key.

    httpPOST /v1/payments HTTP/1.1
Content-Type: application/json
Idempotency-Key: 8e0f6c1a-6d5b-4c1e-9a7a-3f1f2b9d1c44

{"orderId": 9876, "amountCents": 5998, "currency": "INR"}
    How an idempotency key turns a retry into a no-op
    1. The client generates a unique key (a UUID) once per logical operation and reuses it on every retry.
    2. The server stores the key with the request fingerprint and the final response (status + body), scoped to the caller, with an expiry such as 24 hours.
    3. On a repeat with the same key, it returns the stored response without doing the work again.
    4. Same key but a different body → reject (e.g. 422) because it is a client bug.
    5. Same key while the first request is still running → return 409 Conflict so the client retries later.
    ⚠️
    Store the key and the side effect atomically (same database transaction, or a unique constraint on the key). Otherwise two concurrent retries can both slip through.
    📝
    The Idempotency-Key header is used by Stripe, Adyen and others and is being standardised by the IETF. Safe and idempotent methods (GET, PUT, DELETE) do not need it.

    🗄️ HTTP caching: Cache-Control, ETag and 304

    Caching lets browsers, CDNs and proxies reuse responses. The fastest request is the one that never reaches your server.

    HeaderExampleMeaning
    Cache-Controlpublic, max-age=300Any cache may store it for 300 seconds
    Cache-Controlprivate, max-age=60Only the user's own browser may cache it (personal data)
    Cache-Controlno-cacheMay be stored, but must be revalidated with the server before each use
    Cache-Controlno-storeDo not store at all (tokens, payment details)
    ETag"v7-a1b2c3"A version identifier for this representation
    Last-ModifiedTue, 06 Oct 2026 10:00:00 GMTWhen the resource last changed (second precision)
    VaryAccept, Accept-EncodingThe cached copy depends on these request headers

    Conditional requests let a client ask “has it changed?” instead of downloading it again:

    http# First request
GET /v1/products/42
-> 200 OK
   ETag: "v7-a1b2c3"
   Cache-Control: private, max-age=0, must-revalidate
   { ...full product... }

# Later: revalidate

-> 304 Not Modified        (no body, client reuses its copy)

    ETags also prevent lost updates when two people edit the same resource (optimistic concurrency):

    javascriptimport express from 'express';
import crypto from 'node:crypto';

const app = express();
const SECRET = process.env.WEBHOOK_SECRET;

// Use the RAW body: re-serialised JSON would not match the signature
app.post('/webhooks/payments', express.raw({ type: 'application/json' }), async (req, res) => {
  const id = req.get('Webhook-Id');
  const ts = req.get('Webhook-Timestamp');
  const sig = (req.get('Webhook-Signature') || '').replace(/^v1,/, '');

  // 1. Reject old messages (replay protection)
  if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) return res.sendStatus(400);

  // 2. Recompute HMAC-SHA256 over "id.timestamp.body"
  const expected = crypto.createHmac('sha256', SECRET)
    .update(`${id}.${ts}.${req.body}`)
    .digest('base64');

  // 3. Constant-time comparison
  const a = Buffer.from(sig), b = Buffer.from(expected);
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) return res.sendStatus(401);

  // 4. Deduplicate: providers retry, so the same event may arrive twice
  if (await alreadyProcessed(id)) return res.sendStatus(200);

  // 5. Acknowledge fast, do heavy work in a background job
  await queue.add('payment-succeeded', JSON.parse(req.body));
  res.sendStatus(200);
});

    NEXT_ID += 1

    GraphQL APIs

    A typed schema, one endpoint and client-chosen fields — plus the resolvers, batching and security work that make it production-ready.

    🧩 Why GraphQL? Over-fetching and under-fetching

    GraphQL is a query language and runtime for APIs, created at Facebook (2012, open-sourced 2015). The server publishes a typed schema; the client sends a query that names exactly the fields it needs, and gets back JSON in the same shape.

    REST: a mobile order screen

    httpGET /orders/9876          -> 30 fields, need 4
GET /customers/7          -> 25 fields, need 1
GET /orders/9876/items    -> list
GET /products/42          -> per item...

    Over-fetching (too many fields) and under-fetching (several round trips).

    GraphQL: one request

    graphqlquery {
  order(id: "9876") {
    status
    total
    customer { name }
    items { quantity product { name } }
  }
}

    One round trip, only the requested fields.

    🎯
    Client-driven
    Each screen asks for exactly what it renders. Great for mobile on slow networks.
    📐
    Strongly typed
    The schema is the contract. Queries are validated before they run.
    🔍
    Introspection
    Tools such as GraphiQL and Apollo Sandbox read the schema for autocomplete and docs.
    🧬
    Evolve without versions
    Add fields freely; mark old ones @deprecated instead of creating /v2.
    📝
    GraphQL is transport-agnostic, but almost always runs over HTTP: a single endpoint such as POST /graphql with a JSON body {"query": "...", "variables": {...}}.

    ⚙️ Resolvers, context and Apollo Server

    A resolver is a function that produces the value for one field. The GraphQL engine walks the query tree and calls resolvers level by level. Every resolver receives four arguments: (parent, args, context, info).

    ArgumentWhat it holds
    parentThe value returned by the parent field's resolver (e.g. the Order object when resolving Order.customer)
    argsField arguments, e.g. { id: "9876" }
    contextPer-request shared data: the authenticated user, database clients, DataLoaders
    infoThe query AST and path — used for advanced optimisation and tracing
    javascriptimport { ApolloServer } from '@apollo/server';
import { startStandaloneServer } from '@apollo/server/standalone';

const resolvers = {
  Query: {
    order: (_parent, { id }, ctx) => db.orders.findById(id),
    me: (_parent, _args, ctx) => ctx.user ? db.customers.findById(ctx.user.id) : null,

  Mutation: {
    placeOrder: async (_parent, { input }, ctx) => {
      if (!ctx.user) {
        throw new GraphQLError('Not signed in', { extensions: { code: 'UNAUTHENTICATED' } });

    🐢 The N+1 problem and DataLoader

    Because resolvers run per field, a naive implementation can explode into many database calls. Fetch 50 orders and their customers:

    textSELECT * FROM orders LIMIT 50;           -- 1 query
SELECT * FROM customers WHERE id = 7;    -- +1
SELECT * FROM customers WHERE id = 12;   -- +1
... 50 times                             -- = 51 queries (N+1)

    DataLoader fixes this by batching all .load(id) calls made during one tick of the event loop into a single call, and caching results for the rest of the request.

    javascriptimport DataLoader from 'dataloader';

export function createLoaders() {
  return {
    customerById: new DataLoader(async (ids) => {
      // ONE query for all requested ids
      const rows = await db.query('SELECT * FROM customers WHERE id = ANY($1)', [ids]);
      const byId = new Map(rows.map((c) => [c.id, c]));
      // must return results in the SAME order as ids, same length
      return ids.map((id) => byId.get(id) ?? null);
    }),
  };
}

    textSELECT * FROM orders LIMIT 50;
SELECT * FROM customers WHERE id = ANY('{7,12,15,...}');   -- 2 queries total
    ⚠️
    Create DataLoaders per request (in the context function). A global loader would cache data across users — a data leak and a stale-data bug.
    📝
    Other fixes: look ahead at the query (info) to JOIN eagerly, or let tools like Prisma, Hasura or PostGraphile generate batched SQL.

    📄 Errors and pagination in GraphQL

    GraphQL can return partial success: some fields resolve, others fail. Errors go in a top-level errors array, next to data. Over HTTP with the classic application/json response type, the status is usually 200 even when errors are present.

    json{

    "order": { "id": "9876", "status": "PAID", "courier": null }

    • For expected business outcomes, many teams return typed results instead of errors: union PlaceOrderResult = Order | OutOfStock | InvalidAddress.
    • The GraphQL-over-HTTP spec and the application/graphql-response+json media type allow 4xx codes for requests that fail parsing or validation.

    gRPC and Protocol Buffers

    Contract-first, binary, streaming RPC over HTTP/2 — the workhorse of internal service-to-service communication.

    ⚡ What is gRPC?

    gRPC is an open-source RPC (Remote Procedure Call) framework originally built at Google and now a CNCF project. Instead of thinking in URLs and verbs, you call a method on a remote service as if it were a local function: orderClient.GetOrder({ orderId: '9876' }).

    📜
    Contract-first
    You define services and messages in a .proto file. Everything else is generated.
    🧬
    Protocol Buffers
    Compact binary serialisation — typically several times smaller and faster to parse than JSON.
    🚄
    HTTP/2
    Multiplexed streams on one connection, header compression, full-duplex streaming.
    🌍
    Polyglot
    Official code generation for Go, Java, C++, Python, C#, Node.js, Kotlin, Swift, Dart, Ruby, PHP and more.
    The gRPC development loop
    📝
    gRPC shines inside your system: microservice to microservice, mobile apps to their own backend, and low-latency streaming. Public APIs for third parties are still usually REST, because every language and tool speaks HTTP + JSON.

    🧬 Protocol Buffers: messages, field numbers and types

    Protocol Buffers (protobuf) is the interface definition language and the wire format. Here is a complete .proto file for an order service:

    protobufsyntax = "proto3";

    🛡️ Backward compatibility rules

    Old clients and new servers (and vice versa) will run side by side during every deployment. Protobuf is designed for this — if you follow the rules.

    EXAMPLE · Why reusing a number is dangerous

    Version 1 had string coupon_code = 9;. You delete it, and later add string referral_id = 9;. An old mobile app still sends a coupon code as field 9 — the new server silently reads it as a referral id. No error, just corrupted data. Writing reserved 9; reserved "coupon_code"; makes the compiler reject any reuse.

    📝
    In proto3 every scalar field has a default (0, "", false) and unset fields are not sent. Without optional you cannot tell “not set” from “set to 0”. Tools like buf breaking check compatibility automatically in CI.

    ⏳ Deadlines, status codes and metadata

    Every gRPC call should have a deadline — an absolute point in time after which the client gives up. It is sent to the server in the grpc-timeout header and should be propagated to downstream calls, so a whole chain of services stops work when the user has already given up.

    0OKSuccess200
    1CANCELLEDThe caller cancelled the call499 (client closed)

    5NOT_FOUNDEntity does not exist404
    6ALREADY_EXISTSEntity to create already exists409

    8RESOURCE_EXHAUSTEDQuota or rate limit hit, out of space429

    Metadata is gRPC's version of headers: key/value pairs sent at the start of a call (and as trailers at the end). Keys are lowercase ASCII; keys ending in -bin carry binary values. Typical uses: auth tokens, request ids, tracing context, tenant ids.

    ⚠️
    A call with no deadline can hang forever and hold resources on every service in the chain. Set deadlines at the edge and pass the remaining time downstream.

    📡 Polling, long polling, SSE and WebSockets

    Plain HTTP is client-initiated: the server can only answer when asked. For live data — chat, order tracking, dashboards — we need the server to push. There are four common techniques.

    🟢 A WebSocket server in Node.js and a browser client

    The ws library is the standard, minimal WebSocket implementation for Node.js. This server authenticates during the upgrade, tracks subscriptions and detects dead connections with ping/pong.

    javascriptimport http from 'node:http';
import { WebSocketServer, WebSocket } from 'ws';

const server = http.createServer();
const wss = new WebSocketServer({ noServer: true, maxPayload: 64 * 1024 });
const ALLOWED_ORIGINS = new Set(['https://app.food.example.com']);

// 1. Authenticate BEFORE accepting the upgrade
server.on('upgrade', async (req, socket, head) => {
  const user = await authenticate(req);            // cookie or short-lived ticket
  if (!user || !ALLOWED_ORIGINS.has(req.headers.origin)) {
    socket.write('HTTP/1.1 401 Unauthorized\r\n\r\n');
    socket.destroy();
    return;
  }
  wss.handleUpgrade(req, socket, head, (ws) => wss.emit('connection', ws, user));
});

// 2. Handle messages
wss.on('connection', (ws, user) => {
  ws.isAlive = true;
  ws.on('pong', () => { ws.isAlive = true; });

  ws.on('message', async (raw) => {
    let msg;
    try { msg = JSON.parse(raw); } catch { return ws.send(JSON.stringify({ type: 'error', error: 'bad_json' })); }

      subscribe(msg.orderId, ws);
      ws.send(JSON.stringify({ type: 'subscribed', orderId: msg.orderId }));
    }
  });

  ws.on('close', () => unsubscribeAll(ws));
});

// 3. Heartbeat: drop connections that stop answering pings
const timer = setInterval(() => {
  for (const ws of wss.clients) {
    if (!ws.isAlive) { ws.terminate(); continue; }
    ws.isAlive = false;
    ws.ping();

    💓 Heartbeats, close codes and reliability

    Long-lived connections die silently: phones switch networks, laptops sleep, NAT gateways and load balancers drop idle connections (AWS ALB's default idle timeout is 60 seconds). Without heartbeats both sides may believe a dead connection is alive.

    MechanismPurpose
    Ping / pong framesServer pings every 20–30 s; a missing pong means the connection is dead → terminate and clean up
    Application-level heartbeatBrowsers cannot send ping frames from JavaScript, so clients that need to detect dead servers send a small {"type":"ping"} message
    Reconnect with backoff + jitterAvoids thousands of clients reconnecting at the same instant after a deploy
    Message acknowledgementsClient acks important messages; server resends unacked ones after reconnect
    BackpressureCheck ws.bufferedAmount and slow down or drop low-priority messages for slow clients
    Close codeMeaning
    1000Normal closure
    1001Going away (server shutting down, page navigated away)
    1006Abnormal closure — no close frame received (connection dropped). Never sent on the wire
    1008Policy violation (e.g. auth failure after connect)
    1009Message too big
    1011Server error
    4000–4999Free for your application's own codes
    ⚠️
    During deploys, send close code 1001 (or 1012 Service Restart) and drain connections gradually. Killing all servers at once makes every client reconnect simultaneously.

    🔐 Authentication and security for WebSockets

    The browser WebSocket API cannot set custom headers such as Authorization. You need another way to authenticate the upgrade request.

    ApproachHowWatch out for
    Session cookieThe browser sends cookies with the upgrade request automaticallyCross-Site WebSocket Hijacking — always check the Origin header; use SameSite cookies
    Short-lived ticket in the URLClient gets a one-time token via an authenticated REST call, then connects to wss://…/ws?ticket=abcURLs end up in logs — make tickets single-use and expire in ~30 s

    • Validate and size-limit every incoming message (maxPayload); rate-limit messages per connection.
    • Use wss:// only.

    🔌 Fundamentals

    What happens, end to end, when a mobile app calls GET https://api.example.com/v1/orders/9876?

    The client resolves the hostname via DNS (usually cached), opens or reuses a TCP connection and performs a TLS handshake. It sends the request line, headers (Authorization, Accept) and no body. A load balancer forwards it, often after terminating TLS; an API gateway validates the token, applies rate limits and routes it to the order service. The handler validates input, checks the caller may see this order, reads from cache or the database and serialises JSON. The response — status, headers such as Content-Type and Cache-Control, and body — travels back the same way. Tracing ids let you see the time spent in each hop.

    What is the difference between an API and a protocol?

    A protocol (HTTP, HTTP/2, WebSocket, TCP) defines how bytes are exchanged. An API is an application-level contract built on top: which operations exist, their inputs, outputs and errors. REST and GraphQL APIs both typically use the HTTP protocol; gRPC is both a framework and a protocol on HTTP/2.

    What do the status code classes mean, and why do correct codes matter?

    1xx informational, 2xx success, 3xx redirection/caching, 4xx client errors, 5xx server errors. Correct codes drive behaviour outside your code: clients decide whether to retry (5xx/429 maybe, 4xx no), caches decide what to store, gateways and monitoring compute error rates and alerts, and SDKs map codes to exceptions. A 200 with an error body breaks all of that.

    Synchronous vs asynchronous APIs — when would you return 202 Accepted?

    Synchronous: the client waits for the result within one request. Use it when work completes in well under a few seconds. When work is long (reports, video encoding, bulk imports), accept it, queue it and return 202 Accepted with a Location to a job resource the client can poll, or notify completion via webhook or a push channel. This keeps request timeouts short and servers responsive.

    How do you document and share an API contract?

    Use a machine-readable spec: OpenAPI for REST, the SDL schema for GraphQL, .proto files for gRPC, AsyncAPI for event and WebSocket APIs. Keep it in version control, review changes like code, lint it, check for breaking changes in CI, and generate docs, SDKs, mocks and contract tests from it so the spec and the implementation cannot drift apart.

    🧭 REST design

    What are the REST constraints, and which do most “REST APIs” actually follow?

    Client–server, stateless, cacheable, uniform interface (resource identification, manipulation through representations, self-descriptive messages, HATEOAS), layered system and optional code-on-demand. Most real APIs reach Richardson level 2 — resources, correct methods and status codes, statelessness, cacheability — but skip full hypermedia. That is pragmatic, but it is worth saying so in an interview.

    Explain safe and idempotent methods. Is PATCH idempotent?

    Safe methods (GET, HEAD, OPTIONS) do not change state. Idempotent methods produce the same server state whether called once or many times: the safe ones plus PUT and DELETE. PATCH is not guaranteed idempotent: {"stock": 5} is, but a JSON Patch “add item to array” or “increment counter” is not. POST is neither. This matters for retries: infrastructure may retry idempotent requests automatically, while POST needs an idempotency key.

    How would you design URLs for customers, their orders and order items?

    GET /customers/7, GET /customers/7/orders (orders owned by a customer), GET /orders/9876 (canonical URL for an order), GET /orders/9876/items. Plural nouns, lowercase with hyphens, at most one level of nesting, ids in the path, filters/sort/paging in the query string, no verbs. For non-CRUD actions like cancel, either model a state change with PATCH or a sub-resource such as POST /orders/9876/cancellation.

    Offset vs cursor pagination — which would you choose for an activity feed?

    Cursor (keyset) pagination. Offset makes the database read and discard all skipped rows, so deep pages get slow, and inserts during paging cause duplicates or gaps. A cursor encodes the last seen sort key (e.g. createdAt + id as a tie-breaker), and the query uses WHERE (created_at, id) < (:t, :id) ORDER BY created_at DESC, id DESC LIMIT 20 with an index — constant speed and stable results. Offset is fine for small admin tables that need “page 7 of 12”.

    How should a REST API report errors?

    Use the correct status code plus a consistent, machine-readable body — ideally RFC 9457 Problem Details (application/problem+json) with type, title, status, detail, instance and extensions such as per-field errors and a traceId. Never leak stack traces or SQL. Document the error types so clients can branch on type rather than parsing messages.

    🏭 Production REST

    How do you prevent a double charge when a client retries POST /payments?

    Require an Idempotency-Key header generated once per logical operation. On first use, atomically record the key (unique constraint, scoped to the caller) with a request fingerprint, process the payment, and store the final response. Retries with the same key replay the stored response; a different body with the same key is rejected; a concurrent in-flight duplicate gets 409. Keys expire after e.g. 24 hours. Downstream, pass the key to the payment provider too.

    Compare API versioning strategies. Which do you prefer?

    URL path (/v2/) is the most visible and easiest to route and cache; header-based (API-Version: 2026-10-01) keeps URLs stable and enables fine-grained, date-based versions; media-type versioning is the most RESTful but least ergonomic. More important than the mechanism: avoid breaking changes through additive evolution and tolerant readers, run old and new versions side by side, announce deprecation with Deprecation/Sunset headers and measure usage before removal.

    Explain ETags and how they help with both caching and concurrency.

    An ETag is a version token for a representation. For caching, the client sends If-None-Match with its ETag; if unchanged the server returns 304 Not Modified with no body, saving bandwidth. For concurrency, the client sends If-Match on PUT/PATCH; if the resource has changed since it was read the server returns 412 Precondition Failed, preventing lost updates (optimistic locking).

    How would you implement rate limiting across 20 API instances?

    Enforce it centrally — at the API gateway, or with a shared store such as Redis using an atomic token-bucket or sliding-window script keyed by API key/user. Return 429 Too Many Requests with Retry-After and remaining-quota headers. Use different limits per plan and per endpoint cost, allow small bursts, fail open or closed deliberately if Redis is down, and make clients back off with jitter.

    How do you make webhooks secure and reliable?

    Sender: sign each payload with HMAC-SHA256 over the event id, timestamp and raw body; include a unique event id; retry with exponential backoff for hours; offer a way to replay events. Receiver: verify the signature on the raw body with a constant-time comparison, reject old timestamps to stop replays, deduplicate by event id, return 2xx quickly and process asynchronously, and never assume events arrive in order — fetch current state from the API if ordering matters.

    🧩 GraphQL

    When would you choose GraphQL over REST, and when not?

    Choose GraphQL when many clients (web, iOS, Android) need different, nested views of data from several backends — it removes over- and under-fetching and gives a strongly typed, introspectable contract. Avoid it for simple CRUD services, public APIs where HTTP caching and universal tooling matter, file-heavy APIs, or teams not ready to handle query cost limits, N+1 and field-level authorisation.

    What is the N+1 problem and how does DataLoader solve it?

    Resolving a list of N items and then a related field per item triggers 1 + N backend calls. DataLoader collects all .load(key) calls made in the same event-loop tick and invokes one batch function with all keys (e.g. WHERE id = ANY($1)), returning results in key order. It also memoises per request. Loaders must be created per request so cached data never leaks between users.

    How are errors returned in GraphQL?

    The response can contain both data and an errors array; each error has message, path, locations and extensions such as a code. Failed nullable fields become null; a failed non-null field propagates null to its parent. With classic application/json responses the HTTP status is usually 200, so monitoring must inspect the errors array. Expected domain outcomes are often modelled as union result types instead of errors.

    How do you protect a GraphQL API from expensive or malicious queries?

    Depth limiting, query cost/complexity analysis with a per-request budget, mandatory pagination arguments with maximums, timeouts, cost-based rate limiting, and persisted queries / operation allow-lists for first-party clients. Add field-level authorisation in resolvers, disable introspection for private APIs if desired, and limit batching/aliases that multiply work.

    What is GraphQL federation?

    A way to split one graph across teams. Each team publishes a subgraph schema and declares shared entities with @key; a router composes the supergraph, plans each query across subgraphs and merges the results. It keeps team autonomy while clients still see a single endpoint. Costs: an extra network hop, schema composition checks in CI, and distributed tracing to debug query plans.

    ⚡ gRPC

    Why is gRPC faster than REST with JSON?

    Protocol Buffers are compact binary messages that are cheap to encode and decode (no field names on the wire, varint integers). HTTP/2 multiplexes many calls over one connection with header compression, avoiding connection setup and head-of-line blocking at the HTTP layer. Generated stubs also avoid hand-written parsing. The gain matters most for high-volume internal traffic.

    Describe the four gRPC call types with examples.

    Unary: one request, one response (GetOrder). Server streaming: one request, stream of responses (TrackOrder pushing status updates). Client streaming: stream of requests, one response (courier app uploading GPS points, then a summary). Bidirectional streaming: both sides send independently over one stream (chat, live dispatch negotiation).

    How do you evolve a .proto file without breaking clients?

    Only add fields with new numbers; never change a field's number or reuse a deleted one — mark removed numbers and names reserved. Do not change types incompatibly. Keep enum value 0 as UNSPECIFIED and make clients tolerate unknown values. Version packages (shop.orders.v1) for real breaking changes and run buf breaking in CI.

    What are deadlines in gRPC and why propagate them?

    A deadline is the absolute time by which a call must complete; it travels as grpc-timeout. If it passes, the call fails with DEADLINE_EXCEEDED and the server can stop work. Propagating the remaining deadline to downstream calls ensures the whole call tree gives up together, instead of services wasting resources on answers nobody will read — a common cause of cascading failures.

    How do you call gRPC services from a browser, and how do you load-balance gRPC?

    Browsers cannot access HTTP/2 trailers, so use gRPC-Web through a proxy such as Envoy, the Connect protocol, or a REST/JSON gateway generated from google.api.http annotations. For load balancing, long-lived HTTP/2 connections defeat connection-level (L4) balancing, so use an L7 proxy or service mesh that balances per request, or client-side load balancing with service discovery.

    📡 WebSockets and choosing

    Walk through the WebSocket handshake.

    The client sends an HTTP/1.1 GET with Upgrade: websocket, Connection: Upgrade, a random Sec-WebSocket-Key and Sec-WebSocket-Version: 13. The server authenticates, checks Origin, and replies 101 Switching Protocols with Sec-WebSocket-Accept (base64 SHA-1 of the key plus a fixed GUID). The TCP connection then carries WebSocket frames — text, binary, ping, pong, close — in both directions.

    WebSockets vs Server-Sent Events — how do you choose?

    SSE is one-way server-to-client over plain HTTP, text only, with built-in reconnection and Last-Event-ID resume; it works well with existing HTTP infrastructure and HTTP/2. WebSockets are bidirectional, support binary, and have very low per-message overhead, but you must handle heartbeats, reconnection, auth and scaling yourself. Use SSE for notifications and feeds; WebSockets for chat, games and collaboration.

    How do you scale a WebSocket service to millions of connections?

    Run many stateless-ish connection servers behind a load balancer that supports upgrades and long idle timeouts. Fan out messages via a broker (Redis pub/sub or Streams, NATS, Kafka) so any server can deliver to sockets it holds. Keep connection metadata (who is subscribed to what) local or in a shared registry. Use heartbeats, backpressure, per-connection rate limits, graceful draining on deploys with jittered reconnection, and a replay mechanism for missed messages. Managed services are an option at very large scale.

    How do you authenticate WebSocket connections from a browser?

    The browser API cannot set an Authorization header. Use a session cookie with strict Origin checking (to prevent cross-site WebSocket hijacking), a short-lived single-use ticket obtained over an authenticated REST call and passed in the URL, or an auth message as the first frame with a short timeout. Authorise each subscription, and handle token expiry on long-lived connections.

    A food-delivery company asks which API styles to use. What do you recommend?

    Public REST + OpenAPI for restaurant partners (universal, cacheable, documented). A GraphQL BFF for the customer mobile app to fetch nested screens in one round trip. gRPC between internal services (orders, pricing, dispatch, payments) for typed, fast calls with deadlines and streaming. WebSockets (or SSE for one-way) for live order tracking and courier chat, fanned out via Redis. Webhooks to notify partners of order events. Each choice follows the client type, data shape and freshness needs.

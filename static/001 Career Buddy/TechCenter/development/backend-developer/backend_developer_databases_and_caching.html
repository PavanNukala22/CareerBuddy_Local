    What are Databases & Caching?

    Start from zero: what a database is, the main types, and why caches sit in front of them.

    🗄️ What is a database?

    A database is an organised collection of data that applications can store, find, update and delete reliably. A DBMS (database management system) such as PostgreSQL is the software that does this work for you: storage, queries, security, backups and concurrent access.

    🔴 Plain files (CSV, JSON)

    Slow to search, no safe concurrent writes, no rules, easy to corrupt.

    🟢 A DBMS

    Fast indexed search, transactions, constraints, access control, backups and replication.

    🧩 Types of databases

    DocumentJSON-like documents in collectionsMongoDBFlexible, nested, fast-changing data

    ⚡ What is caching and why?

    A cache keeps a copy of frequently read data in a faster place so the database is not asked every time. Redis answers in well under a millisecond from memory; a disk-based query may take tens of milliseconds.

    Figure 1.1 · Read path with a cache
    • Cache hit: data found in cache. Cache miss: not found, so read the database.
    • TTL (time to live) removes stale entries automatically.

    🔒 ACID, BASE and CAP

    IdeaMeaning
    ACIDAtomicity (all or nothing), Consistency (rules hold), Isolation (transactions do not interfere), Durability (committed data survives crashes)
    BASEBasically Available, Soft state, Eventually consistent: favours availability at scale
    CAP theoremDuring a network partition a distributed system must choose between consistency and availability
    💡
    Rule of thumb: SQL for money and relationships, MongoDB for flexible documents, Redis for speed. Most real systems use several together (polyglot persistence).

    📖 Key terms

    QueryA request to read or change data.
    TransactionA group of operations that succeed or fail together.
    IndexA structure that speeds up lookups.
    ReplicationCopying data to other servers.
    ShardingSplitting data across servers.
    EvictionRemoving cache entries when memory is full.
    LatencyTime taken to answer one request.

    Module 02 · PostgreSQL

    PostgreSQL

    An open-source relational database known for correctness, SQL standards and rich features.

    🐘 What is PostgreSQL?

    PostgreSQL (Postgres) is an object-relational database with strong ACID guarantees. It stores data in tables; each row is a record, each column has a type, and primary and foreign keys link tables.

    Common typeUse
    integer, bigint, serialWhole numbers and auto-ids
    numeric(10,2)Exact money values
    text, varchar(n)Strings
    timestamptzTime with time zone (preferred)
    boolean, uuidFlags and unique ids
    jsonbIndexed binary JSON
    arrayLists inside a column

    🧪 SQL basics with examples

    sqlCREATE TABLE users (
  id BIGSERIAL PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ DEFAULT now()
);
CREATE TABLE orders (
  id BIGSERIAL PRIMARY KEY,
  user_id BIGINT REFERENCES users(id),
  total NUMERIC(10,2) CHECK (total >= 0),
  status TEXT DEFAULT 'new'
);
INSERT INTO users(email) VALUES ('asha@example.com');
SELECT u.email, COUNT(o.id) AS orders, SUM(o.total) AS spent
FROM users u LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.email HAVING SUM(o.total) > 1000
ORDER BY spent DESC LIMIT 10;
    JoinReturns
    INNERRows matching in both tables
    LEFTAll left rows, matches from right (NULL if none)
    FULLAll rows from both
    CROSSEvery combination

    🔁 Transactions, isolation and MVCC

    sqlBEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;   -- or ROLLBACK;

    MVCC (multi-version concurrency control) keeps old row versions so readers never block writers. Default isolation is READ COMMITTED; stricter levels are REPEATABLE READ and SERIALIZABLE.

    ⚠️
    Dead row versions pile up. VACUUM (run by autovacuum) reclaims them; ignoring it causes table bloat.

    🚀 Intermediate: CTEs, window functions, JSONB

    sqlWITH monthly AS (
  SELECT user_id, date_trunc('month', created_at) m, SUM(total) t
  FROM orders GROUP BY 1, 2)
SELECT user_id, m, t,
       RANK() OVER (PARTITION BY m ORDER BY t DESC) AS rnk,
       LAG(t) OVER (PARTITION BY user_id ORDER BY m) AS prev
FROM monthly;

SELECT * FROM events WHERE payload @> '{"type":"click"}';  -- jsonb containment

    Module 03 · MySQL

    MySQL

    The widely deployed relational database behind many web applications.

    🐬 What is MySQL?

    MySQL is an open-source relational database that uses SQL. It is pluggable: the SQL layer talks to a storage engine. Always choose InnoDB (default): transactions, row-level locking, foreign keys and crash recovery. MyISAM is legacy and has none of these.

    sqlCREATE TABLE products (
  id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(120) NOT NULL,
  price DECIMAL(10,2) NOT NULL,
  stock INT DEFAULT 0,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;
SELECT name, price FROM products WHERE stock > 0 ORDER BY price LIMIT 20;

    ⚖️ MySQL vs PostgreSQL

    AreaMySQLPostgreSQL
    Default isolationREPEATABLE READREAD COMMITTED
    StrengthSimple, fast reads, huge ecosystemAdvanced SQL, JSONB, extensions
    Table storageClustered on primary key (InnoDB)Heap tables plus separate indexes
    ReplicationBinlog-based async / semi-sync, Group ReplicationWAL streaming and logical

    🔧 Intermediate and advanced

    • Clustered index: InnoDB stores rows in primary-key order, so keep the primary key short and sequential; every secondary index stores the primary key.
    • Binary log (binlog) records changes for replication and point-in-time recovery; replicas replay it.
    • Replication lag: read replicas may be seconds behind. Read-your-own-writes from the primary.
    • Strict mode (sql_mode) rejects bad data instead of silently truncating it.
    • High availability: Group Replication / InnoDB Cluster, ProxySQL for routing, Percona XtraBackup for hot backups.
    ⚠️
    Use utf8mb4, not utf8, so emoji and all Unicode characters are stored correctly.
    Q. Which MySQL storage engine supports transactions and foreign keys?
    • A MyISAM
    • B InnoDB
    • C MEMORY
    • D CSV

    Module 04 · MongoDB

    MongoDB

    A document database: store flexible JSON-like (BSON) documents without a fixed schema.

    🍃 What is MongoDB?

    MongoDB stores data as documents inside collections. Documents can nest objects and arrays, and two documents in a collection can have different fields.

    SQLMongoDB
    TableCollection
    RowDocument
    ColumnField
    JOIN$lookup or embedded documents
    IndexIndex

    🧪 CRUD examples

    javascriptdb.users.insertOne({ name: "Asha", email: "asha@example.com",
  address: { city: "Vijayawada" }, tags: ["vip", "beta"] });
db.users.find({ "address.city": "Vijayawada" }, { name: 1, _id: 0 });
db.users.updateOne({ email: "asha@example.com" }, { $set: { plan: "pro" }, $inc: { logins: 1 } });
db.users.deleteOne({ email: "asha@example.com" });
    OperatorUse
    $gt $lt $inCompare values
    $set $inc $pushUpdate fields, counters, arrays
    $and $orCombine conditions

    🧱 Data modelling: embed or reference?

    📦 Embed

    Data read together and owned by the parent (order with its line items). One read, atomic update.

    🔗 Reference

    Data shared, large or unbounded (comments on a post). Store ids and fetch with $lookup.

    ⚠️
    A document is limited to 16 MB. Never embed an array that grows forever.

    📊 Aggregation pipeline

    javascriptdb.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$userId", total: { $sum: "$amount" }, n: { $sum: 1 } } },
  { $sort: { total: -1 } },
  { $limit: 5 }
]);

    Stages run in order; put $match and $limit early so indexes can be used and less data flows on.

    🏆 Advanced: replica sets, sharding, transactions

    • Replica set: one primary and several secondaries with automatic failover through elections. Use write concern majority for safety.
    • Sharding: splits a collection across shards by a shard key. A poor key (monotonic, low cardinality) creates hot shards.
    • Multi-document transactions exist but cost performance; good modelling usually avoids them.
    • Schema validation ($jsonSchema) adds rules while keeping flexibility.
    Q. Best choice for an ever-growing list of comments on a post?
    • A Embed them all in the post
    • B Reference them in a separate collection
    • C Store as one big string
    • D Use a transaction

    Module 05 · Redis

    Redis

    An in-memory data store used for caching, sessions, rate limiting, queues and leaderboards.

    ⚡ What is Redis?

    Redis (Remote Dictionary Server) keeps data in RAM and serves it in microseconds. Commands run on a single thread, so each one is atomic. It is mostly a cache in front of a primary database, but it can also be a primary store.

    Data typeExample commandsUse
    StringSET GET INCRCache values, counters
    HashHSET HGETALLObjects (user profile)
    ListLPUSH RPOPQueues
    SetSADD SISMEMBERUnique items, tags
    Sorted setZADD ZRANGELeaderboards, scheduling
    StreamXADD XREADEvent logs

    🧪 Commands in action

    redisSET user:42 '{"name":"Asha"}' EX 300     # expires in 300 s
GET user:42
INCR page:views
HSET session:abc user 42 role admin
ZADD leaderboard 1500 "asha"
ZREVRANGE leaderboard 0 2 WITHSCORES
TTL user:42

    🧠 Caching patterns

    PatternHow it worksTrade-off
    Cache-asideApp reads cache; on miss reads DB and fills cacheSimple; first read is slow
    Write-throughWrite to cache and DB togetherFresh cache; slower writes
    Write-behindWrite to cache, flush to DB laterFast writes; risk of data loss
    Read-throughCache layer loads from DB itselfCleaner app; needs a cache library
    pythondef get_user(uid):
    key = f"user:{uid}"
    cached = redis.get(key)
    if cached:
        return json.loads(cached)                 # hit
    user = db.fetch_user(uid)                      # miss
    redis.set(key, json.dumps(user), ex=300)       # fill with TTL
    return user

def update_user(uid, data):
    db.update_user(uid, data)
    redis.delete(f"user:{uid}")                    # invalidate

    Module 06 · Indexing & Optimization

    Database Indexing & Query Optimization

    Understand how indexes work, read query plans and make slow queries fast.

    📚 What is an index?

    An index is a separate sorted structure, like a book index, that lets the database jump to rows instead of scanning the whole table (a sequential / full scan). Cost: extra disk space and slower writes, because every INSERT, UPDATE and DELETE must also update the indexes.

    sqlCREATE INDEX idx_orders_user ON orders(user_id);
CREATE UNIQUE INDEX idx_users_email ON users(email);
-- MongoDB:  db.orders.createIndex({ userId: 1, createdAt: -1 })

    🧩 Types of indexes

    TypeGood forNotes
    B-treeEquality, ranges, ORDER BYDefault in all databases
    HashEquality onlyPostgreSQL hash, Redis keys
    CompositeMulti-column filtersColumn order matters
    CoveringIndex-only readsINCLUDE columns (PostgreSQL)
    PartialOnly a subset of rowsWHERE status = 'new'
    GIN / GiSTJSONB, arrays, full text, geoPostgreSQL
    Text / TTL / geoMongoDB search, expiry, locationMongoDB

    🔎 Reading query plans

    sqlEXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 10;
-- Seq Scan            -> reads the whole table (bad on big tables)
-- Index Scan          -> uses an index
-- Index Only Scan     -> answered from the index alone
-- compare estimated vs actual rows; large gaps mean stale statistics (run ANALYZE)

    MySQL uses EXPLAIN / EXPLAIN ANALYZE (check type, key, rows); MongoDB uses .explain("executionStats") and looks for IXSCAN instead of COLLSCAN.

    🧠 Composite index rules

    sqlCREATE INDEX idx_o ON orders(user_id, status, created_at);
-- Uses the index:   WHERE user_id = 1
--                   WHERE user_id = 1 AND status = 'paid'
-- Cannot use it well: WHERE status = 'paid'   (skips the leftmost column)
    • Leftmost-prefix rule: an index on (a, b, c) helps a, a+b and a+b+c.
    • Order: equality columns first, then range, then sort columns.
    • Functions on a column (WHERE lower(email)=…, WHERE date(created_at)=…) hide it from the index; use an expression index or rewrite the filter.
    • Low-cardinality columns (e.g. boolean) alone rarely benefit from an index.

    🏆 Query optimization checklist

    ProblemFix
    SELECT *Select only the columns you need
    N+1 queries (one query per row)Use a JOIN, IN list or batch loading
    Deep OFFSET paginationKeyset pagination: WHERE id < :last ORDER BY id DESC LIMIT 20
    Slow repeated readsCache results in Redis
    Unknown slow queriesEnable the slow query log / pg_stat_statements
    Stale statisticsANALYZE; keep autovacuum healthy
    Too many indexesDrop unused ones; they slow every write
    Huge tablesPartition, archive old data, add read replicas
    Before and after

    Query: SELECT * FROM orders WHERE user_id = 42 on 10 million rows. Without an index: sequential scan, about 2 s. After CREATE INDEX ON orders(user_id): index scan, a few ms.

    Practice: Design the Data Layer for ShopKart

    Apply everything: pick the right database, model data, add indexes and cache safely.

    0 / 0 correct

    🛒 Scenario

    ShopKart is an e-commerce site with 2 million users. It stores orders and payments, a product catalogue with varying attributes (phones, shirts, books), user sessions, and a "top sellers" list. The orders page has become slow.

    1️⃣ Task 1 · Choose databases

    ✍️ Which database would you use for orders, the catalogue, and sessions/top sellers? Say why.
    Model answer: Orders and payments: PostgreSQL or MySQL (ACID transactions, foreign keys). Catalogue: MongoDB (flexible attributes per product) or PostgreSQL JSONB. Sessions and top sellers: Redis (TTL for sessions, sorted set for the leaderboard).

    2️⃣ Task 2 · Index it

    sqlSELECT id, total, created_at FROM orders
WHERE user_id = 42 AND status = 'paid'
ORDER BY created_at DESC LIMIT 20;
    ✍️ Write the best index for this query and explain the column order.
    Model answer: CREATE INDEX idx_orders_user_status_created ON orders(user_id, status, created_at DESC); Two equality columns come first, then the sort column, so the database filters and returns rows already ordered, with no extra sort.

    3️⃣ Task 3 · Diagnose

    Q. EXPLAIN shows "Seq Scan" on a 10-million-row table for a filter on user_id. What is the first step?
    • A Add more RAM
    • B Create an index on user_id and re-run EXPLAIN ANALYZE
    • C Switch to MongoDB
    • D Delete old rows
    ✍️ The dashboard runs 101 queries to show 100 orders with their products. What is wrong and how do you fix it?
    Model answer: This is the N+1 query problem. Fetch orders, then load all products in one query (JOIN or WHERE id IN (…)), or batch-load them.

    4️⃣ Task 4 · Cache safely

    ✍️ Product pages are cached in Redis with a 10-minute TTL. A sale starts and a hot product page expires, sending thousands of requests to the database. Propose two fixes.
    Model answer: Use a short lock so only one request rebuilds the cache (others wait or serve stale data); refresh before expiry; add random jitter to TTLs; pre-warm the cache before the sale. Invalidate the key on price or stock updates.

    5️⃣ Task 5 · Scale

    Q. Reads are heavy but writes are modest. The best first scaling step is…
    • A Shard immediately
    • B Add read replicas and caching
    • C Remove all indexes
    • D Use a bigger text column

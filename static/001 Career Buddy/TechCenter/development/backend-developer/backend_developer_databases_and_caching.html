    Data Storage Fundamentals

    Why backends need databases and caches, the main kinds of data store, and the guarantees they give.

    🗄️ What the database does in a backend

    A backend service is usually stateless: any instance can serve any request, and instances come and go. Anything that must survive a restart — users, orders, payments, sessions — lives in a database. The database is the source of truth; everything else (caches, search indexes, analytics copies) is derived from it.

    💾
    Durability
    Once a write is confirmed, it survives crashes and power loss (written to a log on disk).
    🔒
    Integrity
    Constraints (NOT NULL, UNIQUE, foreign keys, CHECK) reject bad data before it is stored.
    🤝
    Concurrency
    Many requests read and write at once without corrupting each other's work.
    🔍
    Querying
    Find, filter, join and aggregate data efficiently, often with indexes.
    ⚡
    Caching layer
    A fast, in-memory copy of hot data (for example Redis) that takes load off the database.
    📈
    Scale
    Replicas, partitioning and sharding let data and traffic grow beyond one machine.

    In a typical web request the path is: load balancer → app instance → (cache) → database → back to the client. Most backend performance problems are really data access problems: too many queries, missing indexes, or fetching far more data than needed.

    📝
    Rule of thumb: the app tier is easy to scale (add instances); the database is the hard part. Good backend developers protect the database — fewer, cheaper queries and a sensible cache.

    ⚖️ ACID and BASE

    ACID describes the guarantees of a classic database transaction:

    LetterPropertyPlain meaningExample
    AAtomicityAll statements in the transaction happen, or none do.Debit one account and credit another — never only one of them.
    CConsistencyA transaction moves the data from one valid state to another; constraints always hold.A foreign key never points to a missing customer.
    IIsolationConcurrent transactions do not see each other's half-finished work (to a chosen level).A report does not see an order whose lines are only half-inserted.
    DDurabilityOnce committed, the change survives a crash.The write-ahead log is flushed to disk before COMMIT returns.

    BASE (Basically Available, Soft state, Eventually consistent) describes many distributed stores that favour availability and scale: a write is accepted quickly and copies converge later. Reads may briefly return stale data.

    ACID mindset

    • Correctness first
    • Strong consistency inside one database
    • Good for money, stock, bookings

    BASE mindset

    • Availability and scale first
    • Stale reads are acceptable for a while
    • Good for feeds, likes, view counts
    📝
    This is not a strict SQL vs NoSQL split. MongoDB supports multi-document ACID transactions; a PostgreSQL read replica is eventually consistent with its primary. Ask what guarantee each operation needs.

    🔺 The CAP theorem, practically

    CAP is about a data store replicated across nodes. It names three properties:

    Consistency (C)Every read sees the most recent write (linearizability) — not the same 'C' as in ACID.
    Availability (A)Every request to a non-failed node gets a non-error response.
    Partition tolerance (P)The system keeps working when the network between nodes drops messages.

    Network partitions will happen, so P is not optional. The real statement is: during a partition you must choose between refusing some requests (keep C, lose A) or answering with possibly stale data (keep A, lose C).

    Choice during a partitionBehaviourFits
    CPMinority side rejects writes or reads until it can reach a majorityPayments, inventory, leader election
    APEvery node keeps answering; conflicts are resolved laterShopping carts, social counters, DNS-style data

    When there is no partition, the trade-off is between latency and consistency (the PACELC extension): waiting for replicas to confirm is safer but slower.

    ⚠️
    Avoid saying 'MongoDB is CP' or 'Cassandra is AP' as absolute facts. Most modern stores let you tune it per operation — for example MongoDB write concern majority vs 1, or Cassandra consistency level QUORUM vs ONE.

    📊 OLTP vs OLAP

    Backends mostly run OLTP (online transaction processing) workloads. Reporting and analytics are OLAP (online analytical processing). They want different designs.

    AspectOLTPOLAP

    ExamplePlace order #8812, load user 42's cartRevenue by region by month for 3 years
    VolumeThousands of short queries per secondFew long-running queries

    StorageRow-oriented (PostgreSQL, MySQL)Column-oriented (BigQuery, Snowflake, ClickHouse, Redshift)

    ⚠️
    Running heavy reports on the primary OLTP database steals CPU, I/O and buffer cache from user requests. Move them to a read replica or, better, copy the data into a warehouse (ETL/ELT or change data capture).

    ⚡ A read with a cache in front

    A cache keeps a copy of frequently read data in fast memory. The most common pattern in application code is cache-aside (lazy loading):

    Cache-aside read path: on a hit the database is never touched
    pythonimport json

def get_product(product_id: int) -> dict:
    key = f"product:{product_id}"
    cached = redis.get(key)                      # 1. check the cache
    if cached is not None:
        return json.loads(cached)                # 2. hit: about 1 ms
    row = db.fetch_one(                          # 3. miss: go to the database
        "SELECT id, name, price FROM products WHERE id = %s", (product_id,))
    if row is not None:
        redis.set(key, json.dumps(row), ex=300)  # 4. populate with a 5-minute TTL
    return row
    Hit ratioHits ÷ (hits + misses). A ratio of 0.95 means only 5% of reads reach the database.
    TTLTime to live: the cache entry expires automatically, which bounds how stale it can get.
    Stale dataA cached copy that no longer matches the database. Every cache trades some freshness for speed.
    💡
    Cache data that is read often, changes rarely and is expensive to compute. Do not cache everything — a cache with a poor hit ratio only adds latency and complexity.

    ⚠️

    🔌 Connections and key terms

    Talking to a database means opening a connection: a TCP (or Unix socket) session, TLS handshake, authentication and session setup. That costs milliseconds, and on the server each connection uses memory — in PostgreSQL each one is a separate backend process.

    Connection lifecycle with a pool
    • Never open a new connection per query in a busy service — use a connection pool (HikariCP, SQLAlchemy pool, node-postgres Pool, or PgBouncer in front of PostgreSQL).
    • Always return connections, even on errors (try/finally, with blocks, using).
    • Set timeouts: connect timeout, statement timeout, and pool acquire timeout, so one slow query cannot hang every request.
    • Keep transactions short; an idle open transaction holds locks and (in PostgreSQL) blocks cleanup.
    SchemaThe structure of the data: tables, columns, types, constraints.
    Primary keyColumn(s) that uniquely identify a row or document.
    IndexAn extra data structure that finds rows without scanning the whole table.
    TransactionA group of operations that commit or roll back together.
    ReplicaA copy of the database kept in sync from the primary, usually for reads and failover.
    ShardOne horizontal slice of a dataset that is split across several servers.
    LatencyTime for one operation (for example p99 = 25 ms).
    ThroughputOperations completed per second.

    PostgreSQL & MySQL for Backends

    Types, constraints, transactions, isolation, locking, MVCC, pooling and migrations — what a backend developer must know.

    🏗️ Schema design and constraints

    A good relational schema is normalised (each fact stored once), uses the right types, and lets the database enforce the rules. Application validation is helpful, but only database constraints protect you from every code path, script and race condition.

    sql-- PostgreSQL
CREATE TABLE customers (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL UNIQUE,
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  bigint NOT NULL REFERENCES customers(id),
    status       text NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
    total        numeric(12,2) NOT NULL CHECK (total >= 0),
    created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX orders_customer_id_idx ON orders (customer_id);  -- FKs are not auto-indexed in PostgreSQL
    ConstraintProtects againstNote
    PRIMARY KEYDuplicate or missing identityImplies NOT NULL + UNIQUE and creates an index
    NOT NULLMissing required dataThe cheapest constraint; use it by default
    UNIQUETwo users with the same emailCreates a unique index; also the safe way to stop duplicate sign-ups under concurrency
    FOREIGN KEYOrders for a customer that does not existIndex the referencing column yourself in PostgreSQL; InnoDB adds one if missing

    💡
    A UNIQUE constraint beats a 'check then insert' in code. Two requests can both check, both see nothing, and both insert — the constraint is the only reliable guard.

    🔄 Transactions and isolation levels

    A transaction groups statements so they commit or roll back together. The isolation level decides how much concurrent transactions can see of each other.

    sqlBEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- or ROLLBACK; on any error
    AnomalyWhat goes wrong
    Dirty readYou read another transaction's uncommitted change, which may be rolled back.
    Non-repeatable readYou read a row twice in one transaction and get different values.
    Phantom readYou re-run a range query and new rows appear.
    Lost updateTwo transactions read the same value, both write, one write silently overwrites the other.
    Write skewTwo transactions each check a condition, then write different rows, breaking a rule together (e.g. both on-call doctors go off call).
    LevelPostgreSQLMySQL InnoDB
    READ UNCOMMITTEDBehaves as READ COMMITTED (no dirty reads ever)Allows dirty reads
    READ COMMITTEDDefault. Each statement sees data committed before it startedEach consistent read takes a fresh snapshot
    REPEATABLE READSnapshot for the whole transaction; no phantoms; concurrent update of the same row raises a serialization errorDefault. Snapshot for plain SELECTs; locking reads and writes see the latest data and use next-key locks
    SERIALIZABLESerializable Snapshot Isolation (SSI): detects dangerous patterns and aborts one transactionPlain SELECTs become shared locking reads (when autocommit is off)

-- MySQL (applies to the next transaction)

    ⚠️
    At REPEATABLE READ and SERIALIZABLE in PostgreSQL, transactions can fail with SQLSTATE 40001 (serialization failure). Your code must retry the whole transaction, not just the last statement.

    🔐 Locking, lost updates and deadlocks

    Writers take row locks: a second transaction that updates the same row waits until the first commits or rolls back. Plain reads do not block writers (thanks to MVCC).

    EXAMPLE · Lost update with read-modify-write

    Two requests both run SELECT stock FROM products WHERE id = 7 and see 5. Each computes 5 − 1 = 4 in code and writes UPDATE … SET stock = 4. Two items were sold, but stock dropped by one.

    FixHowWhen
    Atomic updateUPDATE products SET stock = stock - 1 WHERE id = 7 AND stock > 0Best when the change can be expressed in SQL
    Pessimistic lockSELECT … FOR UPDATE inside the transaction, then updateHigh contention, complex logic between read and write
    Optimistic lockA version column: UPDATE … SET …, version = version + 1 WHERE id = 7 AND version = 3; 0 rows updated means retryLow contention, long user think-time
    sqlBEGIN;
SELECT stock FROM products WHERE id = 7 FOR UPDATE;   -- locks the row until COMMIT
-- business logic in the app...
UPDATE products SET stock = stock - 1 WHERE id = 7;
COMMIT;

-- Job queue: each worker grabs different rows instead of waiting
SELECT id FROM jobs WHERE status = 'ready'
ORDER BY id LIMIT 10
FOR UPDATE SKIP LOCKED;

    A deadlock happens when transaction A holds lock 1 and waits for lock 2, while B holds lock 2 and waits for lock 1. Both databases detect it and abort one transaction (PostgreSQL SQLSTATE 40P01, MySQL error 1213).

    • Lock rows in a consistent order (for example by ascending id).
    • Keep transactions short; never wait for a user or an HTTP call while holding locks.
    • Retry the aborted transaction with a small backoff.
    • Use NOWAIT or lock_timeout / innodb_lock_wait_timeout to fail fast instead of piling up waiters.

    🧹 MVCC, VACUUM and undo logs

    Both engines use Multi-Version Concurrency Control (MVCC): readers see a consistent snapshot while writers create new versions, so readers and writers do not block each other. They store old versions differently.

    PostgreSQL

    • An UPDATE writes a new row version (tuple) in the table; the old one becomes dead once no snapshot needs it.
    • Each tuple has xmin/xmax transaction ids that decide visibility.
    • VACUUM (run automatically by autovacuum) reclaims dead tuples and freezes old ones to prevent transaction-id wraparound.
    • Heavy updates without enough vacuuming cause bloat: bigger tables and indexes, slower scans.

    MySQL InnoDB

    • An UPDATE changes the row in place and writes the previous version to the undo log.
    • Older snapshots rebuild old versions by following undo records.
    • A background purge thread removes undo records no longer needed by any read view.
    • Long transactions make the history list length grow and slow reads that walk long undo chains.
    sql-- PostgreSQL: which tables have many dead tuples, and when were they vacuumed?
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
    ⚠️
    The common enemy in both engines is the long-running or idle-in-transaction session. It pins an old snapshot, so cleanup cannot remove anything newer. In PostgreSQL set idle_in_transaction_session_timeout and watch pg_stat_activity.

    🚚 Schema migrations

    Schema changes are code: versioned, reviewed, applied in order by a tool such as Flyway, Liquibase, Alembic, Prisma Migrate or framework migrations (Rails, Django, EF Core). The tool records which versions ran in a history table.

    Expand–contract: zero-downtime column rename
    sql-- PostgreSQL: build an index without blocking writes (cannot run inside a transaction block)
CREATE INDEX CONCURRENTLY orders_status_idx ON orders (status);

-- Fail fast instead of queueing behind a long query while holding a lock request
SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN source text;           -- fast: no table rewrite

-- MySQL 8.x: request an instant metadata-only change (errors if not possible)
ALTER TABLE orders ADD COLUMN source VARCHAR(20), ALGORITHM=INSTANT;
    • Make every migration backward compatible with the code version still running during deploy.
    • Backfill large tables in batches, not one giant UPDATE that locks and bloats.
    • PostgreSQL DDL is transactional (a failed migration rolls back cleanly); MySQL DDL commits implicitly, so a half-applied multi-step migration needs manual repair.
    • Test migrations against a production-sized copy to see how long they lock.

    Indexing

    How indexes work, when the planner uses them, and how to design the few indexes that make queries fast.

    🌳 How a B-tree index works

    Without an index, finding WHERE email = 'ana@example.com' means reading every row — a sequential scan. An index is a separate, sorted structure that maps column values to row locations, like the index at the back of a book.

    The default index in PostgreSQL and MySQL is a B-tree (strictly a B+tree): a balanced tree of fixed-size pages. The root and inner pages hold separator keys; the leaf pages hold every key in sorted order plus a pointer to the row, and leaves are linked to their neighbours.

    text                     [ root:  M ]
                    /            \
        [ D   H ]                  [ R   W ]
       /   |    \                 /   |    \
[A B C]→[D E F G]→[H .. L]→[M .. Q]→[R .. V]→[W .. Z]   ← sorted, linked leaves
                   each leaf entry: key → row location
    PropertyConsequence
    Balanced and wide (hundreds of keys per page)3–4 levels cover millions of rows: a lookup touches only a few pages — O(log n)
    Keys sortedSupports =, <, >, BETWEEN, IN, ORDER BY and prefix LIKE 'abc%'
    Leaves linkedRange scans walk sideways along leaves without going back to the root
    Must stay sorted on every writeEach INSERT/UPDATE/DELETE also updates every affected index
    📝
    In PostgreSQL, a B-tree only serves LIKE 'abc%' if the column uses the C collation or the index is built with text_pattern_ops. MySQL B-trees handle prefix LIKE directly.

    🚫 When an index is used — and when it is not

    The query planner estimates the cost of each plan and picks the cheapest. Having an index does not force its use. These are the classic reasons an index is ignored:

    CauseBadBetter
    Function or expression on the columnWHERE lower(email) = 'ana@x.com'Expression index on lower(email), or store normalised data
    Maths or casts on the columnWHERE created_at::date = '2026-10-01'WHERE created_at >= '2026-10-01' AND created_at < '2026-10-02'
    Leading wildcardWHERE name LIKE '%phone'Trigram GIN index (pg_trgm) or a search engine
    Implicit type conversion (MySQL)WHERE phone = 5551234 on a VARCHAR columnWHERE phone = '5551234' — match the column's type
    Low selectivityWHERE is_active = true when 95% of rows are activeA seq scan is genuinely cheaper; use a partial index for the rare value
    Leading column missingWHERE b = 1 with an index on (a, b)Index on (b) or reorder the composite
    Stale statisticsPlanner thinks the table is tinyRun ANALYZE (autovacuum normally does this)

    A selective predicate matches a small fraction of rows. As a rough guide, once a query needs more than a few percent of a table, reading the whole table sequentially can beat thousands of random index lookups.

    💡
    Write predicates as column operator constant. Leave the column bare and move all the work to the other side — this is called making the predicate sargable (search-argument-able).

    🧱 Composite indexes and column order

    A composite (multi-column) index is sorted by the first column, then by the second within equal first values, and so on — like a phone book sorted by surname, then first name.

    Leftmost-prefix rule: an index on (customer_id, status, created_at) can be searched efficiently for:

    Query filterUses the index?
    customer_id = ?Yes — first column
    customer_id = ? AND status = ?Yes — first two columns
    customer_id = ? AND status = ? AND created_at > ?Yes — all three
    customer_id = ? ORDER BY status, created_atYes — filter and sort from the index, no sort step
    status = ?Not as a normal seek (leading column missing)
    customer_id = ? AND created_at > ?Partly — seeks on customer_id, then filters created_at inside that range

    Order the columns: equality first, then range (or sort). Once the index hits a range condition, the columns after it can no longer narrow the seek.

    sql-- Query: a customer's recent orders
SELECT id, total, created_at
FROM orders
WHERE customer_id = 42 AND created_at >= now() - interval '30 days'
ORDER BY created_at DESC;

-- Good: equality column first, range/sort column second
CREATE INDEX orders_cust_created_idx ON orders (customer_id, created_at);

-- Weaker: range column first; every customer's rows in the date range are scanned
-- CREATE INDEX ... ON orders (created_at, customer_id);
    📝
    Skip scan lets a database use a composite index without a condition on its leading column when that column has few distinct values. MySQL 8.0.13+ has it, and PostgreSQL 18 added it for B-trees. It is a bonus, not a design strategy — still put the columns you filter on most at the front.

    📦 Covering indexes and index-only scans

    A normal index lookup finds the key, then visits the table to fetch the other columns. If the index already contains every column the query needs, the database can skip the table — a covering index.

CREATE INDEX orders_cust_created_cov

    🗂️ Clustered vs heap tables, and the cost of indexes

    InnoDB: clustered primary key

    • The table is a B+tree ordered by the primary key; leaf pages hold full rows.
    • Secondary indexes store the primary key value, so a secondary lookup does a second B-tree walk.
    • A long PK (say a 36-char string) bloats every secondary index.
    • Random UUIDv4 keys insert all over the tree → page splits and poor cache use. Use auto-increment or time-ordered ids.
    • No explicit PK? InnoDB uses the first NOT NULL UNIQUE index, else a hidden row id.

    PostgreSQL: heap

    • Rows live in a heap in no guaranteed order; every index (including the PK) points to a tuple location (ctid).
    • Primary and secondary indexes cost the same to use.
    • CLUSTER reorders a table once, but order is not maintained.
    • HOT updates skip index maintenance when no indexed column changes and the page has space — fewer indexes means more HOT updates.

    Every index has a write cost. An INSERT into a table with 8 indexes performs 9 B-tree writes. Indexes also use disk, memory (buffer cache) and WAL/redo volume, and slow down VACUUM and backups.

    🔁 The N+1 query problem

    An ORM makes it easy to load a list and then touch a relation on each item. Each access fires another query: 1 query for the list plus N queries for the related rows.

    📄 Pagination: OFFSET vs keyset

    LIMIT 20 OFFSET 100000 still reads and discards 100,000 rows before returning 20. Pages get slower the deeper the user goes, and rows inserted between requests shift results so users see duplicates or miss items.

    sql-- OFFSET pagination: page 5001 reads 100,020 rows
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;

-- Keyset (seek) pagination: continue after the last row of the previous page
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < ('2026-10-01 09:15:00+00', 81234)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Supporting index (a B-tree can be read backwards)
CREATE INDEX posts_created_id_idx ON posts (created_at, id);

    ✂️ Fetch less, write in batches

    Two simple habits remove a lot of load:

    • Select only needed columns. SELECT * transfers wide columns (descriptions, JSON, blobs) you never use, prevents index-only scans, and breaks silently when columns are added.
    • Batch writes. 10,000 single-row INSERTs mean 10,000 round trips and, in autocommit mode, 10,000 commits each waiting for a log flush.

-- Large UPDATE/DELETE in chunks to keep locks and transactions short (PostgreSQL)
DELETE FROM events
WHERE id IN (SELECT id FROM events WHERE created_at < now() - interval '90 days' LIMIT 5000);
-- repeat until 0 rows affected

    🪞 Read replicas and replication lag

    A read replica receives a continuous stream of changes from the primary (PostgreSQL WAL, MySQL binary log) and serves read-only queries. It scales reads and offloads reporting, but replication is usually asynchronous, so replicas lag behind.

    EXAMPLE · Read-your-own-writes bug

    A user updates their profile (write → primary), the page reloads and reads from a replica that is 800 ms behind — the old name appears and the user thinks the save failed.

    MitigationHow
    Sticky primary readsAfter a user writes, route that user's reads to the primary for a few seconds
    Read critical paths from primaryCheckout, balances and anything read-after-write
    Wait for positionRemember the write's LSN/GTID and read from a replica only once it has replayed past it
    Monitor lagPostgreSQL pg_stat_replication.replay_lag; MySQL SHOW REPLICA STATUS → Seconds_Behind_Source
    Synchronous replicationPrimary waits for a replica to confirm — no loss on failover, but higher write latency
    ⚠️
    Replicas do not scale writes: every replica must apply every write. For write scale you need partitioning, sharding or a different data model.

    🧬 Schema design: embed or reference?

    • Data is read together with the parent
    • One-to-few, bounded (addresses, line items of an order)
    • Child has no life of its own
    • One read, atomic single-document updates

    Reference

    • Child is queried or updated on its own
    • One-to-many or many-to-many that can grow large
    • Data shared by many parents (a product in many orders)
    • Avoids duplication and the 16 MB limit

    🌐 Replica sets and sharding

    A replica set is a primary plus secondaries (at least three members recommended) that copy the primary's oplog. If the primary fails, the members elect a new one automatically, usually within seconds. Drivers rediscover the primary and retryable writes resend the failed write.

    Sharding splits a collection across several shards (each a replica set). mongos routers send each query to the right shards using metadata on the config servers.

    ⏳ TTL, memory limits and eviction

    A TTL makes a key expire automatically. An eviction policy decides what to remove when Redis reaches its maxmemory limit. They are different mechanisms: TTL is about freshness; eviction is about running out of memory.

    bashSET session:abc '...' EX 1800      # set with a 30-minute TTL

SET product:42 '...' KEEPTTL        # overwrite value but keep the TTL (plain SET clears it)

    1. Request A misses the cache and reads price 10 from the DB.

    🐘 Cache stampedes and hot keys

    A cache stampede (thundering herd, dog-piling) happens when a popular key expires and hundreds of concurrent requests all miss at once and run the same expensive query, overloading the database.

    FixIdea
    Lock / mutexOnly the request that wins SET lock:key token NX PX 5000 recomputes; others wait briefly or serve stale data
    Request coalescingWithin one process, concurrent misses for the same key share one in-flight load (singleflight, DataLoader-style)
    Jittered TTLAdd randomness (300 s ± 10%) so keys written together do not expire together
    Stale-while-revalidateKeep serving the old value past its soft expiry while one worker refreshes it
    Probabilistic early refreshEach read has a small, rising chance of refreshing before expiry (XFetch)
    Pre-warmingLoad known hot keys before an event such as a flash sale
    pythonimport json, random, time, uuid

    val = redis.get(key)
    if val is not None:
        return json.loads(val)
    token = str(uuid.uuid4())

            redis.set(key, json.dumps(data), ex=int(ttl * random.uniform(0.9, 1.1)))

        finally:
            release_lock(f"lock:{key}", token)                   # compare-and-delete (Lua)
    time.sleep(0.05)                                             # someone else is rebuilding

    A hot key is a single key read so often that one Redis node (one thread) becomes the bottleneck — for example the flash-sale product.     🧭 Fundamentals

    How do you choose between a relational database and a NoSQL store for a new service?

    I start from the data and access patterns. If the data is relational, needs multi-entity transactions, constraints and ad-hoc queries (orders, payments, inventory), I choose PostgreSQL or MySQL. If the data is naturally a self-contained document read as a whole, has a varying shape, or needs built-in horizontal write scale, a document store like MongoDB fits. Key-value stores like Redis are for speed by key, not as the source of truth for business records. I default to one general-purpose relational database and add others only for a clear need, because each store adds operational cost and sync complexity.

    Explain the CAP theorem without the usual myths.

    It applies to replicated data. Network partitions are unavoidable, so the real choice is what to do during one: refuse some requests to stay consistent (CP), or keep answering with possibly stale data (AP). 'CA' is not a real option for a distributed system. Outside partitions the trade-off is latency vs consistency (PACELC). Many databases let you tune this per operation, for example MongoDB write concern or Cassandra consistency levels, so labelling a whole product 'CP' or 'AP' is an oversimplification.

    What does ACID mean, and how is durability actually achieved?

    Atomicity (all or nothing), Consistency (constraints always hold), Isolation (concurrent transactions do not interfere, to a chosen level) and Durability (committed data survives crashes). Durability comes from the write-ahead log: on COMMIT the log record is flushed to disk with fsync before success is returned. Data pages are written later; after a crash the database replays the log. Settings like PostgreSQL synchronous_commit = off or InnoDB innodb_flush_log_at_trx_commit = 2 trade some durability for speed.

    Why are database connections pooled, and how do you size a pool?

    Connections are expensive to open (TCP, TLS, auth) and each uses server memory — a whole process in PostgreSQL. A pool reuses a small number of them. Size from the database's capacity, not request concurrency: roughly a small multiple of the DB's cores, divided across all app instances, so instances × pool size stays below max_connections. Extra connections only queue inside the database. With many instances or serverless functions, add PgBouncer or RDS Proxy in front.

    When would you NOT add a cache?

    When data must always be exactly fresh (balances during payment), when the hit ratio would be low (each item read once), when the underlying query can simply be fixed with an index, or when the added invalidation complexity outweighs the gain. A cache also hides problems: if the database cannot survive a cold cache, an outage or flush becomes a full outage. I measure first and fix queries before caching.

    🔄 Relational and transactions

    Compare the default isolation levels of PostgreSQL and MySQL and what they prevent.

    PostgreSQL defaults to READ COMMITTED: each statement sees data committed before it began, so non-repeatable reads and phantoms can occur within a transaction. InnoDB defaults to REPEATABLE READ: plain SELECTs use one snapshot for the whole transaction, while locking reads and writes see the latest data and use next-key locks. Neither default prevents lost updates in read-modify-write code or write skew; for those I use atomic updates, SELECT … FOR UPDATE, optimistic versioning or SERIALIZABLE with retries.

    What is a lost update, and how do you prevent it?

    Two transactions read the same value, compute new values in the application, and the second write overwrites the first. Fixes: do the change atomically in SQL (SET stock = stock - 1); lock the row with SELECT … FOR UPDATE; optimistic locking with a version column where zero updated rows means retry; or a higher isolation level — PostgreSQL REPEATABLE READ raises a serialization error on the second write.

    What is write skew? Give an example.

    Two transactions read an overlapping set of rows, each checks a rule, then each updates different rows, so neither conflicts on a row but together they break the rule. Example: two doctors on call, each checks 'at least one other doctor is on call' and removes themselves. Snapshot isolation allows this. Fixes: SERIALIZABLE (PostgreSQL SSI detects it), locking the rows read with FOR UPDATE, or materialising the rule as a row or constraint.

    Explain MVCC in PostgreSQL and why long transactions are harmful.

    An UPDATE creates a new tuple version and marks the old one with xmax; readers pick visible versions from their snapshot, so readers and writers do not block each other. Dead tuples are removed by (auto)VACUUM once no running snapshot can see them. A long-running or idle-in-transaction session holds an old snapshot, so VACUUM cannot clean anything newer: tables and indexes bloat, index-only scans degrade, and in extreme cases transaction-id wraparound protection kicks in. InnoDB has the equivalent problem with a growing undo history.

    How do you run a zero-downtime schema change on a large table?

    Use expand–contract: add new structures in a backward-compatible way, deploy code that writes both, backfill in small batches, switch reads, then remove the old structure in a later release. Use non-blocking operations (CREATE INDEX CONCURRENTLY, MySQL ALGORITHM=INSTANT/INPLACE or tools like gh-ost), set a short lock_timeout so DDL does not queue behind long queries and block everyone, and rehearse on production-sized data.

    🗂️ Indexing

    How does a B-tree index speed up a query, and what does it cost?

    It keeps keys sorted in a shallow, balanced tree, so finding a key or the start of a range takes a few page reads instead of scanning the table, and sorted leaves give ordered results without a sort step. The cost: every insert, delete and update of an indexed column must maintain each index, indexes take disk and cache memory, add WAL volume, and in PostgreSQL extra indexes reduce HOT updates.

    How do you choose the column order of a composite index?

    Columns used with equality first, then the column used for range or sort. Among equality columns, order matters less for that query, so I consider which prefixes other queries need (leftmost-prefix rule). For WHERE tenant_id = ? AND status = ? AND created_at > ? ORDER BY created_at I would create (tenant_id, status, created_at). Putting the range column earlier would stop later columns narrowing the seek.

    Give reasons an existing index might not be used.

    A function or cast on the column (lower(email), created_at::date); a leading wildcard LIKE '%x'; implicit type conversion such as comparing a VARCHAR column to a number in MySQL; low selectivity so a seq scan is cheaper; the query not using the leading column of a composite index; stale statistics; or the table being so small that a scan is cheaper. I check with EXPLAIN and fix the predicate or add an expression index.

    What is a covering index, and how does it differ between PostgreSQL and InnoDB?

    An index containing every column the query needs, so the table is not visited. In PostgreSQL I add non-key columns with INCLUDE, and the plan shows an Index Only Scan — which also depends on the visibility map being kept up to date by VACUUM. In InnoDB every secondary index already contains the primary key, so the PK comes for free; EXPLAIN shows 'Using index'.

    Why are random UUIDv4 primary keys a problem in InnoDB, and what do you use instead?

    InnoDB clusters the table on the primary key, so random keys insert into random leaf pages: page splits, fragmentation, poor buffer-cache locality and write amplification. Every secondary index also stores the PK, so a 16- or 36-byte key enlarges all of them. Use an auto-increment BIGINT internally, or a time-ordered id such as UUIDv7 or ULID stored as BINARY(16). In PostgreSQL the heap is not clustered, but index locality still favours time-ordered ids.

    🚀 Query optimisation

    Walk me through diagnosing a slow endpoint.

    First, measure: APM traces or logs show whether the time is in the database and which queries — often many fast queries (N+1) rather than one slow one. Second, find heavy queries with pg_stat_statements or the slow query log, sorted by total time. Third, run EXPLAIN (ANALYZE, BUFFERS) on realistic data: look for seq scans with many rows removed by filter, estimates far from actual rows, large sorts or hash spills to disk, and nested loops with many loops. Fix with an index, a rewritten predicate, fresh statistics, fewer columns or batching — then verify the plan and the endpoint latency again.

    What is the N+1 problem, and how do you fix it in an ORM?

    Loading N parent objects with one query and then lazily loading a relation per object issues N more queries. Fix with eager loading: a JOIN for to-one relations (select_related, joinedload, JOIN FETCH) or one batched IN (…) query for collections (prefetch_related, selectinload, @BatchSize), or DataLoader in GraphQL. I add tests or middleware that assert query counts per request so it does not come back.

    Compare nested loop, hash join and merge join.

    A nested loop iterates the outer input and probes the inner for each row — ideal when the outer side is small and the inner has an index, terrible when both are large without one. A hash join builds a hash table on the smaller input and streams the larger one through it — good for large unsorted equality joins, needs memory (work_mem). A merge join walks two inputs sorted on the join key — good when indexes already provide the order or both inputs are large.

    Why is keyset pagination faster than OFFSET, and what are its limits?

    OFFSET makes the database generate and discard all skipped rows, so cost grows with page depth, and inserts shift pages. Keyset uses WHERE (created_at, id) < (last_created_at, last_id) ORDER BY created_at DESC, id DESC LIMIT 20 with a matching index: each page is a cheap index seek and results are stable. Limits: no jumping to an arbitrary page number, and the sort key must be unique (add the id as tie-breaker) and indexed.

    When do you use read replicas, partitioning or sharding?

    Read replicas scale read traffic and isolate reporting but add replication lag, so read-after-write paths go to the primary. Partitioning splits one large table on one server, mainly for pruning and cheap data retention by dropping partitions. Sharding splits data across servers for write and storage scale, at the cost of cross-shard queries and transactions, so it comes last, after query fixes, caching and replicas are exhausted.

    🍃 MongoDB

    How do you decide whether to embed or reference in MongoDB?

    Embed when the child is read with the parent, belongs only to it and is bounded (order line items, a few addresses). Reference when the child is accessed on its own, is shared by many parents, or can grow without bound (comments on a viral post, log entries), keeping the 16 MB document limit and update cost in mind. I design from the most frequent queries, and I sometimes duplicate a few stable fields (extended reference) to avoid a $lookup on hot paths.

    Explain the ESR rule with an example.

    For compound indexes, place Equality fields first, then Sort fields, then Range fields. For find({ userId: 7, score: { $gt: 50 } }).sort({ createdAt: -1 }) the index is { userId: 1, createdAt: -1, score: 1 }. That lets MongoDB walk the userId range in createdAt order and filter score from the index, avoiding a blocking in-memory SORT stage.

    What does explain('executionStats') tell you?

    The winning plan's stages (COLLSCAN vs IXSCAN, FETCH, SORT) and counts: nReturned, totalKeysExamined and totalDocsExamined. In a well-indexed query these are close to each other. A COLLSCAN, a SORT stage or documents examined far above documents returned point to a missing or badly ordered index.

    When are MongoDB transactions needed, and what are their requirements?

    Single-document writes are already atomic, so with good embedding many workflows need no transaction. Multi-document transactions are for updates that must succeed together across documents or collections, such as a transfer plus ledger entry. They require a replica set or sharded cluster, have a default 60-second lifetime, should be short, and should be run with the driver's withTransaction helper so transient errors are retried. Typical settings are write concern majority and read concern snapshot.

    How do you choose a shard key?

    High cardinality, an even spread of values, not monotonically increasing (or hashed if it is), and present in the most common queries so they target one shard instead of broadcasting. For a multi-tenant activity feed, a compound key such as { tenantId: 1, userId: 1 } or a hashed userId spreads load while keeping a user's data together. A plain timestamp or ObjectId key creates a hot shard that receives all inserts.

    ⚡ Redis and caching

    Describe cache-aside and how you keep the cache consistent with the database.

    Reads check the cache, load from the database on a miss and store the result with a TTL. Writes update the database first, then delete the cache key after commit. Deleting (not updating) avoids out-of-order writes leaving an old value. A TTL is always set as a safety net for races, such as a slow reader re-populating a value it read before the update. Where freshness matters more, I use event-driven invalidation from change data capture.

    What is a cache stampede and how do you prevent it?

    When a hot key expires, many concurrent requests miss and all hit the database at once. Prevention: a short distributed lock (SET … NX PX) so one request rebuilds while others wait or get stale data; in-process request coalescing; jittered TTLs so keys do not expire together; stale-while-revalidate or probabilistic early refresh; and pre-warming before known peaks like a flash sale.

    How would you implement rate limiting with Redis?

    Fixed window: INCR rl:{user}:{minute}; if the result is 1, set EXPIRE … 60; reject when over the limit. Do both atomically (a Lua script, MULTI, or EXPIRE … NX) so a crash cannot leave a counter without a TTL. Fixed windows allow bursts at the boundary; a sliding-window log uses a sorted set of timestamps (ZADD, ZREMRANGEBYSCORE, ZCARD), and a token bucket in Lua smooths traffic best.

    Are Redis distributed locks safe?

    A single-instance lock with SET key token NX PX ttl and a compare-and-delete release is fine for efficiency — avoiding duplicate work. It is not a correctness guarantee: the holder can pause past the TTL while another client acquires the lock, and asynchronous replication can lose the lock on failover. Redlock across several nodes is debated for the same timing reasons. For correctness, the protected resource must check a fencing token, or the database must enforce the invariant with constraints or row locks.

    RDB vs AOF — which would you enable?

    RDB takes periodic snapshots: compact, fast restarts, good for backups, but loses changes since the last snapshot. AOF logs every write; with appendfsync everysec you lose about a second at most, at the cost of larger files and background rewrites. For a pure cache I may disable persistence or keep RDB only for warm restarts; for sessions, queues or other data I cannot rebuild I enable AOF (often with RDB too) plus replication and failover.

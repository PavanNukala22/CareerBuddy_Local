    Security Fundamentals for Backend Developers

    The ideas every later module builds on: what we protect, who may do what, and how to store secrets and passwords safely.

    🛡️ What security means: the CIA triad

    Security is about protecting data and systems from people who should not touch them, while keeping them usable for people who should. Most goals fit into three words, called the CIA triad.

    🔒
    Confidentiality
    Only the right people can read data. Tools: encryption (TLS, at rest), access control, not logging secrets.
    🧾
    Integrity
    Data is not changed without permission, and changes are detectable. Tools: signatures, MACs, hashes, audit logs, validation.
    🟢
    Availability
    The system works when users need it. Tools: rate limiting, redundancy, backups, DDoS protection.

    A real incident usually hits one corner hardest. A leaked database dump breaks confidentiality. A tampered price in a request breaks integrity. A flood of login attempts that takes the API down breaks availability.

    IncidentMain property brokenTypical defence
    Customer emails exposed by an open S3 bucketConfidentialityPrivate by default, least-privilege IAM, encryption
    Attacker changes price in a checkout requestIntegrityRecalculate on the server; never trust client values
    Bot sends 50,000 requests per second to /loginAvailabilityRate limiting, WAF, autoscaling, CAPTCHA after failures
    Audit log rows silently deletedIntegrity (and accountability)Append-only / write-once log storage
    📝
    Two more words often join the list: authenticity (the data really came from who it claims) and non-repudiation (the sender cannot later deny sending it). Digital signatures give both.

    🪪 Authentication vs authorisation

    These two words sound alike but answer different questions. Mixing them up causes real bugs.

    Authentication (AuthN)

    Who are you? Proving identity: password, passkey, one-time code, certificate, Google sign-in.

    Failure response: 401 Unauthorized (the name is historical — it really means unauthenticated).

    Authorisation (AuthZ)

    What are you allowed to do? Checking permissions: roles, ownership, scopes, policies.

    Failure response: 403 Forbidden (or 404 to hide that the resource exists).

    Authentication always comes first. You cannot decide what someone may do until you know who they are. But passing authentication proves nothing about permissions: a logged-in user must still be checked on every object they touch.

    EXAMPLE · Same user, two answers

    Priya logs in successfully (authenticated). She calls GET /invoices/42 — invoice 42 belongs to her company, so it returns 200. She then calls GET /invoices/43, which belongs to another company. The server must answer 403 or 404. If it returns the invoice, that is a broken access control bug (IDOR), not an authentication bug.

    ModelIdeaExample
    RBACRole-based: permissions attach to rolesadmin can delete users; viewer can only read
    ABACAttribute-based: rules over user, resource and context attributesAllow if user.dept == doc.dept and during work hours
    ReBACRelationship-based: permissions follow a graphYou can edit a doc if you are a member of its folder's team (Google Zanzibar style)
    Ownership checksResource has an owner or tenant fieldWHERE id = ? AND tenant_id = ?
    💡
    A simple rule: authenticate once per request, authorise per action and per object.

    🧠 Threat modelling, STRIDE and the OWASP Top 10

    Threat modelling means thinking like an attacker before you build. You ask four simple questions: What are we building? What can go wrong? What will we do about it? Did we do a good job?

    Draw the system: clients, APIs, databases, queues, third parties. Mark trust boundaries — places where data crosses from less trusted to more trusted (internet → API, API → database). Most bugs live at these boundaries.

    STRIDE letterThreatProperty violatedBackend example and defence
    SSpoofingAuthenticationForged JWT → verify signature and pin the algorithm
    TTamperingIntegrityEdited request body → server-side validation, signatures
    RRepudiationNon-repudiationUser denies a transfer → signed, tamper-evident audit logs
    IInformation disclosureConfidentialityStack trace in an error → generic errors, log details server-side
    DDenial of serviceAvailabilityHuge JSON body → size limits, rate limiting, timeouts
    EElevation of privilegeAuthorisationUser sets role=admin via mass assignment → allowlist fields
    EXAMPLE · Ten-minute threat model for a password reset
    • Spoofing: attacker requests a reset for someone else → token sent only to the registered email.
    • Information disclosure: response says “no such email” → always reply “If the account exists, we sent a link”.
    • Tampering: guessable token → 128+ bits of randomness from a CSPRNG, stored hashed, single use, 15–60 minute expiry.
    • Denial of service: email flooding → rate limit per account and per IP.

    🧱 Defence in depth, least privilege and secure defaults

    No single control is perfect, so we stack several. That idea is defence in depth. If one layer fails, another still stops or detects the attack.

    🌐
    Edge
    TLS, WAF, DDoS protection, rate limits at the gateway.
    🚪
    Application
    Authentication, per-object authorisation, input validation, output encoding.
    🗄️
    Data
    Parameterised queries, encryption at rest, a DB user with minimal rights.
    🔭
    Detection
    Audit logs, alerts on anomalies, incident response runbooks.

    Least privilege means every user, service and key gets only the permissions it needs, for only as long as it needs them. A reporting service gets a read-only DB user. A CI job gets a short-lived cloud role, not an admin key.

    Secure defaults means the easy path is the safe path: new endpoints require authentication unless explicitly marked public; storage buckets start private; cookies are Secure and HttpOnly by default; debug mode is off in production.

    javascript// Secure default: authentication applies to every route…
app.use(requireAuth);

// …and public routes must opt out explicitly and visibly.
app.get('/health', allowAnonymous, (req, res) => res.send('ok'));
    💡
    Also remember fail closed: if the permission service is down, deny the request rather than allow it.

    🗝️ Secrets management

    A secret is anything that grants access: database passwords, API keys, JWT signing keys, OAuth client secrets, private TLS keys.

    Do notDo instead
    Hard-code secrets in source codeRead them at runtime from the environment or a secrets manager
    Commit .env files to gitAdd .env to .gitignore; commit a .env.example with dummy values
    Share one admin key across all servicesOne credential per service, least privilege, easy to rotate
    Keep a key for yearsRotate on a schedule and immediately after any suspected leak
    Print config at startupLog only that a secret is present, never its value
    pythonimport os

DATABASE_URL = os.environ["DATABASE_URL"]      # fail fast if missing
JWT_PRIVATE_KEY = os.environ["JWT_PRIVATE_KEY"]

    Environment variables are fine for small apps, but larger systems use a vault: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault or Google Secret Manager. Vaults add access policies, audit logs, rotation and even dynamic secrets (a fresh DB password per service, valid for one hour).

    ⚠️
    Deleting a leaked secret in a new commit does not remove it — it stays in git history and in every clone. Treat any committed secret as compromised: revoke and rotate it first, then clean history. Enable secret scanning (GitHub secret scanning, gitleaks) to catch it before the push.

    🔐 Storing passwords safely

    Never store passwords in plain text, and never encrypt them (encryption is reversible — whoever steals the key gets every password). Store a slow, salted password hash.

    AlgorithmUse for passwords?Why
    Argon2id✅ First choice (OWASP)Memory-hard: expensive on GPUs and ASICs; tunable memory, time and parallelism
    scrypt✅ GoodMemory-hard; widely available
    bcrypt✅ Good, very commonDeliberately slow with a cost factor; inputs over 72 bytes are truncated
    PBKDF2-HMAC-SHA256✅ When FIPS is requiredNeeds a high iteration count (OWASP suggests 600,000)
    MD5, SHA-1, SHA-256 (plain)❌ NeverFast by design — billions of guesses per second on a GPU

    A salt is a random value stored with each hash. It makes identical passwords produce different hashes and defeats precomputed rainbow tables. Modern libraries generate the salt for you and store it inside the hash string.

    pythonfrom argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher()                 # Argon2id with sensible defaults

stored = ph.hash("correct horse battery staple")
# '$argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>'

def check(stored_hash: str, attempt: str) -> bool:
    try:
        return ph.verify(stored_hash, attempt)
    except VerifyMismatchError:
        return False

    javascriptimport bcrypt from 'bcrypt';

const hash = await bcrypt.hash(password, 12);   // cost factor 12
const ok = await bcrypt.compare(attempt, hash); // constant-time compare
    💡
    Add a pepper (a secret kept outside the database, e.g. in a vault) for extra protection if only the DB leaks. Re-hash with stronger parameters when a user logs in successfully and their hash uses old settings.

    HTTP is stateless. After login, the server gives the client something to send back on every request: a session ID in a cookie (server-side session) or a token such as a JWT.

    HTTPS and TLS: Protecting Data in Transit

    How TLS keeps traffic private and trustworthy, and how to configure it correctly in front of your APIs.

    🌍 Why HTTPS, and what TLS gives you

    HTTPS is simply HTTP sent inside a TLS (Transport Layer Security) connection. Without it, anyone on the path — public Wi-Fi, a compromised router, an ISP — can read and change traffic, including passwords, cookies and tokens.

    🔒
    Confidentiality
    Traffic is encrypted. An eavesdropper sees only the server name (via SNI) and sizes, not URLs, headers or bodies.
    🧾
    Integrity
    Every record is authenticated (AEAD ciphers). Any change in transit is detected and the connection fails.
    🪪
    Authentication
    The server proves it owns the domain using a certificate signed by a trusted CA. Optionally the client proves itself too (mTLS).

    HTTPS is required for almost everything modern: bearer tokens and session cookies are only safe over TLS, Secure cookies need it, HTTP/2 in browsers and service workers need it, and browsers label plain HTTP pages “Not secure”.

    ⚠️
    TLS protects data in transit only. It does not fix SQL injection, weak passwords or broken access control, and the server still sees the plaintext. Use it everywhere — including internal traffic — but do not treat it as your only control.

    🔑 Symmetric vs asymmetric crypto: the two roles

    TLS uses both kinds of cryptography, each for what it is good at.

    SymmetricAsymmetric (public key)
    KeysOne shared secret keyA key pair: public key (share freely) + private key (keep secret)
    SpeedVery fast — used for bulk dataSlow — used for small operations
    ExamplesAES-GCM, ChaCha20-Poly1305ECDHE (key exchange), RSA / ECDSA / Ed25519 (signatures)
    Role in TLSEncrypts all application data after the handshakeAgrees on the shared key and proves the server's identity

    In TLS 1.3 the client and server run an ephemeral Diffie–Hellman exchange (ECDHE, e.g. X25519). Both sides compute the same secret without ever sending it. The server then signs the handshake with its certificate's private key, proving it is the real owner of the domain. Session keys are derived from the shared secret and used for fast symmetric encryption.

    📝
    Because the keys are ephemeral, TLS 1.3 always gives forward secrecy: stealing the server's private key later does not decrypt recorded past traffic. Modern stacks also add post-quantum hybrid key exchange (X25519 + ML-KEM) to protect against “record now, decrypt later” attacks.

    📜 Certificates, CAs and the chain of trust

    A certificate (X.509) binds a public key to one or more domain names. It is signed by a Certificate Authority (CA). Browsers and operating systems ship a list of trusted root CAs.

    The chain of trust: each certificate is signed by the one above it

    When a client connects, the server sends its leaf certificate plus the intermediates. The client checks:

    1. Each signature in the chain is valid, up to a root it already trusts.
    2. The hostname matches a name in the certificate's Subject Alternative Name (SAN).
    3. The certificate is within its validity dates and not revoked.
    4. The key usage allows TLS server authentication.
    Validation levelWhat the CA checksTypical use
    DV (Domain Validated)You control the domain (HTTP or DNS challenge)Almost all APIs and websites; Let's Encrypt
    OV (Organisation Validated)Domain + the legal organisationSome corporate sites
    EV (Extended Validation)Stricter organisation checksRarely worth it today; browsers no longer show a special bar
    ⚠️
    Never disable certificate verification in client code (verify=False in Python requests, rejectUnauthorized: false or NODE_TLS_REJECT_UNAUTHORIZED=0 in Node). It turns TLS into encryption with an unknown party — a perfect man-in-the-middle. For internal CAs, add the CA certificate to the trust store instead.
    💡
    A common production error is a server that forgets to send the intermediate certificate. Browsers may cope, but API clients fail with “unable to get local issuer certificate”. Serve the full chain (fullchain.pem).

    🤝 The TLS 1.3 handshake (high level)

    TLS 1.3 (RFC 8446, 2018) is faster and simpler than TLS 1.2. A full handshake takes one round trip (1-RTT) instead of two, because the client guesses the key-exchange group and sends its key share immediately.

    TLS 1.3 full handshake: 1 round trip before application data

    0-RTT early data can be replayed by an attacker. Only allow it for safe, idempotent requests such as GET — never for a payment POST.

    ↪️ HSTS, redirects and certificate renewal

    Users often type shop.com without https://. The first request goes over plain HTTP. Redirect it with a 301 (or 308) to HTTPS — and then tell the browser never to use HTTP again with HSTS.

    httpStrict-Transport-Security: max-age=63072000; includeSubDomains; preload
    • max-age — seconds the browser remembers to use HTTPS only (two years here).
    • includeSubDomains — applies to every subdomain. Make sure they all support HTTPS first.
    • preload — signals consent to be added to the browser HSTS preload list (hstspreload.org), so even the very first visit uses HTTPS. Removal is slow, so roll out gradually: start with a short max-age.
    📝
    HSTS matters for browsers. API clients (mobile apps, server code) should simply be configured with https:// URLs; some APIs refuse plain HTTP entirely rather than redirecting, so tokens are never sent in clear even once.

    Let's Encrypt and renewal

    Let's Encrypt is a free, automated CA using the ACME protocol. A client such as Certbot, Caddy, cert-manager (Kubernetes) or Traefik proves domain control and renews automatically. Certificates are short-lived (90 days today, and the industry is moving to even shorter lifetimes), so renewal must be automated and monitored.

    bash# Obtain and install a certificate for nginx, then test auto-renewal
sudo certbot --nginx -d api.shop.com
sudo certbot renew --dry-run
    💡
    Alert on certificate expiry (e.g. 14 days before). Expired certificates are one of the most common causes of avoidable outages.

    🏗️ Where TLS ends: termination, end-to-end and mTLS

    PatternHow it worksProsCons
    TLS termination at the load balancerLB decrypts; forwards plain HTTP to backendsSimple; central certificates; LB can inspect trafficTraffic inside the network is unencrypted
    Re-encryption (TLS bridging)LB decrypts, inspects, then opens a new TLS connection to the backendEncrypted everywhere; LB still routes on contentTwo sets of certificates to manage

    Modern zero-trust guidance says: encrypt internal traffic too. Networks get breached, and cloud “internal” traffic may cross shared infrastructure.

    ⚠️
    When TLS terminates at a proxy, your app sees HTTP. Trust X-Forwarded-Proto and X-Forwarded-For only from your own proxy (e.g. Express app.set('trust proxy', 1)); otherwise clients can spoof their IP and bypass IP-based rate limits.

    Mutual TLS (mTLS)

    In normal TLS only the server shows a certificate. In mTLS the client also presents a certificate, and the server verifies it against a CA it trusts. Both sides are authenticated at the connection level.

    • Service-to-service inside a platform — service meshes such as Istio and Linkerd issue and rotate workload certificates automatically (often with SPIFFE IDs).
    • Partner and banking APIs — open banking standards (FAPI) use mTLS for client authentication.
    • Certificate-bound tokens (RFC 8705) — an access token is tied to the client certificate, so a stolen token is useless without the private key.
    nginxserver {
    listen 443 ssl;
    ssl_certificate         /etc/tls/server-fullchain.pem;
    ssl_certificate_key     /etc/tls/server.key;
    ssl_client_certificate  /etc/tls/partners-ca.pem;  # CA that signs client certs
    ssl_verify_client       on;                        # require a valid client cert
}

    ⚙️ Hardening: versions, ciphers and security headers

    Disable SSL 2/3, TLS 1.0 and TLS 1.1 — they are formally deprecated (RFC 8996) and vulnerable to attacks such as POODLE and BEAST. Support TLS 1.2 and 1.3; for TLS 1.2 allow only ECDHE + AEAD suites.

    nginxssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers off;   # TLS 1.3 suites are all strong
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
    💡
    Use the Mozilla SSL Configuration Generator for a vetted config, and test with SSL Labs (ssllabs.com/ssltest) or testssl.sh.

    JSON Web Tokens (JWT)

    What is inside a JWT, how to verify one properly, and how to run access and refresh tokens safely.

    🧩 JWT structure: header.payload.signature

    A JSON Web Token (RFC 7519) is a compact, URL-safe string that carries claims (statements such as “user 42, expires at 10:15”). The common form is a JWS — a signed token — made of three Base64url parts joined by dots.

    texteyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCIsImtpZCI6ImsxIn0   <- header
.eyJzdWIiOiI0MiIsImV4cCI6MTc2MDAwMDAwMH0              <- payload (claims)
.Gk3…Qw                                                <- signature

    jsonc// header
{ "alg": "RS256", "typ": "JWT", "kid": "k1" }

// payload
{
  "iss": "https://auth.shop.com",
  "sub": "42",
  "aud": "https://api.shop.com",
  "exp": 1760000000,
  "iat": 1759999100,
  "scope": "orders:read"
}

    The signature is computed over base64url(header) + "." + base64url(payload). If anyone changes a single character in the header or payload, verification fails.

    ⚠️
    Base64url is encoding, not encryption. Anyone holding the token can decode and read the payload (try jwt.io). Never put passwords, card numbers or other secrets in a JWT. If the contents must be confidential, use an encrypted JWT (JWE) — or better, keep the data on the server.

    JWS — signed

    Proves integrity and origin. Contents are readable. This is what people usually mean by “JWT”.

    JWE — encrypted

    Provides confidentiality: five parts, payload encrypted for a recipient. Less common; often nested (sign, then encrypt).

    🏷️ Registered claims

    ClaimNameMeaningWho checks it
    issIssuerWho created the token, e.g. https://auth.shop.comMust equal your expected issuer exactly
    subSubjectWho the token is about — a stable user or client IDUsed to look up the principal
    audAudienceWho the token is for — the API(s) that should accept itReject if your API is not in it
    expExpiration timeUnix seconds after which the token is invalidReject if now ≥ exp (small leeway allowed)
    nbfNot beforeToken is not valid before this timeReject if now < nbf
    iatIssued atWhen the token was createdUseful for max-age checks and debugging
    jtiJWT IDUnique ID for this tokenReplay detection and denylists

    Apps also add private claims, such as scope, roles, tenant_id or token_version. Keep them small — the token travels on every request — and namespace custom claims (e.g. https://shop.com/roles) when using a third-party IdP.

    💡
    The aud check is often forgotten. Without it, a token issued for another API by the same issuer will be accepted by yours — a classic token-confusion bug.

    ✍️ Signing algorithms: HS256 vs RS256 / ES256

    AlgorithmTypeWho can verifyWhen to use
    HS256HMAC with SHA-256 — one shared secretAnyone who has the secret — who can also create tokensOne service issues and verifies its own tokens
    RS256RSA signature (PKCS#1 v1.5) + SHA-256Anyone with the public keyMany services verify; only the auth server signs. Widest support
    PS256RSA-PSS + SHA-256Public keyModern RSA choice where supported (required by FAPI)
    ES256ECDSA P-256 + SHA-256Public keySame model as RS256 with smaller keys and signatures
    EdDSAEd25519 signaturesPublic keyFast and robust; check library and IdP support

    The key point: with HS256, verifying requires the same secret that signs. Give that secret to ten microservices and any one of them (or a leak from any one) can mint tokens for any user. With asymmetric algorithms, the private key stays on the authorisation server and APIs only get the public key, usually fetched from a JWKS endpoint and selected by the kid header.

    ⚠️
    An HS256 secret must be long and random — at least 256 bits from a CSPRNG (e.g. openssl rand -base64 32). Short secrets like "secret123" can be brute-forced offline from any captured token.

    ✅ Verifying a JWT properly

    Decoding is not verifying. A secure verification checks all of these:

    1. Pin the algorithm you expect (e.g. only RS256). Never let the token's alg header choose.
    2. Reject alg: none (unsigned tokens).
    3. Verify the signature with the right key (by kid from a trusted JWKS, not a URL in the token).
    4. Check exp and nbf with a small clock-skew leeway (e.g. 30–60 s).
    5. Check iss equals your issuer and aud contains your API.
    6. Then apply your own rules: required scopes, roles, token type, revocation.
    ⚠️
    Algorithm confusion attack: a server verifies RS256 tokens with a library that trusts alg. The attacker changes alg to HS256 and signs with the server's public key as the HMAC secret. A naive library “verifies” it. Pinning the algorithm (and key type) prevents this.

    Rotation: every time a refresh token is used, the server returns a new one and invalidates the old.     OAuth 2.0: Delegated Authorisation

    Let apps act on a user's behalf — or on their own — without ever sharing passwords, using the flows recommended today.

    🎯 The problem OAuth solves, and the four roles

    Before OAuth, a photo-printing site that wanted your cloud photos asked for your cloud password. It then had full access to everything, forever, and you could not revoke it without changing your password.

    OAuth 2.0 (RFC 6749) fixes this with delegated authorisation: you approve a limited permission (a scope), and the app gets an access token — never your password. You can revoke that token at any time.

    🤖 Client credentials and device code

    Client credentials — machine to machine

    When no user is involved — a nightly billing job, a partner's backend calling your API — the client authenticates as itself and receives a token for its own permissions.

    Device authorization grant — TVs and CLIs

    For devices with no browser or keyboard (smart TVs, CLI tools), RFC 8628 defines the device code flow:

    Device authorization grant (RFC 8628)

    The device polls the token endpoint at the given interval, receiving authorization_pending until the user finishes, or slow_down if polling too fast. Examples: gh auth login, az login --use-device-code.

    OpenID Connect: Identity on Top of OAuth 2.0

    🆔 OIDC: an identity layer on OAuth 2.0

    OAuth 2.0 answers “may this app access the API?”. It does not define a standard way to say who the user is. OpenID Connect (OIDC) adds exactly that: a standard ID token, standard user claims, a UserInfo endpoint and automatic discovery.

    OIDC reuses the OAuth flows. You run the authorization code flow with PKCE and simply add openid to the scope. The token response then contains an id_token next to the access_token.

    🎟️ ID token vs access token

    ID token

    For the client (your app). Proves that the user authenticated: who, when, how, and for which client.

    Always a signed JWT. aud is your client ID. Never send it to APIs as an access token.

    Access token

    For the resource server (API). Grants permission to call it, limited by scopes.

    May be a JWT or opaque. The client should treat it as opaque and not parse it for identity.

    ✅ Validating an ID token step by step

    OIDC Core section 3.1.3.7 lists the checks. In practice:

    ID token validation
    1. Verify the signature with a key from the issuer's JWKS, using an allowed algorithm (e.g. RS256). Reject none.
    2. iss must exactly match the expected issuer.
    3. aud must contain your client ID. If there are several audiences, check azp too.
    4. exp must be in the future (allow small clock skew); iat should be recent.
    5. nonce must equal the value you stored in the session for this login (one-time use).
    6. If you requested max_age or a specific acr, check auth_time / acr.
    7. Only then trust the claims and map (iss, sub) to your local user.

    🚪 Nonce, logout and SAML vs OIDC

    Nonce

    The nonce is a random value the client puts in the authorisation request and stores in the user's session. The IdP copies it into the ID token. When the ID token arrives, the client checks they match. This stops an attacker from replaying or injecting an ID token from another login. state protects the redirect; nonce protects the ID token.

    Logout considerations

    Input Validation and Secure APIs

    Treat every input as hostile, stop the classic injection bugs, and check permissions on every object.

    🚧 Never trust input: validate at the boundary

    Input is anything you did not create yourself: body, query string, path parameters, headers, cookies, uploaded files, webhooks, messages from queues — and even data from your own database that a user once wrote. Attackers control all of it; the frontend's validation is only a convenience.

    Allowlist (preferred)

    Define what is allowed and reject everything else: status must be one of pending|paid|shipped; quantity is an integer 1–100.

    Denylist (weak)

    Try to block known bad values: strip <script>, reject ' OR 1=1. Attackers find encodings and variants you did not list.

    Validate type, length, format and range once, at the edge, using a schema. Reject unknown fields. Then pass typed, trusted objects to the rest of the code.

    🎭 CSRF and SSRF

    CSRF — cross-site request forgery

    If your API authenticates with cookies, a malicious site can make the victim's browser send a request to your API, and the browser attaches the cookie automatically. The attacker cannot read the response but can trigger actions (change email, transfer money).

    • SameSite=Lax or Strict cookies — the browser does not send them on cross-site POSTs. Strong baseline.
    • CSRF tokens — a random token in the page/session that must be echoed in a header or form field (synchroniser token or signed double-submit cookie).
    • Check the Origin (or Sec-Fetch-Site) header on state-changing requests.
    • Never change state on GET.
    • APIs using Authorization: Bearer headers are not exposed to classic CSRF, because browsers do not add that header automatically.

    SSRF — server-side request forgery

    A feature fetches a URL supplied by the user (“import image from URL”, webhooks, PDF renderers). An attacker supplies an internal address instead: http://169.254.169.254/latest/meta-data/iam/security-credentials/ (cloud metadata), http://localhost:6379 or http://10.0.0.5/admin.

    DefenceDetail
    Allowlist destinationsOnly permitted hosts/domains and schemes (https)
    Resolve and check the IPBlock private, loopback, link-local and metadata ranges (IPv4 and IPv6) — after DNS resolution, and pin the resolved IP to stop DNS rebinding
    Do not follow redirects blindlyRe-validate each hop or disable redirects
    Network egress controlsRun fetchers in a segment that cannot reach internal services
    Harden cloud metadataRequire IMDSv2 on AWS (session token, hop limit 1)

    Interview Preparation

    Click a question to reveal a model answer.

    🛡️ Fundamentals

    What is the difference between authentication and authorisation?

    Authentication proves identity (password, passkey, SSO); failure is 401. Authorisation decides what that identity may do — roles, scopes, ownership; failure is 403 (or 404 to hide existence). Authentication happens once per request; authorisation must be checked per action and per object.

    How should a backend store passwords?

    With a slow, salted, memory-hard password hash: Argon2id first, or scrypt / bcrypt (PBKDF2 when FIPS is required). The library generates a unique salt and stores it in the hash string. Never plain text, never reversible encryption, never fast hashes like MD5 or SHA-256. Optionally add a pepper from a vault, re-hash when parameters are upgraded, and compare in constant time via the library's verify function.

    Which cookie attributes would you set on a session cookie and why?

    HttpOnly so JavaScript (and XSS) cannot read it; Secure so it only travels over HTTPS; SameSite=Lax or Strict to block cross-site sending (CSRF); Path=/ and the __Host- prefix to prevent subdomain overrides; a sensible Max-Age. Also regenerate the session ID at login and destroy it server-side on logout.

    How do you manage secrets in a backend application?

    Never in source code or git. Inject at runtime via environment variables or, better, a secrets manager (Vault, AWS Secrets Manager, Azure Key Vault) with access policies and audit logs. One credential per service with least privilege, regular rotation, secret scanning in CI and push protection. If a secret is committed, revoke and rotate it immediately — deleting the commit is not enough.

    Walk me through threat modelling a new feature.

    Draw a data-flow diagram with clients, services, stores and trust boundaries. For each element and boundary, apply STRIDE: spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege. Rank threats by likelihood and impact, choose mitigations (authN, authZ, validation, rate limits, logging), turn them into tickets and tests, and revisit when the design changes.

    🔒 HTTPS / TLS

    What does TLS provide, and what does it not provide?

    Confidentiality (encryption), integrity (AEAD detects tampering) and server authentication (certificate chain to a trusted CA, hostname check), optionally client authentication with mTLS. It does not protect data at rest, at the endpoints, or against application bugs like injection or broken access control.

    Explain the TLS 1.3 handshake at a high level.

    The client sends ClientHello with supported ciphers, SNI, ALPN and an ECDHE key share. The server replies with ServerHello and its key share; both derive handshake keys. The server sends its certificate, a CertificateVerify signature and Finished — all encrypted. The client verifies the chain and signature, sends Finished, and application data flows. One round trip; forward secrecy always; only AEAD ciphers.

    What is HSTS and what is the preload list?

    Strict-Transport-Security tells browsers to use HTTPS only for the host (and optionally subdomains) for max-age seconds, preventing SSL-stripping after the first visit. The preload list is built into browsers so even the first visit is HTTPS; you opt in with preload and submission to hstspreload.org. Removal is slow, so ensure all subdomains support HTTPS first.

    Where should TLS terminate in a cloud deployment?

    Commonly at the load balancer or API gateway for central certificate management and L7 routing. But traffic behind it should also be encrypted (re-encryption or a service mesh with mTLS) under zero-trust principles. If terminating at a proxy, trust X-Forwarded-* headers only from that proxy.

    What is mTLS and when would you use it?

    Mutual TLS: the client also presents a certificate that the server validates against a trusted CA. Use it for service-to-service authentication (service meshes like Istio with automatic rotation), partner and banking APIs (FAPI), and certificate-bound access tokens (RFC 8705). It requires PKI management: issuance, rotation and revocation.

    🎟️ JWT

    How do you securely verify a JWT?

    Pin the allowed algorithm(s) in code and reject none; verify the signature with a trusted key (by kid from a configured JWKS); check exp/nbf with small leeway; check iss exactly and that aud contains your API; require needed claims; then enforce scopes/roles and any revocation check. Use a maintained library (jose, PyJWT, Nimbus) — never just decode.

    HS256 or RS256 — which would you choose?

    HS256 uses one shared secret for signing and verifying, so anyone who can verify can also forge — fine when one service issues and consumes its own tokens. RS256/ES256 sign with a private key held only by the auth server; many APIs verify with the public key from JWKS, and keys can rotate via kid. For multi-service or third-party scenarios, choose asymmetric.

    How do you revoke a JWT before it expires?

    Keep access tokens short (5–15 min) and revoke the refresh token. For immediate revocation add a lookup: a denylist of jti in Redis until expiry, a per-user token_version bumped on logout-all or password change, or token introspection with opaque tokens. Each adds state — which is the trade-off against pure statelessness.

    Explain refresh token rotation and reuse detection.

    Each refresh returns a new refresh token and invalidates the old one, all in one family. If an already-used refresh token is presented again, either the attacker or the user holds a stolen copy, so the server revokes the whole family and forces re-authentication. RFC 9700 requires rotation or sender-constraining (DPoP/mTLS) for public clients.

    Where should a browser app store tokens?

    Ideally nowhere in the browser: use a BFF that keeps tokens server-side and gives the SPA an HttpOnly; Secure; SameSite session cookie. If the SPA must hold tokens, keep the access token in memory and avoid localStorage, which any XSS can read. Cookie-based approaches need CSRF defences. No storage choice fixes XSS itself.

    🔁 OAuth 2.0

    What problem does OAuth 2.0 solve? Is it an authentication protocol?

    Delegated authorisation: letting a client access a user's resources with limited scope without the user sharing their password, revocable at any time. It is not an authentication protocol — an access token is meant for the API, not as proof of identity to the client. OpenID Connect adds authentication.

    Describe the authorization code flow with PKCE.

    The client creates a random code_verifier and its S256 code_challenge plus a state, then redirects to the authorisation endpoint. The user logs in and consents; the AS redirects back to the registered redirect_uri with a short-lived code. The client checks state and POSTs the code and verifier to the token endpoint; the AS checks the hash matches the challenge and issues tokens. A stolen code is useless without the verifier.

    Why are the implicit and password grants deprecated?

    Implicit returns tokens in the URL fragment — exposed to history, referrers and injection, with no sender binding. The password grant makes the client handle the user's credentials, breaking MFA/SSO and normalising phishing. RFC 9700 and OAuth 2.1 replace both with authorization code + PKCE.

    Confidential vs public clients?

    Confidential clients run on servers and can keep a secret, so they authenticate at the token endpoint (client_secret_basic, private_key_jwt, mTLS). Public clients — SPAs, mobile and desktop apps — cannot, because any secret ships to users. They rely on PKCE, exact redirect URIs and refresh-token rotation or DPoP.

    How would you secure machine-to-machine access for a partner?

    Register a confidential client for the partner and use the client credentials grant with narrowly scoped permissions. Prefer private_key_jwt or mTLS over a shared secret; issue short-lived tokens with aud set to your API; authorise by client ID and scope; rate limit per client; log usage; support key rotation and quick revocation.

    🆔 OpenID Connect

    What does OIDC add to OAuth 2.0?

    A standard authentication layer: the openid scope, the ID token (a signed JWT about the login), standard claims (sub, email, name), the UserInfo endpoint, discovery via /.well-known/openid-configuration, JWKS, nonce, and session/logout specifications.

    ID token vs access token — what is each for?

    The ID token is for the client: it tells the client who logged in, with aud = client ID. The access token is for the resource server: it authorises API calls with scopes and aud = API. Never send ID tokens to APIs as bearer tokens, and never use access tokens as proof of login.

    How do you validate an ID token?

    Verify the signature using the issuer's JWKS key with an expected algorithm; check iss exactly; aud contains your client ID (and azp if several audiences); exp and iat are sensible; nonce matches the session value; optionally auth_time/acr. Then map (iss, sub) to a local account.

    What is the nonce for, and how is it different from state?

    state protects the authorisation response/redirect against CSRF and carries client context. nonce is copied into the ID token and binds that token to the login attempt in this browser session, preventing replay or injection of an ID token from elsewhere. Both are random and single-use.

    How would you handle logout in an SSO setup?

    Always destroy the local session and revoke refresh tokens. Optionally use RP-initiated logout to end the IdP session (end_session_endpoint with id_token_hint). To react to logouts elsewhere, implement back-channel logout: the IdP posts a signed logout token and you terminate matching sessions. Front-channel logout is unreliable with third-party cookie blocking.

    🚧 Input validation and secure APIs

    How do you prevent SQL injection?

    Use parameterised queries or an ORM's safe query builder for all values; never build SQL by string concatenation. Map identifiers like sort columns through an allowlist. Add defence in depth: input validation, least-privileged DB users and avoiding detailed DB errors in responses.

    What is IDOR/BOLA and how do you prevent it?

    The API returns or modifies an object based on an ID in the request without checking that the caller may access it. Prevent it by scoping every query to the caller's user/tenant, centralising authorisation policies, checking every endpoint including nested and bulk ones, and writing cross-user tests. Unguessable IDs help but are not access control.

    Explain XSS vs CSRF and the main defences for each.

    XSS runs attacker script inside your origin — defend with context-aware output encoding, safe templating, HTML sanitisation and CSP. CSRF makes the victim's browser send authenticated requests from another site — defend with SameSite cookies, CSRF tokens, Origin checks, and no state change on GET. Bearer-header APIs avoid classic CSRF.

    What is SSRF and how do you defend against it?

    The server fetches a user-supplied URL that points to internal resources (cloud metadata at 169.254.169.254, localhost services). Defend with destination allowlists, resolving and blocking private/link-local IPs (and pinning the resolved IP against DNS rebinding), controlling redirects, isolating fetchers with egress rules and enforcing IMDSv2.

    How do you protect a login endpoint against brute force and credential stuffing?

    Rate limit per account and per IP with increasing delays rather than permanent lockouts; add MFA or passkeys; check passwords against breached-password lists; use bot detection or CAPTCHA after failures; return the same generic message and similar timing for unknown users and wrong passwords; log and alert on spikes.

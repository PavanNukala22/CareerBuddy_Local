    Module 01 · Security Basics

    Security & Authentication Foundations

    Start from zero: what authentication and authorization are, the building blocks, and where each topic in this course fits.

    🔐 What is Authentication vs Authorization?

    Authentication (AuthN) proves who you are. Authorization (AuthZ) decides what you may do. Always authenticate first, then authorize every request.

    AuthenticationAuthorization
    QuestionWho are you?Are you allowed to do this?
    HappensAt login / token issueOn every request
    Failure code401 Unauthorized403 Forbidden
    ExamplePassword, OTP, passkeyRole = instructor can edit course
    EXAMPLE · LMS

    A student logs in (AuthN). Opening GET /courses/7/grades is allowed only if they are enrolled in course 7 (AuthZ).

    🗂️ Types of Authentication

    TypeHow it worksBest for
    Session + cookieServer stores session; browser holds session IDServer-rendered web apps
    Token (JWT)Client sends signed token in Authorization headerAPIs, SPAs, mobile
    API keyStatic secret identifies a client appServer-to-server, low risk
    Basic AuthBase64 user:password each request (only over HTTPS)Quick internal tools
    SSO / FederatedTrusted identity provider logs the user in (OIDC, SAML)Many apps, one login
    MFA / PasskeysTwo or more factors: know, have, areHigh-value accounts
    ⚠️
    Passwords must be stored with a slow salted hash: Argon2id, bcrypt or scrypt. Never plain text, never fast hashes like MD5/SHA-1.

    Module 02 · HTTPS / TLS

    HTTPS & TLS

    What encrypts web traffic, how certificates and the handshake work, and how to configure it safely.

    🔒 What is HTTPS / TLS?

    HTTPS = HTTP over TLS (Transport Layer Security, successor of SSL). It gives three guarantees:

    🙈
    Confidentiality
    Eavesdroppers cannot read data.
    ✅
    Integrity
    Data cannot be altered unnoticed.
    🪪
    Authenticity
    You are talking to the real server.

    🗂️ Types and Versions

    ItemTypes / versionsNotes
    ProtocolSSL 2/3, TLS 1.0, 1.1Deprecated, disable
    TLS 1.2Acceptable with strong ciphers
    TLS 1.3Preferred; faster, safer
    Certificate validationDV, OV, EVDV = domain only; OV/EV verify organization
    Certificate scopeSingle, Wildcard, SAN/multi-domain*.lms.com covers one level
    Mutual TLS (mTLS)Client also presents a certificateService-to-service trust
    EncryptionSymmetric (AES-GCM, ChaCha20) + asymmetric key exchange (ECDHE)Asymmetric sets up, symmetric carries data

    🤝 The TLS 1.3 Handshake

    1) ClientHello: versions, ciphers, key share. 2) ServerHello: chosen cipher, key share, certificate, signature. 3) Client verifies the certificate chain, both derive the same session keys. 4) Encrypted application data flows (1 round trip).

    Chain levelRole
    Root CATrusted by OS/browser
    Intermediate CASigned by root, issues leaf
    Leaf (server) certificateYour domain; browser checks name, dates, signature, revocation

    ⚙️ Practice: Secure Server Config

    nginxserver {
  listen 443 ssl http2;
  server_name lms.example.com;
  ssl_protocols TLSv1.2 TLSv1.3;
  ssl_certificate     /etc/ssl/lms/fullchain.pem;
  ssl_certificate_key /etc/ssl/lms/privkey.pem;
  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
}
server { listen 80; return 301 https://$host$request_uri; }
    • Redirect HTTP → HTTPS; send HSTS so browsers never use HTTP again.
    • Automate renewal with ACME (Let's Encrypt/certbot).
    • Set cookies with Secure; HttpOnly; SameSite=Lax.

    🧠 Expert Notes

    • Forward secrecy: ECDHE keys are ephemeral, so a stolen private key cannot decrypt past traffic.
    • OCSP stapling and short-lived certificates improve revocation.
    • Certificate pinning is risky in browsers; prefer Certificate Transparency monitoring.
    • Terminate TLS at the load balancer, but re-encrypt (or mTLS) inside untrusted networks.
    • Test with SSL Labs or openssl s_client -connect host:443.

    Module 03 · Input Validation

    Input Validation

    Treat all input as hostile: validate, sanitize and encode so attackers cannot inject code or data.

    🛡️ What is Input Validation?

    Input validation checks that data matches what you expect (type, length, format, range) before using it. It is the first defense against injection, the most common web vulnerability family.

    ValidationAccept only well-formed data; reject the rest.
    SanitizationClean or strip dangerous parts of input.
    Output encodingEscape data for where it is placed (HTML, SQL, URL).

    🗂️ Types of Validation

    TypeChecksExample
    SyntacticFormat, type, lengthEmail regex, max 254 chars
    SemanticMeaning in contextStart date before end date
    Allowlist (good)Only known-good valuesrole in [student, teacher]
    Denylist (weak)Block known-badEasy to bypass
    Client-sideUX hints onlyNever a security control
    Server-sideAuthoritativeAlways required

    💥 Common Attacks it Prevents

    AttackWhat happensDefense
    SQL injectionInput changes the queryParameterized queries
    XSSScript runs in victim browserOutput encoding, CSP
    Command injectionInput reaches the shellAvoid shell; allowlist args
    Path traversal../../etc/passwdCanonicalize, restrict directory
    SSRFServer fetches attacker URLAllowlist hosts, block internal IPs
    Mass assignmentExtra fields set isAdminPick allowed fields only

    💻 Practice: Safe Code

    Vulnerable vs safe query:

    javascript// ❌ string concatenation -> SQL injection
db.query("SELECT * FROM users WHERE email='" + email + "'");

// ✅ parameterized query
db.query("SELECT * FROM users WHERE email = $1", [email]);

    Schema validation (Zod) with allowlisted fields:

    javascriptconst Signup = z.object({
  email: z.string().email().max(254),
  password: z.string().min(12).max(128),
  role: z.enum(["student","teacher"])
}).strict();            // rejects unknown fields
const data = Signup.parse(req.body);

    🧠 Expert Notes

    • Canonicalize (decode, normalize Unicode) before validating, or encoded payloads slip through.
    • Encode output by context: HTML body, attribute, JavaScript, URL each differ.
    • Beware ReDoS: catastrophic regex backtracking; set input length limits.
    • File uploads: check size, magic bytes, store outside web root, random names.
    • Layer it: validation + parameterization + least-privilege DB user + CSP + WAF.

    Module 04 · JWT

    JSON Web Tokens (JWT)

    A compact, signed token that carries claims, widely used for stateless API authentication.

    🎫 What is a JWT?

    A JWT (RFC 7519) is a URL-safe string of three Base64url parts: header.payload.signature. The signature proves it was not changed; the payload is encoded, not encrypted.

    jsonheader  : { "alg": "RS256", "typ": "JWT", "kid": "key-2026-10" }
payload : { "iss": "https://auth.lms.com", "sub": "user_42",
            "aud": "lms-api", "exp": 1790000000, "role": "student" }
signature: RSA-SHA256(base64url(header) + "." + base64url(payload))

    🗂️ Types and Claims

    KindMeaning
    JWS (signed)Integrity + authenticity; most common
    JWE (encrypted)Payload confidential
    Access tokenShort-lived (5–15 min), sent to API
    Refresh tokenLong-lived, used only to get new access tokens
    HS256HMAC, one shared secret (both sides can forge)
    RS256 / ES256 / EdDSAPrivate key signs, public key verifies (preferred across services)
    issIssuer
    subSubject (user id)
    audIntended audience
    exp / nbf / iatExpiry, not-before, issued-at
    jtiUnique token id

    💻 Practice: Issue and Verify

    javascriptimport jwt from "jsonwebtoken";
const token = jwt.sign({ role: "student" }, PRIVATE_KEY,
  { algorithm: "RS256", subject: "user_42", issuer: "https://auth.lms.com",
    audience: "lms-api", expiresIn: "10m", keyid: "key-2026-10" });

// verify: ALWAYS pin algorithm, issuer, audience
const claims = jwt.verify(token, PUBLIC_KEY,
  { algorithms: ["RS256"], issuer: "https://auth.lms.com", audience: "lms-api" });

    ⚠️ Pitfalls

    MistakeRiskFix
    Accepting alg: noneUnsigned token acceptedPin allowed algorithms
    Algorithm confusion (RS→HS)Public key used as HMAC secretFixed algorithm per key
    Secrets in payloadAnyone can decode itStore only needed claims
    Long expiry, no revocationStolen token works for daysShort TTL + refresh rotation
    Token in localStorageXSS can steal itHttpOnly Secure cookie or memory

    🧠 Expert Notes

    • JWKS: publish public keys at /.well-known/jwks.json; pick by kid; rotate keys with overlap.
    • Refresh rotation: issue a new refresh token each use; reuse of an old one means theft, revoke the whole family.
    • Revocation: denylist by jti, or short TTL plus session check for sensitive actions.
    • Sender-constrained tokens (DPoP, mTLS) stop replay of stolen tokens.
    • JWT is a format, not a protocol; do not use it where a plain session is simpler.

    Module 05 · OAuth 2.0

    OAuth 2.0

    A framework that lets an app access resources on a user's behalf without ever seeing their password.

    🤝 What is OAuth 2.0?

    OAuth 2.0 (RFC 6749) is a delegated authorization framework. Example: "Allow CalendarSync to read your LMS course schedule" without sharing your password.

    RoleMeaningLMS example
    Resource OwnerThe userStudent
    ClientApp requesting accessCalendarSync
    Authorization ServerAuthenticates user, issues tokensauth.lms.com
    Resource ServerAPI holding the datalms-api
    ScopePermission requestedcourses.read

    🗂️ Grant Types

    GrantUse forStatus
    Authorization Code + PKCEWeb, SPA, mobile with a userRecommended
    Client CredentialsMachine-to-machine, no userRecommended
    Device CodeTVs, CLIs, limited inputRecommended
    Refresh TokenGet new access tokenRecommended
    ImplicitToken in URL fragmentDeprecated
    Password (ROPC)App sees user passwordDeprecated
    💡
    Client types: confidential clients can keep a secret (server apps); public clients cannot (SPA, mobile), so they must use PKCE.

    🔁 Authorization Code + PKCE Flow

    1. Client creates code_verifier (random) and code_challenge = BASE64URL(SHA256(verifier)).
    2. Redirect user to the authorization endpoint (below).
    3. User logs in and consents; server redirects back with code and state.
    4. Client checks state, then POSTs code + code_verifier to the token endpoint.
    5. Server returns access_token (+ refresh_token). Client calls the API with Authorization: Bearer ….
    httpGET /authorize?response_type=code&client_id=calsync
  &redirect_uri=https://calsync.app/cb&scope=courses.read
  &state=xyz123&code_challenge=E9Melhoa...&code_challenge_method=S256

POST /token
grant_type=authorization_code&code=SplxlOBe&redirect_uri=https://calsync.app/cb
&client_id=calsync&code_verifier=dBjftJeZ4CVP...

    💻 Practice: Protect an API

    javascriptfunction requireScope(scope) {
  return (req, res, next) => {
    const t = req.headers.authorization?.split(" ")[1];
    if (!t) return res.sendStatus(401);
    try {
      const c = jwt.verify(t, PUBLIC_KEY, { algorithms:["RS256"], audience:"lms-api" });
      if (!c.scope.split(" ").includes(scope)) return res.sendStatus(403);
      req.user = c; next();
    } catch { res.sendStatus(401); }
  };
}
app.get("/courses", requireScope("courses.read"), listCourses);

    🧠 Expert Notes

    • Match redirect_uri exactly; open redirects lead to code theft.
    • Always validate state (CSRF) and bind tokens to an aud.
    • Opaque tokens + introspection (RFC 7662) allow instant revocation; JWT access tokens are faster to verify.
    • Hardening: PAR, RAR, DPoP, mTLS-bound tokens; OAuth 2.1 consolidates best practice (PKCE mandatory, no implicit/ROPC).
    • Minimal scopes, short access-token life, rotating refresh tokens.

    Module 06 · OpenID Connect

    OpenID Connect (OIDC)

    The identity layer on top of OAuth 2.0: how "Sign in with Google" tells your app who the user is.

    🪪 What is OpenID Connect?

    OAuth 2.0 alone says what an app may access, not who logged in. OIDC adds a standard login result: the ID token (a JWT), plus a /userinfo endpoint.

    OAuth 2.0OpenID Connect
    PurposeAuthorizationAuthentication
    Key tokenAccess tokenID token (+ access token)
    Audience of tokenResource server (API)The client app
    Trigger scopeCustom (courses.read)openid (+ profile, email)

    🗂️ Types of Flows and Terms

    FlowNotes
    Authorization Code (+PKCE)Recommended for all clients
    ImplicitLegacy, avoid
    HybridCode + token in front channel, special cases
    OP / IdPOpenID Provider, e.g. Google, Okta, Keycloak
    RPRelying Party: your app
    Discovery/.well-known/openid-configuration lists endpoints and keys
    nonceRandom value binding ID token to the session (replay defense)
    Standard claimssub, name, email, email_verified, picture

    ✅ ID Token and Validation

    json{ "iss":"https://accounts.google.com", "sub":"110169484474386276334",
  "aud":"your-client-id", "exp":1790000000, "iat":1789996400,
  "nonce":"n-0S6_WzA2Mj", "email":"asha@example.com", "email_verified":true }

    The client must verify, in order:

    1. Signature, using the key from the provider's JWKS.
    2. iss equals the expected provider.
    3. aud contains your client_id.
    4. exp not passed; nonce matches.
    🚫
    Never send an ID token to your API as an access token. Identify users by the pair (iss, sub), not by email.

    💻 Practice: Sign-in Request

    httpGET /authorize?response_type=code&client_id=lms-web
  &redirect_uri=https://lms.com/callback&scope=openid%20profile%20email
  &state=abc&nonce=n-0S6_WzA2Mj&code_challenge=...&code_challenge_method=S256

    Then exchange the code at /token; the response includes id_token. Validate it with a library (e.g. openid-client, Authlib), do not hand-roll.

    🧠 Expert Notes

    • Logout: RP-initiated, front-channel and back-channel logout keep SSO sessions in sync.
    • acr / amr claims tell you how strongly the user authenticated; request step-up MFA when needed.
    • Federation: map external identities to local accounts safely (no auto-linking on unverified email).
    • OIDC vs SAML: OIDC is JSON/JWT and mobile-friendly; SAML is XML and common in enterprise SSO.
    • Keycloak, Auth0, Okta, Entra ID and Cognito are production OIDC providers; avoid building your own.

    🏫 Scenario: LearnHub LMS API

    LearnHub has a React SPA, a mobile app, a Node.js API, and a partner tool (GradeSync) that must read grades nightly. Design the security and auth.

    1️⃣ Task 1 · Short Answers

    ✍️ Which OAuth 2.0 grant should the SPA, the mobile app and GradeSync use, and why?
    Model answer: SPA and mobile: Authorization Code + PKCE (public clients cannot keep a secret). GradeSync: Client Credentials (no user, machine-to-machine) with a narrow scope such as grades.read.
    ✍️ List 4 server-side checks for an incoming ID token.
    Model answer: Verify signature via JWKS; iss matches; aud equals our client_id; exp valid and nonce matches.

    2️⃣ Task 2 · Choose and Decide

    Q. Where should the SPA keep its access token?
    • A localStorage
    • B In memory (or HttpOnly Secure cookie via a backend)
    • C In the URL
    • D In a JS global on window
    Q. A login form builds SQL with string concatenation. Best fix?
    • A Escape quotes manually
    • B Client-side validation
    • C Parameterized queries
    • D Block the word SELECT
    Q. The API receives a valid token whose aud is other-api. What now?
    • A Accept it
    • B Reject with 401
    • C Accept for read-only
    • D Ask the user
    Q. Browsers should be told to always use HTTPS with…
    • A CORS header
    • B X-Frame-Options
    • C Strict-Transport-Security
    • D Referrer-Policy

    3️⃣ Task 3 · Review a Design

    ✍️ A teammate proposes: HS256 JWTs valid 30 days, stored in localStorage, alg read from the token header. List the problems and fixes.
    Model answer: Header-driven alg allows none/confusion attacks: pin the algorithm. 30 days is too long: 10-minute access + rotating refresh token. localStorage is XSS-exposed: use memory or HttpOnly cookie. HS256 shares one secret across services: prefer RS256/ES256 with JWKS.

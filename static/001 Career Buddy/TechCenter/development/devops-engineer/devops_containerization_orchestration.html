    Module 01 · Containerization

    Containerization Foundations

    What containers are, how they differ from VMs, and the vocabulary you need before touching Docker, Kubernetes or Helm.

    📦 What is Containerization?

    Containerization packages an application together with everything it needs to run — code, runtime, libraries, config — into one portable unit called a container. The same container runs identically on a laptop, a test server and a cloud VM, which kills the classic "it works on my machine" problem.

    Orchestration is the layer above: once you have hundreds of containers you need something to schedule them onto machines, restart them when they crash, scale them, connect them and roll out new versions without downtime. That "something" is mostly Kubernetes (K8s).

    🐳
    Docker
    Builds and runs containers on a single host.
    ☸️
    Kubernetes
    Orchestrates containers across a cluster of machines.
    ⎈
    Helm
    Package manager for Kubernetes — templates and versions your manifests.
    The stack, bottom to top
    Hardware / Cloud VMphysical or virtual machine
    Host OS + Linux kernelshared by every container (namespaces + cgroups)
    Container runtimecontainerd / CRI-O / runc
    Docker images → containersyour packaged apps
    Kubernetesschedules, heals, scales, networks
    Helmpackages & releases the whole app
    Containers share the host kernel — that is why they start in milliseconds.

    🆚 Containers vs Virtual Machines

    Virtual MachineContainer
    IsolationFull guest OS per VM (hypervisor)Process-level isolation on a shared kernel
    SizeGBsMBs (often 10–300 MB)
    StartupMinutesMilliseconds to seconds
    DensityFew per hostDozens–hundreds per host
    Security boundaryStrong (separate kernel)Weaker by default — needs hardening
    Best forLegacy apps, strong tenant isolation, different OSMicroservices, CI/CD, scalable stateless apps

    How isolation really works

    • Namespaces — give a process its own view of PIDs, network, mounts, hostname, users.
    • cgroups (control groups) — limit CPU, memory, I/O a process may use.
    • Union file system (OverlayFS) — stacks read-only image layers with one thin writable layer.
    💡
    Interview one-liner: a container is just a Linux process with namespaces for isolation and cgroups for limits.

    Docker

    Build, ship and run containers — from your first docker run to multi-stage builds and hardened production images.

    🐳 What is Docker?

    Docker is the most popular platform to build, ship and run containers. Its main pieces: the Docker Engine (daemon dockerd + REST API), the CLI (docker), images, registries and Docker Compose for multi-container apps.

    Docker workflow
    Dockerfileinstructions
    →
    docker buildcreates image
    →
    Imagelayers
    →
    docker pushto registry
    →
    docker runcontainer
    Build once, run anywhere.

    Your first containerBasic

    bashdocker run hello-world                 # pull + run a test image
docker run -d -p 8080:80 --name web nginx   # run nginx in background, map ports
docker ps                              # running containers
docker ps -a                           # all containers incl. stopped
docker logs -f web                     # follow logs
docker exec -it web bash               # shell inside container
docker stop web && docker rm web       # stop and delete
docker images                          # list local images

    -d detached · -p host:container publish a port · --name readable name · -it interactive terminal · --rm auto-delete on exit.

    📝 Dockerfile — Basic to Expert

    Basic DockerfileBasic

    dockerfileFROM python:3.12-slim          # base image
WORKDIR /app                   # working directory
COPY requirements.txt .        # copy deps list first (cache!)
RUN pip install --no-cache-dir -r requirements.txt
COPY . .                       # then copy source
EXPOSE 8000                    # documentation only
CMD ["python", "app.py"]       # default command
    InstructionPurpose
    FROMBase image (every Dockerfile starts here)
    RUNExecute a command at build time → creates a layer
    COPY / ADDCopy files in (prefer COPY; ADD also extracts tar & fetches URLs)
    ENV / ARGRuntime env var / build-time variable
    CMDDefault command — easily overridden
    ENTRYPOINTFixed executable; CMD supplies default args
    USERSwitch to non-root user
    HEALTHCHECKCommand Docker runs to test health

    Layer cachingIntermediate

    Every instruction is a layer, and Docker reuses unchanged layers. Order matters: put rarely-changing steps (installing dependencies) before frequently-changing steps (copying source). That is why requirements.txt is copied first above.

    Multi-stage build — smaller & safer imagesExpert

    dockerfile# ---- stage 1: build ----
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

# ---- stage 2: runtime (tiny, no compiler, no shell) ----
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
USER nonroot
ENTRYPOINT ["/app"]
    ✅
    Multi-stage builds routinely shrink images from ~1 GB to ~15 MB and remove build tools an attacker could use.
    📌
    CMD vs ENTRYPOINT: ENTRYPOINT ["curl"] + CMD ["--help"] → docker run img runs curl --help, while docker run img https://x.io runs curl https://x.io. Always use the exec form (JSON array) so signals reach your process.

    Expert: image hardening checklistExpert

    • Pin versions/digests (nginx@sha256:…) — never :latest in production.
    • Run as non-root, use --read-only root FS, drop capabilities (--cap-drop ALL).
    • Scan images in CI (Trivy, Grype, Docker Scout); sign with cosign; generate an SBOM.
    • Use .dockerignore to keep .git, secrets and node_modules out of the build context.
    • Never bake secrets into layers — use BuildKit secrets: RUN --mount=type=secret,id=npm …
    • Set resource limits: --memory 512m --cpus 1.

    Module 03 · Orchestration

    Kubernetes (K8s)

    Architecture, workloads, networking, storage, autoscaling and security — the full journey from your first Pod to production-grade clusters.

    ☸️ What is Kubernetes?

    Kubernetes (K8s) is an open-source container orchestrator created by Google and donated to the CNCF. You describe the desired state ("run 3 copies of this image, expose them on port 80") and K8s continuously works to make reality match — the reconciliation loop.

    Cluster architecture
    Control Planekube-apiserver · etcd · kube-scheduler · kube-controller-manager · cloud-controller-manager
    Worker Node 1…Nkubelet · kube-proxy · container runtime (containerd)
    Podsyour containers run here
    Control plane decides; worker nodes do the work.
    ComponentRole
    kube-apiserverFront door — every kubectl/controller call goes through this REST API
    etcdConsistent key-value store holding all cluster state
    schedulerChooses which node a new Pod runs on (resources, affinity, taints)
    controller-managerRuns controllers (ReplicaSet, Node, Deployment…) that reconcile state
    kubeletAgent on each node; starts containers described by Pods
    kube-proxyPrograms iptables/IPVS rules so Services route traffic
    bashkubectl cluster-info
kubectl get nodes -o wide
kubectl get pods -A               # all namespaces
kubectl describe pod mypod        # events = first place to debug
kubectl logs mypod -c sidecar     # specific container
kubectl exec -it mypod -- sh

    Local practice: minikube, kind or k3d. Managed production clusters: EKS, AKS, GKE.

    🧊 Core Objects (Basic → Intermediate)

    PodBasic

    Smallest unit. Containers in one Pod share an IP, localhost and volumes. Pods are ephemeral — you rarely create them directly.

    Deployment — the workhorseBasic

    yamlapiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: {app: web}
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxSurge: 1, maxUnavailable: 0}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
      - name: web
        image: myrepo/web:1.4.2
        ports: [{containerPort: 8000}]
        resources:
          requests: {cpu: 100m, memory: 128Mi}
          limits:   {cpu: 500m, memory: 256Mi}
        readinessProbe:
          httpGet: {path: /healthz, port: 8000}
        livenessProbe:
          httpGet: {path: /healthz, port: 8000}
          initialDelaySeconds: 10

    Deployment → manages a ReplicaSet → manages Pods. Change the image and K8s creates a new ReplicaSet and rolls pods over gradually; kubectl rollout undo deployment/web goes back.

    Workload typesIntermediate

    KindUse for
    DeploymentStateless apps (web, APIs)
    StatefulSetStateful apps needing stable names & storage (databases, Kafka)
    DaemonSetOne pod per node (log agents, node exporters)
    Job / CronJobRun-to-completion and scheduled tasks
    ReplicaSetKeeps N pods alive (managed by Deployment)

    Namespaces & labelsBasic

    Namespaces split a cluster into virtual sub-clusters (dev/test/prod, per team) with their own quotas and RBAC. Labels (app=web) are key/value tags; selectors use them to wire Services to Pods.

    🌐 Services, Ingress & Networking

    Pod IPs change constantly, so a Service gives a stable virtual IP + DNS name and load-balances across matching pods.

    Service typeReachable fromNotes
    ClusterIP (default)Inside cluster onlyweb.default.svc.cluster.local
    NodePortNode IP:30000-32767Simple dev/test exposure
    LoadBalancerInternet via cloud LBOne cloud LB per Service ($$)
    ExternalNameDNS CNAME aliasMaps to an external hostname
    Headless (clusterIP: None)Direct pod IPs via DNSUsed with StatefulSets
    yamlapiVersion: v1
kind: Service
metadata: {name: web}
spec:
  selector: {app: web}
  ports: [{port: 80, targetPort: 8000}]
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: {name: web}
spec:
  ingressClassName: nginx
  rules:
  - host: shop.example.com
    http:
      paths:
      - {path: /, pathType: Prefix, backend: {service: {name: web, port: {number: 80}}}}

    Ingress = HTTP(S) routing (host/path rules, TLS) via an Ingress controller such as NGINX, Traefik or cloud ALB. The newer Gateway API is its more expressive successor. CNI plugins (Calico, Cilium, Flannel) provide the pod network; NetworkPolicies act as pod-level firewalls.

    📈 Scaling, Scheduling & Security (Expert)

    AutoscalingIntermediate

    • HPA — scales pod count on CPU/memory/custom metrics: kubectl autoscale deployment web --min 3 --max 20 --cpu-percent 70
    • VPA — right-sizes pod requests/limits.
    • Cluster Autoscaler / Karpenter — adds or removes nodes when pods can't be scheduled.
    • KEDA — event-driven scaling (queue length, Kafka lag), including scale-to-zero.

    Scheduling controlsExpert

    FeatureWhat it does
    nodeSelector / nodeAffinityRun pods only on matching nodes (e.g. GPU nodes)
    podAffinity / antiAffinityCo-locate or spread pods (spread replicas across zones)
    Taints & tolerationsNodes repel pods unless the pod tolerates the taint
    topologySpreadConstraintsEven spread across zones/nodes
    PriorityClass & PodDisruptionBudgetEviction order; minimum available pods during maintenance

    SecurityExpert

    • RBAC — Roles/ClusterRoles bound to users and ServiceAccounts; least privilege.
    • Pod Security Standards (privileged / baseline / restricted) enforced per namespace.
    • NetworkPolicy default-deny, then allow only needed flows.
    • Admission control with OPA Gatekeeper / Kyverno; image signature verification.
    • GitOps: Argo CD or Flux keep the cluster synced to a Git repo.

    Troubleshooting cheat-sheetIntermediate

    SymptomLikely cause → first command
    PendingNo node fits (CPU/mem/taint/PVC) → kubectl describe pod
    ImagePullBackOffWrong tag or no registry credentials → check events, imagePullSecrets
    CrashLoopBackOffApp exits repeatedly → kubectl logs --previous
    OOMKilledMemory limit too low/leak → raise limit, profile app
    Service has no endpointsSelector doesn't match pod labels → kubectl get endpoints
    Readiness failingProbe path/port wrong or app slow → tune probe

    Module 04 · Package Management

    Helm

    Template, package, version and roll back Kubernetes applications — from installing a chart to authoring production charts.

    ⎈ What is Helm?

    Helm is the package manager for Kubernetes. Instead of maintaining a dozen near-identical YAML files for dev/stage/prod, you write templates once, feed them values, and Helm renders and installs them as a versioned release.

    ConceptMeaning
    ChartPackage: templates + defaults + metadata
    ReleaseA running installation of a chart in a cluster (with revision history)
    RepositoryPlace charts are hosted (HTTP repo or OCI registry)
    values.yamlDefault configuration; overridden with -f or --set
    bashhelm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update
helm search repo nginx
helm install my-web bitnami/nginx -n demo --create-namespace
helm list -A
helm upgrade my-web bitnami/nginx --set replicaCount=3
helm history my-web -n demo
helm rollback my-web 1 -n demo
helm uninstall my-web -n demo

    🏗️ Building Your Own Chart

    bashhelm create mychart
mychart/
  Chart.yaml        # name, version, appVersion, dependencies
  values.yaml       # default values
  templates/        # Go-templated manifests
    deployment.yaml
    service.yaml
    _helpers.tpl    # reusable named templates
    NOTES.txt       # message shown after install
  charts/           # sub-chart dependencies

    Template + valuesIntermediate

    yaml# values.yaml
replicaCount: 2
image: {repository: myrepo/web, tag: "1.4.2"}
service: {port: 80}

# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "mychart.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
      - name: web
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        {{- if .Values.resources }}
        resources: {{- toYaml .Values.resources | nindent 10 }}
        {{- end }}

    {{ .Values.x }} reads values, .Release.Name gives release info, if/range/with add logic, and pipes (| quote | default "x") transform output.

    bashhelm lint mychart
helm template my-web ./mychart -f prod-values.yaml   # render locally, no cluster needed
helm install my-web ./mychart --dry-run --debug
helm package mychart                                  # creates mychart-0.1.0.tgz

    🚀 Advanced Helm (Expert)

    • Per-environment values: -f values.yaml -f values-prod.yaml (later files win).
    • Dependencies: declare in Chart.yaml, then helm dependency update (e.g. app + PostgreSQL sub-chart).
    • Hooks: annotations such as "helm.sh/hook": pre-upgrade run Jobs for DB migrations.
    • Tests: helm test runs pods marked helm.sh/hook: test.
    • values.schema.json validates user-supplied values.
    • OCI registries: helm push chart.tgz oci://registry.example.com/charts.
    • GitOps: Argo CD / Flux render charts declaratively — avoids "helm install from a laptop".
    • helm diff plugin previews changes; --atomic auto-rolls back a failed upgrade; --wait waits for readiness.

    Helm

    • Go templating + values
    • Releases, rollback, packaging
    • Huge public chart ecosystem

    Kustomize

    • Patch-based overlays, no templates
    • Built into kubectl -k
    • Great for small env differences
    💡
    Many teams combine both: Helm to install third-party software, Kustomize overlays for in-house apps — or Helm charts rendered by Argo CD with per-env values.

    End-to-End & Best Practices

    How Docker, Kubernetes and Helm fit into one delivery pipeline, and what to learn next.

    🔁 End-to-End Delivery Flow

    Typical CI/CD to Kubernetes
    Git pushdeveloper
    →
    CI buildtests + docker build
    →
    Scan & signTrivy, cosign
    →
    Push imageregistry
    →
    Update chartimage tag in Git
    →
    Argo CD synccluster updated
    GitOps: Git is the single source of truth.
    1. Developer pushes code; CI runs tests and builds an image tagged with the Git SHA.
    2. Image is scanned and signed, pushed to the registry.
    3. The Helm values (or manifest) in a config repo are updated to the new tag.
    4. Argo CD/Flux detects the change and rolls it out with a RollingUpdate; probes gate traffic.
    5. Prometheus alerts and automatic rollback protect against bad releases.

    🎯 Learning Path & Best Practices

    LevelSkills to master
    BasicRun containers, write Dockerfiles, volumes, networks, Compose; kubectl basics; Pods/Deployments/Services

    • Always set requests and limits and readiness/liveness probes.

    • Certifications: CKA, CKAD, CKS, Docker DCA.

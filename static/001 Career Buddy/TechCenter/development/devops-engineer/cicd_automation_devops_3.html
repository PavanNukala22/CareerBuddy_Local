    Module 01 · Foundations

    CI/CD Fundamentals

    Before touching Jenkins, GitLab, GitHub Actions or ArgoCD, understand the idea they all implement: turning "code pushed to Git" into "software running safely in production" with no manual steps in between.

    🔁 What is CI/CD?

    CI/CD stands for Continuous Integration and Continuous Delivery / Continuous Deployment. It is a set of practices — plus the automation that enforces them — that moves every code change through build → test → release → deploy automatically and repeatedly.

    🏭
    Analogy: think of a car factory assembly line. Without one, each car is hand-built by a person who may forget a bolt. With an assembly line, every car passes the same stations (weld, paint, inspect, test-drive) in the same order, and a defect is caught at the station where it occurs, not by the customer. A CI/CD pipeline is the assembly line for software.
    🔗
    Continuous Integration
    Developers merge small changes to a shared branch many times a day; each merge is automatically built and tested.
    📦
    Continuous Delivery
    Every passing change is packaged and kept ready to release at the push of a button.
    🚀
    Continuous Deployment
    Every passing change is released to production automatically, with no human approval.

    😰 Why it exists

    Before CI/CD, teams worked in long-lived branches and released every few months. Merging was painful ("integration hell"), testing was manual, and deployments were scary weekend events.

    ❌ Without CI/CD

    • Big-bang merges, frequent conflicts

    • "Works on my machine" bugs

    • Manual, error-prone releases

    • Releases every weeks or months

    • Fear of deploying; slow rollback

    ✅ With CI/CD

    • Small changes merged daily

    • Same automated build every time

    • Tests gate every change

    • Releases many times a day if needed

    • Boring, repeatable, reversible deploys

    ⚖️ CI vs Continuous Delivery vs Continuous Deployment

    The three terms are often blurred together. They are really three increasing levels of automation:

    Figure 1.1 · How far the automation extends
    PracticeAutomates up toHuman step?Typical user
    Continuous IntegrationBuild + automated testsReview & mergeEvery team
    Continuous DeliveryRelease-ready artifact, deployed to stagingApproval click for productionRegulated industries, banks, enterprise
    Continuous DeploymentProduction releaseNone — tests are the gatekeeperSaaS, web products with strong test coverage

    🧬 Anatomy of a pipeline

    A pipeline is an automated workflow made of ordered stages, each containing one or more jobs. If any stage fails, the pipeline stops and the team is told immediately.

    1 · Source→2 · Build→3 · Test→4 · Scan→5 · Package→6 · Deploy→7 · Verify
    StageWhat happensExample tools
    SourceA push, pull request or tag triggers the pipelineGit, GitHub, GitLab webhooks
    BuildCompile code, resolve dependenciesMaven, Gradle, npm, pip, Go
    TestUnit, integration, end-to-end testsJUnit, pytest, Jest, Cypress
    ScanStatic analysis, dependency & secret scanningSonarQube, Trivy, Snyk, Gitleaks
    PackageCreate an immutable artifact or container imageDocker, Helm, JAR, Nexus, ECR
    DeployRoll the artifact to an environmentkubectl, Helm, Terraform, ArgoCD
    VerifySmoke tests, monitoring, auto-rollbackPrometheus, Grafana, k6
    📌
    Golden rule — build once, deploy many. The same artifact (e.g. one Docker image tagged with the commit SHA) should travel through dev → staging → prod. Never rebuild per environment, or you are no longer testing what you ship.

    📖 Key vocabulary

    TermMeaning
    PipelineThe full automated workflow from commit to deployment
    Stage / Job / StepStage = phase; job = unit of work; step = single command inside a job
    TriggerEvent that starts a pipeline: push, pull request, tag, schedule, manual, API
    Runner / Agent / NodeThe machine or container that actually executes jobs
    ArtifactOutput of a job: binary, image, test report — passed to later stages
    Pipeline as CodePipeline definition stored in the repo (Jenkinsfile, .gitlab-ci.yml, workflow YAML)
    EnvironmentTarget such as dev, staging, production
    Quality gateA rule that must pass (coverage ≥ 80%, no critical CVEs) before proceeding
    RollbackReturning to the previous known-good version

    📊 Measuring success — the DORA metrics

    The industry standard for measuring delivery performance comes from the DORA research programme. Four numbers tell you whether your CI/CD is actually working:

    Deployment Frequency
    How often you release to production. Elite teams: on demand, multiple per day.
    Lead Time for Changes
    Time from commit to running in production.
    Change Failure Rate
    Percentage of deployments causing an incident or rollback.
    Time to Restore
    How fast you recover when something breaks.

    Module 02 · Landscape

    Types & Methods of CI/CD

    CI/CD can be classified along several independent axes. Knowing these axes tells you why Jenkins, GitLab CI, GitHub Actions and ArgoCD feel so different even though they all "run pipelines".

    🗺️ Types of CI/CD methods

    There is no single "type" of CI/CD. Instead, every setup is a combination of choices on these five axes — each covered in the sections below:

    AxisOptions
    1 · How code reaches the environmentPush-based (CI server pushes) · Pull-based / GitOps (cluster pulls)
    2 · Where the tool runsSelf-hosted · SaaS/managed · Hybrid
    3 · How pipelines are definedUI-configured · Scripted code · Declarative YAML/DSL
    4 · How code is branched & mergedTrunk-based · GitHub Flow · GitFlow
    5 · How releases roll outRecreate · Rolling · Blue-green · Canary · Feature flags

    🔀 Push-based vs Pull-based (GitOps)

    ⬆️ Push-based CI/CD

    The CI server finishes the build and then pushes the change into the environment using credentials (kubectl apply, ssh, helm upgrade).

    Tools: Jenkins, GitLab CI, GitHub Actions

    Trade-off: simple and flexible, but the CI system holds powerful production credentials, and the cluster can drift from Git unnoticed.

    ⬇️ Pull-based CI/CD (GitOps)

    An agent inside the cluster watches a Git repo and pulls changes, continuously reconciling live state to match Git.

    Tools: ArgoCD, Flux

    Trade-off: no outside credentials, automatic drift correction, full audit trail in Git — but mainly suited to declarative targets like Kubernetes.

    ✅

    🚦 Deployment strategies

    This is the "CD" side: how do you swap the old version for the new one? Each strategy trades speed, cost and risk differently.

    StrategyHow it worksProsCons

    Module 03 · Jenkins

    Jenkins — the Automation Server

    The oldest and most flexible CI/CD tool. Self-hosted, plugin-driven and able to automate almost anything. This module goes from your first job to production-grade, Kubernetes-scaled pipelines.

    🤵 What is Jenkins? Basic

    Jenkins is an open-source automation server written in Java. It watches your repositories, runs build/test/deploy jobs on worker machines, and reports the result. Its power comes from 1,800+ plugins (Git, Docker, Kubernetes, Slack, SonarQube, cloud providers…).

    🧑‍🍳
    Analogy: Jenkins is a head chef (controller) who reads the order ticket (Jenkinsfile) and hands tasks to line cooks (agents). The chef doesn't cook everything personally — they coordinate, so many orders can be prepared at once.
    👍 Strengths
    Total flexibility, huge plugin ecosystem, runs anywhere (on-prem, air-gapped), free.
    👎 Weaknesses
    You operate it: upgrades, plugin compatibility, security, scaling. Groovy has a learning curve.

    🏗️ Architecture Basic

    Figure 3.1 · Jenkins controller–agent architecture
    • Controller — the brain: web UI, job scheduling, plugin host, stores config and history.
    • Agent — a machine/VM/container that runs the steps. Connected via SSH or JNLP/WebSocket.
    • Executor — one build slot on an agent. An agent with 4 executors runs 4 jobs at once.
    • Workspace — the checked-out working directory for a build on an agent.

    ⚙️ Install & first job Basic

    The fastest way to try Jenkins is Docker (requires Docker installed):

    bashdocker run -d --name jenkins \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts

# get the first-login admin password
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
    1. Open http://localhost:8080, paste the password, choose Install suggested plugins.
    2. Create an admin user.
    3. New Item → Freestyle project, add a Git repo URL and an Execute shell build step such as echo "Hello CI". Click Build Now.
    ⚠️
    Freestyle jobs are configured through the UI, so they can't be code-reviewed or versioned. Use them only to learn; real work uses a Jenkinsfile (next section).

    📄 Declarative Jenkinsfile Basic

    A Jenkinsfile in the repo root defines the pipeline. The Declarative syntax is the recommended starting point — it is structured and validated.

    Jenkinsfilepipeline {
    agent any

    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('Build') {
            steps { sh 'npm ci && npm run build' }
        }
        stage('Test') {
            steps { sh 'npm test' }
            post {
                always { junit 'reports/junit.xml' }   // publish test results
            }
        }
        stage('Package') {
            steps { sh 'docker build -t myapp:${GIT_COMMIT} .' }
        }
    }

    post {
        success { echo 'Pipeline succeeded 🎉' }
        failure { echo 'Pipeline failed ❌' }
    }
}
    BlockPurpose
    pipelineRequired top-level wrapper
    agentWhere to run (any, a label, a Docker image, a K8s pod)
    stages / stage / stepsPhases and the commands inside them
    postActions after completion: always, success, failure, unstable, cleanup

    🔑 Environment, credentials & parameters Intermediate

    Jenkinsfilepipeline {
    agent any
    options {
        timeout(time: 30, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '20'))
        disableConcurrentBuilds()
    }
    parameters {
        choice(name: 'ENV', choices: ['dev', 'staging', 'prod'], description: 'Target')
        booleanParam(name: 'RUN_E2E', defaultValue: false)
    }
    environment {
        REGISTRY = 'registry.example.com/team'
        IMAGE    = "${REGISTRY}/myapp:${env.BUILD_NUMBER}"
        // bound from Jenkins Credentials store — never hard-code secrets
        DOCKER_CREDS = credentials('dockerhub-creds')
    }
    stages {
        stage('Push image') {
            steps {
                sh 'echo $DOCKER_CREDS_PSW | docker login -u $DOCKER_CREDS_USR --password-stdin'
                sh 'docker build -t $IMAGE . && docker push $IMAGE'
            }
        }
        stage('Deploy') {
            when { expression { params.ENV != 'prod' } }
            steps { sh "helm upgrade --install myapp ./chart --set image.tag=${env.BUILD_NUMBER} -n ${params.ENV}" }
        }
        stage('Approve prod') {
            when { expression { params.ENV == 'prod' } }
            steps { input message: 'Deploy to production?', ok: 'Deploy' }
        }
    }
}
    🔐
    credentials('id') reads a secret from Manage Jenkins → Credentials. Jenkins automatically masks the value in console logs. The input step is how Jenkins implements the manual approval of Continuous Delivery.

    🔔 Triggers & webhooks Intermediate

    TriggerSyntaxNotes
    Webhook (recommended)GitHub/GitLab plugin; add webhook → /github-webhook/Instant, no polling load
    Poll SCMtriggers { pollSCM('H/5 * * * *') }Fallback when webhooks can't reach Jenkins
    Crontriggers { cron('H 2 * * *') }Nightly builds; H spreads load
    Upstream jobtriggers { upstream(upstreamProjects: 'build-lib') }Chain pipelines

    For repositories with many branches and pull requests use a Multibranch Pipeline: Jenkins scans the repo and automatically creates a pipeline for every branch/PR that contains a Jenkinsfile, and removes it when the branch is deleted.

    ⚡ Parallel stages, when & Docker agents Intermediate

    Jenkinsfilepipeline {
    agent none                       // each stage picks its own agent
    stages {
        stage('Build') {
            agent { docker { image 'maven:3.9-eclipse-temurin-21' } }   // clean, reproducible toolchain
            steps { sh 'mvn -B -DskipTests package' }
        }
        stage('Quality') {
            parallel {                // run simultaneously, cut wall-clock time
                stage('Unit tests') {
                    agent { docker { image 'maven:3.9-eclipse-temurin-21' } }
                    steps { sh 'mvn -B test' }
                }
                stage('Lint') {
                    agent { docker { image 'node:20' } }
                    steps { sh 'npx eslint .' }
                }
                stage('SAST') {
                    agent any
                    steps { sh 'trivy fs --exit-code 1 --severity HIGH,CRITICAL .' }
                }
            }
        }
        stage('Deploy main only') {
            when { branch 'main' }
            agent any
            steps { sh './deploy.sh' }
        }
    }
}
    💡
    Why Docker agents? The build tools live in the image, so every build starts from the same clean environment — no more "the agent has the wrong Java version".

    📚 Shared libraries Expert

    When 50 repos copy the same 80 lines of pipeline, one change means 50 pull requests. A Shared Library is a separate Git repo of reusable Groovy code that every Jenkinsfile can import.

    shared-lib repo: vars/standardPipeline.groovydef call(Map cfg = [:]) {
    pipeline {
        agent any
        stages {
            stage('Build') { steps { sh cfg.buildCmd ?: 'make build' } }
            stage('Test')  { steps { sh cfg.testCmd  ?: 'make test'  } }
            stage('Image') {
                steps { sh "docker build -t ${cfg.image}:${env.GIT_COMMIT} ." }
            }
        }
    }
}
    application repo: Jenkinsfile@Library('company-pipelines@v2') _      // pinned to a tag

standardPipeline(
    image:    'registry.example.com/shop/api',
    buildCmd: 'mvn -B package',
    testCmd:  'mvn -B verify'
)

    The application's Jenkinsfile shrinks to five lines, and a security fix to the template rolls out to every team by bumping one version tag. Register the library under Manage Jenkins → System → Global Pipeline Libraries.

    🧑‍💻 Scripted pipelines Expert

    The older Scripted syntax is plain Groovy: loops, try/catch, functions. Use it when Declarative is too restrictive, e.g. generating stages dynamically.

    Jenkinsfile (scripted)node('linux') {
    def services = ['auth', 'orders', 'payments']
    try {
        stage('Checkout') { checkout scm }

        // dynamic parallel stages built from a list
        def branches = [:]
        services.each { svc ->
            branches[svc] = {
                stage("Build ${svc}") { sh "make -C services/${svc} build" }
            }
        }
        parallel branches

        retry(3) { stage('Deploy') { sh './deploy.sh' } }
    } catch (err) {
        currentBuild.result = 'FAILURE'
        slackSend color: 'danger', message: "Build failed: ${env.JOB_NAME} #${env.BUILD_NUMBER}"
        throw err
    } finally {
        cleanWs()
    }
}

    Declarative

    Strict structure, easier to read and validate, built-in post, when, options. Prefer by default.

    Scripted

    Full Groovy freedom, but easy to write unmaintainable code. Use sparingly, or hide it inside a shared library.

    ☸️ Kubernetes agents Expert

    With the Kubernetes plugin, Jenkins creates a fresh pod per build and deletes it afterwards. You get elastic scaling, perfect isolation and no idle agents.

    Jenkinsfilepipeline {
    agent {
        kubernetes {
            yaml '''
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: maven
    image: maven:3.9-eclipse-temurin-21
    command: ["sleep"]
    args: ["infinity"]
  - name: kaniko
    image: gcr.io/kaniko-project/executor:debug
    command: ["sleep"]
    args: ["infinity"]
'''
        }
    }
    stages {
        stage('Build') { steps { container('maven')  { sh 'mvn -B package' } } }
        stage('Image') { steps { container('kaniko') { sh '/kaniko/executor --context . --destination registry/app:${BUILD_NUMBER}' } } }
    }
}

    Kaniko builds images without needing a privileged Docker daemon — safer inside a cluster.

    🛠️ Jenkins Configuration as Code & scaling Expert

    Clicking through settings makes a Jenkins server a fragile "snowflake". JCasC (Configuration as Code) describes the whole controller in YAML so it can be rebuilt from Git.

    jenkins.yamljenkins:
  systemMessage: "Managed by JCasC — do not edit in the UI"
  numExecutors: 0                  # controller runs NO builds
  securityRealm:
    ldap: { configurations: [{ server: ldap.example.com, rootDN: "dc=example,dc=com" }] }
  authorizationStrategy:
    roleBased:
      roles:
        global:
          - { name: admin, permissions: [Overall/Administer], entries: [{ group: devops }] }
          - { name: dev,   permissions: [Overall/Read, Job/Build], entries: [{ group: developers }] }
unclassified:
  location: { url: https://jenkins.example.com/ }

    Scaling & reliability checklist

    • Set controller executors to 0; build only on agents.
    • Use ephemeral agents (Kubernetes pods, EC2 spot) instead of long-lived VMs.
    • Keep JENKINS_HOME on persistent, backed-up storage; test restores.
    • Pin and test plugin upgrades in a staging Jenkins first.
    • Add buildDiscarder to avoid disk exhaustion; export metrics with the Prometheus plugin.

    🛡️ Security & common pitfalls Expert

    PitfallFix
    Secrets hard-coded in JenkinsfileCredentials store, or Vault / cloud secret manager plugin
    Running builds on the controllerExecutors = 0; use agents
    Everyone is adminRole-based access + SSO (LDAP/OIDC)
    Unreviewed pipeline changes from PRsTrust only maintainers' Jenkinsfile on PR builds; use Script Security sandbox
    Outdated Jenkins/plugins (frequent CVEs)Track LTS releases and the security advisories; update on a schedule
    Using sh "...${userInput}"Never interpolate untrusted values into shell; pass them as environment variables
    Flaky snowflake agentsImmutable, ephemeral agents built from images

    Module 04 · GitLab CI/CD

    GitLab CI/CD

    CI/CD built directly into the GitLab platform: one tool for repos, merge requests, pipelines, container registry and security scanning. Pipelines are defined in a single YAML file.

    🦊 What is GitLab CI/CD? Basic

    Add a file named .gitlab-ci.yml to the root of any GitLab project and GitLab automatically runs it on every push. No separate server to install on GitLab.com — you just need runners (shared ones are provided, or bring your own).

    Figure 4.1 · GitLab pipeline structure

    🚀 Your first pipeline Basic

    .gitlab-ci.ymlstages:
  - build
  - test
  - deploy

build-job:
  stage: build
  image: node:20            # job runs inside this Docker image
  script:
    - npm ci
    - npm run build

unit-tests:
  stage: test
  image: node:20
  script:
    - npm ci
    - npm test

deploy-staging:
  stage: deploy
  script:
    - echo "Deploying to staging..."
  environment: staging
    KeywordMeaning
    stagesOrdered list of phases
    stageWhich phase a job belongs to
    imageDocker image the job runs in
    scriptShell commands (required in every job)
    before_script / after_scriptSetup / cleanup commands
    environmentLinks the job to a deployment target and records deploy history
    ✅
    Use CI/CD → Editor → Validate in the GitLab UI, or glab ci lint, to check your YAML before committing.

    🏃 Runners & executors Basic

    A GitLab Runner is the program that picks up jobs and runs them. Each runner has an executor that decides how a job is isolated.

    ExecutorIsolationUse when
    dockerNew container per jobDefault, most common
    kubernetesNew pod per jobElastic scaling on a cluster
    shellNone — runs on hostQuick setups; avoid for shared use
    docker-autoscalerCloud VMs scaled on demandLarge fleets, cost control
     
    bashgitlab-runner register \
  --url https://gitlab.example.com \
  --token $RUNNER_TOKEN \
  --executor docker \
  --docker-image alpine:latest

    Use tags to route a job to the right runner: tags: [gpu] or tags: [linux, prod-network].

    🔑 Variables & secrets Intermediate

    .gitlab-ci.ymlvariables:
  APP_NAME: shop-api
  DOCKER_TLS_CERTDIR: "/certs"

build-image:
  stage: build
  image: docker:27
  services: [docker:27-dind]          # Docker-in-Docker sidecar
  script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    • Predefined variables such as CI_COMMIT_SHA, CI_COMMIT_BRANCH, CI_REGISTRY_IMAGE, CI_PIPELINE_ID are provided automatically.
    • Custom secrets live in Settings → CI/CD → Variables. Tick Masked (hidden in logs) and Protected (only available on protected branches/tags like main).
    • Variables can be scoped to a specific environment (e.g. a different DB_URL for staging and production).

    📦 Artifacts & cache Intermediate

    📦 Artifacts

    Files a job produces and passes to later jobs and to the UI (binaries, reports). Stored on GitLab for a set time.

    ⚡ Cache

    Files that speed up jobs by being reused between runs (node_modules, .m2). Best-effort — a job must still work without it.

    .gitlab-ci.ymlbuild:
  stage: build
  image: node:20
  cache:
    key:
      files: [package-lock.json]        # new cache only when lockfile changes
    paths: [.npm/]
  script:
    - npm ci --cache .npm --prefer-offline
    - npm run build
  artifacts:
    paths: [dist/]
    expire_in: 1 week

test:
  stage: test
  image: node:20
  script: [npm test]
  artifacts:
    when: always
    reports:
      junit: reports/junit.xml          # shows test results in the merge request

    🧭 rules, needs & the DAG Intermediate

    rules decide whether a job runs. needs lets a job start as soon as its dependencies finish, ignoring stage order — creating a faster DAG (directed acyclic graph).

    .gitlab-ci.ymlworkflow:
  rules:                                  # avoid duplicate pipelines for push + MR
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

unit:
  stage: test
  script: [make unit]
  needs: [build]                          # start right after build, don't wait for the whole stage

docs-only-check:
  stage: test
  script: [make lint-docs]
  rules:
    - changes: ["docs/**/*"]              # run only when docs change

deploy-prod:
  stage: deploy
  script: [./deploy.sh prod]
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/    # only on release tags
      when: manual                                  # Continuous DELIVERY approval click

    🌍 Environments & deployment Intermediate

    .gitlab-ci.ymldeploy-review:
  stage: deploy
  script: [./deploy-review.sh $CI_COMMIT_REF_SLUG]
  environment:
    name: review/$CI_COMMIT_REF_SLUG       # a throw-away "review app" per merge request
    url: https://$CI_COMMIT_REF_SLUG.review.example.com
    on_stop: stop-review
  rules: [{ if: $CI_MERGE_REQUEST_IID }]

stop-review:
  stage: deploy
  script: [./destroy-review.sh $CI_COMMIT_REF_SLUG]
  environment: { name: review/$CI_COMMIT_REF_SLUG, action: stop }
  when: manual

deploy-production:
  stage: deploy
  script:
    - helm upgrade --install shop ./chart --set image.tag=$CI_COMMIT_SHORT_SHA
  environment: { name: production, url: https://shop.example.com }
  resource_group: production              # only one deploy at a time
  when: manual

    GitLab's Environments page then shows what version is live where, who deployed it, and offers one-click Rollback to a previous deployment. Protected environments restrict who can approve production.

    🧩 Includes & templates Expert

    Avoid copy-pasting pipeline YAML across projects: include pulls in shared configuration from other files, projects, or GitLab's built-in templates.

    .gitlab-ci.ymlinclude:
  - template: Security/SAST.gitlab-ci.yml                  # GitLab-provided
  - template: Security/Secret-Detection.gitlab-ci.yml
  - project: platform/ci-templates                         # your company's shared repo
    ref: v3.2.0
    file: /templates/docker-build.yml

.deploy-base:                                              # hidden job = reusable template
  image: bitnami/kubectl
  before_script: [kubectl config use-context $KUBE_CONTEXT]

deploy-staging:
  extends: .deploy-base                                    # inherit, then override

    Module 05 · GitHub Actions

    GitHub Actions

    Event-driven automation built into GitHub. Any repo event — push, pull request, release, issue, schedule — can start a workflow made from reusable community actions.

    🐙 What is GitHub Actions? Basic

    GitHub Actions lets you automate workflows directly in your repository. Workflows are YAML files under .github/workflows/. GitHub provides hosted Linux, Windows and macOS runners, so there is nothing to install to get started.

    🔌
    Analogy: Actions is like a smart-home automation app. A trigger ("someone opens the door" = a push) starts a routine (workflow) made of steps, many of which are ready-made apps from a marketplace (actions) rather than code you write yourself.

    🧱 Core concepts Basic

    Figure 5.1 · Workflow → jobs → steps
    ConceptMeaning
    WorkflowA YAML automation file; a repo can have many
    EventWhat triggers it: push, pull_request, schedule, workflow_dispatch…
    JobGroup of steps on one runner; jobs run in parallel unless needs orders them
    StepOne command (run) or one reusable action (uses)
    ActionPackaged reusable step from the Marketplace or your own repo
    RunnerThe VM/container that executes a job (GitHub-hosted or self-hosted)

    🚀 Your first workflow Basic

    .github/workflows/ci.ymlname: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4          # get the code
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm                       # built-in dependency cache
      - run: npm ci
      - run: npm test
      - run: npm run build

    Commit this file, push, and open the repo's Actions tab: you will see the run, per-step logs, and a green check or red cross on the commit and pull request.

    🔔 Events & triggers Basic

    YAMLon:
  push:

  pull_request:

  workflow_dispatch:                          # manual "Run workflow" button

    🧮 Matrix, cache & artifacts Intermediate

    .github/workflows/test.ymljobs:
  test:

      fail-fast: false                       # let other combos finish if one fails
      matrix:
        os: [ubuntu-latest, windows-latest]

    🔑 Secrets, variables & environments Intermediate

    • Secrets — encrypted values (Settings → Secrets and variables → Actions), read as ${{ secrets.NAME }} and masked in logs.
    • Variables — non-secret configuration, read as ${{ vars.NAME }}.
    • Environments — named targets (staging, production) with their own secrets, required reviewers, wait timers and branch restrictions.
    YAMLjobs:
  deploy-prod:
    runs-on: ubuntu-latest
    environment:
      name: production                       # pauses until a required reviewer approves
      url: https://shop.example.com
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh
        env:
          API_TOKEN: ${{ secrets.PROD_API_TOKEN }}   # env-scoped secret
    ⚠️
    Secrets are not passed to workflows triggered by pull requests from forks. This is deliberate protection — don't try to bypass it with pull_request_target unless you fully understand the risk.

    🧩 Composite actions Expert

    A composite action bundles several steps into one reusable step (a reusable workflow bundles whole jobs).

  node-version: { default: '20' }

    🪪 OIDC cloud authentication Expert

    Storing long-lived cloud keys as secrets is risky. With OpenID Connect, each job gets a short-lived identity token that your cloud (AWS, Azure, GCP) exchanges for temporary credentials.

    YAMLpermissions:
  id-token: write                            # allow requesting the OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: ap-south-1
      - run: aws s3 sync ./dist s3://my-site-bucket

    On the AWS side, the IAM role's trust policy restricts the assumable identity to a specific repository and branch (for example repo:my-org/shop:ref:refs/heads/main), so a fork or another repo can never use it.

    🏃 Self-hosted runners Expert

    Use your own machines when you need private network access, special hardware (GPU), more CPU/RAM, or lower cost at high volume.

    YAMLjobs:
  build:
    runs-on: [self-hosted, linux, x64, gpu]   # labels choose the runner
    • Prefer ephemeral runners (one job, then destroyed). On Kubernetes use Actions Runner Controller (ARC) to auto-scale runner pods.
    • Never attach self-hosted runners to public repositories — a malicious pull request could run code on your network.
    • Keep runner images patched; isolate them from production networks.

    Module 06 · ArgoCD

    ArgoCD & GitOps

    ArgoCD is not a build tool — it is the delivery half. It keeps Kubernetes clusters in sync with what is declared in Git, continuously, from inside the cluster.

    🌱 What is GitOps? Basic

    GitOps means Git is the single source of truth for the desired state of your infrastructure and applications. To change production, you change a Git repo (via a pull request) — never run commands against the cluster by hand.

    1 · Declarative
    The whole system is described as manifests (YAML), not step-by-step scripts.
    2 · Versioned & immutable
    Desired state lives in Git: full history, review, instant revert.
    3 · Pulled automatically
    An agent fetches approved state; humans don't push to the cluster.
    4 · Continuously reconciled
    The agent detects drift and corrects it back to Git's version.
    🌡️
    Analogy: a thermostat. You set the desired temperature (Git). The thermostat constantly compares it to the actual room temperature (cluster) and turns the heating on or off to close the gap. ArgoCD is the thermostat for your cluster.

    🐙 What is ArgoCD? Basic

    ArgoCD is a declarative GitOps controller for Kubernetes (a CNCF graduated project). It watches Git repos, compares the manifests there with what is running, shows the difference in a visual UI, and syncs the cluster to match.

    • Drift detection: someone ran kubectl edit? ArgoCD marks the app OutOfSync and can auto-heal it.
    • Easy rollback: deploy a previous Git commit with one click or git revert.
    • Multi-cluster: one ArgoCD can manage dev, staging and prod clusters.
    • Great UI: live resource tree, diffs, logs, health status.

    🏗️ Architecture Basic

    Figure 6.1 · ArgoCD components
    ComponentRole
    API ServerServes the web UI, CLI and API; handles auth & RBAC
    Repo ServerClones Git repos and renders Helm/Kustomize/plain YAML into manifests
    Application ControllerThe reconciler: compares desired state to live state and applies changes

    📜 The Application manifest Intermediate

    The core ArgoCD object is the Application custom resource: "take this path in this repo and keep it deployed to this cluster/namespace". It is itself YAML you keep in Git.

    application.yamlapiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop-api
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/my-org/shop-config.git
    targetRevision: main                  # branch, tag or commit
    path: apps/shop-api/overlays/staging

    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true                         # delete resources removed from Git
      selfHeal: true                      # revert manual cluster changes
    syncOptions:
      - CreateNamespace=true

    🌳 App-of-apps & ApplicationSet Expert

    Managing 200 Application manifests by hand does not scale. ArgoCD offers two patterns:

    App of Apps

    One "root" Application whose Git path contains other Application manifests. Syncing the root bootstraps an entire platform (ingress, monitoring, apps) from one command.

    ApplicationSet

    A template + generator that stamps out Applications automatically — one per cluster, per folder, per Git branch or per pull request.

    applicationset.yamlapiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata: { name: shop-services, namespace: argocd }
spec:
  generators:
    - git:                                      # one app per folder under services/
        repoURL: https://github.com/my-org/shop-config.git
        revision: main
        directories: [{ path: services/* }]
  template:
    metadata: { name: '{{path.basename}}' }
    spec:
      project: default
      source:
        repoURL: https://github.com/my-org/shop-config.git
        targetRevision: main
        path: '{{path}}'
      destination: { server: https://kubernetes.default.svc, namespace: '{{path.basename}}' }
      syncPolicy: { automated: { prune: true, selfHeal: true } }

    Add a new folder services/payments/, merge the PR — a new Application appears and deploys with zero extra clicks.

    🌊 Sync waves & hooks Expert

    Real deployments have ordering needs: create the database before the app, run schema migrations before new pods start. Annotations control this:

    YAML# Sync WAVES: lower numbers apply first (default 0)
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "-1"       # e.g. namespace / CRDs / database

# Sync HOOKS: run a Job at a lifecycle point
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migrate
  annotations:
    argocd.argoproj.io/hook: PreSync          # before the main sync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - { name: migrate, image: ghcr.io/my-org/shop-api:a1b2c3d, command: ["./migrate.sh"] }

    Hook phases: PreSync, Sync, PostSync, SyncFail. A failing PreSync hook aborts the release — so a bad migration never reaches new pods.

    🐤 Progressive delivery with Argo Rollouts Expert

    Plain Kubernetes Deployment only supports a basic rolling update. Argo Rollouts (a companion project) adds canary and blue-green with automated, metric-based promotion and rollback — and ArgoCD shows and syncs it like any other resource.

    rollout.yamlapiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: shop-api }
spec:
  replicas: 5
  selector: { matchLabels: { app: shop-api } }
  template:
    metadata: { labels: { app: shop-api } }
    spec:
      containers: [{ name: api, image: ghcr.io/my-org/shop-api:a1b2c3d }]
  strategy:
    canary:
      steps:
        - setWeight: 10
        - pause: { duration: 2m }
        - analysis:                           # query Prometheus; auto-rollback if failing
            templates: [{ templateName: success-rate }]
        - setWeight: 50
        - pause: { duration: 5m }
        - setWeight: 100

    🔐 RBAC, SSO & secrets Expert

    • AppProjects restrict which repos, clusters and namespaces a team's Applications may use — multi-tenancy boundaries.
    • RBAC (argocd-rbac-cm) maps SSO groups to roles such as read-only, sync, admin.
    • SSO via OIDC/SAML (Okta, Azure AD, Google, GitHub) through Dex or direct OIDC.
    🔒
    Never commit plain Kubernetes Secrets to Git. GitOps needs a secret strategy: Sealed Secrets (encrypted in Git), External Secrets Operator (syncs from AWS Secrets Manager / Vault), or SOPS encryption. Git holds a reference or ciphertext, never the plaintext.

    Expert Practices & Decision Guide

    What separates a working pipeline from a great one: security, speed, reliability, rollbacks — plus a guide for picking the right tool and a roadmap for what to practise next.

    🛡️ DevSecOps — shift security left

    Finding a vulnerability in a pull request costs minutes; finding it in production costs weeks. Add automated security checks at every stage:

    ⛓️ Software supply-chain security

    • SBOM (Software Bill of Materials): generate a list of every component in the image (Syft, docker sbom).
    • Sign images with cosign and verify the signature at deploy time (Kyverno, Sigstore policy controller).
    • Provenance (SLSA): record which pipeline built this artifact from which commit.
    • Pin base images by digest and third-party actions by commit SHA.
    • Least privilege: short-lived OIDC credentials, per-environment secrets, protected branches.
    bashtrivy image --exit-code 1 --severity HIGH,CRITICAL $IMAGE      # fail the build on serious CVEs
syft $IMAGE -o spdx-json > sbom.json                            # generate SBOM
cosign sign --yes $IMAGE                                        # keyless signing via OIDC

    🏗️ Infrastructure as Code in CI/CD

    Pipelines should deploy infrastructure the same way as applications. The standard Terraform flow gives a human-reviewable plan before anything changes:

    GitHub Actions: terraform.ymlon:
  pull_request: { paths: ['infra/**'] }
  push: { branches: [main], paths: ['infra/**'] }

jobs:
  terraform:
    runs-on: ubuntu-latest
    permissions: { id-token: write, contents: read, pull-requests: write }
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform -chdir=infra init -input=false
      - run: terraform -chdir=infra fmt -check
      - run: terraform -chdir=infra validate
      - run: terraform -chdir=infra plan -out=tfplan -input=false     # shown on the PR
      - if: github.ref == 'refs/heads/main'
        run: terraform -chdir=infra apply -input=false tfplan          # only after merge

    Store Terraform state in a remote, locked backend (S3 + DynamoDB lock, Terraform Cloud) — never in the runner.

    ⚡ Speed & reliability

    Cache aggressively
    Dependency caches keyed on lockfile hashes; Docker layer caching; remote build caches (Bazel, Gradle).
    Parallelise
    Run independent jobs/test shards at the same time; use DAG / needs.
    Fail fast
    Put cheap checks (lint, unit tests) first; stop on first failure.
    Run only what changed
    Path filters and monorepo tooling avoid rebuilding unaffected services.
    Ephemeral runners
    Clean environments per job eliminate "polluted agent" flakiness.
    Kill flaky tests
    Quarantine and fix; a pipeline people re-run "until green" teaches them to ignore red.
    ⏱️
    Target: developer feedback on a pull request in under ~10 minutes. Longer than that and engineers context-switch and batch up risky large changes — the opposite of what CI is for.

    ↩️ Rollbacks & observability

    ToolHow to roll back
    JenkinsRe-run a previous build / redeploy the previously tagged artifact; automate with a parameterised "deploy version X" job
    GitLab CIEnvironments page → Rollback on an earlier deployment
    GitHub ActionsRe-run the old workflow run, or workflow_dispatch with a version input
    ArgoCDgit revert the config commit (preferred) or argocd app rollback
    Argo RolloutsAutomatic abort + rollback when analysis metrics fail

    Close the loop with observability: send deploy markers to Grafana/Datadog, alert on error-rate and latency regressions right after a release, and track the four DORA metrics from Module 01.

    🧭 Choosing the right tool

    If your situation is…Choose
    Code already on GitHub, want zero infrastructure to manageGitHub Actions
    Want one platform for repo + CI/CD + registry + security scanningGitLab CI/CD
    Complex legacy builds, air-gapped network, need unlimited customisation, have a platform teamJenkins
    Deploying to Kubernetes with audit, drift detection and multi-cluster needsArgoCD (paired with any CI above)
    Regulated environment needing approvals and an audit trailAny CI + ArgoCD with PR-based promotion

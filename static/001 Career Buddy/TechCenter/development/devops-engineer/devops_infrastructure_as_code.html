    Module 01 · Infrastructure as Code

    IaC Foundations

    What IaC is, the key ideas behind it (declarative, idempotent, immutable) and how the major tools compare.

    🏗️ What is Infrastructure as Code?

    Infrastructure as Code (IaC) means defining servers, networks, databases, load balancers, permissions — your whole infrastructure — in text files that are version-controlled, reviewed, tested and applied automatically, instead of clicking in a cloud console.

    IaC lifecycle
    Writecode in Git
    →
    Reviewpull request
    →
    Planpreview changes
    →
    Applycreate / update
    →
    Detect driftcompare real vs code
    Same workflow as application code.
    ♻️
    Repeatable
    Spin up identical dev/test/prod environments on demand.
    📜
    Auditable
    Every change is a Git commit with author and reason.
    ⚡
    Fast
    Minutes instead of days to provision.
    🛡️
    Consistent
    No manual snowflake servers; fewer human errors.

    🧭 Types & Key Concepts — "What is What"

    ConceptOptionsExplanation
    Declarative vs ImperativeTerraform, CloudFormation (declarative) · Ansible playbooks, scripts (largely imperative/procedural)Declarative: describe the end state, tool works out the steps. Imperative: you list the steps.
    Provisioning vs Configuration MgmtTerraform/CloudFormation · Ansible/Chef/PuppetProvisioning creates infrastructure (VMs, VPCs). Configuration management sets up software inside it (packages, files, services).
    Mutable vs ImmutablePatch servers in place · Replace with new imageImmutable is safer: build new AMI/container, swap, throw old away — no configuration drift.
    Push vs PullAnsible, Terraform (push) · Puppet, Chef, Argo CD (pull)Push: a controller sends changes. Pull: agents fetch desired state periodically.
    Agent vs AgentlessPuppet/Chef (agent) · Ansible (agentless, SSH/WinRM)Agentless needs nothing installed on targets.
    IdempotencyAll good toolsRunning twice gives the same result as running once. The core IaC property.
    Cloud-native vs Multi-cloudCloudFormation/ARM/Bicep (one cloud) · Terraform/Pulumi (many)Cloud-native tools get new features first; multi-cloud tools give one workflow.

    Module 02 · Provisioning

    Terraform

    Declarative multi-cloud provisioning: HCL, providers, state, modules and production workflows.

    🌍 What is Terraform?

    Terraform (HashiCorp; open-source fork: OpenTofu) is a declarative, cloud-agnostic provisioning tool. You write .tf files in HCL (HashiCorp Configuration Language); providers (AWS, Azure, GCP, Kubernetes, Datadog…) translate them into API calls.

    Core workflow
    terraform initdownload providers
    →
    terraform planpreview diff
    →
    terraform applymake changes
    →
    terraform destroytear down
    Terraform stores what it manages in a state file.

    Your first configurationBasic

    hclterraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = "ap-south-1"
}

resource "aws_s3_bucket" "logs" {
  bucket = "my-company-logs-12345"
  tags   = { Env = "dev" }
}

output "bucket_arn" {
  value = aws_s3_bucket.logs.arn
}
    bashterraform init
terraform fmt && terraform validate
terraform plan -out tfplan
terraform apply tfplan
terraform destroy

    🔧 Terraform Building Blocks

    BlockPurposeExample
    providerPlugin that talks to an APIprovider "aws" {}
    resourceCreates/manages an objectresource "aws_instance" "web" {}
    dataReads existing info (read-only)data "aws_ami" "ubuntu" {}
    variableInput parametervar.instance_type
    outputValues printed / exportedoutput "ip" {}
    localsNamed expressions inside a modulelocal.name_prefix
    moduleReusable group of resourcesmodule "vpc" { source = "./vpc" }

    Variables, locals, data & referencesIntermediate

    hclvariable "instance_type" {
  type        = string
  default     = "t3.micro"
  description = "EC2 size"
}

variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "stage", "prod"], var.env)
    error_message = "env must be dev, stage or prod."
  }
}

locals {
  name = "${var.env}-web"
}

data "aws_ami" "al2023" {
  most_recent = true
  owners      = ["amazon"]
  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.al2023.id     # implicit dependency
  instance_type = var.instance_type
  tags          = { Name = local.name }
}

    References like data.aws_ami.al2023.id create an implicit dependency graph so Terraform builds things in the right order and in parallel where possible. Use depends_on only for hidden dependencies.

    count, for_each, lifecycle & dynamic blocksIntermediate

    hclresource "aws_iam_user" "dev" {
  for_each = toset(["asha", "ravi", "meena"])
  name     = each.key
}

resource "aws_instance" "app" {
  count         = var.env == "prod" ? 3 : 1     # conditional expression
  ami           = data.aws_ami.al2023.id
  instance_type = var.instance_type

  lifecycle {
    create_before_destroy = true
    prevent_destroy       = false
    ignore_changes        = [tags]
  }
}
    📌
    Prefer for_each over count for collections — items are tracked by key, so removing one doesn't shift and recreate the others.

    🗃️ State, Backends & Workspaces

    The state file (terraform.tfstate) maps your code to real resources and caches attributes. It can contain secrets, so never commit it to Git.

    hclterraform {
  backend "s3" {
    bucket         = "company-tf-state"
    key            = "prod/network/terraform.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "tf-locks"        # state locking
    encrypt        = true
  }
}
    TopicDetail
    Remote backendS3 + DynamoDB lock, Azure Blob, GCS, Terraform Cloud — shared state and locking so two people can't apply at once
    WorkspacesMultiple state files from one config (terraform workspace new stage). Many teams prefer separate directories/backends per environment.
    DriftReal infra changed outside Terraform. terraform plan shows it; apply reverts it.
    Importterraform import or an import {} block adopts an existing resource into state.
    State commandsstate list, state show, state mv (refactor), state rm

    🧱 Modules & Expert Patterns

    hcl# modules/web/main.tf is a normal set of resources with variables + outputs
module "web_prod" {
  source        = "./modules/web"
  env           = "prod"
  instance_type = "m6i.large"
}

# registry module with pinned version
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.8.1"
  name    = "main"
  cidr    = "10.0.0.0/16"
}

    Expert checklistExpert

    • Layout: small, focused root modules per layer (network, data, apps) to limit the blast radius; share outputs via terraform_remote_state or data sources.
    • Pin provider and module versions; commit .terraform.lock.hcl.
    • CI/CD: run fmt -check, validate, tflint, security scanners (tfsec/Trivy, Checkov), then plan on PR and apply after approval (Atlantis, Terraform Cloud, GitHub Actions).
    • Policy as code: Sentinel or OPA/Conftest to block e.g. public S3 buckets.
    • Secrets: never hard-code; use sensitive = true, Vault / cloud secret managers, and OIDC federation for CI credentials.
    • Testing: terraform test (native), Terratest.
    • Zero-downtime changes: create_before_destroy, moved {} blocks for refactors, -target only for emergencies.
    • Debug: TF_LOG=DEBUG terraform plan.
    ⚠️
    Always read the plan. A line marked -/+ (destroy and re-create) on a database is a data-loss event.

    Module 03 · Configuration Management

    Ansible

    Agentless automation: inventories, playbooks, roles, vault and enterprise-scale patterns.

    🅰️ What is Ansible?

    Ansible (Red Hat) is an agentless automation engine for configuration management, application deployment and orchestration. It connects over SSH (Linux) or WinRM (Windows) and runs modules described in YAML playbooks. Modules are idempotent: they only change what needs changing.

    Ansible architecture
    Control nodewhere ansible runs (Linux/macOS/WSL)
    Inventorywhich hosts, in which groups
    Playbooks → Plays → Tasks → Moduleswhat to do
    Managed nodesservers/network devices; no agent needed

    Inventory & ad-hoc commandsBasic

    yaml# inventory.ini
[web]
web1.example.com
web2.example.com ansible_user=ubuntu

[db]
db1.example.com

[prod:children]
web
db
    bashansible all -i inventory.ini -m ping
ansible web -i inventory.ini -m apt -a "name=nginx state=present" --become
ansible db -i inventory.ini -m shell -a "df -h"

    📖 Playbooks — Basic to Intermediate

    yaml---
- name: Configure web servers
  hosts: web
  become: true
  vars:
    http_port: 8080
  tasks:
    - name: Install nginx
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true

    - name: Deploy config from template
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/conf.d/app.conf
        mode: "0644"
      notify: Reload nginx

    - name: Ensure nginx is running
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Reload nginx
      ansible.builtin.service:
        name: nginx
        state: reloaded
    bashansible-playbook -i inventory.ini site.yml --check --diff   # dry run
ansible-playbook -i inventory.ini site.yml --limit web1 -v
    • Handlers run only if a task reported changed, and only once at the end.
    • Templates use Jinja2: listen {{ http_port }};
    • Facts are auto-gathered system info (ansible_distribution, ansible_memtotal_mb).

    Conditionals, loops, registerIntermediate

    yaml- name: Install packages
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop: [git, curl, htop]
  when: ansible_os_family == "Debian"

- name: Check app health
  ansible.builtin.uri:
    url: http://localhost:8080/health
  register: health
  retries: 5
  delay: 3
  until: health.status == 200

    🧰 Roles, Vault & Expert Features

    Roles — reusable structureIntermediate

    yamlroles/nginx/
  tasks/main.yml
  handlers/main.yml
  templates/
  defaults/main.yml     # lowest-precedence variables
  vars/main.yml
  meta/main.yml         # dependencies

# site.yml
- hosts: web
  roles:
    - common
    - { role: nginx, http_port: 8080 }

    Share roles through Ansible Galaxy and Collections (ansible-galaxy collection install amazon.aws).

    Expert topicsExpert

    • Ansible Vault: ansible-vault encrypt_string / encrypt group_vars/prod/secrets.yml — keep secrets safe in Git.
    • Dynamic inventory: plugins for AWS EC2, Azure, GCP and Kubernetes build host lists from live cloud tags.
    • Variable precedence: role defaults < inventory vars < play vars < extra-vars (-e, highest).
    • Rolling updates: serial: 2 and max_fail_percentage update few hosts at a time.
    • Performance: forks, pipelining, strategy: free, fact caching, async/poll for long tasks.
    • Quality: ansible-lint, Molecule for role testing, Execution Environments (containerised runtimes).
    • At scale: AWX / Ansible Automation Platform adds RBAC, scheduling, credentials, audit and a web UI; ansible-pull enables pull mode.
    • Beyond servers: network devices, Kubernetes (kubernetes.core), cloud resources and even Terraform wrappers.

    Module 04 · AWS-native IaC

    AWS CloudFormation

    Templates, stacks, change sets, StackSets and CDK — AWS-native infrastructure as code.

    ☁️ What is CloudFormation?

    AWS CloudFormation is AWS's native, declarative IaC service. You describe resources in a template (YAML or JSON); CloudFormation creates them as a single unit called a stack, handles ordering, and rolls back automatically if something fails. It is free — you pay only for the resources.

    TermMeaning
    TemplateYAML/JSON file describing resources
    StackA deployed instance of a template; the unit of create/update/delete
    Change setPreview of what an update will change (like terraform plan)
    StackSetsDeploy one template to many accounts and regions
    Drift detectionFinds resources changed outside CloudFormation
    Nested stacks / ModulesReuse and compose templates
    CDKDefine infrastructure in TypeScript/Python/Java; synthesises CloudFormation

    Template anatomyBasic

    yamlAWSTemplateFormatVersion: "2010-09-09"
Description: S3 bucket plus an EC2 instance
Parameters:
  EnvName:
    Type: String
    AllowedValues: [dev, prod]
    Default: dev
  InstanceType:
    Type: String
    Default: t3.micro
Mappings:
  RegionAmi:
    ap-south-1: {Ami: ami-0123456789abcdef0}
Conditions:
  IsProd: !Equals [!Ref EnvName, prod]
Resources:
  LogsBucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
    Properties:
      BucketName: !Sub "logs-${EnvName}-${AWS::AccountId}"
  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: !If [IsProd, m6i.large, !Ref InstanceType]
      ImageId: !FindInMap [RegionAmi, !Ref "AWS::Region", Ami]
Outputs:
  BucketArn:
    Value: !GetAtt LogsBucket.Arn
    Export: {Name: !Sub "${EnvName}-LogsBucketArn"}

    Only Resources is mandatory. Parameters = inputs, Mappings = lookup tables, Conditions = if-logic, Outputs = results (optionally exported to other stacks).

    Intrinsic functionsIntermediate

    FunctionUse
    !RefParameter value or resource ID
    !GetAttAttribute of a resource (e.g. ARN, DNS name)
    !SubString substitution with ${Var}
    !Join / !SplitCombine / split strings
    !If / !Equals / !AndConditions
    !FindInMapRead from Mappings
    !ImportValueUse another stack's export

    🚦 Operating Stacks

    bashaws cloudformation validate-template --template-body file://app.yml
aws cloudformation deploy --template-file app.yml --stack-name app-dev \
     --parameter-overrides EnvName=dev --capabilities CAPABILITY_NAMED_IAM
aws cloudformation create-change-set --stack-name app-dev --change-set-name cs1 \
     --template-body file://app.yml
aws cloudformation describe-stack-events --stack-name app-dev
aws cloudformation delete-stack --stack-name app-dev
    StatusMeaning / action
    CREATE_COMPLETESuccess
    ROLLBACK_COMPLETECreation failed and everything was rolled back — read stack events, delete stack, retry
    UPDATE_ROLLBACK_COMPLETEUpdate failed; previous state restored
    UPDATE_ROLLBACK_FAILEDRollback itself failed — fix cause then continue update rollback
    DELETE_FAILEDA resource couldn't be removed (e.g. non-empty S3 bucket)

    Expert featuresExpert

    • DeletionPolicy / UpdateReplacePolicy: Retain or Snapshot protects data resources. Stack policies and termination protection prevent accidents.
    • CreationPolicy + cfn-signal / WaitCondition make a stack wait until an instance has finished bootstrapping.
    • Custom resources (Lambda-backed) cover things CloudFormation doesn't support natively; Registry/Modules package best-practice patterns.
    • Resource import adopts existing resources; cfn-lint and cfn-guard lint and enforce policy.
    • Cross-stack design: export values, or split into layered stacks (network → data → app) to keep updates small and safe.
    • CI/CD: CodePipeline / GitHub Actions with change sets and manual approval; AWS SAM extends CloudFormation for serverless.
    ✅
    CloudFormation vs Terraform in one line: CloudFormation = AWS-only, no state file to manage, automatic rollback. Terraform = any cloud, richer language and ecosystem, you manage state.

    Comparison & Best Practices

    When to use which tool, and the habits that make IaC safe at scale.

    ⚖️ Choosing the Right Tool

    TerraformAnsibleCloudFormation
    Primary roleProvision infraConfigure & deployProvision AWS infra
    StyleDeclarativeProcedural YAML (idempotent modules)Declarative
    LanguageHCLYAML + Jinja2YAML / JSON
    StateState file (remote backend)StatelessManaged by AWS (stack)
    CloudsAnyAny (and on-prem)AWS only
    AgentNoneNone (SSH)None
    Preview changesplan--check --diffChange sets
    RollbackRe-apply older codeRe-run older playbookAutomatic on failure

    ✅ IaC Best Practices & Learning Path

    • Everything in Git; changes via pull request; plan output visible in review.
    • Small modules/stacks, one concern each; semantic versioning for shared modules.
    • Remote, locked, encrypted state; least-privilege credentials, OIDC instead of long-lived keys.
    • Never hard-code secrets; use a secrets manager.
    • Scan with Checkov / tfsec / cfn-guard; enforce policy as code.
    • Detect and fix drift on a schedule; forbid console changes in prod.
    • Prefer immutable infrastructure: bake with Packer, replace instead of patch.

    Framework Fundamentals

    The ideas every UI framework shares — components, props, state, reactivity and rendering — before you learn React, Vue, Angular or Next.js.

    🧭 Why use a UI framework at all?

    A browser gives you the DOM (Document Object Model): a tree of elements you can create, change and remove with JavaScript. For a small page, plain ("vanilla") JavaScript is fine. As an app grows, keeping the screen in sync with the data by hand becomes the hardest part of the job.

    javascript// Vanilla JS: you must remember every place the count appears
let count = 0;
const btn = document.querySelector("#inc");
const label = document.querySelector("#count");
const badge = document.querySelector("#badge");

btn.addEventListener("click", () => {
  count++;
  label.textContent = count;          // update #1
  badge.textContent = count;          // update #2 - easy to forget
  badge.hidden = count === 0;         // update #3
});

    A UI framework flips this around. You describe what the screen should look like for a given state, and the framework works out which DOM changes are needed. You change the data; the UI follows.

    React
    A library for building UIs from components with JSX. Huge ecosystem. Made by Meta.
    🟩
    Vue.js

    🅰️
    Angular

    📝
    Strictly, React calls itself a library (it only handles the view), while Angular is a framework (it decides the architecture). In job adverts and day-to-day talk, all of them are loosely called “frameworks”.

    🧩 Components and declarative UI

    A component is a reusable, self-contained piece of UI — a button, a product card, a whole page. It takes inputs, may keep its own data, and returns markup. An app is a tree of components: App contains Header, ProductList and Footer; ProductList contains many ProductCards.

    Imperative (how)

    “Find the list. Create an <li>. Set its text. Append it. If the list is empty, show the empty message, otherwise hide it.”

    Declarative (what)

    “The list shows one item per product. If there are no products, show ‘No results’.” The framework handles the steps.

    The same tiny greeting component in the three big frameworks:

    jsx// React (JSX)
function Greeting({ name }) {
  return <h1>Hello, {name}!</h1>;
}

    vue<!-- Vue (Single-File Component) -->
<script setup>

</script>

<template>
  <h1>Hello, {{ name }}!</h1>
</template>

    typescript// Angular (standalone component)
import { Component, input } from "@angular/core";

@Component({
  selector: "app-greeting",
  template: `<h1>Hello, {{ name() }}!</h1>`,
})

}

    Think in components: before coding a page, sketch it and draw boxes around each piece. Each box with its own job is a candidate component.

    📦 Props, state and one-way data flow

    Two kinds of data drive every component:

    Props (inputs)State
    Who owns it?The parent passes it inThe component itself
    Can the component change it?No — treat it as read-onlyYes — through the framework's update API
    ExampleA ProductCard receives product and onAddToCartA SearchBox remembers the text typed so far
    Name in each frameworkReact props · Vue props · Angular inputsReact useState · Vue ref() · Angular signal()

    Most frameworks use one-way data flow: data flows down from parent to child through props, and events flow up from child to parent through callbacks or emitted events. This makes it easy to answer “where did this value come from?”.

    Data down, events up — the child never edits the parent's data directly
    EXAMPLE · Cart counter

    The App component owns cartCount. It passes cartCount to Header (to show a badge) and an onAdd callback to each ProductCard. When a card's button is clicked, it calls onAdd(); App updates its state, and both the badge and the cards re-render with the new value.

    ⚠️
    Never mutate props. If a child needs to change a value, it should ask the owner (parent) to change it by raising an event. Two-way binding helpers such as Vue's v-model and Angular's [(ngModel)] are just shortcuts for “prop down + event up”.

    ⚡ Reactivity: virtual DOM, signals and compilers

    Reactivity means: when data changes, the UI that depends on it updates automatically. Frameworks achieve this in different ways.

    ApproachHow it worksUsed by
    Virtual DOM + diffingOn a state change the component function runs again and returns a new lightweight tree of objects. The framework compares (diffs) it with the previous tree and patches only the real DOM nodes that changed.React; Vue also uses a virtual DOM, optimised by its compiler
    Fine-grained reactivity (signals)Each piece of state is a reactive value that tracks who reads it. When it changes, only the exact computations and bindings that read it are re-run.Vue ref/reactive, Angular signals, SolidJS, Preact Signals
    Compiler-firstA build-time compiler analyses components and generates direct DOM-update code, so less work happens at run time.Svelte; Angular's template compiler; Vue's template compiler; the React Compiler (automatic memoisation)
    Zone-based change detectionAngular's older default: Zone.js notices async events (clicks, timers, HTTP) and then checks component bindings for changes.Angular (being replaced by signals + zoneless)

    You do not need to master the internals to be productive, but knowing them explains everyday rules — for example, why React needs keys on list items, and why you must not mutate state objects in React.

    📝
    The virtual DOM is not “faster than the DOM” by magic. It is a convenient way to let you re-describe the whole UI while still doing only the minimum real DOM work. Fine-grained systems skip much of the diffing by knowing exactly what changed.

    🔄 What happens in a render cycle

    Whatever the framework, an update follows the same broad steps:

    A typical virtual-DOM update. Fine-grained frameworks skip the full re-render and diff, updating only bindings that read the changed value.
    1. Trigger. A click, a timer, or a network response changes state (for example setCount(c => c + 1)).
    2. Schedule. The framework batches several changes together so it renders once, not many times.
    3. Render. Affected components produce a new description of the UI. This step should be pure: no network calls, no DOM changes.
    4. Reconcile / diff. The new description is compared with the previous one.
    5. Commit. Only the changed DOM nodes are created, updated or removed.
    6. Effects. After the DOM is updated, side effects run (React useEffect, Vue onUpdated/watchers, Angular afterNextRender/effect).
    💡
    “Render” in React means “call the component function”, not “paint pixels”. A component can render without any DOM change if the output is the same.

    🌐 SPA, MPA, SSR, SSG and ISR

    Where and when HTML is produced is a big architectural choice. You will hear these acronyms in every frontend interview.

    StrategyWhere HTML is builtWhenGood forWatch out for
    MPA (multi-page app)ServerEvery navigation loads a new pageContent sites, classic server appsFull page reloads, less app-like
    SPA / CSR (single-page app, client-side rendering)Browser (JavaScript)After the JS bundle loadsDashboards behind a login, highly interactive toolsBlank page until JS runs; weaker SEO; large bundles
    SSR (server-side rendering)ServerOn every requestPersonalised or frequently changing pages that need SEOServer cost; slower time-to-first-byte than static
    SSG (static site generation)Build serverOnce, at build timeDocs, blogs, marketing pagesContent is stale until the next build

    With SSR and SSG the browser receives ready HTML, then JavaScript hydrates it — attaching event listeners and state so the page becomes interactive.

    EXAMPLE · Online shop
    • Home and category pages: SSG/ISR — fast and SEO-friendly, revalidated every few minutes.
    • Product page with live stock: SSR or static shell + streamed dynamic part.
    • Account dashboard after login: CSR is fine — no SEO needed.
    • Meta-frameworks such as Next.js, Nuxt and Angular SSR let you mix these per route.

    ⚛️ JSX, function components and props

    A React component is a JavaScript function that returns JSX. JSX looks like HTML but is really JavaScript: a build tool (Vite, Next.js, etc.) turns <h1>Hi</h1> into function calls that create React elements.

    jsxfunction ProductCard({ name, price, inStock }) {
  const label = price.toFixed(2);           // plain JS before the return
  return (
    <article className="card">               {/* className, not class */}
      <h2>{name}</h2>                       {/* {} = any JS expression */}
      <p style={{ color: inStock ? "green" : "red" }}>
        £{label}
      </p>
      <label htmlFor="qty">Qty</label>      {/* htmlFor, not for */}
      <input id="qty" type="number" defaultValue={1} />
    </article>
  );
}
    JSX ruleWhy
    Return one root element (or a Fragment <>...</>)A function can only return one value
    Close every tag: <img />, <br />JSX is stricter than HTML
    Use className and htmlForclass and for are reserved words in JavaScript
    Attributes are camelCase: onClick, tabIndexThey map to DOM properties
    {} holds an expression, not a statementSo use ? : or &&, not if inside JSX
    style takes an object: style={{ marginTop: 8 }}Outer braces = JS, inner braces = object literal
    Component names start with a capital letter<card> is treated as an HTML tag; <Card> as your component
    💡
    JSX escapes values automatically, so {userInput} cannot inject HTML. The escape hatch dangerouslySetInnerHTML is named that way on purpose — only use it with sanitised content.

    Props and children

    Props are the arguments of your component. React passes them as a single object, which you usually destructure. The special children prop holds whatever you put between the opening and closing tags.

    jsxfunction Panel({ title, variant = "info", children }) {   // default value
  return (
    <section className={`panel panel-${variant}`}>
      <h3>{title}</h3>
      {children}
    </section>
  );
}

export default function App() {
  return (
    <Panel title="Shipping" variant="warning">
      <p>Orders after 2 pm ship tomorrow.</p>
    </Panel>
  );
}
    • Props are read-only. Never write props.title = ....
    • You can pass anything: strings, numbers, objects, arrays, functions, even other JSX elements.
    • Spread an object as props with <Button {...rest} /> — handy for wrapper components, but do not overuse it.
    • With TypeScript, describe props with a type: type PanelProps = { title: string; variant?: 'info' | 'warning'; children: React.ReactNode }.
    📝
    children is the key to composition: layout components (Card, Modal, Layout) wrap content without knowing what it is.

    🎛️ State with useState

    useState gives a component memory between renders. It returns the current value and a setter. Calling the setter schedules a re-render with the new value.

    jsximport { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  function addThree() {
    // Functional updates: each one receives the latest value
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1);   // count goes up by 3
  }

  return <button onClick={addThree}>Clicked {count} times</button>;
}

    Two rules trip up every beginner:

    1. State is a snapshot. Inside one render, count is a constant. Writing setCount(count + 1) three times only adds 1, because all three read the same old count. Use the functional form setCount(c => c + 1) when the new value depends on the old one.
    2. Treat state as immutable. React compares the old and new value with Object.is. If you mutate an object or array and pass the same reference back, React may skip the update.
    jsxconst [todos, setTodos] = useState([]);
const [user, setUser] = useState({ name: "Ana", city: "Leeds" });

// ❌ Mutation - same reference, UI may not update
todos.push(newTodo); setTodos(todos);

// ✅ Create new arrays / objects
setTodos(prev => [...prev, newTodo]);                         // add
setTodos(prev => prev.filter(t => t.id !== id));              // remove
setTodos(prev => prev.map(t => t.id === id ? { ...t, done: !t.done } : t)); // update
setUser(prev => ({ ...prev, city: "York" }));                 // update one field
    💡
    Keep state minimal. If a value can be calculated from props or other state (a filtered list, a total, a full name), compute it during render instead of storing it in another useState.

    🖱️ Events, conditional rendering, lists and keys

    Event handlers are passed as functions: onClick={handleClick}, not onClick={handleClick()} (that would call it during render). To pass arguments, wrap it: onClick={() => remove(item.id)}.

    jsxfunction ProductList({ products, onRemove, loading }) {
  if (loading) return <Spinner />;                      // early return

  return (
    <>
      {products.length === 0 && <p>No products found.</p>}
      <ul>
        {products.map(p => (
          <li key={p.id}>                                 {/* stable, unique key */}
            {p.name} {p.onSale ? <strong>SALE</strong> : null}
            <button onClick={() => onRemove(p.id)}>Remove</button>
          </li>
        ))}
      </ul>
    </>
  );
}
    PatternUse when
    if (...) return ... before the JSXWhole component output changes (loading, error, empty)
    cond ? <A /> : <B />Choose between two pieces of UI
    cond && <A />Show something or nothing
    list.map(item => <Row key={item.id} ... />)Render a list
    ⚠️
    The && trap: {items.length && <List />} renders a literal 0 when the list is empty, because 0 is a renderable number. Write {items.length > 0 && <List />}.
    ⚠️
    Keys tell React which item is which between renders. Use a stable ID from your data. Using the array index as a key breaks when items are inserted, removed or re-ordered — input text and component state can end up attached to the wrong row.

    Events in React are wrapped in a cross-browser synthetic event. Use e.preventDefault() to stop a form submit, and e.stopPropagation() to stop bubbling.

    📝 Forms: controlled vs uncontrolled

    Controlled input

    React state is the single source of truth. value comes from state and onChange updates it. Easy to validate, format or disable buttons as the user types.

    Uncontrolled input

    The DOM keeps the value. You read it when needed — via a ref or from FormData on submit. Less code and fewer re-renders; use defaultValue for the start value.

    jsx// Controlled
function SignupForm() {
  const [email, setEmail] = useState("");
  const invalid = !email.includes("@");

  function handleSubmit(e) {
    e.preventDefault();
    api.signup(email);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={email} onChange={e => setEmail(e.target.value)} />
      <button disabled={invalid}>Sign up</button>
    </form>
  );
}

// Uncontrolled with FormData
function SearchForm({ onSearch }) {
  function handleSubmit(e) {
    e.preventDefault();
    const data = new FormData(e.currentTarget);
    onSearch(data.get("q"));
  }
  return (
    <form onSubmit={handleSubmit}>
      <input name="q" defaultValue="" />
      <button>Search</button>
    </form>
  );
}
    ⚠️
    Switching an input between controlled and uncontrolled causes a React warning. A common cause is value={user.name} when name starts as undefined. Initialise with an empty string.
    💡
    For large forms, libraries such as React Hook Form (uncontrolled, fast) with a schema validator such as Zod save a lot of boilerplate.

    🔁 useEffect: syncing with the outside world

    useEffect runs code after React has updated the DOM. Use it to synchronise with things outside React: subscriptions, timers, browser APIs, third-party widgets, or fetching data in a client-only app.

    jsxuseEffect(() => {
  // setup
  const id = setInterval(() => setSeconds(s => s + 1), 1000);
  return () => clearInterval(id);        // cleanup
}, []);                                   // dependency array
    Dependency arrayWhen the effect runs
    OmittedAfter every render
    []Once after mount (cleanup on unmount)
    [userId]After mount and whenever userId changes (cleanup runs before each re-run)
    jsxfunction UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    let ignore = false;                       // guards against race conditions
    fetch(`/api/users/${userId}`)
      .then(r => r.json())
      .then(data => { if (!ignore) setUser(data); });
    return () => { ignore = true; };          // a newer request replaces this one
  }, [userId]);

  return user ? <h2>{user.name}</h2> : <p>Loading…</p>;
}

    Common mistakes

    • Missing dependencies — the effect uses stale values. Let the eslint-plugin-react-hooks rule exhaustive-deps guide you.
    • Infinite loops — setting state that is also a dependency, or depending on an object/array literal created on every render.
    • No cleanup — intervals, listeners and subscriptions keep running after unmount.
    • Effects for derived data — computing a filtered list in an effect and storing it in state. Just compute it during render.
    • Effects for user events — logic that should happen because the user clicked belongs in the click handler, not an effect.
    📝
    In development, React Strict Mode mounts, unmounts and re-mounts each component once to expose missing cleanups. Seeing your effect run twice in dev is expected; it does not happen in production.

    🧠 useRef, useMemo, useCallback and React.memo

    ToolWhat it doesTypical use
    useRef(initial)A mutable box { current } that survives renders. Changing it does not re-render.DOM access (inputRef.current.focus()), timer IDs, previous values
    useMemo(() => calc, deps)Caches a computed value until deps changeExpensive filtering/sorting; keeping an object reference stable
    useCallback(fn, deps)Caches a function reference until deps changePassing callbacks to memoised children or effect deps
    memo(Component)Skips re-rendering a component if its props are shallow-equalHeavy child components that receive the same props often
    jsximport { useRef, useMemo, useCallback, memo } from "react";

const Row = memo(function Row({ item, onSelect }) {
  return <li onClick={() => onSelect(item.id)}>{item.name}</li>;
});

function Catalogue({ items, query }) {
  const inputRef = useRef(null);

  const visible = useMemo(
    () => items.filter(i => i.name.toLowerCase().includes(query.toLowerCase())),
    [items, query]
  );

  const handleSelect = useCallback(id => console.log("selected", id), []);

  return (
    <>
      <input ref={inputRef} />
      <button onClick={() => inputRef.current.focus()}>Focus search</button>
      <ul>{visible.map(i => <Row key={i.id} item={i} onSelect={handleSelect} />)}</ul>
    </>
  );
}

    useCallback(fn, deps) is the same as useMemo(() => fn, deps). Without useCallback, handleSelect would be a new function every render, so memo(Row) would always see changed props.

    💡
    Measure first with React DevTools Profiler. Memoisation has a cost and adds complexity. The React Compiler (an optional build plugin) can add this memoisation automatically, which is why many new codebases write fewer manual useMemo/useCallback calls.

    🪝 Custom hooks, Context and the rules of hooks

    A custom hook is a function whose name starts with use and which calls other hooks. It lets components share stateful logic (not state itself — each caller gets its own copy).

    jsxfunction useLocalStorage(key, initial) {
  const [value, setValue] = useState(() => {
    const saved = localStorage.getItem(key);      // lazy initialiser runs once
    return saved !== null ? JSON.parse(saved) : initial;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];
}

// usage
const [theme, setTheme] = useLocalStorage("theme", "light");

    Context passes a value deep down the tree without threading props through every level ("prop drilling").

    jsximport { createContext, useContext, useState } from "react";

const ThemeContext = createContext("light");

export function App() {
  const [theme, setTheme] = useState("dark");
  return (
    <ThemeContext value={theme}>          {/* React 19; older: <ThemeContext.Provider value=...> */}
      <Toolbar onToggle={() => setTheme(t => (t === "dark" ? "light" : "dark"))} />
    </ThemeContext>
  );
}

function ThemedButton() {
  const theme = useContext(ThemeContext);  // reads the nearest provider
  return <button className={`btn-${theme}`}>OK</button>;
}
    ⚠️
    Every component that reads a context re-renders when its value changes. Context is great for rarely-changing values (theme, locale, current user). For fast-changing global state, consider a store such as Zustand, Redux Toolkit or a server-state library like TanStack Query.

    Rules of hooks

    1. Call hooks only at the top level of a component or custom hook — never inside conditions, loops or nested functions. React relies on the call order to match each hook with its stored state.
    2. Call hooks only from React function components or custom hooks, not from plain functions or class components.
    3. (The new use API is the exception: it may be called conditionally.)

    🆕 React 19 highlights

    React 19 (stable since December 2024) added features mostly aimed at forms, async work and less boilerplate.

    FeatureWhat it does

function Dashboard() {
  return (
    <ErrorBoundary fallback={<p>Reports failed to load.</p>}>
      <Suspense fallback={<Spinner />}>
        <Reports />
      </Suspense>
    </ErrorBoundary>
  );
}
    • Suspense shows a fallback while something inside it is suspended — a lazy component loading its code, or data read with use() / a Suspense-enabled library.
    • lazy() splits a component into its own JavaScript chunk, downloaded only when first rendered.
    • Error boundaries catch errors thrown during rendering of their children and show a fallback instead of a blank screen. They must be written as class components using static getDerivedStateFromError / componentDidCatch, so most teams use the small react-error-boundary package.
    • Error boundaries do not catch errors in event handlers or in async code such as a setTimeout — use try/catch there.

  const y = ref(0);

}

    📶 Signals: signal, computed and effect

    Signals are Angular's fine-grained reactive primitive. A signal is a getter function that holds a value and notifies the framework (and other signals) that read it when it changes.

    typescriptimport { Component, signal, computed, effect } from "@angular/core";

@Component({
  selector: "app-cart",
  template: `
    <p>{{ count() }} items · total £{{ total() }}</p>
    <button (click)="add({ id: 3, price: 5 })">Add</button>
  `,
})
export class Cart {
  items = signal<{ id: number; price: number }[]>([]);   // writable signal
  count = computed(() => this.items().length);          // read-only, cached
  total = computed(() => this.items().reduce((s, i) => s + i.price, 0));

  constructor() {
    effect(() => {                                      // re-runs when items() changes
      localStorage.setItem("cart", JSON.stringify(this.items()));
    });
  }

  add(item: { id: number; price: number }) {
    this.items.update(list => [...list, item]);         // or this.items.set(newList)
  }
}
    APIPurpose
    signal(v)Writable state. Read with s(), write with .set(v) or .update(fn)
    computed(fn)Derived, read-only, lazily evaluated and memoised
    effect(fn)Side effect that re-runs when signals it reads change. Use sparingly (sync to storage, logging, non-Angular APIs)
    linkedSignalA writable signal that resets when a source signal changes (e.g. selected item when the list changes)
    toSignal(obs$) / toObservable(sig)Bridges between RxJS and signals (@angular/core/rxjs-interop)
    ⚠️
    Signals use reference equality by default. Mutating an array inside a signal (this.items().push(x)) does not notify anyone. Always set a new array or object, as with React state.

    • Props passed from a Server to a Client Component must be serialisable (strings, numbers, plain objects, arrays, Dates, Promises…) — not ordinary functions (Server Actions are the exception).

    🗄️ Data fetching and caching basics

    In Server Components you fetch data with plain async/await — fetch, an ORM, or any SDK. Next.js adds caching and revalidation options on top.

    🔢 Same component, three frameworks

    React

    jsximport { useState } from "react";

  const [count, setCount] = useState(0);
  const [text, setText] = useState("");
  const [todos, setTodos] = useState([]);
  const remaining = todos.length;                          // derived during render

    e.preventDefault();

    setText("");
  }

  return (

      <form onSubmit={add}>

        <button>Add</button>
      </form>

        {todos.map(t => (
          <li key={t.id}>
            {t.text} <button onClick={() => setTodos(prev => prev.filter(x => x.id !== t.id))}>×</button>
          </li>
        ))}
      </ul>
      <p>{remaining} item(s)</p>
    </section>
  );
}

    🧱 Component design best practices

    • Single responsibility. A component should do one job. If its name needs “and” (ProductListAndFilters), split it.
    • Composition over configuration. Prefer passing children/slots to adding a dozen boolean props (showHeader, showFooter, compact…).
    • Presentational vs container. Keep UI components dumb (props in, events out) and put data fetching in a parent, hook, composable or service.
    • Lift state up to the closest common parent when two siblings need the same data.
    • Avoid prop drilling through many layers: use composition first, then Context / provide-inject / a service or store.
    • Keep state minimal and derived values computed. Duplicated state gets out of sync.
    • Colocate. Keep a component's styles, tests and stories next to it.

    Glossary and Cheat Sheet

    Grouped definitions, look-alike terms that interviewers love to compare, and one syntax table across React, Vue, Angular and Next.js.

    🧩 Core concepts

    ComponentA reusable, self-contained unit of UI: markup + logic + optional styles.
    Props / inputsRead-only values passed from a parent to a child.
    StateData a component owns that changes over time and drives re-rendering.
    Event / output / emitHow a child notifies its parent that something happened.
    Declarative UIDescribing what the UI should look like for a given state.
    One-way data flowData moves down through props; changes move up through events.
    Lifting state upMoving shared state to the closest common parent of the components that need it.
    Prop drillingPassing props through intermediate components that do not use them.
    CompositionBuilding complex UI by nesting and combining small components (children, slots).
    Side effectWork outside rendering: network calls, timers, subscriptions, DOM APIs.

    ⚡ Rendering and reactivity terms

    Virtual DOMAn in-memory tree of objects describing the UI; compared between renders to find changes.
    Reconciliation / diffingComparing the new and old virtual trees to compute minimal DOM updates.
    Fine-grained reactivityTracking dependencies per value so only code reading a changed value re-runs.
    SignalA reactive value with a getter that notifies dependants when it changes.

    🧭 Fundamentals

    What problem do UI frameworks solve compared with vanilla JavaScript?

    They keep the UI in sync with application state. Instead of writing imperative DOM updates in many places, you describe the UI declaratively as a function of state, and the framework computes and applies the minimal DOM changes. They also give you components for reuse, conventions for data flow, routing, and tooling for builds, testing and server rendering.

    What is the virtual DOM and how does it differ from fine-grained reactivity?

    A virtual DOM is a lightweight in-memory tree describing the UI. On a state change a component re-renders into a new tree, the framework diffs it against the old one and patches only the changed DOM nodes (React). Fine-grained reactivity (signals in Angular, Solid; Vue's reactivity system) tracks which computations read which values, so a change re-runs only those exact bindings, avoiding much of the diffing work. Vue combines both: fine-grained tracking decides which components update, and a compiler-optimised virtual DOM updates them.

    Explain CSR, SSR, SSG and ISR. When would you use each?

    CSR builds HTML in the browser with JS — fine for logged-in dashboards. SSR builds HTML on the server per request — personalised or fast-changing pages that need SEO. SSG builds HTML at build time — docs, blogs, marketing. ISR is SSG that re-generates pages in the background after a time or on demand — large catalogues. Meta-frameworks let you choose per route.

    What is hydration and what causes a hydration mismatch?

    Hydration is when client-side JavaScript takes over server-rendered HTML: it rebuilds the component tree, attaches event listeners and state. A mismatch happens when the first client render differs from the server HTML — for example rendering new Date(), Math.random(), window.innerWidth or localStorage values during render, or invalid HTML nesting. Fix it by rendering browser-only values after mount (in an effect) or making the server and client output identical.

    Why do lists need keys (React key, Vue :key, Angular track)?

    Keys give each item a stable identity so the framework can match old and new items when a list changes. With stable keys it can move, insert or remove DOM nodes and keep each row's state. Without them, or with array indexes on a list that is re-ordered, it may reuse the wrong DOM node — inputs keep the wrong text, animations jump, and work is wasted re-creating nodes.

    ⚛️ React

    What are the rules of hooks and why do they exist?

    Call hooks only at the top level of a function component or custom hook — not in loops, conditions or nested functions — and only from React functions. React stores hook state in a list per component and matches each call by its order. If a condition skipped a hook on one render, every following hook would read the wrong state. The eslint-plugin-react-hooks plugin enforces this. (The use API is an exception and may be called conditionally.)

    Explain the useEffect dependency array and cleanup function.

    The effect runs after render. With no array it runs after every render; with [] once after mount; with [a, b] after mount and whenever a or b change (compared with Object.is). The function you return is the cleanup: React runs it before the effect re-runs and on unmount — use it to clear timers, unsubscribe, abort fetches or ignore stale responses. Every reactive value used inside should be in the array, otherwise you get stale closures.

    When would you use useMemo, useCallback and React.memo — and when not?

    memo skips re-rendering a component when its props are shallow-equal. useCallback and useMemo keep function and object references (or expensive results) stable so memo and effect dependencies work. Use them after profiling shows a real cost: expensive calculations, large lists, or memoised children. Avoid wrapping everything — it adds code and memory, and cheap calculations are faster to just redo. The React Compiler can apply this memoisation automatically.

    How do you share state between components in React?

    In order of preference: lift state to the nearest common parent; use composition (pass components as children) to avoid drilling; use Context for low-frequency global values such as theme, locale or the current user; use a store (Zustand, Redux Toolkit, Jotai) for complex client state; and use a server-state library (TanStack Query, SWR) or Server Components for data that really lives on the server. Do not copy server data into global client state by hand.

    What changed in React 19 that you would use in a new project?

    Actions for async updates with <form action={fn}> and useActionState for pending/error state; useFormStatus for submit buttons; useOptimistic for optimistic UI; the use API to read promises and context; ref as a normal prop so forwardRef is unnecessary; <Context> as its own provider; and native support for <title>/<meta> in components. Server Components and Server Actions are stable for frameworks such as Next.js.

    🟩 Vue

    What is the difference between ref and reactive?

    ref wraps any value in an object with a .value property; it can hold primitives and be reassigned, and it is unwrapped automatically in templates. reactive returns a deep Proxy of an object, accessed without .value, but it only works with objects, and you lose reactivity if you destructure it or replace the whole object. The Vue docs recommend ref as the default.

    When do you use computed vs watch vs watchEffect?

    Use computed to derive a value from other state — it is cached and should be pure. Use watch to run a side effect when a specific source changes, when you need the old value, or when you want it lazy (not run immediately). Use watchEffect to run a side effect immediately and re-run it whenever any reactive value it reads changes.

    How do parent and child components communicate in Vue 3?

    Parent → child with props (defineProps). Child → parent with events (defineEmits and emit('save', data)). Two-way with v-model on a component, implemented with defineModel() (Vue 3.4+). Content via slots, including scoped slots that pass data back to the parent's template. For deep trees, provide/inject; for app-wide state, Pinia.

    What is a composable and how is it different from a mixin?

    A composable is a function (by convention useXxx) that uses Composition API features — refs, computed, watchers, lifecycle hooks — and returns reactive state and functions. Unlike Vue 2 mixins, it is explicit about what it returns (no hidden properties merged into this), avoids name clashes, can take arguments, and has full TypeScript support.

    Explain v-if vs v-show and why v-if and v-for should not be on the same element.

    v-if creates and destroys the element (and child components); v-show always renders it and toggles display. Use v-show for frequent toggles, v-if for rare ones or when the content is expensive. In Vue 3, v-if has higher priority than v-for on the same element, so it cannot access the loop variable; filter with a computed list or move v-for to a wrapping <template>.

    🅰️ Angular

    What are signals and why did Angular introduce them?

    Signals are reactive values (signal, computed, effect) that track exactly who reads them. They let Angular know precisely which components need updating, instead of relying on Zone.js to detect that “something async happened” and checking the whole tree. This enables faster, more predictable change detection, zoneless apps, simpler component state and signal-based APIs like input(), output() and model().

    Explain dependency injection in Angular and the meaning of providedIn: 'root'.

    Classes declare what they need and Angular's hierarchical injectors supply instances. @Injectable({ providedIn: 'root' }) registers the service with the root injector, so there is one shared singleton for the app, and it is tree-shaken if never used. Providing a service in a component's providers array creates a separate instance for that component subtree. DI makes testing easy because you can provide a mock instead.

    What is the difference between switchMap, mergeMap, concatMap and exhaustMap?

    All map each source value to an inner Observable. switchMap cancels the previous inner one — ideal for type-ahead search. mergeMap runs them all in parallel. concatMap queues them and runs one at a time in order — good for ordered saves. exhaustMap ignores new values while one is running — good for preventing double-submits on a login button.

    Compare reactive forms and template-driven forms.

    Reactive forms define the form model in the component class with FormGroup/FormControl/FormBuilder; they are explicit, synchronous, strongly typed and easy to unit test — best for complex or dynamic forms. Template-driven forms build the model from ngModel directives in the template; they are quick for simple forms but harder to test and scale.

    How does change detection work, and what do OnPush and zoneless change?

    Classically, Zone.js patches async APIs and after each event Angular checks every component's bindings top-down. With OnPush, a component is only checked when an input reference changes, an event originates inside it, an async pipe emits, or a signal it reads changes. Zoneless removes Zone.js entirely: Angular schedules change detection when signals change, template event handlers run, or markForCheck() is called. It is enabled with provideZonelessChangeDetection() and is the default for new projects in recent versions.

    ▲ Next.js

    What is the difference between Server Components and Client Components?

    Server Components are the default in the App Router. They run only on the server, can be async, can read databases and secrets directly, and send no JavaScript for themselves to the browser. Client Components are marked with 'use client'; they are pre-rendered on the server and hydrated in the browser, and can use state, effects, event handlers and browser APIs. Keep most of the tree on the server and make interactive leaves client components.

    Explain layout.tsx, page.tsx, loading.tsx and error.tsx.

    page.tsx makes a route reachable and renders its content. layout.tsx wraps a segment and its children and persists state across navigation; the root layout must render <html> and <body>. loading.tsx wraps the page in a Suspense boundary to show instant loading UI while it streams. error.tsx is a Client Component error boundary for the segment, receiving error and a reset function.

    How does caching and revalidation work in Next.js 15+?

    Since Next.js 15, fetch is not cached by default; you opt in with cache: 'force-cache' or next: { revalidate: n }. Routes without request-time APIs are still prerendered statically. Segment config such as export const revalidate = 60 sets ISR timing. After a mutation, revalidatePath or revalidateTag purge cached data so the next request gets fresh content. Next.js 16 adds an opt-in Cache Components model using 'use cache'.

    What are Server Actions and what security concerns do they have?

    Server Actions are async functions marked 'use server' that run on the server and can be passed to <form action> or called from Client Components, so you can mutate data without writing an API route. They work with progressive enhancement. Each one is effectively a public POST endpoint: you must authenticate and authorise the user, validate all input (e.g. with Zod), and never trust IDs sent from the client.

    When would you use a route handler instead of a Server Action?

    Use route handlers (app/api/.../route.ts) for endpoints consumed by things other than your React UI: webhooks from Stripe or GitHub, a public REST API, a mobile app, file downloads, or when you need full control of HTTP methods, headers and status codes. Use Server Actions for mutations triggered from your own forms and components.

    🏗️ Architecture and scenarios

    A product listing page is slow to load. How would you investigate and fix it?

    Measure first: Lighthouse/PageSpeed for LCP, INP and CLS, the network tab for bundle size and waterfalls, and the framework profiler for re-renders. Typical fixes: render the list on the server (SSR/SSG/ISR) instead of fetching after load; optimise images (next/image, correct sizes, priority for the hero); split code and lazy-load below-the-fold widgets; fetch in parallel; virtualise very long lists; memoise expensive rows or use stable keys; and remove heavy dependencies. Re-measure after each change.

    How would you structure state in a large single-page application?

    Separate state by type. Server state (products, orders) belongs in a caching layer such as TanStack Query, Server Components, or Angular services with signals/RxJS. URL state (filters, page, tab) belongs in the query string so it is shareable. Global UI state (theme, session, cart) goes in Context/Pinia/a service or a small store. Local state stays in components. Derive rather than duplicate, and keep a single source of truth for each value.

    Your team must choose between React, Vue and Angular for a new enterprise app. How do you decide?

    Start from constraints, not preference: the team's current skills and hiring market; the existing codebase and design system; the need for SEO/SSR (Next.js, Nuxt, Angular SSR); how much structure the team needs (Angular gives conventions and built-ins, React gives flexibility, Vue sits between); long-term support and upgrade path; and integration needs such as mobile (React Native). Build a small spike of a real feature in the top two options and compare developer experience, bundle size and testability before deciding.

    How do you design a reusable component library for several teams?

    Base it on design tokens (colours, spacing, typography) and accessible primitives; keep components small and composable with clear props/events and slots/children rather than many flags; type the public API with TypeScript; document with Storybook and usage guidelines; test behaviour and accessibility (Testing Library, axe); version with semantic versioning and changelogs; and avoid app-specific logic or data fetching inside library components.

    How would you migrate a large app to a newer framework version or a new framework?

    Incrementally, not big-bang. Upgrade dependencies step by step using official tools (Angular ng update, React codemods, the Vue migration build), keep tests green at each step, and use feature flags. For a framework change, use the strangler-fig pattern: host new routes or micro-frontends in the new stack while old screens keep working, share a design system, and migrate the highest-value screens first. Track bundle size and errors during rollout.

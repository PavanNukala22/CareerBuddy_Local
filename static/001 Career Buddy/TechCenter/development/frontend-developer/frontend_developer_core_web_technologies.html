    How the Web Works

    What happens between typing a URL and seeing a page — and where HTML, CSS and JavaScript fit in.

    🧑‍💻 What does a frontend developer do?

    A frontend developer builds the part of a website or web app that people see and use in the browser. You turn designs into working pages, make them respond to clicks and typing, load data from servers, and make sure the result is fast, accessible and works on phones, tablets and desktops.

    The browser is your runtime. It only understands three core languages — HTML, CSS and JavaScript (plus WebAssembly for special cases). Everything else you meet — React, Angular, Vue, TypeScript, Sass, Tailwind — is eventually turned into those three.

    🧱

    Says what the content is: headings, paragraphs, links, forms, images.
    🎨
    CSS — presentation
    Says how it looks: colours, fonts, spacing, layout, animation, responsiveness.
    ⚙️
    JavaScript — behaviour
    Says what happens: reacting to events, fetching data, updating the page.
    🔷

    JavaScript plus static types. Compiled to plain JavaScript before the browser runs it.

    🌐 From URL to pixels: what happens when you open a page

    When you type https://shop.example.com/products and press Enter, a lot happens in well under a second. Knowing these steps helps you debug slow pages and understand why things like <script defer> matter.

    The critical path from a URL to pixels on screen
    1. Parse the URL — scheme (https), host (shop.example.com), path (/products).
    2. DNS lookup — the browser asks the Domain Name System for the server's IP address (results are cached).
    3. Connect — open a TCP (or QUIC for HTTP/3) connection and do a TLS handshake so traffic is encrypted.
    4. HTTP request — send GET /products with headers such as Accept and cookies.
    5. Response — the server returns a status code (200 OK), headers and the HTML body.
    6. Parse HTML into the DOM — the browser reads HTML top to bottom and builds a tree of nodes. When it finds <link rel="stylesheet">, <script> or <img> it requests those too.
    7. Parse CSS into the CSSOM — a tree of style rules. CSS is render-blocking: the page is not painted until it is ready.
    8. Run JavaScript — a classic <script> without defer/async pauses HTML parsing until it downloads and runs.
    9. Render tree → layout → paint → composite — DOM + CSSOM are combined, sizes and positions are calculated, pixels are drawn in layers and combined on screen.
    📝
    This sequence is called the critical rendering path. Shortening it — fewer render-blocking resources, smaller files, deferred scripts — is the core of frontend performance work.

    🌳 The DOM: the page as a tree

    The DOM (Document Object Model) is the browser's live, in-memory tree of your page. Every element, attribute and piece of text becomes a node. JavaScript does not edit your HTML file — it edits the DOM, and the browser re-renders what changed.

    html<body>
  <h1 id="title">Hello</h1>
  <ul class="list">
    <li>One</li>
    <li>Two</li>
  </ul>
</body>

    This HTML becomes a tree: body has two children (h1 and ul), and ul has two li children, each with a text node.

    javascriptconst title = document.querySelector("#title");   // find one element by CSS selector
title.textContent = "Welcome!";                    // change its text

const li = document.createElement("li");           // create a new node
li.textContent = "Three";
document.querySelector(".list").append(li);         // insert it into the tree

console.log(document.querySelectorAll("li").length); // 3

    Change text safelyel.textContent = value

    📨 HTTP basics: methods and status codes

    HTTP is the request/response protocol between the browser and servers. Each request has a method, a URL, headers and sometimes a body. Each response has a status code, headers and usually a body (HTML, JSON, an image…).

    MethodMeaningSafe?Idempotent?

    POSTCreate something / submit dataNoNo

    🔒 Same-origin, CORS, cookies and storage

    An origin is the combination of scheme + host + port. https://app.example.com and https://api.example.com are different origins. The same-origin policy stops a page from reading responses from another origin unless that server allows it with CORS headers such as Access-Control-Allow-Origin.

    📝
    CORS is enforced by the browser, and it is configured on the server. If you see a CORS error in the console, the fix is almost always a server header — not frontend code.

    HTML5: Structure, Semantics and Accessibility

    Write HTML that browsers, search engines and assistive technologies all understand.

    📄 Document structure

    Every HTML page follows the same skeleton. HTML is made of elements written as tags (<p>…</p>), which can carry attributes (lang="en"). Some elements are void and have no closing tag: <img>, <input>, <br>, <meta>, <link>.

    html<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Desk Lamps | Brightly</title>
  <meta name="description" content="Shop energy-saving desk lamps with free delivery.">
  <link rel="stylesheet" href="/css/main.css">
  <script src="/js/app.js" defer></script>
</head>
<body>
  <!-- visible content goes here -->
</body>
</html>
    LineWhy it matters
    <!DOCTYPE html>Puts the browser in standards mode. Without it you get quirks mode and odd layout.
    lang="en"Tells screen readers which pronunciation to use and helps translation tools and search engines.
    <meta charset="utf-8">Text encoding. Must be in the first 1024 bytes so accents and emoji display correctly.
    <meta name="viewport">Without it, phones render the page at ~980px wide and zoom out. Essential for responsive design.
    <title>Shown in the tab, bookmarks and search results. Unique per page.
    deferDownloads the script in parallel and runs it after the HTML is parsed, in order.
    💡
    Put scripts in the <head> with defer (or use type="module", which is deferred by default). This is cleaner than putting <script> at the end of <body>.

    🏛️ Semantic elements, headings and landmarks

    Semantic HTML means choosing the element that describes the meaning of the content, not its looks. A <div> says nothing; a <nav> says “this is navigation”. Screen readers, search engines and browser reader modes all use this meaning.

    Headings

    • Use one <h1> describing the page, then <h2> for sections, <h3> for subsections.
    • Do not skip levels for styling (h2 → h4). Choose the level by structure, then style it with CSS.
    • Screen reader users often jump through headings to scan a page — they are the table of contents.
    📝
    “Divitis” — building everything from <div> and <span> — works visually but is invisible to assistive technology. Use <div> only when no semantic element fits (e.g. a pure layout wrapper).

    ♿ Accessibility essentials and ARIA

    Accessibility (a11y) means people using screen readers, keyboards, switch devices, voice control or zoom can use your site. It is also a legal requirement in many countries (for example under the European Accessibility Act and the ADA), usually measured against WCAG 2.2 level AA.

    The five rules of ARIA

    1. Use native HTML first. A <button> already has the button role, focus and keyboard support. “No ARIA is better than bad ARIA.”
    2. Do not change native semantics unless you must (don't put role="button" on an <h2> — wrap a button inside it).
    3. All interactive ARIA controls must be keyboard-operable.
    4. Do not use role="presentation" or aria-hidden="true" on focusable elements.
    5. Every interactive element needs an accessible name (visible text, <label>, aria-label or aria-labelledby).
    html<!-- Icon-only button: give it a name -->
<button type="button" aria-label="Close dialog">
  <svg aria-hidden="true" focusable="false">…</svg>
</button>

<!-- Disclosure (show/hide) pattern -->
<button type="button" aria-expanded="false" aria-controls="filters">Filters</button>
<div id="filters" hidden>…</div>

<!-- Announce dynamic messages politely -->
<p role="status">3 items added to your basket</p>
    CheckTarget
    KeyboardEverything reachable with Tab/Shift+Tab, operable with Enter/Space/arrows, visible focus outline, no keyboard traps
    Colour contrast (WCAG AA)Normal text 4.5:1; large text (24px, or ~18.66px bold) 3:1; UI components and focus indicators 3:1
    Do not rely on colour aloneErrors need text or an icon, not only a red border
    Focus orderFollows the visual order; avoid positive tabindex values
    MotionRespect prefers-reduced-motion
    💡
    Test with your keyboard only for five minutes, then with a screen reader (NVDA on Windows, VoiceOver on macOS/iOS). Automated tools like Lighthouse or axe catch only part of the problems.

    CSS3 and Modern CSS

    🎯 Selectors and specificity

    A CSS rule is a selector plus declarations: selector { property: value; }. When several rules set the same property on the same element, the browser picks a winner using the cascade, and specificity is a big part of it.

    🌊 The cascade and inheritance

    When declarations conflict, the browser decides in this order (first difference wins):

    1. Origin and importance — user-agent (browser defaults) < user styles < author (your) styles; !important flips the order for important declarations.
    2. Cascade layers — with @layer, later layers beat earlier layers (unlayered styles beat all layers).
    3. Specificity — higher wins.
    4. Order of appearance — the later rule wins.
    css@layer reset, base, components, utilities;

@layer base       { a { color: navy; } }
@layer components { .btn { color: white; } }
@layer utilities  { .text-red { color: crimson; } }  /* wins over components, even with equal specificity */

    Inheritance: some properties pass from parent to child automatically — mostly text-related ones like color, font-family, font-size, line-height, visibility. Box-related ones like margin, padding, border, background, width do not inherit.

    KeywordMeaning
    inheritTake the parent's computed value
    initialUse the property's initial value from the spec (e.g. display: inline)
    unsetinherit if the property inherits, otherwise initial
    revertRoll back to the browser's default style for that element
    📝
    A common surprise: button and input do not inherit font by default. Add button, input, select, textarea { font: inherit; } to your reset.

    📦 The box model, box-sizing and units

    Every element is a rectangular box: content → padding → border → margin.

    box-sizingwidth: 300px; padding: 20px; border: 5px means…Rendered width

    border-boxwidth includes padding and border; content shrinks300px (content = 250px)

    📐 repeat, minmax and auto-fit vs auto-fill

    The single most useful Grid line in real projects — a responsive card grid with no media queries:

    css.products {
  display: grid;
  grid-template-columns: repeat(auto-fill, minmax(min(220px, 100%), 1fr));
  gap: 1.25rem;
}

    The browser fits as many columns of at least 220px as possible, then stretches them to fill the row. min(220px, 100%) stops overflow on very narrow screens.

    KeywordBehaviour when there are fewer items than fit in a row
    auto-fillKeeps the empty tracks. Items stay at the column width; empty columns hold space. (3 items in a row that fits 5 → 3 cards + 2 empty slots.)
    auto-fitCollapses empty tracks to 0, so the 1fr items stretch to fill the whole row. (3 items → 3 wide cards.)

    When there are enough items to fill the row, both behave identically. The difference only appears with few items on a wide screen.

    💡

    A nested grid normally has its own independent tracks, so content in sibling cards does not line up. With subgrid (all major browsers since 2023) a child grid reuses its parent's tracks.

    ⏳ Promises, async/await and fetch

    Network requests, timers and file reads take time. JavaScript is single-threaded, so instead of blocking it uses asynchronous code. A Promise is an object representing a value that will be available later. It is pending, then settles once as fulfilled (with a value) or rejected (with an error).

    javascriptconst wait = ms => new Promise(resolve => setTimeout(resolve, ms));

  .then(res => res.json())

  .finally(() => hideSpinner());

    async/await is syntax over Promises that reads like synchronous code. An async function always returns a Promise; await pauses that function (not the whole page) until the Promise settles.

    🔁 The event loop: microtasks vs macrotasks

    JavaScript runs on one main thread with a call stack. Slow work (timers, network, events) is handled by the browser, which queues callbacks to run later. The event loop decides what runs next:

    One turn of the browser event loop
    QueueExamplesWhen it runs
    MicrotasksPromise.then/catch/finally, code after await, queueMicrotask, MutationObserverRight after the current script/task, all of them, before rendering or the next macrotask
    Macrotasks (tasks)setTimeout, setInterval, DOM events, MessageChannel, network callbacksOne per loop turn, after microtasks are drained
    Animation framerequestAnimationFrameBefore the next paint (~every 16.7 ms on a 60 Hz screen)
    EXAMPLE · Predict the output order
    javascriptconsole.log("1: script start");
setTimeout(() => console.log("2: setTimeout"), 0);
Promise.resolve()
  .then(() => console.log("3: promise 1"))
  .then(() => console.log("4: promise 2"));
queueMicrotask(() => console.log("5: microtask"));
(async () => {
  console.log("6: async fn body");
  await null;
  console.log("7: after await");
})();
console.log("8: script end");

    Output: 1, 6, 8, 3, 5, 7, 4, 2

    1. Synchronous code runs first: 1, then 6 (an async function runs synchronously until its first await), then 8.
    2. Microtask queue now holds [3, 5, 7] in the order they were queued. They run: 3, 5, 7. Running 3 queues 4, which runs next in the same drain.
    3. Only when microtasks are empty does the timer macrotask run: 2 — even though its delay was 0.
    ⚠️
    A long synchronous loop or a microtask that keeps queueing microtasks blocks rendering and input — the page freezes. Split heavy work into chunks (setTimeout, scheduler.yield() where supported) or move it to a Web Worker.

    🌐 Web fundamentals

    What happens when you type a URL into the browser and press Enter?

    The browser parses the URL, resolves the hostname via DNS (using caches first), opens a TCP or QUIC connection and performs a TLS handshake for HTTPS, then sends an HTTP request. The server responds with a status, headers and HTML. The browser parses the HTML into the DOM, fetching CSS, scripts and images it discovers; CSS is parsed into the CSSOM and blocks rendering; classic scripts block parsing unless defer/async. DOM and CSSOM form the render tree, then the browser runs layout, paint and compositing. JavaScript and later resources can update the page afterwards.

    What is the critical rendering path and how do you optimise it?

    It is the sequence of work needed for the first render: HTML → DOM, CSS → CSSOM, render tree, layout, paint. To optimise: inline or minimise critical CSS, defer non-critical JavaScript, reduce and compress resources, preload key fonts and the LCP image (fetchpriority="high"), avoid lazy-loading above-the-fold images, set image dimensions to prevent layout shift, and use HTTP caching and a CDN.

    Explain the same-origin policy and CORS. How do you fix a CORS error?

    The same-origin policy stops scripts on one origin (scheme + host + port) from reading responses from another. CORS is the mechanism by which a server opts in, using headers such as Access-Control-Allow-Origin. For non-simple requests (e.g. JSON PUT or custom headers) the browser first sends an OPTIONS preflight. CORS errors are fixed on the server (or via a same-origin proxy in development), not by changing frontend code.

    Compare cookies, localStorage and sessionStorage.

    Cookies are small (~4 KB), sent with every matching request, and can be HttpOnly (invisible to JavaScript), Secure and SameSite — best for session identifiers. localStorage holds ~5 MB per origin, persists until cleared, is never sent automatically and is synchronous. sessionStorage is the same but scoped to one tab and cleared when it closes. Neither web storage is safe for secrets because any XSS can read it.

    What are Core Web Vitals and how would you improve a poor LCP?

    They are Google's user-centred metrics: LCP (Largest Contentful Paint, good ≤ 2.5 s), INP (Interaction to Next Paint, good ≤ 200 ms) and CLS (Cumulative Layout Shift, good ≤ 0.1). For LCP: find the LCP element in DevTools, make sure it is discoverable in the HTML (not injected by JS), give it fetchpriority="high", do not lazy-load it, serve a correctly sized modern format (AVIF/WebP), reduce server response time, and remove render-blocking CSS/JS.

    ♿ HTML & accessibility

    Why does semantic HTML matter?

    Semantic elements carry meaning that browsers, assistive technologies and search engines use. Screen readers expose landmarks (<nav>, <main>) and headings for navigation; native controls like <button> come with focus, keyboard support and roles for free; search engines understand structure; reader modes work. It also makes code more readable for developers. A page of <div>s looks the same but is much harder to use for many people.

    When should you use ARIA, and what is the first rule of ARIA?

    The first rule: if a native HTML element or attribute gives the semantics and behaviour you need, use it instead of ARIA. Use ARIA to fill gaps — naming icon-only buttons (aria-label), communicating state (aria-expanded, aria-current, aria-invalid), relationships (aria-describedby, aria-controls) and live updates (role="status"). ARIA changes only what is announced, not behaviour — you still must add keyboard handling. Incorrect ARIA is worse than none.

    How do you make a form accessible?

    Every control has a visible <label for> (placeholders are not labels); related radios/checkboxes are grouped in <fieldset> with <legend>; use correct input types and autocomplete values; link hints and errors with aria-describedby and mark invalid fields with aria-invalid="true"; show errors in text, not colour alone; move focus to an error summary on submit; ensure everything works with the keyboard and that contrast meets 4.5:1.

    Explain srcset, sizes and the picture element.

    srcset lists image candidates with their widths (400w) or densities (2x). sizes tells the browser how wide the image will be rendered at different viewport widths, so it can choose the smallest suitable file before layout. <picture> with <source> is for art direction (different crops per breakpoint via media) or format fallback (AVIF → WebP → JPEG). The inner <img> still needs alt, width and height.

    What is the difference between defer and async on a script tag?

    Both download the script in parallel without blocking the parser. async executes as soon as the download finishes — possibly before parsing completes — and multiple async scripts run in whatever order they arrive; good for independent scripts like analytics. defer executes after the document is parsed, just before DOMContentLoaded, in document order; good for app code that needs the DOM. Module scripts are deferred by default.

    🎨 CSS & layout

    How is CSS specificity calculated? How do you avoid specificity problems?

    Specificity is compared as (IDs, classes/attributes/pseudo-classes, types/pseudo-elements), left to right. Inline styles beat selectors and !important beats normal declarations; :where() contributes zero and :is()/:not()/:has() take their most specific argument. To avoid wars: style with single classes (BEM or utility classes), avoid IDs and deep nesting in CSS, use @layer to order resets, components and utilities, and reserve !important for utilities.

    Explain the box model and box-sizing.

    Each element has content, padding, border and margin. With the default content-box, width sets only the content, so padding and border add to the rendered size. With border-box, width includes padding and border, which makes sizing predictable — which is why most resets apply box-sizing: border-box to everything. Margins sit outside the box and vertical margins can collapse in normal block flow.

    When would you choose Flexbox and when Grid?

    Flexbox is one-dimensional and content-driven: items size themselves and you distribute space along a row or column — navbars, toolbars, aligning an icon and text, a row of buttons. Grid is two-dimensional and layout-driven: you define rows and columns and place items — page layouts, card galleries where columns must align, dashboards, overlapping items. They combine well: Grid for the macro layout, Flexbox inside components.

    What is a stacking context and why might z-index not work?

    A stacking context is an isolated layer group; z-index only orders elements within the same context. Contexts are created by the root, positioned elements with a non-auto z-index, flex/grid items with a z-index, opacity < 1, transform, filter, isolation: isolate and others. If a modal is inside a parent that forms a context with a lower position, no z-index on the modal can lift it above that parent's siblings. Also, z-index has no effect on non-positioned elements outside flex/grid. Fixes: restructure the DOM, use <dialog>/popover (top layer), or remove the property creating the context.

    What are container queries and how are they different from media queries?

    Media queries respond to the viewport and user/device features. Container queries respond to the size of an ancestor declared with container-type: inline-size, using @container (min-width: 30rem) and container units like cqi. They make components truly reusable: the same card can be compact in a sidebar and horizontal in a wide column without knowing the page layout. Media queries remain right for page-level layout and preferences like dark mode and reduced motion.

    ⚙️ JavaScript

    Explain closures with a practical example.

    A closure is a function bundled with references to the variables of the scope where it was created, so it can use them after that scope has finished. Example: function debounce(fn, ms) { let t; return (...args) => { clearTimeout(t); t = setTimeout(() => fn(...args), ms); }; } — the returned function remembers t between calls. Closures give privacy (module pattern, counters), power callbacks and hooks, and can cause leaks if long-lived closures hold large objects.

    What is the difference between var, let and const? What is the TDZ?

    var is function-scoped, can be redeclared and is hoisted initialised to undefined. let and const are block-scoped and cannot be redeclared; const cannot be reassigned, though objects it references can be mutated. let/const are hoisted but uninitialised: accessing them before the declaration throws a ReferenceError — that window is the Temporal Dead Zone. Use const by default, let when reassignment is needed.

    How does this work in JavaScript? How do arrow functions differ?

    this is decided by how a regular function is called: obj.method() → obj; plain call → undefined in strict mode; new → the new object; call/apply/bind → the given value; DOM listener → the element. Arrow functions have no own this; they capture it lexically from the surrounding scope, which is ideal for callbacks inside methods, but wrong for object methods that need the object. Arrows also have no arguments and cannot be used with new.

    What is event delegation and why use it?

    Instead of a listener on each child, attach one listener to a common ancestor and use the event's bubbling: in the handler, find the relevant child with event.target.closest(selector). Benefits: fewer listeners and less memory, and it automatically handles children added later (e.g. infinite scroll lists). Caveats: some events don't bubble (focus — use focusin), and you must guard against clicks outside the intended targets.

    Explain == vs === and give some surprising results.

    === compares without type conversion; == applies the abstract equality algorithm, converting operands. Surprises: "" == 0 is true, [] == false is true, "0" == false is true, but null == 0 is false while null == undefined is true. NaN is not equal to itself under either. Use === everywhere; x == null is an accepted idiom for “null or undefined”.

    ⏳ Async JavaScript

    Explain the event loop, microtasks and macrotasks.

    JavaScript runs on a single thread with a call stack. Async APIs hand work to the browser and queue callbacks. When the stack is empty, the event loop runs all queued microtasks (Promise reactions, code after await, queueMicrotask), may render a frame, then takes one macrotask (timer, event, message) and repeats. So Promise.resolve().then(a) always runs before setTimeout(b, 0). Long synchronous work blocks everything, including rendering and input.

    What is the difference between Promise.all, allSettled, race and any?

    Promise.all resolves with all values in order, but rejects as soon as one rejects. allSettled waits for every promise and reports each as fulfilled or rejected — good when partial success is fine. race settles with the first promise to settle, either way — used for timeouts. any resolves with the first fulfilment and only rejects (with AggregateError) if all reject — good for redundant sources.

    How do you handle errors with fetch and async/await?

    Wrap awaits in try/catch (or attach .catch). Remember that fetch only rejects on network failure, CORS or abort — HTTP errors like 404 or 500 resolve, so check res.ok / res.status and throw. Parse JSON inside the try because it can also fail. Use AbortController or AbortSignal.timeout() for cancellation and timeouts, show the user a meaningful state (error message, retry button), and log unexpected errors.

    How would you prevent race conditions in a search-as-you-type box?

    Debounce the input (e.g. 300 ms) to reduce requests. For each new request, abort the previous one with an AbortController so a slow, older response cannot overwrite a newer one; alternatively tag requests with an incrementing id and ignore responses that are not the latest. Also handle the AbortError quietly, cache recent results, and show a loading state.

    Are async functions run in parallel? How do you run independent requests concurrently?

    No. An async function runs synchronously until its first await, then yields; awaiting in sequence makes requests wait for each other. To run independent requests concurrently, start them all first and then await together: const [a, b] = await Promise.all([getA(), getB()]). For many requests, limit concurrency (e.g. batches) to avoid overwhelming the server. True parallel CPU work needs Web Workers.

    🔷 TypeScript

    What is the difference between interface and type?

    Both can describe object shapes and be extended/implemented. Only type can name unions, primitives, tuples, mapped and conditional types. Interfaces support declaration merging (useful for augmenting library or global types, e.g. Window) and give clearer errors when extending. Common convention: interfaces for object contracts like props and API models, types for unions and computed types — and consistency matters more than the choice.

    Explain any, unknown and never.

    any turns off type checking and leaks into everything it touches. unknown is the safe top type: anything can be assigned to it, but you must narrow it (typeof, instanceof, type guards, schema validation) before using it — ideal for JSON and caught errors. never is the bottom type: no value has it — it is the return type of functions that always throw, the result of narrowing away all options, and is used for exhaustive checks in switch statements.

    What are generics and when do you use constraints?

    Generics are type parameters that preserve the relationship between inputs and outputs, e.g. function first<T>(xs: T[]): T | undefined. Constraints (T extends { id: number }, K extends keyof T) limit what can be passed so the body can safely use certain properties. Use them for reusable utilities, typed API helpers (getJson<T>), components and data structures; avoid them when a type parameter appears only once.

    What are discriminated unions and why are they good for UI state?

    A union of object types that share a literal property such as status: "loading" | "success" | "error". Checking the discriminant narrows to one member, so data is only accessible in the success branch and error only in the error branch. This removes impossible combinations of separate booleans, and with a never default case the compiler flags any new state you forget to handle.

    What does satisfies do and how is it different from a type annotation or as?

    value satisfies T checks the value against T (catching typos and missing keys) but keeps the value's own precise inferred type. An annotation const x: T = value widens x to T, losing literal and per-property details. as T is an assertion that largely skips checking and can hide mistakes. Use satisfies for config objects, route maps and theme tokens.

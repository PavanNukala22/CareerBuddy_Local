    State Fundamentals

    What state is, where it should live, why we update it immutably and how data flows through a UI — the ideas every library builds on.

    🧭 What is state?

    State is any data that can change while your app is running and that affects what the user sees. A counter value, the text in a search box, the logged-in user, the items in a cart and whether a modal is open are all state.

    A UI is a function of state: given the same state, a component should render the same output. When state changes, the framework (React, Vue) re-renders the parts of the screen that depend on it. Your job is to decide what the state is, where it lives and how it changes.

    jsximport { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);   // state + setter
  return (
    <button onClick={() => setCount(count + 1)}>
      Clicked {count} times
    </button>
  );
}

    Here count is state. Calling setCount tells React the state changed, so React calls Counter again and the button shows the new number.

    📦
    Data
    State holds values: numbers, strings, objects, arrays.
    ⏱️
    Changes over time
    Constants and props you never change are not state.
    🖼️
    Drives the UI
    Change the state and the screen updates to match.
    📝
    Props are inputs passed from a parent. State is data a component (or a store) owns and changes. A child cannot change its props directly — it asks the owner to change the state.

    🗂️ Kinds of state

    Not all state is the same. Sorting state into kinds is the first step to choosing the right tool. Most bugs and over-engineering come from treating every kind of state the same way.

    KindExamplesTypical homeNotes
    Local UI stateIs a dropdown open? Current tab. Hover state.useState / ref() in the componentUsed by one component (and maybe its children). Keep it local.
    Shared / global client stateLogged-in user, theme, cart, feature flagsContext, Redux Toolkit, Zustand, PiniaNeeded by many unrelated components. Owned by the browser.
    Server / cache stateProduct list, order history, user profile from an APITanStack Query, RTK Query, SWRA copy of data owned by the server. Can go stale; needs caching and refetching.
    URL stateSearch query, filters, page number, selected idRouter / URLSearchParamsShareable, bookmarkable, survives refresh, works with Back.

    • The product list from /api/products → server state.
    • The selected category ?category=shoes → URL state.
    • The cart (before checkout) → global client state.
    • Whether the filter drawer is open → local UI state.
    • The address form at checkout → form state.
    💡
    Ask two questions: Who owns this data — the browser or the server? and How many components need it? The answers usually tell you where it belongs.

    🧮 Derived state and the single source of truth

    Derived state is a value you can calculate from other state. A cart total is derived from the cart items. A filtered list is derived from the full list plus the filter text. You should calculate derived values, not store them.

    jsx// BAD: total is stored separately and can drift out of sync
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);   // must remember to update every time

// GOOD: total is derived during render - always correct
const [items, setItems] = useState([]);
const total = items.reduce((sum, i) => sum + i.price * i.qty, 0);

    If the calculation is expensive, memoise it (useMemo in React, computed in Vue, createSelector in Redux, a getter in Pinia) instead of storing a second copy.

    Single source of truth

    Each piece of data should have one owner. If the same user object lives in a component, in a store and in a cache, the copies will eventually disagree. Pick one place, and let everything else read from it or derive from it.

    Two sources (bug-prone)

    • Store keeps selectedProduct as a full object copy.
    • List is refetched with a new price.
    • Detail panel still shows the old price.

    One source (safe)

    • Store keeps only selectedProductId.
    • Detail panel finds the product by id in the list.
    • Price is always the latest.
    ⚠️
    Store ids, not copies of objects, when you need to remember a selection. Copies go stale.

    🧊 Immutability and why it matters

    An immutable update creates a new object or array instead of changing the existing one. React, Redux and Zustand detect changes by reference equality (Object.is(oldValue, newValue)). If you mutate an object in place, the reference is the same, so the library thinks nothing changed and may skip the re-render.

    jsxconst [user, setUser] = useState({ name: "Asha", age: 29 });

// WRONG: mutates the same object - React sees the same reference
user.age = 30;
setUser(user);            // may not re-render

// RIGHT: create a new object with the spread operator
setUser({ ...user, age: 30 });

    Common immutable patterns in JavaScript

    ⚡
    Cheap change detection
    Comparing two references is O(1). No deep comparison needed.
    ⏪
    History and time travel
    Old states are untouched, so DevTools can replay them.
    🐞
    Fewer hidden bugs
    No other code can change your data behind your back.
    📝
    Redux Toolkit uses Immer, and Zustand can too, so you may write mutating code inside reducers. Immer records the changes and produces a new immutable object for you. Vue/Pinia is different: its reactivity is built on proxies, so you do mutate state directly there.

    🔁 Unidirectional data flow

    Modern UI state follows a one-way loop. The UI never changes data directly. It raises an event; the event becomes an action or a setter call; the state updates; the UI re-renders from the new state.

    Unidirectional data flow: data goes down to the view, events go up as actions
    jsxfunction TodoApp() {
  const [todos, setTodos] = useState([]);           // 3. state lives here

  function addTodo(title) {                         // 2. the "action"
    setTodos(prev => [...prev, { id: crypto.randomUUID(), title }]);
  }

  return (
    <>
      <AddTodoForm onAdd={addTodo} />               {/* 1. event goes up */}
      <TodoList todos={todos} />                    {/* 4. data flows down */}
    </>
  );
}

    Because changes only happen in one place and one direction, you can always answer “why did this change?” by looking at which action ran. Redux, Zustand and Pinia are all formal versions of this same loop.

    💡
    Use the functional updater setTodos(prev => ...) when the new state depends on the old one. It always receives the latest value, even if several updates are batched.

    🪜 Prop drilling and lifting state up

    Lifting state up means moving state to the closest common parent of the components that need it. The parent passes the value down as props and passes a callback down so children can request changes.

    jsxfunction Parent() {
  const [query, setQuery] = useState("");   // lifted to the common parent
  return (
    <>
      <SearchBox value={query} onChange={setQuery} />
      <Results query={query} />
    </>
  );
}

    Prop drilling happens when a value must pass through many layers of components that do not use it, only to reach a deep child.

    jsx<App user={user}>
  <Layout user={user}>           {/* does not use user */}
    <Sidebar user={user}>        {/* does not use user */}
      <Avatar user={user} />     {/* finally uses it */}
    </Sidebar>
  </Layout>
</App>
    FixWhen it fits
    Component composition (pass <Avatar user={user} /> as children)Only 2–3 levels; often the simplest fix.
    Context (React) / provide/inject (Vue)Rarely changing values many components read: theme, user, locale.
    A store (Redux Toolkit, Zustand, Pinia)Frequently changing shared state, complex update logic, DevTools needed.
    📝
    Prop drilling through two levels is fine — it is explicit and easy to follow. It becomes a problem when many layers just forward props and every change touches many files.

    🙅 When you do NOT need a global store

    A global store is a tool, not a requirement. Many apps need far less global state than people expect, especially once server data is handled by a data-fetching library.

    • State used by one component or one small subtree → keep it local.
    • Data from an API → use TanStack Query or RTK Query, not a hand-written store slice.
    • Filters, search and pagination that should be shareable → put them in the URL.
    • Form fields → local state or a form library.
    • A few rarely changing app-wide values (theme, current user) → Context is enough.
    EXAMPLE · A small marketing site with a contact form

    It has no shared state at all. Adding Redux would add files, boilerplate and a learning curve with zero benefit. useState inside the form is the right answer.

    ✅
    Rule of thumb: start local, lift when needed, reach for a store only when sharing gets painful. It is easy to move state up later; it is harder to untangle an everything-global store.

    React Context API

    Share values across the component tree without prop drilling — and learn exactly when Context is the right tool and when it is not.

    🧩 createContext, Provider and useContext

    The Context API is built into React. It lets a parent make a value available to every component below it, at any depth, without passing props through each level. It has three parts:

    PartWhat it does
    createContext(defaultValue)Creates a context object. The default is used only when there is no matching Provider above the consumer.
    <MyContext.Provider value={...}>Supplies a value to all descendants. The nearest Provider above a consumer wins.
    useContext(MyContext)Reads the current value inside a component and subscribes it to changes.
    jsximport { createContext, useContext, useState } from "react";

const ThemeContext = createContext("light");          // 1. create

export default function App() {
  const [theme, setTheme] = useState("light");
  return (
    <ThemeContext.Provider value={theme}>             {/* 2. provide */}
      <Toolbar />
      <button onClick={() => setTheme(t => (t === "light" ? "dark" : "light"))}>
        Toggle theme
      </button>
    </ThemeContext.Provider>
  );
}

function Toolbar() {
  return <ThemedButton />;                            // no props passed
}

function ThemedButton() {
  const theme = useContext(ThemeContext);             // 3. consume
  return <button className={`btn-${theme}`}>I am {theme}</button>;
}
    📝
    Context is a transport mechanism, not a state manager. It does not store or update anything by itself. The state still lives in useState or useReducer; Context just delivers it down the tree.

    🛡️ Typed context with TypeScript and a custom hook

    In real projects you usually create the context with null as the default, then write a custom hook that throws a clear error if a component is used outside the Provider. This gives you full type safety and no undefined checks in every consumer.

    tsximport { createContext, useContext, useMemo, useState, type ReactNode } from "react";

type User = { id: string; name: string };

type AuthContextValue = {
  user: User | null;
  login: (user: User) => void;
  logout: () => void;
};

const AuthContext = createContext<AuthContextValue | null>(null);

export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const value = useMemo<AuthContextValue>(
    () => ({
      user,
      login: (u) => setUser(u),
      logout: () => setUser(null),
    }),
    [user]
  );

  return <AuthContext.Provider value={value}>{children}</AuthContext.Provider>;
}

export function useAuth(): AuthContextValue {
  const ctx = useContext(AuthContext);
  if (ctx === null) {
    throw new Error("useAuth must be used inside <AuthProvider>");
  }
  return ctx;                       // type is narrowed: never null here
}

    tsxfunction Header() {
  const { user, logout } = useAuth();   // fully typed, no null checks
  return user ? <button onClick={logout}>Log out {user.name}</button> : null;
}
    💡
    Export the Provider component and the hook, not the raw context object. Consumers then cannot forget the null check or bypass your API.

    🛒 The useReducer + Context pattern (cart example)

    For state with several related update rules, combine useReducer with Context. The reducer is a pure function (state, action) => newState. Components call dispatch(action) to describe what happened; the reducer decides how the state changes. This is a mini-Redux built from React alone.

    tsx// cart-context.tsx
import { createContext, useContext, useReducer, type Dispatch, type ReactNode } from "react";

type CartItem = { id: string; name: string; price: number; qty: number };
type CartState = { items: CartItem[] };

type CartAction =
  | { type: "added"; item: Omit<CartItem, "qty"> }
  | { type: "removed"; id: string }
  | { type: "qtyChanged"; id: string; qty: number }
  | { type: "cleared" };

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case "added": {
      const existing = state.items.find(i => i.id === action.item.id);
      if (existing) {
        return {
          items: state.items.map(i =>
            i.id === action.item.id ? { ...i, qty: i.qty + 1 } : i
          ),
        };
      }
      return { items: [...state.items, { ...action.item, qty: 1 }] };
    }
    case "removed":
      return { items: state.items.filter(i => i.id !== action.id) };
    case "qtyChanged":
      return {
        items: state.items.map(i =>
          i.id === action.id ? { ...i, qty: Math.max(1, action.qty) } : i
        ),
      };
    case "cleared":
      return { items: [] };
    default:
      return state;
  }
}

const CartStateContext = createContext<CartState | null>(null);
const CartDispatchContext = createContext<Dispatch<CartAction> | null>(null);

export function CartProvider({ children }: { children: ReactNode }) {
  const [state, dispatch] = useReducer(cartReducer, { items: [] });
  return (
    <CartStateContext.Provider value={state}>
      <CartDispatchContext.Provider value={dispatch}>
        {children}
      </CartDispatchContext.Provider>
    </CartStateContext.Provider>
  );
}

export function useCart() {
  const ctx = useContext(CartStateContext);
  if (!ctx) throw new Error("useCart must be used inside <CartProvider>");
  return ctx;
}

export function useCartDispatch() {
  const ctx = useContext(CartDispatchContext);
  if (!ctx) throw new Error("useCartDispatch must be used inside <CartProvider>");
  return ctx;
}

    tsxfunction AddToCartButton({ product }: { product: { id: string; name: string; price: number } }) {
  const dispatch = useCartDispatch();          // does NOT re-render when the cart changes
  return <button onClick={() => dispatch({ type: "added", item: product })}>Add</button>;
}

function CartSummary() {
  const { items } = useCart();                 // re-renders when the cart changes
  const total = items.reduce((s, i) => s + i.price * i.qty, 0);   // derived, not stored
  return <p>{items.length} lines · ₹{total}</p>;
}
    💡
    Name actions in the past tense (added, removed) — they describe events that happened, not commands. The React docs and Redux style guide both recommend this.

    🔄 Re-render behaviour and how to control it

    This is the most important thing to understand about Context: when a Provider's value changes, every component that reads that context re-renders — even if it only uses one field that did not change. React compares the old and new value with Object.is.

    jsxfunction App() {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState("light");

  // PROBLEM: a new object is created on EVERY render of App,
  // so all consumers re-render whenever App re-renders for any reason.
  return (
    <AppContext.Provider value={{ user, setUser, theme, setTheme }}>
      <Page />
    </AppContext.Provider>
  );
}

    Fix 1 · Memoise the value

    jsxconst value = useMemo(() => ({ user, setUser, theme, setTheme }), [user, theme]);
return <AppContext.Provider value={value}><Page /></AppContext.Provider>;

    Fix 2 · Split contexts

    Put values that change independently into separate contexts — e.g. state vs dispatch (as in the cart example), or auth vs theme. A component that only needs dispatch never re-renders on state changes, because dispatch from useReducer has a stable identity.

    TechniqueStops which re-renders?
    useMemo on the valueRe-renders caused by the Provider's parent re-rendering with unchanged data.
    Split state / dispatch contextsRe-renders of components that only send actions.
    Split by domain (auth, theme, cart)Re-renders of theme consumers when the cart changes, and so on.
    React.memo on childrenRe-renders of children that do not read the context, when the Provider's parent re-renders.
    ⚠️
    Context has no built-in selectors. You cannot subscribe to just state.user.name. If you need fine-grained subscriptions to frequently changing data, use Zustand, Redux Toolkit or another store.

    ⚖️ Good and bad use cases

    Good fits for Context

    • Theme (light/dark) — changes rarely.
    • Auth — current user and login/logout functions.
    • Locale / i18n — language and formatters.
    • Dependency injection — an API client, a feature-flag service.
    • Compound components (<Tabs> sharing the active tab with <Tab>).

    Poor fits for Context

    • High-frequency updates — mouse position, typing in a big form, animation frames, live prices.
    • Large objects where each consumer uses a small slice.
    • Server data that needs caching, refetching and deduplication.
    • Complex state that benefits from DevTools, middleware and time travel.
    EXAMPLE · Live stock ticker

    A context holding 500 prices that update every second would re-render every consumer every second. A Zustand or Redux store with per-symbol selectors lets each row re-render only when its price changes.

    💡
    Context + useReducer is perfectly fine for small and medium apps with low-frequency shared state. Do not add a library until you feel a specific pain.

    🆕 React 19 notes: Context as a provider and use()

    React 19 added two conveniences. They change the syntax, not how Context behaves.

    FeatureWhat changed
    Context as providerYou can render <ThemeContext value="dark"> directly instead of <ThemeContext.Provider value="dark">. The React team has said .Provider will be deprecated in a future version; it still works in React 19.

    Redux Toolkit

    The official, modern way to write Redux — slices, typed hooks, async thunks, memoised selectors, normalised data and RTK Query.

    🏛️ Redux core ideas

    Redux keeps all global client state in one store. The only way to change it is to dispatch an action; a pure reducer calculates the next state; components read data with selectors. Middleware sits between dispatch and the reducer to handle side effects like logging or API calls.

    The Redux data flow — strict, one-way and predictable
    StoreThe single object holding the whole state tree. Created once per app.
    ActionA plain object describing what happened: { type: 'cart/itemAdded', payload: { id: 'p1' } }.
    ReducerA pure function (state, action) => newState. No API calls, no randomness, no mutation of the input.
    Dispatchstore.dispatch(action) — the only way to trigger a state change.
    SelectorA function that reads (and may derive) data from state: state => state.cart.items.
    MiddlewareCode that wraps dispatch, e.g. thunks for async logic, loggers, analytics.
    📝
    The three principles: one source of truth (the store), state is read-only (change it only via actions) and changes are made with pure functions (reducers).

    🧰 Why Redux Toolkit?

    Classic hand-written Redux needed action type constants, action creators, switch-based reducers, manual immutable spreads and manual store setup. Redux Toolkit (RTK) is the official, recommended way to write Redux today; the Redux team says new Redux code should use it.

    Pain in classic ReduxHow RTK fixes it
    Action type constants and action creators by handcreateSlice generates them from reducer names.
    Verbose nested spreads for immutable updatesImmer lets you write state.items.push(x) safely inside reducers.
    Manual store setup with middleware and DevToolsconfigureStore adds thunk, DevTools and dev-only checks by default.
    Async boilerplate (three action types per request)createAsyncThunk generates pending/fulfilled/rejected.
    Hand-written data fetching and cachingRTK Query generates hooks and caches results.
    ⚠️
    The old createStore from the redux package is marked deprecated (it still works) to nudge people to configureStore. RTK 2.x also removed the object syntax for extraReducers — you must use the builder callback.

    🍰 configureStore, createSlice and the Provider

    A slice is the reducer logic and actions for one feature. createSlice takes a name, initial state and reducer functions, and returns the reducer plus an action creator for each reducer.

    typescript// features/cart/cartSlice.ts
import { createSlice, type PayloadAction } from "@reduxjs/toolkit";

type CartItem = { id: string; name: string; price: number; qty: number };
type CartState = { items: CartItem[] };

const initialState: CartState = { items: [] };

const cartSlice = createSlice({
  name: "cart",
  initialState,
  reducers: {
    itemAdded(state, action: PayloadAction<Omit<CartItem, "qty">>) {
      const existing = state.items.find(i => i.id === action.payload.id);
      if (existing) existing.qty += 1;           // "mutation" is safe: Immer
      else state.items.push({ ...action.payload, qty: 1 });
    },
    itemRemoved(state, action: PayloadAction<string>) {
      state.items = state.items.filter(i => i.id !== action.payload);
    },
    cartCleared() {
      return initialState;                       // returning a new value also works
    },
  },
});

export const { itemAdded, itemRemoved, cartCleared } = cartSlice.actions;
export default cartSlice.reducer;
// itemAdded({...}) creates { type: "cart/itemAdded", payload: {...} }

    typescript// app/store.ts
import { configureStore } from "@reduxjs/toolkit";
import cartReducer from "../features/cart/cartSlice";
import authReducer from "../features/auth/authSlice";

export const store = configureStore({
  reducer: { cart: cartReducer, auth: authReducer },   // combined automatically
});

export type RootState = ReturnType<typeof store.getState>;
export type AppDispatch = typeof store.dispatch;

    tsx// main.tsx

    ⚠️
    Inside an Immer reducer, either mutate the draft or return a new value — never both in the same reducer. Also never mutate state outside reducers; the dev-mode immutability check will warn you.

    🪝 useSelector, useDispatch and typed hooks

    useSelector reads data and re-renders the component only when the selected value changes (compared with === by default). useDispatch returns the store's dispatch.

    typescript// app/hooks.ts  (React-Redux v9.1+)
import { useDispatch, useSelector } from "react-redux";
import type { AppDispatch, RootState } from "./store";

export const useAppDispatch = useDispatch.withTypes<AppDispatch>();
export const useAppSelector = useSelector.withTypes<RootState>();

    tsximport { useAppDispatch, useAppSelector } from "../../app/hooks";
import { itemAdded } from "./cartSlice";

export function CartBadge() {
  const count = useAppSelector(state => state.cart.items.length);   // a number: cheap ===
  return <span className="badge">{count}</span>;
}

export function AddButton({ product }: { product: { id: string; name: string; price: number } }) {

    🌐 Async logic with createAsyncThunk

    Reducers must be pure, so API calls go in thunks — functions that receive dispatch and getState. createAsyncThunk wraps an async function and automatically dispatches three actions: pending, fulfilled and rejected. Handle them in extraReducers, because they were not defined in this slice's reducers.

    typescript// features/products/productsSlice.ts
import { createAsyncThunk, createSlice } from "@reduxjs/toolkit";

type Product = { id: string; name: string; price: number; category: string };
type ProductsState = {
  items: Product[];
  status: "idle" | "loading" | "succeeded" | "failed";
  error: string | null;
};

export const fetchProducts = createAsyncThunk(
  "products/fetchAll",                       // action type prefix
  async (category: string, { rejectWithValue }) => {
    const res = await fetch(`/api/products?category=${encodeURIComponent(category)}`);
    if (!res.ok) return rejectWithValue(`HTTP ${res.status}`);
    return (await res.json()) as Product[];  // becomes action.payload
  }
);

const initialState: ProductsState = { items: [], status: "idle", error: null };

const productsSlice = createSlice({
  name: "products",
  initialState,
  reducers: {},
  extraReducers: (builder) => {
    builder
      .addCase(fetchProducts.pending, (state) => {
        state.status = "loading";
        state.error = null;
      })
      .addCase(fetchProducts.fulfilled, (state, action) => {
        state.status = "succeeded";
        state.items = action.payload;
      })
      .addCase(fetchProducts.rejected, (state, action) => {
        state.status = "failed";
        state.error = (action.payload as string) ?? action.error.message ?? "Unknown error";
      });
  },
});

export default productsSlice.reducer;

    🎯 Memoised selectors with createSelector

    A selector that filters, maps or sorts returns a new array each time, which forces re-renders and repeats work. createSelector (from Reselect, re-exported by RTK) memoises: it only recomputes when its input selectors return different references.

    Zustand

    A tiny, hook-based store with no Provider and no boilerplate — selectors, actions, slices, middleware and TypeScript in Zustand 5.

    🐻 Creating a store with set and get

    Zustand (German for “state”) is a small state library for React. You call create with a function that receives set and get and returns your initial state and actions. The result is a hook. There is no Provider to wrap your app in.

    jsximport { create } from "zustand";

export const useCounterStore = create((set, get) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),  // based on previous state
  reset: () => set({ count: 0 }),                                  // plain object
  logCount: () => console.log("count is", get().count),             // read current state
}));
    FunctionWhat it does
    set(partial)Merges partial into the state (a shallow merge at the top level only).
    set(state => partial)Same, but computes the change from the current state. Use it when the new value depends on the old one.
    set(newState, true)Replaces the whole state instead of merging (careful: you can lose your actions).
    get()Returns the current state. Useful inside actions that need to read without updating.
    ⚠️
    set only merges one level deep. For nested objects you must spread yourself: set(s => ({ user: { ...s.user, name } })) — or use the immer middleware.

    🎯 Selectors in components

    A component subscribes by calling the hook with a selector. It re-renders only when the selected value changes (compared with Object.is).

    jsxfunction CountLabel() {
  const count = useCounterStore((s) => s.count);          // re-renders when count changes
  return <span>{count}</span>;
}

function IncrementButton() {
  const increment = useCounterStore((s) => s.increment);  // actions are stable: never re-renders
  return <button onClick={increment}>+1</button>;
}
    ⚠️
    Avoid const state = useCounterStore() with no selector. It subscribes to the whole store, so the component re-renders on every change to any field.

    Selecting several values with useShallow

    A selector that returns a new object or array fails the Object.is check every time. In Zustand 5 this can even cause an infinite render loop (“Maximum update depth exceeded”). Wrap it in useShallow, which compares the result's top-level keys instead.

    jsximport { useShallow } from "zustand/react/shallow";

// BAD in v5: a new object every render
// const { count, increment } = useCounterStore((s) => ({ count: s.count, increment: s.increment }));

// GOOD: shallow-compared
const { count, increment } = useCounterStore(
  useShallow((s) => ({ count: s.count, increment: s.increment }))
);

// Also fine: an array tuple
const [count2, reset] = useCounterStore(useShallow((s) => [s.count, s.reset]));
    💡
    Several atomic selectors (useStore(s => s.a), useStore(s => s.b)) are often the simplest choice and are always safe.

    🛒 Actions and async actions

    Keep the logic that changes state inside the store as actions. Components then just call addItem(product) and do not need to know how the state is shaped. Async actions are just async functions — no thunks or middleware needed.

    typescriptimport { create } from "zustand";

type Product = { id: string; name: string; price: number };
type CartItem = Product & { qty: number };

type CartState = {
  items: CartItem[];
  status: "idle" | "saving" | "error";
  addItem: (p: Product) => void;
  removeItem: (id: string) => void;
  checkout: () => Promise<void>;
};

export const useCartStore = create<CartState>()((set, get) => ({
  items: [],
  status: "idle",

  addItem: (p) =>
    set((s) => {
      const found = s.items.find((i) => i.id === p.id);
      return {
        items: found
          ? s.items.map((i) => (i.id === p.id ? { ...i, qty: i.qty + 1 } : i))
          : [...s.items, { ...p, qty: 1 }],
      };
    }),

  removeItem: (id) => set((s) => ({ items: s.items.filter((i) => i.id !== id) })),

  checkout: async () => {
    set({ status: "saving" });
    try {
      const res = await fetch("/api/orders", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(get().items),        // read the latest items
      });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      set({ items: [], status: "idle" });
    } catch {
      set({ status: "error" });
    }
  },
}));
    📝
    Derived values such as the cart total are best computed in a selector: useCartStore(s => s.items.reduce((t, i) => t + i.price * i.qty, 0)). It returns a number, so the Object.is comparison works.

    🔤 TypeScript typing with the curried create form

    With TypeScript, write create<State>()(...) — note the extra pair of parentheses. The curried form lets TypeScript infer the middleware types while you give the state type explicitly. Without it, typing middleware such as persist or devtools breaks.

    typescriptimport { create } from "zustand";

interface BearState {
  bears: number;
  increase: (by: number) => void;
}

// correct

  bears: 0,
  increase: (by) => set((s) => ({ bears: s.bears + by })),

// create<BearState>((set) => ({ ... }))

    🧱 The slices pattern

    For a larger store, split it into slices — functions that each create part of the state and actions — and combine them into one store. Each slice can read the whole store through get.

    typescriptimport { create, type StateCreator } from "zustand";

type AuthSlice = { user: string | null; login: (name: string) => void; logout: () => void };
type CartSlice = { items: string[]; addItem: (id: string) => void; clearCart: () => void };
type Store = AuthSlice & CartSlice;

const createAuthSlice: StateCreator<Store, [], [], AuthSlice> = (set, get) => ({
  user: null,
  login: (name) => set({ user: name }),
  logout: () => {
    set({ user: null });
    get().clearCart();                    // a slice can call another slice's action
  },
});

const createCartSlice: StateCreator<Store, [], [], CartSlice> = (set) => ({
  items: [],
  addItem: (id) => set((s) => ({ items: [...s.items, id] })),
  clearCart: () => set({ items: [] }),
});

export const useStore = create<Store>()((...a) => ({
  ...createAuthSlice(...a),
  ...createCartSlice(...a),
}));
    📝
    An alternative many teams prefer is simply several small stores (useAuthStore, useCartStore). Zustand stores are cheap. Use slices when the parts are tightly coupled or you want one persisted object.

    🧾 defineStore — options syntax

    defineStore(id, options) creates a store definition and returns a useXxxStore function. The id must be unique; DevTools use it. The options syntax mirrors the Vue Options API:

    typescript// stores/cart.ts
import { defineStore } from "pinia";

export const useCartStore = defineStore("cart", {
  state: () => ({
    items: [] as CartItem[],
    coupon: null as string | null,
  }),
  getters: {
    count: (state) => state.items.reduce((n, i) => n + i.qty, 0),
    total: (state) => state.items.reduce((s, i) => s + i.price * i.qty, 0),
    // a getter using another getter: use `this` and give a return type
    totalWithTax(): number {
      return Math.round(this.total * 1.18);
    },
  },
  actions: {
    add(product: Omit<CartItem, "qty">) {
      const found = this.items.find(i => i.id === product.id);
      if (found) found.qty++;                 // direct mutation is fine in Vue
      else this.items.push({ ...product, qty: 1 });
    },
    remove(id: string) {
      this.items = this.items.filter(i => i.id !== id);
    },
  },
});

    ⚙️ defineStore — setup syntax

    The setup syntax passes a function, like a component's setup(). ref() becomes state, computed() becomes getters and functions become actions. You must return everything you want to expose.

    typescript// stores/auth.ts
import { defineStore } from "pinia";
import { computed, ref } from "vue";

type User = { id: string; name: string; role: "admin" | "user" };

export const useAuthStore = defineStore("auth", () => {
  const user = ref<User | null>(null);                    // state
  const token = ref<string | null>(null);

  const isLoggedIn = computed(() => user.value !== null); // getter
  const isAdmin = computed(() => user.value?.role === "admin");

  async function login(email: string, password: string) { // action
    const res = await fetch("/api/login", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ email, password }),
    });
    if (!res.ok) throw new Error("Login failed");
    const data = await res.json();
    user.value = data.user;
    token.value = data.token;
  }

  function logout() {
    user.value = null;
    token.value = null;
  }

  return { user, token, isLoggedIn, isAdmin, login, logout };   // expose all state!
});

    🔗 Async actions and composing stores

    Actions can be async and can call other stores. Call the other useXxxStore() inside the action or getter, not at the top of the file.

    typescript// stores/orders.ts
import { defineStore } from "pinia";

import { useCartStore } from "./cart";

export const useOrdersStore = defineStore("orders", {
  state: () => ({ placing: false, error: null as string | null, lastOrderId: null as string | null }),
  actions: {
    async placeOrder() {
      const auth = useAuthStore();     // compose: use another store
      const cart = useCartStore();
      if (!auth.isLoggedIn) throw new Error("Please log in");

      this.placing = true;
      this.error = null;
      try {
        const res = await fetch("/api/orders", {
          method: "POST",
          headers: { Authorization: `Bearer ${auth.token}`, "Content-Type": "application/json" },
          body: JSON.stringify({ items: cart.items }),
        });
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        this.lastOrderId = (await res.json()).id;
        cart.$reset();
      } catch (e) {
        this.error = (e as Error).message;
      } finally {
        this.placing = false;
      }
    },
  },
});

    Server State & Architecture

    Separate server data from client state, put the right state in the URL and forms, choose a solution with confidence, and keep it fast and testable.

    🌐 Server state vs client state

    Client state is owned by the browser: the cart before checkout, the theme, whether a panel is open. Server state is owned by a backend and the browser only holds a cached copy. That copy can go stale at any moment because other users and processes change the source.

    Client stateServer state
    OwnerThe browserThe server / database
    Always up to date?Yes — you are the only writerNo — it may be stale
    NeedsSimple reads and updatesFetching, caching, deduplication, refetching, retries, pagination, invalidation
    Good toolsuseState, Context, Zustand, Redux Toolkit, PiniaTanStack Query, RTK Query, SWR, Apollo (GraphQL)
    ⚠️
    Writing server data into a generic store by hand (loading/error/data flags in every slice) means re-implementing a caching library badly — no deduplication, no background refresh, easy to show stale data.

    🔄 TanStack Query essentials

    TanStack Query (formerly React Query; also available for Vue, Svelte, Solid and Angular) manages server state. You give each query a query key and a function that returns a promise. The library caches the result under that key and keeps it fresh.

const queryClient = new QueryClient({

export function Root() {
  return (
    <QueryClientProvider client={queryClient}>
      <Products category="shoes" />

    </>

}

    🚀 Performance: avoiding unnecessary re-renders

    • Select narrowly. Subscribe to the smallest value you need: s => s.cart.items.length, not s => s.cart.
    • Return stable references. Selectors that build new arrays/objects need memoisation (createSelector) or shallow comparison (useShallow, shallowEqual).
    • Memoise expensive derivations with createSelector, useMemo, Vue computed or Pinia getters.
    • Split stores and contexts by domain and by update frequency, so a fast-changing value does not wake up unrelated components.
    • Memoise Context values and keep dispatch/actions in a separate context.
    • Keep state local when only one component uses it — local updates re-render a small subtree.
    • Normalise large collections so updating one item does not replace references for all items.
    • Virtualise long lists (e.g. TanStack Virtual) — rendering 5,000 rows is slow no matter where the state lives.

    React DevTools Profiler (“Highlight updates when components render”) shows which components re-render on each change. If typing in the search box flashes the whole product grid, the search text is probably stored too high or the grid selects too much.

    🧭 Fundamentals

    What is state, and how is it different from props?

    State is data that changes over time and drives what is rendered; it is owned by a component or a store. Props are read-only inputs a parent passes to a child. A child cannot change its props — it calls a callback so the owner updates its state, and the new value flows back down as props.

    What kinds of state exist in a frontend app?

    Local UI state (a dropdown open), shared client state (auth, theme, cart), server/cache state (API data), URL state (filters, page) and form state (field values, validation). Each has a natural home: local hooks, a store or Context, a query library, the router, and a form library or local state respectively.

    Why do React and Redux require immutable updates?

    They detect changes by comparing references with Object.is/===. If you mutate an object in place, the reference stays the same and the change is missed, so components do not re-render. Immutability also makes change detection cheap, enables time-travel debugging and avoids hidden side effects. Immer lets you write mutating syntax while still producing new objects.

    What is derived state and why should you not store it?

    A value computable from other state, such as a cart total or a filtered list. Storing it creates a second source of truth that must be kept in sync and eventually drifts. Compute it during render, and memoise if expensive (useMemo, createSelector, Vue computed, Pinia getters).

    What is prop drilling and how do you solve it?

    Passing a prop through several components that do not use it to reach a deep child. Solutions, in order of weight: restructure with composition (pass elements as children), use Context for rarely changing values, or use a store (Zustand, Redux Toolkit, Pinia) for frequently changing shared state. Light drilling through two levels is fine.

    🧩 Context API

    Is React Context a state management tool?

    Not by itself. Context is a dependency-injection / transport mechanism: it passes a value down the tree. The state still lives in useState or useReducer in the Provider component. Combined with useReducer it forms a simple state management solution.

    What triggers a re-render of a Context consumer, and how do you limit it?

    Any change to the Provider's value (by Object.is) re-renders every consumer, even if it uses an unchanged field. Limit it by memoising the value with useMemo, splitting contexts by domain and update frequency, separating state and dispatch into two contexts, and moving fast-changing data into a store with selectors.

    Why create a context with null and a custom hook?

    A null default lets the hook detect a missing Provider and throw a clear error (useAuth must be used inside <AuthProvider>). In TypeScript the null check narrows the type, so consumers get a non-null value with no repeated checks. It also hides the raw context object behind a clean API.

    When would you choose useReducer over useState?

    When several values change together, when the next state depends on the previous state in non-trivial ways, or when you want named, testable transitions. The reducer is a pure function you can unit test, and dispatch is stable, which makes it ideal to pass through Context.

    When is Context a poor choice?

    For high-frequency updates (mouse position, live prices, every keystroke of a large form), for large objects where consumers use small parts, and for server data that needs caching. Context has no selectors, so every consumer re-renders on every change.

    🧰 Redux Toolkit

    What problems does Redux Toolkit solve compared with classic Redux?

    createSlice generates action types and creators; Immer allows simple mutating syntax in reducers; configureStore sets up thunk, DevTools and dev-time immutability and serializability checks; createAsyncThunk standardises async request lifecycles; createEntityAdapter normalises collections; and RTK Query replaces hand-written fetching and caching. It is the officially recommended way to write Redux.

    Explain createAsyncThunk and how you handle its actions.

    It takes a type prefix and an async payload creator. When dispatched it emits pending, then fulfilled with the returned value as payload, or rejected if it throws (or returns rejectWithValue(...)). Handle them in extraReducers with builder.addCase to update status, data and error. The dispatch result supports .unwrap() and .abort().

    Why use createSelector?

    Selectors that filter, map or compute return new references every call, causing re-renders on every store update and repeating work. createSelector memoises: it recomputes only when its input selectors return new references, so the component gets the same reference back and skips re-rendering.

    What is normalised state and why use it?

    Storing each entity once in a lookup table keyed by id, with an ids array for order: { ids, entities }. It gives O(1) lookups, prevents duplicated copies going out of sync, and makes updating one item cheap. createEntityAdapter generates this structure plus CRUD reducers and selectors.

    How does RTK Query cache invalidation work?

    Queries declare providesTags (e.g. { type: 'Product', id } and a LIST tag). Mutations declare invalidatesTags. When a mutation succeeds, every active query providing a matching tag is refetched automatically. Unused cache entries are removed after keepUnusedDataFor seconds (60 by default).

    🐻 Zustand

    How does Zustand differ from Redux Toolkit?

    Zustand is a minimal external store: one create call returns a hook, no Provider, actions live inside the store and you update with set. There are no action objects or reducers by default and very little boilerplate. Redux Toolkit is more opinionated, with actions, reducers, middleware conventions, first-class DevTools and RTK Query — valuable in large teams.

    How do you avoid unnecessary re-renders with Zustand?

    Always select the smallest value: useStore(s => s.count). Never call useStore() without a selector, which subscribes to everything. When selecting several values as an object or array, wrap the selector in useShallow — in Zustand 5, returning a new object each time can even cause an infinite loop. Actions are stable, so selecting them does not cause re-renders.

    Why does TypeScript use create<T>()(…) with two calls?

    The curried form lets you specify the state type explicitly while TypeScript still infers the middleware types (persist, devtools, immer). TypeScript cannot partially infer generic arguments in a single call, so the extra parentheses split the explicit and inferred parts.

    How do you persist part of a Zustand store?

    Wrap the creator in persist with a unique name (storage key), optionally a storage via createJSONStorage, and a partialize function returning only the fields to save. Add version and migrate when the stored shape changes.

    How do you use a Zustand store outside React components?

    The hook also carries the store API: useStore.getState() to read, useStore.setState(partial) to update and useStore.subscribe(listener) to react to changes (it returns an unsubscribe function). This works in API interceptors, WebSocket handlers and tests.

    🍍 Pinia

    Why did Pinia replace Vuex?

    Pinia removes mutations (actions change state directly), uses many flat modular stores instead of nested modules, has excellent TypeScript inference, supports the Composition API through setup stores, is lightweight and integrates with Vue DevTools and SSR. It is now the official recommendation; Vuex is in maintenance mode.

    Compare options stores and setup stores.

    Options stores use state (a function), getters and actions and get $reset() for free. Setup stores are a function using ref (state), computed (getters) and functions (actions); they can use watchers and composables, but must return all state and implement their own reset.

    Why does destructuring a store break reactivity, and what is the fix?

    The store is a reactive object. Destructuring reads the current values into plain variables, cutting the link to the proxy. storeToRefs(store) returns refs for state and getters that stay connected; actions can be destructured directly from the store.

    When would you use $patch?

    To apply several changes as one update, producing a single $subscribe notification and one DevTools entry. The object form merges partial state; the function form receives the state and is best for array operations like push or splice.

    What should you watch out for with Pinia and SSR?

    Each request must get its own Pinia instance so users never share state; with Nuxt the @pinia/nuxt module handles this and serialises state for hydration. Keep state serialisable, return all state from setup stores, and call useStore() inside setup, actions or middleware rather than at module top level.

    🏗️ Architecture & scenarios

    How would you structure state for an e-commerce app?

    Product data, product details and orders as server state in TanStack Query or RTK Query. Category, search, sort and page in the URL. The cart and auth session as global client state in a small store (or Context for auth), persisting the cart. UI toggles as local state. Checkout forms in React Hook Form. Cart totals are derived via selectors, never stored.

    A page is slow because typing in a search box re-renders a large product grid. How do you debug and fix it?

    Profile with React DevTools to confirm what re-renders. Typical causes: search text stored in a big Context or selected via the whole store, or a selector returning a new array. Fixes: keep the input's text local and debounce it before it reaches the URL or query key, narrow selectors, memoise the filtered list with createSelector/useMemo, memoise grid rows with React.memo, and virtualise the grid.

    How do you decide between Context, Zustand and Redux Toolkit for a new React project?

    Start by moving server data to a query library and filters to the URL, then look at what is left. Low-frequency values only → Context. Moderate shared client state, small team, want simplicity → Zustand. Large codebase, many developers, complex workflows, need strict conventions, middleware and time-travel debugging → Redux Toolkit.

    What is an optimistic update and what are its risks?

    Updating the UI immediately as if the server request succeeded, then rolling back on failure. It makes the app feel instant (likes, toggles, reordering). Risks: you must snapshot the previous state, roll back correctly on error, handle races with in-flight refetches (cancel them first) and finally refetch or invalidate to sync with the server. TanStack Query and RTK Query both support this pattern.

    How do you test state logic?

    Unit test reducers and store actions as pure input → output (Redux reducers directly; Zustand via getState/setState with a reset in beforeEach; Pinia with setActivePinia(createPinia()) per test). For components, render them with a fresh real store, mock the network with MSW and assert on what the user sees, not on internal action names.

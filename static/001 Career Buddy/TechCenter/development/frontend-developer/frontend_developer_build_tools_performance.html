    Build Fundamentals

    Why front-end projects need a build step, how packages and modules work, and what bundling, transpiling, minification, tree shaking and cache busting actually do.

    🧭 Why build tools exist

    In the early web you wrote a few .js and .css files and linked them straight from your HTML. Modern front-end code is different. A typical app has hundreds of modules, uses JSX or TypeScript that browsers cannot run, pulls in npm packages, and must load fast on a cheap phone over a slow network.

    A build tool is the program that turns the code you write into the files the browser downloads. It solves four problems at once:

    🧩
    Modules
    Resolve import statements, including bare names like react that point into node_modules.
    🔤
    Syntax
    Turn JSX, TypeScript, Vue/Svelte files and modern syntax into plain JavaScript the target browsers understand.
    🌍
    Browser support
    Lower newer syntax for older browsers and add vendor prefixes to CSS where needed.
    📦
    Size and speed
    Minify, remove unused code, split into chunks and add content hashes so files cache well.
    Without a build stepWith a build step
    Many separate HTTP requests, one per fileA few optimised chunks, loaded when needed
    Bare imports such as import React from 'react' fail in the browserThe bundler resolves them to real files
    JSX and TypeScript cannot runTranspiled to plain JavaScript
    Comments, whitespace and long names shipped to usersMinified output, often 50–70% smaller before compression
    Users keep stale cached files after a deployHashed file names force a fresh download only when content changes
    📝
    Browsers now support ES modules natively, so small sites can skip a build. Once you use npm packages, JSX/TypeScript or care about load performance, a build tool pays for itself.

    🔢 Semantic versioning and lockfiles

    npm packages use semantic versioning: MAJOR.MINOR.PATCH. A major bump may break your code, a minor bump adds features without breaking, a patch bump only fixes bugs. The range you write in package.json says which future versions are acceptable.

    RangeAllowsExample matches for 1.4.2
    1.4.2Exactly that version1.4.2 only
    ^1.4.2Same major: >=1.4.2 <2.0.01.4.3, 1.9.0 — not 2.0.0
    ~1.4.2Same minor: >=1.4.2 <1.5.01.4.9 — not 1.5.0
    ^0.4.2Below 1.0 the caret is stricter: >=0.4.2 <0.5.00.4.7 — not 0.5.0
    * or latestAnythingAvoid in real projects

    Ranges alone are not reproducible: two developers installing a week apart could get different versions. A lockfile records the exact resolved version and integrity hash of every package in the tree, including dependencies of dependencies.

    bash# Local development: installs and may update the lockfile
npm install

# CI / production builds: installs exactly what the lockfile says,
# deletes node_modules first, and fails if package.json and the lockfile disagree
npm ci

# See what is out of date
npm outdated
    ⚠️
    Always commit the lockfile, and use only one package manager per project. Mixing package-lock.json and yarn.lock leads to “works on my machine” bugs.

    🔗 ES modules vs CommonJS

    JavaScript has two module systems. ES modules (ESM) are the official standard and run natively in browsers. CommonJS (CJS) is the older Node.js system. You will meet both in node_modules.

    ES modules

    javascript// math.js
export function add(a, b) { return a + b; }
export default function mul(a, b) { return a * b; }

// app.js
import mul, { add } from './math.js';
const { heavy } = await import('./heavy.js'); // dynamic import

    CommonJS

    javascript// math.js
function add(a, b) { return a + b; }
module.exports = { add };

// app.js
const { add } = require('./math.js');
// require can run anywhere, e.g. inside an if
    AspectES modulesCommonJS
    Syntaximport / exportrequire() / module.exports
    StructureStatic — imports are known before code runsDynamic — require is a normal function call
    LoadingAsynchronous; supports top-level awaitSynchronous
    Browser supportNative via <script type="module">None — needs a bundler
    Tree shakingWorks well, because exports can be analysed staticallyHard; bundlers usually keep the whole module
    💡
    Prefer ESM in new code and prefer libraries that publish an ESM build. Static structure is what lets bundlers remove unused exports.

    🛠️ What a build actually does

    Different tools use different names, but almost every front-end build performs the same jobs:

    TranspilingTranslating one form of source into another at a similar level: TypeScript → JavaScript, JSX → jsx() calls, a?.b → older syntax for old browsers. Done by Babel, SWC, esbuild or tsc.
    BundlingFollowing import statements from an entry file to build a dependency graph and combining modules into a small number of output files (chunks).
    MinificationRemoving whitespace and comments, shortening local variable names and simplifying expressions without changing behaviour (Terser, esbuild, SWC, Lightning CSS).
    Tree shakingDropping exports that are never imported anywhere — dead-code elimination based on the static ESM graph.
    Code splittingBreaking the bundle into several chunks so a page loads only what it needs; dynamic import() creates a split point.
    Source maps.map files that map minified output back to your original source so DevTools shows real file names and line numbers.
    Content hashingPutting a hash of the file's content in its name (index-4f2a9c1b.js) so a changed file gets a new URL — this is cache busting.
    Asset handlingCopying, optimising, inlining or fingerprinting images, fonts and CSS that your code imports.
    EXAMPLE · Tree shaking in practice

    A utility module exports formatPrice, formatDate and slugify. Your app only imports formatPrice. In a production build the bundler sees that the other two exports are never used and, as long as the module has no side effects, leaves them out of the output.

    ⚠️
    Type checking is not the same as transpiling. esbuild and SWC strip TypeScript types very fast but do not check them. Run tsc --noEmit (or tsc -b) in your build or CI to catch type errors.

    ⚡ Dev server vs production build

    Build tools run in two very different modes. Development is optimised for fast feedback; production is optimised for fast users.

    AspectDev server (npm run dev)Production build (npm run build)
    GoalInstant start and instant updatesSmallest, fastest, cache-friendly output
    OutputServed from memory, nothing written to dist/Files written to dist/
    MinificationOffOn
    Source mapsDetailed, cheap to generateOften separate or hidden, or off
    Hot Module ReplacementYes — edit and see changes without a full reloadNo
    Environmentimport.meta.env.DEV / process.env.NODE_ENV === 'development'PROD / 'production' — dev-only warnings are stripped
    ⚠️
    Never measure performance on the dev server. It serves unminified, unbundled code with extra checks. Run a production build and serve it locally (for example vite preview) before you measure.
    HMRHot Module Replacement: swaps an edited module in the running page, keeping component state where possible.
    Entry pointThe file where the dependency graph starts (src/main.tsx, or index.html in Vite).
    ChunkOne output JavaScript file produced by the bundler.
    TargetThe oldest browsers or JS version the output must run on.

    Vite

    The fast, modern default for new front-end projects — how its dev server and production build work, and how to configure aliases, proxies, env variables, assets, CSS and library builds.

    ⚡ How Vite works

    Vite (French for “fast”, pronounced “veet”) is a build tool created by Evan You. It became popular because the dev server starts in well under a second even on large projects. It does this by treating development and production differently.

    PhaseWhat Vite doesWhy it is fast
    Dependency pre-bundling (first dev start)Uses esbuild to convert packages in node_modules into ESM and merge packages with many internal files (like lodash-es) into one file each. Cached in node_modules/.vite.esbuild is written in Go and is very fast; the cache is reused until your lockfile or config changes.
    Dev serverServes your source files as native ES modules. The browser requests each import; Vite transforms only that file (TS, JSX, Vue) on demand.No up-front bundling of your app. Only the modules the current page needs are processed.
    Production buildBundles with Rollup: tree shaking, code splitting, minification, hashing, CSS extraction.Fully optimised output — thousands of small ESM requests would be slow on real networks.
    Dev mode: the browser drives module loading; Vite transforms files on request
    📝
    Rolldown: the Vite team has been replacing the esbuild + Rollup pair with Rolldown, a Rust bundler with a Rollup-compatible plugin API. It started as an opt-in rolldown-vite package alongside Vite 7, and newer major versions make it the default. Most Rollup-style plugins keep working, but check the release notes for the Vite version you use.
    💡
    Vite 7 requires Node.js 20.19+ or 22.12+. If npm create vite fails with odd syntax errors, check node -v first.

    ⚙️ vite.config.ts

    Vite works with zero config, but most real projects add a vite.config.ts. The defineConfig helper gives you type checking and auto-complete.

    typescriptimport { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import { fileURLToPath, URL } from 'node:url';

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      '@': fileURLToPath(new URL('./src', import.meta.url)),
    },
  },
  server: {
    port: 3000,
    open: true,
    proxy: {
      // /api/products -> http://localhost:8080/products
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
    },
  },
  build: {
    outDir: 'dist',
    sourcemap: true,
    rollupOptions: {
      output: {
        manualChunks: { react: ['react', 'react-dom'] },
      },
    },
  },
});
    OptionWhat it does
    pluginsArray of Vite/Rollup plugins (framework support, legacy builds, PWA…).
    resolve.aliasShort import paths: import Button from '@/components/Button'. Mirror it in tsconfig.json paths so TypeScript understands it too.
    server.proxyForwards matching requests from the dev server to your API, avoiding CORS problems in development only.
    server.port / server.hostDev server port (default 5173); host: true exposes it on your LAN for phone testing.
    basePublic base path when the app is not served from / (e.g. '/shop/' on GitHub Pages).
    build.outDir, build.sourcemap, build.targetOutput folder, source map generation and the browser/JS level to compile down to.
    build.rollupOptionsPass-through options for the underlying Rollup build, e.g. manualChunks or external.
    ⚠️
    server.proxy only exists in vite dev. In production the deployed site calls the real API URL, so configure CORS or a reverse proxy on the server side too.

    🔥 Hot Module Replacement

    When you save a file, Vite sends a message over a WebSocket to the page. Only the changed module (and the modules that must re-run because of it) are replaced. Framework plugins add smart HMR: React Fast Refresh keeps component state, and Vue keeps component instances.

    You edit…What happens
    A React component fileFast Refresh re-renders it; useState values are kept.
    A CSS fileStyles are swapped without reloading the page.
    A module with no HMR boundary (e.g. a plain utility used by main.tsx)The update bubbles up; if nothing accepts it, Vite does a full page reload.
    vite.config.ts or .envThe dev server restarts.
    typescript// Low-level HMR API (framework plugins usually do this for you)
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // re-initialise using the updated module
  });
  import.meta.hot.dispose(() => {
    // clean up timers, listeners, sockets from the old version
  });
}
    💡
    If Fast Refresh keeps doing full reloads, check that component files only export components. Mixing a component export with a non-component export (like a constant) can break the refresh boundary.

    🖼️ Static assets and the public folder

    There are two ways to use images, fonts and other files.

    Imported assets (src/)

    Import the file from code. Vite processes it, adds a content hash and returns the final URL.

    typescriptimport logoUrl from './assets/logo.svg';
// dev:  /src/assets/logo.svg
// prod: /assets/logo-3fa9c2.svg
<img src={logoUrl} alt="Shop logo" />

    public/ folder

    Files are copied to dist/ untouched, with no hash. Reference them by absolute path.

    html<!-- public/robots.txt -> /robots.txt -->
<link rel="icon" href="/favicon.ico" />
    Import suffixReturns
    (none) for an image/fontThe public URL of the processed file
    ?urlThe URL even for file types that would otherwise be processed (e.g. a worklet)
    ?rawThe file contents as a string (e.g. an SVG or a shader)
    ?inlineThe asset inlined as a base64 data URL
    ?workerA constructor for a Web Worker bundled from that file

    Small imported assets below build.assetsInlineLimit (4 KiB by default) are inlined as data URLs to save a request.

    💡
    Use public/ only for files that must keep a fixed name (robots.txt, favicon.ico, manifest.webmanifest). Everything else should be imported so it gets a hash and long-term caching.

    Webpack

    The configurable bundler behind countless production apps — entry, output, loaders, plugins, code splitting, tree shaking, bundle analysis and Module Federation, plus when to migrate.

    🧱 Core concepts

    Webpack is a module bundler. Starting from one or more entry files it builds a dependency graph of everything they import — JavaScript, CSS, images, fonts — and emits bundles. Version 5 is the current major version. Unlike Vite, Webpack bundles your app in development too.

    🚪
    Entry
    Where the graph starts. Default ./src/index.js.
    📤
    Output
    Where bundles are written and how they are named. Default ./dist/main.js.
    🔁
    Loaders
    Transform individual files so Webpack can treat them as modules (TS → JS, CSS → JS module).
    🔌
    Plugins
    Hook into the whole compilation to do bigger jobs: generate HTML, extract CSS, define constants, analyse bundles.
    🎚️
    Mode
    development, production or none — turns on sensible built-in defaults.
    🧭
    Resolve
    How import paths are found: extensions to try, aliases, module folders.
    ModeWhat it switches on
    developmentReadable output, fast rebuilds, process.env.NODE_ENV = 'development', useful module names for debugging
    productionMinification (Terser), tree shaking (usedExports), scope hoisting, NODE_ENV = 'production', deterministic IDs
    noneNo defaults at all — rarely used
    📝
    Loader vs plugin in one line: a loader works on one file at a time as it is imported; a plugin works on the whole build at any stage.

    📝 A complete webpack.config.js

    Here is a realistic configuration for a React + TypeScript app. Read it top to bottom — every key maps to one of the concepts above.

    javascript// webpack.config.js
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');
const MiniCssExtractPlugin = require('mini-css-extract-plugin');

module.exports = (env, argv) => {
  const isProd = argv.mode === 'production';
  return {
    entry: './src/index.tsx',
    output: {
      path: path.resolve(__dirname, 'dist'),
      filename: isProd ? '[name].[contenthash].js' : '[name].js',
      publicPath: '/',
      clean: true,                       // empty dist/ before each build
    },
    resolve: {
      extensions: ['.tsx', '.ts', '.js'],
      alias: { '@': path.resolve(__dirname, 'src') },
    },
    module: {
      rules: [
        {
          test: /\.[jt]sx?$/,
          exclude: /node_modules/,
          use: 'babel-loader',           // or 'ts-loader'
        },
        {
          test: /\.css$/i,
          // loaders run right-to-left: css-loader first, then style/extract
          use: [isProd ? MiniCssExtractPlugin.loader : 'style-loader', 'css-loader'],
        },
        { test: /\.(png|jpe?g|gif|svg|webp|avif)$/i, type: 'asset' },
        { test: /\.(woff2?)$/i, type: 'asset/resource' },
      ],
    },
    plugins: [
      new HtmlWebpackPlugin({ template: './public/index.html' }),
      isProd && new MiniCssExtractPlugin({ filename: '[name].[contenthash].css' }),
    ].filter(Boolean),
    devtool: isProd ? 'source-map' : 'eval-cheap-module-source-map',
    devServer: { port: 3000, hot: true, historyApiFallback: true },
    optimization: {
      splitChunks: { chunks: 'all' },
      runtimeChunk: 'single',
    },
  };
};

npx webpack serve --mode development

    🔁 Loaders and asset modules

    Out of the box Webpack only understands JavaScript and JSON. Loaders teach it other file types. A rule matches files with test and applies use.

    Loader / typeJob
    babel-loaderRuns Babel: JSX, TypeScript (via @babel/preset-typescript) and modern syntax down to your browserslist targets. No type checking.
    ts-loaderRuns the TypeScript compiler. Type-checks by default (slower); often combined with transpileOnly: true plus fork-ts-checker-webpack-plugin.
    swc-loader / esbuild-loaderMuch faster drop-in transpilers written in Rust / Go.
    css-loaderResolves @import and url() in CSS and turns CSS into a JS module. Supports CSS Modules.
    style-loaderInjects that CSS into a <style> tag at run time — great for dev HMR.
    MiniCssExtractPlugin.loaderExtracts CSS into real .css files for production so CSS can load in parallel and be cached.
    postcss-loader, sass-loaderAutoprefixer / Sass compilation. Placed to the right of css-loader.

    Webpack 5 replaced file-loader, url-loader and raw-loader with built-in asset modules:

    Responsive Web Design

    One codebase that works on a 320px phone, a tablet and a 4K monitor — viewport, mobile-first CSS, fluid layouts, media and container queries, fluid type, responsive images and user preferences.

    📱 The viewport meta tag and mobile-first thinking

    Mobile browsers originally assumed every page was a desktop site. They rendered it on a virtual canvas about 980px wide and shrank it to fit, so text was tiny. The viewport meta tag tells the browser to use the device's real width instead.

    html<meta name="viewport" content="width=device-width, initial-scale=1" />
    ⚠️
    Do not add maximum-scale=1 or user-scalable=no. Blocking pinch-zoom is an accessibility failure for people with low vision.

    Mobile-first means you write the base styles for the smallest screen, then add layout for larger screens with min-width media queries. Small screens get the simplest CSS, and you are forced to decide what content really matters.

    Mobile-first (recommended)

    css.grid { display: grid; gap: 1rem; }          /* 1 column */
@media (min-width: 768px) {
  .grid { grid-template-columns: 1fr 1fr; }
}
@media (min-width: 1200px) {
  .grid { grid-template-columns: repeat(4, 1fr); }
}

    Desktop-first

    css.grid { display: grid; grid-template-columns: repeat(4, 1fr); }
@media (max-width: 1199px) {
  .grid { grid-template-columns: 1fr 1fr; }
}
@media (max-width: 767px) {
  .grid { grid-template-columns: 1fr; }  /* undoing work */
}
    💡
    Most real traffic for consumer sites is mobile, and Google indexes the mobile version of your pages. Design and test the phone layout first.

    📐 Relative units

    Fixed pixel sizes break when the screen or the user's font size changes. Relative units scale with their context.

    📦 Container queries and fluid typography

    Media queries look at the viewport. But a product card may sit in a wide main column on one page and a narrow sidebar on another. Container queries let a component respond to the size of its container. They are Baseline since 2023.

    css.card-slot { container-type: inline-size; container-name: card; }

.product-card { display: grid; gap: 0.75rem; }

@container card (min-width: 420px) {
  .product-card { grid-template-columns: 160px 1fr; }  /* image beside text */
}

    Fluid typography scales text smoothly between a minimum and maximum instead of jumping at breakpoints. clamp(MIN, PREFERRED, MAX) does this in one line.

    cssh1 {
  /* never below 1.75rem, never above 3rem, grows with viewport in between */
  font-size: clamp(1.75rem, 1.2rem + 2.5vw, 3rem);
}
.section { padding-block: clamp(2rem, 6vw, 5rem); }
    ⚠️
    Avoid a pure vw preferred value like clamp(1rem, 4vw, 3rem) for body text: vw does not grow when the user zooms, which can fail WCAG resize-text requirements. Mixing in rem (1rem + 1vw) keeps zoom working.

    🖼️ Responsive images

    Images are usually the heaviest part of a page. Sending a 2400px photo to a 375px phone wastes data and slows LCP. HTML gives you two tools:

    1. srcset + sizes — same image, different resolutions

    html<img
  src="shoe-800.jpg"
  srcset="shoe-400.jpg 400w, shoe-800.jpg 800w, shoe-1600.jpg 1600w"
  sizes="(min-width: 1024px) 33vw, 100vw"
  width="800" height="600"
  alt="Red running shoe, side view" />

    400w tells the browser each file's real width. sizes says how wide the image will be displayed. The browser combines that with the screen's pixel density and picks the smallest file that looks sharp.

    2. picture — different formats or art direction

    html<picture>
  <!-- Art direction: a tighter crop on small screens -->
  <source media="(max-width: 600px)" srcset="hero-crop.avif" type="image/avif" />
  <source media="(max-width: 600px)" srcset="hero-crop.jpg" />
  <!-- Modern formats for larger screens, with fallback -->
  <source srcset="hero.avif" type="image/avif" />
  <source srcset="hero.webp" type="image/webp" />
  <img src="hero.jpg" width="1600" height="900" alt="Summer sale banner" />
</picture>

    🪜 Progressive enhancement and graceful degradation

    Progressive enhancement

    Start with a baseline that works everywhere (semantic HTML, a real form that submits), then layer on CSS and JavaScript enhancements for browsers that support them.

    • A search form that posts to the server, enhanced with instant results when JS loads
    • A flex fallback, upgraded to grid with @supports

    Graceful degradation

    Build the full modern experience first, then make sure it still works acceptably (perhaps with fewer features) in older or limited browsers.

    • A 3D product viewer that falls back to a static image gallery
    • Animated transitions that are simply skipped where unsupported
    EXAMPLE · Progressive enhancement with a modern API
    javascript// Baseline: a normal link that navigates to /share

  btn.addEventListener('click', async (e) => {
    e.preventDefault();
    try {
      await navigator.share({ title: document.title, url: location.href });
    } catch { /* user cancelled */ }
  });
}
    ✅
    Progressive enhancement also improves resilience: if a script fails to load on a flaky mobile network, the core task still works.

    Web Vitals and Performance

    Measure what users feel — LCP, INP and CLS — in the lab and the field, then fix them with preloading, smaller JavaScript, reserved space, caching, compression and budgets.

    🎯 Core Web Vitals and their thresholds

    Core Web Vitals are Google's three user-centred metrics for loading, responsiveness and visual stability. They are part of Google Search's page-experience signals, but more importantly they correlate with real user behaviour: slow, janky pages lose sales.

    MetricMeasuresGoodNeeds improvementPoor
    LCP — Largest Contentful PaintLoading: when the largest image or text block in the viewport is rendered≤ 2.5 s2.5 s – 4.0 s> 4.0 s
    INP — Interaction to Next PaintResponsiveness: delay from a click, tap or key press until the next frame is painted (roughly the worst interaction on the page)≤ 200 ms200 ms – 500 ms> 500 ms
    CLS — Cumulative Layout ShiftVisual stability: the largest burst of unexpected layout shifts (unitless score)≤ 0.10.1 – 0.25> 0.25
    📝
    INP replaced FID (First Input Delay) as a Core Web Vital in March 2024. FID only measured the delay before the first interaction's handler started; INP measures the full latency — input delay, processing time and presentation delay — of all interactions.
    💡
    A page “passes” when the 75th percentile of real page loads is in the Good range, measured separately for mobile and desktop. So 1 in 4 users can still have a worse experience — aim well inside the threshold.

    ⏱️ Supporting metrics and lab vs field data

    MetricWhat it tells youGood
    TTFB — Time to First ByteServer and network time until the first byte of the HTML arrives. Includes redirects, DNS, TLS, server work.≤ 0.8 s
    FCP — First Contentful PaintWhen the first text or image appears. Users see “something is happening”.≤ 1.8 s
    TBT — Total Blocking TimeLab-only: sum of the part of each long task above 50 ms between FCP and interactive. The lab proxy for INP.≤ 200 ms (Lighthouse, mobile)

    Lab data (synthetic)

    A tool loads the page once in a controlled environment: fixed device, CPU throttling, network speed.

    • Tools: Lighthouse, PageSpeed Insights (lab section), WebPageTest, DevTools Performance panel
    • Reproducible — great for debugging and CI checks
    • Cannot measure INP (no real user interactions); uses TBT instead
    • May not match real devices, networks or user flows

    Field data (real users)

    Measurements collected from real visits — Real User Monitoring (RUM).

    • Sources: Chrome UX Report (CrUX), PageSpeed Insights field section, Search Console, your own RUM via the web-vitals library
    • Reflects the true mix of devices and networks
    • CrUX is a rolling 28-day window from opted-in Chrome users
    • Harder to debug — you need attribution data
    ⚠️
    A Lighthouse score of 98 on your fast laptop does not mean you pass Core Web Vitals. Google judges you on field data. Use lab tools to diagnose and field data to decide.

    📡 Measuring real users with the web-vitals library

    Google's small web-vitals library measures each metric the same way Chrome reports it to CrUX. Send the values to your analytics endpoint.

    🖼️ Optimising LCP

    LCP is usually a hero image or a large heading. Break its time into four parts and fix the biggest one:

    The four LCP sub-parts: server response, waiting to start the download, the download itself, and rendering
    Sub-partCommon causesFixes
    TTFBSlow server, no CDN, redirectsCDN / edge caching, server-side rendering or static generation, remove redirect chains
    Load delayThe image is discovered late — set by JS or as a CSS backgroundPut the <img> in the HTML, fetchpriority="high", or <link rel="preload">
    Load timeHuge file, old formatAVIF/WebP, correct dimensions with srcset, compression, CDN image resizing
    Render delayRender-blocking CSS/JS, client-side rendering waits for a JS bundleInline critical CSS, defer scripts, SSR so HTML contains the content

    👆 Optimising INP

    An interaction feels slow when the main thread is busy. A task longer than 50 ms is a long task; while it runs, the browser cannot respond to input or paint.

    INP phaseWhat happensFix
    Input delayAnother task (hydration, analytics, a timer) is already running when the user clicksShip less JS, split long start-up work, defer third-party scripts
    Processing timeYour event handlers runDo the minimum, then yield; move heavy work to a Web Worker
    Presentation delayStyle, layout and paint of the updateSmaller DOM, avoid layout thrashing, content-visibility: auto for off-screen sections
    javascript// Yield to the main thread so the browser can paint and handle input
function yieldToMain() {
  if (globalThis.scheduler?.yield) return scheduler.yield();   // Chromium; others may lack it
  return new Promise((resolve) => setTimeout(resolve, 0));
}

button.addEventListener('click', async () => {
  showSpinner();            // 1. give instant visual feedback
  await yieldToMain();      // 2. let the browser paint it

  let lastYield = performance.now();
  for (const item of bigList) {
    process(item);
    if (performance.now() - lastYield > 50) {   // keep each task under ~50 ms
      await yieldToMain();
      lastYield = performance.now();
    }
  }
});

    javascript// Debounce expensive work on fast-firing input
function debounce(fn, ms = 200) {
  let t;
  return (...args) => { clearTimeout(t); t = setTimeout(() => fn(...args), ms); };
}

    📐 Optimising CLS

    A layout shift happens when a visible element moves without the user causing it. Shifts within 500 ms after a user input (like opening an accordion) do not count.

    CauseFix
    Images and videos without dimensionsSet width and height attributes, or CSS aspect-ratio
    Ads, embeds and iframes that load lateReserve space with a fixed-size container or min-height
    Banners (cookie, promo) injected above contentOverlay them (fixed position) or reserve the slot in the initial HTML
    Web fonts swapping in with different metricsfont-display: optional, preload key fonts, or match fallback metrics with size-adjust
    Animating top/left/heightAnimate transform and opacity instead — they do not cause layout shifts
    Content inserted while loading (skeletons of the wrong size)Make skeletons the same size as the final content
    css.ad-slot { min-height: 250px; }                 /* reserve the ad's space */
.video-embed { aspect-ratio: 16 / 9; width: 100%; }

  font-family: 'Brand';
  src: url('/fonts/brand.woff2') format('woff2');

}

  src: local('Arial');
  size-adjust: 104%;
  ascent-override: 92%;
}
body { font-family: 'Brand', 'Brand Fallback', sans-serif; }

    🧭 Build fundamentals

    Why do we need a build tool for a modern front-end app?

    Browsers cannot run JSX or TypeScript, cannot resolve bare imports like react, and download many small files inefficiently. A build tool transpiles source, resolves and bundles modules, minifies and tree-shakes, splits code into chunks, and adds content hashes for caching. It also provides a dev server with HMR for fast feedback.

    What is the difference between dependencies and devDependencies?

    dependencies are needed at run time — libraries your app imports, like React. devDependencies are only needed to build, test or lint — Vite, TypeScript, ESLint. For a bundled SPA the bundler includes whatever is imported either way, so the split is mainly about clarity; for published libraries and Node servers it controls what consumers and npm install --omit=dev install.

    What do ^ and ~ mean in package.json, and why do we commit the lockfile?

    ^1.4.2 allows any 1.x.x at or above 1.4.2; ~1.4.2 allows only 1.4.x patches. Ranges let installs drift over time, so the lockfile pins the exact resolved version of every package in the tree. Committing it and using npm ci in CI makes builds reproducible.

    Explain tree shaking and what can stop it working.

    Tree shaking removes exports that are never imported, using the static structure of ES modules. It fails when a library ships only CommonJS, when Babel converts ESM to CommonJS, when modules have side effects the bundler must keep (fix with the sideEffects field), or when code accesses exports dynamically such as utils[name].

    What are source maps and should you ship them to production?

    Source maps map minified output back to original files and lines so stack traces and DevTools are readable. In production many teams generate them but either upload them privately to an error tracker (Sentry) or use hidden source maps, so users do not download them and source is not exposed — while errors are still readable.

    ⚡ Vite

    Why is Vite's dev server so much faster to start than Webpack's?

    Vite does not bundle your app in development. It pre-bundles dependencies once with esbuild and caches them, then serves your source as native ES modules, transforming each file only when the browser requests it. Start-up cost no longer grows with app size, and HMR updates only the changed module.

    If Vite is so fast in dev, why does it bundle for production?

    Serving hundreds of unbundled ESM files causes many network round trips and waterfall imports on real networks. The production build (Rollup, moving to Rolldown) applies tree shaking, code splitting, minification, CSS extraction and content hashing to produce a small number of cache-friendly files.

    How do environment variables work in Vite and what is the security risk?

    Vite loads .env, .env.local, .env.[mode] and .env.[mode].local. Only variables prefixed with VITE_ are exposed on import.meta.env and they are replaced statically in the bundle. Anything exposed is public to every user, so secrets must never be prefixed — they belong on a server.

    How would you call a backend on another port during development without CORS errors?

    Configure server.proxy in vite.config.ts, for example forwarding /api to http://localhost:8080 with changeOrigin: true. The browser sees a same-origin request. In production you still need real CORS headers or a reverse proxy, because the dev proxy does not exist there.

    What is the difference between importing an asset and putting it in public/?

    Imported assets go through the pipeline: they get a content hash, can be inlined if small, and missing files fail the build. Files in public/ are copied as-is with fixed names and referenced by absolute path — appropriate only for things like robots.txt or favicon.ico that must keep their name.

    📦 Webpack

    Explain entry, output, loaders, plugins and mode.

    Entry is where the dependency graph starts; output says where bundles go and how they are named. Loaders transform individual files (TS, CSS, images) into modules. Plugins hook into the whole compilation for tasks like generating HTML or extracting CSS. Mode (development/production) enables built-in defaults such as minification and tree shaking.

    Why use [contenthash] in file names, and why a separate runtime chunk?

    [contenthash] changes only when the file's content changes, so you can cache files for a year with immutable and users only re-download what changed. Webpack's runtime and chunk manifest change on almost every build; putting them in their own small chunk (runtimeChunk: 'single') stops those changes altering vendor and app chunk hashes.

    How does code splitting work in Webpack?

    Three ways: multiple entry points, dynamic import() (each call creates an async chunk loaded on demand), and SplitChunksPlugin which extracts shared and vendor modules into common chunks based on optimization.splitChunks rules. In React you pair dynamic imports with React.lazy and Suspense for route-level splitting.

    When would you use style-loader versus MiniCssExtractPlugin?

    style-loader injects CSS into <style> tags from JavaScript — fast and HMR-friendly, so ideal in development. In production, MiniCssExtractPlugin writes real .css files that download in parallel with JS, can be cached separately and avoid a flash of unstyled content while JS loads.

    A team asks whether to migrate from Webpack to Vite. How do you decide?

    Weigh the benefit (much faster dev start and HMR, simpler config) against the cost: custom loaders and plugins without Vite equivalents, Module Federation, process.env usage, require.context, Node polyfills. For a large, heavily customised config, Rspack may give most of the speed with minimal change. Prove it on a branch: compare dev times, bundle sizes and test results before switching.

    📱 Responsive design

    What does the viewport meta tag do, and what happens without it?

    It tells mobile browsers to set the layout viewport to the device width (width=device-width, initial-scale=1). Without it, mobile browsers lay the page out on a virtual canvas around 980px wide and shrink it, so text is tiny and media queries do not fire as expected.

    Explain mobile-first CSS and why it is preferred.

    You write base styles for the smallest screen and add complexity with min-width media queries. Small devices — often the slowest — get the simplest CSS, you avoid overriding desktop rules, and it forces content prioritisation. It matches how most consumer traffic arrives and how Google indexes pages.

    When would you use a container query instead of a media query?

    When a component's layout should depend on the space it is given, not the screen — for example a product card used in a full-width grid and in a narrow sidebar. Set container-type: inline-size on the wrapper and use @container (min-width: …) in the component's CSS, making it truly reusable.

    How do srcset and sizes work together?

    srcset lists candidate files with their intrinsic widths (800w). sizes tells the browser how wide the image will be displayed at different viewport widths. The browser multiplies the display width by the device pixel ratio and downloads the smallest candidate that is large enough. Use <picture> when you need different crops or formats.

    How do you make typography responsive without breaking accessibility?

    Use rem units so text respects the user's font-size setting, and clamp(min, preferred, max) for fluid scaling. Include a rem component in the preferred value (1rem + 1vw) because pure vw text does not scale with browser zoom. Keep line length around 45–75 characters with max-width in ch.

    🌐 Cross-browser

    What is the difference between a polyfill and transpiling?

    Transpiling rewrites unsupported syntax (optional chaining, class fields) into older syntax at build time. A polyfill adds a missing API (Promise, Array.prototype.at) with JavaScript at run time. You often need both: Babel's preset-env with useBuiltIns: 'usage' and core-js does exactly that.

    Why is feature detection better than user-agent sniffing?

    Feature detection tests the real capability (@supports, 'IntersectionObserver' in window), so it keeps working when browsers add features and is not fooled by spoofed or reduced UA strings. UA sniffing guesses from names and versions, breaks with every release and misclassifies browsers. Use UA checks only for analytics or a known engine bug that cannot be detected.

    What is browserslist and which tools use it?

    A shared list of target browsers in package.json or .browserslistrc, such as defaults or > 0.5%, last 2 versions, not dead. Babel's preset-env uses it to choose transforms and polyfills, Autoprefixer to add CSS prefixes, and many other tools (PostCSS, Lightning CSS, SWC when configured) read it so all tools agree on targets.

    Name some Safari or iOS-specific issues you have handled.

    100vh sections hidden behind the mobile toolbar — fixed with 100dvh plus a 100vh fallback. iOS zooming into inputs with font size under 16px. Non-ISO date strings parsing to Invalid Date. Notch and home-indicator overlap fixed with viewport-fit=cover and env(safe-area-inset-*). I confirm all of them on a real iPhone, because desktop emulation does not reproduce them.

    How do you set up cross-browser testing for a team?

    Start from analytics to define a support matrix. Run automated end-to-end tests with Playwright across Chromium, Firefox and WebKit in CI. Use a cloud device lab (BrowserStack, Sauce Labs) for real iPhones, Android devices and older versions before releases. Add error monitoring grouped by browser to catch what tests miss.

    ⚡ Web Vitals and performance

    What are the Core Web Vitals and their thresholds?

    LCP (loading) good at ≤ 2.5 s, poor above 4 s; INP (responsiveness) good at ≤ 200 ms, poor above 500 ms; CLS (visual stability) good at ≤ 0.1, poor above 0.25. They are assessed at the 75th percentile of real page loads, separately for mobile and desktop. INP replaced FID in March 2024.

    Lighthouse gives 95 but Search Console says LCP is poor. Why?

    Lighthouse is lab data: one simulated load on a fixed profile. Search Console uses CrUX field data from real users over 28 days — slower phones, worse networks, different pages, logged-in states, ad and consent banners. Google assesses with field data. Use RUM attribution to find which pages and elements are slow, then reproduce with throttled lab runs.

    How would you improve a poor LCP?

    Find the LCP element and break the time into TTFB, load delay, load time and render delay. Typical fixes: CDN and caching or SSR for TTFB; make the image discoverable in HTML with fetchpriority="high" or a preload, and never lazy-load it; serve AVIF/WebP at the right size with srcset; remove render-blocking CSS/JS and inline critical CSS.

    How would you improve a poor INP?

    Find slow interactions with RUM attribution or the Performance panel. Reduce input delay by shipping and running less JS during load (code split, defer third parties). Shorten handlers: give immediate visual feedback, then yield to the main thread (scheduler.yield() or setTimeout), break long tasks up, debounce input, move heavy work to a Web Worker, and use startTransition in React. Reduce presentation cost with a smaller DOM.

    What causes layout shift and how do you prevent it?

    Images and embeds without dimensions, ads and banners injected above content, web fonts swapping with different metrics, and animations of layout properties. Prevent it with width/height or aspect-ratio, reserved space for dynamic content, overlays instead of inserted banners, font-display plus metric-matched fallbacks, and animating transform instead of top or height.

    Module 01 · Basic · Styling Fundamentals

    Styling Fundamentals

    Why plain CSS gets hard in big apps, the main ways teams solve it, and how your styles actually reach the browser.

    🧭 Why styling needs tools at all

    CSS is simple to start with. You write a selector, add some declarations, and the browser paints the page. On a small site that is all you need. The trouble starts when the app grows to hundreds of components and several developers.

    Every rule in a normal stylesheet is global. A class called .title written for the blog page also hits every other element with class="title" anywhere in the app. Nothing stops two people choosing the same name.

    🌍
    Global scope
    Every selector can match anything on the page. A change in one file can break a screen you never opened.
    💥
    Naming collisions
    Two teams both write .card. The last stylesheet loaded wins, so the bug depends on load order.
    ⚔️
    Specificity wars
    To beat an old rule, people add more selectors, then IDs, then !important. Each fix makes the next one harder.
    🪦
    Dead code
    Nobody dares delete a rule because they cannot tell if it is still used. The CSS file only ever grows.
    🔁
    Repetition
    The same blue, the same spacing and the same media query are copied into dozens of places.
    🧩
    Disconnected from components
    Markup lives in a component file but its styles live somewhere else, so they drift apart.
    EXAMPLE · A collision in real life

    Team A writes .button { padding: 8px; } for the header. Team B later adds .button { padding: 16px; background: red; } for a promo banner. Now every header button is red with big padding, but only on pages where the promo CSS happens to load. Styling tools exist to make this class of bug impossible or easy to spot.

    📝
    None of the tools in this course replace CSS. They all produce normal CSS in the end. They change how you write and organise it.

    ⚖️ Specificity and the cascade in two minutes

    When two rules set the same property on the same element, the browser picks a winner. It looks at origin and !important, then cascade layers, then specificity, then source order (the later rule wins).

    SelectorSpecificity (ID, class, type)Notes
    p0, 0, 1Type selectors are the weakest.
    .note0, 1, 0Classes, attributes and pseudo-classes count here.
    .card .note0, 2, 0Two classes beat one class.
    #sidebar .note1, 1, 0One ID beats any number of classes.
    :where(.card) .note0, 1, 0:where() always adds zero specificity.
    Inline style="..."Beats all selectorsOnly !important in a stylesheet beats it.
    css/* Specificity war: each fix is stronger than the last */
.button { color: white; }
.header .button { color: black; }          /* 0,2,0 */
#top .header .button { color: blue; }      /* 1,2,0 */
.button { color: green !important; }       /* now nothing else can win */
    💡
    Most styling methods aim for flat, single-class selectors. When every rule has the same low specificity, source order is predictable and you never need !important.

    Modern CSS also offers @layer (cascade layers). Rules in a later-declared layer beat rules in an earlier layer regardless of specificity. Tailwind v4 uses layers internally (theme, base, components, utilities).

    🔄 How styles reach the browser

    Whatever you write — SCSS, Tailwind classes, a .module.css file or a styled component — the browser only understands CSS. Build tools translate your source into plain CSS files (or, for runtime CSS-in-JS, into style tags created while the page runs).

    🏷️ Naming with BEM

    BEM stands for Block, Element, Modifier. It is a naming convention for plain CSS or Sass. It does not need any tool — only discipline. Every class is a single flat selector, so specificity stays low and equal.

    PartPatternMeaningExample
    BlockblockA standalone component.card
    Elementblock__elementA part that only makes sense inside its block.card__title
    Modifierblock--modifierA variation or state.card--featured
    html<article class="card card--featured">
  <img class="card__image" src="hero.jpg" alt="">
  <h3 class="card__title">Summer sale</h3>
  <a class="card__link" href="/sale">Shop now</a>
</article>

    css.card { border: 1px solid #ddd; border-radius: 8px; padding: 16px; }
.card__title { font-size: 1.25rem; margin: 0 0 8px; }
.card__link { color: #2563eb; }
.card--featured { border-color: #f59e0b; }
    💡
    Do not chain elements: write .card__title, never .card__body__title. The element belongs to the block, not to another element.

    BEM still relies on people choosing unique block names. CSS Modules and CSS-in-JS solve the same problem automatically by generating unique class names, which is one reason they became popular.

    🎨 Design tokens

    A design token is a named design decision: a colour, a font size, a spacing step, a radius, a shadow, a duration. Instead of writing #2563eb in 40 places, you write a name such as color-primary once and reference it everywhere.

    TierExamplePurpose
    Primitive (global)blue-600: #2563ebThe raw palette and scales
    Semantic (alias)color-primary: {blue-600}Meaning, not value. Theming swaps these.
    Componentbutton-bg: {color-primary}Optional. Ties a component to semantic tokens.
    css:root {
  --blue-600: #2563eb;
  --color-primary: var(--blue-600);
  --space-2: 0.5rem;
  --radius-md: 8px;
}
.button {
  background: var(--color-primary);
  padding: var(--space-2) calc(var(--space-2) * 2);
  border-radius: var(--radius-md);
}

    Every tool in this course has a home for tokens: CSS custom properties, Sass variables and maps, Tailwind's @theme, and theme objects in CSS-in-JS. Tools such as Style Dictionary take one token source (often JSON) and generate all of these formats.

    ✅
    Tokens are what make a redesign cheap. Change --color-primary once and every button, link and badge follows.

    📘 Key terms

    CascadeThe algorithm that decides which rule wins when several set the same property.
    SpecificityA score based on IDs, classes and type selectors used to rank competing rules.
    Global scopePlain CSS selectors can match any element on the page.
    PreprocessorA language such as Sass that compiles to CSS and adds variables, mixins and loops.
    Utility classA class that does one thing, e.g. p-4 sets padding.
    Scoped stylesStyles that only apply to one component, usually by generating unique class names.
    CSS-in-JSWriting styles inside JavaScript or TypeScript files.
    Zero-runtimeStyles are extracted to static CSS at build time; no styling library runs in the browser.

    BEMBlock__Element--Modifier naming convention for flat, predictable class names.

    Tailwind CSS

    Utility-first styling with Tailwind v4: setup, core utilities, responsive and state variants, dark mode, theming and keeping class lists tidy.

    🧱 The utility-first idea

    Traditional CSS asks you to invent a class name (.profile-card), then write its rules in a separate file. Utility-first flips this. You build the design directly in the markup by combining small classes that each do one thing.

    html<div class="flex items-center gap-4 rounded-xl bg-white p-6 shadow-md">
  <img class="size-12 rounded-full" src="/avatar.png" alt="">
  <div>
    <p class="text-lg font-semibold text-gray-900">Asha Rao</p>
    <p class="text-sm text-gray-500">Frontend Developer</p>
  </div>
</div>
    ClassCSS it produces (roughly)
    flexdisplay: flex;
    items-centeralign-items: center;
    gap-4gap: calc(var(--spacing) * 4); → 1rem by default
    p-6padding: calc(var(--spacing) * 6); → 1.5rem
    rounded-xlborder-radius: var(--radius-xl);
    text-gray-500color: var(--color-gray-500);
    🚫
    No naming
    You stop inventing class names like .inner-wrapper-2.
    📦
    CSS stops growing
    Utilities are reused, so the CSS file stays small as the app grows.
    🔒
    Safe changes
    Editing a class list only affects that element. Nothing global breaks.
    📏
    Built-in design system
    Spacing, colours and font sizes come from a shared scale, so the UI stays consistent.
    📝
    Tailwind only generates CSS for classes it finds in your source files. A huge library of possible utilities becomes a small CSS file in production.

    📱 Responsive design: mobile-first prefixes

    Tailwind is mobile-first. A class with no prefix applies at every screen size. A prefix such as md: means from this width and up. You style the phone layout first, then add overrides for bigger screens.

    PrefixMinimum widthCSS

    🖱️ State variants: hover, focus, group and peer

    Variants are prefixes that apply a utility only in a certain state. They stack, so md:hover:bg-blue-700 means “on medium screens and up, when hovered”.

    🌙 Dark mode

    Add dark: to any utility to apply it in dark mode. By default in v4 the dark: variant follows the operating system setting through prefers-color-scheme.

    html<div class="bg-white text-gray-900 dark:bg-gray-900 dark:text-gray-100">
  Adapts to the user's system theme.
</div>

    If you want a manual theme toggle, override the variant so it follows a .dark class on a parent (usually <html>):

    css@import "tailwindcss";
@custom-variant dark (&:where(.dark, .dark *));

    typescript// Toggle the class and remember the choice
document.documentElement.classList.toggle("dark");
localStorage.theme = document.documentElement.classList.contains("dark") ? "dark" : "light";
    💡
    A cleaner long-term pattern is to put semantic colours in theme variables (for example --color-surface) and swap their values for dark mode. Then you write bg-surface once instead of bg-white dark:bg-gray-900 everywhere.

    When you need a value that is not on the scale, use square brackets. Use them sparingly — each one is a value outside your design system.

    🧹 @apply, components and tidy class lists

    @apply copies utility declarations into your own CSS rule. It is useful for styling HTML you do not control (CMS output, third-party widgets) or very small, repeated pieces.

    css.prose-link {
  @apply font-medium text-brand-700 underline underline-offset-2 hover:text-brand-500;
}
    ⚠️
    Do not use @apply to recreate a whole CSS framework (.btn, .card, .header…). You lose the benefits of utilities and get naming problems back. In v4, a separate CSS file (CSS Module, Vue or Svelte style block) must add @reference "../app.css"; before @apply can see your theme.

    The preferred way to avoid repetition is to extract a component in your framework. The class list lives in one place and is reused through props.

    jsximport { clsx } from "clsx";
import { twMerge } from "tailwind-merge";

// cn(): conditional classes + conflict resolution (popularised by shadcn/ui)
export function cn(...inputs) {
  return twMerge(clsx(inputs));
}

export function Button({ variant = "primary", className, ...props }) {
  return (
    <button
      className={cn(
        "rounded-md px-4 py-2 font-medium focus-visible:ring-2 disabled:opacity-50",
        variant === "primary" && "bg-brand-500 text-white hover:bg-brand-700",
        variant === "ghost" && "bg-transparent text-brand-700 hover:bg-brand-500/10",
        className
      )}
      {...props}
    />
  );
}

// <Button className="px-8" /> → twMerge removes px-4, keeps px-8
    ToolJob
    clsxJoins class names and drops falsy values: clsx("a", false && "b") → "a"
    tailwind-mergeRemoves conflicting Tailwind classes so the last one wins: twMerge("p-2 p-4") → "p-4"
    prettier-plugin-tailwindcssSorts classes into a consistent recommended order on save
    class-variance-authority (cva)Declares variants (size, intent) as a typed config object
    ⚠️
    Never build class names from pieces such as `bg-${color}-500`. Tailwind scans source text for complete class names, so the generated name will not exist in the CSS. Map props to full class strings instead.

    Pros and cons of Tailwind

    Strengths

    • Very fast to build UI once you know the names.
    • Small production CSS; it grows slowly as the app grows.
    • Design-system constraints (spacing and colour scales) by default.
    • Styles live next to markup, so deleting a component deletes its styles.
    • Zero runtime and works with React Server Components.

    Weaknesses

    • Long class lists can be hard to read in markup.
    • A learning curve for the class vocabulary.
    • Dynamic class names must be full strings.
    • Complex animations and rare selectors are clumsy as utilities.
    • Markup is tied to Tailwind, so leaving it later is a big change.
    💡
    Most readability complaints disappear when you extract components and let Prettier sort the classes.

    Sass and SCSS

    The most widely used CSS preprocessor: variables, nesting, the module system, mixins, functions, loops and how to organise a large Sass codebase.

    🧭 What Sass is and its two syntaxes

    Sass is a language that compiles to CSS. It adds features CSS lacked for years: variables, nesting, reusable mixins, functions, loops and a module system. The browser never sees Sass; a compiler turns it into a normal .css file.

    Sass has two syntaxes. Almost every project today uses SCSS, because any valid CSS file is already valid SCSS.

    SCSS (.scss)

    scss$primary: #2563eb;

.button {
  color: white;
  background: $primary;
  &:hover { opacity: 0.9; }
}

    Indented syntax (.sass)

    scss$primary: #2563eb

.button
  color: white
  background: $primary
  &:hover
    opacity: 0.9
    ImplementationStatusNotes
    Dart Sass (npm package sass or sass-embedded)Primary, actively developedThe reference implementation. Gets new features first.
    LibSass / node-sassDeprecatedC++ implementation. No module system, no new features. Migrate away.
    Ruby SassEnd of lifeThe original implementation. Retired years ago.
    📝
    When people say “Sass” today they nearly always mean the SCSS syntax compiled with Dart Sass.

    🔤 Variables and nesting

    Sass variables start with $. They exist only at compile time; in the output CSS they are replaced by their values.

    scss$font-stack: system-ui, sans-serif;
$space: 8px;
$radius: 6px !default;   // can be overridden by whoever loads this file

.card {
  font-family: $font-stack;
  padding: $space * 2;
  border-radius: $radius;
}

    Nesting lets child rules sit inside the parent. The & character means “the parent selector”. In Sass it can also join text, which is perfect for BEM.

    scss.card {
  padding: 16px;

  &:hover { box-shadow: 0 2px 8px rgb(0 0 0 / 0.1); }  // .card:hover
  &__title { font-size: 1.25rem; }                      // .card__title
  &--featured { border-color: gold; }                    // .card--featured
  .theme-dark & { background: #111; }                    // .theme-dark .card

  @media (width >= 768px) { padding: 24px; }            // media query bubbles up
}
    ⚠️
    Keep nesting shallow (about 3 levels max). Deep nesting creates long, high-specificity selectors such as .page .main .list .item a span that are slow to override — the same specificity war Sass was meant to help with.

    📦 Partials, @use and @forward (the module system)

    A partial is a Sass file whose name starts with an underscore, such as _variables.scss. It is not compiled on its own; other files load it. You load modules with @use.

    scss// _tokens.scss
$primary: #2563eb !default;
$radius: 6px;
$-internal: 42px;   // a leading - or _ makes a member private to this module

// button.scss
@use "tokens";                  // namespace = last part of the URL
.button {
  background: tokens.$primary;
  border-radius: tokens.$radius;
}

// other ways to load
@use "tokens" as t;             // custom namespace: t.$primary
@use "tokens" as *;             // no namespace: $primary (use with care)
@use "tokens" with ($primary: #7c3aed);  // configure !default variables

    @forward re-exports another module's members, so you can build one entry point for a folder.

    scss// abstracts/_index.scss
@forward "tokens";
@forward "mixins";
@forward "functions";

// anywhere else
@use "abstracts";   // loads abstracts/_index.scss
.x { color: abstracts.$primary; }

    Built-in functions also moved into modules. Prefer @use "sass:math";, "sass:color", "sass:map" and "sass:string" over old global names such as map-get() or darken(). The official sass-migrator tool can convert a codebase automatically.

    🧩 Mixins and functions

    A mixin is a reusable block of declarations. Define it with @mixin and use it with @include. Mixins can take arguments, defaults and a content block.

    scss@mixin focus-ring($color: #2563eb, $width: 2px) {

    A map is a set of key–value pairs. Combined with @each it generates many related rules from one source of truth.

    Math: why slash division changed

    In CSS, / is often a separator, not division: font: 16px/1.5 serif, grid-area: 1 / 2 / 3, aspect-ratio: 16 / 9. Sass used to treat / as division in some places, which was confusing. Dart Sass deprecated slash-as-division; use math.div().

    scss@use "sass:math";

$gutter: 24px;

.col {
  padding: math.div($gutter, 2);        // 12px
  width: math.percentage(math.div(1, 3)); // 33.3333333333%
}

// Deprecated:  padding: $gutter / 2;

    The sass:math module also has math.round(), math.floor(), math.clamp(), math.max(), math.$pi and more. Remember that native CSS can do some maths at run time with calc(), min(), max() and clamp() — and those can mix units and read CSS variables, which Sass cannot.

    CSS Modules

    Write ordinary CSS and let the build tool make every class name unique to its file — scoped styles with zero runtime.

    🔐 How CSS Modules scope your styles

    A CSS Module is a CSS file in which every class name is local by default. At build time the tool renames each class to something unique, such as Button_primary__x7Gk2, and gives your JavaScript an object that maps the original name to the generated one.

    You write .primary; the browser sees a unique, file-specific class name

    What you write

    css/* Button.module.css */
.primary {
  background: #2563eb;
  color: white;
}

    What the browser gets (example)

    css.Button_primary__x7Gk2 {
  background: #2563eb;
  color: white;
}

    The exact format of the generated name depends on the tool and its settings (Next.js, Vite and webpack all differ, and production builds are often shorter). What matters is that two files can both define .primary and never clash.

    📝
    CSS Modules is not a library you call at run time. It is a build-time convention supported by Vite, Next.js, webpack (css-loader), Parcel and others. The output is a normal CSS file.

    📥 Naming and importing in React, Next.js and Vite

    The file name must end in .module.css (or .module.scss). That suffix is what tells the bundler to treat it as a module. A plain Button.css stays global.

    jsx// Button.jsx
import styles from "./Button.module.css";

export function Button({ children }) {
  return <button className={styles.primary}>{children}</button>;
}
    FrameworkSetup neededNotes
    ViteNone — built inOptions under css.modules in vite.config (naming pattern, case convention).
    Next.jsNone — built inGlobal CSS is imported in the root layout (App Router); CSS Modules can be imported in any component, including Server Components.
    webpackcss-loader with modules enabledMost templates already enable it for *.module.css.
    💡
    Name the module after the component (Card.jsx + Card.module.css) and keep them in the same folder. Deleting the component folder deletes its styles too — no dead CSS left behind.

    🐫 Accessing class names: kebab-case vs camelCase

    Class names become keys of the styles object. A name like .primary is easy: styles.primary. A kebab-case name such as .is-active is not a valid JavaScript identifier, so you need bracket notation.

    jsximport styles from "./Tabs.module.css";

<li className={styles["is-active"]}>Home</li>   // always works
<li className={styles.isActive}>Home</li>       // only if camelCase conversion is on

    typescript// vite.config.ts — expose camelCase keys
export default defineConfig({
  css: {
    modules: {
      localsConvention: "camelCaseOnly",  // .is-active → styles.isActive
    },
  },
});
    💡
    The simplest rule for a team: write class names in camelCase inside module files (.isActive). Then dot access works everywhere with no configuration.
    ⚠️
    A missing key returns undefined silently, so a typo like styles.prmary just renders class="undefined" or no class at all. TypeScript typing (below) catches this.

    🧬 composes, :global and :local

    composes lets one class reuse another class. Instead of copying declarations, the module exports both class names, so the element gets both.

    css/* Button.module.css */
.base {
  padding: 8px 16px;
  border-radius: 6px;
  font-weight: 600;
}

.primary {
  composes: base;
  background: #2563eb;
  color: white;
}

.danger {
  composes: base;
  background: #dc2626;
  color: white;
}

.link {
  composes: focusRing from "./shared.module.css";  /* from another file */
  color: #2563eb;
}

    Now styles.primary is a string with two generated classes, such as "Button_primary__a1 Button_base__b2".

    Sometimes you must target a class you do not control — a library class, or a theme class on <html>. Wrap it in :global() so it is not renamed.

    css/* .card is hashed; .dark is left exactly as written */
:global(.dark) .card {
  background: #111827;
}

/* style third-party markup inside your scoped wrapper */
.editor :global(.ql-toolbar) {
  border: none;
}

    .nameLocal (the default in a module) — will be renamed
    :global(.name)Global — kept exactly as written
    :local(.name)Explicitly local — mainly useful inside a :global block or in global-mode files
    ⚠️
    composes only works with single class selectors, and composing from several files can make the final CSS order unpredictable. Keep it for simple, shared base classes.

    🎛️ Dynamic classes, Sass and theming

    For conditional classes, combine module keys with clsx (or the older classnames package).

    🟦 Typing CSS Modules in TypeScript

    TypeScript does not understand CSS imports by default. Vite's client types (/// <reference types="vite/client" />) and Next.js's generated types already declare *.module.css as a string map. Otherwise, add a declaration file yourself:

    typescript// src/types/css-modules.d.ts
declare module "*.module.css" {
  const classes: { readonly [key: string]: string };
  export default classes;
}
declare module "*.module.scss" {
  const classes: { readonly [key: string]: string };
  export default classes;
}

    That generic type accepts any key, so typos still compile. For exact keys, generate a .d.ts per module with a tool such as typed-css-modules, or use the typescript-plugin-css-modules editor plugin for autocomplete.

    typescript// Button.module.css.d.ts (generated)
declare const styles: {
  readonly base: string;
  readonly primary: string;
  readonly danger: string;
};
export default styles;

    CSS-in-JS

    Styles written in JavaScript: runtime libraries like styled-components and Emotion, their costs, and the zero-runtime tools that replaced them in many new projects.

    🧭 What CSS-in-JS means

    CSS-in-JS means writing styles inside JavaScript or TypeScript files, usually right next to the component. The library generates unique class names (so styles are scoped) and can use JavaScript values — props, state, a theme object — inside the styles.

    FamilyWhen CSS is createdExamples
    RuntimeIn the browser (and on the server during SSR) while components render. A JS library serialises styles and injects <style> tags.styled-components, Emotion
    Zero-runtime / build-timeAt build time. A compiler or bundler plugin extracts static .css files.vanilla-extract, Linaria, Panda CSS, StyleX
    Runtime CSS-in-JS does this work in the browser on every new style combination
    📝
    CSS-in-JS became popular around 2016–2020 with React because it solved scoping, dead code and dynamic styling in one go. Its runtime cost and poor fit with React Server Components have since pushed many teams towards build-time options.

    💅 styled-components: tagged templates and props

    styled-components uses tagged template literals. styled.button`...` returns a React component that renders a <button> with a generated class.

    jsximport styled, { css } from "styled-components";

const Button = styled.button`
  padding: 8px 16px;
  border: 0;
  border-radius: 6px;
  background: #e5e7eb;
  color: #111827;

  &:hover { filter: brightness(0.95); }

  ${(props) =>
    props.$primary &&
    css`
      background: #2563eb;
      color: white;
    `}

  @media (width >= 768px) { padding: 10px 20px; }
`;

// Extend an existing styled component
const DangerButton = styled(Button)`
  background: #dc2626;
  color: white;
`;

export function Toolbar() {
  return (
    <>
      <Button>Cancel</Button>
      <Button $primary>Save</Button>
      <DangerButton>Delete</DangerButton>
    </>
  );
}
    💡
    Prefix style-only props with $ ($primary). These transient props are used for styling but not passed to the DOM, avoiding React warnings like “unknown prop on button”. styled-components v6 no longer filters props automatically, so this matters more.

    Each unique combination of prop values produces a new class name, so a prop that takes many values (for example a pixel width from a slider) can generate thousands of classes. Use a CSS variable or the .attrs() helper with an inline style for such values.

    🎨 Theming with ThemeProvider and Emotion's css prop

    Both styled-components and Emotion provide a ThemeProvider. It puts a theme object into React context, and every styled component can read it.

    jsximport styled, { ThemeProvider } from "styled-components";

const light = { colors: { bg: "#ffffff", text: "#111827", primary: "#2563eb" }, radius: "8px" };
const dark  = { ...light, colors: { bg: "#0f172a", text: "#e5e7eb", primary: "#60a5fa" } };

const Card = styled.div`
  background: ${({ theme }) => theme.colors.bg};
  color: ${({ theme }) => theme.colors.text};
  border-radius: ${({ theme }) => theme.radius};
`;

export function App({ isDark }) {
  return (
    <ThemeProvider theme={isDark ? dark : light}>
      <Card>Hello</Card>
    </ThemeProvider>
  );
}

    Emotion offers a similar styled API (@emotion/styled) and also a css prop that styles any element directly.

    jsx/** @jsxImportSource @emotion/react */
import { css } from "@emotion/react";

const badge = css`
  display: inline-block;
  padding: 2px 8px;
  border-radius: 999px;
  font-size: 12px;
`;

export function Badge({ tone = "#16a34a", children }) {
  return <span css={[badge, { background: tone, color: "white" }]}>{children}</span>;
}
    📝
    The css prop needs Emotion's JSX runtime: the @jsxImportSource pragma shown above, or the jsxImportSource option set in your Babel/TypeScript/SWC config.
    💡
    Switching a theme object re-renders every component that reads it. For large apps, map the theme to CSS variables once at the root and reference var(--color-bg) in styles; switching themes then only changes a few variables.

    ✍️ Inline style objects vs CSS-in-JS

    ✅

    🧠 When CSS-in-JS still makes sense

    🏛️

    A large app already on styled-components or Emotion should not be rewritten just because of trends. Migrate gradually, starting with performance-critical or server-rendered pages.
    📚
    Component libraries
    MUI uses Emotion by default and Chakra UI also relies on Emotion. If you adopt one of these libraries, you work with its styling engine.
    🧪
    Highly dynamic UIs
    Editors and design tools that compute many styles from user input sometimes prefer a runtime approach, accepting the cost.
    🆕
    New projects
    Prefer zero-runtime tools, Tailwind or CSS Modules, especially with Next.js App Router and Server Components.

    🧭 Fundamentals

    What problems do styling tools solve that plain CSS struggles with at scale?

    Plain CSS is global: any selector can match anything, so names collide and changes have unexpected side effects. Teams escalate specificity to win conflicts, which leads to !important chains. Dead CSS piles up because nobody knows what is safe to delete, and values like colours are duplicated. Tools address this with conventions (BEM), scoping (CSS Modules, CSS-in-JS), constraints (Tailwind scales, tokens) and abstraction (Sass variables and mixins).

    Explain specificity and how you keep it under control.

    Specificity ranks selectors by (IDs, classes/attributes/pseudo-classes, element types). Higher wins; ties go to the later rule. I keep it flat: single class selectors, no IDs for styling, shallow Sass nesting, :where() for zero-specificity defaults, and cascade layers to order groups such as reset, base, components and utilities. Then !important is almost never needed.

    What is BEM and is it still relevant?

    Block__Element--Modifier is a naming convention that gives every element a flat, unique-looking class: .card, .card__title, .card--featured. It keeps specificity equal and shows structure in the name. It is still relevant for global CSS and Sass codebases; with CSS Modules or CSS-in-JS the tool provides uniqueness, so BEM matters less, though its element/modifier thinking still helps.

    What are design tokens and why do they matter?

    Tokens are named design decisions — colour, spacing, type scale, radius, shadow, motion. They give one source of truth shared between design and code, make theming and rebrands a matter of changing values, and keep the UI consistent. Usually there is a primitive tier (blue-600) and a semantic tier (color-primary); components use semantic tokens so themes can remap them.

    How do styles get from source code to the browser?

    Source (SCSS, utilities, modules, JS styles) is compiled to CSS — Sass compiles, Tailwind generates used utilities, CSS Modules hash class names, zero-runtime tools extract CSS. The bundler combines and splits it per route, a minifier compresses it, and the result is written as hashed, cacheable CSS files linked in the HTML. Runtime CSS-in-JS is the exception: it generates and injects style tags with JavaScript while rendering.

    🌬️ Tailwind CSS

    What does “utility-first” mean, and what are its trade-offs?

    You compose small single-purpose classes in the markup instead of writing custom classes. Benefits: no naming, CSS size stays small, consistent design scales, styles are co-located and safe to change. Trade-offs: long class lists, learning the vocabulary, dynamic class names must be complete strings, and markup is coupled to Tailwind. Components and class sorting address readability.

    What changed in Tailwind v4 compared with v3?

    Configuration moved into CSS: @import "tailwindcss"; replaces the three @tailwind directives, and @theme defines tokens instead of tailwind.config.js (which can still be loaded with @config). Content detection is automatic. Theme values are exposed as CSS variables. There are new directives such as @utility, @custom-variant, @source and @reference, first-party Vite and PostCSS plugins, and built-in container queries.

    How is responsive design done in Tailwind?

    It is mobile-first. Unprefixed utilities apply at all widths; breakpoint prefixes like md: apply from that min-width up. So flex-col md:flex-row stacks on phones and goes horizontal from 768px. For ranges you can stack md:max-lg:. Container query variants like @md: respond to a parent marked @container.

    When would you use @apply, and when not?

    Use it for markup you cannot add classes to (CMS or markdown output, third-party widgets) or for tiny repeated patterns. Avoid using it to rebuild a component class library — that reintroduces naming, global CSS and specificity issues. Prefer extracting a framework component that holds the class list. In v4, separate style files need @reference to the main stylesheet before @apply can use theme values.

    Why do you need tailwind-merge if you already use clsx?

    clsx only joins strings and drops falsy values. If a component has px-4 and a caller passes px-8, both end up in the class list, and which wins depends on the order in the generated CSS, not in the attribute. tailwind-merge understands Tailwind's groups and removes the earlier conflicting class, so the override reliably wins. The common cn() helper combines both.

    🎀 Sass

    What is the difference between @use and @import?

    @import puts everything into one global namespace and re-evaluates the file each time it is imported, causing name clashes and duplicate CSS. @use loads each module once, namespaces its members (tokens.$primary), supports private members with - or _ prefixes, and allows configuration with with (...). @import is deprecated (Dart Sass 1.80) and planned for removal in Dart Sass 3.

    Mixin, function or @extend — how do you choose?

    A function returns a value (unit conversion, colour maths). A mixin outputs declarations and can take arguments and a content block (media query helpers, focus styles). @extend shares a rule by grouping selectors, but it cannot cross media queries, can generate surprising selector combinations and changes where styles appear in the output, so I prefer mixins or placeholder-only extends in limited cases.

    Why did Sass change slash division?

    In CSS, / is a separator in properties such as font, grid-area and aspect-ratio. Treating it as division was ambiguous. Dart Sass deprecated slash-as-division; you now use math.div() from the sass:math module, and / is kept as a separator.

    Is Sass still worth using now that CSS has variables and nesting?

    Often yes, but for fewer reasons. Native custom properties are better for anything runtime (themes), and native nesting covers simple cases. Sass still adds mixins, functions, loops, maps, modules, and &-suffix concatenation for BEM. A good modern setup uses Sass for authoring and outputs CSS custom properties for tokens. For small projects plain modern CSS may be enough.

    How do you structure a large Sass codebase?

    A common choice is the 7-1 pattern: abstracts, vendors, base, layout, components, pages, themes plus one main.scss. Abstracts output no CSS and are exposed through an _index.scss with @forward. In component apps, I keep only shared abstracts globally and put component styles in .module.scss files next to components. Stylelint enforces nesting depth and bans IDs.

    🔐 CSS Modules

    How do CSS Modules achieve scoping?

    At build time, every class in a .module.css file is renamed to a unique name (often based on file name, class name and a hash). The import returns an object mapping original names to generated names, which you put in className. There is no runtime; the output is ordinary CSS, so it works with Server Components and caching.

    What do composes, :global and :local do?

    composes makes a class also export another class's name (from the same file or another module), so elements get both — reuse without copying declarations. :global(.x) stops a selector from being renamed, used for theme classes on <html> or third-party markup. :local switches back to local renaming, which is the default in module files.

    How do you type CSS Modules in TypeScript?

    Vite and Next.js ship ambient declarations that type a module as { readonly [key: string]: string }, or you add a declare module "*.module.css" file. That allows any key, so typos compile. For exact keys, generate per-file .d.ts files with typed-css-modules or use typescript-plugin-css-modules for editor checks.

    How do you handle dynamic styles and theming with CSS Modules?

    For a finite set of states, conditionally apply module classes with clsx (styles[variant]). For continuous values, pass a CSS variable through the style prop and read it in the module. For theming, define semantic custom properties globally and switch them with a data-theme attribute; module classes only read var(--token).

    What are common CSS Modules mistakes?

    Forgetting the .module suffix so styles become global; writing element-only selectors that are still global; overusing :global until scoping is meaningless; relying on cross-file composes ordering; styling a child component's internals from the parent instead of passing className; and using kebab-case names then accessing them with dot notation.

    💅 CSS-in-JS

    Explain how runtime CSS-in-JS works.

    Libraries like styled-components and Emotion run during render. They evaluate the template or object with current props and theme, serialise it to a CSS string, hash it to a class name, insert the rule into a style tag if it is new, and return the class to the element. On the server they collect the styles and inline them in the HTML so the page is not unstyled before hydration.

    What are the downsides of runtime CSS-in-JS?

    Extra JavaScript (the library), CPU work during renders, more complex SSR setup, styles bundled in JS instead of cacheable CSS files, and incompatibility with React Server Components — styled components need "use client". Highly variable props can also generate many classes. Additionally, styled-components announced maintenance mode in 2025, which affects long-term choices.

    What are transient props in styled-components?

    Props prefixed with $, such as $primary. They are available inside the style interpolations but are not passed to the underlying DOM element, avoiding invalid-attribute warnings. In v6 this matters more because props are no longer filtered automatically; alternatively use shouldForwardProp.

    Compare vanilla-extract, Linaria, Panda CSS and StyleX.

    All are build-time with no styling runtime. vanilla-extract uses TypeScript style objects in .css.ts files and themes as CSS variables — strongly typed. Linaria keeps a styled-components-like tagged-template API and turns dynamic props into CSS variables. Panda CSS generates atomic CSS from css() calls and recipes with a token system. StyleX, from Meta, compiles stylex.create objects to atomic CSS with predictable merging.

    Inline styles vs CSS-in-JS — what is the difference?

    The style prop writes declarations straight onto the element: no pseudo-classes, no media queries, very high specificity, no reuse. CSS-in-JS generates real class-based CSS, so it supports all selectors and queries. Inline style is still the right tool for a single dynamic value, ideally passed as a CSS variable.

    🏗️ Architecture and scenarios

    You are starting a new Next.js App Router app. Which styling approach would you pick and why?

    I would pick Tailwind v4 or CSS Modules (possibly with SCSS), both zero-runtime and fully compatible with Server Components. Tailwind if the team values speed and strict design scales; CSS Modules if they prefer writing CSS. Either way tokens live as CSS variables, and theming uses a data-theme attribute set before first paint. I would avoid adopting new runtime CSS-in-JS.

    The CSS bundle is 600 KB. How do you reduce it?

    Measure first with DevTools Coverage and bundle analysis. Remove dead rules and unused vendor CSS, replace big frameworks imported whole, split CSS per route (modules), dedupe Sass @import duplication by moving to @use, check @extend selector explosion, minify with Lightning CSS and serve Brotli. Consider critical CSS for the landing page. Add a size budget in CI so it does not grow back.

    How would you implement dark mode in a design system used by several apps?

    Define semantic tokens (--color-surface, --color-text) as CSS variables. Provide light values on :root and dark values under prefers-color-scheme and a [data-theme="dark"] override. Components only reference semantic tokens, whatever tool they use. Set color-scheme, check contrast for both themes, and apply the stored preference before paint to avoid a flash.

    How would you migrate a large styled-components codebase?

    Incrementally. First convert the theme to CSS variables so old and new code share tokens. Pick the target (Tailwind, CSS Modules or a zero-runtime library such as Linaria with a similar API). Write new components in the target, then migrate leaf components and the pages that benefit most (server-rendered, performance-critical). Use visual regression tests, track progress, and remove the library and registry when nothing imports it.

    How do you make styling accessible by default?

    Bake it into tokens and base components: visible :focus-visible styles everywhere, never removing outlines without replacement; contrast-checked token pairs (4.5:1 text, 3:1 UI); prefers-reduced-motion handling; adequate touch target sizes; respecting user font size with rem units; and a screen-reader-only utility. Lint for these and include them in component reviews.

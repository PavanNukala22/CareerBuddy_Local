    What is a Distributed System?

    Start from zero: what distributed systems are, their types and why they are hard.

    🧭 What is a Distributed System?

    A distributed system is a group of independent computers (nodes) that cooperate over a network and appear to users as one system.

    🔴 Single machine

    Simple, but limited by one machine's capacity and a single point of failure.

    🟢 Distributed

    Scales out and survives failures, but adds network, consistency and coordination problems.

    🗂️ Types of Distributed Systems

    TypeIdeaExample
    Client–serverClients call central serversWeb apps, APIs
    Peer-to-peerNodes are equalsBitTorrent, blockchain
    MicroservicesMany small services over RPC/eventsE-commerce platforms
    Distributed data storesData partitioned and replicatedCassandra, DynamoDB, Spanner
    Stream / batch processingParallel data pipelinesKafka, Spark, Flink

    ⚠️ Why It Is Hard: The 8 Fallacies

    • The network is reliable.
    • Latency is zero.
    • Bandwidth is infinite.
    • The network is secure.
    • Topology never changes.
    • There is one administrator.
    • Transport cost is zero.
    • The network is homogeneous.
    ⚠️
    Partial failure is the core difficulty: some parts fail while others keep running, and you often cannot tell which.

    📖 Key Terms

    NodeOne machine or process in the system.
    LatencyTime for a request to complete.
    ThroughputWork completed per unit time.
    ReplicationKeeping copies of data on several nodes.
    Partition (shard)A slice of data held by one node group.
    Network partitionNodes cannot reach each other.

    RPCs & Service Communication

    What an RPC is, its types, and how to make calls safe.

    📞 What is an RPC?

    A Remote Procedure Call lets code call a function on another machine as if it were local. A client stub serialises arguments, sends them, and a server skeleton runs the function and returns the result.

    StyleFormatStrengths
    REST/HTTPJSON over HTTPSimple, universal, cacheable
    gRPCProtobuf over HTTP/2Fast, typed contracts, streaming
    GraphQLQuery languageClient chooses fields
    Thrift / JSON-RPCBinary / JSONCross-language RPC

    📄 Example: gRPC Contract

    protobufservice Orders {
  rpc Create (CreateReq) returns (CreateRes);
  rpc Watch  (WatchReq)  returns (stream Event);  // server streaming
}
message CreateReq { string request_id = 1; string item = 2; int32 qty = 3; }

    🔁 Timeouts, Retries & Idempotency

    • Always set a deadline/timeout; no call may wait forever.
    • Retry with exponential backoff + jitter to avoid retry storms.
    • Make writes idempotent with a request ID so a retry is safe.
    pythonimport random, time
def call_with_retry(fn, tries=5, base=0.1):
    for n in range(tries):
        try:
            return fn(timeout=2)
        except TimeoutError:
            if n == tries - 1: raise
            time.sleep(base * 2**n + random.random() * base)
    💡
    Delivery guarantees: at-most-once (may lose), at-least-once (may duplicate), exactly-once (effect once, via idempotency).

    Module 03 · Messaging

    Messaging Queues & Event Streams

    Decouple services with asynchronous messages.

    📬 What and Why

    A message queue stores messages between a producer and a consumer so they work independently, absorb spikes and survive each other's downtime.

    ModelHowExamples
    Point-to-point queueEach message goes to one consumerSQS, RabbitMQ
    Publish/subscribeEach subscriber gets a copySNS, Google Pub/Sub
    Log / streamOrdered, replayable partitioned logKafka, Pulsar, Kinesis

    🧩 Key Concepts

    PartitionOrdered sub-log; ordering guaranteed only within one.
    Consumer groupConsumers sharing partitions to scale reads.
    Offset / ackPosition or confirmation that a message was processed.
    Dead-letter queueHolds messages that keep failing.
    BackpressureSlowing producers when consumers lag.

    🧪 Example: Idempotent Consumer

    pythondef handle(msg):
    if db.exists("processed", msg.id):    # duplicate delivery?
        return ack(msg)
    with db.transaction():
        apply_business_logic(msg)
        db.insert("processed", msg.id)
    ack(msg)                              # ack AFTER commit
    ✅
    At-least-once delivery + idempotent consumer = effectively exactly-once.

    🔌 Circuit Breaker

    States: Closed (normal) → Open (fail fast after repeated errors) → Half-open (probe) → Closed.

    gotype Breaker struct{ fails, limit int; openUntil time.Time }
func (b *Breaker) Call(fn func() error) error {
    if time.Now().Before(b.openUntil) { return ErrOpen }
    if err := fn(); err != nil {
        if b.fails++; b.fails >= b.limit { b.openUntil = time.Now().Add(10*time.Second) }
        return err
    }
    b.fails = 0
    return nil
}

    ⚖️ CAP, Consistency & Replication

    ConceptMeaning

    Strong consistencyReads see the latest write (e.g. Spanner)
    Eventual consistencyReplicas converge over time (e.g. DynamoDB default)
    Leader–followerOne writer, many readers
    Multi-leader / leaderlessWrites on many nodes; conflicts resolved by quorum or CRDTs
    📝
    Quorum rule: with N replicas, choose W and R such that W + R > N for read-your-writes.

    Module 05 · Consensus

    Distributed Consensus: Paxos & Raft

    How nodes agree on one value despite failures.

    🤝 What is Consensus?

    Consensus lets a cluster agree on a single value or log order even if some nodes crash. It underpins leader election, locks, config stores and replicated databases (etcd, ZooKeeper, Consul, Spanner).

    ⚠️
    FLP result: in a fully asynchronous network, no algorithm can guarantee consensus if even one node may fail. Real systems use timeouts to make progress.

    🚣 Raft in Brief

    PartRole
    Leader electionRandomised timeouts; a candidate needs a majority of votes in a new term
    Log replicationLeader appends entries; commits when a majority stores them
    SafetyOnly a node with an up-to-date log can win
    Cluster size2f+1 nodes tolerate f failures (3 → 1, 5 → 2)
    textTerm 3: A (leader) --append(x)--> B, C
        B ack, C ack  => majority (2 of 3) => commit x
A crashes -> B times out -> B requests votes (term 4) -> C votes -> B leader

    🧭 Paxos vs Raft & Other Tools

    PaxosRaft
    GoalAgree on a valueReplicated log
    ClarityNotoriously subtleDesigned to be understandable
    Used byChubby, Spanner (Multi-Paxos)etcd, Consul, CockroachDB
    • Two-phase commit: atomic multi-node transactions, but blocks if the coordinator fails.
    • Sagas: sequence of local transactions with compensating actions.
    • Clocks: use logical/vector clocks or hybrid clocks, not wall-clock time.

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🎤 Core Questions

    Explain CAP.
    During a network partition you can keep consistency or availability, not both. CP systems reject requests; AP systems serve possibly stale data.
    How do you get exactly-once processing?
    At-least-once delivery plus idempotent handlers or transactional writes with deduplication keys.
    Why retry with jitter?
    Without randomness, clients retry in sync and overload a recovering service (retry storm).
    Why odd cluster sizes in Raft?
    A majority quorum is needed; 3 and 4 nodes both tolerate one failure, so the fourth adds cost not tolerance.
    Kafka vs RabbitMQ?
    Kafka: durable partitioned log, replay, huge throughput. RabbitMQ: flexible routing, per-message acks, task queues.
    What is a split brain?
    Two nodes both believe they are leader after a partition; prevented by quorums and fencing tokens.

    🛠️ Scenario

    Checkout calls Inventory and Payment, then emits an OrderPlaced event. Payment is sometimes slow and messages can be duplicated.

    ✍️ Which protections would you add on the Payment call?
    Model answer: Timeout, retries with backoff + jitter, an idempotency key, a circuit breaker and a fallback (e.g. queue the order for later).
    ✍️ How do you keep order creation and event publishing consistent?
    Model answer: Use the transactional outbox pattern: write the order and the event in one DB transaction; a relay publishes the outbox to the queue.

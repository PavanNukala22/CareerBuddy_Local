    What is Operational Excellence?

    Start from zero: running software reliably in production.

    🧭 What is Operational Excellence?

    Operational excellence is the discipline of running services reliably: you can see what the system is doing, test changes automatically, ship safely and fix problems fast.

    🔴 Without it

    Manual deploys, no dashboards, users report outages first, long firefights.

    🟢 With it

    Automated pipelines, alerts on symptoms, fast rollback, blameless learning.

    🏛️ The Four Pillars

    📈
    Metrics
    Measure health and behaviour.
    🧪
    Automated testing
    Catch regressions before users do.
    🚀
    CI/CD
    Build, test and release automatically.
    🔍
    Debugging
    Diagnose production issues quickly.

    📖 Key Terms

    SLIService Level Indicator: a measured number, e.g. success rate.
    SLOObjective for an SLI, e.g. 99.9% over 30 days.
    SLAContract with consequences if the SLO is missed.
    Error budgetAllowed unreliability = 100% − SLO.
    MTTRMean time to recover.
    ObservabilityInferring internal state from logs, metrics, traces.
    💡
    A 99.9% SLO allows about 43 minutes of downtime per 30 days.

    Metrics Instrumentation

    What to measure, metric types and how to instrument code.

    📊 Metric Types

    TypeWhat it isExample
    CounterOnly goes uprequests_total, errors_total
    GaugeGoes up and downqueue_depth, memory_bytes
    HistogramDistribution in bucketsrequest_duration_seconds
    SummaryPre-computed quantilesp50/p99 on the client

    🎯 Frameworks: RED, USE & Golden Signals

    FrameworkSignalsFor
    REDRate, Errors, DurationServices / requests
    USEUtilisation, Saturation, ErrorsResources (CPU, disk)
    Golden signalsLatency, traffic, errors, saturationAny user-facing system

    🧪 Example: Instrumenting a Handler

    pythonfrom prometheus_client import Counter, Histogram
REQS = Counter("http_requests_total", "Requests", ["route", "status"])
LAT  = Histogram("http_request_seconds", "Latency", ["route"])

def handle(route):
    with LAT.labels(route).time():
        try:
            result = work()
            REQS.labels(route, "200").inc()
            return result
        except Exception:
            REQS.labels(route, "500").inc()
            raise
    ⚠️
    Avoid high-cardinality labels (user ID, URL with IDs): they explode storage. Alert on symptoms (error rate, latency), not causes.

    🐳 Example: Real Database in a Test

    pythonimport pytest, psycopg2
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="session")
def db():
    with PostgresContainer("postgres:16") as pg:
        yield psycopg2.connect(pg.get_connection_url())

def test_create_order(db):
    repo = OrderRepo(db)
    oid = repo.create(item="book", qty=2)
    assert repo.get(oid).qty == 2

    🧰 Good Practices

    • Each test creates and cleans its own data; no shared state or ordering.
    • Fake only what you don't own (third-party APIs); use real infra for your own.
    • Fight flaky tests: no sleeps, fixed clocks, retries are a smell.
    • Run on every pull request and block merges on failure.

    🔄 CI vs CD

    TermMeaning
    Continuous IntegrationMerge often; every change is built and tested automatically
    Continuous DeliveryEvery passing build is releasable; deploy is one click
    Continuous DeploymentEvery passing build goes to production automatically

    📄 Example Pipeline (GitHub Actions)

    yamlname: ci
on: [pull_request]
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make lint
      - run: make unit
      - run: make integration
      - run: docker build -t app:${{ github.sha }} .

    🚦 Deployment Strategies

    StrategyHowRisk
    RollingReplace instances graduallyMixed versions briefly
    Blue/greenSwitch traffic between two environmentsDouble capacity
    CanarySend 1–5% traffic first, watch metricsNeeds good metrics
    Feature flagsShip code dark, enable per userFlag debt
    ✅
    Automate rollback on SLO breach: canary + metrics gate is the gold standard.

    Module 05 · Debugging

    Production Debugging & Incidents

    Find and fix problems in live systems safely.

    👁️ Three Pillars of Observability

    📜
    Logs
    Structured events; include request/trace IDs.
    📈
    Metrics
    Spot that something is wrong.
    🧵
    Traces
    Show where time is spent across services (OpenTelemetry).

    🕵️ Debugging Method

    • Stabilise first: roll back, fail over or disable the flag; investigate after.
    • Form a hypothesis from dashboards → trace → logs; narrow by service, version, region.
    • Check what changed: deploys, config, traffic, dependencies.
    • Use safe tools: sampled profiling, pprof, thread dumps, read-only queries.
    bashkubectl logs deploy/orders --since=15m | grep trace_id=abc123
kubectl rollout undo deploy/orders      # stabilise first
go tool pprof http://orders:6060/debug/pprof/profile?seconds=30

    Module 06 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🎤 Core Questions

    SLI vs SLO vs SLA?
    SLI is the measurement, SLO the internal target, SLA the external contract with penalties.
    Counter vs gauge vs histogram?
    Counter only increases; gauge moves both ways; histogram records value distributions for percentiles.
    How do you handle flaky tests?
    Quarantine, find the root cause (timing, shared state, ordering), fix or delete; never ignore.
    Canary vs blue/green?
    Canary shifts a small percentage gradually using metrics; blue/green swaps all traffic between two full environments.
    A service is slow in prod. What do you do?
    Check dashboards for scope, compare with recent deploys, roll back if correlated, then use traces and profiles for root cause.

    🛠️ Scenario

    You own a payments API with a 99.95% availability SLO.

    ✍️ Which metrics and alerts would you set up?
    Model answer: RED metrics per route; SLIs for success rate and p99 latency; alert on error-budget burn rate (fast and slow windows), plus saturation of DB connections.
    ✍️ Describe your CI/CD pipeline.
    Model answer: PR: lint, unit, integration (containers), contract tests. Merge: build image, deploy to staging, smoke test, canary 5% with automated metric gate, then progressive rollout and auto-rollback.

    Module 01 · Foundations

    What is System Design?

    Start from zero: what HLD and LLD are, how they differ, and the framework for approaching any design question.

    🧭 What is system design?

    System design is the process of deciding how the parts of a software system — services, databases, caches, queues, classes — fit together so the system meets its requirements for functionality, scale, reliability and cost.

    🏙️ High-Level Design (HLD)

    The architecture: which services, databases, caches, queues and protocols; how data flows; how it scales and survives failure. Boxes and arrows.

    🔧 Low-Level Design (LLD)

    The code structure of one component: classes, interfaces, relationships, design patterns, method signatures, state and concurrency.

    EXAMPLE · Designing "Uber"
    • HLD: rider app → API gateway → matching service, location service (geo-index), trip service, payment service; Kafka for events; sharded DBs; caches.
    • LLD: classes Rider, Driver, Trip, PricingStrategy, MatchingStrategy, with state transitions of a trip.

    📋 Requirements: functional and non-functional

    TypeQuestionExamples
    FunctionalWhat must the system do?Shorten a URL, redirect, post a tweet, send a message
    Non-functionalHow well must it do it?Latency < 200 ms, 99.99% availability, 10M DAU, durability, security, consistency
    ⚡
    Scalability
    Handles growth in users, data, traffic.
    🟢
    Availability
    Uptime: 99.9% ≈ 8.8 h downtime/year; 99.99% ≈ 53 min.
    🕒
    Latency / Throughput
    Time per request vs requests per second.
    🛡️
    Reliability & Durability
    Works correctly and never loses data.

    🧮 Back-of-the-envelope estimation

    Quick maths to decide whether you need one server or a thousand. Learn a few anchors: 1 day ≈ 10⁵ seconds (86,400); 1M requests/day ≈ 12 requests/second; a read from RAM is ~100 ns, SSD ~100 µs, a network round trip within a data-centre ~0.5 ms, across continents ~150 ms.

    EXAMPLE · URL shortener: 100M new URLs per month, read:write = 100:1
    • Write QPS = 100M / (30 × 86,400) ≈ 40/s; read QPS ≈ 4,000/s.
    • Storage for 5 years: 100M × 12 × 5 = 6B records × 500 bytes ≈ 3 TB.
    • Conclusion: read-heavy → add a cache; 3 TB fits a sharded or distributed store.
    📝
    Always state assumptions and round generously. Interviewers care about reasoning, not exact digits.

    🪜 A framework to approach any design question

    1. Clarify scope and requirements (functional + non-functional).
    2. Estimate scale: users, QPS, storage, bandwidth.
    3. API & data model: main endpoints and entities.
    4. High-level architecture: draw the main components and data flow.
    5. Deep-dive the bottleneck: database, cache, queue, consistency.
    6. Failure & scale: single points of failure, monitoring, trade-offs.
    Q. Which is a NON-functional requirement?
    • A Users can upload a photo
    • B p99 latency under 200 ms
    • C Users can follow others
    • D Users can search

    Module 02 · Scalability Building Blocks

    Scalability, Load Balancing & Core Components

    Vertical vs horizontal scaling, stateless services, load balancer types and algorithms, reverse proxies, CDNs and API gateways.

    📈 Scaling: vertical vs horizontal

    ⬆️ Vertical (scale up)

    Bigger machine: more CPU/RAM. Simple, no code change, but has a hard ceiling, costs more per unit and is a single point of failure.

    ➡️ Horizontal (scale out)

    More machines behind a load balancer. Near-unlimited and fault tolerant, but needs stateless design, data partitioning and distributed-systems thinking.

    💡
    To scale a service horizontally, make it stateless: keep session and data in external stores (Redis, DB) so any instance can serve any request.

    ⚖️ Load balancing

    A load balancer (LB) distributes incoming requests across multiple servers, removes unhealthy ones via health checks, and hides the server fleet behind one address.

    A load balancer spreads traffic and removes failed servers.
    LayerWorks onPros / use
    L4 (transport)IP + port (TCP/UDP)Very fast, simple; no content awareness
    L7 (application)HTTP headers, path, cookiesSmart routing (/api vs /static), TLS termination, A/B routing
    AlgorithmHow it picksBest for
    Round robinNext server in turnSimilar servers, similar requests
    Weighted round robinProportional to capacityMixed hardware
    Least connectionsServer with fewest active requestsLong-lived or uneven requests
    IP / consistent hashHash of client or keySticky sessions, cache locality
    Random with 2 choicesPick 2 randomly, choose less loadedLarge fleets, low overhead
    ⚠️
    The load balancer itself can be a single point of failure — run it as an active-passive or active-active pair, or use DNS / anycast with multiple LBs.

    🧱 Other essential building blocks

    🌐
    DNS
    Maps names to IPs; can route by geography or health (GeoDNS).
    🚚
    CDN
    Caches static content near users; cuts latency and origin load.
    🚪
    API Gateway
    Single entry: auth, rate limiting, routing, request transformation.
    🪞
    Reverse proxy
    Sits in front of servers: TLS, compression, caching (Nginx, Envoy).
    📨
    Message queue
    Decouples producers from consumers; absorbs spikes (Kafka, SQS, RabbitMQ).
    🔎
    Service discovery
    Instances register and are found dynamically (Consul, Kubernetes DNS).

    Rate limiting protects services from overload and abuse. Common algorithms: fixed window, sliding window, token bucket (allows bursts, refills at a steady rate) and leaky bucket (smooths output).

    Module 03 · Caching

    Caching Strategies

    What a cache is, where to cache, read/write patterns, eviction policies and the classic cache problems.

    ⚡ What is a cache?

    A cache is a fast, small store that keeps copies of frequently used data so future requests avoid slower sources (database, remote API, heavy computation). It works because of locality of reference: a small portion of data receives most of the traffic.

    LayerExamples
    Browser / clientHTTP cache headers, local storage
    CDN / edgeCloudFront, Cloudflare, Akamai
    Application (in-process)Guava, Caffeine, lru_cache
    Distributed cacheRedis, Memcached
    DatabaseBuffer pool, query cache, materialised views

    Key metric: hit ratio = hits / (hits + misses). Average latency = hit_ratio × cache_latency + (1 − hit_ratio) × DB_latency.

    🔄 Caching patterns

    PatternHow it worksTrade-off
    Cache-aside (lazy)App checks cache; on miss reads DB and fills cacheMost common; stale data possible; first request slow
    Read-throughCache itself loads from DB on a missSimpler app code; cache library must know the DB
    Write-throughWrite goes to cache and DB synchronouslyConsistent, but slower writes
    Write-back (behind)Write to cache, flush to DB asynchronouslyVery fast writes; risk of data loss on cache crash
    Write-aroundWrite to DB only; cache fills on readAvoids polluting cache with rarely-read data
    pythondef get_user(uid):                         # cache-aside
    key = f"user:{uid}"
    val = redis.get(key)
    if val is not None: return json.loads(val)       # hit
    row = db.query("SELECT * FROM users WHERE id=%s", uid)   # miss
    redis.setex(key, 300, json.dumps(row))           # TTL = 5 minutes
    return row

def update_user(uid, data):
    db.update(uid, data)
    redis.delete(f"user:{uid}")                      # invalidate, do not update

    🗑️ Eviction policies and invalidation

    🕰️
    LRU
    Evict least recently used. Best general default.
    📊
    LFU
    Evict least frequently used. Good for stable hot sets.
    📥
    FIFO / TTL
    Evict oldest or expired entries.

    "There are only two hard things in computer science: cache invalidation and naming things." Strategies: TTL expiry, explicit invalidation on write, versioned keys, and event-driven invalidation via change-data-capture.

    🌩️ Classic cache problems

    ProblemWhat happensFix
    Cache stampede / thundering herdA hot key expires; thousands of requests hit the DB at onceRequest coalescing / locks, early refresh, jittered TTL
    Cache penetrationRequests for keys that never exist bypass the cacheCache negative results, Bloom filter
    Cache avalancheMany keys expire together or the cache cluster failsRandomise TTLs, replicate / cluster the cache
    Hot keyOne key overloads a single cache nodeReplicate hot keys, local in-process cache
    Stale dataCache and DB disagreeShorter TTL, invalidate on write, accept eventual consistency
    Q. Which pattern risks data loss if the cache crashes?
    • A Write-through
    • B Write-back
    • C Cache-aside
    • D Read-through
    Q. Best defence against a stampede on one expiring hot key?
    • A Delete the cache
    • B Request coalescing / locking with jittered TTL
    • C Bigger DB
    • D Disable TTL everywhere

    Module 04 · Data Storage & Partitioning

    Databases, Replication & Sharding

    SQL vs NoSQL, indexing, replication, partitioning strategies, consistent hashing and how to pick a datastore.

    🗄️ Choosing a database

    TypeExamplesBest for
    Relational (SQL)PostgreSQL, MySQLStructured data, joins, transactions (ACID)
    Key-valueRedis, DynamoDBSessions, caches, simple fast lookups
    DocumentMongoDB, FirestoreFlexible schema, nested objects
    Wide-columnCassandra, HBaseHuge write-heavy, time-series, high availability
    GraphNeo4jRelationships: social graph, recommendations
    SearchElasticsearchFull-text search, analytics
    Object storeS3Images, videos, backups
    💡
    Start with a relational database unless you have a clear reason not to. Move to NoSQL for scale patterns, flexible schemas, or specific access patterns — and remember most large systems are polyglot (several stores).

    🔖 Indexing

    An index is an auxiliary structure (usually a B-tree) that makes lookups O(log n) instead of a full table scan, at the cost of extra storage and slower writes. Rules of thumb: index columns used in WHERE, JOIN and ORDER BY; use composite indexes ordered by selectivity and query shape; avoid indexing low-cardinality columns; use EXPLAIN to verify.

    sqlCREATE INDEX idx_orders_user_date ON orders (user_id, created_at DESC);
-- Fast: WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;

    🪞 Replication

    Replication keeps copies of data on several nodes for availability and read scaling.

    ModelHowNotes
    Leader–followerWrites to the leader; followers replicate; reads from followersSimple; replication lag causes stale reads; failover needed
    Multi-leaderSeveral nodes accept writesGood for multi-region; needs conflict resolution
    Leaderless (quorum)Write to W nodes, read from R nodes, with R + W > NDynamo / Cassandra style; tunable consistency

    Replication can be synchronous (durable, slower) or asynchronous (fast, may lose the last writes on failover).

    🔪 Sharding (partitioning)

    Sharding splits one large dataset across many machines so that each holds a part (a shard), scaling storage and write throughput beyond one node.

    StrategyHowProsCons
    Range-basedKey ranges (A–F, G–M…)Range queries easyHotspots (e.g. recent timestamps)
    Hash-basedshard = hash(key) mod NEven distributionRange queries hard; resharding moves most data
    Directory / lookupA map service tells where each key livesFlexibleLookup service is a dependency
    Geo-basedBy region of the userLow latency, data residencyUneven load, cross-region queries

    Consistent hashing

    With hash(key) mod N, changing N remaps almost every key. Consistent hashing places servers and keys on a ring; each key belongs to the next server clockwise. Adding or removing a node moves only about 1/N of keys. Virtual nodes spread each server at many points for balance.

    Each key is served by the next node clockwise on the ring.
    ⚠️
    Sharding adds cost: cross-shard joins and transactions are hard, resharding is operationally heavy, and a poor shard key creates hotspots. Pick a key with high cardinality and even access, and shard only when a single node (with replicas and cache) can no longer cope.

    • B Adding/removing a node remaps only a small fraction of keys
    • C It supports range queries
    • D It avoids replication
    Q. Quorum reads and writes guarantee overlap when…
    • A R + W > N
    • B R + W < N
    • C R = W = 1
    • D N = 1 only

    Module 05 · Trade-offs

    CAP Theorem & Consistency Models

    The fundamental trade-offs of distributed data: CAP, PACELC, ACID vs BASE and the spectrum of consistency.

    🔺 CAP theorem

    In a distributed data store, when a network partition happens you cannot have both consistency and availability:

    🔁
    Consistency (C)
    Every read sees the latest write (linearizable).
    🟢
    Availability (A)
    Every request to a live node gets a non-error response.
    ✂️
    Partition tolerance (P)
    System continues despite lost or delayed messages between nodes.

    Partitions will happen on real networks, so the real choice is CP (refuse or delay requests to stay correct) or AP (keep answering, possibly with stale data).

    ChoiceBehaviour during a partitionExamples
    CPMinority side stops accepting writes/readsZooKeeper, etcd, HBase, MongoDB (default), Spanner
    APBoth sides keep serving; reconcile laterCassandra, DynamoDB (eventual), Riak, CouchDB
    📝
    CAP is often misquoted as "pick two of three". Without partitions you can have all three; CAP only describes the trade-off during a partition.

    ⏳ PACELC: the full picture

    PACELC extends CAP: if there is a Partition choose Availability or Consistency; Else (normal operation) choose Latency or Consistency. Even without failures, stronger consistency costs latency because replicas must coordinate.

    📚 Consistency models

    ModelGuaranteeCost
    Strong / linearizableBehaves like a single copy; reads see latest writeHighest latency, lower availability
    SequentialAll see operations in one agreed orderModerate
    CausalRelated operations are seen in orderLower
    Read-your-writesYou see your own updatesLow
    EventualReplicas converge if updates stopLowest latency, highest availability
    EXAMPLE · Social media "likes" vs bank balance
    • A like counter can be eventually consistent — a few seconds of stale count is harmless (AP).
    • A bank transfer needs strong consistency and transactions (CP).

    🧪 ACID vs BASE

    🏦 ACID

    Atomicity, Consistency, Isolation, Durability. All-or-nothing transactions; typical of relational databases.

    🌐 BASE

    Basically Available, Soft state, Eventual consistency. Favours availability and scale in distributed stores.

    Isolation levelPreventsStill allows
    Read committedDirty readsNon-repeatable reads, phantoms
    Repeatable readDirty + non-repeatable readsPhantoms (DB-dependent)
    SerializableAll anomaliesLowest concurrency
    Q. During a network partition, a CP system will…
    • A Serve stale data from both sides
    • B Reject or delay some requests to stay consistent
    • C Ignore the partition
    • D Lose consistency but stay available
    Q. Which fits an eventually consistent design?
    • A Bank ledger
    • B Social media like counter
    • C Inventory reservation at checkout
    • D Payment capture

    Module 06 · High-Level Design Cases

    High-Level Design Case Studies

    Apply everything: four classic designs with requirements, estimates, architecture and trade-offs.

    🔗 Case 1 · URL Shortener (TinyURL)

    Requirements: shorten a URL, redirect fast, optional custom alias, expiry; 100M new URLs/month, read-heavy (100:1), high availability.

    1. API: POST /shorten {url} → short code; GET /{code} → 301/302 redirect.
    2. Code generation: base62 encode (a–z, A–Z, 0–9) of a unique ID. 7 chars → 62⁷ ≈ 3.5 trillion codes. Unique IDs from a counter service with ranges handed to app servers, or Snowflake-style IDs. Avoid plain hashing of the URL (collisions).
    3. Storage: key-value store (code → long URL, created, expiry) — DynamoDB / Cassandra / sharded SQL by code.
    4. Read path: CDN/edge + Redis cache in front of DB (hot links dominate). Use 302 if you need analytics, 301 to cut load.
    5. Scale: stateless app servers behind an LB; shard by code; rate-limit creation; background job deletes expired links.
    pythonALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
def base62(n):
    s = ""
    while n: n, r = divmod(n, 62); s = ALPHABET[r] + s
    return s or "0"

    🚦 Case 2 · Distributed Rate Limiter

    Goal: limit each user/IP/API-key to N requests per window across many servers, with very low overhead.

    • Algorithm: token bucket (burst-friendly) or sliding-window counter.
    • Shared state: Redis with atomic operations (INCR + EXPIRE or a Lua script) so all servers see one counter.
    • Placement: API gateway / sidecar; return 429 Too Many Requests with Retry-After.
    • Trade-offs: exact global limits cost a network call per request; approximate with local counters synced periodically. Decide fail-open vs fail-closed if Redis is down.

# tokens = min(capacity, tokens + (now-last)*refill); if tokens >= 1: tokens -= 1; allow

    📰 Case 3 · News Feed (Twitter / Instagram)

    • Fan-out on write (push): when a user posts, write the post ID into each follower's precomputed feed (Redis list). Reads are O(1) and fast; writes are expensive for celebrities with millions of followers.
    • Fan-out on read (pull): compute the feed at read time by merging followees' recent posts. Cheap writes, slow reads.
    • Hybrid: push for normal users, pull for celebrities, merge at read time.
    • Components: post service + blob store/CDN for media, graph (follow) service, feed service + cache, async workers via Kafka, ranking service.
    • Data: posts sharded by user or post ID; feed lists in Redis; cursor-based pagination.

    💬 Case 4 · Chat System (WhatsApp)

    • Connection: WebSockets via a gateway fleet; a presence/session service maps user → gateway server.
    • Message flow: sender → gateway → message service → persist (wide-column store keyed by conversation ID, ordered by message ID) → look up recipient's gateway → deliver; if offline, queue and send a push notification.
    • Ordering and delivery: per-conversation sequence IDs; acks (sent / delivered / read); idempotent retries by message ID.
    • Group chat: fan-out to members through a queue; limit group size or fan-out lazily.
    • Media: upload to object storage, send only the reference. E2E encryption keeps servers blind to content.

    Module 07 · Low-Level Design Basics

    OOP Fundamentals & SOLID Principles

    Objects, classes, the four pillars of OOP, relationships, UML basics and the five SOLID principles with before/after code.

    🧩 What is Low-Level Design?

    LLD turns requirements into classes, interfaces and interactions that are easy to understand, change and test. You identify entities (nouns → classes), behaviours (verbs → methods), relationships, and the rules (invariants, state transitions).

    🏛️ The four pillars of OOP

    📦
    Encapsulation
    Bundle data with the methods that guard it; hide internals behind a public interface.
    🎭
    Abstraction
    Expose what an object does, hide how.
    🧬
    Inheritance
    A class reuses and extends another (is-a). Prefer composition when possible.
    🔀
    Polymorphism
    One interface, many implementations; the right method is chosen at runtime.
    RelationshipMeaningExample
    AssociationUses / knowsTeacher — Student
    AggregationHas-a, parts can live independentlyTeam — Player
    CompositionOwns; parts die with the wholeHouse — Room
    InheritanceIs-aCar → Vehicle
    DependencyTemporarily usesService uses a Logger
    💡
    Favour composition over inheritance: it keeps classes small, swappable and avoids fragile deep hierarchies.

    🧱 SOLID principles

    S · Single Responsibility Principle

    A class should have one reason to change.

    python# Bad: one class does business logic, persistence and email
class Order:
    def total(self): ...
    def save_to_db(self): ...
    def send_email(self): ...

# Good: separate responsibilities
class Order: ...                      # domain logic
class OrderRepository: ...            # persistence
class OrderNotifier: ...              # notifications

    O · Open/Closed Principle

    Open for extension, closed for modification: add new behaviour by adding code, not editing tested code.

    python# Bad: every new shape changes this function
def area(s):
    if s.kind == "circle": return 3.14159 * s.r ** 2
    elif s.kind == "rect": return s.w * s.h

# Good: new shapes extend the abstraction
class Shape:
    def area(self): raise NotImplementedError
class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r ** 2
class Rect(Shape):
    def __init__(self, w, h): self.w, self.h = w, h
    def area(self): return self.w * self.h

    L · Liskov Substitution Principle

    Subtypes must be usable wherever the base type is expected without breaking behaviour. The classic violation: Square extends Rectangle but setting width also changes height, breaking code that assumes independent sides. Fix: model them as separate shapes under a common interface.

    I · Interface Segregation Principle

    Prefer many small, specific interfaces over one fat interface. A Printer class should not be forced to implement fax() and scan() just because a MultiFunctionDevice interface demands it.

    D · Dependency Inversion Principle

    High-level modules should depend on abstractions, not concrete implementations. Inject dependencies instead of creating them inside.

    pythonclass PaymentGateway:                      # abstraction
    def charge(self, amount): ...

class Stripe(PaymentGateway):
    def charge(self, amount): ...
class PayPal(PaymentGateway):
    def charge(self, amount): ...

class Checkout:
    def __init__(self, gateway: PaymentGateway):   # injected
        self.gateway = gateway
    def pay(self, amount): self.gateway.charge(amount)   # easy to test with a fake
    PrincipleSmell it fixes
    SRPGod classes, many reasons to change
    OCPLong if/else or switch chains on type
    LSPSubclasses throwing "not supported" or breaking assumptions
    ISPEmpty or throwing methods forced by fat interfaces
    DIPnew ConcreteClass() deep inside business logic, hard to test
    Q. A long if/elif chain on object type that grows with each feature violates…
    • A Single Responsibility
    • B Open/Closed
    • C Interface Segregation
    • D Encapsulation
    Q. Injecting a PaymentGateway interface into Checkout demonstrates…
    • A Dependency Inversion
    • B Liskov
    • C Inheritance only
    • D Singleton

    Module 08 · Design Patterns

    Design Patterns: Creational, Structural, Behavioural

    Reusable solutions to recurring design problems — what each pattern is, when to use it and code to recognise it.

    📚 What are design patterns?

    A design pattern is a named, proven solution template for a common design problem. They give teams a shared vocabulary ("use a Strategy here"). Use them to solve a real problem — not to decorate code.

    🏗️
    Creational
    How objects are created: Singleton, Factory, Abstract Factory, Builder, Prototype.
    🧱
    Structural
    How objects are composed: Adapter, Decorator, Facade, Proxy, Composite.
    🎬
    Behavioural
    How objects interact: Strategy, Observer, Command, State, Template Method, Iterator.

    🏗️ Creational patterns

    PatternIntentUse when
    SingletonExactly one instance with global accessConfig, logger, connection pool (beware global state & tests)
    Factory MethodSubclass / method decides which class to createCreation logic varies by type
    Abstract FactoryCreate families of related objectsUI themes, cross-platform kits
    BuilderConstruct complex objects step by stepMany optional parameters
    PrototypeClone an existing objectCostly creation
    pythonclass Notification: ...
class Email(Notification): ...
class Sms(Notification): ...

def notification_factory(kind):            # Factory
    return {"email": Email, "sms": Sms}[kind]()

class Singleton:
    _inst = None
    def __new__(cls):
        if cls._inst is None: cls._inst = super().__new__(cls)
        return cls._inst

class QueryBuilder:                        # Builder (fluent)
    def __init__(self): self.parts = {}
    def select(self, c): self.parts["select"] = c; return self
    def frm(self, t): self.parts["from"] = t; return self
    def where(self, w): self.parts["where"] = w; return self
    def build(self): return f"SELECT {self.parts['select']} FROM {self.parts['from']} WHERE {self.parts.get('where', '1=1')}"

    PatternIntentExample
    AdapterConvert one interface into anotherWrap a legacy payment SDK to your interface
    DecoratorAdd behaviour dynamically by wrappingCompression / encryption streams, middleware
    FacadeSimple front for a complex subsystemVideoConverter.convert(file)
    ProxyStand-in that controls accessLazy loading, caching, access control
    CompositeTreat single and grouped objects uniformlyFile / folder trees, UI components
    pythonclass Coffee:
    def cost(self): return 50

    🎬 Behavioural patterns

    PatternIntentExample
    StrategySwap algorithms at runtimePricing, sorting, routing, payment methods
    ObserverNotify dependents when state changesEvent listeners, pub/sub, UI updates
    CommandEncapsulate a request as an objectUndo/redo, job queues
    StateBehaviour changes with internal stateOrder status, vending machine, trip lifecycle
    Template MethodSkeleton in base class, steps in subclassesData import pipelines
    IteratorTraverse without exposing structureCollections, generators
    pythonclass PricingStrategy:                     # Strategy
    def price(self, base): raise NotImplementedError
class Regular(PricingStrategy):
    def price(self, base): return base
class Festival(PricingStrategy):
    def price(self, base): return base * 0.8

class Cart:
    def __init__(self, strategy): self.strategy = strategy
    def total(self, base): return self.strategy.price(base)

class Subject:                             # Observer
    def __init__(self): self._obs = []

    def publish(self, event):
        for fn in self._obs: fn(event)

    Module 09 · Low-Level Design Cases

    Low-Level Design Case Studies

    Turn a requirement into classes: parking lot, elevator and rate limiter — with the reasoning for each decision.

    🧠 LLD approach

    1. Clarify requirements and use cases.
    2. Extract entities (nouns) and actions (verbs).
    3. Define classes, interfaces and relationships.
    4. Spot variation points → Strategy / Factory / State.
    5. Write core methods; handle concurrency and edge cases.
    6. Walk through 2–3 scenarios to validate.

    🅿️ Case 1 · Parking Lot

    Requirements: multiple floors, spot types (bike, car, truck), entry/exit gates, ticketing, fee calculation by duration, find nearest free spot.

    pythonfrom enum import Enum
from datetime import datetime

class VehicleType(Enum): BIKE = 1; CAR = 2; TRUCK = 3

class Vehicle:
    def __init__(self, plate, vtype): self.plate, self.type = plate, vtype

class Spot:
    def __init__(self, sid, vtype): self.id, self.type, self.vehicle = sid, vtype, None
    def free(self): return self.vehicle is None

class Ticket:
    def __init__(self, vehicle, spot): self.vehicle, self.spot, self.entry = vehicle, spot, datetime.now()

class FeeStrategy:                                   # Strategy for pricing
    def fee(self, hours): raise NotImplementedError
class HourlyFee(FeeStrategy):
    def __init__(self, rate): self.rate = rate
    def fee(self, hours): return max(1, hours) * self.rate

class ParkingLot:
    def __init__(self, spots, strategy): self.spots, self.strategy, self.active = spots, strategy, {}
    def park(self, v):
        spot = next((s for s in self.spots if s.free() and s.type == v.type), None)
        if not spot: raise Exception("Lot full")
        spot.vehicle = v
        t = Ticket(v, spot); self.active[v.plate] = t; return t
    def exit(self, plate):
        t = self.active.pop(plate)
        hours = (datetime.now() - t.entry).seconds // 3600 + 1
        t.spot.vehicle = None
        return self.strategy.fee(hours)
    • Why Strategy for fees? pricing changes often (hourly, flat, weekend) — Open/Closed.
    • Concurrency: two cars may take the same spot; use a lock per floor or an atomic compare-and-set on the spot.
    • Extensions: a min-heap of free spots per type for nearest-spot in O(log n); EV-charging spots; payment service via DIP.

    🛗 Case 2 · Elevator System

    • Entities: Elevator (state: IDLE, MOVING_UP, MOVING_DOWN, DOORS_OPEN), Request (floor, direction), Controller.
    • State pattern: behaviour differs per state (a moving elevator ignores "open door").
    • Scheduling strategy: the controller assigns a request to the elevator that is closest and heading the same way (SCAN / LOOK algorithm: keep going in one direction serving stops, then reverse).
    • Data: each elevator keeps two sorted sets of stops (up, down).
    pythonimport bisect

class Elevator:
    def __init__(self): self.floor, self.dir, self.up, self.down = 0, "IDLE", [], []
    def add_stop(self, f):
        target = self.up if f >= self.floor else self.down
        if f not in target: bisect.insort(target, f)
        if self.dir == "IDLE": self.dir = "UP" if f >= self.floor else "DOWN"
    def step(self):
        if self.dir == "UP" and self.up:
            self.floor = self.up.pop(0)
            if not self.up: self.dir = "DOWN" if self.down else "IDLE"
        elif self.dir == "DOWN" and self.down:
            self.floor = self.down.pop()
            if not self.down: self.dir = "UP" if self.up else "IDLE"

    🚦 Case 3 · Rate Limiter (class design)

    pythonimport time, threading

class RateLimiter:                                   # interface
    def allow(self, key): raise NotImplementedError

class TokenBucket(RateLimiter):
    def __init__(self, capacity, refill_per_sec):
        self.cap, self.rate, self.buckets, self.lock = capacity, refill_per_sec, {}, threading.Lock()
    def allow(self, key):
        now = time.monotonic()
        with self.lock:
            tokens, last = self.buckets.get(key, (self.cap, now))
            tokens = min(self.cap, tokens + (now - last) * self.rate)
            if tokens >= 1:
                self.buckets[key] = (tokens - 1, now); return True
            self.buckets[key] = (tokens, now); return False

    Interview Preparation

    🏙️ High-level design questions

    How do you scale a read-heavy system?
    Cache aggressively (CDN, Redis), add read replicas, denormalise hot read models, paginate, and move expensive work to async precomputation.
    How do you scale a write-heavy system?
    Shard by a well-distributed key, batch and queue writes (Kafka), use append-friendly stores (LSM / wide-column), and avoid hot partitions.
    Explain the CAP theorem with an example.
    During a partition you choose consistency or availability. A bank ledger picks CP (reject operations rather than diverge); a shopping-cart or like counter picks AP (accept writes and reconcile later).
    SQL or NoSQL?
    Start with SQL for relational data and transactions. Choose NoSQL for massive scale, flexible schemas, or specific access patterns (key-value, wide-column). Often use both.
    What is consistent hashing and why?
    A ring-based key placement where adding or removing nodes moves only ~1/N keys, unlike mod-N hashing which reshuffles nearly everything.
    How do you make a service highly available?
    Remove single points of failure: redundant instances across zones, load balancing with health checks, replicated data, graceful degradation, timeouts/retries/circuit breakers, and automated failover.

    🔧 Low-level design questions

    Explain SOLID briefly.
    S: one reason to change. O: extend without modifying. L: subtypes are substitutable. I: small focused interfaces. D: depend on abstractions, inject dependencies.
    Composition vs inheritance?
    Inheritance models is-a but couples subclass to parent. Composition models has-a, is more flexible and testable. Prefer composition; use inheritance for true is-a and shared contracts.
    Why can Singleton be harmful?
    It is hidden global state: hard to test, tightly couples code and can hurt concurrency. Prefer dependency injection with a single instance managed by the container.
    Strategy vs State pattern?
    Both swap behaviour objects. Strategy is chosen by the client (algorithm choice); State transitions internally as the object's state changes.
    How do you make a class thread-safe?
    Prefer immutability; otherwise guard shared mutable state with locks or atomics, minimise lock scope, avoid shared state, and use concurrent collections.
    Design a cache with LRU eviction at class level.
    A Cache interface with EvictionPolicy strategy; storage = hash map + doubly linked list for O(1) get/put; make operations thread-safe; support TTL and metrics.

    🗣️ How to perform in a design round

    • Spend the first minutes on requirements and scale — never jump to boxes.
    • Draw a simple end-to-end flow first, then deepen one or two hard parts.
    • Make trade-offs explicit: "I choose X because Y; the cost is Z."
    • Talk about failure: what if the cache, queue or region goes down?
    • For LLD, show the class diagram first, then code the core flow cleanly.

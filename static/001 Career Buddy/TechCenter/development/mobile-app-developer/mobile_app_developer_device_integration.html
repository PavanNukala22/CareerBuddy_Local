    What is Device Integration?

    Start from zero: how an app talks to phone hardware and OS services, the types of capabilities, and the permission model that guards them.

    🧭 What is Device Integration?

    Device integration means your app uses the phone's own hardware (camera, GPS) and operating-system services (push, local database) through platform APIs. It is what separates a mobile app from a plain website.

    📷
    Camera
    Capture photos, video, scan codes
    📍
    Location
    Where the user is, and where they go
    🔔
    Push
    Reach users when the app is closed
    💾
    Offline storage
    Work without a network
    💡
    Your app never touches hardware directly. It asks the OS, the OS checks permission, then a driver talks to the hardware.

    🗂️ Types of Device Capabilities

    CategoryExamplesAccess via
    SensorsCamera, microphone, GPS, accelerometer, gyroscopeCameraX / AVFoundation, Fused Location / Core Location
    ConnectivityWi-Fi, cellular, Bluetooth LE, NFCConnectivityManager, NWPathMonitor, CoreBluetooth
    OS servicesPush notifications, background tasks, biometricsFCM / APNs, WorkManager / BGTaskScheduler
    StorageKey-value, files, SQLite, secure storageDataStore, Room, Core Data, Keychain / Keystore

    Module 02 · Camera APIs

    Camera APIs

    What a camera API is, the ways to access it, image/video concepts, working code, then performance, privacy and ML analysis.

    📷 What is a Camera API?

    A camera API lets your app preview the live sensor feed, capture still images or video, and analyse frames (barcodes, faces, text). Choose the highest-level option that meets your need: less code, fewer device bugs.

    🗂️ Types of Camera Access

    LevelAndroidiOSUse when
    System capture (easiest)ACTION_IMAGE_CAPTURE, Photo PickerUIImagePickerController, PHPickerProfile photo, attach image; no custom UI
    In-app camera (recommended)CameraXAVFoundation (AVCaptureSession)Custom UI, scanning, filters
    Low-levelCamera2 APIAVCaptureDevice manual controlsManual exposure, RAW, pro camera
    Cross-platformcamera (Flutter), expo-camera, react-native-vision-camerasameOne codebase

    🧠 Core Concepts

    PreviewLive view rendered to a surface (PreviewView, AVCaptureVideoPreviewLayer).
    Use cases (CameraX)Preview, ImageCapture, ImageAnalysis, VideoCapture, bound to a lifecycle.
    Image formatsJPEG (compressed), HEIC (smaller, iOS), YUV (raw frames for analysis), RAW (unprocessed).
    Orientation / EXIFSensor image is rotated; EXIF stores rotation, time, even GPS.
    Resolution & aspect4:3 vs 16:9; higher resolution = more memory and upload cost.
    Focus, exposure, flashAuto or tap-to-focus; torch for scanning in the dark.

    🚀 Expert: Analysis, Performance & Privacy

    • Frame analysis: ImageAnalysis + ML Kit / Vision for barcode, OCR, face detection. Use STRATEGY_KEEP_ONLY_LATEST and always close the frame.
    • Memory: never load full-size bitmaps; downsample (inSampleSize, ImageDecoder), use Coil / Glide / UIGraphicsImageRenderer.
    • Threading: capture and analysis on background executors; update UI on the main thread.
    • Upload: compress (quality ~80%), resize, queue with WorkManager, resume on failure.
    • Privacy: strip EXIF GPS before sharing, save to app-scoped storage, release the camera in onPause.
    • Fragmentation: test on low-end devices; handle camera-in-use and foldable orientation changes.
    ⚠️
    Forgetting to release the camera drains battery and blocks other apps. Bind to the lifecycle so it is released automatically.

    Module 03 · GPS & Geolocation

    GPS & Geolocation

    How phones find position, the providers and modes available, APIs on both platforms, then battery, geofencing and accuracy engineering.

    📍 What is GPS / Geolocation?

    GPS is one satellite system; GNSS covers all (GPS, GLONASS, Galileo, BeiDou). Geolocation is the OS service that fuses satellites, Wi-Fi, cell towers and sensors into a position: latitude, longitude, accuracy (metres), plus altitude, speed and bearing.

    🗂️ Types: Sources, Accuracy & Modes

    SourceAccuracyBatteryWorks indoors
    GPS / GNSS3–10 mHighNo
    Wi-Fi positioning20–50 mLowYes
    Cell towers100 m–kmVery lowYes
    Fused (Google) / Core LocationBest availableBalancedYes
    ModeWhat it doesExample
    One-shotSingle current location“Find stores near me”
    Continuous updatesStream at an intervalNavigation, run tracker
    Significant-changeWake on large movementWeather, check-ins
    GeofencingEvent on entering/exiting a region“Arrived at warehouse”
    BackgroundTracking when app is closedDelivery tracking (needs justification)

    🔐 Permissions

    AndroidACCESS_COARSE_LOCATION (approx.), ACCESS_FINE_LOCATION (precise), ACCESS_BACKGROUND_LOCATION asked separately.
    iOSWhen-In-Use vs Always; user can grant “Approximate Location”.
    Best practiceAsk for the least needed; explain why; app must work if the user chooses approximate or denies.

    pythonfrom math import radians, sin, cos, asin, sqrt
def km(lat1, lon1, lat2, lon2):
    dlat, dlon = radians(lat2-lat1), radians(lon2-lon1)
    a = sin(dlat/2)**2 + cos(radians(lat1))*cos(radians(lat2))*sin(dlon/2)**2
    return 6371 * 2 * asin(sqrt(a))

    🚀 Expert: Battery, Geofencing & Accuracy

    • Priority tuning: use balanced or low-power unless navigation needs high accuracy; raise the interval and distance filter.
    • Background: Android needs a foreground service with a notification; iOS needs the background mode and Always permission. Stop updates when not needed.
    • Geofencing: OS limits (Android 100 per app, iOS 20); use a radius of 100 m+; expect delay of seconds to minutes.
    • Filtering noise: discard fixes with poor accuracy or old timestamps; smooth with a Kalman filter; snap to roads for routes.
    • Trust: detect mock locations (isMock) for fraud-sensitive apps.
    • Privacy: collect least data, coarsen stored coordinates, encrypt in transit, set retention limits.
    💡
    Location is the top battery drain. Always measure with the OS battery profiler before shipping tracking.

    Module 04 · Push Notifications

    Push Notifications

    What push is, the delivery architecture, message types, setup on Android and iOS, then reliability, targeting and security.

    🔔 What are Push Notifications?

    A push notification is a message sent from your server to a device even when the app is closed. Delivery goes through platform gateways: FCM (Firebase Cloud Messaging) for Android and APNs (Apple Push Notification service) for iOS. Your app cannot open its own connection to the device while closed.

    Push path: server sends to the platform gateway, which delivers to the device OS, which shows or wakes the app.

    🗂️ Types of Notifications

    TypeDescriptionUse
    LocalScheduled by the app on device, no serverReminders, timers
    Remote (notification message)OS displays it automaticallyOffers, alerts
    Data / silentPayload only; wakes app to sync, nothing shownRefresh content (limited on iOS)
    RichImage, actions, reply fieldChat, delivery tracking
    TargetingToken · Topic · SegmentOne user, a group, a cohort

    🧠 Core Concepts

    Device tokenUnique address for an app install; changes on reinstall or restore, so refresh it on the server.
    Notification channelAndroid 8+ category the user can mute independently (Orders, Promotions).
    PermissionAndroid 13+ POST_NOTIFICATIONS; iOS authorization request.
    Priority / TTLHigh priority wakes the device; TTL discards stale messages.
    Collapse keyReplaces older pending messages with the newest.
    Deep linkPayload field that opens the right screen on tap.

    💻 Example: Receive and Send

    🚀 Expert: Reliability, Targeting & Security

    • Not guaranteed: delivery is best-effort; Doze, battery savers and OEM restrictions delay messages. Always let the app fetch the truth on open.
    • Idempotency: include a message ID and deduplicate; never rely on one push for critical state.
    • Token hygiene: store per user + device, delete on logout, prune tokens that return UNREGISTERED.
    • iOS silent push: throttled by the OS; use content-available sparingly.
    • Relevance: segment, cap frequency, respect quiet hours and time zones; measure opt-in and open rates.
    • Security: never put sensitive data in the payload (it passes through third parties and shows on lock screens); verify with server-side auth.
    📝
    Ask for notification permission after the user sees value, not at first launch. Opt-in rates rise sharply.

    Module 05 · Offline Storage

    Offline Data Storage

    Why apps need local storage, the types, SQLite fundamentals, Room (Android) and Core Data (iOS), then offline-first sync and migrations.

    💾 What is Offline Data Storage?

    Phones lose network often. Local storage keeps data on the device so the app opens fast, works offline, and syncs later. The pattern of treating the local database as the source of truth is called offline-first.

    🗂️ Types of Local Storage

    TypeAndroidiOSBest for
    Key-valueDataStore, SharedPreferencesUserDefaultsSettings, flags
    FilesInternal / app-scoped storageFileManager (Documents, Caches)Images, downloads, logs
    Relational DBSQLite via RoomSQLite, Core Data, SwiftDataStructured, queryable data
    Object DBRealm, ObjectBoxRealmFast object graphs
    Secure storageKeystore, EncryptedSharedPreferencesKeychainTokens, secrets
    ⚠️
    Never store passwords or tokens in plain key-value storage or files. Use Keystore / Keychain.

    🗄️ SQLite Fundamentals

    SQLite is a serverless relational database in a single file, built into both platforms. It is the engine under Room and (usually) Core Data.

    sqlCREATE TABLE task (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  done INTEGER DEFAULT 0,
  updated_at INTEGER NOT NULL
);
CREATE INDEX idx_task_done ON task(done, updated_at);
BEGIN; INSERT INTO task(title, updated_at) VALUES('Inspect pump', 1700000000); COMMIT;
SELECT * FROM task WHERE done = 0 ORDER BY updated_at DESC LIMIT 20;
    • CRUD: INSERT, SELECT, UPDATE, DELETE.
    • Transactions: group writes so they succeed or fail together; far faster for bulk inserts.
    • Indexes: speed up reads, slow writes slightly; index columns you filter and sort by.
    • Parameterised queries: always bind values, never concatenate strings (SQL injection).

    🚀 Expert: Offline-First & Sync

    • Single source of truth: UI reads only from the DB; a repository refreshes it from the network.
    • Write queue: save locally with a pending flag, push with WorkManager / BGTaskScheduler, retry with backoff, use client-generated IDs for idempotency.
    • Conflicts: last-write-wins (simple), field-level merge, version vectors, or CRDTs for collaboration.
    • Migrations: never drop user data; test every version jump; ship schema export files.
    • Performance: WAL mode, paging (Paging 3), batch in transactions, avoid main-thread DB calls.
    • Security: encrypt at rest (SQLCipher / data protection classes), wipe on logout, exclude from backup if sensitive.
    kotlin// Repository: offline-first

suspend fun refresh() = runCatching { api.tasks() }.onSuccess { dao.upsertAll(it) }

    Rule of thumb: the UI never waits for the network to show data it already has.

    🧪 Testing & Quality

    • Unit-test repositories with fake providers; use Room in-memory DB and Core Data in-memory store.
    • Instrumentation / UI tests with pre-granted permissions; test denial paths too.
    • Use emulator location mocks and the Firebase test console for device farms.

    🎤 Interview Questions

    Fused location vs raw GPS?
    Fused combines GPS, Wi-Fi, cell and sensors to pick the best accuracy/battery trade-off; raw GPS is precise outdoors but costly and slow indoors.
    Why might a push not arrive?
    Invalid or expired token, Doze or battery optimisation, notifications disabled, TTL expired, or OEM restrictions. Push is best-effort.
    How do you design an offline-first app?
    Local DB as source of truth, repository syncing in background, write queue with retries, conflict policy, and clear UI for pending state.
    Room vs Core Data?
    Room is a thin typed layer over SQL (explicit control); Core Data is an object-graph manager with its own faulting and context model.
    How do you handle a denied permission?
    Explain value, offer a fallback (picker, manual address), and deep link to Settings only if “don’t ask again”.
    How do you reduce a tracking app's battery use?
    Lower priority and frequency, distance filter, stop when stationary, use significant-change or geofences, batch uploads.

    🛠️ Scenario

    Build an app for inspectors who visit remote sites with poor network. They photograph equipment, the app records where each inspection happened, saves everything locally, uploads when online, and notifies a manager when a report is approved.

    ✍️ Which local storage would you use for the reports, photos and the auth token?
    Model answer: Reports in Room / Core Data (queryable, relational); photo files in app-scoped storage with their paths in the DB; the token in Keystore / Keychain.
    ✍️ How do you capture and attach location without draining the battery?
    Model answer: Request a one-shot balanced-accuracy fix at capture time, reject low-accuracy results, store latitude, longitude and accuracy with the report. No continuous tracking needed.
    ✍️ Design the upload flow when the inspector returns to coverage.
    Model answer: Mark rows pending; a WorkManager / BGTaskScheduler job with network constraint uploads compressed photos then the report, retries with backoff, uses a client UUID for idempotency, and marks rows synced.
    ✍️ How is the manager notified, and what if the push is lost?
    Model answer: Server sends FCM / APNs with a deep link to the report. Because push is best-effort, the app also refreshes the report list on open.

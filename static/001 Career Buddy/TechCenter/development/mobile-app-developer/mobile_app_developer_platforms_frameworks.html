    Mobile Platforms & Frameworks: The Big Picture

    Start from zero: what a mobile app is, the two platforms, the four ways to build one, and how code becomes an installed app.

    📱 What is a mobile app?

    A mobile app is software that runs on a phone or tablet operating system and can use the device's hardware (touch screen, camera, GPS, sensors) in a way a normal website cannot. It is installed from a store (App Store, Google Play) or from a file, and it runs inside a protected area called a sandbox.

    🌐 Website

    Opens in a browser, no install, limited access to device features, works only with a connection (unless built as a PWA).

    📲 Mobile app

    Installed on the device, icon on the home screen, full access to hardware (with permission), can work offline, can send push notifications.

    PlatformThe operating system your app runs on: iOS (Apple) or Android (Google and many phone makers).
    FrameworkA toolkit of ready-made pieces (buttons, lists, navigation) plus rules for building an app: SwiftUI, Jetpack Compose, Flutter, React Native.
    SDKSoftware Development Kit: libraries, tools and documentation for one platform (iOS SDK, Android SDK).
    IDEThe editor you code in: Xcode (iOS), Android Studio (Android), VS Code (Flutter / React Native).
    UI toolkitThe part of a framework that draws screens. Declarative toolkits describe what the screen looks like for a given state.
    SandboxA restricted area: an app cannot read another app's data or use hardware without user permission.
    Binary / packageThe built file: .ipa (iOS), .apk or .aab (Android).

    🧩 Types of mobile apps

    There are four ways to build a mobile app. Each makes a different trade-off between performance, speed of development and access to the device.

    🍎
    Native
    One codebase per platform in the platform's own language. Best performance and newest features. Swift/SwiftUI, Kotlin/Compose.
    🔀
    Cross-platform
    One codebase for iOS and Android, compiled or bridged to native UI. Flutter (Dart), React Native (TypeScript).
    🧱
    Hybrid (WebView)
    A web app wrapped in a native shell (Ionic/Capacitor, Cordova). Fast for web teams, weakest performance feel.
    🌍
    PWA
    A website that can be installed and work offline. No store required, but limited device access (especially on iOS).
    ApproachLanguagesCode reusePerformanceDevice accessBest for
    Native iOSSwift (SwiftUI / UIKit)None★★★★★Full, day-oneApple-only, camera/AR/health heavy apps
    Native AndroidKotlin (Compose / Views)None★★★★★Full, day-oneAndroid-only, deep OS integration
    FlutterDart~90–100%★★★★☆Via plugins / channelsCustom UI, brand-heavy apps, fast MVPs

    💡
    Remember: "native" does not mean "better" — it means "closest to the OS". The right choice depends on team skills, budget, timeline and the features you need.

    ⚙️ How code becomes an app

    Every app, whatever the framework, goes through the same pipeline.

    Debug vs release builds. A debug build is slower and has developer tools (hot reload, logs). A release build is optimised, smaller and is what users get. Always measure performance on a release build on a real device.

    App lifecycle. Both platforms move your app between states: foreground / active (user sees it), background (hidden, limited work), and terminated (the OS can kill a background app any time to free memory). Good apps save state when they go to the background.

    Swift & SwiftUI (iOS)

    From your first Swift variable to state management, navigation and architecture in SwiftUI.

    🍎 What are Swift, SwiftUI and UIKit?

    Swift is Apple's modern, type-safe language. SwiftUI is Apple's declarative UI framework (you describe the screen from state). UIKit is the older, imperative framework (you create and update view objects yourself) that is still used in many production apps.

    SwiftUIUIKit
    StyleDeclarative: UI = function(state)Imperative: create views, mutate them
    Code amountLessMore (storyboards / Auto Layout code)
    MaturityNewer; improves every iOS releaseVery mature, huge ecosystem
    Use todayNew apps and screensLegacy apps, advanced custom behaviour
    InteropEmbed UIKit with UIViewRepresentableEmbed SwiftUI with UIHostingController

    🎨 Your first SwiftUI screen

    In SwiftUI everything is a View. Views are small structs; you combine them with stacks (VStack, HStack, ZStack) and style them with modifiers.

    swiftimport SwiftUI

struct CounterView: View {
    @State private var count = 0          // local state

    var body: some View {
        VStack(spacing: 16) {
            Text("Count: \(count)")
                .font(.title)
            Button("Add") { count += 1 }  // changes state -> UI re-renders
                .buttonStyle(.borderedProminent)
        }
        .padding()
    }
}
    EXAMPLE · What happens when you tap Add

    The button changes count. Because count is @State, SwiftUI calls body again and updates only what changed. You never touch the label yourself.

    🧭 Navigation, lifecycle & concurrency

    Navigation. Use NavigationStack with NavigationLink or a typed path (.navigationDestination(for:)) for deep links. Modals use .sheet / .fullScreenCover. Tabs use TabView.

    App lifecycle. The entry point is a struct marked @main that conforms to App. React to foreground/background with @Environment(\.scenePhase) (active, inactive, background).

    swift@MainActor
final class FeedViewModel: ObservableObject {
    @Published var items: [String] = []
    @Published var error: String?

    func load() async {
        do {
            let url = URL(string: "https://api.example.com/items")!
            let (data, _) = try await URLSession.shared.data(from: url)
            items = try JSONDecoder().decode([String].self, from: data)
        } catch { self.error = error.localizedDescription }
    }
}

struct FeedView: View {
    @StateObject private var vm = FeedViewModel()
    var body: some View {
        List(vm.items, id: \.self) { Text($0) }
            .task { await vm.load() }      // runs when view appears
    }
}
    • @MainActor guarantees UI updates happen on the main thread.
    • .task auto-cancels when the view disappears.
    • Actors protect shared mutable data from data races.

    🏆 Expert level: architecture & performance

    • MVVM is the common pattern: View (SwiftUI) ← ViewModel (state + logic) ← Repository (data) ← Network / Database. Inject dependencies through initialisers so you can test with fakes.
    • Modularisation with Swift Package Manager: feature modules compile faster and enforce boundaries.
    • Performance: keep body cheap, use LazyVStack/List for long data, give identifiable data stable IDs, avoid heavy work in body. Profile with Instruments (Time Profiler, Allocations, SwiftUI template).
    • Memory: avoid retain cycles in closures with [weak self] (mainly in class-based code).
    • Testing: unit tests (Swift Testing / XCTest), UI tests (XCUITest), previews as visual checks.

    • C @Published

    Q. Why is @MainActor used on a view model?
    • A To run code in the background
    • B To ensure UI-related state changes happen on the main thread
    • C To cache images
    • D To sign the app

    Kotlin & Jetpack Compose (Android)

    Kotlin fundamentals, declarative UI with Compose, state, ViewModel, navigation and architecture.

    🤖 What are Kotlin, Compose and Views?

    Kotlin is Google's preferred language for Android: concise, null-safe and works with Java. Jetpack Compose is Android's modern declarative UI toolkit. The older View system uses XML layouts and is still found in many apps.

    Jetpack ComposeXML Views
    StyleDeclarative Kotlin functionsXML layouts + imperative code
    StateUI recomposes when state changesYou call setText(), notifyDataSetChanged()
    ListsLazyColumnRecyclerView + adapter
    TodayRecommended for new appsMaintain legacy; interop with AndroidView / ComposeView

    Key building blocks (all apps): Activity (a screen host), Manifest (declares app, permissions), Gradle (build system), Resources (strings, images, themes).

    EXAMPLE · Recomposition

    When count changes, Compose recomposes only the composables that read it. remember keeps the value across recompositions; rememberSaveable also survives rotation and process death.

    🔄 State, ViewModel & lists (intermediate)

    ToolPurpose
    remember { mutableStateOf() }Local UI state inside a composable
    rememberSaveableLocal state that survives configuration change / process death
    State hoistingMove state up; pass value + onChange lambda down (makes composables reusable and testable)
    ViewModelHolds screen state; survives rotation; talks to repositories
    StateFlow + collectAsStateWithLifecycle()Stream of state from ViewModel to UI, lifecycle-aware
    kotlinclass TaskViewModel : ViewModel() {
    private val _tasks = MutableStateFlow<List<String>>(emptyList())
    val tasks: StateFlow<List<String>> = _tasks.asStateFlow()

    fun add(title: String) { _tasks.update { it + title } }
}

@Composable
fun TaskScreen(vm: TaskViewModel = viewModel()) {
    val tasks by vm.tasks.collectAsStateWithLifecycle()
    var text by rememberSaveable { mutableStateOf("") }

    Column(Modifier.fillMaxSize().padding(16.dp)) {
        LazyColumn(Modifier.weight(1f)) {
            items(tasks) { Text(it, Modifier.padding(8.dp)) }
        }
        Row {
            OutlinedTextField(text, { text = it }, Modifier.weight(1f))
            Button(onClick = { vm.add(text); text = "" }) { Text("Add") }
        }
    }
}

    🧭 Navigation & lifecycle

    Navigation Compose maps routes to screens with a NavHost and NavController. Use typed routes and pass only IDs, not whole objects.

    kotlinval nav = rememberNavController()
NavHost(nav, startDestination = "list") {
    composable("list") { ListScreen(onOpen = { id -> nav.navigate("detail/$id") }) }
    composable("detail/{id}") { entry ->
        DetailScreen(id = entry.arguments?.getString("id").orEmpty())
    }
}
    Activity callbackWhenTypical use
    onCreateCreatedSet content, init
    onStart / onResumeVisible / interactiveStart camera, sensors
    onPause / onStopLosing focus / hiddenStop updates, save state
    onDestroyFinishing or rotatingRelease resources
    ⚠️
    Rotation recreates the Activity. State kept only in a plain variable is lost — keep it in a ViewModel or rememberSaveable.

    🏆 Expert level: architecture & performance

    • Architecture: UI layer (Compose + ViewModel) → Domain (optional use cases) → Data layer (repositories, Room, Retrofit). Single source of truth, unidirectional data flow.
    • Dependency injection: Hilt (or Koin) for ViewModels and repositories.
    • Recomposition performance: use stable/immutable types, key in lazy lists, derivedStateOf, avoid creating objects in composables, defer state reads. Inspect with Layout Inspector and Compose compiler reports.
    • Startup & size: Baseline Profiles, R8 shrinking, App Startup library, Android App Bundle.
    • Testing: JUnit + Turbine for flows, Compose UI tests, Espresso for Views.

    Module 04 · Flutter

    Flutter (Dart)

    Dart fundamentals, the widget model, layout, state management, navigation and the rendering engine.

    🐦 What are Flutter and Dart?

    Flutter is Google's open-source UI toolkit for building iOS, Android, web and desktop apps from one codebase. It is written in Dart. Flutter does not use the platform's native buttons; it draws every pixel itself using its own rendering engine (Impeller, replacing Skia on modern platforms), so your UI looks identical everywhere.

    ✅ Strengths

    Single codebase, hot reload, consistent UI, rich widget library, high performance (compiled to native ARM code), great for custom branded design.

    ⚠️ Trade-offs

    Larger app size, Dart is a smaller ecosystem than JS, new OS UI features need plugin updates, native look needs extra effort.

    WidgetEverything in Flutter is a widget: a button, padding, the whole screen. Widgets are immutable descriptions of UI.
    Hot reloadInject changed code into the running app in under a second, keeping state.
    pub.devThe package repository for Dart/Flutter. Dependencies are listed in pubspec.yaml.
    JIT / AOTDebug uses JIT (fast reload); release uses AOT (fast native code).

    🧱 Widgets, layout & your first app

    Flutter UI is a widget tree. StatelessWidget has no changing data. StatefulWidget owns a State object and calls setState() to rebuild.

}

  @override

    🏆 Expert level: rendering, performance & architecture

    • Three trees: Widget tree (cheap config) → Element tree (live instances) → RenderObject tree (layout & paint). Rebuilding widgets is cheap; layout and paint are what cost.
    • Rebuild control: use const constructors, split big build methods into small widgets, scope listeners narrowly (select), use Keys in reorderable lists.
    • Jank: stay inside the ~16 ms frame budget (60 fps) or ~8 ms (120 Hz). Profile in DevTools in profile mode; fix shader warm-up, big images (use cache sizes), expensive saveLayer / opacity.
    • Architecture: feature-first folders; layers UI → state (notifier/Bloc) → repository → data sources; dependency injection with Riverpod/get_it; immutable models (freezed).
    • Testing: unit, widget tests (testWidgets), integration tests, golden tests for pixel checks.

    React Native (TypeScript)

    Components, hooks, TypeScript types, styling, navigation, Expo and the New Architecture.

    ⚛️ What is React Native?

    React Native lets you build iOS and Android apps with React and TypeScript. Your JavaScript code describes the UI, and React Native renders real native views (a <Text> becomes UILabel on iOS and TextView on Android). So the app feels native while most code is shared.

    ComponentA function that returns UI. Components are reusable and composable.
    JSX / TSXXML-like syntax inside JavaScript / TypeScript describing UI.
    PropsInputs passed into a component by its parent (read-only).
    StateData owned by a component that changes over time and triggers re-render.
    HookA function such as useState that lets components use state and effects.
    MetroThe JavaScript bundler used by React Native.
    HermesThe JavaScript engine optimised for mobile; precompiles to bytecode for faster startup.
    ExpoA framework and toolchain on top of React Native (builds, OTA updates, ready modules).
    Expo (recommended start)Bare React Native CLI
    Setupnpx create-expo-app, run instantlyManage Xcode / Android Studio projects yourself
    Native codeConfig plugins & dev builds, can add custom native modulesFull direct access
    BuildsEAS Build in cloud (no Mac needed for iOS builds)Local or your own CI
    UpdatesEAS Update (OTA JS updates)Self-hosted / third party

    • Structure: feature folders (features/auth, features/feed) with components, hooks, api, types.

    🏆 Expert level: New Architecture, performance & native code

    • Old vs New Architecture. The old architecture used an asynchronous bridge that serialised JSON between JS and native. The New Architecture uses JSI (direct synchronous calls from JS to native), Fabric (new renderer), TurboModules (lazy native modules) and Codegen (type-safe interfaces).
    • Performance: avoid unnecessary re-renders (React.memo, stable props), tune FlatList (getItemLayout, windowSize, smaller items) or use FlashList, run animations on the UI thread with Reanimated, keep heavy work off the JS thread, use Hermes, inspect with React DevTools and the profiler.
    • Native modules: when a feature is missing, write a TurboModule/Expo module in Swift/Kotlin and call it from TypeScript.
    • Quality: strict TypeScript, ESLint, Jest + React Native Testing Library, Detox/Maestro for end-to-end tests, Sentry for crashes.

    💬 Interview questions — basic to expert

    Basic

    What is the difference between native and cross-platform development?
    Native uses each platform's own language and SDK (Swift/Kotlin) for the best performance and immediate API access; cross-platform shares one codebase (Flutter, React Native) to save time and cost, with some trade-offs in native feature access and size.
    What is the difference between declarative and imperative UI?
    Imperative: you create views and mutate them step by step. Declarative: you describe the UI for the current state and the framework updates the screen. SwiftUI, Compose, Flutter and React are declarative.
    What happens when a user rotates the phone on Android?
    The Activity is destroyed and recreated by default. State in plain variables is lost; keep it in a ViewModel or rememberSaveable (or handle the configuration change yourself).

    Intermediate

    Explain state vs props (React Native) or StatelessWidget vs StatefulWidget (Flutter).
    Props / constructor parameters are inputs from the parent and are read-only; state is data owned inside the component that triggers a rebuild when it changes. Lift state up when siblings need it.
    How do you avoid unnecessary UI re-renders?
    Keep state close to where it is used, split big components, use immutable data and stable keys, memoise (React.memo, const widgets, remember/derivedStateOf), and select only the needed slice of shared state.
    How would you structure a medium-sized app?
    Feature-based modules; UI layer with ViewModel/state holder; repository layer as single source of truth merging remote and local data; dependency injection; shared design system; separate environments (dev/staging/prod).

    Expert

    Why can a Flutter or React Native list drop frames and how do you fix it?
    Work on the UI/JS thread exceeds the frame budget (16 ms at 60 fps): heavy build/render, large images, non-lazy lists, expensive layouts. Fix with lazy builders, fixed item extents, image resizing/caching, isolating heavy computation (isolates / worker threads), Reanimated/native-driven animations, and profiling a release/profile build.
    Explain the React Native New Architecture.
    JSI lets JS call native code directly and synchronously, Fabric is the new renderer that can render synchronously and supports concurrent React features, TurboModules load native modules lazily with typed Codegen interfaces, and Hermes runs precompiled bytecode.
    How do you decide when to drop to native code in a cross-platform app?
    When you need a platform API without a mature plugin, hard real-time or GPU work, platform-specific UI (widgets, Live Activities, Wear), or measured performance problems. Isolate it behind a typed interface (platform channel / TurboModule / Pigeon) so the rest of the app stays shared.

    Module 01 · Foundations

    What is Mobile Networking?

    Start from zero: how a phone talks to a server, the main API styles, and the vocabulary.

    📡 What is mobile networking?

    A mobile app rarely works alone. It asks a server for data (feeds, profiles, orders) and sends data back. This conversation over the internet is networking. Unlike a website on Wi-Fi, a phone moves between 5G, 4G, Wi-Fi and no signal at all, so mobile networking must be built for slow, flaky and expensive connections.

    🔴 Naive app

    Calls the API on the UI thread, shows a spinner forever, crashes or goes blank when offline.

    🟢 Resilient app

    Shows cached data instantly, fetches in the background, queues writes offline, retries safely.

    🧩 Types of networking

    Request/response over HTTP is the base. On top of it you choose a style:

    StyleWhat it isBest for
    RESTResources at URLs, verbs like GET/POSTMost CRUD apps, simple caching
    GraphQLOne endpoint; client asks for exact fieldsComplex screens, many clients
    WebSocket / SSELong-lived connection, server pushesChat, live scores
    gRPCBinary Protobuf over HTTP/2Internal, high-throughput services
    Push (FCM/APNs)Server wakes the app via the OSAlerts, silent sync triggers
    💡
    This module focuses on REST, GraphQL, offline sync and background workers — the core of most production apps.

    🔬 How one request works

    DNS lookup → TCP/QUIC connect → TLS handshake → HTTP request → server work → response → parse → update UI. Every step can fail or be slow on mobile.

    HTTPGET /v1/orders?limit=20 HTTP/2
Host: api.shop.com
Authorization: Bearer <token>
Accept: application/json

HTTP/2 200 OK
Content-Type: application/json
ETag: "a91f"
{"items":[...],"next":"cursor_20"}

    📖 Key terms

    LatencyTime for a request to get a response.
    BandwidthAmount of data per second the link can carry.
    PayloadThe body of a request or response (usually JSON).
    TimeoutHow long to wait before giving up.
    IdempotentRepeating the call gives the same result as doing it once.
    SerializationConverting objects to/from JSON or Protobuf.
    Connectivity stateOnline, offline, metered, or captive-portal.
    Q. Why must mobile apps assume the network is unreliable?
    • A Servers are slow
    • B Phones switch networks and lose signal
    • C JSON is large
    • D HTTP is old

    Module 02 · REST Consumption

    Consuming REST APIs

    From a first GET request to caching, retries and idempotency — how production apps call REST.

    🧭 What is REST?

    REST models data as resources (/users/7) and uses HTTP verbs to act on them. It is stateless: each request carries everything the server needs (token, params).

    VerbPurposeIdempotent?Typical status
    GETReadYes200
    POSTCreateNo201
    PUTReplaceYes200/204
    PATCHPartial updateUsually200
    DELETERemoveYes204
    StatusMeaningApp should…
    2xxSuccessParse and show
    401UnauthorizedRefresh token, retry once
    404Not foundShow empty/missing state
    429Rate limitedWait for Retry-After
    5xxServer errorRetry with backoff

    🛠️ Basic: making calls

    Never call the network on the main/UI thread. Use your platform client and map JSON to typed models.

    Kotlin · Retrofitinterface Api {
  @GET("orders") suspend fun orders(@Query("limit") n:Int): Page<Order>
  @POST("orders") suspend fun create(@Body o: NewOrder): Order
}
val orders = try { api.orders(20) } catch (e: IOException) { showOffline() }
    Swift · URLSessionlet (data, resp) = try await URLSession.shared.data(from: url)
guard (resp as! HTTPURLResponse).statusCode == 200 else { throw ApiError.bad }
let page = try JSONDecoder().decode(Page<Order>.self, from: data)
    EXAMPLE · Loading states

    Model every screen as Loading → Success(data) → Error(retry). Never leave the user with a blank screen.

    ⚙️ Intermediate: pagination, errors, auth

    • Pagination: offset (?page=2) is simple but breaks on changing data; cursor (?after=abc) is stable — prefer it for feeds.
    • Interceptors: one place to add auth headers, logging, and refresh an expired token on 401.
    • Timeouts: set connect (~10s), read (~30s) and overall limits.
    • Error model: parse server error bodies into typed errors (network, HTTP, validation).
    Q. Which pagination style is safest for a live feed?
    • A Offset
    • B Cursor
    • C Random
    • D None

    🚀 Expert: caching, retries, idempotency

    • HTTP caching: send If-None-Match: "a91f"; server replies 304 with no body — saves data.
    • Retry policy: exponential backoff with jitter (1s, 2s, 4s + random). Retry only idempotent calls and 5xx/timeouts.
    • Idempotency keys: send Idempotency-Key: uuid on POST so a retried payment is not charged twice.
    • Compression & size: gzip/brotli, field filtering, image resizing on the CDN.
    • Versioning: /v2/ or headers; handle unknown JSON fields gracefully.
    Kotlinsuspend fun <T> retry(times:Int=3, block: suspend()->T):T {
  var d=1000L
  repeat(times-1){ try { return block() } catch(e:IOException){ delay(d+Random.nextLong(300)); d*=2 } }
  return block()
}
    ⚠️
    Blindly retrying a non-idempotent POST can create duplicates. Use an idempotency key.
    ✍️ Why is a 304 response valuable on mobile?
    Model answer: It confirms cached data is still fresh without re-downloading the body, saving battery, data and time.

    Module 03 · GraphQL Consumption

    Consuming GraphQL

    Ask for exactly the data a screen needs — from first query to normalized caching and persisted queries.

    🧭 What is GraphQL?

    GraphQL is a query language and runtime where the client sends one query to a single endpoint (POST /graphql) describing the exact fields it wants. A typed schema defines what is available.

    OperationUseREST analogy
    QueryRead dataGET
    MutationChange dataPOST/PUT/DELETE
    SubscriptionLive updates over WebSocketWebSocket/SSE
    GraphQLquery Home($id: ID!) {
  user(id: $id) { name avatarUrl
    orders(first: 3) { id total status } }
}

    ⚖️ REST vs GraphQL

    RESTGraphQL
    EndpointsManyOne
    Over-fetchingCommonAvoided
    Round trips per screenOften severalUsually one
    HTTP cachingEasy (GET + ETag)Harder (POST)
    ErrorsHTTP status200 + errors array
    Learning curveLowMedium
    📝
    GraphQL returns HTTP 200 even on partial failure. Always check the errors field.

    🛠️ Basic → Intermediate: in the app

    Use a typed client (Apollo Kotlin/iOS, urql, Relay). Write .graphql files; the tool generates type-safe models.

    Kotlin · Apolloval r = apollo.query(HomeQuery(id="7")).execute()
r.data?.user?.let(::render)
r.errors?.let(::report)
    EXAMPLE · Variables, fragments

    Use variables (never string-concatenate) and fragments so each UI component declares its own data needs.

    🚀 Expert: caching and performance

    • Normalized cache: objects stored by __typename:id, so updating a user once updates every screen.
    • Fetch policies: cache-first, network-only, cache-and-network.
    • Persisted queries: send a hash instead of the full query to cut bytes and block arbitrary queries.
    • Pagination: Relay-style edges/pageInfo/cursor.
    • Optimistic UI: update the cache instantly, roll back on error.
    • Watch out: N+1 resolvers, huge nested queries — ask backend for depth/complexity limits.
    Q. What does a normalized cache give you?
    • A Smaller schema
    • B One update refreshes the same entity everywhere
    • C Faster DNS
    • D No errors
    ✍️ When would you still choose REST over GraphQL?
    Model answer: Simple CRUD, heavy HTTP/CDN caching, file uploads/downloads, small team without GraphQL tooling.

    Module 04 · Offline Synchronization

    Offline-First & Sync

    Make the app useful with no signal: local storage, write queues, conflict resolution and delta sync.

    🧭 What is offline-first?

    In an offline-first app the local database is the source of truth for the UI. The network only synchronizes it with the server in the background. Users read and write instantly, with or without signal.

    UI ⇄ Repository ⇄ Local DB (Room / Core Data / SQLite)
    ↕ Sync engine ⇄ API

    🗂️ Basic: caching strategies

    StrategyHow it worksUse for
    Cache-firstRead local; fetch only if missingStatic content
    Network-firstTry network; fall back to cacheFresh-critical data
    Stale-while-revalidateShow cache now, refresh and updateFeeds, profiles
    Write-throughWrite local + server togetherSimple apps

    Storage options: key-value (SharedPreferences/UserDefaults), SQLite wrappers (Room, GRDB, Realm), file cache for media.

    📬 Intermediate: the outbox pattern

    Offline writes are saved locally and added to an outbox queue. A sync worker sends them when online, in order, with retries.

    Kotlin@Entity data class Outbox(@PrimaryKey val id:String, val op:String,
  val json:String, val tries:Int=0, val createdAt:Long)
// 1. save note locally  2. insert Outbox row (one transaction)
// 3. worker POSTs with Idempotency-Key = id, deletes row on success
    💡
    Use client-generated UUIDs so records have a stable id before the server ever sees them.

    ⚔️ Expert: conflicts and delta sync

    A conflict happens when two devices edit the same record offline.

    ApproachIdeaTrade-off
    Last-write-winsNewest timestamp winsSimple; can lose edits
    Field-level mergeMerge non-overlapping fieldsMore logic
    Version / ETag checkServer rejects stale update (409), client resolvesNeeds UI/rules
    CRDTsMath guarantees convergenceComplex, storage overhead
    • Delta sync: ask GET /changes?since=token instead of everything; keep a per-collection sync token.
    • Tombstones: mark deletes (deleted_at) so they sync to other devices.
    • Don’t trust device clocks: prefer server versions or logical/hybrid clocks.
    • Migrations & partial failure: sync must be resumable and safe to run twice.
    Q. Why use tombstones for deletes?
    • A To save disk
    • B So deletions can propagate to other devices
    • C To speed up queries
    • D To encrypt data
    ✍️ Why is LWW risky with device timestamps?
    Model answer: Device clocks can be wrong or manipulated, so an old edit may overwrite a newer one. Use server-assigned versions.

    Module 05 · Background Workers

    Background Work

    Run uploads, sync and refresh reliably even when the app is closed — within OS limits.

    🧭 What are background workers?

    A background worker is a task the OS runs for your app when it is not on screen — syncing the outbox, uploading photos, refreshing data. Mobile OSes aggressively limit this to save battery, so you request work and the system decides when.

    🧰 Types and platform tools

    NeedAndroidiOS
    Deferrable, guaranteedWorkManagerBGProcessingTask
    Periodic refreshPeriodicWorkRequest (≥15 min)BGAppRefreshTask
    Long upload/downloadWorkManager + foreground serviceBackground URLSession
    Push-triggered syncFCM high-priority data messageSilent push (content-available)
    Exact-time user alarmAlarmManagerLocal notification
    ⚠️
    Never rely on a background timer or a long-running thread. The OS will kill it.

    🛠️ Basic → Intermediate: a sync worker

    Kotlin · WorkManagerclass SyncWorker(c:Context, p:WorkerParameters):CoroutineWorker(c,p){
  override suspend fun doWork() =
    try { repo.syncOutbox(); Result.success() }
    catch(e:IOException){ Result.retry() }
}
val req = OneTimeWorkRequestBuilder<SyncWorker>()
  .setConstraints(Constraints.Builder()
     .setRequiredNetworkType(NetworkType.CONNECTED).build())
  .setBackoffCriteria(BackoffPolicy.EXPONENTIAL,30,TimeUnit.SECONDS).build()
WorkManager.getInstance(ctx).enqueueUniqueWork("sync",ExistingWorkPolicy.KEEP,req)
    • Constraints: network, charging, battery-not-low.
    • Unique work: avoid duplicate syncs.
    • Result: success / retry / failure drives backoff.

    🚀 Expert: limits, reliability, battery

    • Doze / App Standby / Low Power Mode: work is batched and delayed; design for “eventually”.
    • iOS budgets: BG tasks have short time windows — save progress and finish in expirationHandler.
    • Chaining: split work into small resumable steps (upload chunk → confirm → delete local).
    • Metered networks: let users choose Wi-Fi-only for large uploads.
    • Observability: log run time, retries, failures; alert on stuck outboxes.
    • Combine: push says “something changed” → worker runs delta sync.
    Q. Who decides exactly when your background task runs?
    • A Your app
    • B The operating system
    • C The server
    • D The user
    ✍️ Why prefer WorkManager over a plain thread for uploads?
    Model answer: It survives process death and reboots, respects constraints and battery policies, and retries with backoff.

    Module 06 · Security & Reliability

    Secure, Fast, Observable

    Expert practices that apply across REST, GraphQL, sync and workers.

    🔐 Security

    🔒
    TLS only
    No cleartext HTTP; enforce ATS / network security config.
    📌
    Certificate pinning
    Pin public keys for high-risk apps; plan rotation.
    🗝️
    Token storage
    Keychain / Keystore, never plain prefs or logs.
    🔁
    Refresh flow
    Single-flight refresh so parallel 401s trigger one refresh.

    ⚡ Performance

    • Reuse connections (HTTP/2, HTTP/3), batch requests, compress, paginate.
    • Prefetch on Wi-Fi; cancel requests when screens close.
    • Use image CDNs with responsive sizes and disk caching.
    • Measure p50/p95 latency and payload size, not just averages.

    📈 Observability & testing

    • Add request IDs, structured logs, crash and network-error analytics.
    • Test with MockWebServer / URLProtocol stubs; simulate offline, slow 3G, and 500s.
    • Chaos test sync: kill the app mid-upload and verify recovery.
    Q. Why use a single-flight token refresh?
    • A Faster UI
    • B Parallel 401s should not trigger many refresh calls
    • C Smaller tokens
    • D Offline mode

    Apply everything: API calls, offline writes, sync and background work.

    📝 Scenario

    You are building NoteSync, a notes app used on trains and in basements. Users create and edit notes offline; notes must appear on all their devices without duplicates or lost edits.

    1️⃣ Task 1 · REST

    Q. Create-note POST times out. What is safest?
    • A Retry immediately forever
    • B Retry with backoff using the same Idempotency-Key
    • C Never retry
    • D Drop the note
    ✍️ List 3 fields every note should have for sync.
    Model answer: Client UUID id, server version/ETag (or updated_at from server), deleted_at tombstone — plus a dirty/sync-state flag locally.

    2️⃣ Task 2 · GraphQL

    ✍️ Write a query for the notes list screen needing only id, title, updatedAt (first 20).
    Model answer: query { notes(first:20){ edges{ node{ id title updatedAt } } pageInfo{ endCursor hasNextPage } } }

    3️⃣ Task 3 · Offline sync

    Q. Two devices edit the same note title offline. Best first strategy?
    • A Silently overwrite
    • B Server version check; on 409 merge by field or ask the user
    • C Delete both
    • D Ignore
    ✍️ Describe the steps from “user saves note offline” to “server has it”.
    Model answer: Save to local DB + outbox row in one transaction → UI updates instantly → worker runs when connected → POST with idempotency key → on success mark synced/remove outbox; on failure retry with backoff.

    4️⃣ Task 4 · Background worker

    ✍️ Choose tools and constraints for syncing on Android and iOS.
    Model answer: Android: unique WorkManager job, CONNECTED constraint, exponential backoff. iOS: BGAppRefreshTask/BGProcessingTask plus silent push. Save progress and handle expiration.

    5️⃣ Task 5 · Expert review

    ✍️ Name three failure scenarios you would test.
    Model answer: App killed mid-sync; offline for days then 500 notes queued; token expires during sync; server returns 429; duplicate retry; clock skew; schema migration with pending outbox.

1. Foundations of OOP

Before classes and objects existed, programs were just instructions in a row. This section traces how programming evolved from raw procedural code to structured modules to the object-oriented worldview — and explains why each shift happened.

1.1Programming Paradigm Evolution

A paradigm is a way of thinking about programs. Three major paradigms preceded modern OOP, each solving a problem the previous one created.

Figure 1.1 — Each paradigm answered a question the previous one couldn't.

1.1.1Procedural Programming

Programs are top-down: a main function calls smaller functions, which call smaller functions still. Code is organized around actions (verbs).

// Procedural style — payroll for one employee
float computeTax(float salary) { return salary * 0.2; }
float computeNet(float salary) { return salary - computeTax(salary); }
int main() {
    float salary = 50000;
    printf("Net: %f", computeNet(salary));
}
⚠️
Limitations Global data is accessible to every function — no boundaries. Adding a new field (say, bonus) means hunting down every function that touches a salary. Code grows linearly; complexity grows quadratically.

1.1.2Structured Programming

Dijkstra's "Goto Considered Harmful" (1968) pushed programmers toward three control structures: sequence, selection (if/else), and iteration (loops). Programs became modular — broken into reusable functions — but data and the functions that operated on it still lived apart.

Figure 1.2 — Structured programs separate what you have from what you do. Any function can corrupt any data.

1.1.3Object-Oriented Programming

OOP is bottom-up: identify entities in the problem domain (Account, Customer, Loan), wrap their data and behavior together, then compose the system from those entities. The shift is philosophical: nouns become first-class.

AspectProceduralObject-Oriented
Primary unitFunctionObject (class instance)
Data locationGlobal / passed aroundEncapsulated inside object
ReuseCopy-paste functionsInheritance, composition
Modeling style"What steps?""What things?"
CouplingHigh (shared state)Low (message passing)

1.2OOP Philosophy and Principles

1.2.1The Software Crisis

By the late 1960s, software projects were notoriously over-budget, late, and buggy — the "software crisis". Programs grew faster than humans could mentally track them. OOP became a leading response by promising three things:

♻️ Reusability
Write a class once; reuse via inheritance and composition across projects.
🔧 Maintainability
A change inside a class shouldn't ripple outside it (encapsulation barrier).
📈 Scalability
Add new types without rewriting old code (open/closed principle).

1.2.2Benefits — concrete

  • Modularity — a class is a unit you can test, version, and ship independently.
  • Data security — encapsulation makes invariants enforceable (a BankAccount can guarantee balance ≥ 0).
  • Real-world mapping — domain experts and programmers can share vocabulary: "the order has line items."
  • Extensibility — polymorphism lets you plug in new types behind the same interface.

1.3OOP Languages Landscape

Selection rule of thumb Choose Java/C# for enterprise apps, C++ for systems & performance, Python for scripting/ML/prototyping, Ruby for web DSLs. Language is a tool — match it to the problem.

2. Class & Object Fundamentals

A class is a blueprint. An object is the house built from that blueprint. The same drawing can produce many houses, each with its own paint color, but the same room layout.

2.1Classes

2.1.1Class Definition and Structure

A class declaration introduces a new user-defined type. The compiler then treats your class name like it would int or string — you can declare variables of that type, pass instances to functions, store them in collections.

# Python — a class as a blueprint
class Car:
    # class-level constant
    WHEELS = 4
    def __init__(self, brand, color):
        self.brand = brand        # instance attribute
        self.color = color
        self._speed = 0           # convention: leading _ = "private"
    def accelerate(self, delta):
        self._speed += delta

2.2.2Object Characteristics — Identity, State, Behavior

  • Identity — every object has a unique address. Two distinct Person("Alice") objects are not the same object.
  • State — current values of attributes. Mutable state changes over time.
  • Behavior — methods the object can perform.

2.2.3Object Comparison — == vs equals

🚨
Classic interview gotcha In Java, == compares references (same memory address). .equals() compares values. "hello" == "hello" may print true due to string interning, but new String("hello") == new String("hello") is false. Always use .equals() for value comparison.

2.3Constructors and Destructors

2.3.1Constructor Types

class Point {
    private int x, y;

    // 1. Default — no arguments
    Point() { x = 0; y = 0; }

    // 2. Parameterized
    Point(int x, int y) { this.x = x; this.y = y; }

    // 3. Copy constructor
    Point(Point other) { this(other.x, other.y); }  // chains to #2
}

2.3.2Constructor Chaining

this(...) calls another constructor of the same class. super(...) calls the parent's constructor. The parent constructor always runs first (initialization order: parent → child).

3. The Four Pillars of OOP

If OOP were a temple, these four columns hold up the roof. Remove any one and the whole structure becomes wobbly.

Figure 3.1 — A·E·I·P — the load-bearing pillars of every OO system.

3.1Abstraction

Abstraction is the act of showing only what matters. When you drive a car, you turn the steering wheel — you don't think about the rack-and-pinion mechanism, hydraulic fluid, or tie rods. The wheel is the abstraction.

3.1.1Concept and Purpose

  • Hides implementation complexity behind a clean interface.
  • Lets the implementation change without breaking callers.
  • Forces you to think in terms of what, not how.

3.1.2Types of Abstraction

Data abstraction
A Stack exposes push/pop/peek — you don't see the array or linked list inside.
Procedural abstraction
sort(list) — you don't care if it's quicksort or merge sort.
Control abstraction
for x in items abstracts the index, bounds, and increment.

3.1.3Implementation Mechanisms

// Java — abstraction via abstract class
abstract class PaymentMethod {
    public abstract void pay(double amount);   // no body
    public void log(String msg) { /* shared code */ }
}
class CreditCard extends PaymentMethod {
    public void pay(double amt) { /* call Stripe */ }
}

3.1.4Abstract Data Types (ADTs)

An ADT defines a contract — operations + behavior — without specifying implementation. Stack is an ADT: push, pop, peek, isEmpty. It can be implemented with an array, a linked list, or a deque.

3.2Encapsulation

Encapsulation = bundling data and the methods that operate on it inside a single capsule, plus controlling access to that data. Think of a medicine capsule: you don't open it to inspect the powder; you swallow the whole thing.

Figure 3.2 — The encapsulation barrier: callers interact via the public skin, not the private guts.
class BankAccount {
    private double balance;            // hidden

    public double getBalance() { return balance; }   // accessor

    public void deposit(double amt) {              // mutator with rule
        if (amt <= 0) throw new IllegalArgumentException();
        balance += amt;
    }
}
✅
Best practices Make fields private by default. Expose only the methods that respect invariants. Validate inside setters. Prefer immutability where the entity has no real-world identity (e.g., Money, Point).

3.3Inheritance

Inheritance models the IS-A relationship: a Dog is a Mammal; a SavingsAccount is an Account. The child class gets the parent's fields and methods automatically.

3.3.1–3.3.2Types of Inheritance

Figure 3.3 — Five inheritance shapes. Java/C# disallow multiple class inheritance to avoid the diamond ambiguity.

3.3.3Method Overriding & super

class Animal {
    public void speak() { System.out.println("some sound"); }
}
class Dog extends Animal {
    @Override
    public void speak() {
        super.speak();              // optional: call parent first
        System.out.println("woof!");
    }
}

3.3.4Inheritance Problems

💎 Diamond problem
Multiple inheritance + shared grandparent → which version of a method does D get from A?
🪨 Fragile base class
A change in the base class silently breaks subclasses. Test coverage is your only defense.
🔗 Tight coupling
Subclass depends on parent's internals. Refactoring the parent ripples downward.
🐦 Ostrich problem
Forcing inheritance where no real IS-A exists ("Square extends Rectangle" is the classic).

3.4Polymorphism

Greek for "many forms". The same method call behaves differently depending on the actual type of the object receiving it.

Figure 3.4 — One shape.draw() call; three different behaviors at runtime.

3.4.1Compile-Time Polymorphism (Static)

Resolved at compile time. Method overloading — same name, different parameters:

int    add(int a, int b)        { return a + b; }
double add(double a, double b)  { return a + b; }
String add(String a, String b)  { return a + b; }

3.4.2Runtime Polymorphism (Dynamic)

Resolved at runtime via method overriding + a parent reference:

Shape s = new Circle();   // upcast
s.draw();                  // calls Circle.draw() — picked at runtime!

3.4.3How It Works — VTables

The compiler builds a virtual method table for each class — an array of function pointers, one per overridable method. At runtime, the call s.draw() looks up vtable[0] on the object's actual class and jumps there. Cost: one extra pointer dereference per virtual call.

3.4.4Benefits

  • Eliminates long if/else or switch chains on type.
  • Enables plugin architectures — drop in a new class, the existing code works unchanged.
  • Foundation for many design patterns (Strategy, State, Template Method).

4. Advanced OOP Concepts

Once you've mastered the four pillars, the next layer adds runtime mechanics, generics, contracts, and inter-object communication — the gears that make OOP scale to large systems.

Binding = associating a method call with the actual code that runs.

4.1.2Virtual Method Resolution

Figure 4.1 — How a virtual call gets dispatched: object → vptr → vtable → code.

4.1.3Across Languages

  • C++ — opt in with virtual; non-virtual calls compile to direct addresses.
  • Java — every non-final, non-static, non-private method is dynamically dispatched.
  • Python — duck typing: "if it walks like a duck and quacks like a duck…" The interpreter looks up the method by name on the actual object every call.

4.2Message Passing

Alan Kay (who coined "object-oriented") said the big idea wasn't objects — it was messaging. An object is an autonomous agent; calling a method is sending it a message: "please do X."

account.deposit(100)        # message: "deposit 100" → receiver: account

4.2.2Synchronous vs Asynchronous

Synchronous blocking
Caller waits for the receiver to respond. Standard method call: order.checkout().
Asynchronous non-blocking
Caller fires the message and continues. Implemented via events, promises, queues (Kafka, RabbitMQ).

4.4Generics and Templates

Generics let you write a class or method that works with any type, while keeping compile-time type safety.

// Java generics
class Box<T> {
    private T value;
    public void set(T v)  { value = v; }
    public T    get()    { return value; }
}

Box<Integer> ib = new Box<>();   // only ints allowed
ib.set(42);
String s = ib.get();              // COMPILE ERROR — caught early

4.4.3Advanced

  • Bounded type parameters — <T extends Comparable<T>> means "any T that is comparable."
  • Wildcards — List<? extends Number> reads any number subtype; List<? super Integer> writes integers.
  • Type erasure (Java) — List<String> and List<Integer> are the same at runtime; generics are a compile-time check only.
  • C++ templates — true code generation. vector<int> and vector<string> are different machine code.

4.5Covariance, Contravariance & Return Types advanced

When a subclass overrides a method, how far can it deviate from the parent's signature? Two rules govern this, and interview panels love testing whether you know the difference.

📥 Covariant return types
An override may return a narrower (more specific) type than the parent declared. Safe, because callers expecting the parent type still get something compatible.
📤 Contravariant parameters
In theory, an override could accept a wider parameter type and still be safe. Java/C++ don't allow this for overriding (it becomes overloading instead); C# and Kotlin support it via in/out generics.
class Animal { Animal reproduce() { return new Animal(); } }

class Cat extends Animal {
    @Override
    Cat reproduce() { return new Cat(); }   // ✅ covariant return — narrower type, legal in Java
}
⚠️
Why parameters can't be contravariant on override in Java If Animal.feed(Food f) were overridden as Cat.feed(Object o), the compiler treats it as an overload, not an override — the vtable slot for feed(Food) is untouched, silently breaking polymorphism. This is why @Override exists: it forces a compile error if the signature doesn't actually match.

4.6Double Dispatch & the Visitor Pattern advanced

Normal virtual calls are single dispatch — the method chosen depends on the runtime type of one object (the receiver). Some problems need the decision to depend on two runtime types at once — e.g. "how does a Circle collide with a Square?" That needs double dispatch, and OOP fakes it with the Visitor pattern.

interface Shape { void accept(Visitor v); }
class Circle implements Shape {
    public void accept(Visitor v) { v.visit(this); }   // dispatch #1: which shape?
}
interface Visitor {
    void visit(Circle c);   // dispatch #2: overload resolved on Circle at compile time
    void visit(Square s);
}

The first call (shape.accept(visitor)) dispatches on the shape's runtime type. Inside accept, calling v.visit(this) dispatches again — this time on this's compile-time type inside that method, which correctly resolves to the matching overload. Two single-dispatch calls chained together simulate true double dispatch. This is the mechanism behind serializers, AST compilers, and collision-detection engines.

4.7Object Slicing & Late-Binding Pitfalls gotcha

🔪
C++ object slicing Animal a = Cat(); copies only the Animal portion of the Cat object into a — the Cat-specific data and vtable pointer are "sliced off." Polymorphism silently breaks. The fix: always pass/store polymorphic objects by pointer or reference (Animal& a = cat; or unique_ptr<Animal>), never by value.
🏗️
Calling virtual methods from a constructor In C++ and Java, calling an overridable method inside a base-class constructor does not invoke the subclass's override — the derived part of the object hasn't been constructed yet, so the object briefly behaves as its base type. This is a classic bug source in framework base classes; most style guides ban virtual calls from constructors/destructors entirely.

5. Composition vs Inheritance

Two ways to build complex things from simple ones. Inheritance says "I am a"; composition says "I have a." Choosing wrong is the source of many design disasters.

5.1Composition Fundamentals

Composition = HAS-A. A Car has an Engine. The engine is an object stored as a field of the car.

class Engine { void start() { /*...*/ } }

class Car {
    private Engine engine = new Engine();   // HAS-A
    public void start() { engine.start(); }    // delegates
}

5.1.2Strong Composition vs Aggregation

Figure 5.1 — UML diamond fill encodes lifetime: filled = part dies with whole; hollow = part outlives whole.

5.2Composition vs Inheritance — How to Choose

5.2.1Choose Inheritance When…

  • The relationship is genuinely IS-A, not "kind-of-similar-to."
  • The subtype could be passed wherever the supertype is expected (Liskov Substitution).
  • The hierarchy is stable — you don't expect frequent restructuring.

5.2.2Choose Composition When…

  • The relationship is HAS-A or "USES-A."
  • You need to combine behaviors that don't fit a single hierarchy (a Duck that flies and swims).
  • Behavior should be swappable at runtime (think Strategy pattern).

5.2.3"Favor Composition Over Inheritance"

From Design Patterns (Gang of Four) — possibly the most important sentence in OOP design.

🏛️
Why composition usually wins Inheritance is a compile-time, white-box reuse mechanism — the subclass sees the parent's internals. Composition is runtime, black-box — you only see the public interface. Loose coupling = easier to test, swap, and refactor.
// ❌ Bad — inheritance for code reuse only
class Stack extends ArrayList<Integer> { /* leaks add(int, x), get(i)… */ }

// ✅ Good — composition
class Stack {
    private ArrayList<Integer> data = new ArrayList<>();
    public void push(int v) { data.add(v); }
    public int  pop()       { return data.remove(data.size() - 1); }
}

6. SOLID Principles

Five rules from Robert C. Martin ("Uncle Bob") that turn OOP code from a tangle into a system. The acronym is mnemonic gold.

Figure 6.1 — Five letters, five principles, one healthier codebase.

6.1Single Responsibility (SRP)

"A class should have one, and only one, reason to change."
// ❌ Two responsibilities — calculation AND persistence
class Invoice {
    double calculateTotal() { /*...*/ }
    void   saveToDB()       { /*...*/ }
    void   printPDF()       { /*...*/ }
}

// ✅ Each class has one job
class Invoice           { double calculateTotal() {} }
class InvoiceRepository { void save(Invoice i) {} }
class InvoicePrinter    { void print(Invoice i) {} }

6.2Open/Closed (OCP)

"Open for extension, closed for modification."

Adding a new behavior shouldn't force you to edit existing, tested code. Achieved through abstraction (interfaces, abstract classes, the Strategy pattern).

// New shape? Just implement Shape — never touch the renderer.
interface Shape { double area(); }
class Renderer {
    double totalArea(List<Shape> shapes) {
        return shapes.stream().mapToDouble(Shape::area).sum();
    }
}

6.3Liskov Substitution (LSP)

"Any subtype must be usable wherever its supertype is expected — without surprises."
📐
Classic violation: Square extends Rectangle Mathematically a square is a rectangle. But if Rectangle.setWidth(5) is supposed to change only width, Square.setWidth(5) must also change height to stay square — breaking the parent's contract.

6.4Interface Segregation (ISP)

"Don't force clients to depend on methods they don't use."
// ❌ A "fat" interface — Robot can't eat or sleep
interface Worker { void work(); void eat(); void sleep(); }

// ✅ Segregated — pick what fits
interface Workable { void work(); }
interface Eatable  { void eat(); }
interface Sleepable { void sleep(); }
class Robot implements Workable { /* only work */ }

6.5Dependency Inversion (DIP)

"Depend on abstractions, not on concrete classes."
Figure 6.2 — High-level code stops depending on low-level details. Both meet at the interface.
interface Database { void save(Order o); }

class OrderService {
    private final Database db;
    public OrderService(Database db) { this.db = db; }   // injected
}

7. Design Patterns

Patterns are reusable solutions to recurring design problems — the vocabulary experienced developers use to talk about architecture. The Gang of Four (GoF) catalog of 23 patterns is the canonical reference.

Figure 7.1 — GoF's three families of patterns.

7.1Creational Patterns

7.1.1Singleton

Guarantees a class has exactly one instance and provides a global access point. Useful for caches, loggers, configs.

public class Logger {
    private static Logger instance;
    private Logger() {}                       // private ctor
    public static synchronized Logger getInstance() {
        if (instance == null) instance = new Logger();
        return instance;
    }
}

7.1.2Factory Method

Defers instantiation to a method, so callers don't new concrete classes directly.

abstract class DialogFactory {
    abstract Dialog createDialog();          // factory method
    void render() { createDialog().show(); }
}
class WindowsFactory extends DialogFactory {
    Dialog createDialog() { return new WindowsDialog(); }
}

7.1.3Builder

Constructs complex objects step-by-step with a fluent interface. Useful when an object has many optional fields.

Pizza p = new Pizza.Builder()
    .size("large").cheese(true).pepperoni(true).olives(false)
    .build();

7.1.4Prototype

Create new objects by cloning an existing one — useful when construction is expensive. Distinguishes shallow (copy references) vs deep (recursively copy contents) cloning.

7.3Behavioral Patterns

7.3.1Strategy

Encapsulate interchangeable algorithms behind a common interface. Swap them at runtime.

interface SortStrategy { <T> void sort(List<T> data); }
class QuickSort  implements SortStrategy { /*...*/ }
class MergeSort  implements SortStrategy { /*...*/ }

class Sorter {
    private SortStrategy strategy;
    public void setStrategy(SortStrategy s) { this.strategy = s; }
}

7.3.2Observer

One-to-many dependency: when the subject changes state, all observers are notified. Foundation of event systems and reactive frameworks.

Figure 7.2 — Observer: subject fans out updates to all subscribers.

7.3.3 – 7.3.7Quick reference

Iterator
Walk a collection without exposing its structure. Built into Python (__iter__) and Java (Iterable).
Template Method
Parent defines the skeleton; child fills in steps. HttpServlet.service() is a textbook case.
Command
Encapsulate a request as an object — enables undo, queueing, logging. Used in editor apps.
State
Object's behavior changes when its internal state changes. Models a state machine cleanly.
Chain of Responsibility
Pass a request along a chain until one handler accepts. Used in middleware (Express, ASP.NET).

9. Practical Implementation

Theory meets keyboard. How major OOP languages differ, how to handle errors object-oriented-ly, and the conventions that signal "this code was written by a professional."

9.1Language-Specific OOP

9.1.1Java

  • Single inheritance for classes, multiple for interfaces.
  • Packages (com.company.module) provide namespacing + access control.
  • Annotations (@Override, @Deprecated) + reflection power frameworks like Spring.
  • Garbage-collected; everything except primitives is heap-allocated.

9.1.2C++

  • Multiple inheritance allowed (with virtual base classes for diamond).
  • Templates — most powerful generic system; STL is built on it.
  • RAII — destructors run deterministically when objects leave scope; no GC needed.
  • Programmer controls memory — power and footguns.

9.1.3Python

  • Duck typing — if it has the method, it works. No interfaces needed.
  • Dunder methods (__init__, __str__, __add__) hook into language operators.
  • Multiple inheritance with the C3 MRO (Method Resolution Order) algorithm.
  • Properties via @property decorator.
class Vector:
    def __init__(self, x, y): self.x, self.y = x, y
    def __add__(self, o):  return Vector(self.x+o.x, self.y+o.y)
    def __repr__(self):    return f"({self.x},{self.y})"

v = Vector(1,2) + Vector(3,4)   # operator overloading via dunder

9.1.4C#

  • Properties + indexers — clean syntax for getters/setters.
  • Delegates & events — type-safe function pointers, native pub-sub.
  • LINQ brings query syntax + functional flavor to OOP collections.
  • Extension methods add behavior to types you don't own.

10. Modern & Advanced OOP

Where OOP meets concurrency, functional programming, and the realities of large-scale software. The frontier where the four pillars are no longer enough.

10.1Concurrent OOP

Threads make everything harder. An object's invariants must hold even when two threads poke at it simultaneously.

🔒 Synchronization
Mutexes / synchronized blocks serialize access to shared state.
🧊 Immutability
If state never changes, no synchronization is needed. Java's String, Integer, records.
🎭 Actor Model
Each actor has private state + a mailbox. No shared memory; communicate via messages. Erlang, Akka.
⚛️ Atomic primitives
AtomicInteger, compareAndSet for lock-free patterns.

10.5Anti-Patterns to Avoid

👹 God Object
A class that does everything. Smell: 2000+ lines, 50+ methods. Fix: split by responsibility (SRP).
🩸 Anemic Domain Model
Classes are just bags of getters/setters; logic lives in service classes. Reverts to procedural.
🔁 Circular Dependencies
A↔B can't be compiled or unit-tested independently. Break the cycle with an interface.
🪀 Yo-yo Problem
Inheritance hierarchy so deep you scroll up and down to follow the logic.
🛬 Premature Abstraction
Building a flexible framework before you have two real use cases. Wait until duplication appears.
🪞 Feature Envy
Method uses another class's data more than its own. The method belongs in the other class.

10.6Object Lifecycle & Memory Models Across Languages advanced

Every OOP language answers the same question differently: who destroys an object, and when? Understanding this is the difference between an intermediate developer and one who can debug production memory leaks.

🧠
The interview-ready explanation "An object's fields die with strategy X; therefore, in language Y, I must be careful about Z." For Java: fields live until no GC root reaches them — so unregister listeners and clear static collections. For Python: watch for circular references holding onto expensive resources (file handles, sockets) — prefer with blocks and context managers. For C++: prefer stack allocation and smart pointers over raw new/delete.

10.6.2Weak References & Caches

Sometimes you want to reference an object without keeping it alive — e.g. a cache that should let entries be garbage-collected under memory pressure.

  • Java — WeakReference<T>, WeakHashMap for listener registries and caches.
  • C++ — std::weak_ptr, typically paired with a shared_ptr owner to break cycles (e.g. parent↔child tree nodes).
  • Python — weakref.ref(obj); used internally by functools.lru_cache-style patterns.

Frequently Asked Questions

Q1. What is the difference between a class and an object?
A class is a blueprint — it defines structure (fields) and behavior (methods) but consumes no runtime memory by itself. An object is an instance created from that blueprint; each instance has its own field values and lives in memory. One class can produce many objects.
Q2. Explain the four pillars of OOP with one-line examples.
  • Abstraction — show what, hide how. List.add() doesn't reveal whether it's an array or linked list.
  • Encapsulation — bundle + protect. BankAccount with private balance + public deposit().
  • Inheritance — IS-A reuse. Dog extends Animal.
  • Polymorphism — one call, many forms. shape.draw() draws a circle or square.
Q3. Abstract class vs Interface — when do you choose which?
Use an abstract class when sub-types share code as well as a contract (e.g., HttpServlet). Use an interface when unrelated classes need to share a capability (e.g., Comparable). Java 8+ blurred the line — interfaces can have default methods, but they still cannot hold mutable state.
Q4. What is method overloading vs method overriding?
Overloading — same method name, different parameter list, same class, resolved at compile time. Overriding — same signature, defined in a subclass, resolved at runtime via dynamic dispatch. 
// Overload
int add(int a, int b);
double add(double a, double b);

// Override
class Cat extends Animal { @Override void speak() { ... } }
Q5. What is the diamond problem and how do languages solve it?
Diamond: class D inherits from B and C, both of which inherit from A. If both override method(), which version does D get? Solutions:
  • Java/C# — disallow multiple class inheritance; use interfaces.
  • C++ — virtual inheritance; programmer explicitly disambiguates.
  • Python — C3 linearization (MRO); deterministic order via ClassName.__mro__.
Q6. Composition vs inheritance — which would you favor?
Composition, by default. It produces loosely-coupled, runtime-flexible designs. Reach for inheritance only when the relationship is genuinely IS-A and the subtype satisfies the Liskov Substitution Principle. The GoF book's slogan — "favor composition over inheritance" — captures decades of hard-won industry experience.
Q7. What does SOLID stand for?
Single Responsibility · Open/Closed · Liskov Substitution · Interface Segregation · Dependency Inversion. Five class-design principles by Robert C. Martin. Following them reduces coupling, increases cohesion, and makes systems easier to extend without breaking.
Q8. Explain the Singleton pattern. Is it an anti-pattern?
Singleton ensures one instance of a class. Critique: it acts as global state, which makes testing painful (state leaks between tests) and hides dependencies. Modern teams often replace it with dependency injection — pass the single instance explicitly via the constructor.
Q9. What are virtual functions and vtables?
A virtual function can be overridden in derived classes; the actual function called is decided at runtime. The compiler implements this with a vtable — an array of function pointers per class. Each object holds a vptr to its class's vtable. A virtual call costs one extra memory dereference compared to a direct call.
Q10. What is the difference between == and equals() in Java?
== compares references (do both variables point to the same object in memory?). .equals() compares values, but only if the class overrides it; the default Object.equals falls back to ==. Always override equals together with hashCode.
Q11. Can you have multiple inheritance in Java?
Not for classes — Java explicitly forbids it to avoid the diamond problem. But you can implement multiple interfaces, and since Java 8, interfaces can supply default methods. If two interfaces provide conflicting defaults, the implementing class must override.
Q12. What is the Liskov Substitution Principle in simple terms?
If your code works with class Bird, swapping in any subtype (e.g., Sparrow) should still work — no surprises. Subclasses must honor the parent's contract: same method signatures, same expected behavior, no narrower preconditions, no broader postconditions. The Square-extends-Rectangle example violates LSP because mutating a square via setWidth changes height too.
Q13. What is dependency injection?
Instead of a class creating its dependencies (new Database()), you pass them in — usually through the constructor. The class then depends on an abstraction (interface), not the concrete implementation. This makes testing trivial (inject a mock) and follows the Dependency Inversion Principle. Spring, Angular, and ASP.NET have built-in DI containers.
Q14. What is the difference between an abstract method and a virtual method?
Abstract = declared without a body; subclass must implement it. Virtual (C#) / overridable (Java) = has a body but can be overridden; subclass may override. An abstract method is implicitly virtual.
Q15. Why do we override equals() and hashCode() together?
Hash-based collections (HashMap, HashSet) use hashCode to find the bucket and equals to compare within it. The contract: if a.equals(b), then a.hashCode() == b.hashCode(). Breaking this leads to objects "disappearing" in hash sets — they're stored in one bucket but searched for in another.

// Modern C++ — RAII + smart pointer + virtual
class Shape {
public:
    virtual double area() const = 0;       // pure virtual
    virtual ~Shape() = default;             // virtual destructor!
};
class Circle : public Shape {
    double r;
public:
    Circle(double r) : r(r) {}
    double area() const override { return 3.14159 * r * r; }
};

std::unique_ptr<Shape> s = std::make_unique<Circle>(5.0);
std::cout << s->area();

    Course Overview & Fundamentals

    Understand the security tester role, your learning objectives, the prerequisites and the vulnerability standards every tester uses.

    📘 1. Course Overview

    A Security QA Tester / Penetration Tester looks at software the way an attacker would, but with permission and a plan. You find weaknesses before criminals do, prove them with evidence, rate their risk and help developers fix them. The work combines testing discipline with knowledge of how web applications, APIs and networks fail.

    📚
    Standards and methodology
    OWASP Top 10 for web and API, CWE and SANS Top 25, NIST SP 800-115 and STRIDE threat modeling.
    🧰
    Tooling
    Burp Suite, OWASP ZAP, Nmap, Wireshark, SQLMap and Metasploit, used in a safe lab.
    🔓
    Technical domains
    Authentication, OAuth, JWT, SAML, injection, XSS, CSRF, file upload, sessions and business logic flaws.
    🛡️
    Compliance and remediation
    SAST, DAST and SCA in CI/CD, CVSS scoring, developer guidance and reporting.
    RoleMain focusTypical output
    Security QA testerSecurity checks inside the normal test cycle and CI/CDSecurity test cases, scanner findings, gate results
    Penetration testerScoped, time-boxed attack simulationExploit evidence and a penetration test report
    AppSec engineerSecure design, code review and tooling for developersThreat models, standards, training
    ⚖️
    Legal and ethical rule: only test systems you own or have written permission to test. Unauthorised testing is illegal, even with good intentions.

    A Security QA Tester thinks like an attacker but works like an engineer: find weaknesses, prove impact safely, and help developers fix them.

    Confidentiality
    Only authorised people can read data.
    🧾
    Integrity
    Data cannot be changed without detection.
    ⚡
    Availability
    Service stays usable when needed.
    🕵️
    Attacker view
    Ask: what can I abuse, bypass or chain?

    NIST SP 800-115 Methodology

    The NIST Technical Guide to Information Security Testing and Assessment gives a repeatable process.

    📋
    Planning
    Scope, rules of engagement, approvals.
    🔭
    Discovery
    Scanning, enumeration, vulnerability analysis.
    💥
    Attack
    Gain access, escalate, pivot, browse (safely).
    📝
    Reporting
    Findings, risk, mitigation.
    💡
    Techniques in 800-115: review (docs, logs, config), target identification & analysis (port and vulnerability scan), and target vulnerability validation (exploitation, password cracking, social engineering).

    Threat Modeling with STRIDE

    Threat modeling finds design flaws before code exists. Draw a data-flow diagram, then ask which STRIDE threat applies to each element.

    LetterThreatViolatesLogin example
    SSpoofingAuthenticationStolen password used from another device
    TTamperingIntegrityModify price in the request body
    RRepudiationNon-repudiationUser denies placing an order; no audit log
    IInformation disclosureConfidentialityStack trace reveals DB details
    DDenial of serviceAvailabilityFlood the login endpoint
    EElevation of privilegeAuthorizationNormal user opens /admin
    💡
    Mark every trust boundary (browser↔server, server↔DB, internal↔third-party). Most vulnerabilities live where data crosses one.

    Types of Security Assessment

    TypeGoalDepth
    Vulnerability assessmentList as many weaknesses as possibleBroad, mostly automated
    Penetration testProve real exploitability and impactNarrow & deep, manual + tools
    Red teamTest detection and response with realistic goalsStealthy, long-running

    ⬛ Black-box

    Tester knows nothing; simulates an outside attacker.

    ⬜ White / grey-box

    Tester gets code, docs or user accounts; finds more issues in less time.

    CVE vs CWE: a CWE is a type of weakness (CWE-89 SQL injection); a CVE is one specific, publicly catalogued flaw in one product (CVE-2021-44228, Log4Shell).

    ⚙️ 5. Core Concepts

    Authentication vs Authorization

    🪪 Authentication

    "Who are you?" Passwords, MFA, tokens, certificates.

    🚦 Authorization

    "What may you do?" Roles, ownership, scopes.

    Common flawTest
    Weak password policy / no lockoutTry common passwords against limited attempts
    Session fixationIs the session ID renewed after login?
    IDOR / BOLAChange IDs across users
    Privilege escalationCall admin functions as a normal user
    Missing logout/expiryIs the token invalid after logout?

    OAuth 2.0 / OpenID Connect

    OAuth 2.0 delegates access; OIDC adds identity. Prefer Authorization Code + PKCE.

    • redirect_uri not strictly validated → code/token theft.
    • Missing or predictable state → login CSRF.
    • Implicit flow / tokens in URLs → leakage via logs and referrer.
    • Over-broad scopes or refresh tokens that never expire.

    JWT (JSON Web Tokens)

    A JWT has three Base64URL parts: header.payload.signature. The payload is encoded, not encrypted.

    decoded tokenheader:  {"alg":"HS256","typ":"JWT"}
payload: {"sub":"1042","role":"user","exp":1767225600}
    AttackWhat to check
    alg:noneServer must reject unsigned tokens
    Algorithm confusion (RS256 → HS256)Server must pin the expected algorithm
    Weak HMAC secretBrute-force secret offline (lab)
    No exp / long expiryTokens should be short-lived
    Sensitive data in payloadAnyone can decode it
    Claim tamperingChange role; signature must fail

    SAML

    XML-based SSO used in enterprises. The Identity Provider (IdP) signs an assertion; the Service Provider (SP) must verify it.

    • XML Signature Wrapping (XSW): attacker moves the signed element so the SP reads unsigned data.
    • SP accepts unsigned assertions or any valid signature.
    • No check of Audience, Recipient, NotOnOrAfter → replay.
    • XXE in the XML parser.
    💡
    In Burp, the SAML Raider extension helps decode, edit and re-sign assertions for authorised testing.

    🗂️ 6. Topics & Subtopics

    SQL Injection

    Untrusted input changes the meaning of a database query.

    vulnerable vs safe (python)# VULNERABLE
q = "SELECT * FROM users WHERE name='" + name + "'"

# SAFE: parameterised query
cur.execute("SELECT * FROM users WHERE name = %s", (name,))
    test payloads (authorised target)'                          -> syntax error = suspicious
' OR '1'='1' --            -> boolean change
' AND SLEEP(5)--            -> time-based blind
' UNION SELECT NULL,NULL--  -> find column count
    📥
    In-band
    Result shows in the response.
    ❓
    Blind
    True/False or timing only.
    📡
    Out-of-band
    DNS/HTTP callback.

    Cross-Site Scripting (XSS)

    TypeWhere it runs
    ReflectedPayload in URL is echoed in the response
    StoredPayload saved (comments, profiles) and shown to others
    DOM-basedClient-side JS writes untrusted data into the page
    safe proof-of-concept payloads<script>alert(document.domain)</script>
"><img src=x onerror=alert(1)>

    Fix: output-encode for the right context (HTML, attribute, JS, URL), use a strict Content-Security-Policy, set cookies HttpOnly; Secure; SameSite.

    CSRF (Cross-Site Request Forgery)

    A malicious page makes the victim's browser send an authenticated request (cookies attach automatically).

    html: proof of concept (lab only)<form action="https://bank.test/transfer" method="POST">
  <input name="to" value="attacker"> <input name="amount" value="500">
</form>
<script>document.forms[0].submit()</script>

    Test: remove or reuse the anti-CSRF token; if the request still works, report it. Fix: per-session tokens, SameSite=Lax/Strict cookies, re-authentication for sensitive actions.

    File Upload & XXE

    📤 Insecure upload

    Server trusts file name or Content-Type. Test: upload .php/.jsp, double extension shell.jpg.php, oversized files. Fix: allow-list types, rename files, store outside web root, scan content.

    📄 XXE

    XML parser resolves external entities, allowing local file read or SSRF. Fix: disable DTDs/external entities in the parser.

    xml: XXE test payload (lab)<?xml version="1.0"?>
<!DOCTYPE d [ <!ENTITY x SYSTEM "file:///etc/hostname"> ]>
<order><note>&x;</note></order>

    Session Management & Security Headers

    Header / flagProtects against
    Content-Security-PolicyXSS, data injection
    Strict-Transport-SecurityDowngrade to HTTP
    X-Content-Type-Options: nosniffMIME sniffing
    X-Frame-Options / frame-ancestorsClickjacking
    Referrer-PolicyLeaking URLs in Referer
    Set-Cookie: HttpOnly; Secure; SameSiteCookie theft and CSRF
    terminal: quick header checkcurl -sI https://staging.example.com | grep -iE "content-security|strict-transport|x-frame|x-content"

    Business Logic Flaws

    Scanners cannot understand your rules. Think about how the workflow could be abused.

    • Negative quantity or price changes in the cart.
    • Applying one coupon repeatedly (race condition).
    • Skipping steps: jump from step 1 straight to “payment success”.
    • Password reset token that never expires or is guessable.

    💻 7. Practical Examples

    Burp Suite Professional

    Set the browser proxy to 127.0.0.1:8080, install Burp's CA certificate, then every request flows through Burp.

    ModuleUse
    ProxyIntercept and edit requests live
    RepeaterRe-send one request with manual changes
    IntruderAutomated payloads (fuzzing, brute force, ID enumeration)

    💡

    OWASP ZAP

    Free and automation-friendly, which makes it ideal for CI pipelines.

    terminal: baseline passive scan with Docker (staging only)docker run --rm -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t https://staging.example.com -r zap-report.html
    terminal: API scan from OpenAPI speczap-api-scan.py -t https://staging.example.com/openapi.json -f openapi -r api-report.html

    👀 Baseline scan

    Passive only. Safe, fast, good for every build.

    🎯 Full / active scan

    Sends attack payloads. Slower and may alter data; run on test environments only.

    Nmap

    terminalnmap -sn 192.168.1.0/24                  # host discovery

    Wireshark

    Captures packets and decodes protocols. Use capture filters to limit what is recorded and display filters to find packets afterwards.

    Lab 1 · Recon with Nmap

    Lab 1: Discover a lab host

    Goal: Find open ports, services and versions on your practice target.

    NmapMetasploitable
    1. Find the target IP: nmap -sn 192.168.56.0/24.
    2. Scan all ports: nmap -sS -p- <ip> -oA full.
    3. Identify versions: nmap -sV -sC -p <open-ports> <ip>.
    4. Run vulnerability scripts: nmap --script vuln <ip>.
    5. List each service and look up its version for known CVEs.

    🔎 Expected finding

    Outdated FTP/SSH/HTTP services, anonymous access, risky exposed ports.

    🛠️ Fix to recommend

    Disable unused services, upgrade versions, restrict with a firewall.

    Lab 2 · Broken Access Control (BOLA/IDOR)

    Lab 2: Read another user's data

    Goal: Prove that changing an object ID exposes data of another account.

    Burp ProxyRepeaterJuice Shop / crAPI
    1. Create two users, A and B. Add data (e.g. basket, profile) to B.
    2. Log in as A with Burp intercepting. Find a request containing an ID (/rest/basket/6).
    3. Send to Repeater and change the ID to B's value.
    4. Check whether the response returns B's data (200) or is blocked (403).
    5. Save evidence: both requests and responses.

    🔎 Expected finding

    Server returns B's basket to A: Broken Object Level Authorization.

    🛠️ Fix to recommend

    Check object ownership on the server for every request; do not rely on hidden IDs.

    Lab 3 · SQL Injection

    Lab 3: Bypass login and extract version

    Goal: Confirm and safely prove a SQL injection.

    BrowserBurpSQLMapDVWA
    1. Set DVWA security to Low; open the SQL Injection page.
    2. Enter ' and note the database error.
    3. Try 1' OR '1'='1 and compare the number of rows returned.
    4. Find column count with ' ORDER BY 2-- -, then ' UNION SELECT null, version()-- -.
    5. Repeat with SQLMap using a saved request: sqlmap -r req.txt --batch --dbs.
    6. Raise DVWA to Medium/High and observe the defences.

    🔎 Expected finding

    Database version displayed, proving injection.

    🛠️ Fix to recommend

    Use parameterised queries and least-privilege DB accounts.

    Lab 4 · JWT Tampering

    Lab 4: Modify token claims

    Goal: Check whether the server truly verifies token signatures.

    Burp + JWT Editorjwt.ioJuice Shop
    1. Log in and capture the Authorization: Bearer token.
    2. Decode it in jwt.io and read the claims.
    3. Change a claim (e.g. role) and resend with the original signature.
    4. Try alg: none with the signature removed.
    5. Check exp: is an expired token still accepted?

    🔎 Expected finding

    Server accepts altered or unsigned tokens, or never expires them.

    🛠️ Fix to recommend

    Verify signature with a pinned algorithm, validate exp/aud/iss, keep tokens short-lived.

    Lab 5 · Reflected & Stored XSS

    Lab 5: Execute script in the browser

    Goal: Find, prove and fix XSS.

    BrowserBurpDVWA / Juice Shop
    1. Enter a unique marker like zz123 into every input and search the response for it.
    2. Note the context (HTML body, attribute or script).
    3. Try <img src=x onerror=alert(document.domain)>.
    4. For stored XSS, submit in a comment and reload as a second user.
    5. Verify that the cookie lacks HttpOnly using DevTools.

    🔎 Expected finding

    Alert box executes; session cookie readable by script.

    🛠️ Fix to recommend

    Encode output by context, add CSP, set HttpOnly cookies.

    Lab 6 · Security Gate in CI

    Lab 6: Fail the build on High vulnerabilities

    Goal: Automate SCA and DAST on every pull request.

    GitHub ActionsSnykZAPSonarQube
    1. Fork a sample app with an outdated dependency.
    2. Add the workflow from Module 04 using snyk test --severity-threshold=high.
    3. Add ZAP baseline against your staging container.
    4. Open a PR and watch the build fail.
    5. Upgrade the dependency, push again and confirm the gate turns green.

    🔎 Expected finding

    Pipeline blocks the vulnerable PR automatically.

    🛠️ Fix to recommend

    Keep the gate; add exceptions only with a documented expiry.

    CVSS Severity Scoring

    CVSS v3.1 / v4.0 produces a 0–10 score from Base metrics (exploitability + impact), adjustable by Temporal and Environmental metrics.

    ScoreRating
    0.0None
    0.1 – 3.9Low
    4.0 – 6.9Medium
    7.0 – 8.9High
    9.0 – 10.0Critical
    example vector (v3.1)CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H  =  9.8 Critical
AV Network | AC Low | PR None | UI None | Scope Unchanged | C/I/A High
    💡
    CVSS measures technical severity, not business risk. Combine it with asset value, exposure and exploit availability when setting priority.

    🩺 15. Common Errors & Troubleshooting

    Symptom, likely cause and fix

    SymptomLikely causeFix
    Burp or ZAP shows no HTTPS trafficCA certificate not installed or proxy not setInstall the proxy CA in the browser, confirm the proxy address and port, then reload
    Mobile or thick client ignores the proxyCertificate pinning or no proxy supportUse a pinned-bypass approach in a lab only, or intercept at network level with permission
    Nmap shows all ports filteredFirewall dropping probes, or host downCheck reachability first, try -Pn, slow the timing template and confirm you are allowed to scan
    SQLMap finds nothing but you suspect injectionWrong parameter, WAF, or injection in a header or JSON bodyTest manually first, supply the full request file with -r and set the injection point
    Scanner reports hundreds of findingsNo tuning, duplicates and informational noiseTriage by severity, verify the top items manually and suppress false positives with a recorded reason
    A request works in Burp but not in a scriptMissing cookie, token or headerCompare the raw requests and copy the session or CSRF token handling
    XSS payload does not runOutput encoding, CSP or a different contextIdentify the exact context (HTML, attribute, script) and adjust the payload to it
    Developers dispute a findingReport lacks reproduction or impactAdd exact steps, evidence and a short demo; explain the business impact
    ⚠️
    Beginner mistake: running an active scan against a production system without approval. Always confirm scope and timing, and prefer a staging copy.

    Troubleshooting routine

    1. Confirm connectivity and that the target is in scope.
    2. Reproduce the request manually in a proxy before automating it.
    3. Change one thing at a time: parameter, header, encoding, user role.
    4. Read the full response and server errors; they often show the filter or the stack.
    5. Record every step so the result can be reproduced in the report.

    🎤 16. Interview Preparation

    Questions and model answers

    Q1. What is the difference between authentication and authorisation?

    Answer: Authentication proves who you are; authorisation decides what you may do. Broken authorisation (IDOR, BOLA) is the most common serious web and API flaw.

    Q2. Explain SQL injection and how to prevent it.

    Answer: Untrusted input is concatenated into a SQL query and changes its meaning. Prevent it with parameterised queries, least-privilege database accounts and input validation.

    Q3. What is the difference between stored, reflected and DOM-based XSS?

    Answer: Stored is saved on the server and shown to others, reflected comes back from the request immediately, DOM-based happens entirely in client-side script. Prevent with context-aware output encoding and a Content Security Policy.

    Q4. What is CSRF and how is it mitigated?

    Answer: It tricks a logged-in browser into sending an unwanted request. Mitigate with anti-CSRF tokens, SameSite cookies and re-authentication for sensitive actions.

    Q5. How is a JWT attacked?

    Answer: Weak or missing signature validation, the "none" algorithm, guessable secrets and long lifetimes. Verify signatures and algorithms server-side, use strong keys and short expiry.

    Q6. What is the difference between SAST, DAST and SCA?

    Answer: SAST analyses source code, DAST attacks the running application, SCA checks third-party dependencies for known vulnerabilities.

    Q7. How do you rate a vulnerability?

    Answer: Use CVSS for technical severity, then adjust for exploitability, asset value and business impact.

    Q8. Walk me through a penetration test.

    Answer: Scope and rules of engagement, reconnaissance, threat modeling, vulnerability discovery, exploitation with evidence, post-exploitation within scope, reporting and retest.

    Q9. What is BOLA/IDOR?

    Answer: Changing an identifier to access another user's object because the server does not check ownership. Fix with server-side object-level authorisation checks.

    Q10. What would you do if you found a critical flaw in a live system?

    Answer: Stop testing that path, document it with minimal evidence, notify the agreed contact immediately and follow the escalation process; do not exploit further or share data.

    Course Overview & Fundamentals

    Understand what a manual tester does, what you will learn, what you need first, and the testing foundations you use every day.

    📘 1. Course Overview

    This course builds the foundations of software testing: principles, lifecycles, test design techniques, defect management, functional and system-level testing, the tools testers use daily, and how testing fits inside Agile teams.

    By the end: Analyse requirements, design high-quality test cases, execute and report testing clearly, and work confidently inside a Scrum team using Jira, TestRail and SQL/API checks for end-to-end verification.

    The Role of a Manual Tester / Test Analyst

    A Test Analyst does more than click buttons. Typical daily responsibilities:

    • Attend stand-ups, refinement and planning meetings and ask questions about requirements
    • Design and review test cases, prepare test data
    • Execute tests on each new build; log and retest defects
    • Run smoke tests on every deployment and regression before releases
    • Update test management tools and report progress
    • Verify data with SQL and APIs; investigate logs when needed

    Skills that make a great tester

    🧠
    Analytical thinking
    Break features into conditions, rules and edge cases.
    👀
    Attention to detail
    Notice the one wrong label, rounding or state.
    💬
    Communication
    Write clear bugs, give honest status, disagree politely.
    🌱
    Curiosity
    "What happens if…?" is a tester’s favourite question.
    🧰
    Tool knowledge
    Jira, TestRail, Postman, SQL, DevTools.

    A typical sprint day

    🧱 4. Fundamentals

    What Is Software Testing?

    Software testing is the process of evaluating a product to find defects, check that it meets requirements, and give stakeholders information about its quality and risk. A manual tester does this by hand: reading requirements, designing tests, using the application like a real user, and reporting what they find.

    Testing does not prove software is bug-free. It reduces risk by finding problems before customers do. The later a defect is found, the more it costs to fix.

    Stage where bug is foundRelative cost to fixExample
    Requirements1×A rule is unclear; fixed by editing a document
    Design / development5–10×Developer rewrites a function
    QA testing10–20×Fix, rebuild, retest, regression
    Production50–100×Hotfix, customer impact, lost trust, support tickets

    QA vs QC vs Testing

    🛡️
    Quality Assurance (QA)
    Process-oriented and preventive: defining standards, reviews, checklists so defects are not introduced.
    🔬
    Quality Control (QC)
    Product-oriented and detective: checking the actual product against requirements.
    🧪
    Testing
    The activity of executing the software to find defects. It is the main QC technique.

    Verification vs Validation

    Verification: "Are we building the product right?"

    Static checks without running code: reviews, walkthroughs, inspections of requirements and designs.

    Validation: "Are we building the right product?"

    Dynamic checks by running the software and confirming it satisfies real user needs.

    💡
    Interview answer in one line: QA prevents defects through process, QC detects defects in the product, testing is the hands-on execution.

    The 7 Testing Principles

    These principles (from the ISTQB syllabus) guide every decision a tester makes.

    #PrincipleWhat it means in practice
    1Testing shows the presence of defectsPassing tests never prove there are no bugs. They only lower the risk.
    2Exhaustive testing is impossibleA single form with 10 fields has billions of combinations. Use techniques and risk to choose.
    3Early testing saves time and moneyReview requirements and designs. Join refinement meetings. Shift left.
    4Defects cluster togetherA small number of modules (payments, login) usually contain most bugs. Test them harder.
    5Pesticide paradoxRunning the same tests forever stops finding new bugs. Review and refresh them.
    6Testing is context dependentA banking app and a game need very different testing.
    7Absence-of-errors fallacyA bug-free product that does not meet user needs is still a failure.
    🧠 Exercise: Apply a principle

    A release has 400 regression cases and the team has 1 day. Which principles help you decide what to run?

    Answer / model solution
    Principle 2 (cannot test everything) and 4 (defects cluster): run a risk-based subset covering the most critical flows (login, payment, recent changes) plus modules with historical defects. Principle 5 reminds you to add new cases for recent bug areas.

    SDLC Models and Where Testing Fits

    The Software Development Life Cycle (SDLC) describes how software is built. The model decides when you test and how much documentation you receive.

    ModelHow it worksTesting role
    WaterfallPhases run in sequence: requirements → design → code → test → releaseTesting starts late, after development. Heavy documentation.
    V-ModelEach development phase has a matching test phaseTest planning begins as soon as requirements exist.
    Agile / ScrumShort iterations (sprints) delivering working incrementsTesting is continuous, inside every sprint, with developers.
    KanbanContinuous flow with work-in-progress limitsTesters pull items as they reach the Test column.

    The V-Model mapping

    Development phaseMatching test level
    Business requirementsUser acceptance testing
    System requirementsSystem testing
    High-level designIntegration testing
    Detailed design / codeUnit testing
    📝
    Most modern teams use Agile. A tester is expected to join backlog refinement, clarify acceptance criteria and test stories during the same sprint.

    The Software Testing Life Cycle (STLC)

    The STLC is the sequence of activities a test team follows. Each phase has entry criteria (what must be ready to start) and exit criteria (what proves it is done).

    STLC: every phase produces a deliverable.
    PhaseEntry criteriaActivitiesDeliverables
    Requirement analysisApproved requirements / user storiesFind testable requirements, ask questions, spot gapsRTM draft, clarification list
    Test planningRequirement analysis doneScope, approach, risks, effort, schedule, toolsTest plan / strategy
    Test case designPlan approvedWrite scenarios, cases, prepare test dataTest cases, test data, reviewed RTM
    Environment setupPlan and design readyPrepare servers, builds, accounts, dataReady environment, smoke test result
    Test executionStable build, smoke passedRun cases, log defects, retest, regressExecution results, defect reports
    Test closureExit criteria metMetrics, lessons learned, sign-offTest summary report
    🧠 Exercise: Write exit criteria

    Write 4 realistic exit criteria for a release test cycle.

    Answer / model solution
    • 100% of planned high-priority test cases executed
    • ≥ 95% of all test cases passed
    • No open Critical or High severity defects
    • All remaining Medium/Low defects reviewed and accepted by the product owner
    🎯
    Key takeaways
    • STLC = analyse, plan, design, set up, execute, close.
    • Entry criteria say when you may start; exit criteria say when you may stop.

    Levels of Testing

    🧩
    Unit
    Single function or class. Written by developers.
    🔗
    Integration
    Modules/services working together, such as UI + API + DB.
    🏗️
    System
    The complete application against requirements. The main manual QA level.
    🤝
    Acceptance (UAT)
    Business users confirm the product meets their needs.

    Integration approaches

    • Big-bang: combine everything then test. Fast to plan, hard to locate defects.
    • Top-down: test high-level modules first using stubs for lower ones.
    • Bottom-up: test low-level modules first using drivers.
    • Sandwich / hybrid: combination of both.

    Alpha vs Beta testing

    Alpha

    Done in-house by internal testers or staff in a controlled environment before release.

    Beta

    Done by a limited group of real users in their own environment before general release.

    Types of Testing

    Testing types describe what you are checking. Levels describe where in the product you check it.

    Functional types

    SmokeSanityRegressionRetestingIntegrationSystemUATExploratoryAdhocLocalization

    Non-functional types

    TypeQuestion it answersExample
    PerformanceHow fast and stable under load?Page loads in under 3 s with 500 users
    UsabilityIs it easy to use?New user finds checkout in under a minute
    CompatibilityDoes it work across browsers/devices?Layout correct on Safari iOS and Chrome Android
    SecurityCan data be stolen or misused?User A cannot open user B’s invoice by changing the URL
    AccessibilityCan disabled users use it?Whole form works by keyboard only
    LocalizationCorrect for each language/region?Dates, currency and text in German

    Black-box, white-box, grey-box

    Black-box

    Tester knows inputs and expected outputs only, not the code. This is the manual tester’s main approach.

    White-box / Grey-box

    White-box uses code knowledge (developers). Grey-box mixes both, for example using database or API knowledge while testing the UI.

    Anatomy of a Good Test Case

    A good test case is atomic (one purpose), repeatable, independent, traceable and has a clear expected result. Anyone on the team should be able to run it and reach the same verdict.

    FieldPurposeExample
    IDUnique referenceTC_LOGIN_003
    TitleOne-line goalLogin fails with wrong password
    Module / RequirementTraceabilityAuth / REQ-AUTH-02
    PreconditionsState before startingUser qa@test.com exists and is active
    Test dataExact inputsqa@test.com / Wrong@123
    StepsNumbered actions1. Open /login 2. Enter data 3. Click Sign in
    Expected resultWhat should happenError "Invalid credentials"; stays on /login
    Priority / TypeOrder and categoryHigh / Negative
    Actual result / StatusFilled during executionPass / Fail / Blocked

    ❌ Weak test case

    Title: "Check login". Steps: "Try to login". Expected: "Works properly". Impossible to verify; different testers get different results.

    ✅ Strong test case

    Exact data, numbered steps, and observable expected result: "User lands on /dashboard and name “Asha” appears in the header".

    Rules for writing cases

    • One verification per case (or closely related checks).
    • Use present-tense, action verbs: Enter, Click, Select, Verify.
    • State the expected result for every important step.
    • Include positive, negative, boundary and security cases.
    • Do not depend on another case having run first.
    • Review cases with a peer or developer.

    Test Planning and Risk-Based Testing

    A test plan answers: what will we test, how, who, when, and with what. A one-page plan agreed with the team is better than a 40-page document nobody reads.

    SectionContents
    ScopeFeatures in scope and out of scope
    ApproachTest types, techniques, manual vs automated
    EnvironmentBrowsers, devices, build, test data, accounts
    RolesWho tests, who fixes, who approves
    Schedule & effortDates and estimates, dependencies
    Entry / exit criteriaWhen to start and finish
    Risks & mitigationLate builds, unstable environment, tight deadline
    DeliverablesTest cases, defect reports, summary report

    Risk-based prioritisation

    Risk = likelihood × impact. Test the highest scores first.

    FeatureLikelihood of failureImpact if it failsRiskTest priority
    PaymentMediumVery highHigh1
    LoginLowHighMedium-High2
    New coupon engine (changed this sprint)HighMediumHigh1
    Footer linksLowLowLow4
    🧠 Exercise: Estimate effort

    You have 60 new test cases. Executing each takes ~6 minutes, and about 20% fail and need retest and bug logging (+10 minutes each). Estimate the execution time.

    Answer / model solution
    60 × 6 = 360 min. Failures: 12 × 10 = 120 min. Total ≈ 480 min = 8 hours, plus ~20% buffer for blocked cases and environment issues ≈ 9.5–10 hours (about 1.5 days).

    Environments, Builds and Releases

    Code moves through environments so problems are caught safely before real users are affected.

    Typical promotion path of a build.
    • Build / version number: always record it in bug reports (e.g. 2.14.3).
    • Test data: use test accounts, never real customer data.
    • Environment issues: not every failure is a bug. Check that the environment, data and configuration are correct first.
    • Release types: major release, minor release, hotfix (urgent production fix, needs quick targeted regression).
    ⚠️
    Never test destructive actions (deleting accounts, sending real emails or payments) on production unless explicitly approved.
    🎯
    Key takeaways
    • Always note build version and environment.
    • Smoke-test every new deployment before deep testing.
    • Hotfixes still need targeted regression.

    🗂️ 6. Topics & Subtopics

    Equivalence Partitioning (EP)

    You cannot try every value. EP divides inputs into partitions that the system treats the same way. If one value from a partition works, the others are assumed to work. Pick one representative per partition.

    Worked example 1: age field accepts 18 to 60

    partitionsInvalid (<18)  |  Valid (18-60)  |  Invalid (>60)
   e.g. 10            e.g. 35             e.g. 70

Also consider: blank, text "abc", negative -5, decimal 25.5

    Worked example 2: discount by order value

    Order totalDiscountPartition
    0.01 – 99.990%P1
    100 – 499.995%P2
    500 and above10%P3
    ≤ 0 or non-numericErrorInvalid

    Representatives: 50, 250, 800, -5, "abc". Five tests cover all behaviours instead of hundreds.

    🧠 Exercise: Password rule

    A password must be 8 to 16 characters. Identify the partitions and pick representatives.

    Answer / model solution
    Partitions: too short (1–7), valid (8–16), too long (17+), plus empty. Representatives: abc12 (5 chars), Passw0rd! (9 chars), a 20-character string, and empty.

    Boundary Value Analysis (BVA)

    Bugs love edges: developers mix up < and <=. BVA tests values at and next to each boundary of a partition.

    age 18-602-value BVA : 17, 18, 60, 61
3-value BVA : 17, 18, 19, 59, 60, 61

Min boundary = 18   -> test 17 (invalid), 18 (valid), 19 (valid)
Max boundary = 60   -> test 59 (valid), 60 (valid), 61 (invalid)
    RequirementBoundaries to test
    Quantity 1–100, 1, 2, 9, 10, 11
    Username 5–12 characters4, 5, 6, 11, 12, 13 characters
    Withdraw up to ₹20,000 per day19,999 / 20,000 / 20,001
    Coupon valid until 31-Dec30-Dec, 31-Dec, 01-Jan
    💡
    Combine EP and BVA: EP finds the groups, BVA picks the sharpest values inside each group.
    🧠 Exercise: Do it yourself

    A text box accepts 1 to 255 characters. List the BVA test inputs by length.

    Answer / model solution
    0 (invalid, empty), 1, 2, 254, 255, 256 (invalid). Also test a very long paste (e.g. 10,000 chars) as an extra robustness check.

    Decision Table Testing

    When the result depends on combinations of conditions, list them all in a decision table so none is missed.

    Example: free-shipping rule

    Shipping is free if the customer is a member and the cart is ≥ ₹999, or if a free-shipping coupon is applied.

    RuleMemberCart ≥ 999CouponFree shipping?
    R1YYNYes
    R2YNNNo
    R3NYNNo
    R4NNNNo
    R5NNYYes
    R6YYYYes

    Each column (rule) becomes at least one test case. With 3 conditions there are 2³ = 8 combinations; collapse impossible or identical outcomes to reduce the table.

    🧠 Exercise: Login lockout

    Build a decision table for: valid user/valid password → success; valid user/wrong password → error; locked user/any password → "Account locked".

    Answer / model solution
    Conditions: user valid? password valid? account locked? Rules: (Y,Y,N) success; (Y,N,N) error + attempts+1; (Y,Y,Y) locked message; (Y,N,Y) locked message; (N,*,N) generic "Invalid credentials" (never reveal which part was wrong).

    State Transition Testing

    Use it when the system has states and events that move it between states, such as order status, account lock, or ATM PIN entry.

    Valid order flow. Cancel is allowed only before Shipped.
    From stateEventTo stateValid?
    NewPayPaidYes
    PaidCancelCancelled (refund)Yes
    ShippedCancel—No: must be blocked
    DeliveredPay—No: negative test
    CancelledShip—No: negative test

    Test every valid transition and the most important invalid transitions. Example ATM: 3 wrong PINs lock the card; test PIN attempts 1, 2, 3 and then a correct PIN on a locked card.

    Pairwise (Combinatorial) Testing

    A form with Browser (4) × OS (3) × Language (3) × Role (3) has 108 combinations. Research shows most bugs are caused by the interaction of two parameters, so pairwise testing covers every pair of values at least once with far fewer tests (around 12).

    3 parameters, 2 values each: 8 full combos vs 4 pairwiseBrowser   OS        Role
Chrome    Windows   Admin
Chrome    Mac       User
Safari    Windows   User
Safari    Mac       Admin
    📝
    Free tools such as PICT or online pairwise generators build these tables for you. Use pairwise for configurations and filters, not for business-rule logic (use decision tables there).

    Error Guessing and Checklist-Based Testing

    Experience tells you where bugs usually hide. Error guessing turns that experience into tests.

    AreaTypical inputs to try
    Text fieldsLeading/trailing spaces, very long text, emojis, quotes ' ", <script>, SQL fragments, copy-pasted text
    Numbers0, negative, decimals, huge values, comma/period formats
    DatesLeap day, 31 Dec → 1 Jan, past dates, different timezones, DST change
    FilesEmpty, oversized, wrong extension, special characters in name
    BehaviourDouble-click submit, back button, refresh mid-payment, two tabs, session expiry
    NetworkSlow connection, offline, API timeout

    A checklist is a reusable list of items to verify. It is lighter than full cases and ideal for repeated areas such as "every form" or "every page".

    Designing Test Data

    Good tests need good data. Plan it just like cases.

    • Valid data: realistic users, orders, products.
    • Invalid / boundary data: from EP and BVA.
    • Special data: Unicode names (José, 李雷), long names, apostrophes (O’Brien).
    • Role-based accounts: admin, normal user, locked user, new user with no history.
    • Data states: empty cart, cart with 1 item, cart with 100 items, expired subscription.
    ⚠️
    Never copy real customer data into test environments without masking it. Personal data rules (GDPR and similar) apply to test systems as well.

    🧪 8. Hands-on Practice

    SQL Practice

    🧠 Exercise: Q1 – Paid orders

    Write a query to list the 5 most recent PAID orders with customer name.

    Answer / model solution
    SELECT o.id, c.name, o.total, o.created_at FROM orders o JOIN customers c ON c.id = o.customer_id WHERE o.status = 'PAID' ORDER BY o.created_at DESC LIMIT 5;
    🧠 Exercise: Q2 – Orders per city

    How many orders did each city place?

    Answer / model solution
    SELECT c.city, COUNT(o.id) AS orders FROM customers c LEFT JOIN orders o ON o.customer_id = c.id GROUP BY c.city;
    🧠 Exercise: Q3 – Verify a registration

    You registered asha@test.com in the UI. Confirm the record exists once and was created today.

    Answer / model solution
    SELECT id, email, created_at FROM customers WHERE email = 'asha@test.com'; Expect exactly 1 row and today’s date. To check duplicates also run the GROUP BY … HAVING COUNT(*) > 1 query.
    🧠 Exercise: Q4 – Stock check

    After ordering 2 units of product 7 (stock was 10), what should the DB show?

    Answer / model solution
    SELECT stock FROM products WHERE id = 7; returns 8. If it still shows 10 (or 6) you have found a bug.

    📈 9. Intermediate Concepts

    Smoke Testing

    Smoke testing is a broad, shallow, quick check that the build is stable enough for further testing. The name comes from hardware: switch it on and see if smoke comes out. If smoke fails, the build is rejected and sent back to development; nobody wastes time on deeper testing.

    example smoke checklist (e-commerce, about 15 minutes)[ ] Application URL loads, no server error
[ ] Login with a valid user works
[ ] Search returns products
[ ] Add item to cart
[ ] Checkout page opens and totals appear
[ ] Test payment succeeds
[ ] Logout works
    • Runs on every new build or deployment.
    • Covers the most critical end-to-end paths only.
    • Result is binary: build accepted or rejected.
    • Prime candidate for automation later.

    Sanity Testing

    Sanity testing is a narrow, focused check after a small change or bug fix to confirm that the specific functionality behaves rationally before more expensive testing is done.

    SmokeSanity
    ScopeBroad, whole application, critical pathsNarrow, one feature or fix
    DepthShallowDeeper on that area
    WhenNew build receivedAfter a minor change / bug fix
    DocumentedUsually scripted checklistOften unscripted
    GoalIs the build stable?Does the change work as intended?
    💡
    Example: developer fixes the "coupon with a space" bug. Sanity: apply a coupon with and without space. Then regression: check that cart totals, other coupons and checkout still work.

    Regression Testing

    Every change can break something that used to work. Regression testing re-runs existing tests to confirm that recent changes did not introduce new defects in unchanged areas.

    Types of regression

    🧱
    Full regression
    Entire suite. Before major releases.
    🎯
    Partial / selective
    Only areas impacted by the change plus critical flows.
    ⏱️
    Progressive
    When new tests are added for new features.
    🔥
    Hotfix regression
    Tiny targeted run for an urgent production fix.

    How to select regression tests

    • All critical business flows (login, search, checkout, payment).
    • Areas touched by the change and modules that depend on it (ask developers for impact analysis).
    • Areas with a history of defects.
    • Tests of recently fixed bugs (to be sure they stay fixed).

    Keeping the suite healthy

    • Remove obsolete cases, update cases when requirements change.
    • Tag cases: smoke, sanity, regression, priority P1/P2/P3.
    • Mark stable repetitive cases as automation candidates.
    • Keep execution time realistic for the release schedule.

    Retesting (confirmation)

    Re-run the failed test case on the fixed build to confirm that exact defect is fixed.

    Regression

    Run other tests to ensure nothing else broke. Not limited to failed cases.

    Test Execution in Practice

    Execution is more than "run and mark pass or fail".

    Execution workflow for a new build.
    StatusMeaningAction
    PassActual equals expectedNone
    FailActual differs from expectedLog defect, link it to the case
    BlockedCannot run (environment down, dependent bug)Note blocker, raise it in stand-up
    Skipped / N/ANot applicable for this buildRecord reason
    Not runPlanned but not yet executedSchedule

    Good execution habits

    • Read the whole case before starting. Follow steps exactly first, then explore around it.
    • Capture evidence as you go: screenshots, short screen recordings, logs, build version.
    • Verify actual vs expected at every step, not only at the end.
    • If something looks odd but the case passes, investigate and note it.
    • Retest on a clean state (clear cache, new session) before declaring a bug "not reproducible".

    The Defect Life Cycle

    A defect (bug) is a deviation between actual and expected behaviour. The life cycle tracks it from discovery to closure so nothing is lost.

    Main path. A defect is Closed only after QA verifies the fix.
    Extra stateWhen it is used
    ReopenedFix did not work or the bug returned; goes back to the developer
    DuplicateSame bug already logged; link to the original
    Rejected / Not a bugBehaviour matches requirements (after discussion)
    Cannot reproduceDeveloper cannot recreate it; tester adds more data and steps
    Deferred / PostponedValid but scheduled for a later release
    Won’t fixAccepted risk with business approval
    📝
    State names differ by company (Open, To Do, Ready for QA, Verified…) but the logic is the same. Learn the idea, not the label.

    Writing a Great Bug Report

    A bug report is a communication tool. Its job: let a developer understand, reproduce and fix the problem without asking you questions.

    FieldWhat to write
    Title / SummarySpecific: what + where + condition. "Checkout returns 500 when coupon contains a space"
    EnvironmentApp build, URL/env, browser + version, OS, device, user role
    PreconditionsAccount type, data state
    Steps to reproduceNumbered, minimal, exact data
    Expected resultFrom requirement / acceptance criteria
    Actual resultWhat really happened, exact error text
    Severity & priorityImpact and urgency (see next section)
    FrequencyAlways / 3 of 5 times / once
    EvidenceScreenshot, video, HAR file, console log, server log lines, API response
    LinksRelated story, failed test case, regression info

    ❌ Bad bug report

    Title: "Payment not working". Steps: "Tried to pay". Actual: "Error". No build, no browser, no evidence. The developer must come back with 6 questions.

    ✅ Good bug report

    Title: "Card payment returns HTTP 500 for amounts above ₹50,000". Exact steps, build 2.14.3, Chrome 126, response body, HAR attached, happens 5/5 times.

    complete exampleTitle:     Order total ignores discount when quantity is changed after applying coupon
Env:       QA, build 2.14.3, Chrome 126 / Windows 11, user: member@test.com
Steps:     1. Add "Blue Shirt" (₹1,000) to cart
           2. Apply coupon SAVE10 -> total ₹900
           3. Change quantity from 1 to 2
Expected:  Total = ₹1,800 (10% off ₹2,000)
Actual:    Total = ₹2,000, coupon line still shows "applied"
Frequency: 5/5
Severity:  Major   Priority: High
Evidence:  cart-total.mp4, network call PUT /api/cart/42 response attached
    🎯
    Key takeaways
    • One bug per report.
    • Steps must be minimal and reproducible.
    • Stay factual: describe the behaviour, never blame a person.

    Severity vs Priority

    Severity

    Technical impact on the system/user. Usually set by the tester. Levels: Critical, Major, Minor, Trivial.

    Priority

    Business urgency of the fix. Usually set by product owner / manager. Levels: High, Medium, Low.

    CombinationExample
    High severity, High priorityPayment fails for all users
    High severity, Low priorityApp crashes when opening an old report used by 1 user per year
    Low severity, High priorityCompany name misspelled on the home page before a marketing launch
    Low severity, Low prioritySlight misalignment on a rarely used admin page
    SeverityTypical definition
    CriticalSystem crash, data loss, security breach, no workaround
    MajorMain feature broken, workaround is hard
    MinorFeature partly affected; easy workaround
    TrivialCosmetic: typo, colour, spacing
    💡
    Interview favourite. Always be ready with one example for each of the four combinations.

    Investigating and Reproducing Bugs

    Great testers do a bit of detective work before logging a bug.

    When the bug is intermittent

    • Note exact time, user, data and steps for the failing and passing runs.
    • Change one variable at a time: browser, user role, data, network speed.
    • Try a clean profile/incognito and another environment.
    • Capture logs and network traces at the moment of failure.
    • Record the frequency and report it even if rare ("2 of 10 attempts").

    Evidence toolbox

    EvidenceHow to get it
    Screenshot (annotated)Mark the wrong element, include URL bar and time
    Screen recordingBest for multi-step or timing bugs
    Console logDevTools → Console, copy red errors
    HAR fileDevTools → Network → "Export HAR" to share all requests
    API request/responseNetwork tab → copy as cURL, or Postman
    Server log excerptAsk dev/ops for the log around the timestamp

    Defect triage

    Triage meetings review new bugs: confirm validity, set severity/priority, assign an owner and decide the target release. Come prepared with reproduction steps and the business impact.

    Release Testing, UAT and Go/No-Go

    Before release, QA gives an honest quality status. The final decision belongs to the business, but it must be based on your evidence.

    • Confirm exit criteria were met (see STLC).
    • List open defects with severity, impact and workaround.
    • Run final smoke on staging / pre-production.
    • Support UAT: help business users prepare scenarios and data, log and clarify their findings.
    • After release do a production sanity check with safe, read-only actions.
    ✅
    A strong tester says: "Here is the risk, here is the evidence, here is my recommendation," instead of simply "it’s ready" or "it’s not ready".
    🧠 Exercise: Make the call

    One day before release a Major defect is found in the profile page. Everything else passes. What do you do?

    Answer / model solution
    Log it with evidence, assess impact (how many users, workaround?), tell the product owner immediately, and present options: fix and retest, release with the profile fix deferred and documented, or delay. Record the decision. Do not hide or silently downgrade the severity.

    User Stories and Acceptance Criteria

    A user story states a need: As a [user], I want [goal], so that [benefit]. Acceptance criteria define when it is done, and are the source of your test cases.

    Given / When / ThenStory: As a customer I want to apply a coupon so that I get a discount.

Scenario: Valid coupon
  Given my cart total is ₹1,000
  When I apply coupon SAVE10
  Then the total becomes ₹900 and "SAVE10 applied" is shown

Scenario: Expired coupon
  Given coupon OLD20 expired yesterday
  When I apply OLD20
  Then I see "Coupon expired" and the total does not change

    Definition of Ready vs Definition of Done

    Definition of Ready

    A story is clear enough to start: acceptance criteria written, dependencies known, estimable and testable.

    Definition of Done

    Code reviewed, tests executed and passed, no open critical bugs, documentation updated, deployed to QA/staging.

    🧠 Exercise: Find the gap

    Story: "As a user I want to search products." What questions would you ask in refinement?

    Answer / model solution
    Is search by name only or also category/SKU? Case sensitivity? Partial match? Maximum results and pagination? Sorting? What if there are no results? Special characters? Performance expectations? These questions become test cases and prevent defects before coding.

    Accessibility Basics

    Accessibility (a11y) means people with visual, hearing, motor or cognitive disabilities can use the product. The common standard is WCAG.

    • Keyboard only: Tab through the page, focus is visible, Enter/Space activate controls, no keyboard traps.
    • Contrast: normal text needs at least 4.5:1 against its background.
    • Alt text on meaningful images; decorative images ignored by screen readers.
    • Labels: every input has a visible label, errors are not shown by colour alone.
    • Zoom: page usable at 200% zoom.
    • Try a screen reader (NVDA, VoiceOver) and tools such as Lighthouse or axe DevTools.

    SQL: Aggregates, GROUP BY and JOIN

    sql: aggregate functionsSELECT COUNT(*) FROM orders;                   -- how many rows
SELECT SUM(total), AVG(total) FROM orders;      -- totals
SELECT MIN(created_at), MAX(created_at) FROM orders;

SELECT status, COUNT(*) AS total_orders
FROM orders
GROUP BY status;

SELECT customer_id, SUM(total) AS spent
FROM orders
GROUP BY customer_id
HAVING SUM(total) > 5000;

FROM orders o

WHERE o.id = 1042;

-- customers who never ordered
SELECT c.id, c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
    JoinReturns
    INNER JOINOnly rows that match in both tables
    LEFT JOINAll rows from left table, matched rows from right (NULL if none)
    RIGHT JOINAll rows from right table, matched from left
    FULL JOINAll rows from both

    Typical tester checks

    • Duplicates: SELECT email, COUNT(*) FROM customers GROUP BY email HAVING COUNT(*) > 1;
    • Orphans: order_items whose order does not exist (LEFT JOIN … WHERE o.id IS NULL).
    • Totals: compare SUM(qty*price) of items with the order total.
    • Audit fields: created_at set, updated_at changes after edit.

    ⭐ 14. Best Practices

    Habits of a reliable manual tester

    🎯
    Test the risk first
    Start with the features that would hurt most if they failed: money, security, data loss, legal exposure and the main user journey.
    📝
    One idea per test case
    Atomic cases are easier to execute, to repeat and to trace back to a requirement. If a case has two expected results from two actions, split it.
    🔁
    Make every bug reproducible
    Numbered steps, exact data, build number, environment and a screenshot or recording. A bug nobody can reproduce is rarely fixed.
    🧭
    Ask early
    Review requirements and stories before coding finishes. Ambiguity found in a meeting costs minutes; found in production it costs days.
    DoAvoid
    Write expected results from the requirement, before you run the testDeciding the expected result after you see the actual result
    Re-test the fix, then run a focused regression around itClosing a bug because the exact steps now pass
    Keep test data separate from test cases and reset it between runsReusing a data record that earlier tests have modified
    Record the build, browser, device and environment in every resultWriting "tested on QA" with no version
    Report facts and impact in a neutral toneBlaming a developer or exaggerating severity
    Update test cases when requirements changeLetting the suite drift until nobody trusts it
    ✅
    Quality gate for your own work: before you hand over results, check that every executed case has a status, every failure has a bug ID, and every bug has steps, data, evidence and a severity.

    Checklist before logging a defect

    • Searched the tracker for a duplicate
    • Reproduced it at least twice, or noted how often it happens
    • Checked the requirement so you know it is really a defect
    • Attached evidence (screenshot, video, console or network log)
    • Set severity honestly and left priority to the product owner

    Communication and Collaboration Skills

    Tools do not make a good tester. Communication does.

    • Report facts, not blame: "Total shows ₹2,000 instead of ₹1,800" not "Your discount code is broken".
    • Talk to the developer before and after logging a complex bug: a 2-minute call saves a day.
    • Disagree with evidence: show requirement, screenshot, steps.
    • Give honest status early. Raise risks as soon as you see them.
    • Ask questions in refinement. A question asked early costs nothing.
    • Close the loop: update the ticket, tell the person when a fix is verified.
    daily status update (Slack / stand-up)Yesterday: executed 40/60 cases for Story SHOP-221; logged 3 bugs (BUG-301..303)
Today: retest fixes, start regression of cart module
Blockers: QA environment payment sandbox is down since 10:00 (waiting on DevOps)
    ✅
    Testers who write clear bugs, communicate risk early and respect developers become the people teams trust with releases.

    🩺 15. Common Errors & Troubleshooting

    Symptom, likely cause and fix

    Most day-to-day testing problems fall into a small set of patterns. Use this table as a first-aid guide before you escalate.

    SymptomLikely causeWhat to do
    Developer says "cannot reproduce"Different build, data, browser or role; steps skip a preconditionRe-run on a clean session, add the exact build, account role and test data, and attach a screen recording
    A test passes on one run and fails on the nextShared data, timing, an unstable environment or a hidden dependencyIsolate the data, repeat three times, check environment health and note the pattern in the bug
    Many "bugs" are rejected as "works as designed"Requirements were not read or were never clarifiedConfirm the expected behaviour with the product owner first and link the requirement in the report
    Defects found late in the cycleLate test design, thin coverage of risky areas, no early reviewsReview stories before development and run a smoke test on every new build
    Duplicate bug reportsNo search before logging; vague titlesSearch by component and keyword, and write titles as "feature: problem when condition"
    Regression bugs keep returningFixes are retested narrowly and no regression suite existsAdd a regression case for every escaped bug and run the suite before release
    Test execution is blockedEnvironment down, build not deployed, missing accessLog it as a blocker with impact and owner, and move to unblocked tests meanwhile
    Results disagree with another testerAmbiguous steps or expected resultsRewrite the case so any tester gets the same outcome, then review it together
    ⚠️
    Common beginner mistake: marking a test as "Pass" because nothing looked wrong. A pass needs the expected result to be checked explicitly and recorded.

    A simple troubleshooting routine

    1. Reproduce the problem and write down the exact steps.
    2. Change one variable at a time: data, user role, browser, device, network.
    3. Check the browser console and the network tab for errors and failed requests.
    4. Check the data behind the screen with a SQL query, if you have access.
    5. Compare with the previous build to see whether it is a regression.
    6. Log the bug with all findings, or ask for help with those facts in hand.

    🎤 16. Interview Preparation

    Interview Questions and Model Answers

    🧠 Exercise: 1. What is the difference between QA, QC and testing?

    Explain the three terms.

    Answer / model solution
    QA is process-focused and preventive; QC is product-focused and detects defects; testing is the activity of executing software to find defects (a QC technique).
    🧠 Exercise: 2. Explain the bug life cycle.

    Walk through the states.

    Answer / model solution
    New → Assigned → In Progress → Fixed → Retest → Closed. If the fix fails: Reopened. Other outcomes: Duplicate, Rejected, Cannot reproduce, Deferred.
    🧠 Exercise: 3. Severity vs priority with an example.

    Give four combinations.

    Answer / model solution
    High/High: payment fails. High/Low: crash in a feature used once a year. Low/High: brand name typo on the home page. Low/Low: minor alignment on a rarely visited page.
    🧠 Exercise: 4. A bug is "not reproducible" for the developer. What do you do?

    Describe your approach.

    Answer / model solution
    Re-check build, environment, data and role; capture a screen recording, console/network logs and exact timing; try a clean session and other browser; pair with the developer; document frequency; keep the bug open until resolved.
    🧠 Exercise: 5. How do you decide what to test with limited time?

    Explain prioritisation.

    Answer / model solution
    Risk-based: likelihood × impact. Run smoke first, then critical flows, recent changes and defect-prone modules; skip low-risk areas and report the coverage gap.
    🧠 Exercise: 6. Smoke vs sanity vs regression?

    Differentiate.

    Answer / model solution
    Smoke: broad shallow build check. Sanity: narrow check of a fix/change. Regression: re-run existing tests to ensure no side effects.
    🧠 Exercise: 7. What would you test on a text field that accepts 1–50 characters?

    List the cases.

    Answer / model solution
    BVA: 0, 1, 2, 49, 50, 51; paste long text; spaces only; special characters/emoji/HTML; leading/trailing spaces; copy-paste; required/optional behaviour; error messages.
    🧠 Exercise: 8. How do you test an API in Postman?

    Describe the process.

    Answer / model solution
    Create a collection and environment variables, send the request, check status code, body, headers and response time in the Tests tab, test negative and auth cases, and run the collection with the Runner.
    🧠 Exercise: 9. How do you verify data with SQL?

    Give an example.

    Answer / model solution
    After placing an order in the UI, query orders joined with customers by order id and verify total, status and customer; check order_items and stock changes and look for duplicates.
    🧠 Exercise: 10. What makes a good test case?

    List qualities.

    Answer / model solution
    Atomic, clear title, preconditions, exact data, numbered steps, specific expected result, traceable to a requirement, independent and repeatable.
    🧠 Exercise: 11. What is exploratory testing and when do you use it?

    Explain.

    Answer / model solution
    Simultaneous learning, test design and execution using charters and time-boxes. Used for new features, unclear requirements and to find defects scripted tests miss.
    🧠 Exercise: 12. What is your role in Scrum?

    Describe.

    Answer / model solution
    Take part in refinement (testability, acceptance criteria), plan tests, test stories inside the sprint, smoke every deployment, regression before the demo, and share quality risks in stand-ups and retros.
    🧠 Exercise: 13. What would you do if you find a critical bug right before release?

    Describe the escalation.

    Answer / model solution
    Verify and document quickly, inform the product owner and developers immediately with impact and evidence, support fix-and-retest or a documented risk decision. Never hide it.
    🧠 Exercise: 14. What is a traceability matrix?

    Explain.

    Answer / model solution
    A table mapping requirements to test cases, results and defects to prove coverage and to assess change impact.
    🧠 Exercise: 15. 200 vs 201 vs 400 vs 401 vs 403 vs 500?

    Explain.

    Answer / model solution
    OK; created; invalid input; not authenticated; not authorised; server error.

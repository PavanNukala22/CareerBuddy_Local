    🧱 4. Fundamentals

    Role of QA & the STLC

    QA is about preventing and finding defects early, not just clicking through screens. A Test Analyst studies requirements, designs tests, executes them and reports risk.

    📑
    Requirement Analysis
    Find gaps, ambiguity and testable conditions.
    🗂️
    Test Planning
    Scope, risks, environments, entry/exit criteria.
    ✍️
    Test Design
    Write cases using design techniques.
    ▶️
    Execution
    Run tests, log defects, retest, regress.
    📊
    Closure
    Metrics, lessons learned, sign-off.

    Test Design Techniques

    Techniques give you maximum coverage with minimum tests.

    example: age field accepts 18–60Equivalence partitions:
  invalid (<18) | valid (18-60) | invalid (>60)
Boundary Value Analysis (test at the edges):
  17 (fail), 18 (pass), 19, 59, 60 (pass), 61 (fail)
Decision table (login):
  valid user + valid pwd   -> success
  valid user + wrong pwd   -> error, attempt count +1
  locked user + any pwd    -> "account locked"

    ✅ Black-box

    Equivalence partitioning, BVA, decision tables, state transition. Based on requirements only.

    🔧 Experience-based

    Exploratory testing and error guessing. Great for finding what scripts miss.

    Test Cases & Bug Reports

    A good test case is atomic, repeatable and has an expected result. A good bug report lets a developer reproduce it in one read.

    bug reportTitle:     Checkout fails with 500 when coupon contains a space
Env:       Staging, Chrome 126, build 2.14.3
Steps:     1. Add any item  2. Go to cart  3. Enter coupon "SAVE 10"  4. Click Apply
Expected:  Validation message "Invalid coupon"
Actual:    HTTP 500, blank page
Severity:  Major     Priority: High
Evidence:  screenshot.png, HAR file, console log

    Severity vs Priority

    Severity

    Technical impact of the defect. Set by QA. E.g. crash = Critical.

    Priority

    How urgently to fix. Set by product/business. E.g. wrong logo on home page = Low severity, High priority.

    💡
    Interview favourite: give one example for each combination (high/low severity × high/low priority).

    Test Lifecycle at a Glance

    Software Test Life Cycle (STLC) with one deliverable per phase.

    Test Pyramid

    The test automation pyramid: automate most at the bottom, least at the top.
    💡
    Manual testers focus on exploratory, usability and new-feature testing. Stable, repeated checks move down the pyramid into automation.

    Types of Testing

    SmokeSanityRegressionFunctionalIntegrationSystemUATExploratoryUsabilityPerformanceSecurityCompatibilityAccessibility

    Smoke vs Sanity

    Smoke: broad, shallow check that the build is stable. Sanity: narrow check that one fix or feature works.

    Regression vs Retest

    Retest: re-run the failed test after a fix. Regression: re-run other tests to confirm nothing else broke.

    Defect Life Cycle

    A defect is Closed only after QA verifies the fix; otherwise it is Reopened.

    Sample Test Case

    TC_LOGIN_003ID:             TC_LOGIN_003
Title:          Login fails with wrong password
Precondition:   User qa@test.com is registered
Test data:      email=qa@test.com, password=Wrong@123
Steps:          1. Open /login  2. Enter data  3. Click "Sign in"
Expected:       Error "Invalid credentials"; user stays on /login
Type/Priority:  Negative / High
Traceability:   REQ-AUTH-02
    ✅
    Always include positive, negative, boundary and security cases for each requirement. Link every case to a requirement ID.

    🗂️ 6. Topics & Subtopics

    Async in JS/TS

    Browser and HTTP calls return Promises. Forgetting await is the #1 cause of flaky JS tests.

    typescriptconst res = await fetch("/api/users/1");   // wait for the response
const body = await res.json();             // wait for the parsing
if (body.id !== 1) throw new Error("Wrong user");
    ⚠️
    A missing await makes the assertion run before the data arrives, so the test passes or fails randomly.

    Functions, Classes & Exceptions

import pytest

    javapublic class Calculator {
    public int divide(int a, int b) {

        return a / b;

    Playwright (TypeScript)

    typescriptimport { test, expect } from "@playwright/test";

test("user can log in", async ({ page }) => {

  await page.getByLabel("Email").fill("qa@test.com");
  await page.getByRole("button", { name: "Sign in" }).click();

});

    • Shared or dirty test data
    • Tests depending on order
    • Slow or unstable environments

    • Create and clean data per test
    • Independent tests
    • Retries only as a safety net

    Schema & Payload Validation

    ✅ 12. Testing & Quality

    API Test Checklist

    • Status codes for success and every error path
    • Body: fields, types, nulls, arrays, pagination
    • Headers: content-type, caching, CORS
    • Auth: missing, expired, wrong-role tokens
    • Negative & boundary input
    • Performance: response time under threshold
    • Idempotency: repeat PUT/DELETE safely

    Regression Best Practices

    • Run a fast smoke suite on every commit, the full regression nightly
    • Run tests in parallel and shard large suites
    • Always publish reports, screenshots and traces as artifacts
    • Quarantine and fix flaky tests, never ignore them
    • Keep secrets in CI variables, never in the repo

    Measuring the quality of your automation suite

    An automation suite is a product too. Track a few numbers so you know whether it is helping or just adding noise.

    MeasureHow to calculate itHealthy signal
    Flake rateTests that fail then pass on rerun ÷ total runsBelow 1–2%; every flaky test has an owner
    Suite durationWall-clock time of the pipeline stageSmoke under 10 minutes; full regression parallelised
    Defects caught by automationBugs first found by an automated test ÷ all bugs found before releaseRising over time for stable areas
    Escaped defectsProduction bugs in areas the suite claims to coverEach one gets a new regression test
    Maintenance costHours per sprint spent fixing broken testsFalling as the framework matures
    Requirement coverageRequirements with at least one automated check ÷ totalRisk-based: high-risk areas close to 100%
    📝
    Coverage is not quality. A test with no assertion still counts as coverage. Review that each test checks a meaningful outcome, not just that a page opened.

    Reporting that people actually read

    • Publish an HTML report (Allure, Playwright report or pytest-html) as a pipeline artifact.
    • Attach screenshots, videos and logs to failed tests automatically.
    • Post a one-line summary to the team channel: passed, failed, flaky, duration, link.
    • Tag tests (smoke, regression, api, ui) so you can slice results by purpose.

    ⭐ 14. Best Practices

    Automation best practices

    PracticeWhy it matters
    Automate stable, repeatable, high-value checks firstUnstable features and one-off checks cost more to automate than they save
    Keep tests independent and order-freeYou can run them in parallel, rerun one alone and trust the result
    Use explicit waits for conditions, never fixed sleepsSleeps make suites slow and still flaky
    Prefer stable locators: data-testid, role, labelLayout-based XPath breaks on every redesign
    Put assertions in tests, behaviour in page objectsPage objects stay reusable and tests stay readable
    Create test data through the API, not the UIFaster setup and fewer unrelated failures
    Test at the lowest level that can catch the bugFollow the pyramid: many unit and API checks, fewer UI checks
    Treat test code like production codeCode review, linting, naming rules and version control
    Keep secrets out of the repoUse CI secrets or a vault for passwords and tokens

    🩺 15. Common Errors & Troubleshooting

    Symptom, likely cause and fix

    SymptomLikely causeFix
    NoSuchElementException / locator not foundElement not rendered yet, wrong frame, or locator changedWait for the condition, switch to the iframe, and replace the locator with a stable attribute
    ElementNotInteractable / click interceptedOverlay, animation, or element outside the viewportWait until clickable, scroll into view, close the overlay, or disable animations in the test environment
    StaleElementReferenceExceptionThe page re-rendered after you found the elementLocate the element again right before using it, or use a locator-based wait
    Passes locally, fails in CIDifferent screen size, slower machine, missing data or environment variableSet the same viewport, use headless flags, seed data in the pipeline and print the environment in logs
    Random failures (flaky)Shared data, race conditions, network varianceIsolate data per test, wait on conditions, find the root cause before adding a retry
    API test returns 401 or 403Expired token, wrong scope or missing headerLog the request, refresh the token in a setup step and assert the status early
    Schema validation fails after a deployContract changed or a field became optionalCompare with the API spec, raise it with the service owner, update the schema deliberately
    Pipeline takes too longEverything runs serially at the UI levelShard and parallelise, move checks to the API level, and run smoke on pull requests only
    ⚠️
    Retries hide problems. A retry can keep a pipeline green while a real race condition ships. Use retries sparingly, track the retried tests and fix them.

    Debugging routine for a failing UI test

    1. Re-run the single test locally with the same browser and viewport.
    2. Open the screenshot, video and trace from the failed run.
    3. Check the console and network log for errors or slow calls.
    4. Confirm the locator in DevTools and the state of the data.
    5. Fix the cause (wait, locator, data) and run the test ten times to confirm.

    🎤 16. Interview Preparation

    Questions and model answers

    Q1. What should you automate and what should you leave manual?

    Answer: Automate stable, repetitive, high-risk checks such as smoke, regression and API tests. Keep exploratory testing, usability checks and one-off scenarios manual.

    Q2. How do you handle flaky tests?

    Answer: Reproduce, find the root cause (timing, shared data, environment), fix it, and quarantine the test meanwhile. Retries are a temporary measure, not a fix.

    Q3. Explain the Page Object Model and its benefit.

    Answer: Each page is a class with locators and actions. Tests call actions, so a UI change is fixed in one place instead of in every test.

    Q4. Selenium, Playwright or Cypress: how do you choose?

    Answer: Selenium for broad language and browser support, Playwright for fast, reliable cross-browser tests with auto-waiting, Cypress for developer-friendly JavaScript apps on Chromium-family browsers. Choose by team skills, browsers needed and app type.

    Q5. Implicit vs explicit waits?

    Answer: Implicit waits apply globally to element lookup; explicit waits wait for a specific condition. Prefer explicit waits and do not mix them.

    Q6. How do you test an API beyond the status code?

    Answer: Check headers, response body against a schema, data values, error messages, performance, authentication and authorisation, and negative and boundary inputs.

    Q7. How do you integrate tests in CI/CD?

    Answer: Run fast tests on every pull request, the wider regression nightly, publish reports as artifacts, and fail the build on test failures.

    Q8. How would you design a framework from scratch?

    Answer: Layers for tests, page objects or clients, test data, configuration and utilities; tagging, reporting and parallel execution; secrets from the environment.

    Q9. How do you decide when a test should be deleted?

    Answer: When it duplicates a lower-level test, covers removed behaviour, or is permanently flaky and costs more than it protects.

    Q10. Tell me about a bug your automation caught.

    Answer: Use the STAR format: the situation, the test you wrote, the defect found, and the impact of catching it before release.

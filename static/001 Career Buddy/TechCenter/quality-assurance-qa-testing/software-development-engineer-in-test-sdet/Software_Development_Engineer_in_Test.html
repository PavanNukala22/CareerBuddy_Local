    Data Structures & Big-O

    Right structure = fast framework. Use a set to de-duplicate test data, a hash map to map test IDs to results, a stack for undo or nested teardown and a queue for BFS crawling or job runners.

    StructureAccessSearchInsertSDET use
    Array / ListO(1)O(n)O(n)Ordered test steps
    Hash Map / Dict—O(1) avgO(1) avgResults by ID, config
    Set—O(1) avgO(1) avgUnique emails, dedupe
    Stack (LIFO)——O(1)Undo, nested fixtures
    Queue (FIFO)——O(1)BFS, parallel job queue
    Binary Search—O(log n)—Sorted logs, version search
    python · hash map patterndef two_sum(nums, target):        # O(n) instead of O(n²)
    seen = {}
    for i, n in enumerate(nums):
        if target - n in seen:
            return [seen[target - n], i]
        seen[n] = i

def first_duplicate(xs):
    seen = set()
    for x in xs:
        if x in seen: return x
        seen.add(x)
    📈
    Big-O order: O(1) < O(log n) < O(n) < O(n log n) < O(n²). Nested loops over the same data are usually O(n²).

    Algorithms You Must Know

    Expect these in coding rounds: two pointers, sliding window, binary search, BFS/DFS, recursion, sorting.

    python · binary searchdef search(a, x):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == x: return mid
        if a[mid] < x:  lo = mid + 1
        else:           hi = mid - 1
    return -1                      # O(log n)
    python · BFS on a page graphfrom collections import deque
def crawl(start, links):
    seen, q = {start}, deque([start])
    while q:
        page = q.popleft()
        for nxt in links.get(page, []):
            if nxt not in seen:
                seen.add(nxt); q.append(nxt)
    return seen

    ⚙️ 5. Core Concepts

    Object-Oriented Design

    OOP keeps a 2,000-test framework maintainable.

    🔒
    Encapsulation
    Hide internals (private driver, helpers); expose clean methods.
    🎭
    Abstraction
    Tests say checkout.pay(), not 12 clicks.
    🧬
    Inheritance
    BaseTest / BasePage share setup & waits.
    🔀
    Polymorphism
    Same driver.get() across Chrome / Firefox / remote.
    python · base page with compositionclass BasePage:
    def __init__(self, driver):
        self._driver = driver               # encapsulated
    def click(self, locator):
        WebDriverWait(self._driver, 10).until(
            EC.element_to_be_clickable(locator)).click()

class CartPage(BasePage):                   # inheritance
    PAY = ("id", "pay")
    def pay(self): self.click(self.PAY)
    ⚖️
    Prefer composition over inheritance when behaviour is not a true "is-a" relationship — e.g. give pages a WaitHelper instead of a 6-level class tree.

    Design Patterns for Test Frameworks

    🏭
    Factory
    Create driver / client by name or config.
    1️⃣
    Singleton
    One config, one logger, one DB pool.
    ♟️
    Strategy
    Swap auth, browser or report strategy.
    🏗️
    Builder
    Fluent test-data construction.
    👀
    Observer
    Listeners for test events & screenshots.
    🎁
    Decorator
    Add retry, logging, timing to functions.
    python · builder + factoryclass UserBuilder:
    def __init__(self): self.d = {"name": "Asha", "role": "user"}
    def admin(self): self.d["role"] = "admin"; return self
    def build(self): return dict(self.d)

admin = UserBuilder().admin().build()

def make_driver(name):
    return {"chrome": Chrome, "firefox": Firefox}[name]()
    python · retry decoratordef retry(times=3):
    def deco(fn):
        def run(*a, **k):
            for i in range(times):
                try: return fn(*a, **k)
                except AssertionError:
                    if i == times - 1: raise
        return run
    return deco

    Clean Code & SOLID

    S → O → L → I → D
    • Single Responsibility — one reason to change
    • Open/Closed — extend, don't edit working code
    • Liskov — subclasses must be usable as the parent
    • Interface Segregation — small, focused interfaces
    • Dependency Inversion — depend on abstractions → easy mocking

    ❌ Smelly

    One 300-line test_everything(), magic numbers, copy-pasted logins, sleep(5) everywhere.

    ✅ Clean

    Small intention-revealing tests, constants, shared fixtures, explicit waits, one assertion theme per test.

    ✅
    Review checklist: meaningful names · functions under ~20 lines · DRY · no commented-out code · tests reviewed like production code.

    🗂️ 6. Topics & Subtopics

    The Test Pyramid

    Put most checks where they are fast, cheap and precise.

    LayerShareSpeedTools
    Unit~70%millisecondspytest, JUnit, TestNG
    API / Integration~20%secondsrequests, RestAssured, Postman
    UI / E2E~10%minutesSelenium, Playwright, Cypress
    ⚠️
    Anti-pattern — the ice-cream cone: mostly UI tests, few unit tests. Slow, brittle, expensive to debug.

    Framework Architecture

    Build in layers so a UI change touches one file, not hundreds of tests.

    layered structureframework/
├── core/        driver_factory.py  config.py  logger.py  waits.py
├── pages/       login_page.py  cart_page.py        (UI layer)
├── api/         users_client.py  orders_client.py  (service layer)
├── data/        builders.py  factories.py  fixtures/
├── tests/       ui/  api/  e2e/
├── reports/     allure-results/
└── conftest.py  pytest.ini  Dockerfile  Jenkinsfile
    Tests → Pages / API clients → Core utilities → Config + Reports

    A flaky test passes and fails with no code change. Main causes: fixed sleeps, shared state, order dependency, live third parties, timezones.

    🚀 10. Advanced Concepts

    Contract Testing with Pact

    In microservices, a provider can silently break a consumer. Consumer-driven contract testing lets each consumer record what it needs; the provider proves it still delivers — without deploying both together.

    Consumer test → Pact file → Pact Broker → Provider verifies → can-i-deploy
    python · consumer side (pact-python)pact.given("user 1 exists") \
    .upon_receiving("a request for user 1") \
    .with_request("GET", "/users/1") \
    .will_respond_with(200, body={"id": 1, "name": Like("Asha")})
with pact:
    assert UsersClient(pact.uri).get(1)["id"] == 1
    bash · publish & gatepact-broker publish pacts --consumer-app-version $GIT_SHA
pact-broker can-i-deploy --pacticipant Orders --version $GIT_SHA
    💡
    Contract tests are fast and isolated. They replace many slow E2E "do the services still agree?" tests.

    Secrets, Quality Gates & Good Habits

    ✅ Do

    Keep secrets in the CI secret store; fail pipelines on coverage / failing tests; cache dependencies; publish reports as artifacts; pin image versions.

    ❌ Don't

    Mutation Testing

    Mutation tools change your code slightly (> → >=, + → -) and re-run tests. If tests still pass, the mutant survived — your tests are weak there.

    bash · toolsmutmut run            # Python
mvn org.pitest:pitest-maven:mutationCoverage   # Java (PIT)
    ✅
    Mutation score = killed mutants ÷ total. Aim for strong scores on critical business logic, not everywhere.

    ⭐ 14. Best Practices

    Engineering practices for test code

    PracticeWhy it matters
    Apply SOLID and keep classes smallTest frameworks grow for years; clean structure keeps changes cheap
    Favour composition over inheritance in page objects and clientsAvoids deep hierarchies that are hard to change
    Use dependency injection and fixtures for setupTests stay isolated and easy to read
    Mock at the boundary, not everywhereOver-mocking makes tests pass while the real system is broken

    🩺 15. Common Errors & Troubleshooting

    Symptom, likely cause and fix

    SymptomLikely causeFix
    Tests pass alone but fail togetherShared state, database rows or static variablesGive each test its own data, reset state in fixtures, run in random order to expose coupling
    Container tests fail on startupThe app is not ready when the tests beginUse health checks and wait for readiness; in Compose use depends_on with a healthy condition
    Contract verification fails on the providerResponse shape changed or a provider state is missingCompare the pact with the response, fix the provider or version the contract, and add the provider state
    Mutation score is low despite high coverageTests execute code without asserting resultsAdd assertions on outputs and side effects; target surviving mutants in critical code
    Mocks hide real integration bugsMock behaviour differs from the real serviceAdd contract tests and a few Testcontainers integration tests against the real dependency
    CI is much slower than localCold caches, serial execution, heavy imagesCache dependencies, parallelise by shard, slim the test image
    Secrets leak into logsPrinting environment or full requestsMask secrets in CI, never print headers with tokens and rotate any exposed credential
    Kubernetes test pod crashesMissing config, resource limits or image pull errorsRun kubectl describe and kubectl logs, check ConfigMaps and requests/limits

    Debugging a failing pipeline

    1. Read the first error in the log, not the last one.
    2. Reproduce locally with the same container image and environment variables.
    3. Run only the failing test and then the failing shard.
    4. Check timing: slow dependency, startup order, timeouts.
    5. Fix the cause, add a regression test if the failure revealed a gap, and rerun the full pipeline.

    🎤 16. Interview Preparation

    Questions and model answers

    Q1. How does an SDET differ from a manual QA engineer and a developer?

    Answer: An SDET writes production-quality code to test software: frameworks, tools and pipelines. Compared with manual QA they automate and engineer; compared with a developer their focus is testability and risk, not features.

    Q2. What is the time complexity of searching a sorted array and a hash map?

    Answer: Binary search is O(log n); a hash map lookup is O(1) on average.

    Q3. Which design patterns are useful in test frameworks?

    Answer: Page Object, Factory and Builder for objects and data, Strategy for interchangeable behaviour such as browsers or environments, Singleton sparingly for configuration.

    Q4. Explain the test pyramid.

    Answer: Many fast unit tests, fewer integration and API tests, and a small number of end-to-end tests. It balances speed, cost and confidence.

    Q5. What is contract testing and when do you use it?

    Answer: It checks that a consumer and provider agree on an API. Use it between microservices so each team can deploy independently without a full end-to-end environment.

    Q6. Mock, stub, fake and spy: what is the difference?

    Answer: A stub returns canned answers, a mock also verifies interactions, a fake is a working lightweight implementation, and a spy records calls on a real object.

    Q7. What does mutation testing tell you that coverage does not?

    Answer: Whether tests actually fail when code changes. It injects small faults and reports how many your tests detect.

    Q8. How would you containerise a test run?

    Answer: Package the tests in an image, use Docker Compose for the app and dependencies, wait for health checks, run the tests, and export reports as artifacts.

    Q9. How do you stop flaky tests from spreading?

    Answer: Isolate data, avoid sleeps, run tests in random order, track flake rate, quarantine and fix with an owner and a deadline.

    Q10. What quality gates would you add to a pipeline?

    Answer: Unit and integration pass rate, coverage threshold on new code, contract verification, SAST and dependency scans, and a smoke test after deployment.

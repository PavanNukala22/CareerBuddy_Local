    Debugging Backend & Frontend Code

    Tier 3 reads code to find the real cause of a failure. Learn a repeatable workflow and the typical failure signatures per language.

    🔁 The Debugging Workflow

    1. Reproduce the failure with exact inputs, version and environment.
    2. Isolate the failing layer: client, API, service, database.
    3. Hypothesise from logs and stack trace; change one thing at a time.
    4. Inspect with breakpoints, prints or a debugger.
    5. Fix or hand off with a minimal patch or precise bug report.
    6. Verify and add a regression test.

    🧬 Failure Signatures by Language

    LanguageTypical failureFirst look
    PythonAttributeError on None, KeyErrorTraceback bottom line, input data shape
    JavaNullPointerException, ConcurrentModificationExceptionStack trace top frame, shared mutable state
    JavaScriptundefined access, unhandled promise rejectionConsole/network tab, async ordering
    Gonil pointer, goroutine leak, deadlockPanic trace, pprof goroutines
    RubyNoMethodError for nil, N+1 queriesRails log, byebug

    Practice

    1) Get request ID, time, payload and version. 2) Pull logs for that request ID. 3) Read the stack trace to find the failing frame. 4) Reproduce locally or in staging with the same payload. 5) Form one hypothesis and test it with a breakpoint or log.

    Module 02 · Concepts

    Bugs, Call Stacks & Breakpoints

    What a bug really is, how a program remembers where it is, and how a debugger pauses time so you can look around.

    🐞 Three Kinds of Bugs

    A bug is any gap between what the code does and what it was meant to do. They fall into three families, and recognising the family tells you where to look first.

    TypeWhen it appearsExampleHow you find it
    Syntax errorBefore the program even runsMissing colon or bracketThe compiler/interpreter points at the line
    Runtime errorWhile running, on a specific inputDivide by zero, None accessStack trace names the failing line
    Logic errorSilently, the output is just wrongUsing < instead of <=Tests, debugger, comparing expected vs actual
    🧴
    Analogy: a syntax error is a sentence with broken grammar (the editor flags it instantly), a runtime error is a car that stalls on a hill, and a logic error is a car that drives smoothly to the wrong city. The last one is the hardest because nothing complains.

    📚 The Call Stack, Explained Slowly

    When function a() calls b(), which calls c(), the program must remember where to return after each call. It keeps these notes in a call stack: a pile of frames, newest on top. Each frame stores that function's local variables and the line it is currently on. A stack trace is simply a printout of this pile at the moment of failure.

    pythondef a(): return b()
def b(): return c()
def c(): return 1 / 0     # fails here

a()
# Traceback: a() -> b() -> c() -> ZeroDivisionError
# Stack at failure (top first): c, b, a, <module>

    Read it like breadcrumbs. The top frame is where it broke; the frames below are how you got there. In a debugger you can click each frame and see that function's variables exactly as they were, which often reveals the true mistake (a bad argument passed down from a) rather than the symptom.

    🧴
    Analogy: a stack of plates. You can only touch the top plate, and the plates underneath tell you the order in which they were stacked.

    ⏸️ Breakpoints & Stepping

    A breakpoint tells the debugger to pause when execution reaches a line. Once paused you control time with four moves:

    ActionShortcut (typical)Meaning
    Step overF10 / nRun this line; if it calls a function, treat the call as one step
    Step intoF11 / sEnter the function being called
    Step outShift+F11 / rFinish the current function and stop at its caller
    ContinueF5 / cRun until the next breakpoint
    📌
    Watch expressions keep a variable or formula on screen as you step. Conditional breakpoints pause only when something is true, such as user_id == 8841, which saves you from stepping through thousands of good iterations.

    🏋️ Practice & Quick Check

    Practice
    P1.Explain in your own words why the top frame of a stack trace is not always the real cause of the bug.
    The top frame shows where the error was detected. The bad value may have been created earlier and passed down through several calls, so you must walk down the stack, inspect each frame's variables and find where the value first became wrong.
    Q1.Which action runs a function call as ONE step without entering it?
    • A Step into
    • B Step over
    • C Step out
    • D Restart

    Debugging Python & Java

    Read tracebacks and stack traces quickly and recognise the bugs that show up again and again.

    🐍 Reading a Python Traceback

    tracebackTraceback (most recent call last):
  File "api.py", line 42, in handle
    total = calc(order)
  File "billing.py", line 17, in calc
    return sum(i['price'] for i in order['items'])
TypeError: 'NoneType' object is not iterable

    Read bottom to top: the last line is the error, the frame above it is where it surfaced, and the frames above that show how you got there.

    ExceptionUsual meaning
    AttributeError / TypeError on NoneA value was never set upstream
    KeyErrorMissing dict key in payload or config
    RecursionErrorInfinite or very deep recursion
    UnicodeDecodeErrorWrong encoding on input file
    python: classic bugdef add(x, bucket=[]):   # default list is shared between calls!
    bucket.append(x)
    return bucket
# Fix: bucket=None; if bucket is None: bucket = []

    ☕ Reading a Java Stack Trace

    javajava.lang.IllegalStateException: Payment failed
  at PaymentService.charge(PaymentService.java:88)
  at CheckoutController.pay(CheckoutController.java:31)
Caused by: java.sql.SQLTransientConnectionException: Connection is not available
  at HikariPool.getConnection(HikariPool.java:179)
    💡
    In Java, jump to the Caused by line: it is the root exception. Here the real issue is an exhausted DB connection pool, not the payment code.
    ProblemClueFix direction
    NullPointerExceptionLine number + helpful NPE messageNull check or fix upstream data
    ConcurrentModificationExceptionModifying a list while iteratingUse iterator.remove or copy
    OutOfMemoryErrorHeap or metaspace in messageHeap dump, find the leak
    DeadlockThreads BLOCKED in jstackLock ordering

    🏋️ Practice & Quick Check

    Practice
    P1.In the Java trace above, which line is the real root cause and why?
    The Caused by line (SQLTransientConnectionException): the DB connection pool had no free connection. The IllegalStateException is only a wrapper raised higher up.
    Q1.In a Python traceback the actual error message is…
    • A On the first line
    • B On the last line
    • C Hidden
    • D In the file name

    Debugging JavaScript, Go & Ruby

    Async bugs, goroutine leaks and N+1 queries: the three problems Tier 3 sees most in these stacks.

    🟨 JavaScript: Async Bugs

    javascriptasync function load() {
  const user = fetchUser(id);      // BUG: missing await -> Promise, not user
  console.log(user.name);          // undefined
}
// Fix: const user = await fetchUser(id);
// Also: wrap in try/catch or add .catch() to avoid unhandled rejections

    Use browser DevTools (Network and Sources tabs) for frontend and node --inspect for backend. Check CORS and status codes before blaming the code.

    🐹 Go: Nil Pointers & Goroutine Leaks

    govar m map[string]int      // nil map
m["a"] = 1                // panic: assignment to entry in nil map

ch := make(chan int)
go func(){ ch <- 1 }()   // leaks if nobody ever receives

    Use go tool pprof goroutine profile or runtime.NumGoroutine() over time: a number that keeps rising means a leak.

    💎 Ruby: N+1 Queries

    ruby (rails)# N+1: one query for posts, then one per post for the author
Post.all.each { |p| puts p.author.name }
# Fix: eager load
Post.includes(:author).each { |p| puts p.author.name }
    📌
    Rails log lines repeating the same SELECT with different ids are the signature of N+1.

    🏋️ Practice & Quick Check

    Practice
    P1.A Go service's memory grows daily and goroutine count keeps rising. What is your hypothesis and how do you confirm it?
    Goroutine leak: goroutines blocked forever on channels or I/O. Confirm with a goroutine pprof profile at two times and compare stacks that grow; fix with context cancellation or buffered/closed channels.
    Q1.Missing await on an async call usually results in…
    • A A Promise instead of the value
    • B A faster program
    • C A syntax error
    • D A deleted file

    Stepping Through Code

    Use debuggers and logging to follow execution, inspect state and confirm root cause.

    🐍 Example: Python Debugging

# Fails: TypeError: 'NoneType' object is not iterable

    Module 06 · Tooling

    Debuggers, Remote Debugging & Profiling

    Move from print statements to proper tooling, and learn to debug code that runs on a server you cannot sit at.

    🖥️ Using an IDE Debugger

    IDEs such as VS Code, IntelliJ and PyCharm wrap the debugger in a visual interface: click the gutter to set a breakpoint, press run-in-debug, and the Variables, Watch and Call Stack panels fill in. A launch.json file stores how to start your program, so the whole team debugs the same way.

    json (.vscode/launch.json){
  "version": "0.2.0",
  "configurations": [{
    "name": "Debug API",
    "type": "python",
    "request": "launch",
    "module": "uvicorn",
    "args": ["app.main:app", "--reload"],
    "env": { "APP_ENV": "staging" }
  }]
}

    Line by line: request: launch means the IDE starts the process itself, module and args are the command, and env injects environment variables, so you can reproduce a staging-only bug locally without editing code.

    📡 Remote Debugging

    Sometimes the bug only exists on a server. Remote debugging starts the program with a small debug server listening on a port; your IDE attaches to it over the network.

    bashpython -m debugpy --listen 0.0.0.0:5678 --wait-for-client app.py
# Java:  java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar
# Node:  node --inspect=0.0.0.0:9229 server.js
    ⚠️
    Never expose a debug port to the public internet: it allows code execution. Use an SSH tunnel (ssh -L 5678:localhost:5678 host) and never pause a production process that is serving live customers.

    🔥 Profiling: Finding Slow Code

    A profiler measures where time (or memory) is spent. Guessing which function is slow is wrong surprisingly often, so measure first.

    pythonimport cProfile, pstats
cProfile.run('process_orders()', 'out.prof')
pstats.Stats('out.prof').sort_stats('cumulative').print_stats(10)
# Look at: ncalls (how often), tottime (time inside), cumtime (including callees)
    LanguageProfiler
    PythoncProfile, py-spy (attach to a live process)
    Javaasync-profiler, JFR, VisualVM
    Gopprof (go tool pprof)
    Node--prof, Chrome DevTools Performance
    🧴
    Analogy: a profiler is a stopwatch on every room of a factory. You stop blaming the whole factory and find that 80% of the time is spent in one corridor.

    🏋️ Practice & Quick Check

    Practice
    P1.Why is it risky to use a breakpoint on a production server, and what is a safer alternative?
    A breakpoint freezes the process, so live requests hang or time out. Safer: reproduce in staging, add structured logging, use non-blocking tools such as py-spy or a sampling profiler, or capture a thread/heap dump.

    • B Time including the functions it calls

    • D Memory used

    Module 07 · Method

    Logs, Evidence & Minimal Reproduction

    Good debugging starts with good evidence. Learn to read logs and shrink a failure down to a tiny repro.

    📜 Log Levels & Correlation IDs

    LevelUse
    ERROROperation failed, needs attention
    WARNUnexpected but handled
    INFONormal business events
    DEBUG/TRACEDetailed flow, usually off in production

    A correlation / request ID passed through every service lets you pull every log line for one request. Always ask the customer for one.

    log searchgrep "req-7f3a91" app.log | sort
# or in your log tool: request_id:"req-7f3a91" AND level:ERROR

    🔬 Building a Minimal Reproduction

    1. Copy the failing request or input exactly.
    2. Remove fields, steps and config until the failure stops; the last thing removed matters.
    3. Pin versions of the app and key dependencies.
    4. Write it as a script or test anyone can run.
    5. Attach it to the ticket.

    🕵️ Finding the Breaking Change

    git bisectgit bisect start
git bisect bad HEAD          # current version is broken
git bisect good v4.1.0       # this version worked
# test each commit git suggests; mark: git bisect good / bad
# git reports the first bad commit
git bisect reset

    🏋️ Practice & Quick Check

    Practice
    P1.A bug appeared between v4.1.0 and v4.2.1, 140 commits apart. How do you find the culprit commit quickly?
    Use git bisect: mark v4.1.0 good and v4.2.1 bad, run the repro at each step; it finds the first bad commit in about 8 steps (log2 of 140).

    Race Conditions, Deadlocks & Memory Leaks

    The hardest bugs are the ones that depend on timing. Learn how they appear and how to catch them.

    🏁 Race Conditions

    A race condition happens when two threads touch the same data and the result depends on who gets there first. The bug appears only sometimes, which is why it is often 'cannot reproduce'.

    pythoncounter = 0
def work():
    global counter
    for _ in range(100000):
        counter += 1      # read, add, write: NOT atomic

# Two threads -> final counter is less than 200000 on some runs
# Fix: use a lock
import threading
lock = threading.Lock()
with lock:
    counter += 1

    counter += 1 looks like one step but is three: read, add, write. If thread B reads before thread A writes, one increment is lost. Locks make the three steps one indivisible unit.

    🧴
    Analogy: two people editing the same shared document offline, then both saving: the second save silently erases the first person's change.

    🔒 Deadlocks

    A deadlock is when thread A holds lock 1 and waits for lock 2, while thread B holds lock 2 and waits for lock 1. Both wait forever, so the service hangs with low CPU. A thread dump shows both threads BLOCKED and names the locks.

    PreventionHow
    Lock orderingAlways acquire locks in the same global order
    TimeoutsUse acquire(timeout=...) and handle failure
    Smaller critical sectionsHold locks for as short a time as possible

    💧 Memory Leaks in Python & Node

    Even garbage-collected languages leak when something keeps a reference alive: a growing global list, a cache with no limit, or event listeners that are never removed.

    pythonimport tracemalloc
tracemalloc.start()
# ... run the workload ...
snap = tracemalloc.take_snapshot()
for s in snap.statistics('lineno')[:5]:
    print(s)          # shows which lines allocate the most memory
    💡
    Take two snapshots minutes apart and compare them (snap2.compare_to(snap1, 'lineno')). Whatever keeps growing is your suspect.

    🏋️ Practice & Quick Check

    Practice
    P1.Two threads each increment a shared counter 100,000 times but the total is 187,342. Explain why and how to fix it.
    counter += 1 is read-add-write, not atomic. Interleaving causes lost updates. Fix with a lock, an atomic counter, or message passing so only one thread mutates the value.
    Q1.A service hangs with near-zero CPU and two threads are BLOCKED on each other's locks. This is a…
    • A Memory leak
    • B Deadlock
    • C Slow query
    • D Race condition

    Module 09 · Resolution

    Writing the Fix and Proving It

    Finding the cause is half the job. Now make the smallest safe change and prove it with a test.

    🧪 Failing Test First

    Before changing code, write a test that fails because of the bug. When your fix makes it pass, you have proof, and the test stays forever to stop the bug from returning (a regression test).

    python (pytest)def test_total_handles_missing_items():
    order = {'id': 7, 'items': None}      # the real payload that broke production
    assert calc_total(order) == 0          # RED before the fix

# fix in billing.py
def calc_total(order):
    items = order.get('items') or []
    return sum(i['price'] * i['qty'] for i in items)   # GREEN after the fix

    The test uses the exact payload from the customer, so it is proof about their case, not a guess.

    🩺 Minimal, Safe Changes

    A good support-level patch is small, targeted and easy to review. Resist the urge to refactor nearby code during an incident: every extra line is another place for a new bug.

    DoAvoid
    Fix the root cause at the right layerHiding the error with a blanket try/except: pass
    Add a guard plus a log lineSilently returning default values
    One change per commitMixing the fix with formatting changes
    Explain WHY in the commit messageMessages like 'fix bug'
    ⚠️
    A swallowed exception turns a loud, easy bug into a silent data-corruption bug. Catch only what you can handle, and always log it.

    🔍 Who Changed This and Why?

    gitgit blame -L 40,60 billing.py        # who last touched each line
git log -S"items" -- billing.py        # commits that added/removed this text
git show 3fa91c2                         # the full change and its message
git log --oneline v4.1.0..v4.2.1 -- billing.py

    History tells you the intent of the code. Before 'fixing' a strange line, read the commit and linked ticket; it may be a deliberate workaround for a different customer's problem.

    🏋️ Practice & Quick Check

    Practice
    P1.Why must a regression test use the customer's real failing input?
    It proves the fix works for the exact case that failed, and guards against reintroducing it. A generic happy-path test might pass even with the bug present.
    Q1.What is wrong with wrapping the failing code in try/except: pass?
    • A Nothing, it is best practice
    • B It hides the error and can cause silent bad data
    • C It makes code faster
    • D It fixes the root cause

    Module 10 · Scenarios

    Real-World Debugging Scenarios

    Worked examples that combine the workflow, tools and communication.

    💥 Scenario: Intermittent 500 after a release

    • Symptom: 2% of checkouts return 500 since v4.2.1.
    • Logs show Connection is not available; the error rate rises with traffic.
    • Diff shows a new report query holding connections for 30 s.
    • Mitigation: raise pool size temporarily and flag off the report; fix: add index and timeout.
    • Hand-off: ticket with request IDs, query, diff and graphs.

    🧊 Scenario: Works on my machine

    • Fix passes locally but fails in staging.
    • Compare versions, environment variables, locale/timezone, data volume and feature flags.
    • Run the same container image locally to remove drift.

    ⏱️ Scenario: UI freezes for one customer

    • Capture a HAR file and DevTools performance profile.
    • Find a long task or a huge API response (50 MB) on that tenant.
    • Raise to engineering: pagination or virtual scrolling needed, with the HAR attached.

    🏋️ Practice & Quick Check

    Practice
    P1.Staging passes but production fails for one tenant only. List four differences to check.
    Tenant data size/shape, feature flags or config, integration credentials/endpoints, and software or dependency versions on that cluster.
    Q1.A bug appears only for one tenant. First thing to compare?
    • A Their data and configuration
    • B The logo
    • C The browser colour
    • D The office location

    How do you debug code you did not write?Reproduce first, read the stack trace, trace data flow from entry point, use a debugger and read tests for intended behaviour.

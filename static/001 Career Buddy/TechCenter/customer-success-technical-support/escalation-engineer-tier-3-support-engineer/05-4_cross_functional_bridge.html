    Module 02 · Analysis

    Understanding a Client's Failure State

    Before you can translate a complaint you must understand exactly what state the system is in: what failed, when, for whom, and how badly.

    🩻 What Is a Failure State?

    Clients describe pain ('the system is broken'); engineers need a failure state: the precise combination of the observed symptom, the conditions that trigger it, the actual versus expected behaviour and the blast radius (who and what is affected). Your job as the bridge is to turn the first into the second.

    🧴
    Analogy: a weather report. 'The weather is bad' is a complaint; '38 mm of rain per hour, wind 60 km/h from the west, starting 14:00 in the north district' is a state someone can act on.
    CategoryMeaningExampleFirst question to ask
    FunctionalWrong result or missing behaviourDiscount not appliedWhat did you expect and what did you get?
    AvailabilityDown, errors, timeoutsLogin returns 503Since when, and for whom?
    PerformanceWorks but too slowReport takes 3 minHow long did it take before?
    Data integrityWrong, lost or duplicated dataInvoice created twiceWhich records, and how do you know?
    Security / accessWrong permissionsUser sees other tenant's dataTreat as urgent: what data and who?
    IntegrationBreaks between systemsCRM sync stopsWhich direction, which endpoint, which error?

    🧩 Symptom, Trigger, Cause, Impact

    ElementQuestionExample
    SymptomWhat is observed?Invoice PDFs are blank
    TriggerUnder what conditions?Tenants with a custom template and more than 10 line items
    Cause (hypothesis)Why might this happen?Template engine timeout on large tables (unproven)
    ImpactWho and how much?About 40 invoices a day, month-end close at risk
    ⚠️
    Never write an unproven cause as fact in the ticket title. Keep symptom and trigger factual and label causes as hypotheses; a wrong cause sends engineering in the wrong direction.

    📋 The Intake Questionnaire

    checklistWHAT   exactly happened? Error text / screenshot / wrong value
EXPECT what should have happened (reference to doc or previous behaviour)
WHEN   first seen, last seen, still happening now?
HOW OFTEN always, intermittent (about what %), only at certain times
WHO    which users, tenants, regions, roles, browsers
CHANGE what changed recently: release, config, data load, traffic, integration
WORKAROUND is there one, and does the client use it
DEADLINE  business date or SLA that makes this urgent

    Ask in this order: facts about the failure first, then conditions, then change history. 'What changed?' is the single most productive question in diagnosis, because most failures begin with a change.

    🏋️ Practice & Quick Check

    Practice
    P1.A client says 'our totals are wrong in the export'. Write five intake questions to turn this into a failure state.
    1) Which totals and which export (report/date range)? 2) What value did you expect and where does it come from? 3) What value did you get, with a sample record? 4) Is it every export or only some tenants/dates, since when? 5) What changed recently (release, data import, currency/tax settings)?
    Q1.The most productive diagnostic question is usually…
    • A Who is to blame?
    • B What changed recently?
    • C How big is the screen?
    • D Do you like the product?

    Module 03 · Evidence

    Gathering Reproducible Evidence

    Engineers believe evidence, not adjectives. Learn what to collect, how to capture it, and how to protect customer data while doing it.

    ⚖️ The Evidence Hierarchy

    Not all evidence is equal. Strong evidence lets an engineer reproduce and prove the problem without talking to you again.

    🧴
    Analogy: a court case. A recorded timestamped log is a witness who cannot change their story; 'I think it was slow around lunchtime' is hearsay.
    StrengthEvidenceWhy
    StrongestRequest ID/trace ID + matching server logsPinpoints the exact request
    StrongReproducible steps or script with sample payloadAnyone can re-run it
    GoodHAR file, video, screenshot with timestampShows what the user saw
    WeakVerbal description, 'it is slow sometimes'Cannot be verified

    🧰 Capturing It Properly

    bash# Reproduce an API failure with a redacted token
curl -sS -i -X POST https://api.example.com/v2/export \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"account":"acme","rows":80000}' -w "\ntime_total=%{time_total}s\n"

# Pull the matching server logs for the request ID returned in the response header
grep "req-7f3a91" /var/log/app/api.log | head -50
    1. Ask the client to export a HAR file from browser DevTools (Network tab, Save all as HAR) while repeating the failure.
    2. Record the exact UTC time of the failing attempt and any request ID shown on screen.
    3. Capture app version and tenant from the About or admin page.
    4. Save sample input that triggers the failure (sanitised).
    5. Attach everything to the ticket, not to a private chat.
    💡
    -i keeps response headers (where request IDs live) and -w prints timing, so one command gives status, headers, body and latency.

    🕰️ Building a Timeline

    timeline (UTC)09:58  Release 4.2.1 deployed to EU cluster
10:12  First failed export (customer report)
10:40  Error rate on /export rises from 0.1% to 6%
11:05  Support confirms failure only for accounts above 50k rows
11:20  Workaround: export by date range (works)

    A timeline turns scattered messages into a story with cause and effect. Always use UTC so logs, deployments and customer reports line up across time zones; the key insight here is that the first failure came minutes after a deployment.

    🔐 Redaction and Privacy

    ⚠️
    Before attaching evidence, remove passwords, tokens, API keys, card numbers and personal data from logs, HARs and screenshots. Replace values with placeholders like REDACTED but keep structure intact so engineers can still reproduce the issue. Follow your company's data-handling policy and only share through approved ticket systems.

    🏋️ Practice & Quick Check

    Practice
    P1.Why is 'request ID plus server logs' stronger evidence than a customer's screenshot alone?
    The request ID links the customer's action to the exact server-side processing and error, so engineers can see inputs, stack trace and timing. A screenshot shows only the symptom and cannot be traced into the system.
    Q1.Why record timestamps in UTC?
    • A It looks professional
    • B Logs, deployments and reports from different time zones line up
    • C It uses less storage
    • D It is required by browsers

    Module 04 · Requirements

    From Complaint to Acceptance Criteria

    Engineers build what is written. Learn to turn a client's pain into something testable.

    📝 User Story + Acceptance Criteria

    gherkinAs a finance user
I want CSV export to work for large reports
So that I can close the month on time

Given an account with 80,000 rows
When I click Export CSV
Then the file downloads within 60 seconds
And contains all 80,000 rows
And no HTTP 5xx error is logged

    The story states who, what and why. The Given/When/Then lines are acceptance criteria: concrete checks that tell everyone the work is done. Without them, two people can disagree forever about whether a bug is 'fixed'.

    🧴
    Analogy: ordering a custom suit. 'Make it look nice' gets you a surprise; exact measurements get you a fit. Acceptance criteria are the measurements.

    🎯 Vague → Concrete

    Customer saysEngineering requirement
    It is slowp95 load time of dashboard under 3 s for 10k widgets
    It keeps failingError rate under 0.5% on /api/orders over 24 h
    Data is wrongTotals in report must equal sum of invoice lines to 2 decimals
    I cannot log in sometimesSSO login succeeds within 5 s for 99.9% of attempts
    💡
    Quantify with a number, a condition and a time window. If you cannot measure it, engineers cannot test it.

    🏋️ Practice & Quick Check

    Practice
    P1.Turn 'the sync is unreliable' into one measurable acceptance criterion.
    'Given 1,000 changed records, when sync runs, then 100% appear in the destination within 5 minutes, with zero duplicates and no errors in the sync log.'
    Q1.Acceptance criteria exist to…
    • A Define when the work is done
    • B Increase ticket count
    • C Replace testing
    • D Assign blame

    Module 05 · Requirements

    Turning Failures into Engineering Requirements

    The core skill of the bridge: converting a described failure into precise, testable requirements that Core Engineering can design, build and verify.

    🏗️ Functional vs Non-Functional Requirements

    A functional requirement says what the system must do. A non-functional requirement (NFR) says how well it must do it: speed, reliability, security, scale. Client complaints are often about NFRs ('it is slow', 'it keeps failing') and need to be converted into numbers.

    🧴
    Analogy: building a house. Functional: three bedrooms and a kitchen. Non-functional: survives an earthquake, keeps heat in winter, supports 10 people. Both matter; only the first is obvious to the buyer.
    TypeClient statementRequirement
    FunctionalExport must include archived ordersExport includes orders with status ARCHIVED when filter 'include archived' is on
    PerformanceReports are slowp95 report generation under 10 s for 100k rows
    ReliabilityIt keeps failingSuccess rate of /sync at least 99.9% over 30 days
    SecurityAnyone can see itRole VIEWER cannot access invoice amounts
    ScalabilityIt breaks at month-endHandle 5x normal load (2,500 requests/min) for 2 hours

    🚫 Requirement Smells

    Vague wordingProblemBetter
    fast, quickNo numberp95 < 3 s
    robust, reliableCannot be tested99.9% success over 30 days, retries 3x
    user-friendlySubjectiveUser completes checkout in at most 4 clicks
    should workOptional and unclearmust succeed for files up to 100 MB
    etc., and so onOpen-endedList all cases
    handle all errorsInfiniteReturn HTTP 400 with error code for invalid input; 5xx never exposes stack traces

    🎫 A Complete Engineering Ticket

    ticketTITLE: CSV export fails (HTTP 500) for accounts with more than 50,000 rows since v4.2.1

PROBLEM: Finance users at Acme cannot close month-end; 3 users blocked, 5 attempts failed.
CURRENT: Export returns 500 after about 30 s; log: TimeoutError in ExportWorker (req-7f3a91).
EXPECTED: Export completes and downloads all rows.

REQUIREMENTS
R1 (Must)   Export of up to 200,000 rows completes within 60 s (p95).
R2 (Must)   On failure, return 4xx/5xx with a clear message and error code, never a blank file.
R3 (Should) Stream results so memory stays under 512 MB.

ACCEPTANCE
Given an account with 80,000 rows, when exporting CSV, then all rows are downloaded within 60 s and no 5xx appears in logs.

OUT OF SCOPE: Excel export format.
EVIDENCE: HAR, logs, sample payload, timeline (attached)
IMPACT: month-end close at 3 enterprise accounts; SLA credit risk

    Notice the structure: facts first, then numbered requirements with priority, then a testable acceptance condition and an explicit out-of-scope line to prevent scope creep. Numbered requirements let engineers and reviewers refer to 'R2' unambiguously.

    🧮 Prioritising Requirements: MoSCoW

    LevelMeaningExample
    MustRelease is useless without itExport completes for 200k rows
    ShouldImportant, but a workaround existsStreaming to lower memory
    CouldNice to haveProgress bar
    Won't (now)Agreed not to do this timeExcel format

    🏋️ Practice & Quick Check

    Practice
    P1.Rewrite 'the report should be faster and more reliable' as two testable requirements.
    R1: The monthly sales report for up to 100,000 rows must generate within 10 s at p95. R2: Report generation must succeed for at least 99.9% of requests over a rolling 30 days, with automatic retry up to 3 times on transient errors.
    Q1.Which is a well-formed non-functional requirement?
    • A The app should be fast
    • B p95 page load under 3 s for 10,000 users
    • C Make it better
    • D Improve everything

    Module 07 · Prioritisation

    Quantifying Impact and Making the Case

    Engineering time is limited. Numbers and clear business impact decide what gets fixed first.

    📐 Quantifying Impact

    Impact is a combination of how many are affected, how often it happens, how badly it hurts and what it costs the business or client. A simple model is impact = users affected × frequency × severity of consequence.

    DimensionQuestionsExample
    ReachHow many users, tenants, regions?3 of 400 tenants, all enterprise
    FrequencyAlways, daily, intermittent?Every month-end
    SeverityBlocked, degraded, cosmetic?Blocked: cannot close books
    MoneyRevenue at risk, SLA credits, penaltiesContract ARR 1.2 M; 5% SLA credit
    ComplianceRegulatory or security exposureWrong tax totals: audit risk
    ReputationPublic, referenceable, executive attentionCustomer escalated to their CIO
    🧴
    Analogy: a hospital triage nurse. Not first-come-first-served; she ranks by how many are hurt, how seriously, and how fast it gets worse.

    🚦 Severity Levels and Response Targets

    SeverityDefinitionFirst responseUpdate cadence
    Sev 1Outage, data loss or security breach for many customers15 minEvery 30 min
    Sev 2Major function broken, no workaround1 hourEvery 4 hours
    Sev 3Function impaired, workaround exists1 business dayDaily
    Sev 4Cosmetic or question3 business daysOn change
    📌
    Severity is the technical and customer impact. Priority is the order of work, decided by product/engineering management using severity, effort, contracts and roadmap.

    💼 Making the Business Case

    escalationWhy now: 3 enterprise tenants (1.2 M ARR) cannot export month-end finance data.
Deadline: close deadline on 5 Oct; failure repeats every month.
Cost of delay: SLA credit 5% (about 6 k) plus churn risk, CIO escalation.
Workaround: date-range export, 12 manual steps per tenant, not sustainable.
Ask: assign an engineer today; target fix in staging by 4 Oct.

    A good case is five lines: why now, deadline, cost of delay, current workaround, specific ask. It lets a manager decide in a minute and shows you have already reduced the problem to its essentials.

    ⚔️ Handling Conflicting Priorities

    1. Put each issue on the same impact scale so comparison is fair.
    2. Check contracts and deadlines: an SLA clock can change the order.
    3. Offer engineering options: quick mitigation now, full fix later.
    4. Escalate to the owner of priority with the comparison, not a complaint.
    5. Record the decision and communicate it to affected clients.

    🏋️ Practice & Quick Check

    Practice
    P1.Two issues compete for the same engineer: (A) a cosmetic bug for 200 users, (B) a month-end failure for 3 enterprise tenants with a deadline in 2 days. How do you argue the order?
    B has higher severity (blocked), concentrated revenue and a hard deadline with SLA risk; A is cosmetic with a workaround. Present both on the impact scale, request B first with a defined fix target, and schedule A afterwards.
    Q1.Priority is mainly decided by…
    • A The reporter's urgency tone
    • B Product/engineering management using impact and effort
    • C Alphabetical order
    • D Support alone

    Module 08 · Handoff

    Handing Off to Core Engineering and Closing the Loop

    A clean handoff saves hours; a closed loop turns one fix into lasting improvement.

    📦 The Escalation Package

    checklist[ ] Ticket title: component + error + condition
[ ] Version, environment, tenant, region, timestamps (UTC)
[ ] Steps to reproduce or sample payload (sanitised)
[ ] Logs / request IDs / trace link / HAR
[ ] Expected vs actual
[ ] Impact: users, revenue, deadline, SLA
[ ] Workaround and its cost
[ ] What you already tried and ruled out
[ ] Suspected area (marked as hypothesis)
[ ] Customer contact and next update time

    'What you already ruled out' is the most overlooked line: it stops engineers repeating your work and shows that the problem was seriously investigated.

    👥 Who Does What (RACI)

    ActivityTier 3 SupportCore EngineeringProduct ManagerCustomer Success
    Gather evidenceR / ACIC
    Root cause and fixCR / AII
    Set priorityCCR / AC
    Customer updatesRCIA
    Verify fix with customerRCIA
    💡
    R = Responsible, A = Accountable, C = Consulted, I = Informed. One accountable owner per activity prevents the 'everyone thought someone else did it' failure.

    🤝 Working Agreements

    1. The ticket is the single source of truth: decisions in chat get copied back.
    2. Sev 1: live war room; Sev 2 to 4: asynchronous updates on the ticket.
    3. Agree update cadence per severity and keep it, even when there is no news.
    4. Use a clear escalation path (on-call, then engineering manager) instead of private messages.
    5. Ask for what you need: 'need hypothesis by 15:00' beats 'any update?'.
    slack@core-eng-oncall Sev 2: CSV export 500 for accounts above 50k rows since v4.2.1 (deployed 09:58 UTC).
Ticket: SUP-4521 with HAR, logs, repro script. 3 enterprise tenants blocked, month-end deadline 5 Oct.
Ask: owner assigned and first hypothesis by 15:00 UTC. Workaround: export by date range.

    🔄 Closing the Loop

    1. Verify the fix with the customer's real scenario, not just in staging.
    2. Confirm acceptance criteria are met and mark the ticket resolved with notes.
    3. Update the knowledge base so the next case is solved in minutes.
    4. Make sure a regression test exists for the failure.
    5. Feed patterns to Product (top recurring failures) and hold a short review for Sev 1 and 2.

    🏋️ Practice & Quick Check

    Practice
    P1.Engineering returns the ticket saying 'insufficient information'. How do you avoid this next time?
    Use the escalation package checklist: version, environment, repro steps, evidence, expected vs actual, impact and what you ruled out. Add a ticket template so every field is required before submission.

    • A Assigned
    • B Accountable
    • C Approved
    • D Alerted

    Module 09 · Communication

    Talking to Customers, Product & Executives

    Same incident, four audiences. Tailor the message so each person gets what they need.

    🗣️ Know Your Audience

    AudienceThey wantStyle
    Customer userIs it fixed? What do I do now?Plain language, workaround first
    Customer adminImpact, timeline, preventionClear timeline, ownership
    EngineerRepro, logs, version, hypothesisPrecise and technical
    Executive / PMBusiness impact, risk, ETA3 lines, numbers, decision needed
    🧴
    Analogy: a doctor explaining the same diagnosis differently to the patient, a nurse and a surgeon. The facts are the same; the wording and detail change.

    📨 Status Update Template

    templateSubject: [Update 2] CSV export failures — fix in testing

Impact: Exports over 50k rows fail for 3 accounts (since 2 Oct).
Cause: Timeout after a query change in v4.2.1.
Action: Fix built, validating in staging.
Workaround: Export in date ranges under 30 days.
Next update: Today 17:00 IST.

    Every update has five parts: impact, cause (as far as known), action, workaround and a time for the next update. Naming that time matters more than having news; silence is what upsets customers.

    🛡️ Handling Pushback

    1. Restate their concern so they feel heard.
    2. Separate facts (logs, timings) from opinions.
    3. Give options with trade-offs, not just 'no'.
    4. Escalate with data when priorities conflict.
    5. Document the decision in the ticket.

    Module 10 · Scenarios

    Bridge Scenarios from the Field

    Four realistic cases showing how to translate client failure states for engineering.

    🧾 Scenario: Duplicate invoices

    • Client says: "The billing system is charging my customers twice!"
    • Failure state: data integrity; 37 invoices duplicated between 02:00 and 03:30 UTC on 2 Oct; all from the nightly job.
    • Evidence: job log shows retry after timeout; both attempts committed. Idempotency key missing.
    • Requirement: billing job must be idempotent; the same invoice key is never created twice (R1 Must); alert on duplicates (R2 Should).
    • Impact: financial and trust; marked Sev 1 and refunds started immediately.

    🌍 Scenario: Intermittent timeouts for one region

    • Complaints only from the APAC region, 5 to 10 times a day.
    • Trace shows the slow span is a call to a US-only service, adding about 600 ms and sometimes timing out.
    • Requirement: regional routing or caching so p95 latency in APAC stays under 800 ms; timeout and retry policy documented.

    🎁 Scenario: A feature request disguised as a bug

    • Client reports "bug: cannot bulk-edit 5,000 records".
    • Check documented behaviour: bulk edit has always been limited to 500.
    • Reframe: not a defect but a product gap. Open a feature request with the business case, offer the supported workaround (batches of 500), and set expectations with the client.

    🙅 Scenario: Engineering says 'won't fix'

    • Core Engineering closes the ticket as low priority.
    • Do not argue; add data: 14 tenants affected in 30 days, 22 support hours, SLA risk for two accounts.
    • Propose options: quick guard now, root fix next sprint; escalate with the comparison to the product owner and record the decision.

    🏋️ Practice & Quick Check

    Practice
    P1.An engineer says a ticket is 'not a bug, it works as designed'. How do you handle it professionally?
    Check the specification and customer's expectation; if it matches the design, reframe as a feature request with the business case and offer a workaround. If the design contradicts documentation or contract, show the evidence and ask product to decide.
    Q1.A request that works as designed but the client wants different behaviour is best handled as…

    • B A feature request with a business case
    • C A closed ticket

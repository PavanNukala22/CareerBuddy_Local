    Module 01 · Hotfixes

    Patches, Hotfixes & Releases

    Know what each change type means and how it moves to production safely.

    🩹 Patch vs Hotfix vs Release

    TypePurposeRisk
    HotfixUrgent fix for a production issueHigh speed, needs strict validation
    PatchSmall planned fix to a releaseMedium
    ReleaseBundle of features and fixesLarger regression surface

    🔁 Hotfix Lifecycle

    1. Confirm root cause and the minimal change.
    2. Branch from the production tag, not main.
    3. Peer review and automated tests.
    4. Validate locally, then in staging.
    5. Approve (change/CAB or emergency approval).
    6. Deploy with canary and watch metrics; keep rollback ready.
    7. Merge the fix back to main.

    🏋️ Practice & Quick Check

    Practice
    P1.Why branch a hotfix from the production tag instead of main?
    Main may contain unreleased changes; branching from the production tag ships only the fix and avoids unintended code.
    Q1.A hotfix should be…
    • A Large and broad
    • B Minimal and targeted
    • C Untested
    • D Skipped

    Module 02 · Local

    Reproducing the Bug & Verifying the Fix Locally

    Never fix what you have not reproduced. Build a local setup that behaves like production, prove the bug exists, then prove the fix removes it.

    🔁 Reproduce Before You Fix

    Reproduction means making the failure happen on demand with the same version, configuration and input that the customer used. It is the foundation of validation: if you cannot reproduce the bug, you cannot honestly say your fix works. A fix that 'seems to work' on a case that never failed proves nothing.

    🧴
    Analogy: a doctor confirming the diagnosis before prescribing. Giving medicine for an illness you have not confirmed may help, harm, or do nothing, and you will never know which.
    1. Collect the exact app version, config, request payload and timing from the ticket.
    2. Run that version locally, not the latest.
    3. Feed in the same input and confirm the same error appears.
    4. Note the evidence (error text, stack trace) to compare after the fix.
    5. Only now change the code.

    🐳 A Local Setup That Matches Production

    yaml (docker-compose.yml)services:
  api:
    image: registry.example.com/orders-api:4.2.1   # exact prod tag, never :latest
    env_file: .env.staging                         # same config keys as production
    ports: ["8080:8080"]
    depends_on: [db]
  db:
    image: postgres:15.4                           # same major.minor as prod
    volumes: ["./sanitised_dump.sql:/docker-entrypoint-initdb.d/seed.sql"]

    Pin the exact image tag so you run the same bits as production; :latest changes silently. env_file loads configuration so differences are visible, and the database seed uses sanitised customer-like data so the data shape triggers the same paths.

    ⚠️
    Never point a local build at production databases or real payment gateways. Use sanitised copies and sandbox credentials.

    🧪 Failing Test → Fix → Passing Test

    bash# 1. Add a test that reproduces the bug
pytest tests/test_export.py::test_large_export -x      # RED: fails, as expected

# 2. Apply the fix, run again
pytest tests/test_export.py::test_large_export -x      # GREEN

# 3. Prove the test really guards the fix: remove the fix temporarily
git stash push src/export.py
pytest tests/test_export.py::test_large_export -x      # must be RED again
git stash pop

# 4. Run the whole suite for regressions
pytest -q

    Step 3 is the one people skip: a test that passes both with and without the fix is worthless. Running the full suite at the end checks you did not break something else.

    🏋️ Practice & Quick Check

    Practice
    P1.You cannot reproduce the customer's bug locally. List four things you would compare before giving up.
    Application version, configuration and feature flags, data shape or volume for that tenant, and environment differences (OS, locale/time zone, dependency versions, network or integration endpoints).
    Q1.Why pin an exact image tag instead of using :latest when reproducing a bug?
    • A It is faster
    • B Latest may differ from what production runs
    • C Latest is insecure
    • D Tags are required by Docker

    Module 04 · Staging

    Staging: The Dress Rehearsal Before Production

    What a good staging environment is, how close it must be to production, and how to detect and fix drift.

    🎭 What Staging Is For

    Staging (or pre-production) is an environment built to mirror production so that a change can be rehearsed under realistic conditions before real customers see it. Its value is exactly proportional to how similar it is to production.

    🧴
    Analogy: a full dress rehearsal before opening night. Same stage, same costumes, same lighting. If the rehearsal is on a different stage with no costumes, the opening night will still surprise you.
    EnvironmentPurposeTypical data
    Dev / localWrite and debug codeFake or small samples
    Test / QAAutomated and manual testingSynthetic data
    Staging / pre-prodFinal validation, mirrors productionSanitised production-like
    ProductionReal customersReal data

    📋 Parity Checklist

    DimensionMust matchCommon drift that hides bugs
    Software versionsApp, runtime, OS, DB, librariesStaging a minor version behind
    Configuration & flagsKeys and defaultsA flag on in staging, off in production
    Data shape & volumeRow counts, edge cases, encodingsStaging has 1k rows, production 50M
    InfrastructureCPU, memory, replicas, limitsSingle replica vs autoscaled cluster
    IntegrationsEndpoints, auth, rate limitsSandbox API more lenient than live
    Network & TLSProxies, gateways, certs, timeoutsNo WAF or gateway timeout in staging
    Locale & time zoneUTC offset, character setServer in UTC vs local
    💡
    The most common 'passed staging, failed production' causes are data volume and configuration differences.

    🔒 Test Data Without Leaking Customer Data

    sql-- Mask personal data while keeping shape and relationships
UPDATE users SET
  email      = CONCAT('user', id, '@example.test'),
  full_name  = CONCAT('User ', id),
  phone      = NULL,
  card_last4 = '0000';
TRUNCATE TABLE audit_tokens;   -- remove secrets entirely

    Masking keeps primary and foreign keys, row counts and distribution (so queries behave like production) but removes anything that identifies a person. Regulations such as GDPR and DPDP restrict copying raw personal data into lower environments.

    🕵️ Detecting Drift

    bash# Compare images actually running in each environment
kubectl --context staging get deploy -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.template.spec.containers[0].image}{"\n"}{end}' > stg.txt
kubectl --context prod    get deploy -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.template.spec.containers[0].image}{"\n"}{end}' > prd.txt
diff stg.txt prd.txt

# Compare config keys (never print secret values)
diff <(sort stg.env | cut -d= -f1) <(sort prd.env | cut -d= -f1)

    The first diff reveals version differences per service; the second compares only config keys, so you can spot a missing setting without exposing secrets.

    🏋️ Practice & Quick Check

    Practice
    P1.A fix passes staging but fails in production. Give four possible environment causes and one check for each.
    1) Data volume: compare row counts/query plans. 2) Config/flags: diff config keys and flag values. 3) Version drift: diff running image tags. 4) Integration/network: compare gateway timeouts, TLS and third-party endpoints (sandbox vs live).
    Q1.Which is the best way to get realistic test data into staging?
    • A Copy raw production data
    • B Use masked or sanitised production-like data
    • C Use empty tables
    • D Type data by hand

    Module 05 · Release

    Git Branching for Hotfixes

    Ship exactly the fix, track it with a version, and bring it back to main without losing anything.

    🌿 Hotfix Branch Workflow

    bashgit fetch --tags
git checkout -b hotfix/4.2.2 v4.2.1        # branch from the production tag
git cherry-pick 3fa91c2                    # take only the fix commit
git push origin hotfix/4.2.2               # open a pull request
# after approval and deploy
git tag -a v4.2.2 -m "Hotfix: export 500"
git checkout main && git merge --no-ff hotfix/4.2.2   # bring fix back

    Line by line: branch from v4.2.1 so only released code is included; cherry-pick copies a single commit rather than everything on main; the tag marks exactly what shipped; the final merge makes sure the next release still contains the fix.

    🧴
    Analogy: a hospital giving one urgent injection instead of rebuilding the entire treatment plan. You treat the emergency precisely, then update the patient's main chart so nobody repeats the mistake.

    🔢 Semantic Versioning

    Version partIncrement whenExample
    MAJORBreaking change4.0.0 → 5.0.0
    MINORNew feature, compatible4.2.0 → 4.3.0
    PATCHBug fix only4.2.1 → 4.2.2
    💡
    A hotfix normally bumps only the PATCH number. If it needs a MINOR or MAJOR bump, it is no longer a hotfix; take it through the normal release process.

    🏋️ Practice & Quick Check

    Practice
    P1.Why must the hotfix be merged back into main after deployment?
    If it is not, the next release built from main will not contain the fix and the bug returns (a regression).
    Q1.A bug-fix-only release changes which version number?
    • A MAJOR
    • B MINOR
    • C PATCH
    • D None

    Module 06 · Pipeline

    CI/CD Pipelines & Quality Gates for Hotfixes

    How automation enforces validation consistently, even under pressure, and why you build once and promote the same artifact.

    📦 Build Once, Promote the Same Artifact

    A fix should be built one time into an immutable artifact (container image or package with a version/hash). That same artifact is deployed to staging, tested, and then promoted to production. If you rebuild for production, you are shipping something different from what you tested.

    🧴
    Analogy: a sealed, numbered parcel. You inspect it at the sorting centre and deliver that very parcel. Re-packing it at the last mile voids the inspection.

    ⚙️ Example Pipeline

    yaml (GitHub Actions style)jobs:
  test:
    steps: [ {run: "pytest -q --cov=src --cov-fail-under=80"}, {run: "ruff check ."} ]
  build:
    needs: test
    steps: [ {run: "docker build -t $REG/orders-api:${{ github.sha }} ."}, {run: "docker push $REG/orders-api:${{ github.sha }}"} ]
  deploy-staging:
    needs: build
    steps: [ {run: "deploy staging $REG/orders-api:${{ github.sha }}"}, {run: "./smoke.sh https://staging.example.com"} ]
  deploy-prod:
    needs: deploy-staging
    environment: production      # requires manual approval
    steps: [ {run: "deploy prod $REG/orders-api:${{ github.sha }}"} ]

    Read it top to bottom: tests must pass before a build; the image is tagged with the commit hash (traceable); staging runs smoke tests; production requires an approval and deploys the same hash that passed staging.

    🚧 Quality Gates

    GateTypical toolFails the pipeline when
    Unit testspytest, JUnit, JestAny test fails
    Lint / static analysisruff, ESLint, SonarQubeRules violated
    Dependency & security scanTrivy, Snyk, DependabotCritical CVE found
    Coveragecoverage.py, JaCoCoBelow threshold
    Integration testsTestcontainers, PostmanContract or flow breaks
    Smoke testcurl scriptHealth or key endpoint fails
    ApprovalChange manager / CABNot approved
    ⚠️
    Do not skip gates to 'save time' during a hotfix. If a gate is too slow, make it faster or run the relevant subset; skipping removes the safety net exactly when risk is highest. Treat flaky tests as bugs: quarantine and fix them, do not just re-run until green.

    🏋️ Practice & Quick Check

    Practice
    P1.Why is it risky to rebuild the application for production after it passed staging?
    The rebuilt artifact may contain different dependencies or code than what was tested, so the staging validation no longer applies. Build once and promote the identical artifact.
    Q1.A CI/CD 'quality gate' is…
    • A An automated check that must pass to proceed
    • B A physical door
    • C A meeting
    • D A bug

    Module 07 · Safety

    Regression Testing, Migrations & Rollback

    How to prove a fix is safe and how to undo it quickly when it is not.

    🔺 Test Pyramid for a Hotfix

    LayerSpeedWhat it provesUse in hotfix
    UnitVery fastOne function is correctAdd test for the bug
    IntegrationMediumComponents work togetherRun for affected service
    End-to-endSlowReal user journey worksRun key flows only
    SmokeSecondsThe app is alive after deployAlways after release

    Run as many fast tests as possible and a few slow ones. Time is limited in an incident, so choose the tests nearest to the changed code first.

    🗄️ Database Changes: Expand and Contract

    sql-- Step 1 (deploy 1): ADD, never rename or drop in the same release
ALTER TABLE orders ADD COLUMN currency VARCHAR(3) DEFAULT 'USD';
-- Step 2: new code writes both columns, reads the new one
-- Step 3 (later release): drop the old column once nothing uses it

    Because the old and new application versions run side by side during a rollout, the database must work for both. Additive changes are safely reversible; destructive changes (DROP, RENAME) cannot be rolled back with a code rollback.

    ⚠️
    Always take a backup or snapshot before a schema change in a hotfix, and test the rollback script in staging.

    ↩️ Rollback Plan

    MethodSpeedCaveat
    Redeploy previous artifactMinutesData written by new code must still be readable
    Feature flag offSecondsCode must be flag-wrapped
    Blue/green switchSecondsDouble the infrastructure
    Database restoreSlowLoses data since backup; last resort

    🏋️ Practice & Quick Check

    Practice
    P1.Why is renaming a database column in a hotfix dangerous?
    Old and new app versions run together during rollout and after rollback; a rename breaks whichever version expects the old name, and it cannot be undone by a code rollback alone.
    Q1.Which test type should ALWAYS run right after a deployment?
    • A Smoke test
    • B Full regression only
    • C Load test
    • D None

    Module 08 · Release

    Deployment Strategies, Smoke Tests & Post-Deploy Monitoring

    Choose how to roll a fix out, prove it works with real traffic, and know exactly when to roll back.

    🚀 Deployment Strategies

    StrategyHow it worksRiskRollback speed
    RecreateStop old, start newDowntimeRedeploy
    RollingReplace instances graduallyMixed versions run togetherRoll back in steps
    Blue/greenTwo full environments, switch trafficDouble costSeconds (switch back)
    CanarySend 1–5% traffic to new version firstLow blast radiusSeconds (route to 0%)
    🧴
    Analogy: opening a new restaurant menu. A canary is serving the new dish to one table first; blue/green is keeping the old kitchen fully ready in case you must switch back instantly.

    🐤 Canary Analysis

    yamlcanary:
  steps: [ {weight: 5, pause: 10m}, {weight: 25, pause: 15m}, {weight: 100} ]
  abort_if:
    - error_rate_5xx > baseline + 1%
    - p99_latency > baseline * 1.3
    - payment_success_rate < 98%

    The canary version is compared with the stable baseline at the same time, so normal traffic changes do not cause false alarms. Include one business metric (payments, signups): a bug can leave technical metrics green while revenue drops.

    💨 Smoke Test Script

    bash#!/usr/bin/env bash
set -e
URL=$1
curl -fsS "$URL/health" | grep -q '"status":"ok"'
curl -fsS -o /dev/null -w "%{http_code}\n" "$URL/api/orders?limit=1" | grep -q 200
curl -fsS -X POST "$URL/api/export" -d '{"rows":80000}' -o /dev/null    # the bug that was fixed
echo "SMOKE PASSED"

    A smoke test is a few fast checks that the app is alive and the most important paths work. set -e stops on the first failure; curl -f turns HTTP errors into non-zero exit codes. Always include a check for the bug you just fixed.

    👀 The First 30 Minutes After Deploy

    1. Watch error rate, latency (p95/p99) and saturation on a dashboard.
    2. Check the business metric tied to the fix.
    3. Read fresh ERROR logs for new exception types.
    4. Confirm the customer's exact scenario now works.
    5. Keep the rollback command ready; define the trigger in advance (for example 5xx above 2% for 5 minutes).
    6. Only then announce resolution to the customer.

    🏋️ Practice & Quick Check

    Practice
    P1.Why compare the canary to a baseline running at the same time rather than to yesterday's metrics?
    Traffic varies by time of day and events, so yesterday's numbers are not comparable. A live baseline experiences the same conditions, so any difference is caused by the change.
    Q1.The fastest rollback method among these is…
    • A Blue/green switch or routing canary to 0%
    • B Rebuilding the image
    • C Restoring a database backup
    • D Writing a new fix

    Module 09 · Scenarios

    Hotfix Validation Scenarios

    Four realistic cases showing how validation catches problems or goes wrong.

    💳 Scenario: Rounding bug in payments

    • Bug: totals off by 1 paisa on orders with 3 or more discounted items.
    • Reproduce with the customer's cart in a local container (v4.2.1), failing test added.
    • Fix: round once at the end instead of per line. Staging smoke test places three test orders and compares with expected totals.
    • Canary 5% for 15 minutes with payment-success and refund-rate metrics; promoted to 100%.
    • Lesson: include a business-level assertion, not just HTTP 200.

    🚩 Scenario: Passes staging, fails in production

    • The feature flag new_export defaulted to on in staging and off in production, so production still ran the old buggy code.
    • Detected by comparing flag configuration, then confirming with a header showing which code path served the request.
    • Fix: enable the flag for the affected tenant first; add flag defaults to the environment parity checklist.

    🎲 Scenario: Flaky smoke test blocks the hotfix

    • The smoke test fails 1 in 5 runs because it depends on a third-party sandbox.
    • Do not simply re-run until green. Stub the third-party call in staging, keep one separate check for it, and record the flakiness as a ticket.
    • Pipeline stays strict, and the hotfix proceeds with reliable evidence.

    🧬 Scenario: Fix works on test data but not the customer's

    • Unit tests pass, but the customer still sees the error.
    • Their data contains emoji and a 4-byte character that the test data lacked; the database column used a 3-byte charset.
    • Reproduce with a sanitised sample that preserves those characters, then fix the charset and migration.
    • Lesson: validate with data shaped like the customer's, not only clean samples.

    🏋️ Practice & Quick Check

    Practice
    P1.A smoke test passes but revenue drops 8% after your hotfix. What did the validation miss and how do you improve it?
    The validation lacked a business-level check: technical health (200 OK) was fine but a key flow degraded. Add canary metrics for payment success/conversion, compare against baseline, and automate abort/rollback on those metrics.
    Q1.A flaky test in your hotfix pipeline should be…
    • A Re-run until it passes
    • B Fixed or quarantined with a ticket
    • C Deleted silently
    • D Ignored forever

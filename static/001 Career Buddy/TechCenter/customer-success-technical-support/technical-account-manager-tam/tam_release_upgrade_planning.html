    Module 01

    Foundations of Release & Upgrade Planning

    Why upgrades are risky, how the TAM helps clients review release notes, spot breaking changes and roll out features in phases with minimal downtime.

    🚀 Course Overview: What the Role Needs

    Software changes constantly. Each new version brings features, fixes and sometimes breaking changes that can stop a client's integrations. In release and upgrade planning, the TAM reviews release notes, previews breaking changes and plans phased feature rollouts to minimise downtime.

    📄
    Release notes
    Read them for what matters to this client.
    💥
    Breaking changes
    Find them before the client does.
    🪜
    Phased rollouts
    Release in small, safe steps.
    ⏱️
    Low downtime
    Plan windows, checks and rollback.
    🏠
    Analogy: upgrading is like renovating a house you still live in. You check the plans (release notes), find which walls are load-bearing (breaking changes), and do one room at a time (phased rollout).

    🎯 Learning Objectives

    By the end of this course you will be able to:

    1. Read release notes and filter them by client impact.
    2. Use semantic versioning to judge upgrade risk.
    3. Build an impact analysis for breaking changes and deprecations.
    4. Create an upgrade plan with environments, checklists and a timeline.
    5. Choose between big-bang, rolling, blue-green, canary and feature-flag rollouts.
    6. Plan downtime, go/no-go and rollback, and communicate the change clearly.

    Module 02

    Reading Release Notes & Versioning

    Turn long release notes into a short, client-specific impact summary, and use version numbers to judge risk.

    📄 Basic: Anatomy of Release Notes

    SectionWhat it containsTAM focus
    New featuresAdded capabilitiesOpportunities for the client
    ImprovementsBetter behaviour or performanceMostly positive
    Bug fixesProblems correctedDoes it fix a client issue?
    DeprecationsFeatures planned for removalStart migration planning
    Breaking changesChanges that may break usageRead first
    Known issuesProblems still presentCheck against client usage

    🔢 Basic: Semantic Versioning

    Many products use MAJOR.MINOR.PATCH (for example 3.4.2).

    PartMeaningRiskFrom 3.4.2 becomes
    MAJORBreaking changes allowedHIGH4.0.0
    MINORNew features, backward compatibleMEDIUM3.5.0
    PATCHBug fixes onlyLOW3.4.3
    📌
    Version numbers are only a hint. Always read the notes; a minor release can still change behaviour for a specific client.

    🎯 Intermediate: Filtering by Client Impact

    Do not forward a 30-page release note. Filter it through the client's usage profile.

    textCLIENT USES: REST API v2, SSO via SAML, scheduled exports, mobile SDK
Release 5.0 items:
  - API v1 removed                      → no impact (client uses v2)
  - SAML default signing changed       → HIGH impact, test SSO
  - Export file naming changed         → MEDIUM, scripts may break
  - New dashboard widgets              → opportunity

    📝 Intermediate: The Impact Summary

    Share a one-page summary instead of the full notes.

    ItemImpact on clientActionOwner
    SAML signing changeHighTest SSO in stagingClient identity team
    Export file renameMediumUpdate scriptsClient data team
    New widgetsOpportunityDemo in review callTAM

    Module 03

    Breaking Changes & Impact Analysis

    Find, classify and test breaking changes before the client upgrades, and plan around deprecation timelines.

    💥 Intermediate: Types of Breaking Change

    TypeExampleWhat breaks
    API removal / changeEndpoint v1 removed, field renamedIntegrations and scripts
    Behaviour changeDefault sorting or timeouts changedReports, user workflows
    Configuration changeSetting renamed or default flippedDeployment scripts
    Dependency / runtimeNeeds newer database or OSInfrastructure
    Security changeOlder TLS or auth methods disabledLegacy clients

    🧩 Intermediate: Mapping Changes to Integrations

    textIMPACT MATRIX (rows = client integrations, columns = changes)
                     API v1 removal | SAML signing | Export rename
CRM sync                 HIGH         |     -        |      -
SSO login                  -          |    HIGH      |      -
Finance export job         -          |     -        |    MEDIUM
Mobile app                LOW         |     -        |      -
    💡
    Ask the client for an integration inventory early. You cannot map impact against a list that does not exist.

    📅 Advanced: Deprecation Timelines

    Figure 3.1 · Typical deprecation timeline

    Track every end-of-life date that affects the client. Missing one can force an emergency upgrade.

    🧪 Advanced: Compatibility Testing

    1. Test in a non-production environment that mirrors production.
    2. Cover critical business flows first (login, payments, key reports).
    3. Run integration and regression tests, not only new features.
    4. Record results and sign-off before production approval.

    🏗️ Intermediate: Environment Promotion

    ✅ Intermediate: Pre-Upgrade Checklist

    textPRE-UPGRADE CHECKLIST
[ ] Release notes reviewed, impact summary approved
[ ] Backup taken and restore tested
[ ] Staging upgrade completed and signed off
[ ] Rollback plan and criteria written
[ ] Change approved, window agreed, on-call named
[ ] Stakeholders notified; support briefed

    🗓️ Advanced: Timeline & Change Calendar

    textEnd of support: 1 December. Production upgrade needs a 4-hour window.
Working back:  test 2 weeks + staging 1 week + approvals 1 week + buffer 2 weeks
Total lead time = 2 + 1 + 1 + 2 = 6 weeks
Start no later than mid-October; avoid the November peak sale and change-freeze weeks.

    Module 05

    Phased Rollout Strategies

    Compare big-bang, rolling, blue-green, canary and feature-flag rollouts and set go/no-go gates with metrics.

    🪜 Intermediate: Rollout Strategies Compared

    StrategyHow it worksStrengthWatch out
    Big-bangEveryone switches at onceSimpleHighest risk and downtime
    RollingUpdate servers in batchesNo full outageMixed versions during rollout
    Blue-greenSwitch traffic between two environmentsFast switch and rollbackDouble the infrastructure
    CanarySmall share of users firstEarly warningNeeds good monitoring
    Feature flagsTurn features on graduallySeparates deploy from releaseFlag clean-up needed

    🐤 Intermediate: Canary Rollout and Gates

    Figure 5.1 · Advance only when the gate passes
    textGATE RULE: error rate must stay below 1%, latency p95 within 20% of baseline
Canary 5%: 200,000 requests/hour x 5% = 10,000 requests
Errors seen = 150  → 150 / 10,000 = 1.5% → gate FAILED → pause and roll back

    🔄 Advanced: Rolling Update Math

    text12 servers, update 3 at a time, each batch takes 4 minutes
Batches = 12 / 3 = 4   →  total time = 4 x 4 = 16 minutes
Capacity during each batch = (12 - 3) / 12 = 75%
Check: can 75% capacity handle the current load? If not, use smaller batches or off-peak.

    🚩 Advanced: Feature Flags

    Feature flags let you deploy code without releasing the feature. You switch it on for a small group, observe, then widen.

    • Start with internal users, then a pilot group, then everyone.
    • Define the flag owner and a removal date.
    • Keep a fast off-switch ready.

    Module 06

    Minimising Downtime & Planning Rollback

    Downtime windows, availability math, safe database changes, go/no-go decisions and rollback plans.

    ⏱️ Intermediate: Availability and Downtime

    textMonth = 30 days = 30 x 24 x 60 = 43,200 minutes
99.9%  availability → allowed downtime = 43,200 x 0.001 = 43.2 min/month
99.99% availability → allowed downtime = 43,200 x 0.0001 = 4.32 min/month
A 2-hour upgrade outage would use up many months of a 99.9% budget.
    💡
    Planned downtime often counts against SLAs. Check the contract and agree how maintenance windows are treated.

    🗄️ Advanced: Safe Database Changes

    Database changes are the hardest to undo. Use the expand and contract pattern so old and new versions can both run.

    Figure 6.1 · Each step is backward compatible

    🚦 Intermediate: Go / No-Go Decision

    CheckGo if…
    TestsStaging tests passed and signed off
    BackupFresh backup with tested restore
    PeopleOn-call, client and our engineers available
    MonitoringDashboards and alerts ready
    RollbackPlan and decision criteria written

    ↩️ Advanced: Rollback Plan

    textROLLBACK CRITERIA (agree before the change)
Trigger: error rate > 2% for 10 min, or any data corruption, or login failures > 5%
Decision owner: client release manager (TAM advises)
Steps: stop traffic to new version → switch back → verify health checks
Time to roll back: 20 minutes (tested in staging)
    ⚠️
    A rollback plan that has never been tested is a hope, not a plan.

    Module 07

    Change Management & Communication

    Keep every stakeholder informed with the right message at the right time, and handle clients who delay upgrades.

    📢 Intermediate: Communication Timeline

    WhenMessageAudience
    T-30 daysRelease preview, impact summary, key datesClient leads, architects
    T-7 daysFinal plan, window, contacts, rollback criteriaAll stakeholders
    T-1 dayReminder and go/no-go readinessOperations, support
    Go-liveStart, progress and completion noticesAll
    T+1 to T+7Health check, issues, lessonsLeads and sponsors

    🏛️ Intermediate: Change Advisory Board

    Many enterprises use a Change Advisory Board (CAB) to approve risky changes. Prepare a short, clear request.

    textCHANGE REQUEST
What: upgrade platform 4.0 → 4.2 in production
Why: security fixes + end of support on 1 December
Risk: medium; SAML change tested in staging
Window: Sunday 02:00-06:00; rolling update, expected 0 minutes full outage
Rollback: tested, 20 minutes

    🐢 Advanced: Clients Who Delay Upgrades

    ReasonResponse
    "We fear breaking things"Show the impact summary and a tested staging result
    "No time for testing"Offer a test plan and workshop; phase the rollout
    "It works today"Explain end-of-support and security risks with dates
    "Too many customisations"Inventory them and migrate the highest-risk first
    📌
    Staying many versions behind makes each future upgrade bigger and riskier. Encourage small, regular upgrades.

    Scenarios & Troubleshooting

    Practise judgement on realistic upgrade situations.

    🔌 Case Study: The Removed API

    Version 5.0 removes API v1. Your client's CRM sync still uses v1 and the production upgrade is planned in six weeks.

    Figure 8.1 · Find it early, migrate, then upgrade

    Outcome: the client migrated to v2 in staging within three weeks and upgraded on schedule.

    🐤 Case Study: The Canary Error Spike

    At 10% rollout, checkout errors rise from 0.2% to 3% in the canary group.

    1. Pause the rollout immediately; do not advance to 50%.
    2. Check against rollback criteria and decide quickly.
    3. Collect logs and request IDs for engineering.
    4. Inform stakeholders with impact, action and next update time.

    ⏳ Troubleshooting: Stuck Near End of Support

    CauseAction
    No test capacityProvide test plan, scripts and a joint test day
    Unknown integrationsRun a discovery sprint to build the inventory
    No sponsorPresent risk and dates to an executive sponsor
    Too big a jumpPlan intermediate versions or request an extension if available

    🔐 Scenario: Change Freeze vs Urgent Security Patch

    A critical vulnerability patch is released during the client's year-end change freeze.

    🎯
    Use the emergency change process: explain exposure and risk, propose a minimal-scope patch with a tested rollback, get explicit approval and document the exception.

    IQ2.Why read release notes before an upgrade?
    To find breaking changes, deprecations and fixes that affect the client.
    IQ3.What does semantic versioning tell you?
    MAJOR may break, MINOR adds compatible features, PATCH fixes bugs, so it hints at risk.

    🌿 Intermediate Interview Questions

    IQ4.How do you prepare an upgrade plan?
    Check the upgrade path, build an impact summary, set environments, checklist, timeline with buffers and get approval.
    IQ5.What is the value of staging?
    It lets you test the upgrade in a production-like setting to find issues safely.
    IQ6.How do you filter release notes?
    Map each item to the client's usage profile and integrations and highlight only what matters.

    🌳 Advanced Interview Questions

    IQ7.Compare rolling, blue-green and canary.
    Rolling updates in batches; blue-green switches between two environments for quick rollback; canary exposes a small share first to detect issues.
    IQ8.How do you decide go or no-go?
    Check tests, backup with tested restore, people, monitoring and rollback readiness against agreed criteria.
    IQ9.How do you handle a client who keeps delaying upgrades?
    Show risks with dates, reduce effort with test support, phase the work and engage a sponsor.

    🏔️ Expert Interview Questions

    IQ10.Describe an upgrade you turned around.
    Tell a story: the risk, how you found the impact, how you phased the rollout, outcome and learnings.
    IQ11.How would you design a safe database migration?
    Use expand and contract steps, keep versions compatible, back up and rehearse rollback.
    IQ12.How would you manage releases across 20 accounts?
    Track versions and end-of-life dates, standardise impact templates and cadence, prioritise by risk and review regularly.

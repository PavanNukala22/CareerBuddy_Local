    Module 01 · Foundations

    Relational Databases for Support Engineers

    Why TSEs query databases, how relational data is organised into tables with keys and relationships, the data types you'll meet, and how support access is usually set up safely.

    🗄️ Why TSEs Use SQL

    The application's screens show what the code decides to show. The database shows what was actually stored. When a customer says "my order disappeared" or "I was charged twice", a quick query proves what happened.

    🔎
    Locate records
    Find a customer, order, payment or event by email, ID or date.
    ✅
    Verify integrity
    Check for duplicates, missing links or mismatched totals.
    🕰️
    Build timelines
    When was it created, updated, deleted?
    📊
    Measure scope
    How many customers are affected by this bug?

    Module 02 · SELECT

    SELECT: Reading Data

    The statement you'll use 95% of the time. Choose columns, choose tables, sort, limit, rename columns with aliases and remove duplicates.

    📖 SELECT & FROM

    sql-- specific columns (preferred)
SELECT id, email, plan
FROM customers;

-- all columns (fine for a quick look at ONE row)
SELECT *
FROM customers
LIMIT 1;
    💡
    SQL keywords aren't case-sensitive (select = SELECT), but writing them in capitals makes queries easier to read.

    🎯 WHERE (Intro)

    sqlSELECT id, email, plan, created_at
FROM customers
WHERE email = 'priya@acme.com';

SELECT id, amount, status
FROM orders
WHERE customer_id = 1;
    📌
    Text values go in single quotes ('priya@acme.com'). Numbers don't need quotes.

    ↕️ ORDER BY & LIMIT

    sql-- newest 10 orders for customer 1
SELECT id, amount, status, created_at
FROM orders
WHERE customer_id = 1
ORDER BY created_at DESC
LIMIT 10;

-- sort by two columns
SELECT id, status, amount FROM orders
ORDER BY status ASC, amount DESC;
    DatabaseLimit rows
    PostgreSQL / MySQL / SQLiteLIMIT 10
    SQL ServerSELECT TOP 10 …
    Oracle (12c+) / standard SQLFETCH FIRST 10 ROWS ONLY

    🏷️ Aliases, DISTINCT & Expressions

    sql-- column and table aliases
SELECT c.email AS customer_email, c.plan
FROM customers AS c;

-- unique values
SELECT DISTINCT status FROM orders;

-- expressions and functions
SELECT id,
       amount / 100.0          AS amount_rupees,
       LOWER(status)           AS status_lower,
       COALESCE(deleted_at::text, 'active') AS state
FROM orders;
    📌
    COALESCE(a, b) returns the first non-NULL value, handy for showing "active" instead of NULL. (::text is PostgreSQL casting syntax.)

    ⚙️ Order of Execution

    SQL is written in one order but executed in another, which explains many errors:

    Written orderExecuted order
    1. SELECT1. FROM / JOIN
    2. FROM / JOIN2. WHERE
    3. WHERE3. GROUP BY
    4. GROUP BY4. HAVING
    5. HAVING5. SELECT
    6. ORDER BY6. ORDER BY
    7. LIMIT7. LIMIT
    💡
    Because WHERE runs before SELECT, you usually can't use a SELECT alias in WHERE, but you can in ORDER BY.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    SELECT * on big tables without LIMITSlow; floods your screenPick columns; add LIMIT
    Double quotes for text valuesIn PostgreSQL, "x" means a column nameUse single quotes
    Forgetting ORDER BY with LIMIT"Latest 10" is randomORDER BY created_at DESC
    Using SELECT aliases in WHEREError: column doesn't existRepeat the expression or use a subquery

    Module 03 · Filters

    Filtering with WHERE

    Precise filters find the exact records you need: comparisons, AND/OR, IN, BETWEEN, LIKE patterns, NULL checks, and date filters that respect timezones.

    ⚖️ Comparison Operators

    OperatorMeaningExample
    =Equalstatus = 'paid'
    <> or !=Not equalstatus <> 'paid'
    > < >= <=Greater / lessamount >= 10000

    🔀 AND, OR, NOT & Parentheses

    sql-- failed OR refunded orders for customer 1
SELECT id, status, amount
FROM orders
WHERE customer_id = 1
  AND (status = 'failed' OR status = 'refunded');
    ⚠️
    AND binds tighter than OR. Without parentheses, customer_id = 1 AND status = 'failed' OR status = 'refunded' returns refunded orders for every customer.

    🧩 IN, BETWEEN & LIKE

    sqlSELECT * FROM orders WHERE status IN ('failed', 'refunded');
SELECT * FROM orders WHERE id IN (5512, 5513, 5520);
SELECT * FROM orders WHERE amount BETWEEN 1000 AND 5000;   -- inclusive
SELECT * FROM customers WHERE email LIKE '%@acme.com';     -- ends with
SELECT * FROM customers WHERE name LIKE 'Pri%';            -- starts with
SELECT * FROM customers WHERE email ILIKE '%ACME%';        -- PostgreSQL: case-insensitive
    WildcardMatches
    %Any number of characters (including none)
    _Exactly one character

    🕳️ NULL Handling

    sql-- active (not soft-deleted) customers
SELECT id, email FROM customers WHERE deleted_at IS NULL;

-- customers with a phone number
SELECT id FROM customers WHERE phone IS NOT NULL AND phone <> '';

-- surprising: this returns NOTHING, even for NULL rows
SELECT id FROM customers WHERE deleted_at = NULL;
    📌
    NOT IN with a list containing NULL returns no rows. Prefer NOT EXISTS or filter out NULLs first.

    🕰️ Dates & Timezones

    sql (PostgreSQL)-- orders in the last 7 days
SELECT id, created_at FROM orders
WHERE created_at >= NOW() - INTERVAL '7 days';

-- a whole IST day (5 Oct 2026) when timestamps are stored in UTC
-- 00:00 IST = 18:30 UTC previous day
SELECT id, created_at FROM orders
WHERE created_at >= '2026-10-04 18:30:00'
  AND created_at <  '2026-10-05 18:30:00';

-- show times in IST
SELECT id, created_at AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Kolkata' AS created_ist
FROM orders;
    💡
    Use >= start and < next-day start for date ranges. BETWEEN '2026-10-05' AND '2026-10-05' on timestamps only matches midnight.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Missing parentheses with ORWrong rows from other customersWrap OR conditions
    = NULLMatches nothingIS NULL
    BETWEEN on timestamps for a dayMisses most of the day>= start AND < next day
    Case-sensitive email matches"Priya@Acme.com" not foundLOWER(email) = LOWER('…') or ILIKE

    Module 04 · Combining Tables

    JOINs: Combining Tables

    Real questions span several tables: which customer owns this payment? Which orders have no payment? Learn INNER, LEFT, RIGHT and FULL joins, multi-table joins and the duplicate-row trap.

    🔗 JOIN Types

    Figure 4.1 · Join types
    INNER JOINLEFT JOIN
    ReturnsOnly rows with a match in both tablesAll rows from the left table, plus matches (NULLs where none)
    Use whenYou need related pairs (orders with their customer)You must keep everything on the left, e.g., find missing data
    Rows lost?Unmatched rows droppedLeft rows never dropped

    🤝 INNER JOIN

    sql-- each order with its customer's email
SELECT o.id AS order_id, c.email, o.amount, o.status
FROM orders o
JOIN customers c ON c.id = o.customer_id      -- JOIN = INNER JOIN
WHERE c.email = 'priya@acme.com'
ORDER BY o.created_at DESC;

    🕳️ LEFT JOIN & Finding Missing Data

    sql-- customers who have never ordered
SELECT c.id, c.email
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- paid orders with NO payment record (integrity problem!)
SELECT o.id, o.amount
FROM orders o
LEFT JOIN payments p ON p.order_id = o.id
WHERE o.status = 'paid'
  AND p.id IS NULL;
    ✅
    LEFT JOIN … WHERE right.id IS NULL is the classic pattern for "find things that are missing a related record", one of the most useful support queries.

    🧱 Multi-table & Self Joins

    sql-- payment → order → customer in one query
SELECT p.id AS payment_id, p.amount, p.status AS payment_status,
       o.id AS order_id, c.email
FROM payments p
JOIN orders o    ON o.id = p.order_id
JOIN customers c ON c.id = o.customer_id
WHERE p.id = 9001;

-- self join: users and the teammate who invited them
SELECT u.email, inviter.email AS invited_by
FROM users u
LEFT JOIN users inviter ON inviter.id = u.invited_by_id;

    ⚠️ The Duplicate-Row Trap

    Joining a one-to-many relationship multiplies rows. If an order has 3 payment attempts, it appears 3 times, and SUM(o.amount) triples.

    sql-- WRONG: order amounts counted once per payment row
SELECT SUM(o.amount) FROM orders o JOIN payments p ON p.order_id = o.id;

-- RIGHT: aggregate payments first, then join
SELECT o.id, o.amount, COALESCE(pay.total_paid, 0) AS total_paid
FROM orders o
LEFT JOIN (
  SELECT order_id, SUM(amount) AS total_paid
  FROM payments WHERE status = 'succeeded'
  GROUP BY order_id
) pay ON pay.order_id = o.id;

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Missing ON conditionCartesian product (every row × every row)Always join on keys
    INNER JOIN when you need missing rowsMissing records silently disappearLEFT JOIN + IS NULL
    Filtering the right table in WHERE after LEFT JOINTurns it into an INNER JOINPut right-table filters in the ON clause
    Summing after a one-to-many joinInflated totalsAggregate first, then join

    Module 05 · Summaries

    Aggregation: COUNT, SUM, GROUP BY & HAVING

    Turn thousands of rows into answers: how many, how much, per what. Essential for measuring the scope of an issue and reconciling totals.

    🧮 Aggregate Functions

    FunctionReturnsExample
    COUNT(*)Number of rowsSELECT COUNT(*) FROM orders;
    SUM(col)TotalSUM(amount)
    AVG(col)AverageAVG(amount)
    MIN / MAXSmallest / largestMAX(created_at)

    📊 GROUP BY

    sql-- orders per status
SELECT status, COUNT(*) AS orders, SUM(amount) AS total
FROM orders
GROUP BY status
ORDER BY orders DESC;

-- failed payments per day (last 7 days)
SELECT DATE(created_at) AS day, COUNT(*) AS failures
FROM payments
WHERE status = 'failed' AND created_at >= NOW() - INTERVAL '7 days'
GROUP BY DATE(created_at)
ORDER BY day;
    📌
    Every column in SELECT must be either in GROUP BY or inside an aggregate function.

    🎚️ HAVING vs WHERE

    WHEREHAVING
    FiltersIndividual rowsGroups (after aggregation)
    RunsBefore GROUP BYAfter GROUP BY
    Can use aggregates?NoYes
    ExampleWHERE status = 'failed'HAVING COUNT(*) > 3
    sql-- customers with more than 3 failed payments today
SELECT o.customer_id, COUNT(*) AS failures
FROM payments p JOIN orders o ON o.id = p.order_id
WHERE p.status = 'failed' AND p.created_at >= CURRENT_DATE
GROUP BY o.customer_id
HAVING COUNT(*) > 3;

    🔢 COUNT Variations

    ExpressionCounts
    COUNT(*)All rows
    COUNT(phone)Rows where phone is NOT NULL
    COUNT(DISTINCT customer_id)Unique customers
    sql-- how many distinct customers were affected by failed payments today?
SELECT COUNT(DISTINCT o.customer_id) AS affected_customers
FROM payments p JOIN orders o ON o.id = p.order_id
WHERE p.status = 'failed' AND p.created_at >= CURRENT_DATE;
    ✅
    "How many customers are affected?" is a question engineering and managers ask in every incident. COUNT(DISTINCT …) answers it.

    🔀 CASE for Conditional Counts

    sqlSELECT DATE(created_at) AS day,
       COUNT(*)                                          AS attempts,
       SUM(CASE WHEN status = 'failed' THEN 1 ELSE 0 END)  AS failed,
       ROUND(100.0 * SUM(CASE WHEN status = 'failed' THEN 1 ELSE 0 END) / COUNT(*), 1) AS failure_pct
FROM payments
WHERE created_at >= NOW() - INTERVAL '7 days'
GROUP BY DATE(created_at)
ORDER BY day;

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Selecting non-grouped columnsError (or random values in MySQL)Add to GROUP BY or aggregate
    Using WHERE with aggregatesErrorUse HAVING
    COUNT(col) when you meant all rowsNULLs excludedCOUNT(*)
    Integer division (5/2 = 2)Wrong percentagesMultiply by 100.0

    Module 06 · Support Queries

    Locating Records: Everyday Support Queries

    Ready-to-adapt queries for the lookups TSEs do daily, plus subqueries, CTEs and CASE to answer more complex questions cleanly.

    🔎 Find a Customer Safely

    sql-- tolerant email lookup (case + spaces)
SELECT id, email, plan, created_at, deleted_at
FROM customers
WHERE LOWER(TRIM(email)) = LOWER(TRIM(' Priya@Acme.com '));

-- partial match when unsure
SELECT id, email FROM customers WHERE email ILIKE '%priya%' LIMIT 20;

-- by external reference (order number from an email)
SELECT o.*, c.email FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.id = 5512;
    ⚠️
    Verify you're looking at the right account (email, company, plan) before sharing anything with the requester.

    🕰️ Activity Timelines

    sql-- everything that happened to order 5512, in time order
SELECT 'order'   AS kind, id, status, amount, created_at FROM orders   WHERE id = 5512
UNION ALL
SELECT 'payment' AS kind, id, status, amount, created_at FROM payments WHERE order_id = 5512
ORDER BY created_at;
    UNIONUNION ALL
    DuplicatesRemovedKept
    SpeedSlower (sorts to dedupe)Faster
    Use for timelinesRarelyUsually

    🪆 Subqueries

    sql-- customers whose latest order failed
SELECT c.id, c.email
FROM customers c
WHERE (SELECT o.status FROM orders o
       WHERE o.customer_id = c.id
       ORDER BY o.created_at DESC LIMIT 1) = 'failed';

-- orders above the average order amount
SELECT id, amount FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);

-- EXISTS: customers with at least one refund
SELECT c.id, c.email FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.status = 'refunded');

    🧱 CTEs (WITH)

    A Common Table Expression names a temporary result so complex queries read top-to-bottom.

    sqlWITH paid AS (
  SELECT order_id, SUM(amount) AS paid_total
  FROM payments
  WHERE status = 'succeeded'
  GROUP BY order_id
)
SELECT o.id, o.amount, COALESCE(paid.paid_total, 0) AS paid_total,
       o.amount - COALESCE(paid.paid_total, 0)     AS balance
FROM orders o
LEFT JOIN paid ON paid.order_id = o.id
WHERE o.customer_id = 1;

    📜 Audit & History Tables

    • Many systems keep audit/event tables (e.g., audit_log, order_events) recording who changed what and when.
    • Use them to answer "who deleted this?", "when did the plan change?", "was this changed by the customer or an admin?"
    • updated_at only shows the latest change; history tables show all of them.
    sqlSELECT created_at, actor_email, action, old_value, new_value
FROM audit_log
WHERE entity = 'customer' AND entity_id = 1
ORDER BY created_at DESC
LIMIT 50;

    Module 07 · Integrity

    Verifying Data Integrity

    Data integrity means the data is complete, consistent and correct. Learn the standard checks TSEs run: duplicates, orphans, mismatched totals, invalid states, NULLs in required fields and impossible dates.

    🛡️ What Integrity Means

    TypeMeaningExample problem
    Entity integrityEvery row is unique and identifiableTwo customer rows for the same email
    Referential integrityForeign keys point to existing rowsOrder pointing to a deleted customer
    Domain integrityValues are valid for the columnNegative amounts; status "pAiD"
    Business-rule integrityData matches business logicOrder "paid" without a successful payment

    👯 Duplicates

    sql-- duplicate customer emails (ignoring case)
SELECT LOWER(email) AS email, COUNT(*) AS n
FROM customers
GROUP BY LOWER(email)
HAVING COUNT(*) > 1;

-- possible double charges: same order, same amount, within 2 minutes
SELECT p1.order_id, p1.id AS first_id, p2.id AS second_id, p1.amount, p1.created_at, p2.created_at
FROM payments p1
JOIN payments p2
  ON p2.order_id = p1.order_id
 AND p2.amount = p1.amount
 AND p2.id > p1.id
 AND p2.created_at <= p1.created_at + INTERVAL '2 minutes'
WHERE p1.status = 'succeeded' AND p2.status = 'succeeded';

    🧩 Orphans & Missing Links

    sql-- orders whose customer doesn't exist (orphans)
SELECT o.id, o.customer_id
FROM orders o
LEFT JOIN customers c ON c.id = o.customer_id
WHERE c.id IS NULL;

-- active subscriptions for soft-deleted customers
SELECT s.id, s.customer_id
FROM subscriptions s
JOIN customers c ON c.id = s.customer_id
WHERE s.status = 'active' AND c.deleted_at IS NOT NULL;
    📌
    Databases with proper foreign-key constraints prevent most orphans, but data imported from other systems, or soft deletes, can still create them.

    ⚖️ Mismatched Totals & States

    sql-- orders marked paid without a successful payment
SELECT o.id, o.amount
FROM orders o
WHERE o.status = 'paid'
  AND NOT EXISTS (SELECT 1 FROM payments p
                  WHERE p.order_id = o.id AND p.status = 'succeeded');

-- payments that don't add up to the order amount
SELECT o.id, o.amount, SUM(p.amount) AS paid
FROM orders o
JOIN payments p ON p.order_id = o.id AND p.status = 'succeeded'
GROUP BY o.id, o.amount
HAVING SUM(p.amount) <> o.amount;
    💡
    Reconciliation checks like these are how support proves "the dashboard total is wrong" versus "the customer's spreadsheet is wrong".

    🧪 Bad Values & Dates

    sql-- negative or zero amounts
SELECT id, amount FROM orders WHERE amount <= 0;

-- unexpected status values
SELECT status, COUNT(*) FROM orders GROUP BY status;

-- required fields missing
SELECT id FROM customers WHERE email IS NULL OR TRIM(email) = '';

-- impossible dates: updated before created, or in the future
SELECT id FROM orders WHERE updated_at < created_at OR created_at > NOW();

    Module 08 · Safe Querying

    Querying Safely & Efficiently

    Support engineers query live systems that hold real customer data. Learn the safety rules, how to avoid slow queries, how indexes and EXPLAIN help, and how to handle personal data responsibly.

    🔐 Read-Only Rules

    👀
    Read-only access
    Use a read-only user or read replica; never a superuser.
    🔢
    Always LIMIT
    Especially while exploring.
    🎯
    Filter first
    Use IDs, emails and date ranges.
    🧾
    Record what you ran
    Paste the query (not the data) in the internal note.

    ⚡ Writing Fast Queries

    • Filter on indexed columns (id, foreign keys, email, created_at).
    • Avoid wrapping indexed columns in functions where possible (WHERE DATE(created_at) = … can skip the index; prefer a range).
    • Avoid leading wildcards on huge tables (LIKE '%abc' can't use a normal index).
    • Select only needed columns; avoid SELECT * on wide tables.
    • Run heavy reports off-peak or on the replica.

    📇 Indexes & EXPLAIN

    An index is like a book's index: the database jumps to matching rows instead of reading every row (a full table scan).

    sqlEXPLAIN
SELECT id, amount FROM orders
WHERE customer_id = 1 AND created_at >= NOW() - INTERVAL '30 days';

-- Look for:
--   Index Scan using orders_customer_id_idx  → good
--   Seq Scan on orders (rows=48,000,000)     → slow full scan
    📌
    TSEs don't usually create indexes, but noticing "this support query does a full scan on a 48M-row table" is worth flagging to engineering.

    🧑‍⚖️ Personal Data (PII)

    • PII (personally identifiable information): names, emails, phone numbers, addresses, IDs.
    • Query only what you need for the ticket; avoid exporting customer lists to personal files.
    • Never paste query results with other customers' data into tickets, chats or screenshots.
    • Follow data-protection laws and company policy (e.g., GDPR, India's DPDP Act).
    ⚠️
    Accessing a customer's data without a legitimate support reason is a policy violation in most companies, and access is usually logged.

    ⛔ Statements You Shouldn't Run

    ALTERChanges table structureNever

    MistakeWhy it hurtsDo this instead

    sql-- how many customers have orders stuck in 'processing' > 24h since the release?
SELECT COUNT(DISTINCT customer_id) AS customers, COUNT(*) AS orders
FROM orders
WHERE status = 'processing'
  AND created_at < NOW() - INTERVAL '24 hours'
  AND created_at >= '2026-10-03 06:00';
--  customers = 214, orders = 389
    ✅
    Add to the bug report: 214 customers / 389 orders affected since the release, with the query, so engineering can prioritise and later verify the fix.

    Module 10 · Interviews

    Interview Preparation: SQL for Support

    SQL questions commonly asked in TSE interviews, with model answers, a comparison cheat sheet, common mistakes and query-writing scenarios.

    🎤 Concept Questions

    QuestionModel answer
    What is a primary key vs foreign key?Primary key uniquely identifies a row; foreign key references another table's primary key to link rows.
    Explain INNER vs LEFT JOIN.INNER returns matches only; LEFT returns all left rows plus matches, with NULLs where none.
    WHERE vs HAVING?WHERE filters rows before grouping; HAVING filters groups after aggregation.
    How do you find duplicates?GROUP BY the column(s) and HAVING COUNT(*) > 1 (normalise case/spaces if needed).
    How do you find records missing a related row?LEFT JOIN … WHERE right.id IS NULL, or NOT EXISTS.
    Why is = NULL wrong?NULL is unknown; comparisons return unknown. Use IS NULL / IS NOT NULL.
    How do you keep queries safe in production?Read-only access/replica, filters + LIMIT, no write statements, minimal PII.

    📋 Comparison Cheat Sheet

    PairKey difference
    INNER vs LEFT JOINMatches only vs all left rows
    WHERE vs HAVINGRow filter vs group filter
    COUNT(*) vs COUNT(col) vs COUNT(DISTINCT col)All rows vs non-NULL vs unique values
    UNION vs UNION ALLRemoves duplicates vs keeps all
    DELETE vs TRUNCATE vs DROPSome rows vs all rows vs whole table
    Primary vs Foreign keyUnique row ID vs link to another table
    SQL vs NoSQLTables + joins vs documents/key-value etc.
    Subquery vs CTENested query vs named, readable WITH block

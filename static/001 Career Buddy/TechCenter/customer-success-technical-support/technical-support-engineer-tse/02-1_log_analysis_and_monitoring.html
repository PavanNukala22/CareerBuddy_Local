    Module 01 · Foundations

    What Logs Are and Why TSEs Depend on Them

    Logs are the evidence trail of everything a system does. Learn what logs contain, log levels, structured vs unstructured logs, centralised logging, and where logs fit in observability.

    📜 What Is a Log?

    A log is a timestamped record of an event that happened in a system: a request received, a payment processed, a job failed. Applications write logs continuously, producing millions of lines per day.

    🕓
    When
    Timestamp of the event (ideally in UTC with milliseconds).
    🏷️
    Where
    Service, host, environment (prod/staging), region.
    👤
    Who
    Account ID, user ID, request ID.
    ❗
    What
    Event name, level, message, error details, status code.
    💡
    For a Technical Support Engineer, logs answer the key question: "What actually happened?" They turn a customer's "it didn't work" into evidence.

    🎚️ Log Levels

    LevelMeaningExampleTSE focus
    TRACE / DEBUGVery detailed developer info"Parsed 12 fields from payload"Rarely enabled in production
    INFONormal operations"Order 42 created"Confirms something happened
    WARNUnexpected but handled"Retrying webhook (attempt 2)"Early signs of trouble
    ERRORAn operation failed"Webhook delivery failed: timeout"Start here when investigating
    FATAL / CRITICALService can't continue"DB connection pool exhausted"Usually an incident
    📌
    Start investigations by filtering ERROR and WARN, then widen to INFO around the same time to see what led up to the failure.

    🧾 Structured vs Unstructured Logs

    📝 Unstructured (plain text)

    log2026-10-05 09:41:17 ERROR webhooks Delivery to
https://hooks.acme.com failed after 30001ms (attempt 3)

    Easy for humans; harder to filter. Needs parsing (regex) to extract fields.

    🧩 Structured (JSON)

    json{"ts":"2026-10-05T09:41:17Z","level":"ERROR",
 "service":"webhooks","account_id":"acct_acme",
 "status_code":504,"duration_ms":30001,"attempt":3}

    Each value is a named field, so you can filter status_code:504 or group by account_id instantly.

    ✅
    Most modern platforms automatically parse JSON logs into fields (called attributes or facets in Datadog, fields in Splunk/Sumo/CloudWatch).

    🏢 Centralised Logging

    Figure 1.1 · How logs reach a central platform
    • Applications run on many servers or containers; logging into each machine is impossible at scale.
    • Agents/shippers (Datadog Agent, Splunk Universal Forwarder, Fluent Bit, CloudWatch agent) collect logs and send them to a central platform.
    • The platform indexes logs so you can search across everything in seconds.
    • Retention is limited (e.g., 15–30 days hot, longer in archives), so old logs may not be searchable.
    ⚠️
    If a customer reports something from 3 months ago, logs may be gone. Ask for recent examples, or check if archives can be rehydrated.

    🔭 Logs, Metrics & Traces

    SignalWhat it isAnswersExample
    LogsIndividual event records"What exactly happened in this request?"ERROR line with stack trace
    MetricsNumbers over time"Is the error rate rising?"5xx errors per minute; p95 latency
    TracesOne request's path across services"Which service made it slow?"API → auth → DB, 2.3 s in DB
    📌
    Together these three are called observability. TSEs use metrics to spot a problem, logs to understand it, and traces to locate it.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Searching only the word "error"Misses failures logged as WARN or with status codesFilter by level and status code fields
    Ignoring timezonesSearching the wrong time windowConvert customer time to UTC first
    Reading one line in isolationThe cause is often a few lines earlierRead the lines before and after
    Assuming no log = no eventLogs may be sampled, filtered or past retentionCheck retention and logging coverage

    Module 02 · Interpretation

    Reading and Interpreting Logs

    How to read a log line, convert timezones, follow a request ID across services, read stack traces, and turn log evidence into a conclusion.

    🔍 Anatomy of a Log Line

    log2026-10-05T09:41:17.342Z ERROR [webhooks] req=req_7f2c91 acct=acct_acme
  POST https://hooks.acme.com/orders -> 504 in 30001ms (attempt 3/5)
    PartValueMeaning
    Timestamp2026-10-05T09:41:17.342Z09:41 UTC ("Z" = UTC) → 15:11 IST
    LevelERRORThe operation failed
    ServicewebhooksWhich component logged it
    Request IDreq_7f2c91Use to find every line for this request
    Accountacct_acmeWhich customer
    Detail504 in 30001ms, attempt 3/5The customer's endpoint timed out after 30 s; we're retrying
    ✅
    Conclusion from one line: our system worked; the customer's endpoint is too slow. Advice: return 200 quickly and process asynchronously.

    🌍 Timestamps & Timezones

    FormatExampleNotes
    ISO 8601 UTC2026-10-05T09:41:17Z"Z" means UTC
    With offset2026-10-05T15:11:17+05:30Same moment, in IST
    Epoch seconds1791193277Seconds since 1 Jan 1970 UTC; convert with a tool
    Epoch milliseconds179119327734213 digits = milliseconds
    timezone conversionCustomer (IST, UTC+5:30): "failed around 3:10 pm"
15:10 IST − 5:30 = 09:40 UTC
Search window: 09:25–09:55 UTC  (±15 minutes)
    ⚠️
    Customers in the US, UK or Europe may be on daylight saving time, which shifts offsets by an hour part of the year. Confirm their timezone.

    🔗 Request IDs & Correlation

    In modern systems one customer action touches several services. A request ID (also called correlation ID or trace ID) is attached to every log line for that request, so you can follow its whole journey.

    logs for req_7f2c91 (sorted by time)09:41:16.901Z INFO  [api]      req=req_7f2c91 POST /v1/orders acct=acct_acme
09:41:16.950Z INFO  [orders]   req=req_7f2c91 order=ord_5512 created
09:41:16.988Z INFO  [webhooks] req=req_7f2c91 queued delivery to hooks.acme.com
09:41:47.342Z ERROR [webhooks] req=req_7f2c91 -> 504 in 30001ms (attempt 3/5)
    💡
    Ask customers for the request ID from API response headers (e.g., X-Request-Id) or error pages. It's the fastest way into the logs.

    🧵 Reading Stack Traces

    A stack trace shows the chain of function calls when an error occurred. In Python, read from the bottom up: the last line is the error, the lines above show where it happened.

    python tracebackTraceback (most recent call last):
  File "/app/api/orders.py", line 88, in create_order
    total = calculate_total(items)
  File "/app/billing/totals.py", line 21, in calculate_total
    return sum(i["price"] * i["qty"] for i in items)
KeyError: 'price'
    ReadWhat it tells you
    Last lineKeyError: 'price': an item had no price field
    Frame just abovebilling/totals.py line 21, inside calculate_total
    Top framesCalled from the create_order API endpoint
    📌
    In Java the error is at the top ("Exception in thread…"), followed by "at …" lines and "Caused by:" sections; the deepest "Caused by" is often the root cause.

    🧠 From Evidence to Conclusion

    1. State what the logs prove (facts), separately from what they suggest.
    2. Check scope: one request, one account, or many accounts?
    3. Check timing: did it start with a release, config change or customer change?
    4. Decide ownership: customer side, our side, or third party.
    5. Document evidence in the ticket: time range, query, example log lines, request IDs.
    ✅
    A good internal note reads like: "Between 09:30–10:10 UTC, 214 POSTs from acct_acme returned 401 (example req_8f3a). Started 2 min after the customer rotated API keys at 09:28. No other accounts affected."

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Reading top-down in a Python tracebackYou focus on the wrong frameStart from the last line
    Using IST time to search UTC logsMisses the event by 5.5 hoursConvert to UTC
    Concluding from one lineIgnores scope and causeCheck before/after and how widespread
    Sharing raw logs with customersMay expose internal or other dataSummarise in plain language

    🏋️ Practice & Quick Check

    Practice
    P1.Read this traceback and explain the error and where it happened.

    File "/app/reports/export.py", line 54, in to_csv → rows = data["rows"] → TypeError: 'NoneType' object is not subscriptable

    The code tried to read data["rows"] but data was None, i.e., no data came back (probably an empty or failed query). It happened in reports/export.py line 54, function to_csv. Worth checking why the data fetch returned nothing, e.g., the date range had no data or an upstream call failed.
    Practice
    P2.A US customer (UTC−4 in summer) says the error happened at 9:15 am their time. What UTC window do you search?
    09:15 + 4:00 = 13:15 UTC → search roughly 13:00–13:30 UTC.

    Module 03 · Querying

    Searching Logs Effectively

    The universal search method that works in every tool: narrow the time, filter by identifiers and fields, use boolean logic and wildcards, then group and count to see the pattern.

    🔻 The Search Funnel

    1. Time range: the customer's time in UTC, ±15 minutes.
    2. Environment / service: production, the relevant service.
    3. Identifier: request ID, account ID, user email, order ID.
    4. Level / status: ERROR/WARN, status code 5xx/4xx.
    5. Group & count: how many, by what (status, account, host).
    6. Drill into examples: open a few matching lines and read context.
    💡
    Narrowing the time window first is the single biggest speed-up: it shrinks millions of lines to thousands.

    🧮 Filters, Booleans & Wildcards

    TechniqueConceptTypical syntax
    Field filterOnly lines where a field has a valuestatus:error, status_code=500
    ANDBoth conditionsservice:api AND status:error (often implied by a space)
    OREither conditionstatus_code:500 OR status_code:503
    NOT / exclusionRemove noise-status:info, NOT level=DEBUG
    WildcardPartial matchhost:web-*, *timeout*
    RangeNumeric comparisons@duration_ms:>5000, status>=500
    Exact phraseWords in order"connection refused"

    📊 Grouping & Counting

    Grouping answers "how widespread is it?", the most important question in triage.

    QuestionGroup by
    Is it one customer or everyone?account_id
    Which error dominates?status_code / error type
    Is one server bad?host
    When did it start?time buckets (e.g., per 5 minutes)
    Which endpoint fails?http.path / route
    example result: errors by account (last 1 h)account_id      count
acct_acme       1,912
acct_zenflow        4
acct_kiranco        2
→ Almost all errors are from one account → account-specific, not an outage

    🧩 Parsing Text with Regex

    When logs are plain text, regular expressions extract values into fields.

    PatternMatches
    \d+One or more digits
    \w+Word characters
    .*Anything
    user=(?<user>\S+)Captures the value after user= into a field named user
    splunk exampleindex=prod "payment failed"
| rex "user=(?<user>\S+) amount=(?<amount>\d+)"
| stats count, sum(amount) by user
    📌
    You don't need to master regex. Learn digits, words, "anything" and named captures, and use an online regex tester to check patterns.

    🔁 Same Query in Four Tools

    Question: "How many 5xx errors did account acct_acme get per status code in the last hour?"

    Datadog (Log Explorer)service:api @account_id:acct_acme @http.status_code:>=500
→ then "Group into fields" / Visualize as: count by @http.status_code
    Splunk (SPL)index=prod service=api account_id=acct_acme status>=500 earliest=-1h
| stats count by status
    Sumo Logic_sourceCategory=prod/api account_id=acct_acme
| where status >= 500
| count by status
    CloudWatch Logs Insightsfields @timestamp, status
| filter account_id = "acct_acme" and status >= 500
| stats count(*) by status

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Searching "all time"Slow, noisy, may time outSet a tight time range first
    Free-text search onlyMisses structured matchesUse field filters
    Not groupingCan't tell scopeCount by account/status/host
    Forgetting exclusionsHealth checks and bots flood resultsExclude noise (e.g., -path:/health)

    🏋️ Practice & Quick Check

    Practice
    P1.Write a tool-agnostic search plan for: "Customer acct_zen says exports failed this morning between 10 and 11 IST."
    Time: 04:30–05:30 UTC. Filters: env=prod, service=exports (or reports), account_id=acct_zen, level=ERROR or status>=500. Group by error type/status and by time bucket. Then open example lines, follow request IDs, and compare with other accounts to check scope.
    Practice
    P2.Results show 2,000 errors in the last hour: 1,950 from one account, 50 spread across 30 others. What does this suggest?

    Scenario: Triage during a busy shift.

    The problem is mainly account-specific (configuration, data, or their integration), while the 50 others may be normal background errors. Investigate the main account first; still check the 50 for a common pattern before ruling out a broader issue.

    🔎 Log Explorer & Query Syntax

    SyntaxMeaning
    service:checkoutReserved attribute / tag filter

    🏷️ Facets, Attributes & Patterns

    • Attributes are fields parsed from logs (JSON keys or pipeline-extracted values).
    • Facets are attributes made searchable in the left panel, showing top values and counts at a glance.
    • Pipelines (set up by admins) parse plain-text logs into attributes with Grok parsers.
    • Patterns view groups similar log lines together, revealing the most common messages fast.
    💡
    Click a facet value (e.g., an account ID) to add it as a filter instantly; it's faster and avoids typos.

    📈 Visualising & Saving Views

    VisualisationUse
    ListRead individual log lines
    TimeseriesSpot when errors started
    Top listTop accounts/endpoints by error count
    TableGrouped counts by several fields
    • Saved views store a query, columns and time range, e.g., "Webhook errors by account".
    • Share links to an exact search when escalating, so engineers see the same results.
    • Live Tail streams logs in real time while a customer reproduces the issue.

    🔔 Monitors & APM Links

    example log monitorQuery:  env:prod service:webhooks status:error

    📌

    Module 05 · Tool 2

    Splunk & SPL

    Splunk is a powerful enterprise log platform with its own Search Processing Language (SPL). Learn indexes, sourcetypes, search pipelines, stats, timecharts, field extraction and alerts.

    🟢 Splunk at a Glance

    TermMeaning
    IndexWhere data is stored (e.g., index=prod)
    SourcetypeFormat/type of the data (e.g., sourcetype=nginx:access)
    Source / hostFile/path and machine the data came from
    _rawThe original log line
    _timeEvent timestamp
    ForwarderAgent that sends logs to Splunk

    🔎 Basic Searches

    splindex=prod sourcetype=app:json level=ERROR
index=prod "payment declined" account_id=acct_acme
index=prod status>=500 earliest=-1h
index=prod host=web-* NOT path="/health"
    💡
    Always start with index= and a time range (time picker or earliest=-1h). Searches without them are slow.

    🔗 The SPL Pipeline

    SPL works like a Bash pipe: each command after | transforms the results of the previous one.

    CommandDoesExample
    statsAggregate| stats count by status
    timechartCounts over time| timechart span=5m count by status
    top / rareMost / least common values| top limit=10 account_id
    tableChoose columns| table _time, account_id, status, message
    sortOrder results| sort -count
    whereFilter after calculations| where count > 100
    dedupRemove duplicates| dedup request_id
    splindex=prod service=webhooks level=ERROR earliest=-24h
| stats count by account_id, status_code
| sort -count
| head 10

    🧩 Extracting Fields with rex

    splindex=prod "Delivery failed"
| rex "to (?<target_url>\S+) after (?<ms>\d+)ms"
| stats count, avg(ms) as avg_ms by target_url
| sort -count
    📌
    rex uses regular expressions with named groups (?<name>…) to create fields on the fly.

    📊 Saved Searches, Dashboards & Alerts

    • Saved search / report: reuse frequent queries ("Top webhook failures by account").
    • Dashboards: panels built from searches, shared with the team.
    • Alerts: scheduled or real-time searches that notify when a condition is met (e.g., count > 500 in 5 min).
    • Share the search URL in escalations so engineers see the same results.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    No index or time rangeVery slow, may time outindex=prod earliest=-1h
    Using where before stats for simple filtersSlowerFilter in the base search when possible
    Case-sensitive field values surpriseValues may not matchCheck exact values with | top field
    Exporting huge raw resultsHeavy and hard to readAggregate with stats first

    Practice

    Practice
    P2.Write SPL that charts errors per 10 minutes over the last day, split by service.

    Sumo Logic & AWS CloudWatch

    Two more platforms named in your role card. Learn Sumo Logic's source categories, parse and LogReduce, and CloudWatch log groups, Logs Insights queries, metric filters and alarms.

    🟦 Sumo Logic Basics

    TermMeaning
    _sourceCategoryLabel describing where logs come from (e.g., prod/api)
    Collector / SourceAgent and configured input sending logs
    Live TailReal-time log stream
    LogReduceGroups similar messages into patterns

    🔎 Sumo Logic Queries

    sumo_sourceCategory=prod/api error
| parse "account=*," as account
| count by account
| sort by _count desc
| limit 10

_sourceCategory=prod/webhooks "Delivery failed"
| timeslice 5m
| count by _timeslice

_sourceCategory=prod/api
| logreduce
    💡
    parse "start*end" as field extracts the text between known anchors. It's simpler than regex for many cases.

    ☁️ CloudWatch Logs Basics

    TermMeaning

    Log streamSequence of events from one source (instance, container, Lambda run)

    Metric filterTurns matching log lines into a CloudWatch metric
    AlarmTriggers notifications when a metric crosses a threshold
    📌

    🔍 CloudWatch Logs Insights

    logs insightsfields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 50

fields @timestamp, status, account_id
| filter status >= 500
| stats count(*) as errors by account_id
| sort errors desc

filter @message like /Delivery failed/
| parse @message "after *ms" as ms
| stats avg(ms), max(ms) by bin(5m)
    CommandPurpose

    filterKeep matching events
    parseExtract values from text
    stats … byAggregate (with bin() for time buckets)
    sort / limitOrder and cap results

    Module 07 · Monitoring

    Monitoring, Dashboards & Alerts

    Monitoring spots problems before customers report them. Learn the golden signals, percentiles, how to read dashboards during an incident, and how good alerts are designed.

    📡 Monitoring vs Logging

    LoggingMonitoring
    DataDetailed event recordsNumeric metrics over time
    Question"What happened in this request?""Is the system healthy right now?"
    Used forInvestigating specific issuesDetecting problems, trends, alerting
    ExampleERROR webhook 504 for acct_acmeWebhook error rate 8% (normally 0.5%)

    🚦 The Four Golden Signals

    ⏱️
    Latency
    How long requests take (watch p95/p99).
    📈
    Traffic
    How much demand: requests per second, logins per minute.
    ❌
    Errors
    Rate of failed requests (5xx, exceptions).
    🔋
    Saturation
    How full resources are: CPU, memory, DB connections, queue length.
    📌
    The golden signals come from Google's Site Reliability Engineering practices and are a common interview topic.

    📐 Percentiles & Baselines

    latency example100 requests sorted by duration:
p50 (median) = 180 ms   → half are faster
p95          = 900 ms   → 95% are faster, 5% slower
p99          = 2.4 s    → the slowest 1% take 2.4 s or more
average      = 260 ms   → hides the slow tail
    • Customers complain about the slow tail, so p95/p99 matter more than the average.
    • Compare with a baseline (same time last week) to judge whether a number is abnormal.

    🖥️ Reading Dashboards

    Dashboard patternLikely meaning
    Errors spike at one moment across all servicesShared dependency (DB, auth) or deployment
    Latency rises slowly over daysGrowing data / resource saturation
    Traffic drops to zeroOutage, DNS or load balancer problem
    Errors spike right after a deploy markerThe release likely caused it
    One host differs from othersBad server/instance
    💡
    When tickets spike, open the service dashboard first. If it shows a clear incident, check the incident channel before investigating tickets one by one.

    🔔 Alert Design & Alert Fatigue

    • Alert on symptoms customers feel (error rate, latency), not every internal blip.
    • Use thresholds and durations (e.g., error rate > 5% for 5 min) to avoid flapping.
    • Every alert should be actionable and link to a runbook.
    • Alert fatigue: too many noisy alerts make people ignore real ones.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Trusting averagesHides slow outliersWatch p95/p99
    No baseline comparisonCan't tell normal from abnormalCompare with last week/day
    Ignoring deploy markersMiss the obvious causeCheck releases near the spike
    Alerting on everythingAlert fatigueActionable, symptom-based alerts

    🏋️ Practice & Quick Check

    Practice
    P1.A dashboard shows error rate jumping from 0.5% to 9% at 14:02, two minutes after a deploy marker. What do you do as a TSE?

    Scenario: Tickets start arriving about failed checkouts.

    Alert the incident/engineering channel with the dashboard link, timing and deploy correlation; link incoming tickets to an incident/problem ticket; give customers a holding message; don't guess causes publicly; follow the incident process (engineering may roll back).
    Practice
    P2.Average latency is 200 ms but customers complain about slowness. What would you check?
    p95/p99 latency, latency by account or endpoint (large accounts or certain routes may be slow), traces for slow downstream calls, and saturation metrics (DB connections, CPU).

    Module 08 · Real-World Workflow

    Real-World Log Investigations

    The end-to-end workflow a TSE follows, from ticket to evidence to conclusion, plus four worked case studies you'll meet on the job.

    🔁 The Investigation Workflow

    Ticket → Define problem → Convert time to UTC → Find identifiers → Search & filter → Group to check scope → Read context → Conclude → Document → Respond / escalate

    1. Clarify what failed, for whom, when (with timezone).
    2. Collect identifiers: account ID, request ID, email, order ID.
    3. Check dashboards/incidents for a wider problem.
    4. Search logs with the funnel; group by status/account/time.
    5. Read lines before/after; follow the request ID across services.
    6. Decide owner: customer, us, or third party; write evidence and next steps.

    📭 Case 1: Webhooks Not Arriving

    evidenceservice:webhooks @account_id:acct_acme  (last 24 h)
→ 1,240 deliveries, 1,238 with status 504, duration ≈ 30,000 ms
→ started 05 Oct 09:12 UTC
→ other accounts: normal
    ✅
    Conclusion: we send webhooks; the customer's endpoint times out after 30 s. Advise returning 200 immediately and processing asynchronously; share example timestamps and request IDs.

    🔐 Case 2: API Returning 401

    evidenceservice:api @account_id:acct_zen @http.status_code:401
→ 214 requests since 09:30 UTC, all with key prefix sk_live_…a9f2
→ audit log: key ...a9f2 revoked by customer admin at 09:28 UTC
    ✅
    Conclusion: the integration still uses a revoked key. Customer must update the integration with the new key. No bug.

    🐢 Case 3: Slow Reports

    evidenceservice:reports @account_id:acct_bigco  p95 duration = 48 s (others ≈ 3 s)
→ trace: 45 s in DB query "monthly_summary" scanning 12M rows
→ only for date ranges > 6 months
    ✅
    Conclusion: performance issue for large accounts with long ranges. Workaround: shorter ranges / scheduled exports. Escalate to engineering with traces and query name.

    🔀 Case 4: Intermittent Login Failures

    evidenceservice:auth event:login_failed (last 2 h), grouped by host
host auth-3 → 412 failures   reason=token_signature_invalid
host auth-1/2/4 → ~0
    ✅
    Conclusion: one server (auth-3) is misconfigured, so roughly 1 in 4 logins fail at random. Escalate urgently to engineering/on-call with host evidence.

    📝 Documenting Findings

    internal note templateSummary:   Webhooks failing for acct_acme since 05 Oct 09:12 UTC
Scope:     1 account; other accounts normal
Evidence:  Datadog view <link>; 1,238/1,240 deliveries returned 504 after 30s
           Example req_7f2c91 at 09:41:17Z
Cause:     Customer endpoint timing out (not our side)
Next:      Advise customer to respond 200 within 5s and process async
Customer told: Findings + recommendation sent 10:20 UTC
    ⚠️
    When sharing with customers, summarise in plain language and never paste raw internal logs that may include other customers' data or internal details.

    🏋️ Practice & Quick Check

    Practice
    P1.A customer says "some" users get "Something went wrong" when uploading. Plan your log investigation step by step.

    Scenario: Ticket from a 200-user account.

    Get example users, times (convert to UTC) and file sizes. Search upload service errors for the account in that window; group by error type, user, host and file size; read a few failing request IDs end to end; compare with successful uploads. If errors cluster by file size, it's a limit; by host, a server issue; by user, permissions. Document evidence and escalate or advise accordingly.
    Practice
    P2.Write a short customer-facing summary for Case 1 (webhooks timing out).
    "We checked our delivery logs: since 5 Oct 09:12 UTC, our system has sent every webhook to your endpoint, but it hasn't responded within our 30-second limit, so the deliveries are marked as failed and retried. Could your team make the endpoint respond with a 200 status straight away and process the data in the background? Once that's in place, deliveries will succeed and we can resend recent events."

    Interview Preparation: Log Analysis & Monitoring

    Interview questions about logs, log platforms and monitoring, with model answers, a comparison cheat sheet, common mistakes and scenarios.

    🎤 Concept Questions

    QuestionModel answer
    Why are logs important for a TSE?They show what actually happened, letting you find root causes, prove scope and give engineers evidence.
    What are log levels?DEBUG, INFO, WARN, ERROR, FATAL, indicating severity; start investigations with ERROR/WARN.
    Structured vs unstructured logs?JSON fields vs plain text; structured logs are easily filtered and grouped.
    How do you search logs efficiently?Narrow time (UTC), filter by service/environment and identifiers, filter level/status, group to check scope, drill into examples.
    What is a correlation/request ID?An ID attached to every log line of one request across services, used to follow its journey.
    Logs vs metrics vs traces?Events vs numbers over time vs a request's path across services.
    What are the four golden signals?Latency, traffic, errors, saturation.

    📋 Comparison Cheat Sheet

    PairKey difference
    Datadog vs SplunkSaaS logs+metrics+APM in one vs very powerful SPL searches, cloud or on-prem
    Sumo Logic vs CloudWatchCloud-native log analytics vs AWS built-in logs/metrics
    Index vs Log group vs _sourceCategorySplunk vs CloudWatch vs Sumo Logic ways of organising logs
    Logging vs MonitoringDetailed events for investigation vs health metrics for detection
    Average vs p95Typical value that hides outliers vs the slow tail customers feel
    WARN vs ERRORUnexpected but handled vs operation failed
    Structured vs UnstructuredJSON fields vs free text needing parsing
    Patterns vs LogReduceDatadog vs Sumo Logic message clustering

    🚫 Common Mistakes & Fixes

    MistakeWhy it hurtsDo this instead
    Searching in local time instead of UTCWrong window, missed eventsConvert to UTC first
    Searching without a time rangeSlow, noisy resultsTight time window first
    Concluding from one log lineMisses scope and causeGroup and read context
    Pasting raw logs to customersLeaks internal/other-customer dataPlain-language summary
    Trusting averagesHides slow outliersUse percentiles
    Not sharing query links in escalationsEngineers redo your workShare the saved view/search link

    🧩 Scenario Questions

    Practice
    P1."A customer says their API calls fail since this morning. How do you use logs?"
    Get account ID, example request IDs and time (convert to UTC); search API logs for the account and status codes; group by status/endpoint and time; read example requests; check whether other accounts are affected and whether anything changed (keys, deploys); conclude owner and document with links.
    Practice
    P2."How would you explain p95 latency to a non-technical manager?"
    "If we line up 100 requests from fastest to slowest, p95 is the 95th one: 95 were faster and 5 slower. It shows what our slowest customers experience, which the average hides."
    Practice
    P3."Which log tool have you used and how?"
    Name one (e.g., Datadog): filtering by service/env/attributes, grouping by account, timeseries to spot starts, Live Tail during reproduction, saved views and sharing links in escalations.

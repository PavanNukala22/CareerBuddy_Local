    Module 01 · Foundations

    What a Bug Is and the TSE's Role

    Not every customer problem is a bug. Learn to tell bugs from configuration issues, feature requests and known issues, the bug lifecycle, and why the TSE's report is so important to engineering.

    🐞 What Is a Bug?

    A bug (or defect) is when software behaves differently from how it was designed, documented or reasonably expected to behave. Bugs can be functional (wrong result), visual (broken layout), performance (too slow), security, or data-related.

    ❌
    Functional
    Export creates an empty file.
    🎨
    UI
    Save button hidden on small screens.
    🐢
    Performance
    Report takes 60 s for large accounts.
    🔐
    Security
    User can see another account's data.
    🗄️
    Data
    Totals don't match records.

    🤔 Bug or Not a Bug?

    It's probably…When…What you do
    User error / how-toProduct works as documentedExplain + KB link
    ConfigurationSettings, permissions, plan limits explain itFix config / guide admin
    EnvironmentOnly their browser/network/deviceCache, extensions, network checks
    Feature requestProduct never claimed to do itLog as feedback/feature request
    Known issueAlready in the trackerLink ticket to existing bug
    BugContradicts design/docs and you can reproduce itMinimal repro → bug report
    💡
    Before filing, search the tracker for the error message or feature name. Linking to an existing bug raises its priority and avoids duplicates.

    🔄 The Bug Lifecycle

    Figure 1.1 · From customer ticket to verified fix
    Status (typical)Meaning

    Needs infoEngineering needs more details
    Triaged / To DoSeverity and priority set; in backlog
    In ProgressEngineer working on it
    In Review / QAFix in code review and testing

    ⚖️ Incident vs Problem vs Bug

    IncidentProblemBug
    MeaningA disruption happening nowThe underlying cause of one or more incidentsA defect in the code
    ExampleCheckout failing for everyone 14:00–14:40Database connection pool too smallConnection not released on error path
    GoalRestore service fastFind root causeFix the code
    OwnerIncident commander / on-callProblem manager / engineeringEngineering team

    📣 Why the TSE Report Matters

    • Engineers can't fix what they can't see; a clear repro saves hours.
    • Accurate impact (how many customers, revenue) drives correct priority.
    • Good reports build trust: engineers act faster on reports from TSEs who are always precise.
    • You are the customer's voice inside the company.
    ✅
    Bad report: "Exports are broken." Good report: "CSV export returns a header-only file for date ranges over 90 days (3/3 attempts, Chrome & API); 14 customers affected; request IDs attached."

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Filing a bug for a configuration issueWastes engineering time; erodes trustRule out config/user error first
    Duplicate bug reportsSplits information and prioritySearch first; link to existing
    Reporting without reproducing"Cannot reproduce" bounce-backReproduce or explain why you couldn't
    Forgetting to link customer ticketsCustomers never hear about the fixLink every affected ticket

    Module 02 · Reproduction

    Reproducing Bugs Reliably

    A bug you can reproduce is a bug that can be fixed. Learn to match the customer's environment, follow and record steps, measure consistency, and tackle intermittent bugs.

    🎯 Why Reproduction Matters

    ✅
    Confirms it's real
    Rules out misunderstandings.
    🧪
    Enables testing
    Engineers can verify the fix.
    🔍
    Reveals the trigger
    Which input, role or browser matters.
    ⏱️
    Saves time
    No back-and-forth "can you send more details?"

    🧭 Matching the Environment

    FactorExamples
    Product versionWeb app release, mobile app v4.2.1, API version, SDK version
    PlatformBrowser + version, OS, device model
    Account setupPlan, feature flags, region, integrations enabled
    User roleAdmin vs member vs read-only
    DataLarge volumes, special characters, specific records
    NetworkVPN, proxy, slow connection
    TimeTimezone, date boundaries, scheduled jobs
    💡
    Use a test account configured like the customer's (same plan, flags, role). Feature flags are a common reason "it works for me".

    👣 Reproduction Steps

    1. Start from a clean state (fresh login, incognito, new test record).
    2. Follow the customer's steps exactly; note each action and result.
    3. Repeat 3 times to measure consistency (e.g., 3/3, 1/5).
    4. Capture evidence: screenshot, recording, console errors, request IDs.
    5. Vary one factor at a time (browser, role, data) to find the trigger.
    reproduction logEnv: Prod, Chrome 129 / Win 11, test acct (Pro plan, Admin), flag new_export=on
1. Reports → Export → Range: 01 Jun – 30 Sep (122 days) → Download CSV
   Result: file with headers only   (3/3)
2. Same, Range: 01 Jul – 30 Sep (92 days)  → headers only (3/3)
3. Same, Range: 01 Aug – 30 Sep (61 days)  → 412 rows ✓ (3/3)
4. Firefox 131, 122 days → headers only (2/2)   → not browser-specific
5. API GET /v1/reports/export?days=122 → 200, empty body → backend issue

    🎲 Reproducible vs Intermittent

    ReproducibleIntermittent
    DefinitionHappens every time with the same stepsHappens sometimes
    Typical causesLogic errors, validation, permissionsRace conditions, load, one bad server, caching, timeouts, network
    ApproachMinimise steps and dataCollect many examples with timestamps/request IDs; look for common factors
    Report includesExact stepsFrequency, times, IDs, patterns (host, region, time of day)
    📌
    For intermittent bugs, frequency matters: "fails 1 in 20 attempts, all failures on host auth-3" is actionable even without a perfect repro.

    🧰 Tools That Help

    ToolUse
    Browser DevToolsConsole errors, network requests, device mode
    Screen recorder (Loom, OBS, Snipping Tool)Show exact steps and timing
    Postman / cURLReproduce at the API level
    Log platformErrors and request IDs for failures
    SQL (read-only)Check stored data state
    Device clouds (BrowserStack etc.)Other browsers/devices you don't own

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Testing as Admin when customer is MemberCan't reproduce permission bugsMatch role
    Trying onceCan't tell consistencyRepeat and record ratio
    Not checking feature flags"Works for me"Match flags/plan
    Reproducing on a customer's live account without permissionPrivacy/policy breachTest account or approved access

    🏋️ Practice & Quick Check

    Practice
    P1.You can't reproduce a customer's "Save fails" issue. List five things you would compare or ask for.

    Scenario: "It works for me".

    Their role/permissions; plan and feature flags; browser/version and extensions; the exact data they enter (length, special characters); a screen recording plus time and request ID, so you can find the failed request in logs.
    Practice
    P2.Login fails "sometimes" for one company. What information do you collect to report it?
    Frequency (e.g., 1 in 10), timestamps and request IDs of failures and successes, users affected, browsers/devices, network/VPN, SSO provider, and log grouping by host/region to find a common factor.

    Module 03 · Minimal Repro

    Creating Minimal, Reproducible Test Cases

    Shrink a complex customer scenario to the smallest set of steps, data or code that still shows the bug. This is the single most valuable thing a TSE gives engineering.

    ✂️ What "Minimal" Means

    QualityMeaning
    MinimalNothing unnecessary: fewest steps, smallest data, simplest code
    CompleteEverything needed to trigger the bug is included
    ReproducibleAnyone can run it and see the bug
    IsolatedNo customer secrets or unrelated systems required

    ❌ Not minimal

    "Customer's 400-line Python integration fails sometimes when syncing their CRM."

    ✅ Minimal

    "PATCH /v2/contacts/{id} with phone '+91 98480 12345' returns 500 every time; same request with '919848012345' returns 200."

    🔪 Reduction Techniques

    1. Remove steps one at a time; keep any whose removal makes the bug disappear.
    2. Shrink data: fewer rows, shorter strings, smaller files. Find the threshold (e.g., fails above 90 days).
    3. Bisect inputs: split the data in half, test each half, repeat until you find the offending record or character.
    4. Strip code: replace the customer's app with a 5-line script or a cURL command.
    5. Use defaults: fresh account, default settings, unless a setting is the trigger.
    💡
    Bisecting a 10,000-row import file takes only about 14 halvings to find a single bad row, much faster than checking rows one by one.

    🖱️ UI Example

    before → afterBEFORE (customer description, 11 steps):
  Log in, open dashboard, change theme, open Projects, filter by owner,
  open "Q3 Plan & Budget", rename, add 3 tasks, upload logo, Save, error.

AFTER (minimal, 3 steps):
  1. Projects → New project
  2. Name: "A & B"
  3. Create → "Something went wrong" (400 on POST /v1/projects)
  Control: Name "A and B" → works

    💻 API & Code Examples

    minimal cURL reprocurl -X PATCH https://sandbox.api.example.com/v2/contacts/con_77 \
  -H "Authorization: Bearer $TEST_KEY" -H "Content-Type: application/json" \
  -d '{"phone":"+91 98480 12345"}'
# → 500, request_id req_a91f

curl ... -d '{"phone":"919848012345"}'
# → 200
    minimal Python repro (replacing a 400-line integration)import requests
r = requests.patch(
    'https://sandbox.api.example.com/v2/contacts/con_77',
    headers={'Authorization': 'Bearer TEST_KEY'},
    json={'phone': '+91 98480 12345'},
)
print(r.status_code, r.text)   # 500 Internal Server Error

    ⏪ Finding Regressions

    A regression is something that used to work and broke after a change. Narrowing when it broke helps engineering find the change.

    • Ask: when did it last work? Check release notes/deploy times around then.
    • Compare behaviour on older app/SDK versions if available.
    • Engineers can use git bisect to find the exact commit between a good and a bad version.
    git bisect (engineering)git bisect start
git bisect bad              # current version has the bug
git bisect good v4.1.0      # this release worked
# Git checks out a middle commit → test → mark good/bad → repeat
git bisect reset

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Attaching the customer's whole codebaseNobody can run itReduce to a cURL/5-line script
    Including customer secrets/dataSecurity and privacy riskUse test accounts and dummy data
    Removing the trigger while minimisingRepro no longer failsRe-test after each removal
    No control caseHard to see what mattersShow failing + working variant

    🏋️ Practice & Quick Check

    Practice
    P1.A 5,000-row CSV import fails with "Import failed" and no detail. How do you build a minimal repro?

    Scenario: Customer import ticket.

    Bisect the file: import the first 2,500 rows and the last 2,500 separately; keep halving the failing half until you find the smallest failing set (often one row). Inspect it (special characters, bad date, empty required field), then create a 2-row CSV (header + bad row) plus a working control row for the report.
    Practice
    P2.Rewrite this as a minimal repro statement: "The customer's dashboard breaks when they use our app with lots of widgets and filters and stuff."
    Example: "Dashboard fails to load (blank, console TypeError) when a dashboard contains a Pie chart widget with a date filter of 'Last 365 days'. 3 steps: create dashboard → add Pie chart → set filter Last 365 days. Control: 'Last 90 days' loads fine."

    • C Sorting it

    Module 04 · Documentation

    Writing Detailed Bug Reports

    The anatomy of a bug report engineers love: precise title, environment, steps, expected vs actual, evidence, impact and workaround, with templates and good vs bad examples.

    🧱 Anatomy of a Bug Report

    SectionPurpose
    TitleOne-line summary engineers can scan and search
    EnvironmentWhere it happens (prod/sandbox, version, browser/OS, region, plan, flags)
    Steps to reproduceNumbered, minimal steps
    Expected resultWhat should happen
    Actual resultWhat happens, with exact error text
    FrequencyAlways / 3 of 5 / intermittent
    EvidenceScreenshots, recordings, logs, request IDs, HAR, queries
    ImpactCustomers affected, revenue, severity
    WorkaroundAny way customers can continue
    Linked ticketsEvery affected customer ticket

    🏷️ Titles That Work

    Weak titleStrong title
    Export broken!!![Reports] CSV export returns header-only file for ranges > 90 days
    Bug in app[Projects] 400 error when project name contains "&"
    Customer angry about login[Auth] SAML login fails with clock-skew error for IdP time drift > 5 min
    API issue[Contacts API v2] PATCH returns 500 when phone contains "+"
    💡
    Pattern: [Area] What fails + under which condition. Avoid emotions and customer names in titles.

    👣 Steps, Expected & Actual

    • Number every step; one action per step; use exact UI labels and endpoints.
    • Start from a known state ("Logged in as Admin on a Pro-plan test account").
    • Expected: based on docs or design, not opinion.
    • Actual: exact error text, status code, what the user sees.

    ✅ Expected

    CSV downloads with all 1,284 orders in the selected range.

    ❌ Actual

    CSV contains only the header row; no error shown. API returns 200 with empty body (request_id req_19c2).

    📈 Impact & Workaround

    Impact detailExample
    Customers affected14 accounts (3 Enterprise); tickets linked
    Business impactMonth-end reporting blocked; renewal for Acme due 31 Oct
    Since whenSince release 4.12 on 2 Oct
    WorkaroundExport in 60-day chunks
    📌
    Impact drives priority. A precise count of affected customers (from logs or SQL) is often what moves a bug up the queue.

    📝 Full Template & Example

    bug reportTitle: [Reports] CSV export returns header-only file for ranges > 90 days

Environment: Production · Web 4.12.0 · Chrome 129 & Firefox 131 · API v1
             Pro plan · flag new_export=on · region IN

Steps to reproduce:
  1. Log in as Admin (test acct tse-test-07)
  2. Reports → Export → Range 01 Jun – 30 Sep 2026 (122 days)
  3. Click Download CSV

Expected: CSV with 1,284 rows
Actual:   CSV with header row only; API GET /v1/reports/export?days=122
          returns 200 with empty body (req_19c2, 05 Oct 09:41 UTC)
Frequency: 5/5 for ranges > 90 days; ranges ≤ 90 days work

Evidence: screen recording, request IDs, Datadog link, SQL count of rows (1,284)
Impact:   14 customers (3 Enterprise) since 4.12 release on 02 Oct; month-end
          reports blocked. Linked Zendesk tickets: #48121, #48160, #48202 …
Workaround: export in ≤ 90-day chunks
Severity: S2 (major feature broken, workaround exists)

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Vague titleHard to triage and search[Area] what fails + condition
    Steps missing the starting stateEngineer can't reproduceState role, plan, flags, data
    "Doesn't work" as actual resultNo detailExact error, code, request ID
    Pasting customer PIIPrivacy breachUse account IDs; redact
    No impact numbersWrong priorityCount affected customers

    Practice

    Practice
    P2.Improve this report: "Customer says payments fail. Please fix ASAP!!"

    Scenario: Reviewing a teammate's bug report.

    Add area + condition in the title (e.g., "[Checkout] UPI payments fail with error PAY_031 since 14:00 UTC"), environment, minimal steps, expected vs actual with error codes and request IDs, frequency, scope (number of customers/transactions from logs), evidence links, workaround, and linked tickets; remove emotional language.

    Module 05 · Prioritisation

    Severity, Priority & Bug Triage

    How bugs are ranked and scheduled: severity levels, priority levels, how triage meetings work, and how TSEs influence prioritisation with evidence.

    🎚️ Severity Levels

    SeverityDefinitionExample
    S1 · CriticalOutage, data loss/corruption, security breach; no workaroundAll customers can't log in; data exposed
    S2 · MajorMajor feature broken for many/key customers; no easy workaroundPayments fail for UPI
    S3 · ModerateFeature impaired; workaround existsExport fails > 90 days; chunking works
    S4 · MinorCosmetic or low-impactTypo; misaligned icon

    🗓️ Priority Levels

    PriorityMeaning
    P0 / HighestDrop everything; fix now (hotfix)
    P1 / HighNext sprint or sooner
    P2 / MediumPlanned in upcoming work
    P3 / LowBacklog; fix when convenient

    ⚖️ Severity vs Priority

    SeverityPriority
    QuestionHow bad is it?How soon do we fix it?
    Set byReporter/QA/TSE (technical impact)Product/engineering leads (business decision)
    Changes withTechnical factsCustomers affected, revenue, deadlines, strategy
    ExampleSeverityPriority
    Rare crash in an admin page used by 2 customersHighLow–Medium
    Wrong logo on the login page before a big launchLowHigh
    Data exposure to other accountsCriticalHighest

    🧑‍⚖️ Triage Process

    1. New bugs are reviewed regularly (daily/weekly triage).
    2. Check completeness: can it be reproduced? Enough evidence?
    3. Confirm or adjust severity; set priority and owner team/component.
    4. Mark duplicates, link related issues, close invalid ones with explanation.
    5. Schedule: hotfix, next sprint, or backlog.
    💡
    TSEs often join triage to represent customers. Bring numbers: affected customers, ARR at risk, ticket count, deadlines.

    🏷️ Labels & Components

    FieldExampleWhy
    ComponentReports, Auth, BillingRoutes to the right team
    Labelscustomer-reported, regression, enterprise, needs-reproFiltering and reporting
    Affects version4.12.0Shows when it started
    Fix version4.12.2Tells support when to expect the fix

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Marking everything S1/urgentReal emergencies get lostUse definitions honestly
    Inflating severity because a customer is angryMisleads triageSeverity = technical impact
    No component setBug sits unassignedPick the right component
    Not updating impact as more tickets arrivePriority stays lowAdd linked tickets and counts

    🏋️ Practice & Quick Check

    Practice
    P1.Assign severity: (a) Users in one org can see another org's invoices (b) Dark-mode text slightly low contrast (c) Bulk import fails above 10,000 rows; smaller files work.
    (a) S1 Critical (data exposure/security). (b) S4 Minor (cosmetic; accessibility may raise priority). (c) S3 Moderate (workaround: split files), possibly S2 if key customers depend on it.
    Practice
    P2.A bug is S3 but 40 enterprise customers have hit it this week. How do you get it prioritised?

    Scenario: Weekly triage meeting.

    Link all 40 tickets, quantify impact (customers, ARR/renewals at risk, ticket volume, time spent), describe the workaround's cost, and raise it in triage or with the product manager with this evidence; severity may stay S3 but priority should rise.

    Logging & Tracking Bugs in Jira

    Jira (by Atlassian) is the most common bug tracker in companies. Learn issue types and fields, workflows, linking help-desk tickets, labels and components, and searching with JQL.

    🟦 Jira at a Glance

    TermMeaning
    ProjectA team's space, with a key like SUP or ENG (issues become ENG-1423)
    IssueOne work item: Bug, Task, Story, Epic, Sub-task
    BoardScrum or Kanban view of issues by status
    SprintTime-boxed iteration (often 2 weeks) in Scrum teams
    BacklogPrioritised list of work not yet started
    Jira Service ManagementAtlassian's help-desk product; can link support requests to engineering issues

    📝 Creating a Bug Issue

    FieldWhat to enter
    ProjectEngineering team that owns the area (ask if unsure)
    Issue typeBug
    SummaryThe bug title: [Area] what fails + condition
    DescriptionFull report: environment, steps, expected, actual, evidence, impact, workaround
    PriorityHighest / High / Medium / Low / Lowest (per team rules)
    Severity (custom field)S1–S4 if your team uses it
    Component / Labelse.g., Reports; labels: customer-reported, regression
    Affects versionRelease where the bug exists
    AttachmentsScreenshots, recordings, HAR (secure), sample files
    Linked issuesDuplicates, related bugs, help-desk tickets
    💡
    Jira descriptions support formatting: headings, numbered lists, code blocks ({code} or ``` in the new editor) and tables. Use code blocks for cURL commands and log lines.

    🔄 Workflows & Statuses

    Figure 6.1 · Example Jira workflow
    ResolutionMeaning
    Fixed / DoneFix released
    DuplicateSame as another issue (linked)
    Cannot ReproduceEngineers couldn't reproduce with the information given
    Won't Fix / Won't DoAccepted behaviour or not worth fixing

    📌
    "Cannot Reproduce" isn't the end: if customers still report it, add new evidence (request IDs, patterns) and ask to reopen.

    🔗 Linking, Labels & Components

    • Link help-desk tickets: Zendesk, Freshdesk, Intercom and Salesforce have Jira integrations, so agents can create or link a Jira issue from the ticket and see its status.
    • Issue links: "is duplicated by", "relates to", "blocks", "is caused by".
    • Components: product areas (Reports, Billing, API), often auto-assigning a team lead.
    • Labels: free tags like customer-reported, regression, enterprise.
    • Watchers: watch the issue to get notified of updates, then update customers.
    ✅
    Linking every affected customer ticket shows impact (10 linked tickets vs 1) and makes sure everyone gets notified when the fix ships.

    🔍 Searching with JQL

    JQL (Jira Query Language) finds issues precisely, e.g., before filing, to check for duplicates.

    JQLproject = ENG AND issuetype = Bug AND status != Done ORDER BY created DESC

text ~ "export csv" AND issuetype = Bug AND created >= -30d

labels = customer-reported AND priority in (Highest, High) AND resolution = Unresolved

component = Reports AND fixVersion = "2026.10.10"

reporter = currentUser() AND status changed to Done after -7d
    JQL pieceMeaning
    =, !=, in, not inComparisons
    ~Text contains
    -30dRelative date (last 30 days)
    resolution = UnresolvedStill open
    ORDER BYSort
    currentUser()You

    Logging Bugs in GitHub Issues

    Many open-source projects, developer tools and startups track bugs in GitHub Issues. Learn issue templates, Markdown formatting, labels, milestones, linking pull requests, and how GitHub compares with Jira.

    🐙 GitHub Issues at a Glance

    FeatureUse
    IssuesBugs, feature requests and tasks, numbered #123 per repository
    Labelsbug, regression, needs-repro, priority:high
    AssigneesWho is working on it
    MilestonesTarget release, e.g., v2.4.0
    ProjectsBoards/tables across issues and PRs
    DiscussionsQ&A that isn't a confirmed bug
    📌
    Public repositories make issues visible to everyone. Never post customer data, secrets or internal details in public issues.

    📋 Issue Templates

    Repositories define templates in .github/ISSUE_TEMPLATE/ so every bug report has the same structure.

    .github/ISSUE_TEMPLATE/bug_report.md---
name: Bug report
about: Report something that isn't working

    Module 08 · Real-World Workflow

    Collaboration, Verification & Closing the Loop

    Filing the bug is half the job. Learn the end-to-end workflow, how to work with engineers, verify fixes, update every affected customer, and turn bugs into knowledge.

    🔁 End-to-End Bug Workflow

    Ticket → Confirm it's a bug → Reproduce → Minimise → Search duplicates → File (Jira/GitHub) → Link tickets → Tell customer next steps → Track → Verify fix → Notify all customers → Update KB

    1. Confirm and reproduce; rule out config/user error.
    2. Build a minimal test case and collect evidence.
    3. Search for an existing bug; link if found, otherwise file a new one.
    4. Link all customer tickets; set ticket status (often On-hold).
    5. Tell the customer: it's confirmed, it's with engineering, workaround, next update time.
    6. Watch the issue; answer engineers' questions quickly.
    7. When fixed: verify, then notify every linked customer and close tickets.

    🤝 Working with Engineers

    • Use the agreed channel (Jira comments, escalation queue), not random DMs.
    • Respond fast to "need more info"; you hold the customer context.
    • Share facts, not pressure. Quantified impact gets priority faster than "urgent!!!".
    • Offer to join a short call or screen-share for complex reproductions.
    • Thank engineers when fixes ship. Good relationships speed up future escalations.

    ✅ Verifying the Fix

    CheckHow
    Original scenarioRun your minimal test case again on the fixed version
    Customer scenarioRe-test with the customer's conditions (role, data, browser)
    Edge casesVariants near the boundary (90/91 days; 1 vs 3 emails)
    No new breakageQuick check of related features (basic regression)
    Release reached productionConfirm the fix version is actually deployed
    ⚠️
    "Fixed in code" isn't "fixed for customers". Confirm the release is live in production (and on mobile, that users have the new app version).

    📣 Updating Customers

    When filingThanks for the details. I've confirmed this is a bug and passed it to our engineering team with your examples. Until it's fixed, exporting in 60-day ranges works. I'll update you by Friday, or sooner if we have news.
    When fixedGood news: the fix for the CSV export issue you reported is now live. I've tested a 120-day export successfully. Could you try again and let me know it works for you? Thanks for your patience and the detailed report.
    💡
    Use the linked-ticket list to notify every affected customer, including those who reported it weeks ago.

    📚 Known Issues, KB & RCAs

    • While a bug is open, a known-issue macro or KB note keeps agent answers consistent.
    • After the fix, retire or update the macro/article.
    • For serious bugs or incidents, engineering writes an RCA (Root Cause Analysis) / post-mortem; support contributes the customer-impact timeline.
    • Look for patterns: repeated bug areas can be raised in product feedback meetings.

    Module 09 · Interviews

    Interview Preparation: Bug Reproduction & Documentation

    Interview questions about reproducing bugs, minimal test cases, bug reports, severity/priority and Jira/GitHub, with model answers, comparisons, common mistakes and scenarios.

    🎤 Concept Questions

    QuestionModel answer
    What makes a good bug report?Clear title, environment, minimal numbered steps, expected vs actual, frequency, evidence (screenshots, logs, request IDs), impact and workaround.
    How do you reproduce a customer's bug?Match their environment (version, browser, role, plan, data), follow precise steps, repeat to confirm, capture evidence, then minimise.
    What is a minimal reproducible example?The smallest set of steps/data that still triggers the bug reliably, ideally with a working variant.
    Severity vs priority?Severity is technical impact; priority is how soon to fix based on business factors.
    How do you handle intermittent bugs?Collect timestamps and request IDs for failures and successes, find patterns (host, data, time), try to trigger with loops/throttling, file with evidence.
    How do you avoid duplicate bugs?Search the tracker (JQL/GitHub search) by error text and area; link to existing issues.
    What happens after a bug is fixed?Verify in production, notify all linked customers, update KB/macros, close tickets.

    📋 Comparison Cheat Sheet

    PairKey difference
    Bug vs Feature requestContradicts design vs never promised
    Severity vs PriorityHow bad vs how soon
    Reproducible vs IntermittentEvery time vs sometimes (needs patterns)
    Jira vs GitHub IssuesConfigurable company tracker vs code-centric issues

    Cannot Reproduce vs Won't FixNot enough info vs intended/not worth fixing
    Regression vs New bugUsed to work vs never worked

    🧩 Scenario Questions

    Practice
    P1."A customer reports a bug you can't reproduce. What do you do?"
    Compare environments (role, plan, data, browser, version, network); ask for a screen recording, exact timestamps and request IDs; check logs for their failures; look for patterns; if still not reproducible, file with all evidence and frequency, labelled needs-repro, and keep monitoring.
    Practice
    P2."Walk me through a bug report you wrote."
    Example: "[Reports] CSV export only headers when range > 90 days": environment, 3 steps, expected ~4,200 rows vs actual header only, logs showing range_limit_exceeded, 7 linked tickets including 2 Enterprise, workaround of 60-day chunks; it was fixed in the next release and I verified and notified all customers.
    Practice
    P3."How would you prioritise two bugs: a typo on the login page and a rare data-loss bug?"
    Data loss is higher severity (S1/S2) and normally higher priority; the typo is low severity but could become high priority before a launch. I'd report both with impact and let product/engineering set priority, flagging the data-loss bug urgently.

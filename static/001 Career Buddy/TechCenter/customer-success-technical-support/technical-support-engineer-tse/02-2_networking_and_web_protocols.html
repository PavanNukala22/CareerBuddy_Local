    Module 01 · Foundations

    How the Internet Works (for Support Engineers)

    A practical model of what happens between a customer's device and our servers: clients and servers, the TCP/IP layers, and the journey of a single web request.

    🌐 Clients, Servers & Networks

    💻
    Client
    The customer's browser, mobile app or their own server calling our API.
    🖥️
    Server
    Our machines that receive requests and send responses.
    🛜
    Network
    Everything in between: Wi-Fi, ISP, corporate firewall, proxies, CDN, load balancers.
    💡
    Most networking tickets come down to one question: at which point between client and server does the request stop?

    🧱 The TCP/IP Model

    Figure 1.1 · The four TCP/IP layers and what fails at each

    ⚖️ OSI vs TCP/IP

    OSI (7 layers)TCP/IP (4 layers)Examples
    7 Application · 6 Presentation · 5 SessionApplicationHTTP, DNS, TLS (often placed here), SMTP
    4 TransportTransportTCP, UDP
    3 NetworkInternetIP, ICMP (ping)
    2 Data Link · 1 PhysicalLinkEthernet, Wi-Fi, cables
    📌
    Interviewers like the OSI model, but real troubleshooting usually uses the simpler TCP/IP view. Know both names for each layer.

    🛣️ Journey of One Request

    1. Browser checks its cache, then asks DNS for the IP of app.example.com.
    2. Opens a TCP connection to that IP on port 443 (three-way handshake).
    3. Performs a TLS handshake: verifies the certificate, agrees on encryption.
    4. Sends an HTTP request: GET /dashboard with headers and cookies.
    5. Request passes CDN / load balancer to an application server, which may call databases and other services.
    6. Server returns an HTTP response: status code, headers, body (HTML/JSON).
    7. Browser renders the page and makes more requests (CSS, JS, API calls).
    ✅
    "What happens when you type a URL into a browser?" is one of the most common TSE interview questions. This list is a strong answer.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Jumping straight to HTTP errorsMiss DNS/TLS/connection failuresTroubleshoot bottom-up
    Assuming "the internet is fine"Corporate networks block specific domainsTest from their network
    Confusing client and server rolesWrong team investigatesIdentify who sends and who receives

    🏋️ Practice & Quick Check

    Practice
    P1.Explain, in 5–7 steps, what happens when a customer opens https://app.example.com.
    DNS lookup to get the IP → TCP connection to port 443 → TLS handshake with certificate check → HTTP GET request → server (via load balancer) builds the response, querying databases if needed → response with status code, headers and HTML → browser renders and loads extra resources.
    Practice
    P2.At which TCP/IP layer would each fail? (a) "Could not resolve host" (b) "Connection timed out" (c) 500 Internal Server Error
    (a) Application layer (DNS). (b) Transport/Internet (TCP connection blocked or host unreachable). (c) Application layer (HTTP; server-side error).

    Module 03 · Name Resolution

    DNS: The Internet's Phone Book

    How names become IP addresses, the record types you'll meet in tickets (A, CNAME, MX, TXT), TTL and propagation, and the commands to check DNS yourself.

    📖 How DNS Resolution Works

    Figure 3.1 · Resolver → root → TLD → authoritative

    🗂️ Record Types

    RecordPurposeExample
    AName → IPv4api.example.com → 104.18.2.7
    AAAAName → IPv6api.example.com → 2606:4700::6812:207
    CNAMEAlias to another namehelp.acme.com → acme.zendesk.com
    MXMail servers for a domainacme.com → mx1.acme-mail.com (priority 10)
    TXTText: SPF, DKIM, DMARC, domain verification"v=spf1 include:mailservice.com ~all"
    NSWhich servers are authoritativeacme.com → ns1.dnsprovider.com
    📌
    A name with a CNAME can't also have other records at the same name, which is why root domains (acme.com) often can't use a plain CNAME; providers offer "ALIAS/ANAME" workarounds.

    ⏳ TTL & Propagation

    • TTL (Time To Live) is how long (in seconds) resolvers may cache an answer, e.g., 300 = 5 minutes, 86400 = 1 day.
    • After changing a record, old answers may persist until the old TTL expires. This delay is called propagation.
    • Browsers and operating systems also cache DNS; flushing caches can help when testing.
    💡
    Before a planned DNS change, lower the TTL (e.g., to 300) a day in advance so the switch takes effect quickly.

    💻 DNS Tools

    terminalnslookup api.example.com              # works on Windows/macOS/Linux
nslookup -type=TXT acme.com
dig api.example.com +short            # macOS/Linux
dig CNAME help.acme.com +short
dig MX acme.com
dig @8.8.8.8 api.example.com          # ask a specific resolver

# Flush local DNS cache
ipconfig /flushdns                    # Windows
sudo dscacheutil -flushcache          # macOS
    📌
    Online tools (e.g., DNS propagation checkers) show answers from resolvers worldwide, useful for "works for me but not for them" DNS issues.

    🎫 Typical DNS Tickets

    TicketCheckFix
    Custom domain not workingCNAME points to the value in our docs?Correct the CNAME; wait for TTL
    Domain verification failingTXT record present with exact value?Add/fix TXT; no extra quotes or spaces
    Our emails landing in spamSPF/DKIM/DMARC TXT records for sending domainAdd records from our docs
    "Site can't be reached" for one userTheir DNS resolver / cacheFlush cache, try 8.8.8.8, try mobile data

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Expecting instant DNS changesCustomer thinks fix failedExplain TTL/propagation
    Including the domain twice in host fieldCreates help.acme.com.acme.comMany DNS panels want only "help"
    Checking only your own resolverCached old answerQuery multiple resolvers

    🏋️ Practice & Quick Check

    Practice
    P1.A customer added a CNAME for help.acme.com 10 minutes ago and it still shows the old site. The old record had TTL 3600. What do you tell them?
    Resolvers may cache the old answer for up to an hour (TTL 3600 s). Verify the new record with dig CNAME help.acme.com +short or nslookup against a public resolver; if correct, it will take effect as caches expire. They can flush local DNS cache to test sooner.
    Practice
    P2.Which record type would you check for: (a) email deliverability (b) a custom subdomain alias (c) domain ownership verification?
    (a) TXT (SPF/DKIM/DMARC) and MX. (b) CNAME. (c) TXT.

    Module 04 · Security

    SSL/TLS & Certificates

    HTTPS keeps traffic private and proves a site is genuine. Learn what TLS does, how certificates and chains work, the errors customers see, and how to inspect certificates.

    🔒 What TLS Does

    🕶️
    Encryption
    Nobody in between (Wi-Fi, ISP) can read the data.
    🪪
    Authentication
    The certificate proves the server really is app.example.com.
    🧷
    Integrity
    Data can't be altered in transit without detection.
    📌
    SSL is the old name; all SSL versions and TLS 1.0/1.1 are deprecated. Modern systems use TLS 1.2 and 1.3. People still say "SSL certificate".

    📜 Certificates & Chains

    FieldMeaning
    Subject / SANWhich domain names the certificate covers (e.g., app.example.com, *.example.com)
    IssuerThe Certificate Authority (CA) that signed it, e.g., Let's Encrypt, DigiCert
    Valid from / toExpiry dates (often 90 days for Let's Encrypt)
    ChainServer cert → intermediate CA → root CA trusted by browsers
    ⚠️
    If the server doesn't send the intermediate certificate, some clients (often older Android devices, Java apps, or curl) fail even though desktop browsers work.

    🤝 The TLS Handshake (Simplified)

    1. Client says hello: supported TLS versions and ciphers, and the hostname (SNI).
    2. Server replies with its chosen settings and its certificate chain.
    3. Client verifies: trusted CA, name matches, not expired.
    4. Both sides agree on session keys; encrypted HTTP traffic begins.
    📌
    SNI (Server Name Indication) lets one IP serve certificates for many domains. That's why openssl s_client needs -servername.

    ⚠️ Common Certificate Errors

    ErrorCauseFix
    NET::ERR_CERT_DATE_INVALID / expiredCertificate expired, or client clock wrongRenew cert; set device clock to automatic
    ERR_CERT_COMMON_NAME_INVALID / name mismatchCert doesn't cover the hostname usedIssue cert including that name; use correct URL
    Unable to get local issuer / untrustedMissing intermediate, self-signed, or corporate proxy CAInstall full chain; trust proxy CA
    Handshake failure / protocol versionClient only supports old TLSUpgrade client/library to TLS 1.2+
    Mixed content warningsHTTPS page loading HTTP resourcesLoad all resources over HTTPS

    🔍 Inspecting Certificates

    terminal# Full certificate chain and handshake details
openssl s_client -connect help.acme.com:443 -servername help.acme.com

# Just the expiry dates
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -dates -subject -issuer

# curl shows TLS problems clearly
curl -v https://api.example.com/health
    💡
    In a browser: click the padlock / site-info icon → Connection is secure → Certificate, to see names, issuer and expiry.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Telling customers to "ignore the warning"Teaches insecure behaviourFix the cause
    Disabling certificate verification in code (verify=False)Opens man-in-the-middle riskFix chain/CA bundle
    Forgetting device clock issuesValid certs look expiredCheck client date/time

    🏋️ Practice & Quick Check

    Practice
    P1.Desktop browsers load https://help.acme.com fine, but the customer's Java integration fails with "unable to find valid certification path". Diagnose.

    Scenario: Enterprise customer's backend integration.

    Likely the server isn't sending the intermediate certificate (browsers often fill the gap, Java doesn't), or their Java trust store lacks the CA, or a corporate proxy re-signs traffic. Check with openssl s_client -showcerts; fix by serving the full chain or importing the right CA/proxy cert into the trust store.
    Practice
    P2.A single user sees "Your connection is not private: certificate expired" on our site; no one else does. What do you check?
    Their device date/time (if wrong, valid certificates appear expired), antivirus/proxy HTTPS inspection, and browser version. Confirm our certificate's expiry yourself to rule out a real expiry.

    HTTP: Requests, Responses, Headers & Status Codes

    HTTP is the language of the web and of APIs. Learn the structure of requests and responses, methods, important headers, cookies, and how to diagnose every common status code.

    📨 Request & Response Structure

    ➡️ Request

    httpPOST /v1/customers HTTP/1.1
Host: api.example.com
Authorization: Bearer sk_live_abc123
Content-Type: application/json
Accept: application/json

{"name":"Priya","email":"priya@acme.com"}

    ⬅️ Response

    httpHTTP/1.1 201 Created
Content-Type: application/json
X-Request-Id: req_7f2c91

{"id":"cus_901","name":"Priya"}
    PartPurpose
    Method + pathWhat to do to which resource
    HeadersMetadata: auth, formats, IDs, caching
    BodyData sent/returned (JSON, XML, form data)
    Status lineResult: code + reason

    🔁 HTTP Methods

    MethodActionIdempotentHas body?
    GETReadYesNo
    POSTCreate / trigger actionNoYes
    PUTReplace entirelyYesYes
    PATCHPartial updateUsuallyYes
    DELETERemoveYesUsually no
    HEAD / OPTIONSHeaders only / CORS preflightYesNo
    📌
    Idempotent = repeating the request has the same effect as doing it once. Retrying a POST after a timeout can create duplicates.

    🏷️ Important Headers

    HeaderDirectionUse in troubleshooting
    AuthorizationRequestMissing/wrong → 401
    Content-TypeBothWrong type → 400/415
    AcceptRequestFormat the client wants
    User-AgentRequestWhich browser/SDK/version made the call
    X-Request-IdResponseFind the request in logs
    Retry-AfterResponseHow long to wait after 429/503
    LocationResponseRedirect target (3xx) or new resource URL (201)
    Cache-ControlResponseExplains stale content
    Access-Control-Allow-OriginResponseCORS: which websites may call the API from a browser

    🚥 Status Codes in Depth

    CodeNameTypical TSE diagnosis
    200 / 201 / 204OK / Created / No ContentSuccess; look at what the client does next
    301 / 302 / 307 / 308Redirectshttp→https, old URLs; POST may become GET on 301/302
    304Not ModifiedCached copy still valid
    400Bad RequestMalformed JSON, missing field; read error body
    401UnauthorizedMissing/invalid/expired credentials
    403ForbiddenAuthenticated but no permission, scope or IP allowlist
    404Not FoundWrong URL/ID, deleted, or test vs live environment
    405Method Not Allowede.g., GET to a POST-only endpoint
    409ConflictDuplicate or version conflict
    415Unsupported Media TypeWrong Content-Type
    422Unprocessable EntityValid JSON, failed validation
    429Too Many RequestsRate limit; respect Retry-After
    500Internal Server ErrorOur bug; escalate with request ID
    502 / 503 / 504Bad Gateway / Unavailable / Gateway TimeoutUpstream failure, overload, slow backend
    💡
    Always read the response body too: APIs usually explain the exact problem, e.g., {"error":"email is invalid"}.

    🍪 Cookies, Sessions & Redirects

    • Server sets Set-Cookie: session=abc; Secure; HttpOnly; SameSite=Lax; browser sends Cookie: session=abc on later requests.
    • Blocked third-party cookies break embedded widgets and some SSO flows.
    • Redirect loops ("too many redirects") usually come from conflicting http/https or www rules, or bad cookies.
    • CORS errors appear only in browsers when a website calls an API on another domain that doesn't allow it.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Reading only the status codeMisses the precise error messageRead the response body
    Confusing 401 and 403Wrong fix401 = who are you? 403 = not allowed
    Blaming the API for CORS in server-to-server callsCORS is browser-onlyCheck if call is from browser JS
    Retrying POSTs blindlyDuplicatesUse idempotency keys

    🏋️ Practice & Quick Check

    Practice
    P1.A customer's browser console shows "blocked by CORS policy" when their website calls our API, but the same call works in Postman. Explain.

    Scenario: Frontend integration ticket.

    CORS is enforced only by browsers. Postman isn't a browser, so it ignores CORS. Our API must allow their website's origin (Access-Control-Allow-Origin), or, more securely, they should call our API from their backend so secret keys aren't exposed in browser code.
    Practice
    P2.Diagnose: POST /v1/orders returns 415 Unsupported Media Type.
    The server doesn't accept the body format sent; usually the Content-Type header is missing or wrong (e.g., text/plain instead of application/json). Set Content-Type: application/json and send valid JSON.

    REST APIs in Practice

    How REST APIs are designed, how authentication works, and the API concepts behind most integration tickets: pagination, rate limits, idempotency, versioning and webhooks.

    🏛️ REST Principles

    • Resources identified by URLs: /v1/customers/cus_901.
    • Methods express actions on them (GET, POST, PATCH, DELETE).
    • Stateless: each request carries everything needed (auth, IDs).
    • Representations usually in JSON.
    • Standard status codes report results.
    RESTSOAPGraphQL
    FormatMostly JSON over HTTPXML envelopesJSON; client chooses fields
    EndpointsMany resource URLsOne endpoint, many operationsUsually one /graphql endpoint
    Common inModern SaaS APIsOlder enterprise/banking systemsApps needing flexible queries

    🔑 Authentication Methods

    MethodHow it worksCommon ticket
    API keySecret in a header (e.g., Authorization: Bearer sk_…)Revoked/rotated key, test vs live key
    Basic authBase64 user:password in Authorization headerWrong credentials; insecure over HTTP
    OAuth 2.0User grants access; app gets short-lived access token + refresh tokenExpired token; refresh failing; missing scope (403)

    📄 Pagination, Rate Limits & Idempotency

    ConceptWhat it isTicket symptom
    PaginationLarge lists returned in pages (limit/offset, page, or cursor)"API returns only 100 records" (they didn't fetch next pages)
    Rate limitingMax requests per time window429 errors during bulk syncs
    Idempotency keysHeader making retries safeDuplicate orders/charges after timeouts
    pagination (cursor)GET /v1/orders?limit=100

    🔔 Versioning & Webhooks

    🔢 Versioning

    APIs change over time: /v1/ vs /v2/ in the URL, or a version header. Old versions get deprecated, which is a common cause of "it suddenly stopped working".

    🔔 Webhooks

    Instead of the customer polling, we call their URL when an event happens (e.g., order.paid). Their endpoint must respond 2xx quickly; we retry on failures.

    💡
    Webhook tickets: check delivery logs (status codes, timeouts), the endpoint URL, signature verification secret, and whether their firewall allows our IPs.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Assuming first page = all dataMissing recordsFollow pagination
    Ignoring rate-limit headersRepeated 429sBack off; respect Retry-After
    Using deprecated API versionsSudden breakageTrack deprecation notices
    Slow webhook handlersTimeouts, retries, duplicatesRespond 200 fast; process async; dedupe by event ID

    🏋️ Practice & Quick Check

    Practice
    P1.A customer says "your API only returns 100 orders, but I have 2,300". What's happening?
    The list endpoint is paginated (100 per page). They need to follow pagination (e.g., has_more + starting_after/next cursor, or page numbers) until all 23 pages are fetched. Share the docs and an example.
    Practice
    P2.A customer's nightly sync gets many 429 errors. What do you advise?

    Scenario: Bulk data sync.

    They're hitting the rate limit. Respect Retry-After, add exponential backoff, spread requests over time, use bulk/batch endpoints if available, and avoid parallel bursts. Check their plan's limits.

    Paste payloads into a JSON validator or Postman's body editor; it highlights the exact line. Many APIs return the failing field in the error body.

    🔍 Comparing Payloads

    When "the same request" works for you but fails for the customer, compare the payloads field by field:

    ✅ Works (yours)

    json{"email":"ravi@test.com","qty":2,
 "currency":"INR"}

    ❌ Fails (customer)

    json{"Email":"ravi@test.com","qty":"2"}
    ✅
    Differences: key case (Email vs email), type ("2" vs 2), missing currency. Any of these can cause 400/422.

    Eyeballing large payloadsEasy to miss one characterUse validators and diff tools
    Ignoring key caseJSON keys are case-sensitiveMatch docs exactly

    Module 08 · Real-World Workflow

    Network Troubleshooting Workflow & Tools

    A layer-by-layer workflow and the command-line tools TSEs use daily, plus worked cases for the network problems you'll meet most.

    🪜 Layer-by-Layer Workflow

    DNS → Connectivity (TCP) → TLS → HTTP status → Response body → Application logs

    1. DNS: does the name resolve to the expected IP? (nslookup, dig)
    2. Connectivity: can we reach the host/port? (curl -v, nc -vz host 443, traceroute)
    3. TLS: valid certificate and chain? (openssl s_client)
    4. HTTP: what status code and headers? (curl -i, DevTools)
    5. Body: what error message does the API return?
    6. Logs: what did our server record for that request ID?

    🧰 Command-Line Toolkit

    pingIs the host reachable? (ICMP may be blocked)ping api.example.com
    nslookup / digDNS answersdig api.example.com +short
    traceroute / tracertWhere along the route it stopstraceroute api.example.com

    Interview Preparation: Networking & Web Protocols

    Common networking and web-protocol interview questions for TSE roles, with model answers, a comparison cheat sheet, common mistakes and scenarios.

    🎤 Concept Questions

    QuestionModel answer
    What happens when you type a URL?DNS lookup → TCP connection → TLS handshake → HTTP request → server response → browser renders and loads resources.
    TCP vs UDP?TCP is connection-oriented and reliable (HTTP, SSH); UDP is connectionless and fast (DNS, video).
    What is DNS TTL?How long resolvers cache a DNS answer; affects propagation after changes.
    401 vs 403?401: not authenticated / bad credentials. 403: authenticated but not permitted.
    PUT vs PATCH?PUT replaces the whole resource; PATCH updates part of it.
    What is idempotency?Repeating a request has the same effect as once; GET/PUT/DELETE are idempotent, POST isn't.
    How do you troubleshoot an SSL error?Check expiry, hostname match, chain/intermediates, TLS version, client clock, proxies; use browser padlock/openssl.

    📋 Comparison Cheat Sheet

    PairKey difference
    TCP vs UDPReliable connection vs fast connectionless
    HTTP vs HTTPSPlain text vs TLS-encrypted (port 80 vs 443)
    A vs CNAME recordName → IP vs name → another name
    401 vs 403Unauthenticated vs unauthorised
    PUT vs PATCHReplace vs partial update
    JSON vs XMLCompact typed data vs verbose tagged text with attributes
    REST vs SOAPResource URLs + JSON vs XML envelopes + operations
    Timeout vs Connection refusedNo reply (dropped) vs active rejection (nothing listening)

    MistakeWhy it hurtsDo this instead
    Starting at HTTP for every issueMisses DNS/TCP/TLS failuresTroubleshoot bottom-up
    Reading only status codesMisses the precise errorRead the response body
    Expecting instant DNS changesFalse "it didn't work"Explain TTL
    Advising verify=False for SSL errorsSecurity riskFix certificate chain/trust store
    Ignoring pagination"Missing data" ticketsFollow next cursor/page
    Pasting secrets in ticketsCredential exposureRedact and rotate

    🧩 Scenario Questions

    Practice
    P1."A customer's webhook endpoint isn't receiving events. How do you troubleshoot?"
    Check our delivery logs for their endpoint: are we sending, what status/timeouts? If timeouts/5xx, it's their endpoint (ask them to respond 2xx fast). If connection errors, check DNS of their URL, firewall allowlisting of our IPs, and TLS validity of their certificate. Verify the URL and signing secret.
    Practice
    P2."Explain DNS to a non-technical person."
    "DNS is like a phone book for the internet: it looks up a website's name and finds its number (IP address) so your computer knows where to connect."
    Practice
    P3."curl shows SSL certificate problem: unable to get local issuer certificate. What next?"
    Inspect with openssl s_client -showcerts to see if the intermediate certificate is missing; check if a corporate proxy is intercepting TLS; update the CA bundle/trust store; fix the server to send the full chain.

    Module 01 · What Is What

    Implementation Projects & the Specialist Role

    Start with the basics: what an implementation is, what an Implementation/Onboarding Specialist does, the phases of an implementation project, the roles involved and the main project methodologies.

    🚀 What Is an Implementation?

    An implementation (or onboarding project) is the work of getting a new customer from "contract signed" to "live and getting value": configuring the platform, migrating data, setting up integrations, training users and handing over to ongoing support/Customer Success.

    📦 Project

    Temporary, with a start, end, defined scope and goal (e.g., "go live in 8 weeks").

    🔄 Operations

    Ongoing, repeating work (e.g., daily support, renewals). The implementation hands over to operations.

    👤 The Specialist's Role

    📋
    Project manager
    Plans scope, milestones and deadlines.
    🗃️
    Data specialist
    Cleans and migrates customer data.
    ⚙️
    Configurator
    Sets up settings, permissions, SSO, integrations.
    🎓
    Trainer
    Runs workshops and creates guides.
    🤝
    Expectation manager
    Controls scope creep; bridges Sales → CS.
    📌
    Titles vary: Implementation Specialist/Manager/Consultant, Onboarding Specialist/Manager, Professional Services Consultant.

    🗓️ Implementation Phases

    AgileShort iterations (sprints), frequent feedbackEvolving requirements, product-like work

    Starting configuration before scope is agreedRework, scope creepSign off scope first

    Treating go-live as the endValue not realisedPlan hypercare and CS handoff

    Module 02 · Scope

    Scoping & Scope Control

    Scope defines what you will and won't deliver. Learn the Statement of Work, scope statements, in/out-of-scope lists, the Work Breakdown Structure and a formal change-control process.

    📏 What Is Scope?

    Scope is the agreed set of work and deliverables for the project. Scope control is making sure only approved work is done, and that changes go through an agreed process.

    TypeMeaningExample
    Product scopeFeatures/configuration delivered3 workflows, SSO, 2 integrations
    Project scopeWork needed to deliver itWorkshops, data migration, training
    Out of scopeExplicitly excludedCustom code, more than 50k records

    📄 SOW & Scope Statement

    scope statement (example)Project: Acme – Support Platform Implementation
Objective: Go live for 80 agents by 30 Nov
In scope:
  - Configure 3 ticket workflows, SLA policies, 20 macros
  - SSO with Okta; up to 4 user roles
  - Migrate up to 50,000 historical tickets from CSV
  - 2 integrations: Slack, Salesforce (standard connectors)
  - 3 training workshops (admins, leads, agents)
Out of scope:
  - Custom code or API development
  - Data older than 2023
  - Integrations beyond the two listed
Assumptions: customer provides clean CSV by 15 Oct; IT available for SSO
Acceptance: UAT sign-off by project owner
    💡
    The out-of-scope list is as important as the in-scope list. It prevents "I thought that was included" later.

    🌳 Work Breakdown Structure

    A WBS breaks the scope into deliverables and smaller work packages you can estimate and assign.

    WBS1. Project management (kickoff, status reports, RAID)
2. Configuration
   2.1 Workflows  2.2 SLA policies  2.3 Macros
3. Access
   3.1 SSO (Okta)  3.2 Roles & permissions
4. Data migration
   4.1 Mapping  4.2 Cleansing  4.3 Test load  4.4 Final load
5. Integrations
   5.1 Slack  5.2 Salesforce
6. Enablement
   6.1 Admin workshop  6.2 Lead workshop  6.3 Agent workshop  6.4 Guides
7. Go-live & handoff

    🔀 Change Control Process

    1. Customer requests a change (new integration, extra workflow).
    2. Log a change request: description, reason, requester.
    3. Assess impact on scope, timeline, cost, risk.
    4. Decision by agreed approvers (sponsor + vendor).
    5. If approved: update scope, plan, SOW/order form; communicate.
    6. If declined/deferred: record it for a later phase.
    change requestCR-004 · Requested by: Acme Ops Manager · Date: 20 Oct
Change: add HubSpot integration
Impact: +5 days configuration, +1 week to go-live, additional services fee
Decision: Deferred to Phase 2 (after go-live) — approved by sponsor 22 Oct

    🔺 The Triple Constraint

    Scope, time and cost are linked: change one and at least one other must move, or quality suffers.

    If scope increases…Then…
    Time fixed, cost fixedQuality/risk suffers
    Time can moveGo-live date shifts
    Cost can moveMore resources/fees

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Vague scope ("set up integrations")Endless expansionName exact integrations and limits
    Saying yes informallyScope creep, missed deadlinesUse change requests
    No acceptance criteriaNever-ending "almost done"Define sign-off criteria

    🏋️ Practice & Quick Check

    Practice
    P1.Write in-scope and out-of-scope items for implementing an HR platform for 300 employees.
    In: configure 2 leave policies, 3 approval workflows, SSO with Azure AD, import 300 employee records from CSV, 2 admin trainings + 1 manager training. Out: payroll integration, custom reports beyond standard, historical leave data older than 1 year, translation into additional languages.
    Practice
    P2.Mid-project, the customer asks for an extra integration "quickly". What do you do?

    Scenario: Week 4 of 8.

    Thank them, log a change request, assess impact (effort, timeline, cost), present options (add with new date/fee, or defer to phase 2), get sponsor approval, update plan and documents.

    Planning & Milestone Scheduling

    Turn scope into a realistic schedule: tasks and estimates, dependencies, milestones, the critical path and buffers.

    ◆ Tasks vs Milestones

    TaskMilestone
    DefinitionWork with durationA point in time marking an achievement
    DurationDays/weeksZero
    Example"Configure SLA policies (3 days)""Scope signed off", "Go-live"
    UseTrack workTrack progress and approvals
    Common implementation milestones
    Kickoff complete
    Scope / design sign-off
    SSO live
    Test data load approved
    UAT sign-off
    Go-live
    Project closed / handoff to CS

    ⏱️ Estimating Durations

    TechniqueHow
    Expert / historicalUse past similar projects
    Bottom-upEstimate each work package, then add up
    Three-point (PERT)(Optimistic + 4×Most likely + Pessimistic) ÷ 6
    TemplatesStandard durations for standard packages
    PERT exampleData cleansing: O = 2 days, M = 4 days, P = 9 days
Estimate = (2 + 4×4 + 9) / 6 = 27 / 6 = 4.5 days

    🔗 Dependencies

    TypeMeaningExample
    Finish-to-Start (FS)B starts after A finishes (most common)Training starts after configuration finishes
    Start-to-Start (SS)B starts when A startsData cleansing starts with mapping
    Finish-to-Finish (FF)B finishes when A finishesGuides finish with configuration
    Start-to-Finish (SF)B finishes when A starts (rare)Old system support ends when new one starts
    📌
    Also track external dependencies: customer IT for SSO, clean data delivery, third-party vendor access.

    🛣️ Critical Path

    The critical path is the longest chain of dependent tasks; it determines the earliest possible finish date. Any delay on it delays go-live. Tasks off the path have slack/float.

    critical path exampleA Kickoff (2d) → B Data mapping (4d) → C Cleansing (5d) → D Test load (3d) → E UAT (5d) → Go-live
Parallel: F SSO (6d, after A) → joins E
Path A-B-C-D-E = 19 days  ← critical
Path A-F-E    = 13 days  → F has 6 days of float

    🧱 Buffers & Realistic Plans

    • Add buffer before key milestones (e.g., 10–20%), not hidden in every task.
    • Plan around customer availability: holidays, month-end, festivals.
    • Confirm customer task owners and dates at kickoff.
    • Re-baseline only with formal agreement.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Ignoring customer-side tasksDelays you don't see comingInclude their tasks with owners
    No dependencies in planUnrealistic datesLink tasks
    Optimistic estimates onlyMissed deadlinesThree-point estimates + buffer

    🏋️ Practice & Quick Check

    Practice
    P1.Calculate a PERT estimate for SSO setup: O=1 day, M=3 days, P=8 days.
    (1 + 4×3 + 8) / 6 = 21 / 6 = 3.5 days.
    Practice
    P2.Path 1: Mapping (3) → Cleansing (6) → Load (2) → UAT (4). Path 2: SSO (5) → UAT. Which is critical and what's the float on SSO?
    Path 1 before UAT = 11 days; Path 2 before UAT = 5 days. Path 1 is critical (15 days total). SSO has 6 days of float.

    Module 04 · Gantt Charts

    Gantt Charts & Project Tracking

    A Gantt chart shows the schedule visually. Learn to read and build one, track progress against a baseline, and report status with RAG colours.

    📊 What Is a Gantt Chart?

    A Gantt chart lists tasks down the left and time across the top. Each task is a bar showing start, duration and progress, with arrows for dependencies and diamonds for milestones.

    Figure 4.1 · Example implementation Gantt chart

    🔍 Reading a Gantt Chart

    ElementMeaning
    Bar lengthTask duration
    Bar shading% complete
    ArrowsDependencies
    Diamond ◆Milestone
    Today lineWhere you are now; tasks left of it should be done
    Highlighted barsCritical path (in many tools)
    💡
    In the example, "Data migration" is behind: today is mid-week 3 but it's only ~60% done, and UAT depends on it. That's a risk to go-live.

    📏 Baseline vs Actual

    TermMeaning
    BaselineThe approved original plan (dates, durations)
    Actual / currentWhere tasks are now
    VarianceDifference between baseline and actual
    Re-baselineOfficially resetting the plan after an approved change
    variance exampleTask: Data migration · Baseline finish: 18 Oct · Forecast finish: 25 Oct
Variance: +5 working days → UAT and go-live at risk

    🚦 Status Reporting & RAG

    StatusMeaning
    🟢 GreenOn track
    🟡 AmberAt risk; recoverable with action
    🔴 RedOff track; needs decision/escalation
    weekly status reportProject: Acme Implementation · Week 3 of 6 · Overall: 🟡 Amber
Done: SSO live; workflows configured; 2 of 3 workshops scheduled
Next: finish data cleansing; test load; Slack integration
Risks/issues: customer CSV had 12% duplicate contacts → cleansing +3 days

    Module 06 · Delivery

    Managing Delivery Deadlines & Risks

    Keep projects on time: RAID logs, risk assessment, issue escalation and the techniques to recover a slipping schedule.

    📒 RAID Log

    LetterMeaningExample
    R – RisksMight happenCustomer IT may not be available for SSO
    A – AssumptionsBelieved trueCustomer provides CSV by 15 Oct
    I – IssuesHappening nowCSV has 12% duplicates
    D – Dependencies (or Decisions)External links / decisions madeOkta admin access; decision to defer HubSpot

    ⚠️ Assessing Risks

    risk scoringRisk                        Probability (1–5)  Impact (1–5)  Score  Response
IT unavailable for SSO      3                  4             12     Book IT slot now; escalate via sponsor
Data quality poor           4                  4             16     Early data profiling; cleansing buffer
Key user on leave in Nov    2                  3              6     Train a backup user
    ResponseMeaning
    AvoidChange plan to remove the risk
    MitigateReduce probability/impact
    TransferShift to another party
    AcceptMonitor; plan contingency

    📣 Issues & Escalation

    1. Log the issue with impact and owner.
    2. Try to resolve at working level within an agreed time.
    3. Escalate to the project owner, then sponsor, if it threatens milestones.
    4. Present options and a recommended decision, not just the problem.
    5. Record the decision and update plan.

    🛠️ Recovering a Slipping Project

    TechniqueHowTrade-off
    Fast-trackingRun tasks in parallel that were sequentialMore risk/rework
    CrashingAdd resources to critical tasksHigher cost
    De-scopingMove non-critical items to phase 2Less delivered at go-live
    Using bufferConsume planned contingencyLess safety later
    Re-baseliningAgree a new date formallyExpectations reset

    ✅ Go-live Readiness

    go-live checklist☐ UAT signed off by project owner
☐ Final data load completed and reconciled
☐ SSO and permissions tested for each role
☐ Integrations tested end-to-end
☐ Users trained; guides published
☐ Support team briefed; escalation path agreed
☐ Rollback / contingency plan documented
☐ Hypercare schedule (e.g., daily check-ins for 2 weeks)
☐ Go/no-go meeting held with sponsor

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Raising risks only when they become issuesNo time to respondWeekly RAID review
    Escalating without optionsSlow decisionsBring options + recommendation
    Skipping go/no-goUnready go-livesFormal readiness check

    Practice

    Module 07 · People Change

    Change Management in Implementations

    New software changes how people work. Learn the people side of implementations: change models, stakeholder communication plans and handling resistance.

    🔄 What Is Change Management?

    Change management is helping people move from the old way of working to the new one so the implementation is actually adopted. Project management delivers the system; change management delivers the usage.

    Type of changeExample
    ProcessApprovals move from email to workflows
    ToolSpreadsheets replaced by a platform
    RoleTeam leads now own dashboards
    OrganisationalCentral team created to manage the system

    🧭 Change Models (ADKAR & Kotter)

    ADKAR (individual)

    Awareness → Desire → Knowledge → Ability → Reinforcement. Each person must pass through all five.

    Kotter (organisation)

    8 steps, e.g., create urgency, build a guiding coalition, communicate the vision, generate short-term wins, anchor the change in culture.

    📣 Communication Plan

    AudienceMessageChannelWhenFrom
    All usersWhy we're changing; go-live dateEmail + town hallKickoff, −2 weeks, go-liveExec sponsor
    ManagersTheir role, dashboardsWorkshop−3 weeksImplementation lead
    End usersHow-to, training datesTraining + guides−2 weeksTrainers
    ITTechnical stepsMeetingsThroughoutTech consultant

    🛡️ Handling Resistance

    CauseResponse
    Fear of extra workShow time saved; simplify workflows
    Comfort with old toolSet switch-off date; migrate templates
    Lack of involvementInclude SMEs in design and UAT
    Skill worriesHands-on training, office hours, champions
    Distrust in dataShow validation results; fix issues fast

    🌱 Sustaining the Change

    • Retire the old system/process on a fixed date.
    • Celebrate early wins publicly.
    • Track adoption metrics after go-live.
    • Hand over to CS with adoption risks noted.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Assuming training = adoptionPeople revertCommunication + reinforcement
    No exec messageSeen as optionalSponsor communicates why
    Ignoring resistersThey spread doubtListen and involve them

    🏋️ Practice & Quick Check

    Practice
    P1.Draft a two-line go-live announcement from the executive sponsor.
    "From 15 November, all customer requests will be handled in our new support platform, giving customers faster replies and giving us one view of every request. Training is on 5–8 November. Please attend your session, and thank you for helping us make this change."
    Practice
    P2.Sales reps keep using spreadsheets instead of the new CRM after go-live. Apply ADKAR to diagnose.

    Scenario: Post-go-live resistance.

    Check Awareness/Desire (do they know why and see personal benefit?), Knowledge/Ability (trained, comfortable?), Reinforcement (are spreadsheets still accepted, do managers use CRM dashboards?). Fix with leadership message, quick personal wins, refresher training, manager reviews only from CRM, and retire the spreadsheets.

    Module 08 · Real-World Workflow

    Real-World Implementation Scenarios

    The end-to-end project workflow and worked scenarios: scope disputes, customer delays and compressed deadlines.

    🔁 End-to-End Workflow

    Sales handoff → Kickoff → Scope & plan (WBS, Gantt, RAID) → Configure & migrate → UAT → Training → Go/no-go → Go-live → Hypercare → Close & handoff

    ⏳ Scenario: Customer Keeps Missing Tasks

    • Make customer tasks visible in the shared plan with owners and dates.
    • Show impact clearly: "Each week of delay on data moves go-live by a week."
    • Escalate to the sponsor with options.
    • Offer help: templates, working sessions.

    ⏩ Scenario: Deadline Pulled Forward

    • Customer wants go-live 3 weeks earlier for a business event.
    • Analyse the critical path; options: de-scope to an MVP, fast-track, add resources.
    • Agree in writing what will be live on the new date and what comes later.

    ⚔️ Scenario: Scope Dispute

    • Customer insists a custom report was "promised".
    • Check SOW and sales handoff notes; talk to the AE.
    • If not in scope: offer change request or phase 2; if promised by sales, escalate internally for a decision.
    • Document the outcome.

    🏋️ Practice & Quick Check

    Practice
    P1.A customer's data delivery is 2 weeks late and go-live is fixed for a launch event. What do you propose?
    Analyse the critical path; propose an MVP go-live with core configuration and a subset of data (e.g., open records only), loading history after go-live; fast-track cleansing with extra customer resources; document the trade-off and get sponsor sign-off.
    Practice
    P2.List 5 items you'd include in a kickoff deck.
    Objectives and success criteria; scope (in/out); timeline with milestones; roles and responsibilities (both sides); communication cadence, RAID approach and next steps/customer tasks.

    Interview Preparation: Project & Change Management

    Interview questions on implementation project management, scope, scheduling, Gantt tools and change management, with model answers, comparisons, common mistakes and scenarios.

    🎤 Concept Questions

    QuestionModel answer
    How do you run an implementation?Kickoff, agreed scope and plan, configure and migrate, UAT, training, go/no-go, go-live, hypercare, handoff to CS, with RAID and weekly status throughout.
    How do you control scope?Clear in/out-of-scope, acceptance criteria and a change-request process assessing impact on time/cost.
    What is a critical path?The longest chain of dependent tasks; it sets the earliest finish date.
    How do you track progress?Gantt with baseline vs actual, % complete, RAG status reports, RAID review.
    What tools have you used?e.g., Smartsheet for Gantt/predecessors/baselines; Asana timeline and portfolios; Monday boards and automations.
    How do you recover a delayed project?Fast-track, crash, de-scope, use buffer or formally re-baseline, with sponsor agreement.
    What is change management?Helping people adopt new ways of working via communication, training, involvement and reinforcement (ADKAR).

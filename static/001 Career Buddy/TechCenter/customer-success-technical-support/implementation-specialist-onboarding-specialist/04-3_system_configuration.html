    Module 01 · What Is What

    What System Configuration Is

    Start from the basics: configuration vs customisation vs development, the types of settings you'll configure, configuration workbooks, and sandbox vs production environments.

    ⚙️ What Is System Configuration?

    System configuration means setting up a SaaS platform for a specific customer using its built-in options, without writing code: settings, users and permissions, login (SSO), fields, workflows and integrations.

    ⚖️ Configuration vs Customisation vs Development

    ConfigurationCustomisationCustom development
    HowBuilt-in settings and admin screensAdvanced options, scripts, custom objectsWriting code via APIs/SDKs
    WhoImplementation specialist / adminSenior admin / consultantDevelopers
    Upgrade riskLowMediumHigher
    ExampleBusiness hours, roles, SSOCustom fields, complex workflowsCustom integration service
    💡
    Prefer configuration first: it's faster, cheaper and survives product upgrades.

    🗂️ Types of Configuration

    AreaExamples
    Account/org settingsCompany name, branding, timezone, currency, language, business hours
    Data modelCustom fields, picklists, forms, layouts
    Users & accessRoles, permissions, teams/groups
    AuthenticationPassword policy, MFA, SSO
    AutomationWorkflow rules, triggers, SLAs, notifications
    TemplatesEmail templates, macros, document templates
    IntegrationsNative connectors, Zapier, webhooks, APIs

    📒 Configuration Workbooks

    A configuration workbook (or design document) records every decision: what to configure, values, and who approved it. It's used to build, test and hand over.

    🧪 Sandbox vs Production

    Sandbox / testProduction
    PurposeBuild and test safelyReal users and data
    DataSample/anonymisedReal
    ChangesExperiment freelyControlled, approved, logged
    WhoImplementation teamEnd users
    ⚠️
    Test risky changes (SSO, automation rules, permissions) in a sandbox first; a wrong SSO setting can lock everyone out.

    MistakeWhy it hurtsDo this instead
    Configuring without documented decisionsDisputes, hard handoverConfiguration workbook
    Custom code for things settings can doCost, upgrade riskConfiguration first
    Testing in productionUsers affectedSandbox first

    Module 02 · Settings

    Configuring Platform Settings

    The settings almost every SaaS platform needs: organisation details, localisation, business hours, fields and forms, automation rules, notifications and templates.

    🏢 Organisation & Localisation

    SettingWhy it matters
    TimezoneTimestamps, SLAs, reports, scheduled jobs
    Business hours & holidaysSLA clocks, routing
    CurrencyAmounts, reports
    Language/localeUI language, date and number formats
    BrandingLogo, colours, email sender name, custom domain
    Data residency/regionWhere data is stored (compliance)
    📌
    Multi-country customers may need multiple business-hour schedules (e.g., India and UK teams).

    🧾 Fields, Picklists & Forms

    ElementTips
    Custom fieldsOnly add fields someone will use or report on
    Field typesText, number, date, picklist, checkbox, lookup
    PicklistsControlled values improve reporting
    Required fieldsUse sparingly: at create or at close
    Forms/layoutsShow the right fields to the right users
    Conditional fieldsShow field B only when field A = X

    ⚡ Automation Rules

    example rulesWHEN ticket created AND subject contains "refund"   → assign group Billing, priority High
WHEN deal stage = Closed Won                           → create onboarding task for CSM
WHEN status = Pending for 5 days                       → send reminder, then close at 7 days
WHEN field "Region" = South                            → notify South team channel
    💡
    Keep rules few, named clearly ("[Routing] Refund → Billing"), ordered from specific to general, and documented in the workbook.

    🔔 Notifications & Templates

    • Customer-facing emails: welcome, ticket received, password reset, invoices.
    • Internal notifications: assignment, SLA warnings, mentions.
    • Use placeholders ({{customer.name}}), consistent tone and branding.
    • Avoid notification overload; users mute noisy systems.

    ✅ Configuration Best Practices

    • Start from vendor best-practice templates.
    • Configure in sandbox; promote to production in a controlled way.
    • Name things consistently.
    • Document every decision and change.
    • Review with the customer before go-live (configuration walkthrough).

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Too many custom fieldsCluttered, unusedJustify each field
    Wrong timezoneSLA and report errorsSet org timezone first
    Overlapping automation rulesUnpredictable resultsOrder, name and test rules

    Module 03 · Access Control

    Users, Roles & Permissions

    Give every user the right access, and no more. Learn role-based access control, roles vs groups, least privilege, permission matrices, provisioning and deprovisioning.

    🔐 Authentication vs Authorisation

    🪪 Authentication (AuthN)

    Proves who you are: password, MFA, SSO.

    🔑 Authorisation (AuthZ)

    Decides what you can do: roles and permissions.

    🧩 Role-Based Access Control

    Figure 3.1 · Users → roles → permissions
    • RBAC: assign permissions to roles, then roles to users.
    • Least privilege: give only the access needed for the job.
    • Some platforms add record-level access (own records, team records, all records).

    👥 Roles, Groups & Teams

    ConceptControlsExample
    Role / profileWhat actions a user can doAgent, Team Lead, Admin
    Group / teamWhich records/queues they work onBilling team, South region
    Permission set (some tools)Extra permissions added to a role"Export data" for analysts

    📋 Permission Matrix

    PermissionAgentTeam LeadAdminRead-only (Finance)
    View own/team tickets✅ own✅ team✅ all✅ all
    Edit tickets✅ assigned✅ team✅—
    View reports—✅ team✅✅
    Export data——✅—
    Manage users——✅—
    Change settings——✅—
    Delete records——✅—
    💡
    Get the matrix approved by the customer before configuring. It's also a security document.

    🔄 Provisioning & Deprovisioning

    MethodHow
    ManualAdmin creates users in the UI
    CSV bulk importUpload user list with roles
    JIT (Just-in-Time)User created automatically at first SSO login
    SCIMIdP (Okta/Entra ID) creates, updates and deactivates users automatically
    ⚠️
    Deprovisioning (removing access when people leave) is a security must. SCIM automates it from the customer's identity provider.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Everyone is adminSecurity risk, accidental changesLeast privilege
    Per-user custom permissionsUnmanageableUse roles/permission sets
    No deprovisioning processEx-employees keep accessSCIM or offboarding checklist

    🏋️ Practice & Quick Check

    Practice
    P1.Design 4 roles for a CRM implementation and list 2 permissions each.
    Sales Rep: edit own deals, view own reports. Sales Manager: view/edit team deals, team dashboards. Admin: manage users, change settings. Finance (read-only): view closed-won deals, export revenue reports (if approved).
    Practice
    P2.Users created via SSO all get the Admin role. What went wrong and how do you fix it?

    Scenario: JIT provisioning misconfigured.

    The default role for JIT-created users is set to Admin, or role mapping from IdP attributes/groups is missing. Set default role to the least-privileged role, map IdP groups to roles, then correct existing users' roles and audit what they changed.

    Module 04 · SSO Basics

    Authentication, MFA & SSO Basics

    How users log in securely: passwords and MFA, what Single Sign-On is, identity providers vs service providers, and the protocols behind SSO (SAML, OIDC, OAuth).

    🔑 Login Methods

    MethodDescription
    Username + passwordSimplest; weakest alone
    MFA / 2FAPassword + second factor (authenticator app, SMS, security key)
    Social loginSign in with Google/Microsoft accounts
    SSOLogin via the company identity provider
    PasswordlessMagic links, passkeys

    🎟️ What Is SSO?

    Single Sign-On (SSO) lets users log in once with their company identity (e.g., Okta, Microsoft Entra ID, Google Workspace) and access many apps without separate passwords.

    Figure 4.1 · SP-initiated SAML SSO flow

    🏛️ IdP vs SP

    Identity Provider (IdP)Service Provider (SP)
    RoleAuthenticates usersThe app users want to access
    ExamplesOkta, Microsoft Entra ID (Azure AD), Google Workspace, OneLogin, PingYour SaaS platform, Salesforce, Zendesk
    OwnsUser directory, MFA, policiesApp permissions and data

    SP-initiated

    User opens the app → redirected to IdP → back to app.

    IdP-initiated

    User clicks the app tile in the Okta dashboard → signed into the app.

    📜 SSO Protocols

    ProtocolFormatTypical use
    SAML 2.0XML assertionsEnterprise SSO for web apps (very common)
    OpenID Connect (OIDC)JSON tokens (JWT), built on OAuth 2.0Modern web/mobile SSO
    OAuth 2.0Access tokensAuthorisation for APIs ("allow app X to access your data"), not login by itself
    SCIMREST/JSONUser provisioning (not login)
    📌
    Interview tip: SAML and OIDC are for authentication (SSO); OAuth is for authorisation; SCIM is for provisioning.

    ⚖️ Benefits & Risks

    ✅ Benefits

    • One login, fewer passwords
    • Central MFA and security policies
    • Instant access removal when people leave
    • Fewer password-reset tickets

    ⚠️ Risks

    • IdP outage blocks all apps
    • Misconfiguration locks users out
    • Need break-glass admin access
    ⚠️
    Always keep at least one break-glass admin who can log in without SSO, in case SSO breaks.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Enforcing SSO before testingEveryone locked outTest with pilot users first
    No break-glass accountNo recovery pathKeep a non-SSO admin
    Confusing OAuth with SSOWrong designUse SAML/OIDC for login

    🏋️ Practice & Quick Check

    Practice

    Module 05 · SSO Setup

    Configuring SAML SSO with Okta

    Step-by-step SAML setup: the values you exchange with the customer's IT team, creating an Okta app integration, attribute mapping, JIT and SCIM, testing, and troubleshooting common errors.

    📖 Key SAML Terms

    TermMeaning
    Entity ID / Audience URIUnique identifier of the SP (and of the IdP)
    ACS URLAssertion Consumer Service URL: where the IdP posts the SAML response
    SSO URLIdP login URL the SP redirects to
    X.509 certificateIdP's public certificate used to verify the signature
    NameIDUser identifier in the assertion (usually email)
    AttributesExtra user data: firstName, lastName, groups/roles
    Metadata XMLFile containing all the above, for quick setup

    🔁 Values to Exchange

    From your platform (SP) → customer IT

    • ACS URL
    • SP Entity ID / Audience URI
    • Required NameID format (email)
    • Attribute names expected

    From customer IdP (Okta) → your platform

    • IdP SSO URL
    • IdP Entity ID / Issuer
    • X.509 signing certificate
    • (or a single metadata URL/XML)

    🛠️ Okta Setup Steps

    1. In Okta Admin: Applications → Create App Integration → SAML 2.0 (or use the app from the Okta Integration Network if available).
    2. Enter Single sign-on URL (ACS URL) and Audience URI (SP Entity ID) from your platform.
    3. Set Name ID format = EmailAddress; Application username = Email.
    4. Add attribute statements (firstName, lastName, email) and optional group attribute.
    5. Finish, then copy the IdP metadata URL (or SSO URL, issuer, certificate).
    6. In your platform's SSO settings, paste the IdP values; save (don't enforce yet).
    7. Assign test users/groups to the app in Okta.
    8. Test login; then enforce SSO for everyone (keeping a break-glass admin).
    📌
    Menu names can differ slightly between Okta versions; the values exchanged are always the same.

    👥 Attributes, JIT & SCIM

    FeatureWhat it doesWatch out
    Attribute mappingPasses names, email, department, groupsAttribute names must match exactly (case-sensitive)
    Group → role mappingOkta group "Support-Leads" → Team Lead roleDefault role should be least privilege
    JIT provisioningCreates user at first loginDoesn't deactivate leavers
    SCIM provisioningCreate/update/deactivate users from Okta automaticallyNeeds SCIM endpoint + API token

    ✅ Testing & Rollout

    SSO test plan☐ Test user in each role logs in (SP-initiated and IdP tile)
☐ New user created via JIT/SCIM with correct role
☐ User removed from Okta group → access removed (SCIM)
☐ MFA prompt follows Okta policy
☐ Mobile app / API access still works as designed
☐ Break-glass admin can log in without SSO
☐ Communicate rollout date and login instructions to users

    🧯 Troubleshooting SAML Errors

    ErrorLikely causeFix
    "User is not assigned to this application" (Okta)User/group not assignedAssign in Okta
    Invalid signature / certificate errorWrong or rotated certificateUpload current IdP certificate
    Audience/Entity ID mismatchTypo or wrong valueMatch Audience URI exactly
    ACS / Recipient mismatchWrong ACS URLCorrect ACS URL in IdP
    Assertion expired / clock skewServer clocks out of syncSync time (NTP); check validity window
    User not foundNameID ≠ user email in app, JIT offAlign NameID or enable JIT
    💡
    Browser extensions like SAML-tracer show the SAML response so you can read NameID, attributes, audience and timestamps.

    Third-Party Integrations with Zapier

    Zapier connects thousands of apps without code. Learn integration types, triggers and actions, multi-step Zaps, filters and formatting, task limits, and error handling.

    TypeDescriptionExample

    ⚡ Zapier Basics

    TermMeaning
    ZapAn automated workflow
    TriggerEvent that starts it ("New form submission")
    ActionWhat happens next ("Create contact")
    TaskEach successful action counts as a task (affects plan limits)
    FilterContinue only if conditions are met
    PathsIf/else branches
    FormatterTransform text, dates, numbers
    Webhooks by ZapierCatch or send custom webhooks
    Figure 6.1 · A multi-step Zap

    🛠️ Building a Zap

    1. Choose the trigger app and event; connect the account.
    2. Test the trigger to pull sample data.
    3. Add filters/formatter steps if needed.
    4. Choose the action app and event; map fields from the trigger data.
    5. Test the action with sample data.
    6. Name the Zap clearly, turn it on, and document it.
    field mapping in a ZapTrigger: Typeform "New Entry"
Action:  SaaS app "Create User"
  Email      ← {{Typeform: Work email}}
  First name ← {{Formatter: Split name → first}}
  Role       ← "Agent" (static)
  Team       ← {{Typeform: Department}}

    🔀 Filters, Paths & Formatter

    FeatureExample
    FilterOnly create Jira issue if priority = High
    PathsIf region = India → Team A; else Team B
    Formatter: textLowercase emails, split full names
    Formatter: datesConvert to ISO / add days
    DelayWait 1 day before sending follow-up
    Lookup tableMap "Gold" → "Enterprise"

    📈 Limits, Errors & Monitoring

    • Plans limit tasks per month and how often polling triggers check (faster with higher plans; instant for webhook-based triggers).
    • Zap history shows each run, data in/out, and errors.
    • Turn on error notifications; set up autoreplay where available.
    • Use a shared/service account for connections, not a person who may leave.
    ⚠️
    If the connected account belongs to an employee who leaves, the Zap breaks. Use an integration/service user.

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    Personal account connectionsBreaks when person leavesService account
    No filtersRuns on every event, wastes tasksFilter early
    Undocumented ZapsNobody knows what runsName + document + owner
    Duplicate creation on retriesDuplicate recordsUse "find or create" steps

    Module 07 · Integrations II

    Webhooks & API-Based Integrations

    Webhooks push real-time events between systems. Learn how they work, payloads, setup, security with signatures, retries, testing, and how they compare with polling and Zapier.

    🔔 What Is a Webhook?

    A webhook is an HTTP request (usually POST with JSON) that one system sends to a URL you provide when an event happens, e.g., "ticket.created" or "payment.succeeded".

    webhook payload (example)POST https://hooks.acme.com/onboarding
Content-Type: application/json
X-Signature: sha256=9f1c…

{
  "event": "user.created",
  "id": "evt_8812",
  "created_at": "2026-10-05T09:41:17Z",
  "data": {"user_id": "usr_501", "email": "priya@acme.com", "role": "agent"}
}

    ⚖️ Webhook vs Polling

    Webhook (push)Polling (pull)
    HowSource sends data when events happenClient asks repeatedly "anything new?"
    SpeedReal-timeDelayed by poll interval
    EfficiencyEfficientMany empty requests
    ComplexityNeeds a reachable endpointSimpler client logic
    ZapierWebhooks/API direct
    SkillsNo-codeTechnical
    Speed to buildMinutesHours–days
    FlexibilityLimited to connectorsFull control
    CostPer-task plansEngineering time

    🛠️ Setting Up a Webhook

    1. Customer provides an HTTPS endpoint URL that can receive POSTs.
    2. In the platform settings, add the URL and choose events to subscribe to.
    3. Copy the signing secret; share it securely with the customer's developers.
    4. Send a test event; confirm the endpoint returns 2xx quickly.
    5. Monitor delivery logs after go-live.

    🔐 Security: Signatures & Secrets

    • Use HTTPS only.
    • Verify the HMAC signature header using the shared secret and the raw request body.
    • Check timestamps to prevent replay attacks.
    • Optionally allowlist the sender's IP ranges.
    • Rotate secrets periodically and when exposed.

    🔁 Retries, Testing & Troubleshooting

    TopicDetail
    RetriesSenders usually retry failed deliveries with backoff (e.g., for up to 24–72 h)
    IdempotencyReceivers should dedupe by event ID (retries can resend)
    Fast responseReturn 2xx quickly; process asynchronously
    Testing toolsRequest inspectors (e.g., webhook.site), Zapier "Catch Hook", Postman/cURL to replay
    Delivery logsStatus codes, response times, payloads per attempt
    SymptomCause
    Timeouts / 504Endpoint too slow
    401/403Auth/IP allowlist blocks sender
    Signature mismatchWrong secret or body altered before verification
    DuplicatesRetries not deduplicated

    🚫 Common Mistakes

    MistakeWhy it hurtsDo this instead
    No signature verificationSpoofed requestsVerify HMAC
    Heavy processing before respondingTimeouts and retriesQueue then respond 2xx
    Not handling duplicatesDouble recordsDedupe by event ID

    🏋️ Practice & Quick Check

    Practice
    P1.A customer's webhook endpoint receives each event 3 times. Explain why and the fix.

    Scenario: Duplicate webhook processing.

    Their endpoint probably responds slowly or with errors, so the sender retries; each retry is processed as new. Fix: respond 2xx immediately and process asynchronously, and deduplicate by event ID (idempotency).
    Practice
    P2.When would you recommend Zapier vs direct webhooks?
    Zapier: quick, no-code connections between supported apps with moderate volume and simple logic. Direct webhooks/API: high volume, real-time, custom logic or security requirements, with developer resources available.

    Module 08 · Real-World Workflow

    Configuration Testing, Documentation & Real-World Scenarios

    How to test configuration end to end, document it for handover, control changes after go-live, and handle common real-world configuration situations.

    🧪 Configuration Testing

    Test typeExample
    Unit (per setting)Business hours apply to SLA
    Role-basedLog in as each role; check what they can see/do
    End-to-end workflowTicket created → routed → SLA → notification → closed
    IntegrationZap/webhook fires and data arrives correctly
    UATCustomer tests real scenarios and signs off

    📒 Documentation for Handover

    • Final configuration workbook (settings, fields, rules).
    • Permission matrix and role mapping.
    • SSO details (IdP, attributes, break-glass admin) without secrets in plain text.
    • Integration inventory: name, purpose, trigger, owner, connected account.
    • Known limitations and phase-2 items.

    🔄 Change Control After Go-live

    • Changes requested via a ticket/form with reason and approver.
    • Test in sandbox first; schedule production changes.
    • Log every change (date, who, what, why).
    • Communicate user-facing changes.

    🔒 Scenario: Locked Out After SSO

    • SSO enforced; certificate wrong → nobody can log in.
    • Use break-glass admin to log in, disable enforcement, fix certificate, re-test with pilot users.
    • Lesson: test before enforcing; keep break-glass access.

    👁️ Scenario: Wrong Data Visibility

    • Agents can see salary fields in HR records.
    • Fix field-level/role permissions immediately; audit who accessed data.
    • Review the permission matrix with the customer; inform security/privacy contacts per policy.

    🏋️ Practice & Quick Check

    Module 09 · Interviews

    Interview Preparation: System Configuration

    Interview questions on platform configuration, permissions, SSO (SAML/Okta) and integrations (Zapier, webhooks), with model answers, comparisons, common mistakes and scenarios.

    🎤 Concept Questions

    QuestionModel answer
    Configuration vs customisation?Configuration uses built-in settings without code; customisation/development adds code or advanced custom logic.
    How do you design permissions?RBAC with least privilege; permission matrix approved by the customer; roles not per-user rules.
    Explain SSO and SAML.Users log in through the company IdP; SAML passes a signed XML assertion from IdP to SP.
    What do you exchange for SAML setup?SP gives ACS URL and Entity ID; IdP gives SSO URL, issuer and certificate (or metadata).
    JIT vs SCIM?JIT creates users at first login; SCIM creates, updates and deactivates users automatically from the IdP.
    Zapier vs webhooks?Zapier: no-code connectors and logic; webhooks: real-time HTTP events requiring an endpoint, often developer-built.
    How do you secure webhooks?HTTPS, HMAC signature verification, timestamp checks, IP allowlists, secret rotation.

    Scripting & Automation for CSEs

    Why a Customer Success Engineer writes scripts, how to choose the language, and when NOT to script.

    🔌 Scripts Bridge Product Gaps

    No product covers every customer workflow. A script is a small, purpose-built program that fills the gap: importing 5,000 users from a spreadsheet, producing a weekly usage report, cleaning stale records, or moving data between your product and the client's tools. Automation means the script runs reliably without a person pressing the buttons.

    🧴
    Analogy: an adapter plug when you travel. The socket (the client's system) and the plug (your product) do not match, so you carry a small adapter instead of rebuilding the wall.
    Typical gapScript solutionTime saved
    Bulk create 5,000 usersPython reads CSV, calls the users APIDays to minutes
    Weekly executive reportNode script queries API, posts to Slack1 hour per week
    Find accounts with failing webhooksBash + curl + jq over the APIInstant daily check
    Clean old test dataPython with dry-run and confirmationSafe bulk cleanup

    🧰 Choosing the Language

    LanguageStrengthsChoose it when
    BashGlue for command-line tools, files, cronShort tasks chaining curl, jq, grep, scp
    PythonReadable, rich libraries (requests, csv, pandas)Data handling, APIs, anything with logic
    JavaScript / Node.jsAsync I/O, same language as many SDKs and webhooksWebhook receivers, SDK-based tools, client already uses JS
    💡
    Use the language the client's team can maintain. A perfect script nobody can read becomes your support burden forever.

    🛑 When Not to Script

    1. The product already has the feature (check docs and roadmap first).
    2. The job is one-off and tiny: do it manually and carefully.
    3. The script would run unsupervised against production data with no safety net.
    4. It needs a permanent custom service: that is an engineering project, not a quick script.
    5. Security or compliance rules forbid extracting the data.

    Good CSEs ask: should this be a script, a configuration, a product request, or a proper integration? A script is the right answer when it is small, repeatable and safe.

    🏋️ Practice & Quick Check

    Practice
    P1.A client wants a nightly sync of 2 million records with complex rules and 99.99% uptime. Why is a quick script the wrong tool?
    It is a permanent, high-volume, high-availability workload: needs proper architecture, monitoring, scaling and ownership, i.e. an integration project, not an ad-hoc script.

    Bash: Command-Line Glue

    The shell is the fastest way to combine existing tools. Learn the safe patterns that stop small scripts from causing big accidents.

    🧱 Core Building Blocks

    ConceptExampleMeaning

    Redirectcmd > out.txt 2>&1Send stdout and stderr to a file
    VariableNAME="acme"; echo "$NAME"Always quote variables
    Exit codecmd; echo $?0 = success, non-zero = failure
    Loopfor f in *.csv; do ...; doneRepeat for each file
    Command substitutionTODAY=$(date -u +%F)Capture command output

    🛡️ A Safe Script Template

    bash#!/usr/bin/env bash
set -euo pipefail                 # stop on error, undefined variable, or failed pipe stage
IFS=$'\n\t'                       # safer word splitting
trap 'echo "FAILED at line $LINENO" >&2' ERR

: "${API_TOKEN:?API_TOKEN is required}"     # fail early if a secret is missing
: "${API_BASE:=https://api.example.com}"    # default value

echo "[$(date -u +%FT%TZ)] starting export" >&2
curl -fsS -H "Authorization: Bearer $API_TOKEN" "$API_BASE/v2/orders?limit=100" -o orders.json
echo "done: $(jq '.items | length' orders.json) orders" >&2

    Line by line: -e exits on the first failing command, -u treats unset variables as errors (catching typos), -o pipefail makes a pipeline fail if any stage fails. trap ... ERR reports where it died. curl -f turns HTTP 4xx/5xx into a failure and -sS hides the progress bar but still shows errors. Messages go to stderr (>&2) so they do not pollute data output.

    ⚠️
    Quote every variable ("$FILE"). An unquoted rm -rf $DIR/* with an empty $DIR becomes rm -rf /*.

    🔍 Text Pipelines with grep, awk and jq

    bash# Count errors per endpoint from an access log
grep ' 500 ' access.log | awk '{print $7}' | sort | uniq -c | sort -nr | head

# List open tickets as CSV from a JSON API response
curl -fsS -H "Authorization: Bearer $API_TOKEN" "$API_BASE/tickets" \
  | jq -r '.items[] | select(.status=="open") | [.id, .priority, .title] | @csv'

    The first pipeline filters lines, extracts the 7th column (the URL), counts duplicates and ranks them. The second uses jq, a JSON query tool: select filters items, the array picks fields, and @csv formats them. Reading pipelines left to right as a series of small transformations is the key skill.

    🏋️ Practice & Quick Check

    Practice
    P1.What do the three flags in set -euo pipefail do?
    -e exits when a command fails, -u errors on unset variables, -o pipefail makes a pipeline fail if any command in it fails, so errors are not hidden.

    📄 Example: Export Open Tickets to CSV

    pythonimport argparse, csv, logging, os, sys
import requests

BASE = os.environ.get("API_BASE", "https://api.example.com")
TOKEN = os.environ["API_TOKEN"]                       # fail fast if missing
log = logging.getLogger("export")

def fetch_all(path, params=None):
    params = dict(params or {}, limit=100)
    while True:
        r = requests.get(f"{BASE}{path}", params=params, timeout=15,
                         headers={"Authorization": f"Bearer {TOKEN}"})
        r.raise_for_status()                          # raise on 4xx/5xx
        body = r.json()
        yield from body["items"]
        if not body.get("next_cursor"):
            return
        params["cursor"] = body["next_cursor"]

def main():
    ap = argparse.ArgumentParser(description="Export open tickets")
    ap.add_argument("--out", default="tickets.csv")
    args = ap.parse_args()
    logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
    n = 0
    with open(args.out, "w", newline="", encoding="utf-8") as f:
        w = csv.DictWriter(f, fieldnames=["id", "priority", "title"])
        w.writeheader()
        for t in fetch_all("/tickets", {"status": "open"}):
            w.writerow({k: t.get(k, "") for k in ("id", "priority", "title")}); n += 1
    log.info("wrote %d tickets to %s", n, args.out)

if __name__ == "__main__":
    main()

    Notice the patterns: configuration comes from environment variables, a generator (yield from) hides pagination from the caller, raise_for_status() turns HTTP errors into exceptions, newline="" and encoding="utf-8" avoid blank rows and garbled characters in CSV, and if __name__ == "__main__" lets the file be both a script and importable code.

    Module 04 · Node.js

    JavaScript / Node.js for Automation

    Async by nature and the language of most SDKs and webhook handlers. Know the patterns and the pitfalls.

    ⚡ Async/Await Basics

    javascriptrequire('dotenv').config();                       // load .env into process.env
const BASE = process.env.API_BASE;
const TOKEN = process.env.API_TOKEN;

async function getJson(path) {
  const res = await fetch(`${BASE}${path}`, { headers: { Authorization: `Bearer ${TOKEN}` } });
  if (!res.ok) throw new Error(`${res.status} ${await res.text()}`);
  return res.json();
}

(async () => {
  try {
    const user = await getJson('/v2/users/42');       // wait for the result
    console.log(user.email);
  } catch (err) {
    console.error('failed:', err.message);
    process.exit(1);                                  // non-zero exit so schedulers notice
  }
})();

    fetch returns a Promise; await pauses until it resolves. Forgetting await gives you a pending Promise instead of data. fetch does not throw on HTTP errors, so you must check res.ok yourself.

    🧴
    Analogy: ordering at a counter and waiting for your number to be called. A Promise is the ticket; await is standing there until it is your turn.

    🚦 Controlling Concurrency

    javascriptconst pLimit = require('p-limit');
const limit = pLimit(5);                              // at most 5 requests at once

const ids = [101, 102, 103 /* ... thousands ... */];
const results = await Promise.allSettled(
  ids.map(id => limit(() => updateUser(id)))
);
const failed = results.filter(r => r.status === 'rejected');
console.log(`ok=${results.length - failed.length} failed=${failed.length}`);

    Promise.all on thousands of calls fires them all at once and triggers rate limits (HTTP 429). A limiter caps parallelism. Promise.allSettled waits for everything and reports each outcome, so one failure does not hide the other 999 results.

    ⚖️ Python or Node?

    PythonNode.js
    Data and CSV workExcellentGood
    Async APIs and webhooksGood (asyncio)Excellent, native
    Official SDK available?Check the product's SDK listCheck the product's SDK list
    Install on clients' machinesOften preinstalled on Linux/macOSNeeds Node runtime
    💡
    Pick based on the vendor SDK and the client's skills, not language preference.

    🏋️ Practice & Quick Check

    Practice
    P1.A Node script fires 5,000 fetch calls with Promise.all and gets many 429 errors. What is the fix?
    Limit concurrency (for example p-limit set to 5), respect Retry-After, add retries with backoff, and use Promise.allSettled so failures are reported without hiding successes.

    Module 05 · APIs

    Robust API Calls: Auth, Pagination and Limits

    Almost every automation is an API client. Make it polite, resilient and correct.

    🔑 Auth and Headers

    bashcurl -fsS -X POST "$API_BASE/v2/users" \
  -H "Authorization: Bearer $API_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: import-row-1042" \
  -d '{"email":"asha@example.com","role":"viewer"}'

    Three headers do most of the work: Authorization proves who you are, Content-Type tells the server how to parse the body, and Idempotency-Key lets you safely retry a create without producing a duplicate.

    📑 Pagination, Limits and Status Codes

    SituationWhat the API saysWhat your script does
    More data than one pagenext_cursor or Link headerLoop until there is no next page
    Too many requests429 + Retry-AfterWait that long, then retry
    Server hiccup500, 502, 503, 504Retry with exponential backoff and jitter
    Bad input400, 422Do not retry; log the row and continue
    Expired or wrong token401Refresh token once, else stop
    No permission403Stop and report scopes needed
    Not found404Skip or report depending on the task
    🧴
    Analogy: a queue at a busy counter. If the clerk says 'come back in two minutes' (Retry-After), you do exactly that rather than shouting louder.

    🧪 Retry Wrapper

    pythonimport random, time, requests
RETRY = {429, 500, 502, 503, 504}

def request_with_retry(method, url, attempts=5, **kw):
    for i in range(attempts):
        try:
            r = requests.request(method, url, timeout=15, **kw)
        except (requests.ConnectionError, requests.Timeout):
            r = None                                   # network trouble: treat as retryable
        if r is not None and r.status_code not in RETRY:
            return r
        delay = min(60, 2 ** i) + random.random()
        if r is not None and "Retry-After" in r.headers:
            delay = float(r.headers["Retry-After"])
        time.sleep(delay)
    raise RuntimeError(f"giving up on {url}")
    📌
    Only retry safe operations: GETs, or POSTs protected by an idempotency key. Blindly retrying a non-idempotent POST can create duplicates.

    🏋️ Practice & Quick Check

    Practice
    P1.Your script receives HTTP 422 for 3 of 1,000 rows. What should it do?
    Do not retry (the data is invalid). Log the failing row and error message, write it to a rejects file, continue with the remaining rows, and report the count at the end.

    Transforming and Validating Data

    Real data is messy. Scripts earn their value by cleaning it and by refusing to push bad data into a customer's system.

    🧹 Common Data Problems

    ProblemExampleHandling
    Encoding'José' appears as 'JosÃ©'Read and write UTF-8 explicitly; handle BOM with utf-8-sig
    Whitespace and case' Asha@Example.COM 'strip() and lower() before matching
    Dates and time zones'03/04/2026' (March or April?)Agree a format; store UTC ISO 8601
    DuplicatesSame email twiceDedupe on a normalised key
    Missing valuesEmpty phoneDefine required vs optional
    Number formats'1.234,50' vs '1,234.50'Parse with locale rules

    ✅ Validate, Transform, Reject

    pythonimport csv, re
EMAIL = re.compile(r"^[^@\s]+@[^@\s]+\.[^@\s]+$")

good, rejects, seen = [], [], set()
with open("users.csv", newline="", encoding="utf-8-sig") as f:
    for line_no, row in enumerate(csv.DictReader(f), start=2):      # row 1 is the header
        email = row["email"].strip().lower()
        if not EMAIL.match(email):
            rejects.append({**row, "error": "invalid email", "line": line_no}); continue
        if email in seen:
            rejects.append({**row, "error": "duplicate", "line": line_no}); continue
        seen.add(email)
        good.append({"email": email, "name": row["name"].strip().title()})

print(f"valid={len(good)} rejected={len(rejects)}")   # always show counts

    The pattern is validate, transform, reject with a reason. Rejected rows are saved with a line number and error, so the client can fix the spreadsheet instead of asking 'why did some users not import?'. utf-8-sig strips the invisible BOM Excel adds to CSV files.

    🧴
    Analogy: a quality check on a factory line. Good items continue, defective ones go into a labelled bin with the reason written on them.

    Module 07 · Scheduling

    Running Scripts Automatically

    A script only becomes automation when it runs on its own, never twice at once, and tells someone when it fails.

    ⏰ Cron Basics

    cron is the classic Unix scheduler. Each line has five time fields followed by the command.

    cron# ┌ minute (0-59)
# │ ┌ hour (0-23)
# │ │ ┌ day of month (1-31)
# │ │ │ ┌ month (1-12)
# │ │ │ │ ┌ day of week (0-6, Sun=0)
  */15 * * * *   /opt/sync/run.sh          # every 15 minutes
  0 2 * * 1-5    /opt/sync/nightly.sh      # 02:00 on weekdays
  30 6 1 * *     /opt/sync/monthly.sh      # 06:30 on the 1st of each month
    🧴
    Analogy: an alarm clock with a repeat pattern. You describe when it rings; it does not care how long the task takes.

    🔒 Avoid Overlaps and Silent Failures

    cron# flock -n skips the run if the previous one still holds the lock
*/5 * * * * flock -n /tmp/sync.lock /opt/sync/run.sh >> /var/log/sync.log 2>&1 || /opt/sync/alert.sh
    1. Prevent overlap with a lock (flock) so two runs never process the same data.
    2. Use UTC on servers to avoid daylight-saving surprises, or document the zone clearly.
    3. Send output to a log file and make failures alert someone (non-zero exit, message to chat or email).
    4. Add a heartbeat check (a monitoring service expects a ping every run); no ping means an alert.
    5. Make runs idempotent so a retry or double run is harmless.

    ☁️ Other Ways to Schedule

    OptionBest forNotes
    cron / systemd timersSingle server tasksSimple; you maintain the host
    GitHub Actions scheduleScripts stored in Git, light jobsCron syntax in UTC; limited runtime
    AWS Lambda + EventBridge / Cloud FunctionsServerless, event-driven jobsNo server; watch time and memory limits
    Airflow / PrefectMulti-step pipelines with dependenciesMore setup, strong monitoring
    Kubernetes CronJobTeams already on KubernetesSet concurrencyPolicy: Forbid

    🏋️ Practice & Quick Check

    Practice
    P1.A cron job runs every 5 minutes but sometimes takes 8 minutes. What problem arises and how do you prevent it?
    Runs overlap and may process the same data twice or fight over resources. Use a lock (flock or a distributed lock), make the job idempotent, and consider a longer interval or a queue.

    Module 08 · Safety

    Writing Scripts That Cannot Do Much Damage

    Scripts act on real customer data at machine speed. Build in brakes before you press run.

    🧯 Dry-Run First

    pythonap.add_argument("--apply", action="store_true", help="actually make changes (default: dry-run)")
...
for acct in stale_accounts:
    if args.apply:
        client.delete_account(acct["id"])
        log.info("DELETED %s", acct["id"])
    else:
        log.info("[dry-run] would delete %s (last login %s)", acct["id"], acct["last_login"])

    Make the safe mode the default: the script only prints what it would do unless you pass --apply. Review the list with the client, then run for real.

    🧴
    Analogy: a pilot's pre-flight checklist. You verify everything on the ground before taking off, not in the air.

    🛡️ Safety Checklist

    1. Backup or export the affected data before changing it.
    2. Canary: run on 5 records first, inspect the result, then widen.
    3. Confirm the target environment (print the host, tenant and count; require typed confirmation for destructive actions).
    4. Idempotent: running twice must not break anything.
    5. Limit blast radius: use a least-privilege token; add --limit N and --tenant options.
    6. Log every change (id, old value, new value) so you can undo.
    ⚠️
    A classic disaster: a script run against production instead of sandbox because the environment variable was left set. Always echo the target and ask for confirmation before writes.

    🧪 Testing with Mocks

    python# test_export.py (pytest)
from unittest.mock import patch, Mock
import export

def test_fetch_all_follows_cursor():
    page1 = Mock(status_code=200, json=lambda: {"items": [{"id": 1}], "next_cursor": "abc"})
    page2 = Mock(status_code=200, json=lambda: {"items": [{"id": 2}], "next_cursor": None})
    with patch("export.requests.get", side_effect=[page1, page2]):
        assert [t["id"] for t in export.fetch_all("/tickets")] == [1, 2]

    A mock replaces the real network call, so the test is fast and safe: it proves the pagination logic works without touching the customer's system. Use the vendor's sandbox for end-to-end tests.

    🏋️ Practice & Quick Check

    Practice
    P1.Why should a destructive script default to dry-run?
    A mistake then only prints a list instead of deleting data. It lets you and the client review exactly what will change before using the explicit flag to apply it.

    Module 10 · Scenarios

    Scripting Scenarios from Real Engagements

    Four realistic tasks, showing the thinking behind safe and useful automation.

    👥 Scenario: Bulk user import from a spreadsheet

    • Ask: create 5,000 users from an HR export.
    • Script: Python reads CSV (utf-8-sig), validates and de-duplicates emails, upserts with an idempotency key per row, limits concurrency, writes rejects.csv.
    • Safety: dry-run first, canary of 20 users, summary counts reconciled with the HR total.
    • Handover: README and a one-command re-run for the next batch.

    📊 Scenario: Weekly usage report to Slack

    • Node script queries the usage API for the last 7 days (UTC), computes top 10 accounts and week-on-week change, posts a formatted message through a chat webhook.
    • Scheduled by GitHub Actions every Monday 06:00 UTC; failures alert the CSE channel.
    • Lesson: handle empty weeks and API pagination, otherwise the report silently lies.

    🧹 Scenario: Cleaning stale sandbox data

    • Delete test accounts untouched for 180 days.
    • Dry-run lists 412 accounts; the client removes 12 they still use; script exports them as a backup then deletes with --apply --limit 100 per run.
    • Every deletion is logged with id and last login so it can be restored if needed.

    🚨 Scenario: Daily webhook health check

    • Bash + curl + jq fetches delivery stats per account every morning.
    • Accounts with more than 5% failures or 20+ consecutive failures are written to a report and posted to the team channel.
    • This becomes the seed of technical health monitoring: proactive outreach before the customer notices.

    Interview Prep: Scripting & Automation

    Questions you are likely to meet, with model answers.

    🎤 Concept Questions

    QuestionModel answer
    How do you make a script safe for production?Dry-run default, canary batch, backup, idempotency, least-privilege token, confirmation of target, logging of every change.
    How do you handle API rate limits?Honour 429 and Retry-After, exponential backoff with jitter, cap concurrency, batch where supported.
    Python or Bash?Bash for short command glue; Python once there is logic, data handling or error handling worth testing.
    How do you stop two runs overlapping?Lock (flock or distributed lock), idempotent processing, appropriate schedule interval.
    How do you manage secrets?Environment variables or a vault, never in code or tickets, scoped tokens, rotation.
    A script that worked for months suddenly fails. First steps?Check logs and exit code, API changes or expired credentials, rate limits, data shape changes, recent deployments, reproduce with the failing input.

    🧠 Whiteboard Task Pattern

    1. Clarify input, output, volume and failure behaviour.

    Module 01

    Technical Health Monitoring Basics

    Identify accounts with failing API calls, broken webhooks, or suboptimal configuration patterns, before the customer opens a ticket.

    🩺 What is Technical Health Monitoring?

    Technical health monitoring means watching how each customer integration behaves in production, spotting trouble early, and fixing it proactively. You look at data across accounts instead of waiting for a ticket.

    📉
    Failing API calls
    Rising error rates, auth failures, rate limits.
    🪝
    Broken webhooks
    Failed deliveries, timeouts, disabled endpoints.
    ⚙️
    Config patterns
    Polling, no backoff, outdated SDKs.
    💯
    Health score
    One number that combines the signals.

    🔁 The Monitoring Loop

    Figure 1.1 · The proactive health monitoring loop
    💡
    Compare each account to its own history. A 2% error rate is normal for one customer and a crisis for another.

    ⚖️ Reactive vs Proactive

    🔔 Reactive

    • Customer files a ticket
    • Damage already done
    • Slow to find root cause

    🔭 Proactive

    • You see the failure first
    • Fix before business impact
    • Patterns feed product advocacy

    API Health Signals

    The handful of metrics that tell you whether an account's API usage is healthy.

    📊 Key Metrics

    MetricWhat it showsWarning sign
    Error rateShare of calls that failSustained rise vs baseline
    p95 latencySpeed for the slowest 5%Sudden jump
    429 rateRate limit hitsMore than a few percent
    Auth failures (401/403)Credential or scope problemsSpike for one account
    Traffic volumeCalls per hourSudden drop or surge

    🚦 Reading the Status Mix

    PatternLikely ownerFirst move
    Mostly 4xxCustomerSample requests, find the common cause
    Mostly 5xxPlatformCheck incidents, escalate with request IDs
    Zero errors, zero trafficCustomerIntegration stopped calling
    📌
    Silence can be a failure. Zero errors with zero traffic means the client stopped calling.

    🧮 Error Rate per Account

    sqlSELECT account_id,
       COUNT(*) FILTER (WHERE status >= 400) * 100.0 / COUNT(*) AS error_pct
FROM api_requests
WHERE ts > now() - interval '1 hour'
GROUP BY account_id
HAVING COUNT(*) > 100
ORDER BY error_pct DESC;

    Module 03

    Webhook Health

    Webhooks fail silently. Delivery data is the only way to know.

    📬 Delivery Metrics

    MetricHealthyInvestigate when
    Success rateAbove 99%Drops below 95%
    Response timeUnder a few secondsClose to the timeout
    Retry countMostly 0Many events need retries

    🔍 Common Failure Causes

    SymptomCauseFix
    TimeoutsReceiver does slow work before replyingReply 200, process async
    4xx from receiverWrong URL or signature check failingVerify URL, use raw body
    TLS errorsExpired or invalid certificateRenew certificate
    Endpoint disabledToo many consecutive failuresFix, re-enable, replay

    📜 Reading a Delivery Log

    logevt_901  POST https://cust.example/hooks  504  timeout 10s  attempt 3/5
evt_902  POST https://cust.example/hooks  200  412ms     attempt 1/5
evt_903  POST https://cust.example/hooks  500  1.2s      attempt 2/5
    ✅
    After the customer fixes the endpoint, replay the missed events so no data is lost.

    Module 04

    Configuration Patterns

    Many problems are not bugs. They are integrations built in a way that will eventually fail.

    🧱 Suboptimal Patterns

    PatternWhy it hurtsRecommend
    Polling every secondBurns rate limitUse webhooks
    Retry in a tight loopTriggers 429 stormsBackoff with jitter
    Reading only page oneMissing dataFollow cursors
    Very old SDKDeprecated endpointsUpgrade
    Over-broad scopesBigger blast radiusLeast privilege

    ✅ Good vs Bad Configuration

    ❌ Fragile

    • Hard-coded keys
    • No timeouts or retries
    • One request per record

    ✔️ Resilient

    • Secrets in env or vault
    • Timeouts and backoff
    • Bulk endpoints and pagination

    🛠️ Retry Settings Example

    configretry:
  max_attempts: 5
  backoff: exponential
  base_delay_ms: 500
  jitter: true
  retry_on: [429, 500, 502, 503, 504]

    Module 05

    Dashboards and Alerts

    Turn raw metrics into a health score and alerts that people actually act on.

    💯 Account Health Score

    ComponentExample weightSource
    Error rate35%API logs
    Webhook success25%Delivery logs
    Usage trend20%Request volume
    Config hygiene20%SDK version, scopes, polling
    💡
    Show the reason behind a low score, not just the number, so the next step is obvious.

    🔔 Alert Thresholds

    AlertConditionAction
    Error spikeAbove 5% for 15 minSample failures, contact owner
    Webhook failingBelow 90% success for 1 hourCheck delivery log
    Traffic dropDown 80% vs same hour last weekAsk if the job stopped

    😴 Avoiding Alert Fatigue

    • Alert on sustained conditions, not single events.
    • Group alerts by account and cause.
    • Review and retire noisy alerts monthly.
    ⚠️
    If people mute an alert, it was not actionable. Fix the alert, do not blame the people.

    Module 06

    Proactive Outreach

    Finding the problem is half the job. Telling the customer well is the other half.

    📋 Outreach Playbook

    1. Gather evidence: request IDs, time range, error counts.
    2. Check the cause: theirs, ours, or unclear.
    3. Contact the right person: the integration owner.
    4. Offer a fix: code sample or config change.
    5. Follow up and confirm recovery.

    ✉️ Message Structure

    messageSubject: Webhook deliveries to your endpoint are failing

Hi Priya,
Since 09:10 UTC about 40% of webhook deliveries to
https://cust.example/hooks have timed out (examples: evt_901, evt_903).
Impact: order updates are delayed.
Likely cause: the handler replies after processing.
Suggested fix: return 200 first, process in a queue.
Happy to review the handler together.

    🤝 Tone

    💡
    Describe what you saw, the impact, and a next step. Never lead with blame, and never include secrets in the message.

    Module 07

    Scenarios and Interview Prep

    Two realistic monitoring cases, then the questions interviewers ask.

    📈 Scenario 1: Error Spike After an Upgrade

    1. Signal: error rate jumps from 1% to 18% for one account at 14:05.
    2. Correlate: their SDK version changed at 14:00.
    3. Diagnose: new version sends a renamed field; 400s.
    4. Fix and verify: update the payload; watch errors return to baseline.

    🔕 Scenario 2: Webhook Endpoint Disabled

    1. Signal: an account has no deliveries for 2 days.
    2. Check: endpoint auto-disabled after repeated 500s.
    3. Fix: customer repairs handler, you re-enable and replay.

    💬 Interview Questions

    How would you find at-risk integrations?

    Track error rate, webhook success, and traffic per account against its own baseline, then rank accounts by deviation and review the top ones.

    How do you avoid alert fatigue?

    Use sustained thresholds, group by cause, and retire alerts nobody acts on.

    Integration Basics

    Helping customer developers connect to your REST/GraphQL APIs, SDKs, and platform endpoints. Start here to understand what an integration is and where it breaks.

    🔌 What is Integration Support?

    Integration support is hands-on technical help for customers who are building against your product. You are not fixing your own code: you read their requests, responses, and logs to find out why the integration misbehaves, then teach the right pattern.

    🌐
    REST APIs
    Resources, HTTP verbs, status codes, auth, pagination.
    ◈
    GraphQL
    One endpoint, a typed schema, exact-field queries.
    📦
    SDKs
    Client libraries that wrap auth, retries, and parsing.
    🪝
    Webhooks
    Your platform calls the customer when events happen.

    🔄 How an Integration Works

    Every integration has two directions: the customer calls you (API requests) and you call them (webhooks).

    Figure 1.1 · Requests in, responses back, events out
    💡
    Always ask which direction is failing. "Our calls return errors" and "we stopped receiving events" are two different investigations.

    🧑‍💻 Your Role as a CSE

    ✅ You do

    • Read and replay customer requests
    • Explain the correct API pattern
    • Share working code samples
    • Escalate with a request ID and reproduction

    🚫 You don't

    • Rewrite their whole application
    • Ask for live secrets in tickets
    • Guess without a reproduction
    • Promise fixes for platform bugs

    📖 Core Vocabulary

    TermMeaning
    EndpointA URL that accepts requests, e.g. /v1/orders
    PayloadThe JSON body sent or received
    IdempotencyRepeating a request has the same effect as sending it once, which makes retries safe
    Rate limitMaximum requests allowed in a time window; exceeding it gives HTTP 429
    WebhookAn HTTP call your platform makes to a URL the customer owns

    Module 02

    REST APIs & Authentication

    Most integration tickets start with one HTTP call. Learn to read it, replay it, and explain the response.

    🧱 Anatomy of a REST Call

    curlcurl -X POST https://api.example.com/v1/orders \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 7f3a-2c91" \
  -d '{"customer_id": "c_102", "amount": 4900}'
    PartCheck this
    Method + URLRight verb? Right API version in the path?
    HeadersAuth present? Content-Type matches the body?
    BodyValid JSON, correct field names and types
    💡
    Reproduce first. Replay the exact failing request with curl. If it fails there too, the problem is the request, not their application code.

    🔑 Authentication

    MethodHow it worksCommon failure
    API keyStatic secret in a headerTest key used on the live endpoint
    OAuth 2.0Short-lived access token from a grant flowExpired token, missing scope
    JWT bearerSigned token with claimsClock skew, wrong audience
    ⚠️
    Never ask for live secrets in a ticket. Ask for the key ID or the last four characters, and have the customer rotate any key that was shared.

    🚦 Status Codes

    CodeMeaningWho acts
    200/201Success / createdNobody
    400Malformed body or paramsCustomer
    401Missing or invalid credentialsCustomer
    403Authenticated but not allowed (scope or plan)Customer or you
    404Wrong path or resource missingCustomer
    429Rate limited; wait and retryCustomer
    5xxServer-side failureYou: escalate

    🔁 Pagination, Retries & Rate Limits

    List endpoints return pages; customers who read only page one see "missing data". Retry only on 429 and 5xx, with backoff.

    fetch_all.pyimport time, requests

def fetch_all(url, headers):
    items, cursor = [], None
    while True:
        r = requests.get(url, headers=headers, params={"cursor": cursor})
        if r.status_code == 429:
            time.sleep(int(r.headers.get("Retry-After", 2)))
            continue
        r.raise_for_status()
        body = r.json()
        items += body["data"]
        cursor = body.get("next_cursor")
        if not cursor:
            return items

    Module 03

    GraphQL Integration

    One endpoint, a typed schema, and clients that ask for exactly the fields they need.

    ⚖️ GraphQL vs REST

    🌐 REST

    • Many endpoints, one per resource
    • Server decides the response shape
    • Errors use HTTP status codes

    ◈ GraphQL

    • One endpoint, typed schema
    • Client picks the exact fields
    • Errors often arrive inside HTTP 200

    ✍️ Writing a Query

    queryquery {
  order(id: "o_88") {
    id
    status
    customer { name email }
  }
}

    Only the fields you list come back. Asking for a field that is not in the schema is a validation error, not a 404.

    🧩 Mutations & Variables

    mutationmutation CreateOrder($input: OrderInput!) {
  createOrder(input: $input) { id status }
}
# variables sent separately as JSON:
{ "input": { "customerId": "c_102", "amount": 4900 } }
    📌
    Use variables instead of building query strings by hand. It avoids injection bugs and quoting mistakes.

    🚨 Reading GraphQL Errors

    response (HTTP 200){
  "data": { "order": null },
  "errors": [{ "message": "Not authorized", "path": ["order"] }]
}
    ⚠️
    A 200 OK does not mean success. Customers who only check the status code miss failures. Always inspect the errors array.

    Module 04

    SDKs & Webhooks

    The libraries customers use to avoid hand-writing HTTP, and the events your platform sends back.

    📦 Working with SDKs

    ⬆️
    Version mismatch
    An old SDK calls a deprecated endpoint. Ask for the SDK version first.
    🔐
    Config errors
    Wrong base URL or environment: the top cause of "works in sandbox".
    🪵
    Debug logging
    Most SDKs can print the raw request and response.
    sdk_example.jsconst client = new ExampleClient({
  apiKey: process.env.EXAMPLE_KEY,
  baseUrl: "https://api.example.com",
  logLevel: "debug"   // prints raw HTTP
});
const order = await client.orders.create({ customerId: "c_102", amount: 4900 });

    🪝 Webhooks

    Your platform sends a signed POST when something happens. The customer's server should verify it, reply 2xx quickly, and process the event asynchronously.

    event happens→ platform signs payload→ POST to customer URL→ verify→ 200 OK→ process async

    ✍️ Verifying Signatures

    verify.pyimport hmac, hashlib

def is_valid(raw_body: bytes, header_sig: str, secret: bytes) -> bool:
    expected = hmac.new(secret, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header_sig)
    ⚠️
    Sign the raw body. If a framework parses and re-serializes the JSON first, the signature will never match.

    📬 Delivery & Retries

    SymptomLikely cause
    Events stopped arrivingReceiver returns non-2xx or is too slow
    Same event arrives twiceRetry after a timeout; handler must be idempotent
    Events arrive out of orderRetries and parallel delivery; use event timestamps or IDs

    Module 05

    Integration Troubleshooting

    A repeatable way to work an integration ticket from the first message to root cause.

    ✅ Triage Checklist

    1. Get the exact request and full response, headers included.
    2. Confirm environment, base URL, API version, and SDK version.
    3. Replay it with curl, outside their code.
    4. Look up the request ID in your platform logs.
    5. Fix it, or escalate with the request ID and a reproduction.

    🩺 Symptom Guide

    SymptomLikely causeAsk or check
    Works in sandbox, 401 in productionSandbox key on liveWhich key and base URL?
    Intermittent 429Bursts without backoffRequest rate, Retry-After
    Data missing from listOnly first page readDo they follow next_cursor?
    Duplicate ordersRetries without idempotency keyIs Idempotency-Key sent?
    Webhook signature failsSigning a parsed bodyAre they using the raw bytes?

    🎬 Scenario Walkthrough

    Ticket: "Our integration worked for an hour, then every call returned 401."

    1. Pattern: works, then fails for all calls, which points to time-based credentials.
    2. Hypothesis: OAuth access token expired.
    3. Check: ask for the token's expires_in and whether they use the refresh token.
    4. Fix: refresh before expiry, and on a 401 refresh once and retry once.
    ✅
    You solved it by recognizing the pattern, not by reading their code. That is the core Integration Support skill.

    Module 06

    Authentication Deep Dive

    Auth is the number one source of integration tickets. Understand the OAuth flow, token lifetimes, and scopes so you can diagnose in minutes.

    🔐 OAuth 2.0 Flow

    The customer app never sees the user's password. It exchanges a one-time code for an access token, and uses a refresh token to get new ones.

    Figure 6.1 · Authorization code flow, step by step

    ⏳ Scopes & Token Lifecycle

    ConceptWhat it controlsTypical error
    ScopeWhich actions the token may perform403 "insufficient scope"
    Access tokenShort-lived credential (minutes to hours)401 after it expires
    Refresh tokenLong-lived, used only to get new access tokensinvalid_grant if revoked or reused
    Redirect URIWhere the code is sent backMust match exactly, or the flow fails

    🛡️ Security Best Practices

    • Keep secrets in environment variables or a secrets manager, never in source control.
    • Request the minimum scopes the integration needs.
    • Rotate keys on a schedule and immediately after exposure.
    • Always use HTTPS; never log full tokens.
    ⚠️
    If a customer pastes a live key into a ticket or chat, treat it as compromised: tell them to rotate it now, then continue troubleshooting with the new one.

    🪵 Request IDs & Logs

    Every response from a well-designed API includes a request ID header (for example X-Request-Id). It is the key that lets you find the exact call in your platform logs.

    Ask the customer forWhy
    Request IDFind the call in internal logs
    Timestamp with timezoneNarrow the log search
    Full response bodyError codes and messages hold the cause
    SDK / language versionRule out known bugs

    🧪 Sandbox & Mock Servers

    Use a sandbox to test without touching real data. For webhooks, a tunnel tool or a request-inspection site lets you see exactly what your platform sends.

    💡
    Build a small working sample in the customer's language. A runnable example ends more tickets than a link to documentation.

    Module 08

    Versioning & Platform Endpoints

    Platforms change. Help customers survive versions, environments, and long-running operations.

    🏷️ API Versioning

    StyleExampleWatch for
    URL path/v1/ordersOld version is retired on a date
    HeaderAPI-Version: 2025-01-01Missing header means a default version
    📌
    Before debugging any "it suddenly changed" ticket, check the changelog and deprecation notices for the customer's API version.

    🏭 Sandbox vs Production

    🧪 Sandbox

    • Separate base URL and keys
    • Test data, relaxed limits
    • Webhooks go to test URLs

    🏭 Production

    • Live keys, real data
    • Strict rate limits
    • Needs a public HTTPS webhook URL

    ⏱️ Async & Bulk Endpoints

    Long jobs (exports, imports) return 202 Accepted with a job ID. The customer must poll the job or wait for a webhook; they should not hold the connection open.

    flowPOST /v1/exports        -> 202 { "job_id": "j_55" }
GET  /v1/jobs/j_55      -> { "status": "running" }
GET  /v1/jobs/j_55      -> { "status": "done", "url": "..." }

    Module 09

    Real-World Scenarios

    Three realistic tickets, worked end to end: symptom, hypothesis, evidence, fix.

    🧾 Scenario 1: Duplicate Orders

    Ticket: "Some orders are created twice, mostly at peak time."

    1. Hypothesis: client times out, retries, and the server processed the first request.
    2. Evidence: two requests with the same body, seconds apart, different request IDs.
    3. Fix: send an Idempotency-Key per order; reuse it on retry.

    🔕 Scenario 2: Webhooks Went Silent

    Ticket: "We stopped receiving events yesterday."

    1. Check delivery log: are attempts failing with 5xx, timeouts, or TLS errors?
    2. Common cause: receiver takes too long because it processes inline.
    3. Fix: return 200 immediately, queue the work, then replay missed events.
    ✅
    Offer a replay of failed deliveries once their endpoint is healthy, so no data is lost.

    🌩️ Scenario 3: 429 Storm

    Ticket: "A nightly sync fails with 429 after a few minutes."

    1. Evidence: thousands of single-record calls in parallel.
    2. Fix: use bulk endpoints, limit concurrency, honour Retry-After, add jittered backoff.

    Module 10

    Interview Prep

    Questions Customer Success Engineer interviews commonly ask about integration support, with model answers.

    💬 Concept Questions

    What is the difference between REST and GraphQL?

    REST exposes many resource endpoints and the server shapes the response. GraphQL has one endpoint and a typed schema, and the client chooses the fields. GraphQL errors can arrive inside a 200 response.

    What is idempotency and why does it matter?

    An idempotent request has the same effect whether sent once or many times. It makes retries safe, preventing duplicate charges or orders.

    How do webhooks differ from polling?

    Webhooks push events to the customer when they happen; polling repeatedly asks for changes. Webhooks are faster and cheaper but need a reliable, verified receiver.

    🎯 Scenario Questions

    A customer says "your API is down". What do you do?

    Get the request ID, status code and timestamp. Replay with curl. Check platform status and logs. Separate their network or auth problem from a real incident, and escalate with evidence if it is ours.

    An integration worked yesterday and fails today. Why?

    Look for what changed: expired token or key, new API version or deprecation, rate limit, payload change, or a platform incident.

    🧭 How to Answer

    1. State the structure: symptom, hypothesis, evidence, fix.
    2. Name concrete tools: curl, request IDs, logs.
    3. Mention communication: update the customer, document the fix, feed patterns to product.
    💡
    Interviewers value a clear method over a lucky guess. Always show how you would prove your hypothesis.

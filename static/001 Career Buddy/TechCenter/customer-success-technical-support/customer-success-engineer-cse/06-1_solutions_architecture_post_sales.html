    Post-Sales Solutions Architecture

    How a CSE designs custom workflows, scripts and webhook automations so that your product fits a specific client's real-world ecosystem after the sale.

    🏛️ What Post-Sales Architecture Means

    Solutions architecture is the discipline of designing how separate systems work together to solve a business problem. Post-sales means the contract is signed and the customer now needs the product to work inside their world: their CRM, ERP, identity provider, data warehouse and internal tools. A CSE designs and often builds that glue.

    🧴
    Analogy: adding a new room to an existing house. The architect must respect the current plumbing, wiring and walls (the client's ecosystem) instead of drawing on an empty plot.
    Pre-sales architecturePost-sales architecture (CSE)
    GoalProve it can workMake it actually work in production
    DetailDiagrams and demosReal data, credentials, volumes, edge cases
    OutputProposal, proof of conceptWorking integration, runbook, handover
    RiskOver-promisingSilent failures, adoption gaps

    🔁 The Delivery Lifecycle

    1. Discover the client's systems, data flows and constraints.
    2. Design the target workflow and agree it in a short design document.
    3. Build scripts, webhooks and configuration in small increments.
    4. Validate with real sample data, error cases and a user acceptance test.
    5. Deploy with monitoring and a rollback plan.
    6. Hand over documentation and training, then monitor the account's health.

    📦 Typical Deliverables

    DeliverablePurposeAudience
    Solution design docAgreed scope, flow, data mapping, risksClient IT, product owner
    Architecture diagramOne-page picture of systems and arrowsEveryone
    Scripts / webhook receiverThe automation itself, in version controlClient developers, you
    RunbookHow to monitor, troubleshoot, redeployClient ops, support
    Test evidenceSample inputs, outputs, UAT sign-offClient sponsor

    Module 03 · Design

    Designing Workflows: Patterns That Work

    Choose the right interaction style, ordering and error path before writing code.

    🧭 Choosing the Interaction Style

    StyleHow it worksBest whenWatch out for
    Request/response (sync)Caller waits for the answerInstant user feedback neededTimeouts, tight coupling
    Event-driven (webhooks)System pushes events when something happensNear real-time syncDuplicates, ordering, retries
    PollingYou ask 'anything new?' on a scheduleNo webhook availableWasted calls, delay, rate limits
    Batch / scheduledProcess many records at set timesLarge volumes, nightly loadsBig failures, stale data
    🧴
    Analogy: a restaurant. A waiter waiting at your table for every dish is request/response; the kitchen ringing a bell when a dish is ready is event-driven; checking the pass every 5 minutes is polling.

    🔧 Anatomy of a Good Workflow

    workflow (pseudo-YAML)trigger:   webhook order.created from Product
validate:  required fields present, currency in [USD, EUR, INR]
transform: map product.order -> erp.sales_order (see mapping table)
act:       POST /erp/sales-orders  (idempotency key = product order id)
onSuccess: write erp_id back to product order; log success
onRetryable (429, 5xx, timeout): retry with backoff, max 5 times
onFatal (400, mapping error):   send to dead-letter queue, alert integration owner

    Every workflow has the same five parts: trigger, validate, transform, act, and an explicit error path. The error path is the part beginners skip; in production it is the part that decides whether the client trusts your solution.

    🎼 Orchestration vs Choreography

    OrchestrationChoreography
    ControlOne coordinator calls each stepEach system reacts to events on its own
    VisibilityEasy: one place to see the flowHarder: spread across systems
    CouplingCoordinator knows all stepsLoose
    Good forMulti-step business processes with rollbacksSimple notifications and fan-out
    💡
    Start simple: one trigger and one action. Add complexity only when a real requirement demands it. Every extra step is another thing that can fail at 3 am.

    🏋️ Practice & Quick Check

    Practice
    P1.Why must every workflow have an explicit error path?
    In production, failures such as timeouts, rate limits and bad data will happen. Without a defined path (retry, dead-letter, alert) records are lost silently and nobody knows until a customer complains.
    Q1.Which style fits 'tell me immediately when an order is created' best?
    • A Nightly batch
    • B Event-driven webhook
    • C Manual export
    • D Polling once a day

    Module 04 · Webhooks

    Webhooks: Anatomy, Security and Delivery

    The most common integration building block a CSE designs and supports.

    🔔 What Is a Webhook?

    A webhook is an HTTP request that a system sends to a URL you provide when an event happens. Instead of repeatedly asking, you are told.

    🧴
    Analogy: a doorbell versus checking the mailbox every five minutes. The doorbell rings only when there is something, so you react immediately and waste no effort.
    json (payload example){
  "id": "evt_8f31c2",
  "type": "order.created",
  "created_at": "2026-10-06T09:14:03Z",
  "data": { "order_id": "ord_1042", "amount": 4999, "currency": "INR" }
}

    The payload has an id (unique per event, used for de-duplication), a type (what happened), a timestamp and the data. Always design around the event id.

    🔐 Verifying the Signature

    pythonimport hmac, hashlib

def is_valid(secret: bytes, raw_body: bytes, signature_header: str) -> bool:
    expected = hmac.new(secret, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature_header)   # constant-time compare

    The sender signs the raw body with a shared secret (HMAC-SHA256) and sends the result in a header. Your receiver recomputes it and compares. If they match, the request really came from the sender and was not changed. Use the raw bytes, because re-serialising JSON changes spacing and breaks the signature, and use compare_digest to avoid timing attacks.

    ⚠️
    Also check the timestamp (reject events older than about 5 minutes) to stop replay attacks, and accept requests only over HTTPS.

    📬 Delivery Behaviour You Must Design For

    BehaviourWhat happensYour design answer
    At-least-once deliveryThe same event may arrive twiceIdempotent handling using the event id
    RetriesNon-2xx or timeout triggers resend, often with backoffReturn 2xx fast, process later
    Out-of-order deliveryUpdate may arrive before createUse timestamps or fetch latest state from the API
    BurstsBulk import sends thousands of eventsQueue and rate-limit your processing
    Endpoint downSender retries then gives up (often after hours or days)Replay tool or reconciliation job

    🏋️ Practice & Quick Check

    Practice
    P1.Why should a webhook receiver return 2xx quickly and process the event asynchronously?
    Senders time out and retry if the response is slow, causing duplicates and load. Acknowledge immediately after verifying and queuing, then process in a worker.

    Module 05 · Build

    Building a Reliable Webhook Receiver

    A production-grade receiver verifies, de-duplicates, queues and acknowledges. Code and architecture side by side.

    💻 A Minimal Receiver in Node.js

    javascriptconst express = require('express');
const crypto = require('crypto');
const app = express();

app.post('/webhooks/orders', express.raw({ type: 'application/json' }), async (req, res) => {
  const sig = req.get('X-Signature') || '';
  const expected = crypto.createHmac('sha256', process.env.WEBHOOK_SECRET)
                         .update(req.body).digest('hex');
  if (!crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected))) return res.sendStatus(401);

  const event = JSON.parse(req.body);
  if (await seen(event.id)) return res.sendStatus(200);   // duplicate: acknowledge, do nothing
  await queue.add('order-events', event);                  // hand off to a worker
  await markSeen(event.id);
  res.sendStatus(202);                                     // accepted, processing later
});

    Step by step: express.raw keeps the raw bytes for the signature; invalid signatures get 401 and are never processed; the seen check makes the handler idempotent; the event goes on a queue; and the reply is sent within milliseconds.

    🏗️ The Architecture

    flowSender --HTTPS--> API gateway --> Receiver (verify, dedupe, enqueue)
                                        |
                                        v
                                     Queue --> Worker (transform, call target API, retry)
                                        |                    |
                                        |                    +--> Dead-letter queue --> Alert + replay tool
                                        v
                                  Store: event id, status, attempts, last error
    🧴
    Analogy: a post office. The front desk accepts and stamps the parcel (receiver), sorting staff deliver it (worker), and undeliverable parcels go to a lost-and-found shelf (dead-letter queue) where someone can look at them later.

    🧪 Testing the Receiver

    bash# Send a signed test event
BODY='{"id":"evt_test1","type":"order.created","data":{"order_id":"ord_1"}}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$WEBHOOK_SECRET" | awk '{print $2}')
curl -i -X POST http://localhost:3000/webhooks/orders -H "X-Signature: $SIG" -H "Content-Type: application/json" -d "$BODY"
# Send it twice: second call must be 200 and must not create a second record

    Test three cases every time: a valid signature, an invalid signature (expect 401) and a duplicate (expect no second effect). Use tools like ngrok to receive real webhooks on your laptop during development.

    🏋️ Practice & Quick Check

    Practice
    P1.Explain what 'idempotent' means for a webhook handler and give one way to achieve it.
    Processing the same event more than once has the same effect as processing it once. Achieve it by storing each event id and skipping ids already processed, or by using an idempotency key when calling the target API.

    Integration Patterns and Data Mapping

    Moving data between systems with different shapes, IDs and rules.

    🔀 Field Mapping

    Two systems describe the same thing differently. A mapping says exactly how each source field becomes a target field, including transformations.

    Source (product)Target (ERP)TransformationNote
    order.idexternal_refCopyKeeps traceability
    order.amount (cents)totalDivide by 100Integer to decimal
    customer.emailcontact.emailLowercase, trimMatch key
    order.created_at (UTC)order_dateConvert to local dateTime zone rule agreed with client
    order.status = paidstate = CONFIRMEDLookup tableDocument unmapped statuses
    yamlmapping:
  total:        { from: order.amount, op: divide, by: 100 }
  external_ref: { from: order.id }
  state:        { from: order.status, lookup: { paid: CONFIRMED, refunded: CANCELLED }, default: REVIEW }

    🔗 Identity, Upserts and Limits

    TopicPractice
    Matching recordsStore the other system's ID (external ID) on both sides; never match on names
    Create vs updateUse upsert (update if exists, else create) keyed on external ID
    PaginationLoop through pages with cursors; never assume all data fits one response
    Rate limitsRespect 429 and Retry-After; batch where supported
    Partial failureProcess records individually; one bad record must not block 999 good ones
    💡
    Keep a sync log table: record id, source id, target id, status, error. It is the first thing you open when the client says 'order 1042 is missing'.

    ⚖️ Build vs Buy: iPaaS or Custom Code?

    iPaaS (Zapier, Make, Workato, MuleSoft)Custom scripts / service
    Speed to first versionFastSlower
    Complex logic and volumeLimited, costly at scaleFull control
    OwnershipBusiness or IT users can editNeeds developers
    MonitoringBuilt-in dashboardsYou must build it

    There is no universal answer: choose based on volume, complexity, who will maintain it, and the client's existing tools.

    Module 07 · Security

    Auth, Secrets and Compliance in Integrations

    Every integration is a door into two systems. Design it so only the right visitors get through.

    🔑 Authentication Methods

    MethodHow it worksUse for
    API keyStatic secret in a headerSimple server-to-server calls
    OAuth 2.0 client credentialsApp exchanges ID and secret for a short-lived tokenMachine-to-machine integrations
    OAuth 2.0 authorization codeUser consents, app receives a tokenActing on behalf of a user
    Basic authUsername and passwordLegacy systems only, over HTTPS
    Mutual TLS / IP allow-listCertificates or fixed addressesHigh-security environments
    bashcurl -X POST https://auth.example.com/oauth/token \
  -d grant_type=client_credentials -d client_id=$CLIENT_ID -d client_secret=$CLIENT_SECRET -d scope=orders.read
# -> {"access_token":"eyJ...","expires_in":3600}   Use it as: Authorization: Bearer <token>

    🛡️ Principles to Apply

    1. Least privilege: request only the scopes the workflow needs (read vs write).
    2. Secrets management: keep keys in a vault or environment variables, never in code or tickets.
    3. Rotate: plan for key rotation without downtime (support two active keys).
    4. Encrypt: HTTPS everywhere; verify certificates.
    5. Minimise data: send only fields needed; mask personal data in logs.
    6. Audit: log who called what, never the secret itself.
    ⚠️
    If a secret is pasted into a ticket, chat or Git commit, treat it as leaked: rotate it immediately, even if you deleted the message.

    📜 Compliance Questions to Raise Early

    TopicQuestion
    Data residencyMay data leave the client's country or region?
    Personal dataWhich fields are personal or regulated (GDPR, DPDP, HIPAA, PCI)?
    RetentionHow long may logs and queued events be stored?
    ApprovalsDoes the client's security team need to review the design?
    🧴
    Analogy: a building's security desk. Visitors need the right badge for the right floor (scopes), badges expire (tokens), and every entry is logged.

    🏋️ Practice & Quick Check

    Practice
    P1.Why is OAuth client credentials usually better than a long-lived API key shared in an email?
    Tokens are short-lived and scoped, the client secret can be rotated centrally, and access can be revoked or audited. A shared static key can leak and stay valid indefinitely.

    Module 08 · Reliability

    Making Automations Reliable

    Networks fail, APIs throttle and data is dirty. Design for it from day one.

    🔁 Retries with Backoff and Jitter

    pythonimport random, time

RETRYABLE = {429, 500, 502, 503, 504}

def call_with_retry(send, max_attempts=5):
    for attempt in range(max_attempts):
        resp = send()
        if resp.status_code not in RETRYABLE:
            return resp                            # success or a non-retryable error (400, 404)
        wait = min(60, 2 ** attempt) + random.random()   # 1s, 2s, 4s, 8s... plus jitter
        time.sleep(float(resp.headers.get('Retry-After', wait)))
    raise RuntimeError('gave up after retries')

    Exponential backoff waits longer after each failure so a struggling system can recover; jitter (a random addition) stops thousands of clients retrying at the same instant. Retry only transient errors: a 400 will fail the same way forever.

    🧴
    Analogy: a crowd leaving a stadium. If everyone rushes the gate together, nobody gets through; staggering the exits (jitter) clears it faster.

    🧯 Failure Patterns

    FailurePatternEffect
    Dependency slow or downTimeout + circuit breakerFail fast instead of hanging threads
    Duplicate deliveryIdempotency keyNo double charges or records
    Bad recordDead-letter queueOthers keep flowing
    Missed eventsReconciliation job (compare both systems daily)Self-healing drift
    Traffic burstQueue + rate limitSmooth load on target

    📈 Observability for Integrations

    1. Log every event with its id, status and timing (structured JSON).
    2. Expose metrics: events received, succeeded, retried, dead-lettered, processing lag.
    3. Alert on symptoms: dead-letter queue growing, lag over 5 minutes, error rate above 2%.
    4. Provide a dashboard and a replay tool the client can use.
    5. Run a daily reconciliation report: counts in source versus target.
    💡
    The best integrations tell you they are broken before the customer does. Alerting on a growing dead-letter queue is usually the highest-value alert you can add.

    🏋️ Practice & Quick Check

    Practice
    P1.Why add jitter to exponential backoff?
    Without jitter many clients retry at the same moments and create synchronised bursts that keep the target overloaded. Random variation spreads the retries out.
    Q1.Which error should NOT be retried automatically?
    • A 503 Service Unavailable
    • B 429 Too Many Requests
    • C 400 Bad Request (invalid data)
    • D Network timeout

    Documenting and Handing Over the Solution

    A solution nobody understands is a liability. Finish the project with documents, tests and training.

    📄 Solution Design Document

    template1. Business goal and success metrics
2. Scope: in / out
3. Architecture diagram (systems, arrows, auth, protocols)
4. Data flow and field mapping table
5. Triggers, schedules, volumes, expected latency
6. Error handling: retries, dead-letter, alerts, reconciliation
7. Security: auth, scopes, secrets, data residency
8. Environments and deployment steps; rollback plan
9. Test plan and UAT acceptance criteria
10. Ownership: who monitors, who is on call, escalation path
11. Assumptions, risks, open questions

    Keep it short (3 to 6 pages). A diagram plus a mapping table communicates more than pages of prose, and it becomes the basis of acceptance.

    ✅ UAT and Go-Live

    1. Prepare test cases from the target state: happy path, edge cases and failure cases.
    2. Run them in the client's sandbox with their real sample data and get written sign-off.
    3. Plan the cut-over: freeze window, data backfill, rollback.
    4. Go live with extra monitoring for the first days.
    5. Hold a short review after 2 weeks: volumes, errors, adoption.

    📘 Runbook for the Client's Team

    runbookSYMPTOM: Orders not appearing in ERP
1. Check dashboard 'orders-sync': events received vs processed in last hour
2. Dead-letter queue size > 0?  -> open record, read error, fix data, click Replay
3. Auth errors (401)?           -> rotate token in vault, restart worker
4. Target API 5xx/429?          -> wait; retries are automatic; escalate if > 30 min
ESCALATE: integration-owner@client.com, then CSE team (support portal, severity 2)
    📌
    Handover is complete only when the client can operate and troubleshoot the solution without you, and knows exactly when to call you.

    Module 10 · Scenarios

    Solutions Architecture Scenarios

    Four realistic post-sales engagements and the design decisions behind them.

    🛒 Scenario: Order sync from product to ERP

    • Need: every paid order must appear in the client's ERP within 2 minutes.
    • Design: webhook order.paid to a receiver, queue, worker mapping fields and calling the ERP sales-order API with the order id as idempotency key.
    • Pitfall: ERP accepts 5 requests per second; the worker rate-limits and the queue absorbs end-of-month bursts.
    • Safety net: nightly reconciliation compares order counts and re-sends missing ones.

    💬 Scenario: Ticket automation to chat

    • Notify a team channel when a high-priority ticket is created or breaches SLA.
    • Use a webhook from the ticketing system and a small script to post a formatted message through the chat tool's incoming webhook.
    • Rate limit and group alerts (digest every 5 minutes) to avoid noisy channels.

    📁 Scenario: Legacy SFTP batch to API

    • The client's old system can only drop a CSV on SFTP nightly and has no API.
    • Design: scheduled job downloads the file, validates each row, upserts through the API, writes a result file back, and sends a summary email.
    • Key decision: process rows individually, report row-level errors, move the file to an archive folder so it is never processed twice.

    🌩️ Scenario: Webhook storm during a bulk import

    • A client imports 200,000 records and the product sends 200,000 webhooks in 10 minutes. The receiver falls over and events are lost.
    • Fix: receiver only verifies and enqueues; workers scale on queue depth; backpressure and rate limiting protect the target; replay from the sender's event log fills any gap.
    • Lesson: design for the burst, not the average.

    🏋️ Practice & Quick Check

    Practice
    P1.A client asks for real-time sync, but their ERP API allows only 2 requests per second. How do you respond?
    Explain the constraint and propose a queue with rate-limited workers, giving near-real-time for normal load and controlled catch-up during bursts. Agree an acceptable maximum delay, batch where the API supports it, and add monitoring for queue lag.
    Q1.The safest way to handle a sudden burst of events is…

    • B Queue them and process at a controlled rate
    • C Drop the extras
    • D Ask the sender to stop

    Interview Prep: Solutions Architecture (Post-Sales)

    Questions you are likely to be asked, with model answers.

    🎤 Concept Questions

    QuestionModel answer
    How do you start a new integration project?Discovery: systems, data, triggers, constraints and success criteria, with real sample data; then a short design doc agreed with the client.
    Webhooks vs polling?Webhooks push events and give low latency with less waste but need security, idempotency and retry handling; polling is simpler to receive but wasteful and delayed, so use it when no webhook exists.
    How do you make an integration reliable?Idempotency, retries with backoff and jitter, dead-letter queue, reconciliation, monitoring and alerts, and a tested runbook.
    How do you secure it?Least-privilege scopes, short-lived tokens, secrets in a vault, HTTPS, signature verification and minimal personal data in logs.
    Client wants a custom feature the product lacks. What do you do?Understand the underlying need, propose a supported workaround or integration, document the gap and take it to Product as technical advocacy with the business case.
    Zapier or custom code?Depends on volume, complexity, maintainability and the client's skills; iPaaS for simple low-volume flows, code for complex or high-volume ones.

    🧠 How to Answer Scenario Questions

    1. Restate the business goal in one sentence.
    2. Ask 2 to 3 clarifying questions (volume, latency, source of truth).
    3. Sketch the flow: trigger, validate, transform, act, error path.
    4. Name the risks: duplicates, ordering, rate limits, security.
    5. Close with monitoring and handover.

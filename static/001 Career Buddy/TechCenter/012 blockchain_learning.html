    Module 01 · Foundations

    Foundations & Setup

    Understand what a blockchain actually is, install the tools you'll use throughout this course, and build the mental model of blocks chained together that everything else in this course builds on.

    ⛓️ What is Blockchain?

    A blockchain is a distributed, append-only ledger shared across many computers (called nodes), where every new entry — grouped into a block — is cryptographically linked to the one before it. No single party owns or controls it, and once a block is buried under enough later blocks, changing it becomes computationally impractical.

    🌐
    Distributed
    Thousands of independent nodes hold identical copies of the ledger — no central server to fail or bribe.
    🔒
    Immutable
    Each block's hash depends on the previous block's hash — edit one, and every later block breaks visibly.
    🤝
    Trustless
    Strangers agree on shared state through math and consensus rules, not through a trusted middleman.
    👁️
    Transparent
    On public chains, anyone can inspect every block and transaction ever recorded.

    💡 Why It Matters

    Before blockchain, moving digital value between strangers required a trusted intermediary — a bank, a payment processor, an escrow agent — to prevent double-spending (spending the same money twice). Blockchain solves this with math and network consensus instead of a middleman.

    🏦 Traditional Ledger

    One organization keeps the "official" record. You trust the bank's database is correct and hasn't been tampered with.

    • Single point of failure
    • Requires a trusted third party
    • Can be edited or reversed by the owner

    ⛓️ Blockchain Ledger

    Thousands of copies exist. The majority of the network must agree before anything is added — and nothing already added can be silently changed.

    • No single point of failure
    • Trust comes from consensus + cryptography
    • Append-only history
    📌
    Bitcoin (2009) was the first working blockchain, built to solve the double-spend problem for digital cash without a bank. Ethereum (2015) extended the idea by letting the ledger run arbitrary code — smart contracts — not just track balances.

    🧾 Your First Transaction

    Every action on a blockchain — sending funds, calling a smart contract — is submitted as a transaction. A transaction is signed with your private key and broadcast to the network for inclusion in the next block.

    Module 02 · Fundamentals

    Core Blockchain Fundamentals

    The building blocks under the hood: hashing, keys and addresses, how new blocks get created, and the two competing models chains use to track who owns what.

    #️⃣ Hashing

    A cryptographic hash function (e.g. SHA-256, Keccak-256) takes any input and produces a fixed-length "fingerprint." Change even one character of the input and the output is completely different — this is called the avalanche effect.

    conceptSHA256("hello")
= 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824

SHA256("Hello")   # just the capital H changed
= 185f8db32271fe25f561a6fc938b2e264306ec304eda518007d1764826381969
# completely different output — this is the avalanche effect
    PropertyMeaning
    DeterministicSame input always produces the same output.
    Fast to computeCheap to verify a hash matches its input.
    One-wayInfeasible to reverse the hash back into the original input.
    Collision-resistantPractically impossible to find two inputs with the same hash.
    💡
    Hashing is what secures the "chain" in blockchain — every block header includes the hash of the block before it, so any change ripples forward and becomes obvious.

    🔑 Wallets, Keys & Addresses

    A wallet doesn't actually "store" coins — it stores a private key, the secret number that proves ownership and authorizes spending. Everything else is derived from it.

    Figure 2.1 · How a wallet address is derived
    ⚠️
    Whoever holds the private key owns the funds — full stop. There's no "forgot password" reset on a blockchain. Losing your private key or seed phrase means losing access permanently.

    ⛏️ Mining & Block Creation

    In a Proof-of-Work chain, miners compete to find a nonce value that makes the block's hash fall below a target threshold — a trial-and-error process called mining. The winner broadcasts the block and earns the block reward.

    pseudocodenonce = 0
while True:
    candidate = blockHeader + nonce
    h = SHA256(SHA256(candidate))
    if h < target:        # e.g. hash must start with 18 zero bits
        return nonce          # found a valid block!
    nonce += 1
    📌
    The difficulty target automatically adjusts so blocks keep arriving at roughly a fixed rate (Bitcoin: ~10 minutes) even as more miners join the network.

    💰 Transactions & the UTXO vs Account Model

    Different chains track ownership differently. Bitcoin uses UTXOs (Unspent Transaction Outputs) — like tracking individual cash bills. Ethereum uses an account model — like a bank balance.

    🟠 UTXO Model (Bitcoin)

    Your "balance" is the sum of unspent outputs sent to your address. Spending consumes whole UTXOs and creates new ones (with change).

    • No global account balance — sum UTXOs to know it
    • Parallel-friendly; each UTXO spent once
    • Harder to build complex logic on top of

    🟣 Account Model (Ethereum)

    Every address has a running balance and a nonce (transaction count), much like a bank account ledger.

    • Simple balance lookups
    • Natural fit for smart contract state
    • Nonce must increment in order per sender

    🖧 Nodes & the Peer-to-Peer Network

    A blockchain network is made of nodes — computers running the protocol's software and talking to each other directly (peer-to-peer), with no central server.

    Node typeStoresRole
    Full nodeEntire blockchain historyIndependently validates every block and transaction
    Miner / validator nodeFull or partial chainProposes and confirms new blocks; earns rewards
    Light nodeOnly block headersVerifies transactions via proofs without the full history
    Archive nodeFull history + all historical statesPowers block explorers and analytics

    🔀 Forks — Soft vs Hard

    Soft Fork Backward-compatible

    Tightens the rules. Old nodes still recognize new blocks as valid, even without upgrading.

    Hard Fork Breaking change

    Changes the rules incompatibly. Non-upgraded nodes reject new blocks — the network can split into two chains (e.g. Ethereum / Ethereum Classic).

    Module 03 · Programmability

    Smart Contracts & Functions

    Move from a passive ledger to a programmable one. Learn how self-executing code is written, deployed, and run identically by every node on the network.

    📜 What is a Smart Contract?

    A smart contract is code deployed to the blockchain that runs exactly as written, with no possibility of downtime, censorship, or third-party interference. Every node executes it identically and agrees on the result — that agreement is what makes its output trustworthy.

    🤖
    Self-executing
    "If X happens, do Y" — enforced by code, not by a human intermediary.
    🔓
    Permissionless
    Anyone can deploy or interact with a public contract — no gatekeeper approval needed.
    🧊
    Immutable by default
    Once deployed, the code generally can't be changed — bugs ship to production forever unless designed otherwise.

    🧩 Anatomy of a Solidity Contract

    Solidity is the most widely used smart-contract language on Ethereum-compatible chains. Its structure will feel familiar if you've written a class in any object-oriented language.

    Solidity// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract SimpleBank {
    mapping(address => uint256) private balances;

    event Deposited(address indexed user, uint256 amount);

    function deposit() external payable {
        balances[msg.sender] += msg.value;
        emit Deposited(msg.sender, msg.value);
    }

    function balanceOf(address user) external view returns (uint256) {
        return balances[user];
    }
}
    Figure 3.1 · State, functions, events and modifiers together form a contract

    🚦 Function Visibility & Modifiers

    VisibilityCallable by
    publicAnyone — inside or outside the contract
    externalOnly from outside the contract (cheaper gas for large inputs)
    internalThis contract and contracts that inherit from it
    privateOnly this exact contract

    Modifiers wrap a function with a reusable precondition — like a decorator that runs before (and optionally after) the function body:

    address public owner;

modifier onlyOwner() {
    require(msg.sender == owner, "Not the owner");
    _;   // runs the wrapped function's body here
}

function withdraw(uint256 amount) external onlyOwner {
    // only the owner can ever reach this line
}

    🖥️ The EVM & Bytecode Deployment

    Solidity source code compiles down to EVM bytecode — the instruction set understood by the Ethereum Virtual Machine, a sandboxed runtime that every node executes identically.

    💡
    This is why gas exists: an EVM program could otherwise loop forever and stall the entire network. Every opcode has a gas cost, and a transaction that runs out of gas reverts.

    📦 Modules — Importing Other Contracts

    Just like Python's modules, Solidity files can import code from other files or trusted libraries such as OpenZeppelin — so you don't reinvent well-audited primitives like token standards or access control.

    import "@openzeppelin/contracts/access/Ownable.sol";

contract MyToken is Ownable {
    // inherits onlyOwner, owner(), transferOwnership() for free
}
    Module 04 · Data

    Data Structures & Storage

    Where data actually lives on a blockchain, the tree structure that lets you prove inclusion without downloading everything, and how contracts report what happened.

    💾 Storage vs Memory vs Calldata

    Unlike a normal program, every byte written to a contract's permanent storage costs real gas — so Solidity forces you to be explicit about where data lives.

    LocationLifetimeGas costTypical use
    storagePermanent, on-chainExpensive (write & read)State variables that must persist
    memoryOnly during function executionCheapTemporary variables, function arguments
    calldataOnly during the external callCheapest — read-onlyArguments to external/public functions
    Figure 4.1 · Three places data can live during execution

    🌳 Merkle Trees

    A Merkle tree hashes data in pairs, repeatedly, up to a single root hash. That root goes in the block header, letting anyone prove a specific transaction is included using only a short path of hashes — a Merkle proof — instead of the entire block.

    Figure 4.2 · To prove Tx1 is included, you only need H2, H34, and the root — not Tx2, Tx3 or Tx4
    💡
    This is exactly what lets light nodes (like mobile wallets) verify a transaction happened without storing the entire blockchain.

    🗂️ Mappings & Structs

    Solidity's two workhorse data structures parallel Python's dictionaries and classes-as-records:

    struct User {
    string name;
    uint256 reputation;
    bool isVerified;
}

mapping(address => User) public users;   // like a Python dict

function register(string calldata name) external {
    users[msg.sender] = User(name, 0, false);
}
    📌
    Solidity mappings have no length and can't be iterated — every possible key already "exists," returning zero-valued defaults. Track a separate array of keys if you need to loop over entries.

    📢 Events & Logs

    Contracts can't return data to the outside world after a transaction is mined — so they emit events, which are written into the transaction log. Front-ends and off-chain services listen for these instead of polling state.

    event Transfer(address indexed from, address indexed to, uint256 amount);

function transfer(address to, uint256 amount) external {
    // ...update balances...
    emit Transfer(msg.sender, to, amount);
}

    🚫 Handling Errors On-Chain

    Solidity's three error mechanisms all revert the entire transaction and refund unused gas — there's no partial success.

    StatementWhen to use
    require(cond, "msg")Validate inputs and external conditions (most common)
    revert CustomError()Gas-efficient, named errors with structured data (modern style)
    assert(cond)Internal invariants that should never be false — signals a bug if triggered

    Module 05

    Object-Oriented Contracts

    Solidity contracts behave a lot like classes: they can inherit from one another, implement interfaces, and be composed together — the same OOP ideas you already know, applied on-chain.

    🏗️ Contracts as Classes

    A contract is Solidity's equivalent of a class: it bundles state (fields) with behavior (functions). A deployed instance of a contract lives at its own address on-chain — just like an object lives at its own memory address at runtime.

    contract Token {
    string public name;
    uint256 public totalSupply;

    constructor(string memory _name, uint256 _supply) {
        name = _name;
        totalSupply = _supply;
    }
}
// Deploying Token("GoldCoin", 1_000_000) creates one on-chain instance
    Figure 5.1 · From contract code to independently addressed instances

    🧬 Inheritance

    A contract can inherit from one or more parent contracts with is, gaining their state and functions — exactly like subclassing.

    contract Animal {
    function speak() public virtual returns (string memory) {
        return "...";
    }
}
    contract Dog is Animal {
    function speak() public override returns (string memory) {
        return "Woof!";
    }
}

    virtual marks a function as overridable in the parent; override marks the child's replacement — Solidity requires both, unlike Python's implicit overriding.

    🔌 Interfaces & Abstract Contracts

    An interface declares function signatures with no implementation — a contract, or any external contract, can promise to support it. This is how contracts safely call other contracts they've never seen the source code of.

    interface IERC20 {
    function transfer(address to, uint256 amount) external returns (bool);
    function balanceOf(address account) external view returns (uint256);
}

// any contract implementing IERC20 can now be called generically:
function payWith(IERC20 token, address to, uint256 amt) external {
    token.transfer(to, amt);
}

    🏁 Constructors & Initialization

    The constructor runs exactly once, at deployment time, and can never be called again — unlike a regular function.

    contract Vault {
    address public immutable owner;

    constructor() {
        owner = msg.sender;   // set once, at deployment
    }
}
    📌
    immutable variables can only be set in the constructor but are as cheap to read as a hardcoded constant — a Solidity-specific optimization with no direct Python equivalent.

    🔗 Composition — One Contract Calling Another

    Contracts frequently hold references to other deployed contracts and call their public functions — composing small, single-purpose contracts into larger systems (sometimes called "money legos").

    contract Escrow {
    IERC20 public token;

    constructor(address tokenAddress) {
        token = IERC20(tokenAddress);   // hold a reference to another contract
    }

    function release(address to, uint256 amt) external {
        token.transfer(to, amt);   // delegate the actual work
    }
}

    Module 06

    Advanced Concepts & Security

    Gas mechanics and the vulnerability classes that have caused the biggest losses in blockchain history — and the patterns that defend against them.

    ⛽ Gas & Gas Optimization

    Gas measures computational work. Every opcode costs a fixed amount of gas; you set a gasLimit and a gasPrice, and pay gasUsed × gasPrice regardless of whether the transaction succeeds.

    PatternWhy it saves gas
    Pack small variables togetherMultiple values fit in one 32-byte storage slot
    Use calldata over memory for read-only argsAvoids an unnecessary copy
    Cache storage reads in a local variableStorage reads are far more expensive than memory reads
    Prefer revert CustomError() over string messagesCustom errors skip storing/encoding the error string

    🔁 Reentrancy Attacks

    The infamous 2016 DAO hack drained ~$60M using this exact flaw: a contract sends funds via an external call before updating its own state, letting the receiver's fallback function call back in and withdraw again before the balance is zeroed.

    ❌ Vulnerable

    function withdraw() external {
    uint256 amt = balances[msg.sender];
    (bool ok, ) = msg.sender.call{value: amt}("");
    require(ok);
    balances[msg.sender] = 0;  // updated too late!
}

    ✅ Fixed (checks-effects-interactions)

    function withdraw() external {
    uint256 amt = balances[msg.sender];
    balances[msg.sender] = 0;   // state updated FIRST
    (bool ok, ) = msg.sender.call{value: amt}("");
    require(ok);
}
    ⚠️
    The rule is checks-effects-interactions: validate conditions, update your own state, and only then call out to another contract or address.

    🔢 Integer Overflow & Checked Math

    Since Solidity 0.8.0, arithmetic automatically reverts on overflow/underflow — before that, uint8 x = 255; x++; silently wrapped to 0, a bug attackers exploited repeatedly.

    uint8 x = 255;
x++;   // Solidity ^0.8: reverts. Pre-0.8: silently becomes 0

    🛡️ Access Control Patterns

    Simple: onlyOwner

    One privileged address. Simple but a single point of failure — if that key is compromised, the whole contract is.

    Robust: Role-Based Access

    OpenZeppelin's AccessControl grants named roles (MINTER_ROLE, PAUSER_ROLE) to multiple addresses, each scoped to specific actions.

    🔄 Upgradeable Contracts & Proxies

    Since contract code is normally immutable, teams use a proxy pattern: users always call a stable proxy address, which delegatecalls into a separate, swappable logic contract — letting bugs be fixed without changing the address users trust.

    📌
    Upgradeability is a trade-off: it fixes bugs, but it also means the "immutable" guarantee users assumed no longer fully holds — whoever controls the upgrade key can change the logic.

    ⚔️ 51% Attacks & Network-Level Threats

    If a single entity controls more than half of a Proof-of-Work network's mining power (or a majority stake in Proof-of-Stake), it can rewrite recent history and double-spend — a 51% attack. This is why large, well-distributed networks are considered far more secure than small ones.

    Cryptography & Data Types

    The math that makes ownership and authorization provable without a central authority, plus Solidity's core value types.

    🔤 Solidity Value Types

    TypeHoldsNotes
    uint2560 to 2^256-1No negative numbers; the default integer size
    int256Signed integersRarely needed — most balances/amounts are unsigned
    address20-byte account/contract identifieraddress payable variant can receive ETH
    booltrue / falseSame as any language
    bytes32Fixed 32-byte valueCommonly stores hashes
    📌
    Unlike Python's arbitrary-precision integers, Solidity integers have a fixed bit width you must choose deliberately — get it wrong and you risk overflow or wasted storage.

    ✍️ Digital Signatures & ECDSA

    Transactions are authorized with the Elliptic Curve Digital Signature Algorithm (ECDSA). Signing with your private key produces a signature that anyone can verify against your public key — proving you approved the message, without ever revealing the private key itself.

    conceptsignature = sign(messageHash, privateKey)
isValid  = verify(messageHash, signature, publicAddress)
# isValid is true only if the signature was made by that address's private key

    📐 Bytes, Strings & ABI Encoding

    The ABI (Application Binary Interface) defines how function calls and their arguments are encoded into the raw bytes actually sent in a transaction — the equivalent of a serialization format like JSON, but fixed-width and byte-precise.

    // calling transfer(address,uint256) encodes to:
0xa9059cbb                                            // 4-byte function selector
0000000000000000000000008f3a...c21e             // address, padded to 32 bytes
00000000000000000000000000000000000000000000000000000000000003e8  // amount = 1000

    Module 08

    Consensus & Tooling

    How thousands of strangers agree on a single shared history without a referee, and the developer tools that make building and testing contracts practical.

    ⛏️ Proof of Work (PoW)

    Miners spend real computational energy competing to solve a puzzle. The winner proposes the next block. Security comes from the fact that attacking the network requires out-computing everyone else combined.

    ✅
    Battle-tested
    Bitcoin has run PoW securely since 2009.
    ⚡
    Energy-intensive
    Massive real-world electricity consumption.

    🥩 Proof of Stake (PoS)

    Instead of computing power, validators lock up ("stake") the network's own coin as collateral. The right to propose a block is assigned roughly proportional to stake, and validators caught cheating lose ("get slashed") part of their stake.

    ⛏️ Proof of Work

    • Security via computation
    • High energy use
    • Specialized mining hardware

    🥩 Proof of Stake

    • Security via economic stake
    • ~99% less energy (Ethereum's 2022 "Merge")
    • Validators run on ordinary servers

    🗳️ Other Consensus Mechanisms

    MechanismCore ideaUsed by
    Delegated PoSToken holders vote for a small set of trusted validatorsEOS, Tron
    Practical Byzantine Fault ToleranceNodes exchange messages and vote directly on each blockHyperledger Fabric
    Proof of AuthorityA fixed set of known, reputable validators sign blocksPrivate/consortium chains

    Module 09

    Web3, APIs & Nodes

    How a website talks to a blockchain: the node infrastructure underneath, and the libraries that turn contract calls into simple JavaScript.

    🌐 Connecting a Frontend to the Chain

    Figure 9.1 · Browser → wallet → RPC node → blockchain

    The frontend never talks to the blockchain directly — it asks the user's wallet (like MetaMask) to sign a transaction, and the wallet forwards it through an RPC node onto the network.

    📡 RPC Nodes & Providers

    Running your own full node is heavy, so most apps use hosted RPC providers that already run nodes for you and expose a simple JSON-RPC API.

    ProviderOffers
    InfuraHosted RPC endpoints across many chains
    AlchemyRPC + enhanced APIs (webhooks, NFT metadata, debug traces)
    QuickNodeManaged nodes with global edge locations

    📚 Reading & Writing with ethers.js

    ethers.js and web3.js are the two dominant JavaScript libraries for talking to Ethereum-compatible chains — the equivalent of an ORM sitting between your app and a database.

    ethers.jsconst provider = new ethers.BrowserProvider(window.ethereum);
const signer   = await provider.getSigner();
const contract = new ethers.Contract(address, abi, signer);

// read (free, no gas)
const balance = await contract.balanceOf(userAddress);

// write (costs gas, needs a signature)
const tx = await contract.deposit({ value: ethers.parseEther("0.1") });
await tx.wait();   // wait for it to be mined

    🔮 Oracles — Getting Off-Chain Data In

    Smart contracts can't natively fetch real-world data (prices, weather, sports scores) — the EVM is sandboxed on purpose. An oracle (e.g. Chainlink) is a service that fetches off-chain data and delivers it on-chain in a verifiable way.

    ⚠️
    This is called the "oracle problem": a contract is only as trustworthy as the data it consumes. A manipulated price feed has caused several major DeFi exploits.

    Module 10

    Libraries & Standards

    Audited, reusable building blocks — and the token standards that let wallets, exchanges, and marketplaces all speak the same language.

    🧱 OpenZeppelin library

    The most widely used Solidity library — battle-tested, audited implementations of token standards, access control, and security utilities, so you never write these primitives from scratch.

    import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MyToken is ERC20 {
    constructor() ERC20("MyToken", "MTK") {
        _mint(msg.sender, 1_000_000 * 10 ** decimals());
    }
}

    🪙 ERC-20 fungible tokens

    The standard interface every fungible token (interchangeable, like currency) implements — this is what lets any wallet or exchange support any ERC-20 token without custom code.

    FunctionPurpose
    totalSupply()Total tokens in existence
    balanceOf(address)Token balance of an account
    transfer(to, amount)Move tokens from caller to another address
    approve(spender, amount)Authorize another address to spend on your behalf
    transferFrom(from, to, amount)Move tokens using a prior approval

    🖼️ ERC-721 NFTs

    The standard for non-fungible tokens — each token ID is unique and not interchangeable with another, unlike ERC-20 where every token is identical.

    import "@openzeppelin/contracts/token/ERC721/ERC721.sol";

contract ArtCollection is ERC721 {
    constructor() ERC721("ArtCollection", "ART") {}

    function mint(address to, uint256 tokenId) external {
        _mint(to, tokenId);   // tokenId is unique — no two are the same
    }
}

    🎒 ERC-1155 multi-token

    Combines fungible and non-fungible tokens into a single contract — a game can manage 10,000 unique swords (non-fungible) and gold coins (fungible) all under one deployment, saving significant gas over deploying separate contracts.

    📋 Other Notable Standards

    StandardPurpose
    ERC-165Lets a contract declare which interfaces it supports
    ERC-4626Standardized "tokenized vault" interface for yield-bearing tokens
    EIP-712Structured, human-readable data for wallet signature prompts

    Module 11

    Platforms & Frameworks

    A tour of the major blockchain ecosystems — public and permissioned, Layer 1 and Layer 2 — and how to pick between them for a given project.

    💠 Ethereum smart contract platform

    The largest smart-contract platform, running the EVM and Proof-of-Stake consensus since 2022's "Merge." Nearly every tool and standard in this course targets Ethereum or an EVM-compatible chain.

    🟠 Bitcoin digital currency

    The original blockchain, purpose-built as peer-to-peer digital cash. Its scripting language is deliberately limited — not Turing-complete — trading programmability for simplicity and security.

    🚀 Layer 2 Scaling rollups

    Ethereum's base layer (Layer 1) is secure but limited in throughput. Layer 2 networks (Arbitrum, Optimism, zkSync) process transactions off the main chain in batches, then post a compressed proof back to Layer 1 — inheriting its security at a fraction of the cost.

    Figure 11.1 · Rollups batch many cheap transactions into one L1 settlement

    🌈 Alternative Layer 1s

    ChainKnown for
    SolanaVery high throughput via parallel transaction processing
    PolygonEVM-compatible sidechain, low fees, easy migration from Ethereum
    AvalancheSub-second finality using a novel consensus protocol
    CardanoResearch-driven, peer-reviewed protocol development

    🏢 Hyperledger & Permissioned Chains

    Not every blockchain is public. Hyperledger Fabric and similar frameworks let a known consortium of organizations (banks, supply-chain partners) run a shared ledger where membership itself is permissioned — trading decentralization for privacy, speed, and regulatory control.

    🧭 Choosing the Right Platform

    🌍 Public chain

    Choose when censorship-resistance, permissionless access, or composability with existing DeFi/NFT ecosystems matters most.

    🔒 Permissioned chain

    Choose when participants are known, data privacy is required, and throughput/compliance matter more than open access.

      Module 01 · Program Manager

      Core Skills

      Core Skills · Program Manager

      About core skills

      Coordinate related projects to deliver strategic outcomes that cannot be managed well through isolated project plans. Learn program governance, strategic alignment, cross-project dependencies, benefit realization, large-budget oversight and vendor management. The emphasis is on decisions, evidence and sustained outcomes rather than simply adding project status reports together.

      Learning Objectives

      • Define program decision rights and escalation boundaries.
      • Connect investments and project outputs to strategic outcomes and benefit owners.
      • Resolve cross-project dependencies and shared constraints.
      • Review allocation, forecast and vendor commitments without double counting.

      Prerequisites

      No previous program-management certification is required. Use basic percentages, read a table and distinguish an estimate from an observed result. Tool accounts are optional: the portable classroom datasets support the exercises. Code examples use Python 3 or labelled JSON/CSV/formula syntax.

      Fundamentals

      The shared classroom program improves workforce readiness through identity access, learning rollout, analytics and change enablement. The approved envelope is 6.0 million fictional currency units. Median onboarding is 10 days at baseline, 7 days at target and 8 days in the pilot. SSO is needed in week 4 and forecast in week 6. All organisations, amounts, dates and records are fictional; week offsets simplify a schedule rather than model a full calendar.

      Module 01 · Program Manager

      Multi-Project and Program Governance

      Core Skills · Program Manager

      Multi-Project and Program Governance

      Define the program-level decision boundary

      A program coordinates related projects and other work to produce outcomes and benefits from managing them together. Project managers control their own delivery within agreed authority; the program manager coordinates shared outcomes, dependencies and decisions beyond an individual project. A portfolio makes investment choices across initiatives and need not contain only interdependent projects. Clarify these relationships instead of treating the terms as different names for a large task list.

      Worked example

      The fictional workforce-learning program contains identity access, learning rollout, analytics and change enablement. Each stream has a delivery owner. The program owns the combined learner journey and benefit plan, while executive governance owns major investment choices.

      Create decision rights, tolerances and evidence

      Define who can approve funding changes, resolve shared priorities, accept outcomes and escalate exceptions. Establish reporting cadence and the evidence required for each decision. Tolerances should describe which deviations require escalation; they do not authorise anyone to ignore an issue. Meeting attendance alone does not prove that an accountable owner decided.

      Worked example

      A project can adjust activities within its agreed boundary. Moving a scarce security specialist between two projects requires a program-level trade-off. Releasing a held program reserve requires the designated funding authority.

      Use governance forums to close decisions

      An effective review separates information, advice, decisions and actions. Prepare a concise exception pack: observed problem, program consequence, options, recommendation, owner and deadline. Record the chosen action and why it was accepted. Follow up until implementation and outcome verification are complete.

      Worked example

      The steering group chooses to sequence access testing before analytics deployment. The decision log identifies the resulting date changes and action owners; the next review checks that the dependency was actually cleared.

      Coordinate governance without duplicating every project meeting

      Program governance should add the integrated view: benefits, dependencies, shared capacity, funding and strategic exceptions. Obtain sufficiently reliable project inputs and retain access to detail, but avoid asking every team to reproduce the same report in several templates.

      Worked example

      A weekly program review uses one agreed cut-off and discusses exceptions affecting the combined launch. Detailed task conversations remain with project owners.

      Adapt or stop work when the program case changes

      Review the continuing purpose and benefits, not just whether the original plan can still be executed. Present the remaining investment, changed assumptions and feasible options to the right authority. A program can retain a useful project, resequence components or stop work through an authorised decision.

      Worked example

      A strategic requirement changes. The program evaluates which capabilities still support the intended outcomes instead of continuing all components solely because they were previously approved.

      Module 01 · Program Manager

      Strategic Alignment

      Core Skills · Program Manager

      Strategic Alignment

      Trace strategy to outcomes and capabilities

      Translate a strategic objective into observable outcomes, required capabilities and the projects that enable them. An output is something delivered; an outcome is a changed condition or behaviour; a benefit is an improvement valued by an owner. A project can produce its output while the intended outcome fails to occur. Keep the chain explicit.

      Worked example

      The strategy is faster workforce readiness. Identity and learning capabilities enable a usable enrolment journey. Reduced onboarding time is an intended outcome; a benefit owner must explain the value and how it will be sustained.

      Test the contribution rather than the label

      An initiative labelled strategic still needs a credible explanation of contribution, dependencies and assumptions. Ask which outcome would improve, who values it and what evidence would support the claim. Distinguish direct contribution from an indirect supporting role. Do not assign full ownership of the same benefit to several projects.

      Worked example

      Analytics provides measurement evidence but does not independently create all of the onboarding improvement. Its contribution is recorded separately from the operational process changes.

      Prioritise within constraints and authority

      Compare contribution, urgency, capacity, risk and feasibility. Screen mandatory conditions before applying a weighted score. Scoring supports a discussion; it does not create funding authority or prove a certain return. Make the criteria, scale and assumptions visible.

      Worked example

      Two options support learner access, but one depends on unavailable specialist capacity. The program identifies the feasibility gap before interpreting its attractive benefit score.

      Review alignment when assumptions change

      A strategic objective, external condition or delivery assumption can change during a program. Review which outcomes remain valuable and which components need adjustment. Retain the rationale and prior commitments so that a revision is traceable.

      Worked example

      The business shifts from regional to national rollout. The program revisits accessibility, support capacity and adoption assumptions instead of treating the original pilot as sufficient evidence.

      Protect the outcome from local optimisation

      A project may meet its own date by transferring work or risk to another team. Evaluate the combined learner or business journey before accepting the trade-off. Optimising one status indicator can weaken the program outcome.

      Worked example

      The learning stream proposes launch before access testing to meet its date. Program review shows that learners would not be able to enrol, so the decision is made against the integrated outcome.

      Strategic Alignment: applied template or code

      strategy-contribution.json · JSON
      {

  "output": "Accepted learning pathway and usable access",
  "outcome": "Faster effective onboarding",
  "benefit_owner": "operations leader",
  "metric": "comparable median onboarding days",
  "baseline_days": 10,
  "target_days": 7,
  "enablers": ["identity", "learning", "analytics", "enablement"]
}

      The contribution map connects work with value and an owner. The four enabling streams contribute to one shared improvement; the benefit must not be counted four times.

      Practice: Strategic Alignment

      Map one strategic objective to two outcomes and four capabilities. Identify each project’s contribution and an assumption that would trigger reprioritisation.

      Check the reasoning

      • Strategic labels alone do not establish contribution.
      • Outputs, outcomes and benefits are different.
      • Mandatory conditions precede weighted ranking.
      Module 01 · Program Manager

      Cross-Project Dependency Management

      Core Skills · Program Manager

      Cross-Project Dependency Management

      Describe the handover as a contract between owners

      A dependency is a relationship in which one stream needs an output, condition or decision from another. Record provider, consumer, required artifact, needed-by date, readiness criteria, owners and current outlook. A line on a roadmap without these fields can conceal disagreement about what ready means.

      Worked example

      Learning enrolment needs the identity stream’s SSO interface and passed integration tests by week 4. The provider forecasts readiness in week 6: a two-week mismatch requiring review.

      Review the integrated consequence

      Assess how the mismatch affects downstream activities, benefits, capacity and commitments. Ask whether an alternative, phased release or changed sequence is feasible. A dependency is not closed because its provider reports an internal task complete; the consumer must be able to use the required output.

      Worked example

      An interface specification is written but the shared tests fail. The consumer cannot enrol learners, so the dependency remains unresolved despite document completion.

      Resolve ownership and escalate trade-offs

      Name both sides of the dependency and agree one coordination owner. Resolve normal working issues between the streams; escalate when priority, funding or tolerance requires higher authority. Record the revised commitment and update affected plans. Do not move the needed-by date silently to make the row green.

      Worked example

      Two projects need the same reviewer. The program presents sequence and additional-capacity options, then records the authorised choice and both projects’ forecast changes.

      Manage dependency chains and shared bottlenecks

      A single external dependency can affect several projects. Trace the chain far enough to explain the program consequence and avoid counting each symptom as an unrelated cause. Review near-critical interfaces and shared specialists as conditions change.

      Worked example

      One identity approval blocks enrolment and analytics test data. The program tracks the shared root constraint and its downstream effects rather than reporting two unrelated unexplained delays.

      Separate a scenario from a commitment

      A what-if sequence can help explore recovery but needs validation of interfaces, capacity and risk. Label the scenario and its assumptions. Confirm acceptance and authority before publishing it as the committed program outlook.

      Worked example

      A week-5 pilot using a temporary interface is explored. It becomes a commitment only after the technical owner, consumer and governance authority accept its limits and verification plan.

      Cross-Project Dependency Management: applied template or code

      dependency_check.py · Python 3
      def mismatch(needed_week, forecast_week):
    if not isinstance(needed_week, int) or not isinstance(forecast_week, int):
        raise ValueError("Weeks must be integers")
    if needed_week < 1 or forecast_week < 1:
        raise ValueError("Weeks must be positive")
    return max(0, forecast_week - needed_week)

print("SSO mismatch:", mismatch(4, 6), "weeks")

      Expected output: SSO mismatch: 2 weeks. Equal or earlier forecast weeks produce zero timing mismatch, which does not establish acceptance or readiness. Negative or non-integer weeks are rejected. This simplified offset check does not model calendars or complex schedules.

      Practice: Cross-Project Dependency Management

      Write the identity-to-learning dependency record. Show the downstream impact and compare resequencing with a temporary-interface scenario.

      Check the reasoning

      • The example has a two-week readiness mismatch.
      • Provider task completion is not consumer acceptance.
      • Recovery scenarios require validation before commitment.

      Benefit Realization

      Core Skills · Program Manager

      Benefit Realization

      Write a benefit profile before claiming success

      Define the benefit, owner, baseline, target, measure, time horizon, assumptions and dependencies. Identify who owns measurement and who owns operational sustainment. A benefit profile makes the expected improvement testable; it is not evidence that the improvement has already occurred.

      Worked example

      The benefit owner targets median onboarding time of 7 days from a measured baseline of 10 days. The measure specifies the eligible population and observation period, rather than using an unexplained percentage.

      Compare observed results with the target

      Use consistent units, definitions and populations, and state the size and period of the observation. Explain gaps and uncertainty. Benefits can depend on adoption, process change and operating capacity as well as a technical release. A deployed feature is an output, not proof of realised business value.

      Worked example

      The fictional pilot median is 8 days. The observed reduction is (10 − 8) / 10 = 20%; the target reduction is 30%. The target is not yet achieved. This comparison does not prove that software alone caused the change.

      Plan transition and sustained ownership

      Identify the operational owner, support arrangements, adoption activities and measurement after project closure. Decide how benefits will be reviewed and what action follows deterioration. A project completion report does not replace the ongoing benefit review.

      Worked example

      The operations owner continues onboarding measurements after handover. Training and support teams monitor adoption and barriers instead of ending measurement when the implementation team leaves.

      Distinguish capacity value from cash savings

      Time released can create useful capacity without reducing cash expenditure. Explain how an efficiency improvement becomes a valued outcome and whether any financial effect is demonstrated. Avoid assigning the same saved time as a full cash benefit to several streams.

      Worked example

      Faster onboarding releases staff time for other work. The program reports the measured capacity improvement separately from any verified reduction in spending.

      Test attribution and avoid double counting

      Compare contextual changes, baseline quality and measurement assumptions before assigning causal credit. Where several projects enable one outcome, define how contributions are described without counting the same total benefit repeatedly. Reassess the profile when evidence changes.

      Worked example

      Identity, learning and process redesign jointly support the journey. The program tracks one onboarding outcome and identifies enabling contributions rather than adding three copies of the same improvement.

      Benefit Realization: applied template or code

      benefit_check.py · Python 3
      def reduction(baseline, current):
    if baseline <= 0 or current < 0:
        raise ValueError("Use a positive baseline and nonnegative duration")
    return (baseline - current) / baseline * 100

baseline, observed, target = 10, 8, 7
actual_pct = reduction(baseline, observed)
target_pct = reduction(baseline, target)
print(f"Observed improvement: {actual_pct:.0f}%")
print(f"Target improvement: {target_pct:.0f}%")
print(f"Improvement gap: {target_pct - actual_pct:.0f} percentage points")
print(f"Median gap: {observed - target} day")

      Expected results are 20%, 30%, 10 percentage points and 1 day. A zero baseline is rejected; no change gives 0%; a longer current duration produces a negative improvement. Arithmetic does not establish a comparable population or causal attribution.

      Practice: Benefit Realization

      Create a benefit profile and calculate the pilot gap. Write a follow-up plan addressing adoption, measurement uncertainty and operational ownership.

      Check the reasoning

      • The example observed reduction is 20%; the target is 30%.
      • Output delivery does not prove benefit realization.
      • Capacity improvements and cash savings are not automatically equivalent.

      Multi-Million Budget Allocation and Oversight

      Core Skills · Program Manager

      Multi-Million Budget Allocation and Oversight

      Separate authorisation, allocation and forecast

      Program finance distinguishes the approved envelope, allocation to components, held reserves, actuals, commitments and remaining estimates. State currency, period, approval authority and reporting policy. A forecast is an estimate of likely cost; it does not automatically change authorisation or release reserves.

      Worked example

      The fictional envelope is 6.0 million currency units: identity 2.0, learning 1.5, analytics 1.0, enablement 0.8 and held reserve 0.7. Allocated delivery totals 5.3 million.

      Reconcile component totals and shared costs

      Use stable component identifiers and a common cut-off. Reconcile actuals and obligations, and record where shared costs belong. Include each cost once. An order converted into an invoice must not remain fully counted as an additional uninvoiced obligation. Large totals do not reduce the need for line-level evidence.

      Worked example

      Actuals of 2.1 million plus reviewed remaining estimates of 3.6 million forecast delivery cost of 5.7 million. A commitment already inside the remaining estimate is not added again.

      Evaluate transfers and reserve use explicitly

      Compare component forecasts with allocations and the program outlook with its approved envelope. Explain which tolerances or authority require escalation. A transfer between projects or draw on held reserve needs an authorised decision and updated records. Keep prior allocations and reasons visible.

      Worked example

      Delivery forecasts are 0.4 million above the 5.3 million delivery allocation. The 0.7 million reserve is held, so its existence does not mean the team can spend it without approval.

      Fund outcomes under capacity and timing constraints

      When funding choices are required, compare strategic contribution, benefit confidence, dependencies and the capacity to use the money effectively. More funding does not instantly create qualified resources or remove integration constraints. Show feasible options rather than only requesting a larger total.

      Worked example

      Analytics could receive more money, but identity readiness still controls launch. The program evaluates the bottleneck and sequencing before treating an analytics increase as recovery.

      Stress-test assumptions and report forecast confidence

      Prepare clearly labelled scenarios for major uncertainty, such as supplier costs or rollout scope. State what would trigger a revision and which obligations are already confirmed. Do not present one precise total as certain when unpriced work remains.

      Worked example

      A supplier change could add 0.2 million. The executive pack distinguishes the reviewed 5.7 million outlook from the conditional 5.9 million scenario and identifies the next commercial decision.

      Multi-Million Budget Allocation and Oversight: applied template or code

      budget_reconciliation.py · Python 3
      from decimal import Decimal as D

allocations = {"identity": D("2.0"), "learning": D("1.5"),
               "analytics": D("1.0"), "enablement": D("0.8")}
reserve, envelope = D("0.7"), D("6.0")
delivery_allocation = sum(allocations.values(), D("0"))
assert delivery_allocation + reserve == envelope
actual, remaining = D("2.1"), D("3.6")
forecast = actual + remaining
print("Delivery allocation:", delivery_allocation)
print("Reviewed delivery forecast:", forecast)
print("Variance above allocation:", forecast - delivery_allocation)
print("Conditional support scenario:", forecast + D("0.2"))
# Amounts are million fictional currency units.
# Reserve release and scenario approval are separate decisions.

      Expected results: 5.3 allocation, 5.7 forecast, 0.4 variance and 5.9 conditional scenario. The assertion detects an envelope mismatch. Commitments already included in remaining work are not added again. The calculation neither releases reserve nor establishes financial inclusion rules.

      Practice: Multi-Million Budget Allocation and Oversight

      Reconcile the classroom budget, show forecast versus delivery allocation and prepare a reserve-use decision note with assumptions and authority.

      Check the reasoning

      • The approved envelope is 6.0 million; allocated delivery is 5.3 million.
      • The delivery forecast is 5.7 million, 0.4 million above allocation.
      • Held reserve is not automatically authorised for use.

      Core Skills · Program Manager

      Vendor and Contract Management

      Connect vendor outputs to program outcomes

      Define the contracted deliverables, interfaces, acceptance evidence, dependencies, owners and operational handover. Vendor completion and business acceptance can differ. Coordinate commercial decisions with procurement, legal, finance and technical owners under the organisation’s authority model.

      Worked example

      The identity supplier provides an interface and agreed test evidence. The program also needs consumer acceptance and support readiness before relying on that output for the learner launch.

      Track obligations and change control

      Maintain a register of milestones, obligations, acceptance criteria, review dates, responsibilities and required decisions. Use the actual contract and authorised specialists for contractual interpretation. A program change request does not automatically amend a supplier’s obligations or pricing.

      Worked example

      An extra integration is requested. The team records technical impact and routes the commercial change through the designated process before presenting it as committed vendor scope.

      Review performance and continuity with evidence

      Compare delivery, quality, responsiveness and agreed service conditions using the relevant evidence. Discuss root causes and recovery actions, and record owners and dates. A supplier score does not by itself establish contractual breach or approve payment. Plan continuity for critical interfaces and support.

      Worked example

      The interface milestone is late. The program records the observed delay and downstream effect, requests a recovery plan and coordinates the commercial review without inventing a remedy not established by the contract.

      Coordinate acceptance across multiple consumers

      One vendor output may support several projects with different readiness needs. Agree shared criteria and identify additional consumer-specific checks. Avoid duplicate contradictory requests and ensure that a common approval does not hide an unmet critical condition.

      Worked example

      Learning and analytics agree the common identity tests. Analytics also needs a specific data handover, which is tracked separately rather than assumed from learning’s acceptance.

      Prepare renewals, exit and knowledge transfer early

      Identify upcoming commercial and operational decisions and assign review owners with sufficient lead time. Check actual notice requirements and transition obligations with the appropriate specialists. Track documentation, access, support and data responsibilities so that an exit does not create an unowned dependency.

      Worked example

      A review is due on 15 October for a service ending later in the month. The program prepares options and a transition plan; the date is an internal review example, not a universal contractual notice rule.

      Practice: Vendor and Contract Management

      Create a supplier register with one interface milestone, one change request and one renewal review. Identify technical acceptance and commercial decision owners.

      Check the reasoning

      • Commercial authority and technical acceptance have different roles.
      • A project request does not automatically amend a contract.
      • Vendor task completion may precede consumer acceptance.
      Module 01 · Program Manager

      Tools & Workflows

      Core Skills · Program Manager

      Core Skills tools and update workflow

      Choose the working records

      Maintain a program charter, benefit map, governance decision log, dependency register, funding reconciliation and supplier-review register. Use stable identifiers and owners so each executive decision can be traced to evidence.

      Run a controlled review cycle

      At the agreed cut-off, confirm consumer readiness, reviewed financial estimates and benefit observations. Identify changed assumptions and prepare the cross-stream decisions that exceed delegated authority. After approval, update controlled records and verify follow-up.

      Core Skills best practices

      • State the owner, cut-off and version for important records.
      • Use the smallest sufficient evidence pack for the decision.
      • Preserve authorised commitments and explain changes.
      • Test small examples and report the limits of automation.

      Primary tool and method references: PMI: strategic alignment through programs, PMI: interlocking program and project governance.

      Module 01 · Program Manager

      Interview Preparation

      Core Skills · Program Manager

      Core Skills interview discussion

      How is program management different from supervising several projects?

      It coordinates related work to deliver shared outcomes and benefits, resolving cross-project dependencies and decisions. Explain why a local project success can still leave the program outcome unmet.

      How do you handle a forecast above stream allocations but within an envelope containing reserve?

      Make the allocation variance visible, confirm inclusion rules and evaluate options. A remaining reserve does not automatically grant authority; obtain the designated decision and update controlled records.

      How do you judge a benefit claim?

      Check comparable definitions, populations and periods, the accountable owner and evidence. Distinguish output from outcome, capacity value from cash savings and observed change from causal proof.

      Explain your portfolio

      Describe the situation, your responsibility, the evidence reviewed, the decision and its verified result. Distinguish your contribution from the team outcome and state one limitation or lesson.

    Module 01 · Basic · Foundations

    Agile Tooling Fundamentals

    Why an Agile Coach needs technical tool skills, how team-level and enterprise tools differ, and how the four technical skills fit together.

    🧭 Why tools matter to an Agile Coach

    Tools do not make an organisation agile, but badly configured tools can stop it. An Agile Coach does not need to be a Jira administrator, but must understand tools well enough to shape how they are configured, connect them into one flow of information and turn their data into insight for teams and executives.

    🧰
    Configure for agility
    Workflows, boards and fields that support flow rather than bureaucracy.
    🏢
    Plan at scale
    Portfolio tools like Jira Align and VersionOne connect strategy to team work.
    🔗
    Integrate the toolchain
    Planning, code, build, test and operations tools share data automatically.
    📊
    Make work visible
    Dashboards that answer real questions for every level.
    💡
    "Individuals and interactions over processes and tools" does not mean tools do not matter. It means tools must serve people and flow, not replace conversation.

    Module 02 · Technical Skill 1 · Advanced Jira Enterprise

    Advanced Jira Enterprise

    Configure Jira for many teams: projects, schemes, workflows, JQL, boards, automation, Advanced Planning and governance.

    🏢 Jira at enterprise scale

    At enterprise scale Jira is usually Jira Cloud Premium or Enterprise, or self-managed Jira Data Center. Higher tiers add enterprise needs such as cross-team planning, stronger admin and security controls and higher availability. The coach's job is to keep Jira consistent enough for enterprise reporting and flexible enough for team autonomy.

    ChoiceOption AOption BCoach guidance
    Project typeCompany-managed (shared schemes, admin-controlled)Team-managed (team configures its own)Use company-managed where cross-team reporting matters
    ProjectsOne project per teamOne project per product/value stream with team field or componentsAlign projects to products or value streams, not org charts
    ConfigurationEvery team customShared standard schemesStandardise the minimum: hierarchy, key statuses, key fields

    ⚙️ Schemes and workflows

    In company-managed projects Jira configuration is built from schemes that can be shared across projects. Shared schemes keep many teams consistent.

    SchemeControls
    Issue type schemeWhich issue types a project can use (Epic, Story, Bug, Task…)
    Workflow schemeWhich workflow each issue type follows
    Screen schemeWhich fields appear when creating, editing or viewing
    Field configuration schemeWhich fields are required, hidden or optional
    Permission schemeWho can browse, create, edit, transition, administer
    Notification schemeWho gets emails for which events
    Workflow partPurposeExample
    StatusWhere the issue isTo Do, In Progress, In Review, Done
    TransitionMove between statusesStart work, Send to review
    ConditionWho can make the transitionOnly the assignee can move to In Review
    ValidatorChecks before transitionAcceptance criteria must be filled
    Post functionAction after transitionSet resolution when moved to Done
    ⚠️
    Every extra status and required field slows teams. Keep workflows lean: most teams need 4–6 statuses. Map status categories (To Do, In Progress, Done) consistently so cross-team reports work.

    🔎 Advanced JQL

    JQL (Jira Query Language) powers filters, boards, dashboards and automation. Fluent JQL lets a coach answer questions in seconds.

    JQLproject in (PAY, MOB) AND issuetype = Bug
  AND priority in (High, Highest) AND resolution = Unresolved
  ORDER BY created ASC
    JQLsprint in openSprints() AND status = "In Progress"
  AND updated <= -3d
    JQLproject = PAY AND status changed to Done
  DURING (startOfMonth(-1), endOfMonth(-1))
    Query purposeJQL idea
    Open high-priority bugsissuetype = Bug AND priority in (High, Highest) AND resolution = Unresolved
    Stuck work (not updated for 3+ days)status = "In Progress" AND updated <= -3d
    Done last monthstatus changed to Done DURING (startOfMonth(-1), endOfMonth(-1))
    Children of an epicparent = PAY-120
    Work in this releasefixVersion = "2026.10"
    My open workassignee = currentUser() AND resolution = Unresolved
    💡
    Use status categories in JQL, such as statusCategory = "In Progress", so queries work across teams whose status names differ.

    On the cumulative flow diagram the "In Review" band keeps widening while "Done" grows slowly. Work is piling up in review: a bottleneck. The coach suggests a WIP limit on In Review and pairing on reviews.

    🤖 Jira Automation

    Jira Automation rules have three parts: a trigger, optional conditions and actions. Good rules remove admin toil; too many rules become an invisible process nobody understands.

    TriggerConditionAction
    All sub-tasks transitioned to DoneParent is a StoryTransition parent to Done
    Issue createdIssue type = Bug and priority = HighestNotify on-call channel, add label "sev1"
    Scheduled dailyJQL: In Progress and not updated in 5 daysComment to remind assignee
    Pull request mergedIssue in In ReviewTransition to Ready for Test
    Field value changed (Sprint)Story points emptyComment asking for an estimate
    📝
    Keep a register of automation rules with an owner and purpose, and watch the rule audit log and execution limits.

    🗓️ Cross-team planning with Advanced Planning

    Jira Premium and Enterprise include advanced planning (previously called Advanced Roadmaps, shown as Plans). It lets you add hierarchy levels above epic (e.g. Initiative), plan across many teams and projects, see dependencies and capacity, and model scenarios before committing.

    CapabilityExample use
    Custom hierarchy above epicInitiative → Epic → Story
    Team capacityTeam velocity of 30 per sprint checked against planned work
    DependenciesShow blocks/is-blocked-by between teams on a timeline
    ScenariosCompare plan A (3 teams) vs plan B (4 teams) without changing live data
    Releases across projectsOne cross-project release for a program
    💡
    For SAFe portfolios with financial and strategy tracking, many enterprises add Jira Align on top of Jira. For a few teams, advanced planning is often enough.

    🏛️ Jira governance

    Governance practiceWhy
    Configuration standards (hierarchy, status categories, core fields)Reliable cross-team reporting
    Custom field controlToo many custom fields hurt performance and confuse users
    Sandbox testing for config changesAvoid breaking live projects
    Naming conventions for projects, boards, filtersPeople find things
    Admin roles: global vs project adminsBalance control and team autonomy
    Regular clean-up (archive old projects, unused fields and filters)Keep the instance fast and clear
    ⚠️
    Over-governed Jira becomes a reporting tool for managers instead of a work tool for teams. Govern the data that cross-team reports need; leave the rest to teams.

    Module 03 · Technical Skill 2a · Jira Align

    Jira Align

    Use Atlassian's enterprise agile planning platform to connect strategy, portfolio, programs and teams, with Jira as the team-level tool.

    🏢 What Jira Align is

    Jira Align is Atlassian's enterprise agile planning platform, originally called AgileCraft and acquired by Atlassian in 2019. Teams keep working in Jira Software; Jira Align sits above it and rolls work up to programs, portfolios and strategy. It supports SAFe and other scaling approaches.

    🎯
    Strategy
    Themes, objectives and key results linked to work.
    📁
    Portfolio
    Epics, funding, capacity and roadmaps.
    🚆
    Program
    PI planning, program board, dependencies, risks.
    👥
    Team
    Stories and sprints synced from Jira.

    🧱 Work hierarchy and Jira mapping

    Jira Align levelTypical ownerUsually maps to in Jira
    ThemeExecutives / portfolioNot synced (lives in Jira Align)
    Epic (portfolio)Portfolio managementOften not synced, or a level above epic
    Capability (optional)Solution managementOptional; used in large solutions
    FeatureProduct managementEpic in Jira
    StoryProduct Owner / teamStory in Jira
    TaskTeamSub-task in Jira
    ⚠️
    The naming trap: a Jira Align Feature is commonly mapped to a Jira Epic. Agree and document the mapping before go-live, or reports will double-count or miss work.

    🔗 The Jira connector

    Jira Align syncs with one or more Jira instances through its Jira connector. Getting the connector right is the most important technical step.

    SettingDecision
    Jira projects and boardsWhich boards map to which Jira Align teams
    Issue type mappinge.g. Jira Epic ↔ Align Feature, Story ↔ Story
    Field mappingPoints, status, sprint, release, team
    Status mappingJira statuses to Align states
    Sync directionWhich fields Jira Align can write back to Jira
    Sprint/PI alignmentJira sprints fall inside Jira Align PIs and iterations
    💡
    Start with a small set of boards in a test environment, check sync results with real teams, then expand.

    🚆 Program-level planning in Jira Align

    FeatureUse
    Program Increment (PI) setupDates, iterations and teams for each PI
    Program boardFeatures by team and iteration with dependency lines
    Program roomOne-page view of PI objectives, risks, dependencies and progress
    DependenciesRequests between teams, with commitment status
    Risks (ROAM)Resolved, Owned, Accepted, Mitigated tracking
    ObjectivesTeam and program PI objectives with business value scores
    Capacity planningEstimate vs capacity per team and PI
    EXAMPLE · PI Planning with Jira Align

    During PI Planning teams pull features onto the program board, link dependencies and enter PI objectives. Business Owners score objectives 1–10. At the end of the PI, actual value is compared with planned value to show predictability.

    📁 Portfolio and strategy

    Portfolio featureWhat it shows
    Strategy room / snapshotsMission, vision, themes, goals for a period
    OKRsObjectives and key results linked to work
    Portfolio KanbanEpics moving from Funnel to Done
    RoadmapsEpics and features over multiple PIs
    Investment vs spendPlanned funding vs actual cost by theme or value stream
    ForecastingEstimate epics by team and PI to check feasibility
    📝
    Jira Align is most valuable when leaders actually use it to make decisions: funding, priorities and trade-offs. If only RTEs update it for reports, the cost outweighs the benefit.

    🛠️ Rolling out Jira Align

    Rollout tipWhy
    Clean up Jira firstBad Jira data becomes bad portfolio data
    Start with one ARTLearn before scaling the configuration
    Train by role (RTE, PM, portfolio)Each role uses different screens
    Define data ownershipWho updates which level and when

    🚧 Jira Align traps

    TrapBetter approach
    Unclear Feature ↔ Epic mappingDocument the mapping and train everyone
    Using Align only for status reportingUse it for planning and funding decisions
    Teams double-entering dataTeams work only in Jira; sync rolls it up
    Too many custom levelsUse the simplest hierarchy that answers leaders' questions

    Module 04 · Technical Skill 2b · VersionOne

    VersionOne (Digital.ai Agility)

    Understand VersionOne's planning model, portfolio items, timeboxes and TeamRooms, and how to coach teams that use it or migrate from it.

    🏢 What VersionOne is

    VersionOne is one of the earliest enterprise agile management tools. After acquisitions it is now sold as Digital.ai Agility, but many organisations still call it VersionOne or "V1". Unlike Jira plus Jira Align, it covers team, program and portfolio planning in one product.

    AspectVersionOne / Digital.ai AgilityJira + Jira Align
    ArchitectureOne tool for team to portfolioTwo tools synced by a connector
    Team workTeamRooms, backlog, sprint boardsJira boards and backlogs
    PortfolioPortfolio items, portfolio Kanban, roadmapsJira Align portfolio and strategy features
    EcosystemSmaller marketplaceVery large Atlassian marketplace

    🧱 VersionOne's data model

    AssetWhat it isExample
    Planning level (project)Hierarchy of the organisation's planning structureEnterprise → Payments program → Team A
    Portfolio itemLarge work item, often with types such as Epic, Initiative or FeatureEpic: "Instant payments"
    Backlog itemStory or defect delivered by a teamStory: "Show payment status"
    Task / TestSmaller pieces of work and test cases under a backlog itemTask: "Build status API"
    TimeboxAn iteration/sprint with start and end datesSprint 2026-21
    Release / program incrementA larger planning period across teamsPI 4
    Team / TeamRoomA team and its shared workspace viewTeamRoom showing board, burndown and conversations
    📝
    Portfolio item types and hierarchy levels are configurable. Map them to your scaling framework, for example SAFe Epic → Feature → Story.

    📋 Working with teams in VersionOne

    FeatureUse
    Backlog and prioritisationOrdered list of backlog items for a planning level
    Sprint planningPull items into a timebox and check against capacity
    Storyboard / taskboardVisual board of backlog item and task status
    TeamRoomOne page with board, burndown, members and conversations
    Test trackingAcceptance and regression tests linked to stories
    ConversationsDiscussion threads attached to work items
    💡
    Make sure the planning level hierarchy reflects how teams really plan; otherwise rollups to programs and portfolio will be wrong.

    📁 Portfolio and analytics

    CapabilityExample use
    Portfolio KanbanEpics flow from Idea → Analysis → Implementing → Done
    RoadmappingPortfolio items on a timeline by quarter
    Strategic themes / investmentTag work to themes to see where effort goes
    Burndown and burnupProgress of a sprint, release or portfolio item
    Velocity and cumulative flowTeam speed and bottlenecks
    Estimate trendHow a portfolio item's estimate grows over time (scope creep signal)
    EXAMPLE · Spotting scope creep

    The "Instant payments" epic was estimated at 200 points in January and is now 340. The estimate trend report makes the growth visible, prompting a portfolio review of what is truly needed.

    🔌 Integrations and API

    VersionOne offers a REST-style API (with its own query language, often called query.v1) and integration services to connect with source control, CI tools and other ALM tools.

    IntegrationPurpose
    Source control (Git)Link commits to backlog items by ID in the commit message
    CI/CDShow build and deployment status on work items
    Other planning toolsSync with Jira or ServiceNow during co-existence or migration
    BI toolsExtract data for enterprise dashboards

    🔀 Migrating to or from VersionOne

    Migration riskMitigation
    Hierarchy does not map 1:1Design a mapping table before moving data
    History lostDecide what history matters; archive the rest
    Teams disrupted mid-PIMigrate at a PI boundary
    Reports breakRebuild key dashboards before cut-over
    Running two tools for too longSet a firm retirement date
    ⚠️
    Migrating tools is a change project, not just a data job. Apply change management: explain why, train people and support them after cut-over.

    🚧 VersionOne traps

    TrapBetter approach
    Planning levels mirror the org chart, not the value streamAlign planning levels to value streams and teams
    Too many portfolio item typesKeep 2–3 levels that leaders actually use
    Tasks tracked in hours for controlFocus on flow and outcomes, not hour policing

    Module 05 · Technical Skill 3 · Toolchain Integration Strategy

    Toolchain Integration Strategy

    Design how planning, code, CI/CD, testing, service management and identity tools connect, so work and data flow end to end.

    🔗 Why integration strategy matters

    A typical enterprise uses dozens of tools across the delivery lifecycle. Without a strategy, people copy data between them by hand, reports disagree and nobody can trace a production incident back to the change that caused it.

    Lifecycle stageExample tools
    PlanJira Software, Jira Align, Digital.ai Agility, Azure Boards
    CodeGitHub, GitLab, Bitbucket
    Build and deploy (CI/CD)Jenkins, GitHub Actions, GitLab CI, Azure Pipelines
    TestTest management tools, automated test frameworks
    Operate (ITSM)ServiceNow, Jira Service Management
    MonitorDatadog, Splunk, Grafana
    CollaborateConfluence, Slack, Microsoft Teams

    📌 Systems of record

    The first rule of integration: every type of data has one system of record that owns the truth. Other tools may show it, but changes are made at the source.

    DataSystem of record (example)
    Strategy, portfolio epics, fundingJira Align
    Features, stories, sprintsJira Software
    Source code and pull requestsGitHub
    Builds and deploymentsCI/CD platform
    Incidents and changesServiceNow
    People and accessIdentity provider (e.g. Microsoft Entra ID, Okta)
    ⚠️
    If two tools both "own" the same field and sync both ways without conflict rules, data will flip-flop and nobody will trust it.

    🧩 Integration patterns

    PatternHow it worksProsCons
    Native connectorVendor-built link (e.g. Jira ↔ GitHub, Jira ↔ Jira Align)Quick, supportedLimited to what the vendor offers
    Point-to-point APICustom scripts call each tool's REST APIFlexibleBecomes a fragile web as tools grow
    Integration hubCentral platform syncs many tools with mappingsScales, one place to manageLicence cost, needs expertise
    Webhooks / eventsTools push events when something changesNear real timeNeeds reliable handling and retries
    Data warehouseExtract data from all tools for reporting onlyGreat for dashboardsNot for operational sync
    📝
    Point-to-point links grow roughly with the square of the number of tools. With 10 tools, a hub is usually simpler to maintain than up to 45 separate connections.

    🧭 Designing a sync

    Design decisionQuestions to answer
    ScopeWhich projects, item types and fields?
    DirectionOne-way or bi-directional per field?
    MappingHow do types, statuses, users and values match?
    Conflict rulesWhich side wins if both change?
    FrequencyReal time, every few minutes, nightly?
    Error handlingWho is alerted when a sync fails?
    SecurityService accounts, least privilege, API tokens rotated
    Example mappingJira Align Feature   <->  Jira Epic       (status: Jira -> Align)
Jira Align Story     <->  Jira Story      (points, sprint: Jira -> Align)
ServiceNow Incident   ->  Jira Bug        (one-way, link kept)
GitHub PR merged      ->  Jira transition "In Review" -> "Ready for Test"

    🧬 End-to-end traceability

    Linking each step lets you answer "What changed in production last night, why, and who approved it?" in minutes. A simple enabler is putting the issue key in branch names and commit messages (e.g. PAY-142 add status API), so development tools link back to the story automatically.

    EXAMPLE · Audit made easy

    An auditor asks for evidence that release 26.4 was tested and approved. Because commits, builds, test runs and the ServiceNow change record are linked to the stories, the team exports the evidence in an hour instead of two weeks.

    🔐 Identity, security and compliance

    AreaPractice
    Single sign-on (SSO)SAML or OIDC with the company identity provider
    User provisioningSCIM to create and remove users automatically
    Service accountsSeparate accounts for integrations with least privilege
    SecretsStore API tokens in a vault; rotate regularly
    Data residencyCheck where each SaaS tool stores data
    Audit logsKeep logs of config and permission changes

    🗺️ Building the integration roadmap

    StepOutput
    Map the current toolchainInventory of tools, owners, users, costs and links
    Find pain pointsManual re-entry, broken traceability, conflicting reports
    Define target architectureSystems of record, patterns, hub or not
    Rationalise toolsRetire overlapping tools
    Deliver in incrementsHighest-pain integration first
    Run and governOwners, monitoring, change control for integrations
    💡
    Treat the integration platform as a product with an owner and a backlog, not a one-off project.

    Enterprise Dashboards

    Design dashboards for each audience, choose meaningful metrics, build a trusted data pipeline and avoid metric misuse.

    📊 Dashboards by audience

    AudienceKey questionExample metricsRefresh
    TeamHow is our flow this sprint?Sprint burndown, WIP, cycle time, blockersReal time
    Program / ARTWill we meet PI objectives?Feature progress, dependencies, risks, predictabilityDaily
    PortfolioAre we investing in the right things?Epic progress, investment by theme, flow distributionWeekly
    ExecutiveAre we getting better results?Lead time, DORA metrics, OKRs, customer metricsMonthly
    Transformation officeIs the change working?Outcome trends, adoption, engagementMonthly
    💡
    One dashboard cannot serve everyone. Start from the audience's decisions, then pick metrics.

    📐 Choosing metrics

    CategoryMetricWhy it matters
    FlowFlow time, flow velocity, flow load, flow efficiency, flow distributionSpeed and health of delivery
    Delivery (DORA)Deployment frequency, lead time for changes, change failure rate, time to restoreEngineering performance
    PredictabilityPlanned vs actual business valueReliability of commitments
    QualityEscaped defects, defect ageCustomer impact
    ValueOKR progress, feature adoption, revenue, NPSBusiness outcomes
    PeopleEngagement, team stabilitySustainability
    Leading indicatorLagging indicator
    WIP growingLead time rising next month
    Dependencies unresolved at PI startMissed PI objectives
    Test automation coverage fallingChange failure rate rising

    🏗️ The data pipeline

    OptionWhen to use
    Built-in Jira dashboards and gadgetsTeam and simple project views
    Jira Align / Digital.ai Agility reportsProgram and portfolio views inside the planning tool
    Marketplace reporting add-ons for JiraAdvanced Jira reports without a full data warehouse
    Data warehouse + BI (e.g. Power BI, Tableau, Looker)Cross-tool enterprise dashboards (planning + CI/CD + ITSM + finance)
    📝
    Dashboards are only as good as the data. Fix data hygiene first: consistent status categories, issue types, team fields and dates.

    🎨 Dashboard design principles

    PrincipleExample
    Few metrics, clear purpose5–7 tiles answering one audience's questions
    Show trends, not snapshotsLead time over 12 months, not just today's value
    Most important at top leftHeadline outcome first
    Context and targetsShow the target line and a note on what changed
    Drill-downFrom portfolio tile to program to team detail
    Accessible coloursDo not rely on red/green alone; add labels
    EXAMPLE · Executive one-pager

    Top row: lead time trend (target 45 days), deployment frequency, change failure rate. Middle: OKR progress by theme. Bottom: top 3 risks and decisions needed. All on one screen with links to detail.

    ⚠️ Metric misuse and Goodhart's law

    Goodhart's law: when a measure becomes a target, it ceases to be a good measure. Pressure on a single number causes people to game it.

    MisuseResultBetter practice
    Comparing velocity between teamsPoint inflation; story points lose meaningUse velocity only within a team for forecasting
    Target of 100% utilisationQueues and long lead timesTrack flow and WIP instead
    Rewarding number of deployments onlyTiny meaningless deploysPair with change failure rate and outcomes
    Dashboards used to blameHidden problems, fake green statusUse data for learning and support
    ⚠️
    Never put individual performance rankings on agile dashboards. Measure teams and systems, not people.

    🔁 Using dashboards in the operating rhythm

    ForumDashboard usedDecision
    Team retrospectiveCycle time and CFDProcess improvement experiments
    ART sync / PO syncFeature progress and dependenciesRe-plan or escalate
    Inspect & AdaptPredictability and quality trendsImprovement backlog items
    Portfolio reviewInvestment and epic progressFund, pivot or stop epics
    Quarterly business reviewOKRs and outcome metricsStrategy adjustments
    💡
    A dashboard nobody uses in a decision forum is decoration. Tie each dashboard to a meeting and a decision.

    Interview Preparation

    Click a question to reveal a model answer.

    🧭 Fundamentals

    Why does an Agile Coach need technical tool skills?
    Because tools shape behaviour and data. A coach must ensure tools support flow and autonomy, connect strategy to delivery and give leaders trustworthy data, without turning tools into control mechanisms.
    How do you stop a tool from driving the process?
    Agree the way of working first, then configure the tool to support it with minimal statuses, fields and rules. Review configuration with teams regularly.

    🧰 Advanced Jira Enterprise

    How would you standardise Jira across 50 teams?
    Use company-managed projects with shared schemes for the minimum needed for reporting: issue hierarchy, status categories and key fields. Let teams own their boards, quick filters and swimlanes. Govern changes through a sandbox and a lightweight change process.
    Write JQL for open high-priority bugs in two projects.
    project in (PAY, MOB) AND issuetype = Bug AND priority in (High, Highest) AND resolution = Unresolved ORDER BY created ASC.
    How do you find bottlenecks in Jira?
    Use the cumulative flow diagram for widening bands, the control chart for cycle time by status, and JQL for items stuck in a status for several days.
    When would you use Advanced Planning instead of Jira Align?
    For a handful of teams needing cross-team timelines, capacity and dependencies. Jira Align fits when you need portfolio strategy, funding and SAFe-style program management across many teams.

    🏢 Jira Align and VersionOne

    How does Jira Align work with Jira?
    Teams work in Jira; the Jira connector syncs boards, issues and sprints to Jira Align, which rolls them up to features, epics, themes and PIs for program and portfolio views.
    What is the most common mapping mistake?
    Not agreeing that a Jira Align Feature maps to a Jira Epic, leading to double counting or missing work in reports.
    Compare VersionOne with Jira plus Jira Align.
    VersionOne (Digital.ai Agility) is one product covering team to portfolio, with timeboxes, portfolio items and TeamRooms. Jira plus Jira Align are two products synced by a connector, with a much larger ecosystem.
    How would you plan a migration from VersionOne to Jira and Jira Align?
    Agree goals, map the data models, clean data, pilot with one program, validate reports, migrate in waves at PI boundaries, train users and retire the old tool on a fixed date.

    🔗 Toolchain Integration Strategy

    How do you design a toolchain integration strategy?
    Inventory tools and pain points, define a system of record per data type, choose patterns (native connectors, hub, webhooks, warehouse), design mappings and conflict rules, secure with SSO and service accounts, and deliver in increments.
    How do you achieve traceability from requirement to production?
    Link the hierarchy in planning tools, put issue keys in branches and commits, link builds and deployments to issues, connect change records in ITSM, and keep audit logs.
    When would you use an integration hub?
    When there are many tools and many sync needs, since point-to-point links become fragile and grow quickly in number.

    📊 Enterprise Dashboards

    How do you design an executive dashboard?
    Start from executives' decisions, choose a few outcome and flow metrics with trends and targets, put the headline top-left, add top risks and decisions needed, and link to drill-down detail.
    Which metrics do you avoid on dashboards?
    Comparisons of velocity between teams, utilisation targets and individual rankings, since they encourage gaming (Goodhart's law).
    How do you make dashboard data trustworthy?
    Fix data hygiene at the source, document metric definitions, automate extraction, reconcile against source tools and show data freshness.

    🏗️ Scenario: Connect a fragmented toolchain

    An insurance company has 40 teams. 25 teams use Jira with 30 different workflows; 15 teams use VersionOne. Portfolio planning is done in spreadsheets. Incidents live in ServiceNow, code in GitHub and builds in Jenkins. Executives get three different "status" numbers each month, and an auditor wants change traceability. You have 6 months to fix this.

    1️⃣ Task 1 · Advanced Jira

    ✍️ How do you bring 30 Jira workflows under control without taking away team autonomy?
    Model answer: Agree a standard issue hierarchy and status categories, create 2–3 shared workflow schemes (e.g. software, support, simple), migrate teams in waves, keep boards, quick filters and swimlanes team-owned, and set up a sandbox and change process for configuration.
    Q. Which shared element matters most for reliable cross-team reporting?
    • A Consistent status categories and issue hierarchy
    • B Same board colours
    • C Same quick filters
    • D Same avatars

    2️⃣ Task 2 · Jira Align

    ✍️ Leadership chooses Jira Align for portfolio planning. What do you set up first?
    Model answer: Define who uses it and for which decisions; design the hierarchy (Theme → Epic → Feature → Story) and mapping (Align Feature ↔ Jira Epic); configure a test instance; connect one ART's boards; train RTE, product and portfolio roles; run the first PI in the tool, then expand.
    Q. Where should teams do daily story updates after Jira Align goes live?
    • A Jira
    • B Jira Align and Jira both
    • C Spreadsheets
    • D Email

    3️⃣ Task 3 · VersionOne migration

    ✍️ Plan the move of 15 teams from VersionOne to Jira.
    Model answer: Map VersionOne portfolio items, backlog items, tasks and timeboxes to Jira/Align types and sprints; clean data; pilot with one program; validate reports with users; migrate in waves at PI boundaries; keep VersionOne read-only for history; retire it on a fixed date; train and support teams.
    Q. What is the best time to migrate a program's teams?
    • A Mid-sprint
    • B At a PI boundary
    • C During PI Planning
    • D The day before a release

    4️⃣ Task 4 · Toolchain integration

    ✍️ Design the integration for traceability across Jira, GitHub, Jenkins and ServiceNow.
    Model answer: Systems of record: Jira Align for portfolio, Jira for stories, GitHub for code, Jenkins for builds, ServiceNow for changes and incidents. Issue keys in branches and commits; Jenkins posts build and deploy info to Jira; ServiceNow change records link to Jira releases; incidents create linked Jira bugs one-way. Use SSO, service accounts and monitoring of sync failures.
    Q. With 10 tools linked point to point, what is the maximum number of connections?
    • A 10
    • B 20
    • C 45
    • D 100

    5️⃣ Task 5 · Enterprise dashboards

    ✍️ Executives get three different status numbers. Design the fix.
    Model answer: Agree single metric definitions with executives; build a data pipeline from Jira, Jira Align, Jenkins and ServiceNow into a warehouse; create one executive dashboard with lead time, deployment frequency, change failure rate, predictability and OKR progress, with trends and targets; show data freshness; use it in the monthly business review.

    • A Build it
    • B Show team outcomes and flow trends instead; avoid comparing story points
    • C Hide all metrics
    • D Rank individuals

    Module 01 · Basic · Foundations

    SDLC Automation Foundations

    Understand the software delivery life cycle, the models behind it and the tool categories that automate each phase.

    🤖 What is SDLC Automation?

    The Software Development Life Cycle (SDLC) runs from planning to operating a product. SDLC automation uses tools to perform repeatable steps (builds, tests, packaging, deployments, ticket updates) without manual effort. The Delivery Manager does not write the pipelines, but must understand the tool chain well enough to spot bottlenecks, ask the right questions and read the metrics.

    📋
    Plan & track
    Jira, Azure Boards: workflows, boards, automation rules.
    🌿
    Source control
    Git with GitHub, GitLab or Bitbucket: branches and pull requests.
    ⚙️
    Build & CI
    Jenkins, GitHub Actions, GitLab CI: build and test every change.
    🧪
    Test automation
    Selenium, Cypress, JUnit, Postman: fast, repeatable checks.
    📦
    Artifacts
    Nexus, Artifactory, container registries: store versioned builds.
    🚀
    Deploy & configure
    Terraform, Ansible, Helm, Argo CD: scripted environments and releases.

    🔄 SDLC Models and Where Automation Fits

    The SDLC can be run in different ways. The model decides how often work flows through the phases, and therefore how much automation pays back.

    ModelHow work flowsRole of automation
    WaterfallPhases run once, in sequence: requirements, design, build, test, releaseLimited; late testing finds problems late
    Agile (Scrum/Kanban)Short iterations deliver small working incrementsAutomated tests and CI keep every increment working
    DevOpsContinuous flow from commit to production with feedback from operationsPipeline automates build, test, deploy and monitoring end to end
    📝
    The shorter the cycle, the more manual work hurts. A team that releases every two weeks cannot afford a three-day manual regression.

    🧱 SDLC Phases and the Automation That Supports Them

    PhaseWhat is automatedTypical toolsWhat the Delivery Manager watches
    PlanTicket workflows, board rules, release notesJira, Azure BoardsBacklog health, ready work
    CodeBranching rules, pull-request checks, lintingGit, GitHub, GitLabPull-request age, review turnaround
    BuildCompile, unit tests, packaging on every commitJenkins, GitHub Actions, GitLab CIBuild success rate, build time
    TestRegression, API, UI and security scansSelenium, Cypress, Postman, SonarQubePass rate, coverage trend, flaky tests
    ReleaseVersioning, artifact storage, approvalsNexus, ArtifactoryRelease readiness, rollback plan
    DeployEnvironment provisioning, scripted deploymentsTerraform, Ansible, Argo CDDeployment time, failure rate
    OperateMonitoring, alerting, automatic ticket creationPrometheus, Grafana, DatadogUptime, incident count

    📖 Key Terms

    Continuous Integration (CI)Merge small changes often; each merge triggers an automated build and tests.
    PipelineAutomated sequence of stages from commit to release.
    ArtifactVersioned output of a build (package, image, binary).
    Quality gatePass/fail rule such as "coverage at least 80%" a build must meet to move on.
    Pull requestProposal to merge a branch, reviewed and checked automatically.
    Flaky testTest that passes and fails randomly with no code change.
    💡
    Automate the repetitive, stable and error-prone steps first. Keep human judgement for design, code review and release decisions.

    Pipelines & Test Automation in Practice

    See how a CI pipeline runs step by step, what is worth automating, how Jira automation helps, and which pitfalls to avoid.

    🪜 A Typical CI Pipeline, Step by Step

    StageWhat runsIf it fails
    1. CheckoutPull the latest code and dependenciesFix access or dependency problem
    2. Static checksLinting, code style, secret scanning, SonarQube analysisDeveloper fixes before review continues
    3. BuildCompile and package the applicationBuild is red; the author fixes it first
    4. Unit testsFast tests with a coverage reportQuality gate blocks the merge
    5. Integration/API testsServices tested together with Postman or similarInvestigate contract or data issue
    6. Package and publishCreate image or package, store in Nexus/ArtifactoryRelease is not created
    7. Deploy to testScripted deployment, smoke testsRollback and alert the team

    Pipelines are written as pipeline as code (for example a Jenkinsfile, a GitHub Actions workflow or a .gitlab-ci.yml file) and stored in Git, so they can be reviewed, versioned and reused.

    Branching strategyIdeaFits when
    Trunk-basedSmall changes merged to main daily, behind feature flagsTeams aiming for continuous delivery
    GitFlowLong-lived develop, release and hotfix branchesScheduled releases and several supported versions

    🎯 Choosing What to Automate

    Rank candidates by how often the task runs, how long it takes and how risky manual errors are. The test automation pyramid guides test mix: many fast unit tests, fewer API/integration tests, very few slow end-to-end UI tests.

    Automate

    Regression suites, builds, deployments, environment setup, status reporting, repetitive ticket updates.

    Keep manual

    Exploratory testing, usability review, architecture decisions, go/no-go calls, one-off tasks.

    Example

    A team spends 4 hours on manual regression per release and releases twice a week = 8 hours/week. Automating 70% saves about 5.6 hours/week, roughly 22 hours per month.

    📋 Jira Automation and Reporting for Delivery Managers

    Jira is the planning backbone. Automation rules remove admin work and keep data trustworthy, which makes your reports credible.

    Example ruleBenefit
    When a pull request is merged, move the issue to "Done"Status reflects reality without manual updates
    When an issue stays "Blocked" for 2 days, notify the Delivery ManagerImpediments surface early
    Auto-assign by component or labelWork reaches the right team faster
    When all sub-tasks are done, transition the parentLess board maintenance
    ReportWhat it tells you
    Burndown / velocityProgress and delivery rate in iterations
    Cycle time and control chartHow long work takes and how predictable it is
    Cumulative flow diagramWhere work is piling up (bottlenecks)
    Created vs resolvedWhether the backlog is growing or shrinking

    ⚠️ Risks and Pitfalls of Automation

    PitfallWhy it hurtsBetter approach
    Automating a broken processYou just make the mistake fasterFix or simplify the process first
    Too many slow UI testsLong, flaky pipelines nobody trustsFollow the test pyramid
    Tool sprawlMany overlapping tools, hard to maintainStandardise on a small supported tool set
    No owner for the pipelineFailures sit unfixedName an owner and a fix-the-build rule
    Ignoring maintenance costScripts rot as the product changesBudget time for upkeep

    Payback period = Effort to automate ÷ Hours saved per month

    Example

    Building an automated regression suite takes 60 hours and saves 22 hours per month. Payback = 60 ÷ 22 ≈ 2.7 months, so the investment is worth it if the suite will be used for longer than that.

    Module 03 · Intermediate · DevOps

    DevOps Foundations & CI/CD

    DevOps joins development and operations through shared ownership, automation and measurement. Start with the culture, the life cycle and the CI/CD pipeline.

    🔁 What DevOps Is (and Is Not)

    DevOps is a culture plus a set of practices, not just a toolset or a job title. Teams that build a service also help run it, which shortens feedback loops. The CALMS model is a handy checklist.

    CALMSMeaning
    CultureShared responsibility between development, operations and security.
    AutomationBuild, test, deploy and provision without manual steps.
    LeanSmall batches, limited work in progress, remove waste.
    MeasurementDecide with data: DORA metrics, SLAs, error rates.
    SharingOpen knowledge, blameless learning, common tooling.

    ♾️ The DevOps Life Cycle and Toolchain

    DevOps is often drawn as an infinity loop: what you learn in operations feeds the next round of planning.

    PhaseGoalExample tools
    PlanDecide what to buildJira, Confluence
    CodeWrite and reviewGit, GitHub, GitLab
    BuildCompile and packageMaven, Gradle, npm, Docker
    TestVerify qualityJUnit, Selenium, SonarQube
    ReleaseApprove and versionArtifactory, Nexus
    DeployPut it liveArgo CD, Ansible, Helm
    OperateRun and scaleKubernetes, Terraform, cloud services
    MonitorObserve and alertPrometheus, Grafana, Datadog, ELK

    🚦 The CI/CD Pipeline

    A pipeline moves each change through automated stages. Three related terms are often confused:

    TermMeaningRelease to production
    Continuous IntegrationMerge often; every change is built and testedNot included
    Continuous DeliveryCode is always in a releasable stateManual approval, one click
    Continuous DeploymentEvery passing change goes live automaticallyFully automatic

    Commit → Build → Unit tests → Package → Deploy to staging → Automated tests → Approval → Production → Monitor

    🧰 Core DevOps Practices

    📜
    Infrastructure as Code
    Servers and networks defined in version-controlled files (Terraform, CloudFormation).
    🐳
    Containers
    Docker packages an app with its dependencies; Kubernetes orchestrates many containers.
    🔭
    Observability
    Logs, metrics and traces explain what a live system is doing.
    🛡️
    DevSecOps
    Shift security left: scan code and dependencies inside the pipeline.
    🚩
    Feature flags
    Turn functionality on or off without redeploying.
    🔄
    GitOps
    Git is the single source of truth for declarative infrastructure and deployments.

    Module 04 · Intermediate · Release & Operations

    DevOps in Delivery & Operations

    How changes reach production safely: deployment strategies, environments, monitoring, DORA metrics and the Delivery Manager role.

    🚀 Deployment Strategies

    StrategyHow it worksBenefitWatch out for
    RollingReplace instances graduallyNo full downtimeMixed versions run together
    Blue-greenTwo identical environments; switch traffic to the new oneInstant rollbackDouble infrastructure cost
    CanaryRelease to a small share of users firstLimits blast radiusNeeds good monitoring
    Big-bangReplace everything at onceSimpleHigh risk, long outage if it fails

    🌍 Environments and Release Management

    EnvironmentPurpose
    DevelopmentDevelopers build and try changes
    Test / QAAutomated and manual testing
    StagingProduction-like final check and System Demo
    ProductionLive customers

    Keep environments as similar as possible (same images, same configuration structure) so that "it worked in test" means something. Keep secrets such as passwords and API keys in a secrets manager (for example HashiCorp Vault or a cloud secrets service), never in source code.

    Rollback

    Return to the previous version quickly. Best when the last release is clearly the cause.

    Roll-forward

    Ship a quick fix instead. Best when rollback is risky, for example after a database change.

    💡
    Plan the rollback before the deployment, including database changes. A release without a tested rollback plan is a gamble.

    📡 Monitoring, Alerting and SRE Ideas

    Site Reliability Engineering (SRE) applies software engineering to operations. A useful starting set of signals is the four golden signals:

    SignalQuestion it answers
    LatencyHow long do requests take?
    TrafficHow much demand is there?
    ErrorsHow many requests fail?
    SaturationHow full is the system (CPU, memory, queue)?

    Good alerts are actionable, urgent and tied to customer impact. Dashboards show trends; alerts wake people up, so use them sparingly.

    📊 DORA Metrics

    The four DORA metrics measure delivery performance. Two measure speed and two measure stability.

    MetricMeaningType
    Deployment frequencyHow often you release to productionSpeed
    Lead time for changesTime from commit to running in productionSpeed
    Change failure ratePercentage of deployments causing a failure that needs a fix or rollbackStability
    Time to restore serviceHow quickly service recovers after a failure (MTTR)Stability
    📝
    Speed and stability are not a trade-off: high-performing teams are strong on both. Do not rank people by these metrics; use them to find system bottlenecks.

    🧯 Anti-patterns and the Delivery Manager Role

    Anti-patternProblem
    A separate "DevOps team" as a new siloHand-offs remain; others stop caring about operations
    Tool-first adoptionTools without culture or process change give little benefit
    Manual approvals at every stepQueues form and lead time grows
    Security at the very endLate, expensive fixes and delayed releases
    Measuring individuals with DORA metricsEncourages gaming instead of improving the system
    Delivery Manager actionExample
    Remove impedimentsGet environment access or tool licences approved
    Track flow metricsReview DORA metrics monthly with the teams
    Manage riskMake sure every release has a rollback plan and owner
    Align calendarsCoordinate release windows across dependent teams
    Grow capabilityFund training and pipeline improvement work

    Module 05 · Advanced · Incident Process

    Incident Management Process

    When production breaks, speed and coordination matter. Learn the life cycle, severity levels, roles, communication and change management.

    🚨 The Incident Life Cycle

    StageWhat happens
    DetectMonitoring alert or a user report reveals a problem.
    Log & classifyTicket created; category, impact and severity set.
    Triage & assignThe right team or on-call engineer takes ownership.
    Diagnose & mitigateRestore service first (rollback, failover, workaround).
    Resolve & closeService confirmed healthy; ticket closed with notes.
    ReviewPost-incident review finds causes and improvement actions.
    💡
    Restore service first, find the root cause second. Rollbacks and workarounds beat long debugging while customers are affected.

    ⚖️ Severity and Priority

    Severity describes the impact; priority decides how fast to act. Targets below are typical examples and differ between organisations.

    Priority = Impact × Urgency

    LevelExampleTypical responseUpdates
    SEV1 / CriticalFull outage, data loss, security breachWithin 15 minutes, 24x7Every 30 minutes
    SEV2 / MajorKey feature down for many usersWithin 30 minutesEvery 1 hour
    SEV3 / MinorDegraded feature, workaround existsWithin 4 business hoursDaily
    SEV4 / LowCosmetic issue, questionNext business dayOn resolution

    🧑‍🚒 Roles, Problem Management and Blameless Reviews

    In a major incident, an Incident Commander coordinates, a Communications Lead updates stakeholders, subject-matter experts fix, and a scribe keeps a timeline.

    Incident management

    Restore service as fast as possible.

    Problem management

    Find and remove the root cause of recurring incidents.

    📝
    A blameless post-incident review records the timeline, contributing factors and action items with owners and dates. It focuses on systems and process, never on punishing individuals.

    📣 Major Incident Communication

    During a major incident, silence creates more damage than the outage. Agree a communication cadence by severity and use a fixed template.

    AudienceWhat they needChannel
    RespondersTechnical detail, who owns whatWar-room chat, bridge call
    LeadershipImpact, risk, ETA, decisions neededShort updates on a schedule
    CustomersWhat is affected and when the next update comesStatus page, email

    Update = What happened · Customer impact · Current status · Next step · Time of next update

    Example

    "14:10 UTC: Checkout is failing for about 30% of customers since 13:55. We rolled back release 4.2 and are watching error rates. Next update at 14:40."

    🔀 Change Management and Release Risk

    Many incidents are caused by changes. ITIL-style change management balances speed with risk.

    Change typeMeaningApproval
    StandardLow-risk, pre-approved, repeatable (for example a routine patch)Pre-approved
    NormalNeeds assessment of risk and impactChange authority or CAB
    EmergencyUrgent fix for a major incidentFast-track, reviewed afterwards
    📝
    In a DevOps setting, automated testing, small batches and peer review replace much of the manual approval. Use JSM to link each incident to the change that likely caused it.

    Jira Service Management & PagerDuty

    The two tools most teams use for service desks and on-call response, how they integrate, and how to run reviews and track incident metrics.

    🎫 Jira Service Management (JSM)

    JSM is an IT service management (ITSM) tool built on Jira. It manages incidents, service requests, problems and changes with a customer portal and agent queues.

    FeatureHow it helps
    Request types & portalCustomers raise tickets in a structured form; fields drive routing.
    QueuesAgents see tickets grouped by priority, status or team.
    SLAsGoals such as time to first response and time to resolution, with timers and breach alerts.
    Automation rulesAuto-assign, escalate when an SLA is near breach, notify channels.
    Linked issuesLink incident → problem → change to see the full story.
    Knowledge base & reportsDeflect repeat questions; track volume, SLA and resolution trends.

    📟 PagerDuty

    PagerDuty turns monitoring alerts into notified, tracked incidents for the right on-call person.

    ConceptMeaning
    ServiceA component being monitored and owned by a team.
    IntegrationMonitoring tools (Datadog, CloudWatch, Prometheus) send events to a service.
    On-call scheduleWho is responsible, and when (rotations, overrides).
    Escalation policyWho is notified next if the first responder does not acknowledge in time.
    UrgencyHigh urgency notifies immediately; low urgency can wait for working hours.
    Status page & analyticsCommunicate with stakeholders; report MTTA, MTTR and alert volume.

    Alert → PagerDuty incident → on-call paged → Acknowledge → (no ack: escalate) → Resolve → JSM ticket and review

    📘 Runbooks, ChatOps and Tool Integration

    A runbook is a step-by-step guide for a known alert (for example "database connections exhausted"). Good runbooks cut diagnosis time and let less experienced engineers respond safely. ChatOps brings alerts and actions into Slack or Microsoft Teams so everyone sees the same timeline.

    Integration stepResult
    Monitoring tool sends events to a PagerDuty serviceAlerts become tracked incidents
    PagerDuty notifies on-call and posts in the incident channelFast, visible response
    PagerDuty creates or updates a linked Jira Service Management ticketOne record for SLA, history and audit
    Resolving the incident updates both toolsConsistent status and clean reporting

    📝 Post-Incident Review and Metrics

    Review sectionContent
    Summary and impactWhat happened, who was affected, for how long
    TimelineDetection, response, mitigation, resolution with timestamps
    Contributing factorsTechnical and process causes, not individuals
    What went well / poorlyLearning for the whole organisation
    Action itemsOwner, due date, tracked in the backlog
    MetricWhy track it
    Incidents by severityTrend of customer-impacting problems
    Repeat incidentsShows whether problem management works
    MTTA / MTTR trendSpeed of response and recovery
    Action completion rateWhether reviews lead to real change
    Example

    Five incidents were restored in 20, 35, 50, 15 and 30 minutes. Total = 150 minutes, so MTTR = 150 ÷ 5 = 30 minutes.

    Module 07 · Advanced · Service Metrics

    SLA Fundamentals & Metrics

    Define targets and learn the core formulas: SLA, SLO, SLI, MTTR, MTBF, availability and error budgets, with worked calculations.

    📐 SLA, SLO, SLI and OLA

    TermMeaningExample
    SLI (indicator)A measured value of service behaviourPercentage of successful requests
    SLO (objective)Internal target for an SLI99.9% of requests succeed each month
    SLA (agreement)Customer-facing commitment, often with penaltiesCritical tickets resolved within 4 hours; credits if missed
    OLA (operational level)Internal agreement between teams that supports an SLAInfrastructure team responds to app team within 30 minutes
    💡
    Set the SLO tighter than the SLA so you get an early warning before you breach the contract.

    ✍️ Designing a Good SLA

    A strong SLA is specific, measurable and achievable. It usually contains: scope of the service, support hours, targets by priority, exclusions, how performance is measured, reporting frequency and remedies for a miss.

    Priority (example)First responseResolution target
    P1 Critical15 minutes4 hours
    P2 High30 minutes8 hours
    P3 Medium4 business hours3 business days
    P4 Low1 business day10 business days
    🚨
    Do not promise targets you cannot measure. If the tool cannot report it reliably, fix the measurement before signing the SLA.

    📊 Core Service Metrics

    MetricMeaningFormula
    MTTDMean time to detectTotal detection time ÷ incidents
    MTTAMean time to acknowledgeTotal time to acknowledge ÷ incidents
    MTTRMean time to restore/resolveTotal repair time ÷ incidents
    MTBFMean time between failuresOperating time ÷ number of failures
    AvailabilityShare of time the service works(Total time − downtime) ÷ total time × 100
    SLA complianceTickets that met the SLATickets within SLA ÷ total tickets × 100

    ⏱️ Availability and Error Budget

    Each extra "nine" shrinks the allowed downtime sharply. Values below use a 30-day month (43,200 minutes).

    Availability targetAllowed downtime / 30 days
    99%7.2 hours (432 minutes)
    99.9%43.2 minutes
    99.95%21.6 minutes
    99.99%4.32 minutes

    Error budget = 100% − SLO

    Example

    SLO 99.9% gives a 43.2-minute budget. After 30 minutes of downtime, 30 ÷ 43.2 ≈ 69% of the budget is used and 13.2 minutes remain. If the budget is nearly spent, slow risky releases and prioritise reliability work.

    🧮 Worked Calculations

    QuestionCalculationAnswer
    3 failures in 720 operating hours: MTBF?720 ÷ 3240 hours
    90 minutes of downtime in 30 days: availability?(43,200 − 90) ÷ 43,200 × 100About 99.79%
    46 of 50 P1 tickets resolved in time: compliance?46 ÷ 50 × 10092%
    SLO 99.95%: monthly budget?0.05% × 43,20021.6 minutes
    💡
    When asked for "availability", always state the period (for example 30 days) and whether planned maintenance is excluded.

    Module 08 · Expert · Reporting

    SLA Tracking & Breach Management

    Track SLAs in real tools, report to different audiences, manage breaches, and use burn rate and percentiles for honest reporting.

    🧭 Tracking SLAs in Practice

    PracticeWhy it matters
    Clear start/stop rulesDefine when the clock starts (ticket created) and stops (resolved).
    Pause conditionsPause the SLA clock while "Waiting for customer"; log every pause.
    Business-hours calendarsCount only agreed working hours for non-24x7 services.
    Breach warningsAlert at about 75% of the time elapsed so someone can act before the breach.
    Dashboards and weekly reviewTrack compliance, MTTR trend, backlog age and repeat incidents.
    Breach handlingLog it, find the cause, inform the customer, apply service credits if contracted.

    📺 Dashboards and Reporting Cadence

    AudienceShowsCadence
    EngineersLive SLA timers, open breaches, alert volumeDaily / real time
    Delivery ManagerCompliance by priority, MTTR trend, backlog age, repeat incidentsWeekly
    LeadershipSLA compliance, availability vs SLO, top risks, actionsMonthly
    CustomersAgreed service report and credits if duePer contract

    Mix leading indicators (tickets near breach, alert volume, backlog age) with lagging indicators (monthly compliance, availability) so that you can act before the month ends.

    🔧 Breach Management and Continuous Improvement

    StepAction
    1. DetectAlert at about 75% of elapsed time so action is possible before breach
    2. RespondEscalate, reassign or add help
    3. RecordLog the breach with reason (capacity, wrong routing, waiting on third party)
    4. AnalysePareto the breach reasons across the month
    5. FixUpdate routing, staffing, automation or the SLA itself
    6. ReportTell the customer, apply service credits if the contract says so
    Example

    A contract gives a 10% service credit when availability falls below 99.9%. If last month was 99.7%, the credit applies; the review should also show how much of the error budget was spent and by which causes.

    🧪 Advanced: Burn Rate, Percentiles and Honest Reporting

    Burn rate is how fast the error budget is consumed compared with the allowed pace. A burn rate of 1 uses exactly the whole budget by the end of the window; a burn rate of 2 would exhaust it in half the time, so alert early.

    Prefer percentiles (p90, p95) over averages: an average resolution time hides the slow tickets that actually breach SLAs. Segment results by priority and customer tier.

    Example

    200 tickets were raised and 184 met their SLA: compliance = 184 ÷ 200 = 92%. Against a 95% target that is a miss of 3 points, so review the 16 breaches by cause before the next cycle.

    🚨
    Beware of gaming: closing tickets early, pausing clocks unnecessarily or reclassifying priority improves the number but not the customer experience.

    Practice: Stabilising a Delivery Pipeline

    Apply the four technical skills to one realistic scenario.

    🏗️ Scenario

    A product team of 40 engineers deploys once a month. Builds and regression tests are run by hand, and 25% of deployments need a rollback. Monitoring alerts go to a shared email inbox, so SEV1 incidents are noticed 45 minutes late on average. Last month SLA compliance was 88% against a 95% target, and availability was 99.7% against a 99.9% SLO. Leadership has asked for a one-page improvement plan and a monthly service report.

    0 / 0 correct

    1️⃣ Task 1 · SDLC Automation & DevOps

    ✍️ Which automation would you introduce first, and how will you measure improvement?
    Model answer: Start with CI on every commit plus automated unit, API and smoke/regression tests with quality gates, then scripted deployments with rollback (blue-green or canary). Measure with DORA metrics: deployment frequency, lead time for changes, change failure rate and time to restore.
    Q. Which metric best shows whether automated tests and quality gates improve release quality?
    • A Number of commits
    • B Meeting attendance
    • C Change failure rate
    • D Story points per sprint

    What is a Jira Administrator? Role, Products & Building Blocks

    Start from zero: what Jira is, what an admin owns, and how projects, workflows, fields and permissions connect.

    0 / 0 correct

    🧭 What is a Jira Administrator?

    A Jira Administrator configures and governs Jira so teams can track work consistently, securely and with little friction. The admin does not just click settings - they translate how teams really work into projects, workflows, fields, permissions and queries, and keep the instance clean as it grows.

    ⚙️
    Configure
    Projects, schemes, boards, request types.
    🔀
    Design workflows
    Statuses, transitions, rules.
    🔐
    Control access
    Permissions, roles, issue security.
    🧩
    Shape data
    Custom fields, screens, contexts.
    🔎
    Query & report
    JQL, filters, dashboards.
    🛡️
    Govern
    Standards, clean-up, audit, performance.
    💡
    Golden rule of Jira admin: start simple, standardise, and change only when a real need appears. Over-customised Jira is slow, confusing and hard to migrate.

    Set up projects the right way: schemes, boards, request types, portals, queues and SLAs.

    🏗️ Project Types & Templates

    ChoiceCompany-managedTeam-managed
    Controlled byJira adminsProject admins (team)
    SchemesShared across projectsPrivate to the project
    Best forStandard processes at scaleFast-moving independent teams
    GovernanceStrong, centralLight, flexible
    • Pick the template (Scrum, Kanban, Bug tracking, IT service) after you understand the process.
    • Use a clear project key (e.g. ENG, HR) - it appears in every issue key and is hard to change later.

    🗂️ Schemes Explained

    A scheme bundles configuration so many projects can share it.

    SchemeDecides
    Issue type schemeWhich issue types a project has
    Workflow schemeWhich workflow each issue type uses
    Issue type screen schemeWhich screen scheme each issue type uses
    Screen schemeWhich screen is used for Create, Edit, View
    Field configuration schemeRequired / optional / hidden fields
    Permission schemeWho can do what
    Notification schemeWho gets email for which events
    Issue security schemeWho can see which issues
    💡
    Changing a shared scheme changes every project using it. Check the "Used by" list before editing.

    📋 Boards, Sprints & Releases

    • Scrum board: sprints, backlog, velocity, burndown. Kanban board: continuous flow, WIP limits.
    • A board is driven by a filter (JQL); columns map to workflow statuses.
    • Versions track releases; components split a project into parts with default assignees.
    EXAMPLE · Board filter

    Board shows team issues: project = ENG AND resolution = Unresolved ORDER BY Rank. If an issue is missing from the board, the filter is the first thing to check.

    🛎️ JSM: Request Types, Portals & Queues

    • A request type is what customers see on the portal (e.g. "Get IT help"). It maps to an issue type and has its own form fields.
    • Portal: the customer-facing site; group request types for easy finding.
    • Queues are JQL-based lists agents work from (e.g. "Unassigned", "Breaching soon").
    • Knowledge base suggestions can deflect tickets before they are raised.
    ITSM practiceTypical issue type
    IncidentService disruption - restore fast
    Service requestStandard request - e.g. new laptop
    ProblemRoot cause of repeated incidents
    ChangeControlled modification with approval

    ⏱️ JSM: SLAs, Customers & Agents

    • An SLA has a goal (e.g. first response in 4 h), a start, pause and stop condition, and a working-hours calendar.
    • Pause the clock when waiting for the customer; stop when the first agent response or resolution happens.
    • Customers raise requests (free in many setups); agents are licensed users who work them.
    • Customer permissions decide who may raise requests: anyone, logged-in, or allowed domains/organizations.
    EXAMPLE · SLA

    Goal: resolve P1 incidents in 4 working hours. Start = created; Pause = "Waiting for customer"; Stop = Resolved. Add a "Breaching soon" queue and a warning automation.

    🤖 Automation & Notifications

    • Automation rule = Trigger → Condition → Action (e.g. when issue is created in HR and Priority is High, assign to the HR lead).
    • Use automation for repetitive routing, reminders, approvals and field updates - fewer manual errors.
    • Notification schemes should be tuned to avoid email overload; use watchers and Slack/Teams integrations instead of notifying everyone.

    • B A JQL-driven list agents work from

    Custom Workflow Design

    Design workflows that match real processes, enforce rules and stay maintainable.

    0 / 0 correct

    🔀 Workflow Basics

    StatusWhere an issue is now (To Do, In Review, Done).
    TransitionMove between statuses (e.g. Start progress).
    Initial statusStatus given when an issue is created.
    ResolutionWhy an issue is closed: Done, Won't do, Duplicate.
    Workflow schemeMaps issue types to workflows for a project.
    Draft workflowEditable copy used to change an active workflow.

    🏷️ Statuses & Categories

    Status categoryMeaningExamples
    To DoNot startedOpen, Backlog
    In ProgressBeing workedIn Development, In Review
    DoneFinishedDone, Closed, Resolved
    • Categories drive board columns, reports and the statusCategory JQL field.
    • Reuse statuses and keep names short and consistent across workflows.

    🧰 Conditions, Validators & Post Functions

    Rule typeRunsPurposeExample
    ConditionBefore the button showsHide the transitionOnly Project Role "QA" can see "Approve"
    ValidatorWhen transition is clickedBlock if data is wrongComment required to reject
    Post functionAfter transitionDo an actionSet Resolution, assign, update field
    💡
    Remember: Conditions hide, Validators block, Post functions act.
    • Use a transition screen to collect needed data at the moment it matters (e.g. Resolution, Root cause).
    • Use workflow properties (e.g. jira.permission.edit.group) for advanced control; test carefully.

    📐 Designing a Good Workflow

    • Map the real process first on paper: states, owners, handoffs.
    • Keep statuses to what you report on or hand off; too many statuses slow people down.
    • Allow "global" or backward transitions only when needed (e.g. Reopen).
    • Document who owns each status and what "done" means.
    Anti-patternBetter
    25+ statuses5-8 meaningful statuses
    One workflow per team copyShared workflow with variants only where needed
    Rules in people's headsValidators and required fields
    Direct edits of live workflowDraft, test, publish in a quiet window

    🔁 Workflow Schemes & Changes

    • Assign workflows by issue type using a workflow scheme; unmapped types use the default workflow.
    • Editing an active workflow creates a draft; publishing may ask you to map existing issues if a status was removed.
    • Test in a sandbox or staging site first; back up or export before large changes.

    🧪 Worked Examples

    EXAMPLE · Bug workflow

    Open → In Progress → In Review → Testing → Done. Validator: Fix Version required to move to Done. Post function: set Resolution = Done. Condition: only developers see "Start progress".

    EXAMPLE · Change approval (JSM)

    Draft → Awaiting CAB approval → Approved → Implementing → Review → Closed. Approvers gate "Approved"; rejected moves to Closed with a required comment.

    Permission Schemes & Issue Security

    Control who can enter Jira, what they can do in each project, and which individual issues they can see.

    0 / 0 correct

    🔐 Permission Model

    Figure 4.1 · Layers of access

    🌍 Global vs Project Permissions

    TypeExamples
    GlobalAdminister Jira, Browse users, Create shared objects, Bulk change
    ProjectBrowse Projects, Create Issues, Edit Issues, Assign Issues, Transition Issues, Administer Projects
    Issue-levelIssue security levels
    ⚠️
    Browse Projects is required to see anything in a project, including issues, boards and filters showing its data.

    👥 Permission Schemes & Project Roles

    • A permission scheme grants each permission to groups, project roles, users or special types (Reporter, Assignee, Project Lead).
    • Prefer project roles (Developers, Admins, Users) - each project fills them differently, so one scheme serves many projects.
    • Prefer groups over individuals; avoid granting to "anyone" unless the project is intentionally public.
    Grant toUse when
    Project roleDifferent membership per project
    GroupSame people across many projects
    Single userRare; avoid for maintainability
    Reporter / AssigneeContext-based rights (e.g. reporter can edit own issue)
    EXAMPLE · Least privilege

    Contractors in role "Viewers" get Browse Projects only. Developers get Create, Edit, Transition. Only the Project Lead and Admin role get Administer Projects.

    🕶️ Issue Security Schemes

    • An issue security scheme defines security levels (e.g. Public, Internal, HR-only). Each level lists who may see issues at that level.
    • Set a default level on the scheme; users with "Set Issue Security" can change it per issue.
    • A user must both have Browse Projects and belong to the level to see the issue.
    EXAMPLE · HR cases

    Levels: Employee-visible (all staff), HR-only (role HR), Confidential (HR Lead only). Grievances default to HR-only; an automation raises Confidential for legal terms.

    💡
    Use issue security for sensitive subsets inside a project. If a whole project is sensitive, use a separate project and permission scheme.

    🛎️ JSM Access & Customer Permissions

    • Agents use project roles and permissions; customers are not agents and raise requests via the portal.
    • Customer access options: only invited, any logged-in Atlassian account, or open to anyone with the portal link (including by email).
    • Organizations let customers share requests with their colleagues.

    ✅ Security Best Practices

    • Review admin groups and public / "anyone" grants quarterly; keep an audit log review.
    • Use SSO + MFA at organization level; offboard users promptly.
    • Test with "Permission helper" or Jira's permission tools before rolling out changes.
    Q. Which gives the best maintainability in a permission scheme?
    • A Granting rights to each user
    • B Granting rights to project roles
    • C Granting everything to "anyone"
    • D Duplicating a scheme per user

    TypeUseExample

    NumberCounts, valuesStory points, effort hours

    Select (single/multi), radio, checkboxControlled listsEnvironment, Region

    💡

    🎯 Contexts & Configuration

    • A field context defines where a field applies (all projects, selected projects, selected issue types) and its options and default value.
    • The same field can have different options per context (e.g. "Region" options differ per project).
    • A field configuration scheme sets whether each field is required, optional, hidden and its description/help text.
    • Always search for an existing field before creating a duplicate.
    EXAMPLE · Context

    Custom field "Environment" with options Dev/QA/Prod in project ENG, but Cloud/On-prem in project OPS - one field, two contexts.

    Issue type screen schemeWhich screen scheme each issue type uses
    Transition screenFields shown during a workflow transition
    ⚠️
    A field must be on the screen, in the right context and not hidden in the field configuration - otherwise users cannot see or edit it.

    🧹 Field Hygiene & Performance

    • Fewer, well-named fields are faster and easier to report on; unused fields can be trashed or hidden.
    • Limit the number of global-context fields with many options and avoid too many cascading selects.
    • Use a naming convention and descriptions: e.g. Team - Region.
    • Review and clean up regularly; changing a field type can lose data.

    🧪 Worked Example

    EXAMPLE · Add "Customer Impact" to bugs only
    1. Create a single-select field "Customer Impact" (None, Minor, Major, Critical).
    2. Limit its context to Bug issue type in the target projects.
    3. Add it to the Bug Create and Edit screens.
    4. Make it required in the field configuration for Bug.
    5. Test as a normal user and create a filter: "Customer Impact" = Critical AND resolution = Unresolved.

    🔎 JQL Basics

    A JQL query is field + operator + value, joined with AND, OR, NOT and optionally sorted by ORDER BY.

    EXAMPLE · Starter queries

    project = ENG AND status = "In Progress"
    assignee = currentUser() AND resolution = Unresolved
    created >= -7d ORDER BY created DESC

    OperatorMeaning
    = , !=Equals / not equals
    IN, NOT INMatches any of a list
    ~ , !~Contains text (text fields)
    > < >= <=Compare numbers and dates
    IS EMPTY / IS NOT EMPTYField has no value / has value
    WAS, CHANGEDHistory of values
    💡
    Quote values with spaces: status = "In Progress". Use resolution = Unresolved for open issues.

    🧮 Operators, Functions & History

    FunctionUse
    currentUser()Logged-in user
    openSprints() / closedSprints()Sprint-based queries
    startOfWeek(), endOfMonth()Date helpers
    membersOf("group")Users in a group
    unreleasedVersions()Versions not released
    linkedIssues(KEY)Issues linked to KEY
    EXAMPLE · History

    status CHANGED FROM "In Progress" TO "Done" DURING (startOfWeek(), now()) - issues finished this week.
    status WAS "Blocked" BEFORE -14d - issues blocked at some point before 14 days ago.

    • Sorting: ORDER BY priority DESC, created ASC.
    • Text search with ~ does not support a leading wildcard (like *bug).

    📋 Common Admin Queries

    GoalJQL
    Stale open issuesresolution = Unresolved AND updated <= -90d
    Unassigned issuesassignee IS EMPTY AND resolution = Unresolved
    No component setproject = ENG AND component IS EMPTY
    High priority openpriority in (Highest, High) AND statusCategory != Done
    Overdueduedate < now() AND resolution = Unresolved
    JSM breaching soonproject = SD AND "Time to resolution" < remaining("2h")
    📌
    JQL function and field names for SLAs come from JSM; confirm exact SLA names in your site before saving a queue.

    📊 Filters, Dashboards & Performance

    • Filters save a JQL query; share them with the right group/role. Dashboards display gadgets built on filters.
    • Boards, queues, gadgets and notifications can all depend on one filter - changing it affects them all.
    • Prefer indexed, specific fields; avoid broad unbounded queries, heavy text searches and deeply nested subqueries on large sites.
    • Use ORDER BY Rank for boards; limit gadget count on a dashboard.
    EXAMPLE · Dashboard

    "Service health": filter "Open P1 incidents", "SLA breaches this week", "Unassigned >24h", and "Created vs Resolved" - each backed by a named, owned filter.

    🤖 Scripting & Automation

    • Automation rules can use smart values (e.g. {{issue.key}}) and JQL conditions to branch and update fields.
    • Use scheduled rules with JQL to chase stale tickets and auto-close resolved ones.
    • Marketplace apps (e.g. ScriptRunner, Automation add-ons) extend JQL with extra functions and scripted post functions - test in staging; know the app's Cloud/Data Center differences.
    • The REST API supports bulk configuration and reporting; protect tokens and limit scopes.

    🏛️ Governance, Migration & Expert Practice

    • Governance: naming standards, request process for new fields/workflows, scheme ownership, regular clean-ups.
    • Change management: sandbox → UAT → production; release notes and a rollback plan.
    • Migration: audit and simplify before moving (Cloud migration assistant, project imports); map users, fields, workflows; verify counts after.
    • Monitoring: audit log, license usage, app health, index and performance checks (Data Center).
    • Data hygiene: archive old projects, remove unused schemes/fields, review automation usage.

    Module 07 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🧭 Role & Fundamentals

    What does a Jira Administrator do?
    Configures and governs Jira: projects, schemes, workflows, fields, permissions and JQL; supports users and keeps Jira consistent, secure and fast.
    Company-managed vs team-managed?
    Company-managed projects use shared schemes controlled by admins; team-managed projects are configured by the team, simpler but isolated and less standardised.
    What is a scheme and why use one?
    A reusable configuration bundle shared by projects, giving consistency and central control. Editing it changes every project using it.

    🔀 Workflows, Permissions & Fields

    Condition vs validator vs post function?
    Condition hides a transition; validator blocks it if data is invalid; post function performs an action after the transition.
    How do you design a permission scheme?
    Use least privilege with project roles and groups, grant Browse Projects to the right audience, and review "anyone" grants regularly.
    A field is missing on a screen. How do you debug?
    Check the screen, screen scheme, issue type screen scheme, field context and field configuration (hidden/required).

    🔎 JQL, JSM & Governance

    Find issues unresolved for 90 days without updates.
    resolution = Unresolved AND updated <= -90d
    How do you set up SLAs in JSM?
    Define goals per request type or priority, choose start/pause/stop conditions, set the working calendar, then add breach warnings through queues or automation.
    How do you manage change safely?
    Request process, sandbox testing, UAT, scheduled release, communication, and a rollback plan; review impact of shared schemes first.

    🏢 Scenario: IT Helpdesk Rollout

    A 600-person company needs an IT helpdesk in Jira Service Management. Employees raise incidents and requests via a portal. A manager approves hardware requests. P1 incidents must be resolved in 4 working hours. HR also wants a separate confidential area for employee cases.

    1️⃣ Task 1 · Project & Schemes

    ✍️ List what you configure to launch the helpdesk project.
    Model answer: IT service project (company-managed), portal and request types (Get IT help, New hardware, Report an incident), issue types mapped, notification scheme, customer permissions (company domain), agents and roles, queues and SLAs.
    Q. Before editing a shared notification scheme you should…
    • A Edit immediately
    • B Check which projects use it and assess impact
    • C Delete it
    • D Rename it

    2️⃣ Task 2 · Workflow

    ✍️ Design the hardware-request workflow with an approval step.
    Model answer: Waiting for approval → Approved → Ordered → Delivered → Closed, plus Declined. Approver-only condition on Approve, validator for comment on Decline, post function to set resolution and notify the requester.
    Q. Which rule is best to require a comment on Decline?
    • A Condition
    • B Validator
    • C Notification scheme
    • D Board column

    3️⃣ Task 3 · Security & Fields

    ✍️ How do you keep HR cases confidential and capture needed data?
    Model answer: Separate project with its own permission scheme, or an issue security scheme with levels (HR-only default). Custom fields scoped by context (Case type, Region), put on the right screens and required where needed.
    Q. A confidential HR project is best protected by…
    • A Anyone can browse
    • B A dedicated permission scheme and restricted roles
    • C Disabling notifications only
    • D A label "confidential"

    4️⃣ Task 4 · JQL & Queues

    ✍️ Write queues for "Unassigned P1" and "Open > 30 days".
    Model answer: Unassigned P1: project = SD AND priority = Highest AND assignee IS EMPTY AND resolution = Unresolved. Stale: project = SD AND resolution = Unresolved AND created <= -30d.
    Q. Which JQL lists unassigned open issues?
    • A assignee = EMPTY AND status = Done
    • B assignee IS EMPTY AND resolution = Unresolved
    • C assignee ~ none
    • D resolution = Unassigned

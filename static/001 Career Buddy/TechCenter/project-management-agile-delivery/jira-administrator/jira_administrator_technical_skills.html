    Jira Administration Fundamentals

    Start from zero: what a Jira Administrator does, how Cloud and Data Center differ, how identity and access work, and how projects are organised.

    🧭 What a Jira Administrator Does

    A Jira Administrator is the owner of how work is modelled and secured in Jira. Teams ask for new projects, fields, workflows, reports and integrations — the admin delivers them safely, consistently and at scale.

    🏗️
    Configure
    Projects, workflows, fields, screens and schemes.
    🔐
    Secure
    Users, groups, permissions, SSO and audit logs.
    ⚙️
    Automate
    Automation rules, scripts and integrations.
    🔌
    Integrate
    REST API, webhooks and Marketplace apps.
    🚚
    Migrate
    Cloud, Data Center and cloud-to-cloud moves.
    📊
    Govern
    Standards, clean-up, cost and licence control.
    💡
    Mindset: configure for the organisation, not for one team. Every change you make is multiplied across projects and users.

    ☁️ Jira Cloud vs Data Center

    Know both. Many organisations run Data Center today and are moving to Cloud — Atlassian has announced Data Center end of life on March 28, 2029.

    AreaJira CloudJira Data Center
    HostingAtlassian-hosted SaaSSelf-hosted (your servers / cloud IaaS)
    UpgradesContinuous, automaticYou plan and run upgrades
    ScalingManaged by AtlassianAdd nodes, tune JVM/DB, manage indexes
    Admin hubadmin.atlassian.com + Jira settingsJira administration console
    AuthenticationAtlassian accounts, SSO (SAML), SCIMLDAP/Crowd/SSO configured by you
    API tokensAPI token (Basic) / OAuth 2.0Personal Access Tokens (Bearer)
    AppsCloud apps (Forge/Connect)Server-style apps (UPM), installed by admin
    📌
    Always ask first: which deployment am I administering? Menus, limits and capabilities differ.

    🛡️ Atlassian Administration & Identity

    In Cloud, identity is managed at the organization level in Atlassian Administration.

    OrganizationTop-level container for sites, users and policies.
    SiteA Jira (or Confluence) instance such as company.atlassian.net.
    Verified domainProves you own an email domain so you can manage those accounts.
    Managed accountsAccounts controlled by your organization (can enforce SSO, 2FA).
    SAML SSO / SCIMSingle sign-on and automatic user provisioning/deprovisioning (via Atlassian Guard).
    Audit logRecord of who changed what in administration.
    ⚠️
    Remove leavers promptly. Orphaned accounts and unused licences are both a security and a cost risk.

    👥 Users, Groups & Roles

    Follow one rule: grant access to groups or roles, never to individuals.

    ConceptScopeUse
    UserIndividualHolds a licence and product access
    GroupSite/org-wideBulk access, e.g. jira-developers
    Project rolePer projectReusable meaning: Administrators, Developers, Viewers
    Application accessProduct-levelWho may use Jira Software / JSM
    Project leadPer projectOwner; can be a permission grantee
    Example

    A permission scheme says "Developers can Create Issues". Each project maps its own people to the Developers role. One scheme, many projects.

    🗂️ Projects & Issue Types

    Two project styles exist in Jira Cloud:

    🏢 Company-managed

    Configuration lives in shared schemes owned by Jira admins. Best for governance, consistency and cross-project reporting.

    🙋 Team-managed

    Each project has its own settings managed by project admins. Fast autonomy, less central control.

    Issue typeTypical use
    EpicLarge body of work
    Story / TaskDeliverable unit of work
    BugDefect
    Sub-taskPiece of a parent issue

    Atlassian Administration: Schemes, Workflows & Permissions

    The core of daily admin work: how schemes fit together, how to design workflows and fields, and how to control who can see and do what.

    🧩 How Schemes Fit Together

    In company-managed projects, a project is a bundle of schemes. Change a scheme and every project using it changes.

    SchemeControls
    Issue type schemeWhich issue types a project offers
    Workflow schemeWhich workflow each issue type uses
    Field configuration schemeRequired / hidden fields per type
    Issue type screen schemeWhich screens per type and operation
    Permission schemeWho can do what
    Notification schemeWho is emailed for which event
    Issue security schemePer-issue visibility levels
    💡
    Before editing a scheme, check "Used in X projects". Need a one-off? Clone it instead.

    🔄 Workflows

    A workflow is a set of statuses connected by transitions.

    ElementPurposeExample
    ConditionControls who sees the transitionOnly role QA sees "Approve"
    ValidatorBlocks if data is wrongResolution comment required
    Post functionRuns after the transitionAssign to reporter, set field
    PropertiesAdvanced behaviourStatus category / app flags
    ⚠️
    Editing an active workflow creates a draft; publishing may require mapping issues from removed statuses. Always test first.
    Design tip

    Keep workflows short and shared: 5–7 statuses covers most teams. Dozens of near-identical workflows become unmanageable.

    🧱 Fields, Contexts & Screens

    • Custom field – extra data on issues (e.g. Customer, Environment).
    • Context – limits a field's options/default to chosen projects and issue types.
    • Screen – the group of fields shown for Create / Edit / View.
    • Field configuration – required, hidden, description, renderer.
    📌
    Avoid field sprawl: reuse fields with contexts instead of creating "Priority – Team A", "Priority – Team B".

    🔐 Permissions, Notifications & Security

    Permission schemes grant permissions to groups, roles, users, application access, project lead, reporter or assignee.

    PermissionMeaning
    Browse ProjectsSee project and issues
    Create IssuesRaise new issues
    Edit IssuesChange fields
    Transition IssuesMove through workflow
    Administer ProjectsProject-level admin
    Administer Jira (global)Full site admin

    Issue security levels hide specific issues (e.g. HR or security incidents) even from people who can browse the project.

    ⚠️
    Never grant "Administer Jira" to "everyone" or to large groups. Review admins quarterly.

    🔎 JQL, Filters, Boards & Dashboards

    JQL is the glue behind boards, filters, dashboards and automation.

    JQLproject = ABC AND status != Done AND assignee = currentUser()
ORDER BY priority DESC, created ASC

resolution = Unresolved AND updated <= -14d
    ItemBuilt fromUsed by
    FilterJQLBoards, dashboards, subscriptions
    BoardA filterScrum / Kanban views
    DashboardGadgetsReporting
    💡
    Share filters with a group/project, not "Public", and give important ones an owner who will not leave.

    🧪 Safe Change Management

    1. Capture the request and the business reason.
    2. Check impact (which projects use this scheme?).
    3. Test in a sandbox / staging site.
    4. Back up or export configuration; define rollback.
    5. Release in a quiet window and announce it.
    6. Verify and document.
    ✅
    Document every change: what, why, who approved, when. Your audit trail is your protection.

    Automation Rules: Triggers, Smart Values & Governance

    Automate repetitive work: design rules, use smart values and branching, call other systems, and keep automation reliable.

    🤖 Anatomy of a Rule

    Every rule is When → If → Then.

    💡
    Scope: a rule can be single-project, multi-project or global. Prefer the narrowest scope that works.

    🧱 Triggers, Conditions & Actions

    Triggers
    Issue created, field changed, transitioned, scheduled, manual, incoming webhook, commented…
    Conditions
    Issue fields condition, JQL condition, user condition, if/else blocks, compare values.
    Actions
    Edit issue, transition, assign, comment, create issue/sub-task, send email, send web request, log action.
    Example: auto-assign bugs

    Trigger: Issue created → Condition: issue type = Bug → Action: assign to project lead → add comment Thanks {{issue.reporter.displayName}}, triaged.

    🧬 Smart Values

    Smart values are placeholders resolved at run time.

    Smart valueReturns
    {{issue.key}}Issue key, e.g. PROJ-12
    {{issue.summary}}Summary text
    {{issue.assignee.displayName}}Assignee name
    {{triggerIssue.key}}The original issue inside a branch
    {{now.plusDays(7)}}Date 7 days ahead
    📌
    Inside a branch, {{issue}} is the related issue and {{triggerIssue}} is the issue that started the rule.

    🌿 Branching & Related Issues

    Branches let one rule act on sub-tasks, linked issues, epic children, parent, or a JQL result.

    Example: close sub-tasks

    When a Story moves to Done → branch on sub-tasks → if status ≠ Done → transition to Done.

    ⚠️
    Avoid loops: a rule editing an issue can re-trigger itself. Add conditions (field changed) and review the "allow other rule actions to trigger this rule" setting.

    ⏰ Scheduled, Webhook & Web Requests

    • Scheduled trigger – run on a schedule over JQL results (e.g. nightly stale-issue reminder).
    • Incoming webhook – let an external system start a rule.
    • Send web request – call Slack, Teams, CI/CD or any REST API.
    Send web request (body){
  "text": "{{issue.key}} moved to {{issue.status.name}} by {{initiator.displayName}}"
}
    💡
    Store secrets in the rule's protected headers / secrets area, never in plain text comments.

    📈 Governance, Limits & Troubleshooting

    • Name rules clearly – [PROJ] Auto-assign new bugs; add owners and descriptions.
    • Check the audit log to see why a rule did or did not run.
    • Monitor usage – Cloud plans limit monthly rule runs; inefficient global rules waste them.
    • Check the rule actor – actions run as the actor; they need permission.
    • Review quarterly – disable or delete unused rules.
    ✅
    Rule of thumb: automate frequent, rule-based, low-judgement work first.

    REST API & Webhooks

    Integrate Jira with other systems: call the REST API securely, handle paging and rate limits, and react to events with webhooks.

    🔗 REST API Basics

    Jira exposes JSON over HTTPS. In Cloud the base path is https://YOUR-SITE.atlassian.net/rest/api/3/ (v2 also exists). Data Center uses /rest/api/2/.

    MethodUse
    GETRead (issue, search, fields)
    POSTCreate (issue, comment, webhook)
    PUTUpdate
    DELETERemove
    📌
    API v3 uses Atlassian Document Format (ADF) for rich text such as descriptions and comments; v2 accepts simple text/wiki markup.

    🔑 Authentication

    • API token + email (Basic) – simple scripts; token is a secret.
    • OAuth 2.0 (3LO) – apps acting for users with scopes.
    • Forge / Connect – Atlassian app platforms.
    • Data Center: Personal Access Token (Bearer).
    ⚠️
    Never hard-code tokens in code or Git. Use a secret manager, a service account with least privilege, and rotate/expire tokens.

    🧪 Common Calls

    Create an issue:

    curlcurl -u you@company.com:$API_TOKEN \
  -X POST -H "Content-Type: application/json" \
  https://YOUR-SITE.atlassian.net/rest/api/3/issue \
  -d '{"fields":{"project":{"key":"ABC"},
       "issuetype":{"name":"Task"},
       "summary":"Created from API"}}'

    Python – search with JQL (enhanced search):

    Pythonimport os, requests
auth = (os.environ["JIRA_EMAIL"], os.environ["JIRA_TOKEN"])
url = "https://YOUR-SITE.atlassian.net/rest/api/3/search/jql"
body = {"jql": "project = ABC AND resolution = Unresolved",
        "fields": ["summary", "status"], "maxResults": 50}
r = requests.post(url, json=body, auth=auth, timeout=30)
r.raise_for_status()
for i in r.json()["issues"]:
    print(i["key"], i["fields"]["summary"])

    🚦 Paging & Rate Limits

    • Page through results; request only needed fields. Enhanced JQL search pages with a nextPageToken; many other endpoints use startAt/maxResults.
    • 429 Too Many Requests – read Retry-After, wait, retry with exponential back-off.
    • Prefer bulk endpoints and webhooks over frequent polling.
    Retry pattern

    Attempt 1 fails with 429 → wait Retry-After seconds → retry → if still 429, double the wait up to a limit → log and alert.

    📡 Webhooks

    A webhook lets Jira push an event (issue created, updated, comment added…) to your URL in near real time.

    TypeNotes
    Admin-created (Jira settings → System → WebHooks)Set URL, events, optional JQL filter; does not expire
    REST-registered (apps/OAuth)Must be refreshed – they expire after 30 days
    Automation "Send web request"Rule-based outbound call with custom payload
    ⚠️
    Secure webhooks: use HTTPS, configure a secret and verify the HMAC signature, ignore replays, respond quickly (2xx) and process asynchronously.
    Verify signature (concept)expected = "sha256=" + hmac_sha256(secret, raw_body)
if not constant_time_equal(expected, header_signature): reject()

    ✅ Integration Best Practices

    1. Use a dedicated service account, not a person.
    2. Request the minimum scopes/permissions.
    3. Make handlers idempotent (safe to receive twice).
    4. Log, monitor, alert on failures.
    5. Version-pin and read Atlassian deprecation notices.

    Apps & Plugins: ScriptRunner, Advanced Roadmaps & Tempo

    Extend Jira responsibly: choose, evaluate and govern Marketplace apps, then use ScriptRunner, Advanced Roadmaps (Plans) and Tempo effectively.

    🛒 Marketplace & App Governance

    Apps add power and risk. Treat every app as a long-term commitment.

    CheckWhy
    Cloud / DC compatibilityVersion and platform must match
    Vendor support & roadmapAvoid abandoned apps
    Security & data handlingReview permissions and data residency
    Licence cost per userCosts grow with user count
    Migration pathDoes app data move to Cloud?
    💡
    Evaluate in a sandbox first and keep a register: app, owner, purpose, cost, renewal date.

    📜 ScriptRunner

    ScriptRunner brings Groovy scripting to Jira.

    ⚙️
    Workflow functions
    Custom conditions, validators and post functions.
    👂
    Listeners
    Run scripts on events like issue updated.
    🔎
    Custom JQL
    Search with functions such as linked-issue queries.
    🪄
    Behaviours / script fields
    Dynamic form behaviour and calculated fields.
    🖥️
    Script console
    Run one-off admin fixes (with great care).
    Groovy// Concept: set a field when an issue is created
if (issue.issueType.name == "Bug" && !issue.assignee) {
    // assign to project lead
}
    ⚠️
    Scripts run with power. Keep them in version control, test in a sandbox, comment them, and give each an owner. Prefer native features when they exist.

    🗺️ Advanced Roadmaps (Plans)

    In Jira Cloud this capability is called Plans (Premium/Enterprise). It supports cross-project planning.

    ConceptMeaning
    Issue sourcesBoards, projects or filters feeding the plan
    HierarchySub-task → Story → Epic → higher levels (e.g. Initiative)
    Teams & capacityWho works on what and how much
    DependenciesWhich work blocks other work
    Scenarios"What-if" changes before committing
    ReleasesGroup work into delivery milestones
    📌
    Admins configure the issue type hierarchy and permissions that decide who can create and edit plans.

    ⏱️ Tempo

    Tempo adds time, resource and cost management.

    🕒
    Timesheets
    Log and approve work time against issues.
    📅
    Planner
    Plan resources and capacity.
    💰
    Accounts / Cost Tracker
    Budgets, rates and billing/costs.
    🔌
    Tempo API
    Pull worklogs and reports into other tools.
    💡
    Typical admin tasks: configure work attributes and approval rules, set permissions, link accounts to projects, and secure Tempo API tokens.

    ⚖️ Choosing Native vs App

    1. Can native Jira (workflows, automation, Plans) solve it?
    2. If not, is a supported Marketplace app available?
    3. Only then consider custom scripts and document them.
    ✅
    Fewer moving parts = easier upgrades and migrations.

    Atlassian Cloud & Data Center Migrations

    Plan and execute migrations: assess, clean up, test, cut over and verify — plus the operations and governance skills expected at expert level.

    🧭 Choosing a Migration Path

    Atlassian announced Data Center end of life on March 28, 2029, so most roadmaps now include Cloud.

    PathTypical case
    Server/DC → CloudMove to SaaS using the Jira Cloud Migration Assistant (JCMA)
    Cloud → CloudMerge or split sites, consolidate organisations
    DC → DCHardware/hosting change or version upgrade
    💡
    Start early: large migrations usually need many months for assessment, testing and change management.

    🧹 Assessment & Clean-up

    • Inventory – projects, users, workflows, fields, apps, integrations, automations.
    • Archive/delete unused projects and inactive users.
    • Simplify duplicate fields, workflows and schemes.
    • App assessment – needed? available on Cloud? data migratable?
    • Check user emails – users are matched by email.
    Example decision

    App X has no Cloud data-migration path → decide: replace with native feature, choose an alternative, or export/re-create data.

    🧰 Tools: JCMA & Cloud-to-Cloud

    The Jira Cloud Migration Assistant (JCMA) assesses apps, runs pre-migration checks and migrates selected projects, users and groups. Cloud-to-cloud moves use Atlassian's cloud migration tooling.

    StepWhat to do
    AssessRun JCMA assessment; review apps and issues
    PrepareVerify domains, users, licences, sandbox
    TestRun test migrations; validate
    MigrateProduction run in agreed window
    VerifyChecklist and user acceptance

    🧪 Test Migrations & Cutover

    1. Run at least one full test migration; record duration and defects.
    2. Have users perform UAT.
    3. Define freeze window and communication plan.
    4. Prepare rollback criteria – keep source read-only until verified.
    5. Cut over, redirect URLs, update integrations and webhooks.
    ⚠️
    Integrations are often forgotten: re-point REST clients, webhooks, SSO and apps to the new site.

    ✅ Post-Migration Verification

    • Permissions, groups and roles behave correctly.
    • Workflows, fields and screens match.
    • Automation rules/scripts re-created and tested.
    • Attachments, comments and links intact.
    • Reports, dashboards and filters return the same results.
    • Licences and billing are correct.
    ✅
    Keep a hyper-care period: a dedicated channel and fast fixes for the first weeks.

    🏭 Data Center Operations & Governance

    • Clustering – multiple nodes behind a load balancer for availability and scale.
    • Performance – JVM/heap, database tuning, indexing, attachment storage.
    • Upgrades – test in staging; check app compatibility first.
    • Backups – database + shared home; test restore.
    • Governance – naming standards, change board, quarterly clean-up, cost and licence reviews.
    📌
    An expert admin runs Jira like a product: roadmap, standards, metrics and stakeholder communication.

    Module 07 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🧭 Role & Administration

    What does a Jira Administrator do?
    Configures and secures Jira: users and groups, projects, workflows, fields, permissions and notifications; supports automation and integrations; manages apps, upgrades and migrations; and governs standards and cost.
    Company-managed vs team-managed projects?
    Company-managed projects use shared schemes controlled by Jira admins (consistent, governed). Team-managed projects have project-level settings controlled by project admins (fast, autonomous but less standardised).
    How do you grant permissions safely?
    Use permission schemes with groups and project roles, apply least privilege, avoid individual grants, and review access regularly.
    How do you change a workflow used by active projects?
    Edit as a draft, assess impacted projects, map issues from removed statuses, test in a sandbox, publish in a quiet window and communicate.

    ⚙️ Automation, API & Apps

    Explain the structure of an automation rule.
    Trigger (when) → conditions (if) → actions (then), optionally with branches for related issues and smart values for dynamic data.
    How do you avoid rule loops?
    Add conditions (e.g. field actually changed), limit scope, and review the setting that lets other rule actions trigger the rule.
    How would you authenticate and call the REST API securely?
    Use a service account with an API token or OAuth 2.0, store secrets in a vault, request minimum scopes, page results, and respect 429 Retry-After with back-off.
    How do you secure a webhook receiver?
    HTTPS, a shared secret with HMAC signature verification, replay protection, quick 2xx responses with async processing, and idempotent handling.
    When would you use ScriptRunner?
    When native workflows/automation cannot meet a need — complex validators, listeners, custom JQL or behaviours — with sandbox testing, version control and an owner.

    🚚 Migration & Governance

    How would you plan a Data Center to Cloud migration?
    Assess and clean up, run app assessment, decide on app replacements, prepare users/domains, run test migrations with UAT, plan cutover and rollback, migrate, verify and provide hyper-care.
    Why run test migrations?
    They reveal data issues, app gaps and timing, so the production cutover is predictable and low-risk.
    What is the Data Center end-of-life date?
    March 28, 2029, as announced by Atlassian — so long-term plans should include Cloud.
    How do you keep a large Jira instance healthy?
    Standards and naming, scheme consolidation, regular clean-up, app/automation reviews, monitoring, documentation and a change process.

    Work through a realistic end-to-end scenario covering configuration, automation, integration, apps and migration.

    0 / 0 correct

    🏢 Scenario: Northwind Corp

    Northwind runs Jira Data Center with 120 projects, 3,000 users and many Marketplace apps, and plans to move to Jira Cloud. Problems today: contractors have broad access, 40 near-identical workflows exist, a nightly report is manual, an external CI tool polls the API every 5 seconds, and teams ask for Tempo, ScriptRunner and Plans.

    1️⃣ Task 1 · Access & Schemes

    ✍️ How would you reduce contractor access risk and simplify the 40 workflows?
    Model answer: Create contractor groups/roles with least privilege and time-boxed review; remove direct user grants; audit "Administer Jira". Consolidate workflows into a few shared ones, map issue types through workflow schemes, test in staging and migrate issues via draft publish.
    Q. Which is the best way to grant contractors access to one project?
    • A Make them Jira admins
    • B Add them to a scoped group/role
    • C Share an employee account
    • D Use anonymous access

    2️⃣ Task 2 · Automation

    ✍️ Design a rule that posts stale-issue reminders every Monday.
    Model answer: Scheduled trigger (weekly Monday) with JQL like resolution = Unresolved AND updated <= -14d; branch or loop over results; add comment/email with {{issue.key}} and assignee; check the audit log and rule actor permissions.
    Q. Which trigger best runs a rule every Monday?
    • A Issue created
    • B Scheduled
    • C Comment added
    • D Field changed

    3️⃣ Task 3 · API & Webhooks

    ✍️ The CI tool polls every 5 seconds and receives 429 errors. What do you change?
    Model answer: Replace polling with a webhook (secured by a secret, HTTPS, idempotent); if polling remains, use JQL filters, limited fields, paging, and respect Retry-After with exponential back-off.
    Q. What is the right response to HTTP 429?
    • A Retry immediately in a loop
    • B Wait for Retry-After then retry with back-off
    • C Delete the issue
    • D Switch to HTTP

    4️⃣ Task 4 · Apps

    ✍️ How do you decide on Tempo, ScriptRunner and Plans requests?
    Model answer: Define the need, check native options, evaluate each app in a sandbox (compatibility, security, cost, Cloud migration path), assign owners, document configuration and review renewals.
    Q. Plans (Advanced Roadmaps) is mainly for…
    • A Time approvals
    • B Cross-project planning and capacity
    • C User provisioning
    • D Backups

    5️⃣ Task 5 · Migration

    ✍️ Outline the migration plan to Jira Cloud.
    Model answer: Inventory and clean up; app assessment and decisions; verify domains and emails; run JCMA assessment and test migrations with UAT; plan cutover, freeze and rollback; migrate; re-point integrations and webhooks; verify permissions, workflows, automations, reports; hyper-care and decommission.
    Q. What should happen before production cutover?
    • A Skip testing
    • B Run test migrations and UAT
    • C Delete the old system
    • D Disable SSO

    Module 01 · Basic · Foundations

    Technical Skills Fundamentals for the Agile PM

    Start from zero: why an Agile Project Manager needs tools, what each of the six tools is for, and how they connect on one project.

    🧭 Why tools matter

    An Agile Project Manager does not write code, but must know the tools that hold the plan, the work, the documents and the releases. Good tool skill means the team and sponsors see the same truth without long meetings. This course covers six tools: Jira, Azure DevOps, Asana, MS Project (Agile views), Confluence and Release Management Software.

    🎫
    Track work
    Jira, Azure DevOps and Asana hold backlogs, tasks and boards.
    🗓️
    Plan and schedule
    MS Project and roadmap views show dates, dependencies and baselines.
    📚
    Share knowledge
    Confluence keeps plans, decisions and meeting notes in one place.
    🚀
    Ship safely
    Release management software controls deployments, approvals and rollback.
    EXAMPLE · One question, four tools

    “What is in the next release?” Jira shows the sprint items, Confluence holds the release notes draft, MS Project shows the go-live milestone and the release tool shows the deployment status.

    ⚖️ Choosing a tool

    QuestionPoints toward
    Is the team mostly software engineers?Jira or Azure DevOps
    Does the company already use Microsoft 365 and Azure?Azure DevOps and MS Project
    Are most users non-technical?Asana
    Is a critical path schedule required?MS Project
    Is documentation heavy?Confluence

    ⚠️

    Module 02 · Technical Skill 1 · Jira

    Jira

    Set up projects, run sprints, read agile reports, write JQL and build dashboards.

    🎫 What Jira is and its building blocks

    Jira (Atlassian) tracks work as issues in projects. Scrum and Kanban templates give boards, backlogs and reports.

    ItemMeaningExample
    ProjectContainer for issuesPORTAL
    Issue typeKind of work: Epic, Story, Task, Bug, Sub-taskStory: customer login
    EpicLarge body of work split into storiesPayments
    ComponentPart of the productMobile, API
    Version (release)Group of work shipped togetherv1.2
    LabelFree tagsecurity
    📝
    Jira offers company-managed and team-managed projects. Company-managed ones share schemes across projects. Team-managed ones are configured per project.

    🔄 Workflows and issue statuses

    ElementMeaningExample
    StatusWhere the issue isTo Do, In Progress, In Review, Done
    TransitionMove from one status to anotherIn Progress → In Review
    ResolutionWhy an issue is closedDone, Won’t Do, Duplicate
    Condition / validatorRule that allows or blocks a transitionCannot close with open sub-tasks
    EXAMPLE · Workflow

    A bug moves To Do → In Progress → In Review → Done. A validator requires a fix version before Done so release notes are accurate.

    🏃 Scrum boards, backlog and sprints

    StepWhat you do in Jira
    1. BacklogCreate and order issues, estimate with story points
    2. Create sprintName it and set a goal
    3. PlanDrag issues into the sprint within capacity
    4. Start sprintSet dates and start
    5. TrackUse the board and daily check-in
    6. Complete sprintMove unfinished issues to the backlog or next sprint
    💡
    Always write a sprint goal. It appears on the board and in the sprint report.

    📊 Agile reports

    ReportShowsUse
    Burndown chartWork remaining in the sprintSprint progress
    Burnup chartWork done against total scopeScope change
    Velocity chartCommitted versus completed per sprintForecasting
    Sprint reportWhat was done, not done, addedReview and retrospective
    Cumulative flow diagramIssues per status over timeSpotting bottlenecks
    Control chartCycle time for issuesPredictability
    EXAMPLE · Reading velocity

    Committed 32, completed 26. Completion rate = 26 ÷ 32 = 81%. Plan next sprint closer to 26 to 28 than 32.

    🔎 JQL and filters

    JQL (Jira Query Language) searches issues. Save a query as a filter and reuse it on boards and dashboards.

    GoalJQL
    Open high-priority bugs in the current sprintproject = PORTAL AND type = Bug AND sprint in openSprints() AND priority = High AND statusCategory != Done
    Issues not assignedproject = PORTAL AND assignee is EMPTY
    Done in last 7 daysproject = PORTAL AND statusCategory = Done AND resolved >= -7d
    Issues in a releaseproject = PORTAL AND fixVersion = "v1.2"
    💡
    Use statusCategory instead of listing every Done-like status. It stays correct when the workflow changes.

    📈 Dashboards, roadmaps and links

    FeaturePurpose
    Dashboard gadgetsFilter results, pie charts, sprint health, created vs resolved
    Roadmap (timeline)Epics on a time axis for stakeholders
    Plans (Premium)Cross-team planning, formerly Advanced Roadmaps
    Issue linksblocks, is blocked by, relates to, duplicates
    Releases pageProgress of each version
    EXAMPLE · Dependency

    Story A “blocks” story B. The link shows on both issues, so the Agile PM can raise the dependency in the sprint review.

    🤖 Automation and permissions

    ItemHow it worksExample
    Automation ruleTrigger → condition → actionWhen issue moves to Done, comment and notify
    Permission schemeWho can create, edit, transitionOnly leads can release
    Notification schemeWho gets which emailsAssignee and reporter on comment
    ⚠️
    Automation can flood people with notices. Test rules on a small project first and name every rule clearly.

    🪤 Jira traps

    TrapBetter approach
    Too many custom fieldsKeep only fields used in reports
    One status per personStatuses show state, not owner
    Never grooming the backlogRefine each sprint
    Counting unfinished storiesCount only Done in velocity
    Dashboards no one readsDesign for a named audience

    Module 03 · Technical Skill 2 · Azure DevOps

    Azure DevOps

    Use Azure Boards, capacity planning, queries, dashboards and pipelines to manage work from backlog to release.

    🧩 What Azure DevOps includes

    ServicePurpose
    Azure BoardsWork items, backlogs, boards, sprints
    Azure ReposGit repositories and pull requests
    Azure PipelinesBuild, test and deploy automation
    Azure Test PlansManual and exploratory testing
    Azure ArtifactsPackage feeds
    💡
    The main strength is that code, builds, tests and work items link together, giving traceability from requirement to release.

    📋 Work item types and processes

    ProcessTypical types
    BasicEpic, Issue, Task
    AgileEpic, Feature, User Story, Task, Bug
    ScrumEpic, Feature, Product Backlog Item, Task, Bug, Impediment
    CMMIEpic, Feature, Requirement, Task, Bug, Change Request, Risk, Issue
    EXAMPLE · Choosing a process

    A team following Scrum uses the Scrum process so work appears as Product Backlog Items and impediments have their own type.

    📍 Area paths and iteration paths

    PathMeaningExample
    Area pathWhich team or product area owns the itemPortal\Payments
    Iteration pathWhich sprint or release the item is planned inPortal\Sprint 6
    📝
    Teams are linked to area paths and iterations, so each team sees only its own backlog and sprints.

    🧮 Boards, sprints and capacity

    ItemWhat it does
    BacklogOrdered list of Features and stories
    Sprint backlogItems planned in the iteration
    TaskboardTasks by state for the sprint
    Kanban boardFlow view with columns and WIP limits
    CapacityHours per person per day and days off
    Capacity exampleValue
    Team members5
    Productive hours per day each6
    Sprint days10
    Days off (one person)2
    Capacity5 × 6 × 10 − 2 × 6 = 288 hours
    EXAMPLE · Capacity check

    If tasks total 320 hours against 288 hours capacity, the taskboard shows the team over capacity. Remove or defer work.

    🔎 Queries and dashboards

    FeatureUse
    Work item queries (WIQL)Filter by type, state, area and iteration
    Query chartsPie and bar charts from queries
    Dashboard widgetsSprint burndown, velocity, cumulative flow, query tile
    Delivery PlansTimeline across teams
    Analytics viewsPower BI reporting
    EXAMPLE · Query

    Active bugs in the current iteration, area Portal, sorted by severity. Pin the result as a dashboard tile for the sponsor.

    ⚙️ Pipelines and release control

    ElementMeaning
    Pipeline (YAML)Code that defines build and deploy steps
    StageGroup of jobs, for example Build, Test, Deploy
    EnvironmentTarget such as Staging or Production
    Approvals and checksManual sign-off before an environment deploy
    Branch policyPull request review and build must pass
    ⚠️
    Production deployments should have approvals and checks. Do not allow direct pushes to the main branch.

    🪤 Azure DevOps traps

    TrapBetter approach
    Wrong process chosen at startPick the process that matches the method
    Empty iteration pathsSet sprint dates so burndown and capacity work
    Work items not linked to commitsLink commits and pull requests to items
    Dashboards with no ownerName an owner and audience for each

    Module 04 · Technical Skill 3 · Asana

    Asana

    Plan non-technical and cross-team work with tasks, timelines, dependencies, status updates and portfolios.

    ✅ What Asana is and its building blocks

    Asana is a flexible work management tool. It suits marketing, operations and PMO teams, and can run light agile with sections and custom fields.

    ItemMeaningExample
    ProjectContainer for tasksPortal Launch
    TaskOne piece of work with owner and due dateWrite launch email
    SubtaskPart of a taskDraft, review
    SectionGroup or columnSprint 6
    Custom fieldExtra data such as priority or pointsStory points
    MilestoneTask marking a key pointGo-live

    👁️ Views

    ViewBest for
    ListSimple to-do work
    BoardKanban-style flow
    TimelineDates and dependencies, Gantt-like
    CalendarDue dates and events
    WorkloadWho is overloaded (paid plans)
    📝
    Feature availability depends on the Asana plan. Confirm which features your organisation has.

    🔗 Dependencies and milestones

    ItemWhat it does
    DependencyA task waits for another to finish
    MilestoneMarks a key date, no work attached
    TimelineShows the effect of moving a date
    Critical datesHighlight what drives the end date
    EXAMPLE · Dependency

    The “Publish launch page” task depends on “Legal approval”. When legal slips two days, the timeline shows the launch page moving too.

    🤖 Rules, forms and templates

    FeatureExample
    RulesWhen task moves to Review, assign to the approver
    FormsIntake form creates tasks with required fields
    TemplatesReuse a launch checklist each time
    Custom fieldsPriority, Effort, Team
    💡
    A request form with required fields reduces back-and-forth and keeps new work in one place.

    📣 Status updates, goals and portfolios

    FeaturePurpose
    Project status updateOn track, At risk or Off track with a written note
    PortfolioStatus of many projects in one view
    GoalsLink work to objectives
    Reporting dashboardsCharts across projects
    EXAMPLE · Status

    At risk: “Legal approval is two days late. Decision needed: move launch or shorten testing.” The note is short and contains the ask.

    🪤 Asana traps

    TrapBetter approach
    Using Asana as a full Scrum toolUse Jira or Azure Boards for engineering sprints, link when needed
    Tasks with no owner or dateRequire both
    No naming rulesAgree sections and field names
    Status updates never writtenSchedule a weekly update

    Module 05 · Technical Skill 4 · MS Project (Agile Views)

    MS Project (Agile Views)

    Build schedules with dependencies and baselines, and use board and sprint views to bridge agile and traditional plans.

    🗓️ What MS Project does

    Microsoft Project is a scheduling tool. It calculates dates from task durations, dependencies and resources. Its agile support, such as board and sprint views, lets one file show both the traditional plan and agile work.

    📝
    Features differ between Project desktop, Project for the web and Planner. Confirm which views and agile features your edition includes.
    ItemMeaningExample
    TaskUnit of scheduled workBuild login
    Summary taskGroup of tasksPhase 1
    MilestoneZero-duration markerGo-live
    DurationWorking time to finish5 days
    ResourcePerson or equipmentDeveloper 1
    BaselineSaved original planBaseline 0

    🔗 Dependencies and the critical path

    LinkMeaning
    Finish-to-Start (FS)B starts when A finishes
    Start-to-Start (SS)B starts when A starts
    Finish-to-Finish (FF)B finishes when A finishes
    Start-to-Finish (SF)B finishes when A starts, rare
    Lead / lagOverlap or delay between tasks
    TaskDurationDepends on
    A5 days—
    B3 daysA
    C6 days—
    D4 daysB and C
    EXAMPLE · Critical path

    Path A → B → D = 5 + 3 + 4 = 12 days. Path C → D = 6 + 4 = 10 days. The critical path is A-B-D and task C has 2 days of slack.

    📏 Baselines and variance

    TermMeaning
    BaselineSaved snapshot of scope, dates and cost
    VarianceDifference between baseline and current
    SlippageFinish later than baseline
    Re-baselineNew baseline after an approved change
    ⚠️
    Re-baselining hides history. Only do it after formal approval and record the reason.

    🧭 Agile views and agile work in Project

    View or featureUse
    Task board / board viewKanban-style columns for task status
    Sprint planningGroup tasks into sprints, set sprint dates
    Gantt chartTime-based schedule for sponsors
    TimelineSummary view for steering committees
    Resource viewLoad by person
    EXAMPLE · Bridge

    Sprints appear as summary tasks, sprint goals as milestones and the board shows task status. The sponsor reads the Gantt while the team works on the board.

    ⚖️ Resources and levelling

    TopicMeaningAction
    Over-allocationResource assigned more than availableRe-assign, extend or add resource
    Resource levellingDelay tasks to remove over-allocationCheck effect on critical path
    CalendarWorking days and holidaysSet before scheduling
    💡
    Level resources, then re-check the critical path. Levelling can push the end date.

    💰 Earned value in Project

    Project fieldCommon nameMeaning
    BCWSPlanned Value (PV)Budgeted cost of work scheduled
    BCWPEarned Value (EV)Budgeted cost of work performed
    ACWPActual Cost (AC)Actual cost of work performed
    MeasureFormulaExample
    Schedule variance (SV)EV − PV360 − 400 = −40
    Cost variance (CV)EV − AC360 − 375 = −15
    SPIEV ÷ PV0.90
    CPIEV ÷ AC0.96

    🪤 MS Project traps

    TrapBetter approach
    Typing dates by handUse durations and links so dates calculate
    No baselineSet it after approval
    Hundreds of links with no logicKeep logic simple and reviewed
    Treating agile tasks as fixedPlan sprint work at a rolling level of detail
    Updating only at month endUpdate on the same day each week

    Module 07 · Technical Skill 6 · Release Management Software

    Release Management Software

    Plan, approve, deploy and monitor releases safely, with clear go/no-go decisions and rollback.

    🚀 What release management covers

    Release management controls how changes move from development to users. Software helps plan releases, track versions, run deployments, record approvals and report results.

    Type of toolExamples (illustrative)Purpose
    CI/CD pipelinesAzure Pipelines, Jenkins, GitLab CIBuild, test, deploy
    Deployment orchestrationOctopus Deploy, HarnessControl environments and approvals
    Version trackingJira ReleasesGroup work by version
    Feature flagsLaunchDarkly and similarSwitch features on or off
    Change managementServiceNow and similarRecord changes and approvals
    📝
    Tool names above are examples only. Your organisation may use others.

    🌍 Environments and the release path

    EnvironmentPurpose
    DevelopmentBuild and try changes
    TestAutomated and manual checks
    StagingProduction-like final check
    ProductionLive for real users

    🔢 Versions and release types

    ItemMeaningExample
    Semantic versioningMAJOR.MINOR.PATCH2.4.1
    MajorBreaking change3.0.0
    MinorNew feature, compatible2.5.0
    PatchBug fix2.4.2
    HotfixUrgent fix to production2.4.2 outside the normal cycle
    Release trainFixed schedule releasesEvery two weeks

    🛤️ Deployment strategies

    StrategyHow it worksBenefit
    Big bangEveryone gets the change at onceSimple but risky
    RollingServers updated in batchesLower risk
    Blue-greenSwitch between two identical environmentsFast rollback
    CanaryRelease to a small percentage firstEarly warning
    Feature flagDeploy hidden, enable laterSeparate deploy from release
    EXAMPLE · Canary

    Release to 5% of users, watch errors for an hour, then 25%, then 100%. If errors rise, stop and roll back.

    ✅ Go/no-go and release readiness

    CheckQuestion
    ScopeIs every release item Done?
    QualityTests passed, no open critical bugs?
    ComplianceSecurity and audit evidence ready?
    OperationsSupport trained, monitoring ready?
    CommunicationUsers and stakeholders told?
    RollbackPlan tested and owner named?
    💡
    A go/no-go decision should rest on a checklist and evidence, not on pressure from the date.

    ↩️ Rollback and incident handling

    ItemMeaning
    RollbackReturn to the last good version
    Roll forwardFix the problem with a new release
    Post-release verificationSmoke test after deploy
    Incident recordLog the issue and the fix
    Post-incident reviewLearn without blame

    📊 Release metrics (DORA)

    MetricMeaningExample
    Deployment frequencyHow often you deployDaily
    Lead time for changesCommit to production time2 days
    Change failure rateShare of deployments causing failure3 ÷ 40 = 7.5%
    Time to restoreHow long to recover45 minutes
    EXAMPLE · Change failure rate

    40 deployments, 3 caused failures. 3 ÷ 40 = 7.5%.

    🪤 Release traps

    TrapBetter approach
    Release on Friday evening without supportPick a window with staff on call
    No tested rollbackPractise rollback before the release
    Skipping stagingAlways test in a production-like place
    Manual steps with no recordAutomate and log each step
    Release notes written after the factDraft during the sprint

    🧭 Tool fundamentals

    Which tools have you used and for what?
    Name each tool with its job: Jira or Azure Boards for backlog and sprints, Asana for cross-team tasks, MS Project for schedule and baselines, Confluence for documents and decisions, and release software for deployments. Give one outcome for each.
    How do you decide which tool to use?
    Start from the need and the audience. Engineering sprints go in Jira or Azure Boards, business launches in Asana, critical path schedules in MS Project, knowledge in Confluence and deployments in the release tool. Avoid duplicate sources of truth.
    How do you avoid tool sprawl?
    Agree what lives where, name an owner for each tool, link rather than copy, and review tool use every quarter.

    🎫 Jira

    How do you set up a sprint in Jira?
    Refine and estimate the backlog, create the sprint with a goal, drag in items within capacity, start with dates, track on the board, then complete and review the sprint report.
    Write a JQL query for open high-priority bugs in the current sprint.
    project = PORTAL AND type = Bug AND sprint in openSprints() AND priority = High AND statusCategory != Done.
    Which Jira reports do you use and why?
    Burndown and burnup for progress, velocity for forecasting, sprint report for review, cumulative flow for bottlenecks and control chart for cycle time.
    Committed 32 and completed 26. What do you do?
    Completion rate is 81%. Look for the cause in the retrospective, then plan the next sprint near 26 to 28.
    How can automation help?
    Rules can notify, assign or comment when a trigger occurs. Test on a small project and name each rule clearly.

    ⚙️ Azure DevOps

    What is the difference between area path and iteration path?
    Area path says which team or area owns an item. Iteration path says which sprint or release it is planned in.
    How do you check sprint capacity in Azure Boards?
    Set hours per day per person and days off. For 5 people, 6 hours, 10 days and one person off 2 days, capacity is 288 hours. Compare it to the task total.
    How are work items linked to code?
    Link commits, branches and pull requests to the work item, so traceability runs from requirement to release.
    How do you control production deploys?
    Use environments with approvals and checks, branch policies and a pull request review before the pipeline can release.

    ✅ Asana and MS Project

    When is Asana a better choice than Jira?
    When most users are non-technical and the work is campaigns or operations. Link to Jira where engineering work is involved.
    How do you show a delay in Asana?
    Use dependencies and the timeline, then post an At risk status update with the cause and the decision needed.
    How do you find the critical path?
    Add the durations along each dependent chain. The longest chain is the critical path, and other tasks have slack.
    Why set a baseline?
    It saves the approved plan so variance can be measured. Re-baseline only after formal approval.
    How do agile views help in MS Project?
    Board and sprint views show agile work while the Gantt shows milestones for sponsors, so one file serves both audiences.

    📚 Confluence

    How do you structure a project space?
    A home page with goal and links, then roadmap, risk log, sprint pages, decision log and release notes, in a shallow, labelled tree.
    How do you connect Confluence and Jira?
    Use the Jira issues macro with a JQL query for live lists, and create Jira issues from action items on meeting pages.
    How do you keep documentation current?
    Give each page an owner and review date, link to one source of truth and archive old pages.

    🚀 Release management

    What goes into a go/no-go checklist?
    Scope Done, tests passed, no critical bugs, compliance evidence, support ready, communication sent and a tested rollback plan.
    What is the difference between deploy and release?
    Deploy puts code into an environment. Release makes the feature available to users. Feature flags separate the two.
    Explain canary and blue-green.
    Canary sends the change to a small group first. Blue-green keeps two identical environments and switches traffic, giving fast rollback.
    What is change failure rate?
    Failed deployments divided by total. With 3 failures in 40 deployments it is 7.5%.
    A release fails in production. What do you do?
    Follow the incident process, decide rollback or roll forward, inform stakeholders, verify with a smoke test and hold a blameless review.

    🏗️ Scenario: Customer portal program

    A customer portal program uses Jira for the dev team, Azure DevOps for the vendor team’s pipelines, Asana for the marketing launch, MS Project for the sponsor schedule, Confluence for documents and a release tool for deployments. In week 10 sprint results are weak, the launch plan has a late approval, and the release date is close.

    1️⃣ Task 1 · Jira

    ✍️ Sprint 5 committed 32 points and completed 26. Write the completion rate and say how you would find open high-priority bugs.
    Model answer: Completion rate = 26 ÷ 32 = 81%. Plan the next sprint near 26 to 28 and discuss causes in the retrospective. Bugs: project = PORTAL AND type = Bug AND sprint in openSprints() AND priority = High AND statusCategory != Done.
    Q. Committed 32 and completed 26. What is the completion rate?
    • A 75%
    • B 81%
    • C 84%
    • D 90%

    2️⃣ Task 2 · Azure DevOps

    ✍️ The vendor team has 5 people, 6 productive hours a day, 10 days, and one person off 2 days. Tasks total 310 hours. What do you do?
    Model answer: Capacity = 5 × 6 × 10 − 2 × 6 = 288 hours. Tasks of 310 hours are 22 hours over. Remove or defer about 22 hours of work, or add capacity, before the sprint starts.
    Q. What is the capacity in hours?
    • A 288
    • B 300
    • C 310
    • D 240

    3️⃣ Task 3 · Asana

    ✍️ Legal approval is two days late and the launch page depends on it. What do you do in Asana?
    Model answer: Check the dependency on the timeline to see the effect, then post an At risk status update with the cause and a clear ask: move the launch or shorten testing. Notify the owner of the dependent task.
    Q. Which status best fits a two-day late dependency with a recovery option?
    • A On track
    • B At risk
    • C Complete
    • D No status

    4️⃣ Task 4 · MS Project

    ✍️ Task A is 5 days, B is 3 days after A, C is 6 days, D is 4 days after B and C. What is the critical path and C’s slack?
    Model answer: A → B → D = 12 days is the critical path. C → D = 10 days, so C has 2 days of slack.
    Q. What is the critical path length?
    • A 10 days
    • B 12 days
    • C 14 days
    • D 18 days

    5️⃣ Task 5 · Confluence

    ✍️ How do you give the sponsor a live view of open risks and a record of decisions?
    Model answer: Add a Jira issues macro with a JQL filter for open risks on the project home page, and keep a decision log using the Decision template with owner and date for each entry.
    Q. Which Confluence feature shows a live list of Jira issues?
    • A Inline comment
    • B Jira issues macro
    • C Page history
    • D Label

    6️⃣ Task 6 · Release

    ✍️ 40 deployments this quarter and 3 failed. What is the change failure rate and how do you release the portal safely?
    Model answer: 3 ÷ 40 = 7.5%. Use a canary release to 5% of users, watch errors, then expand. Run the go/no-go checklist, test the rollback plan and keep support on call.
    Q. 3 failed deployments out of 40. What is the change failure rate?
    • A 3%
    • B 7.5%
    • C 12%
    • D 13.3%

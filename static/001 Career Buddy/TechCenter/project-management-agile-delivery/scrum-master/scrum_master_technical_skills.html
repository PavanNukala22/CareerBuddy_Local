    Agile Work Tracking — What, Why & Which Tool

    Understand why Scrum Masters use tools, the work-item hierarchy, the main platforms and the principle that tools serve the process.

    🧭 Why Agile Tools?

    Agile work-tracking tools make work transparent: what is planned, in progress, blocked and done. As a Scrum Master you configure and coach tools so they support Scrum and Kanban — not the other way round.

    👁️
    Visibility
    Boards, backlogs, dashboards.
    📊
    Data
    Velocity, burndown, flow metrics.
    🔗
    Traceability
    Link stories to code, tests, releases.
    🤝
    Collaboration
    Comments, mentions, remote teams.
    ⚠️
    Agile Manifesto: individuals and interactions over processes and tools. A perfect Jira setup cannot fix a broken team conversation.

    Jira Setup & Administration

    Set up Jira projects, boards, workflows, fields and permissions — and use JQL, automation and reports to run Scrum well.

    🏗️ Project Types

    👥 Team-managed

    Configured by the team itself; simple, independent settings; quick setup. Good for autonomous single teams.

    🏢 Company-managed

    Configured by Jira admins with shared schemes; consistent across many projects; more powerful (e.g. boards across projects).

    Scheme (company-managed)Controls
    Issue type schemeWhich issue types the project uses
    Workflow schemeWhich workflow each issue type follows
    Screen schemeFields shown on create/edit/view
    Field configuration schemeRequired/hidden fields
    Permission schemeWho can browse, create, transition, administer
    Notification schemeWho receives emails for events

    🔀 Workflows & Boards

    • Keep workflows simple: To Do → In Progress → In Review → Done is often enough.
    • Use statuses that reflect real work states; add transitions conditions/validators sparingly.
    • Map statuses to board columns; set column constraints (WIP limits) on Kanban boards.
    • Scrum board: backlog view, sprints, active sprint board; Kanban board: continuous flow.
    • Board filter (a JQL query) decides which issues appear.

    🔍 JQL — Jira Query Language

    jqlproject = PAY AND sprint in openSprints() AND status != Done

project = PAY AND issuetype = Bug AND priority in (Highest, High) AND resolution = EMPTY ORDER BY created DESC

assignee = currentUser() AND updated >= -7d

parent = PAY-120
    • Use saved filters for boards, dashboards and subscriptions.
    • Common functions: openSprints(), closedSprints(), currentUser(), startOfWeek().

    🤖 Automation & Custom Fields

    Rule partExample
    TriggerIssue transitioned to Done
    ConditionAll sub-tasks are Done
    ActionTransition parent story to Done; comment; notify Slack
    • Useful rules: auto-assign reviewer, close parent when sub-tasks done, flag items stuck > 3 days, sync fields to sub-tasks.
    • Add custom fields only when they drive a decision — field sprawl slows everyone.

    📊 Jira Reports & Dashboards

    ReportUse
    Sprint reportCompleted vs not completed, scope added
    Burndown chartRemaining work in a Sprint
    Velocity chartCommitted vs completed per Sprint
    Cumulative flow diagramWIP and bottlenecks by status over time
    Control chartCycle time per issue
    Epic/release burndownProgress toward a larger goal
    Q. Which JQL finds incomplete issues in the active sprint of project PAY?
    • A project = PAY AND sprint in openSprints() AND status != Done
    • B project = PAY OR status = Done
    • C sprint = all
    • D assignee = PAY

    Azure DevOps Boards Administration

    Configure Azure DevOps processes, area and iteration paths, backlogs, capacity, queries and dashboards for Scrum teams.

    🏛️ Organisation, Projects & Processes

    Process templateDeliverable itemNotes
    BasicIssueSimplest: Epic → Issue → Task
    AgileUser StoryIncludes Issue work item type
    ScrumProduct Backlog ItemIncludes Impediment work item type
    CMMIRequirementFormal change/risk tracking
    • System processes are locked; create an inherited process to customise work item types, fields, states and rules.
    • Changes to an inherited process apply to all projects using it.

    🗺️ Area & Iteration Paths

    • Area paths group work by team or product area (e.g. Payments\Checkout). Each team owns one or more areas.
    • Iteration paths define Sprints with start/end dates (e.g. Release 1\Sprint 5).
    • Teams select which iterations they use in Team configuration.

    📋 Backlogs, Sprints & Capacity

    • Backlog levels: Epics → Features → Backlog items; drag to order.
    • Sprint backlog: assign items to an iteration; break into Tasks with remaining work.
    • Capacity planning: hours per day per person and days off; the tool compares capacity with remaining work.
    • Taskboard shows tasks per backlog item; Kanban board shows flow with WIP limits and split columns.

    🔍 Queries & Dashboards

    wiqlSELECT [System.Id], [System.Title], [System.State]
FROM WorkItems
WHERE [System.TeamProject] = @project
  AND [System.WorkItemType] = 'Bug'
  AND [System.State] <> 'Done'
  AND [System.IterationPath] = @CurrentIteration
ORDER BY [Microsoft.VSTS.Common.Priority]
    WidgetShows
    Sprint burndownRemaining work in Sprint
    VelocityCompleted work per Sprint
    Cumulative flowFlow and bottlenecks
    Cycle time / Lead timeFlow time per item
    Query tile / chartCounts and charts from saved queries

    🔐 Permissions & Integration

    • Security groups: Project Administrators, Contributors, Readers; area-path permissions restrict edits.
    • Link work items to commits, pull requests and builds (Repos/Pipelines) for traceability.
    • Delivery Plans show multiple teams' work on a timeline; Analytics views feed Power BI.
    Q. To add a custom field to the Scrum process in Azure DevOps you must…
    • A Edit the system process directly
    • B Create an inherited process and customise it
    • C Use Jira
    • D Edit WIQL

    Agile Work Tracking Practices & Tool Hygiene

    Keep tracking data accurate and useful so reports reflect reality and support inspection and adaptation.

    🧹 Tracking Hygiene

    PracticeWhy
    Update status when work actually changesAccurate boards and flow metrics
    Small, well-titled items with acceptance criteriaClarity and better estimates
    Link items to epics/featuresRoll-up progress
    Mark blocked items with a flag and reasonVisible impediments
    Close done items only when DoD is metHonest velocity
    Avoid duplicate/zombie items; regular backlog clean-upFocused backlog

    🏷️ Organising Work

    • Use epics/features for value grouping; components/area paths for system areas; labels/tags sparingly.
    • Swimlanes by epic, assignee or expedite class.
    • Fix versions / releases to track deliveries.

    🔗 Integrations

    IntegrationBenefit
    Git (Bitbucket/GitHub/Azure Repos)Commits and PRs linked to work items
    CI/CD (Jenkins/Azure Pipelines)Build and deploy status on items
    Confluence / WikiRequirements, DoD, working agreements
    Slack / TeamsNotifications and quick updates
    Test management (Xray, Zephyr, Azure Test Plans)Test coverage per story

    🧭 Coaching Teams on Tools

    • Tool configuration should follow team working agreements — co-design with the team.
    • Teach the team to read their own charts during Daily Scrum and Retrospective.
    • Avoid using tools for individual surveillance (e.g. hours logged per person) — it destroys trust.
    Q. Velocity in the tool looks high but customers see little value. Likely cause?
    • A Items closed before meeting DoD
    • B Too few epics
    • C Wrong colour scheme
    • D Long sprint names

    Team-Level Kanban

    Use Kanban practices to optimise flow — on their own or alongside Scrum.

    🧭 What is Kanban?

    Kanban is a strategy for optimising the flow of value through a process using a visual, pull-based system. The Kanban Guide for Scrum Teams lists four practices:

    👁️
    Visualise the workflow
    Board columns show states.
    🚦
    Limit WIP
    Cap items in progress.
    🏃
    Actively manage work items
    Watch age, unblock, swarm.
    🔧
    Inspect & adapt the workflow
    Improve the definition of workflow.

    🗂️ Designing a Team Kanban Board

    ElementExample
    ColumnsBacklog → Ready → In Progress → Review → Testing → Done
    Split columnsDoing / Done inside Review to show waiting
    WIP limitsIn Progress ≤ 4, Review ≤ 2
    Explicit policies"Pull into Testing only when PR approved"
    Classes of serviceExpedite, fixed date, standard, intangible
    Blocked markersRed flag + reason + date

    📈 Flow Metrics & Charts

    • WIP, throughput, cycle time, work item age.
    • Little's Law: cycle time = WIP ÷ throughput.
    • Cumulative Flow Diagram: widening band = growing queue/bottleneck.
    • Cycle time scatterplot: percentile-based service level expectation (SLE), e.g. 85% in ≤ 8 days.

    🔄 Scrum with Kanban (Scrumban)

    • Scrum events and accountabilities stay; Kanban adds flow practices inside the Sprint.
    • Sprint Planning can use throughput forecasts; Daily Scrum walks the board right-to-left and checks item age.
    • Retrospective inspects the workflow definition and WIP limits.
    Q. A CFD shows the "In Review" band steadily widening. This means…
    • A Work is flowing smoothly
    • B A bottleneck is building in review
    • C The team finished early
    • D Throughput doubled

    Scaling, Governance & Reporting with Agile Tools

    Design tool strategy for multiple teams: portfolio views, governance, automation, migration and stakeholder reporting.

    🌐 Multi-Team & Portfolio Views

    NeedJiraAzure DevOps
    Cross-team timelinePlans (Advanced Roadmaps)Delivery Plans
    Hierarchy above epicsInitiatives/custom levels (Premium)Epics → Features → PBIs
    DependenciesIssue links + Plans dependency viewPredecessor/successor links in Delivery Plans
    SAFe supportJira Align / PlansPortfolio backlogs, area paths

    🛡️ Governance & Data Quality

    • Standardise the minimum: issue types, key fields, Done definition; leave teams room for their own board design.
    • Naming conventions for projects, boards, sprints (e.g. "PAY Sprint 24").
    • Admin roles and change process for schemes/process templates.
    • Quarterly clean-up: unused fields, workflows, stale items.
    • Security: least-privilege permissions; no sensitive data in work items.

    🤖 Automation Strategy

    • Automate repetitive hygiene (transitions, notifications, ageing alerts).
    • Avoid "automation spaghetti" — document rules and owners.
    • Monitor rule execution limits and failures.

    📊 Stakeholder Reporting

    • Report outcomes and forecasts, not task counts: Sprint Goal achievement, release burnup, probabilistic forecasts.
    • Use dashboards per audience: team (flow), PO (backlog/release), leadership (portfolio).
    • Export to Power BI via Jira connectors or Azure DevOps Analytics views for cross-team trends.

    🚚 Tool Migration

    1. Define why and success criteria.
    2. Map work item types, fields, workflows and users.
    3. Clean data before migrating.
    4. Pilot with one team; validate reports.
    5. Train, migrate in waves, decommission old tool.
    Q. Best way to report progress to executives?
    • A Count of tasks closed per person
    • B Release burnup and Sprint Goal achievement with forecasts
    • C Hours logged
    • D Number of Jira comments

    Module 07 · Interview Preparation

    Interview Preparation

    Click a question to reveal a model answer.

    🛠️ Jira & Azure DevOps

    Team-managed vs company-managed projects in Jira?
    Team-managed projects are configured by the team with independent settings and quick setup; company-managed projects use shared admin-controlled schemes for consistency and advanced features across projects.
    How do you build a sprint board for a team?
    Create the project/board with a JQL filter, map workflow statuses to columns, configure estimation, quick filters and swimlanes, then create sprints from the backlog.
    How do you customise Azure DevOps work item types?
    Create an inherited process from the system process, add fields/states/rules, and assign projects to it.
    What are area and iteration paths?
    Area paths group work by team or product area; iteration paths define Sprints with dates that teams select for planning.

    📋 Tracking & Kanban

    What makes tracking data trustworthy?
    Timely status updates, small items with clear acceptance criteria, honest DoD before closing, flagged blockers and regular backlog clean-up.
    What are the four Kanban practices for Scrum teams?
    Visualise the workflow, limit WIP, actively manage work items, inspect and adapt the definition of workflow.
    How do you read a cumulative flow diagram?
    Bands show items per state over time; widening bands reveal bottlenecks, flat Done line shows no delivery, and band thickness relates to WIP.
    What is a service level expectation?
    A forecast like "85% of items finish within 8 days", based on historical cycle times.
    Which Jira reports do you use in retros?
    Sprint report, velocity chart, burndown, cumulative flow and control chart for cycle time.

    🌐 Expert

    How do you scale tool setup across 10 teams?
    Standardise minimum shared elements, give teams freedom in board design, use portfolio views (Plans/Delivery Plans), governance for scheme changes and dashboards per audience.
    What automation rules do you recommend?
    Close parent when sub-tasks are done, alert on items stuck beyond a threshold, auto-link PRs, notify chat channels on blockers — documented with owners.
    How do you avoid tools becoming surveillance?
    Measure team flow and outcomes rather than individual activity, co-design configuration with the team and use data in retros for learning.
    How would you migrate from one tool to another?
    Clarify goals, map data model, clean data, pilot with one team, validate reports, train users, migrate in waves and retire the old tool.

    Practice: Set Up Tools for Two Teams

    Configure and coach Jira/Azure DevOps and Kanban for real teams.

    0 / 0 correct

    🏢 Scenario

    You are Scrum Master for Team Alpha (Scrum, mobile app, Jira) and Team Ops (support and infrastructure, unpredictable work, Azure DevOps). Alpha's board has 14 columns; velocity chart shows huge swings. Ops is overwhelmed: 40 items "In Progress" for 6 people.

    1️⃣ Task 1 · Jira for Team Alpha

    ✍️ Redesign Alpha's workflow/board and fix data quality.
    Model answer: Simplify to To Do → In Progress → In Review → Done (+ Blocked flag), set board filter JQL for the project, configure story point estimation, swimlanes by epic, close items only when DoD met, use sprint report and velocity chart in retros.

    2️⃣ Task 2 · Kanban for Team Ops

    Q. First change for Team Ops?
    • A Add more columns
    • B Introduce WIP limits and finish work before starting new
    • C Switch to 4-week Sprints
    • D Hide the board
    ✍️ Ops throughput is 10 items/week. If WIP drops to 12, what average cycle time does Little's Law predict?
    Model answer: Cycle time = WIP ÷ throughput = 12 ÷ 10 = 1.2 weeks (≈ 6 working days), down from 40 ÷ 10 = 4 weeks.

    3️⃣ Task 3 · Azure DevOps Setup

    ✍️ Configure Azure DevOps for Ops.
    Model answer: Use the Basic or Agile inherited process, area path Ops\Infra, Kanban board with columns New → Doing → Waiting → Done (split), WIP limits, classes of service via tags/swimlanes (Expedite), cycle time and CFD widgets on the team dashboard, query for items older than 5 days.

    4️⃣ Task 4 · Reporting

    ✍️ What do you show the head of engineering monthly?
    Model answer: Per team: delivery outcomes (Sprint Goals met, releases), throughput trend, cycle-time percentiles/SLE, blocked time and top systemic impediments, plus probabilistic forecast for key deliveries.

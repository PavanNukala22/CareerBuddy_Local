    What is Scrum? Agile, the Scrum Framework & the Scrum Master

    Start from zero: what Agile and Scrum are, why empiricism works, the Scrum accountabilities, events, artifacts and commitments, and what a Scrum Master really does.

    🧭 What is Agile?

    Agile is a mindset for delivering value in small, frequent increments, learning from feedback and adapting — instead of planning everything upfront. It is defined by the Agile Manifesto (2001): 4 values and 12 principles.

    We value……over
    Individuals and interactionsProcesses and tools
    Working softwareComprehensive documentation
    Customer collaborationContract negotiation
    Responding to changeFollowing a plan
    📌
    The items on the right still matter — the items on the left matter more.

    🔁 What is Scrum?

    Scrum is a lightweight framework that helps people, teams and organisations generate value through adaptive solutions for complex problems. It is defined in the Scrum Guide (latest 2020) by Ken Schwaber and Jeff Sutherland.

    👁️
    Transparency
    Work and progress are visible to everyone.
    🔍
    Inspection
    Frequently inspect artifacts and progress.
    🔧
    Adaptation
    Adjust as soon as something drifts.

    These three pillars come from empiricism (knowledge from experience) and lean thinking (reduce waste, focus on essentials).

    Scrum valueIn practice
    CommitmentCommit to the Sprint Goal and to supporting each other
    FocusFocus on Sprint work and the goal
    OpennessBe open about work and challenges
    RespectRespect each other as capable people
    CourageDo the right thing and tackle tough problems

    👥 The Scrum Team & Accountabilities

    AccountabilityAccountable for
    Product OwnerMaximising product value; managing the Product Backlog; Product Goal; ordering items
    Scrum MasterScrum Team's effectiveness; establishing Scrum as defined in the Scrum Guide; coaching team and organisation
    DevelopersCreating a usable Increment each Sprint; Sprint Backlog; adhering to Definition of Done
    • A Scrum Team is usually 10 or fewer people, cross-functional and self-managing.
    • No sub-teams or hierarchies inside the Scrum Team.

    Executing the Scrum Framework

    Turn the Scrum Guide into daily reality: launch a team, run Sprints end to end, define Done, and spot anti-patterns early.

    🚀 Launching a Scrum Team

    1. Clarify the product, Product Goal and Product Owner.
    2. Form a cross-functional team (≤ 10) with all skills to create a Done Increment.
    3. Agree Sprint length (commonly 2 weeks) and event calendar.
    4. Create the first Definition of Done.
    5. Build an initial ordered Product Backlog; refine the top items.
    6. Create working agreements.
    7. Run Sprint 1 — expect learning, not perfection.

    🔄 The Sprint Lifecycle

    Day (2-week Sprint)ActivitySM focus
    Day 1Sprint PlanningClear Sprint Goal, realistic forecast
    DailyDaily ScrumDevelopers own it; focus on goal progress
    Mid-SprintRefinement (ongoing)Keep top of backlog ready
    ThroughoutImpediment removalFast escalation, visible board
    Last daySprint Review → RetrospectiveInspect product, then process
    • The Sprint Goal stays fixed; scope may be renegotiated with the PO as more is learned.
    • Only the Product Owner can cancel a Sprint (if the Sprint Goal becomes obsolete).
    • A new Sprint starts immediately after the previous one ends.

    ✅ Definition of Done

    EXAMPLE · Sample DoD
    • Code reviewed and merged to main
    • Unit tests written and passing; coverage ≥ 80% for new code
    • Acceptance criteria verified by the team
    • No open critical/major bugs
    • Deployed to staging; documentation updated
    • If the organisation has a DoD, the team follows it as a minimum; otherwise the team creates one.
    • Work not meeting DoD returns to the Product Backlog — it is not part of the Increment.
    • Strengthen DoD over time as capability grows.
    📌
    Definition of Ready is a common team practice for refined items but is not part of the Scrum Guide — use it lightly, never as a gate that blocks collaboration.

    ⚠️ Common Scrum Anti-Patterns

    Anti-patternWhy it hurtsSM response
    Daily Scrum as status report to SM/managerKills ownershipCoach Developers to run it around the Sprint Goal
    No Sprint GoalSprint becomes a task listFacilitate goal-first planning
    "Done" but not deployableHidden work, false progressStrengthen DoD, make undone work visible
    Skipping retrosNo improvementVary formats, show value of past actions
    PO absentSlow decisions, wrong prioritiesCoach PO, set availability agreements
    Carrying over most work every SprintOver-commitmentUse historical data, smaller items

    Facilitating Scrum Events

    Run Sprint Planning, Daily Scrum, Sprint Review and Retrospective so they are purposeful, timeboxed and owned by the team.

    ⏱️ Event Timeboxes (Scrum Guide)

    EventMax timebox (1-month Sprint)Typical for 2-week SprintAttendees
    Sprint Planning8 hours≈ 4 hours or lessScrum Team (+ invited advisors)
    Daily Scrum15 minutes15 minutesDevelopers (SM/PO if working on items)
    Sprint Review4 hours≈ 2 hoursScrum Team + key stakeholders
    Sprint Retrospective3 hours≈ 1.5 hoursScrum Team

    📋 Sprint Planning

    TopicQuestionOutput
    OneWhy is this Sprint valuable?Sprint Goal
    TwoWhat can be Done this Sprint?Selected Product Backlog items
    ThreeHow will the chosen work get done?Plan (tasks, often ≤ 1 day each)
    EXAMPLE · Planning agenda (2-week Sprint, 3 h)
    1. PO presents objective and top items (20 min).
    2. Team reviews capacity: holidays, support load (10 min).
    3. Draft and agree Sprint Goal (20 min).
    4. Select items using past velocity/throughput (40 min).
    5. Developers break down work and plan first days (60 min).
    6. Confirm Sprint Goal and forecast; risks (15 min).

    ☀️ Daily Scrum

    • Purpose: inspect progress toward the Sprint Goal and adapt the Sprint Backlog.
    • Same time and place; 15 minutes; owned by the Developers.
    • The three questions are optional — try "walk the board" from right to left.
    • Detailed discussions happen right after (the "after-party").

    🔴 Status meeting

    Each person reports yesterday/today to the SM. No mention of the goal. Problems hidden.

    🟢 Effective Daily Scrum

    Team walks the board, asks "are we on track for the Sprint Goal?", swarms on blocked items, plans next 24 h.

    🎯 Sprint Review

    • A working session, not a demo-only presentation.
    • Inspect the Increment with stakeholders, discuss progress toward the Product Goal, market changes and next steps.
    • Outcome: revised Product Backlog.
    • Prepare: invite the right stakeholders, agree demo flow, show real working product.

    🔄 Sprint Retrospective

    Phase (Derby & Larsen)PurposeExample activity
    Set the stageGet everyone talkingCheck-in word / weather report
    Gather dataShared picture of the SprintTimeline, Mad-Sad-Glad
    Generate insightsFind root causes5 Whys, fishbone
    Decide what to do1–3 improvement actionsDot voting, SMART actions
    CloseAppreciate and improve the retroROTI, appreciations
    💡
    Add the most impactful improvement to the next Sprint Backlog so it actually happens.

    🧰 Facilitation Techniques

    • Agenda with purpose, timebox and expected outcome.
    • Diverge then converge: 1-2-4-All, silent brainstorming, dot voting, fist of five.
    • Parking lot for off-topic items; visible timer.
    • Equal participation: round-robins, written input for quieter people.
    • Remote: cameras-on agreement, digital whiteboards (Miro/Mural), breakout rooms.
    Q. What is the main output of the Sprint Review?
    • A A signed acceptance form
    • B A revised Product Backlog
    • C The Sprint Goal
    • D Task estimates

    Facilitating Backlog Refinement

    Help the Product Owner and Developers keep the Product Backlog clear, small, estimated and ordered.

    🧾 What is Refinement?

    Product Backlog refinement is the ongoing act of breaking down and adding detail, size and order to Product Backlog items. It is not a formal Scrum event — teams commonly spend up to ~10% of capacity on it.

    DEEP backlogMeaning
    Detailed appropriatelyTop items detailed; lower items rough
    EstimatedItems have relative sizes
    EmergentChanges as we learn
    Prioritised (ordered)Most valuable first

    ✍️ User Stories & Acceptance Criteria

    Format: As a [user], I want [goal] so that [benefit].

    INVESTMeaning
    IndependentCan be delivered separately
    NegotiableDetails discussed, not fixed contract
    ValuableDelivers value to user/customer
    EstimableTeam can size it
    SmallFits comfortably in a Sprint
    TestableClear acceptance criteria
    EXAMPLE · Acceptance criteria (Given/When/Then)

    Given a registered user with a saved card, when they pay ₹500, then the payment succeeds and a receipt email is sent within 1 minute.

    ✂️ Splitting Large Items

    PatternExample
    Workflow stepsCheckout: cart → address → payment → confirmation
    Business rule variationsDiscount: flat, percentage, coupon
    Data variationsPay by UPI, card, net banking
    Happy path firstSuccessful payment before error handling
    InterfaceWeb first, then mobile
    SpikeTime-boxed research before estimating

    🃏 Estimation

    • Story points: relative size (effort, complexity, uncertainty), often Fibonacci 1, 2, 3, 5, 8, 13.
    • Planning Poker: simultaneous reveal to avoid anchoring; discuss outliers.
    • T-shirt sizing (S/M/L/XL) for rough, early items.
    • No-estimates / counting items: right-size items and forecast by throughput.
    • Estimates belong to the Developers — the SM facilitates, never estimates for them.

    🗓️ Running a Refinement Session

    1. PO shares upcoming goals and top items beforehand.
    2. Clarify value and questions; add acceptance criteria.
    3. Split items that are too big.
    4. Estimate; identify dependencies and risks.
    5. Confirm next 1–2 Sprints of items are "ready enough".
    Q. Which INVEST letter means the item fits comfortably in a Sprint?
    • A I
    • B V
    • C S
    • D T

    Impediment Removal

    Identify, prioritise and remove obstacles — and grow the team's ability to remove its own.

    🚧 What is an Impediment?

    An impediment is anything that slows or blocks the team from achieving its Sprint Goal or improving — beyond what the team can solve itself quickly.

    TypeExample
    TechnicalBroken test environment, slow builds
    DependencyWaiting for another team's API
    OrganisationalApprovals take weeks; team members pulled into other projects
    People / teamConflict, missing skill
    ProcessHandoffs, unclear DoD
    ExternalVendor delays, compliance sign-offs

    🗂️ Managing Impediments

    Figure 5.1 · Impediment lifecycle
    • Ask first: "Can the team solve this?" — coach self-management before stepping in.
    • Track impediments with owner, date raised, impact and status.
    • Escalate quickly when the team cannot act; bring facts and impact.

    🧠 Systemic Impediments & Root Cause

    • Recurring blockers usually have organisational causes (structure, policies, funding, approvals).
    • Use 5 Whys, value stream mapping and data (blocked time, wait time).
    • Partner with managers and other SMs; create an organisational impediment backlog.
    EXAMPLE · 5 Whys — slow releases
    1. Why slow? → Release needs CAB approval.
    2. Why? → All changes treated as high risk.
    3. Why? → No automated tests to prove safety.
    4. Why? → No time allocated for test automation.
    5. Action: agree DoD with automated tests + standard-change pathway with CAB.

    🔗 Dependencies

    • Visualise on a dependency board; agree dates and owners with other teams.
    • Reduce through team design (feature teams), contracts/mocks, and joint planning.
    • Use Scrum of Scrums or Nexus integration events in multi-team setups.
    Q. A developer says "I'm blocked waiting for a test environment." First SM move?
    • A Fix it yourself immediately every time
    • B Ask whether the team can resolve it, make it visible, then help/escalate if not
    • C Ignore until retro
    • D Reassign the developer

    Agile Metrics, Forecasting & Coaching

    Use velocity, burn charts and flow metrics to help the team inspect and adapt — and coach without weaponising data.

    📊 Velocity

    • Story points (or items) completed to DoD per Sprint.
    • Use the average of the last 3–5 Sprints for planning; not a target.
    • Never compare velocity across teams — points are relative per team.
    EXAMPLE · Forecast with velocity

    Last 4 Sprints: 28, 32, 30, 26 → average 29. Backlog remaining 180 points → ≈ 180 ÷ 29 ≈ 6.2 Sprints (range using min 26 / max 32: ≈ 5.6–6.9).

    📉 Burndown & Burnup Charts

    📉 Burndown

    Shows remaining work over time. Simple for a Sprint. Scope changes are hidden in the line.

    📈 Burnup

    Shows completed work and total scope as two lines. Scope changes are visible — better for releases.

    • Flat burndown mid-Sprint: work not finishing — look for large items, blockers, too much WIP.
    • Rising burndown: scope added during Sprint.

    ⏳ Flow Metrics

    MetricMeaning
    Cycle timeTime from work started to finished
    Lead timeTime from request to delivery
    ThroughputItems finished per unit time
    WIPItems in progress
    Work item ageHow long an in-progress item has been active

    Little's Law: Average cycle time = Average WIP ÷ Average throughput. Example: WIP 12, throughput 6/week → cycle time ≈ 2 weeks.

    • Cycle time scatterplots: use percentiles — "85% of items finish within 6 days".
    • Monte Carlo simulation of throughput gives probabilistic forecasts ("85% chance by 15 Nov").

    ⚠️ Metric Anti-Patterns

    • Velocity as a performance target → point inflation.
    • Comparing teams by velocity.
    • Measuring individuals instead of team flow.
    • Ignoring outcomes (customer value) and quality (escaped defects).
    • Goodhart's law: when a measure becomes a target, it ceases to be a good measure.

    🧑‍🏫 Coaching the Team

    StanceWhen
    TeachingTeam new to Scrum
    CoachingHelp team find own answers with questions
    MentoringShare experience
    FacilitatingNeutral process holder
    Removing impedimentsBlockers beyond team control
    Change agentOrg-level change
    • Shu-Ha-Ri: follow rules → adapt rules → transcend rules.
    • Use metrics in retros as conversation starters, not judgements.
    • Track team maturity: self-management, DoD strength, predictability, outcomes.

    Interview Preparation

    Click a question to reveal a model answer.

    🔁 Scrum Framework

    What are the three Scrum accountabilities?
    Product Owner (maximises value, manages Product Backlog), Scrum Master (Scrum Team effectiveness, establishing Scrum) and Developers (create usable Done Increments each Sprint).
    What are the three Scrum artifacts and their commitments?
    Product Backlog → Product Goal; Sprint Backlog → Sprint Goal; Increment → Definition of Done.
    What are the three pillars of empiricism?
    Transparency, inspection and adaptation.
    Is Definition of Ready part of Scrum?
    No. It is a complementary practice some teams use; the Scrum Guide has Definition of Done only.

    🎯 Events, Refinement & Impediments

    How do you make a Daily Scrum effective?
    Developers own it, focus on the Sprint Goal, walk the board, keep to 15 minutes, raise blockers and take detailed discussions offline afterwards.
    What happens in Sprint Planning?
    The team answers why (Sprint Goal), what (selected items) and how (plan), using past performance and capacity.
    How do you facilitate a good retrospective?
    Prepare a purposeful format, set the stage, gather data, generate insights, decide 1–3 actionable improvements, and add the top one to the next Sprint Backlog.
    How do you handle an impediment?
    Make it visible, check whether the team can solve it, assess impact on the Sprint Goal, help or escalate with facts, and address root causes if it recurs.
    How much time should refinement take?
    It is ongoing and usually takes no more than about 10% of the Developers' capacity.

    📊 Metrics & Coaching

    Burndown vs burnup?
    Burndown shows remaining work; burnup shows completed work and total scope, making scope changes visible.
    What is Little's Law?
    Average cycle time equals average WIP divided by average throughput — reducing WIP shortens cycle time.
    Why not compare velocity between teams?
    Story points are relative to each team; comparing creates gaming and point inflation.
    How do you coach a team that relies on you to run everything?
    Shift ownership gradually: ask powerful questions, let Developers facilitate the Daily Scrum, rotate facilitation, celebrate team decisions and step back.

    Apply Scrum execution, facilitation, refinement, impediment removal and metrics to a realistic team.

    0 / 0 correct

    🏦 Scenario: Payments Team

    You join a 7-person Scrum Team building a payments app. Last 5 Sprints: velocity 40, 18, 35, 15, 30; about 40% of committed items carry over every Sprint. The Daily Scrum takes 35 minutes and the manager asks each person for status. There is no Sprint Goal. The test environment is down 2–3 days per Sprint. Retros were cancelled "to save time".

    1️⃣ Task 1 · Diagnose

    ✍️ List the top problems you see and their likely effects.
    Model answer: No Sprint Goal (unfocused work), Daily Scrum as manager status meeting (low ownership, long), over-commitment and unstable velocity (unreliable forecasts), recurring environment impediment (blocked work), no retros (no improvement), likely large items and weak refinement.

    2️⃣ Task 2 · Events

    Q. Best first change to the Daily Scrum?
    • A Make it 45 minutes
    • B Coach Developers to own it around the Sprint Goal; manager observes or doesn't attend
    • C Cancel it
    • D Have SM collect written status
    ✍️ Design a 2-hour Sprint Planning for the next Sprint.
    Model answer: Objective from PO → capacity check → Sprint Goal → select items using average velocity (~28) minus environment risk → Developers plan first tasks → confirm goal and risks.

    3️⃣ Task 3 · Impediment

    ✍️ How do you remove the test-environment impediment for good?
    Model answer: Make blocked time visible (track hours lost), raise with platform/ops owner with impact data, agree short-term workaround (shared env slot, mocks), then root cause (5 Whys) → long-term fix such as automated environment provisioning; add to organisational impediment backlog and follow up.

    4️⃣ Task 4 · Metrics

    Q. Average velocity of 40, 18, 35, 15, 30?
    • A 25.6
    • B 27.6
    • C 30.0
    • D 35.0
    ✍️ How will you show improvement after 3 Sprints?
    Model answer: Sprint Goal met rate, carry-over %, velocity stability (smaller range), cycle time trend, blocked time, retro actions completed, team happiness/engagement — reviewed with the team in retros.

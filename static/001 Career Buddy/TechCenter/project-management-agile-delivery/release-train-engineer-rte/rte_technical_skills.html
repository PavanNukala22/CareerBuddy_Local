    Module 01 · Basic · Landscape

    RTE Tooling Landscape & Data Model

    The RTE needs the right tool for each job and a clean, shared data model underneath all of them.

    🧰 Why Tools Matter to the RTE

    📋
    Plan
    Features, PIs, capacity and dependencies in an ALM tool.
    🗺️
    Visualise
    Program boards and ROAM boards on Miro/Mural.
    📊
    Measure
    Dashboards for PI progress, flow and predictability.
    🔗
    Integrate
    Team tools roll up to program and portfolio views.
    🔐
    Govern
    Access control, audit trail, data quality.
    🔁
    Automate
    Reports, syncs and reminders reduce manual effort.

    🧬 Enterprise Data Model

    SAFe level / conceptTypical tool object
    Strategy / portfolioThemes, strategic objectives, OKRs
    Portfolio EpicEpic / Initiative
    Capability / FeatureCapability, Feature (ART scope)
    Team workStory, Task, Defect
    Time-boxesIteration / Sprint, Release or PI object
    PlanningPI Objectives, Risks, Dependencies, Capacity
    📝
    Object names differ across tools; agree one enterprise definition (states, fields, hierarchy) before configuring.

    🧭 Which Tool for What

    ToolPrimary use for the RTE
    Jira AlignEnterprise agility planning: strategy-to-delivery rollups across portfolio, program and teams.
    TargetprocessHighly configurable, visual work management with custom entities, boards and views.
    RallyAgile ALM with portfolio items, iterations, releases and team execution.
    SAFe Enterprise DashboardsMetrics: PI progress, predictability, flow, business agility.
    Miro / MuralVisual collaboration for PI planning boards and workshops.

    🏗️ Integration Architecture and Single Source of Truth

    LayerTypical toolsData direction
    Strategy / portfolioJira Align, TargetprocessDown: priorities and funding; Up: rollups
    Program / ARTJira Align, Rally, TargetprocessPlan Features and PIs; track progress
    Team executionJira, RallyUp: story status and estimates
    Visual collaborationMiro, MuralSnapshot plans; sync final plan to ALM
    Analytics / BIDashboards, BI toolsRead-only from the system of record

    Decide, for every data type (Feature, Story, PI, Risk), one master system. Two-way sync of the same field creates conflicts; prefer one-way flows or clear field ownership.

    🚨
    Two tools editing the same field without ownership rules is the most common cause of "dashboards disagree".

    🛂 Tool Governance Checklist

    AreaQuestion the RTE asks
    OwnershipWho administers the tool and approves configuration changes?
    Change controlAre new fields, states and workflows reviewed before release?
    Data dictionaryIs every state, field and metric defined in writing?
    AccessAre roles least-privilege and reviewed each PI?
    RetentionHow long are boards, snapshots and PI data kept?
    TrainingDo new teams get onboarding before first use?

    Module 02 · Advanced · ALM

    Jira Align

    Connects strategy to execution and rolls team work up to program and portfolio views.

    🎯 Positioning and Capabilities

    CapabilityRTE use
    Work hierarchyThemes/Epics → Capabilities → Features → Stories: track alignment to strategy.
    Program planningPlan Features per PI; view program board, dependencies and roadmaps.
    Capacity & loadCompare planned work with team capacity before committing.
    Progress & healthFeature completion, risks, objectives and OKR alignment.
    ReportingRoadmaps and rollups for leadership.

    🔗 Working with Jira Integration

    Teams usually execute Stories and Tasks in Jira; Jira Align aggregates and rolls up. Sync depends on field mappings, project/team mapping and state mapping. Broken mappings produce missing or wrong data in dashboards.

    CheckWhy
    Sync health and errorsFailed syncs hide progress
    State/status mappingDone in Jira must equal Done in Align
    Team/ART assignmentCorrect rollups
    Estimation fieldsConsistent sizing for capacity
    PermissionsRight people edit the right items

    📘 RTE Playbook

    Configure PI calendar → Validate teams & capacity → Prepare/prioritise Features → Run PI Planning → Lock plan → Track weekly → Review at I&A

    Run data-quality checks (missing sizes, owners, PI, state) before PI Planning, and weekly during execution.

    🧭 PI Planning Workflow in the Tool

    StepWhat the RTE doesCheck
    1Create the PI and ART calendar, assign teamsDates match all tools
    2Load prioritised Features with sizes and ownersNo unsized Features
    3Teams break Features into Stories (in Jira) and syncSync healthy
    4Compare planned load with capacity per iterationLoad below capacity
    5Record dependencies and ownersNo orphan dependencies
    6Capture PI Objectives, BV and stretch flagsAll teams covered
    7Log and ROAM risksOwners assigned
    8Lock and baseline the planPlan versioned
    9Track weekly against baselineVariance reviewed

    Duplicated itemsTwo sync pathsDisable the duplicate integration

    Stale numbersSync delay or failed jobsRerun sync, add monitoring

    Targetprocess

    Flexible, visual work management that can be configured to model SAFe.

    🧩 Strengths

    🛠️
    Custom entities
    Model Epics, Features, Stories, PIs, Teams to your process.
    🖼️
    Visual views
    Boards, lists, timelines and cards tailored to roles.
    🔗
    Relations
    Link items to show dependency and hierarchy.
    📈
    Reporting
    Configurable views and charts for rollups.

    ⚙️ Configuration Priorities

    AreaRTE focus
    Process templateUse or adapt a SAFe-style template; keep hierarchy simple.
    PI & iteration objectsOne authoritative PI calendar and team iteration schedule.
    Custom fieldsBusiness value, WSJF components, risk class (ROAM).
    ViewsProgram board view, dependency view, risk view for each audience.
    AccessRole-based permissions; limit who can edit planning data.
    🚨
    Over-customisation hurts: every extra field/state increases training cost and data-quality risk.

    📘 RTE Playbook

    Define entities → set PI/iteration calendar → configure views → import/prepare Features → run planning → track on shared views → review metrics at I&A. Use saved views instead of ad-hoc exports so everyone sees the same numbers.

    Module 04 · Advanced · ALM

    Rally

    Agile ALM that supports team execution with portfolio items, iterations and releases.

    🧱 Core Concepts

    ConceptUse
    Portfolio itemsHigher-level items (e.g. initiatives/features) above stories.
    User Stories & DefectsTeam-level work, estimated and scheduled.
    IterationsTime-boxes in which stories are scheduled.
    ReleasesLonger time-boxes; often used to model a PI.
    Capacity / loadPlan team load per iteration.

    📏 Planning and Tracking

    Model the PI as a release/time-box, link Features to it, and schedule stories into iterations. Track feature progress by rolling up story completion, and watch defects and blocked work for risk. Use query-based filters and saved dashboards for consistency.

    📘 RTE Playbook

    Align iteration dates across teams → confirm hierarchy → prepare Features with sizes → plan stories per iteration → monitor weekly with consistent filters → archive PI data after I&A.

    💡
    Stable calendars matter: if release/iteration dates differ per team, rollups and burn-ups are unreliable.

    📐 Hierarchy and Estimation

    LevelTypical itemCommon sizing
    PortfolioInitiative / EpicT-shirt size or points
    ProgramFeaturePoints rolled up from stories
    TeamUser StoryStory points (relative)
    TaskTaskHours (optional)

    Use relative estimation consistently inside a team and avoid comparing points across teams. Normalise only when planning shared capacity.

    🗓️ Planning Workflow

    StepRTE action
    CalendarSet PI/release and iteration dates identically for all teams
    HierarchyCheck Feature-to-Story parent links
    SizingEnsure Features are sized and prioritised
    CapacitySet team capacity per iteration
    PlanSchedule stories into iterations; flag blocked work
    TrackUse saved filters and dashboards weekly
    CloseArchive or label PI data after I&A
    Q. Why avoid comparing story points across teams?
    • A points are secret
    • B points are relative to each team
    • C teams dislike charts
    • D tools cannot count them

    Module 05 · Expert · Metrics

    SAFe Enterprise Dashboards

    Measure outcomes and flow, not activity. Dashboards are for decisions.

    📊 Core Dashboard Metrics

    MetricUse
    PI progressFeature completion vs plan
    PI predictabilityActual BV ÷ planned BV
    Flow velocity / time / loadThroughput, speed, WIP
    Flow efficiencyActive ÷ total time
    Flow distributionFeatures, enablers, defects, risks mix
    QualityEscaped defects, defect trends
    Risk burndownROAM status over time
    CFDBottlenecks and WIP growth
    Example

    Planned BV 62, actual BV 51 → predictability = 51 ÷ 62 ≈ 82%, inside the reliable range.

    🧠 Interpreting Charts

    A widening band in a cumulative flow diagram signals growing WIP or a bottleneck. A burn-up shows scope changes that a burndown hides. Leading indicators (aging WIP, flow load) predict problems; lagging ones (predictability) confirm them.

    🚫 Pitfalls

    📉
    Vanity metrics
    Comparing velocity points across teams is meaningless.
    🎯
    Gaming
    Targets on single metrics distort behaviour.
    🕓
    Stale data
    Show refresh time and automate updates.
    🔀
    Many sources
    Keep one system of record per data type.

    🧮 Metrics Pack by Audience

    AudienceMetricsCadence
    TeamsIteration burn-up, aging WIP, escaped defectsDaily / iteration
    ART (RTE)PI progress, flow load, dependency and risk status, CFDWeekly
    Business OwnersPI predictability, objective achievement, flow timePer PI
    ExecutivesPredictability trend, flow distribution, quality, customer outcomesQuarterly

    🪪 Metric Definition Card

    Write one card per metric: name, formula, data source, owner, refresh cadence, threshold, action when breached. Unowned metrics decay into noise.

    Example · Flow efficiency

    Feature touch time 6 days, total flow time 30 days → efficiency = 6 ÷ 30 = 20%. The other 24 days are waiting, so attack queues and handoffs, not developer speed.

    Example · Aging WIP

    Features in progress longer than 2 × median flow time are flagged. The RTE reviews them weekly: split, unblock or stop.

    Module 06 · Expert · Visual Planning

    PI Planning Boards (Miro / Mural)

    Design, run and secure digital planning boards that feed your system of record.

    🗺️ Board Anatomy

    BoardContains
    Program BoardFeatures by iteration lane, milestones, dependency connectors.
    Team Planning BoardsStories per iteration, capacity and load, objectives.
    PI Objectives boardObjective statements with BV scores and stretch flag.
    ROAM / Risk boardRisks in Resolved, Owned, Accepted, Mitigated lanes.
    Confidence voteFist-of-five results per team.
    Parking lotOpen questions to resolve.

    🎛️ Facilitation Setup

    Pre-build templates and frames per team, lock fixed structure, give teams edit rights only to their frames, add a timer, use voting and private mode where useful, and rehearse with a dry run. For distributed ARTs split sessions by time zone and keep a visible agenda.

    🔐 Security and Governance

    Use SSO and role-based access, avoid public links for sensitive plans, limit guests, and set retention. Keep boards light (separate frames or boards per team) to avoid performance issues.

    🔄 After the Event: Sync to the System of Record

    The board is a snapshot; the ALM tool is the source of truth. Transfer the final plan (Features, PI, objectives, risks, dependencies) into Jira Align/Rally/Targetprocess, reconcile differences, and archive the board.

    🚨
    Using screenshots or copy-paste leads to drift. Prefer native integrations or ID-linked cards.

    ⏱️ Run-of-Show for a 2-Day PI Planning on Boards

    SessionBoard / elementFacilitator action
    Day 1 contextAgenda and vision boardsShare links, time-box talks
    Breakout #1Team planning boardsTeams draft stories, objectives, risks
    Draft plan reviewProgram BoardPresent, gather feedback
    Management reviewRisk and problem boardResolve issues, adjust scope
    Day 2 breakout #2Final team boardsFinalise BV and objectives
    Plan review & ROAMProgram and ROAM boardsReview risks, assign owners
    Confidence voteVote frameCollect fist-of-five; rework if below 3

    🎨 Digital Facilitation Patterns

    ⏲️
    Timers
    Visible countdown for each session.
    🗳️
    Voting
    Dot voting and confidence frames.
    🕶️
    Private mode
    Silent individual input before sharing.
    🧱
    Frames per team
    Limit edit rights to owners.
    ♿
    Accessibility
    High-contrast colours and readable sizes.
    🔗
    Linked cards
    IDs link cards to ALM items.

    🧯 Failure Modes and Mitigations

    RiskMitigation
    Board lag with many usersSplit into team boards; lighter objects
    Accidental editsLock frames; limit permissions; version snapshots
    Plan lost or divergesExport snapshots; sync to ALM immediately
    Time-zone fatigueSplit sessions; rotate inconvenient slots
    Unauthorised accessSSO, restricted links, guest limits
    Q. To reduce accidental edits on boards…

    • B share a public link
    • C disable voting
    • D lock frames and limit edit permissions

    Module 07 · Advanced · Data

    Reporting, Queries & Automation

    Get trustworthy answers out of the tools quickly, repeatably and safely.

    🔎 Queries and Filters

    ToolTypical approach
    JiraJQL filters and saved filters
    RallyQuery expressions on grids and saved queries
    TargetprocessFilters on views, saved views
    Jira AlignSaved filters and reports
    BI toolsDatasets with defined joins and measures
    Example · Illustrative JQL

    status = Blocked AND updated <= -3d lists blocked items untouched for three days. Field names such as a PI field are organisation-specific; confirm in your instance.

    QuestionFilter idea
    Features without an ownerType = Feature AND owner is empty
    Work not in any PIPI field is empty
    Stale in-progress itemsState = In Progress AND not updated for N days
    Unsized FeaturesSize/estimate is empty

    🤖 Automation Patterns

    PatternUseCaution
    Scheduled reportWeekly PI status to stakeholdersCheck data freshness first
    Rule-based alertNotify when a Feature is stale or blockedAvoid alert fatigue
    Webhook / eventUpdate a board or chat on state changeRetry and idempotency
    REST API scriptBulk updates, extracts, snapshotsRate limits, least-privilege tokens
    Template cloningCreate next-PI boards and viewsVersion templates

    🗄️ Data Pipelines to BI

    Extract from the system of record → transform with a documented data dictionary → load to a BI dataset → refresh on a schedule → apply row-level security. Take a PI baseline snapshot at plan lock so changes can be compared with the original commitment.

    🚨
    Reports built on exports from several tools without a master definition will drift. Reconcile counts at every refresh.

    🔐 API Good Practice

    🎟️
    Scoped tokens
    Least privilege; rotate; never paste into boards or chats.
    🚦
    Rate limits
    Throttle, back off, paginate.
    🧪
    Test first
    Use sandbox or dry-run before bulk updates.
    🧾
    Log changes
    Keep an audit of scripted updates.

    Module 08 · Expert · Planning Data

    Dependency, Risk & Capacity Management

    Model dependencies, risks and capacity in the tools so the plan stays honest.

    🔗 Dependencies

    FieldWhy it matters
    From / to team or itemDirection of need
    TypeHard (blocks) vs soft; internal vs external
    Needed-by dateSequencing against iterations
    OwnerSomeone accountable for resolving
    Status and ageAging dependencies need escalation
    Link to Feature/StoryTraceability in rollups
    💡
    Track dependency health: count open, count overdue, average age. Rising age means a systemic problem.

    ⚠️ Risk Register in the Tool

    FieldUse
    Description / cause / effectClear statement
    ROAM statusResolved, Owned, Accepted, Mitigated
    Probability × impactExposure score
    Owner and due dateAccountability
    Mitigation actionsLinked work items
    TrendRising or falling exposure
    Example

    Probability 0.6 × impact 5 = exposure 3.0. Compare against other risks to decide where the ART spends effort first.

    🧮 Capacity and Load

    Capacity = (people × available days − PTO/holidays) × focus factor

    Example

    7 people × 10 days = 70; minus 8 PTO days = 62; × 0.8 focus = ≈ 50 person-days. Compare with planned load and leave a buffer instead of loading to 100%.

    For points-based planning, use recent velocity (e.g. average of the last few iterations) rather than aspiration.

    🗺️ Roadmaps and Forecasting

    Show the current PI as committed, the next as forecast and later items as tentative. Throughput and flow-time data support probabilistic forecasts; avoid single-date promises for uncertain work.

    Rollout, Migration & Governance

    Introduce, change and govern tooling without breaking delivery.

    🚀 Phased Rollout

    PhaseActivitiesExit criteria
    PilotOne ART, configured template, champions trainedTeam can run a PI without workarounds
    ExpandMore ARTs, support desk, office hoursData completeness above target
    StandardiseCommon definitions and reportsSingle definition for key metrics
    OptimiseAutomation, integrations, cleanupReporting effort reduced

    📦 Migration

    StepDetail
    InventoryObjects, volumes, owners, integrations
    CleanArchive stale items; fix owners and states
    MapHierarchy, states, fields, user IDs
    Dry runMigrate a sample; compare counts and values
    Freeze & cutoverShort freeze, final load, reconcile
    Rollback planDefined trigger and steps

    🔐 Access and Security

    ControlPractice
    RolesAdmin, planner, contributor, viewer; least privilege
    IdentitySSO and automated provisioning/deprovisioning
    AuditRetain change logs for compliance
    Segregation of dutiesApprovers differ from editors where required

    📈 Adoption and Change

    Use a change model such as ADKAR (Awareness, Desire, Knowledge, Ability, Reinforcement). Track adoption: active users, data completeness %, sync error rate, support tickets, and time needed to produce the PI report.

    Module 10 · Practice

    Practice: Tooling for a 9-Team ART

    Apply the five technical skills to one scenario.

    🏗️ Scenario

    An ART of 9 teams uses Jira for execution and Jira Align for planning, while one legacy team uses Rally. PI Planning will be hybrid on Miro. Leaders complain dashboards disagree: Features show 70% complete in one place and 55% in another. Board data from last PI was copied manually into the tool.

    0 / 0 correct

    1️⃣ Task 1 · Data Quality

    ✍️ How do you resolve the conflicting percentages?
    Model answer: Define one system of record; compare status/estimation mappings; fix sync errors; align calendars; standardise "done" and sizing; schedule automated checks; publish a data dictionary.
    Q. The first step to resolve conflicting numbers is…
    • A identify differing definitions and mappings
    • B trust the highest number
    • C delete a tool
    • D ignore it

    2️⃣ Task 2 · Dashboards

    ✍️ Which metrics will you show leadership and why?
    Model answer: PI predictability, feature progress, flow time/load, escaped defects, risk burndown; explain with trends and actions; avoid cross-team velocity comparisons.
    Q. Which is a vanity metric?
    • A Flow time
    • B Comparing story-point velocity across teams
    • C Escaped defects
    • D PI predictability

    3️⃣ Task 3 · Hybrid PI Planning Boards

    ✍️ Plan the Miro setup and the post-event sync.
    Model answer: Pre-built frames per team, locked structure, timers, SSO access control, ID-linked cards, dry run, time-zone split sessions; after the event, load final plan into the ALM, reconcile, archive.
    Q. To avoid drift between board and tool…
    • A rely on screenshots
    • B retype all later
